Lingvamyxa Structural Core Specification

Status

Revision 9 draft. Dot-indent syntax update.

This document specifies the structural core of Lingvamyxa as a self-contained language model.

Revision 9 note:

    Lingvamyxa source indentation is now represented by leading dot characters (`.`), not by spaces or tab characters. Spaces and tabs may be used by this document for prose layout, but they do not define source block depth.

The document is descriptive and semantic. Surface syntax builds Structures. Receivers and subroutines consume Structures and assign typed meaning to them.

Open points are marked with three distinct block types.

Marker convention:

    !!!
    This block marks an actual ambiguity, contradiction or unresolved rule in the syntax or source semantics.
    !!!

    ?
    This block marks a section that is intentionally not specified in this document. It is a future or external specification area, not necessarily a contradiction.
    ?

    variant 1:
    variant 2:
    variant 3:

    Variant blocks list possible designs for an unresolved or external area. They are not normative unless a later specification chooses one.

    ---ANSI C---
    This block gives possible implementation or lowering strategies for an ANSI C based translator/runtime. It is not part of Lingvamyxa source semantics.
    ---ANSI C---


0. Core Formula

Lingvamyxa is based on the following model:

    L0 binaries run.
    L1 is an external bootstrap, implementation and lowering layer.
    L2-L5 are Lingvamyxa levels.
    Source syntax builds Structures.
    Receivers and subroutines consume Structures.
    The parser has a native structural syntax and a mathematical expression syntax.
    Mathematical expressions also produce Structures.
    Levels restrict the active receiver/operator set.

The language does not assign final meaning directly from surface syntax. Surface syntax builds generic Structures. A receiver or subroutine consumes a Structure and assigns typed semantics to it.

Canonical semantic pipeline:

    source text
        -> structural and mathematical parse
        -> generic Structure values
        -> receiver/subroutine consumption
        -> typed semantic structures
        -> interpretation or lowering

A Structure does not execute merely because it exists. Execution, translation, registration, validation or query handling starts only when a receiver or subroutine consumes the Structure under a defined mode.


1. Levels

1.1. L0

L0 is a native binary artifact or machine-code artifact. It is the level actually executed by the CPU and operating system.

Examples of L0 artifacts:

    app.lm0.exe
    app.lm0
    core.lm0.dll
    core.lm0.so
    core.lm0.dylib
    core.lm0.a
    core.lm0.lib

1.2. L1

L1 is an external bootstrap, implementation and lowering layer. It may host initial parsers, translators, runtime components and receivers. L1 has its own syntax and semantics and is not part of the Lingvamyxa source-semantic core described by this document.

This document does not specify the L1 target language, physical calling convention, memory ownership rules or low-level runtime representation. Those belong to translator and runtime specifications.

1.3. L2

L2 is the low-level unsafe Lingvamyxa level. It is the low-level systems layer. It may expose memory, pointers, handles, structures, explicit low-level operations and low-level concurrency.

L2 is compiled. It is not executed as a casual script.

1.4. L3

L3 is the algorithmic and computational Lingvamyxa level. It supports safe top-level actions, computations and calls. L3 code may be interpreted by the core runtime or compiled through the lowering pipeline.

1.5. L4

L4 is the non-executive model level. It describes models, types, protocols, contracts, constraints, relation signatures and registry metadata.

L4 may update or check the compiler/runtime model. L4 does not perform ordinary runtime actions by default.

1.6. L5

L5 is the level of messages, configuration, behavior descriptors, fact registries, build/run/query/startup receivers and high-level dispatch.

L5 may attach message behavior to L4 structural models. L5 may also represent registry data as typed facts and rules. This draft places that fact/behavior layer in L5. A later level split may move part of it to L6. This document treats the L5 fact/behavior model as source-semantic infrastructure, not as ordinary runtime I/O.

1.7. Level Receivers

`L2`, `L3`, `L4` and `L5` are level receivers. A level receiver consumes its nested Structure and sets the active receiver/operator set for that body.

Example:

L4
.operator
..if
..callableFrom L5
..implementation l5_if
.end operator
end L4

Semantic normal form:

    L4(
      operator(
        if,
        callableFrom L5,
        implementation(l5_if)
      )
    )

The receiver `L4` consumes its body as model and registry input.


2. Value Ontology

The minimal core has two classes of values:

    1. primitive/scalar/reference/handle values
    2. Structure / Frame values

Primitive/scalar/reference/handle values include numbers, booleans, atoms, symbols, enum-like values, handles, references, pointers and L2-level callable references.

All non-primitive values are Structures or handles/references to Structures. This includes arrays, text, objects, call frames, bodies, configurations, expressions and model fragments.

A Structure can contain fields. A field can be positional, named or derived during normalization from a receiver signature.

At L3 and above, Structures are normally passed by reference/handle. They are not copied by value at every call unless a receiver explicitly defines copy semantics.

At L2, Structures may be lowered to pointers, handles, layout structures or primitive representations.

There is no fundamental keyword `Struct` in the minimal source syntax.


3. Structures and Frames

3.1. Structure

A Structure is a value containing an ordered set of fields. Fields may have names. Field order is part of the logical structure and may become part of layout or signature semantics.

A Structure may contain nested Structures. Tree-shaped data is represented as nested Structures.

3.2. Frame

A Frame is a Structure with a receiver/callee name and an argument Structure.

Example source:

    f(a, b, c)

Generic logical form:

    Frame(
      name: f,
      args: (
        field0: a,
        field1: b,
        field2: c
      )
    )

In ordinary prose this document may write `f(a, b, c)` as a Structure or Frame. The exact internal representation is implementation-defined as long as receiver semantics are preserved.

3.3. Structures Do Not Execute Themselves

A Structure is data. It may describe code, a call, a model, an expression, a relation, a query or a configuration. It does not execute merely by existing.

Execution starts only through explicit receiver/subroutine consumption, for example:

    compileCallFrame(frame)
    evalExpression(expr)
    call(subRef, args)
    registerOperator(frame)
    query(relationFrame)

A callable reference is also data until explicitly called or consumed by a receiver that calls it.


4. Surface Forms and Normalization

4.1. Compact Call Form

Compact call form:

    f(a, b, c)

It creates a Frame named `f` with one logical argument Structure containing three positional fields.

Normal form:

    f(
      field0: a,
      field1: b,
      field2: c
    )

4.2. Line Command Form

Line command form:

    f a b c

It creates the same logical Frame as:

    f(a, b, c)

A newline terminates the line command unless the parser is inside a parenthesized Structure or another explicitly open form.

Line command form does not infer hidden nesting.

Critical rule:

    print getTypedValue values[i]

normalizes as:

    print(getTypedValue, values[i])

It does not normalize as:

    print(getTypedValue(values[i]))

Explicit nesting must be written with parentheses or vertical structure.

4.3. Vertical Frame Form

Vertical frame form:

f
.a
.b
.c
end f

It creates a Frame named `f` with the same logical argument Structure as:

    f(a, b, c)

The explicit closing marker must be valid for the currently open vertical Structure. Closing validation is defined in section 7.5.

4.4. Parenthesized Bounded Structure

Parentheses create a bounded Structure:

    (a, b, c)

Inside parentheses, arguments are separated by comma or by the matching closing parenthesis.

Line command form inside parentheses continues until a comma or the matching closing parenthesis.

Example:

    if( i == 1, print choose hello, print choose world )

Logical argument sections:

    field0: <expression Structure for `i == 1`>
    field1: (print(choose, hello))
    field2: (print(choose, world))

Receiver-signature roles:

    field0 -> condition
    field1 -> then
    field2 -> else

The names `condition`, `then` and `else` are not created by the parser alone. They are assigned by receiver-signature normalization for the active `if` receiver. The internal layout of the expression Structure is outside this structural-core document.

4.5. Dot-Indentation Structures

A dot-indented block after a line opens a vertical Structure. A source indentation prefix is a run of one or more `.` characters at the logical start of a source line. Only the maximal leading dot run before the first non-dot source character is indentation; dots after a token remain ordinary syntax, such as field access.

Spaces and tabs are not indentation in Lingvamyxa source. In strict source mode, leading spaces or tabs before a source token are invalid outside comments and literals. A document renderer may add presentation padding around examples, but the language indentation depth is computed only from leading dots.

A newline at the same dot depth separates elements of the current Structure. A dot-dedent closes the current dot-indentation Structure by returning to a previous dot depth.

Explicit `end` forms remain preferred for readable named vertical frames because they allow the parser, translator and formatter to verify intended closure.

4.6. Bare `end` and `---`

The form:

    end

closes the current open vertical Structure.

The standalone line:

    ---

is a visual alias for bare `end`. It is not a receiver, not an operator, not a runtime action and not a separate section-separator construct.

A closing line uses the same dot indentation prefix as the block that it closes. For a named vertical Structure, the closing line has exactly the same number of leading dots as the header line of that Structure.

A standalone `---` at dot depth N closes the current open Structure whose header is at dot depth N. It does not close the previous sibling merely because it follows a deeper child line.

Example:

match value
.case 1
..print one
.---
.case 2
..print two
.---
.default
..print other
.---
---

This is equivalent to:

match value
.case 1
..print one
.end
.case 2
..print two
.end
.default
..print other
.end
end

The first three `---` lines close the current `case` or `default` Structures. The final `---` closes the enclosing `match` Structure.

The same form may be written with explicit validation tokens:

match value
.case 1
..print one
.end case
.case 2
..print two
.end case
.default
..print other
.end default
end match

A closing line whose dot depth does not match the current open block is a syntax error. Dot indentation is exact. Spaces and tabs do not adjust depth and must not be used to repair alignment.

4.6.1. Ultra-short Anonymous Positional Structures

Some receivers expect positional Structure arguments whose semantic role is assigned by the receiver signature. Such Structure arguments may be written in ultra-short anonymous form.

Example:

if a
..doSomething
.---
..doOtherThing
.---
---

Under an `if(condition, thenBody, elseBody)` receiver signature, this builds:

    if(
      a,
      (
        doSomething
      ),
      (
        doOtherThing
      )
    )

The names `thenBody` and `elseBody` are assigned by the `if` receiver signature. They are not surface keywords in this form.

A one-line form is also possible when the receiver defines it:

    if a doSomething

This is a Frame whose final meaning is assigned by the active `if` receiver.

Ultra-short anonymous Structures are intended for positional Structure arguments whose meaning is given by the enclosing receiver. If a nested Structure argument has its own semantic receiver/name, that receiver/name must be written explicitly.

Example:

f
.structName
..aa
..ab
.---
.a
.b
---

This builds:

    f(
      structName(aa, ab),
      a,
      b
    )

A receiver call has one logical argument Structure. A source form that appears to pass several arguments and a source form that appears to pass one Structure argument are not separate syntactic categories. The argument list itself is a Structure. Therefore a function that receives one Structure and a function that receives several positional fields may have the same source call shape. The receiver signature decides whether the fields of the argument Structure are consumed as one structural value, as several positional parameters, or through an explicitly defined equivalence rule.

This is an intentional property of the language, not an accidental ambiguity. In short forms without parentheses and commas, `f a b c` and the corresponding vertical form build one argument Structure containing `a`, `b` and `c`. A receiver with one structural parameter may consume that whole Structure. A receiver with several parameters may consume the same Structure by positional fields.

If a receiver has more than one argument and the first argument is itself a nested Structure in short form without parentheses and commas, that first nested Structure must be written as a named Structure. Otherwise the same surface form is reserved for the ordinary flat argument Structure of the enclosing receiver.

4.7. No Native `=` Assignment or Named-Field Operator

The structural syntax does not use `=` for assignment and does not use `=` as a native named-field operator.

A semantic field name may still exist after receiver normalization. It is produced by receiver signatures, positional conventions, explicit nested Structures, declaration forms or model/type constructors.

Explicit source-level naming is written as an ordinary Structure, not as `name = value`.

Example source:

model
.name PlantBed
.condition plantBedCondition
end model

Conceptual receiver-level interpretation:

    model(
      name(PlantBed),
      condition(plantBedCondition)
    )

The receiver `model` may interpret `name(PlantBed)` as semantic field `name` and `condition(plantBedCondition)` as semantic field `condition`.

The token `=` belongs only to the mathematical expression syntax if that syntax chooses to use it, for example as equality/comparison. It is not native structural assignment.

4.8. Positional Fields and Semantic Named Fields

A Structure may contain positional fields. A receiver may assign semantic names to those fields through its signature.

Example:

if a
..doSomething
.---
..doOtherThing
.---
---

With an `if(condition, thenBody, elseBody)` receiver signature, the second and third positional Structure arguments receive semantic names `thenBody` and `elseBody`.

Explicit semantic field-like input should be represented by nested Structures:

config
.batchSize 500
.reportMode Daily
end config

This builds ordinary nested Structures such as `batchSize(500)` and `reportMode(Daily)`. The active `config` receiver decides whether those Structures are interpreted as settings, fields, messages or ordinary child items.

4.9. Field Order

Field order is part of the logical Structure. When a receiver supports positional arguments, positional fields are mapped to receiver signature fields in order.

Semantic field names may be assigned by receiver normalization. A receiver may reject a Structure that contains unknown child Structures, missing required fields or incompatible field ordering.


5. Receiver-Based Semantics

5.1. Core Rule

Surface syntax builds Structures. Receivers and subroutines give those Structures meaning.

Semantic formula:

    surface syntax -> generic Structure -> receiver/subroutine -> typed semantic structure

A receiver has a signature. The signature defines how positional fields, semantic field names, anonymous positional Structures, expression fields and body fields are interpreted.

5.2. Receiver Consumption Modes

A receiver may consume a field as one of the following semantic modes:

    primitive value
    expression
    body Structure
    declaration
    model fragment
    configuration message
    data Structure
    delayed branch
    relation frame
    query frame

The mode is receiver-defined. The parser does not decide that a field is executable merely because it looks like code.

5.3. Example: `if`

For a computational L3 `if`, the receiver may define fields:

    condition
    then
    else

and consume them as:

    condition -> boolean-producing expression
    then      -> body Structure
    else      -> body Structure

During translation, the receiver lowers these fields into target control flow. During interpretation, the receiver evaluates the condition and then interprets only the selected body.

5.4. Example: `fn`

For an `fn` definition receiver, fields may be consumed as:

    name -> function name
    args -> argument Structure
    ret  -> return Structure
    body -> function body Structure

The receiver creates or registers an executable definition. The `fn` frame itself is not a function call.

5.5. Same Shape, Different Receivers

The same surface shape can have different semantics under different receivers.

Example:

    (a, b)

As a function argument Structure, it may mean two positional arguments.

As a return layout Structure, it may mean two return fields.

As a model fragment, it may mean a structural model.

As query input, it may mean a tuple of terms.

The receiver defines the interpretation.


6. Mathematical Expression Parser

6.1. Two Syntax Modes in One Parser

Lingvamyxa has one parsing system with two syntax modes:

    native structural syntax
    mathematical expression syntax

Native structural syntax builds ordinary receiver Frames and bounded Structures.

Mathematical expression syntax is entered when the parser detects mathematical expression indicators in an argument position. Indicators include explicit numeric literals and mathematical/operator tokens such as:

    =
    ==
    !=
    <
    >
    <=
    >=
    +
    -
    *
    /

The parser does not need to reinterpret forms such as `i == 1` or `i = 1` as ordinary Lingvamyxa receiver syntax first. It detects the mathematical operator token and parses the expression with the expression rules. The token `=` is not assignment in native structural syntax.

6.2. Expression Output

The mathematical syntax returns an expression Structure. This expression Structure is a tree-shaped Structure made of nested Structures.

Example source:

    i == 1

The parser detects this as mathematical syntax because of the `==` token. The exact internal expression-tree layout is not specified in this document. It belongs to the separate mathematical-syntax specification.

The native structural syntax described by this document is not the canonical representation of mathematical expressions. A form such as a receiver call with the name `==` is not defined here as the canonical expression output. It may be omitted entirely from the native receiver set if that makes lexical separation between native syntax and mathematical syntax simpler.

The important semantic rule is that mathematical syntax produces an expression Structure, not a separate fundamental AST type and not an ordinary runtime action.

The expression Structure is consumed later by a receiver that expects an expression, for example the `condition` field of `if`.

?
The mathematical expression syntax is specified separately. It must define operator tokens, precedence, grouping rules, expression Structure layout and translation rules. It may borrow an established mathematical/operator-precedence convention instead of inventing a full new expression language.
?

variant 1:
Use a compact C-like precedence table for arithmetic, comparison and boolean operators.

variant 2:
Use a minimal mathematical table that includes only numeric literals, grouping and explicitly listed mathematical operators.

variant 3:
Use a profile-based expression grammar selected by level, module or build configuration.

A translator may lower expression Structures to ANSI C expressions when precedence, evaluation order and side effects are fully known. Otherwise it may lower them to helper calls, temporary Structures or generated evaluator code.

6.3. Expressions Are Data Before Consumption

An expression Structure is data until a receiver consumes it as an expression.

For example, the `if` receiver consumes its `condition` field as an expression. A configuration receiver might instead store the same Structure as data.


7. `fn`, `sub` and Structural Closure

7.1. `fn` and `sub` Are Receivers

`fn` and `sub` are definition receivers. Each consumes a Structure and registers an executable definition. During bootstrap they may be present in an L1 prelude table or parser switch.

An `fn` frame consumes a Structure and registers or creates a function definition.

A `sub` frame consumes a Structure and registers or creates a subroutine definition.

7.2. Function Definition Form

Example source:

fn myFunc (int i, int j 1, p1, p2) (int r1, int r2)
.print i
.print j
.p1
.p2
end myFunc

Strict conceptual form:

    fn(
      name(myFunc),
      args(
        int(i),
        int(j, 1),
        p1,
        p2
      ),
      ret(
        int(r1),
        int(r2)
      ),
      body(
        print(i),
        print(j),
        p1,
        p2
      )
    )

Explicit nested-source form:

fn
.name myFunc
.args
..int i
..int j 1
..p1
..p2
.---
.ret
..int r1
..int r2
.---
.body
..print i
..print j
..p1
..p2
.---
end myFunc

The receiver `fn` consumes its child Structures by receiver-defined semantic roles. The explicit nested forms `name(...)`, `args(...)`, `ret(...)` and `body(...)` are ordinary Structures consumed by `fn`. They are not `=` named fields.

The names `int`, `boolean` and similar names are primitive/type-constructor receivers when registered in the active receiver set. In declaration context, a type/constructor receiver consumes the following raw identifier as a new binding name. If that name already exists in the current namespace, the declaration is invalid.

7.3. Subroutine Definition Form

Example source:

sub l5_if (boolean condition) then else
.return
end l5_if

Strict conceptual form:

    sub(
      name(l5_if),
      args(
        boolean(condition),
        then,
        else
      ),
      body(...)
    )

Explicit nested-source form:

sub
.name l5_if
.args
..boolean condition
..then
..else
.---
.body
..return
.---
end l5_if

The receiver `sub` consumes its child Structures by receiver-defined semantic roles. The argument `condition` is a primitive/evaluated argument through the registered constructor `boolean`. The bare names `then` and `else` are structural arguments. No `Struct then` annotation is required.

7.3.1. Single Namespace and No Silent Shadowing

Types, variables, functions, subroutines, receivers, model names, generic operation names and local executable definitions share one lexical namespace within a lexical scope chain.

A new binding may be introduced only if the same name is not already visible in the active lexical scope chain. This includes names introduced by declarations, nested `fn` definitions, nested `sub` definitions, imports and model/type constructors.

A local variable cannot reuse the name of a visible type. A local `fn` or `sub` cannot reuse the name of a visible variable, type, receiver, model or executable definition. Imports must not silently shadow visible names. Conflict resolution must be explicit through a future import/qualification rule.

L5 message selectors are looked up through a receiver object's behavior table. A selector is not automatically a lexical binding unless it is also imported or registered as an ordinary receiver/generic operation. The implementation name attached to a message is a lexical executable binding and follows the single-namespace rule.

In expression position, a visible `fn` name is callable. In head/update position inside its own body, the current `fn` name denotes the current return binding.

Example:

fn factorial
.int n
---
.int
---
.if n <= 1
...factorial 1
...return
..---
.---
.factorial n * factorial(n - 1)
end factorial

Inside the body, `factorial 1` updates the return binding of the current function. The expression `factorial(n - 1)` is a recursive function call because it appears in expression position.

7.3.2. Nested `fn` and `sub` Definitions

Nested `fn` and `sub` definitions are allowed inside executable bodies. A nested definition creates a local executable binding in the current lexical scope.

Example:

fn outer
.int x
---
.int
---
.fn addX
..int y
.---
..int
.---
..addX x + y
.end addX

.outer addX(10)
end outer

The nested `fn` `addX` is visible inside the body of `outer` after its definition and inside its own body for recursion. It is not visible outside `outer`.

A nested executable has its own local scope. It may read visible outer bindings according to lexical lookup. Mutation of outer bindings from a nested executable is not part of the minimal semantics unless a later execution-model specification defines explicit capture, reference or closure rules.

A nested `fn` or `sub` may not escape its defining scope unless a later closure/environment specification defines how its environment is represented. Returning a nested executable as a value, storing it in a longer-lived Structure or passing it to a context that may outlive the defining scope requires such closure semantics.

Because names are shared across types, variables, models and executables, nested definitions do not introduce shadowing. The following is invalid if `helper` is already visible as a variable, type, receiver, model or executable binding:

fn outer
.int helper
---
.int
---
.fn helper
..int x
.---
..int
.---
..helper x
.end helper
end outer

?
Closure representation, explicit capture, mutation of outer bindings and escaping nested executables are not specified in this document. They belong to a future execution-model and runtime specification.
?

7.4. Body Names

Variables or names used inside an `fn` or `sub` body do not become arguments automatically. Arguments are defined only by the argument Structure consumed by the definition receiver.

7.5. `end` as General Closing Syntax

`end` is a syntactic closing element. It is analogous to a closing parenthesis for vertical Structures. It has no runtime-return meaning by itself.

The parser recognizes these closing forms:

    end
    ---
    end <node-name>
    end <entity-name>

The forms:

    end
    ---

carry no explicit validation token. They close the current open vertical Structure. `---` is only a visual alias for bare `end`.

The closing line uses the same dot indentation prefix as the current block being closed. For a named Structure, this means the closing line has the same dot depth as the Structure header. For an ultra-short anonymous positional Structure, the closing line has the same dot depth as the implicit anonymous block level established by the enclosing receiver form.

The form:

    end <node-name>

closes the current vertical Structure and validates the closing token against the current node/receiver name.

The form:

    end <entity-name>

closes the current vertical Structure and validates the closing token against the normalized `name` field of the current Structure, if such a field exists. If no normalized `name` field exists, the closing policy may fall back to the first positional field when that field is a string-like name, atom or symbol.

Examples:

if condition
.bodyCall
end if

Here `if` validates against the node/receiver name.

fn myFunc (int i) (int r)
.myFunc i
.return
end fn

Here `fn` validates against the node/receiver name.

fn myFunc (int i) (int r)
.myFunc i
.return
end myFunc

Here `myFunc` validates against the normalized `name` field of the current `fn` Structure. In this form the normalized `name` field is derived from the first positional argument.

fn
.name myFunc
.args
..int i
.---
.ret
..int r
.---
.body
..myFunc i
..return
.---
end myFunc

Here `myFunc` also validates against the normalized semantic `name` field, but that field is written as an ordinary nested Structure.

fn
.args
..int i
.---
.name myFunc
.ret
..int r
.---
.body
..myFunc i
..return
.---
end myFunc

This is also valid because validation uses the normalized semantic `name` field rather than the raw first source argument.

All four forms are valid structural surface forms. A style guide may prefer explicit named closure for long or deeply nested Structures, but the structural core allows all of them.

A translator may implement vertical closure by internal closing handlers. Those handlers are implementation mechanisms. Source semantics only requires that the correct Structure is closed and that invalid closing tokens are rejected according to the active closing policy.


8. Runtime Return and Return-Binding Updates

8.1. `return` Receiver

Runtime exit from an `fn` or method-like executable body is represented by the `return` receiver/operator.

`return` is not the same as `end`. `end` closes source structure. `return` exits the current executable body.

8.2. Return Forms

The core return form has no explicit value arguments:

    return

`return` exits the current executable body. In an `fn`, it returns the current return binding. In a `sub`, it exits without producing a normal return value.

The `return` line has no argument tail and no parenthesized argument list. Any non-empty argument tail after the `return` token is a syntax error in this core specification.

Return values are established before `return`, either by updating declared named return variables or by using the current function name in head/update position inside its own body.

There is no native named-field variant of the `return` receiver because `=` is not a structural named-field operator. Named return fields are updated as ordinary bindings before `return`, or by receiver-defined nested Structures if a later return syntax explicitly adds them.

8.3. Named Return Variables and Function-Name Return Binding

Return values are ordinary declared return variables inside the executable body when the return signature gives them names.

Example:

fn estimateHarvest (PlantBed bed) (f32 harvest, f32 redApples, f32 greenApples)
.harvest bed.area
.redApples 0
.greenApples 0
.return
end estimateHarvest

The empty `return` returns the current values of the declared return variables.

Inside an `fn` body, the current function name may be used in head/update position as the current return binding. This update does not call the function.

Example:

fn factorial
.int n
---
.int
---
.if n <= 1
...factorial 1
...return
..---
.---
.factorial n * factorial(n - 1)
end factorial

The line `factorial 1` writes the current return binding. The expression `factorial(n - 1)` calls the function recursively.

8.4. Implicit Return at Function End

If execution reaches the end of an `fn` body and the function has a return binding, the current value of that return binding is returned implicitly.

A style guide may still require explicit `return` in some contexts, but the source semantics allow an implicit final return of the current return binding.

8.5. Return Source Semantics

At the source-semantic level, every `fn` has one logical return value. That value may be a primitive value or a return Structure. A return signature with several fields defines one return Structure, not a separate non-structural mechanism.

Updating several declared return fields and updating one Structure-compatible return binding are source-semantically equivalent when the produced Structure matches the declared return Structure. A caller may consume the returned value as one Structure or, through receiver-defined destructuring/update forms, bind or update separate variables from its fields.

Multiple named return fields are ordinary declared return variables inside the executable body. An empty `return` returns their current values as the declared return Structure.

The `return` receiver itself does not fill the declared return Structure. It only exits the executable body after the current return binding has already been updated. A single primitive return is the degenerate case where the declared return Structure has one primitive result according to the active return-value model.

Physical return strategy, storage ownership and low-level runtime representation are translator/runtime implementation details. They are not part of the source-semantic core.

The error mechanism is not specified by this document. A function may represent an erroneous result as one of the values allowed by its declared return type unless a later error-system specification defines a separate convention.

?
The general error/status system is not specified in this document. It may be defined later as ordinary return values, tagged result Structures, receiver-level diagnostics or another mechanism.
?

---ANSI C---
Possible return-lowering variants for an ANSI C implementation:

variant 1:
A single primitive source return lowers to a direct C primitive return.

variant 2:
A multi-field source return lowers to a caller-provided output Structure passed through a hidden or explicit implementation-level pointer.

variant 3:
A small return Structure lowers to a C struct returned by value if the translator/runtime profile allows it.

variant 4:
A structural return lowers to a handle/pointer allocated or managed by a runtime arena, heap, region or other implementation-owned storage.

These variants are implementation strategies only. The language-level rule remains that `return` returns the declared primitive value or return Structure.
---ANSI C---


9. Type and Model Forms

9.1. Type and Model Information

Type and model information is expressed by registered receivers and Structures.

The structural core does not require a separate `field` receiver. In declaration context, a type or model constructor consumes a raw identifier token and creates a binding/slot.

Example:

    u32 id
    Text crop
    f64 harvest 0.0

Conceptual meaning:

    declare binding/slot `id` with type `u32`
    declare binding/slot `crop` with type `Text`
    declare binding/slot `harvest` with type `f64` and default/initial value `0.0`

The token after the type constructor is not evaluated as an existing value. It is a raw name introduced by the declaration. If the name already exists in the current namespace, the declaration is invalid.

9.2. Type Constructors

A form such as:

    int i

or:

    PlantBed bed

is meaningful only if `int` or `PlantBed` is a registered primitive/type/model constructor receiver in the active level.

A receiver such as `fn`, `sub`, `autoModel` or `args` may consume these Structures as typed declarations.

9.3. Model Definitions

A model definition is a Structure consumed by a model receiver. One possible direction is to derive a model from a condition function:

L4
.model
..name PlantBed
..condition plantBedCondition
.end model
end L4

L3
.fn plantBedCondition
..u32 id
..Text crop
..f64 area
..f64 soilWater
..f64 harvest 0.0
.---
..boolean
.---
..return
...area > 0.0 &&
...soilWater >= 0.0 &&
...soilWater <= 100.0
..---
.end plantBedCondition
end L3

In this direction, the input binding section of `plantBedCondition` defines the model slots and defaults. The boolean body defines the validation predicate.

Another possible direction is an `autoModel` receiver that receives a model name and two Structure arguments: one declaration Structure and one condition Structure.

Example:

L4
.autoModel PlantBed
..vars
...u32 id
...Text crop
...f64 area
...f64 soilWater
...f64 harvest 0.0
..---
..condition
...area > 0.0
...soilWater >= 0.0
...soilWater <= 100.0
..---
.end PlantBed
end L4

This section does not define a final type/model language. It only states that model declarations are ordinary Structures consumed by model receivers.

?
The model/type declaration syntax is only partially specified. The preferred direction avoids a separate `field` receiver and uses declaration-context type constructors such as `u32 id` and `f64 harvest 0.0`. Still unspecified: canonical alias syntax, explicit layout syntax, relation signature syntax, and whether canonical model definitions use condition functions, `autoModel`, or both.
?

variant 1:
Define models through condition functions. Function input bindings define model slots and the boolean body defines validation.

variant 2:
Define models through an `autoModel` receiver with explicit child Structures such as `vars(...)` and `condition(...)`.

variant 3:
Allow both forms and define one as canonical normalization for the other.

9.4. Normalized Model Descriptor

A model receiver may normalize its input into a model descriptor. This document uses the term `ModelSpec` for that normalized descriptor. `ModelSpec` is not a magical built-in source keyword; it is the conventional semantic result produced by receivers such as `model`, `autoModel`, imported schema receivers or future mapping receivers.

A minimal `ModelSpec` contains:

    name
    vars
    defaults
    conditions or validator
    layout policy
    derivation requests
    source/provenance metadata

`name` is the model name registered in the shared namespace.

`vars` is the ordered Structure of slots/bindings. Field order is part of the logical model and may be used for positional construction, return Structures, destructuring, layouts, relation signatures and serialization.

`defaults` are default initial values for slots. They may be represented directly in `vars`, for example `f64 harvest 0.0`, or materialized as a separate descriptor view.

`conditions` or `validator` define which values are valid instances of the model. Conditions may be listed as expression Structures or delegated to a boolean function.

`layout policy` describes how stable or externally constrained the slot order/representation is. The physical representation is still a lowering decision unless an explicit layout receiver fixes it.

`derivation requests` describe which artifacts may be derived from the model, such as constructors, validators, accessors, relation signatures, serializers or documentation schemas.

`source/provenance metadata` records the source receiver, file, line, import or external origin of the descriptor for diagnostics and incremental rebuilds.

9.5. Union Descriptors and Variant Membership

A `union` receiver defines a closed set of allowed model variants.

Example:

L4
.union Shape
..Circle
..Square
..Triangle
.---
---

Conceptual normalized descriptor:

UnionSpec
.name Shape
.variants
..Circle
..Square
..Triangle
.---
---

At source-semantic level, a value of `Shape` is a value whose concrete variant is one of the listed model names. A concrete variant value may be injected into the union when the expected type is the union.

Example:

    Circle 10.0

creates a `Circle` value through the `Circle` constructor. If the expected type is `Shape`, the translator/receiver may inject that value into `Shape` by attaching the variant name `Circle` and the concrete `Circle` value.

Conceptual source meaning:

Shape
.tag Circle
.payload
..Circle
...radius 10.0
..---
.---
---

`tag` is the variant name. `payload` is the concrete value produced by the variant constructor. The union does not create the payload by itself.

The physical representation of a union value is not defined by this structural core. A translator may use tagged inline storage, tagged handles, model-id plus value-handle pairs, pointer-based payloads or another representation.

9.6. Registry Facts Generated by Structural Descriptors

Model, union, operator and behavior descriptors may be represented internally as typed facts. For example, a model descriptor for `Circle` may materialize facts such as:

    model Circle
    slot Circle radius f64

A union descriptor may materialize facts such as:

    union Shape
    variant Shape Circle
    variant Shape Square
    variant Shape Triangle

These facts are registry facts. They are not ordinary runtime assertions unless a receiver exposes them to a runtime query system. The fact representation gives one uniform way to index, query, validate and derive registry information.

9.7. Model Extension and Conflict Policy

A model name has one structural `ModelSpec` unless an explicit extension/refinement receiver defines controlled composition. A second independent structural model definition for the same name is a conflict.

Adding constraints, behavior, generic methods, union membership or documentation to an existing model must be explicit through registered receivers such as `refineModel`, `behavior`, `method`, `variant`, `extendUnion` or future extension forms.


10. L5 Behavior, Objects, Messages and Facts

10.1. L4 Model vs L5 Behavior

The word `model` may appear at different levels, but the source semantics must distinguish two roles:

    L4 structural model -> slots, types, defaults, constraints, layout and derivations
    L5 behavior model   -> messages, selectors, method implementations and object dispatch

The canonical term for the L5 role in this document is `behavior`. If a future L5 profile allows the receiver name `model`, it must consume Structures as an L5 behavior/message descriptor, not as the L4 structural `ModelSpec` receiver.

10.2. Behavior Descriptor

A behavior descriptor attaches message responses to an existing model name.

Example:

L5
.behavior Circle
..message drawOn drawCircleOn
..message area circleArea
.---
---

Conceptual descriptor:

BehaviorSpec
.model Circle
.messages
..drawOn drawCircleOn
..area circleArea
.---
---

The implementation names `drawCircleOn` and `circleArea` are ordinary executable bindings and must be visible in the shared namespace. Duplicate message selectors for the same model are conflicts unless an explicit override/refinement receiver defines another policy.

A behavior descriptor does not redefine the structural fields of `Circle`. It attaches message behavior to the structural model already registered under `Circle`.

10.3. Runtime Object Value

An L5 object value is a Structure or handle/reference to a Structure together with enough model information to resolve behavior. Conceptually:

object
.model Circle
.slots
..radius 10.0
.---
---

The `slots` layout and validation come from the L4 `ModelSpec`. The message table comes from the L5 `BehaviorSpec` or from registry facts materialized from it.

10.4. Message Send

A message send has a receiver object, a selector and an argument Structure.

Example source form:

    shape drawOn canvas

Conceptual send fields:

    receiver shape
    selector drawOn
    args (canvas)

Resolution:

    model shape.model
    method lookupMessage(model, drawOn)
    call method(shape, canvas)

The receiver object is passed as the first semantic argument to the selected implementation.

If `shape.model` is `Circle`, and the behavior registry contains:

    message Circle drawOn drawCircleOn

then the send lowers or interprets as:

    drawCircleOn(shape, canvas)

10.5. Message Lookup Strategies

The source semantics require lookup by `(model, selector)`. The implementation may use dictionaries, selector indexes, method tables, inline caches or static lowering when the receiver model is known.

If no message exists for `(model, selector)`, the behavior is not fixed by this document. A strict profile may report an error. A dynamic L5 profile may route the send to a `doesNotUnderstand` receiver.

!!!
L5 message-missing behavior is not fixed. A final L5 behavior specification must decide whether missing messages are compile-time errors, runtime errors, `doesNotUnderstand` sends, receiver-defined diagnostics or query failures.
!!!

10.6. L5 Facts and Rules

L5 may store registry information as typed facts and rules. Examples:

    fact model Circle
    fact slot Circle radius f64
    fact behavior Circle
    fact message Circle drawOn drawCircleOn
    fact variant Shape Circle
    fact method draw Circle drawCircle

The same information may also be materialized as descriptors such as `ModelSpec`, `UnionSpec`, `BehaviorSpec`, `OperatorSpec` or `GenericMethodSpec`. Descriptors and facts are two views of one registry model.

L5 rules may derive registry facts from other facts. For example, a rule may derive that a generic operation is complete for a union when every union variant has a registered method implementation.

10.7. L5 Configuration and Build Example

Example:

L5
.target
..app
..kind executable
..sources ("src/hello.lm3")
..entry hello
..output "build/bin/hello.lm0.exe"
.---

.build app
---

The `target` and `build` receivers define build semantics. They may also emit registry facts used by the builder. The structural core only creates Structures and specifies that L5 receivers consume them as messages, configuration, behavior descriptors, facts, rules or build/query requests.

11. Operators and Receiver Registration

11.1. Operator as Receiver Registration

`operator` is a receiver used during bootstrap or model loading. It registers receiver names, visibility levels and implementations.

Example:

L4
.operator
..while
..callableFrom L3
..implementation
...while_func
...level L2
..end implementation
.end operator
end L4

Semantic meaning:

    Register a receiver/operator named `while`.
    Make it callable from L3.
    Use implementation `while_func`.
    Treat that implementation as L2-level implementation.

The `operator` frame is not the runtime/control operation being registered.

11.2. Runtime Use of Registered Operators

After registration, runtime/control source may contain:

L3
.while i < beds.len
..print beds[i].crop
..i i + 1
.end while
end L3

Here `while` is the opened frame and therefore may close as `end while`.

The active L3 `while` receiver consumes its argument Structure according to its registered signature, typically as:

    condition -> expression
    body      -> body Structure

11.3. Multiple Level-Specific Implementations

The same surface receiver name may have different implementations at different levels.

Example registrations may define:

    if callable from L3 -> l3_if
    if callable from L4 -> l4_model_if
    if callable from L5 -> l5_if

The active level determines which receiver implementation consumes the Structure.

11.4. Generic Operations and Method Registration

A generic operation is a registered receiver whose implementation is selected by a dispatch rule rather than by one fixed executable definition.

Example:

L4
.operator draw
..callableFrom L3
..dispatchBy firstArgumentModel
..domain Shape
.---

.method draw Circle drawCircle
.method draw Square drawSquare
.method draw Triangle drawTriangle
---

The `operator draw` frame registers `draw` as a callable generic receiver. The child Structure `dispatchBy firstArgumentModel` says that the concrete implementation is selected by the model of the first argument. The child Structure `domain Shape` restricts or documents the generic domain.

Each `method` frame registers one dispatch entry:

    method <generic-name> <model-name> <implementation-name>

Example semantic facts:

    generic draw
    dispatchBy draw firstArgumentModel
    domain draw Shape
    method draw Circle drawCircle
    method draw Square drawSquare
    method draw Triangle drawTriangle

The implementation names are ordinary `fn` or `sub` bindings and must satisfy the signature contract of the generic operation. For example, if `draw` returns no value, each drawing implementation is normally a `sub`. If `draw` returns a `DrawCommand`, each implementation must return a compatible value.

11.5. Dispatch from Union Domain

If a generic operation has a union domain, the union variants and method facts together define complete dispatch.

Example union facts:

    variant Shape Circle
    variant Shape Square
    variant Shape Triangle

Example method facts:

    method draw Circle drawCircle
    method draw Square drawSquare
    method draw Triangle drawTriangle

At a call site:

    Shape shape
    draw shape

translation may derive:

match shape
.case Circle c
..drawCircle c
.---
.case Square s
..drawSquare s
.---
.case Triangle t
..drawTriangle t
.---
---

The `match` form checks the union tag/variant name, extracts the payload as the concrete model and calls the registered implementation. If the first argument is statically known to be `Circle`, the call `draw c` may lower directly to `drawCircle c`.

Completeness for a union domain is a registry check: for every `variant(Shape, V)`, there must be a compatible `method(draw, V, Impl)` unless a default or fallback method is explicitly registered.

11.6. Generic Operation vs L5 Message

A generic operation such as `draw shape` dispatches through a generic operation registry:

    (generic name, first argument model) -> implementation

An L5 message send such as:

    shape drawOn canvas

dispatches through the receiver object's behavior table:

    (receiver.model, selector) -> implementation

Both mechanisms may be represented as registry facts. They are different source-semantic forms. A generic operation is centered on the operation name. A message send is centered on the receiver object.


12. Conditional Structures

12.1. L3 `if`

L3 `if` is a computational control-flow receiver. It consumes:

    condition -> boolean-producing expression
    then      -> executable body Structure
    else      -> executable body Structure

At interpretation time, only the selected body is interpreted.

At translation time, the receiver lowers the condition and body Structures into target control flow.

12.2. L4 `if`

L4 `if` is a model-conditional receiver. It does not execute runtime effects. It may conditionally include, exclude or normalize model Structures, registry entries and constraints.

12.3. L5 `if`

L5 `if` is a message/configuration dispatch receiver. It may conditionally dispatch build, run, query, startup or configuration messages.

12.4. Conditional Forms

Ultra-short conditional form:

if mode == debug
..build debugTarget
.---
..build releaseTarget
.---
---

Normal form under signature `if(condition, thenBody, elseBody)`:

    if(
      <expression Structure for `mode == debug`>,
      (build(debugTarget)),
      (build(releaseTarget))
    )

The same conditional may be written with explicit named branch Structures:

if mode == debug
.then
..build debugTarget
.---
.else
..build releaseTarget
.---
---

This builds:

    if(
      <expression Structure for `mode == debug`>,
      then(build(debugTarget)),
      else(build(releaseTarget))
    )

The ultra-short form is valid when the active `if` receiver assigns semantic roles to the anonymous positional Structure arguments.


13. Pointers, References and Callable References

13.1. L3 Passing Model

At L3 and above, explicit pointer syntax is usually unnecessary. Structures, arrays, text, objects and other non-primitive values are passed as references or handles by default.

At L3 and above, ordinary names denote primitives, symbols, handles or Structures according to the active semantic environment. They are not raw function pointers.

13.2. L2 Pointer Constructor

At L2, `^` may be a low-level pointer/reference constructor.

Examples:

    ^p
    ^ PlantBed bed

Possible meanings:

    ^p              untyped reference / void* / pointer to structure
    ^ PlantBed bed  typed pointer/reference if the type model is known

The name `^` may be handled as a parser-level constructor or as a primitive L2 receiver during bootstrap.

13.3. Fn and Sub References

Function/subroutine reference operators are strictly L2 operators.

At L2, reference forms such as `&` and `*` may be used for address-taking and callable-reference construction if they are defined by the L2 operator set.

At L3 and above, names are references to Structures, handles or primitive values. Calls are expressed as receiver Frames and resolved by the active receiver/operator registry, not by raw callable pointers.

?
The exact L2 forms for `^`, `&` and `*` are specified by the L2 memory and callable-reference specification. The structural core only states that raw pointer/address/callable-reference syntax belongs to L2, not to the general high-level source model.
?

variant 1:
Treat `^`, `&` and `*` as built-in L2 parser forms.

variant 2:
Treat them as bootstrap-registered L2 operators with parser support only for tokenization and precedence.

variant 3:
Allow both forms: parser-level recognition for core operators and receiver-level extension for specialized memory models.


14. Arrays, Text and Indexing

14.1. Logical Model

At L3 and above, an array is a Structure or handle/reference to a Structure. Text is also a Structure or handle/reference to a Structure.

The logical array model includes at least a length field and an indirect storage reference. It may also include capacity, encoding, element type and storage handle.

14.2. L2 Lowering

At L2, arrays and text may lower to pointers, length-plus-pointer records or other layout-specific representations.

Example conceptual lowering for an array:

    (len, ptr)

Lowering does not change source semantics.

14.3. Indexing

The mathematical expression parser is specified separately. Indexing is treated as a level-dependent operator/form.

At L2, `[]` is a low-level operator, similar in status to `=`. It uses a computed address and is governed by the L2 memory model.

Example conceptual L2 meaning:

    beds[i] -> element at computed address

subject to the actual L2 layout and pointer rules.

At L3 and above, `[]` accesses an array Structure indirectly and performs bounds checking through the array metadata, at minimum the `len` field.

Example conceptual L3 meaning:

    beds[i] -> index(beds, i)

where `index` receives the array Structure or handle, checks `0 <= i < beds.len`, and returns the element or reports a bounds error.

?
The final array/text specification must define exact index result semantics, slicing, negative indexes if any, multidimensional arrays, text encoding and the boundary between parser form and receiver/operator form.
?

---ANSI C---
Possible array-lowering variants:

variant 1:
L2 array access lowers to computed-address access with no automatic bounds check.

variant 2:
L3+ array access lowers to a length-plus-pointer or length-plus-handle Structure with generated bounds checks.

variant 3:
Dynamic arrays lower to runtime handles with accessor calls when layout is not statically known.
---ANSI C---


15. Field Access

15.1. Dot Form

Named field access uses dotted syntax:

    result.harvest

The dot form is a built-in parser form. It exists so the translator can generate direct field access through known Structures and layouts.

Possible normal form:

    field(result, harvest)

or an internal field-access expression Structure equivalent to it.

15.2. Lowering

If the model/layout of `result` is known, the translator may lower:

    result.harvest

into direct structure access, pointer access or generated accessor code.

If the model/layout is dynamic, the receiver/runtime may perform a checked lookup.

!!!
Field-access failure semantics are not fixed. A final source-semantic rule must define behavior for missing fields, unknown models, dynamic Structures and nullable handles, including whether such cases are compile-time errors, runtime errors or receiver-defined diagnostics.
!!!

---ANSI C---
Possible field-access lowering variants:

variant 1:
Known static layouts lower to direct C struct-field access.

variant 2:
Known pointer layouts lower to direct pointer-field access.

variant 3:
Dynamic Structures lower to checked runtime lookup or generated accessor calls.
---ANSI C---


16. Update, Return Structures and Destructuring

16.1. Binding Update Instead of `=` Assignment

The native structural core does not use `=` for assignment.

A declaration with initialization is written through a declaration-context constructor:

    int a 3

A later update to an existing mutable binding is written by placing the binding in head/update position:

    a 4

Example:

    int a 3
    print a
    a 4
    print a

The first `print` observes `3`. The second `print` observes `4`.

The update form is valid only if the head name resolves to an existing mutable binding or to a receiver that explicitly accepts such a call. Because Lingvamyxa uses one lexical namespace, a binding name and a receiver/type/function name cannot silently mean different things in the same scope.

At L2, update may lower to direct storage write according to the L2 memory model. At L3 and above, update is receiver-defined over variables, fields, handles and Structures.

?
Binding, mutability, scope, initialization, reassignment and shadowing rules are not specified in full in this document. They require a dedicated execution-model specification.
?

16.2. Return Structures

A function return value is one logical source-level value. That value may be primitive or structural. If the return value is structural, updating its declared fields and updating a Structure-compatible return binding are source-semantically equivalent under the receiver-defined return signature.

A function may return a Structure with ordered and/or semantic named fields.

Example return signature:

    (f32 harvest, f32 redApples, f32 greenApples)

Named return variables may be updated before a bare return:

    harvest bed.area
    redApples 0
    greenApples 0
    return

The current function name may also update the whole current return binding in head/update position.

16.3. Destructuring

Destructuring syntax using `=` is not part of the current native structural core.

The semantic operation still exists: a produced Structure may be assigned or bound as one value, stored in a temporary service binding, or used to update target bindings from its fields by name or by position.

Possible explicit receiver form:

unpack toEat(myFilter, Monday)
.harvest
.redApples
.greenApples
end unpack

Conceptual meaning:

    tmp receives toEat(myFilter, Monday)
    harvest receives tmp.harvest
    redApples receives tmp.redApples
    greenApples receives tmp.greenApples

If the produced Structure has no field names, a receiver-defined positional unpack form may map fields by order.

?
The canonical destructuring/update syntax is not specified. A final execution-model specification must define whether destructuring is written through an `unpack` receiver, through target-list syntax without `=`, or through another explicit structural form.
?

---ANSI C---
A translator may implement destructuring by assigning the produced Structure or handle to a temporary service variable and then generating field updates one by one.

variant 1:
For known static layouts, generated code reads fields directly from the temporary Structure.

variant 2:
For handle-based Structures, generated code reads fields through generated accessors or runtime lookup.
---ANSI C---


17. L4 Non-Executive Semantics

L4 consumes Structures as model/type/contract/registry input. It may:

    register models
    register relation signatures
    check contracts
    normalize schemas
    derive layouts
    derive validators
    update the internal compiler/runtime model
    prepare compilation or self-compilation metadata

L4 does not directly perform ordinary runtime effects by default.

Runtime effect receivers such as file I/O, network send, process launch, database write, ordinary runtime print and thread start are not visible from L4 unless a special compile-time diagnostic or model receiver explicitly exposes a non-runtime effect.

A diagnostic receiver visible from L4 is not the same as L3 runtime `print`.


18. L5 Message, Fact and Build Semantics

18.1. L5 Input

An L5 file contains messages, configuration Structures, behavior descriptors, registry facts, rules and build/query/startup receivers. It is not a special `project` file unless a project receiver is explicitly registered.

The builder may be given a `.lm5`, `.lm3`, `.lmx` or other Lingvamyxa source file. It handles the top-level Structures through active receivers.

18.2. Registry-as-Facts Model

L5 may treat registry information as a typed fact store. Structural declarations from L4 can materialize facts. L5 behavior/configuration receivers can add facts. L5 query/build receivers can ask questions over those facts.

Examples:

    fact model Circle
    fact slot Circle radius f64
    fact variant Shape Circle
    fact behavior Circle
    fact message Circle drawOn drawCircleOn
    fact generic draw
    fact method draw Circle drawCircle

The registry may also expose materialized descriptors such as `ModelSpec`, `UnionSpec`, `BehaviorSpec`, `OperatorSpec`, `GenericMethodSpec` and `RelationSpec`. These descriptors are derived views over facts or the facts are derived views over descriptors. The source semantics only require consistency between these views.

18.3. Target Example

Possible L5 build input:

L5
.target
..app
..kind executable
..sources ("src/hello.lm3")
..entry hello
..output "build/bin/hello.lm0.exe"
.---

.build app
---

The `target` and `build` receivers define the build semantics. The core only creates Structures.

18.4. Entry Resolution

The builder either finds an entry/target through receivers, messages, facts and signatures, or reports:

    no entry point

An executable entry wrapper is created from build/target/entry information or from an implicit L3 top-level entry. It is not derived from a source file name.

The symbol `main` may be a conventional entry symbol, but it is not a required startup-file convention.

19. Compilation and Lowering

19.1. Compilation Pipeline

Compilation means:

    Lingvamyxa source
        -> Structures
        -> semantic receiver handling
        -> L1 projection or another implementation target
        -> L0 artifact

This document specifies only the source-semantic side of that pipeline. The exact L1 syntax, L1 file format, L1 compiler interface and L0 build mechanism are outside this document.

---ANSI C---
An ANSI C based translator may use the following implementation pipeline:

    Lingvamyxa source
        -> Structures
        -> semantic receiver handling
        -> generated ANSI C projection
        -> platform C compiler/linker
        -> L0 artifact

Generated/debuggable C projections may preserve source mapping with `#line` directives, comments or a separate source-map file. This is a translator feature, not source syntax.
---ANSI C---

19.2. Source File Extensions

Lingvamyxa source files may use:

    *.lm2    L2-only source
    *.lm3    L3-only source
    *.lm4    L4-only source
    *.lm5    L5-only source
    *.lmx    mixed Lingvamyxa source

Generated/debuggable projections may exist for translator diagnostics and verification. Their exact format and file extensions are implementation-defined.

A debug build may preserve source mapping through an implementation-defined source-map mechanism.

19.3. Per-Level Build Semantics

L2 sources are unsafe modules/libraries/objects. They are compiled, not interpreted as scripts.

L3 sources may be interpreted or compiled. A top-level L3 sequence may become an implicit executable entry.

L4 sources are checked, loaded and registered as model/contract/registry input. They are not launched as programs.

L5 sources are message/configuration/build/startup/query inputs consumed by L5 receivers.

Mixed `.lmx` sources are handled according to level receivers and entry rules. L5 entry messages take precedence if present; otherwise an L3 top-level sequence may become an implicit entry if the builder allows it.


20. Source Semantics and Implementation Lowering

20.1. Logical Argument Structure

Every source call has one logical argument Structure.

Example:

    mySub(1, 2, 3, 4)

Logical source semantics:

    mySub(
      field0: 1,
      field1: 2,
      field2: 3,
      field3: 4
    )

20.2. Physical Optimization

The logical Structure always exists at the source-semantic level. A translator may optimize away the physical Structure if the observable source semantics are preserved.

This means that the source call:

    f(a, b, c)

is always semantically treated as a call with one argument Structure containing `a`, `b` and `c`.

A concrete translator may pass fields directly, use a handle, use a temporary Structure, inline the call, specialize adapters or apply any other physical strategy. These choices do not change the Lingvamyxa source semantics.

20.3. Return Lowering Independence

The same rule applies to returns. A return signature defines a source-level return value: either a primitive value or a return Structure. The translator may choose any physical return strategy that preserves this source-level result.

The Lingvamyxa source-semantic core does not define physical calling conventions or storage strategies.

---ANSI C---
Possible internal call-lowering variants for an ANSI C implementation:

variant 1:
Pass up to three primitive/reference source fields directly to an internal generated C function. References and handles may be treated as primitive scalar values for this implementation convention.

variant 2:
If more logical fields exist, generate an args Structure and pass a pointer/handle to it.

variant 3:
Generate specialized adapters for concrete call sites, including direct calls, temporary args Structures, inlining or whole-program specialization.

Possible exported ABI variant:

    LmStatus f(LmRuntime *rt, const F_Args *in, F_Ret *out)

This shape is only an implementation option. The language does not know about `LmRuntime`, C function signatures, hidden arguments or slot counting.
---ANSI C---


21. Facts, Rules, Relations and Query

21.1. Relation Signatures

Relational mode is a receiver-based semantic mode over Structures. It does not introduce a separate Prolog-like surface syntax.

A relation signature describes the shape and types of a relation. Relation signatures belong primarily to L4.

Example:

L4
.relation variant
..Symbol unionName
..Symbol modelName
.---

.relation method
..Symbol genericName
..Symbol modelName
..Symbol implementationName
.---
---

The relation receiver registers relation signatures. It does not assert facts by itself.

21.2. Facts

A fact assertion is an ordinary Structure consumed by a `fact` receiver or another fact-producing receiver.

Examples:

    fact variant Shape Circle
    fact method draw Circle drawCircle
    fact message Circle drawOn drawCircleOn

A relation frame such as:

    parent(Astra, NyufNyuf)

is a fact only when consumed by a fact receiver. It is a query only when consumed by a query receiver.

21.3. Registry as Typed Fact Store

The compiler/runtime registry may be modeled as a typed fact store. The following are examples of registry facts:

    model Circle
    slot Circle radius f64
    union Shape
    variant Shape Circle
    behavior Circle
    message Circle drawOn drawCircleOn
    generic draw
    dispatchBy draw firstArgumentModel
    domain draw Shape
    method draw Circle drawCircle

Descriptors such as `ModelSpec`, `UnionSpec`, `BehaviorSpec`, `OperatorSpec` and `GenericMethodSpec` may be materialized views over these facts. Conversely, source receivers may first produce descriptors and then materialize facts from them.

21.4. Rules

A rule defines a relation in terms of other relations.

Example conceptual form:

rule
.completeGeneric draw Shape
if
.variant Shape ?model
.method draw ?model ?implementation
---

The exact syntax for rule heads, rule bodies, conjunction, disjunction, negation and aggregation is not specified by this document.

Rules are useful for deriving registry-level information, for example:

    a generic operation is complete for a union
    a model has a slot inherited from a refinement
    an object responds to a message
    a build target has all required sources

21.5. Query

A query asks for bindings that satisfy relation Structures.

Example:

query
.method draw ?model ?implementation
---

Meaning:

    find model and implementation pairs for generic operation draw

A query may contain unknowns such as:

    ?model
    ?implementation
    ?who

Unknowns are logical variables interpreted by relational receivers. They are not ordinary uninitialized variables.

21.6. Generic Dispatch as Query

Generic dispatch can be derived by querying registry facts.

For a call:

    draw shape

where `shape` has type `Shape`, the translator may query:

    variant Shape ?model
    method draw ?model ?implementation

For each result, the translator can generate a `match` case over the union variant.

For a concrete call:

    Circle c
    draw c

the translator may query:

    method draw Circle ?implementation

and lower directly to the returned implementation.

21.7. Message Lookup as Query

L5 message lookup can also be represented as a query over facts.

For a send:

    shape drawOn canvas

where `shape.model` is `Circle`, the runtime or translator queries:

    message Circle drawOn ?implementation

and calls the returned implementation with the receiver object and message arguments.

21.8. Fact Persistence

Facts may accumulate faster than source modules. Persistent fact storage may be separate from source files.

Recommended division:

    signatures/contracts/rules       -> L4/L5 source modules
    generated registry facts         -> compiler/runtime registry
    accumulating domain facts        -> persistent store or database backend
    query/relation engine            -> receiver layer over Structures and storage backend

SQLite or another database may be used as a backend, but it is not part of the core syntax.

21.9. Unification

Relational search is based on unification. Unification attempts to make two relation Structures compatible by assigning unknowns.

It respects:

    relation name
    argument count
    positional order
    semantic named fields when used
    L4 relation signatures
    contracts and constraints when attached

21.10. Query Result

A query returns a Structure, for example:

QueryResult
.bindings
..binding ?model Circle
..binding ?implementation drawCircle
.---
.status success
---

?
The exact syntax and core status of `?name` logical variables, list literals, rule bodies, negation, aggregation and query result Structures belong to the relation/query specification. That specification must define these forms or map them to registered receivers.
?

22. Structural Grammar Sketch

This grammar sketch describes the structural parser only. It does not define final receiver semantics.

    program             ::= { item }

    item                ::= empty_line
                          | comment_line
                          | line_frame
                          | vertical_frame
                          | expr_line

    compact_frame       ::= name "(" [ argument_list ] ")"

    line_frame          ::= name [ line_arguments ] newline

    vertical_frame      ::= dot_prefix name [ line_arguments ] newline
                              dot_child_prefix { vertical_item }
                            dot_prefix close_form newline

    dot_prefix          ::= { "." }

    dot_child_prefix    ::= dot_prefix "." { "." }

    vertical_item       ::= item
                          | close_form

    close_form          ::= end_form
                          | dash_end_form

    end_form            ::= "end" [ name ] newline

    dash_end_form       ::= "---" newline

    argument_list       ::= argument { "," argument } [ "," ]

    argument            ::= expression_or_structure

    bounded_structure   ::= "(" [ argument_list ] ")"

    expression_or_structure
                         ::= mathematical_expression
                          | compact_frame
                          | bounded_structure
                          | atom_or_value

    mathematical_expression
                         ::= parsed by the mathematical expression syntax

This grammar is intentionally incomplete around full update semantics, full indexing, full field access, type constructors, literals and relation forms because those areas require final design decisions. Native structural grammar does not include `=` assignment or `=` named-field syntax.


23. Canonical Examples

23.1. Hello World

Source:

L3
.print Hello World
end L3

Normal form:

    L3(
      print(Hello, World)
    )

`Hello` and `World` are accepted only if the active L3 `print` receiver and lexical rules allow bare atoms/symbols in that position.

23.2. Function with Structural Return

Source:

fn estimateHarvest (PlantBed bed) (f32 harvest, f32 redApples, f32 greenApples)
.if bed.crop == Apples
..harvest bed.area * 1.7
..redApples bed.area * 1.7
..greenApples bed.area * 1.1
..return
.end if

.estimateHarvest bed.area 0 0
end estimateHarvest

Semantic outline:

    `fn` consumes a definition Structure.
    `PlantBed bed` is a typed/model constructor Structure if `PlantBed` is registered.
    The return Structure has three named fields.
    `if` consumes condition and body Structures.
    The named return variables update fields of the current return Structure.
    `return` exits the current function and returns the current return binding.
    `estimateHarvest bed.area 0 0` updates the current function return binding.
    Reaching the end of the function returns the current return binding implicitly.
    `end estimateHarvest` closes the definition Structure by normalized entity name.

23.3. Empty Return with Named Return Variables

Source:

fn estimateHarvest (PlantBed bed) (f32 harvest, f32 redApples, f32 greenApples)
.harvest bed.area
.redApples 0
.greenApples 0
.return
end estimateHarvest

Semantic outline:

    Named return fields are local return variables.
    Head/update position updates existing bindings.
    Empty `return` exits and returns their current values.

23.3.1. Recursive Function with Function-Name Return Binding

Source:

fn factorial
.int n
---
.int
---
.if n <= 1
...factorial 1
...return
..---
.---
.factorial n * factorial(n - 1)
end factorial

Semantic outline:

    In head/update position, `factorial` denotes the current return binding.
    In expression position, `factorial(n - 1)` is a recursive call.
    The final line updates the return binding, and the end of the function returns it implicitly.

23.4. L5 Conditional Build

Source:

L5
.if mode == debug
..build debugTarget
.---
..build releaseTarget
.end if
end L5

Conceptual form:

    L5(
      if(
        <expression Structure for `mode == debug`>,
        (build(debugTarget)),
        (build(releaseTarget))
      )
    )

The semantic roles `condition`, `then` and `else` are assigned by the active `if` receiver signature.

23.5. Operator Registration

Source:

L4
.operator
..if
..callableFrom L5
..implementation l5_if
.end operator
end L4

Semantic outline:

    `L4` consumes the body as model/registry input.
    `operator` registers the receiver name `if`.
    `callableFrom L5` sets visibility.
    `implementation l5_if` names the implementation receiver/subroutine.

23.6. L5-if Implementation Subroutine

Source:

sub l5_if (boolean condition) then else
.return
end sub

Conceptual form:

    sub(
      name(l5_if),
      args(
        boolean(condition),
        then,
        else
      ),
      body(...)
    )


24. Summary Table

    f(a, b)                    compact Frame named f
    f a b                      line command Frame named f
    f ... end f                vertical Frame named f
    (a, b)                     bounded Structure
    name value                 ordinary nested Structure, often consumed as a setting/semantic field by receiver
    leading .                  source indentation unit at logical line start
    ---                        visual alias for bare `end`
    end                        close current vertical Structure
    end name                   close current vertical Structure with validation token
    L2/L3/L4/L5                level receiver frames
    sub                        receiver that registers subroutine definitions
    fn                         receiver that registers function definitions
    return                     executable-body return receiver/operator
    operator                   receiver that registers receivers/operators
    if                         registered receiver, semantics depend on level
    while                      registered receiver, semantics depend on level
    mathematical infix         parsed into expression Structure
    []                         L2 address operator; L3+ checked array-Structure access
    .                          built-in parser form for field access when not in line-prefix position
    ^ & *                      L2 pointer/address/callable-reference operators
    relation/fact/rule/query   receiver-defined relational Structures
    union                      receiver that registers a closed set of variants
    method                     receiver that registers a generic dispatch entry
    behavior                   L5 receiver that attaches message behavior to a model
    message                    L5 behavior child Structure / registry fact
    nested fn/sub              local executable definitions with lexical scope

Core invariant:

    leading dots, not spaces or tabs, define source block depth;
    syntax builds Structures;
    receivers give Structures meaning;
    Structures do not execute themselves;
    return exits executable bodies;
    function name in head/update position updates the current return binding inside its own body;
    nested fn/sub definitions create local executable bindings;
    visible names share one lexical namespace and do not silently shadow;
    `=` is not native assignment or native named-field syntax;
    L4 structural descriptors and L5 behavior/fact descriptors may materialize registry facts;
    end closes source Structures.

25.3. ANSI C Implementation Variants

---ANSI C---
These variants are implementation notes for a possible ANSI C based translator. They are not part of Lingvamyxa source semantics.

Call lowering:

variant 1:
Pass a small number of primitive/reference fields directly in internal generated C functions.

variant 2:
Pass an args Structure pointer/handle when the logical argument Structure is large or dynamic.

variant 3:
Generate specialized adapters, inline calls or eliminate physical args Structures when observable source semantics are preserved.

Return lowering:

variant 1:
Return a single primitive as a direct C primitive value.

variant 2:
Return multi-field results through caller-provided output storage.

variant 3:
Return small Structures by value where the implementation profile allows it.

variant 4:
Return handles/pointers to runtime-managed Structures for dynamic or large results.

Destructuring lowering:

variant 1:
Store the returned Structure or handle in a temporary service variable and update target variables from its fields.

variant 2:
For known layouts, generate direct field access.

variant 3:
For dynamic layouts, generate checked accessors or runtime lookup.

Field and array lowering:

variant 1:
Known field access lowers to direct C struct or pointer access.

variant 2:
L2 indexing lowers to computed-address access under the L2 memory model.

variant 3:
L3+ indexing lowers to checked access through array metadata such as `len`.

The language does not define C slot counting, hidden runtime pointers, hidden output pointers or C storage ownership rules. Those are translator/runtime design choices.
---ANSI C---

26. L3 Control Operators

26.0. Scope of This Section

This section defines the normative L3 control-flow receiver set for executable bodies.

The operators in this section are source-level control receivers. They are not raw low-level jumps. A translator may lower them to branches, labels, hidden control-result Structures, cleanup-stack operations or other implementation artifacts.

Unless stated otherwise, these operators are L3 operators. Some of them may also be exposed in L2 by an implementation profile, but this section specifies the L3 semantics.

Operator summary:

    0.  if / then / else                                  L3
    1.  match / case / default                            L3
    2.  while                                             L3
    3.  until                                             L3
    4.  for                                               L3
    5.  each                                              L3
    6.  return                                            L3 executable body
    7.  break                                             L3 loop frame
    8.  continue                                          L3 loop frame
    9.  finally                                           L3 executable/scope frame cleanup
    10. guard / fail / throws / failure labels / handlers  L3 recoverable failure flow
    11. retry / retryable                                 L3 retry frame
    12. assert                                            L3 diagnostic failure flow
    13. redo                                              L3 loop frame
    14. yield                                             L3 iterator function
    15. labelled break / labelled continue                L3 labelled loop frame

The following namespaces are distinct:

    normal lexical namespace:
        models, types, variables, fn, sub, receivers and ordinary names

    control-label namespace:
        loop labels, retry labels and failure labels

Normal names and control labels do not shadow each other. A control label may not be ambiguous inside its control-label scope.

26.1. `if`, `then` and `else`

`if` consumes a condition and one or two body Structures.

Semantic form:

    if(condition, thenBody, elseBody?)

Explicit form:

if condition
.then
..thenBody
.---
.else
..elseBody
.---
---

Short structural form:

if condition
..thenBody
.---
..elseBody
.---
---

Single-line form:

    if condition doSomething

The condition is evaluated once before branch selection.

Only the selected body is executed.

If no `else` body is provided and the condition is false, `if` completes normally without executing a body.

`then` and `else` are structural section markers inside `if`. They are not ordinary runtime calls when consumed by the `if` receiver.

26.2. `match`, `case` and `default`

`match` selects one body from a set of cases.

Example:

match value
.case 1
..print one
.---
.case 2
..print two
.---
.default
..print other
.---
---

There is no automatic fallthrough from one `case` to the next.

A `case` body is a closed Structure. Completion of one `case` completes the `match` unless another control operator such as `break`, `return`, `fail`, `retry`, `redo` or `assert` transfers control.

For union values, a `match` may destructure the active variant.

Example:

match shape
.case Circle c
..drawCircle c
.---
.case Square s
..drawSquare s
.---
---

If the matched value is a closed union and no `default` is present, an implementation may require exhaustive cases.

?
The exact pattern syntax for `case`, including guards, nested destructuring, constants, model names, union variants and relation patterns, is not specified in this section.
?

26.3. `while`

`while` is a pre-condition loop.

Semantic form:

    while(condition, body)

Example:

while i < n
.print i
.i i + 1
---

The condition is evaluated before each iteration.

If the condition is false before the first iteration, the body is not executed.

A `while` body is a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

26.4. `until`

`until` is a post-condition loop with the argument order reversed relative to `while`.

Semantic form:

    until(body, condition)

Example:

until
.readNext record
.process record
---
.endOfInput record
---

The body is executed first. The condition is evaluated after the body.

The loop repeats until the condition is true.

Equivalent informal form:

    do
      body
    while not condition

`until` creates a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

26.5. `for`

`for` is a controlled loop receiver for numeric ranges, counters, index ranges or other bounded iteration policies.

Example form:

for i 0 n
.print i
---

Semantic requirement:

    `for` creates one or more loop-local iteration bindings.
    `for` advances those bindings according to the selected control policy.
    `for` executes the body once for each produced iteration state.

`for` creates a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

?
The exact canonical source forms for numeric ranges, inclusive/exclusive bounds, step values, reverse iteration, index/value pairs and destructuring of iteration bindings are not specified in this section.
?

variant 1:
Use compact positional forms such as `for i 0 n`.

variant 2:
Use named structural forms such as `for i from 0 to n step 1`.

variant 3:
Treat all range policies as ordinary receiver Structures consumed by `for`.

26.6. `each`

`each` iterates over a container or iterator-compatible Structure.

Array-like example:

each item in items
.draw item
---

Receiver-like example:

each items item
.draw item
---

Semantic requirement:

    `each` obtains a sequence of values from its source.
    For each value, `each` binds the iteration variable or variables.
    `each` executes the body once for that value.

`each` creates a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

For arrays or array-like containers, `each` may lower to an index loop.

For iterator-compatible Structures, `each` repeatedly calls the iterator `next(env)` implementation until no value is produced.

Iterator consumption by `each` is specified in section 26.14.

26.7. `return`

`return` exits the current `fn` or `sub` executable body.

Bare form:

    return

For an `fn`, `return` returns the current return binding.

For an `fn`, `return` does not accept value arguments and does not fill the declared return Structure. Return fields or the whole current return binding must be updated before `return`.

For a `sub`, `return` exits the `sub` body. A `sub` does not produce a normal return value.

Before control leaves the current executable frame, all `finally` cleanups registered for the exited scopes are executed in reverse registration order.

26.8. `break`

`break` exits the nearest active loop frame.

Example:

while running
.if stopRequested
..break
.---
.step
---

`break` is valid only inside a loop frame unless a labelled form is used as described in section 26.15.

Before control leaves the exited loop body scopes, all affected `finally` cleanups are executed in reverse registration order.

`break` is not a source-level raw jump. It is a structured loop-frame exit.

26.9. `continue`

`continue` starts the next iteration of the nearest active loop frame.

Example:

each item in items
.if skip item
..continue
.---
.process item
---

For `while`, `continue` transfers control to the next condition check.

For `until`, `continue` transfers control to the post-body condition check for the current iteration.

For `for`, `continue` transfers control to the next iteration-state update.

For `each`, `continue` transfers control to the next container or iterator value.

Before control leaves the current loop body scopes, all affected `finally` cleanups are executed in reverse registration order.

26.10. `finally`

`finally` registers cleanup code in the current execution context.

Block form:

finally
.cleanupBody
---

Single-line form:

    finally cleanupCall

`finally` is not part of a `try` block in this specification. It is a standalone cleanup registration operator.

A cleanup registered by `finally` is associated with the current executable/scope frame.

Cleanups are executed when their associated frame or scope is exited by:

    normal completion;
    return;
    break;
    continue;
    labelled break;
    labelled continue;
    fail;
    retry;
    redo;
    assert diagnostic exit;
    thread/task termination in the default runtime profile.

Cleanups are executed in reverse registration order.

A cleanup body is executed outside the registration operation. It is not executed at the point where `finally` is encountered, except when the frame exits immediately after registration.

`finally` cleanups are part of the execution context model defined in section 27.

!!!
The exact semantics of a cleanup failure are not fixed. A final runtime specification must define what happens if a cleanup itself executes `fail`, `assert`, `return`, `break`, `continue`, `retry`, `redo` or another `finally` registration while cleanup processing is already active.
!!!

26.11. `guard`, `fail`, `throws`, failure labels and handlers

`guard` and `fail` define declared recoverable failure flow.

They are distinct from `assert`.

    guard / fail:
        declared, expected, recoverable failure path

    assert:
        diagnostic invariant violation

26.11.1. `throws`

An executable definition may declare failure labels with `throws`.

Example:

fn parseInt
.Text text
---
.int
---
.throws
..ParseError
.---

.guard validInteger text
..fail ParseError text
.---

.parseInt parseInteger text
---

`throws` lists the failure labels that may leave the executable body as recoverable failures.

A caller must handle, propagate or remap a declared failure.

26.11.2. `guard`

`guard` executes its failure body when its condition is false.

Example:

guard radius > 0.0
.fail InvalidRadius radius
---

Semantic form:

if not condition
.failureBody
---

`guard` is a convenience control receiver. It does not itself define the failure transport mechanism. That is defined by `fail`.

26.11.3. `fail`

`fail` exits the current executable body with a declared failure label and optional payload.

Example:

    fail ParseError text

Semantic effect:

    set failure label to ParseError;
    set failure payload from the remaining arguments;
    execute affected finally cleanups for the current frame exit;
    return a structured failure result to the caller or visible handler.

`fail` is part of the declared `throws` set. It is not a diagnostic abort.

`fail` does not transfer to the thread diagnostic root.

`fail` does not use the `assert` channel.

26.11.4. Failure labels and handlers

Failure labels belong to the control-label namespace, not to the normal lexical namespace.

A handler consumes a failure label and payload.

The exact handler surface syntax is not finalized in this section.

variant 1:
Use label-like handler syntax:

ParseError:
.Text badText
---
.print badText
---

variant 2:
Use explicit receiver syntax:

handler ParseError
.Text badText
---
.print badText
---

variant 3:
Represent handlers as L5 event/message handlers for failure events.

!!!
The exact source syntax, placement, visibility and lifetime of failure handlers are not fixed. A final source specification must define whether handlers are lexical Structures, executable labels, L5 event handlers, caller-side receivers or a combination of these forms.
!!!

26.11.5. Failure propagation

If a failure is not handled in the current body, it must be propagated by an enclosing or calling executable whose `throws` declaration includes the failure label.

Failure propagation is structured. It is not a raw jump through arbitrary stack frames in the source semantics.

---ANSI C---
A translator may lower declared failures using:

variant 1:
Return-status wrappers.

variant 2:
Status return plus output parameters.

variant 3:
A hidden control-result channel.

variant 4:
A non-local transfer mechanism for a selected runtime profile, provided that Lingvamyxa `finally` semantics are preserved.

The strict default for this draft is structured failure propagation, not root-level `longjmp`.
---ANSI C---

26.12. `retry` and `retryable`

`retryable` defines a restartable frame.

`retry` restarts the nearest or named retryable frame.

Example:

loadAttempt:
.retryable
..loadNetworkData
.---

Possible failure-handler use:

NetworkError:
.reconnect
.retry loadAttempt
---

A `retry` transfer executes the affected `finally` cleanups for the abandoned attempt before re-entering the retryable frame.

`retry` does not roll back external side effects. It only repeats the source frame according to the retryable-frame semantics.

Local bindings declared inside the retryable frame are re-created when the frame is re-entered.

Outer bindings keep their current values unless the retryable receiver defines a stronger rollback policy.

`retry` without a label targets the nearest active retryable frame.

`retry labelName` targets the named retryable frame.

!!!
The exact interaction between `retry`, failure handlers, iterator frames, partially executed cleanups and mutable outer bindings requires a final rule. This draft defines retry as re-execution, not as transactional rollback.
!!!

26.13. `assert`

`assert` checks a diagnostic invariant.

Example:

    assert index >= 0
    assert index < values.len

If the condition is true, execution continues normally.

If the condition is false, the current execution/checking phase fails with an `AssertionViolation` diagnostic.

`assert` is not recoverable `fail` control flow.

`assert` is not part of the declared `throws` set.

`assert` is not caught by failure labels or failure handlers.

Default L3 runtime semantics in the thread profile defined in section 27:

    record AssertionViolation diagnostic;
    execute all active `finally` cleanups in the current thread ExecutionContext;
    transfer control to the thread diagnostic root;
    terminate the current thread/task by default after reporting the diagnostic.

Default L4 model-time use, if exposed by a level profile:

    an assertion violation terminates the current model-loading or translation pass with a diagnostic error.

`assert` is intended for impossible states, broken invariants, corrupted internal assumptions or translator/model errors. Expected input failure must use `guard` and `fail`.

26.14. `redo`

`redo` repeats the current loop iteration without advancing the loop source.

For `each`, `redo` repeats the body with the same current element.

For iterator-based `each`, `redo` does not call `next(env)` before repeating the body.

For `for`, `redo` repeats the body with the same loop bindings.

For `while`, `redo` repeats the body without re-evaluating the condition first.

For `until`, `redo` repeats the body without evaluating the post-condition first.

Before the current iteration is restarted, all `finally` cleanups registered inside the abandoned iteration attempt are executed.

`redo` is dangerous because it can create non-progressing loops. It is valid only inside a loop frame.

26.15. `yield`

`yield` is valid only inside an iterator function.

An iterator function declares a return model compatible with `Iterator T`.

Calling an iterator function does not execute its body to completion. It creates an iterator state Structure.

The translator lowers the iterator body into a `next(env)` implementation.

Each `yield` emits one value compatible with `T` from `next(env)` and records the resume state in `env`.

The `each` receiver consumes iterator-compatible Structures by repeatedly calling their `next(env)` implementation until no value is produced.

26.15.1. Iterator function

Example:

fn makePoints
---
.Iterator Point
---
.yield 1.0 2.0
.yield 3.0 4.0
.yield 5.0 6.0
---

Calling:

    makePoints

creates an iterator state Structure. It does not return an `Array Point` and does not execute all `yield` statements immediately.

26.15.2. Iterator state Structure

An iterator state Structure contains enough state to resume execution after each `yield`.

For a simple iterator, generated state may include:

    state index;
    captured arguments;
    local variables that survive across yields;
    cleanup registrations owned by the iterator frame;
    a reference to the generated `next(env)` implementation.

Source-level code does not depend on the physical layout of this state Structure.

26.15.3. `next(env)`

The generated `next(env)` implementation executes the iterator until it either reaches a `yield` or terminates.

At a `yield`, `next(env)` returns a produced value and records where execution must resume.

When the iterator terminates, `next(env)` returns a no-value result.

Conceptual result model:

Next T
.boolean hasValue
.T value
---

?
The exact standard name and structural layout for the result of `next(env)` is not specified. A final iterator specification must choose canonical names and fields, such as `Next T`, `Option T`, `Some/None` or another equivalent representation.
?

26.15.4. `yield` value construction

If `T` is a primitive, `yield value` emits that primitive.

If `T` is a Structure, the arguments of `yield` fill that Structure according to the same structural rules used by `return`.

Example:

    yield 1.0 2.0

inside an `Iterator Point` function emits one `Point` value if `Point` has two positional fields such as `x` and `y`.

26.15.5. Iterator consumption by `each`

Example:

each point in makePoints
.draw point
---

Semantic form:

iterator makePoints

while true
.result next iterator.env
.if not result.hasValue
..break
.---
.point result.value
.body
---

This is semantic pseudocode. A translator may lower it to a direct state machine or inline loop.

26.15.6. Iterator termination

A bare `return` inside an iterator function terminates the iterator.

A `yield` after termination is unreachable.

`break` and `continue` inside an iterator body operate on the nearest active loop frame inside the iterator body, not on the consumer's `each` loop.

!!!
Iterator close semantics are not fully specified. A final specification must define when iterator-owned `finally` cleanups run if an iterator is abandoned before exhaustion, discarded, moved to another thread or terminated by diagnostic failure.
!!!

26.16. Labelled `break` and labelled `continue`

A control label may be attached to a loop frame.

Example:

outerLoop:
.for row in rows
..for cell in row
...if found cell
....break outerLoop
...---
..---
.---

`labelName:` belongs to the control-label namespace.

`break labelName` exits the labelled loop frame.

`continue labelName` continues the labelled loop frame if the target label names a loop frame.

Before the transfer, all `finally` cleanups registered in scopes exited by the transfer are executed in reverse registration order.

It is a compile-time error for `break labelName` or `continue labelName` to target a label that is not visible in the control-label scope.

It is a compile-time error for `continue labelName` to target a non-loop frame.

?
The exact grammar rule for attaching labels to frames is not specified beyond the form `labelName:` before a frame. A final grammar must define whether labels can attach to retryable frames, blocks, handlers, iterator frames and arbitrary Structures.
?


27. L2 Thread Context and L5 Event Delivery Profile

27.0. Scope of This Section

This section defines a default runtime profile for:

    L2 execution threads;
    thread-local ExecutionContext;
    `finally` cleanup storage;
    `assert` diagnostic exit;
    Java-style synchronized inbox/outbox event delivery;
    L5 object/message event dispatch.

This profile is intentionally simple. It is based on cooperative thread loops that periodically check inbound messages and flush outbound messages. It does not define blocking request/reply as a primitive operation.

27.1. ExecutionContext

Each L2 execution thread owns one current ExecutionContext.

The ExecutionContext is thread-local.

Conceptual Structure:

ExecutionContext
.Thread currentThread
.CleanupStack cleanupStack
.DiagnosticRoot diagnosticRoot
.Diagnostic currentDiagnostic
.FrameDepth currentDepth
---

The ExecutionContext is not an ordinary user data model. It is runtime infrastructure.

The ExecutionContext stores active `finally` cleanup registrations for the current thread.

The ExecutionContext stores the diagnostic root used by `assert`.

27.2. CleanupStack

A cleanup stack is a LIFO stack of active cleanup entries.

Conceptual entry:

CleanupEntry
.cleanupSub
.cleanupEnv
.frameDepth
.scopeDepth
---

`finally` pushes a cleanup entry into the current thread ExecutionContext.

Normal frame/scope exit runs cleanup entries owned by the exited frame/scope.

Diagnostic thread exit runs all remaining cleanup entries in the current thread.

Cleanup entries are removed when they are executed. A cleanup must not execute twice.

27.3. L2Thread

An L2 thread owns:

    thread id;
    thread-local ExecutionContext;
    synchronized inbox;
    synchronized outbox;
    running/stopping state;
    body step or thread entry procedure.

Conceptual Structure:

L2Thread
.ThreadId id
.ExecutionContext context
.Inbox inbox
.Outbox outbox
.ThreadState state
.BodyStep body
---

The inbox and outbox are synchronized FIFO containers.

This profile describes them as Java-style synchronized Vectors. A translator/runtime may implement them as ring buffers, queues or other FIFO containers if the observable semantics are preserved.

27.4. Thread loop

Canonical thread loop:

initialize ExecutionContext
establish diagnostic root

while running
.checkInbox
.body
.flushOutbox
---

run all remaining finally cleanups
terminate thread

Java-style pseudocode:

    class L2Runnable implements Runnable {
        Vector<Message> inbox;
        Vector<Message> outbox;
        ExecutionContext context;

        public void run() {
            try {
                while (running) {
                    checkInbox();
                    body();
                    flushOutbox();
                }
            } catch (AssertException e) {
                context.currentDiagnostic = e.diagnostic;
                report(e);
            } finally {
                closeAllFinally(context);
            }
        }
    }

ANSI C style profile:

    initialize ExecutionContext;
    setjmp(context.diagnosticRoot);
    run thread loop;
    on assert longjmp, report diagnostic;
    run all remaining cleanups;
    terminate thread;

The Java-style and ANSI C-style profiles are implementation strategies for the same source-level thread model.

27.5. Assertion failure in the thread profile

When an L3 `assert` condition is false:

    an AssertionViolation diagnostic is created;
    all active cleanups in the current thread ExecutionContext are executed;
    control transfers to the thread diagnostic root;
    the current thread/task terminates by default after diagnostic reporting.

In a Java runtime, the transfer may be implemented by throwing an internal `AssertException` caught by the thread root.

In an ANSI C runtime, the transfer may be implemented by `setjmp` at the thread root and `longjmp` from the assertion failure path.

---ANSI C---
Conceptual implementation:

    typedef struct ExecutionContext {
        CleanupStack cleanupStack;
        jmp_buf diagnosticRoot;
        Diagnostic currentDiagnostic;
    } ExecutionContext;

    _Thread_local ExecutionContext *LX_CTX;

    void lx_assert_fail(Diagnostic d) {
        ExecutionContext *ctx = LX_CTX;
        ctx->currentDiagnostic = d;
        run_all_cleanups(ctx);
        longjmp(ctx->diagnosticRoot, 1);
    }

This implementation note does not define ordinary `fail`. Declared `fail` remains structured recoverable control flow.
---ANSI C---

!!!
The policy for assertion failure during cleanup is not fixed. A final runtime specification must define whether the runtime continues cleanup, stops cleanup, records secondary diagnostics or terminates immediately.
!!!

27.6. L2Message

A message is an event envelope delivered between threads or active L5 objects.

Conceptual Structure:

L2Message
.target
.selector
.sender
.args
.replyTo
.correlation
.flags
---

Fields:

    target:
        object, service or behavior target

    selector:
        message name / L5 selector

    sender:
        sender object or thread, if present

    args:
        argument Structure

    replyTo:
        optional inbox or target for asynchronous replies

    correlation:
        optional id used to match request and reply

    flags:
        runtime delivery metadata

`L2Message` is a transport envelope. The target's L5 behavior table decides which implementation consumes the selector.

27.7. Inbox and outbox operations

Sending a message appends it to a synchronized FIFO container and returns.

Basic operation:

    send target message

Semantic effect:

    append message to target thread inbox;
    do not execute the handler in the sender thread;
    return immediately.

Outbox operation:

    enqueue message into current thread outbox;
    later `flushOutbox` appends queued messages to target inboxes.

The outbox is optional as a physical layer. The source-level event model requires asynchronous delivery, not a particular buffering strategy.

variant 1:
Direct asynchronous send appends immediately to the target inbox.

variant 2:
The current thread appends to its outbox, and `flushOutbox` performs delivery.

variant 3:
The runtime combines both strategies according to scheduling and batching policy.

27.8. Inbox checking

`checkInbox` drains or checks the inbox periodically.

Handlers must not execute while the inbox synchronization lock is held.

Safe pattern:

localMessages drain inbox under lock

each message in localMessages
.dispatchMessage message
---

Unsafe pattern:

synchronized inbox
.dispatchMessage message
---

The unsafe pattern is forbidden by this profile because it executes user/L5 behavior while holding the inbox lock.

27.9. L5 event dispatch

L5 behavior dispatch for a delivered message uses the target object's behavior descriptor.

Conceptual dispatch:

    model = target.model
    behavior = lookupBehavior model
    method = lookup behavior.messageTable selector
    call method target args

If the target belongs to the current thread and the source form is a local L5 message, the translator/runtime may use direct Smalltalk-style synchronous dispatch.

If the target belongs to another thread or the source form is an explicit event send, delivery is asynchronous through the target inbox.

This profile distinguishes:

    local L5 message:
        receiver selector args
        direct behavior lookup and call in the current thread

    L5 event send:
        send receiver selector args
        asynchronous inbox delivery

    L5 request:
        request receiver selector args replyTo/correlation
        asynchronous inbox delivery with a later reply message

There is no blocking `ask` primitive in this profile.

27.10. Request and reply

A request is an asynchronous send with a correlation id and reply target.

A reply is an ordinary message carrying the same correlation id.

Request flow:

    requester sends request message to target inbox;
    requester continues executing its thread loop;
    target eventually handles request;
    target sends reply message to requester inbox;
    requester eventually handles reply during `checkInbox`.

No thread blocks waiting for a reply in the base profile.

A thread may store pending request ids in ordinary state and inspect them during its body step or message handlers.

Blocking request/reply is outside this profile.

?
A future profile may define blocking wait, timeout, inbox-pumping wait, futures, promises or structured async/await. Those are not part of this section.
?

27.11. Deadlock and progress properties

The synchronized inbox/outbox model avoids ordinary lock-order deadlocks if:

    inbox/outbox locks are held only for short append/drain operations;
    user code and L5 message handlers do not execute while holding those locks;
    the base profile does not block while waiting for replies.

This does not prove protocol termination.

A message protocol may still fail to make useful progress, send messages forever, exhaust memory or starve some tasks. Those are architecture/protocol properties, not synchronization-lock deadlocks in the mailbox mechanism.

27.12. Atomic operations and L5 messages

L5 message dispatch is not the universal mechanism for all computation.

L2 and L3 ordinary computation remains direct:

    primitive arithmetic;
    comparisons;
    field access;
    array access;
    direct fn/sub calls;
    loops and branches;
    generated low-level operations.

L5 messages are used for behavior, configuration, object/service interaction, active objects and high-level event delivery.

Lingvamyxa does not require Smalltalk-style message dispatch for every atomic operation.

27.13. Open points for the thread/event profile

?
The scheduling policy is not specified. A final runtime specification must define fairness, inbox drain limits, body step frequency, outbox flush timing and priority rules.
?

?
Inbox capacity, backpressure, message dropping, overflow diagnostics and memory limits are not specified.
?

?
Message ordering across multiple senders is not specified beyond FIFO order inside one synchronized target inbox after messages have been appended.
?

?
Object ownership, migration between threads, shared immutable objects and cross-thread object references require a separate runtime specification.
?

?
The exact source forms for `send`, `request`, `reply`, `checkInbox`, `flushOutbox`, thread creation and thread shutdown are not specified in this section.
?

?
The interaction between L5 fact registries, persistent event logs and runtime inbox messages is not specified.
?
