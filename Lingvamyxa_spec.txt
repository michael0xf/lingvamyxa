Lingvamyxa Language Structural Core Specification
Part I: General Syntax and L0-L1-L2-L3 Core

Status

Split draft extracted from Lingvamyxa_new.txt.

This part contains the common structural description, source syntax, P0 grammar,
receiver consumption rules and the L0/L1/L2/L3 execution-facing core. Sections
or subsections that define L4/L5 registry tables, message runtime services or
core authentication are moved to Part II.

0. Core Formula

Lingvamyxa is based on the following model:

    L0 binaries run.
    L1 is an external bootstrap, implementation and lowering layer.
    L2-L5 are Lingvamyxa levels.
    Source syntax builds Structures.
    Source traversal also builds MIX overlay intervals in parallel with
    Structures and arrays.
    Receivers and subroutines consume Structures.
    The core parser has one structural syntax.
    Operator tokens that cannot be namespace identifiers are parsed as operator fields without `:`.
    Whitespace-bounded operator forms are accepted directly by the core structural parser.
    Compact non-quoted spellings with invalid bare-name characters are split into ordinary fields and operator-token fields by the same structural tokenization pipeline.
    Levels restrict the active receiver/operator set.

The language does not assign final meaning directly from surface syntax. Surface syntax builds generic Structures. A receiver or subroutine consumes a Structure and assigns typed semantics to it.

Canonical semantic pipeline:

    source text
        -> core structural parse
        -> generic Structure values
        -> receiver/operator/subroutine consumption
        -> resolved semantic Structures or table-cell decisions
        -> interpretation or lowering

A Structure does not execute merely because it exists. Execution, translation, registration, validation or query handling starts only when a receiver or subroutine consumes the Structure under a defined mode.

Argument position does not change that rule. A Structure supplied as an argument
remains a Structure for the parser. During translation or interpretation, a
compact Frame/Structure is treated as a call only when its head resolves in the
active namespace as a function, subroutine or registered receiver. A bounded,
anonymous or vertical Structure is not executed merely because it appears among
arguments.

0.0.1. Language Scope

Lingvamyxa is one structural language with several consumption modes.

The same source mechanism builds Structures. Different receivers and profiles
consume those Structures as data, executable code, model descriptors, registry
table rows, messages, service routes, build instructions or transport payloads.

Part II defines the high-level registry model as tables. In that model, a
`class` is a named registry form/table/entity, expressions ask for table cells,
and validation/resolution turns generic Structures into concrete expressions or
terminal lowering decisions. The word `type` remains available in narrower
storage/lowering contexts such as L2 and ANSI C.

0.0.1.0. First, Lingvamyxa is a general structural data notation.

It can be used for human-readable records, trees, nested configurations,
schemas, registries, message payloads and table-like data in the same problem
domain as XML, JSON, YAML and CSV.

Unlike those formats, Lingvamyxa does not have a separate data syntax and
program syntax. Both are source forms that build Structures.

Example of mixed tree and table-like data:

dataset: harvest
    meta:
        title: "Regional harvest report"
        season: 2026
        source:
            organization: `Field Bureau`
            system: `manual survey`
        ---
        location:
            country: Uruguay
            region: `north field group`
        ---
        note:
            "This part is XML-like tree data: nested named Structures."
    ---

    table:
        columns: int(id)  Text(region)        Text(crop)  real(tons)  decimal(moisture)
        rows:
                 1        `north field`       wheat       12.50       0.14
                 2        `south field`       corn         8.75       0.19
                 3        `east ridge`        barley      10.00       0.16
                 4        `river lowland`     rice        21.30       0.22
end: harvest

The `meta` section is tree-shaped data, similar in role to an XML/YAML document.

The `columns:` line is a compact schema row. Each schema field is an explicit
compact Frame such as `int(id)`, `Text(region)`, `real(tons)` or
`decimal(moisture)`. Horizontal whitespace separates those schema fields.

The `rows:` section is true table-like data. Each physical row is one row
Structure. Horizontal whitespace separates row fields. Extra horizontal spacing
is only visual alignment and does not create additional fields.

The row values are visually aligned under the corresponding schema fields from
`columns:`. This alignment is presentation only; the structural meaning still
comes from ordinary whitespace-separated row fields.

Exact quoted identifiers such as `north field` and `river lowland` keep
multi-word field values atomic.

The `dataset`, `meta`, `table`, `columns` and `rows` receivers are not special
parser syntax. They consume ordinary Structures. A profile may lower this data
to CSV, SQL rows, binary records, in-memory arrays, Lingvamyxa Structure
serialization, JSON for legacy interoperability, or another backend
representation.

0.0.2.0. Secondly, Lingvamyxa has MIX overlay markup and document semantics.

MIX is the Lingvamyxa overlay markup model. It is not an XML-like tree
markup system, not an HTML preprocessor and not a separate mini-language.
MIX is a parallel active mark and interval overlay built during the same
source traversal that builds ordinary Structures and arrays.

The compact formula is:

    source traversal
        -> Structures and arrays
        -> MIX active mark / interval overlay
        -> receiver/profile consumption

The source text may still look tree-shaped, because that is convenient for
human reading and for structural parsing. The MIX view is different: it
projects source positions, Structure nodes, array rows, fields and explicit
marks into overlapping active sets. Therefore a Lingvamyxa source file can have
MIX overlay information even when it contains no explicit curly-brace marks.
Ordinary structural forms are also markable source-interval entities. Curly
braces are only the explicit document-facing spelling for adding extra active
marks to the same overlay model.

Curly braces introduce MIX bounded forms `{...}`. They are bounded structural
forms like parentheses and index brackets, but their result is a MIX payload
Structure. When the P0 parser sees `{` outside ordinary string/comment/raw
payload, it enters MIX payload parsing. The payload between `{` and its
matching `}` is parsed by the same structural parser in its own local level-0
context, so quoted strings, python-like raw strings, exact identifiers, block
strings and comments keep their ordinary payload rules. A `}` inside such a
payload is payload text, not the closing delimiter of the surrounding MIX
bounded form.

The resulting MIX bounded form payload Structure is stored immediately as a
parser node with the source position/span of the mark and a MIX flag. Physical
line breaks inside the mark do not create source-level/layout events for the
surrounding Structure. The opener column of `{` does not become the local
indentation base for the MIX payload. Ordinary structural consumers and
translators may ignore MIX-flagged nodes, while document/MIX consumers project
them into the active mark/overlay view. A mark frame such as:

    {color: red}

opens one active MIX mark entry. In this example the mark head is `color` and
the active close name/value is `red`. The entry remains active until it is
closed or until the containing source/document unit ends according to the
selected profile. Unclosed entries are not silently forgotten; they remain
tracked as still-open entries and may become diagnostics, document-wide
intervals or profile-specific state.

Explicit close forms operate over the active mark stack:

    {color: red}
    {color: green}
    text
    {end: red}
    {end: green}

`{end}` closes the last still-active explicit mark. `{end: name}` closes the
most recent still-active explicit mark whose close name/value is `name`.
Closing `red` in the example above closes the `{color: red}` entry; the
`{color: green}` entry remains open until it is closed separately.

When several active entries share the same close name/value, the most recent
matching entry wins, regardless of the mark head:

    {style: red}
    {color: red}
    text
    {end: red}

Here `{end: red}` closes `{color: red}`, not `{style: red}`. The close operand is
the active close value, not an XML-style repeated element name.

This is intentionally different from XML and HTML nesting. Closing names the
active value that is no longer wanted; it is not a repeated tag name and it
does not force all open marks into a single strict element tree. A later or
inner mark does not destroy the earlier one. For example, while the parser is
inside both `{color: red}` and `{color: green}`, the current `color` value for a
simple renderer may be `green`, but the underlying active chain still contains
`red` below it. A consumer may inspect the whole chain.

The active attribute view is therefore not just a flat map from name to one
value. It is at least a key-to-stack, key-to-list or key-to-active-set view over
the ordered active MIX entries. A rendering profile may project this view to a
simple last-open-wins table. A semantic, editor, diagnostic or registry profile
may use the complete active chain and all intersecting active sets. P0 does not
perform conflict resolution for MIX marks.

Example of the same tree and table-like data with explicit MIX overlay marks:

{style: system}
dataset: harvest
    meta:
{style: title}
{color: blue}
        title: "Regional harvest report"
{style: date}
        season: 2026
{end: title}
        month: April
{end: date}
        source:
            organization: `Field Bureau`
            system: `manual survey`
        ---
        location:
{color: green}
            country: Uruguay
            region: `north field group`
        ---
        note:{color: blue}
            "This part is {color: red} marked {end} document data over ordinary Structures."

    ---
{end: blue}

    table:
        columns: int(id)  Text(region)        Text(crop)  real(tons)  decimal(moisture)
        rows:
                 1        `north field`       wheat       12.50       0.14
                 2        `south field`       corn         8.75       0.19
                 3        `east ridge`        barley      10.00       0.16
                 4        `river lowland`     rice        21.30       0.22
{end: green}
end: harvest
{end: system}

From one compact unified syntax, the parser can simultaneously create
hierarchical Structures, arrays and the MIX overlay graph. The MIX graph is a
layer of overlapping, partially hierarchical active sets laid over source
positions and structural data. The language algorithm can therefore know the
active values of all relevant elements at every position and can update them
directly.

MIX scanning is universal. MIX interpretation is profile-dependent.

A source/document consumer may know the ordinary Structure context, the array
or row context, the source position context, the active explicit marks and the
implicit structural intervals around the current position. Marks found inside a
string or raw text payload are recorded under that payload context, with their
own isolated marker table and namespace, instead of being mixed into the
surrounding source-level active mark table. Additional interpretation is needed
only when a consumer chooses to activate, render or consume such internal
payload marks.

For example, a surrounding mark such as `{style: system}` may select a profile
in which printed strings are treated as document text and their internal MIX
marks are interpreted. A SQL string profile may highlight or bind internal
placeholders. A plain string profile may ignore them completely. The raw string
value is not changed merely because MIX marks are visible to the parser or
document consumer.

The MIX layer maintains active marks while traversing the source. It can
therefore expose all data at a position, including Structure context,
structural-array context, current top attributes and the full active mark
chains, with fast access and without requiring large contiguous memory blocks.

MIX overlay data is produced below or alongside the level receivers; it is not
ordinary L5 execution by itself. However, L5 receivers may consume accepted
MIX-derived intervals, annotations and structural evidence through the ordinary
relation/table, query, registry, message and validation machinery.

0.0.3.0. Thirdly, Lingvamyxa is a high-level programming language.

The executable layer supplies ordinary algorithmic computation, function and
subroutine definitions, control receivers, expressions and calls.

The model layer describes structural models, classes-as-registry-tables,
contracts, constraints, protocols and registry descriptors.

The message and table-driven dispatch layer describes messages,
validation/merge, expression execution, logical message generation,
configuration, table/rule/query receivers and high-level dispatch.

Low-level programming is not a foreign escape hatch. The low-level and
implementation-facing layers provide controlled access to storage, addresses,
external functions, unsafe operations and implementation-specific lowering when
the selected profile admits them.

The exact level names and their boundaries are defined in the next section.

At service level, Lingvamyxa is a registry-driven service and message system.

Lingvamyxa treats compiler knowledge, runtime knowledge and service knowledge
as one structural registry/table model. Descriptors, models, operation tables,
routes, messages, handlers, build targets, validation rules and transport
profiles are all Structures accepted by receivers and stored, derived, queried
or lowered through the registry.

For this reason, a Lingvamyxa implementation is not only a compiler in the
narrow sense. A complete implementation may also act as a runtime, build system,
registry host and service framework for small and large services.

The built-in HTTP Lingvamyxa REST profile provides a standard HTTP transport
for Lingvamyxa messages between service instances, service thread groups
and external HTTP clients. HTTP is the transport envelope. REST routes are
service/route descriptors stored as registry table rows. Lingvamyxa messages
and serialized Lingvamyxa Structures remain the semantic payload.

JSON may be supported as a legacy or interoperability adapter, but JSON is not
the default payload model of the HTTP Lingvamyxa REST profile and does not
define Lingvamyxa message semantics.

0.1. Mixed L4/L5/L3 Smoke Example

The following example defines no new syntax. It illustrates the core formula in
one file: L4 consumes model/registry table descriptors, L5 consumes message,
route, build and rule descriptors, and L3 consumes executable definitions and
ordinary control receivers.

Short version of the "hello.lm3" file in the default executable script profile:

print: "Hello World"

In this profile, the file root is consumed as an L3 top-level executable body.
The long `.lmx` version below spells out the surrounding model, registry, build
target and explicit executable entry point.

0.1.1. Source File Level Profiles

The source file extension may select the outer level profile. This is not
inferred from the first receiver in the file.

In the default profile:

    `.lm2` means that the file root is consumed as an implicit L2 body.
    `.lm3` means that the file root is consumed as an implicit L3 body.
    `.lm4` means that the file root is consumed as an implicit L4 registry/model body.
    `.lm5` means that the file root is consumed as an implicit L5 service/message body.

The explicit wrapper form remains valid for compatibility and for mixed `.lmx`
examples:

    L2:
        ...
    end: L2

But a `.lm2` file does not need that outer wrapper. The same rule applies to
`.lm3`, `.lm4` and `.lm5`.

The dependency is deliberately attached to the source profile, not to a receiver
name. For example, a root-level `table:` in a `.lm4` registry file is consumed
as L4 registry input because the file is `.lm4`. A root-level `table:` in a
plain `.lmx` file is only ordinary Structure data unless it appears inside an
explicit `L4:`/`registry:` context or another profile admits it. This prevents
ordinary data from becoming registry input merely because it uses a receiver
spelled `table`.

Long version of the "hello.lmx" file:

The `relation:`, `fact:` and `behavior:` receivers in this example are
illustrative table-row or message-row receivers. Part II defines the general
table model; this Part I example uses them only to show that the same
structural syntax can be consumed as registry input.

L4:
    model: HelloConfig
        vars:
            Text: greeting owned
            int: maxI
            int: maxJ
        ---
        condition:
            maxI > 0 && maxJ > 0
        ---
    ---

    relation: entryPoint
        Symbol: targetName
        Symbol: implementationName
    ---
end: L4

L5:
    behavior: HelloConfig
        message: run helloMain
    ---

    fact: model HelloConfig
    fact: message HelloConfig run helloMain
    fact: entryPoint app helloMain

    target:
        app
        kind: executable
        sources: ("src/hello_world.lm3")
        entry: helloMain
        output: "build/bin/hello_world.lm0.exe"
    ---

    build: app
end: L5

L3:
    fn: words () iterator(Text)
        yield: "Hello"
        yield: "World"
    end: words

    fn: factorial (int(n)) (int)
        if: n <= 1
            return: 1
    return: n * factorial(n - 1)

    sub: helloMain
        HelloConfig: cfg
            greeting: "Hello World"
            maxI: 3
            maxJ: 3
        ---

        System\out\println: cfg\greeting

        each: word in words
            System\out\println: word
        end: each

        outerLoop:
            for: int(i, 1) (i <= cfg\maxI) i++
                for: int(j, 1) (j <= cfg\maxJ) j++
                    if: i = 2 && j = 2
                        System\out\println: "--- continue outerLoop ---"
                        continue: outerLoop
                    ---

                    System\out\println: ("i: " + factorial(i) + ", j: " + factorial(j))
        end: outerLoop

        System\out\println: "Done."
    end: helloMain
end: L3

Notes:

    `end: words` explicitly closes the `fn: words () iterator(Text)` definition.
    The `return:` at the source level of `fn: factorial (int(n)) (int)` is
    terminal return for that function definition. It appends the runtime return
    and closes the executable definition. The `sub: helloMain` definition is
    closed explicitly by `end: helloMain`. The enclosing `L3` frame is closed by
    `end: L3`.

    `fn: words () iterator(Text)` gives the `fn` receiver the fields
    `words`, `()`, `iterator(Text)` and the following `yield:` fields. The
    `fn` receiver consumes them as name, empty formal argument Structure,
    return descriptor and executable body.

    `yield: "Hello"` gives the `yield` receiver one produced value. The
    receiver inspects the current `fn` return descriptor, verifies that
    `iterator(Text)` declares a yield-protocol, and checks the produced value
    against that protocol. Neither `iterator` nor `Text` is a parser keyword;
    both are ordinary namespace names interpreted by the active L3 profile.

    `each: word in words` gives the identifier `words` to the `each` receiver as
    an iterator source. The explicit compact call form `words()` is also a valid
    Frame when a profile/receiver wants the iterator state to be created before
    `each` consumes it.

    The `match`, default-pattern, failure-handler and full build-target semantics
    are not implied by this example. They remain receiver/profile semantics
    described in their own sections.

This example should be read with five simple structural rules in mind:

1. Source text builds Structures.

   A source form does not execute merely because it looks like a statement.
   It first builds a generic Structure. The active receiver later consumes that
   Structure and assigns typed meaning to it.

2. `head: tail` means that `head` consumes one argument Structure.

   The colon is a receiver-valence marker, not assignment syntax and not a
   keyword-specific grammar. Forms such as `fn:`, `if:`, `model:`, `fact:`,
   `int:` and `return:` share the same surface mechanism. Their meanings differ
   because their receivers consume their argument Structures differently.

   Therefore omitting the colon changes the Structure:

       return 1   # two neighboring fields; not "return value 1"
       return: 1  # a return Frame whose receiver consumes value 1

   `return:` has a deliberate double role: inside an executable body it is a
   runtime return receiver, and at an admitted executable trailer position it
   may also close the executable definition. `end:` is different. It is only a
   structural close receiver; it has no ordinary body-level runtime action.

3. Source levels build the tree.

   The parser tracks source-level changes, not physical source lines as
   containers. Dots in canonical notation, indentation in relaxed notation,
   colon short-form, semicolon, bounded parentheses/brackets, source-level markers and
   physical newline separators may all affect the current level model. Comma is
   an explicit field separator without source-level effect. Child
   items are written at the next deeper source level. An atomic increase of the
   current source level opens a Structure. Returning by one source level
   completes the currently open Structure before the next source item is parsed.
   Cutting more than one level at once is reserved for admitted tail-cutter
   semantics in the next layer.

4. A source-level cut is the ordinary trailer event.

   A block does not need an explicit close merely because it is named. The
   ordinary trailer event is the source-level cut when a following source item
   or admitted marker makes that cut visible. It is not the physical newline
   character by itself, and it is not the text of the following lower-level
   item. Explicit forms such as `end: name` and
   terminal return forms become tail-cutter trailers only in a valid
   source-level tail-cutter position. They may close source-level/block tails,
   but they do not close unmatched parenthesized/bracketed bounded Structures;
   those must still be closed by the matching `)` or `]`. Short colon forms are
   not bounded by those delimiters, so an
   admitted `end: name` may terminate a short form in a valid source-level
   tail-cutter position.

5. `end: name`, `---` and terminal return forms are not competing block systems.

   `end: name` is an explicit named tail-cutter, useful in long or deeply
   nested blocks and when the close target should be visible. P0 records it as a
   tail-cutter trailer only when it actually closes an open source-level frame.

   `---` is an explicit source-level marker. It materializes a level point
   without adding an ordinary receiver item. It is mainly useful for anonymous
   same-level sections where an ordinary source item cannot show the necessary
   down/up level transition.

   A terminal return form is an executable-specific trailer when the semantic
   executable layer admits it at the source level of the executable definition.
   For a value-producing `fn`, that form is `return: value`; for a no-value
   executable profile, a bare `return` may be admitted. A `return` written
   inside the body level is an ordinary runtime return.

Style convention used by this example:

    Use the ordinary source-level cut for short local Structures.
    Use `end: name` when the closed target is long, important or not visually
    obvious.
    Use `---` for anonymous same-level sections or visible empty level markers.
    Use terminal `return: value` for compact final function returns when the
    source level makes the target clear.

These notes are only a reading guide for the example. The exact syntactic and
semantic rules for Structures, Frames, source levels, short forms, bounded
Structures, receivers, `end:`, `---` and terminal return forms are specified in the
following sections.

1. Levels

1.0. General Language Role and External Lexical Standards

Lingvamyxa is a cross-platform structural language with an explicit external L1 bootstrap, implementation and lowering substrate. In the default hosted bootstrap profile, L1 may lower through ANSI C / C99, but ANSI C / C99 is a porting and implementation substrate, not the language's semantic parent and not the language's self-hosting level. Lingvamyxa source text builds Structures; registered receivers, functions, subroutines, operators, model descriptors, table descriptors and query receivers consume those Structures and assign typed meaning to them.

A compact description is:

    Lingvamyxa is an object-oriented, functional and logical structural language whose self-hosting infrastructure begins at L2/lm2 and whose hosted bootstrap may lower through an external L1 substrate.

More precisely:

    * L1 supplies the external procedural, portable, implementation-facing substrate and may map to ANSI C / C99 in a hosted bootstrap profile.
    * L2/lm2 exposes low-level typed storage, addresses, layouts and unsafe operations and is the first Lingvamyxa self-hosting infrastructure layer.
    * L3 supplies ordinary algorithmic computation and executable definitions.
    * L4 describes structural models, classes-as-tables, contracts, unions, constraints and registry descriptors.
    * L5 describes messages, validators, expression executors, logical message generators, configuration, rules, build/query/startup receivers, L5 Threads and high-level dispatch.

Lingvamyxa implementations may also act as service runtimes. The built-in HTTP Lingvamyxa REST profile provides a standard event/message transport between groups of L5 Threads and service instances. HTTP is the transport envelope; Lingvamyxa messages and Structures remain the semantic payload.

The object-oriented side is structural, not class-magical. A model descriptor contributes field, class/type, default, constraint and layout table rows. Operations are selected by registry tables that map receiver/class and selector/expression shape to concrete implementations. A runtime object is a Structure or handle/reference to a Structure together with enough table information to resolve the expression being consumed.

The functional side is also structural. A function or subroutine definition is a
Structure consumed by the `fn` or `sub` receiver. A call spelling is a Frame, but
it becomes a generated call only after namespace resolution proves that the head
is a function, subroutine or registered receiver. Function return is represented
by `return` receivers and terminal return, not by a separate assignment syntax.

The logical side is represented by relation tables, rules and query receivers. Model, union, operator, method, message and validator descriptors may materialize registry rows. Generic dispatch, message validation, completeness checks and lowering may be expressed as table lookup over this registry model. This gives one uniform way to index, validate, derive and lower structural information.

The source syntax itself does not hard-code object semantics, functional semantics or logic semantics. It builds generic Structures. The active level and the active receiver/operator registry determine which semantic domain consumes a Structure. The same surface form may describe a low-level storage declaration, a function definition, a model descriptor, a table row, a validator, a rule, a query, a message or a build configuration, depending on receiver consumption.

Lingvamyxa deliberately reuses selected mature external lexical standards instead of redefining every atom. Numeric literals, character constants and text/string literals follow ANSI C / C99 spelling because L1 is ANSI C / C99 and many such literals can be copied directly into generated L1 code. Exact quoted identifiers use SQLite-compatible exact-name semantics because Lingvamyxa Structures may describe external relational schemas and because SQLite provides a simple exact quoted-name model.

This reuse applies only to lexical atoms. It does not adopt C assignment syntax, C declaration grammar, C control syntax, SQL expression syntax, SQL execution semantics, YAML mapping semantics or indentation semantics. Lingvamyxa owns the structural syntax and structural semantics: colon-governed frames, source-level tree composition, compact calls, short colon source items, short-tail field separation, terminal return, namespace Structures, `fn` / `sub` / label / variable registration, typed model/table descriptors, relation/query declarations and declared head consumption.

The practical rule is:

    Lingvamyxa owns structure.
    External standards may own selected lexical atoms.

Consequently, an ANSI C numeric literal, character constant or string literal may often be preserved as text during L1 lowering, while its surrounding Lingvamyxa Structure is still parsed, typed and consumed by Lingvamyxa receivers. Likewise, an exact quoted identifier may preserve an external SQLite name without forcing that name into the narrower bare Lingvamyxa identifier grammar.

1.1. L0

L0 is a native binary artifact or machine-code artifact. It is the level actually executed by the CPU and operating system.

Examples of L0 artifacts:

    app.lm0.exe
    app.lm0
    core.lm0.dll
    core.lm0.so
    core.lm0.dylib
    core.lm0.a
    core.lm0.lib

1.2. L1

L1 is an external bootstrap, implementation and lowering layer. It may host initial parsers, translators, runtime components and receivers. L1 has its own syntax and semantics and is not part of the Lingvamyxa source-semantic core described by this document.

This document does not specify the L1 target language, physical calling convention, memory ownership rules or low-level runtime representation. Those belong to translator and runtime specifications.

1.3. L2

L2 is the low-level unsafe Lingvamyxa level. It is the low-level systems layer. It may expose memory, typed addresses, handles, layout-based storage and explicit low-level operations. Selected low-level L2 Thread primitives may be introduced later for operations over shared memory arrays or other implementation-facing data, but ordinary interactive, concurrent, UI and service programming belongs to the L5 Thread model.

L2 is compiled. It is not executed as a casual script.

1.4. L3

L3 is the algorithmic and computational Lingvamyxa level. It supports safe top-level actions, computations and calls. L3 code may be interpreted by the core runtime or compiled through the lowering pipeline.

1.5. L4

L4 is the non-executive model level. It describes models, classes as registry
tables/entities, protocols, contracts, constraints, relation signatures and
registry metadata.

L4 may update or check the compiler/runtime model. L4 does not perform ordinary runtime actions by default.

1.6. L5

L5 is the level of messages, validators, expression executors, logical message
generators, configuration, registry tables, build/run/query/startup receivers,
L5 Threads and high-level dispatch.

An L5 Thread is the ordinary source-semantic active unit for interactive, concurrent, event-driven and service-like Lingvamyxa programs. A service instance is a placement or bundling mode of one or more L5 Threads, not a separate later paradigm.

L5 may attach message and operation handling to L4 structural models by adding
registry table rows. L5 may also represent registry data as relation tables and
rules. This draft keeps that message/table layer within L5 as source-semantic
infrastructure, not as ordinary runtime I/O.

L5 may consume accepted MIX-derived intervals, annotations and structural
evidence as registry table rows through the ordinary registry/query/message
machinery. MIX itself is produced by source traversal and structural overlay
processing; it is not ordinary L5 execution merely because L5 can store or
react to accepted MIX-derived rows.

1.7. Level Receivers

`L2`, `L3`, `L4` and `L5` are level receivers. A level receiver consumes its nested Structure and sets the active receiver/operator set for that body.

Example:

L4:
. operator:
. . if
. . callableFrom: L5
. . implementation: l5_if
end: L4

Semantic normal form:

    L4(
      operator(
        if,
        callableFrom L5,
        implementation(l5_if)
      )
    )

The receiver `L4` consumes its body as model and registry input.

1.8. Startup and Entry Targets

An entry point is not the first event in the physical life of a program. A
binary loader, target runtime, C runtime, Lingvamyxa runtime, restored state,
registry data, build profile or service host may already exist before source
level execution begins. The entry point is only the selected target to which
control is handed after that environment is ready.

Different Lingvamyxa levels use different default startup conventions:

    L2
        L2 is compiled and close to L1 / ANSI C. For an executable artifact,
        the default L2 entry target is `main`, because that convention maps
        directly to C99 and to ordinary native executable startup.

        Example:

        L2:
        . fn: main () int
        . . c.puts: "Hello"
        . . return: 0
        . end: main
        end: L2

        lowers conceptually to a C `main` function. This is a bootstrap and
        lowering convention, not a philosophical center of the language. A
        raw `L1:` block may also contain an ordinary C `main`; in that case
        the raw C block supplies the executable entry target.

    L3
        L3 is the ordinary algorithmic/script level. In the default script
        profile, the root body of an L3 source item may be consumed from the
        beginning of the file, Python-style. A build or runtime profile may
        also select a visible L3 function or subroutine as the executable
        target, but `main` is not a source-semantic requirement for L3.

    L4
        L4 is applied, validated and registered. It is not ordinary runtime
        control flow. An L4 source body may describe models, classes, registry
        patches, build profiles, constraints or registry table rows; applying
        that body is descriptor consumption, not program execution from a first
        statement.

    L5
        L5 is the message, service and high-level table-driven dispatch layer.
        Its startup model is closer to a selected message/callable target than
        to a hard-coded `main`. A runtime or build profile may choose any
        visible L5 startup target, such as a `start` receiver, an `onStart`
        handler, a service descriptor, or an explicit message send.

        Example conceptual target:

        L5:
        . HelloWorld:
        . . start:
        . . . System\out\println: "Hello"
        end: L5

        The startup target may be described as `HelloWorld\start` by the
        runtime profile. The language does not require every L5 file to run
        linearly from its first source item.

The common rule is:

    startup = prepared environment + selected visible target

The selected target may be the conventional C-compatible `main` at L2, the file
root in an L3 script profile, descriptor application for L4, or an explicit
message/callable target for L5.


2. Value Ontology

The minimal core has two classes of values:

    1. primitive/scalar/reference/handle values
    2. Structure / Frame values

Primitive/scalar/reference/handle values include numbers, booleans, atoms, symbols, enum-like values, handles, references, typed addresses and L2-level callable references.

All non-primitive values are Structures or handles/references to Structures. This includes arrays, text, objects, call frames, bodies, configurations, expressions, model fragments and executable/callable descriptors.

At source-semantic level, executable definitions are ordinary values bound in
the active lexical namespace view. A translator may lower such a value to any
implementation-level callable representation, such as a descriptor Structure,
registry index, trampoline, closure record or target-language callable
primitive. That lowering choice is not a separate source-level kind.

A Structure can contain fields. A field can be positional, named or derived during normalization from a receiver signature.

At L3 and above, Structures are normally passed by reference/handle. They are not copied by value at every call unless a receiver explicitly defines copy semantics.

At L2, aggregate layouts do not have to be source-level value objects. They may be represented by typed addresses to storage, handles, layout structures or primitive representations according to the translator profile.

There is no fundamental keyword `Struct` in the minimal source syntax.


3. Structures and Frames

3.1. Structure

A Structure is a value containing an ordered set of fields. Fields may have names. Field order is part of the logical structure and may become part of layout or signature semantics.

A Structure may contain nested Structures. Tree-shaped data is represented as nested Structures.

3.2. Frame

A Frame is a Structure with a receiver/callee name and an argument Structure.

Example source:

    f(a, b, c)

Generic logical form:

    Frame(
      name(f),
      args(
        field0(a),
        field1(b),
        field2(c)
      )
    )

In ordinary prose this document may write `f(a, b, c)` as a Structure or Frame. The exact internal representation is implementation-defined as long as receiver semantics are preserved.

3.3. Structures Do Not Execute Themselves

A Structure is data. It may describe code, a call, a model, an expression, a relation, a query or a configuration. It does not execute merely by existing.

Execution starts only through explicit receiver/subroutine consumption, for example:

    compileCallFrame(frame)
    evalExpression(expr)
    call(subRef, args)
    registerOperator(frame)
    query(relationFrame)

A callable reference is also data until explicitly called or consumed by a receiver that calls it.

3.4. Identifiers, Exact Quoted Identifiers, Numeric Literals and Strings

Lingvamyxa distinguishes convenient bare identifiers, exact quoted identifiers and text/string literals. This distinction is required because whitespace and comma may separate fields or format source, semicolon may terminate open short forms or act as an explicit separator/trailing marker, dots define vertical structure, and external systems such as SQLite may contain identifiers that would collide with Lingvamyxa syntax.

3.4.1. Numeric Literals

Numeric literals use the ANSI C / C99 numeric literal model.

Examples of integer literals:

    0
    123
    0123
    0x7B
    123u
    123UL
    123ll
    0xffULL

Examples of floating literals:

    1.0
    .5
    1.
    1e9
    1.25e-3
    1.0f
    1.0L
    0x1.8p+2
    0x1p-4

The source numeric lexer follows the ANSI C / C99 shape of integer and floating constants. In ordinary physical short-line tail form, whitespace separates numeric literal fields:

    print: 1 2 3

normalizes as:

    print(1, 2, 3)

Comma is an ordinary explicit field separator, like whitespace without indentation effects. It may separate fields inside an open short tail and may act as optional conventional notation for data or as a trailing marker. Semicolon is the explicit scan-depth separator that can terminate an open short form.

3.4.2. Bare Identifiers

The first ordinary Lingvamyxa identifier form is the convenient bare form.

A single bare identifier word uses the ANSI C identifier shape in the portable core profile:

    [A-Za-z_][A-Za-z0-9_]*

Examples of bare identifiers:

    PlantBed
    branch
    very_long_name

Bare identifiers do not contain spaces. A source spelling such as:

    red apples

is not one bare identifier in the portable profile.

Use an exact quoted identifier for a name that contains spaces:

    `red apples`
    `estimate harvest`
    `2 dim example`

Inside exact quoted identifiers, the spelling is preserved exactly except for the defined quote-escaping rule.

By contrast, numeric-looking text outside backticks is tokenized as numeric literals and split by the ordinary short-tail whitespace rule:

    1 2 3

normalizes as:

    fields `1`, `2`, `3`

Therefore:

    stack: PlantBed `2 dim`

has two fields:

    PlantBed
    `2 dim`

The first bare form is intentionally narrower than SQLite-style exact quoted identifiers. If an identifier contains whitespace, punctuation, operator characters, dots, commas, leading/trailing spaces, repeated spaces that must be preserved exactly, newlines, an empty spelling, or any spelling that must round-trip byte-for-byte through an external schema, use the second identifier form: an exact quoted identifier.

3.4.3. Exact Quoted Identifiers

The second identifier form is the exact quoted identifier. It is intended for SQLite names, external schemas, generated bindings, multi-word names and unusual names that are not representable as bare Lingvamyxa identifiers.

An exact quoted identifier is delimited by backtick characters and follows the
SQLite-compatible grave-accent identifier rule:

    `exact name`

It starts with a backtick, preserves raw identifier content, treats two
consecutive backticks as one literal backtick, and terminates at a backtick that
is not part of such a doubled pair. It is a namespace identifier/name, not a
text/string literal. Its contents are taken as the exact identifier string after
backtick-pair unescaping. No whitespace normalization is applied inside
backticks. Commas, dots, spaces, physical line breaks, indentation after those
line breaks, numeric-looking text, reserved words and operator characters inside
the backticks are part of the identifier.

The NUL character U+0000 is not valid inside an exact quoted identifier. This
follows the SQLite tokenizer model for grave-accent quoted identifiers. A source
file containing a NUL byte before the closing backtick is a syntax error, not an
identifier containing an embedded zero character.

Examples:

    `a,b`
    `x.y`
    `return`
    `1 2`
    `a  b`
    `line
        continued`
    ``

Inside an exact quoted identifier, two consecutive backticks represent one literal backtick character:

    `a``b`

names the exact identifier:

    a`b

Therefore:

    int: `a``b`
    `a``b`: 10

Declares and updates the binding whose exact name contains a literal backtick.

Exact quoted identifiers behave as atomic name tokens in head position, tail/name position and expression/name position.

Physical newlines inside an exact quoted identifier follow SQLite-style quoted identifier behavior: the newline is ordinary identifier content, not source-level syntax. The physical line break and any spaces or tabs after it are preserved in the exact identifier value. Source levels, comments, delimiters, cutters and ordinary structural syntax are not recognized until the closing backtick is reached.

Example:

    `line
        continued`

names an exact identifier containing one newline followed by eight spaces before `continued`.

3.4.4. Text/String Literals

Text/string literals use ANSI C / C99 string literal syntax. They are values, not identifiers.

An ordinary double-quoted string literal does not admit an unescaped physical newline. A physical newline before the closing double quote is a syntax error unless it is removed by the ANSI C backslash-newline line-splicing rule. Lingvamyxa does not add any separate source-level string wrapping or implicit adjacent-string concatenation rule.

The only physical-line continuation for an ordinary double-quoted string is the ANSI C / C99 one: a backslash immediately followed by the physical line ending is deleted before string-literal tokenization. While the lexer is inside the string literal, the following physical line is not treated as a new source-level line. Any spaces or tabs physically written after the spliced line ending are ordinary string-literal characters under the ANSI C / C99 rules.

Examples:

    "hello"
    "line one\nline two"
    "tab\tseparated"
    "quote: \""
    "backslash: \\"
    "question: \?"
    "alert\a backspace\b formfeed\f newline\n carriage\r tab\t vertical\v"
    "octal A: \101"
    "hex A: \x41"
    "lambda: \u03BB"
    "grinning face: \U0001F600"
    L"wide text"

Column-0 continuation example:

"physical\
line break"

The backslash-newline in that example is C line splicing and does not contribute a newline character. The value is the same as `"physicalline break"`. A real newline character inside the value must be written through an escape such as `\n`, or through the block string form below.

The string spelling, escape rules and backslash-newline line splicing follow the ANSI C / C99 string-literal model. Lingvamyxa does not use C99 adjacent string-literal concatenation as a source-level list shorthand. Adjacent string literals are separate values unless an explicit receiver later consumes and concatenates them.

After the closing double quote of a text/string literal, the next source character must be a field boundary: horizontal whitespace, a physical line break, comma/semicolon, `(`, `)`, or the end of the source item. Any other following character is a missing-separator syntax error rather than implicit string concatenation.

In ordinary physical short-line tail form, adjacent string literals are separate fields separated by whitespace or comma. Comma adds another field to the open short tail. Semicolon terminates the open short form. When no short form is open at the current scan depth, comma may act as optional conventional notation for data, and semicolon may act as an explicit source-item separator or trailing marker. This makes manual table and list declarations compact without using C99 adjacent string-literal concatenation.

Examples:

    print: "hello" "world"

is equivalent to:

    print("hello", "world")

And:

    []: labels
    . "red" "green" "blue"
    . "cyan" "magenta" "yellow"

contains two row-like child Structures whose string values are separated by whitespace.

The hexadecimal escape `\x...` consumes hexadecimal digits according to the C string-literal rule. Octal escapes consume up to three octal digits. Universal character names `\uXXXX` and `\UXXXXXXXX` are literal character escapes.
The double-quoted string form is separate from exact quoted identifiers. Therefore:

    "hello"

is a text value, while:

    `hello`

is the exact identifier/name `hello`.

3.4.4.1. Python-Like Triple-Quoted Text/String Literals

Lingvamyxa also supports Python-like triple-quoted text/string literals. They are ordinary atom tokens, not source-level fence blocks:

    """text"""
    '''text'''

A Python-like string starts with exactly three double quotes or exactly three single quotes in ordinary token position. It closes at the next matching run of exactly three opening-quote characters. Longer same-quote runs inside the literal are content by the quote-run shortening rule below. It may appear inline, inside a short form, inside a parenthesized form or as a vertical child item with ordinary source-level indentation.

Physical line breaks inside the literal are string content. Source levels, `#` comments, colons, commas, parentheses, dash delimiters, tail cutters and other structural syntax are not recognized inside the literal before the matching closing delimiter is reached. For the surrounding structural parser, the whole literal is one source item even when it crosses physical lines; those internal line breaks do not create outer source-level/layout events. If the closing delimiter is followed by a field boundary and another token on the same physical closing line, that following token continues the surrounding field sequence.

This literal form is not an ANSI C / C99 string and does not use ANSI C / C99 escape decoding. Its purpose is readable multi-line raw text with no backslash escaping.

This literal is a length-based raw source payload, not a null-terminated C string. A physical U+0000 / NUL byte inside the literal is ordinary content and does not terminate the source item. Consumers that interpret the payload as UTF-8, UTF-16, UTF-32 or another representation must do so explicitly.

Inside a Python-like string, backslash is an ordinary character. `\n` is two characters, backslash and `n`; `\t` is two characters, backslash and `t`; `\"` is two characters, backslash and double quote; `\'` is two characters, backslash and single quote.

The only delimiter-writing rule is quote-run shortening for the same quote character that opened the literal:

    Source run      Parser/value meaning
    " or '          ordinary raw character
    "" or ''        ordinary raw characters
    """ or '''      closes the matching Python-like string
    """" or ''''    content containing one fewer quote character
    N >= 4 quotes   content containing N - 1 quote characters

The opposite quote character is always ordinary raw text. For example, single quotes inside a `"""..."""` literal do not need this rule, and double quotes inside a `'''...'''` literal do not need this rule.

A physical line break written directly inside the literal is decoded as a newline character after source newline normalization.

Examples:

    text: """line one
    line two # not a comment
    line three: not a frame"""

    text: '''single-quote form
    four quotes produce three: ''''
    still text'''

The opening and closing triple delimiters are part of the preserved source spelling at P0. Value decoding belongs to the literal/value layer above P0 and uses the quote-run rule above. After the closing triple delimiter, the next source character must be a field boundary: horizontal whitespace, a physical line break, comma/semicolon, `(`, `)`, `[`, `]`, or the end of the source item.

This form is different from the column-0 block string fence below. It does not create or close a source-level block by itself. For example, as a child of a frame it still needs an ordinary child level:

    doc:
    . """text child
    still text"""
    end: doc

3.4.4.2. Character Constants

Single-quoted ANSI C / C99 character constants are numeric values. They are not text/string literals and not identifiers.

Examples:

    'A'
    '\n'
    '\101'
    '\x41'
    L'A'

The spelling and escape rules follow the ANSI C / C99 character-constant model, including the backslash-newline line-splicing rule before tokenization. The resulting value is numeric. Multi-character constants, wide character constants and implementation-defined details follow the selected ANSI C / C99 L1 profile. After the closing single quote of a character constant, the next source character must be a field boundary: horizontal whitespace, a physical line break, comma/semicolon, `(`, `)`, or the end of the source item.

A source line whose entire column-0 content is a run of three through 80 `=` characters is a block string fence.

3.4.4.3. Block Text/String Literals

Lingvamyxa also has a block text/string literal form. It uses the same fence-matching algorithm as raw file comment blocks, but the fence character is `=`.

A block string fence is a run of equals characters:

    ===
    ====

A block string fence is recognized only when the physical line begins at column 0 with a run of `=` characters of length 3 through 80, and the rest of the fence line contains only optional spaces or tabs before the line ending. No source item, title text or line comment is allowed on the opening or closing fence line.

The opening fence records the exact run length, exactly like a raw file-comment fence records the `*` run length. The block string is closed only by a column-0 fence line with the same `=` run length. A fence-looking line inside the block whose run length does not match the opener is ordinary string content, not a nested opener and not a closer.

The opening and closing fence lines do not contribute characters to the string value. The physical lines between them are the string content. Physical line breaks between content lines are preserved as newline characters after source newline normalization. Source levels, comments, operator/expression structures, closing forms and ordinary structural syntax are not recognized inside the block string content.

The non-ANSI-C text forms `"""..."""`, `'''...'''` and `===...===` are raw text
forms. They do not use ANSI C escapes, line splicing or adjacent string
concatenation. The two inline triple-quoted forms have exactly one delimiter
content rule: a same-quote run of length N greater than 3 contributes N - 1 quote
characters to the decoded value. The column-0 `=` block string has no quote-run
shortening rule; all content lines between the matching fence lines are raw text
after source newline normalization. These raw text forms are length-based source
payloads: a physical U+0000 / NUL byte is ordinary content, not a terminator.
Because they are length-based raw payloads, all three raw text forms may carry
payloads intended for any explicitly selected text representation, including
UTF-8, UTF-16 and UTF-32. The structural parser records the source bytes and the
surrounding Structure; the receiver/profile that consumes the value decides how
to interpret, validate or transcode those bytes. Encoding words such as `utf8`,
`utf16` and `utf32` are ordinary structural metadata, not special P0 syntax.

Examples with an explicit storage-width marker and an encoding receiver:

    @: u32 utf32:
    ===
    текст utf32
    ===

    @: u16 utf16: '''текст utf16'''
    @: u32 utf32: """текст utf32"""

The same idea can be made clearer by naming the value model explicitly:

    String: u32 utf32:
    ===
    текст utf32
    ===

    String: u16 utf16: '''текст utf16'''
    String: u32 utf32: """текст utf32"""

In these examples the raw text value is a field of the innermost encoding frame
(`utf16` or `utf32`). For example, in `String: u16 utf16: '''текст utf16'''`
the raw literal is the implicit level N + 1 body field of `utf16`. A following
ordinary source item at level N closes that short-form tail by the normal
source-level cut rule. A column-0 `===` block string fence does not itself
change the source level; it only supplies the raw value for the currently open
receiver body.

Examples:

===
line one
line two
===

is one text/string literal whose value contains a newline between `line one` and `line two`.

Example with a longer fence:

====
This line may contain === without closing the block.
====

This is a source-level fence form. The rule is the same fence principle as raw file comments: the fence must begin at column 0, the opening fence line is pure fence, and the closing fence must have exactly the same run length as the opening fence.

3.4.4.4. MIX Mark-Based String Templates

Curly-brace marks inside text/string payloads provide a passive MIX analogue of
string templates. They are internal payload marks first, not automatic runtime
substitution.

Example:

    SQL: "select * from users where id = {userId}"

MIX scanning may record `{userId}` as an internal mark, placeholder or interval
event inside the string payload. An editor or document consumer may highlight it
according to the selected string profile, such as SQL, JSON, regular expression
text or Lingvamyxa source text. This recognition does not evaluate `userId`,
does not read variables and does not change the string value.

Internal payload marks have their own isolated marker table and namespace. They
are visible to consumers that inspect the string under a selected profile, but
they are not mixed into the surrounding source-level active MIX table unless an
explicit consumer profile defines such a projection.

Substitution or binding happens only when an explicit receiver consumes the
string under a profile that defines that behavior. For example, a SQL receiver
or driver may consume the string as a parameterized query, bind `userId` as an
argument and apply the driver-specific escaping, encoding or binary parameter
rules. The internal MIX mark only identifies a potential placeholder; the
receiver decides whether it is meaningful and how it is consumed.

This keeps string payload interpretation passive by default. The same source can
be inspected, highlighted and formatted safely, while execution, substitution or
transport binding requires an explicit consuming receiver.

4. Surface Forms and Normalization

4.0. Colon as Receiver-Valence Marker

The colon `:` is the mandatory visible head/tail marker of Lingvamyxa surface syntax. It is required because it makes source navigation and tooling simple, but it does not by itself assign semantic meaning to the head. The head role is positional: the head is the source item before the following argument Structure. The colon is not an assignment operator, not a YAML-like key-value separator and not a special type-annotation symbol.

General form:

    head: tail

Source meaning:

    the head governs the following argument Structure;
    the tail supplies the fields consumed by that head.

The parser could identify the head by this position, but the source spelling keeps
the colon as explicit punctuation so humans, editors, formatters and simple
tools can see the head/tail boundary without receiver-specific knowledge.

In receiver terminology, `head` is a receiver, operator, callable, constructor, updater, model receiver, message receiver or other consuming head. The parser builds the generic Structure; the active receiver signature later assigns semantic roles to its fields.

The colon itself does not evaluate the tail. It only creates the head/tail frame.
The following argument Structure may later be consumed as values, an expression,
an executable body, a tuple, model data, configuration data or another
receiver-defined role. A nested Structure in the tail is still a Structure unless
the active receiver explicitly consumes that field in a mode that executes,
translates or otherwise interprets it.

In linguistic terminology, this colon may be described as a valence colon or a marker of government/rection. It marks a predicate-argument frame: the left side is the governing predicate/head, and the right side or the following vertical children are its actants/arguments. The predicate/head status still comes from position and receiver consumption, not from a separate colon-specific semantic operator.

Therefore:

    fn: ...
    if: ...
    return: ...
    int: ...
    stack: ...
    []: ...
    model: ...
    operator: ...

all share the same structural rule. They differ only in the receiver that consumes the Structure and in the receiver signature that interprets its fields.

A form such as:

    x: value

is not primitive assignment by syntax alone. After name resolution, it may be a local binding update, a receiver consumption, a callable invocation/update, a message-like consumption, a model/configuration entry or another receiver-defined operation. The colon only says that `x` governs and consumes the following Structure.

A form such as:

    Type: x

is not a separate declaration grammar. It is the same receiver-valence form: the registered `Type` constructor receiver consumes the raw name `x` in declaration context and introduces a typed binding.

A form such as:

    name: Alice

is not a YAML key-value pair by syntax alone. It is the receiver/head `name` consuming the argument field `Alice`; a model/configuration receiver may later interpret that child Structure as a semantic field.

Compact call form and colon form are two surface ways to build Frames/Structures. The compact form makes the bounded argument list explicit with parentheses. The colon form makes the governing head explicit through valence/government and then uses the short tail or vertical source-level children as its argument Structure. There is no semantic "flat field" after `:`, `(` or a source-level increase: fields are always fields of the current Structure. In a dump, `Frame head=f body=Structure ...` means the named frame `f` owns that argument Structure.

Syntactically anonymous Structures are not semantically ownerless. Every
Structure is reached through a parent edge: a receiver body, a declared argument
position, a positional argument index, a rest/list argument, an array index, a table
row, a document root or another consumer-defined edge. That edge gives the
Structure its semantic identity. For example, in `token: (@ lock)`, the bounded
Structure `(@ lock)` is still an argument of the `token` Frame. A receiver or
function signature may consume an ordinary argument named exactly `name`; some
receivers also define their first positional field as their `name` argument.
The value of that argument is used as the visible semantic name / close target
only if it is a single atom accepted by the close-name table. This table is much
broader than the executable namespace: it may store identifiers, exact quoted
identifiers, strings, operators or other literal atoms, because its only job is
to make `end: <name>` readable and checkable. If the argument does not pass that
structural check, it is treated as absent for close-target selection, and the
whole Structure defaults to the receiver/head name, such as `token`. This target
category is structural, literal and is compared by atom equality; it is not
computed through ordinary namespace evaluation. Other consumed fields get their names
from declared argument positions; repeated or variadic positions have that
argument name plus a positional index.

In L2, consumed arguments are expected to be named by the active receiver,
function, subroutine, operator or generated lowering rule. A consumed field
therefore has a name, or a name plus an index for repeated/variadic positions.
When L2 lowers to L1 / ANSI C, the same semantic identity may become a C formal
parameter name, a generated temporary name, a generated indexed field name or an
implementation-only argument descriptor; this is a lowering choice, not a
different source syntax.

4.1. Compact Call Form

Compact call form:

    f(a, b, c)

It creates a Frame named `f` with one logical argument Structure containing three positional fields.
The comma is an ordinary explicit field separator in compact and short forms.
It behaves like whitespace as a token separator, but it does not carry
indentation/source-level meaning. The semicolon `;` is the explicit scan-depth
separator/trailer: inside an open short form it terminates that short form.
This is useful before a following block string:

    include: "<direct.h>";
===
...
===

Normal form:

    f(
      field0(a),
      field1(b),
      field2(c)
    )

4.2. Line Command Form

Line command form:

    f: a b c

It creates the same logical Frame as:

    f(a, b, c)

The token before `:` is the head identifier or symbolic head. The tail after `:` is the line argument Structure. In an ordinary physical short line, whitespace separates fields inside that Structure. A physical newline separator in an open short form performs the short-form level step from the implicit argument level N + 1 back to the form's source level N, but it is not by itself the trailer of the short form. The following source item determines whether the frame continues with vertical fields or is complete. If a line command already has inline fields and the next source item is written at the child level, the level step N -> N + 1 opens a Structure field of the same short-form argument sequence, so `receiver: value` followed by an indented body is structurally the same body boundary as `receiver: value (body)`. If the line command opens a bounded continuation, such as `fn: i(`, the matching close of that bounded Structure terminates the open continuation and the parser then resumes according to the surrounding line/block rules.

Bare heads do not contain spaces in the portable profile. A receiver/procedure name or entity name that contains spaces must be written as an exact quoted identifier.

Examples:

Canonical source-level notation:

L2:
. []: `1 dimension variable`
. . 1 2
. . 3 4
. []: `2 dimension variable`
. . []: 1 2
. . []: 3 4
end: L2

Relaxed indentation notation with an explicit same-level separator:

L2:
    []: `1d variable`
      1 2
      3 4
    ---
    [][]: `2d variable`
      []: 1 2
      []: 3 4
---

Relaxed indentation notation with a canonical dotted delimiter spelling at the sibling level:

L2:
    []: `1d variable`
      1 2
      3 4
 .  ---
    [][]: `2d variable`
      []: 1 2
      []: 3 4
---

Relaxed indentation notation relying on the dedent from row level back to L2-child level:

L2:
    []: `1d variable`
      1 2
      3 4
    [][]: `2d variable`
      []: 1 2
      []: 3 4
---


The head is the `[]` or `[][]` receiver/procedure. The first inline tail field is the exact identifier naming the array value. The vertical lines are child fields of that frame.

In the one-dimensional examples, `1 2` and `3 4` are sibling row/value items. A deeper line under `1 2` would be invalid unless `1 2` were written as a Structure-opening item; scalar/value rows do not become heads merely because a deeper line follows them.

In the relaxed examples, `[][]:` is a sibling of the preceding `[]:` under `L2`. The optional middle delimiter must therefore be written at the same source level as those sibling array frames. It may be written as a relaxed dash-fence line with the same indentation, or as a delimiter line whose leading zone contains one canonical dot, such as ` .  ---`. A root-level dash-fence line there would close/cut at the `L2` level instead of merely separating the two array declarations.

4.2.1. Whitespace Short-Tail Rule

In ordinary physical short-line tail form, horizontal whitespace separates fields inside the current open short form.

Example:

    head: arg0 arg1 arg2

normalizes as:

    head(arg0, arg1, arg2)

Multi-word names are exact quoted identifiers. Therefore:

    stack: PlantBed `2 dim`

normalizes as:

    stack(PlantBed, `2 dim`)

where `2 dim` is one exact identifier field.

When a short colon-form is open at source level N, its argument fields live at the implicit argument level N + 1. Inline tail fields on the same physical line are simply the first fields at that implicit argument level.

Parser event view for a short colon-form opened at source level N:

    syntax/event                          atomic level effect          structural effect
    head:                                 N -> N + 1                   opens the short argument Structure
    horizontal whitespace                 no level change              separates neighboring fields
    physical newline separator            N + 1 -> N                   delimiter only; not a trailer
    following source item at N + 1         N -> N + 1                   continues the same short form as a new field
    following source item at N             visible item/trailer at N    completes the short form; the item is a sibling
    following admitted tail-cutter         tail-cutter-specific         may close the admitted target
    comma                                 no level change              separates neighboring fields
    semicolon                             scan-depth trailer           completes the current open short form immediately
    matching ) or ]                       bounded-context trailer      closes the bounded form and any open short form inside it

The important point is that the parser watches source-level changes, not
physical source lines as containers. Physical newline in a short form performs
the N + 1 -> N step, but that step alone does not complete the form: the
following source item/trailer does. If the following source item is written at
N + 1, the parser observes the atomic down/up sequence N + 1 -> N -> N + 1.
That source-level increase opens a Structure boundary instead of merging the
vertical item flatly with the previous inline field sequence.

This rule is intentionally asymmetric. Any atomic source-level increase opens a
Structure, because a deeper source level is already a visible request for a
nested object. Closing is not triggered by a bare separator in the same way:
the close needs a following source item, a visible source-level marker,
semicolon, `)` or an admitted tail-cutter. This preserves one shared mechanism for
anonymous block separation with the minimum number of logical markers while
still allowing many surface forms. In particular, after a short form has
accepted a vertical block as one of its arguments, there are few remaining
logical anchors, but the down/up level event is explicit enough to identify the
next structural field unambiguously.

The same mechanism gives short colon-form three common writing modes. These are
style modes over the same source-level machine, not three separate grammars.

1. Mostly-inline argument spelling:

    receiver: arg0 arg1 arg2

2. Mostly-vertical argument spelling, useful when the argument list is too long
   for one readable line:

    receiver:
    . arg0
    . arg1
    . arg2

3. A short header followed by block or positional argument Structures. This is
   useful when the first fields name/configure the receiver and the remaining
   tail is naturally written as a body:

    fn: test (int: arg) (int)
    . body
    . body
    end: test

   The existing `match: value` examples in the anonymous-branch and shorter
   positional sections below show the same mode used both with visible nameless
   block arguments and with a direct positional argument stream.

Physical newline is not a short-form trailer. It only performs the short-form
separator step described above. The source level of the following non-empty
source item decides whether the current short form continues or closes:

    next item at N + 1  -> another argument field of the current short form
    next item at N      -> the current short form is complete; the next item is a sibling
    next item below N   -> the current short form is complete and ordinary level-close rules apply
    next item deeper than N + 1 -> valid only if the preceding field can own that deeper level

If the last field of a short tail is itself a colon-form, that nested colon-form
is the current open continuation target for the corresponding deeper source
level. Therefore a compact nested spelling may be continued vertically:

    L1: utf8:
    ===
    raw text
    ===

normalizes like the explicit vertical spelling:

    L1:
    . utf8:
    ===
    raw text
    ===

In both cases the block string is a field of `utf8`, not a sibling of `L1`.

Comma is different from physical newline because it is only an explicit field separator. It does not terminate the current open short form:

    head: arg0, arg1

normalizes as `head(arg0, arg1)` in ordinary short-tail form. The following `arg1` remains a field of the same short-tail Structure.

When no short form is open at the current scan depth, comma may be ordinary conventional separator notation or a trailing marker. Therefore `(a b c)`, `(a, b, c)` and `(a b c,)` may produce the same three data fields.

Semicolon is the explicit short-form separator/trailer:

    head: arg0; arg1

does not normalize as `head(arg0, arg1)`. The semicolon terminates `head(arg0)`. The following `arg1` is parsed as the next item at the current scan depth. A later receiver/profile may reject that neighboring item if a value item is not meaningful there, but it is not a short-tail field of `head`.

A receiver may later interpret an identifier field as a name, signature, selector, atom, message name or another semantic object. The parser only builds the field.

4.2.1.1. Short-Form Trailer Rule

A short colon-form is a physical source-item form.

A physical source line may contain several source items when an earlier short form is closed by semicolon. A short colon-form may appear anywhere a Structure field/source item may appear, including inside another short form, inside a bounded Structure and inside an anonymous/block Structure.

Examples:

    call(int: a b; ret: int)

normalizes as a compact `call` Frame whose bounded argument Structure contains two neighboring short-form Frames:

    call(int(a, b), ret(int))

And:

    call(int: a; b)

normalizes as:

    call(int(a), b)

The semicolon after `a` terminates `int: a`; it does not add `b` to the `int` tail.

The same rule applies outside parentheses:

    print: a b; c

normalizes as two neighboring items at the current scan depth:

    print(a, b)
    c

Here `c` is not an argument of `print`. Its later validity depends on the surrounding receiver/profile and statement/value position.

Physical newline alone does not close a short form. In a short form, the
newline separator changes the current short-form level from N + 1 back to N,
but the visible completion is caused by the following source item/trailer at N
or below, not by the newline character itself. If the following source item is
again at N + 1, the short form continues and the atomic N -> N + 1 step opens
a new Structure field in the same argument sequence. Semicolon closes the
current open short form immediately. A matching `)` or `]` closes the current
bounded/compact form; if a short form is still open inside that bounded form,
the short form is completed as part of closing the bounded context. Comma
remains an ordinary field separator inside the short form.

Example of continuation by implicit argument level:

ShortForm1: 1 ShortForm2: 2
. . ShortForm2_arg2
. ShortForm1_arg3
---

normalizes structurally as:

ShortForm1(
    1,
    ShortForm2(
        2,
        ShortForm2_arg2
    ),
    ShortForm1_arg3
)

This is valid but intentionally hard to read. Prefer clearer vertical or bounded spelling when nested short forms are not visually obvious.

4.2.2. Operator Tokens and Compact Operator-Looking Spellings

Whitespace separates short-tail fields. The core structural parser keeps
operator-looking spellings in the same structural token stream as ordinary
fields.

Operator spellings such as `+`, `-`, `*`, `/`, `%`, `=`, `!=`, `<`, `<=`, `>`, `>=`, `&&`, `||`, `!`, `~`, `&`, `|`, `^`, `++`, `--`, `[` and `]` are not valid bare namespace identifiers in the portable profile. The parser classifies them as operator-token fields. An operator-token field is not a head/name frame and does not require the colon marker that ordinary head/frame forms require.

The structural parser does not decide whether an operator token is prefix,
postfix or infix. That role is assigned by the active receiver/operator profile.
For the C-profile L2 operator categories, see section 20.3.

Example:

    print: 1 + 2

normalizes structurally as:

    print(1, +, 2)

Here `1` and `2` are value fields. Because there is no colon after `1`, `1` is not a receiver/head. The token `+` is an operator field. A later receiver/operator consumer may interpret `+` as an infix operator and consume the neighboring fields from the Structure as its left and right operands.

Whitespace remains structural field separation:

    print: a + b c

normalizes as:

    print(a, +, b, c)

A compact spelling chunk such as:

    print: a+b c

normalizes structurally as:

    print(a, +, b, c)

The compact non-quoted chunk `a+b` contains a character that is not valid inside
a bare identifier, so P0 splits it as if `+` had token boundaries around it. The
token `+` is simply an operator-token field, and a later receiver/operator
consumer may consume neighboring fields according to the active profile.

To keep an operator-looking spelling as an exact name, use an exact quoted identifier:

    print: `a+b`

To make grouping explicit at the structural layer, use a bounded Structure:

    print: (a + b)

The bounded form produces one Structure field containing the spellings `a`, `+` and `b`; expression meaning is assigned later by the consumer.

4.2.3. No Hidden Receiver-Signature Grouping

Line command form does not infer hidden nesting from receiver signatures.

Critical rule:

    print: getTypedValue values[i]

normalizes as:

    print(getTypedValue, values[i])

It does not normalize as:

    print(getTypedValue(values[i]))

Explicit nesting must be written with parentheses, compact Frame form or vertical anonymous Structure form.

If a receiver argument must itself be one Structure, the source must make that nesting explicit with a bounded Structure, compact Frame or anonymous vertical Structure.

Examples:

    args: int(v, j)

This gives `args` one compact declaration Frame `int(v, j)`.

The following is also valid. It gives `args` one bounded Structure containing the short-form Frame `int(v, j)`:

    args: (int: v j)

The vertical source form is equivalent at the Structure level:

    args:
    . int: v j

A head followed by `:` must have a continuation. The continuation may be an inline tail on the same physical line, vertical child fields at source level N + 1, or an explicit close through `end: <target>` when allowed by the open target policy. A line `head:` with no inline tail and no following vertical child fields is a syntax error unless the receiver/profile explicitly defines an empty Structure form for that head.

A line without `:` is not a non-nullary receiver call. In executable statement position, a bare receiver/callable line is valid only when the resolved binding can be consumed with zero arguments. This includes registered nullary line operators such as `return`, `break` and nullary `continue`, registered nullary receivers, and visible `fn`/`sub` bindings whose signature has zero required arguments.

A bare atom/expression line may still appear as a value item inside a Structure; the consuming receiver decides whether that value names a callable body, a symbol, a type, a branch placeholder or something else.

4.3. Vertical Frame Form

Vertical frame form:

f:
. a
. b
. c
end: f

It creates a Frame named `f` with the same logical argument Structure as:

    f(a, b, c)

The explicit close is an ordinary receiver form `end: f`. Closing validation is defined in section 7.5.

A compact first field may still appear in the opening line:

    f: a
    . b
    . c
    end: f

This creates:

    f(a, b, c)

The inline tail contributes initial fields. The vertical child lines at level N + 1 contribute following fields.

A physical newline ends the physical source line, but it is not a short-form trailer. If the following source item is at level N + 1, it continues the open frame's logical argument Structure. If the following source item is at level N or smaller, the open frame is complete and ordinary sibling/close rules apply.

Do not confuse the logical argument Structure of a Frame with semantic arguments declared by a receiver. For example, the fields of an `fn` frame are fields consumed by the `fn` receiver; they are not automatically formal parameters of the function being defined. The `fn` receiver later classifies its fields as function name, formal parameter Structure, single-value return type and executable body fields. The related `fm` receiver uses a return-description Structure for multiple return.

4.4. Parenthesized Bounded Structure

Parentheses create a bounded Structure:

    (a b c)

Inside parentheses, bounded elements may be separated by whitespace, by physical newline/source-level composition, by comma, by semicolon, or by the matching closing parenthesis. Comma is not required for ordinary bounded fields and does not close an open short form. When no short form is open at the current scan depth, comma is optional conventional notation for simple data fields and may leave the same field sequence as whitespace separation:

    (a b c)
    (a, b, c)
    (a b c,)

For short colon-forms, semicolon carries structural load because it terminates the current open short form. This rule is universal; it is not specific to parenthesized Structures.

Parentheses do not disable the source-level system. Vertical child items inside parentheses are still written with dots. Inline short colon-forms are also allowed inside parentheses:

    call(int: a b; ret: int)

The semicolon terminates `int: a b`, then `ret: int` starts the next source item inside the same bounded Structure. The vertical spelling remains valid:

    call(
    . int: a b
    . ret: int
    )

In `call(int: a b)`, the closing `)` terminates the short form `int: a b` and closes the bounded argument Structure of `call`.

When a bounded Structure continues after a physical newline, the next physical
line must remain inside the bounded Structure. In canonical dotted notation it
must be written at the deeper dotted level. In relaxed notation it must use a
deeper indentation column than the line that opened the bounded form. The only
ordinary exception is the closing line itself: a line whose next source token is
the matching `)` or `]` may return to the level of the line that opened the
bounded form, because that token closes the bounded Structure rather than
continues it. The following is valid:

    value (1
    . +
    . 1)

and the relaxed spelling of the same source-level tree is:

    value (1
        +
        1)

The following is invalid because the `+` continuation returns to the owner
level before the matching `)`:

    value (1
    +
    1)

Bare identifiers are single tokens. Exact quoted identifiers are atomic name tokens and may contain spaces, commas, punctuation and other external spelling. Numeric literal, character constant and string literal fields in ordinary short-tail form are separated by whitespace or comma. Bounded Structures also use whitespace/newline composition for ordinary fields; comma is ordinary conventional separator notation or a trailing marker, while semicolon terminates an open short form at the current scan depth.

Example:

    if( i = 1, print(choose, hello), print(choose, world) )

Logical argument sections:

    field0 -> <expression Structure for `i = 1`>
    field1 -> (print(choose, hello))
    field2 -> (print(choose, world))

Receiver-signature roles:

    field0 -> condition
    field1 -> then
    field2 -> else

The names `condition`, `then` and `else` are not created by the parser alone. They are assigned by receiver-signature normalization for the active `if` receiver. The internal layout of the expression Structure is outside this structural-core document.

4.5. Vertical Source Levels: Canonical Source-Level Notation and Relaxed Indentation Notation

Vertical composition is source-level tree composition. Lingvamyxa has one source-level tree model and two surface notations for writing it.

The canonical source-level notation is the visible dotted notation. It is always valid and is the reference spelling of source levels. In canonical dotted notation, the leading indentation zone of a source line is the run of dots, spaces and tab characters before the first non-indentation source token. The source level of the line is the number of dot characters in that zone. Spaces and tab characters in the indentation zone are ignored for source block depth.

Examples of equal source level in canonical dotted notation:

    ....call
    . . . . call
    .	. .	.     call

Relaxed indentation notation is a readability notation over the same source-level tree. It may replace leading dots before ordinary source items with ordinary indentation. In relaxed indentation notation, the source level is computed from leading spaces/tabs before the first non-space character by the implementation's indentation-stack rule and then mapped to the same source levels used by canonical dotted notation. Internal spaces remain ordinary source characters and may still participate in exact quoted identifiers, short-tail field separation and manual alignment.

Shared source-level rule after either surface notation has been mapped to source levels:

    The parser observes a stream of source items and source-level events.
    Physical source lines are not semantic containers. The phrase "line" in
    this section names the usual visual spelling of the next source item, not a
    separate AST object.

    A source item has a source level.

    In canonical dotted notation, source level is the count of leading dots.

    In relaxed indentation notation, source level is computed from the
    leading spaces/tabs indentation stack.

    Source levels are not only indentation. All surface syntax that opens,
    continues, bounds, separates or closes a Structure participates in the
    level model. A colon short-form opens an implicit argument level N + 1.
    Inside that short-form scan, physical newline performs the separator step
    N + 1 -> N. Parentheses bound a compact Structure. Comma is an explicit
    field separator at the current scan depth. Semicolon is a trailer at the
    current scan depth. `---` and canonical dotted delimiter lines
    materialize source-level points.

    Internal spaces remain ordinary source characters and may still participate
    in exact quoted identifiers, short-tail field separation and manual
    alignment.

    An atomic source-level increase opens a Structure. A source item at a
    source level deeper than the previous structural head is a
    child item of that head.

    A following source item that returns by one source level is a level
    delimiter and closes the open structure above that level before that source
    item is parsed as an ordinary item at its own level. The separator that
    precedes it, such as a physical newline, is not the trailer by itself.
    Returning by more than one level is not a plain P0 level transition; it
    requires an admitted tail-cutter layer.

    A source-level cut is the ordinary structural trailer event. The event is
    the level transition itself, not any receiver/data written on the following
    source line.

    For a frame opened at source level N:

        source items at level N + 1 are child/body fields of that frame;
        a following source item at level N completes the open frame at level N
        and starts a sibling item at the same parent level;
        a following source item at level N - 1 completes the open frame above
        that level before the new item is parsed; larger decreases require an
        admitted tail-cutter layer.

    This rule applies to named frames, anonymous frames and executable
    definitions. A named frame does not require `end: name` merely because it
    is named. The receiver later validates whether the completed Structure is
    semantically valid.

    `end: name` is an explicit named tail-cutter. It is useful for readability,
    diagnostics and closing a long or deeply nested visible target. P0 records
    it as a tail-cutter trailer only in a valid source-level tail-cutter
    position. A tail-cutter closes only source-level/block tails; it never
    closes an unmatched parenthesized/bracketed bounded Structure. Therefore an
    `end:` at a source position that is still inside one or more unmatched `(`
    or `[` frames does not replace the required matching `)` or `]`.

    `end: name` closes a visible named target explicitly.

    `---` is an explicit source-level marker at its own source level. Like the
    canonical dotted delimiter, it materializes a source-level point without
    adding an ordinary receiver item. Open, separate and close behavior follows
    from the neighboring source levels.

This rule is not a Python-like license to hide every same-level anonymous separator in whitespace. A one-step smaller source-level line closes the open structure above that smaller level. But when two anonymous/implicit Structures must be separated at the same source level, no smaller-level line exists between them, so Lingvamyxa requires a visible same-level delimiter: a canonical dotted delimiter line or `---`.

Visible structural transition forms in the full language are:

    end: name
    return
    return: value
    ---
    a canonical source-level delimiter line
    a following source item at the same parent level
    a following source item one source level smaller

These forms belong to one closer/trailer family, but they are admitted in
different contexts:

    form                              admitted context                         closes or materializes
    source-level cut                  ordinary vertical source structure        the current open source frame by one visible level step
    dotted delimiter / ---            explicit source-level marker             anonymous same-level section boundary or level point
    end: name                         valid structural tail-cutter position     the visible target named by the receiver's close target
    return: value                     valid fn/fm terminal trailer position     runtime return plus executable source-frame close
    return                            admitted no-value executable trailer      runtime return plus executable source-frame close
    until: condition                  admitted post-condition loop position     loop body tail plus its condition

This table is not a list of competing block syntaxes. It is the shared
source-level close model with receiver/profile-specific admission rules.

Visible named Structures may be completed by the ordinary one-step source-level cut. `end: name` is the explicit named close form, normally used when a visible, checked or long-distance close is clearer than relying on the next one-step smaller-level or same-parent-level source item. Executable definitions may also be closed by an admitted terminal return form: `return: value` for a core `fn`, or bare `return` for no-value executable profiles such as `sub` or labels. Anonymous positional Structures and nameless implicit sections are closed by a one-step smaller-level source line when the source tree dedents. They are opened, separated or closed at the same source level by a canonical source-level delimiter line in canonical source-level notation or by `---` in relaxed indentation notation.

Therefore the term "dot-only line" is not a general word for all closure. It names only the canonical source-level notation for an anonymous/nameless structural delimiter. Explicit named closure is written as `end: name`.

Terminology:

    source-level cut
        A transition from the current open source item to a source point that
        cannot remain inside it: a sibling level or a surrounding level. It
        completes the current open item and any deeper open Structures before
        the new source item is parsed. The cut is observed when the next source
        item or admitted marker appears at that level. A physical newline may
        be the separator that makes the next item visually start elsewhere, but
        it is not the cut/trailer object by itself.

    trailer
        The structural completion event of an opened frame or anonymous
        Structure. In ordinary P0 source this is usually a following source
        item at the sibling/surrounding source level: the parser has observed
        that the next item cannot remain inside the open Structure. The
        physical newline separator is not the trailer. The next item's text is
        also not automatically a special trailer receiver; ordinary text at the
        sibling level is just the next item. Larger cuts are not ordinary P0
        level transitions; they require an admitted tail-cutter layer.
        Explicit forms such as `end: name` and terminal `return` become
        specialized tail-cutter trailers only in admitted source-level
        tail-cutter positions. A tail-cutter may close source-level/block
        tails, including deeply nested ones, but it does not close unmatched
        parenthesized/bracketed bounded Structures; those remain governed by
        the matching `)` or `]`. `---`
        is different: it is a visible source-level marker, not a receiver item.

    explicit source-level marker
        A visible source line, such as a dotted delimiter line or `---`, that
        materializes a source level without adding an ordinary receiver item.

A useful parser view is the head-body-trailer envelope:

    head
    body Structure
    trailer

The body Structure is the primary Structure consumed by the opened frame or anonymous positional argument. The head and trailer are structural envelope roles, not ordinary child fields of that body. For a named frame, the head is a source item such as `if: condition`, `fn: name ...` or `outerLoop:`. For an anonymous positional Structure, the head may be a canonical dotted delimiter line or a relaxed dash-fence delimiter line.

In canonical dotted notation:

    .                               # head: open anonymous positional Structure
    . . body1                       # body
    .                               # trailer of previous + head of next anonymous Structure
    . . body2                       # body
    .                               # trailer

The middle dotted delimiter line has both roles: it closes/separates the preceding anonymous Structure and, because it is followed by a deeper source item, opens the next anonymous positional Structure. A relaxed dash-fence line follows the same head/body/trailer envelope rule.

Example: ordinary source-level cut after a nested executable definition

fn: outer () (int)
    fn: inner (int: a) (int)
        return: a + 1
    int: a 1
return: inner(a)

The line `int: a 1` is at the source level of the nested `fn: inner` item. Before `int: a 1` is parsed as the next body item of `outer`, the source-level cut completes the nested `fn: inner` frame.

This is structurally equivalent to:

fn: outer () (int)
    fn: inner (int: a) (int)
        return: a + 1
    end: inner

    int: a 1
return: inner(a)

In this example, the body-level `return: a + 1` is an ordinary runtime return inside `inner`. It is not the terminal-return trailer of `inner`. The trailer of `inner` is the source-level cut before `int: a 1`.

The final `return: inner(a)` is at the source level of `fn: outer`; therefore it is terminal return for `outer`.

A source item at level N may open a frame/Structure. Its vertical child arguments are written at level N + 1.

A following source item at level N + 1 is one positional child item of the open frame/Structure at level N.

A following source item at level greater than N + 1 belongs to the immediately preceding child item only when that preceding child item is a Structure-opening item. If no such open item exists, the level increase itself materializes an anonymous positional Structure at the intervening parent level. Scalar literals and ordinary value items do not become headers merely because a deeper item follows them.

A following source item one level smaller than the current open child resumes the parent level and starts a sibling item there. That smaller-level source item makes the level delimiter visible; the physical newline before it is not the delimiter by itself. A larger decrease is reserved for an admitted tail-cutter layer. If the next item starts at the same level as the current anonymous/implicit section, use a canonical dotted delimiter line or relaxed `---` at that level.

A smaller-level ordinary item is still an ordinary item. It is not treated as a
named trailer merely because it closes deeper open structure before it is read.
For example:

.
. . block0
. . block0
. trailer_word
. . block1
. . block1
.

has three root fields: an anonymous Structure containing the two `block0`
items, the atom `trailer_word`, and an anonymous Structure containing the two
`block1` items. Because `trailer_word` has no `:`, it is not a receiver-form and
not a trailer form.

Physical empty lines are level-0 structural boundary events. They close an open
level-1 vertical tail by the ordinary source-level decrease to 0. They do not
open Structures, do not separate same-level anonymous siblings below level 1,
and do not replace a required same-level delimiter.

4.5.1. Canonical Source-Level Delimiters

A canonical source-level delimiter line is a dotted delimiter line. It contains only dots, spaces and tabs before the newline and contains at least one dot.

A canonical source-level delimiter line at level K may serve as an anonymous positional Structure delimiter at level K. When followed by source items at level K + 1, it opens an anonymous positional Structure. Otherwise it separates or closes the current anonymous/implicit section at level K.

If a canonical source-level delimiter line at level K is followed by source items at level K + 1, it opens an anonymous positional Structure at level K. That anonymous Structure is one child item of the surrounding parent Structure.

The anonymous Structure continues until the next canonical source-level delimiter line at level K, a following source item at source level K - 1, an explicit `end: <target>` in a valid tail-cutter position, terminal `return` / `return: value` where valid, or EOF.

A canonical source-level delimiter line at level K may close the previous anonymous Structure at K and, if followed by deeper items, open the next anonymous Structure at K.

Every source line written with leading dots remains valid in the relaxed language profile. A canonical source-level delimiter line may therefore still be used instead of a dash-fence line as the visible anonymous delimiter / nameless close form.

Canonical anonymous-branch example:

match: value
.
. . 1
. . print: World
.
. . 2
. . print: Hello
.
end: match

Conceptual normal form:

    match(
      value,
      (
        1,
        print(World)
      ),
      (
        2,
        print(Hello)
      )
    )

The canonical source-level delimiter lines at level 1 delimit anonymous branch Structures. No source keyword `case` (not structural syntax) is involved.

A shorter positional `match` form may avoid anonymous branch Structures:

match: value
. 1
. print: World
. 2
. print: Hello
end: match

Conceptual normal form:

    match(value, 1, print(World), 2, print(Hello))

4.5.2. Relaxed Indentation Notation and Dash Fences

Relaxed indentation notation is a readability shorthand for the same source-level tree. It replaces leading dots before ordinary source items with spaces/tabs indentation. It does not remove the requirement for visible nameless delimiters.

The simple replacement rule is:

    leading dots before source text may be replaced by indentation;
    a textless canonical source-level delimiter line must remain visible either
    as that dotted delimiter line or as a dash-fence line at the corresponding
    source level.

4.5.2.1. Relative Indentation and Bounded Continuation

Relaxed indentation is not a character-for-character replacement of dots.
Canonical dots are absolute: two leading dots always spell source level 2.
Relaxed spaces and tabs are relative to the indentation columns already visible
in the current layout scan. A first indentation column deeper than the current
column creates the next source level, regardless of whether it is one space away
or many spaces away. Adding more spaces to a whole relaxed block therefore
usually changes only the chosen column spelling, not the source level of that
block.

Inside a bounded form, such as `(...)` or `[...]`, a physical newline does not
close the bounded form and does not perform the short-form newline step by
itself. The following physical line must still be visibly inside the bounded
form: in relaxed notation it must use an indentation column deeper than the
line that opened the bounded form; in canonical notation it must use the
corresponding deeper dotted source level. Returning to the owner level before
the matching `)` or `]` is a syntax error unless the next source token on that
line is exactly that matching closer.

This rule keeps relaxed indentation and canonical dotted notation aligned. A
well-formed relaxed bounded continuation has a canonical dotted spelling with
the same source-level tree. Differences between relaxed and dotted examples are
therefore differences in the source levels explicitly written by the author,
not a special parenthesized-form exception.

A standalone dash-fence line:

    ---
    ----
    -----

at source level K is an explicit source-level marker. The dash fence is a run of `-` characters of length 3 through 80 after the leading indentation/source-level zone. It materializes level K in the source stream without adding an ordinary receiver item.

Its primary role is to make a level transition visible when ordinary indentation or dots would otherwise hide an empty structural step.

A dash-fence line performs no receiver call by itself. Its effect is derived from ordinary source-level rules:

    1. If the parser is currently inside a deeper level, the move to the dash fence at
       level K performs the ordinary one-step source-level cut/trailer for the
       open Structure above K. A dash-fence line is not a general multi-level
       tail cutter.

    2. If the following non-empty source item is at level K + 1, the dash-fence line
       acts as the visible head of an anonymous positional Structure at level
       K.

    3. If both conditions hold, the same dash-fence line separates two sibling
       anonymous Structures: it closes the previous deeper Structure and opens
       the next deeper Structure.

Therefore a dash-fence line is not a special close operator, not a special open operator and not a third independent separator syntax. It is the explicit spelling of a structural level point K. Close/open/separator behavior follows from the same source-level cut and child rules used everywhere else.

If a dash-fence line at level K is followed by source items at level K + 1, it opens an anonymous positional Structure at level K. The anonymous Structure continues until the next dash-fence line at level K, a following source item at source level K - 1, an explicit `end: <target>` in a valid tail-cutter position, terminal `return` / `return: value` where valid, or EOF.

If a dash-fence line at level K is not followed by deeper source items, it closes or cuts the current open anonymous/implicit section at that level and resumes parsing at level K.

A dash-fence delimiter line must contain no source item other than the delimiter itself. It may have leading spaces/tabs in relaxed indentation notation, leading canonical dots in canonical source-level / automatic-rewrite notation, horizontal whitespace after the delimiter, and an optional trailing `#` line comment. The `#` comment text is ignored by the structural parser, exactly like comments after ordinary source text.

A trailing `#` comment is not an exception to the dash-fence rule. It is the
ordinary line-comment syntax: after the comment is removed, the line is still a
pure dash-fence line. The intentional exception is payload text: although
worded cutters such as `end: name` may carry a target/body at the later
semantic layer, `---` never carries a trailer name or payload. Write `end:
name` when the close target must be visible; `--- trailer word` is invalid.

Valid delimiter lines:

    ---
    ----
    --- # anonymous branch delimiter
    .---
    . ---- # automatically rewritten dotted separator

Invalid delimiter lines:

    ---else:
    ----else:
    --- return: x
    --- int: x
    --- trailer word

A dash fence is not a prefix operator and cannot be combined with a receiver or any other source item on the same physical line.

A following named receiver line at the same indentation/source level may close the previous anonymous section and start the next structural item of the same parent frame. For example, `else:` at the correct level may close the preceding anonymous branch and start the named `else` branch; it does not need to be attached to `---`.

`---` may be used instead of `end: name` only when the close target is unambiguous and the receiver/profile permits a nameless close. For checked public examples and long blocks, `end: name` remains clearer.

Example with two anonymous branch Structures:

match: value
    ---
        1
        print: World
    ---
        2
        print: Hello
---

Conceptual normal form:

    match(
      value,
      (
        1,
        print(World)
      ),
      (
        2,
        print(Hello)
      )
    )

The final `---` closes the open `match` ladder without naming it. The same position could also use `end: match`.

A separator effect is just a visible down/up level transition.

For example:

if: condition
    ---
        thenBody
    ---
        elseBody
end: if

means:

    level 0: if
    level 1: explicit marker
    level 2: first anonymous body
    level 1: explicit marker
    level 2: second anonymous body

The second `---` is not a special `else` separator. It is the visible level-1 point between two level-2 anonymous bodies. It closes the first anonymous body and, because the next source item is deeper, opens the next anonymous body.

Example with four positional arguments and no anonymous branch Structures:

match: value
    1
    print: World
    2
    print: Hello
---

Conceptual normal form:

    match(value, 1, print(World), 2, print(Hello))

Example with two positional branch Structures in an `if` receiver:

if: condition
    ---
        thenBody
    ---
        elseBody
end: if

The two `---` sections are two anonymous Structure arguments of `if` after the condition.

Equivalent named-argument form in canonical source-level notation:

if: a
. then:
. . doSomething
. else:
. . doOtherThing
end: if

Relaxed indentation notation with explicit delimiter followed by a named continuation receiver:

if: condition
    ---
        # doSomething
    ---
        # doOtherThing
end: if

if: condition
    ---
        # doSomething
    else: # This "else" is at the correct level and therefore automatically closes the previous block.
        # doOtherThing
end: if

The line `else:` is at the same source level as the preceding anonymous section. It therefore closes/separates that anonymous section and starts the ordinary nested Structure `else:`. The active `if` receiver may consume `else(...)` as a semantic field. A spelling such as `---else:` is invalid because `---` must be alone on its delimiter line, except for an optional trailing `#` comment.

Example with an explicit nameless close after a nested `if`:

outerLoop:
    for: int(i, 1) (i <= 3) i++
        for: int(j, 1) (j <= 3) j++
            if: i = 2 && j = 2
                System\out\println: "--- continue outerLoop ---"
                continue: outerLoop
            ---
            System\out\println: "i: " + i + ", j: " + j
end: outerLoop

The `---` at the source level of the inner `for` body replaces the canonical source-level delimiter line:

outerLoop:
. for: int(i, 1) (i <= 3) i++
. . for: int(j, 1) (j <= 3) j++
. . . if: i = 2 && j = 2
. . . . System\out\println: "--- continue outerLoop ---"
. . . . continue: outerLoop
. . .
. . . System\out\println: "i: " + i + ", j: " + j
end: outerLoop

The shorter relaxed indentation version without this delimiter is not valid Lingvamyxa, because it hides a required nameless close in indentation alone.

4.5.3. Matrix and Nested Array Examples

Matrix-like data does not require a special table context. It follows ordinary source-level tree and line-item rules.

Canonical source-level notation example:

[]: `2 dim example`
. 1 2
. 3 4

Relaxed indentation notation example:

[]: `2 dim example`
    1 2
    3 4
---

Conceptual normal form:

    [](`2 dim example`, (1, 2), (3, 4))

The rows are ordinary child items. The ordinary short-tail whitespace rule makes `1 2` two numeric fields inside each row item.

Mixed identifier/numeric rows use the same whitespace short-tail rule:

[]: `2 dim example`
. a b
. 3 4

Conceptual normal form:

    [](`2 dim example`, (a, b), (3, 4))

Named nested rows may be written with nested `[]` frames:

[]: matrix
. []: row1
. . 1 2
. []: row2
. . 3 4
end: matrix

The close target is `matrix`, the visible entity name introduced by the frame. The close form is not `end: [] matrix`.

4.6. `end:` Close Receiver and Nameless Close

Bare `end` is not valid Lingvamyxa source syntax. The structural close operation is not bare `end` and is not `end <target>`.

The source-level named close form is the ordinary colon receiver form. It is valid in both canonical source-level notation and relaxed indentation notation:

    end: <target>

`end:` consumes its tail as a close target. The target names a visible frame, label block or entity block. This tail is a structural close operand, not an ordinary namespace expression: it is not looked up as a variable, not called, not evaluated and not available to user code as a runtime argument. The colon spelling is source syntax for a privileged structural instruction to the parser/translator validation layer.

If an opening form such as `[]: matrix` introduces the visible name `matrix`, then the close form is:

    end: matrix

not:

    end: [] matrix

The close target is not blindly the receiver/head spelling. A receiver defines
which visible target it introduces. The privileged spelling is the ordinary
argument name `name`: if a receiver consumes a valid `name` argument, that
argument value becomes the visible close target. This is why `[]: matrix` closes
as `end: matrix`, and why `fn: square ...` closes as `end: square`. If an
opening receiver has no valid `name` argument, the general named-close default
is its own head spelling, so `if: ...` closes as `end: if` and `Label: ...`
closes as `end: Label`. A receiver may explicitly define a nameless/anonymous
opening form, but that is an opt-out from named close, not the default.

`end:` may close several currently open implicit vertical levels at once, as long as the target matches a visible open target at or above the current source level and no receiver-specific rule forbids that jump. This makes `end:` a readable tail-cutter for deeply nested named vertical code.

`end:` is not the default close mechanism for all named frames. The default structural close is the ordinary source-level cut. `end:` is the explicit named form of that close. It is useful when the source wants to identify the close target directly, close across a long nested tail, or improve diagnostics and readability in long blocks.

A standalone dash-fence source line is an explicit source-level marker used primarily by relaxed indentation notation as the counterpart of a canonical source-level delimiter line. It does not consume a target and performs no receiver call by itself. When followed by source items at the next deeper level, it materializes the head of an anonymous positional Structure at its own source level. Otherwise it separates or closes the current open anonymous/implicit section at that level by ordinary source-level rules. When the current named frame allows nameless close and there is no ambiguity, a dash-fence line may close that frame as a shorter alternative to `end: name`.

Example named close:

outerLoop:
. for: int(i, 1) (i <= 3) i++
. . for: int(j, 1) (j <= 3) j++
. . . if: i = 2 && j = 2
. . . . continue: outerLoop
end: outerLoop

The final line closes the labelled block `outerLoop` directly. The intermediate vertical levels are closed by the named close.

4.6.1. Vertical Positional Structures

Some receivers expect positional Structure arguments whose semantic role is assigned by the receiver signature. Such Structure arguments may be written vertically as child items at the next source level of the open receiver frame.

Canonical source-level notation single-body example:

if: a
. doSomething
end: if

Under an `if(condition, thenBody, elseBody)` receiver signature, this builds:

    if(
      a,
      (
        doSomething
      )
    )

The name `thenBody` is assigned by the `if` receiver signature. It is not a surface keyword in this form.

Relaxed indentation notation:

if: a
    doSomething
end: if

Two-body positional example using relaxed anonymous sections:

if: a
    ---
        doSomething
    ---
        doOtherThing
end: if

Under the same `if(condition, thenBody, elseBody)` receiver signature, this builds:

    if(
      a,
      (
        doSomething
      ),
      (
        doOtherThing
      )
    )

The same branches may also be written as explicit named argument Structures:

if: a
. then:
. . doSomething
. else:
. . doOtherThing
end: if

or in relaxed indentation notation:

if: a
    then:
        doSomething
    else:
        doOtherThing
end: if

The names `then` and `else` are ordinary nested Structures consumed by the active `if` receiver as semantic fields. They are not global reserved words. If the first branch is written in named form, following branches in that same argument sequence must also be written in named form according to the named-argument ordering rule.

A one-line form is also possible when the receiver defines it:

    if: a doSomething

This builds a Frame whose final meaning is assigned by the active `if` receiver.

A receiver call has one logical argument Structure. A source form that appears to pass several arguments and a source form that appears to pass one Structure argument are not separate syntactic categories. The argument list itself is a Structure. Therefore a function that receives one Structure and a function that receives several positional fields may have the same source call shape. The receiver signature decides whether the fields of the argument Structure are consumed as one structural value, as several positional parameters, or through an explicitly defined equivalence rule.

This does not mean that Structure arguments are evaluated automatically. If a
direct argument field resolves as a function, subroutine or registered receiver
in a position that expects a value producer, that field may be lowered as a call
or expression. A Structure field remains a Structure unless the receiver
signature consumes it as a statement tail, expression, tuple/data, model fragment
or another explicit role.

This is an intentional property of the language, not an accidental ambiguity. In ordinary colon line forms, whitespace creates short-tail fields and expression operators may bind neighboring fields into expression Structures. In vertical form, child items at the next source level create fields. A receiver with one structural parameter may consume the whole argument Structure. A receiver with several parameters may consume the same Structure by positional fields.

4.7. No Native `=` Assignment or Named-Field Operator

The structural syntax does not use `=` for assignment and does not use `=` as a native named-field operator.

A semantic field name may still exist after receiver normalization. It is produced by receiver signatures, positional conventions, explicit nested Structures, declaration forms or model/type constructors.

Explicit source-level naming is written as an ordinary Structure, not as `name = value`.

Example source:

model:
    name: PlantBed
    condition: plantBedCondition
end: model

Conceptual receiver-level interpretation:

    model(
      name(PlantBed),
      condition(plantBedCondition)
    )

The receiver `model` may interpret `name(PlantBed)` as semantic field `name` and `condition(plantBedCondition)` as semantic field `condition`.

The token `=` is an operator token used by expression/operator consumers as equality/comparison. It is not native structural assignment and not native named-field syntax.

4.8. Positional Fields and Semantic Named Fields

A Structure may contain positional fields. A receiver may assign semantic names to those fields through its signature.

Example:

if: a
    doSomething
    doOtherThing
end: if

With an `if(condition, thenBody, elseBody)` receiver signature, the two vertical child items are consumed positionally as `thenBody` and `elseBody`.

Named vertical form:

if: a
    then:
        doSomething
    else:
        doOtherThing
end: if

Here `then` and `else` are explicit nested Structures consumed as named semantic fields.

Explicit semantic field-like input should be represented by nested Structures:

config:
    batchSize: 500
    reportMode: Daily
end: config

This builds ordinary nested Structures such as `batchSize(500)` and `reportMode(Daily)`. The active `config` receiver decides whether those Structures are interpreted as settings, fields, messages or ordinary child items.

4.9. Field Order

Field order is part of the logical Structure. When a receiver supports positional arguments, positional fields are mapped to receiver signature fields in order.

Semantic field names may be assigned by receiver normalization. A receiver may reject a Structure that contains unknown child Structures, missing required fields or incompatible field ordering.

4.10. Comments and Disabled Blocks

The line-comment marker is:

    #

Outside string/text literals and other literal syntaxes that define their own character rules, `#` starts a comment that continues to the end of the current physical line. The comment text is ignored by the source parser.

If `#` follows source text on the same line, the source text before `#` is parsed normally and the rest of the physical line is ignored.

Examples:

print: count # print the current value of count
# this whole physical line is a comment

The disabled-block marker is:

    %

`%` may appear at the start of a source item, immediately after that item's indentation zone. Optional horizontal whitespace after `%` is ignored. The parser removes `%` for the purpose of identifying the disabled item and records an inactive placeholder for that disabled item/block in the P0 tree.

If the disabled item opens a vertical Structure, the whole vertical Structure is disabled. The parser does not build the normal P0 subtree for that disabled body. Instead, a lightweight disabled-block validator scans the disabled range and checks only structural integrity: source-level nesting, accepted tail-cutter lines, balanced parenthesized forms, quoted-token closure and block-string closure. Therefore disabled code may still produce structural syntax errors, but ordinary receiver/P0 body validation is not run inside it.

Disabled code remains present in the P0 tree as an inactive placeholder. Later receiver consumption skips inactive items, does not register definitions from them, does not update models or registries from them and does not lower them to executable/runtime behavior.

The `%` marker does not contribute to source level. The source level of a disabled item is computed exactly as if `%` were absent, whether the file uses canonical dotted form or relaxed indentation form. Child lines are written at the same source levels they would use for the enabled form.

Example:

%if: mode = debug
    then:
        print: debug branch
    ---
    else:
        print: release branch
    ---


This whole `if` Structure is disabled, but the parser still verifies the syntax and closing structure.

Example inside an enabled block:

if: mode = debug
    %then:
        print: disabled then branch
    ---
    else:
        print: active else branch
    ---


Here only the `then` Structure is disabled. Its body is still parsed and syntax-checked.

The `%` marker is not a receiver, not an operator and not a runtime action. It is a source-control marker handled before receiver consumption.

The raw file-comment fence is a run of asterisks:

    ***
    ****
    *****

A raw file-comment fence is recognized only when the physical line begins at column 0 with a run of `*` characters of length 3 through 80 and is followed only by optional spaces or tabs before the line ending. No source indentation, leading spaces, title text, trailing `#` line comment or other non-whitespace characters are allowed on the fence line.

The first fence opens a raw file comment block and records its exact fence length. The block is closed only by a column-0 fence line with the same number of `*` characters. All physical lines between the matching fences are ignored completely by the Lingvamyxa parser. Source levels are not tracked inside the raw file comment block, operator/expression structures are not parsed, closing forms are not validated and source syntax errors inside the block are not reported.

Raw file comment blocks do not nest. A fence-looking line inside an open raw file comment block whose `*` run length does not match the opener is treated as ignored comment content, not as a nested opener and not as a closer. An unclosed raw file comment block is a file-level syntax error.

Example:

***
This text is ignored by the parser.
Broken Lingvamyxa source may appear here:
    if (
***

Example with inner fence-looking lines:

*****
This line is ignored.
***       # ignored raw comment content, because the opener has length 5
****      # also ignored raw comment content
*****


5. Receiver-Based Semantics

5.1. Core Rule

Surface syntax builds Structures. Receivers and subroutines give those Structures meaning.

Semantic formula:

    surface syntax -> generic Structure -> receiver/subroutine -> typed semantic structure

A receiver has a signature. The signature defines how positional fields, semantic field names, anonymous positional Structures, expression fields and body fields are interpreted.

5.2. Receiver Consumption Modes

A receiver may consume a field as one of the following semantic modes:

    primitive value
    expression
    value-producing Structure
    statement/body Structure
    named function/subroutine/receiver reference
    declaration
    model fragment
    configuration message
    data Structure
    delayed branch
    relation frame
    query frame

The mode is receiver-defined. The parser does not decide that a field is
executable merely because it looks like code. Likewise, ordinary argument passing
does not execute Structure fields merely because they are present in argument
position. A translator lowers a Frame as a call only after its head has been
resolved through the active namespace as a function, subroutine or registered
receiver.

5.3. Expected Field Positions and Anonymous Bodies

Parentheses create ordinary bounded Structures. A bounded Structure is not executable merely because it is parenthesized.

A receiver signature assigns an expected role to each field. If a field position
is defined as a statement/body role, the receiver consumes the supplied
Structure as its own statement list or control tail. This is receiver-defined
translation/interpretation of Structure data; it does not create a separate
anonymous-function syntax.

If a field position expects a named function, subroutine or receiver reference,
the supplied name must resolve through the ordinary namespace. A bounded
Structure supplied in argument position remains Structure data unless the active
receiver explicitly consumes it under its own rule.

If a field position expects a primitive/scalar value and the source supplies a bounded Structure that is not already a direct primitive/scalar value, the receiver consumes that Structure as a value producer for the expected type. An operator-consumed Structure is the usual compact case of this rule.

If the expected type is boolean, the value producer must produce a boolean value. If the expected type is numeric or another primitive/scalar type, the value producer must produce that type or be convertible according to the active profile.

Example:

for: int(i, 0) (i < n) i++
    print: i


The `for` receiver consumes:

    field0 -> initialization Structure
    field1 -> boolean-producing condition expression
    field2 -> iteration-step statement Structure
    body   -> vertical statement Structure consumed by `for`

Compact body example:

    for: int(i, 0) (i < n) i++ print(i)

Here `print(i)` is the last argument Structure of `for`. The `for` receiver
signature names that position as its statement tail and lowers it as the loop
body. The compact body example uses only compact Frames and contains no inline
short colon-form.

5.4. Example: `if`

For a computational L3 `if`, the receiver may define fields:

    condition
    then
    else

and consume them as:

    condition -> boolean-producing expression
    then      -> statement Structure
    else      -> statement Structure

During translation, the receiver lowers these fields into target control flow. During interpretation, the receiver evaluates the condition and then interprets only the selected body.

5.5. Example: `fn`

For an `fn` definition receiver, fields may be consumed as:

    name -> function name
    args -> argument Structure
    ret  -> return Structure
    body -> function statement Structure

The receiver creates or registers an executable definition. The `fn` frame itself is not a function call.

5.6. Same Shape, Different Receivers

The same surface shape can have different semantics under different receivers.

Example:

    (a, b)

As a function argument Structure, it may mean two positional arguments.

As a return layout Structure, it may mean two return fields.

As a model fragment, it may mean a structural model.

As query input, it may mean a tuple of terms.

The receiver defines the interpretation.


6. Operator Tokens and Expression Consumption

Mathematics is a core runtime domain because expressions, numeric models,
arrays, queries, reductions, constraints, validation, scheduling metrics,
build rules and diagnostics all rely on typed computation.

The core parser builds Structures first. Operator tokens and compact
operator-looking spelling chunks stay in the same structural pipeline: P0
tokenization produces ordinary value/name fields and operator-token fields,
then receiver/operator profiles consume those fields according to context.

6.1. One Structural Parser and Operator Tokens

Lingvamyxa has one core structural parsing system. It builds ordinary receiver
Frames, bounded Structures, value fields and operator-token fields.

Operator spellings such as the following are not valid bare namespace identifiers
in the portable profile:

    =
    !=
    <
    >
    <=
    >=
    +
    -
    *
    /

When such a spelling is whitespace-bounded, the parser can classify it
immediately as an operator token. Because it is not an ordinary namespace
identifier, it does not require `:` and it is not parsed as a head/frame form.

Example source:

    i = 1

Core structural form:

    (i, =, 1)

Here `i` and `1` are value fields. The token `=` is an operator field. It is
equality/comparison for expression/operator consumers, not assignment and not
native named-field syntax.

Example inside a receiver frame:

    print: 1 + 2

Core structural form:

    print(1, +, 2)

Because there is no colon after `1`, `1` is a value field, not a receiver/head.
The `+` operator may consume the neighboring values supplied by the
Structure.

6.2. Compact Spellings and P0 Token Boundaries

The core parser always accepts whitespace-bounded operator spellings. With explicit whitespace:

    print: 1 + 2

normalizes directly as:

    print(1, +, 2)

A compact spelling such as:

    print: 1+2

contains the compact non-quoted chunk `1+2`. Because `+` is not valid inside a
portable bare identifier, P0 inserts token boundaries around the operator
spelling and produces the same structural form:

    print(1, +, 2)

The same rule applies to compact sequences such as `a+b*c==d` and `arr[i+1]`:
they become ordinary field sequences containing value/name fields and
operator-token fields.

Exact quoted identifiers are never split this way. For example:

    `1+2`
    `a+b`

remain exact identifier/name values.

6.3. Expression Structures Are Data Before Consumption

An expression-like Structure is data until a receiver consumes it as an
expression.

For example, the `if` receiver consumes its `condition` field as an expression. A
configuration receiver might instead store the same Structure as data.

When consumed in a primitive/scalar field position, an expression-like Structure
is a value producer for that expected type. A comparison or logical operator
structure may satisfy a boolean field. A numeric operator structure may satisfy a
numeric field, subject to the active profile's conversion rules.

The important semantic rule is that operator-token consumption produces ordinary
Structures or typed semantic Structures; it is not an ordinary runtime action.

The bootstrap expression profile keeps expression handling inside ordinary P0
tokenization. P0 produces ordinary token fields and registered
receiver/operator consumption works over those fields.

For the ANSI C projection, arithmetic, comparison and boolean token sequences
keep ANSI C precedence and associativity. Higher Lingvamyxa levels that lower
to ANSI C use the same projection rule; they may add semantic checks around an
expression, but they do not need to reorder primitive C-like expressions.

Backends that do not target ANSI C may define their own lowering for the same
token Structures. Such a backend-specific rule belongs to that backend profile,
not to the source syntax.

6.4. Registered Operator Forms

An operator profile may recognize token sequences as registered operator forms
before ordinary receiver consumption. This document does not define a final
operator set for increment, decrement or similar forms, but it defines the
expected source-semantic shape for such operator methods.

For example, if a profile registers prefix decrement:

    --i

P0 tokenization produces the operator-token field `--` and the source target
name `i`. The operator profile may consume that sequence as:

    decBefore("i")

The operator method resolves `i` in the same active lexical namespace view used by ordinary
source. It may lower the operation as a read-update-write sequence. The
write/update step uses the ordinary head/update form:

    i: newValue

If `i` resolves to mutable storage, the sequence may lower to a direct storage
update. If `i` resolves to a function, subroutine or registered receiver that
defines zero-argument read and one-argument update consumption, the sequence may
lower to generated temporary code that calls/consumes `i` to read, computes the
new value, then calls/consumes `i: newValue` to write.

The exact operator methods, temporary names, evaluation order, numeric rules and
diagnostics belong to the operator-consumption specification. The core point is
that operator methods do not introduce a separate assignment syntax; they compose
with the same namespace resolution and head/update form as ordinary source.

6.5. Basic Array Operations

An array is a typed Structure whose value is described by element type, shape,
rank, storage and optional stride metadata.

An array is not a special execution object. It is ordinary structured data.
Operations over arrays are ordinary typed procedure/function/operator calls
resolved through the same registry/query mechanism as other operations.

A scalar value may be treated as a rank-0 array for array-expression purposes.
A vector is a rank-1 array, a matrix is a rank-2 array, and higher-dimensional
arrays are rank-N arrays.

Minimal array descriptor:

array:
. elementType = T
. rank = N
. shape = [d0, d1, ... dN-1]
. storage = contiguous | view | external | arena
. stride = optional byte strides
. data = implementation-defined storage reference
end: array

The canonical constructor receiver is [].

Examples:

[]: values
. 1
. 2
. 3
end: values

[]: matrix
. []: row
.. 1
.. 2
.. 3
. []: row
.. 4
.. 5
.. 6
end: matrix

The exact compact literal form is implementation-defined at early bootstrap
levels, but the resulting value must be a typed array Structure.

6.5.1. Indexing

Indexing selects an element or a subview.

For a rank-N array, a full index has N integer coordinates.

Example:

matrix[0, 2]

A partial index may produce a view rather than a copy.

Example:

matrix[0]

may produce the first row as a rank-1 array view.

Bounds checking is profile-dependent.

L2 may allow unchecked raw pointer indexing.
L3 and higher should use checked indexing unless the operation is explicitly
marked unsafe.

6.5.2. Views and Copies

Array operations may produce either a view or a copy.

A view shares storage with another array and carries shape/stride metadata.
A copy owns independent storage.

Examples of view-producing operations:

slice
reshape, when compatible with storage layout
transpose
broadcast
partial indexing

Examples of copy-producing operations:

explicit clone/copy
materialize view
result of elementwise arithmetic unless assigned into an existing output buffer

A view is borrowed by default. To retain it beyond the owner lifetime, handler
frame or message boundary, it must be copied into an owned array/branch according
to the L5 memory model.

6.5.3. Shape

shape(array) returns the array dimensions as a rank-1 integer array or shape
Structure.

rank(array) returns the number of dimensions.

length(array) returns the size of the first dimension for rank greater than zero.

size(array) returns the total number of elements:

size = d0 * d1 * ... * dN-1

6.5.4. Reshape

reshape changes the shape descriptor without changing element values.

reshape is valid only if the total element count remains unchanged, unless the
operation is explicitly defined as a copy/fill/truncate operation.

Example:

reshape(values, shape = [3, 1])

A reshape may return a view if the underlying storage layout permits it.
Otherwise it may materialize a copy.

6.5.5. Transpose and Permute

transpose(array) swaps the two last dimensions for rank >= 2, or follows the
profile-defined matrix convention.

permute(array, axes) returns a view with reordered axes when possible.

Example:

permute(tensor, axes = [1, 0, 2])

These operations normally modify shape and stride metadata only. They do not
copy data unless materialization is requested or required by the target backend.

6.5.6. Elementwise Operations

Arithmetic and comparison operators over arrays are elementwise by default.

Examples:

array + array
array - array
array * array
array / array
array == array
array < array

For numeric arrays, the operator is resolved by element type.

Example:

+(array<i64>, array<i64>)
  -> elementwise i64 addition

+(array<decimal>, array<decimal>)
  -> elementwise decimal addition using the decimal backend

Elementwise operations return an array whose shape is derived from the operand
shapes by the broadcasting rules.

6.5.7. Broadcasting

Broadcasting is a shape-compatibility rule for elementwise operations.

It does not require copying data.

Two shapes are broadcast-compatible if, after aligning dimensions from the
right, every corresponding dimension pair satisfies one of the following:

1. the dimensions are equal;
2. one dimension is 1;
3. one side has no dimension there and is treated as dimension 1.

The result dimension is the maximum of the two dimensions.

Examples:

[3] + []
  -> result shape [3]

[2, 3] + [3]
  -> [2, 3] + [1, 3]
  -> result shape [2, 3]

[2, 3] + [2, 1]
  -> result shape [2, 3]

A broadcasted dimension may be represented as stride = 0 in an array view.
This means that the same element is read repeatedly along that dimension.

Example:

[1, 2, 3] + 4

is semantically equivalent to:

[1 + 4, 2 + 4, 3 + 4]

but the scalar 4 is not copied into [4, 4, 4]. It is read through a rank-0 or
stride-0 broadcast view.

6.5.8. Reduction

A reduction collapses one or more dimensions using an associative or explicitly
ordered operation.

Examples:

reduce(+, values)
reduce(+, matrix, axis = 0)
reduce(max, matrix, axis = 1)

If no axis is provided, the reduction applies to all elements and returns a
scalar/rank-0 result.

If an axis is provided, only that axis is collapsed.

The operation must define:

identity value, if required;
element operation;
result type;
ordering guarantees.

For floating/real/decimal values, deterministic profiles should define stable
reduction order to avoid profile-dependent rounding differences.

6.5.9. Scan

scan is a prefix reduction.

Example:

scan(+, [1, 2, 3, 4])
  -> [1, 3, 6, 10]

scan may be inclusive or exclusive according to its descriptor.

6.5.10. Map

map applies a function/procedure to every element.

Example:

map(sin, values)

For pure functions, map may be vectorized, parallelized or lowered to a backend
array operation.

For impure procedures, ordering and side effects must be explicit. The default
array map profile should require pure functions.

6.5.11. Filter

filter selects elements according to a boolean predicate.

Example:

filter(values, predicate = isPositive)

The result is normally a new owned array, because the selected elements are not
guaranteed to form a regular strided view.

6.5.12. Concatenation

concat joins arrays along a selected axis.

Example:

concat(a, b, axis = 0)

All dimensions except the concatenation axis must match.

concat normally materializes a new owned array.

6.5.13. Matrix and Tensor Operations

Elementwise multiplication and matrix multiplication are distinct operations.

The * operator remains elementwise for arrays.

Matrix multiplication, tensor contraction and dot products should be represented
by explicit receivers/operators such as:

matmul(a, b)
dot(a, b)
contract(a, b, axes = ...)
outer(a, b)

A profile may define a symbolic operator for matrix multiplication, but it must
not overload elementwise * ambiguously.

6.5.14. C99 Lowering

A simple C99 lowering may represent arrays as descriptors:

LmArray:
. elementType
. rank
. shape
. stride
. data
. owner/borrow metadata
end: LmArray

Elementwise operations lower to loops over the broadcast result shape.

Broadcasting is lowered by computed strides. A broadcasted dimension uses
stride = 0.

Scalar plus array may therefore lower to the same generic loop as matrix plus
vector or tensor plus lower-rank array.

The implementation may later replace generic loops with specialized kernels,
SIMD kernels, BLAS calls or external numeric backends. This optimization must
not change the observable typed array semantics.

6.5.15. Minimal Bootstrap Profile

The bootstrap profile may support only:

rank-1 arrays;
rank-2 arrays;
contiguous owned storage;
checked indexing;
shape;
copy;
elementwise + - * /;
scalar-array broadcasting;
array-array elementwise operations with equal shape;
reduce over all elements.

Full broadcasting, slicing views, transpose, permute, scan, filter and tensor
contraction may be added later without changing the core array model.

6.6. Numerical Types and Built-In Mathematics

A high-level structural runtime without built-in mathematics is incomplete.

The default numeric model has two broad classes:

    native C99-backed numeric types;
    library-backed mathematical types.

Native C99-backed numeric types are scalar values whose ordinary lowering may
use C99 arithmetic, C99 storage and C99 call/return conventions.

Library-backed mathematical types are ordinary Lingvamyxa numeric types whose
operations are resolved through the registry and lowered to registered backend
functions.

Default bootstrap map:

    char       -> C char
    schar      -> C signed char
    uchar      -> C unsigned char

    short      -> C short
    ushort     -> C unsigned short
    int        -> C int
    uint       -> C unsigned int
    long       -> C long
    ulong      -> C unsigned long
    llong      -> C long long
    ullong     -> C unsigned long long

    i/u        -> implementation-profile C integer family

    i8         -> C99 fixed-width or profile-defined 8-bit signed integer
    u8         -> C99 fixed-width or profile-defined 8-bit unsigned integer
    i16        -> C99 fixed-width or profile-defined 16-bit signed integer
    u16        -> C99 fixed-width or profile-defined 16-bit unsigned integer
    i32        -> C99 fixed-width or profile-defined 32-bit signed integer
    u32        -> C99 fixed-width or profile-defined 32-bit unsigned integer
    i64        -> C99 fixed-width or profile-defined 64-bit signed integer
    u64        -> C99 fixed-width or profile-defined 64-bit unsigned integer

    isize      -> profile-defined pointer-sized signed integer
    usize      -> profile-defined pointer-sized unsigned integer

    bool       -> C int / C99 _Bool / stdbool bool according to profile

    f32        -> C float
    f64        -> C double
    flong      -> C long double

    bigint     -> GMP mpz_t
    real       -> MPFR mpfr_t
    decimal    -> decNumber

The fixed-width aliases are valid only when the selected C99/runtime profile can
provide the corresponding width. If a target cannot provide an exact-width
storage type, the profile must reject that alias or define an explicit emulation
backend.

The `i/u` family denotes implementation-profile integer types over C integer
storage. A concrete profile may define names such as `i`, `u`, `i32`, `u64`,
`isize` and `usize` as separate type constructors or as aliases over a smaller
primitive set.

The special mathematical types are not primitive C values:

    bigint:
        exact integer arithmetic backed by GMP `mpz_t`;

    real:
        arbitrary-precision or profile-defined high-precision real arithmetic
        backed by MPFR `mpfr_t`;

    decimal:
        decimal arithmetic backed by decNumber and a decimal context.

`bigint`, `real` and `decimal` are ordinary names/receivers/descriptors in the
active lexical namespace view when the active profile registers them. Their physical
representation and linked libraries belong to the selected L1/runtime profile.

6.6.1. Mathematics Uses Registry Resolution

Operator-token syntax does not directly call C symbols.

Operator-token fields and compact operator spellings produce ordinary Structures. A receiver that
expects an expression later consumes that expression Structure. During that consumption,
operators and function calls are resolved through the active numeric registry.

Canonical pipeline:

    source structure
        -> operator-consumption Structure
        -> numeric operator/function resolution
        -> typed numeric semantic Structure
        -> interpretation or lowering

Example:

    sqrt(x) + y

Conceptual resolution:

    resolve sqrt(class(x))
    resolve +(resultClass(sqrt(x)), class(y))
    select accepted numeric descriptors
    lower to L1/backend calls if the profile allows it

The observable Lingvamyxa semantics are defined by registered descriptors, not
by accidental C symbol spelling.

6.6.2. Native C99 Numeric Operations

Native C99-backed numeric types may lower to direct C99 operations when the
active profile defines the overflow, conversion, comparison and evaluation
rules.

Examples:

    i32 + i32        -> i32 or promoted profile-defined integer result
    u64 * u64        -> u64 or checked/profile-defined result
    f64 / f64        -> f64
    bool && bool     -> bool

The operator/numeric specification must define or reference the active profile's
rules for:

    integer overflow;
    signed/unsigned mixing;
    integer promotion;
    floating conversion;
    comparison;
    boolean conversion;
    rounding;
    division by zero;
    NaN and infinity handling for floating values.

A deterministic profile should avoid silently inheriting target-dependent C
behavior when that behavior would make Lingvamyxa results platform-dependent.

6.6.3. Library-Backed Numeric Operations

Library-backed numeric operations are normal registered operations.

Example source:

    a + b

If `a` and `b` are `bigint`, the `+` operator resolves to the accepted
`bigint` addition descriptor and may lower to GMP.

If `a` and `b` are `real`, the `+` operator resolves to the accepted `real`
addition descriptor and may lower to MPFR using the active real context.

If `a` and `b` are `decimal`, the `+` operator resolves to the accepted
`decimal` addition descriptor and may lower to decNumber using the active
decimal context.

Conceptual examples:

    +(bigint, bigint)  -> bigint
    +(real, real)      -> real
    +(decimal, decimal)-> decimal

The operator spelling is not tied to one backend function. The registry may
select a backend-specific implementation according to operand types, precision
context, rounding policy, target profile and optimization profile.

6.6.4. Destination-First Backend Procedures

Many mathematical C libraries expose procedures rather than value-returning
functions.

Example backend style:

    result is stored in the first argument;
    operands are read from following arguments;
    rounding/context/status may be additional arguments;
    the C return value may be `void`, `int` status or diagnostic metadata.

Such a C function can still implement a Lingvamyxa value-producing mathematical
operation.

Example conceptual wrapper:

    C backend:
        void mpz_add(mpz_t rop, const mpz_t op1, const mpz_t op2)

    Lingvamyxa operation:
        +(bigint, bigint) -> bigint

Lowering concept:

    allocate or reuse result storage owned by the current owner/arena;
    initialize backend value if required;
    call backend destination-first function;
    return the Lingvamyxa numeric value.

Therefore C `void` does not mean "not mathematical". It may mean "the value is
written into a destination argument". Lingvamyxa exposes the value operation,
not necessarily the raw C procedure shape.

6.6.5. Return Models

Every external function descriptor visible to the numeric registry must declare
a return model.

Return models include:

    ret: T
        value-producing function;

    ret: Unit
        effect-only function corresponding to C `void`;

    ret: Status
        status-only function;

    ret: Status T
        status/value pair or profile-defined checked result;

    ret: destinationArg(N) T
        destination-first backend procedure that produces a Lingvamyxa value;

    ret: pointer / handle / borrowed / owned
        unsafe or explicitly managed low-level result.

Only value-producing functions may appear in value-required expression
positions.

Valid:

    x = sqrt(y)

Invalid in a pure value-required expression/operator context:

    x = Lingvamyxa\GMP\raw\mpz_clear(y)

because raw clear is an effect/release operation, not a pure value.

A `Unit` function may be callable as a statement-level receiver or namespace
function if its descriptor allows that level and effect profile.

6.6.6. L2 Universal L1 Adapter and L4 Wrappers

L1 / ANSI C symbols are not automatically high-level Lingvamyxa functions.

The level boundary is:

    L2
        may expose a universal adapter to the selected L1 / ANSI C profile.
        Raw C functions, raw pointers, raw storage, C headers and platform
        calls belong here. This adapter is governed by the L2/L1 build profile,
        not by high-level L4 semantic wrapper descriptors.

    L3 and above
        may not call raw L1 / ANSI C symbols directly. They may call only
        Lingvamyxa receivers, functions, methods, wrappers, handles or
        capabilities whose registry entries define the needed contract.

The L2 universal ANSI C adapter does not read high-level wrapper instructions
from L4 in order to assign semantic meaning to raw L2 code. Its inputs are the
L2 source and the L2/L1 build profile:

    target compiler;
    target ABI;
    calling convention;
    include paths;
    headers;
    defines;
    compiler flags;
    linker inputs;
    platform profile.

The build profile itself may be described by an L4 build/configuration
Structure. In that role, L4 is not assigning high-level meaning to C functions;
it is supplying mechanical toolchain inputs that will be passed to the
compiler/linker.

This is intentionally close to an ordinary C compilation environment. The same
L2 source should not acquire a different raw C meaning because a higher-level
registry state changed.

For raw C-visible names, L2 uses an explicit C-surface spelling:

    c.name

`c.name` is a reserved L2 spelling form. It is not Structure field access, not
`/` namespace path access, not `\` typed field-follow, and not high-level
registry lookup. It denotes the C spelling `name` as seen by the active L2/L1
translation unit after the build profile's headers, defines and toolchain
inputs have been applied. This is the canonical and permanent L2 C-surface
escape; it is not a Lingvamyxa namespace and not a temporary bootstrap shortcut.

A dotted continuation after the explicit C door remains in the C surface:

    c.tree.branch

lowers to the ANSI C value-field spelling:

---ANSI C---
tree.branch
---ANSI C---

This is intentionally separate from Lingvamyxa typed field-follow. `x\field`
means address/reference field-follow in the Lingvamyxa L2 model and may lower to
`x->field`; `c.x.field` is a direct C value-structure/member spelling. In
head/update position, `c.x.field: value` lowers to `x.field = value`.
Dotted field spelling without the explicit `c.` door is not Lingvamyxa field
access. Ordinary L2 Structures use `\` for typed field-follow; any dotted
value/member path belongs to the explicit C surface and must be spelled through
`c.`.

For convenience, the L2 parser treats a compact token that starts with `c.` as
one C-surface token up to the next Lingvamyxa field boundary, such as horizontal
whitespace, a physical line break, comma/semicolon, `(`, `)`, `:`, a line
comment start, or the end of the current source item. The L2 lowering then drops the `c.`
prefix and copies the remaining ANSI C spelling directly into the generated C
code. For example:

L2:
    c.boxes[1].value: 7
    return: c.boxes[1].value != 7

may lower as:

---ANSI C---
boxes[1].value = 7;
return boxes[1].value != 7;
---ANSI C---

This is an intentional low-level L2 C-surface escape. It does not introduce
Lingvamyxa dot syntax or Lingvamyxa array/member semantics outside the explicit
`c.` door; the copied spelling is checked by the selected ANSI C toolchain.

The `c.` prefix may be used directly in C call or value position. Primitive
L2/C-profile type receivers such as `int`, `char`, `size_t`, `u32`, `i32` and
`FILE` are ordinary bare L2 type spellings and do not use `c.`:

L2:
    fn: main () int
        c.printf: "Hello C\n"
        c.printf: "%s\n" "message"
        size_t: n c.strlen("abc")
        @: FILE file
        c.puts: "Hello C"
        return: 0
    end: main
end: L2

Here `c.printf`, `c.strlen`, `size_t`, `FILE` and `c.puts` do not need
Lingvamyxa descriptors for raw L2 use. They become valid only if the L2/L1
build profile makes the corresponding C spelling visible or otherwise accepted
in that C grammar position, for example through `#include <stdio.h>`, `#include
<stddef.h>` or another selected header. The C compiler, preprocessor and linker
validate whether each spelling is actually a function, object, typedef, enum
constant, object-like macro or function-like macro in that position. Bare
primitive type receivers are checked by the L2 profile before ANSI C lowering.

The same source may also call ordinary Lingvamyxa names such as `println` when
they are already visible in the active Lingvamyxa namespace, for example from a
prelude/core `sub` declaration. Such names are language names, not
C-visible identifiers.

A bare unresolved L2 head or atom such as `printf` is not automatically treated
as a raw C fallback. Direct C-visible access is explicit through `c.printf`.
Bare primitive type receivers such as `size_t` or `int` are ordinary L2
receivers. A bare Lingvamyxa name is not an implicit C fallback; after
resolution it is an ordinary Lingvamyxa `fn`, `sub`, label, variable or
registered receiver, and that binding may choose to lower to C internally.

The `c.` spelling covers raw C-visible names, C preprocessor-like spellings,
object-like macros, function-like macros and explicit C value-field paths in
the selected L2 profile. It does not cover primitive type receivers, C tag
names as tags, labels or declarator syntax. Those are provided by the minimal L2
structural bridge, by selected profile-specific L2 forms, or by an explicit raw
L1 text escape.

L2 storage/address/index forms are Lingvamyxa structural spellings; the C base
type words used inside them are ordinary bare primitive/type receivers:

    int: x
    char: ch
    @: int p
    @@: char pp
    []: int values 16
    \p
    p\field

Thus L2 may have many C-visible identifiers through headers, but the structural
spelling of pointers, arrays, raw loads and field-follow remains Lingvamyxa
syntax.

L4 may still describe checked wrappers, high-level constants, numeric
backends, type mappings, ownership rules, borrow rules, effect rules,
capability requirements and operator implementations for L3+ visibility. That
is the same mechanism used for other receiver/operator registration.

The L4 semantic wrapper layer does not declare every C function for L2. A
selected L2 universal ANSI C adapter may discover or bind raw symbols from
headers, toolchain metadata, build metadata or explicit L2 adapter syntax such
as `c.name`. Those raw symbols remain L2-only unless a checked Lingvamyxa
wrapper is registered.

When structural L2 spelling is not enough, a source may use an explicit raw L1
text block. This is a text escape into L1, not C-visible identifier lookup:

L1:
===
printf("Hello C\n");
===

The raw block body is governed by the raw text/block rules. A trailing
`end: L1` is not required when ordinary source-level decrease already closes
the `L1` frame.

No special mechanism for making C headers visible to mathematics is required.
Mathematics and ordinary L3+ code see only accepted Lingvamyxa descriptors.

Canonical rule:

    L2 source + L2/L1 build profile define raw L1 toolchain visibility;
    L4 may provide that build profile as compiler/linker configuration data;
    L4 wrappers define high-level contracts and visibility;
    registry validation accepts or rejects high-level descriptors;
    accepted high-level descriptors enter the L3+ lexical/registry view;
    expression/operator resolution uses accepted descriptors only.

An L5 system message may also propose a candidate descriptor at runtime. Such a
candidate is data, not authority. It may affect L3+ high-level descriptors only
after ordinary registry validators accept it. It does not rewrite the raw L2
translator.

6.6.7. L2 Raw Adapter and Checked Wrapper Example

A raw L1 function does not need an L4 semantic wrapper declaration merely to be
used by an L2 universal adapter. L2 is the low-level adapter boundary. Headers,
include paths and link inputs are build-profile data. They may be written in L4
configuration syntax, but they are passed mechanically to the toolchain rather
than used as high-level receiver/class policy.

Using MPFR from L2 may therefore be as direct as ordinary C-profile use, if the
L2/L1 build profile provides `mpfr.h` and the MPFR link inputs.

This does not make `mpfr_sqrt` callable from ordinary expression/operator consumption
or L3 source.

A safe value-producing wrapper may be registered separately.

Example conceptual wrapper:

L4:
    externFn: Lingvamyxa\MPFR\sqrt
        sourceLevel: L1
        sourceName: mpfr_sqrt
        header: `mpfr.h`
        pkg: `PkgConfig::mpfr`
        args:
            real: x
        ret:
            real
        backendShape:
            destinationArg: 0
            operandArg: 1
            roundingArg: activeRealContext\rounding
            statusReturn: int
        effects:
            pureWrapper
        context:
            activeRealContext
        implementation:
            Lingvamyxa\MPFR\raw\mpfr_sqrt
        callableFrom:
            L3
            L4 expression
            L5 expression
    ---
end: L4

This wrapper is the high-level descriptor. It is the thing that L3+ code calls.
It defines the value result, ownership behavior, context use and effect profile.

Expression use:

    y = sqrt(x)

Conceptual lowering:

    allocate result real in the current owner/arena;
    initialize MPFR storage according to activeRealContext;
    call mpfr_sqrt(result\storage, x\storage, activeRealContext\rounding);
    record status/exactness according to profile;
    return result.

6.6.8. Namespace Calls Outside Pure Expressions

Checked external wrappers may also be called through ordinary structural path
receiver/call syntax when their descriptors allow it.

Example safe namespace call:

    Lingvamyxa\MPFR\sqrt: x

Example raw/runtime-only call through the L2 adapter:

    Lingvamyxa\MPFR\raw\mpfr_sqrt: rop op rnd

Functions that return `Unit` or perform effects should normally be exposed as
namespace calls or explicit receivers, not as pure expression
functions.

Examples:

    Lingvamyxa\GMP\init: x
    Lingvamyxa\GMP\clear: x
    Lingvamyxa\Decimal\setPrecision: ctx 34
    Lingvamyxa\Real\setRounding: ctx nearest

High-level numeric code should not normally call backend initialization and
clear functions directly. The owner/arena runtime should initialize, retain and
clear backend storage according to the numeric value's owner lifetime.

6.6.9. Pure Expression Profile

The default expression/operator profile is pure.

A pure expression may call only functions registered as pure value functions or
pure wrappers.

Allowed examples:

    sqrt(x)
    sin(x)
    cos(x)
    pow(x, y)
    abs(x)
    gcd(a, b)
    roundDecimal(x)
    a + b
    a * b

There is no blacklist of forbidden C names in this profile. The rule is simpler:
raw L1 / ANSI C calls are not visible to L3+ expression profiles at all. They
belong to the L2 universal adapter boundary.

Effectful operations may be visible at L3+ only as checked Lingvamyxa receivers
or wrappers with declared effects, capabilities, ownership and failure behavior.
Even then, they are statement-level or effect-profile calls, not pure
expression/operator calls.

Required rule:

    raw L1 / ANSI C symbol
        -> L2 adapter only;

    no high-level wrapper descriptor
        -> no L3+ visibility;

    no capability
        -> no high-level call;

    unsafe or pointer-bearing wrapper
        -> L2 only, or L3+ only through an explicitly checked handle/receiver;

    effectful descriptor
        -> not callable from pure expression profile.

6.6.10. Pointer and Memory Rule

An L1 function with raw pointer parameters or raw pointer return values is not a
safe value-producing expression function and is not directly visible at L3+.

At L2, the selected universal ANSI C adapter may call it according to the L2
memory profile.

At L3 and above, it must be wrapped by a Lingvamyxa descriptor that defines:

    ownership;
    borrow duration;
    null policy;
    bounds;
    element type;
    mutation effects;
    thread safety;
    failure behavior;
    visibility;
    capability requirements.

Without such a wrapper, the function belongs to L2 adapter semantics only, not
to ordinary L3+ expression or namespace syntax.

6.6.11. Contexts for `real` and `decimal`

`real` and `decimal` operations use explicit or profile-selected numeric
contexts.

A `real` context may define:

    precision;
    rounding mode;
    status flags;
    trap policy;
    exactness handling.

A `decimal` context may define:

    precision;
    exponent limits;
    rounding mode;
    status flags;
    trap policy;
    quantization policy.

The active context may be lexical, thread-local, receiver-provided or explicit
in the expression/function call according to the active profile.

Examples:

    withRealContext: precision 256 rounding nearest
        y = sqrt(x)
    ---

    withDecimalContext: precision 34 rounding halfEven
        total = price * quantity
    ---

The exact context receiver names are profile-defined. The semantic rule is that
context-dependent numeric operations must not silently depend on hidden
platform state when the deterministic profile requires reproducible results.

6.6.12. Arrays and Numeric Backends

Array operations over library-backed numeric types use the same numeric
registry.

Examples:

    +(array<bigint>, array<bigint>)
        -> elementwise GMP-backed integer addition

    +(array<real>, array<real>)
        -> elementwise MPFR-backed real addition using activeRealContext

    +(array<decimal>, array<decimal>)
        -> elementwise decNumber-backed decimal addition using activeDecimalContext

Broadcasting, reduction, map and tensor operations do not introduce separate
numeric semantics. They repeatedly apply or lower the accepted scalar operation
over the derived array shape.

For floating, real and decimal values, deterministic profiles should define
stable reduction order or another explicit reproducibility rule.

6.6.13. Minimal Built-In Mathematics Profile

The minimal built-in mathematics profile should include:

    native integer arithmetic;
    native floating arithmetic;
    boolean operations;
    comparisons;
    bigint construction and arithmetic;
    real construction and arithmetic;
    decimal construction and arithmetic;
    numeric conversions with explicit loss/rounding policy;
    selected pure functions such as sqrt, abs, min, max and pow;
    array elementwise arithmetic over supported numeric types;
    reduction over supported numeric arrays.

Additional functions may be registered through ordinary L4 descriptors and
registry validation.

The language core does not require every C library function to be visible.

The source-visible mathematical model is:

    typed numeric values;
    typed operators;
    typed function descriptors;
    explicit contexts;
    registry-controlled external bindings;
    safe expression profiles;
    unsafe L2/L3 escape hatches when deliberately enabled.

7. `fn`, `sub` and Structural Closure

7.1. `fn` and `sub` Are Receivers

`fn` and `sub` are definition receivers. Each consumes a Structure and registers
a function or subroutine binding in the active lexical namespace view. During
bootstrap they may be present in an L1 prelude table or parser switch.

An `fn` frame consumes a Structure and creates an executable function binding.

A `sub` frame consumes a Structure and creates an executable subroutine binding.

For the parser-facing L1 / ANSI C bootstrap, a registered receiver such as `fn` is represented as an L1 function whose first argument is the already-built frame argument Structure. Any parser context, symbol table, arena or diagnostic object is an implementation argument after that Structure.

Conceptual L1 shape:

    lm_status lm_receiver_fn(LmStructure *structure, LmContext *context);

The exact C names are implementation details. The important rule is that `fn` receives one Structure value, not several primitive parser arguments.

7.2. Function Definition Form

Example source:

fn: myFunc (int(i), int(j, 1), p1, p2) (int(r1), int(r2))
    print: i
    print: j
    p1()
    p2()
return: r1 r2

Strict conceptual form:

    fn(
      name(myFunc),
      args(
        int(i),
        int(j, 1),
        p1,
        p2
      ),
      ret(
        int(r1),
        int(r2)
      ),
      body(
        print(i),
        print(j),
        p1,
        p2,
        return(r1, r2)
      )
    )

Explicit nested-source form:

fn:
    name: myFunc
    args:
        int: i
        int: j 1
        p1
        p2
    ret:
        int: r1
        int: r2
    body:
        print: i
        print: j
        p1()
        p2()
        return: r1 r2
end: myFunc

The L1 receiver function registered as `fn` or `fm` receives the whole frame argument Structure as its first argument and consumes that Structure by receiver-defined argument positions. The explicit nested forms `name(...)`, `args(...)`, `ret(...)` and `body(...)` are ordinary Structures inside that first argument Structure. They are not `=` named fields.

The `fn`/`fm` frame's logical argument Structure is not the same thing as the formal parameter Structure of the function being defined. In the compact short definition profile, `fn` consumes its fields as:

    name -> field 0
    args -> field 1, required bounded formal argument Structure
    ret  -> field 2, required single-value return type
    body -> fields 3..end as the statement Structure consumed by fn/sub

The `fn` receiver returns one source-level value. The difference between `fn`
and `fm` is not primitive versus non-primitive. A single `fn` value may be
lowered by the active translator as a primitive, pointer, reference, handle or
another single-value representation. A pointer/reference/handle to a Structure
is still one returned value; it is not a multiple return.

The `fm` receiver uses the same field order, but field 2 is a return-description
Structure. That Structure explicitly declares the returned fields. `fm` is the
multiple-return form: the source result is one return Structure, and consumers
may treat that Structure as one value or unpack/map it as a sequence of returned
values where their receiver signature admits it. The explicit return Structure
also gives the translator an optimization surface: it may lower the same source
result as a C struct returned by value, a hidden output pointer, direct scalar
returns, register-like internal convention, arena handle or another
profile-defined representation.

Function definition is not function call syntax. The first compact `fn`/`sub`
field must be the declared name as its own field. A spelling with no separator
before the bounded argument Structure is parsed as a Frame/call-like Structure
and is syntactically correct P0 source, but it is a receiver-level semantic
error for `fn`:

    fn: test(body) int     # syntactically valid, semantically invalid for fn
                           # field 0 is Frame test(...), not name atom test
    fn: test (body) int    # valid shape: field 0 is name atom test, field 1 is args Structure

The `fn` receiver must not try to extract the declared function name from the
inner Frame `test(body)`. That Frame is ordinary source data produced by compact
call syntax. If the active receiver is `fn`, the declared function name is the
separate field consumed as the `name` argument.

Calls intentionally use the no-space callable form:

    test()
    test

Likewise, ordinary head/update consumption remains separate from call syntax:

    test: <int: 5>

Before lowering or interpreting a function body, `fn`/`sub` consumes the formal
argument Structure and introduces the formal bindings into the local namespace.
A direct call consumes its actual argument Structure against that formal
signature. Positional fields are assigned first in order. Once a named argument
field is encountered, all following actual fields in that call must be named
fields; the receiver/translating profile maps them by formal parameter name and
reports unknown, duplicate, missing or out-of-order arguments.

P0 does not know that a nested compact Frame is a function call. For example:

    print(1, 2, get(1,2))

is parsed as the `print` Frame with three fields; the third field is the nested
Structure/Frame `get(1,2)`. During L2 lowering, `get(1,2)` becomes a generated
call only if `get` is already visible in the namespace as an `fn`/`sub` or other
registered receiver. If `get` is a variable, label or named Structure, the same
source field is not a function call. If it is unknown, the translator reports an
unknown Lingvamyxa name unless the source explicitly uses the permanent ANSI C
door, such as `c.get(1,2)`.

Structures are never executed merely because they exist. A translator or
interpreter may lower a named Structure/Frame as a call only when that field is
in an executable/consumed position and namespace resolution has already proven
that the head is an `fn`, `sub` or registered receiver/operator that consumes
the supplied argument Structure as executable input. Anonymous Structures and
named Structures whose heads resolve to variables, labels, records, arrays,
tables or ordinary data remain data until a receiver explicitly consumes them.

P0 does not know these receiver-specific meanings. It only builds the field
sequence. After receiver normalization, a valid `name` argument is privileged
visible metadata of the normalized Structure. Editors, highlighters and
translators may use that metadata to show the introduced name and to validate
`end: <target>` against the receiver-exposed close target. A receiver that
consumes no valid `name` argument still uses the general named-close default,
its own head spelling, unless it explicitly defines an anonymous/nameless close
form.

The formal argument field must be an argument-list Structure even when there is only one formal argument. Therefore:

    fn: factorial (int(n)) int

is valid, while:

    fn: factorial int(n) int

is invalid in the compact `fn` definition profile. The second form gives `fn` the declaration Frame `int(n)` directly where the `fn` receiver expects the bounded formal argument Structure that contains it. The empty formal argument list is written as `()`.

The `fn` return field is a single-value type field, not a return-description
Structure. Write the visible single-value type descriptor admitted by the active
profile. Use `fm` when the source return itself is a Structure with explicitly
declared returned fields:

    fm: `split harvest` (PlantBed(bed))
        (
            f32: harvest
            f32: redApples
            f32: greenApples
        )
        return: bed\area 0 0
    end: `split harvest`

Example with no required formal parameters:

fn: words () iterator(Text)
    yield: "Hello"
    yield: "World"
end: words

Generic structural reading:

    fn(
      words,
      (),
      iterator(Text),
      yield("Hello"),
      yield("World")
    )

Receiver-level interpretation:

    name -> words
    args -> empty formal parameter Structure
    ret  -> iterator(Text)
    body -> yield("Hello"), yield("World")

The physical newline after `iterator(Text)` does not close the `fn` frame. The following `yield:` lines are at the implicit argument level of the `fn` frame, so they become following fields in the same field sequence. They are body fields only because the `fn` receiver consumes fields 3..end as executable body.

If an explicit anonymous Structure is wanted as one field, write a delimiter:

fn: words () iterator(Text)
    ---
        yield: "Hello"
        yield: "World"
end: words

Generic structural reading:

    fn(
      words,
      (),
      iterator(Text),
      Structure(
        yield("Hello"),
        yield("World")
      )
    )

The names `int`, `boolean` and similar names are primitive/type-constructor receivers when registered in the active receiver set. In declaration context, a type/constructor receiver consumes the following raw identifier or exact identifier as a new binding name. If that name already exists in the current namespace, the declaration is invalid.

Compact definition form with vertical children inside the bounded argument list:

fn: i(
    args: int(v, j)
    ret: int
    body:
        j: v / 2
        return: v
)

This parses as a colon line Frame named `fn` whose first argument is a compact Frame named `i` with vertical child Structures. Parentheses do not disable source-level composition.

The `fn` receiver may define this as a compact definition form. In that form, the compact Frame name `i` becomes the function name, and the compact Frame children become definition child Structures.

Conceptual receiver-level interpretation:

    fn(
      name(i),
      args(
        int(v, j)
      ),
      ret(
        int
      ),
      body(
        j(v / 2),
        return(v)
      )
    )

The `args` child receives one compact declaration Frame:

    int(v, j)

In declaration context, this means an `int` binding named `v` whose default/initial value is `j`.

The same declaration may also be written with short forms inside bounded Structures:

    fn: i(args: int(v, j); ret: int; body: (j: v / 2; return: v))
    fn: i(args: (int: v j); ret: int; body: (j: v / 2; return: v))

In the first spelling, `args: int(v, j)` uses a compact declaration Frame as the `args` tail. In the second spelling, `args: (int: v j)` gives `args` a bounded Structure containing the short-form Frame `int(v, j)`. Inside `body: (j: v / 2; return: v)`, the semicolon terminates `j: v / 2`; `return: v` is the next short-form item in the same bounded Structure.

The form:

    args: int v j

is valid ordinary short-tail syntax and normalizes as:

    args(int, v, j)

It does not secretly create `args(int(v, j))`; that interpretation requires a compact Frame such as `args: int(v, j)` or a receiver-defined semantic equivalence.

Here `j: v / 2` updates the visible binding `j`. The final result is returned with `return: v`.

7.2.1. Descriptor-Only `fn` Form

A profile may admit an `fn` form without executable body as a callable
descriptor declaration:

    fn: AddX (int) int

This is not a separate parser feature. It is ordinary receiver consumption of
an ordinary `fn` Structure. The active descriptor/model profile may consume this
shape when the normalized `fn` Structure has a name field, a formal argument
Structure, a result descriptor and no body fields.

The receiver-level algorithm is:

    1. Consume the same `fn` Structure shape used by executable `fn`.
    2. Normalize field 0 as the descriptor name.
    3. Normalize field 1 as the callable formal argument Structure.
    4. Normalize field 2 as the callable result descriptor.
    5. Verify that fields 3..end are empty for the descriptor-only profile.
    6. Create a callable descriptor value with no executable body.
    7. Bind that descriptor value in the current lexical namespace view or in
       the active registry view, according to the consuming profile.
    8. Reject the declaration if it silently conflicts with a visible
       incompatible binding in the same lexical namespace chain.

Conceptual registry rows produced by this consumption may be:

    callableName[AddX]   -> AddX
    callableArgs[AddX]   -> (int)
    callableResult[AddX] -> int
    callableKind[AddX]   -> callableDescriptor

The descriptor is data. It does not define an implementation and cannot be
called merely because its name is visible. It may be used as a compatibility
descriptor for arguments, return values, local bindings, table rows, validators
or message targets. A later executable binding or returned executable reference
may be checked against that descriptor.

Example:

fn: AddX (int) int

fn: makeAdder (int: x) AddX
    fn: addX (int: y) int
        return: x + y
    end: addX

    return: addX
end: makeAdder

Here `AddX` is a callable descriptor binding in the visible lexical/registry
view. `makeAdder` is an executable binding. `x` is a formal binding in
`makeAdder`'s local namespace view. `addX` is a nested executable binding in
that local view, and `y` is local to `addX`. The final `return: addX` returns
the local executable binding/reference if it is compatible with `AddX`. If that
reference escapes the lifetime of `makeAdder`, the implementation must
materialize whatever environment/capture representation is required for `x`.
This is a lexical namespace rule, not a global namespace rule.

7.2.2. Returned Callable as Residual Executable

Because functions may return references or handles to Structures, and because a
Structure may be an executable/callable Structure, a function may return a
callable value. When that returned callable carries captured values, resolved
cells, evidence or other already-bound context, it may be viewed as a residual
executable produced by partial evaluation.

In the example above:

    makeAdder(10) -> residual callable compatible with AddX

The call has already bound `x = 10`. The returned `addX` callable represents the
remaining computation:

    y -> 10 + y

This is partial evaluation in the source-semantic sense: part of the expression
has been consumed/resolved/bound, and the result is a callable residual
Structure or callable reference that can be consumed later.

Not every returned callable is partial evaluation. If a function simply returns
an already-existing callable with no specialization, no captured values and no
additional evidence, it is just a callable reference. The partial-evaluation
reading applies when the returned callable preserves some already-computed
environment, bound argument, selected registry cell, validator evidence or other
specialized context.

Keep this distinct from the two other deferred/result mechanisms:

    lazy / yield
        delays production of sequence values. A consumer asks for one step at a
        time through `next(env)`, `each`, `awaitNext` or an equivalent receiver.

    returned callable / residual executable
        returns a callable Structure/reference whose environment already
        contains some bound or resolved information. Calling it later consumes
        the remaining arguments/computation.

    L5 reply wrapping
        wraps any produced result, including a callable/residual Structure, as a
        reply ProposedMessage only when the message boundary supplies a reply
        target, future, continuation or correlation id.

7.3. Subroutine Definition Form

Example source:

sub: l5_if (boolean(condition)) then else
return

Strict conceptual form:

    sub(
      name(l5_if),
      args(
        boolean(condition),
        then,
        else
      ),
      body(...)
    )

Explicit nested-source form:

sub:
    name: l5_if
    args:
        boolean: condition
        then
        else
    body:
        return
end: l5_if

The receiver `sub` consumes its child Structures by receiver-defined semantic roles. The argument `condition` is a primitive/evaluated argument through the registered constructor `boolean`. The bare names `then` and `else` are structural arguments. No `Struct then` annotation is required.

7.3.1. Shared Lexical Namespace View and No Silent Shadowing

Types, variables, functions, subroutines, receivers, callable descriptors, model
names, generic operation names, labels and local executable definitions share
one active lexical namespace view within a lexical scope chain. There is no
separate local function namespace, variable namespace or label namespace inside
the same active view.

This does not mean that Lingvamyxa defines one global namespace for all programs,
registries and services. Executable definitions, blocks, receivers, modules,
registry imports and service/runtime profiles may create local namespace views
or overlays over enclosing views.

A new binding may be introduced only if the same name is not already visible in the active lexical scope chain. This includes names introduced by declarations, nested `fn` definitions, nested `sub` definitions, imports and model/type constructors.

A local variable cannot reuse the name of a visible type. A local `fn` or `sub` cannot reuse the name of a visible variable, type, receiver, model or executable definition. Imports must not silently shadow visible names. Conflict resolution must be explicit through a future import/qualification rule.

L5 message selectors are looked up through the receiver's message/operation
tables. A selector is not automatically a lexical binding unless it is also
imported or registered as an ordinary receiver/generic operation. The
implementation selected by a message table cell is a lexical executable binding
and follows the single-namespace rule.

In expression position, a visible `fn` name can be lowered as a call after
namespace resolution. The canonical way to return a value is `return: value`,
including terminal return at the source level of the current function. The
function name remains an ordinary namespace binding for function lookup unless
ordinary binding-update rules explicitly change that visible binding.

Example:

fn: factorial (int(n)) (int)
    if: n <= 1
        return: 1
return: n * factorial(n - 1)

Inside the body, `return: 1` exits with value `1` when the condition holds. The expression `factorial(n - 1)` is a recursive function call because it appears in expression position. The final `return:` line is terminal return and closes the function.

7.3.2. Function/Subroutine Names and Binding Updates

Executable definitions do not create a separate source-semantic category that
must be distinguished from ordinary values before resolution. A function or
subroutine name is an ordinary binding in the same active lexical namespace view
that also holds primitive values, Structures, model names, labels, variables,
callable descriptors and other bindings. A Frame is lowered as a call only when
its head resolves to such a function/subroutine binding or to a registered
receiver.

The line form:

    i: 5

has one surface shape. After name resolution, it may mean an update to a mutable
value binding `i`, or a call/receiver consumption of a function/subroutine
binding `i` with argument `5`. The language does not use `=` assignment to
distinguish these cases.

If a function/subroutine binding is declared mutable by a higher profile, it may
be updated by the same head/update form as other bindings:

    i: otherCallable

When `otherCallable` resolves to a compatible function/subroutine binding, the
binding `i` receives that binding/reference. Source semantics does not require a
separate function-pointer syntax for this operation.

For a function/subroutine binding or registered receiver with no required
arguments, value-like consumption may be receiver/profile-defined. For example,
an operator method or receiver may lower a read of `i` to a zero-argument call
`i()`, and a write/update of `i` to a one-argument call or binding update
`i(newValue)`, depending on the resolved binding and active profile.

The exact mutability, compatibility and signature rules are part of the
execution-model and type/model specifications. The structural core only requires
that function/subroutine names live in the ordinary namespace and that the same
head/update surface form is used after resolution.

7.3.3. Nested `fn` and `sub` Definitions

Nested `fn` and `sub` definitions are allowed inside executable bodies. A nested definition creates a local executable binding in the current lexical scope.

Example:

fn: outer (int(x)) (int)
    fn: addX (int(y)) (int)
    return: x + y
return: addX(10)

The nested `fn` `addX` is visible inside the body of `outer` after its definition and inside its own body for recursion. It is not visible outside `outer`.

A nested executable has its own local scope. It may read visible outer bindings according to lexical lookup. Mutation of outer bindings from a nested executable is not part of the minimal semantics unless a later execution-model specification defines explicit capture, reference or closure rules.

A nested `fn` or `sub` may not escape its defining scope unless a later closure/environment specification defines how its environment is represented. Returning a nested executable as a value, storing it in a longer-lived Structure or passing it to a context that may outlive the defining scope requires such closure semantics.

Because names are shared across types, variables, models and executables, nested definitions do not introduce shadowing. The following is invalid if `helper` is already visible as a variable, type, receiver, model or executable binding:

fn: outer () (int)
    int: helper
    fn: helper (int(x)) (int)
    return: x
return: 0

?
Closure representation, explicit capture, mutation of outer bindings and escaping nested executables are not specified in this document. They belong to a future execution-model and runtime specification.

7.4. Body Names

Variables or names used inside an `fn` or `sub` body do not become arguments automatically. Arguments are defined only by the argument Structure consumed by the definition receiver.

7.5. `end:` as General Closing Receiver

`end` is written with the ordinary colon Frame surface form, but it is not an ordinary executable body receiver. It is analogous to a closing parenthesis for vertical Structures. It has no runtime-return meaning by itself and no body-level runtime action.

The source-level closing form is:

    end: <target>

The bare form `end` and the old-looking form `end <target>` are not valid Lingvamyxa source syntax.

`end:` validates `<target>` against a visible open close target: a frame/entity
name introduced by the active receiver, a labelled block or another
receiver-defined visible target. The target is not necessarily the receiver/head
spelling. The privileged source spelling is the ordinary argument name `name`:
when a receiver consumes a valid `name` argument, that value is the close target.
If the receiver has no valid `name` argument, the default close target is the
receiver's own head spelling. Multi-word target names may be written as exact
quoted identifiers or as string close targets, depending on what the receiver
accepted into its close-name table.

The `<target>` operand of `end:` is outside the ordinary namespace expression
rules. It is a literal close target consumed by the structural validation layer,
not a variable, function call, computed value or user-level receiver argument.
Therefore `end: someName` never means "evaluate `someName` and close whatever it
returns"; it means "close the currently visible target whose source name is
exactly `someName`". In this sense `end:` has broader structural authority than
ordinary function receivers: it may cut an admitted open tail, while ordinary
calls can only consume and produce runtime values inside already-open structure.

Unlike `return: value`, which may be a valid runtime item inside an executable
body, `end: <target>` is valid only as a structural close from an admitted close
position. If P0 records `end: <target>` as an ordinary nested Frame because it is
written inside a body position rather than at a close position, the close
validation layer must reject it unless an explicit profile defines another
non-runtime meaning for that receiver.

For `fn`, the canonical explicit close target is the function name consumed by
the `fn` receiver. Therefore `fn: myFunc ...` closes as `end: myFunc`, and an
expanded form with `name: myFunc` also closes as `end: myFunc`.

The closing line has its own source level. It may close several currently open implicit vertical levels at once if the named target is visible at or above that level. This allows a long tail of nested blocks to be cut with one named close. A parser must reject `end: <target>` if the target is ambiguous, not visible or not valid for closing from that position.

`end:` is not the default close mechanism for all named frames. The default structural close is the ordinary source-level cut. `end:` is the explicit named form of that close. It is useful when the source wants to identify the close target directly, close across a long nested tail, or improve diagnostics and readability in long blocks.

Examples:

if: condition
    bodyCall()
end: if

Here `if` has no separate `name` argument, so the core `if` receiver exposes its
head spelling as the close target.

fn: myFunc (int(i)) (int(r))
    return: i
end: myFunc

Here `fn` exposes the function name `myFunc` as the close target.

fn:
    name: myFunc
    args:
        int: i
    ---
    ret:
        int: r
    ---
    body:
        return: i
end: myFunc

Here `fn` exposes the explicit `name: myFunc` field as the close target.

fn:
    args:
        int: i
    ---
    name: myFunc
    ret:
        int: r
    ---
    body:
        return: i
end: myFunc

This is also valid because close-target validation uses the normalized valid
`name` argument, not the physical position of the `name:` field.

The same rule applies to any receiver that consumes a valid `name` argument as
its visible name. In this example the receiver/head is `hello`, but the visible
close target is `world`:

hello: name: world
. "!"
. "!"
end: world

When the same close target is visible at several levels, the source level of
the closing line participates in target selection. A parent-level close selects
the matching target opened at that parent level and cuts the open deeper tail
along the way:

hello: name: world  # world #1, opened at level 0
. "1"
. hello: name: world  # world #2, opened at level 1
. . "2"
. . "!"
end: world  # closes world #1 and also closes its still-open tail

To close the inner `world` explicitly, place the close at the inner opening
level:

hello: name: world  # world #1
. "1"
. hello: name: world  # world #2
. . "2"
. . "!"
. end: world  # closes world #2
end: world    # closes world #1

All core examples above close by the receiver-exposed visible target. For
receivers with a valid `name` argument, that argument value is the close target.
For receivers without a valid `name` argument, the ordinary default is the
receiver/head spelling. A receiver that wants no named close target must define
that explicitly.

The argument name `name` is privileged for readable structural closing, not for
ordinary execution semantics. Tools may highlight it specially, the normalized
Structure exposes its value as the introduced visible close name, and
`end: <target>` validation uses it as the only valid named close target for that
opened Structure. If the `name` argument value fails the close-name table check,
the receiver behaves for named close as though no such argument was supplied and
therefore falls back to the head target.

A translator may implement vertical closure by internal closing handlers. Those handlers are implementation mechanisms. Source semantics only requires that the correct Structure is closed and that invalid closing tokens are rejected according to the active closing policy.


7.6. Label Blocks as Local Nullary Executables

Labels are not a separate source grammar category. A label spelling such as:

readLoop:
    readNext: record
    process: record
end: readLoop

is an ordinary colon Frame with an empty inline tail and a vertical body. When the active executable/control profile consumes this shape as a label block, the label name introduces a local namespace binding for that block.
Because this receiver has no separate `name` argument, its visible close target
is its own head spelling. Therefore the explicit close form is:

Label:
    step0
    step1
end: Label

A label block can also be closed by the ordinary source-level cut when the
surrounding structure makes the target clear. `end: Label` is the explicit
checked form for long or visually separated label bodies.

A label-block binding is a local executable binding with no source arguments and
no normal return value. Its compatibility descriptor is the no-argument,
no-value executable profile admitted by the active label/control receiver, not a
separate parser syntax. It shares the same lexical namespace as variables,
functions, subroutines, receivers, model names and other bindings. There is no
separate label namespace.

In executable statement position, a bare identifier or exact identifier may resolve to a visible zero-argument label-block binding. In that context, the bare or exact name is the canonical call/consumption syntax for the label block:

readLoop

This is not a special parser form and it does not require `readLoop()`. The parser builds an identifier/value line. Name resolution in the current executable statement context decides that `readLoop` denotes the local nullary executable block and consumes/calls it with no arguments.

The same visible label binding may also carry a control-target role when the active profile materializes it as a loop/block label. Control-transfer receivers such as `break: readLoop`, `continue: readLoop`, `redo: readLoop`, `retry: readLoop` or failure-control receivers use that control-target role. A plain executable statement `readLoop` uses the callable/nullary-executable role.

Example post-condition loop:

readLoop:
    readNext: record
    process: record
until: endOfInput(record)

Here `readLoop:` opens a labelled executable block. The `until:` receiver closes that block and consumes it as the body of a post-condition loop. The label name `readLoop` is still a local namespace name for the block; the `until` lowering may implement the loop by direct structured control flow, by a generated label and branch, by an inline nullary block, or by another representation preserving the same source semantics.

Calling or consuming a label block does not by itself create a new function namespace, return binding or closure object. A later profile may define escaping label values, addressable label callables or call-frame labels, but the structural core only requires a local nullary executable binding and ordinary namespace resolution.


8. Runtime Return and Terminal Return

8.1. `return` Receiver

Runtime exit from an `fn`, `sub`, iterator-like executable body or method-like executable body is represented by the `return` receiver/operator.

`return` is not the same as the general structural close receiver `end:`. `end:` closes source structure by visible target name. `return` exits executable control flow. In a terminal trailer position inside an open executable definition, an admitted `return` form may also serve as the structural close of that executable definition.

For `fn`, the ordinary explicit structural close uses the function name exposed
by the `fn` receiver, for example `end: square`. A value return, written as
`return: value`, may also close the function when it appears in a valid terminal
trailer position. The same spelling inside the body is still an ordinary runtime
return and does not structurally close the definition.

8.2. Return Forms

The core return forms are:

    return
    return: value

Inside an executable body, `return` exits the current executable body.

For an `fn`, the core profile requires a value-bearing return form. `return: value` evaluates or consumes `value` as one logical value compatible with the declared return model and exits the current executable body. If the function return model is structural, the tail of `return:` is consumed as one return Structure. Whitespace-separated short-tail fields may be mapped positionally to the return Structure by the `return` receiver signature.

For a `sub`, `return` without tail exits without producing a normal return value.

For a `sub`, `return: value` is invalid unless a later profile defines a status/result convention for subroutines.

For a label/procedure-like executable with no return value, a bare `return` may be valid when the profile admits it.

A bare `return` is not a valid `fn` return in the core profile. A compatibility profile may define a different convention, but that is not the default source semantics of this revision.

`return` is a receiver. It consumes the Structure supplied by its tail. It is not assignment syntax and does not introduce `=` as a native assignment or named-field operator.

Examples:

fn: square (int(x)) (int)
return: x * x

Conceptual executable body:

    return(x * x)

Example with early runtime return and terminal return:

fn: factorial (int(n)) (int)
    if: n <= 1
        return: 1
return: n * factorial(n - 1)

The indented `return: 1` line is an ordinary runtime return inside the `if` body. The final `return: n * factorial(n - 1)` is terminal return for the surrounding `fn` definition.

8.3. Terminal Return as Executable Structural Close

A terminal return is a `return` source item written in a structural trailer position for an open executable definition. The common compact position is the source level of the executable definition itself, where a structural close of that executable definition is expected.

If an executable definition is opened at source level N, then its ordinary vertical body items are normally written at level N + 1. A `return` line at level N is not a sibling root item. It is parsed as terminal return for the currently open executable definition, provided that the current open executable target is visible and compatible with that return form.

Here "at the source level of the executable definition" means the level of the opening source item, such as `fn: name` or `sub: name`, not the ordinary body level. A `return` or `return: value` item written at level N + 1 or deeper is a runtime return inside the executable body. It exits the executable at runtime, but it is not the structural trailer of the executable definition.

Terminal return is equivalent to appending the corresponding runtime `return` as
the final body item and then closing the executable definition by its admitted
executable close target. For an `fn`, this is equivalent to appending `return:
value` to the body and closing the function with its receiver-exposed name, such
as `end: square`.

If the terminal `return` item is written at a smaller source level than the executable definition itself, it may still act as the terminal trailer for the visible executable tail when the normal source-level cut reaches that tail and all intervening frames admit such closure. In that case, the `return` role belongs to the executable tail. Enclosing non-executable frames are closed by the source-level cut, not because `return` is a general close receiver for them.

Example:

fn: square (int(x)) (int)
return: x * x

is source-semantically equivalent to:

fn: square (int(x)) (int)
    return: x * x
end: square

The first form is the canonical compact form for a short function. The second form is an explicit expanded explanation of the same source semantics.

Example with an enclosing level receiver:

L3:
    sub: helloMain
        print: "Hello"
    return
end: L3

means:

L3:
    sub: helloMain
        print: "Hello"
        return
    end: helloMain
end: L3

The source-level `return` at the level of `sub: helloMain` closes the `sub: helloMain` definition. The following `end: L3` closes only the enclosing level receiver.

Example where the same terminal return item is written at a lower source level:

L3:
    sub: helloMain
        print: "Hello"
return

means, when the active level profile admits this cut:

L3:
    sub: helloMain
        print: "Hello"
        return
    end: helloMain
end: L3

Terminal return may close the open executable tail in the same checked way as the executable's admitted `end:` target. For an `fn`, that target is the function name exposed by the `fn` receiver, such as `end: square`. It is not a general close form for arbitrary Structures. It is valid only for executable definitions or executable-like receivers that explicitly admit terminal return.

A terminal `return` may also cut through still-open nested body frames above its target level in the same structural-trailer sense as `end: <name>` or an allowed nameless delimiter, provided all intervening frames admit such closure.

Invalid examples:

return: 1

at root level with no open executable is invalid.

config: app
return: 1

is invalid unless `config` is an executable-like receiver that explicitly admits terminal return. `return` does not replace `end:` for ordinary data, model, configuration or registry Structures.

8.4. Runtime Return vs Terminal Return

The source level separates the two roles.

Runtime return inside a body:

fn: abs (int(x)) (int)
    if: x < 0
        return: -x
return: x

Here the indented `return: -x` line is runtime control inside the `if` body. It does not structurally close the `fn` source item. The final `return: x` is terminal return at the function level and closes the function.

Terminal value return may use values prepared in named return variables:

fn: `estimate harvest` (PlantBed(bed)) (f32(harvest), f32(redApples), f32(greenApples))
    harvest: bed\area
    redApples: 0
    greenApples: 0
return: harvest redApples greenApples

This is equivalent to appending a body-level `return: harvest redApples greenApples` and closing the function.

8.5. Named Return Variables

Multiple return values may be represented by declared return variables inside an executable body when the `fm` return-description Structure gives them names.

Example:

fm: `estimate harvest` (PlantBed(bed))
    (
        f32: harvest
        f32: redApples
        f32: greenApples
    )
    harvest: bed\area
    redApples: 0
    greenApples: 0
return: harvest redApples greenApples

The terminal `return:` returns the current values of the declared return variables and closes the function definition.

An `fm` return-description Structure with several fields defines one return Structure. Updating several declared return fields and returning one Structure-compatible value are source-semantically equivalent when the produced Structure matches the declared return Structure.

Example positional structural return:

fm: `split harvest` (PlantBed(bed))
    (
        f32: harvest
        f32: redApples
        f32: greenApples
    )
return: bed\area 0 0

Here the `return:` tail is one logical return Structure with three fields consumed by the return signature.

8.6. Function Name Binding Update

The current function name is not a special return target. It is an ordinary name in the shared lexical namespace.

If an execution/type profile exposes a mutable local result binding with the same visible name as the function and the declared type is compatible with the assigned value, the ordinary head/update form may update that binding:

fn: square (int(x)) (int)
    square: x * x
return: square

This is not a dedicated return form. The line `square: x * x` is an ordinary
binding update in the active lexical namespace view. After that update, the
visible name `square` denotes the updated result binding, so recursive lookup
through `square(...)` is no longer available through that same visible name in
the remaining local scope.

The function still returns explicitly with `return: square`. The canonical return mechanism for an `fn` is `return: value`. When written in a valid terminal trailer position, `return: value` also closes the function definition.

8.7. Implicit Return at Function End

Implicit return at function end is not a core source form in this revision.

In the core profile, an explicit structural close such as `end: f` does not append an implicit runtime return for a value-producing function.

The preferred style is:

fn: f (int(x)) (int)
return: x + 1

rather than relying on a value left in a local binding at structural close.

8.8. Return Source Semantics

At the source-semantic level, every `fn` has one logical single-value return.
That value may be lowered as a primitive, pointer, reference, handle or another
single-value representation by the active translator. A pointer/reference/handle
to a Structure is still one value returned by `fn`.

At the source-semantic level, `fm` has one logical return Structure. The
return-description Structure explicitly declares the returned fields. This is
the multiple-return mechanism. The returned Structure may be consumed as one
value or unpacked/mapped as a sequence of returned values where the receiving
receiver signature admits it. The field types themselves do not define the
`fn`/`fm` boundary; the boundary is whether the source return is one value or an
explicit return Structure.

The `return:` receiver consumes its tail as the current function result and exits. For a `sub` or no-value label/procedure executable, a bare `return` exits without producing a value. Terminal return additionally closes the current executable definition in source structure when the active executable receiver admits that return form in a trailer position.

Physical return strategy, storage ownership and low-level runtime representation are translator/runtime implementation details. They are not part of the source-semantic core.

The error mechanism is not specified by this document. A function may represent an erroneous result as one of the values allowed by its declared return type unless a later error-system specification defines a separate convention.

The general error/status system is not specified in this document. It may be defined later as ordinary return values, tagged result Structures, receiver-level diagnostics or another mechanism.

---ANSI C---
Possible return-lowering variants for an ANSI C implementation:

variant 1:
A single-value `fn` return lowers to the active profile's chosen single-value C representation.

variant 2:
An `fm` multi-field source return lowers to a caller-provided output Structure passed through a hidden or explicit implementation-level address.

variant 3:
A small `fm` return Structure lowers to a C struct returned by value if the translator/runtime profile allows it.

variant 4:
A structural return lowers to a handle/address allocated or managed by a runtime arena, heap, region or other implementation-owned storage.

variant 4b:
An `fm` return Structure may be optimized away when the translator can map its
fields directly to the consuming context without changing source semantics.

variant 5:
Terminal return lowers as an ordinary body-level return followed by no further generated body statements. Source-level structural closure is resolved before lowering.

These variants are implementation strategies only. The language-level rule remains that `return: value` returns the declared single value from an `fn` or the declared return Structure from an `fm`, bare `return` exits a no-value executable when admitted, and terminal return also closes the current executable definition.

9. Type and Model Forms

9.0. Default C99 Bootstrap Type and Dependency Map

The default ANSI C / C99 bootstrap profile may use the following implementation mapping for primitive and service-level source types. This is an implementation/dependency map, not a separate source grammar.

    i/u      -> C integer          -> no vcpkg
    bool     -> C int / bool       -> no vcpkg
    bigint   -> GMP mpz_t          -> vendored `third_party/gmp.zip`
    real     -> MPFR mpfr_t        -> vendored `third_party/mpfr.zip`
    decimal  -> decNumber         -> vendored `third_party/decNumber.zip`
    SQL      -> SQLite            -> vendored `third_party/sqlite.zip`
    Regex    -> PCRE2 8/16/32     -> vendored `third_party/pcre2.zip`

The default project bootstrap keeps third-party source archives under
`third_party/*.zip`. A full local build expands them into `build/third_party/`
and emits static libraries into `build/libs/`. `vcpkg` may be used as a
download/cache helper for upstream archives, but the default build does not
depend on live package-manager libraries. The bundled PCRE2 profile builds
8-bit, 16-bit and 32-bit code-unit libraries so raw length-based payloads can be
interpreted by the receiver profile instead of being forced through a single
null-terminated UTF-8-only representation.

The `i/u` family denotes implementation-profile integer types over C integer
storage. `bigint`, `real`, `decimal`, `SQL` and `Regex` are ordinary
names/receivers/descriptors in the active lexical namespace view when the active
profile registers them. Their physical representation and linked libraries
belong to the selected L1/runtime profile.

9.1. Type and Model Information

Type and model information is expressed by registered receivers and Structures.
At L4/L5, those receivers may materialize registry table rows as defined by
Part II. At L2/L3, they may instead lower directly to storage, address or
function metadata used by the translator.

The structural core does not require a separate `field` receiver. In declaration context, a type or model constructor consumes a raw identifier token and creates a binding, field entry or registry table row.

Example:

    u32: id
    Text: crop
    f64: harvest 0.0

Conceptual meaning:

    declare binding `id` with type `u32`
    declare binding `crop` with type `Text`
    declare binding `harvest` with type `f64` and default/initial value `0.0`

The token after the type constructor is not evaluated as an existing value. It is a raw name introduced by the declaration. If the name already exists in the current namespace, the declaration is invalid.

9.1.1. Nested Type and Storage Forms

Type, storage and mutability descriptors are ordinary receiver heads. They do
not require a separate declaration syntax. A colon only builds the right-nested
form; it is not a named semantic node.

For example:

    const: char: (): s "hello" "world!"
    const: char: []: s "hello" "world!"
    const: String: (): s "hello" "world!"
    const: String: []: s "hello" "world!"

These are parsed as nested forms:

    const(char(()(s, "hello", "world!")))
    const(char([](s, "hello", "world!")))
    const(String(()(s, "hello", "world!")))
    const(String([](s, "hello", "world!")))

The heads `const`, `char`, `String`, `()` and `[]` are ordinary visible names
resolved by the active semantic profile. In this profile:

    const       qualifies the introduced storage/value as immutable
    char        selects ANSI C compatible character storage semantics
    String      selects the Lingvamyxa immutable string value/reference model
    ()          introduces a named Structure-like aggregate
    []          introduces a named array-like aggregate

Therefore the examples mean:

    const: char: (): s "hello" "world!"
        `s` is an immutable char aggregate whose fields are character storage
        compatible with ANSI C.

    const: char: []: s "hello" "world!"
        `s` is an immutable array of references/pointers to character storage
        fragments compatible with ANSI C string storage.

    const: String: (): s "hello" "world!"
        `s` is an immutable Structure whose fields are references to immutable
        Lingvamyxa String values.

    const: String: []: s "hello" "world!"
        `s` is an immutable array of references to immutable Lingvamyxa String
        values.

`char` and `String` are intentionally different types. `char` exists for the
low-level ANSI C compatible model. `String` has higher-level string behavior and
must not be treated as merely a spelling of `char *`.

---ANSI C---
A possible ANSI C projection of the four examples is:

    static const struct {
        char field0[6];
        char field1[7];
    } s_char_struct = { "hello", "world!" };

    static const char * const s_char_array[] = {
        "hello",
        "world!"
    };

    typedef struct LmString {
        const char *data;
        unsigned long size;
    } LmString;

    static const LmString lm_string_0 = { "hello", 5 };
    static const LmString lm_string_1 = { "world!", 6 };

    static const struct {
        const LmString *field0;
        const LmString *field1;
    } s_string_struct = { &lm_string_0, &lm_string_1 };

    static const LmString * const s_string_array[] = {
        &lm_string_0,
        &lm_string_1
    };

The concrete field names, descriptor type, length type, string interning and
object naming are implementation details. The important distinction is that
`char` lowers toward ANSI C character storage, while `String` lowers toward
Lingvamyxa immutable string objects or references.
---ANSI C---

9.2. Type Constructors

A form such as:

    int: i

or:

    PlantBed: bed

is meaningful only if `int` or `PlantBed` is a registered primitive/type/model constructor receiver in the active level.

A receiver such as `fn`, `sub`, `autoModel` or `args` may consume these Structures as typed declarations.

10. Conditional Structures: L3 Core Extract
10.1. L3 `if`

L3 `if` is a computational control-flow receiver. It consumes:

    condition -> boolean-producing expression
    then      -> statement Structure consumed by `if`
    else      -> statement Structure consumed by `if`

At interpretation time, only the selected body is interpreted.

At translation time, the receiver lowers the condition and statement Structures into target control flow.

10.2. Conditional Forms

Short positional conditional form:

if: mode = debug
    build: debugTarget
    build: releaseTarget

Normal form under signature `if(condition, thenBody, elseBody)`:

    if(
      <expression Structure for `mode = debug`>,
      (build(debugTarget)),
      (build(releaseTarget))
    )

The same conditional may be written with explicit named branch Structures:

if: mode = debug
    then:
        build: debugTarget
    else:
        build: releaseTarget

This builds:

    if(
      <expression Structure for `mode = debug`>,
      then(build(debugTarget)),
      else(build(releaseTarget))
    )

The short positional form is valid when the active `if` receiver assigns sibling child Structures to semantic fields by signature order. Named vertical form remains available for readability or when a style/profile requires explicit names.

11. L2 Addresses

11.0. L2 Addresses, References and Callable References

11.1. L3 Passing Model

At L3 and above, explicit address syntax is usually unnecessary. Structures, arrays, text, objects and other non-primitive values are passed as references or handles by default.

At L3 and above, ordinary names denote primitives, symbols, handles or Structures according to the active semantic environment. They are not raw L2 addresses to executable code.

11.2. L2 Address Values and Storage Allocation

At L2, the source model uses primitive values and typed address values. Aggregate model names such as `PlantBed` denote storage layouts, not ordinary source-level aggregate values.

Allocation and storage receivers create storage and bind the requested name to the address of that storage.

Bare L2 value reading is intentionally narrow. A primitive/scalar storage slot
such as `u32`, `int`, `size_t`, an enum-like scalar or an address slot may
be read as a direct value by naming it. An aggregate storage slot may be embedded
physically by the target backend, but source-level L2 does not treat the whole
aggregate as an ordinary expression value merely because it has a name. Aggregate
storage is consumed through its typed address, through field-follow/index forms,
or by an explicit copy/serialization receiver. In the hosted ANSI C profile this
allows a backend to lower an aggregate storage slot to a C automatic object or
embedded struct field while keeping L2 source semantics address-oriented.

Examples:

stack: PlantBed branch
heap: PlantBed tree
static: PlantBed root
int: count 5
[]: leafs count

int: x 5
@: int p
@@: int pp
@@@: int ppp

p: @x
pp: @p
ppp: @pp

Meanings:

    branch  address of stack storage with layout `PlantBed`
    tree    address of heap storage with layout `PlantBed`
    root    address of static storage with layout `PlantBed`
    count   primitive value/storage initialized to `5`
    leafs   address of array/byte storage sized by `count`, according to the active `[]` receiver/profile
    x       primitive storage/value initialized to `5`
    p       address-depth-1 slot whose base type is `int`
    pp      address-depth-2 slot whose base type is `int`
    ppp     address-depth-3 slot whose base type is `int`
    p: @x   stores the address of storage location `x` into `p`
    pp: @p  stores the address of storage location `p` into `pp`
    ppp: @pp stores the address of storage location `pp` into `ppp`

The receivers `stack`, `heap`, `static`, primitive constructors such as `int`, and allocation constructors such as `[]` are parser/bootstrap constructors in the same broad sense as type constructors: they consume layout/type information and a raw binding name, then introduce that binding with type metadata.

An L2 address value is not necessarily a source-level integer. It may carry, or be statically associated with, layout/type metadata. Receivers and L1 lowering may use that metadata to treat an address as a typed reference rather than as a printable numeric address.

The core L2 syntax does not use a separate `*` or `^` marker for address types. Address-ness is introduced by storage/allocation forms, by the reserved address-depth operator family `@ⁿ`, by address-producing expressions, and by typed field or index operations.

Minimal L2 field-follow is address-oriented. If the binding is a typed address,
`value\field` is the direct Lingvamyxa field-follow form. A direct ANSI C
value-structure operation is written through the explicit C door:
`c.value.field`, which lowers to `value.field`. This keeps C value-member access
visible as C-surface syntax while leaving ordinary Lingvamyxa structures as
typed addresses/references.

11.2.1. Reserved Address-Depth Operator Family `@ⁿ`

The token sequences:

    @
    @@
    @@@

form the reserved L2 address-depth operator family `@ⁿ`. They are reserved operator heads, not ordinary user-defined identifiers. Ordinary source cannot bind procedures, functions, receivers or variables named `@`, `@@`, `@@@` and so on, unless a privileged core/prelude profile explicitly defines the reserved operator metadata.

In head position before `:`, `@ⁿ:` declares an address/reference slot of depth n:

    @: BaseType name
    @@: BaseType name
    @@@: BaseType name

Examples:

    @: int p
    @@: int pp
    @@@: int ppp

Meanings:

    p    address-depth-1 slot whose base type is `int`
    pp   address-depth-2 slot whose base type is `int`
    ppp  address-depth-3 slot whose base type is `int`

Whitespace separates the base type and the binding name under the ordinary short-tail rule. Therefore:

    @@@: int ppp

has two fields, `int` and `ppp`, while:

    @@@: int; ppp

terminates the `@@@:` short form after `int`. The following `ppp` is not the binding-name field of that declaration; it is the next source item at the current level.

The prefix expression form `@x` remains the depth-1 address-of operation. Higher address depth is expressed by declaring deeper address slots and storing ordinary depth-1 addresses of those slots:

    int: x 5
    @: int p
    @@: int pp
    @@@: int ppp

    p: @x
    pp: @p
    ppp: @pp

This keeps prefix address-of simple while preserving arbitrary address depth in declarations.

The implementation of `@ⁿ` may be represented by reserved operator descriptors in the L2 operator table. The source semantics only require that `@ⁿ` is parsed as a reserved operator family and that its declaration form produces typed address slots compatible with the active L2 memory profile.

11.3. Address-of, Raw Load and Callable References

The prefix form:

    @x

returns the address of the storage location `x`.

If `x` is already an address binding, `@x` is the address of the binding that stores that address. It is address-of-address, not the address of the target object. This is the expression-side companion of the declaration-side `@ⁿ:` family: `@@: int pp` declares an address-depth-2 slot, while `pp: @p` fills that slot with the address of the depth-1 slot `p`.

The prefix form:

    \a

performs a raw L2 load at address expression `a`. It reads the primitive cell, word or value defined by the active L2 memory profile. It does not perform typed structural rendering by itself.

The field-follow form:

    a\field

follows typed address/reference `a` to the named field `field`. It uses the known layout/type metadata of `a`, reads or writes the field slot, and returns the field content as either a primitive value or another typed address/reference.

C-profile mnemonic table:

    @: char c        # C declarator role: char *c
    const: @: T p    # C declarator role: const T *p
    @c               # C expression role: &c

    parent\child     # C expression role: parent->child
    c.parent.child   # C expression role: parent.child
    \parent\child    # parsed as \(parent\child); C expression role: *(parent->child)
    (\parent)\child  # explicit grouping: raw-load parent first, then follow child

In expression position, field-follow and index chains are assembled before
prefix `@` and prefix `\`; parentheses override this order.

The last spelling is not the default parse. It is the explicit grouped form for a profile that needs the meaning "first raw-load `parent`, then field-follow `child` from the loaded typed address/reference".

Examples:

print: @count
print: \leafs
print: leafs[3]
print: \(leafs + 3)
tree\branch: branch
root\branch: tree
print: tree\branch
print: @tree\branch
print: root\branch\branch
print: \root\branch\branch

Meanings under the declarations in section 11.2:

    print: @count
        Print the address of the primitive storage location `count`.
        To print the primitive value `5`, write `print: count`.

    print: \leafs
        Raw-load and print the first primitive cell/element at address `leafs`.
        This bypasses typed array/string rendering.

    print: leafs[3]
        Print the indexed element at address/index position `3` under the active `[]` profile.

    print: \(leafs + 3)
        Compute address `leafs + 3`, raw-load the primitive cell/element at that address, then print it.

    tree\branch: branch
        Store the typed address value `branch` into the field slot `branch` inside the storage addressed by `tree`.

    root\branch: tree
        Store the typed address value `tree` into the field slot `branch` inside the storage addressed by `root`.

    print: tree\branch
        Read the field `branch` through typed address `tree`.
        If that field contains a typed `PlantBed` address, `print` may render the whole object/tree addressed by that field.

    print: @tree\branch
        Print the address of the field slot `branch` inside the storage addressed by `tree`.
        This is parsed as `print: @(tree\branch)`.

    print: root\branch\branch
        Follow `root\branch` to the typed address stored there, then follow its `branch` field.
        If the final result is a typed `PlantBed` address, `print` may render that whole nested object/tree.

    print: \root\branch\branch
        Follow `root\branch\branch`, then raw-load the primitive cell/element at the resulting address.
        This is parsed as `print: \(root\branch\branch)` and bypasses typed object rendering.

Field-follow and index chains bind tighter than prefix `@` and prefix `\`.

Therefore:

    @tree\branch

is parsed as:

    @(tree\branch)

and means the address of the field slot `branch` inside the storage addressed by `tree`.

Likewise:

    \root\branch\branch

is parsed as:

    \(root\branch\branch)

and means a raw load from the address produced by the typed field-follow chain.

At L1 lowering time, a receiver such as `print` receives typed values or typed references when the source expression preserves type metadata. For example, `leafs` may be printed as a whole array/string/buffer when its allocation metadata is known, and `tree\branch` may lower to a `PlantBed*`-like reference or an equivalent `(layout, address)` pair, so `print: tree\branch` may render a whole object/tree according to the active print receiver. The prefix raw-load form `\expr` bypasses that structural interpretation and produces the primitive cell/value loaded at the computed address, so `print: \leafs` prints the first primitive cell/element under the active L2 memory profile.

Function/subroutine address forms are strictly L2. A static L2 executable binding may be addressable through `@name` if the active L2 profile exposes it as storage or callable-address metadata.

At L3 and above, calls are expressed as receiver Frames and resolved by the active receiver/operator registry, not by raw callable addresses. L5 message selectors and message-operation table entries are not automatically L2 callable addresses.

?
The exact L2 memory profile must define primitive cell size, address arithmetic, alignment, storage duration, allocation failure, callable-address representation and which bindings are addressable through `@`.
?

variant 1:
Treat `@ⁿ`, prefix `@`, prefix `\`, field-follow `\field` and `[]` as built-in L2 parser forms.

variant 2:
Treat them as bootstrap-registered L2 operators with parser support only for tokenization and precedence.

variant 3:
Allow both forms: parser-level recognition for core operators and receiver-level extension for specialized memory models.


12. Arrays, Text and Indexing

12.1. Logical Model

At L3 and above, an array is a Structure or handle/reference to a Structure. Text is also a Structure or handle/reference to a Structure.

The logical array model includes at least a length field and an indirect storage reference. It may also include capacity, encoding, element type and storage handle.

12.2. L2 Lowering

At L2, arrays and text may lower to typed addresses, length-plus-address records or other layout-specific representations.

Example conceptual lowering for an array:

    (len, addr)

Lowering does not change source semantics.

12.3. Indexing

Operator-token consumption rules are specified by level and profile. Indexing is treated as a level-dependent operator/form.

At L2, `[]` is a low-level index operator. It uses a typed or computed address and is governed by the L2 memory model.

Example conceptual L2 meaning:

    beds[i] means the element at the computed address

subject to the actual L2 layout and address rules.

At L3 and above, `[]` accesses an array Structure indirectly and performs bounds checking through the array metadata, at minimum the `len` field.

Example conceptual L3 meaning:

    beds[i] means index(beds, i)

where `index` receives the array Structure or handle, checks `0 <= i < beds\len`, and returns the element or reports a bounds error.

?
The final array/text specification must define exact index result semantics, slicing, negative indexes if any, multidimensional arrays, text encoding and the boundary between parser form and receiver/operator form.
?

---ANSI C---
Possible array-lowering variants:

variant 1:
L2 array access lowers to computed-address access with no automatic bounds check.

variant 2:
L3+ array access lowers to a length-plus-address or length-plus-handle Structure with generated bounds checks.

variant 3:
Dynamic arrays lower to runtime handles with accessor calls when layout is not statically known.
---ANSI C---


13. Typed Field Follow

13.1. Backslash Structural Traversal Form

Structural traversal / dereference-like access uses backslash syntax:

    result\harvest

The backslash form is a built-in parser form. It exists so the translator can generate direct structural traversal through known Structures, typed addresses, handles and layouts. It is not a textual namespace separator and it is not equivalent to the L2 foreign/substrate qualified-symbol form such as `c.printf`.

At L2, the left side is normally a typed address. At L3 and above, the left side may be a Structure, handle or reference according to the active semantic environment. In all cases, `\` implies an actual traversable source-semantic object, not a dotted or slash-separated external name.

The same `\` character also has a prefix L2 raw-load form, described in section 11.3. These forms are distinguished by position:

    \address      raw L2 load from an address expression
    value\field   typed field follow/access

Possible normal form:

    field(result, harvest)

or an internal field-follow expression Structure equivalent to it.

13.2. Lowering

If the model/layout of `result` is known, the translator may lower:

    result\harvest

into direct structure access, typed-address field-follow access or generated accessor code.

If the model/layout is dynamic, the receiver/runtime may perform a checked lookup.

!!!
Field-follow failure semantics are not fixed. A final source-semantic rule must define behavior for missing fields, unknown models, dynamic Structures and nullable handles, including whether such cases are compile-time errors, runtime errors or receiver-defined diagnostics.
!!!

---ANSI C---
Possible field-follow lowering variants:

variant 1:
Known static layouts lower to direct C struct-field access.

variant 2:
Known typed-address layouts lower to direct pointer-field access in ANSI C.

variant 3:
Dynamic Structures lower to checked runtime lookup or generated accessor calls.
---ANSI C---


14. Update, Return Structures and Destructuring

14.1. Binding Update Instead of `=` Assignment

The native structural core does not use `=` for assignment.

A declaration with initialization is written through a declaration-context constructor:

    int: a 3

A later update to an existing mutable binding or addressable field/index location is written by placing that location in head/update position:

    a: 4

Example:

    int: a 3
    print: a
    a: 4
    print: a

The first `print` observes `3`. The second `print` observes `4`.

The update form is valid only if the head resolves to an existing mutable binding, addressable field/index location, or visible language name that explicitly accepts such a call. Because Lingvamyxa uses one lexical namespace, a binding name and a type/function/procedure name cannot silently mean different things in the same scope.

The same surface form is used for resolved consumption. For example, `i: 5` is
parsed as a Frame with head `i` and argument `5`. If `i` resolves to mutable
storage, the form may update storage. If `i` resolves to a function, subroutine
or registered receiver, the translator may lower it as a call/receiver
consumption. This is a compile-time resolution choice, not a syntactic
distinction.

A bounded Structure or compact Frame in an argument/update position remains one
Structure after parsing. A nested compact Frame is lowered as a call only if its
head resolves in the ordinary namespace as a function, subroutine or registered
receiver. For example, in `print(1, 2, get(1,2))`, `get(1,2)` is just the third
field for P0; it is generated as a call only after `get` resolves as callable
during lowering.

This is declared head consumption, not automatic execution of every Structure in
an argument list.

At L2, update may lower to direct storage write according to the L2 memory model. At L3 and above, update is receiver-defined over variables, fields, handles and Structures.

?
Binding, mutability, scope, initialization, reassignment and shadowing rules are not specified in full in this document. They require a dedicated execution-model specification.
?

14.2. Return Structures

A function return value is one logical source-level value. That value may be primitive or structural. If the return value is structural, updating its declared fields and returning one Structure-compatible value are source-semantically equivalent under the receiver-defined return signature.

A function may return a Structure with ordered and/or semantic named fields.

Example return signature:

    (f32 harvest, f32 redApples, f32 greenApples)

Canonical structural return:

    return: bed\area 0 0

Named return variables may also be updated before an explicit terminal value return:

    harvest: bed\area
    redApples: 0
    greenApples: 0
    return: harvest redApples greenApples

The canonical return mechanism for an `fn` is `return: value`. In a valid terminal trailer position, `return: value` also closes the `fn` source frame. Named return variables are ordinary typed bindings whose current values may be returned explicitly.

14.3. Destructuring

Destructuring syntax using `=` is not part of the current native structural core.

The semantic operation still exists: a produced Structure may be assigned or bound as one value, stored in a temporary service binding, or used to update target bindings from its fields by name or by position.

Possible explicit receiver form:

unpack: toEat(myFilter, Monday)
    harvest
    redApples
    greenApples
end: unpack

Conceptual meaning:

    tmp receives toEat(myFilter, Monday)
    harvest receives tmp\harvest
    redApples receives tmp\redApples
    greenApples receives tmp\greenApples

If the produced Structure has no field names, a receiver-defined positional unpack form may map fields by order.

?
The canonical destructuring/update syntax is not specified. A final execution-model specification must define whether destructuring is written through an `unpack` receiver, through target-list syntax without `=`, or through another explicit structural form.
?

---ANSI C---
A translator may implement destructuring by assigning the produced Structure or handle to a temporary service variable and then generating field updates one by one.

variant 1:
For known static layouts, generated code reads fields directly from the temporary Structure.

variant 2:
For handle-based Structures, generated code reads fields through generated accessors or runtime lookup.
---ANSI C---

15. Structural Grammar Sketch

This grammar sketch describes the structural parser only. It does not define final receiver semantics.

15.0. P0 Source-Event Automaton

This subsection is normative for P0 structure recognition. The grammar below is
only a compact readable projection of the same machine.

P0 is one recursive source-event automaton over source positions:

    P0 = (S, E, delta, O)

where:

    S  is the parser state;
    E  is the stream of source events produced by the source scanner;
    delta consumes one event and updates the state;
    O  is the produced parser tree with source spans and node flags.

There is no separate line parser, brace parser, bracket parser or expression
parser at P0. Physical lines are input fragments, not containers in the
abstract tree. Parentheses, index brackets and MIX braces all enter nested P0
contexts; their difference is the channel where the resulting Structure is
used.

State:

    S.position
        current source position and absolute span base.

    S.lexical_mode
        SOURCE
        C_STRING
        EXACT_IDENTIFIER
        PYTHON_RAW_QUOTE
        BLOCK_STRING
        RAW_COMMENT
        LINE_COMMENT

    S.level_state
        the normalized source level state. Canonical dotted spelling maps
        leading dots to integer source levels. Relaxed indentation maps
        indentation columns to the same integer source levels through the
        indentation-stack rule.

    S.form_stack
        ROOT(level 0)
        VERTICAL(level K)
        SHORT(head at level N, implicit argument level N + 1)
        BOUNDED_PAREN(base level B)
        BOUNDED_INDEX(base level B)
        BOUNDED_MIX(local base level 0)

    S.output_cursor
        the current ordinary Structure insertion point, plus the current
        source span being attached to the next node.

Events:

    LEVEL(K)
        next source item is at normalized source level K.

    ATOM(value)
        ordinary token/value after operator splitting and payload recognition.

    HEAD(value)
        head token before `:`.

    COLON
        opens a short form for the preceding HEAD.

    NEWLINE
        physical newline separator.

    COMMA_SEPARATOR
        comma separator at the current scan depth. It separates fields like
        whitespace, but it has no indentation/source-level effect.

    SEMICOLON_SEPARATOR
        semicolon separator/trailer at the current scan depth. It may terminate
        the current open short form.

    OPEN_PAREN / CLOSE_PAREN
        `(` and matching `)` bounded Structure delimiters.

    OPEN_INDEX / CLOSE_INDEX
        `[` and matching `]` bounded index/access delimiters.

    OPEN_MIX / CLOSE_MIX
        `{` and matching `}` MIX bounded form delimiters.

    TAIL_CUTTER(candidate)
        a candidate visible close/cut form, such as `end`, `return`, `until`
        or a dash-fence delimiter. Candidate status is later validated by the
        current receiver/profile context.

    EOF
        end of source.

Lexical shielding:

    If S.lexical_mode is not SOURCE, braces, parentheses, brackets, commas,
    semicolons, colons, dots, indentation and tail-cutter words are payload
    characters for that lexical mode. They do not produce structural events
    until that lexical mode closes.

    C_STRING closes by its C string delimiter rules.
    EXACT_IDENTIFIER closes by its exact identifier delimiter rules.
    PYTHON_RAW_QUOTE closes by its matching raw quote run.
    BLOCK_STRING closes by its matching column-0 `===...` fence.
    RAW_COMMENT closes by its matching column-0 `***...` fence.
    LINE_COMMENT closes at physical newline.

    Therefore a `}` inside a string, exact identifier, raw string, block string
    or comment inside a MIX bounded form does not close that MIX bounded form.

Level transitions:

    delta(LEVEL(K -> K + 1))
        opens one Structure field under the current source parent. Portable P0
        source-level syntax opens block structure by one atomic level increase.

    delta(LEVEL(K -> K))
        produces a sibling item at the current source level, unless the current
        scan depth is controlled by an open short/bounded form.

    delta(LEVEL(K -> K - 1))
        closes the current visible vertical Structure by the ordinary one-step
        source-level cut.

    delta(LEVEL(K -> K - M), M > 1)
        is not ordinary block syntax. It is admitted only when the current
        source event is consumed by a valid tail-cutter layer for that context.

    An empty physical line is a level-0 boundary event. It may close an open
    level-1 vertical tail by the ordinary level decrease, but it is not a
    same-level delimiter below level 1.

Short-form transitions:

    HEAD COLON at source level N creates:

        Frame(head, BodyStructure at implicit argument level N + 1)

    Inline tail fields after `:` are appended to that BodyStructure at the
    implicit argument level N + 1.

    NEWLINE inside an open short form performs the synthetic short-form level
    step from N + 1 back to N. This step is only a separator step. It is not by
    itself the trailer of the short form.

    After that newline:

        if the next source item appears at level N + 1, the atomic level
        increase N -> N + 1 opens a new Structure field in the same short-form
        argument sequence;

        if the next source item appears at level N or smaller, the short form
        is complete and the next item is handled by ordinary sibling, cut or
        receiver-trailer rules.

    COMMA at the current scan depth separates fields and does not append an
    empty field. It is an ordinary bounded/sequence separator or a cosmetic
    trailing marker according to the surrounding context.

    SEMICOLON at the current scan depth terminates the current open short form.
    It does not append an empty field. If no short form is open at that scan
    depth, it is an explicit source-item separator or a cosmetic trailing marker
    according to the surrounding context.

Bounded-form transitions:

    OPEN_PAREN starts a nested BOUNDED_PAREN context. Its contents are parsed by
    the same P0 source/token rules, with source-level composition measured
    relative to the bounded opener. CLOSE_PAREN closes that context. If a short
    form is still open inside the bounded context, it is completed as part of
    closing the bounded context.

    OPEN_INDEX after a target starts a nested BOUNDED_INDEX context. Its
    contents are parsed by the same P0 source/token rules. CLOSE_INDEX closes
    that context and attaches the resulting Structure as an index/access suffix
    to the preceding target or to a receiver form that admits bracket syntax.

    OPEN_MIX starts a nested BOUNDED_MIX context for a MIX bounded form `{...}`.
    Its contents are parsed by
    the same P0 source/token rules in a local level-0 context. CLOSE_MIX closes
    that context. The resulting Structure is stored as a MIX-flagged parser
    node with its source position/span. Ordinary structural consumers may skip
    MIX-flagged nodes; document/MIX consumers project them into active overlay
    intervals and marks.

    A matching closing delimiter line may return to the opener level. The
    closer token itself is the bounded-form close event, not an ordinary
    sibling source item.

Tail-cutter transitions:

    Tail-cutters are not magic words in P0 by spelling alone. A token such as
    `return` or `until` becomes a tail-cutter only when it appears at a source
    event where a valid receiver/profile context admits that close/cut role.
    Otherwise it remains an ordinary item/operator/receiver token for later
    semantic processing.

    `end: name` is a visible structural close form. Its argument is not
    evaluated as a runtime expression. It is compared with the visible close
    target supplied by the receiver being closed: normally the privileged
    `name` argument of that receiver, or the receiver head when no such valid
    close name exists.

    `return`, `return: value`, `until` and dash-fence delimiter forms are
    members of the same tail-cutter family, but each is admitted only in the
    receiver/profile positions defined for it.

EOF transition:

    EOF closes the root context after all open structures that may be closed by
    EOF have been completed. Any remaining open bounded form or lexical mode is
    a syntax error.

Output invariants:

    P0 constructs Structure, Frame, Atom/value and MIX-flagged nodes with source
    spans. It does not execute Structures, evaluate expressions, resolve
    functions, declare variables or decide type semantics.

    A named Structure is translated or interpreted as a call/function/subroutine
    only when a later semantic layer resolves its head through the active
    namespace. An anonymous Structure remains Structure data until a receiver
    consumes it under a receiver-defined rule.

    Any search for a matching `)`, `]` or `}` must use the same lexical modes as
    P0 itself. There is no separate opaque boundary walker that merely counts
    characters.

    program             ::= { empty_line | physical_item }

    physical_item       ::= raw_file_comment_block
                          | block_string_literal
                          | logical_line

    raw_file_comment_block
                        ::= raw_comment_fence(N) trailing_horizontal_space newline
                              raw_ignored_line*
                            raw_comment_fence(N) trailing_horizontal_space newline
                            where 3 <= N <= 80

    raw_comment_fence(N)
                        ::= exactly N "*" characters at column 0

    block_string_literal
                        ::= block_string_fence(N) trailing_horizontal_space newline
                              block_string_content_line*
                            block_string_fence(N) trailing_horizontal_space newline
                            where 3 <= N <= 80

    block_string_fence(N)
                        ::= exactly N "=" characters at column 0

    trailing_horizontal_space
                        ::= { " " | tab }

    horizontal_space    ::= " " | tab

    logical_line        ::= source_level line_content newline

    indentation         ::= { "." | " " | tab }

    source_level        ::= integer source level assigned by the
                            source-level normalization prepass

    source-level normalization prepass:
                            maps the physical source spelling to source-level
                            item/level events
                            before the structural grammar consumes it;
                            in canonical dotted notation, source_level is the
                            count of leading dot characters;
                            in relaxed indentation notation, source_level is
                            computed by the indentation-stack rule.

    empty_line          ::= trailing_horizontal_space newline
                            level-0 structural boundary event;
                            closes an open level-1 vertical tail by ordinary
                            source-level decrease, but is not a same-level
                            delimiter below level 1

    line_content        ::= dot_only_marker [ comment_body ]
                          | comment_body
                          | disabled_body [ comment_body ]
                          | line_item_sequence [ comment_body ]

    dot_only_marker     ::= empty content after indentation
                            valid only if source_level > 0;
                            may delimit/open an anonymous Structure at that level

    comment_body        ::= "#" ignored_until_newline

    disabled_body       ::= "%" enabled_line_body

    enabled_line_body   ::= line_item_sequence

    compact_frame       ::= name "(" [ argument_list ] ")"

    line_frame          ::= source_level line_item_sequence newline

    line_item_sequence  ::= source_item { ";" source_item } [ ";" ]

    source_item         ::= colon_frame_body
                          | nullary_line_body
                          | structural_value

    colon_frame_body    ::= head ":" [ line_arguments ]

    // Semicolon terminates the current source_item at the current scan depth.
    // Comma is an ordinary field separator.

    head                ::= bare_identifier
                          | exact_identifier
                          | symbolic_head

    nullary_line_body   ::= name
                            valid in executable statement position only when
                            `name` resolves to a zero-argument consumable binding:
                            registered nullary operator/receiver or visible zero-argument fn/sub

    line_arguments      ::= short_tail

    short_tail          ::= short_field { (horizontal_space+ | ",") short_field } [ "," ]

    short_field         ::= colon_frame_body
                          | structural_value

    // In ordinary physical short-line form, comma separates fields in the
    // current short form. Semicolon terminates the current short form.
    // Physical newline is not a short-form trailer; after newline, the next
    // source-level event decides whether the open frame receives more fields
    // or is completed by level rules.
    // Operator-token consumption is deferred to a later consumer.

    argument_list       ::= bounded_item_sequence

    bounded_item_sequence
                         ::= bounded_item { bounded_item_separator bounded_item }
                             [ bounded_item_separator ]

    bounded_item_separator
                         ::= horizontal_space+
                          | ","
                          | ";"
                          | newline/source-level composition

    bounded_item        ::= colon_frame_body
                          | nullary_line_body
                          | structural_value

    // Inside bounded Structures, short colon-forms may appear inline.
    // Horizontal whitespace separates simple bounded fields only when no
    // short colon-form is open. Inside an open short colon-form it remains
    // the short-tail field separator. Comma is also a short-tail field
    // separator. Semicolon terminates an open short form at any scan depth.
    // Newline/source-level composition is not a short-form
    // trailer by itself; the following source level determines continuation
    // or closure. Inside a bounded form that continues across a physical
    // newline, the next physical line must remain inside that bounded form:
    // it must be at the corresponding deeper dotted source level or, in
    // relaxed notation, at an indentation column deeper than the line that
    // opened the bounded form. A line whose next source token is the matching
    // RPAREN/RBRACKET is the closing line and may return to the opener level.
    // The matching RPAREN/RBRACKET closes the bounded Structure; if a short
    // form is still open inside it, that short form is completed as part of
    // closing the bounded context.

    bounded_structure   ::= "(" [ argument_list | vertical_argument_list ] ")"

    source_fragment     ::= P0 source parsed in a local level-0 context

    mix_structure       ::= "{" source_fragment "}"
                            parsed by the same P0 source/token rules in a
                            local level-0 context and stored as a MIX-flagged
                            Structure node

    index_access_suffix ::= "[" [ argument_list | vertical_argument_list ] "]"
                            attached to a preceding target by an expression,
                            update or receiver profile that admits index/access
                            syntax

    vertical_argument_list
                         ::= newline source_line { source_line }
                            where each contained source_line follows the same
                            source-level rules as ordinary vertical composition

    structural_value
                         ::= compact_frame
                          | bounded_structure
                          | mix_structure
                          | atom_or_value

Square brackets in the portable core are not a free-standing replacement for
parentheses. `target[...]` is bounded index/access syntax attached to a preceding
target or to a receiver form that explicitly admits bracket syntax. `[]:` in
head position is a symbolic receiver spelling, such as an array/storage
constructor, not the same thing as an index suffix. A standalone `[a b]` has no
portable core meaning unless a profile explicitly admits it.

The vertical Structure tree is produced by source levels and explicit visible delimiters: following source items at one-step smaller source level as level delimiters, canonical dotted delimiter lines, relaxed dash-fence lines, and admitted source-level tail-cutter forms such as `end:` or terminal return where valid. The physical newline separator is not itself the trailer; it only helps expose the next source item and its level.

For a source item at level N, vertical child arguments are written at level N + 1. A following source item at level N + 1 is one positional child item of that frame/Structure. In a short colon-form, the inline tail fields are also treated as fields at the implicit argument level N + 1. A following source item deeper than N + 1 belongs to the immediately preceding child item only if that child item opens a Structure. Scalar literals and identifier values do not become headers merely because a deeper item follows.

A canonical dotted delimiter line or relaxed dash-fence line at level K may delimit an anonymous positional Structure at level K. If it is followed by source items at level K + 1, it opens such an anonymous Structure. The next delimiter at level K closes the previous anonymous Structure and may open another one when followed by deeper items. A following source item at level K - 1 closes that anonymous Structure by the ordinary one-step cut. A larger cut is not ordinary P0 syntax and requires an admitted tail-cutter layer.

A `colon_frame_body` whose tail is empty must be followed by vertical child fields at the next source level, a canonical dotted delimiter or relaxed dash-fence anonymous Structure delimiter when that is valid in the current parent, or an admitted tail-cutter such as `end: <target>` when the receiver/profile allows an empty frame. Otherwise it is a syntax error.

This grammar is intentionally incomplete around full update semantics, full indexing, full field-follow access, type constructors, literals and relation forms because those areas require final design decisions. Native structural grammar does not include `=` assignment, `=` named-field syntax, bare `end`, `end <target>`, bare non-nullary receiver/callable calls or `case` (not structural syntax) as syntax. The standalone dash-fence line is part of vertical structure syntax as a nameless delimiter: it may open an anonymous positional Structure when followed by a deeper item, separate sibling anonymous Structures, or close/cut an anonymous/implicit section.

Ordinary line arguments are whitespace-separated short-tail fields. A parser must not use receiver signatures to insert hidden nesting while parsing `line_arguments`.

Comma and semicolon have different P0 roles at the current scan depth. Comma is an ordinary explicit field separator, like whitespace without indentation/source-level effects; it may add another field to an open short tail. Semicolon is the explicit separator/trailer: for a short form, it terminates that short form and never adds another field to the open short tail. When no short form is open at the current scan depth, comma is optional conventional separator notation and semicolon may act as an explicit source-item separator or trailing marker. A trailing comma or semicolon with no following item is accepted as a cosmetic trailing marker at any block level, including file/root level 0. A comma or semicolon inside a deeper bounded Structure or compact Frame belongs to that deeper form.

Structural grammar has no separate anonymous-function syntax. A bounded
Structure, compact Frame or vertical anonymous Structure remains Structure data.
The parser never marks a Structure as executable merely because it is nested
inside arguments. Translation or interpretation of that Structure happens only
when the active receiver consumes it under a receiver-defined rule, or when a
compact Frame head resolves through the namespace as a function, subroutine or
registered receiver.

Labels are not a separate structural grammar category. A source line such as `outerLoop:` is a colon frame with an empty inline tail and a required following vertical block. The active receiver/profile decides whether that frame introduces a local nullary executable binding, a control label role, both, or an error. A later bare line such as `outerLoop` is also not special label grammar; in executable statement position it may resolve through the ordinary namespace to that zero-argument label-block binding.

15.1. Structural Semantics in EBNF Form

The following EBNF describes the structural-semantic normal form produced by the
parser. It is not a separate surface syntax and it does not assign binding,
variable, type, field, atom, class, method or execution semantics. Those meanings
are assigned later by receiver consumption, model/class descriptors and the active
level/profile.

The notation uses `Structure(...)` and `Frame(...)` as semantic constructors:

    SourceFile
        ::= RootBlock

    RootBlock
        ::= Block(0)

    Block(K)
        ::= Structure({ BlockElement(K) })

    BlockElement(K)
        ::= FrameElement(K)
         |  ValueElement(K)
         |  ExpressionElement(K)
         |  AnonymousStructure(K)

    FrameElement(K)
        ::= Frame(Head, BodyStructure, FrameTrailer)

    Head
        ::= BareIdentifier
         |  ExactIdentifier
         |  SymbolicHead
         |  ProfileHeadPath

    BodyStructure
        ::= Structure({ Field })

    Field
        ::= FrameElement(current)
         |  ValueElement(current)
         |  ExpressionElement(current)
         |  BoundedStructure
         |  CompactFrame
         |  AnonymousStructure(current)

    ValueElement(K)
        ::= NumericLiteral
         |  StringLiteral
         |  BareIdentifier
         |  ExactIdentifier

    ExpressionElement(K)
        ::= ExpressionStructure

    CompactFrame
        ::= Frame(Head, BoundedBody, RPAREN_BOUNDED)

    BoundedStructure
        ::= Structure({ BoundedElement }, RPAREN_BOUNDED | RBRACKET_BOUNDED)

    BoundedElement
        ::= FrameElement(bounded)
         |  ValueElement(bounded)
         |  ExpressionElement(bounded)
         |  CompactFrame
         |  BoundedStructure

    AnonymousStructure(K)
        ::= Structure({ BlockElement(K + 1) })

This semantic EBNF is read with these structural rules:

    ShortTail
        ::= Field { (HorizontalSpace+ | COMMA_SEPARATOR) Field }
            [ COMMA_SEPARATOR ]

    BoundedBody
        ::= [ BoundedElement { BoundedSeparator BoundedElement }
             [ BoundedSeparator ] ]

    BoundedSeparator
        ::= HorizontalSpace+
         |  COMMA_SEPARATOR
         |  SEMICOLON_SEPARATOR
         |  NewlineSourceComposition

    FrameTrailer
        ::= SEMICOLON_SHORT
         |  RPAREN_BOUNDED
         |  RBRACKET_BOUNDED
         |  LEVEL_DROP
         |  DELIM_NAMELESS
         |  RECEIVER_TRAILER
         |  EOF_TRAILER

    RECEIVER_TRAILER
        ::= END_NAMED
         |  UNTIL_CLOSE
         |  TERMINAL_RETURN
         |  ProfileTrailer

Comma and semicolon semantics:

    COMMA_SEPARATOR appends/separates fields in the open ShortTail. It never
    terminates the current open short form.

    SEMICOLON_SHORT never appends a field to the open ShortTail. It terminates
    the current open short form at any scan depth.

    When no short form is open at the current scan depth, comma may act as
    ordinary separator notation and semicolon may act as an explicit source-item
    separator or cosmetic trailing marker.

Physical newline semantics:

    Physical newline is not a short-form trailer. It ends the physical line.
    If the next source item is at the open short form's implicit argument
    level, that item continues the open short form. If the next source item is
    at the short form's own source level or smaller, the short form is complete
    and ordinary sibling/level-close rules apply.

Bounded delimiter semantics:

    RPAREN_BOUNDED closes the current parenthesized BoundedStructure or
    CompactFrame. RBRACKET_BOUNDED closes the current bracketed
    BoundedStructure. If a short form is open inside that bounded form, that
    short form is completed as part of closing the bounded context, and then
    the bounded form itself is closed.

Source-level semantics:

    A line at source level K + 1 is a child field of the current item at level K.
    A line at source level K - 1 closes the current open Structure by the
    ordinary one-step cut. Larger decreases require an admitted tail-cutter
    layer.
    A delimiter at level K may open an AnonymousStructure(K) when followed by
    items at K + 1, or close/separate the current anonymous or implicit section
    at level K.

Receiver semantics:

    Frame(Head, BodyStructure, FrameTrailer) is still only data after parsing.
    The receiver named by Head consumes BodyStructure and assigns semantic roles
    to positional fields, anonymous Structures, named child Frames, labels,
    operators, declarations, model descriptors, message/table descriptors and control
    trailers. The parser does not infer those meanings from spelling alone.

16. Canonical Examples

16.1. Hello World

Source:

print: "Hello World"

Full form:

L3:
    print: "Hello World"
end: L3

Normal form:

L3(
    print("Hello World")
)

Shortest form:

print: Hello World

`Hello` and `World` are accepted only if the active L3 `print` receiver and lexical rules allow bare atoms/symbols in that position.

16.2. Function with Structural Return

Source:

fn: estimateHarvest (PlantBed(bed)) (f32(harvest), f32(redApples), f32(greenApples))
    if: bed\crop = Apples
        return: bed\area * 1.7 bed\area * 1.7 bed\area * 1.1
return: bed\area 0 0

Semantic outline:

    `fn` consumes a definition Structure.
    `PlantBed: bed` is a typed/model constructor Structure if `PlantBed` is registered.
    The return Structure has three named fields.
    `if` consumes condition and body Structures.
    The inner `return:` exits with the Apple-specific structural result.
    The final `return:` is terminal return. It supplies the default structural result and closes the function definition.

16.3. Explicit Return with Named Return Variables

Source:

fn: estimateHarvest (PlantBed(bed)) (f32(harvest), f32(redApples), f32(greenApples))
    harvest: bed\area
    redApples: 0
    greenApples: 0
return: harvest redApples greenApples

Semantic outline:

    Named return fields are local return variables.
    Head/update position updates existing bindings.
    Terminal `return:` exits, returns their current values as one return Structure and closes the function definition.

16.3.1. Recursive Function with Terminal Return

Source:

fn: factorial (int(n)) (int)
    if: n <= 1
        return: 1
return: n * factorial(n - 1)

Semantic outline:

    `return: 1` is a runtime return inside the `if` branch.
    In expression position, `factorial(n - 1)` is a recursive call.
    The final `return:` supplies the recursive result and closes the function definition.

18.1. Source-Semantic or Syntax Uncertainties

18.3. ANSI C Implementation Variants

---ANSI C---
These variants are implementation notes for a possible ANSI C based translator.
They are not part of Lingvamyxa source semantics.

Call lowering:

variant 1:
Pass a small number of primitive/reference fields directly in internal generated C functions.

variant 2:
Pass an args Structure address/handle when the logical argument Structure is large or dynamic.

variant 3:
Generate specialized adapters, inline calls or eliminate physical args Structures when observable source semantics are preserved.

Return lowering:

variant 1:
Return a single primitive as a direct C primitive value.

variant 2:
Return multi-field results through caller-provided output storage.

variant 3:
Return small Structures by value where the implementation profile allows it.

variant 4:
Return handles/addresses to runtime-managed Structures for dynamic or large results.

Destructuring lowering:

variant 1:
Store the returned Structure or handle in a temporary service variable and update target variables from its fields.

variant 2:
For known layouts, generate direct field-follow access.

variant 3:
For dynamic layouts, generate checked accessors or runtime lookup.

Field and array lowering:

variant 1:
Known field-follow access lowers to direct C struct or pointer access.

variant 2:
L2 indexing lowers to computed-address access under the L2 memory model.

variant 3:
L3+ indexing lowers to checked access through array metadata such as `len`.

The language does not define C slot counting, hidden runtime addresses, hidden output addresses or C storage ownership rules. Those are translator/runtime design choices.
---ANSI C---

19. L3 Control Operators

19.0. Scope of This Section

This section defines the normative L3 control-flow receiver set for executable bodies.

The operators in this section are source-level control receivers. They are not raw low-level jumps. A translator may lower them to branches, labels, hidden control-result Structures, cleanup-stack operations or other implementation artifacts.

Unless stated otherwise, these operators are L3 operators. Some of them may also be exposed in L2 by an implementation profile, but this section specifies the L3 semantics.

Operator summary:

    0.  if / then / else                                  L3
    1.  match / default-pattern receivers                            L3
    2.  while                                             L3
    3.  until                                             L3
    4.  for                                               L3
    5.  each                                              L3
    6.  return                                            L3 executable body; terminal executable close at definition level
    7.  break                                             L3 loop frame
    8.  continue                                          L3 loop frame
    9.  finally                                           L3 executable/scope frame cleanup
    10. guard / fail / throws / failure labels / handlers  L3 recoverable failure flow
    11. retry / retryable                                 L3 retry frame
    12. assert                                            L3 diagnostic failure flow
    12a. log / error                                      L3 observation receivers
    13. redo                                              L3 loop frame
    14. yield                                             L3 iterator-profile fn
    15. labelled break / labelled continue                L3 labelled loop frame

Labels are written as ordinary colon frames such as `outerLoop:`. A profile may materialize such a frame as a local nullary executable binding, a labelled control/block target, or both. A bare line such as `outerLoop` in executable statement position may resolve through the ordinary namespace to that zero-argument label-block binding and consume/call it. Control-transfer receivers such as `break:` and `continue:` resolve their target to the labelled control/block role of the same visible binding. The parser does not need a separate label grammar category.

19.1. `if`, `then` and `else`

`if` consumes a condition and one or two statement Structures.

Semantic form:

    if(condition, thenBody, elseBody?)

Explicit form:

if: condition
    then:
        thenBody
    else:
        elseBody
end: if


Short positional form:

if: condition
    thenBody

    elseBody

Nested short positional form:

    if: condition
        thenBody
    ---
        elseBody
    ---

Nested explicit `else` form:

    if: condition
        thenBody
    else:
        elseBody
    ---


Single-line form:

    if: condition doSomething

The condition is evaluated once before branch selection.

Only the selected body is executed.

If no `else` body is provided and the condition is false, `if` completes normally without executing a body.

In named form, `then` and `else` are structural section markers inside `if`. They are not ordinary runtime calls when consumed by the `if` receiver. In positional form, sibling child Structures are mapped to `thenBody` and `elseBody` by receiver signature order.

19.2. `match` and default-pattern receivers

`match` selects one body from a set of positional pattern/body pairs or from anonymous branch Structures. `case` (not structural syntax) is not structural syntax.

Simple positional example:

match: value
    1
    print: one
    2
    print: two
    default
    print: other
    ---

Conceptual argument stream:

    match(value, 1, print(one), 2, print(two), default, print(other))

The `match` receiver may interpret the tail after `value` as repeating `(pattern, branch)` pairs. `default` is an ordinary atom/receiver-defined pattern value, not a parser keyword.

Block branch example:

match: value
    1
    ---
        print: one
        log: matched one
    ---
    2
    ---
        print: two
        log: matched two
    ---

Conceptual argument stream:

    match(
      value,
      1,
      (print(one), log(matched one)),
      2,
      (print(two), log(matched two))
    )

Anonymous branch Structure example:

match: value
    ---
        1
        print: one
    ---
        2
        print: two
    ---
        default
        print: other
    ---

Conceptual argument stream:

    match(
      value,
      (1, print(one)),
      (2, print(two)),
      (default, print(other))
    )

There is no automatic fallthrough from one branch to the next unless the active `match` receiver explicitly defines such behavior.

For union values, a `match` may destructure the active variant by ordinary pattern Structures.

Example:

match: shape
    ---
        Circle c
        drawCircle: c
    ---
        Square s
        drawSquare: s
    ---

If the matched value is a closed union and no default pattern is present, an implementation may require exhaustive patterns.

19.3. `while`

`while` is a pre-condition loop.

Semantic lowering shape:

    while(condition, statementStructure)

Example:

while: i < n
    print: i
    i: i + 1


The condition is evaluated before each iteration.

If the condition is false before the first iteration, the body is not executed.

A `while` body is a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

19.4. `until`

`until` is a conditional close for the current executable block. It closes the current block, executes that block as a post-condition loop body, then evaluates its condition.

Semantic form:

    until(currentStatementStructure, condition)

Labelled example:

readLoop:
    readNext: record
    process: record
until: endOfInput(record)

In this example, `until:` closes the labelled executable block `readLoop`. The condition is the boolean-producing Structure `endOfInput(record)`. The name `readLoop` is also the local nullary executable binding for the block, as described in section 7.6.

The body is executed first. The condition is evaluated after the body.

The loop repeats until the condition is true. If the condition is false, control transfers to the beginning of the block closed by `until`.

`until` creates a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

19.5. `for`

`for` is a controlled loop receiver for numeric ranges, counters, index ranges or other bounded iteration policies.

Compact counter/triplet form:

for: int(i, 0) (i < n) i++
    print: i


The first three arguments are consumed as loop-control fields:

    init      -> initialization Structure
    condition -> boolean-producing expression
    step      -> iteration-step statement Structure

The vertical child Structure is consumed as the loop body.

Single-line compact body form:

    for: int(i, 0) (i < n) i++ print(i)

In this form, `print(i)` is the fourth argument. The `for` receiver signature
consumes that fourth argument as its statement tail, so it lowers as the loop
body. The token form `i++` is valid only in profiles that register it as an
operator-token form.

Range-style example:

for: i 0 n
    print: i


Semantic requirement:

    `for` creates one or more loop-local iteration bindings.
    `for` advances those bindings according to the selected control policy.
    `for` executes the body once for each produced iteration state.

`for` creates a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

?
The compact counter/triplet form is specified above. Other source forms for numeric ranges, inclusive/exclusive bounds, step values, reverse iteration, index/value pairs and destructuring of iteration bindings are not specified in this section.
?

variant 1:
Use compact positional forms such as `for(i, 0, n)`.

variant 2:
Use explicit short-tail fields such as `for: i 0 n 1`, or use a future exact-identifier/profile descriptor only when the `for` receiver explicitly defines that descriptor shape.

variant 3:
Treat all range policies as ordinary receiver Structures consumed by `for`.

19.6. `each`

`each` iterates over a container or iterator-compatible Structure.

Array-like example:

each: item in items
    draw: item


Receiver-like example:

each: items item
    draw: item


Semantic requirement:

    `each` obtains a sequence of values from its source.
    For each value, `each` binds the iteration variable or variables.
    `each` executes the body once for that value.

`each` creates a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

For arrays or array-like containers, `each` may lower to an index loop.

For iterator-compatible Structures, `each` repeatedly calls the iterator `next(env)` implementation until no value is produced.

In the source form:

    each: item in source

the `source` field is consumed by the `each` receiver as an iteration source. If `source` resolves to a container, `each` iterates over that container. If `source` resolves to an iterator-compatible Structure, `each` consumes that iterator-compatible Structure. If `source` resolves to a visible zero-argument iterator function, `each` may consume the callable binding by creating its iterator state, equivalent to the explicit compact form `source()`.

Therefore both forms are valid for a zero-argument iterator source:

    each: word in words
    each: word in words()

The first form lets `each` consume the callable binding as an iterator source. The second form explicitly creates the iterator state Structure before `each` consumes it. This is receiver consumption of an already parsed field; it is not hidden receiver-signature grouping.

Iterator consumption by `each` is specified in section 19.15.5.

19.7. `return`

`return` exits the current `fn`, `sub` or executable-like body.

Runtime forms inside an executable body:

    return
    return: value

For an `fn`, `return: value` consumes a compatible primitive or Structure value and exits. A bare `return` is not a valid `fn` return in the core profile.

For a `sub`, `return` exits the `sub` body. `return: value` is invalid for `sub` unless a later profile defines status/result subroutines.

At a valid terminal trailer position for the open executable definition, an admitted return form is terminal return. It appends the corresponding runtime return as the final body item and closes the executable definition. For an `fn`, this terminal form is `return: value`; for a `sub` or no-value label/procedure executable, this terminal form may be bare `return`. This is an executable-specific close, not a general replacement for `end: name`.

For a definition opened by `fn: name` or `sub: name` at level N, the source level of the definition is N. An admitted return form at level N is the common terminal structural trailer. The same return form at level N + 1 or deeper is an ordinary runtime return inside the body. A return form at a smaller source level may still be terminal return when the normal source-level cut reaches the visible executable tail and the intervening frames admit that closure. See section 8.3.

Examples:

fn: square (int(x)) (int)
return: x * x

fn: factorial (int(n)) (int)
    if: n <= 1
        return: 1
return: n * factorial(n - 1)

Before control leaves the current executable frame, all `finally` cleanups registered for the exited scopes are executed in reverse registration order.

19.8. `break`

`break` exits the nearest active loop frame.

Example:

while: running
    if: stopRequested
        break
    ---
    step


`break` is valid only inside a loop frame unless a labelled form is used as described in section 19.15.

Before control leaves the exited loop body scopes, all affected `finally` cleanups are executed in reverse registration order.

`break` is not a source-level raw jump. It is a structured loop-frame exit.

19.9. `continue`

`continue` starts the next iteration of the nearest active loop frame.

Example:

each: item in items
    if: skip item
        continue
    ---
    process: item


For `while`, `continue` transfers control to the next condition check.

For `until`, `continue` transfers control to the post-body condition check for the current iteration.

For `for`, `continue` transfers control to the next iteration-state update.

For `each`, `continue` transfers control to the next container or iterator value.

Before control leaves the current loop body scopes, all affected `finally` cleanups are executed in reverse registration order.

19.10. `finally`

`finally` registers cleanup code in the current execution context.

Block form:

finally:
    cleanupBody


Single-line form:

    finally: cleanupCall

`finally` is not part of a `try` block in this specification. It is a standalone cleanup registration operator.

A cleanup registered by `finally` is associated with the current executable/scope frame.

Cleanups are executed when their associated frame or scope is exited by:

    normal completion;
    return;
    break;
    continue;
    labelled break;
    labelled continue;
    fail;
    retry;
    redo;
    assert diagnostic exit;
    thread/task termination in the default runtime profile.

Cleanups are executed in reverse registration order.

A cleanup body is executed outside the registration operation. It is not executed at the point where `finally` is encountered, except when the frame exits immediately after registration.

`finally` cleanups are part of the execution context model defined in Part II section 11.

!!!
The exact semantics of a cleanup failure are not fixed. A final runtime specification must define what happens if a cleanup itself executes `fail`, `assert`, `return`, `break`, `continue`, `retry`, `redo` or another `finally` registration while cleanup processing is already active.
!!!

19.11. `guard`, `fail`, `throws`, failure labels and handlers

`guard` and `fail` define declared recoverable failure flow.

They are distinct from `assert`.

    guard / fail:
        declared, expected, recoverable failure path

    assert:
        diagnostic invariant violation

19.11.1. `throws`

An executable definition may declare failure labels with `throws`.

Example:

fn: parseInt (Text(text)) (int)
    throws:
        ParseError
    ---

    guard: validInteger text
        fail: ParseError text
    ---

    parseInt: parseInteger text


`throws` lists the failure labels that may leave the executable body as recoverable failures.

A caller must handle, propagate or remap a declared failure.

19.11.2. `guard`

`guard` executes its failure body when its condition is false.

Example:

guard: radius > 0.0
    fail: InvalidRadius radius


Semantic form:

if: not condition
    failureBody


`guard` is a convenience control receiver. It does not itself define the failure transport mechanism. That is defined by `fail`.

19.11.3. `fail`

`fail` exits the current executable body with a declared failure label and optional payload.

Example:

    fail: ParseError text

Semantic effect:

    set failure label to ParseError;
    set failure payload from the remaining arguments;
    execute affected finally cleanups for the current frame exit;
    return a structured failure result to the caller or visible handler.

`fail` is part of the declared `throws` set. It is not a diagnostic abort.

`fail` does not transfer to the thread diagnostic root.

`fail` does not use the `assert` channel.

19.11.4. Failure labels and handlers

Failure labels are ordinary source labels consumed under failure-control semantics. A profile may keep a separate lookup table for diagnostics and control transfer, but the surface grammar is still the same colon-frame grammar.

A handler consumes a failure label and payload.

The exact handler surface syntax is not finalized in this section.

variant 1:
Use label-like handler syntax:

ParseError:
    Text: badText

    print: badText


variant 2:
Use explicit receiver syntax:

handler: ParseError
    Text: badText

    print: badText


variant 3:
Represent handlers as L5 event/message handlers for failure events.

!!!
The exact source syntax, placement, visibility and lifetime of failure handlers are not fixed. A final source specification must define whether handlers are lexical Structures, executable labels, L5 event handlers, caller-side receivers or a combination of these forms.
!!!

19.11.5. Failure propagation

If a failure is not handled in the current body, it must be propagated by an enclosing or calling executable whose `throws` declaration includes the failure label.

Failure propagation is structured. It is not a raw jump through arbitrary stack frames in the source semantics.

---ANSI C---
A translator may lower declared failures using:

variant 1:
Return-status wrappers.

variant 2:
Status return plus output parameters.

variant 3:
A hidden control-result channel.

variant 4:
A non-local transfer mechanism for a selected runtime profile, provided that Lingvamyxa `finally` semantics are preserved.

The strict default for this draft is structured failure propagation, not root-level `longjmp`.
---ANSI C---

19.12. `retry` and `retryable`

`retryable` defines a restartable frame.

`retry` restarts the nearest or named retryable frame.

Example:

loadAttempt:
    retryable:
        loadNetworkData
    ---

Possible failure-handler use:

NetworkError:
    reconnect
    retry: loadAttempt


A `retry` transfer executes the affected `finally` cleanups for the abandoned attempt before re-entering the retryable frame.

`retry` does not roll back external side effects. It only repeats the source frame according to the retryable-frame semantics.

Local bindings declared inside the retryable frame are re-created when the frame is re-entered.

Outer bindings keep their current values unless the retryable receiver defines a stronger rollback policy.

`retry` without a label targets the nearest active retryable frame.

`retry: labelName` targets the named retryable frame.

!!!
The exact interaction between `retry`, failure handlers, iterator frames, partially executed cleanups and mutable outer bindings requires a final rule. This draft defines retry as re-execution, not as transactional rollback.
!!!

19.13. `assert`

`assert` checks a diagnostic invariant.

Example:

    assert: index >= 0
    assert: index < values\len

If the condition is true, execution continues normally.

If the condition is false, the current execution/checking phase fails with an `AssertionViolation` diagnostic.

`assert` is not recoverable `fail` control flow.

`assert` is not part of the declared `throws` set.

`assert` is not caught by failure labels or failure handlers.

Default L3 runtime semantics in the thread profile defined in Part II section 11:

    record AssertionViolation diagnostic;
    execute all active `finally` cleanups in the current thread ExecutionContext;
    transfer control to the thread diagnostic root;
    terminate the current thread/task by default after reporting the diagnostic.

Default L4 model-time use, if exposed by a level profile:

    an assertion violation terminates the current model-loading or translation pass with a diagnostic error.

`assert` is intended for impossible states, broken invariants, corrupted internal assumptions or translator/model errors. Expected input failure must use `guard` and `fail`.

19.13.1. `log` and `error`

`log` and `error` are observation receivers.

Canonical forms:

    log: value
    error: value

The tail may be a constant/literal value or a name visible in the active local
namespace view. The receiver consumes the resolved value and records it through
the active observation profile.

Examples:

    log: "matched one"
    log: matchedValue
    error: "parse failed"
    error: diagnostic

`log` records an ordinary observation, trace, note, audit event, metric payload
or profile-defined informational record.

`error` records an error/diagnostic observation. It is not reserved parser
syntax and it is not automatically equivalent to `fail`, `assert`, `return` or
thread termination. If a profile wants an error observation to also fail,
abort, throw, send an L5 failure message or terminate a task, that behavior must
be defined by that profile or by an explicit surrounding receiver.

Both receivers use ordinary namespace resolution for non-literal tails. A bare
unknown name is not magically logged as text unless the active profile admits
such symbol logging explicitly. Write a string/exact identifier when the source
wants a literal textual record.

19.14. `redo`

`redo` repeats the current loop iteration without advancing the loop source.

For `each`, `redo` repeats the body with the same current element.

For iterator-based `each`, `redo` does not call `next(env)` before repeating the body.

For `for`, `redo` repeats the body with the same loop bindings.

For `while`, `redo` repeats the body without re-evaluating the condition first.

For `until`, `redo` repeats the body without evaluating the post-condition first.

Before the current iteration is restarted, all `finally` cleanups registered inside the abandoned iteration attempt are executed.

`redo` is dangerous because it can create non-progressing loops. It is valid only inside a loop frame.

19.15. `yield`

`yield` is valid only inside an `fn` whose return descriptor defines a yield-protocol.

The standard iterator-like profile is expressed by ordinary namespace names:

    iterator(T)

Here `iterator` and `T` are not parser keywords. They are ordinary identifier
values resolved in the active lexical namespace view by the active L3/profile
receiver set. For example, `Text` or `Point` must be visible type/model names if
they are used in `iterator(Text)` or `iterator(Point)`.

Calling a function with an iterator-compatible return descriptor does not execute its body to completion. It creates an iterator state Structure.

The translator lowers the iterator body into a `next(env)` implementation.

Each `yield` consumes one produced value. It inspects the current function's return descriptor, verifies that the descriptor defines a yield-protocol, checks the produced value against that protocol, emits one value from `next(env)` and records the resume state in `env`.

The `each` receiver consumes iterator-compatible Structures by repeatedly calling their `next(env)` implementation until no value is produced.

This is the standard lazy-production protocol for sequences. A call to an
iterator-compatible function creates a resumable state Structure; it does not
force every later produced value immediately. One consumer step asks for one
value, `next(env)` runs until the next `yield` or termination, then the state is
saved for a later step.

For example:

    fn: words () iterator(Text)
        yield: "Hello"
        yield: "World"
    end: words

is not source-semantically:

    words() -> Array("Hello", "World")

It is:

    words() -> iterator state Structure
    next(env) -> "Hello"
    next(env) -> "World"
    next(env) -> noValue

Therefore `yield` provides demand-driven production:

    one value now;
    state saved;
    next value later;
    later value may never be requested.

This does not make all Lingvamyxa evaluation globally non-strict. Without a
receiver/profile that admits deferred consumption, an expression such as:

    print: expensive()

is ordinary value-producing input to the `print` receiver, not automatically a
thunk. Laziness is attached to descriptors, receivers and registry protocols.
Examples of such profiles may be:

    iterator(T)  zero or more T, forced by next(env);
    stream(T)    zero or more T, possibly asynchronous, forced by next/awaitNext;
    thunk(T)     one deferred T, forced by value(thunk) or an equivalent receiver;
    future(T)    one scheduled/deferred T or failure, forced by await(future);
    continuation(T) profile-defined resumable computation.

The common rule is that Structures are data until a receiver consumes them. A
lazy profile is a receiver/descriptor/table protocol that decides when to
consume the next step. This is different from Haskell-style global laziness:
Lingvamyxa does not make every argument and every data field lazy by default.
That keeps effects, ownership, validation and message scheduling explicit.

19.15.1. Iterator function

Example:

fn: makePoints () iterator(Point)
    yield: Point(1.0 2.0)
    yield: Point(3.0 4.0)
    yield: Point(5.0 6.0)
end: makePoints

Another zero-argument example:

fn: words () iterator(Text)
    yield: "Hello"
    yield: "World"
end: words


Calling:

    makePoints()

creates an iterator state Structure. It does not return an `Array Point` and does not execute all `yield` statements immediately.

P0 reads the first definition structurally as a plain `fn` frame:

    fn(
      makePoints,
      (),
      iterator(Point),
      yield(Point(1.0 2.0)),
      yield(Point(3.0 4.0)),
      yield(Point(5.0 6.0))
    )

The `fn` receiver consumes field 2 as the return descriptor and fields 3..end as the executable body. The `yield` receiver then checks each produced value against the yield-protocol declared by the current function return descriptor.

19.15.2. Iterator state Structure

An iterator state Structure contains enough state to resume execution after each `yield`.

For a simple iterator, generated state may include:

    state index;
    captured arguments;
    local variables that survive across yields;
    cleanup registrations owned by the iterator frame;
    a reference to the generated `next(env)` implementation.

Source-level code does not depend on the physical layout of this state Structure.

19.15.3. `next(env)`

The generated `next(env)` implementation executes the iterator until it either reaches a `yield` or terminates.

At a `yield`, `next(env)` returns a produced value and records where execution must resume.

When the iterator terminates, `next(env)` returns a no-value result.

Conceptual result model:

Next: T
    boolean: hasValue
    T: value


?
The exact standard name and structural layout for the result of `next(env)` is not specified. A final iterator specification must choose canonical names and fields, such as `Next T`, `Option T`, `Some/None` or another equivalent representation.
?

19.15.4. `yield` value construction

For the `iterator(T)` profile, the canonical source form is:

    yield: value

The current `fn` return descriptor, such as `iterator(T)`, tells `yield` which yield-protocol is active. The `yield` tail is the produced value. The `yield` receiver checks whether that value is compatible with `T`.

There is no hidden flattening. If `value` itself has an iterator type, then `yield: value` yields that iterator value as the produced value when the active protocol admits it. Flattening or forwarding another iterator requires a separate receiver such as `yieldFrom`.

If `T` is primitive, `value` is checked against that primitive type:

    fn: words () iterator(Text)
        yield: "Hello"
    end: words

If `T` is structural, write the produced Structure explicitly:

    fn: makePoints () iterator(Point)
        yield: Point(1.0 2.0)
    end: makePoints

inside an `iterator(Point)` function emits one `Point` value if `Point(1.0 2.0)` is a valid Point construction in the active profile.

19.15.5. Iterator consumption by `each`

Example:

each: point in makePoints
    draw: point

For a zero-argument iterator function, the source may also be written as an explicit compact call:

each: point in makePoints()
    draw: point

Both forms are valid. The bare form gives the callable binding to `each` as an iterator source; the compact-call form creates the iterator state Structure first and gives that Structure to `each`.

Semantic form:

iterator: makePoints

while: true
    result: next iterator\env
    if: not result\hasValue
        break
    ---
    point: result\value
    body


This is semantic pseudocode. A translator may lower it to a direct state machine or inline loop.

19.15.6. Iterator termination

An iterator-like `fn` terminates when its generated `next(env)` reaches the end of the executable body or reaches a profile-defined completion path.

A `yield` after termination is unreachable.

In the core profile, a bare `return` is not a valid `fn` return. If an iterator profile wants an explicit early iterator-completion operator, it must define that receiver/profile rule separately. `return: value` remains an ordinary `fn` runtime return form when admitted by the function's return descriptor; when written in a terminal trailer position, it may also close the `fn`.

`break` and `continue` inside an iterator body operate on the nearest active loop frame inside the iterator body, not on the consumer's `each` loop.

!!!
Iterator close semantics are not fully specified. A final specification must define when iterator-owned `finally` cleanups run if an iterator is abandoned before exhaustion, discarded, moved to another thread or terminated by diagnostic failure.
!!!

19.16. Labelled `break` and labelled `continue`

A control label may be attached to a loop frame.

Example:

outerLoop:
    for: row in rows
        for: cell in row
            if: found cell
                break: outerLoop
            ---
        ---
    ---

`labelName:` is an ordinary colon frame that the active profile materializes as a visible control target for the following block.

The label name is visible in the ordinary namespace as a control target, but it
is not callable merely by being mentioned. A standalone `labelName` item is a
compile-time error in the default profile: Lingvamyxa has no implicit `goto`.
Only control forms that define label consumption, such as `break: labelName`,
`continue: labelName`, failure handlers or other profile-defined control
operators, may consume a label as a target.

`break: labelName` exits the labelled loop frame.

`continue: labelName` continues the labelled loop frame if the target label names a loop frame.

Before the transfer, all `finally` cleanups registered in scopes exited by the transfer are executed in reverse registration order.

It is a compile-time error for `break: labelName` or `continue: labelName` to target a label that is not visible in the control-label scope.

It is a compile-time error for `continue: labelName` to target a non-loop frame.

?
The exact grammar rule for attaching labels to frames is not specified beyond the form `labelName:` before a frame. A final grammar must define whether labels can attach to retryable frames, blocks, handlers, iterator frames and arbitrary Structures.
?

20. L2 Primitive, Address and Parser Operators

20.0. Scope of This Section

This section defines the minimal L2 operator/parser-form set.

L2 has primitive values, typed address values and Structures/descriptors. Aggregate model names denote layouts or descriptors. Storage and allocation forms produce typed address values. Receiver signatures and parser profiles assign final semantics to the Structures built from source syntax.

The minimal L2 profile therefore has no separate source syntax for C-style
direct aggregate value access. Primitive/scalar values may be direct; aggregate
values are storage/layout objects and are normally reached by address. This
keeps `u32: x` simple while preventing an embedded record from silently becoming
a copyable whole-Structure expression.

This section is deliberately smaller than the L3 control set in section 19. L2 is low-level and unsafe, but it does not need every L3 convenience operator by default.

20.1. Pointer and Field Syntax Exclusions

L2 does not use `*`, `&`, `^`, `.`, or `->` as pointer/field syntax.

This rule should be stated once as an L2 invariant instead of repeated at every address example.

Consequences:

    `*`  remains available as a multiplication operator token.
    `&`  is not address-of.
    `^`  is not pointer dereference and is not a field-follow marker.
    `.`  is source indentation only when it appears in the leading dot prefix; it is not field access.
    `->` is not a Lingvamyxa field-follow operator.

L2 address and field forms are:

    @ⁿ: T x     reserved address-depth declaration head, for example `@@@: int ppp`
    @x          address of storage location `x`
    \x          raw load from address expression `x`
    x\field     typed field-follow through address/reference `x`
    x[i]        indexed access through address/reference/container `x`

Field-follow and index chains bind tighter than prefix `@` and prefix `\`.

The C-profile mnemonic table in section 11.3 shows how the L2 forms cover the C declarator/expression roles of `*`, `&` and `->` without using those tokens as Lingvamyxa pointer/field syntax.

20.2. Storage, Address and Indexed Forms

Minimal L2 storage/allocation and address-slot forms:

    stack: Layout name
    heap: Layout name
    static: Layout name
    Primitive: name [initialValue]
    []: ElementType name size [initialValue...]
    @ⁿ: BaseType name

Examples:

stack: PlantBed branch
heap: PlantBed tree
static: PlantBed root
int: count 5
[]: int leafs count
@: int p
@@: int pp
@@@: int ppp

Meanings:

    branch  typed address of stack storage with layout `PlantBed`
    tree    typed address of heap storage with layout `PlantBed`
    root    typed address of static storage with layout `PlantBed`
    count   primitive storage/value initialized to `5`
    leafs   indexed storage/container descriptor for `count` primitive cells, according to the active L2 profile
    p       address-depth-1 slot to base type `int`
    pp      address-depth-2 slot to base type `int`
    ppp     address-depth-3 slot to base type `int`

The first ANSI C bootstrap projection accepts an explicit element type:

    []: int values 3 1 2 3
    []: @ int pointers 2 @ a @ b

which may lower to:

---ANSI C---
int values[3] = {1, 2, 3};
int *pointers[2] = {&a, &b};
---ANSI C---

The leading `@` fields before the element type are address-depth fields for the
array element type, not separate values. Higher profiles may define richer
container descriptors, ownership policies and allocation receivers over the same
surface form.

Names that contain spaces use exact quoted identifiers as ordinary fields:

stack: PlantBed `second branch`

This allocates stack storage with layout `PlantBed` and introduces the exact quoted name `second branch`.

The same short-tail whitespace rule applies to address-depth declarations:

@@@: int ppp

This declares `ppp` as an address-depth-3 slot with base type `int`. The spelling `@@@: int, ppp` is the same declaration with an explicit comma field separator. The spelling `@@@: int; ppp` is different: the semicolon terminates the `@@@:` short form after `int`, so `ppp` is no longer the binding-name field of that declaration. The following `ppp` is parsed as the next source item at the current level.

20.2.1. Named Structures and ANSI C `typedef struct` Projection

At L2, an ordinary named vertical Structure at top level declares one ordinary
Lingvamyxa namespace entry. It is not a second type namespace and it is not C
syntax in the source. It is just a named Structure. Because that Structure has
the same shape as an ANSI C record layout, an ANSI C projection may lower it to
`typedef struct`.

Example:

L2:
    LmTransSymbol:
        LmP0Text: name
        LmTransSymbolKind: kind
        unsigned: depth
    end: LmTransSymbol
end: L2

One possible ANSI C projection:

---ANSI C---
typedef struct LmTransSymbol LmTransSymbol;

struct LmTransSymbol {
    LmP0Text name;
    LmTransSymbolKind kind;
    unsigned depth;
};
---ANSI C---

The field head is consumed by the L2 projection as the field descriptor. It may
name another ordinary Lingvamyxa Structure, an explicit `c.name`, or a future
callable/method descriptor if the profile defines such a descriptor form. Merely
mentioning that descriptor does not call it. The general rule remains the same:
a Structure is not executed because it exists; it is consumed by the active
translator/profile mode.

20.2.2. L1 and L2 Translator Receivers

`L1` and `L2` are ordinary translator receivers that consume one body Structure.
Since a Structure contains an ordered field sequence, this is enough to consume
any number of source fields.

The `L1` receiver walks its body fields in order. If a field is a string/payload
atom, `L1` writes that payload at the current generated L1 position. This rule is
not tied to one spelling: ANSI-style strings, python-like quoted raw strings and
block strings are all string payload forms. If a field is a Lingvamyxa Structure
or Frame, `L1` dispatches it back to the translator. Thus an `L2` frame can be
nested inside `L1`, and an `L1` implementation fragment can be nested inside
`L2`.

A hosted ANSI C bootstrap profile may provide small L1-output receivers at the
root level and inside `L1`. These receivers are translator conveniences, not
high-level language classes.

Example:

include: "<stdio.h>" "<windows.h>" "parser.lm1.h"

This writes:

---ANSI C---
#include <stdio.h>
#include <windows.h>
#include "parser.lm1.h"
---ANSI C---

An include string whose payload is already enclosed in `<...>` or `"..."` is
copied as the C include target. Otherwise the payload is treated as a local
quoted include target.

An `os` receiver may select L1 output branches by target platform:

os:
    win:
        include: "<direct.h>" "<windows.h>"
    unix:
        include: "<unistd.h>"
    default:
        "/* fallback L1 text */"
end: os

The bootstrap profile may lower these branch heads to target preprocessor
conditions such as `_WIN32`, `__APPLE__` or `__unix__`. The branch
body is still ordinary L1-output content: string payload, `include`, nested `os`
or another translator receiver admitted by the profile.

The `L2` receiver also consumes one body Structure, but it does not print
standalone strings as ANSI C. The rule is relative to the Structure being
translated to ANSI C: if a string field appears at level 0 of the body that `L2`
is asked to translate, and no receiver consumes that field, it is a compile-time
error. Nested Structures owned by another receiver are not reclassified by this
generic rule; that receiver defines what its own body fields mean. If a receiver
asks `L2` to translate such a nested Structure, the same level-0 rule applies
again inside that translated body. This is a phase error of the active consumer:
for `L2` it is reported by the compiler/translator, while an interpreter profile
would report the corresponding error in its own execution phase. The `c.name`
form is likewise consumed by the `c` receiver/projection: it prints an ANSI C
ordinary identifier only at the position where that explicit receiver is used.

Example:

L2:
    L1:'''typedef enum LmTransSymbolKind {
        LM_TRANS_SYMBOL_VARIABLE = 1,
        LM_TRANS_SYMBOL_FUNCTION = 2,
        LM_TRANS_SYMBOL_PROCEDURE = 3,
        LM_TRANS_SYMBOL_LABEL = 4,
        LM_TRANS_SYMBOL_STRUCTURE = 5
    } LmTransSymbolKind;'''

    fn: main () int
        return: c.LM_TRANS_SYMBOL_VARIABLE
    end: main
end: L2

The enum constants are not imported into the Lingvamyxa namespace. They remain
ordinary ANSI C names and are referenced explicitly through the permanent C
surface escape, for example `c.LM_TRANS_SYMBOL_VARIABLE`.

When a bootstrap translator reads external registry data, such as
`lm2/trans_registry.lmx`, class/key spelling follows the same identifier rule as
ordinary source names. If the class/key is a valid ordinary Lingvamyxa
identifier, it is written bare:

    u32
    return
    prefix
    sqrt_ansi_c

If the class/key contains operator characters, dots, arrows, whitespace,
punctuation or any spelling that must round-trip exactly, it is written as an
exact quoted identifier:

    `+`
    `!=`
    `c.*`
    `operator.infix`
    `translator type-->spelling`

The backticks are not part of the class/key. They are only the exact identifier
delimiter. The current bootstrap translator may still use a flat
`row: table key payload` registry serialization internally; this is a temporary
storage shape over the same class/key spelling rule, not a different semantic
model.

L2 `fn` and `sub` definitions lower to `static` ANSI C functions by default.
This keeps ordinary L2 helper procedures local to the generated translation
unit. The `external` receiver wraps exactly one `fn` or `sub` and requests
external ANSI C linkage for that definition:

L2:
    external:
        fn: main () int
            return: 0
        end: main
    end: external
end: L2

Declaration qualifiers are ordinary receiver composition in the C-profile
projection. For example, `const: @: LmP0Node p` lowers to `const LmP0Node *p`.
The same qualifier form may appear in structure fields, parameters and local
declarations when the active L2 lowering profile supports the corresponding C
declarator role.

Address-producing and address-consuming forms:

    @count              address of the primitive storage location `count`
    p: @count           store that address into an address-depth-1 slot
    pp: @p              store the address of `p` into an address-depth-2 slot
    \leafs              raw load of the first primitive cell at address `leafs`
    leafs[3]            indexed access at index `3`
    \(leafs + 3)        raw load after address arithmetic


20.3. Primitive Expression Operators

The minimal L2 primitive operator profile assigns explicit operator roles:

    grouping        (expr)
    prefix          @expr, \expr, ++expr, --expr, +expr, -expr, !expr, ~expr
    postfix         expr++, expr--
    infix           +, -, *, /, %, =, !=, <, <=, >, >=, &&, ||, &, |, ^

Indexing is a postfix expression operator with the bracket form `target[index]`,
specified with storage and address forms above. The `index` part is consumed as
its own expression range by the active L2 expression profile. Nested index
operators, calls, bounded Structures, strings and ordinary operator tokens
inside the brackets are therefore lowered by the same expression machinery as
ordinary argument expressions. Field-follow remains the L2 `\field` form, not
ANSI C `.` or `->` source syntax.

This bracket form is separate from the `[]:` receiver spelling. `[]:` is a head
symbol used by receivers such as array/storage constructors. `target[...]` is a
postfix index/access suffix. A bare `[a b]` is not a portable L2 grouping form;
use `(a b)` for a bounded Structure unless a profile explicitly admits standalone
square-bracket values.

The token `=` is comparison/equality for expression/operator consumers. It is not native assignment.

The C-profile lowering maps the listed primitive operators to ANSI C operator
spellings, except that Lingvamyxa `=` lowers to ANSI C `==`, `@expr` lowers to
address-of and `\expr` lowers to raw load/dereference when it is not a
field-follow token. Shifts, overflow rules, integer division rules,
floating-point rules and conversion rules remain L2 profile details unless a
later specification selects a mandatory set.

20.4. Update and Callable Consumption

L2 uses the same head/update surface form as the rest of the structural core:

    target: value

Examples:

    count: 6
    tree\branch: branch
    leafs[3]: 10

After resolution, the form may update mutable storage, update an addressable
field/index slot, or lower a function/subroutine/receiver binding. This is
compile-time resolution, not a separate assignment syntax.

The update operator tokens `++` and `--` are part of the minimal L2 C-profile as
both prefix and postfix expression operators. They are expression operators, not
a second assignment syntax. Other profiles may lower them differently, but they
still compose with the same operator-token consumption model.

20.5. Minimal L2 Control Receivers

The minimal L2 executable-body control set is:

    if / then / else
    while
    synchronized
    until
    for(init, condition, step)
    return
    break
    continue

These are source-level control receivers/parser forms. They are not raw jumps in the source semantics, even if a translator lowers them to labels and branches.

The first ANSI C bootstrap translator needs only:

    if / else
    while
    synchronized
    return
    break
    continue

`until` and `for` remain part of the minimal L2 semantic set, but may be added
after the first procedural bootstrap subset.

20.5.1. `if`, `then` and `else`

L2 `if` consumes:

    condition -> boolean-producing expression
    then      -> statement Structure consumed by the `if` receiver
    else      -> optional statement Structure consumed by the `if` receiver

Example:

if: count > 0
    print: count


Explicit branch example:

if: count > 0
    then:
        print: count
    ---
    else:
        print: 0
    ---


20.5.2. `while`

L2 `while` is a pre-condition loop.

Semantic lowering shape:

    while(condition, statementStructure)

Example:

while: i < n
    print: i
    i: (i + 1)


20.5.3. `until`

L2 `until` is a conditional close for the current executable block.

Example:

readLoop:
    readNext: record
    process: record
until: endOfInput(record)

In this example, `record` is an explicit compact-call argument of `endOfInput`. The `until:` line consumes the whole tail `endOfInput(record)` as a boolean-producing condition Structure. The condition producer is the compact call `endOfInput(record)`, not the invalid space-separated spelling `endOfInput record`.

More explicit condition form:

readLoop:
    readNext: record
    process: record
until: endOfInput(record)

Conceptual lowering shape:

    until(currentStatementStructure, condition)

The body executes first. The loop repeats until the condition is true.

If the condition is false, control transfers to the beginning of the executable block closed by `until`. If the condition is true, the block completes and execution continues after the `until` line.

20.5.4. `for(init, condition, step)`

L2 `for` consumes:

    init      -> initialization Structure
    condition -> boolean-producing expression
    step      -> iteration-step statement Structure
    body      -> statement Structure consumed by the `for` receiver

Vertical body form:

for: int(i, 0) (i < n) i++
    print: i


Compact body form:

    for: int(i, 0) (i < n) i++ print(i)

20.5.5. `return`

L2 `return` exits the current executable body.

Bare runtime form inside a body:

    return

Value runtime form inside a body:

    return: value

For an `fn`, `return: value` consumes a compatible primitive or Structure value and exits. A bare `return` is not a valid `fn` return in the core profile.

For a `sub`, `return` exits without producing a normal return value. `return: value` is invalid for `sub` unless a later profile defines status/result subroutines.

At a valid terminal trailer position for an open executable definition, an admitted return form may be terminal return. Terminal return appends the corresponding runtime return as the final body item and closes the executable definition, in the same checked close position where the executable's admitted `end:` target would otherwise be expected. For an `fn`, that target is the function name exposed by the `fn` receiver, such as `end: square`, and the terminal return form is `return: value`. The common compact position is the executable definition's own source level; a smaller source level may also be valid when the ordinary source-level cut reaches the visible executable tail and intervening frames admit that closure.

Example:

fn: square (int(x)) (int)
return: x * x

20.5.6. `break` and `continue`

`break` exits the nearest active L2 loop frame.

`continue` starts the next iteration of the nearest active L2 loop frame.

For `while`, `continue` transfers control to the next condition check.

For `until`, `continue` transfers control to the post-condition check for the current iteration.

For `for`, `continue` transfers control to the iteration-step Structure, then to the next condition check.

20.5.7. `synchronized`

`synchronized` consumes an object/address expression and a statement Structure
owned by the `synchronized` receiver. It is a structured synchronization
receiver, not a raw lock/unlock pair in source syntax.

In the minimal L2 profile, `synchronized` has an object-expression plus
statement-tail receiver signature. The source after `synchronized:` is still the
ordinary P0 argument Structure.
Inline fields remain ordinary fields of that Structure. If an inline object
expression is followed by a child source level, that child part is materialized
as a nested Structure field; therefore:

    synchronized: @ lock
        break

is structurally equivalent to:

    synchronized: @ lock (break)

while:

    synchronized: @ lock break

keeps `break` in the inline object-expression field sequence. A receiver may
then reject that expression semantically, but P0 must not silently reinterpret
the same-line word as a body. If the consumed body tail is a single Structure,
that Structure is consumed as its fields, as in the general
single-Structure-as-N-arguments rule.

Example:

synchronized: @ object
    updateObject: object

The first ANSI C bootstrap projection may lower this to runtime hooks:

---ANSI C---
lm_synchronized_enter(&object);
{
    updateObject(object);
}
lm_synchronized_leave(&object);
---ANSI C---

The runtime hook must implement the selected monitor policy, including
Java-style reentrant entry for the same thread when that profile is selected.

The first ANSI C bootstrap translator registers each active `synchronized`
monitor as a cleanup entry. Ordinary `return`, `break` and `continue` transfers
emit the required `lm_synchronized_leave(...)` calls before leaving the protected
region. A value-return inside `synchronized` is lowered through a temporary of
the current function return type, then the active monitors are released, then
the temporary is returned.

Diagnostic failure across a synchronized boundary belongs to the wider
runtime/translator cleanup rules.

20.6. Outside the Minimal L2 Set

The following section 19 operators are not part of the minimal L2 control set unless an L2 profile explicitly enables or redefines them:

    match / default-pattern receivers
    each
    finally
    guard / fail / throws / handlers
    retry / retryable
    assert
    redo
    yield
    labelled break / labelled continue

They may still exist in L3 or higher levels, or in a richer L2 profile.

21. Structural Operation on a Local Copy of Namespace-Structure

21.1. Lexical Namespace View as Structure

A lexical namespace view is a Structure.

Before translation or receiver consumption, an active namespace view may be
represented as a typed dictionary-like Structure whose entries bind names, exact
quoted signatures, receiver names, function/subroutine descriptors, callable
descriptor bindings, label bindings, type/model descriptors, message/table
descriptors and ordinary values.

Conceptual example:

namespace:
    fn: IntToInt (int) int
    factorial: IntToInt
    print: Sub(...)
    fn: AddX (int) int
    String: TypeDescriptor
    int: TypeDescriptor
    ---

This representation is source-semantic. A translator may lower it to lexical tables, symbol indexes, direct references, C identifiers, dispatch tables, persistent maps or any other implementation representation.

The rule is shared lexical lookup, not global lookup. A view may be local to an
executable definition, block, receiver context, module, service, imported
registry overlay or runtime profile. Names in the visible chain share lookup and
conflict rules, but the language does not define one global dictionary for all
programs and services.

Inside one active lexical namespace view, Lingvamyxa does not use separate
function, variable and label namespaces. A name introduced as a variable,
function, subroutine, label, local executable, callable descriptor, receiver,
model/class descriptor or imported descriptor is one visible name in that view.
It may have several compatible roles only when a profile explicitly defines that
combined binding. It must not silently mean incompatible things depending on
whether the next source form looks like a call, an update or a control target.

21.2. Local Namespace View

Entering an executable definition creates a local namespace view.

The local view may be implemented as:

    an actual copied Structure
    a persistent overlay over the outer namespace
    a copy-on-write dictionary-like Structure
    a statically resolved lexical environment with no runtime dictionary
    another representation preserving the same source semantics

A binding update inside an executable body updates the local namespace view unless a future rule explicitly declares the binding external/global/mutable outside the local view.

Local namespace updates do not mutate the outer namespace and do not change the externally visible signature of the executable definition.

21.3. Typed Compatibility of Local Updates

A local namespace entry has a declared type, callable signature, receiver contract, model descriptor or other compatibility descriptor.

Updating an entry is valid only if the new value is compatible with that descriptor.

Examples of invalid updates:

    a binding declared as `int` receiving a `String` value
    a binding declared by `fn: IntToInt (int) int` receiving non-callable text
    a type descriptor entry receiving an ordinary runtime integer value
    a receiver implementation entry receiving a function/subroutine descriptor with incompatible argument or return Structure

Example of valid function/subroutine binding replacement:

    strategy: optimized strategy

is valid when both `strategy` and `optimized strategy` resolve to compatible
function/subroutine bindings, for example:

    fn: IntToInt (int) int

21.4. Local Function/Subroutine Binding Replacement

Because function/subroutine names are ordinary namespace bindings, local
replacement of such a binding is just a typed update of the local namespace
Structure.

Example:

fn: compute (int(x)) (int)
    fn: `slow path` (int(v)) (int)
    return: v * v
    fn: `fast path` (int(v)) (int)
    return: v << 1
    strategy: `slow path`
    if: x < 10
        strategy: `fast path`
return: strategy(x)

Here `strategy` is a local callable binding. Updating `strategy` to the exact identifier `fast path` is valid only if that callable is compatible with the declared or inferred signature of `strategy`.

This operation does not replace `slow path`, `fast path`, `compute`, or any outer namespace binding. It only changes the local namespace view used inside the current executable body.

21.5. Difference from Dynamic Untyped Rebinding

This model is not Python-like unrestricted rebinding.

The namespace may be dictionary-like, but it is typed. A name may be locally rebound only to a value compatible with its declared type or contract.

Therefore:

    x: 1
    x: "hello"

is invalid if `x` is an `int` binding.

And:

    factorial: "hello"

is invalid if `factorial` is a function/subroutine binding with signature
`fn: IntToInt (int) int`.

21.6. Interaction with Return and Function Names

The canonical return mechanism for an `fn` is `return: value`. When `return: value` is written in a valid terminal trailer position, it also closes the `fn` source frame. The current function name is an ordinary namespace binding, not a separate return syntax.

The same visible name may participate in ordinary function/subroutine lookup,
recursion and local namespace overlay operations. If ordinary binding-update
rules replace that visible name with a compatible non-function value, later
recursive function lookup through that spelling is no longer available in the
remaining local scope.

21.7. Translation and Optimization

The source semantics allow a local namespace copy or overlay, but implementations do not have to allocate an actual dictionary at runtime.

A translator may optimize local namespace operations by:

    avoiding a copy when no local updates occur
    using copy-on-write for a small number of updates
    representing the overlay as a persistent map
    replacing lookups by direct references when types and bindings are static
    inlining locally replaced function/subroutine bindings when the replacement is non-escaping
    lowering compatible function/subroutine replacement to a simple local function pointer or descriptor update
    rejecting or de-optimizing cases that escape the local namespace view beyond the executable lifetime

The source rule is structural and typed: local updates modify a local namespace Structure view, and every update must preserve the declared type/signature/contract of the target entry.
