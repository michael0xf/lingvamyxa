Lingvamyxa Structural Core Specification

This Rev.12.12 revision preserves the uploaded Rev.12.10 document body where possible and adds the logical registry/query layer summary to section 21, the L5 branch-arena memory model in section 30, and the L5 Thread/message model in section 31 while keeping canonical dotted syntax valid.

Status

Revision 12.12 draft. General language-role principle, external lexical standards boundary, identifier and string literal conventions, exact quoted identifiers, colon receiver-valence definition, comma tail, phrase signatures, canonical dotted vertical syntax, relaxed indentation syntax, `---` nameless separators, strict short-colon line rule, terminal return, local namespace overlay, reserved L2 address-depth operator update, L5 branch-arena memory model, logical registry/query layer summary, and L5 Thread/message scheduling model.

This document specifies the structural core of Lingvamyxa as a self-contained language model.

Revision 12.12 note:

    Lingvamyxa vertical source levels have two surface forms. The canonical dotted form represents source level by dot characters (`.`) in the leading indentation zone; spaces and tabs between dots or after the last leading dot are readability only. The relaxed indentation form may replace leading dots before ordinary source items with leading spaces/tabs. Textless anonymous/nameless structural transitions remain visible as canonical dotted delimiter lines or as `---` lines at the corresponding indentation level.

    Line command form is `head: tail`. In short linear form, comma is the explicit field separator. Whitespace inside a bare phrase identifier is normalized to one ASCII space and leading/trailing whitespace is trimmed. A pure numeric run may use whitespace as a shorthand field separator, so `print: 1 2 3` is equivalent to `print: 1, 2, 3`, while `stack: PlantBed, branch 2` has two fields: `PlantBed` and the bare phrase name `branch 2`. Exact quoted identifiers in backticks are a separate second identifier form for SQLite/external names and preserve their contents exactly. A short colon-form is a physical source-line form: one physical line may contain at most one short colon-form, and a short colon-form may not appear as an inline item inside a parenthesized comma list.

    The colon `:` is the receiver-valence marker of the structural syntax. In `head: tail`, the head governs the following argument Structure; the tail is not assignment and not a key-value mapping. The receiver signature gives semantic roles to the fields it consumes. In linguistic terms this is a valence/rective colon: the head opens a predicate-argument frame and the following source Structure supplies its actants.

    Vertical composition is source-level tree composition. A frame opened at source level N receives vertical child arguments at source level N + 1. A following source line with a smaller source level is a level delimiter: it closes all open structures above that smaller level. When the next structural item starts at the same source level and no smaller-level source line intervenes, a canonical dotted delimiter line or relaxed `---` line supplies the visible same-level anonymous Structure delimiter. That delimiter opens an anonymous positional Structure when followed by a deeper source item, and separates or closes the current anonymous/implicit section otherwise. Where a profile permits it and the target is unambiguous, `---` may also act as a nameless close for a named frame.

    `case` is not structural syntax. Receivers such as `match` consume ordinary positional argument streams or anonymous Structures and assign case/default semantics themselves.

    `return` has two structural positions. Inside an executable body, `return` is ordinary runtime control. At the source level of the open executable definition, `return` is terminal return: it supplies or returns the current result and structurally closes that executable definition, like a checked executable-specific close.

    The token sequences `@`, `@@`, `@@@`, ... form the reserved L2 address-depth operator family `@ⁿ`. In head position, `@ⁿ: BaseType, name` declares a typed address slot of depth n. Comma separates the base type from the binding name, so `@@@: int, ppp` is a three-level address slot to `int`, while `@@@: int ppp` would be one non-numeric phrase segment. Ordinary source cannot rebind `@ⁿ` as user procedure names.

    The ordinary receiver form `end: <target>` closes by visible target name. If `[]: matrix` introduces the entity name `matrix`, the close form is `end: matrix`, not `end: [] matrix`. Bare `end` and `end <target>` are not Lingvamyxa source syntax. The standalone source line `---` is a nameless structural delimiter. It may replace a canonical dotted delimiter line, opening an anonymous positional Structure when followed by a deeper source item, or separating/closing the current anonymous/implicit section otherwise. It may replace `end: <name>` only when the current close target is unambiguous and the receiver/profile permits nameless close. A `---` line must contain only the delimiter as a structural token; leading spaces/tabs, leading canonical dots and an optional trailing `#` comment are ignored for this restriction.

The document is descriptive and semantic. Surface syntax builds Structures. Receivers and subroutines consume Structures and assign typed meaning to them.

0. Core Formula

Lingvamyxa is based on the following model:

    L0 binaries run.
    L1 is an external bootstrap, implementation and lowering layer.
    L2-L5 are Lingvamyxa levels.
    Source syntax builds Structures.
    Receivers and subroutines consume Structures.
    The parser has a native structural syntax and a mathematical expression syntax.
    Mathematical expressions also produce Structures.
    Levels restrict the active receiver/operator set.

The language does not assign final meaning directly from surface syntax. Surface syntax builds generic Structures. A receiver or subroutine consumes a Structure and assigns typed semantics to it.

Canonical semantic pipeline:

    source text
        -> structural and mathematical parse
        -> generic Structure values
        -> receiver/subroutine consumption
        -> typed semantic structures
        -> interpretation or lowering

A Structure does not execute merely because it exists. Execution, translation, registration, validation or query handling starts only when a receiver or subroutine consumes the Structure under a defined mode.


1. Levels

1.0. General Language Role and External Lexical Standards

Lingvamyxa is a cross-platform structural language built above an external procedural L1 layer. In the default bootstrap and lowering model, that L1 layer is ANSI C / C99. Lingvamyxa is not a replacement spelling of C. It is a structural-semantic superstructure over L1: source text builds Structures; registered receivers, functions, subroutines, operators, model descriptors, behavior descriptors and query receivers consume those Structures and assign typed meaning to them.

A compact description is:

    Lingvamyxa is an object-oriented, functional and logical structural superlanguage over a procedural ANSI C / C99 lowering layer.

More precisely:

    * L1 supplies the procedural, portable, implementation-facing substrate.
    * L2 exposes low-level typed storage, addresses, layouts and unsafe operations.
    * L3 supplies ordinary algorithmic computation and executable definitions.
    * L4 describes structural models, types, contracts, unions, constraints and registry descriptors.
    * L5 describes behavior, messages, configuration, facts, rules, build/query/startup receivers and high-level dispatch.

The object-oriented side is structural, not class-magical. A model descriptor defines slots, types, defaults, constraints and layout information. A behavior descriptor attaches message selectors and implementations to a model. A runtime object is a Structure or handle/reference to a Structure together with enough model information to resolve behavior. Message lookup may lower to tables, dictionaries, inline caches, static calls or query over registry facts.

The functional side is also structural. A function or subroutine definition is a Structure consumed by the `fn` or `sub` receiver. A call is a Frame. A callable value is data until explicitly called or consumed by a receiver that calls it. Function return is represented by `return` receivers and terminal return, not by a separate assignment syntax.

The logical side is represented by facts, rules, relations and query receivers. Model, union, operator, method and behavior descriptors may materialize typed registry facts. Generic dispatch, message lookup, completeness checks and validation may be expressed as queries over this registry model. This gives one uniform way to index, validate, derive and lower structural information.

The source syntax itself does not hard-code object semantics, functional semantics or logic semantics. It builds generic Structures. The active level and the active receiver/operator registry determine which semantic domain consumes a Structure. The same surface form may describe a low-level storage declaration, a function definition, a model descriptor, a behavior descriptor, a fact, a rule, a query or a build configuration, depending on receiver consumption.

Lingvamyxa deliberately reuses selected mature external lexical standards instead of redefining every atom. Numeric literals and text/string literals follow ANSI C / C99 spelling because L1 is ANSI C / C99 and many such literals can be copied directly into generated L1 code. Exact quoted identifiers use SQLite-compatible exact-name semantics because Lingvamyxa Structures may describe external relational schemas and because SQLite provides a simple exact quoted-name model.

This reuse applies only to lexical atoms. It does not import C assignment syntax, C declaration grammar, C control syntax, SQL expression syntax, SQL execution semantics, YAML mapping semantics or indentation semantics. Lingvamyxa owns the structural syntax and structural semantics: colon receiver-valence frames, source-level tree composition, compact calls, short colon source items, comma/numeric/string separation, terminal return, namespace Structures, receiver registration, typed model/behavior descriptors, fact/query receivers and receiver consumption.

The practical rule is:

    Lingvamyxa owns structure.
    External standards may own selected lexical atoms.

Consequently, an ANSI C numeric or string literal may often be preserved as text during L1 lowering, while its surrounding Lingvamyxa Structure is still parsed, typed and consumed by Lingvamyxa receivers. Likewise, an exact quoted identifier may preserve an external SQLite name without forcing that name into the narrower bare Lingvamyxa phrase-identifier grammar.

1.1. L0

L0 is a native binary artifact or machine-code artifact. It is the level actually executed by the CPU and operating system.

Examples of L0 artifacts:

    app.lm0.exe
    app.lm0
    core.lm0.dll
    core.lm0.so
    core.lm0.dylib
    core.lm0.a
    core.lm0.lib

1.2. L1

L1 is an external bootstrap, implementation and lowering layer. It may host initial parsers, translators, runtime components and receivers. L1 has its own syntax and semantics and is not part of the Lingvamyxa source-semantic core described by this document.

This document does not specify the L1 target language, physical calling convention, memory ownership rules or low-level runtime representation. Those belong to translator and runtime specifications.

1.3. L2

L2 is the low-level unsafe Lingvamyxa level. It is the low-level systems layer. It may expose memory, typed addresses, handles, layout-based storage, explicit low-level operations and low-level concurrency.

L2 is compiled. It is not executed as a casual script.

1.4. L3

L3 is the algorithmic and computational Lingvamyxa level. It supports safe top-level actions, computations and calls. L3 code may be interpreted by the core runtime or compiled through the lowering pipeline.

1.5. L4

L4 is the non-executive model level. It describes models, types, protocols, contracts, constraints, relation signatures and registry metadata.

L4 may update or check the compiler/runtime model. L4 does not perform ordinary runtime actions by default.

1.6. L5

L5 is the level of messages, configuration, behavior descriptors, fact registries, build/run/query/startup receivers and high-level dispatch.

L5 may attach message behavior to L4 structural models. L5 may also represent registry data as typed facts and rules. This draft places that fact/behavior layer in L5. A later level split may move part of it to L6. This document treats the L5 fact/behavior model as source-semantic infrastructure, not as ordinary runtime I/O.

1.7. Level Receivers

`L2`, `L3`, `L4` and `L5` are level receivers. A level receiver consumes its nested Structure and sets the active receiver/operator set for that body.

Example:

L4:
. operator:
. . if
. . callableFrom: L5
. . implementation: l5_if
end: L4

Semantic normal form:

    L4(
      operator(
        if,
        callableFrom L5,
        implementation(l5_if)
      )
    )

The receiver `L4` consumes its body as model and registry input.


2. Value Ontology

The minimal core has two classes of values:

    1. primitive/scalar/reference/handle values
    2. Structure / Frame values

Primitive/scalar/reference/handle values include numbers, booleans, atoms, symbols, enum-like values, handles, references, typed addresses and L2-level callable references.

All non-primitive values are Structures or handles/references to Structures. This includes arrays, text, objects, call frames, bodies, configurations, expressions, model fragments and executable/callable descriptors.

At source-semantic level, executable definitions are ordinary values bound in the shared namespace. A translator may lower such a value to any implementation-level callable representation, such as a descriptor Structure, registry index, trampoline, closure record or target-language callable primitive. That lowering choice is not a separate source-level kind.

A Structure can contain fields. A field can be positional, named or derived during normalization from a receiver signature.

At L3 and above, Structures are normally passed by reference/handle. They are not copied by value at every call unless a receiver explicitly defines copy semantics.

At L2, aggregate layouts do not have to be source-level value objects. They may be represented by typed addresses to storage, handles, layout structures or primitive representations according to the translator profile.

There is no fundamental keyword `Struct` in the minimal source syntax.


3. Structures and Frames

3.1. Structure

A Structure is a value containing an ordered set of fields. Fields may have names. Field order is part of the logical structure and may become part of layout or signature semantics.

A Structure may contain nested Structures. Tree-shaped data is represented as nested Structures.

3.2. Frame

A Frame is a Structure with a receiver/callee name and an argument Structure.

Example source:

    f(a, b, c)

Generic logical form:

    Frame(
      name(f),
      args(
        field0(a),
        field1(b),
        field2(c)
      )
    )

In ordinary prose this document may write `f(a, b, c)` as a Structure or Frame. The exact internal representation is implementation-defined as long as receiver semantics are preserved.

3.3. Structures Do Not Execute Themselves

A Structure is data. It may describe code, a call, a model, an expression, a relation, a query or a configuration. It does not execute merely by existing.

Execution starts only through explicit receiver/subroutine consumption, for example:

    compileCallFrame(frame)
    evalExpression(expr)
    call(subRef, args)
    registerOperator(frame)
    query(relationFrame)

A callable reference is also data until explicitly called or consumed by a receiver that calls it.

3.4. Identifiers, Exact Quoted Identifiers, Numeric Literals and Strings

Lingvamyxa distinguishes convenient bare identifiers, exact quoted identifiers and text/string literals. This distinction is required because spaces may participate in phrase names, commas delimit fields, dots define vertical structure, and external systems such as SQLite may contain identifiers that would collide with Lingvamyxa syntax.

3.4.1. Numeric Literals

Numeric literals use the ANSI C / C99 numeric literal model.

Examples of integer literals:

    0
    123
    0123
    0x7B
    123u
    123UL
    123ll
    0xffULL

Examples of floating literals:

    1.0
    .5
    1.
    1e9
    1.25e-3
    1.0f
    1.0L
    0x1.8p+2
    0x1p-4

The source numeric lexer follows the ANSI C / C99 shape of integer and floating constants. In Lingvamyxa structural syntax, a pure numeric run may use whitespace as a field separator:

    print: 1 2 3

is equivalent to:

    print: 1, 2, 3

Numbers are separated by space, comma, newline, closing parenthesis or source-level boundary.

3.4.2. Bare Identifiers and Phrase Identifiers

The first ordinary Lingvamyxa identifier form is the convenient bare form.

A single bare identifier word uses the ANSI C identifier shape in the portable core profile:

    [A-Za-z_][A-Za-z0-9_]*

A bare phrase identifier is a sequence that starts with a bare ANSI-C-shaped identifier word and then continues as a phrase until a structural separator is reached.

Structural separators for bare phrases are:

    comma,
    newline,
    closing parenthesis of the current bounded Structure,
    source-level boundary.

Ordinary horizontal whitespace does not split a bare phrase identifier into separate fields. It separates phrase words only inside the phrase. The parser normalizes all repeated horizontal whitespace between phrase words to one ASCII space and trims leading and trailing whitespace from the phrase.

Examples of bare phrase identifiers:

    PlantBed
    branch
    branch 2
    red apples
    estimate harvest
    my 2d example
    very_long_name

The following source spellings denote the same bare phrase identifier:

    red apples
    red     apples
    red	 apples

After normalization, all of them denote:

    red apples

The following source spellings also denote one bare phrase identifier each, not multiple arguments:

    branch 2
    my 2d example

Because each phrase starts with an identifier word, the later numeric-looking words belong to the phrase. By contrast, a pure numeric run starts in numeric mode and is split as numbers:

    1 2 3

normalizes as:

    1, 2, 3

Therefore:

    stack: PlantBed, branch 2

has two fields:

    PlantBed
    branch 2

and it does not normalize as:

    stack(PlantBed, branch, 2)

A bare phrase identifier is not a text/string literal. It is a namespace name, signature fragment, selector phrase or other receiver-consumed name-like field.

The first bare form is intentionally narrower than SQLite quoted identifiers. If an external name contains punctuation, operator characters, leading/trailing spaces, repeated spaces that must be preserved exactly, newlines, an empty spelling, or any spelling that must round-trip byte-for-byte through an external schema, use the second identifier form: an exact quoted identifier.

3.4.3. Exact Quoted Identifiers

The second identifier form is the exact quoted identifier. It is intended for SQLite names, external schemas, generated bindings and unusual names that are not safe or not intended to be normalized as bare Lingvamyxa phrase identifiers.

An exact quoted identifier is delimited by backtick characters:

    `exact name`

It is a namespace identifier/name, not a text/string literal. Its contents are taken as the exact identifier string after quote unescaping. No bare-phrase whitespace normalization is applied inside backticks. Commas, dots, spaces, numeric-looking text, reserved words and operator characters inside the backticks are part of the identifier.

Examples:

    `a,b`
    `x.y`
    `return`
    `1 2`
    `a  b`
    ``

Inside an exact quoted identifier, two consecutive backticks represent one literal backtick character:

    `a``b`

names the exact identifier:

    a`b

Therefore:

    int: `a``b`
    `a``b`: 10

Declares and updates the binding whose exact name contains a literal backtick.

Exact quoted identifiers behave as atomic name tokens in head position, tail/name position and expression/name position. The quoted spelling does not participate in normal phrase tokenization.

A physical newline is not allowed inside an exact quoted identifier in the portable source profile. External identifiers containing newlines must be imported through an escaping or mapping rule defined by the external integration profile.

3.4.4. Text/String Literals

Text/string literals use ANSI C / C99 string literal syntax. They are values, not identifiers.

Examples:

    "hello"
    "line one\nline two"
    "tab\tseparated"
    "quote: \""
    "backslash: \\"
    "question: \?"
    "alert\a backspace\b formfeed\f newline\n carriage\r tab\t vertical\v"
    "octal A: \101"
    "hex A: \x41"
    "lambda: \u03BB"
    "grinning face: \U0001F600"
    L"wide text"

The string spelling and escape rules follow the ANSI C / C99 string-literal model. However, Lingvamyxa does not use C99 adjacent string-literal concatenation as a source-level list shorthand. Adjacent string literals are separate values unless an explicit receiver later consumes and concatenates them.

In structural syntax, string literals are separated like numeric literals: by space, comma, newline, closing parenthesis or source-level boundary. This makes manual table and list declarations compact.

Examples:

    print: "hello" "world"

is equivalent to:

    print: "hello", "world"

And:

    []: labels
    . "red" "green" "blue"
    . "cyan", "magenta", "yellow"

contains two row-like child Structures whose string values are separated by whitespace or commas.

The hexadecimal escape `\x...` consumes hexadecimal digits according to the C string-literal rule. Octal escapes consume up to three octal digits. Universal character names `\uXXXX` and `\UXXXXXXXX` are literal character escapes.
The double-quoted string form is separate from exact quoted identifiers. Therefore:

    "hello"

is a text value, while:

    `hello`

is the exact identifier/name `hello`.


4. Surface Forms and Normalization

4.0. Colon as Receiver-Valence Marker

The colon `:` is the central valence marker of Lingvamyxa surface syntax. It is not an assignment operator, not a YAML-like key-value separator and not a special type-annotation symbol.

General form:

    head: tail

Source meaning:

    the head phrase governs the following argument Structure;
    the tail supplies the fields consumed by that head.

In receiver terminology, `head` is a receiver, operator, callable, constructor, updater, model receiver, message receiver or other consuming head. The parser builds the generic Structure; the active receiver signature later assigns semantic roles to its fields.

In linguistic terminology, this colon may be described as a valence colon or a marker of government/rection. It opens a predicate-argument frame: the left side is the governing predicate/head, and the right side or the following vertical children are its actants/arguments.

Therefore:

    fn: ...
    if: ...
    return: ...
    int: ...
    stack: ...
    []: ...
    model: ...
    operator: ...

all share the same structural rule. They differ only in the receiver that consumes the Structure and in the receiver signature that interprets its fields.

A form such as:

    x: value

is not primitive assignment by syntax alone. After name resolution, it may be a local binding update, a receiver consumption, a callable invocation/update, a message-like consumption, a model/configuration entry or another receiver-defined operation. The colon only says that `x` governs and consumes the following Structure.

A form such as:

    int: x

is not a separate Pascal-like type grammar. It is the same receiver-valence form: the registered `int` constructor receiver consumes the raw name `x` in declaration context and introduces a typed binding.

A form such as:

    name: Alice

is not a YAML key-value pair by syntax alone. It is the receiver/head `name` consuming the argument field `Alice`; a model/configuration receiver may later interpret that child Structure as a semantic field.

Compact call form and colon form are two surface ways to build Frames/Structures. The compact form makes the bounded argument list explicit with parentheses. The colon form makes the governing head explicit through valence/government and then uses the short tail or vertical source-level children as its argument Structure.

4.1. Compact Call Form

Compact call form:

    f(a, b, c)

It creates a Frame named `f` with one logical argument Structure containing three positional fields.

Normal form:

    f(
      field0(a),
      field1(b),
      field2(c)
    )

4.2. Line Command Form

Line command form:

    f: a, b, c

It creates the same logical Frame as:

    f(a, b, c)

The token sequence before `:` is the head phrase. The tail after `:` is the line argument Structure. A physical newline terminates the short line command. If the line command opens a bounded continuation, such as `fn: i(`, the matching close of that bounded Structure also terminates the open continuation, but it does not allow additional inline short colon-forms on the same physical line.

The head phrase may contain spaces. This allows receiver/procedure signatures and entity names that are not single lexical words. The parser does not split the head phrase into arguments merely because it contains spaces.

Example:

    []: my 2d example
    . 1 2
    . 3 4

The head is the `[]` receiver/procedure. The first inline tail field is the bare phrase name `my 2d example`. The vertical lines are child fields of that frame.

4.2.1. Comma Tail Rule

In short linear tail form, comma is the explicit field separator.

Example:

    head: arg0, arg1, arg2

normalizes as:

    head(arg0, arg1, arg2)

Whitespace inside a non-numeric segment is part of that segment. Therefore:

    stack: PlantBed, branch 2

normalizes as:

    stack(PlantBed, branch 2)

where `branch 2` is one bare phrase name field. It does not normalize as:

    stack(PlantBed, branch, 2)

and it does not allocate `branch` with an extra numeric argument `2`.

A receiver may later interpret a phrase field as a name, signature, selector, atom sequence, message phrase or another semantic object. The parser only builds the field.

4.2.1.1. Strict Short-Colon Line Rule

A short colon-form is a physical source-item form.

A physical source line may contain at most one short colon-form.

A short colon-form may appear only as the main source item of that physical line. It may not appear as an inline element inside a parenthesized comma enumeration, a compact call argument list or another short colon-form tail.

Invalid:

    call2(call(int: a, b), call(int: b, c))
    int: a, int: d
    call(int: a, b)

The last form is invalid because `int: a, b` is a short colon-form placed directly inside a parenthesized argument list. To pass a compact type-constructor Frame, write:

    call(int(a, b))

To use short colon-form inside parentheses, write it as a vertical source item on its own physical line. Parentheses do not disable source-level composition:

    call(
    . int: a, b
    )

When a short colon-form begins on a physical line, commas on that line belong to that form's own tail. They do not resume an outer comma enumeration. Therefore several short colon-forms must be written as separate physical lines, normally by vertical dot composition.

4.2.2. Numeric-Run Shortcut

Whitespace may act as a shorthand field separator only inside a pure numeric run.

Example:

    print: 1 2 3 4 5

is equivalent to:

    print: 1, 2, 3, 4, 5

and normalizes as:

    print(1, 2, 3, 4, 5)

A pure numeric run is a tail segment whose tokens are all numeric literals accepted by the active numeric lexer. Once a non-numeric token appears in the same comma segment, whitespace no longer separates fields in that segment.

Example:

    print: abc d 3 e

normalizes as one phrase/signature field:

    print(abc d 3 e)

or, in an implementation that materializes phrase values explicitly:

    print(phrase("abc d 3 e"))

To pass separate fields, use commas:

    print: abc d, 3, e

normalizes as:

    print(abc d, 3, e)

The numeric-run shortcut is local to the current linear item. It does not flatten through parentheses, compact Frames or vertical anonymous Structures.

4.2.3. No Hidden Receiver-Signature Grouping

Line command form does not infer hidden nesting from receiver signatures.

Critical rule:

    print: getTypedValue, values[i]

normalizes as:

    print(getTypedValue, values[i])

It does not normalize as:

    print(getTypedValue(values[i]))

Explicit nesting must be written with parentheses, compact Frame form or vertical anonymous Structure form.

If a receiver argument must itself be one Structure, the source must make that nesting explicit with a bounded Structure, compact Frame or anonymous vertical Structure.

Examples:

    args: int(v, j)

This gives `args` one compact declaration Frame `int(v, j)`.

The following is invalid under the strict short-colon line rule, because the short colon-form `int: v, j` is placed directly inside parentheses:

    args: (int: v, j)

Write either the compact form above or a vertical source form:

    args:
    . int: v, j

A head phrase followed by `:` must have a continuation. The continuation may be an inline tail on the same physical line, vertical child fields at source level N + 1, or an explicit close through `end: <target>` when allowed by the open target policy. A line `head:` with no inline tail and no following vertical child fields is a syntax error unless the receiver/profile explicitly defines an empty Structure form for that head.

A line without `:` is not a non-nullary receiver call. In executable statement position, a bare receiver/callable line is valid only when the resolved binding can be consumed with zero arguments. This includes registered nullary line operators such as `return`, `break` and nullary `continue`, registered nullary receivers, and visible `fn`/`sub` bindings whose signature has zero required arguments.

A bare atom/expression line may still appear as a value item inside a Structure; the consuming receiver decides whether that value names a callable body, a symbol, a type, a branch placeholder or something else.

4.3. Vertical Frame Form

Vertical frame form:

f:
. a
. b
. c
end: f

It creates a Frame named `f` with the same logical argument Structure as:

    f(a, b, c)

The explicit close is an ordinary receiver form `end: f`. Closing validation is defined in section 7.5.

A compact first field may still appear in the opening line:

    f: a
    . b
    . c
    end: f

This creates:

    f(a, b, c)

The inline tail contributes initial fields. The vertical child lines at level N + 1 contribute following fields.

4.4. Parenthesized Bounded Structure

Parentheses create a bounded Structure:

    (a, b, c)

Inside parentheses, fields may be separated by comma, by physical newline/source-level composition, by the matching closing parenthesis, or by the numeric-run shortcut when the current item is a pure numeric run.

Parentheses do not disable the source-level system. Vertical child items inside parentheses are still written with dots.

A short colon-form is not allowed as an inline argument inside parentheses. It must be the main source item of its physical line. Therefore `call(int: a, b)` is invalid. Use `call(int(a, b))` for a compact constructor Frame, or write the short colon-form vertically:

    call(
    . int: a, b
    )

Numeric literals are separated by space, comma, newline, closing parenthesis or source-level boundary. Bare phrase fields are separated by comma, newline, closing parenthesis or source-level boundary; whitespace alone remains part of the phrase/signature and is normalized according to Section 3.4. Exact quoted identifiers are atomic name tokens.

Example:

    if( i = 1, print(choose, hello), print(choose, world) )

Logical argument sections:

    field0 -> <expression Structure for `i = 1`>
    field1 -> (print(choose, hello))
    field2 -> (print(choose, world))

Receiver-signature roles:

    field0 -> condition
    field1 -> then
    field2 -> else

The names `condition`, `then` and `else` are not created by the parser alone. They are assigned by receiver-signature normalization for the active `if` receiver. The internal layout of the expression Structure is outside this structural-core document.

4.5. Vertical Source Levels: Canonical Source-Level Notation and Relaxed Indentation Notation

Vertical composition is source-level tree composition. Lingvamyxa has one source-level tree model and two surface notations for writing it.

The canonical source-level notation is the visible dotted notation. It is always valid and is the reference spelling of source levels. In canonical dotted notation, the leading indentation zone of a source line is the run of dots, spaces and tab characters before the first non-indentation source token. The source level of the line is the number of dot characters in that zone. Spaces and tab characters in the indentation zone are ignored for source block depth.

Examples of equal source level in canonical dotted notation:

    ....call
    . . . . call
    .	. .	.     call

Relaxed indentation notation is a readability notation over the same source-level tree. It may replace leading dots before ordinary source items with ordinary indentation. In relaxed indentation notation, the source level is computed from leading spaces/tabs before the first non-space character by the implementation's indentation-stack rule and then mapped to the same source levels used by canonical dotted notation. Internal spaces remain ordinary source characters and may still participate in phrase identifiers, numeric runs and manual alignment.

Shared source-level rule after either surface notation has been mapped to source levels:

    A source line has a source level.

    In canonical dotted notation, source level is the count of leading dots.

    In relaxed indentation notation, source level is computed from the
    leading spaces/tabs indentation stack.

    Internal spaces remain ordinary source characters and may still participate
    in phrase identifiers, numeric runs and manual alignment.

    A line at a source level deeper than the previous structural head is a
    child item of that head.

    A line that returns to an earlier source level is a level delimiter and
    closes all open structures above that level.

    `end: name` closes a visible named target explicitly.

    `---` is a structural delimiter at its own source level. Like the
    canonical dotted delimiter, it may open an anonymous positional Structure
    when followed by a source item at the next deeper level, or separate/close
    the current anonymous/implicit section otherwise.

This rule is not a Python-like license to hide every same-level anonymous separator in whitespace. A smaller source-level line closes the open structures above that smaller level. But when two anonymous/implicit Structures must be separated at the same source level, no smaller-level line exists between them, so Lingvamyxa requires a visible same-level delimiter: a canonical dotted delimiter line or `---`.

Visible structural transition forms are:

    end: name
    return
    return: value
    ---
    a canonical source-level delimiter line
    a following source item at a smaller source level

Most visible named Structures are closed by `end: name`. Executable definitions may be closed by terminal `return` or `return: value` when the executable receiver admits terminal return. Anonymous positional Structures and nameless implicit sections are closed by a smaller-level source line when the source tree dedents. They are opened, separated or closed at the same source level by a canonical source-level delimiter line in canonical source-level notation or by `---` in relaxed indentation notation.

Therefore the term "dot-only line" is not a general word for all closure. It names only the canonical source-level notation for an anonymous/nameless structural delimiter. Named closure is normally `end: name`.

A useful parser view is the head-body-trailer envelope:

    head
    body Structure
    trailer

The body Structure is the primary Structure consumed by the opened frame or anonymous positional argument. The head and trailer are structural envelope roles, not ordinary child fields of that body. For a named frame, the head is a source item such as `if: condition`, `fn: name, ...` or `outerLoop:`. For an anonymous positional Structure, the head may be a canonical dotted delimiter line or a relaxed `---` delimiter line.

In canonical dotted notation:

    .                               # head: open anonymous positional Structure
    . . body1                       # body
    .                               # trailer of previous + head of next anonymous Structure
    . . body2                       # body
    .                               # trailer

The middle dotted delimiter line has both roles: it closes/separates the preceding anonymous Structure and, because it is followed by a deeper source item, opens the next anonymous positional Structure. A relaxed `---` line follows the same head/body/trailer envelope rule.

A source item at level N may open a frame/Structure. Its vertical child arguments are written at level N + 1.

A physical source line at level N + 1 is one positional child item of the open frame/Structure at level N.

A physical source line at level greater than N + 1 belongs to the immediately preceding child item only when that preceding child item is a Structure-opening item. Scalar literals and ordinary phrase/value items do not become headers merely because a deeper line follows them.

A physical source line at a smaller level than the current open child resumes the parent level and starts a sibling item there. The smaller-level line itself is the level delimiter. If the next item starts at the same level as the current anonymous/implicit section, use a canonical dotted delimiter line or relaxed `---` at that level.

Physical empty lines are formatting whitespace unless a future profile gives them a diagnostic/style meaning. They are not the general structural close mechanism and they do not replace a required same-level delimiter.

4.5.1. Canonical Source-Level Delimiters

A canonical source-level delimiter line is a dotted delimiter line. It contains only dots, spaces and tabs before the newline and contains at least one dot.

A canonical source-level delimiter line at level K may serve as an anonymous positional Structure delimiter at level K. When followed by source items at level K + 1, it opens an anonymous positional Structure. Otherwise it separates or closes the current anonymous/implicit section at level K.

If a canonical source-level delimiter line at level K is followed by source items at level K + 1, it opens an anonymous positional Structure at level K. That anonymous Structure is one child item of the surrounding parent Structure.

The anonymous Structure continues until the next canonical source-level delimiter line at level K, a following source item at a smaller source level, an explicit `end: <target>` that closes a visible target, terminal `return` / `return: value` where valid, or EOF.

A canonical source-level delimiter line at level K may close the previous anonymous Structure at K and, if followed by deeper items, open the next anonymous Structure at K.

Every source line written with leading dots remains valid in the relaxed language profile. A canonical source-level delimiter line may therefore still be used instead of `---` as the visible anonymous delimiter / nameless close form.

Canonical anonymous-branch example:

match: value
.
. . 1
. . print: World
.
. . 2
. . print: Hello
.
end: match

Conceptual normal form:

    match(
      value,
      (
        1,
        print(World)
      ),
      (
        2,
        print(Hello)
      )
    )

The canonical source-level delimiter lines at level 1 delimit anonymous branch Structures. No source keyword `case` (not structural syntax) is involved.

A shorter positional `match` form may avoid anonymous branch Structures:

match: value
. 1
. print: World
. 2
. print: Hello
end: match

Conceptual normal form:

    match(value, 1, print(World), 2, print(Hello))

4.5.2. Relaxed Indentation Notation and `---`

Relaxed indentation notation is a readability shorthand for the same source-level tree. It replaces leading dots before ordinary source items with spaces/tabs indentation. It does not remove the requirement for visible nameless delimiters.

The simple replacement rule is:

    leading dots before source text may be replaced by indentation;
    a textless canonical source-level delimiter line must remain visible either
    as that dotted delimiter line or as `---` at the corresponding source level.

A standalone line:

    ---

at source level K is a structural delimiter at level K. It may open an anonymous positional Structure when followed by source items at level K + 1, or separate/close the current anonymous/implicit section otherwise.

If `---` at level K is followed by source items at level K + 1, it opens an anonymous positional Structure at level K. The anonymous Structure continues until the next `---` at level K, a following source item at a smaller source level, an explicit `end: <target>`, terminal `return` / `return: value` where valid, or EOF.

If `---` at level K is not followed by deeper source items, it closes or cuts the current open anonymous/implicit section at that level and resumes parsing at level K.

A `---` delimiter line must contain no source item other than the delimiter itself. It may have leading spaces/tabs in relaxed indentation notation, leading canonical dots in canonical source-level / automatic-rewrite notation, horizontal whitespace after the delimiter, and an optional trailing `#` line comment. The `#` comment text is ignored by the structural parser, exactly like comments after ordinary source text.

Valid delimiter lines:

    ---
    --- # anonymous branch delimiter
    .---
    . --- # automatically rewritten dotted separator

Invalid delimiter lines:

    ---else:
    --- return: x
    --- int: x

`---` is not a prefix operator and cannot be combined with a receiver or any other source item on the same physical line.

A following named receiver line at the same indentation/source level may close the previous anonymous section and start the next structural item of the same parent frame. For example, `else:` at the correct level may close the preceding anonymous branch and start the named `else` branch; it does not need to be attached to `---`.

`---` may be used instead of `end: name` only when the close target is unambiguous and the receiver/profile permits a nameless close. For checked public examples and long blocks, `end: name` remains clearer.

Example with two anonymous branch Structures:

match: value
    ---
        1
        print: World
    ---
        2
        print: Hello
---

Conceptual normal form:

    match(
      value,
      (
        1,
        print(World)
      ),
      (
        2,
        print(Hello)
      )
    )

The final `---` closes the open `match` ladder without naming it. The same position could also use `end: match`.

Example with four positional arguments and no anonymous branch Structures:

match: value
    1
    print: World
    2
    print: Hello
---

Conceptual normal form:

    match(value, 1, print(World), 2, print(Hello))

Example with two positional branch Structures in an `if` receiver:

if: condition
    ---
        thenBody
    ---
        elseBody
end: if

The two `---` sections are two anonymous Structure arguments of `if` after the condition.

Equivalent named-argument form in canonical source-level notation:

if: a
. then:
. . doSomething
. else:
. . doOtherThing
end: if

Relaxed indentation notation with explicit delimiter followed by a named continuation receiver:

if: condition
    ---
        # doSomething
    ---
        # doOtherThing
end: if

if: condition
    ---
        # doSomething
    else: # This "else" is at the correct level and therefore automatically closes the previous block.
        # doOtherThing
end: if

The line `else:` is at the same source level as the preceding anonymous section. It therefore closes/separates that anonymous section and starts the ordinary nested Structure `else:`. The active `if` receiver may consume `else(...)` as a semantic field. A spelling such as `---else:` is invalid because `---` must be alone on its delimiter line, except for an optional trailing `#` comment.

Example with an explicit nameless close after a nested `if`:

outerLoop:
    for: int(i, 1), (i <= 3), i++
        for: int(j, 1), (j <= 3), j++
            if: i = 2 && j = 2
                System/out/println: "--- continue outerLoop ---"
                continue: outerLoop
            ---
            System/out/println: "i: " + i + ", j: " + j
end: outerLoop

The `---` at the source level of the inner `for` body replaces the canonical source-level delimiter line:

outerLoop:
. for: int(i, 1), (i <= 3), i++
. . for: int(j, 1), (j <= 3), j++
. . . if: i = 2 && j = 2
. . . . System/out/println: "--- continue outerLoop ---"
. . . . continue: outerLoop
. . .
. . . System/out/println: "i: " + i + ", j: " + j
end: outerLoop

The shorter relaxed indentation version without this delimiter is not valid Lingvamyxa, because it hides a required nameless close in indentation alone.

4.5.3. Matrix and Nested Array Examples

Matrix-like data does not require a special table context. It follows ordinary source-level tree and line-item rules.

Canonical source-level notation example:

[]: my 2d example
. 1 2
. 3 4

Relaxed indentation notation example:

[]: my 2d example
    1 2
    3 4
---

Conceptual normal form:

    [](my 2d example, (1, 2), (3, 4))

The rows are ordinary child items. The numeric-run shortcut makes `1 2` equivalent to `1, 2` inside each row item.

Mixed symbolic/numeric rows require commas for non-numeric segments:

[]: my 2d example
. a, b
. 3 4

Conceptual normal form:

    [](my 2d example, (a, b), (3, 4))

Named nested rows may be written with nested `[]` frames:

[]: matrix
. []: row1
. . 1 2
. []: row2
. . 3 4
end: matrix

The close target is `matrix`, the visible entity name introduced by the frame. The close form is not `end: [] matrix`.

4.6. `end:` Close Receiver and Nameless Close

Bare `end` is not valid Lingvamyxa source syntax. The structural close operation is not bare `end` and is not `end <target>`.

The source-level named close form is the ordinary colon receiver form. It is valid in both canonical source-level notation and relaxed indentation notation:

    end: <target>

`end:` consumes its tail as a close target. The target names a visible frame, label block or entity block. If an opening form such as `[]: matrix` introduces the visible name `matrix`, then the close form is:

    end: matrix

not:

    end: [] matrix

`end:` may close several currently open implicit vertical levels at once, as long as the target matches a visible open target at or above the current source level and no receiver-specific rule forbids that jump. This makes `end:` a readable tail-cutter for deeply nested named vertical code.

The standalone source line `---` is the nameless delimiter form used primarily by relaxed indentation notation as the counterpart of a canonical source-level delimiter line. It does not consume a target. When followed by source items at the next deeper level, it opens an anonymous positional Structure at its own source level. Otherwise it separates or closes the current open anonymous/implicit section at that level. When the current named frame allows nameless close and there is no ambiguity, `---` may close that frame as a shorter alternative to `end: name`.

Example named close:

outerLoop:
. for: int(i, 1), (i <= 3), i++
. . for: int(j, 1), (j <= 3), j++
. . . if: i = 2 && j = 2
. . . . continue: outerLoop
end: outerLoop

The final line closes the labelled block `outerLoop` directly. The intermediate vertical levels are closed by the named close.

4.6.1. Vertical Positional Structures

Some receivers expect positional Structure arguments whose semantic role is assigned by the receiver signature. Such Structure arguments may be written vertically as child items at the next source level of the open receiver frame.

Canonical source-level notation single-body example:

if: a
. doSomething
end: if

Under an `if(condition, thenBody, elseBody)` receiver signature, this builds:

    if(
      a,
      (
        doSomething
      )
    )

The name `thenBody` is assigned by the `if` receiver signature. It is not a surface keyword in this form.

Relaxed indentation notation:

if: a
    doSomething
end: if

Two-body positional example using relaxed anonymous sections:

if: a
    ---
        doSomething
    ---
        doOtherThing
end: if

Under the same `if(condition, thenBody, elseBody)` receiver signature, this builds:

    if(
      a,
      (
        doSomething
      ),
      (
        doOtherThing
      )
    )

The same branches may also be written as explicit named argument Structures:

if: a
. then:
. . doSomething
. else:
. . doOtherThing
end: if

or in relaxed indentation notation:

if: a
    then:
        doSomething
    else:
        doOtherThing
end: if

The names `then` and `else` are ordinary nested Structures consumed by the active `if` receiver as semantic fields. They are not global reserved words. If the first branch is written in named form, following branches in that same argument sequence must also be written in named form according to the named-argument ordering rule.

A one-line form is also possible when the receiver defines it:

    if: a, doSomething

This builds a Frame whose final meaning is assigned by the active `if` receiver.

A receiver call has one logical argument Structure. A source form that appears to pass several arguments and a source form that appears to pass one Structure argument are not separate syntactic categories. The argument list itself is a Structure. Therefore a function that receives one Structure and a function that receives several positional fields may have the same source call shape. The receiver signature decides whether the fields of the argument Structure are consumed as one structural value, as several positional parameters, or through an explicitly defined equivalence rule.

This is an intentional property of the language, not an accidental ambiguity. In colon line forms, commas and numeric-run shortcuts create fields. In vertical form, child items at the next source level create fields. A receiver with one structural parameter may consume the whole argument Structure. A receiver with several parameters may consume the same Structure by positional fields.

4.7. No Native `=` Assignment or Named-Field Operator

The structural syntax does not use `=` for assignment and does not use `=` as a native named-field operator.

A semantic field name may still exist after receiver normalization. It is produced by receiver signatures, positional conventions, explicit nested Structures, declaration forms or model/type constructors.

Explicit source-level naming is written as an ordinary Structure, not as `name = value`.

Example source:

model:
    name: PlantBed
    condition: plantBedCondition
end: model

Conceptual receiver-level interpretation:

    model(
      name(PlantBed),
      condition(plantBedCondition)
    )

The receiver `model` may interpret `name(PlantBed)` as semantic field `name` and `condition(plantBedCondition)` as semantic field `condition`.

The token `=` belongs to mathematical expression syntax as equality/comparison. It is not native structural assignment and not native named-field syntax.

4.8. Positional Fields and Semantic Named Fields

A Structure may contain positional fields. A receiver may assign semantic names to those fields through its signature.

Example:

if: a
    doSomething
    doOtherThing
end: if

With an `if(condition, thenBody, elseBody)` receiver signature, the two vertical child items are consumed positionally as `thenBody` and `elseBody`.

Named vertical form:

if: a
    then:
        doSomething
    else:
        doOtherThing
end: if

Here `then` and `else` are explicit nested Structures consumed as named semantic fields.

Explicit semantic field-like input should be represented by nested Structures:

config:
    batchSize: 500
    reportMode: Daily
end: config

This builds ordinary nested Structures such as `batchSize(500)` and `reportMode(Daily)`. The active `config` receiver decides whether those Structures are interpreted as settings, fields, messages or ordinary child items.

4.9. Field Order

Field order is part of the logical Structure. When a receiver supports positional arguments, positional fields are mapped to receiver signature fields in order.

Semantic field names may be assigned by receiver normalization. A receiver may reject a Structure that contains unknown child Structures, missing required fields or incompatible field ordering.

4.10. Comments and Disabled Blocks

The line-comment marker is:

    #

Outside string/text literals and other literal syntaxes that define their own character rules, `#` starts a comment that continues to the end of the current physical line. The comment text is ignored by the source parser.

If `#` follows source text on the same line, the source text before `#` is parsed normally and the rest of the physical line is ignored.

Examples:

print: count # print the current value of count
# this whole physical line is a comment

The disabled-block marker is:

    $

`$` may appear at the start of a source item, immediately after that item's indentation zone. The parser removes `$` for the purpose of parsing the item, but marks the item as disabled.

If the disabled item opens a vertical Structure, the whole vertical Structure is disabled. The parser still parses the disabled item and its body, tracks source levels, validates closing forms and parses mathematical expressions. Therefore disabled code may still produce syntax errors.

Disabled code does not build source-semantic Structures for receiver consumption, does not register definitions, does not update models or registries and does not lower to executable/runtime behavior.

The `$` marker does not contribute to source level. The source level of a disabled item is computed exactly as if `$` were absent, whether the file uses canonical dotted form or relaxed indentation form. Child lines are written at the same source levels they would use for the enabled form.

Example:

$if: mode = debug
    then:
        print: debug branch
    ---
    else:
        print: release branch
    ---


This whole `if` Structure is disabled, but the parser still verifies the syntax and closing structure.

Example inside an enabled block:

if: mode = debug
    $then:
        print: disabled then branch
    ---
    else:
        print: active else branch
    ---


Here only the `then` Structure is disabled. Its body is still parsed and syntax-checked.

The `$` marker is not a receiver, not an operator and not a runtime action. It is a source-control marker handled before receiver consumption.

The raw file-comment fence is:

    ===

A raw file-comment fence is recognized only when the physical line begins at column 0 with `===` and is followed only by optional spaces or tabs before the line ending. No source indentation, leading spaces, title text or other non-whitespace characters are allowed on the fence line.

The first fence opens a raw file comment block. The next fence closes it. All physical lines between the fences are ignored completely by the Lingvamyxa parser. Source levels are not tracked inside the raw file comment block, mathematical expressions are not parsed, closing forms are not validated and source syntax errors inside the block are not reported.

Raw file comment blocks do not nest. A fence inside an open raw file comment block closes that block. An unclosed raw file comment block is a file-level syntax error.

Example:

===
This text is ignored by the parser.
Broken Lingvamyxa source may appear here:
    if (
===


5. Receiver-Based Semantics

5.1. Core Rule

Surface syntax builds Structures. Receivers and subroutines give those Structures meaning.

Semantic formula:

    surface syntax -> generic Structure -> receiver/subroutine -> typed semantic structure

A receiver has a signature. The signature defines how positional fields, semantic field names, anonymous positional Structures, expression fields and body fields are interpreted.

5.2. Receiver Consumption Modes

A receiver may consume a field as one of the following semantic modes:

    primitive value
    expression
    value-producing Structure
    body Structure
    callable/executable value
    declaration
    model fragment
    configuration message
    data Structure
    delayed branch
    relation frame
    query frame

The mode is receiver-defined. The parser does not decide that a field is executable merely because it looks like code.

5.3. Expected Field Positions and Anonymous Bodies

Parentheses create ordinary bounded Structures. A bounded Structure is not executable merely because it is parenthesized.

A receiver signature assigns an expected role to each field. If a field position is defined as a body, the receiver consumes the supplied Structure as an executable body Structure. This is the ordinary rule used by control receivers and definition receivers; it does not require a separate body keyword or separate anonymous-function syntax.

If a field position expects a callable/executable value and the source supplies a bounded Structure or vertical body Structure, the receiver consumes that Structure as an anonymous executable/callable value. Its argument and return profile come from the expected field position.

If a field position expects a primitive/scalar value and the source supplies a bounded Structure that is not already a direct primitive/scalar value, the receiver consumes that Structure as a value producer for the expected type. A mathematical expression Structure is the usual compact case of this rule.

If the expected type is boolean, the value producer must produce a boolean value. If the expected type is numeric or another primitive/scalar type, the value producer must produce that type or be convertible according to the active profile.

Example:

for: int(i, 0), (i < n), i++
    print: i


The `for` receiver consumes:

    field0 -> initialization Structure
    field1 -> boolean-producing condition expression
    field2 -> iteration-step executable Structure
    body   -> vertical executable body Structure

Compact body example:

    for: int(i, 0), (i < n), i++, print(i)

Here `print(i)` is the last argument Structure of `for`. The `for` receiver signature names that position as `body` and consumes it as the executable loop body. The compact body example uses only compact Frames and contains no inline short colon-form.

5.4. Example: `if`

For a computational L3 `if`, the receiver may define fields:

    condition
    then
    else

and consume them as:

    condition -> boolean-producing expression
    then      -> body Structure
    else      -> body Structure

During translation, the receiver lowers these fields into target control flow. During interpretation, the receiver evaluates the condition and then interprets only the selected body.

5.5. Example: `fn`

For an `fn` definition receiver, fields may be consumed as:

    name -> function name
    args -> argument Structure
    ret  -> return Structure
    body -> function body Structure

The receiver creates or registers an executable definition. The `fn` frame itself is not a function call.

5.6. Same Shape, Different Receivers

The same surface shape can have different semantics under different receivers.

Example:

    (a, b)

As a function argument Structure, it may mean two positional arguments.

As a return layout Structure, it may mean two return fields.

As a model fragment, it may mean a structural model.

As query input, it may mean a tuple of terms.

The receiver defines the interpretation.


6. Mathematical Expression Parser

6.1. Two Syntax Modes in One Parser

Lingvamyxa has one parsing system with two syntax modes:

    native structural syntax
    mathematical expression syntax

Native structural syntax builds ordinary receiver Frames and bounded Structures.

Mathematical expression syntax is entered when the parser detects mathematical expression indicators in an argument position. Indicators include explicit numeric literals and mathematical/operator tokens such as:

    =
    !=
    <
    >
    <=
    >=
    +
    -
    *
    /

The parser does not need to reinterpret forms such as `i = 1` as ordinary Lingvamyxa receiver syntax first. It detects the mathematical operator token and parses the expression with the expression rules. The token `=` is equality/comparison in mathematical expression syntax, not assignment in native structural syntax.

6.2. Expression Output

The mathematical syntax returns an expression Structure. This expression Structure is a tree-shaped Structure made of nested Structures.

Example source:

    i = 1

The parser detects this as mathematical syntax because of the `=` token. The exact internal expression-tree layout is not specified in this document. It belongs to the separate mathematical-syntax specification.

The native structural syntax described by this document is not the canonical representation of mathematical expressions. A form such as a receiver call with the name `=` is not defined here as the canonical expression output. It may be omitted entirely from the native receiver set if that makes lexical separation between native syntax and mathematical syntax simpler.

The important semantic rule is that mathematical syntax produces an expression Structure, not a separate fundamental AST type and not an ordinary runtime action.

The expression Structure is consumed later by a receiver that expects an expression, for example the `condition` field of `if`.

?
The mathematical expression syntax is specified separately. It must define operator tokens, precedence, grouping rules, expression Structure layout and translation rules. It may borrow an established mathematical/operator-precedence convention instead of inventing a full new expression language.
?

variant 1:
Use a compact C-like precedence table for arithmetic, comparison and boolean operators.

variant 2:
Use a minimal mathematical table that includes only numeric literals, grouping and explicitly listed mathematical operators.

variant 3:
Use a profile-based expression grammar selected by level, module or build configuration.

---ANSI C---
A translator may lower expression Structures to ANSI C expressions when precedence, evaluation order and side effects are fully known. Otherwise it may lower them to helper calls, temporary Structures or generated evaluator code.
---ANSI C---

6.3. Expressions Are Data Before Consumption

An expression Structure is data until a receiver consumes it as an expression.

For example, the `if` receiver consumes its `condition` field as an expression. A configuration receiver might instead store the same Structure as data.

When consumed in a primitive/scalar field position, an expression Structure is a value producer for that expected type. A comparison or logical expression may satisfy a boolean field. A numeric expression may satisfy a numeric field, subject to the active profile's conversion rules.

6.4. Parser Methods for Registered Operator Forms

A parser profile may recognize compact operator forms and lower them to parser methods before ordinary receiver consumption. This document does not define a final operator set for increment, decrement or similar forms, but it defines the expected source-semantic shape for such parser methods.

For example, if a profile registers prefix decrement:

    --i

the parser may split it into an operator method and a source target name:

    decBefore("i")

The parser method resolves `i` in the same shared namespace used by ordinary source. It may lower the operation as a read-update-write sequence. The write/update step uses the ordinary head/update form:

    i: newValue

If `i` resolves to mutable storage, the sequence may lower to a direct storage update. If `i` resolves to a callable value that can be consumed as a zero-argument read and one-argument update, the sequence may lower to generated temporary code that calls/consumes `i` to read, computes the new value, then calls/consumes `i: newValue` to write.

The exact parser methods, temporary names, evaluation order, numeric rules and diagnostics belong to the mathematical/operator specification. The core point is that parser methods do not introduce a separate assignment syntax; they compose with the same namespace resolution and head/update form as ordinary source.

6.5. Basic Array Operations

An array is a typed Structure whose value is described by element type, shape,
rank, storage and optional stride metadata.

An array is not a special execution object. It is ordinary structured data.
Operations over arrays are ordinary typed procedure/function/operator calls
resolved through the same registry/query mechanism as other operations.

A scalar value may be treated as a rank-0 array for array-expression purposes.
A vector is a rank-1 array, a matrix is a rank-2 array, and higher-dimensional
arrays are rank-N arrays.

Minimal array descriptor:

array:
. elementType = T
. rank = N
. shape = [d0, d1, ... dN-1]
. storage = contiguous | view | external | arena
. stride = optional byte strides
. data = implementation-defined storage reference
end: array

The canonical constructor receiver is [].

Examples:

[]: values
. 1
. 2
. 3
end: values

[]: matrix
. []: row
.. 1
.. 2
.. 3
. []: row
.. 4
.. 5
.. 6
end: matrix

The exact compact literal form is implementation-defined at early bootstrap
levels, but the resulting value must be a typed array Structure.

6.5.1. Indexing

Indexing selects an element or a subview.

For a rank-N array, a full index has N integer coordinates.

Example:

matrix[0, 2]

A partial index may produce a view rather than a copy.

Example:

matrix[0]

may produce the first row as a rank-1 array view.

Bounds checking is profile-dependent.

L2 may allow unchecked raw pointer indexing.
L3 and higher should use checked indexing unless the operation is explicitly
marked unsafe.

6.5.2. Views and Copies

Array operations may produce either a view or a copy.

A view shares storage with another array and carries shape/stride metadata.
A copy owns independent storage.

Examples of view-producing operations:

slice
reshape, when compatible with storage layout
transpose
broadcast
partial indexing

Examples of copy-producing operations:

explicit clone/copy
materialize view
result of elementwise arithmetic unless assigned into an existing output buffer

A view is borrowed by default. To retain it beyond the owner lifetime, handler
frame or message boundary, it must be copied into an owned array/branch according
to the L5 memory model.

6.5.3. Shape

shape(array) returns the array dimensions as a rank-1 integer array or shape
Structure.

rank(array) returns the number of dimensions.

length(array) returns the size of the first dimension for rank greater than zero.

size(array) returns the total number of elements:

size = d0 * d1 * ... * dN-1

6.5.4. Reshape

reshape changes the shape descriptor without changing element values.

reshape is valid only if the total element count remains unchanged, unless the
operation is explicitly defined as a copy/fill/truncate operation.

Example:

reshape(values, shape = [3, 1])

A reshape may return a view if the underlying storage layout permits it.
Otherwise it may materialize a copy.

6.5.5. Transpose and Permute

transpose(array) swaps the two last dimensions for rank >= 2, or follows the
profile-defined matrix convention.

permute(array, axes) returns a view with reordered axes when possible.

Example:

permute(tensor, axes = [1, 0, 2])

These operations normally modify shape and stride metadata only. They do not
copy data unless materialization is requested or required by the target backend.

6.5.6. Elementwise Operations

Arithmetic and comparison operators over arrays are elementwise by default.

Examples:

array + array
array - array
array * array
array / array
array == array
array < array

For numeric arrays, the operator is resolved by element type.

Example:

+(array<i64>, array<i64>)
  -> elementwise i64 addition

+(array<decimal>, array<decimal>)
  -> elementwise decimal addition using the decimal backend

Elementwise operations return an array whose shape is derived from the operand
shapes by the broadcasting rules.

6.5.7. Broadcasting

Broadcasting is a shape-compatibility rule for elementwise operations.

It does not require copying data.

Two shapes are broadcast-compatible if, after aligning dimensions from the
right, every corresponding dimension pair satisfies one of the following:

1. the dimensions are equal;
2. one dimension is 1;
3. one side has no dimension there and is treated as dimension 1.

The result dimension is the maximum of the two dimensions.

Examples:

[3] + []
  -> result shape [3]

[2, 3] + [3]
  -> [2, 3] + [1, 3]
  -> result shape [2, 3]

[2, 3] + [2, 1]
  -> result shape [2, 3]

A broadcasted dimension may be represented as stride = 0 in an array view.
This means that the same element is read repeatedly along that dimension.

Example:

[1, 2, 3] + 4

is semantically equivalent to:

[1 + 4, 2 + 4, 3 + 4]

but the scalar 4 is not copied into [4, 4, 4]. It is read through a rank-0 or
stride-0 broadcast view.

6.5.8. Reduction

A reduction collapses one or more dimensions using an associative or explicitly
ordered operation.

Examples:

reduce(+, values)
reduce(+, matrix, axis = 0)
reduce(max, matrix, axis = 1)

If no axis is provided, the reduction applies to all elements and returns a
scalar/rank-0 result.

If an axis is provided, only that axis is collapsed.

The operation must define:

identity value, if required;
element operation;
result type;
ordering guarantees.

For floating/real/decimal values, deterministic profiles should define stable
reduction order to avoid profile-dependent rounding differences.

6.5.9. Scan

scan is a prefix reduction.

Example:

scan(+, [1, 2, 3, 4])
  -> [1, 3, 6, 10]

scan may be inclusive or exclusive according to its descriptor.

6.5.10. Map

map applies a function/procedure to every element.

Example:

map(sin, values)

For pure functions, map may be vectorized, parallelized or lowered to a backend
array operation.

For impure procedures, ordering and side effects must be explicit. The default
array map profile should require pure functions.

6.5.11. Filter

filter selects elements according to a boolean predicate.

Example:

filter(values, predicate = isPositive)

The result is normally a new owned array, because the selected elements are not
guaranteed to form a regular strided view.

6.5.12. Concatenation

concat joins arrays along a selected axis.

Example:

concat(a, b, axis = 0)

All dimensions except the concatenation axis must match.

concat normally materializes a new owned array.

6.5.13. Matrix and Tensor Operations

Elementwise multiplication and matrix multiplication are distinct operations.

The * operator remains elementwise for arrays.

Matrix multiplication, tensor contraction and dot products should be represented
by explicit receivers/operators such as:

matmul(a, b)
dot(a, b)
contract(a, b, axes = ...)
outer(a, b)

A profile may define a symbolic operator for matrix multiplication, but it must
not overload elementwise * ambiguously.

6.5.14. C99 Lowering

A simple C99 lowering may represent arrays as descriptors:

LmArray:
. elementType
. rank
. shape
. stride
. data
. owner/borrow metadata
end: LmArray

Elementwise operations lower to loops over the broadcast result shape.

Broadcasting is lowered by computed strides. A broadcasted dimension uses
stride = 0.

Scalar plus array may therefore lower to the same generic loop as matrix plus
vector or tensor plus lower-rank array.

The implementation may later replace generic loops with specialized kernels,
SIMD kernels, BLAS calls or external numeric backends. This optimization must
not change the observable typed array semantics.

6.5.15. Minimal Bootstrap Profile

The bootstrap profile may support only:

rank-1 arrays;
rank-2 arrays;
contiguous owned storage;
checked indexing;
shape;
copy;
elementwise + - * /;
scalar-array broadcasting;
array-array elementwise operations with equal shape;
reduce over all elements.

Full broadcasting, slicing views, transpose, permute, scan, filter and tensor
contraction may be added later without changing the core array model.

7. `fn`, `sub` and Structural Closure

7.1. `fn` and `sub` Are Receivers

`fn` and `sub` are definition receivers. Each consumes a Structure, builds an executable/callable value and binds that value in the shared namespace. During bootstrap they may be present in an L1 prelude table or parser switch.

An `fn` frame consumes a Structure and creates a function callable value.

A `sub` frame consumes a Structure and creates a subroutine callable value.

7.2. Function Definition Form

Example source:

fn: myFunc, (int(i), int(j, 1), p1, p2), (int(r1), int(r2))
    print: i
    print: j
    p1()
    p2()
return: r1, r2

Strict conceptual form:

    fn(
      name(myFunc),
      args(
        int(i),
        int(j, 1),
        p1,
        p2
      ),
      ret(
        int(r1),
        int(r2)
      ),
      body(
        print(i),
        print(j),
        p1,
        p2
      )
    )

Explicit nested-source form:

fn:
    name: myFunc
    args:
        int: i
        int: j, 1
        p1
        p2
    ret:
        int: r1
        int: r2
    body:
        print: i
        print: j
        p1()
        p2()
end: myFunc

The receiver `fn` consumes its child Structures by receiver-defined semantic roles. The explicit nested forms `name(...)`, `args(...)`, `ret(...)` and `body(...)` are ordinary Structures consumed by `fn`. They are not `=` named fields.

The names `int`, `boolean` and similar names are primitive/type-constructor receivers when registered in the active receiver set. In declaration context, a type/constructor receiver consumes the following raw identifier/name phrase as a new binding name. If that name already exists in the current namespace, the declaration is invalid.

Compact definition form with vertical children inside the bounded argument list:

fn: i(
    args: int(v, j)
    ret: int
    body:
        j: v / 2
        return: v
)

This parses as a colon line Frame named `fn` whose first argument is a compact Frame named `i` with vertical child Structures. Parentheses do not disable source-level composition.

The `fn` receiver may define this as a compact definition form. In that form, the compact Frame name `i` becomes the function name, and the compact Frame children become definition child Structures.

Conceptual receiver-level interpretation:

    fn(
      name(i),
      args(
        int(v, j)
      ),
      ret(
        int
      ),
      body(
        j(v / 2),
        return(v)
      )
    )

The `args` child receives one compact declaration Frame:

    int(v, j)

In declaration context, this means an `int` binding named `v` whose default/initial value is `j`.

The following older inline style is invalid under the strict short-colon line rule, because it places short colon-forms directly inside parentheses and also tries to put several short colon-forms on one physical line:

    fn: i(args: int(v, j), ret: int, body: (j: v / 2, return: v))
    fn: i(args: (int: v, j), ret: int, body: (j: v / 2, return: v))

Use the vertical form above instead.

The form:

    args: int v j

parses as one phrase/signature field `int v j`, not as `args(int, v, j)`. To pass several fields through short colon-form, use commas:

    args: int, v, j

Here `j: v / 2` updates the visible binding `j`. The final result is returned with `return: v`. Using `i: v` as a function-name return binding is optional/profile-defined and is not the canonical form in this revision.

7.3. Subroutine Definition Form

Example source:

sub: l5_if, (boolean(condition)), then, else
return

Strict conceptual form:

    sub(
      name(l5_if),
      args(
        boolean(condition),
        then,
        else
      ),
      body(...)
    )

Explicit nested-source form:

sub:
    name: l5_if
    args:
        boolean: condition
        then
        else
    body:
        return
end: l5_if

The receiver `sub` consumes its child Structures by receiver-defined semantic roles. The argument `condition` is a primitive/evaluated argument through the registered constructor `boolean`. The bare names `then` and `else` are structural arguments. No `Struct then` annotation is required.

7.3.1. Single Namespace

7.3.1. Single Namespace and No Silent Shadowing

Types, variables, functions, subroutines, receivers, model names, generic operation names and local executable definitions share one lexical namespace within a lexical scope chain.

A new binding may be introduced only if the same name is not already visible in the active lexical scope chain. This includes names introduced by declarations, nested `fn` definitions, nested `sub` definitions, imports and model/type constructors.

A local variable cannot reuse the name of a visible type. A local `fn` or `sub` cannot reuse the name of a visible variable, type, receiver, model or executable definition. Imports must not silently shadow visible names. Conflict resolution must be explicit through a future import/qualification rule.

L5 message selectors are looked up through a receiver object's behavior table. A selector is not automatically a lexical binding unless it is also imported or registered as an ordinary receiver/generic operation. The implementation name attached to a message is a lexical executable binding and follows the single-namespace rule.

In expression position, a visible `fn` name is callable. The canonical way to return a value is `return: value`, including terminal return at the source level of the current function. A profile may optionally allow Pascal-style function-name return binding, but it is not the canonical return mechanism in this revision.

Example:

fn: factorial, (int(n)), (int)
    if: n <= 1
        return: 1
return: n * factorial(n - 1)

Inside the body, `return: 1` exits with value `1` when the condition holds. The expression `factorial(n - 1)` is a recursive function call because it appears in expression position. The final `return:` line is terminal return and closes the function.

7.3.2. Callable Values and Binding Updates

Executable definitions do not create a separate source-semantic category that must be distinguished from ordinary values before resolution. A function or subroutine name denotes a callable value in the same shared namespace that also holds primitive values, Structures, model names, receivers and other bindings.

The line form:

    i: 5

has one surface shape. After name resolution, it may mean an update to a mutable value binding `i`, or a call/consumption of a callable/receiver binding `i` with argument `5`. The language does not use `=` assignment to distinguish these cases.

If a callable binding is mutable, it may be updated by the same head/update form as other bindings:

    i: otherCallable

When `otherCallable` resolves to a callable value with a compatible callable Structure/signature, the binding `i` receives that callable value. Source semantics does not require a separate function-pointer syntax for this operation.

For a callable with no required arguments, value-like consumption may be receiver/profile-defined. For example, a parser method or receiver may lower a read of `i` to a zero-argument call `i()`, and a write/update of `i` to a one-argument call or binding update `i(newValue)`, depending on the resolved binding and active profile.

The exact mutability, compatibility and callable-signature rules are part of the execution-model and type/model specifications. The structural core only requires that callable values are ordinary namespace values and that the same head/update surface form is used after resolution.

7.3.3. Nested `fn` and `sub` Definitions

Nested `fn` and `sub` definitions are allowed inside executable bodies. A nested definition creates a local executable binding in the current lexical scope.

Example:

fn: outer
    int: x
    ---
    int
    ---
    fn: addX
        int: y
    ---
        int
    return: x + y
return: addX(10)

The nested `fn` `addX` is visible inside the body of `outer` after its definition and inside its own body for recursion. It is not visible outside `outer`.

A nested executable has its own local scope. It may read visible outer bindings according to lexical lookup. Mutation of outer bindings from a nested executable is not part of the minimal semantics unless a later execution-model specification defines explicit capture, reference or closure rules.

A nested `fn` or `sub` may not escape its defining scope unless a later closure/environment specification defines how its environment is represented. Returning a nested executable as a value, storing it in a longer-lived Structure or passing it to a context that may outlive the defining scope requires such closure semantics.

Because names are shared across types, variables, models and executables, nested definitions do not introduce shadowing. The following is invalid if `helper` is already visible as a variable, type, receiver, model or executable binding:

fn: outer
    int: helper
    ---
    int
    ---
    fn: helper
        int: x
    ---
        int
    return: x
end: outer

?
Closure representation, explicit capture, mutation of outer bindings and escaping nested executables are not specified in this document. They belong to a future execution-model and runtime specification.
?

7.4. Body Names

Variables or names used inside an `fn` or `sub` body do not become arguments automatically. Arguments are defined only by the argument Structure consumed by the definition receiver.

7.5. `end:` as General Closing Receiver

`end` is an ordinary receiver/control name used in colon line form. It is analogous to a closing parenthesis for vertical Structures. It has no runtime-return meaning by itself.

The source-level closing form is:

    end: <target>

The bare form `end` and the old-looking form `end <target>` are not valid Lingvamyxa source syntax.

`end:` validates `<target>` against a visible open frame, labelled block or entity block. The target may match the current node/receiver name, the normalized `name` field of the current Structure, or a visible control label according to the active closing policy. The target may be a multi-token label phrase when the active label policy permits such labels.

The closing line has its own source level. It may close several currently open implicit vertical levels at once if the named target is visible at or above that level. This allows a long tail of nested blocks to be cut with one named close. A parser must reject `end: <target>` if the target is ambiguous, not visible or not valid for closing from that position.

Examples:

if: condition
    bodyCall()
end: if

Here `if` validates against the node/receiver name.

fn: myFunc, (int(i)), (int(r))
    return: i
end: fn

Here `fn` validates against the node/receiver name.

fn: myFunc, (int(i)), (int(r))
    return: i
end: myFunc

Here `myFunc` validates against the normalized `name` field of the current `fn` Structure. In this form the normalized `name` field is derived from the first positional argument.

fn:
    name: myFunc
    args:
        int: i
    ---
    ret:
        int: r
    ---
    body:
        return: i
end: myFunc

Here `myFunc` also validates against the normalized semantic `name` field, but that field is written as an ordinary nested Structure.

fn:
    args:
        int: i
    ---
    name: myFunc
    ret:
        int: r
    ---
    body:
        return: i
end: myFunc

This is also valid because validation uses the normalized semantic `name` field rather than the raw first source argument.

All named forms above are valid structural surface forms. A style guide may prefer closing by the normalized entity name for long definitions and by receiver name for short local Structures.

A translator may implement vertical closure by internal closing handlers. Those handlers are implementation mechanisms. Source semantics only requires that the correct Structure is closed and that invalid closing tokens are rejected according to the active closing policy.


7.6. Label Blocks as Local Nullary Executables

Labels are not a separate source grammar category. A label spelling such as:

readLoop:
    readNext: record
    process: record
end: readLoop

is an ordinary colon Frame with an empty inline tail and a vertical body. When the active executable/control profile consumes this shape as a label block, the label name introduces a local namespace binding for that block.

A label-block binding is a local executable binding with no source arguments and no normal return value:

    Callable(() -> void)

or an equivalent implementation-level contract. It shares the same lexical namespace as variables, functions, subroutines, receivers, model names and other bindings. There is no separate label namespace.

In executable statement position, a bare identifier or phrase identifier may resolve to a visible zero-argument label-block binding. In that context, the bare name is the canonical call/consumption syntax for the label block:

readLoop

This is not a special parser form and it does not require `readLoop()`. The parser builds an identifier/value line. Name resolution in the current executable statement context decides that `readLoop` denotes the local nullary executable block and consumes/calls it with no arguments.

The same visible label binding may also carry a control-target role when the active profile materializes it as a loop/block label. Control-transfer receivers such as `break: readLoop`, `continue: readLoop`, `redo: readLoop`, `retry: readLoop` or failure-control receivers use that control-target role. A plain executable statement `readLoop` uses the callable/nullary-executable role.

Example post-condition loop:

readLoop:
    readNext: record
    process: record
until: endOfInput(record)

Here `readLoop:` opens a labelled executable block. The `until:` receiver closes that block and consumes it as the body of a post-condition loop. The label name `readLoop` is still a local namespace name for the block; the `until` lowering may implement the loop by direct structured control flow, by a generated label and branch, by an inline nullary block, or by another representation preserving the same source semantics.

Calling or consuming a label block does not by itself create a new function namespace, return binding or closure object. A later profile may define escaping label values, addressable label callables or call-frame labels, but the structural core only requires a local nullary executable binding and ordinary namespace resolution.


8. Runtime Return and Terminal Return

8.1. `return` Receiver

Runtime exit from an `fn`, `sub`, iterator-like executable body or method-like executable body is represented by the `return` receiver/operator.

`return` is not the same as the general structural close receiver `end:`. `end:` closes source structure by visible target name. `return` exits executable control flow. In one terminal position inside an open executable definition, `return` may also serve as the structural close of that executable definition.

8.2. Return Forms

The core return forms are:

    return
    return: value

Inside an executable body, `return` exits the current executable body.

For an `fn`, `return` without tail returns the current return binding. For a `sub`, `return` without tail exits without producing a normal return value.

For an `fn`, `return: value` evaluates or consumes `value` as one logical value compatible with the declared return model, stores that value in the current return binding, and exits the current executable body. If the function return model is structural, the tail of `return:` is consumed as one return Structure. Comma-separated fields may be mapped positionally to the return Structure by the `return` receiver signature.

For a `sub`, `return: value` is invalid unless a later profile defines a status/result convention for subroutines.

`return` is a receiver. It consumes the Structure supplied by its tail. It is not assignment syntax and does not introduce `=` as a native assignment or named-field operator.

Examples:

fn: square, (int(x)), (int)
return: x * x

Conceptual executable body:

    return(x * x)

Example with early runtime return and terminal return:

fn: factorial, (int(n)), (int)
    if: n <= 1
        return: 1
return: n * factorial(n - 1)

The indented `return: 1` line is an ordinary runtime return inside the `if` body. The final `return: n * factorial(n - 1)` is terminal return for the surrounding `fn` definition.

8.3. Terminal Return as Executable Structural Close

A terminal return is a `return` source item written at the source level of the open executable definition itself, where a structural close of that executable definition is expected.

If an executable definition is opened at source level N, then its ordinary vertical body items are normally written at level N + 1. A `return` line at level N is not a sibling root item. It is parsed as terminal return for the currently open executable definition, provided that the current open executable target is visible and compatible with `return`.

Terminal return is equivalent to appending the corresponding runtime `return` as the final body item and then closing the executable definition by its visible executable name.

Example:

fn: square, (int(x)), (int)
return: x * x

is source-semantically equivalent to:

fn: square, (int(x)), (int)
    return: x * x
end: square

The first form is the canonical compact form for a short function. The second form is an explicit expanded explanation of the same source semantics.

Terminal return may close the open executable tail in the same checked way as `end: <currentExecutableName>`. It is not a general close form for arbitrary Structures. It is valid only for executable definitions or executable-like receivers that explicitly admit terminal return.

Invalid examples:

return: 1

at root level with no open executable is invalid.

config: app
return: 1

is invalid unless `config` is an executable-like receiver that explicitly admits terminal return. `return` does not replace `end:` for ordinary data, model, configuration or registry Structures.

8.4. Runtime Return vs Terminal Return

The source level separates the two roles.

Runtime return inside a body:

fn: abs, (int(x)), (int)
    if: x < 0
        return: -x
return: x

Here the indented `return: -x` line is runtime control inside the `if` body. It does not structurally close the `fn` source item. The final `return: x` is terminal return at the function level and closes the function.

Terminal empty return is also valid when a return binding has already been prepared:

fn: estimate harvest, (PlantBed(bed)), (f32(harvest), f32(redApples), f32(greenApples))
    harvest: bed\area
    redApples: 0
    greenApples: 0
return

This is equivalent to appending a body-level empty `return` and closing the function.

8.5. Named Return Variables

Return values may be represented by declared return variables inside an executable body when the return signature gives them names.

Example:

fn: estimate harvest, (PlantBed(bed)), (f32(harvest), f32(redApples), f32(greenApples))
    harvest: bed\area
    redApples: 0
    greenApples: 0
return

The terminal empty `return` returns the current values of the declared return variables and closes the function definition.

A function return signature with several fields defines one return Structure. Updating several declared return fields and returning one Structure-compatible value are source-semantically equivalent when the produced Structure matches the declared return Structure.

Example positional structural return:

fn: split harvest, (PlantBed(bed)), (f32(harvest), f32(redApples), f32(greenApples))
return: bed\area, 0, 0

Here the `return:` tail is one logical return Structure with three fields consumed by the return signature.

8.6. Function-Name Return Binding

The old Pascal-style function-name return binding is not the canonical return form in this revision.

A profile may still allow the current function name in head/update position to denote the current return binding inside that function body:

fn: square, (int(x)), (int)
    square: x * x
return

However, this form is optional/profile-defined and should not be used as the primary return mechanism. The canonical forms are `return: value` and terminal `return`.

This restriction keeps the function name available for ordinary callable lookup, recursion and future local namespace overlay operations, where a callable binding may be locally replaced by another compatible callable value.

8.7. Implicit Return at Function End

Implicit return at function end is not the canonical source form in this revision.

A profile may still allow implicit final return of the current return binding when execution reaches the end of an `fn` body. A stricter profile may require either terminal `return`, `return: value`, or explicit `end: name` plus a previously established return binding.

The preferred style is:

fn: f, (int(x)), (int)
return: x + 1

rather than relying on an implicit return binding update.

8.8. Return Source Semantics

At the source-semantic level, every `fn` has one logical return value. That value may be a primitive value or a return Structure. A return signature with several fields defines one return Structure, not a separate non-structural mechanism.

The `return:` receiver fills or updates the current return binding from its tail and exits. The empty `return` exits and returns the current return binding. Terminal return additionally closes the current executable definition in source structure.

Physical return strategy, storage ownership and low-level runtime representation are translator/runtime implementation details. They are not part of the source-semantic core.

The error mechanism is not specified by this document. A function may represent an erroneous result as one of the values allowed by its declared return type unless a later error-system specification defines a separate convention.

?
The general error/status system is not specified in this document. It may be defined later as ordinary return values, tagged result Structures, receiver-level diagnostics or another mechanism.
?

---ANSI C---
Possible return-lowering variants for an ANSI C implementation:

variant 1:
A single primitive `return: value` lowers to a direct C primitive return.

variant 2:
A multi-field source return lowers to a caller-provided output Structure passed through a hidden or explicit implementation-level address.

variant 3:
A small return Structure lowers to a C struct returned by value if the translator/runtime profile allows it.

variant 4:
A structural return lowers to a handle/address allocated or managed by a runtime arena, heap, region or other implementation-owned storage.

variant 5:
Terminal return lowers as an ordinary body-level return followed by no further generated body statements. Source-level structural closure is resolved before lowering.

These variants are implementation strategies only. The language-level rule remains that `return` returns the declared primitive value or return Structure, and terminal return also closes the current executable definition.
---ANSI C---

9. Type and Model Forms

9.0. Default C99 Bootstrap Type and Dependency Map

The default ANSI C / C99 bootstrap profile may use the following implementation mapping for primitive and service-level source types. This is an implementation/dependency map, not a separate source grammar.

    i/u      -> C integer          -> no vcpkg
    bool     -> C int / bool       -> no vcpkg
    bigint   -> GMP mpz_t          -> vcpkg: gmp,  CMake: PkgConfig::gmp
    real     -> MPFR mpfr_t        -> vcpkg: mpfr, CMake: PkgConfig::mpfr
    decimal  -> decNumber         -> third_party\decNumber\decNumber-icu-368\
    SQL      -> SQLite            -> vcpkg: sqlite3
    Regex    -> PCRE2             -> vcpkg: pcre2

The `i/u` family denotes implementation-profile integer types over C integer storage. `bigint`, `real`, `decimal`, `SQL` and `Regex` are ordinary names/receivers/descriptors in the shared namespace when the active profile imports them. Their physical representation and linked libraries belong to the selected L1/runtime profile.

9.1. Type and Model Information

Type and model information is expressed by registered receivers and Structures.

The structural core does not require a separate `field` receiver. In declaration context, a type or model constructor consumes a raw identifier token and creates a binding/slot.

Example:

    u32: id
    Text: crop
    f64: harvest, 0.0

Conceptual meaning:

    declare binding/slot `id` with type `u32`
    declare binding/slot `crop` with type `Text`
    declare binding/slot `harvest` with type `f64` and default/initial value `0.0`

The token after the type constructor is not evaluated as an existing value. It is a raw name introduced by the declaration. If the name already exists in the current namespace, the declaration is invalid.

9.2. Type Constructors

A form such as:

    int: i

or:

    PlantBed: bed

is meaningful only if `int` or `PlantBed` is a registered primitive/type/model constructor receiver in the active level.

A receiver such as `fn`, `sub`, `autoModel` or `args` may consume these Structures as typed declarations.

9.3. Model Definitions

A model definition is a Structure consumed by a model receiver. One possible direction is to derive a model from a condition function:

L4:
    model:
        name: PlantBed
        condition: plantBedCondition
end: L4

L3:
    fn: plantBedCondition
        u32: id
        Text: crop
        f64: area
        f64: soilWater
        f64: harvest, 0.0
    ---
        boolean
    ---
        plantBedCondition: area > 0.0 && soilWater >= 0.0 && soilWater <= 100.0
        return
end: L3

In this direction, the input binding section of `plantBedCondition` defines the model slots and defaults. The boolean body defines the validation predicate.

Another possible direction is an `autoModel` receiver that receives a model name and two Structure arguments: one declaration Structure and one condition Structure.

Example:

L4:
    autoModel: PlantBed
        vars:
            u32: id
            Text: crop
            f64: area
            f64: soilWater
            f64: harvest, 0.0
        ---
        condition:
            area > 0.0
            soilWater >= 0.0
            soilWater <= 100.0
        ---
end: L4

This section does not define a final type/model language. It only states that model declarations are ordinary Structures consumed by model receivers.

?
The model/type declaration syntax is only partially specified. The preferred direction avoids a separate `field` receiver and uses declaration-context type constructors such as `u32: id` and `f64: harvest, 0.0`. Still unspecified: canonical alias syntax, explicit layout syntax, relation signature syntax, and whether canonical model definitions use condition functions, `autoModel`, or both.
?

variant 1:
Define models through condition functions. Function input bindings define model slots and the boolean body defines validation.

variant 2:
Define models through an `autoModel` receiver with explicit child Structures such as `vars(...)` and `condition(...)`.

variant 3:
Allow both forms and define one as canonical normalization for the other.

9.4. Normalized Model Descriptor

A model receiver may normalize its input into a model descriptor. This document uses the term `ModelSpec` for that normalized descriptor. `ModelSpec` is not a magical built-in source keyword; it is the conventional semantic result produced by receivers such as `model`, `autoModel`, imported schema receivers or future mapping receivers.

A minimal `ModelSpec` contains:

    name
    vars
    defaults
    conditions or validator
    layout policy
    derivation requests
    source/provenance metadata

`name` is the model name registered in the shared namespace.

`vars` is the ordered Structure of slots/bindings. Field order is part of the logical model and may be used for positional construction, return Structures, destructuring, layouts, relation signatures and serialization.

`defaults` are default initial values for slots. They may be represented directly in `vars`, for example `f64: harvest, 0.0`, or materialized as a separate descriptor view.

`conditions` or `validator` define which values are valid instances of the model. Conditions may be listed as expression Structures or delegated to a boolean function.

`layout policy` describes how stable or externally constrained the slot order/representation is. The physical representation is still a lowering decision unless an explicit layout receiver fixes it.

`derivation requests` describe which artifacts may be derived from the model, such as constructors, validators, accessors, relation signatures, serializers or documentation schemas.

`source/provenance metadata` records the source receiver, file, line, import or external origin of the descriptor for diagnostics and incremental rebuilds.

9.5. Union Descriptors and Variant Membership

A `union` receiver defines a closed set of allowed model variants.

Example:

L4:
    union: Shape
        Circle
        Square
        Triangle
    ---


Conceptual normalized descriptor:

UnionSpec:
    name: Shape
    variants:
        Circle
        Square
        Triangle
    ---


At source-semantic level, a value of `Shape` is a value whose concrete variant is one of the listed model names. A concrete variant value may be injected into the union when the expected type is the union.

Example:

    Circle: 10.0

creates a `Circle` value through the `Circle` constructor. If the expected type is `Shape`, the translator/receiver may inject that value into `Shape` by attaching the variant name `Circle` and the concrete `Circle` value.

Conceptual source meaning:

Shape:
    tag: Circle
    payload:
        Circle
            radius: 10.0
        ---
    ---


`tag` is the variant name. `payload` is the concrete value produced by the variant constructor. The union does not create the payload by itself.

The physical representation of a union value is not defined by this structural core. A translator may use tagged inline storage, tagged handles, model-id plus value-handle pairs, pointer-based payloads or another representation.

9.6. Registry Facts Generated by Structural Descriptors

Model, union, operator and behavior descriptors may be represented internally as typed facts. For example, a model descriptor for `Circle` may materialize facts such as:

    model: Circle
    slot: Circle, radius, f64

A union descriptor may materialize facts such as:

    union: Shape
    variant: Shape, Circle
    variant: Shape, Square
    variant: Shape, Triangle

These facts are registry facts. They are not ordinary runtime assertions unless a receiver exposes them to a runtime query system. The fact representation gives one uniform way to index, query, validate and derive registry information.

9.7. Model Extension and Conflict Policy

A model name has one structural `ModelSpec` unless an explicit extension/refinement receiver defines controlled composition. A second independent structural model definition for the same name is a conflict.

Adding constraints, behavior, generic methods, union membership or documentation to an existing model must be explicit through registered receivers such as `refineModel`, `behavior`, `method`, `variant`, `extendUnion` or future extension forms.


10. L5 Behavior, Objects, Messages and Facts

10.1. L4 Model vs L5 Behavior

The word `model` may appear at different levels, but the source semantics must distinguish two roles:

    L4 structural model -> slots, types, defaults, constraints, layout and derivations
    L5 behavior model   -> messages, selectors, method implementations and object dispatch

The canonical term for the L5 role in this document is `behavior`. If a future L5 profile allows the receiver name `model`, it must consume Structures as an L5 behavior/message descriptor, not as the L4 structural `ModelSpec` receiver.

10.2. Behavior Descriptor

A behavior descriptor attaches message responses to an existing model name.

Example:

L5:
    behavior: Circle
        message: drawOn, drawCircleOn
        message: area, circleArea
    ---


Conceptual descriptor:

BehaviorSpec:
    model: Circle
    messages:
        drawOn: drawCircleOn
        area: circleArea
    ---


The implementation names `drawCircleOn` and `circleArea` are ordinary executable bindings and must be visible in the shared namespace. Duplicate message selectors for the same model are conflicts unless an explicit override/refinement receiver defines another policy.

A behavior descriptor does not redefine the structural fields of `Circle`. It attaches message behavior to the structural model already registered under `Circle`.

10.3. Runtime Object Value

An L5 object value is a Structure or handle/reference to a Structure together with enough model information to resolve behavior. Conceptually:

object:
    model: Circle
    slots:
        radius: 10.0
    ---


The `slots` layout and validation come from the L4 `ModelSpec`. The message table comes from the L5 `BehaviorSpec` or from registry facts materialized from it.

10.4. Message Send

A message send has a receiver object, a selector and an argument Structure.

Example source form:

    shape: drawOn canvas

Conceptual send fields:

    receiver shape
    selector drawOn
    args (canvas)

Resolution:

    model shape\model
    method lookupMessage(model, drawOn)
    call method(shape, canvas)

The receiver object is passed as the first semantic argument to the selected implementation.

If `shape\model` is `Circle`, and the behavior registry contains:

    message: Circle, drawOn, drawCircleOn

then the send lowers or interprets as:

    drawCircleOn(shape, canvas)

10.5. Message Lookup Strategies

The source semantics require lookup by `(model, selector)`. The implementation may use dictionaries, selector indexes, method tables, inline caches or static lowering when the receiver model is known.

If no message exists for `(model, selector)`, the behavior is not fixed by this document. A strict profile may report an error. A dynamic L5 profile may route the send to a `doesNotUnderstand` receiver.

!!!
L5 message-missing behavior is not fixed. A final L5 behavior specification must decide whether missing messages are compile-time errors, runtime errors, `doesNotUnderstand` sends, receiver-defined diagnostics or query failures.
!!!

10.6. L5 Facts and Rules

L5 may store registry information as typed facts and rules. Examples:

    fact: model, Circle
    fact: slot, Circle, radius, f64
    fact: behavior, Circle
    fact: message, Circle, drawOn, drawCircleOn
    fact: variant, Shape, Circle
    fact: method, draw, Circle, drawCircle

The same information may also be materialized as descriptors such as `ModelSpec`, `UnionSpec`, `BehaviorSpec`, `OperatorSpec` or `GenericMethodSpec`. Descriptors and facts are two views of one registry model.

L5 rules may derive registry facts from other facts. For example, a rule may derive that a generic operation is complete for a union when every union variant has a registered method implementation.

10.7. L5 Configuration and Build Example

Example:

L5:
    target:
        app
        kind: executable
        sources: ("src/hello.lm3")
        entry: hello
        output: "build/bin/hello.lm0.exe"
    ---

    build: app


The `target` and `build` receivers define build semantics. They may also emit registry facts used by the builder. The structural core only creates Structures and specifies that L5 receivers consume them as messages, configuration, behavior descriptors, facts, rules or build/query requests.

11. Operators and Receiver Registration

11.1. Operator as Receiver Registration

`operator` is a receiver used during bootstrap or model loading. It registers receiver names, visibility levels and implementations.

Example:

L4:
    operator:
        while
        callableFrom: L3
        implementation:
            while_func
            level: L2
end: L4

Semantic meaning:

    Register a receiver/operator named `while`.
    Make it callable from L3.
    Use implementation `while_func`.
    Treat that implementation as L2-level implementation.

The `operator` frame is not the runtime/control operation being registered.

11.2. Runtime Use of Registered Operators

After registration, runtime/control source may contain:

L3:
    while: i < beds\len
        print: beds[i]\crop
        i: i + 1
end: L3

Here `while` is the opened frame and therefore may close as `end: while` or be closed implicitly by `end: L3`.

The active L3 `while` receiver consumes its argument Structure according to its registered signature, typically as:

    condition -> expression
    body      -> body Structure

11.3. Multiple Level-Specific Implementations

The same surface receiver name may have different implementations at different levels.

Example registrations may define:

    if callable from L3 -> l3_if
    if callable from L4 -> l4_model_if
    if callable from L5 -> l5_if

The active level determines which receiver implementation consumes the Structure.

11.4. Generic Operations and Method Registration

A generic operation is a registered receiver whose implementation is selected by a dispatch rule rather than by one fixed executable definition.

Example:

L4:
    operator: draw
        callableFrom: L3
        dispatchBy: firstArgumentModel
        domain: Shape
    ---

    method: draw, Circle, drawCircle
    method: draw, Square, drawSquare
    method: draw, Triangle, drawTriangle


The `operator: draw` frame registers `draw` as a callable generic receiver. The child Structure `dispatchBy: firstArgumentModel` says that the concrete implementation is selected by the model of the first argument. The child Structure `domain: Shape` restricts or documents the generic domain.

Each `method` frame registers one dispatch entry:

    method <generic-name> <model-name> <implementation-name>

Example semantic facts:

    generic: draw
    dispatchBy: draw, firstArgumentModel
    domain: draw, Shape
    method: draw, Circle, drawCircle
    method: draw, Square, drawSquare
    method: draw, Triangle, drawTriangle

The implementation names are ordinary `fn` or `sub` bindings and must satisfy the signature contract of the generic operation. For example, if `draw` returns no value, each drawing implementation is normally a `sub`. If `draw` returns a `DrawCommand`, each implementation must return a compatible value.

11.5. Dispatch from Union Domain

If a generic operation has a union domain, the union variants and method facts together define complete dispatch.

Example union facts:

    variant: Shape, Circle
    variant: Shape, Square
    variant: Shape, Triangle

Example method facts:

    method: draw, Circle, drawCircle
    method: draw, Square, drawSquare
    method: draw, Triangle, drawTriangle

At a call site:

    Shape: shape
    draw: shape

translation may derive:

match: shape
    ---
        Circle, c
        drawCircle: c
    ---
        Square, s
        drawSquare: s
    ---
        Triangle, t
        drawTriangle: t
    ---


The `match` form checks the union tag/variant name, extracts the payload as the concrete model and calls the registered implementation. If the first argument is statically known to be `Circle`, the call `draw: c` may lower directly to `drawCircle: c`.

Completeness for a union domain is a registry check: for every `variant(Shape, V)`, there must be a compatible `method(draw, V, Impl)` unless a default or fallback method is explicitly registered.

11.6. Generic Operation vs L5 Message

A generic operation such as `draw: shape` dispatches through a generic operation registry:

    (generic name, first argument model) -> implementation

An L5 message send such as:

    shape: drawOn canvas

dispatches through the receiver object's behavior table:

    (receiver\model, selector) -> implementation

Both mechanisms may be represented as registry facts. They are different source-semantic forms. A generic operation is centered on the operation name. A message send is centered on the receiver object.


12. Conditional Structures

12.1. L3 `if`

L3 `if` is a computational control-flow receiver. It consumes:

    condition -> boolean-producing expression
    then      -> executable body Structure
    else      -> executable body Structure

At interpretation time, only the selected body is interpreted.

At translation time, the receiver lowers the condition and body Structures into target control flow.

12.2. L4 `if`

L4 `if` is a model-conditional receiver. It does not execute runtime effects. It may conditionally include, exclude or normalize model Structures, registry entries and constraints.

12.3. L5 `if`

L5 `if` is a message/configuration dispatch receiver. It may conditionally dispatch build, run, query, startup or configuration messages.

12.4. Conditional Forms

Short positional conditional form:

if: mode = debug
    build: debugTarget
    build: releaseTarget

Normal form under signature `if(condition, thenBody, elseBody)`:

    if(
      <expression Structure for `mode = debug`>,
      (build(debugTarget)),
      (build(releaseTarget))
    )

The same conditional may be written with explicit named branch Structures:

if: mode = debug
    then:
        build: debugTarget
    else:
        build: releaseTarget

This builds:

    if(
      <expression Structure for `mode = debug`>,
      then(build(debugTarget)),
      else(build(releaseTarget))
    )

The short positional form is valid when the active `if` receiver assigns sibling child Structures to semantic fields by signature order. Named vertical form remains available for readability or when a style/profile requires explicit names.

13. L2 Addresses

13. L2 Addresses, References and Callable References

13.1. L3 Passing Model

At L3 and above, explicit address syntax is usually unnecessary. Structures, arrays, text, objects and other non-primitive values are passed as references or handles by default.

At L3 and above, ordinary names denote primitives, symbols, handles or Structures according to the active semantic environment. They are not raw L2 addresses to executable code.

13.2. L2 Address Values and Storage Allocation

At L2, the source model uses primitive values and typed address values. Aggregate model names such as `PlantBed` denote storage layouts, not ordinary source-level aggregate values.

Allocation and storage receivers create storage and bind the requested name to the address of that storage.

Examples:

stack: PlantBed, branch
heap: PlantBed, tree
static: PlantBed, root
int: count, 5
[]: leafs, count

int: x, 5
@: int, p
@@: int, pp
@@@: int, ppp

p: @x
pp: @p
ppp: @pp

Meanings:

    branch  address of stack storage with layout `PlantBed`
    tree    address of heap storage with layout `PlantBed`
    root    address of static storage with layout `PlantBed`
    count   primitive value/storage initialized to `5`
    leafs   address of array/byte storage sized by `count`, according to the active `[]` receiver/profile
    x       primitive storage/value initialized to `5`
    p       address-depth-1 slot whose base type is `int`
    pp      address-depth-2 slot whose base type is `int`
    ppp     address-depth-3 slot whose base type is `int`
    p: @x   stores the address of storage location `x` into `p`
    pp: @p  stores the address of storage location `p` into `pp`
    ppp: @pp stores the address of storage location `pp` into `ppp`

The receivers `stack`, `heap`, `static`, primitive constructors such as `int`, and allocation constructors such as `[]` are parser/bootstrap constructors in the same broad sense as type constructors: they consume layout/type information and a raw binding name, then introduce that binding with type metadata.

An L2 address value is not necessarily a source-level integer. It may carry, or be statically associated with, layout/type metadata. Receivers and L1 lowering may use that metadata to treat an address as a typed reference rather than as a printable numeric address.

The core L2 syntax does not use a separate `*` or `^` marker for address types. Address-ness is introduced by storage/allocation forms, by the reserved address-depth operator family `@ⁿ`, by address-producing expressions, and by typed field or index operations.

13.2.1. Reserved Address-Depth Operator Family `@ⁿ`

The token sequences:

    @
    @@
    @@@

form the reserved L2 address-depth operator family `@ⁿ`. They are reserved operator heads, not ordinary user-defined identifiers. Ordinary source cannot bind procedures, functions, receivers or variables named `@`, `@@`, `@@@` and so on, unless a privileged core/prelude profile explicitly defines the reserved operator metadata.

In head position before `:`, `@ⁿ:` declares an address/reference slot of depth n:

    @: BaseType, name
    @@: BaseType, name
    @@@: BaseType, name

Examples:

    @: int, p
    @@: int, pp
    @@@: int, ppp

Meanings:

    p    address-depth-1 slot whose base type is `int`
    pp   address-depth-2 slot whose base type is `int`
    ppp  address-depth-3 slot whose base type is `int`

Comma is required between the base type and the binding name under the Rev.12 comma-tail rule. Therefore:

    @@@: int, ppp

has two fields, `int` and `ppp`, while:

    @@@: int ppp

has one non-numeric phrase segment `int ppp` and is not the canonical address-depth declaration form.

The prefix expression form `@x` remains the depth-1 address-of operation. Higher address depth is expressed by declaring deeper address slots and storing ordinary depth-1 addresses of those slots:

    int: x, 5
    @: int, p
    @@: int, pp
    @@@: int, ppp

    p: @x
    pp: @p
    ppp: @pp

This keeps prefix address-of simple while preserving arbitrary address depth in declarations.

The implementation of `@ⁿ` may be represented by reserved operator descriptors in the L2 operator table. The source semantics only require that `@ⁿ` is parsed as a reserved operator family and that its declaration form produces typed address slots compatible with the active L2 memory profile.

13.3. Address-of, Raw Load and Callable References

The prefix form:

    @x

returns the address of the storage location `x`.

If `x` is already an address binding, `@x` is the address of the binding that stores that address. It is address-of-address, not the address of the target object. This is the expression-side companion of the declaration-side `@ⁿ:` family: `@@: int, pp` declares an address-depth-2 slot, while `pp: @p` fills that slot with the address of the depth-1 slot `p`.

The prefix form:

    \a

performs a raw L2 load at address expression `a`. It reads the primitive cell, word or value defined by the active L2 memory profile. It does not perform typed structural rendering by itself.

The field-follow form:

    a\field

follows typed address/reference `a` to the named field `field`. It uses the known layout/type metadata of `a`, reads or writes the field slot, and returns the field content as either a primitive value or another typed address/reference.

Examples:

print: @count
print: \leafs
print: leafs[3]
print: \(leafs + 3)
tree\branch: branch
root\branch: tree
print: tree\branch
print: @tree\branch
print: root\branch\branch
print: \root\branch\branch

Meanings under the declarations in section 13.2:

    print: @count
        Print the address of the primitive storage location `count`.
        To print the primitive value `5`, write `print: count`.

    print: \leafs
        Raw-load and print the first primitive cell/element at address `leafs`.
        This bypasses typed array/string rendering.

    print: leafs[3]
        Print the indexed element at address/index position `3` under the active `[]` profile.

    print: \(leafs + 3)
        Compute address `leafs + 3`, raw-load the primitive cell/element at that address, then print it.

    tree\branch: branch
        Store the typed address value `branch` into the field slot `branch` inside the storage addressed by `tree`.

    root\branch: tree
        Store the typed address value `tree` into the field slot `branch` inside the storage addressed by `root`.

    print: tree\branch
        Read the field `branch` through typed address `tree`.
        If that field contains a typed `PlantBed` address, `print` may render the whole object/tree addressed by that field.

    print: @tree\branch
        Print the address of the field slot `branch` inside the storage addressed by `tree`.
        This is parsed as `print: @(tree\branch)`.

    print: root\branch\branch
        Follow `root\branch` to the typed address stored there, then follow its `branch` field.
        If the final result is a typed `PlantBed` address, `print` may render that whole nested object/tree.

    print: \root\branch\branch
        Follow `root\branch\branch`, then raw-load the primitive cell/element at the resulting address.
        This is parsed as `print: \(root\branch\branch)` and bypasses typed object rendering.

Field-follow and index chains bind tighter than prefix `@` and prefix `\`.

Therefore:

    @tree\branch

is parsed as:

    @(tree\branch)

and means the address of the field slot `branch` inside the storage addressed by `tree`.

Likewise:

    \root\branch\branch

is parsed as:

    \(root\branch\branch)

and means a raw load from the address produced by the typed field-follow chain.

At L1 lowering time, a receiver such as `print` receives typed values or typed references when the source expression preserves type metadata. For example, `leafs` may be printed as a whole array/string/buffer when its allocation metadata is known, and `tree\branch` may lower to a `PlantBed*`-like reference or an equivalent `(layout, address)` pair, so `print: tree\branch` may render a whole object/tree according to the active print receiver. The prefix raw-load form `\expr` bypasses that structural interpretation and produces the primitive cell/value loaded at the computed address, so `print: \leafs` prints the first primitive cell/element under the active L2 memory profile.

Function/subroutine address forms are strictly L2. A static L2 executable binding may be addressable through `@name` if the active L2 profile exposes it as storage or callable-address metadata.

At L3 and above, calls are expressed as receiver Frames and resolved by the active receiver/operator registry, not by raw callable addresses. L5 message selectors and behavior-table entries are not automatically L2 callable addresses.

?
The exact L2 memory profile must define primitive cell size, address arithmetic, alignment, storage duration, allocation failure, callable-address representation and which bindings are addressable through `@`.
?

variant 1:
Treat `@ⁿ`, prefix `@`, prefix `\`, field-follow `\field` and `[]` as built-in L2 parser forms.

variant 2:
Treat them as bootstrap-registered L2 operators with parser support only for tokenization and precedence.

variant 3:
Allow both forms: parser-level recognition for core operators and receiver-level extension for specialized memory models.


14. Arrays, Text and Indexing

14.1. Logical Model

At L3 and above, an array is a Structure or handle/reference to a Structure. Text is also a Structure or handle/reference to a Structure.

The logical array model includes at least a length field and an indirect storage reference. It may also include capacity, encoding, element type and storage handle.

14.2. L2 Lowering

At L2, arrays and text may lower to typed addresses, length-plus-address records or other layout-specific representations.

Example conceptual lowering for an array:

    (len, addr)

Lowering does not change source semantics.

14.3. Indexing

The mathematical expression parser is specified separately. Indexing is treated as a level-dependent operator/form.

At L2, `[]` is a low-level index operator. It uses a typed or computed address and is governed by the L2 memory model.

Example conceptual L2 meaning:

    beds[i] means the element at the computed address

subject to the actual L2 layout and address rules.

At L3 and above, `[]` accesses an array Structure indirectly and performs bounds checking through the array metadata, at minimum the `len` field.

Example conceptual L3 meaning:

    beds[i] means index(beds, i)

where `index` receives the array Structure or handle, checks `0 <= i < beds\len`, and returns the element or reports a bounds error.

?
The final array/text specification must define exact index result semantics, slicing, negative indexes if any, multidimensional arrays, text encoding and the boundary between parser form and receiver/operator form.
?

---ANSI C---
Possible array-lowering variants:

variant 1:
L2 array access lowers to computed-address access with no automatic bounds check.

variant 2:
L3+ array access lowers to a length-plus-address or length-plus-handle Structure with generated bounds checks.

variant 3:
Dynamic arrays lower to runtime handles with accessor calls when layout is not statically known.

15. Typed Field Follow

15.1. Backslash Field-Follow Form

Named field follow/access uses backslash syntax:

    result\harvest

The field-follow form is a built-in parser form. It exists so the translator can generate direct field-follow access through known Structures, typed addresses, handles and layouts.

At L2, the left side is normally a typed address. At L3 and above, the left side may be a Structure, handle or reference according to the active semantic environment.

The same `\` character also has a prefix L2 raw-load form, described in section 13.3. These forms are distinguished by position:

    \address      raw L2 load from an address expression
    value\field   typed field follow/access

Possible normal form:

    field(result, harvest)

or an internal field-follow expression Structure equivalent to it.

15.2. Lowering

If the model/layout of `result` is known, the translator may lower:

    result\harvest

into direct structure access, typed-address field-follow access or generated accessor code.

If the model/layout is dynamic, the receiver/runtime may perform a checked lookup.

!!!
Field-follow failure semantics are not fixed. A final source-semantic rule must define behavior for missing fields, unknown models, dynamic Structures and nullable handles, including whether such cases are compile-time errors, runtime errors or receiver-defined diagnostics.
!!!

---ANSI C---
Possible field-follow lowering variants:

variant 1:
Known static layouts lower to direct C struct-field access.

variant 2:
Known typed-address layouts lower to direct pointer-field access in ANSI C.

variant 3:
Dynamic Structures lower to checked runtime lookup or generated accessor calls.
---ANSI C---


16. Update, Return Structures and Destructuring

16.1. Binding Update Instead of `=` Assignment

The native structural core does not use `=` for assignment.

A declaration with initialization is written through a declaration-context constructor:

    int: a, 3

A later update to an existing mutable binding or addressable field/index location is written by placing that location in head/update position:

    a: 4

Example:

    int: a, 3
    print: a
    a: 4
    print: a

The first `print` observes `3`. The second `print` observes `4`.

The update form is valid only if the head resolves to an existing mutable binding, addressable field/index location, or receiver that explicitly accepts such a call. Because Lingvamyxa uses one lexical namespace, a binding name and a receiver/type/function name cannot silently mean different things in the same scope.

The same surface form is used for callable consumption. For example, `i: 5` is parsed as a Frame with head `i` and argument `5`. If `i` resolves to mutable storage, the form may update storage. If `i` resolves to a callable/receiver binding, the form may call or consume that callable value. This is a compile-time resolution choice, not a syntactic distinction.

A bounded Structure or compact Frame in an argument/update position remains one Structure after parsing. If the resolved head expects a callable or executable-body value in that position, the Structure is consumed as an anonymous executable/callable value. For example, in `for: int(i, 0), (i < n), i++, print(i)`, the final `print(i)` is the `body` argument consumed by `for`.

At L2, update may lower to direct storage write according to the L2 memory model. At L3 and above, update is receiver-defined over variables, fields, handles and Structures.

?
Binding, mutability, scope, initialization, reassignment and shadowing rules are not specified in full in this document. They require a dedicated execution-model specification.
?

16.2. Return Structures

A function return value is one logical source-level value. That value may be primitive or structural. If the return value is structural, updating its declared fields and returning one Structure-compatible value are source-semantically equivalent under the receiver-defined return signature.

A function may return a Structure with ordered and/or semantic named fields.

Example return signature:

    (f32 harvest, f32 redApples, f32 greenApples)

Canonical structural return:

    return: bed\area, 0, 0

Named return variables may also be updated before an empty terminal return:

    harvest: bed\area
    redApples: 0
    greenApples: 0
    return

The old Pascal-style current function-name return binding is optional/profile-defined. The canonical return mechanism is `return: value` or terminal empty `return` after updating named return variables.

16.3. Destructuring

Destructuring syntax using `=` is not part of the current native structural core.

The semantic operation still exists: a produced Structure may be assigned or bound as one value, stored in a temporary service binding, or used to update target bindings from its fields by name or by position.

Possible explicit receiver form:

unpack: toEat(myFilter, Monday)
    harvest
    redApples
    greenApples
end: unpack

Conceptual meaning:

    tmp receives toEat(myFilter, Monday)
    harvest receives tmp\harvest
    redApples receives tmp\redApples
    greenApples receives tmp\greenApples

If the produced Structure has no field names, a receiver-defined positional unpack form may map fields by order.

?
The canonical destructuring/update syntax is not specified. A final execution-model specification must define whether destructuring is written through an `unpack` receiver, through target-list syntax without `=`, or through another explicit structural form.
?

---ANSI C---
A translator may implement destructuring by assigning the produced Structure or handle to a temporary service variable and then generating field updates one by one.

variant 1:
For known static layouts, generated code reads fields directly from the temporary Structure.

variant 2:
For handle-based Structures, generated code reads fields through generated accessors or runtime lookup.
---ANSI C---


17. L4 Non-Executive Semantics

L4 consumes Structures as model/type/contract/registry input. It may:

    register models
    register relation signatures
    check contracts
    normalize schemas
    derive layouts
    derive validators
    update the internal compiler/runtime model
    prepare compilation or self-compilation metadata

L4 does not directly perform ordinary runtime effects by default.

Runtime effect receivers such as file I/O, network send, process launch, database write, ordinary runtime print and thread start are not visible from L4 unless a special compile-time diagnostic or model receiver explicitly exposes a non-runtime effect.

A diagnostic receiver visible from L4 is not the same as L3 runtime `print`.


18. L5 Message, Fact and Build Semantics

18.1. L5 Input

An L5 file contains messages, configuration Structures, behavior descriptors, registry facts, rules and build/query/startup receivers. It is not a special `project` file unless a project receiver is explicitly registered.

The builder may be given a `.lm5`, `.lm3`, `.lmx` or other Lingvamyxa source file. It handles the top-level Structures through active receivers.

18.2. Registry-as-Facts Model

L5 may treat registry information as a typed fact store. Structural declarations from L4 can materialize facts. L5 behavior/configuration receivers can add facts. L5 query/build receivers can ask questions over those facts.

Examples:

    fact: model, Circle
    fact: slot, Circle, radius, f64
    fact: variant, Shape, Circle
    fact: behavior, Circle
    fact: message, Circle, drawOn, drawCircleOn
    fact: generic, draw
    fact: method, draw, Circle, drawCircle

The registry may also expose materialized descriptors such as `ModelSpec`, `UnionSpec`, `BehaviorSpec`, `OperatorSpec`, `GenericMethodSpec` and `RelationSpec`. These descriptors are derived views over facts or the facts are derived views over descriptors. The source semantics only require consistency between these views.

18.3. Target Example

Possible L5 build input:

L5:
    target:
        app
        kind: executable
        sources: ("src/hello.lm3")
        entry: hello
        output: "build/bin/hello.lm0.exe"
    ---

    build: app


The `target` and `build` receivers define the build semantics. The core only creates Structures.

18.4. Entry Resolution

The builder either finds an entry/target through receivers, messages, facts and signatures, or reports:

    no entry point

An executable entry wrapper is created from build/target/entry information or from an implicit L3 top-level entry. It is not derived from a source file name.

The symbol `main` may be a conventional entry symbol, but it is not a required startup-file convention.

19. Compilation and Lowering

19.1. Compilation Pipeline

Compilation means:

    Lingvamyxa source
        -> Structures
        -> semantic receiver handling
        -> L1 projection or another implementation target
        -> L0 artifact

This document specifies only the source-semantic side of that pipeline. The exact L1 syntax, L1 file format, L1 compiler interface and L0 build mechanism are outside this document.

---ANSI C---
An ANSI C based translator may use the following implementation pipeline:

    Lingvamyxa source
        -> Structures
        -> semantic receiver handling
        -> generated ANSI C projection
        -> platform C compiler/linker
        -> L0 artifact

Generated/debuggable C projections may preserve source mapping with `#line` directives, comments or a separate source-map file. This is a translator feature, not source syntax.
---ANSI C---

19.2. Source File Extensions

Lingvamyxa source files may use:

    *.lm2    L2-only source
    *.lm3    L3-only source
    *.lm4    L4-only source
    *.lm5    L5-only source
    *.lmx    mixed Lingvamyxa source

Generated/debuggable projections may exist for translator diagnostics and verification. Their exact format and file extensions are implementation-defined.

A debug build may preserve source mapping through an implementation-defined source-map mechanism.

19.3. Per-Level Build Semantics

L2 sources are unsafe modules/libraries/objects. They are compiled, not interpreted as scripts.

L3 sources may be interpreted or compiled. A top-level L3 sequence may become an implicit executable entry.

L4 sources are checked, loaded and registered as model/contract/registry input. They are not launched as programs.

L5 sources are message/configuration/build/startup/query inputs consumed by L5 receivers.

Mixed `.lmx` sources are handled according to level receivers and entry rules. L5 entry messages take precedence if present; otherwise an L3 top-level sequence may become an implicit entry if the builder allows it.


20. Source Semantics and Implementation Lowering

20.1. Logical Argument Structure

Every source call has one logical argument Structure.

Example:

    mySub(1, 2, 3, 4)

Logical source semantics:

    mySub(
      field0(1),
      field1(2),
      field2(3),
      field3(4)
    )

20.2. Physical Optimization

The logical Structure always exists at the source-semantic level. A translator may optimize away the physical Structure if the observable source semantics are preserved.

This means that the source call:

    f(a, b, c)

is always semantically treated as a call with one argument Structure containing `a`, `b` and `c`.

A concrete translator may pass fields directly, use a handle, use a temporary Structure, inline the call, specialize adapters or apply any other physical strategy. These choices do not change the Lingvamyxa source semantics.

20.3. Return Lowering Independence

The same rule applies to returns. A return signature defines a source-level return value: either a primitive value or a return Structure. The translator may choose any physical return strategy that preserves this source-level result.

The Lingvamyxa source-semantic core does not define physical calling conventions or storage strategies.

---ANSI C---
Possible internal call-lowering variants for an ANSI C implementation:

variant 1:
Pass up to three primitive/reference source fields directly to an internal generated C function. References and handles may be treated as primitive scalar values for this implementation convention.

variant 2:
If more logical fields exist, generate an args Structure and pass an address/handle to it.

variant 3:
Generate specialized adapters for concrete call sites, including direct calls, temporary args Structures, inlining or whole-program specialization.

Possible exported ABI variant:

    LmStatus f(LmRuntime *rt, const F_Args *in, F_Ret *out)

This shape is only an implementation option. The language does not know about `LmRuntime`, C function signatures, hidden arguments or slot counting.
---ANSI C---


21. Facts, Rules, Relations and Query

21.0. Logical Registry and Query Layer

The logical layer is represented by facts, rules, relations and query receivers.
It is not a separate runtime language and it does not introduce a separate
Prolog-like surface syntax. It is a structured query-and-derivation mechanism
over typed Lingvamyxa Structures and registry facts.

A fact is a typed Structure stored in a registry model. A rule is a typed
derivation procedure over facts and Structures. A relation defines a searchable
logical connection between typed Structures. A query receiver consumes a query
Structure and returns an iterator-compatible result Structure or another
receiver-defined result Structure.

The registry model may contain source facts, generated facts and materialized
descriptor facts. Model, union, operator, method, behavior, protocol, type,
object, relation and build descriptors may materialize typed registry facts.
Conversely, a receiver may derive descriptors as views over existing facts. The
source semantics require consistency between the descriptor view and the fact
view, not one privileged physical storage form.

The same registry/query mechanism may be used for:

    generic dispatch
    message lookup
    operator resolution
    method selection
    protocol satisfaction
    model completeness checks
    union exhaustiveness checks
    validation
    documentation generation
    build target derivation
    lowering rule selection

This gives Lingvamyxa one uniform mechanism to index, validate, derive and lower
structural information. A translator or runtime does not need a separate hidden
mechanism for every registry-like task. It can ask the registry model questions
and consume the query result.

Example conceptual operator-resolution query:

query:
    operator: +, decimal, decimal, ?implementation, ?resultType

Possible result bindings:

    ?implementation -> decNumberAdd
    ?resultType     -> decimal

Example conceptual method-dispatch query:

query:
    method: draw, Circle, ?implementation

Possible result binding:

    ?implementation -> drawCircle

The logical layer may support search, backtracking, unification and constraint
checking, but these are receiver/query-engine semantics over Structures. They do
not make every Structure executable and they do not change the core rule that
source syntax first builds data.

21.1. Relation Signatures

Relational mode is a receiver-based semantic mode over Structures. It does not introduce a separate Prolog-like surface syntax.

A relation signature describes the shape and types of a relation. Relation signatures belong primarily to L4.

Example:

L4:
    relation: variant
        Symbol: unionName
        Symbol: modelName
    ---

    relation: method
        Symbol: genericName
        Symbol: modelName
        Symbol: implementationName
    ---


The relation receiver registers relation signatures. It does not assert facts by itself.

21.2. Facts

A fact assertion is an ordinary Structure consumed by a `fact` receiver or another fact-producing receiver.

Examples:

    fact: variant, Shape, Circle
    fact: method, draw, Circle, drawCircle
    fact: message, Circle, drawOn, drawCircleOn

A relation frame such as:

    parent(Astra, NyufNyuf)

is a fact only when consumed by a fact receiver. It is a query only when consumed by a query receiver.

21.3. Registry as Typed Fact Store

The compiler/runtime registry may be modeled as a typed fact store. The following are examples of registry facts:

    model: Circle
    slot: Circle, radius, f64
    union: Shape
    variant: Shape, Circle
    behavior: Circle
    message: Circle, drawOn, drawCircleOn
    generic: draw
    dispatchBy: draw, firstArgumentModel
    domain: draw, Shape
    method: draw, Circle, drawCircle

Descriptors such as `ModelSpec`, `UnionSpec`, `BehaviorSpec`, `OperatorSpec` and `GenericMethodSpec` may be materialized views over these facts. Conversely, source receivers may first produce descriptors and then materialize facts from them.

21.4. Rules

A rule defines a relation in terms of other relations.

Example conceptual form:

rule:
    completeGeneric: draw, Shape
    if:
        variant: Shape, ?model
        method: draw, ?model, ?implementation


The exact syntax for rule heads, rule bodies, conjunction, disjunction, negation and aggregation is not specified by this document.

Rules are useful for deriving registry-level information, for example:

    a generic operation is complete for a union
    a model has a slot inherited from a refinement
    an object responds to a message
    a build target has all required sources

21.5. Query

A query asks for bindings that satisfy relation Structures.

Example:

query:
    method: draw, ?model, ?implementation


Meaning:

    find model and implementation pairs for generic operation draw

A query may contain unknowns such as:

    ?model
    ?implementation
    ?who

Unknowns are logical variables interpreted by relational receivers. They are not ordinary uninitialized variables.

21.6. Generic Dispatch as Query

Generic dispatch can be derived by querying registry facts.

For a call:

    draw: shape

where `shape` has type `Shape`, the translator may query:

    variant: Shape, ?model
    method: draw, ?model, ?implementation

For each result, the translator can generate a `match` case over the union variant.

For a concrete call:

    Circle: c
    draw: c

the translator may query:

    method: draw, Circle, ?implementation

and lower directly to the returned implementation.

21.7. Message Lookup as Query

L5 message lookup can also be represented as a query over facts.

For a send:

    shape: drawOn canvas

where `shape\model` is `Circle`, the runtime or translator queries:

    message: Circle, drawOn, ?implementation

and calls the returned implementation with the receiver object and message arguments.

21.8. Fact Persistence

Facts may accumulate faster than source modules. Persistent fact storage may be separate from source files.

Recommended division:

    signatures/contracts/rules       -> L4/L5 source modules
    generated registry facts         -> compiler/runtime registry
    accumulating domain facts        -> persistent store or database backend
    query/relation engine            -> receiver layer over Structures and storage backend

SQLite or another database may be used as a backend, but it is not part of the core syntax.

21.9. Unification

Relational search is based on unification. Unification attempts to make two relation Structures compatible by assigning unknowns.

It respects:

    relation name
    argument count
    positional order
    semantic named fields when used
    L4 relation signatures
    contracts and constraints when attached

21.10. Query Result

A query returns a Structure, for example:

QueryResult
    bindings
        binding: ?model, Circle
        binding: ?implementation, drawCircle
    ---
    status: success


?
The exact syntax and core status of `?name` logical variables, list literals, rule bodies, negation, aggregation and query result Structures belong to the relation/query specification. That specification must define these forms or map them to registered receivers.
?

22. Structural Grammar Sketch

This grammar sketch describes the structural parser only. It does not define final receiver semantics.

    program             ::= { empty_line | physical_item }

    physical_item       ::= raw_file_comment_block
                          | logical_line

    raw_file_comment_block
                        ::= "===" trailing_horizontal_space newline
                              raw_ignored_line*
                            "===" trailing_horizontal_space newline

    trailing_horizontal_space
                        ::= { " " | tab }

    horizontal_space    ::= " " | tab

    logical_line        ::= source_level line_content newline

    indentation         ::= { "." | " " | tab }

    source_level        ::= integer source level assigned by the
                            source-level normalization prepass

    source-level normalization prepass:
                            maps each physical line to a source-level event
                            before the structural grammar consumes it;
                            in canonical dotted notation, source_level is the
                            count of leading dot characters;
                            in relaxed indentation notation, source_level is
                            computed by the indentation-stack rule.

    empty_line          ::= trailing_horizontal_space newline
                            formatting whitespace; not a structural close
                            token and not a replacement for a required
                            same-level delimiter

    line_content        ::= dot_only_marker
                          | comment_body
                          | disabled_body
                          | colon_frame_body
                          | nullary_line_body
                          | expr_line_body

    dot_only_marker     ::= empty content after indentation
                            valid only if source_level > 0;
                            may delimit/open an anonymous Structure at that level

    comment_body        ::= "#" ignored_until_newline

    disabled_body       ::= "$" enabled_line_body

    enabled_line_body   ::= colon_frame_body
                          | nullary_line_body
                          | expr_line_body

    compact_frame       ::= name "(" [ argument_list ] ")"

    line_frame          ::= source_level colon_frame_body newline

    colon_frame_body    ::= head_phrase ":" [ line_arguments ]

    // A physical source line may contain at most one short colon-form.
    // A short colon-form must be the main source item of that line.

    head_phrase         ::= head_token { horizontal_space head_token }

    head_token          ::= source token allowed in receiver/head position

    nullary_line_body   ::= name
                            valid in executable statement position only when
                            `name` resolves to a zero-argument consumable binding:
                            registered nullary operator/receiver or visible zero-argument fn/sub

    line_arguments      ::= comma_argument_list | numeric_run | phrase_field

    comma_argument_list ::= line_argument { "," line_argument } [ "," ]

    numeric_run         ::= numeric_literal { horizontal_space numeric_literal }
                            valid as shorthand for comma-separated numeric fields

    phrase_field        ::= non-comma tail segment not parsed as numeric_run or expression

    expr_line           ::= source_level expr_line_body newline

    expr_line_body      ::= expression

    argument_list       ::= argument { "," argument } [ "," ]

    argument            ::= expression_or_structure

    // Short colon-forms are not inline arguments.
    // They may appear inside parentheses only as separate physical
    // source lines under source-level composition.

    bounded_structure   ::= "(" [ argument_list | vertical_argument_list ] ")"

    vertical_argument_list
                         ::= newline source_line { source_line }
                            where each contained source_line follows the same
                            source-level rules as ordinary vertical composition

    expression_or_structure
                         ::= mathematical_expression
                          | compact_frame
                          | bounded_structure
                          | atom_or_value

    mathematical_expression
                         ::= parsed by the mathematical expression syntax

The vertical Structure tree is produced by source levels and explicit visible delimiters: smaller source-level lines as level delimiters, canonical dotted delimiter lines, relaxed `---` lines, named `end:` closes and terminal return where valid.

For a source item at level N, vertical child arguments are written at level N + 1. A source line at level N + 1 is one positional child item of that frame/Structure. A source line deeper than N + 1 belongs to the immediately preceding child item only if that child item opens a Structure. Scalar literals and phrase fields do not become headers merely because a deeper line follows.

A canonical dotted delimiter line or relaxed `---` line at level K may delimit an anonymous positional Structure at level K. If it is followed by source items at level K + 1, it opens such an anonymous Structure. The next delimiter at level K closes the previous anonymous Structure and may open another one when followed by deeper items. A following source item at a smaller source level closes all open Structures above that smaller level.

A `colon_frame_body` whose tail is empty must be followed by vertical child fields at the next source level, a canonical dotted delimiter or relaxed `---` anonymous Structure delimiter when that is valid in the current parent, or an explicit `end: <target>` close when the receiver/profile allows an empty frame. Otherwise it is a syntax error.

This grammar is intentionally incomplete around full update semantics, full indexing, full field-follow access, type constructors, literals and relation forms because those areas require final design decisions. Native structural grammar does not include `=` assignment, `=` named-field syntax, bare `end`, `end <target>`, bare non-nullary receiver/callable calls or `case` (not structural syntax) as syntax. The standalone `---` line is part of vertical structure syntax as a nameless delimiter: it may open an anonymous positional Structure when followed by a deeper item, separate sibling anonymous Structures, or close/cut an anonymous/implicit section.

Line arguments are comma-separated except for the numeric-run shortcut. A parser must not use receiver signatures to insert hidden nesting while parsing `line_arguments`.

Inside a bounded Structure, comma separates elements at the bounded Structure's current level. A comma inside a deeper parenthesized expression or compact Frame belongs to that deeper form.

Structural grammar has no separate anonymous-function syntax. A bounded Structure, compact Frame or vertical anonymous Structure becomes an anonymous executable body/callable only when the receiver consumes that field in a body/callable position.

Labels are not a separate structural grammar category. A source line such as `outerLoop:` is a colon frame with an empty inline tail and a required following vertical block. The active receiver/profile decides whether that frame introduces a local nullary executable binding, a control label role, both, or an error. A later bare line such as `outerLoop` is also not special label grammar; in executable statement position it may resolve through the ordinary namespace to that zero-argument label-block binding.

23. Canonical Examples

23.1. Hello World

Source:

L3:
    print: Hello World
end: L3

Normal form:

    L3(
      print(Hello, World)
    )

`Hello` and `World` are accepted only if the active L3 `print` receiver and lexical rules allow bare atoms/symbols in that position.

23.2. Function with Structural Return

Source:

fn: estimateHarvest, (PlantBed(bed)), (f32(harvest), f32(redApples), f32(greenApples))
    if: bed\crop = Apples
        return: bed\area * 1.7, bed\area * 1.7, bed\area * 1.1
return: bed\area, 0, 0

Semantic outline:

    `fn` consumes a definition Structure.
    `PlantBed: bed` is a typed/model constructor Structure if `PlantBed` is registered.
    The return Structure has three named fields.
    `if` consumes condition and body Structures.
    The inner `return:` exits with the Apple-specific structural result.
    The final `return:` is terminal return. It supplies the default structural result and closes the function definition.

23.3. Empty Return with Named Return Variables

Source:

fn: estimateHarvest, (PlantBed(bed)), (f32(harvest), f32(redApples), f32(greenApples))
    harvest: bed\area
    redApples: 0
    greenApples: 0
return

Semantic outline:

    Named return fields are local return variables.
    Head/update position updates existing bindings.
    Terminal empty `return` exits, returns their current values and closes the function definition.

23.3.1. Recursive Function with Terminal Return

Source:

fn: factorial, (int(n)), (int)
    if: n <= 1
        return: 1
return: n * factorial(n - 1)

Semantic outline:

    `return: 1` is a runtime return inside the `if` branch.
    In expression position, `factorial(n - 1)` is a recursive call.
    The final `return:` supplies the recursive result and closes the function definition.

23.4. L5 Conditional Build

Source:

L5:
    if: mode = debug
        then:
            build: debugTarget
        else:
            build: releaseTarget
end: L5

Conceptual form:

    L5(
      if(
        <expression Structure for `mode = debug`>,
        (build(debugTarget)),
        (build(releaseTarget))
      )
    )

The semantic roles `condition`, `then` and `else` are assigned by the active `if` receiver signature.

23.5. Operator Registration

Source:

L4:
    operator:
        if
        callableFrom: L5
        implementation: l5_if
end: L4

Semantic outline:

    `L4` consumes the body as model/registry input.
    `operator` registers the receiver name `if`.
    `callableFrom: L5` sets visibility.
    `implementation: l5_if` names the implementation receiver/subroutine.

23.6. L5-if Implementation Subroutine

Source:

sub: l5_if, (boolean(condition)), then, else
return

Conceptual form:

    sub(
      name(l5_if),
      args(
        boolean(condition),
        then,
        else
      ),
      body(...)
    )

Define a smaller numeric-only expression grammar for the first implementation.

variant 3:
Allow profiles so the active level or module can select a mathematical grammar.

?
Model/type syntax is not specified in full. It must define model receivers, slot declarations, defaults, constraints, aliases, layouts and relation signatures.
?

?
The L2 memory/operator specification must define exact semantics for `@`, prefix `\`, field-follow `\field`, low-level binding update, raw loads, raw indexing and address arithmetic.
?

?
The array/text specification must define indexing, slicing, bounds errors, multidimensional arrays, text encoding and dynamic storage behavior.
?

?
The execution-model specification must define binding update, mutability, scope, initialization and reassignment rules without native `=` assignment.
?

?
The relation/query specification must define `?name` logical variables, list literals, rule bodies, query result Structures, fact persistence, indexes, transactions and external database integration.

?

?
Generic operation signatures and method compatibility rules are not fully specified. A final specification must define how return types, argument Structures, domains and defaults are checked for `method` registrations.

?
The general error/status system is not specified. Until specified, erroneous results may be represented as ordinary values allowed by the declared return type or by receiver-defined diagnostics.
?

25.3. ANSI C Implementation Variants

---ANSI C---
These variants are implementation notes for a possible ANSI C based translator. They are not part of Lingvamyxa source semantics.

Call lowering:

variant 1:
Pass a small number of primitive/reference fields directly in internal generated C functions.

variant 2:
Pass an args Structure address/handle when the logical argument Structure is large or dynamic.

variant 3:
Generate specialized adapters, inline calls or eliminate physical args Structures when observable source semantics are preserved.

Return lowering:

variant 1:
Return a single primitive as a direct C primitive value.

variant 2:
Return multi-field results through caller-provided output storage.

variant 3:
Return small Structures by value where the implementation profile allows it.

variant 4:
Return handles/addresses to runtime-managed Structures for dynamic or large results.

Destructuring lowering:

variant 1:
Store the returned Structure or handle in a temporary service variable and update target variables from its fields.

variant 2:
For known layouts, generate direct field-follow access.

variant 3:
For dynamic layouts, generate checked accessors or runtime lookup.

Field and array lowering:

variant 1:
Known field-follow access lowers to direct C struct or pointer access.

variant 2:
L2 indexing lowers to computed-address access under the L2 memory model.

variant 3:
L3+ indexing lowers to checked access through array metadata such as `len`.

The language does not define C slot counting, hidden runtime addresses, hidden output addresses or C storage ownership rules. Those are translator/runtime design choices.
---ANSI C---

26. L3 Control Operators

26.0. Scope of This Section

This section defines the normative L3 control-flow receiver set for executable bodies.

The operators in this section are source-level control receivers. They are not raw low-level jumps. A translator may lower them to branches, labels, hidden control-result Structures, cleanup-stack operations or other implementation artifacts.

Unless stated otherwise, these operators are L3 operators. Some of them may also be exposed in L2 by an implementation profile, but this section specifies the L3 semantics.

Operator summary:

    0.  if / then / else                                  L3
    1.  match / case / default                            L3
    2.  while                                             L3
    3.  until                                             L3
    4.  for                                               L3
    5.  each                                              L3
    6.  return                                            L3 executable body; terminal executable close at definition level
    7.  break                                             L3 loop frame
    8.  continue                                          L3 loop frame
    9.  finally                                           L3 executable/scope frame cleanup
    10. guard / fail / throws / failure labels / handlers  L3 recoverable failure flow
    11. retry / retryable                                 L3 retry frame
    12. assert                                            L3 diagnostic failure flow
    13. redo                                              L3 loop frame
    14. yield                                             L3 iterator function
    15. labelled break / labelled continue                L3 labelled loop frame

Labels are written as ordinary colon frames such as `outerLoop:`. A profile may materialize such a frame as a local nullary executable binding, a labelled control/block target, or both. A bare line such as `outerLoop` in executable statement position may resolve through the ordinary namespace to that zero-argument label-block binding and consume/call it. Control-transfer receivers such as `break:` and `continue:` resolve their target to the labelled control/block role of the same visible binding. The parser does not need a separate label grammar category.

26.1. `if`, `then` and `else`

`if` consumes a condition and one or two body Structures.

Semantic form:

    if(condition, thenBody, elseBody?)

Explicit form:

if: condition
    then:
        thenBody
    else:
        elseBody
end: if


Short positional form:

if: condition
    thenBody

    elseBody

Nested short positional form:

    if: condition
        thenBody
    ---
        elseBody
    ---

Nested explicit `else` form:

    if: condition
        thenBody
    else:
        elseBody
    ---


Single-line form:

    if: condition, doSomething

The condition is evaluated once before branch selection.

Only the selected body is executed.

If no `else` body is provided and the condition is false, `if` completes normally without executing a body.

In named form, `then` and `else` are structural section markers inside `if`. They are not ordinary runtime calls when consumed by the `if` receiver. In positional form, sibling child Structures are mapped to `thenBody` and `elseBody` by receiver signature order.

26.2. `match` and default-pattern receivers

`match` selects one body from a set of positional pattern/body pairs or from anonymous branch Structures. `case` (not structural syntax) is not structural syntax.

Simple positional example:

match: value
    1
    print: one
    2
    print: two
    default
    print: other
    ---

Conceptual argument stream:

    match(value, 1, print(one), 2, print(two), default, print(other))

The `match` receiver may interpret the tail after `value` as repeating `(pattern, branch)` pairs. `default` is an ordinary atom/receiver-defined pattern value, not a parser keyword.

Block branch example:

match: value
    1
    ---
        print: one
        log: matched one
    ---
    2
    ---
        print: two
        log: matched two
    ---

Conceptual argument stream:

    match(
      value,
      1,
      (print(one), log(matched one)),
      2,
      (print(two), log(matched two))
    )

Anonymous branch Structure example:

match: value
    ---
        1
        print: one
    ---
        2
        print: two
    ---
        default
        print: other
    ---

Conceptual argument stream:

    match(
      value,
      (1, print(one)),
      (2, print(two)),
      (default, print(other))
    )

There is no automatic fallthrough from one branch to the next unless the active `match` receiver explicitly defines such behavior.

For union values, a `match` may destructure the active variant by ordinary pattern Structures.

Example:

match: shape
    ---
        Circle, c
        drawCircle: c
    ---
        Square, s
        drawSquare: s
    ---

If the matched value is a closed union and no default pattern is present, an implementation may require exhaustive patterns.

26.3. `while`

`while` is a pre-condition loop.

Semantic form:

    while(condition, body)

Example:

while: i < n
    print: i
    i: i + 1


The condition is evaluated before each iteration.

If the condition is false before the first iteration, the body is not executed.

A `while` body is a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

26.4. `until`

`until` is a conditional close for the current executable block. It closes the current block, executes that block as a post-condition loop body, then evaluates its condition.

Semantic form:

    until(currentBody, condition)

Labelled example:

readLoop:
    readNext: record
    process: record
until: endOfInput(record)

In this example, `until:` closes the labelled executable block `readLoop`. The condition is the boolean-producing Structure `endOfInput(record)`. The name `readLoop` is also the local nullary executable binding for the block, as described in section 7.6.

The body is executed first. The condition is evaluated after the body.

The loop repeats until the condition is true. If the condition is false, control transfers to the beginning of the block closed by `until`.

`until` creates a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

26.5. `for`

`for` is a controlled loop receiver for numeric ranges, counters, index ranges or other bounded iteration policies.

Compact counter/triplet form:

for: int(i, 0), (i < n), i++
    print: i


The first three arguments are consumed as loop-control fields:

    init      -> initialization Structure
    condition -> boolean-producing expression
    step      -> iteration-step executable Structure

The vertical child Structure is consumed as the loop body.

Single-line compact body form:

    for: int(i, 0), (i < n), i++, print(i)

In this form, `print(i)` is the fourth argument. The `for` receiver signature consumes that fourth argument as `body`, so it is an executable body Structure. The token form `i++` is valid only in profiles that register it as a parser method.

Range-style example:

for: i, 0, n
    print: i


Semantic requirement:

    `for` creates one or more loop-local iteration bindings.
    `for` advances those bindings according to the selected control policy.
    `for` executes the body once for each produced iteration state.

`for` creates a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

?
The compact counter/triplet form is specified above. Other source forms for numeric ranges, inclusive/exclusive bounds, step values, reverse iteration, index/value pairs and destructuring of iteration bindings are not specified in this section.
?

variant 1:
Use compact positional forms such as `for i 0 n`.

variant 2:
Use named/signature phrase forms such as `for: i from 0 to n step 1` only when the `for` receiver explicitly consumes that phrase as one semantic field; otherwise write explicit comma fields such as `for: i, 0, n, 1`.

variant 3:
Treat all range policies as ordinary receiver Structures consumed by `for`.

26.6. `each`

`each` iterates over a container or iterator-compatible Structure.

Array-like example:

each: item in items
    draw: item


Receiver-like example:

each: items, item
    draw: item


Semantic requirement:

    `each` obtains a sequence of values from its source.
    For each value, `each` binds the iteration variable or variables.
    `each` executes the body once for that value.

`each` creates a loop frame. `break`, `continue`, `redo` and labelled loop transfer operators may target it.

For arrays or array-like containers, `each` may lower to an index loop.

For iterator-compatible Structures, `each` repeatedly calls the iterator `next(env)` implementation until no value is produced.

Iterator consumption by `each` is specified in section 26.14.

26.7. `return`

`return` exits the current `fn`, `sub` or executable-like body.

Runtime forms inside an executable body:

    return
    return: value

For an `fn`, `return` returns the current return binding. `return: value` fills the current return binding with a compatible primitive or Structure value and exits.

For a `sub`, `return` exits the `sub` body. `return: value` is invalid for `sub` unless a later profile defines status/result subroutines.

At the source level of the open executable definition, `return` is terminal return. It appends the corresponding runtime return as the final body item and closes the executable definition. This is an executable-specific close, not a general replacement for `end: name`.

Examples:

fn: square, (int(x)), (int)
return: x * x

fn: factorial, (int(n)), (int)
    if: n <= 1
        return: 1
return: n * factorial(n - 1)

Before control leaves the current executable frame, all `finally` cleanups registered for the exited scopes are executed in reverse registration order.

26.8. `break`

`break` exits the nearest active loop frame.

Example:

while: running
    if: stopRequested
        break
    ---
    step


`break` is valid only inside a loop frame unless a labelled form is used as described in section 26.15.

Before control leaves the exited loop body scopes, all affected `finally` cleanups are executed in reverse registration order.

`break` is not a source-level raw jump. It is a structured loop-frame exit.

26.9. `continue`

`continue` starts the next iteration of the nearest active loop frame.

Example:

each: item in items
    if: skip item
        continue
    ---
    process: item


For `while`, `continue` transfers control to the next condition check.

For `until`, `continue` transfers control to the post-body condition check for the current iteration.

For `for`, `continue` transfers control to the next iteration-state update.

For `each`, `continue` transfers control to the next container or iterator value.

Before control leaves the current loop body scopes, all affected `finally` cleanups are executed in reverse registration order.

26.10. `finally`

`finally` registers cleanup code in the current execution context.

Block form:

finally:
    cleanupBody


Single-line form:

    finally: cleanupCall

`finally` is not part of a `try` block in this specification. It is a standalone cleanup registration operator.

A cleanup registered by `finally` is associated with the current executable/scope frame.

Cleanups are executed when their associated frame or scope is exited by:

    normal completion;
    return;
    break;
    continue;
    labelled break;
    labelled continue;
    fail;
    retry;
    redo;
    assert diagnostic exit;
    thread/task termination in the default runtime profile.

Cleanups are executed in reverse registration order.

A cleanup body is executed outside the registration operation. It is not executed at the point where `finally` is encountered, except when the frame exits immediately after registration.

`finally` cleanups are part of the execution context model defined in section 27.

!!!
The exact semantics of a cleanup failure are not fixed. A final runtime specification must define what happens if a cleanup itself executes `fail`, `assert`, `return`, `break`, `continue`, `retry`, `redo` or another `finally` registration while cleanup processing is already active.
!!!

26.11. `guard`, `fail`, `throws`, failure labels and handlers

`guard` and `fail` define declared recoverable failure flow.

They are distinct from `assert`.

    guard / fail:
        declared, expected, recoverable failure path

    assert:
        diagnostic invariant violation

26.11.1. `throws`

An executable definition may declare failure labels with `throws`.

Example:

fn: parseInt
    Text: text

    int

    throws:
        ParseError
    ---

    guard: validInteger, text
        fail: ParseError, text
    ---

    parseInt: parseInteger, text


`throws` lists the failure labels that may leave the executable body as recoverable failures.

A caller must handle, propagate or remap a declared failure.

26.11.2. `guard`

`guard` executes its failure body when its condition is false.

Example:

guard: radius > 0.0
    fail: InvalidRadius, radius


Semantic form:

if: not condition
    failureBody


`guard` is a convenience control receiver. It does not itself define the failure transport mechanism. That is defined by `fail`.

26.11.3. `fail`

`fail` exits the current executable body with a declared failure label and optional payload.

Example:

    fail: ParseError, text

Semantic effect:

    set failure label to ParseError;
    set failure payload from the remaining arguments;
    execute affected finally cleanups for the current frame exit;
    return a structured failure result to the caller or visible handler.

`fail` is part of the declared `throws` set. It is not a diagnostic abort.

`fail` does not transfer to the thread diagnostic root.

`fail` does not use the `assert` channel.

26.11.4. Failure labels and handlers

Failure labels are ordinary source labels consumed under failure-control semantics. A profile may keep a separate lookup table for diagnostics and control transfer, but the surface grammar is still the same colon-frame grammar.

A handler consumes a failure label and payload.

The exact handler surface syntax is not finalized in this section.

variant 1:
Use label-like handler syntax:

ParseError:
    Text: badText

    print: badText


variant 2:
Use explicit receiver syntax:

handler: ParseError
    Text: badText

    print: badText


variant 3:
Represent handlers as L5 event/message handlers for failure events.

!!!
The exact source syntax, placement, visibility and lifetime of failure handlers are not fixed. A final source specification must define whether handlers are lexical Structures, executable labels, L5 event handlers, caller-side receivers or a combination of these forms.
!!!

26.11.5. Failure propagation

If a failure is not handled in the current body, it must be propagated by an enclosing or calling executable whose `throws` declaration includes the failure label.

Failure propagation is structured. It is not a raw jump through arbitrary stack frames in the source semantics.

---ANSI C---
A translator may lower declared failures using:

variant 1:
Return-status wrappers.

variant 2:
Status return plus output parameters.

variant 3:
A hidden control-result channel.

variant 4:
A non-local transfer mechanism for a selected runtime profile, provided that Lingvamyxa `finally` semantics are preserved.

The strict default for this draft is structured failure propagation, not root-level `longjmp`.
---ANSI C---

26.12. `retry` and `retryable`

`retryable` defines a restartable frame.

`retry` restarts the nearest or named retryable frame.

Example:

loadAttempt:
    retryable:
        loadNetworkData
    ---

Possible failure-handler use:

NetworkError:
    reconnect
    retry: loadAttempt


A `retry` transfer executes the affected `finally` cleanups for the abandoned attempt before re-entering the retryable frame.

`retry` does not roll back external side effects. It only repeats the source frame according to the retryable-frame semantics.

Local bindings declared inside the retryable frame are re-created when the frame is re-entered.

Outer bindings keep their current values unless the retryable receiver defines a stronger rollback policy.

`retry` without a label targets the nearest active retryable frame.

`retry: labelName` targets the named retryable frame.

!!!
The exact interaction between `retry`, failure handlers, iterator frames, partially executed cleanups and mutable outer bindings requires a final rule. This draft defines retry as re-execution, not as transactional rollback.
!!!

26.13. `assert`

`assert` checks a diagnostic invariant.

Example:

    assert: index >= 0
    assert: index < values\len

If the condition is true, execution continues normally.

If the condition is false, the current execution/checking phase fails with an `AssertionViolation` diagnostic.

`assert` is not recoverable `fail` control flow.

`assert` is not part of the declared `throws` set.

`assert` is not caught by failure labels or failure handlers.

Default L3 runtime semantics in the thread profile defined in section 27:

    record AssertionViolation diagnostic;
    execute all active `finally` cleanups in the current thread ExecutionContext;
    transfer control to the thread diagnostic root;
    terminate the current thread/task by default after reporting the diagnostic.

Default L4 model-time use, if exposed by a level profile:

    an assertion violation terminates the current model-loading or translation pass with a diagnostic error.

`assert` is intended for impossible states, broken invariants, corrupted internal assumptions or translator/model errors. Expected input failure must use `guard` and `fail`.

26.14. `redo`

`redo` repeats the current loop iteration without advancing the loop source.

For `each`, `redo` repeats the body with the same current element.

For iterator-based `each`, `redo` does not call `next(env)` before repeating the body.

For `for`, `redo` repeats the body with the same loop bindings.

For `while`, `redo` repeats the body without re-evaluating the condition first.

For `until`, `redo` repeats the body without evaluating the post-condition first.

Before the current iteration is restarted, all `finally` cleanups registered inside the abandoned iteration attempt are executed.

`redo` is dangerous because it can create non-progressing loops. It is valid only inside a loop frame.

26.15. `yield`

`yield` is valid only inside an iterator function.

An iterator function declares a return model compatible with `Iterator T`.

Calling an iterator function does not execute its body to completion. It creates an iterator state Structure.

The translator lowers the iterator body into a `next(env)` implementation.

Each `yield` emits one value compatible with `T` from `next(env)` and records the resume state in `env`.

The `each` receiver consumes iterator-compatible Structures by repeatedly calling their `next(env)` implementation until no value is produced.

26.15.1. Iterator function

Example:

fn: makePoints

    Iterator: Point

    yield: 1.0 2.0
    yield: 3.0 4.0
    yield: 5.0 6.0


Calling:

    makePoints()

creates an iterator state Structure. It does not return an `Array Point` and does not execute all `yield` statements immediately.

26.15.2. Iterator state Structure

An iterator state Structure contains enough state to resume execution after each `yield`.

For a simple iterator, generated state may include:

    state index;
    captured arguments;
    local variables that survive across yields;
    cleanup registrations owned by the iterator frame;
    a reference to the generated `next(env)` implementation.

Source-level code does not depend on the physical layout of this state Structure.

26.15.3. `next(env)`

The generated `next(env)` implementation executes the iterator until it either reaches a `yield` or terminates.

At a `yield`, `next(env)` returns a produced value and records where execution must resume.

When the iterator terminates, `next(env)` returns a no-value result.

Conceptual result model:

Next: T
    boolean: hasValue
    T: value


?
The exact standard name and structural layout for the result of `next(env)` is not specified. A final iterator specification must choose canonical names and fields, such as `Next T`, `Option T`, `Some/None` or another equivalent representation.
?

26.15.4. `yield` value construction

If `T` is a primitive, `yield: value` emits that primitive.

If `T` is a Structure, the arguments of `yield` fill that Structure according to the same structural rules used by `return`.

Example:

    yield: 1.0 2.0

inside an `Iterator Point` function emits one `Point` value if `Point` has two positional fields such as `x` and `y`.

26.15.5. Iterator consumption by `each`

Example:

each: point in makePoints
    draw: point


Semantic form:

iterator: makePoints

while: true
    result: next iterator\env
    if: not result\hasValue
        break
    ---
    point: result\value
    body


This is semantic pseudocode. A translator may lower it to a direct state machine or inline loop.

26.15.6. Iterator termination

A bare `return` inside an iterator function terminates the iterator.

A `yield` after termination is unreachable.

`break` and `continue` inside an iterator body operate on the nearest active loop frame inside the iterator body, not on the consumer's `each` loop.

!!!
Iterator close semantics are not fully specified. A final specification must define when iterator-owned `finally` cleanups run if an iterator is abandoned before exhaustion, discarded, moved to another thread or terminated by diagnostic failure.
!!!

26.16. Labelled `break` and labelled `continue`

A control label may be attached to a loop frame.

Example:

outerLoop:
    for: row in rows
        for: cell in row
            if: found cell
                break: outerLoop
            ---
        ---
    ---

`labelName:` is an ordinary colon frame that the active profile materializes as a visible control target for the following block.

`break: labelName` exits the labelled loop frame.

`continue: labelName` continues the labelled loop frame if the target label names a loop frame.

Before the transfer, all `finally` cleanups registered in scopes exited by the transfer are executed in reverse registration order.

It is a compile-time error for `break: labelName` or `continue: labelName` to target a label that is not visible in the control-label scope.

It is a compile-time error for `continue: labelName` to target a non-loop frame.

?
The exact grammar rule for attaching labels to frames is not specified beyond the form `labelName:` before a frame. A final grammar must define whether labels can attach to retryable frames, blocks, handlers, iterator frames and arbitrary Structures.
?


27. L2 Thread Context and L5 Event Delivery Profile

27.0. Scope of This Section

This section defines a default runtime profile for:

    L2 execution threads;
    thread-local ExecutionContext;
    `finally` cleanup storage;
    `assert` diagnostic exit;
    Java-style synchronized inbox/outbox event delivery;
    L5 object/message event dispatch.

This profile is intentionally simple. It is based on cooperative thread loops that periodically check inbound messages and flush outbound messages. It does not define blocking request/reply as a primitive operation.

27.1. ExecutionContext

Each L2 execution thread owns one current ExecutionContext.

The ExecutionContext is thread-local.

Conceptual Structure:

ExecutionContext:
    Thread: currentThread
    CleanupStack: cleanupStack
    DiagnosticRoot: diagnosticRoot
    Diagnostic: currentDiagnostic
    FrameDepth: currentDepth


The ExecutionContext is not an ordinary user data model. It is runtime infrastructure.

The ExecutionContext stores active `finally` cleanup registrations for the current thread.

The ExecutionContext stores the diagnostic root used by `assert`.

27.2. CleanupStack

A cleanup stack is a LIFO stack of active cleanup entries.

Conceptual entry:

CleanupEntry:
    cleanupSub
    cleanupEnv
    frameDepth
    scopeDepth


`finally` pushes a cleanup entry into the current thread ExecutionContext.

Normal frame/scope exit runs cleanup entries owned by the exited frame/scope.

Diagnostic thread exit runs all remaining cleanup entries in the current thread.

Cleanup entries are removed when they are executed. A cleanup must not execute twice.

27.3. L2Thread

An L2 thread owns:

    thread id;
    thread-local ExecutionContext;
    synchronized inbox;
    synchronized outbox;
    running/stopping state;
    body step or thread entry procedure.

Conceptual Structure:

L2Thread:
    ThreadId: id
    ExecutionContext: context
    Inbox: inbox
    Outbox: outbox
    ThreadState: state
    BodyStep: body


The inbox and outbox are synchronized FIFO containers.

This profile describes them as Java-style synchronized Vectors. A translator/runtime may implement them as ring buffers, queues or other FIFO containers if the observable semantics are preserved.

27.4. Thread loop

Canonical thread loop:

initialize ExecutionContext
establish diagnostic root

while: running
    checkInbox
    body
    flushOutbox


run all remaining finally cleanups
terminate thread

Java-style pseudocode:

    class L2Runnable implements Runnable {
        Vector<Message> inbox;
        Vector<Message> outbox;
        ExecutionContext context;

        public void run() {
            try {
                while (running) {
                    checkInbox();
                    body();
                    flushOutbox();
                }
            } catch (AssertException e) {
                context.currentDiagnostic = e.diagnostic;
                report(e);
            } finally {
                closeAllFinally(context);
            }
        }
    }

ANSI C style profile:

    initialize ExecutionContext;
    setjmp(context.diagnosticRoot);
    run thread loop;
    on assert longjmp, report diagnostic;
    run all remaining cleanups;
    terminate thread;

The Java-style and ANSI C-style profiles are implementation strategies for the same source-level thread model.

27.5. Assertion failure in the thread profile

When an L3 `assert` condition is false:

    an AssertionViolation diagnostic is created;
    all active cleanups in the current thread ExecutionContext are executed;
    control transfers to the thread diagnostic root;
    the current thread/task terminates by default after diagnostic reporting.

In a Java runtime, the transfer may be implemented by throwing an internal `AssertException` caught by the thread root.

In an ANSI C runtime, the transfer may be implemented by `setjmp` at the thread root and `longjmp` from the assertion failure path.

---ANSI C---
Conceptual implementation:

    typedef struct ExecutionContext {
        CleanupStack cleanupStack;
        jmp_buf diagnosticRoot;
        Diagnostic currentDiagnostic;
    } ExecutionContext;

    _Thread_local ExecutionContext *LX_CTX;

    void lx_assert_fail(Diagnostic d) {
        ExecutionContext *ctx = LX_CTX;
        ctx->currentDiagnostic = d;
        run_all_cleanups(ctx);
        longjmp(ctx->diagnosticRoot, 1);
    }

This implementation note does not define ordinary `fail`. Declared `fail` remains structured recoverable control flow.
---ANSI C---

!!!
The policy for assertion failure during cleanup is not fixed. A final runtime specification must define whether the runtime continues cleanup, stops cleanup, records secondary diagnostics or terminates immediately.
!!!

27.6. L2Message

A message is an event envelope delivered between threads or active L5 objects.

Conceptual Structure:

L2Message
    target
    selector
    sender
    args
    replyTo
    correlation
    flags


Fields:

    target ->
        object, service or behavior target

    selector ->
        message name / L5 selector

    sender ->
        sender object or thread, if present

    args ->
        argument Structure

    replyTo ->
        optional inbox or target for asynchronous replies

    correlation ->
        optional id used to match request and reply

    flags ->
        runtime delivery metadata

`L2Message` is a transport envelope. The target's L5 behavior table decides which implementation consumes the selector.

27.7. Inbox and outbox operations

Sending a message appends it to a synchronized FIFO container and returns.

Basic operation:

    send: target, message

Semantic effect:

    append message to target thread inbox;
    do not execute the handler in the sender thread;
    return immediately.

Outbox operation:

    enqueue message into current thread outbox;
    later `flushOutbox` appends queued messages to target inboxes.

The outbox is optional as a physical layer. The source-level event model requires asynchronous delivery, not a particular buffering strategy.

variant 1:
Direct asynchronous send appends immediately to the target inbox.

variant 2:
The current thread appends to its outbox, and `flushOutbox` performs delivery.

variant 3:
The runtime combines both strategies according to scheduling and batching policy.

27.8. Inbox checking

`checkInbox` drains or checks the inbox periodically.

Handlers must not execute while the inbox synchronization lock is held.

Safe pattern:

localMessages: drain inbox under lock

each: message in localMessages
    dispatchMessage: message


Unsafe pattern:

synchronized inbox
    dispatchMessage: message


The unsafe pattern is forbidden by this profile because it executes user/L5 behavior while holding the inbox lock.

27.9. L5 event dispatch

L5 behavior dispatch for a delivered message uses the target object's behavior descriptor.

Conceptual dispatch:

    model: target\model
    behavior: lookupBehavior, model
    method: lookup, behavior\messageTable, selector
    call: method, target, args

If the target belongs to the current thread and the source form is a local L5 message, the translator/runtime may use direct Smalltalk-style synchronous dispatch.

If the target belongs to another thread or the source form is an explicit event send, delivery is asynchronous through the target inbox.

This profile distinguishes:

    local L5 message:
        receiver: selector, args
        direct behavior lookup and call in the current thread

    L5 event send:
        send: receiver, selector, args
        asynchronous inbox delivery

    L5 request:
        request: receiver, selector, args, replyTo/correlation
        asynchronous inbox delivery with a later reply message

There is no blocking `ask` primitive in this profile.

27.10. Request and reply

A request is an asynchronous send with a correlation id and reply target.

A reply is an ordinary message carrying the same correlation id.

Request flow:

    requester sends request message to target inbox;
    requester continues executing its thread loop;
    target eventually handles request;
    target sends reply message to requester inbox;
    requester eventually handles reply during `checkInbox`.

No thread blocks waiting for a reply in the base profile.

A thread may store pending request ids in ordinary state and inspect them during its body step or message handlers.

Blocking request/reply is outside this profile.

?
A future profile may define blocking wait, timeout, inbox-pumping wait, futures, promises or structured async/await. Those are not part of this section.
?

27.11. Deadlock and progress properties

The synchronized inbox/outbox model avoids ordinary lock-order deadlocks if:

    inbox/outbox locks are held only for short append/drain operations;
    user code and L5 message handlers do not execute while holding those locks;
    the base profile does not block while waiting for replies.

This does not prove protocol termination.

A message protocol may still fail to make useful progress, send messages forever, exhaust memory or starve some tasks. Those are architecture/protocol properties, not synchronization-lock deadlocks in the mailbox mechanism.

27.12. Atomic operations and L5 messages

L5 message dispatch is not the universal mechanism for all computation.

L2 and L3 ordinary computation remains direct:

    primitive arithmetic;
    comparisons;
    field-follow access;
    array access;
    direct fn/sub calls;
    loops and branches;
    generated low-level operations.

L5 messages are used for behavior, configuration, object/service interaction, active objects and high-level event delivery.

Lingvamyxa does not require Smalltalk-style message dispatch for every atomic operation.

28. L2 Primitive, Address and Parser Operators

28.0. Scope of This Section

This section defines the minimal L2 operator/parser-form set.

L2 has primitive values, typed address values and Structures/descriptors. Aggregate model names denote layouts or descriptors. Storage and allocation forms produce typed address values. Receiver signatures and parser profiles assign final semantics to the Structures built from source syntax.

This section is deliberately smaller than the L3 control set in section 26. L2 is low-level and unsafe, but it does not need every L3 convenience operator by default.

28.1. Pointer and Field Syntax Exclusions

L2 does not use `*`, `&`, `^`, `.`, or `->` as pointer/field syntax.

This rule should be stated once as an L2 invariant instead of repeated at every address example.

Consequences:

    `*`  remains available for multiplication in mathematical expression syntax.
    `&`  is not address-of.
    `^`  is not pointer dereference and is not a field-follow marker.
    `.`  is source indentation only when it appears in the leading dot prefix; it is not field access.
    `->` is not a Lingvamyxa field-follow operator.

L2 address and field forms are:

    @ⁿ: T, x    reserved address-depth declaration head, for example `@@@: int, ppp`
    @x          address of storage location `x`
    \x          raw load from address expression `x`
    x\field     typed field-follow through address/reference `x`
    x[i]        indexed access through address/reference/container `x`

Field-follow and index chains bind tighter than prefix `@` and prefix `\`.

28.2. Storage, Address and Indexed Forms

Minimal L2 storage/allocation and address-slot forms:

    stack: Layout, name
    heap: Layout, name
    static: Layout, name
    Primitive: name, [initialValue]
    []: name, size
    @ⁿ: BaseType, name

Examples:

stack: PlantBed, branch
heap: PlantBed, tree
static: PlantBed, root
int: count, 5
[]: leafs, count
@: int, p
@@: int, pp
@@@: int, ppp

Meanings:

    branch  typed address of stack storage with layout `PlantBed`
    tree    typed address of heap storage with layout `PlantBed`
    root    typed address of static storage with layout `PlantBed`
    count   primitive storage/value initialized to `5`
    leafs   typed address/container descriptor for `count` primitive cells, according to the active L2 profile
    p       address-depth-1 slot to base type `int`
    pp      address-depth-2 slot to base type `int`
    ppp     address-depth-3 slot to base type `int`

Name phrases may contain spaces when separated by comma from other fields:

stack: PlantBed, branch 2

This allocates stack storage with layout `PlantBed` and introduces the single bare phrase name `branch 2`. Because the phrase starts with an identifier word, the later numeric word belongs to the phrase rather than becoming a numeric field.

The same comma-tail rule applies to address-depth declarations:

@@@: int, ppp

This declares `ppp` as an address-depth-3 slot with base type `int`. Without the comma, `@@@: int ppp` would be one non-numeric phrase segment rather than the canonical two-field declaration.

Address-producing and address-consuming forms:

    @count              address of the primitive storage location `count`
    p: @count           store that address into an address-depth-1 slot
    pp: @p              store the address of `p` into an address-depth-2 slot
    \leafs              raw load of the first primitive cell at address `leafs`
    leafs[3]            indexed access at index `3`
    \(leafs + 3)        raw load after address arithmetic

28.3.

28.3. Primitive Expression Operators

The minimal L2 mathematical expression profile includes:

    grouping        (expr)
    unary numeric   +expr, -expr
    arithmetic      +, -, *, /, %
    comparison      =, !=, <, <=, >, >=
    boolean words   not, and, or

The token `=` is comparison/equality in mathematical expression syntax. It is not native assignment.

Bitwise operators, shifts, overflow rules, integer division rules, floating-point rules and conversion rules are L2 profile details unless a later specification selects a mandatory set.

28.4. Update and Callable Consumption

L2 uses the same head/update surface form as the rest of the structural core:

    target: value

Examples:

    count: 6
    tree\branch: branch
    leafs[3]: 10

After resolution, the form may update mutable storage, update an addressable field/index slot, or consume a callable/receiver binding. This is compile-time resolution, not a separate assignment syntax.

Parser methods such as `++i`, `--i`, `i++` and `i--` are not mandatory source syntax in the minimal L2 set. A profile may register them as compact parser forms that lower to ordinary read-update-write sequences using the same head/update form.

28.5. Minimal L2 Control Receivers

The minimal L2 executable-body control set is:

    if / then / else
    while
    until
    for(init, condition, step)
    return
    break
    continue

These are source-level control receivers/parser forms. They are not raw jumps in the source semantics, even if a translator lowers them to labels and branches.

28.5.1. `if`, `then` and `else`

L2 `if` consumes:

    condition -> boolean-producing expression
    then      -> executable body Structure
    else      -> optional executable body Structure

Example:

if: count > 0
    print: count


Explicit branch example:

if: count > 0
    then:
        print: count
    ---
    else:
        print: 0
    ---


28.5.2. `while`

L2 `while` is a pre-condition loop.

Semantic form:

    while(condition, body)

Example:

while: i < n
    print: i
    i: (i + 1)


28.5.3. `until`

L2 `until` is a conditional close for the current executable block.

Example:

readLoop:
    readNext: record
    process: record
until: endOfInput(record)

In this example, `record` is an explicit compact-call argument of `endOfInput`. The `until:` line consumes the whole tail `endOfInput(record)` as a boolean-producing condition Structure. The condition producer is the compact call `endOfInput(record)`, not a space-separated phrase `endOfInput record`.

More explicit condition form:

readLoop:
    readNext: record
    process: record
until: endOfInput(record)

Conceptual semantic form:

    until(currentBody, condition)

The body executes first. The loop repeats until the condition is true.

If the condition is false, control transfers to the beginning of the executable block closed by `until`. If the condition is true, the block completes and execution continues after the `until` line.

28.5.4. `for(init, condition, step)`

L2 `for` consumes:

    init      -> initialization Structure
    condition -> boolean-producing expression
    step      -> iteration-step executable Structure
    body      -> executable body Structure

Vertical body form:

for: int(i, 0), (i < n), i++
    print: i


Compact body form:

    for: int(i, 0), (i < n), i++, print(i)

28.5.5. `return`

L2 `return` exits the current executable body.

Bare runtime form inside a body:

    return

Value runtime form inside a body:

    return: value

For an `fn`, `return` returns the current return binding. `return: value` fills the current return binding with a compatible primitive or Structure value and exits.

For a `sub`, `return` exits without producing a normal return value. `return: value` is invalid for `sub` unless a later profile defines status/result subroutines.

At the source level of an open executable definition, `return` may be terminal return. Terminal return appends the corresponding runtime return as the final body item and closes the executable definition, in the same checked close position where `end: <functionName>` would otherwise be expected.

Example:

fn: square, (int(x)), (int)
return: x * x

28.5.6. `break` and `continue`

`break` exits the nearest active L2 loop frame.

`continue` starts the next iteration of the nearest active L2 loop frame.

For `while`, `continue` transfers control to the next condition check.

For `until`, `continue` transfers control to the post-condition check for the current iteration.

For `for`, `continue` transfers control to the iteration-step Structure, then to the next condition check.

28.6. Outside the Minimal L2 Set

The following section 26 operators are not part of the minimal L2 control set unless an L2 profile explicitly imports or redefines them:

    match / case / default
    each
    finally
    guard / fail / throws / handlers
    retry / retryable
    assert
    redo
    yield
    labelled break / labelled continue

They may still exist in L3 or higher levels, or in a richer L2 profile.

29. Structural Operation on a Local Copy of Namespace-Structure

29.1. Namespace as Structure

A namespace is a Structure.

Before translation or receiver consumption, a namespace may be represented as a typed dictionary-like Structure whose entries bind names, phrase signatures, receiver names, type/model descriptors, callable values, behavior descriptors and ordinary values.

Conceptual example:

namespace:
    factorial: Callable(int -> int)
    print: Sub(...)
    String: TypeDescriptor
    int: TypeDescriptor
    ---

This representation is source-semantic. A translator may lower it to lexical tables, symbol indexes, direct references, C identifiers, dispatch tables, persistent maps or any other implementation representation.

29.2. Local Namespace View

Entering an executable definition creates a local namespace view.

The local view may be implemented as:

    an actual copied Structure
    a persistent overlay over the outer namespace
    a copy-on-write dictionary-like Structure
    a statically resolved lexical environment with no runtime dictionary
    another representation preserving the same source semantics

A binding update inside an executable body updates the local namespace view unless a future rule explicitly declares the binding external/global/mutable outside the local view.

Local namespace updates do not mutate the outer namespace and do not change the externally visible signature of the executable definition.

29.3. Typed Compatibility of Local Updates

A local namespace entry has a declared slot type, callable signature, receiver contract, model descriptor or other compatibility descriptor.

Updating an entry is valid only if the new value is compatible with that descriptor.

Examples of invalid updates:

    a binding declared as `int` receiving a `String` value
    a binding declared as `Callable(int -> int)` receiving non-callable text
    a type descriptor slot receiving an ordinary runtime integer value
    a receiver implementation slot receiving a callable with incompatible argument or return Structure

Example of valid callable replacement:

    strategy: optimized strategy

is valid when both `strategy` and `optimized strategy` have compatible callable signatures, for example:

    Callable(int -> int)

29.4. Local Callable Replacement

Because callable values are Structures or handles/references to Structures, local replacement of a callable binding is just a typed update of the local namespace Structure.

Example:

fn: compute, (int(x)), (int)
    fn: slow path, (int(v)), (int)
    return: v * v
    fn: fast path, (int(v)), (int)
    return: v << 1
    strategy: slow path
    if: x < 10
        strategy: fast path
return: strategy(x)

Here `strategy` is a local callable binding. The update `strategy: fast path` is valid only if `fast path` is compatible with the declared or inferred signature of `strategy`.

This operation does not replace `slow path`, `fast path`, `compute`, or any outer namespace binding. It only changes the local namespace view used inside the current executable body.

29.5. Difference from Dynamic Untyped Rebinding

This model is not Python-like unrestricted rebinding.

The namespace may be dictionary-like, but it is typed. A name may be locally rebound only to a value compatible with its declared slot type or contract.

Therefore:

    x: 1
    x: "hello"

is invalid if `x` is an `int` binding.

And:

    factorial: "hello"

is invalid if `factorial` is a callable slot with signature `Callable(int -> int)`.

29.6. Interaction with Return and Function Names

The canonical return mechanism is `return: value` or terminal `return`. The current function name is not the primary return binding syntax in this revision.

This avoids overloading a function name with too many roles. The same visible name may participate in ordinary callable lookup, recursion and local namespace overlay operations without also being the canonical way to write the function result.

A compatibility profile may allow Pascal-style function-name return binding, but such a profile must define how it interacts with local namespace overlays and callable replacement.

29.7. Translation and Optimization

The source semantics allow a local namespace copy or overlay, but implementations do not have to allocate an actual dictionary at runtime.

A translator may optimize local namespace operations by:

    avoiding a copy when no local updates occur
    using copy-on-write for a small number of updates
    representing the overlay as a persistent map
    replacing lookups by direct references when types and bindings are static
    inlining locally replaced callable values when the replacement is non-escaping
    lowering compatible callable replacement to a simple local function pointer or descriptor update
    rejecting or de-optimizing cases that escape the local namespace view beyond the executable lifetime

The source rule is structural and typed: local updates modify a local namespace Structure view, and every update must preserve the declared type/signature/contract of the target entry.

Escaping local namespace overlays, closure capture of locally replaced callables, mutation of outer bindings and explicit global/external update syntax are not specified in this document. They belong to a future execution-model and runtime specification.

30. Memory Model

30.0. Scope

This section defines the structural memory model used by Lingvamyxa source semantics above the raw L1 implementation layer.

The model is intentionally region-oriented. It is not a global garbage-collected heap model and it is not a Rust-style per-variable ownership calculus. It treats high-level Structures as branch-owned memory regions, uses borrowed references by default when data is obtained from outside the current owner, and isolates L5 Threads from one another.

The memory model is semantic. A translator may lower it to stack allocation, arenas, reference-counted branch handles, local owner-tree walkers, copy-on-write Structures, immutable value stores, direct C storage, generated cleanup labels or another implementation strategy that preserves the rules below.

30.1. Core Rules

The following rules are normative for the structural memory model:

    1. A branch Structure may own an arena.
    2. Leaf Structures normally do not own arenas.
    3. Heap children of a branch are allocated inside the nearest owning branch arena.
    4. Destroying a branch arena destroys all memory allocated inside it.
    5. Borrowed references into an arena do not extend the arena lifetime.
    6. To keep a borrowed branch beyond its owner scope or message frame, the value must be copied into an owned branch of the current owner.
    7. L5 Threads have isolated arena graphs.
    8. No raw reference may cross an L5 Thread boundary; shared mutable memory is forbidden at L5.
    9. Messages cross L5 Thread boundaries only by copy, serialization or whole-branch ownership transfer.

These rules are the high-level memory contract. Lower levels may expose unsafe storage, addresses and explicit buffer operations, but those operations do not weaken the L5 isolation rule.

30.2. Branch Arenas

A branch arena is a memory region owned by a branch Structure or by another owner that plays the same role, such as a frame, handler, module state or L5 Thread root.

The intended shape is:

    root branch
        branch arena
            child Structure
            child array
            child text
            child expression tree
            child decimal storage

Leaf Structures may be stored inline, in their parent arena, or in implementation-defined compact storage. They normally do not own separate arenas because an arena per leaf would add overhead without improving lifetime management.

A branch far from the leaves may own an arena for the whole sub-tree. When the branch is destroyed, detached or locally collected, the arena can be released as one unit. This is the common case for documents, ASTs, message payloads, configuration trees, model descriptors and high-level runtime state.

30.3. Owner, Borrow and Owner-Copy

An owner is a scope, branch, arena, frame, handler, L5 Thread root or other region that is responsible for the lifetime of a Structure.

A borrowed value is a reference or handle into someone else's owned memory. Borrowing does not transfer cleanup responsibility and does not extend the lifetime of the source arena.

Values obtained from outside the current owner are borrowed by default. This includes values read from an incoming message, values obtained from another branch, and views into an existing Structure.

To retain such a value after the current frame, handler or owner lifetime ends, the program must create an owned copy:

    owner: saved, m\payload

Conceptual meaning:

    copy `m\payload` into an arena owned by the current owner;
    bind `saved` to that owned copy.

A plain binding of an external value may remain a borrow/view:

    borrow: view, m\payload

Conceptual meaning:

    bind `view` as a borrowed view valid only while the source owner is valid.

A profile may choose a different surface spelling for owner-copy, but it must preserve the semantic distinction between borrowed retention and owned retention.

30.4. No Escaping Borrow

The no-escaping-borrow rule is a consequence of the core rules.

A borrowed reference is valid only inside the frame, handler, arena epoch, branch lifetime or owner lifetime that produced it. It may not be stored in longer-lived state and may not be sent to another L5 Thread as a raw reference.

Invalid Lingvamyxa-shaped pattern:

L5:
    handler: retainPayload, m
        saved: m\payload
    ---
end: L5

when `saved` outlives the message frame and `m\payload` is borrowed.

Valid Lingvamyxa-shaped pattern:

L5:
    handler: retainPayload, m
        owner: saved, m\payload
    ---
end: L5

Here the payload is copied into an owned branch of the current L5 Thread or current persistent owner.

If a borrowed value must be sent to another L5 Thread, it must be copied, serialized or included in a whole-branch ownership transfer according to the message rules.

30.5. L5 Thread Memory

An L5 Thread owns an isolated memory tree or forest.

Source-shaped descriptor of the conceptual components:

L5:
    Thread:
        rootState:
        messageQueue:
        currentHandlerFrame:
        temporaryArenas:
        branchArenas:
        immutableValueStore:
        internTable:
    ---
end: L5

Raw references inside one L5 Thread may point only into memory owned by that same L5 Thread or into explicitly shared immutable storage admitted by the implementation profile. Raw references from one L5 Thread into another L5 Thread are invalid.

This makes the unit of memory management local. Releasing memory for one L5 Thread does not require stopping or scanning all L5 Threads in the system.

30.6. Message Boundary

The L5 Thread boundary is a memory boundary.

A message payload may cross the boundary in one of three ways:

    copy
    serialization
    whole-branch ownership transfer

Copy means that the receiver receives an owned copy in one of its own arenas or receives a borrowed message-frame value that must be owner-copied before retention.

Serialization means that the sender converts the payload to a byte/text/record representation and the receiver reconstructs its own Structure from that representation.

Whole-branch ownership transfer means that the sender transfers ownership of an entire branch arena to the receiver. After the transfer, the sender no longer owns that branch and must not use raw references into it.

A message must not contain raw borrowed references into the sender's private arena graph unless the receiver is the same L5 Thread and the active profile explicitly treats the message as an intra-thread frame.

30.7. Temporary Arenas, Tree Cutting and Thread Destruction

Temporary values may be allocated in a frame arena, handler arena or transaction arena and released as a group when that frame, handler or transaction ends.

Long-lived values must be reachable from an owner such as the L5 Thread root state, a branch root, a module state Structure or another persistent owner.

When a branch or subtree is cut from the local owner tree, an implementation may run an automatic tree-cut procedure for that L5 Thread. This procedure may promote deferred-owned edges, pin source owners that are still needed, detach branch roots, or mark local memory as no longer reachable from the thread root.

This procedure is not a general garbage collector in the source semantics and it is not a separately invoked language operation. It is part of the local structural memory machinery of one L5 Thread. Since one L5 Thread processes one handler at a time in the default profile, this procedure does not require cross-thread coordination or global stopping.

Actual memory release is a coarser implementation event. In the default model, memory may remain owned by the L5 Thread until that L5 Thread is destroyed. Explicit shared or externally managed L2 resources, such as large shared arrays, have their own explicit destruction/lifetime contracts. Until such L2 shared resources are introduced, destroying an L5 Thread is the ordinary mechanism that releases its local memory graph.

30.8. Immutable Values and Interning

High-level values may be immutable by default. A variable or Structure field may bind a handle to an immutable value rather than owning mutable storage directly.

An implementation may maintain an immutable value store or intern table:

    hash(value) -> canonical immutable object

Equal immutable values may share storage. Since immutable values cannot be changed through any alias, sharing them does not create mutable aliasing problems.

Examples of values suitable for interning or immutable storage:

    atoms
    symbols
    strings
    numeric constants
    normalized decimal constants
    small immutable arrays
    model descriptors
    expression trees

Interning is an optimization and a representation strategy. The source rule is that mutation of a high-level immutable value creates a new value or a new branch, not an in-place update through an alias.

30.9. Low-Level Interaction

L2 and implementation-facing L3 profiles may expose explicit mutable storage, arrays, buffers, typed addresses and unsafe operations. Such values are not magically immutable and may require explicit cleanup or generated cleanup.

When a low-level mutable buffer is embedded into a high-level Structure, the Structure must declare whether the edge is owned, borrowed or externally managed. An owned edge is cleaned when the owner is destroyed. A borrowed edge is not cleaned and must not outlive the external owner. An externally managed edge follows a profile-defined lifetime contract.

The high-level branch-arena model does not prohibit low-level code. It only requires that raw low-level references do not escape their valid owner lifetime or cross an L5 Thread boundary in violation of the L5 isolation rule.

30.10. Source Receivers and Lifetime Policy Forms

Ownership and lifetime policy should be expressed through ordinary receivers, phrase identifiers and argument Structures. The memory model does not introduce a separate ownership grammar.

L2 storage/allocation receivers remain the low-level unsafe layer:

    stack: T, name
    heap: T, name
    static: T, name
    []: name, size
    @: T, p

An L2 or implementation-facing profile may allow policy arguments on declaration/allocation receivers:

    heap: Buffer, data, owner(frame)
    heap: Buffer, data, external(cleanup freeBuffer)
    []: bytes, n, owner(branch)

These arguments are ordinary Structures consumed by the active receiver signature. They do not create C-like declaration syntax.

L3 profiles may expose safe memory-operation receivers:

    owner: saved, m\payload
    borrow: view, m\payload
    copy: dst, src
    move: dst, src

`owner: saved, value` creates an owned copy in the current owner according to the active type/model descriptor. `borrow: view, value` creates a borrowed view whose lifetime is bounded by the source owner. `copy` creates an independent value according to the target context. `move` transfers a value or branch when the active descriptor permits transfer and invalidates or empties the source binding according to the profile.

The phrase-signature spelling:

    owner saved: m\payload

may be supported by a profile as a readable variant of the same owner-copy operation. If `owner` is consumed as the ordinary receiver identifier, the canonical receiver-level form is:

    owner: saved, m\payload

Both spellings consume ordinary Structures. Neither introduces a new grammar category.

The source meaning of an owned edge is an ownership contract, not a mandatory immediate physical deep copy. An implementation may satisfy owner-copy semantics by:

    immediate deep copy;
    immutable sharing;
    copy-on-write;
    source-owner pinning;
    deferred owner-copy with automatic promotion during local tree-cut / owner-detach processing.

Deferred owner-copy means that an edge is semantically owned by the target owner, but the implementation may temporarily point to storage owned by the source owner. When the local owner tree is cut or an owner is detached, every still-live deferred-owned edge that would otherwise lose its source storage must either be promoted by copying the referenced value into the target owner, redirected to an immutable/shared representation, or keep the source owner pinned inside the same L5 Thread memory graph.

This is valid only when the observable ownership contract is preserved. For mutable values, deferred owner-copy requires a freeze, copy-on-write, explicit mutation barrier or immediate copy; otherwise the target would observe later source mutations instead of the value it retained. For immutable high-level Structures, source text, interned values, model descriptors and parser trees, deferred owner-copy is often a natural implementation strategy.

Promotion is part of the automatic local tree-cut procedure, not a memory cleanup/destructor operation and not a separately invoked source operation. It may allocate new storage, but that allocation belongs to ownership maintenance inside one L5 Thread. Actual memory release is performed later by destroying the L5 Thread memory graph or by destroying explicit L2/external resources with their own lifetime contracts.

L4 model/type descriptors may attach memory-edge policies to fields and payloads:

L4:
    model: MessageEnvelope
        vars:
            MessagePayload: payload, owned
            Text: view, borrowed
            SQL: nativeHandle, external(cleanup close)
        ---
    ---
end: L4

Such descriptors may materialize registry facts such as:

L5:
    fact: edge, MessageEnvelope, payload, owned
    fact: edge, MessageEnvelope, view, borrowed
    fact: cleanup, MessageEnvelope, nativeHandle, close
    fact: copyPolicy, MessageEnvelope, payload, deep
    fact: transferPolicy, MessageEnvelope, payload, forbidden
end: L5

The exact relation names are registry/profile details. The source rule is that L4 descriptors define the ownership contract used by L3/L5 consumption and by L1 lowering.

L5 message and sharing receivers may select boundary behavior explicitly:

    send: worker, m\payload, copy
    send: worker, m\payload, serialize
    send: worker, m\payload, transfer
    intern: value
    share: value, immutable

At an L5 Thread boundary, raw mutable references are invalid. `copy`, `serialize` and `transfer` are the ordinary policies for crossing the boundary. Immutable sharing is permitted only when the implementation profile can preserve immutability and thread-safety.

30.11. ANSI C Lowering Strategy

---ANSI C---
An ANSI C translator may implement this memory model with the following mechanisms:

    LmArena for branch, frame and handler regions;
    LmBranch or equivalent root handles for arena-owned branches;
    generated cleanup labels for L2/L3 resource values;
    frame/handler arena reset at safe exits;
    deep-copy functions for owner-copy;
    lazy-owned edge tables for deferred owner-copy;
    source-owner pinning or promotion during local tree-cut / owner-detach processing;
    serialization functions for message payloads;
    ownership-transfer functions that detach one LmBranch from a sender and attach it to a receiver;
    optional per-L5-Thread local tracing or reference counting for branch roots;
    no global heap scan as a source-semantic requirement.

Possible runtime declarations:

    typedef struct LmArena LmArena;
    typedef struct LmBranch LmBranch;
    typedef struct LmThread LmThread;

    typedef enum LmEdgeKind {
        LM_EDGE_OWNED,
        LM_EDGE_LAZY_OWNED,
        LM_EDGE_BORROWED,
        LM_EDGE_EXTERNAL,
        LM_EDGE_TRANSFERRED
    } LmEdgeKind;

    typedef struct LmTypeOps {
        void (*destroy)(void *value);

        LmEdgeKind kind;

        LmArena *arena;
        const LmTypeOps *type_ops;

    };

Possible arena API:

    void *lm_arena_alloc(LmArena *arena, size_t size, size_t align);
    void  lm_arena_reset(LmArena *arena);
    void  lm_arena_destroy(LmArena *arena);

The exact status/result type is implementation-defined. A profile may use `int`, an `LmStatus` enum, receiver diagnostics or another error convention.

Generated type/model operations may be derived from L4 descriptors:

    destroy       clears owned edges and external resources;
    copy_to       implements owner-copy and ordinary deep copy;
    serialize     implements message serialization;
    trace         supports optional local owner-tree walking or reference tracking.

An owner-copy form such as:

    owner: saved, m\payload

may lower to:

    saved = lm_copy_to_owner(current_owner, m_payload);

or to inlined field-by-field copy when the type/model layout is statically known.

If the implementation uses deferred owner-copy, the same form may lower to a lazy-owned edge:

    saved = lm_lazy_owner_edge(current_owner, m_payload);

The lazy edge is still semantically owned by `current_owner`. During automatic local tree-cut or owner-detach processing, if the source owner would no longer remain reachable, the runtime must either promote the edge:

    lm_tree_cut_promote_lazy_edges(source_owner);

or keep the source owner pinned inside the same L5 Thread memory graph until no lazy-owned edges refer to it.

For immutable values, promotion may be unnecessary if the implementation can prove stable lifetime and immutability. For mutable values, the runtime must use immediate copy, freeze, copy-on-write or a mutation barrier before lazy ownership can preserve source semantics.

L5 message crossing may lower as:

    copy       -> deep-copy payload into receiver-owned arena or message-frame arena;
    serialize  -> encode to bytes/text/records, then reconstruct on receiver side;
    transfer   -> detach an `LmBranch` from the sender, attach it to the receiver and invalidate sender-side raw references/handles.

A generated C function may lower scope cleanup to a single C99 exit label:

    int lm_generated_handler(LmThread *thread, const LmMessage *m)
    {
        int status = 0;
        LmArena *temp_arena = lm_thread_temp_arena(thread);
        LmResource resource;
        int resource_initialized = 0;

        status = lm_resource_init(&resource);
        if (status != 0) {
            goto cleanup;
        }
        resource_initialized = 1;

        status = lm_generated_body(thread, m, &resource);
        if (status != 0) {
            goto cleanup;
        }

    cleanup:
        if (resource_initialized) {
            lm_resource_destroy(&resource);
        }
        lm_arena_reset(temp_arena);
        return status;
    }

For high-level immutable Structures, the translator may represent bindings as handles into an immutable store. For low-level mutable resources, the translator must preserve the declared owned/borrowed/external lifetime edge.

30.12. Shared Low-Level Resources and Large Read-Only Data

The L5 memory model is intentionally message- and branch-oriented. It is the default safe model for active objects, behavior dispatch, high-level events, configuration and query handling. It should not be used to pretend that large shared raw buffers are ordinary per-thread message payloads.

If a program needs a large resource that many L5 Threads read directly, such as a large numeric table, shared index, memory-mapped dataset, model-weight array or external database page cache, that resource belongs in an L2 or implementation-facing L3 profile as an explicit low-level/shared resource.

Example conceptual L2 forms:

L2:
    static: BigArray, table, shared(readonly)

L2:
    static: BigArray, table, shared(readonly), externalLifetime

The exact receiver names and policy arguments are profile-defined. The semantic point is that the resource is not an ordinary mutable L5 branch. It is a shared immutable or externally managed low-level object with an explicit lifetime contract.

L4 may describe such a resource as a model/descriptor:

L4:
    model: BigArray
        field: data, @f64, borrowed
        field: len, u64
        access: shared, readonly

The L4 descriptor may record that the data edge is borrowed from low-level storage, shared only under read-only access, externally managed, memory-mapped or protected by another explicit runtime contract. L5 may use the descriptor and receive handles/selectors/facts about the resource, but ordinary L5 message passing does not send raw mutable references to it.

Shared immutable data may be read by many L5 Threads when the implementation profile guarantees immutability and thread-safe publication. Since no thread can mutate the shared value through an alias, this does not violate the L5 no-shared-mutable-memory rule.

Shared mutable data is different. If multiple threads must write or coordinate over the same resource, the resource must be represented through explicit L2/L3 synchronization or atomic constructs such as locks, read-write locks, atomics, barriers, memory-order policies or transactional receivers. Those constructs are unsafe or implementation-facing unless a higher-level profile wraps them in a checked abstraction.

Therefore:

    L5 default       -> copy, serialization, whole-branch ownership transfer
    L5 shared read   -> immutable / read-only / externally published resource
    L2/L3 explicit   -> shared mutable buffers, atomics, locks and external lifetimes

The long-term bootstrap direction is that L1 should shrink to the target/backend substrate. Language-visible rules for shared resources, memory edges, synchronization and lifetime should move upward into L2, L3, L4 and L5 descriptors/receivers. L1 remains the implementation layer used to lower those rules to C99, platform APIs, libraries and native binaries.

30.13. Control Exit, Assert Diagnostics and Thread-Local Collection

The memory model has no separate source-level cleanup operation.

Memory reclamation is performed by the L5 Thread local collector and by the
local memory-cutter machinery described in this section.

A control operator does not free memory merely because it is a control operator.
It may, however, leave a frame, handler, retry attempt, transaction arena,
branch owner or whole L5 Thread. Such an exit changes the local owner tree and
creates a collector safe point.

The L5 Thread local collector may run at defined safe points:

    after normal frame completion;
    after handler completion;
    after transaction completion;
    after return;
    after break;
    after continue;
    after labelled break;
    after labelled continue;
    after fail;
    after retry;
    after redo;
    after assert diagnostic exit;
    after owner replacement;
    after owner removal;
    after local branch/subtree detachment;
    before or during L5 Thread termination;
    under implementation-defined memory pressure.

The collector is local to one L5 Thread.

It does not stop other L5 Threads.

It does not scan foreign arena graphs.

It does not require a global lock in the default L5 model.

It may inspect the current L5 Thread owner tree, local arena graph, branch
ownership metadata, deferred-owned edges, borrowed edges, local reachability
metadata and implementation priority metadata.

The collector may:

    cut unreachable local branches;
    release frame-local arenas;
    release handler-local arenas;
    release transaction arenas;
    release abandoned retry-attempt arenas;
    release detached branch arenas;
    promote deferred-owned edges when required;
    pin source owners when required;
    copy surviving data into surviving owners when required;
    detach surviving branch roots as independent owners;
    destroy the whole L5 Thread arena graph when the L5 Thread terminates.

Actual memory release is implementation-defined. A profile may release memory
immediately after a local cut, batch releases until the end of the current
handler, or retain local memory until the whole L5 Thread is destroyed.

This is a technical memory collection mechanism by effect, because it
automatically reclaims memory. It is not a global tracing collector by
mechanics. Its unit of collection is an owner region:

    frame arena;
    handler arena;
    retry-attempt arena;
    transaction arena;
    branch arena;
    whole L5 Thread arena graph.

30.13.1. No Source-Level Cleanup Operation

This document does not define a separate source-level cleanup operation.

The term collection means a Thread-local memory collection pass.

A collection pass may include:

    owner-tree cutting;
    arena reclamation;
    deferred-owner promotion;
    source-owner pinning;
    branch detachment;
    whole-thread arena destruction.

The word cleanup is avoided in this memory section because in many programming
languages it denotes finalization code such as finally/destructor logic.
Lingvamyxa memory reclamation is specified as Thread-local collection and
owner-tree cutting instead.

30.13.2. Control Exit and Owner Lifetime

Control exits are connected to memory only through owner lifetime.

Generic sequence:

    control exit is selected;
    affected frame, handler, attempt, transaction or branch owners are marked
    as exited, abandoned, detached or destroyed;
    the owner tree is updated;
    the L5 Thread local collector may run at this safe point;
    unreachable local owner regions may be cut;
    actual arena release follows the implementation profile.

Therefore:

    return / break / continue:
        leave ordinary control scopes and may create collection safe points;

    fail:
        leaves recoverable failure scopes and may create collection safe points;

    retry:
        abandons the current retry attempt and may create a collection safe point;

    redo:
        abandons or restarts the current repeatable unit according to receiver
        semantics and may create a collection safe point;

    assert:
        exits through the diagnostic path and may create a collection safe point;

    thread termination:
        destroys the whole L5 Thread owner graph unless the implementation
        profile preserves selected externally managed resources.

No control operator is a memory operation by itself. Memory is reclaimed because
the operator changes owner lifetime.

30.13.3. `assert` and Memory

`assert` is diagnostic invariant failure, not recoverable failure flow.

If an `assert` condition is false, the runtime records an
`AssertionViolation` diagnostic and exits through the diagnostic path defined by
the execution-context profile.

Default thread-profile sequence:

    assert condition is false;
    record AssertionViolation diagnostic;
    transfer control to the thread diagnostic root;
    terminate the current thread/task by default after reporting the diagnostic;
    run the L5 Thread local collector;
    destroy or release the L5 Thread arena graph according to the thread
    destruction policy.

An `assert` violation is not part of the declared `throws` set.

An `assert` violation is not caught by ordinary failure labels or failure
handlers.

An `assert` violation does not execute `fail`.

An `assert` violation may still cause memory reclamation because it abandons
frames, handlers, attempts or the whole current L5 Thread. The reclamation is
performed by the L5 Thread local collector, not by a special `assert` memory
rule.

If a runtime profile allows a diagnostic root to keep the L5 Thread alive after
an assertion violation, then only the owners abandoned by the diagnostic exit
are cut or released. Persistent state still reachable from the L5 Thread root
remains owned by that L5 Thread unless the diagnostic policy explicitly
destroys, resets or detaches it.

30.13.4. `guard`, `fail`, `throws` and Handlers

`guard`, `fail`, `throws` and failure handlers define declared recoverable
failure flow.

They are distinct from `assert`.

    guard / fail / throws / handlers:
        declared, expected, recoverable failure path

    assert:
        diagnostic invariant violation

`guard` may detect an expected failure condition and select a failure path.

`fail` exits the current executable body with a declared failure label and an
optional payload.

Default failure sequence:

    guard detects an expected failure condition;
    fail creates a declared failure label and optional payload;
    control exits to the nearest visible handler or caller failure channel;
    affected frame, handler or attempt owners are marked as abandoned or exited;
    the L5 Thread local collector may run at this safe point;
    a structured failure result is delivered to the handler or caller.

`fail` does not transfer to the thread diagnostic root.

`fail` does not use the `assert` channel.

`fail` does not directly free memory. It creates a collection safe point because
it exits the current owner context.

A failure payload that must survive the abandoned owner must be owned by a
surviving owner. If the payload is borrowed from the failing frame, handler or
attempt, it must be owner-copied into a surviving owner before it is retained
beyond that owner lifetime.

If a failure payload crosses an L5 Thread boundary, it must cross by copy,
serialization or whole-branch ownership transfer. A raw reference into the
failing L5 Thread arena graph must not cross that boundary.

Failure handlers may be lexical handlers, executable labels, caller-side
receivers or L5 event/message handlers according to the final handler syntax.
In all variants, memory safety is governed by the same owner, borrow,
owner-copy and message-boundary rules.

30.13.5. `retryable`, `retry` and Attempt Arenas

`retryable` defines a restartable frame.

`retry` abandons the current attempt and re-enters the nearest or named
retryable frame.

Default retry sequence:

    select nearest or named retryable frame;
    abandon the current attempt;
    mark attempt-local owners as abandoned;
    run the L5 Thread local collector at the retry safe point;
    release or retain abandoned attempt arenas according to the implementation
    profile;
    recreate local bindings declared inside the retryable frame;
    re-enter the retryable frame.

`retry` is re-execution, not transactional rollback.

`retry` does not roll back external side effects.

`retry` does not automatically restore outer bindings unless the retryable
receiver defines a stronger rollback policy.

Values that must survive `retry` must be owned by an outer owner that is not
abandoned by the retry. A borrowed value or attempt-local branch cannot be
retained across retry unless it is copied or transferred into such an outer
owner.

Example conceptual distinction:

    retry attempt-local value:
        collectible when the attempt is abandoned

    value owner-copied into outer retryable owner:
        survives the abandoned attempt

    value stored in L5 Thread root:
        survives retry unless explicitly replaced, removed or cut

Therefore `retry` may free memory repeatedly without invoking a global tracing
collector. Each abandoned attempt loses its attempt-local owner graph, and the
next attempt starts with fresh local bindings.

30.13.6. Owner Replacement and Null-Like Removal

When a binding update, owner replacement, explicit removal or profile-defined
null-like operation cuts a branch from the local owner tree, the implementation
may run the automatic local tree-cut procedure.

Conceptual sequence:

    old owner edge is removed or replaced;
    old branch/subtree is no longer reachable from the local owner tree;
    deferred-owned edges reachable from still-live owners are promoted, pinned
    or redirected;
    detached branch roots are preserved only if they became independent owners;
    otherwise the old branch/subtree becomes locally unreachable;
    actual arena release occurs according to the implementation profile.

This is the ordinary memory-cutter path for local owner-tree mutation.

It is not required to scan all objects in the process.

It is not required to stop other L5 Threads.

It does not inspect foreign L5 Thread arena graphs.

30.13.7. Emergency Memory Pressure

Emergency memory pressure is an implementation/runtime policy over owner
destruction.

A runtime may reclaim memory urgently by cancelling, failing, aborting or
destroying selected L5 Threads, handlers, transactions, retry attempts or branch
owners according to priority, scheduling policy, diagnostic policy or
service-level policy.

Default emergency sequence for destroying an L5 Thread:

    select a victim L5 Thread or task;
    request cancellation, declared failure, diagnostic termination or forced
    termination according to profile;
    mark the selected owner graph as abandoned or terminating;
    run the L5 Thread local collector;
    destroy the selected owner graph or the whole L5 Thread arena graph;
    return the memory owned by that graph to the implementation allocator.

This is a technical garbage-collection mechanism by effect, because it
automatically reclaims memory.

It is not a global tracing collector by mechanics.

Its unit of collection is not an individual object. Its unit of collection is
an owner region:

    frame arena;
    handler arena;
    retry-attempt arena;
    transaction arena;
    branch arena;
    whole L5 Thread arena graph.

30.13.8. Collection Ordering Rule

For every control exit that changes owner lifetime, the owner-state transition
is ordered before local collection.

Required abstract order:

    1. decide the control exit, failure exit, retry exit, diagnostic exit or
       termination;
    2. mark the affected owners as exited, abandoned, detached or destroyed;
    3. apply failure, retry, return, diagnostic or termination transfer according
       to the active receiver/profile;
    4. update the local owner tree;
    5. run the L5 Thread local collector if this point is selected as a
       collection safe point;
    6. release arenas whose owners are destroyed or whose implementation profile
       permits immediate release.

Borrowed references into a destroyed owner are invalid after that owner is cut
or released.

A surviving owner may retain data only if that data is already owned by the
surviving owner, copied into it, serialized through it, or transferred to it as
a whole branch according to the message and ownership rules.

30.13.9. Mandatory Message-Boundary Collection Policy

The default L5 collector scheduling policy is not profile-arbitrary.

In the default L5 model, the L5 Thread local collector runs at message
boundaries.

A message boundary is reached when one of the following events is completed:

    an incoming message has been received and its payload has been copied,
    serialized into, or ownership-transferred into a valid owner of the
    receiving L5 Thread;

    an outgoing message has been sent and its payload has been copied,
    serialized into, or ownership-transferred to the target queue, transport or
    target owner;

    a message handler has completed normally;

    a message handler has exited by return, fail, retry, redo, assert diagnostic
    exit or thread termination.

At each message boundary, the L5 Thread runtime must run one local collection
pass before continuing ordinary message processing.

The collection pass may be a cheap no-op when no local owner-tree or arena
state changed.

The collection pass is local to the current L5 Thread.

It does not stop other L5 Threads.

It does not scan foreign arena graphs.

It does not require a global lock.

It does not perform global tracing collection.

The collection pass may inspect only the current L5 Thread owner tree, local
arena graph, branch ownership metadata, deferred-owned edges, borrowed edges,
local reachability metadata and implementation priority metadata.

The collector must preserve:

    owner validity;
    no-escaping-borrow;
    no raw cross-thread references;
    message-boundary ownership rules;
    copy / serialization / whole-branch-transfer rules for inter-thread data.

This rule deliberately keeps ordinary collection simple and regular:

    receive message
        -> run local collection pass
        -> execute or schedule handler work

    send message
        -> commit payload transfer
        -> run local collection pass
        -> continue current handler

    finish handler
        -> run local collection pass
        -> wait for or receive next message

30.13.10. Long L5 Computations and Supervisor Termination

An L5 Thread is expected to remain message-responsive.

The default L5 runtime is not required to interrupt arbitrary deep computation
inside one handler in order to run the collector. If an L5 Thread enters a long
computation and does not reach a message boundary or another declared yield
point within the runtime watchdog limit, the supervising L5 Thread may cancel,
fail, abort or destroy that L5 Thread according to the scheduling and diagnostic
policy.

This is intentional.

Long computations in L5 must be written as stepwise or resumable computations if
they need to coexist with message scheduling and regular memory collection.

Valid designs include:

    lazy receiver/operator evaluation;
    iterator/yield-style computation;
    query/search receivers that split work into bounded steps;
    continuation messages sent back to the same or another L5 Thread;
    retryable frames whose attempts are bounded;
    explicit handler-level work slicing;
    profile-defined cooperative yield points.

If a computation must run as a long uninterrupted low-level operation, it should
be lowered to L2/L3 semantics with explicit threading, memory, synchronization
and lifetime rules. Such L2/L3 worker threads are not ordinary message-driven L5
Threads unless wrapped by an L5 owner/message facade.

Therefore the default rule is:

    L5 Thread:
        message-driven;
        regularly collected at message boundaries;
        supervisor may terminate it if it stops reaching boundaries;

    long L5 algorithm:
        must be split into lazy/stepwise/message-visible units;

    long uninterrupted low-level algorithm:
        belongs to explicit L2/L3 execution semantics.

Emergency memory pressure uses the same ownership principle. A supervising
Thread may reclaim memory by terminating low-priority or non-responsive L5
Threads. The memory reclaimed is the memory owned by the selected owner regions
or by the whole selected L5 Thread arena graph. The runtime does not need to
find individual unreachable objects inside a global heap.

31. L5 Thread and Message Model

31.0. Scope

The L5 Thread model defines the default high-level execution and communication model of Lingvamyxa. It is the companion of the section 30 memory model.

An L5 Thread is not necessarily an operating-system thread. It is a logical execution unit with isolated state, a local arena graph and a message queue. An implementation may lower an L5 Thread to an OS thread, a fiber, a coroutine, an event-loop task, an actor, an embedded scheduler entity or another runtime execution unit.

The semantic requirement is isolation, not a particular scheduler primitive:

    L5 Thread -> isolated execution tree + local memory graph + message queue

No raw reference owned by one L5 Thread may point directly into another L5 Thread. Inter-thread communication is by typed messages, whole-branch transfer, serialization or implementation-approved immutable sharing.

31.1. L5 Thread

An L5 Thread owns:

    root state;
    current handler frame;
    message queue;
    local branch arenas;
    temporary frame/handler arenas;
    local immutable value store or intern table, if supplied by the profile;
    local registry view/cache, if supplied by the profile;
    local failure/event queue, if supplied by the profile.

An L5 Thread may process one handler at a time by default. This gives the default L5 profile single-threaded reasoning inside each isolated execution tree. Parallelism is obtained by creating multiple L5 Threads and exchanging messages between them.

The implementation may execute several L5 Threads on the same OS thread, or one L5 Thread per OS thread, or use a work-stealing/event-loop implementation. This does not change the source-level rule that L5 Threads do not share mutable raw references.

31.2. Root State

The root state is the durable state of an L5 Thread. Long-lived owned branches that must survive a single message handler are reachable from the root state or from another branch reachable from the root state.

Values created inside a handler are temporary unless they are:

    stored into root state as owned values;
    copied into an owned branch reachable from root state;
    transferred as a whole owned branch to another L5 Thread;
    returned through a reply/future/result mechanism;
    explicitly retained by a profile-defined persistent store.

A borrowed value received from another owner or another message frame may not be stored in root state as a raw borrow. To retain it, the program must create an owned copy or receive ownership of the whole branch.

31.3. Handler Frame

A handler frame is the dynamic execution frame created when an L5 Thread processes a message. It has its own temporary arena or temporary allocation epoch.

The handler frame may contain:

    parameters and message payload views;
    local variables;
    temporary Structures;
    temporary query results;
    continuation state for yield/await-like receivers;
    failure/status state;
    cleanup records for owned local resources.

When the handler completes normally or by failure, frame-local temporaries are released as a group and owned local resources are cleaned in reverse initialization order. Borrowed payloads do not extend the lifetime of their source.

31.4. Message Structure

A message is a typed Structure. A profile may choose exact field names, but the conceptual fields are:

    receiver          target L5 Thread, object, behavior or service selector;
    selector          message name / receiver name / operation tag;
    payload           typed argument Structure;
    transfer mode     copy, move, serialize, immutable-share or profile-defined mode;
    reply channel     optional Future/Task/reply receiver;
    failure channel   optional failure receiver or result sink;
    priority          optional scheduling priority;
    ordering key      optional stable ordering key;
    metadata          profile-defined tracing, security, capability or scheduling data.

The payload is a Structure, not a raw pointer bag. The receiver consumes the Structure according to its registered receiver signature, type model and message descriptor.

31.5. Message Transfer Modes

The standard conceptual transfer modes are:

    copy
        Deep-copy the payload into the receiver-owned arena, receiver message arena or another receiver-local owner.

    move
        Transfer ownership of a whole owned branch arena from the sender to the receiver. Sender-side raw references/handles into that branch become invalid after transfer.

    serialize
        Encode the payload into bytes/text/records, then reconstruct it in the receiver. This is the default safe form across process, machine, storage or untrusted boundaries.

    immutable-share
        Share an immutable value handle only when the implementation profile guarantees immutability, thread-safe publication and lifetime stability.

    external-handle
        Pass a descriptor/capability to an explicit low-level or external resource. The resource itself is not an ordinary mutable L5 branch.

The default safe transfer mode is copy or serialization. Move is an optimization and a semantic transfer of ownership. Immutable-share is valid only for values that cannot be mutated through any alias. Shared mutable data is outside the default L5 model and must be represented through explicit L2/L3 synchronization or a checked higher-level abstraction.

31.6. Borrowed Payloads

Received payloads are borrowed by default during handler execution. A borrowed payload is valid only for the current handler frame, message frame, arena epoch or owner lifetime that produced it.

The no-escaping-borrow rule applies:

    a borrowed payload may not be stored in root state;
    a borrowed payload may not be sent as a raw reference to another L5 Thread;
    a borrowed payload may not be retained by a continuation unless its owner/arena lifetime covers the continuation;
    a borrowed payload may not outlive the message or branch that owns it.

To keep received data after the handler returns, the handler must perform owner-copy into its own L5 Thread memory graph or receive/move a whole owned branch.

31.7. Queue and Scheduling

Each L5 Thread owns at least one conceptual message queue. The default scheduling profile is deterministic:

    messages are processed one handler at a time;
    FIFO ordering is used within equal priority;
    equal ordering keys preserve stable insertion order;
    a handler runs until it returns, fails, yields or awaits;
    no other handler mutates the same L5 Thread root state concurrently.

A profile may add priorities, deadlines, fairness windows, cooperative yields, preemption points or real-time scheduling. Such profiles must specify whether they preserve deterministic ordering.

The default L5 model avoids data races by construction: root state is local to one L5 Thread and is mutated by at most one active handler in the default profile.

31.8. Dispatch as Registry Query

Message dispatch is not special object magic. It is resolved through receiver signatures, descriptors and the logical registry/query layer.

A dispatch query may use facts such as:

    receiver type;
    selector name;
    payload type;
    protocol/behavior descriptor;
    capability descriptor;
    visibility level;
    target implementation;
    failure contract;
    transfer policy.

Conceptual query:

query:
    relation: message_handler
    receiver: ?receiverType
    selector: parse
    payload: SourceText
    implementation: ?impl

The resulting handler implementation is then invoked by the scheduler with a typed payload Structure. Generic dispatch, behavior lookup, operator/message specialization and validation may all use the same registry facts and relation rules described in section 21.

31.9. Reply, Future and Task Structures

A message may request a reply. The reply mechanism is represented by a typed Structure rather than by hidden control flow.

Conceptual forms:

    Result T E      completed value or failure;
    Future T E      pending result with a reply channel;
    Task T E        scheduled computation with continuation state;
    ReplyChannel    receiver/message target for result delivery.

A synchronous call is a profile-level convenience over message sending plus waiting for a reply inside the same scheduler domain. An asynchronous call sends a message and receives a Future/Task-compatible Structure.

Reply payloads obey the same transfer rules as ordinary message payloads: copy, whole-branch move, serialization or immutable-share.

31.10. Failure Propagation

Failures are not hidden cross-thread exceptions. A failure crossing an L5 Thread boundary is represented as a typed message/result/failure Structure.

Inside one handler, a profile may use local failure control such as guard/fail/throws/handler labels, as described by the failure model. Across L5 Thread boundaries, the failure must be materialized as data:

    Result.Err;
    failure message;
    rejected Future/Task;
    reply-channel failure payload;
    profile-defined event.

This preserves the no-raw-reference and no-hidden-cross-thread-control-flow rules.

31.11. Await and Continuations

`async` and `await`, if provided by a profile, are surface forms over L5 message scheduling and continuation state. They are not a separate concurrency model.

An async procedure returns a Future/Task-compatible Structure. Calling it schedules or constructs a task rather than necessarily running the body to completion immediately.

An await receiver consumes a Future/Task-compatible Structure. If the value is not ready, the current handler/procedure continuation is stored in a scheduler-visible continuation Structure, control returns to the L5 scheduler, and the continuation resumes when a result message arrives.

Conceptual lowering:

    await future
        -> store continuation state
        -> suspend current handler/procedure
        -> return control to scheduler
        -> resume by result message

Values that survive across an await boundary must be owned by the continuation, stored in an arena whose lifetime covers the continuation, immutable with stable lifetime, or copied into continuation state. Frame-local borrows may not survive await unless the owner lifetime is statically known to cover the continuation.

Thus await obeys the same memory model as messages:

    borrow before await -> cannot escape await unless lifetime-stable
    owner value         -> may be stored in continuation state
    immutable value     -> may be shared if profile permits
    branch value        -> may be moved or copied

31.12. Yield and Message Scheduling

`yield` and `await` are related but distinct.

    yield
        emits a value from an iterator-compatible state machine and records resume state.

    await
        waits for a Future/Task/message result and records resume state.

Both lower to explicit continuation state. Both must respect the same lifetime rules for local values, borrowed payloads and branch arenas. Neither introduces hidden shared mutable state between L5 Threads.

31.13. Determinism Profile

The deterministic profile of L5 execution is:

    one active handler per L5 Thread;
    stable queue ordering;
    no shared mutable raw references across L5 Threads;
    message payload transfer by copy, serialization or whole-branch move;
    deterministic handler code unless it uses declared nondeterministic receivers;
    explicit ordering for time, external I/O and scheduler interaction.

A nondeterministic or real-time profile may relax ordering, introduce priorities, interact with external event loops or process messages under deadlines. Such a profile must mark the nondeterministic sources and must not pretend they are ordinary deterministic structural evaluation.

31.14. ANSI C Lowering Strategy

A minimal C99 runtime may represent an L5 Thread as a structure containing root state, queues, arenas and scheduler metadata:

---ANSI C---

typedef struct LmThread LmThread;
typedef struct LmMessage LmMessage;
typedef struct LmBranch LmBranch;
typedef struct LmArena LmArena;

typedef LmStatus (*LmHandlerFn)(LmThread *thread, const LmMessage *message);

struct LmThread {
    LmArena *state_arena;
    LmArena *temp_arena;
    LmQueue *queue;
    void *root_state;
    LmRegistryView *registry;
};

---ANSI C---

A message enqueue operation lowers to:

    construct typed payload;
    copy/move/serialize according to transfer mode;
    enqueue message into receiver queue;
    return status or Future/Task handle.

A scheduler step lowers to:

    pop next message according to scheduling profile;
    resolve handler by registry/query or precomputed dispatch table;
    create handler frame / reset temp arena;
    invoke handler;
    deliver reply/failure if required;
    release handler temporaries.

A whole-branch move lowers to detaching an owned LmBranch from the sender and attaching it to the receiver. The sender must not retain valid raw references into the moved branch.

31.15. Boundaries and Non-Goals

The structural core does not define the binary layout of queues, futures, branch handles, registry caches, scheduler locks, wake-up mechanisms, OS-thread mapping, coroutine ABI, serialization format or network transport.

Those belong to runtime profiles and L1/L2 lowering specifications.

The core rule is stable:

    L5 Thread -> isolated state and arena graph
    communication -> typed messages
    retention -> owner-copy or ownership transfer
    waiting -> continuation state
    dispatch -> logical registry/query layer
    shared mutable memory -> outside default L5, explicit L2/L3/profile construct

32. Reactive Registry, Query Receivers, and Agent Candidates

This section defines the reactive layer of the L5 registry.

The registry is not passive storage. Inserting, updating, or removing a fact or
rule emits a typed registry event message. Deterministic query receivers may
react to that event and derive ordinary typed facts, messages, diagnostics, or
indexes from the accepted registry model. Agent receivers may also react to the
same events, but their output is always a candidate Structure and is never
trusted directly.

The core rule can be summarized as a conceptual equation block, not as Lingvamyxa source:

    query engine = proof and deterministic search
    agent        = hypothesis generator
    validator    = semantic gatekeeper
    registry     = typed memory
    message model = reaction mechanism

AI or heuristic agents may propose. The registry validation path disposes.


32.1. Core Idea

A registry change has observable typed consequences.

A registry event may be consumed by:

    deterministic query receivers
    agent receivers
    diagnostic receivers
    indexing receivers
    lowering receivers
    documentation receivers
    test-generation receivers

Deterministic query receivers are part of the formal language/runtime
semantics. They derive only what follows from accepted typed facts, rules, and
relations.

Agent receivers are advisory. They may use AI, heuristics, pattern matching,
external tools, or human-assisted tools. Their output is never committed
directly to the registry. It is always represented as a candidate Structure.

The normal reaction cycle is:

    fact/rule change
      -> registry event message
      -> deterministic query receivers
      -> derived ordinary messages/facts/diagnostics
      -> optional agent receivers
      -> candidate Structures
      -> validation/query/type checking
      -> accepted ordinary facts/messages or rejected diagnostics


32.2. Registry Events

A registry event is an ordinary typed message emitted by the registry.

Minimal event kinds are:

    registryFactAdded
    registryFactRemoved
    registryRuleAdded
    registryRuleRemoved
    registryFactChanged
    registryRuleChanged
    registryTransactionCommitted
    registryTransactionRejected

Example:

    message:
    . type: registryFactAdded
    . transaction: 1842
    . fact:
    .. relation: operator
    .. name: `+`
    .. leftType: decimal
    .. rightType: decimal
    .. resultType: decimal
    .. implementation: decNumberAdd
    end: message

The event is not a special control-flow primitive. It is a typed message
delivered by the L5 message model.


32.3. Deterministic Query Receivers

A deterministic query receiver subscribes to registry events and runs formal
queries over the accepted registry model.

Example receiver intent:

    receiver:
    . name: numericDomainCompletenessChecker
    . on: registryFactAdded
    . when:
    .. relation: operator
    end: receiver

When an operator fact is added, the receiver may ask:

    query:
    . relation: requiredOperator
    . domain: decimal
    . operator: ?op
    end: query

and:

    query:
    . relation: operator
    . domain: decimal
    . name: ?op
    end: query

The receiver can then derive a diagnostic:

    diagnostic:
    . severity: warning
    . message: decimal numeric domain is incomplete
    . missing: (`-`, `*`, `/`, compare)
    end: diagnostic

This requires no AI. It follows from formal facts and rules already present in
the registry.


32.4. Agent Receivers

An agent receiver is also a message receiver, but its output is not trusted.

An agent receiver may observe the same registry events as deterministic
receivers.

Example:

    agent:
    . name: numericImplementationAgent
    . on: registryFactAdded
    . relation: operator
    end: agent

After observing:

    operator +(decimal, decimal) -> decNumberAdd

the agent may propose:

    candidate:
    . kind: fact
    . fact:
    .. relation: operator
    .. name: `*`
    .. leftType: decimal
    .. rightType: decimal
    .. resultType: decimal
    .. implementation: decNumberMultiply
    end: candidate

This is not inserted into the registry yet.

It must pass the ordinary validation path:

    type checking
    relation validation
    implementation lookup
    arity checking
    level visibility checking
    conflict checking
    completeness rules
    memory/message safety rules

Only after successful validation can the candidate become an ordinary registry
fact.


32.5. Candidate Structures

A candidate Structure is structurally inspectable but semantically untrusted.

Candidate forms include:

    candidate fact
    candidate rule
    candidate message
    candidate diagnostic
    candidate lowering
    candidate test
    candidate documentation
    candidate index hint

A candidate should carry provenance metadata:

    candidate:
    . source: `agent:numericImplementationAgent`
    . event: 1842
    . confidence: optional
    . payload: omitted
    end: candidate

The confidence value is advisory metadata only. It does not affect formal
acceptance unless a receiver explicitly uses it as non-semantic metadata.


32.6. Validation Cycle

Validation converts a candidate into either an ordinary typed Structure or a
diagnostic.

The validation cycle is:

    candidate received
      -> parse/check candidate shape
      -> check declared relation/type
      -> query registry for conflicts and requirements
      -> check implementation availability
      -> check L-level visibility
      -> check memory/message constraints
      -> accept or reject

Accepted example:

    accepted:
    . candidate: 921
    . becomes: registryFactAdded
    end: accepted

Rejected example:

    diagnostic:
    . severity: error
    . candidate: 921
    . reason: implementation decNumberMultiply is not visible from L1 profile
    end: diagnostic

A rejected candidate may be stored for diagnostics, logs, training data,
explanation, or ignored.


32.7. A Simple Implementation Without Full Prolog

The bootstrap implementation does not require a full Prolog engine.

It may start with:

    array/list of facts
    array/list of rules
    array/list of receivers
    simple query matcher
    simple substitution map
    message queue
    candidate validator

Fact:

    typedef struct {
        LmSymbol relation;
        LmStruct *data;
    } LmFact;

Rule:

    typedef struct {
        LmStruct *head;
        LmStruct *body;
    } LmRule;

Message:

    typedef struct {
        LmSymbol type;
        LmStruct *payload;
        uint64_t transaction_id;
    } LmMessage;

Receiver:

    typedef enum {
        LM_RECEIVER_QUERY,
        LM_RECEIVER_AGENT,
        LM_RECEIVER_VALIDATOR,
        LM_RECEIVER_DIAGNOSTIC
    } LmReceiverKind;

    typedef struct {
        LmReceiverKind kind;
        LmStruct *subscription_pattern;
        void (*handle)(LmThread *thread, const LmMessage *message);
    } LmReceiver;

Candidate:

    typedef enum {
        LM_CANDIDATE_FACT,
        LM_CANDIDATE_RULE,
        LM_CANDIDATE_MESSAGE,
        LM_CANDIDATE_DIAGNOSTIC
    } LmCandidateKind;

    typedef struct {
        LmCandidateKind kind;
        LmStruct *payload;
        LmSymbol source;
        uint64_t source_event;
    } LmCandidate;

The first query engine may simply scan all facts:

    query with relation: operator
      -> scan registry facts where relation == operator
      -> match fields
      -> bind ?variables
      -> return result bindings

A later implementation may replace this with indexed lookup:

    relation/name/leftType/rightType -> fact list

The observable semantics remains the same.


32.8. Processing Order

For one registry transaction, processing order is deterministic.

    1. Commit source fact/rule into a registry transaction.
    2. Emit a registry event message.
    3. Run deterministic query receivers in stable registry order.
    4. Validate and enqueue their derived ordinary messages/facts/diagnostics.
    5. Run agent receivers, if enabled by profile/configuration.
    6. Convert agent output into candidate Structures.
    7. Validate candidates using ordinary validators and query receivers.
    8. Commit accepted candidates as ordinary facts/rules/messages.
    9. Store or ignore rejected candidates as diagnostics.

Agent receivers must not mutate registry state directly.


32.9. Avoiding Infinite Reaction Loops

Reactive registry systems can loop.

Example:

    fact added
      -> receiver derives fact
      -> fact added
      -> same receiver derives same fact again

The runtime should track:

    transaction id
    event id
    candidate id
    source receiver
    deduplication hash
    reaction depth

Minimal safety rules are:

    the same fact is not inserted twice into one registry model
    the same receiver/event pair is not repeated in one transaction unless explicitly allowed
    reaction depth may be limited by profile
    cyclic derivations must converge, be rejected, or produce a diagnostic


32.10. Trust Boundary

The trust boundary is simple.

Accepted registry facts and rules are trusted according to the active registry
profile.

Deterministic query receiver output is trusted only after ordinary validation.

Agent receiver output is never trusted directly.

A candidate Structure is data, not authority.

The validator/query/type system is the authority.


32.11. Relationship to AI

AI is optional.

The same mechanism may work with:

    no AI
    simple heuristic agents
    static rule generators
    external analyzers
    LLM-based agents
    human-in-the-loop tools

The language semantics depends only on accepted typed registry state,
deterministic query receivers, accepted facts/rules, and validators.

Agent output is outside trusted semantics until accepted.

Canonical rule:

    AI may propose.
    Registry validation disposes.


32.12. Relationship to Messages and L5 Threads

Registry events are messages.

Query receivers and agent receivers run inside an L5 Thread.

No raw reference from another L5 Thread may be stored in a candidate or accepted
fact.

Message payloads received from outside are borrowed by default. To retain them,
the receiver must owner-copy them into the current L5 Thread arena or receive a
moved whole branch.

This keeps the reactive registry compatible with the L5 memory model.


32.13. Minimal Bootstrap Profile

The bootstrap implementation may support only:

    fact insertion
    registryFactAdded event
    linear fact scan
    deterministic query receivers
    candidate validation
    diagnostic output

Rules, unification, indexing, AI agents, and compiled query plans may be added
later.

Bootstrap profile:

    facts: yes
    rules: optional
    query variables: simple named placeholders
    backtracking: optional
    agent receivers: optional
    validation: required
    diagnostics: required

This still preserves the architecture:

    registry event
      -> deterministic receiver
      -> candidate/ordinary output
      -> validation
      -> accepted structure or diagnostic


32.14. Standard Statement

The reactive registry layer defines how structural knowledge changes cause
typed reactions.

A fact or rule insertion emits a typed registry event message.

Deterministic query receivers may subscribe to registry events and derive
ordinary typed structures from existing accepted facts and rules.

Agent receivers may also subscribe to registry events, but their output is
always a candidate Structure and is not trusted.

Every candidate must pass normal type, query, registry, memory, message, and
validation rules before it can become an ordinary fact, rule, or message.

Rejected candidates are diagnostics, not failed control flow.

The registry, query engine, and validators form the trusted semantic path.
Agent receivers are advisory producers of candidate Structures only.


33. REST/JSON Microservice Runtime and Built-in HTTP Client/Server Profile

This section defines the optional REST/JSON service profile for Lingvamyxa service instances.

The profile is intentionally external to the core language syntax. REST is not the execution model of Lingvamyxa. JSON is not the native syntax of Lingvamyxa. HTTP is not the native message system of Lingvamyxa.

The REST/JSON profile is an adapter layer that maps external HTTP requests into standard typed L5 messages, dispatches them through the ordinary L5 registry/query/message model, and maps reply or failure messages back into HTTP responses.

The compact model is a conceptual summary, not Lingvamyxa source:

    REST route = descriptor
    HTTP request = incoming message
    JSON = adapter
    service = L5 Thread bundle
    dispatch = registry/query
    state = isolated L5 memory tree

33.1. Service Instance

A Lingvamyxa service instance is a bundle of L5 Threads running under one service runtime.

A service instance normally contains:

    root service configuration;
    one registry model;
    one message router;
    one or more service L5 Threads;
    optional HTTP server adapter Thread;
    optional HTTP client adapter Thread;
    optional storage/event-log Thread;
    optional agent/query/validation Threads;
    optional diagnostics and monitoring Threads.

An L5 Thread inside a service instance is still an isolated execution tree. It owns its local state, arenas, frames, message queue and registry view/cache according to the L5 memory and message model.

The service bundle is not a shared mutable heap. It is a managed set of isolated L5 Threads connected by standard typed messages.

33.2. Registry, Router and Event Log

A service instance has a registry and a message router.

The registry stores accepted facts, rules, route descriptors, service descriptors, receiver descriptors, type descriptors and implementation descriptors.

The router receives typed messages and resolves their target receiver through the registry/query layer.

The service may have an optional storage or event-log component. A simple implementation may persist:

    accepted registry facts;
    registry transactions;
    incoming HTTP request summaries;
    outgoing HTTP request summaries;
    messages;
    replies;
    failures;
    diagnostics;
    candidate Structures.

SQLite may be used as one implementation backend for this service-local persistence, but storage is not part of the core language semantics.

33.3. REST/JSON as an Adapter Profile

REST/JSON is an adapter profile.

It is not Lingvamyxa syntax. It is not the canonical internal representation of a Structure. It is not the core message model.

The profile exists for interoperability with existing tools, web clients, service gateways, tests, external agents and simple deployment environments.

The normative internal object is always the typed Lingvamyxa message.

External REST/JSON data is converted into typed Lingvamyxa Structures before dispatch. Lingvamyxa reply or failure messages are converted back into HTTP responses after execution.

33.4. HTTP Request to L5 Message

An incoming HTTP request is treated as an external event.

The HTTP server adapter receives:

    method;
    path;
    query parameters;
    headers;
    body bytes;
    remote peer metadata;
    request id;
    optional authentication context;
    optional timeout/deadline.

The adapter converts the HTTP request into a typed incoming message.

Example abstract message:

    message:
    . type: httpRequest
    . id: "request-1842"
    . method: POST
    . path: "/calculator/add"
    . headers: omitted
    . body: decodedRequestBody
    . peer: omitted
    end: message

If the route declares JSON input, the JSON body is parsed by the JSON adapter and converted into a Lingvamyxa Structure before route dispatch.

The result of this conversion is a normal L5 message:

    message:
    . to: calculator
    . selector: add
    . payload:
    .. a: 2
    .. b: 3
    . replyTo: httpAdapter("request-1842")
    end: message

33.5. L5 Message to HTTP Response

HTTP responses are produced from reply or failure messages.

A successful reply message may map to HTTP 200, 201, 202 or another route-declared success status.

A failure message may map to HTTP 400, 401, 403, 404, 409, 422, 500 or another route-declared failure status.

The mapping is descriptor-driven.

Example reply message:

    message:
    . type: reply
    . request: "request-1842"
    . ok: true
    . result: 5
    end: message

Example JSON response produced by the adapter:

    {
      "ok": true,
      "result": 5
    }

Example failure message:

    message:
    . type: failure
    . request: "request-1842"
    . code: invalidPayload
    . diagnostic: "field 'a' is required"
    end: message

Example JSON failure response:

    {
      "ok": false,
      "error": {
        "code": "invalidPayload",
        "diagnostic": "field 'a' is required"
      }
    }

The JSON text is external representation only. The internal failure is a typed Lingvamyxa Structure.

33.6. L5 Service/Route Descriptor Profile

REST routes belong to the L5 service/route descriptor profile.

A route descriptor maps an external HTTP shape to an internal message target.

Example:

    route:
    . method: POST
    . path: "/calculator/add"
    . input: json
    . output: json
    . to: calculator
    . selector: add
    . successStatus: 200
    end: route

Equivalent compact descriptor:

    route(method(POST), path("/calculator/add"), input(json), output(json), to(calculator), selector(add), successStatus(200))

A route descriptor may specify:

    HTTP method;
    path pattern;
    query parameter schema;
    header requirements;
    input adapter;
    output adapter;
    target receiver;
    selector;
    payload mapping;
    authentication requirement;
    authorization rule;
    timeout;
    success status mapping;
    failure status mapping;
    rate or resource policy;
    visibility level.

Route descriptors are ordinary registry facts. They may be indexed, validated, queried, generated, documented and lowered through the same logical registry layer as operator, method, model and behavior descriptors.

33.7. Dispatch Through Registry/Query

A REST request is not dispatched by hard-coded string switches unless the implementation chooses that as a lowering optimization.

The semantic dispatch path is:

    HTTP request
      -> route descriptor lookup
      -> input adapter
      -> typed L5 message
      -> registry/query dispatch
      -> receiver handler
      -> reply/failure message
      -> output adapter
      -> HTTP response

Route lookup is a query over accepted route descriptors.

Example abstract query:

    query:
    . relation: route
    . method: POST
    . path: "/calculator/add"
    . target: ?target
    . selector: ?selector
    . input: ?inputAdapter
    . output: ?outputAdapter
    end: query

The query result determines how the adapter constructs the internal message.

33.8. JSON Adapter

JSON is one external serialization adapter.

It may be used for:

    incoming REST payloads;
    outgoing REST responses;
    service-to-service HTTP envelopes;
    diagnostics;
    tests;
    external agent input/output;
    debugging dumps.

JSON does not become a native Lingvamyxa syntax. JSON objects are parsed into Lingvamyxa Structures according to adapter rules and route schemas.

A JSON adapter should preserve:

    string values;
    integer values where representable;
    decimal text where declared by schema;
    boolean values;
    null markers if allowed by schema;
    arrays as ordered Structures;
    objects as named-field Structures.

A JSON adapter must reject or mark ambiguous conversions when the route schema requires a type that the JSON value cannot represent safely.

For example, large integers and decimal numbers may be preserved as strings or explicit typed wrappers if exact numeric fidelity is required by the route descriptor.

33.9. Built-in HTTP Server Profile

The HTTP server profile allows a Lingvamyxa service instance to listen for incoming HTTP requests.

The server adapter is represented as one or more L5 Threads or as a hosted native adapter that injects messages into an L5 Thread.

The server adapter owns no application state except adapter-local state such as sockets, request buffers, temporary arenas, route caches and connection metadata.

Application state belongs to service L5 Threads and follows the isolated L5 memory tree model.

A hosted C99 implementation may use an external embedded HTTP server library. This is an implementation detail and does not change the Lingvamyxa service model.

33.10. Built-in HTTP Client Profile

The HTTP client profile allows a Lingvamyxa service instance to send messages to external HTTP endpoints or other Lingvamyxa services.

The client adapter converts an outgoing Lingvamyxa message into an HTTP request and converts the HTTP response into a reply or failure message.

Example outgoing service message:

    message:
    . to: remoteService
    . selector: `calculator.add`
    . payload:
    .. a: 2
    .. b: 3
    . transport: restJson
    . endpoint: "http://service-b/lm/message"
    end: message

The HTTP client adapter may produce:

    HTTP method;
    target URL;
    headers;
    serialized body;
    timeout;
    retry metadata;
    correlation id.

The response is converted back into a typed reply/failure message and delivered to the original L5 Thread through the normal message scheduler.

33.11. Lingvamyxa-to-Lingvamyxa Service Communication

Lingvamyxa services communicate by standard Lingvamyxa messages.

REST/JSON over HTTP is only one transport profile for those messages.

Other transport profiles may include:

    local in-process queue;
    SQLite-backed queue;
    file/event-log transport;
    REST/JSON over HTTP;
    binary Structure over HTTP;
    binary Structure over TCP;
    platform message bus;
    embedded device transport.

The semantic boundary is the typed message, not the transport encoding.

A remote Lingvamyxa service must not receive raw pointers, borrowed references or direct arena references from another service.

A message crossing a service boundary must be copied, serialized or transferred as a whole owned branch under a transport that explicitly supports ownership transfer.

The default REST/JSON profile is copy/serialize only.

33.12. Service Boundaries and Memory Rules

Direct cross-service raw references are forbidden.

A service boundary obeys the same rules as an L5 Thread boundary, with stronger default isolation:

    no raw pointer crosses the boundary;
    no borrow crosses the boundary;
    no service may store a reference into another service's arena;
    no service may mutate another service's local state directly;
    payloads are copied or serialized by default;
    retained incoming data must be owner-copied into the receiver service;
    failures are messages, not exceptions crossing memory spaces.

An incoming HTTP payload is borrowed only for the duration of the HTTP adapter frame unless converted into an owned message payload.

A retained request body, parsed Structure or decoded payload must be copied into an arena owned by the receiving L5 Thread or service bundle.

33.13. Service State

Service state is an isolated L5 memory tree.

The REST adapter does not own domain state. It receives HTTP events and injects typed messages.

The target L5 Thread owns and updates its own state according to the L5 memory model.

Within one L5 Thread, message handling is sequential unless a different scheduling profile is explicitly declared.

Across L5 Threads, communication is by messages only.

Across service instances, communication is by serialized or copied messages only.

33.14. Failure Mapping

Internal failures are typed failure messages.

The REST adapter maps them to HTTP status codes and response bodies.

The route descriptor may define the mapping.

Example:

    failureMap:
    . invalidPayload: 400
    . unauthorized: 401
    . forbidden: 403
    . notFound: 404
    . conflict: 409
    . validationFailed: 422
    . internalFailure: 500
    end: failureMap

The absence of a route-level mapping uses the service profile default.

A failure response should preserve a typed code and a diagnostic Structure where possible.

33.19.1 Module-loaded service endpoints

A Lingvamyxa service host may derive REST endpoints from loaded *.lmx modules.
Loaded modules materialize typed registry facts. Route descriptors may be
explicitly declared or derived by deterministic query receivers from public
service/method descriptors. Endpoint activation is transactional: a new endpoint
map becomes visible only after parsing, type checking, route derivation and
validation succeed.
              
JSON/REST exposure is never implied by procedure existence alone.
Only descriptors visible to the REST adapter profile may be exposed.

33.15. Security and Capabilities

HTTP server and client access should be capability-controlled.

A handler should not acquire network access implicitly.

A service configuration may grant:

    listen capability;
    outbound HTTP capability;
    route exposure capability;
    remote endpoint capability;
    authentication capability;
    storage capability.

Example descriptor:

    service:
    . name: calculatorService
    . capabilities:
    .. `http.listen`: "127.0.0.1:8080"
    .. `http.outbound`: false
    .. `storage.sqlite`: "calculator.db"
    end: service

This keeps HTTP as an explicit service capability rather than hidden global access.

33.16. Implementation Profile: Hosted C99

A hosted C99 implementation may provide the REST/JSON service profile by linking external libraries.

A typical implementation profile may use:

    embedded HTTP server library for incoming HTTP;
    HTTP client library for outgoing HTTP;
    JSON parser/emitter library for JSON adapter;
    SQLite for optional registry/event-log persistence;
    PCRE2 for route patterns or text processing if enabled.

For example, one possible hosted C99 profile is:

    HTTP server: CivetWeb
    HTTP client: libcurl
    JSON adapter: yyjson
    storage: SQLite
    regex: PCRE2

These library choices are non-normative. They are implementation tools, not part of the core language semantics.

33.17. Minimal Bootstrap Service Profile

The minimal REST/JSON service profile may support only:

    one service instance;
    one HTTP server adapter;
    one /lm/message endpoint;
    JSON request body;
    JSON response body;
    local message router;
    synchronous request/reply;
    simple failure mapping;
    no authentication;
    no streaming;
    no service discovery;
    no retry system.

Minimal endpoint:

    POST /lm/message

Example request:

    {
      "to": "calculator",
      "selector": "add",
      "payload": {
        "a": 2,
        "b": 3
      }
    }

Internal message:

    message:
    . to: calculator
    . selector: add
    . payload:
    .. a: 2
    .. b: 3
    end: message

Example response:

    {
      "ok": true,
      "result": 5
    }

This minimal profile is enough to expose a Lingvamyxa L5 Thread bundle as a simple REST/JSON microservice.

33.18. Standard Statement

A Lingvamyxa service instance is a bundle of isolated L5 Threads connected by standard typed messages.

The bundle has a registry, a message router and optional storage or event-log components.

REST/JSON is an adapter profile, not a core language syntax.

HTTP requests are converted into standard typed L5 messages.

HTTP responses are produced from reply or failure messages.

Routes are L5 service/route descriptors stored as typed registry facts.

JSON is only one external serialization adapter.

Lingvamyxa-to-Lingvamyxa services communicate by standard Lingvamyxa messages over a selected transport profile.

Direct cross-service raw references are forbidden.

Service boundaries obey the L5 memory and message model.


34. ANSI C Type Projection and Registry-Class Model

34.0. Scope of This Section

This section describes how the L4/L5 descriptor model may be lowered by an
ANSI C / C99 implementation.

It is an implementation profile. It does not add new source syntax and it does
not replace the structural source rules in earlier sections.

The intended pipeline is:

    Lingvamyxa source
        -> P0 generic Structures
        -> receiver normalization
        -> typed registry descriptors
        -> type checking and relation checking
        -> ANSI C declarations and functions
        -> platform C compiler/linker

The parser builds Structures. Receivers and semantic passes decide whether a
Structure is a model, behavior, message, relation, adapter, service route or
ordinary value.

34.1. Registry Entry as a Decomposed Class

In an object-oriented language such as Java, a class commonly combines fields
and methods in one syntactic block.

Lingvamyxa separates these concerns into registry descriptors attached to the
same registry name.

    L4 ModelSpec
        describes structural data: slots, field types, defaults, constraints,
        layout policy and derived operations.

    L5 BehaviorSpec
        describes object/message behavior: selectors, method implementations,
        delegation, routing and dynamic object behavior.

    Derivation descriptors
        may request constructors, validators, accessors, serializers, C layout
        projection, route schemas or documentation schemas.

Together these descriptors make a registry entry similar to a class, but the
class-like object is accumulated in the registry rather than declared as one
monolithic source form.

Example:

L4:
    model: Circle
        vars:
            f64: radius
        ---
        condition:
            radius > 0.0
        ---
    ---
end: L4

L5:
    behavior: Circle
        message: drawOn, drawCircleOn
        message: area, circleArea
    ---
end: L5

The registry entry for `Circle` may contain:

    ModelSpec
        radius: f64
        validator: radius > 0.0

    BehaviorSpec
        drawOn -> drawCircleOn
        area   -> circleArea

    Derivations
        constructor
        validator
        accessors
        type operations

The structural model says what a `Circle` value is. The behavior descriptor says
how a `Circle` object responds to messages.

34.2. Concrete ModelSpec as a Final C Type

After receiver normalization, a concrete `ModelSpec` is a final concrete type
for an ANSI C projection.

    Plant   -> concrete ModelSpec -> ANSI C struct LmPlant
    Oak     -> concrete ModelSpec -> ANSI C struct LmOak
    Circle  -> concrete ModelSpec -> ANSI C struct LmCircle

The genesis of the type may be structural, rule-derived or registry-driven, but
the normalized result has a concrete typed shape.

Therefore a C99 translator should prefer ordinary C structs and typed pointers
for concrete normalized models.

It should not make every value a dynamic object unless the field, receiver or
implementation profile explicitly requests a dynamic/role/message handle.

Example model source:

L4:
    model: Plant
        vars:
            f64: height
            i32: age
        ---
    ---

    model: Oak
        vars:
            Plant: plant
            i32: acornCount
        ---
    ---
end: L4

---ANSI C---
One possible C99 projection:

    typedef struct LmPlant {
        double height;
        int32_t age;
    } LmPlant;

    typedef struct LmOak {
        LmPlant plant;
        int32_t acornCount;
    } LmOak;
---ANSI C---

This is composition. It is not inheritance.

34.3. ModelSpec vs BehaviorSpec in Lowering

The ANSI C translator must keep the structural model and the behavior model
separate.

The `ModelSpec` controls:

    C struct fields;
    field order;
    primitive lowering;
    inline components;
    pointer/reference fields;
    arrays and slices;
    generated copy/destroy/tree-cut operations.

The `BehaviorSpec` controls:

    message selector lookup;
    method table generation;
    direct static call optimization;
    role/delegation handles;
    dynamic dispatch where the profile allows it.

Known concrete calls may lower directly:

---ANSI C---
    lm_circle_area(&circle);
---ANSI C---

Role or dynamic behavior calls may lower through a behavior table:

---ANSI C---
    ref.behavior->area(ref.object, args);
---ANSI C---

Both forms are implementation choices for the same source-level rule:
behavior is resolved from registry facts and descriptors, not from implicit C
struct inheritance.

34.4. Composition, Roles and Explicit Generalization

If `Plant` and `Oak` are concrete models, `Plant` is a final concrete type and
`Oak` is a final concrete type.

An `Oak` value is not automatically assignable to a `Plant` value.

Allowed relationships must be explicit:

    composition
        `Oak` contains a `Plant` component.

    component projection
        `oak\plant` produces the Plant component.

    role/delegation
        `Oak` may be viewed through a Plant role/reference if registry facts
        say that `Oak` implements or delegates that role.

    union membership
        `Oak` may be wrapped as a member of a union/domain that includes Oak.

    adapter/conversion
        an explicit adapter maps Oak to Plant or to another expected type.

Example explicit registry facts:

L5:
    fact: role, PlantRole
    fact: roleMessage, PlantRole, grow
    fact: implements, Oak, PlantRole
    fact: delegates, Oak, PlantRole, plant
end: L5

---ANSI C---
One possible role/reference lowering:

    typedef struct LmPlantRef {
        void *object;
        LmTypeId concrete_type;
        const LmBehaviorSpec *behavior;
    } LmPlantRef;

    LmPlantRef ref;
    ref.object = oak;
    ref.concrete_type = LM_TYPE_OAK;
    ref.behavior = &LmOak_as_PlantRole_behavior;
---ANSI C---

This is L5 delegation/behavior. It is not C struct inheritance.

34.5. Type Reconciliation Algorithm

When a receiver, assignment target or field expects type `E` and the source
expression produces type `A`, the translator should return a typed match result,
not just a boolean.

The result must distinguish at least:

    exact match;
    named-field unpack;
    explicit component projection;
    role/delegation match;
    union/domain membership;
    explicit adapter/conversion;
    rejection.

Suggested order:

    1. If E and A are the same concrete type, accept exact match.

    2. If E is a concrete model and the source is a Structure, match source
       fields to model fields by name, then check each field recursively.

    3. If A contains a component of type E, accept only when the source
       expression explicitly requests that component, for example `oak\plant`.

    4. If E is a role/protocol/reference type, query the registry for an
       implementation or delegation relation from A to E.

    5. If E is a union/domain and A is a listed member, wrap A with the union
       tag/descriptor.

    6. If an explicit adapter exists and the active profile permits it, lower
       through the adapter.

    7. Otherwise reject and report expected type, actual type and available
       explicit projections/adapters.

Multiple assignment and Structure consumption are named-field unpacking. They
are not inheritance and not implicit structural subtyping.

34.6. C99 Projection API Shape

The first C99 translator should have a projection layer that consumes typed
descriptors, not raw parser nodes.

Conceptual API:

---ANSI C---
    int lm1_emit_struct_decl(
        LmWriter *out,
        const char *c_name,
        const LmModelSpec *model);

    int lm1_emit_struct_typedef(
        LmWriter *out,
        const char *c_name,
        const LmModelSpec *model);

    int lm1_emit_type_ops(
        LmWriter *out,
        const char *c_name,
        const LmModelSpec *model);
---ANSI C---

Type checking should also expose the selected lowering path:

---ANSI C---
    typedef enum LmTypeMatchKind {
        LM_TYPE_MATCH_EXACT,
        LM_TYPE_MATCH_NAMED_UNPACK,
        LM_TYPE_MATCH_COMPONENT_PROJECTION,
        LM_TYPE_MATCH_ROLE_DELEGATION,
        LM_TYPE_MATCH_UNION_MEMBER,
        LM_TYPE_MATCH_ADAPTER,
        LM_TYPE_MATCH_REJECT
    } LmTypeMatchKind;

    typedef struct LmTypeCheckResult {
        LmTypeMatchKind kind;
        LmTypeId expected;
        LmTypeId actual;
        LmSymbol projection_field;
        LmSymbol adapter_name;
        LmDiagnostic diagnostic;
    } LmTypeCheckResult;
---ANSI C---

The exact ABI is implementation-defined. The important rule is that type
checking must preserve why a match succeeded.

34.7. Memory Model Connection

The Section 30 memory model lowers naturally to generated type operations.

For every concrete `ModelSpec`, the implementation may derive:

    destroy
        release owned/external fields according to edge policies.

    copy_to
        copy a value into another owner/arena.

    tree_cut
        maintain deferred owner-copy and lazy-owned edges when a local branch
        is cut or detached.

    serialize
        materialize messages or service-boundary payloads.

    field_projection
        provide explicit component projection helpers.

Inside one parser tree, arena or L5 Thread owner, ordinary typed C pointers are
allowed:

---ANSI C---
    LmNode *node;
    LmStructure *body;
    LmField *field;
    LmOak *oak;
---ANSI C---

Owner metadata is needed at owner roots and cross-owner edges, not on every
local child pointer.

Borrowed source slices, lazy-owned edges and external resources must still obey
Section 30. No raw reference may cross an L5 Thread or service boundary.

34.8. Minimal Bootstrap Profile

The first ANSI C implementation may support only:

    P0 parser Structures;
    normalized ModelSpec descriptors;
    normalized BehaviorSpec descriptors;
    concrete ModelSpec -> typedef struct;
    primitive fields;
    inline component fields;
    typed pointer fields;
    source slices;
    named-field unpack into concrete models;
    explicit component projection;
    role/reference handles;
    rejection of implicit Oak-as-Plant assignment;
    generated copy/destroy/tree-cut operations for the supported fields.

It does not need:

    dynamic object representation for every value;
    implicit inheritance;
    automatic structural subtyping between arbitrary models;
    global object heap;
    global tracing garbage collector;
    runtime reflection for every field access.

34.9. Standard Statement

For an ANSI C implementation, a normalized concrete `ModelSpec` is the source of
an ordinary final C struct type.

Registry-level generalization is expressed through explicit facts and
descriptors: component projection, role/delegation, union membership or
adapter/conversion.

L4 defines what the data is. L5 defines how values respond to messages.

The registry entry may look class-like, but it is a decomposed registry class:
data layout, behavior, derivations and service descriptors are attached by
explicit receiver-normalized facts.

34.RU. ANSI C проекция и registry-class модель

34.RU.0. Область раздела

Этот раздел описывает, как модель L4/L5 может быть реализована транслятором в
ANSI C / C99.

Это профиль реализации. Он не добавляет новый исходный синтаксис.

Рабочая цепочка такая:

    исходник Lingvamyxa
        -> P0 generic Structures
        -> нормализация receivers
        -> типизированные registry descriptors
        -> сверка типов и отношений
        -> объявления и функции ANSI C
        -> C compiler/linker

Парсер строит Structures. Receivers и семантические проходы решают, чем эта
Structure является: моделью, поведением, сообщением, отношением, adapter-ом,
route descriptor-ом или обычным значением.

34.RU.1. Registry entry как разобранный class

В Java-подобном языке class обычно сразу содержит и поля, и методы.

В Lingvamyxa это разложено на descriptors, которые прикрепляются к одному имени
в registry.

    L4 ModelSpec
        описывает данные: slots, типы полей, defaults, conditions, layout
        policy и выводимые операции.

    L5 BehaviorSpec
        описывает поведение: messages/selectors, реализации методов,
        delegation, routing и object behavior.

    Derivation descriptors
        могут запросить constructors, validators, accessors, serializers,
        C layout projection, route schemas или документацию.

Вместе это похоже на class, но class не объявляется одним синтаксическим
монолитом. Он собирается в registry из явных descriptors.

Пример:

L4:
    model: Circle
        vars:
            f64: radius
        ---
        condition:
            radius > 0.0
        ---
    ---
end: L4

L5:
    behavior: Circle
        message: drawOn, drawCircleOn
        message: area, circleArea
    ---
end: L5

Смысл:

    ModelSpec Circle
        Circle имеет поле radius: f64
        radius должен быть больше 0.0

    BehaviorSpec Circle
        Circle понимает drawOn
        Circle понимает area

L4 говорит, чем значение является структурно. L5 говорит, как объект отвечает
на messages.

34.RU.2. Конкретный ModelSpec как конечный C-тип

После нормализации конкретный `ModelSpec` становится конечным конкретным типом
для ANSI C projection.

    Plant   -> concrete ModelSpec -> struct LmPlant
    Oak     -> concrete ModelSpec -> struct LmOak
    Circle  -> concrete ModelSpec -> struct LmCircle

Происхождение типа может быть сложным: receiver, registry facts, rules,
генерация. Но после нормализации это уже конкретная typed shape.

Поэтому C99-транслятору не нужно превращать каждое значение в динамический
object. Если модель конкретная, нормальный lowering - обычная C struct и
обычные C-типизированные указатели.

Пример Lingvamyxa:

L4:
    model: Plant
        vars:
            f64: height
            i32: age
        ---
    ---

    model: Oak
        vars:
            Plant: plant
            i32: acornCount
        ---
    ---
end: L4

---ANSI C---
Возможная C99-проекция:

    typedef struct LmPlant {
        double height;
        int32_t age;
    } LmPlant;

    typedef struct LmOak {
        LmPlant plant;
        int32_t acornCount;
    } LmOak;
---ANSI C---

Это композиция. Это не наследование.

34.RU.3. Почему Oak не является Plant автоматически

Если `Plant` и `Oak` - конкретные модели, то обе являются конечными типами.

`Oak` не присваивается в `Plant` молча.

Допустимые связи должны быть явными:

    composition
        Oak содержит компонент Plant.

    component projection
        `oak\plant` достает компонент Plant.

    role/delegation
        Oak можно видеть как PlantRole/PlantRef, если registry явно говорит,
        что Oak реализует или делегирует эту роль.

    union membership
        Oak можно завернуть как вариант union/domain.

    adapter/conversion
        явный adapter преобразует Oak в Plant или в ожидаемый тип.

Пример явных facts:

L5:
    fact: role, PlantRole
    fact: roleMessage, PlantRole, grow
    fact: implements, Oak, PlantRole
    fact: delegates, Oak, PlantRole, plant
end: L5

Такой подход заменяет объектное наследование делегированием и явными registry
relations.

34.RU.4. Как поле может ссылаться на Oak, если ожидается обобщение

Если поле имеет тип `Oak`, это простое конкретное поле или указатель:

---ANSI C---
    LmOak oak;
    LmOak *oak;
---ANSI C---

Если поле должно хранить "что-то, что ведет себя как Plant", это не `Plant`.
Это role/reference/profile type.

Например, C lowering может быть таким:

---ANSI C---
    typedef struct LmPlantRef {
        void *object;
        LmTypeId concrete_type;
        const LmBehaviorSpec *behavior;
    } LmPlantRef;
---ANSI C---

Тогда внутри `LmPlantRef` может лежать адрес `LmOak`, но только потому, что
registry явно подтвердил: Oak может использоваться как PlantRole.

Это не "Oak наследует Plant". Это "Oak имеет concrete type, а registry дает
способ смотреть на него через role/delegation".

34.RU.5. Сверка типов

Когда receiver или поле ожидает тип `E`, а выражение дает тип `A`,
транслятор должен выяснить, каким именно способом это можно совместить.

Порядок:

    1. E и A совпадают - exact match.

    2. E является concrete ModelSpec, а source является Structure -
       распаковать Structure по именам полей.

    3. A содержит компонент E - разрешить только явный доступ, например
       `oak\plant`.

    4. E является role/protocol/reference type - спросить registry, есть ли
       implements/delegates от A к E.

    5. E является union/domain - проверить, входит ли A в варианты.

    6. Есть явный adapter/conversion - применить adapter, если профиль это
       разрешает.

    7. Иначе ошибка типов.

Множественное присваивание в Lingvamyxa - это распаковка Structure по именам
полей. Это не polymorphism и не inheritance.

34.RU.6. Связь с memory model

Section 30 хорошо ложится на generated type operations.

Для каждого concrete ModelSpec можно вывести:

    destroy
        освобождает owned/external edges по policies.

    copy_to
        копирует значение в другой owner/arena.

    tree_cut
        обслуживает lazy-owned/deferred owner-copy edges при отсечении ветки.

    serialize
        материализует message или service payload.

    field_projection
        дает явные helpers для `oak\plant` и похожих projection-ов.

Внутри одного owner/arena можно использовать простые C-типизированные
указатели:

---ANSI C---
    LmNode *node;
    LmStructure *body;
    LmField *field;
    LmOak *oak;
---ANSI C---

Owner metadata нужна на owner roots и cross-owner edges, а не на каждом
локальном child pointer.

34.RU.7. Минимальный смысл для первого ANSI C bootstrap

Первый C99-транслятор может поддерживать только:

    P0 parser Structures;
    normalized ModelSpec;
    normalized BehaviorSpec;
    concrete ModelSpec -> typedef struct;
    primitive fields;
    inline component fields;
    typed pointer fields;
    source slices;
    named-field unpack;
    explicit component projection;
    role/reference handles;
    запрет неявного Oak-as-Plant;
    generated copy/destroy/tree-cut operations.

Ему не нужны:

    dynamic object для каждого значения;
    implicit inheritance;
    automatic structural subtyping между произвольными models;
    global object heap;
    global tracing GC;
    runtime reflection для каждого field access.

34.RU.8. Короткая формула

L4 ModelSpec отвечает на вопрос:

    какие данные имеет значение?

L5 BehaviorSpec отвечает на вопрос:

    какие messages понимает объект?

ANSI C projection отвечает на вопрос:

    какие structs, pointers, functions и type operations надо сгенерировать?

Concrete model становится final C struct.

Обобщение становится не наследованием, а явной registry-связью:

    component;
    role/delegation;
    union;
    adapter.

Именно поэтому Lingvamyxa может получить class-like модель, но опускать ее в
очень простой C99 код.
