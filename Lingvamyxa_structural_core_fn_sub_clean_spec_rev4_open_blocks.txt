Lingvamyxa Structural Core Specification

Status

This document specifies the structural core of Lingvamyxa as a self-contained language model.

The document is descriptive and semantic. Surface syntax builds Structures. Receivers and subroutines consume Structures and assign typed meaning to them.

Open points are marked with three distinct block types.

Marker convention:

    This block marks an actual ambiguity, contradiction or unresolved rule in the syntax or source semantics.
    !!!

0. Core Formula

Lingvamyxa is based on the following model:

    L0 binaries run.
    L1 is an external bootstrap, implementation and lowering layer.
    L2-L5 are Lingvamyxa levels.
    Source syntax builds Structures.
    Receivers and subroutines consume Structures.
    The parser has a native structural syntax and a mathematical expression syntax.
    Mathematical expressions also produce Structures.
    Levels restrict the active receiver/operator set.

The language does not assign final meaning directly from surface syntax. Surface syntax builds generic Structures. A receiver or subroutine consumes a Structure and assigns typed semantics to it.

Canonical semantic pipeline:

    source text
        -> structural and mathematical parse
        -> generic Structure values
        -> receiver/subroutine consumption
        -> typed semantic structures
        -> interpretation or lowering

A Structure does not execute merely because it exists. Execution, translation, registration, validation or query handling starts only when a receiver or subroutine consumes the Structure under a defined mode.


1. Levels

1.1. L0

L0 is a native binary artifact or machine-code artifact. It is the level actually executed by the CPU and operating system.

Examples of L0 artifacts:

    app.lm0.exe
    app.lm0
    core.lm0.dll
    core.lm0.so
    core.lm0.dylib
    core.lm0.a
    core.lm0.lib

1.2. L1

L1 is an external bootstrap, implementation and lowering layer. It may host initial parsers, translators, runtime components and receivers. L1 has its own syntax and semantics and is not part of the Lingvamyxa source-semantic core described by this document.

This document does not specify the L1 target language, physical calling convention, memory ownership rules or low-level runtime representation. Those belong to translator and runtime specifications.

1.3. L2

L2 is the low-level unsafe Lingvamyxa level. It is the low-level systems layer. It may expose memory, pointers, handles, structures, explicit low-level operations and low-level concurrency.

L2 is compiled. It is not executed as a casual script.

1.4. L3

L3 is the algorithmic and computational Lingvamyxa level. It supports safe top-level actions, computations and calls. L3 code may be interpreted by the core runtime or compiled through the lowering pipeline.

1.5. L4

L4 is the non-executive model level. It describes models, types, protocols, contracts, constraints, relation signatures and registry metadata.

L4 may update or check the compiler/runtime model. L4 does not perform ordinary runtime actions by default.

1.6. L5

L5 is the level of messages, configuration, objects, build/run/query/startup receivers, operator registration and high-level dispatch.

1.7. Level Receivers

`L2`, `L3`, `L4` and `L5` are level receivers. A level receiver consumes its nested Structure and sets the active receiver/operator set for that body.

Example:

    L4
      operator
        if
        callableFrom = L5
        implementation l5_if
      end operator
    end L4

Semantic normal form:

    L4(
      operator(
        if,
        callableFrom = L5,
        implementation(l5_if)
      )
    )

The receiver `L4` consumes its body as model and registry input.


2. Value Ontology

The minimal core has two classes of values:

    1. primitive/scalar/reference/handle values
    2. Structure / Frame values

Primitive/scalar/reference/handle values include numbers, booleans, atoms, symbols, enum-like values, handles, references, pointers and L2-level callable references.

All non-primitive values are Structures or handles/references to Structures. This includes arrays, text, objects, call frames, bodies, configurations, expressions and model fragments.

A Structure can contain fields. A field can be positional, named or derived during normalization from a receiver signature.

At L3 and above, Structures are normally passed by reference/handle. They are not copied by value at every call unless a receiver explicitly defines copy semantics.

At L2, Structures may be lowered to pointers, handles, layout structures or primitive representations.

There is no fundamental keyword `Struct` in the minimal source syntax.


3. Structures and Frames

3.1. Structure

A Structure is a value containing an ordered set of fields. Fields may have names. Field order is part of the logical structure and may become part of layout or signature semantics.

A Structure may contain nested Structures. Tree-shaped data is represented as nested Structures.

3.2. Frame

A Frame is a Structure with a receiver/callee name and an argument Structure.

Example source:

    f(a, b, c)

Generic logical form:

    Frame(
      name = f,
      args = (
        field0 = a,
        field1 = b,
        field2 = c
      )
    )

In ordinary prose this document may write `f(a, b, c)` as a Structure or Frame. The exact internal representation is implementation-defined as long as receiver semantics are preserved.

3.3. Structures Do Not Execute Themselves

A Structure is data. It may describe code, a call, a model, an expression, a relation, a query or a configuration. It does not execute merely by existing.

Execution starts only through explicit receiver/subroutine consumption, for example:

    compileCallFrame(frame)
    evalExpression(expr)
    call(subRef, args)
    registerOperator(frame)
    query(relationFrame)

A callable reference is also data until explicitly called or consumed by a receiver that calls it.


4. Surface Forms and Normalization

4.1. Compact Call Form

Compact call form:

    f(a, b, c)

It creates a Frame named `f` with one logical argument Structure containing three positional fields.

Normal form:

    f(
      field0 = a,
      field1 = b,
      field2 = c
    )

4.2. Line Command Form

Line command form:

    f a b c

It creates the same logical Frame as:

    f(a, b, c)

A newline terminates the line command unless the parser is inside a parenthesized Structure or another explicitly open form.

Line command form does not infer hidden nesting.

Critical rule:

    print getTypedValue values[i]

normalizes as:

    print(getTypedValue, values[i])

It does not normalize as:

    print(getTypedValue(values[i]))

Explicit nesting must be written with parentheses or vertical structure.

4.3. Vertical Frame Form

Vertical frame form:

    f
      a
      b
      c
    end f

It creates a Frame named `f` with the same logical argument Structure as:

    f(a, b, c)

The explicit closing marker must be valid for the currently open vertical Structure. Closing validation is defined in section 7.5.

4.4. Parenthesized Bounded Structure

Parentheses create a bounded Structure:

    (a, b, c)

Inside parentheses, arguments are separated by comma or by the matching closing parenthesis.

Line command form inside parentheses continues until a comma or the matching closing parenthesis.

Example:

    if( i == 1, print choose hello, print choose world )

Logical argument sections:

    condition = <expression Structure for `i == 1`>
    then      = (print(choose, hello))
    else      = (print(choose, world))

The names `condition`, `then` and `else` are not created by the parser alone. They are assigned by receiver-signature normalization for the active `if` receiver. The internal layout of the expression Structure is outside this structural-core document.

4.5. Indentation Structures

An indented block after a line opens a vertical Structure. A newline at the same indentation level separates elements of the current Structure. A dedent closes the current indentation Structure.

Explicit `end` forms remain preferred for readable named vertical frames because they allow the parser, translator and formatter to verify intended closure.

4.6. Structural Separator `---`

A standalone line:

    ---

is a structural separator/closer. It is not a receiver, not an operator and not a runtime action.

Inside a vertical frame, `---` closes the current expanded structural section at the current level and moves normalization to the next section according to the active receiver/subroutine signature.

Example:

    if mode == debug
      build debugTarget
    ---
      build releaseTarget
    end if

If the active `if` signature is:

    if(condition, then, else)

then the normal form is:

    if(
      condition = <expression Structure for `mode == debug`>,
      then = (
        build(debugTarget)
      ),
      else = (
        build(releaseTarget)
      )
    )

The fields `then` and `else` contain branch Structures.

A trailing `---` before an `end` form is allowed as an analogue of a trailing comma. It closes the last current section and does not create a new empty section.

Repeated `---` may close several nested sections if the receiver signature and current nesting state make the closure unambiguous. Canonical readable source uses explicit `end` forms for named frames.

4.7. Named Fields

A named field has the form:

    name = value

It creates a field named `name` inside the current argument Structure.

The value of a named field may be primitive, reference/handle or Structure.

Example:

    then = (
      build debugTarget
    )

This means that the field `then` contains a Structure.

4.8. Positional and Named Fields

A Structure may contain positional fields and named fields.

After the first named field in the same argument Structure, additional positional fields are not allowed.

Valid form:

    f(a, b, c = c1, d = d1)

Invalid form:

    f(a, b = b1, c)

This restriction prevents unstable binding between positional order and named-field mapping.

4.9. Field Order

Field order is part of the logical Structure. When a receiver supports positional arguments, positional fields are mapped to receiver signature fields in order.

Named fields are mapped by name. A receiver may reject a Structure that contains unknown fields, missing required fields or incompatible field ordering.


5. Receiver-Based Semantics

5.1. Core Rule

Surface syntax builds Structures. Receivers and subroutines give those Structures meaning.

Semantic formula:

    surface syntax -> generic Structure -> receiver/subroutine -> typed semantic structure

A receiver has a signature. The signature defines how positional fields, named fields, `---` sections, expression fields and body fields are interpreted.

5.2. Receiver Consumption Modes

A receiver may consume a field as one of the following semantic modes:

    primitive value
    expression
    body Structure
    declaration
    model fragment
    configuration message
    data Structure
    delayed branch
    relation frame
    query frame

The mode is receiver-defined. The parser does not decide that a field is executable merely because it looks like code.

5.3. Example: `if`

For a computational L3 `if`, the receiver may define fields:

    condition
    then
    else

and consume them as:

    condition -> boolean-producing expression
    then      -> body Structure
    else      -> body Structure

During translation, the receiver lowers these fields into target control flow. During interpretation, the receiver evaluates the condition and then interprets only the selected body.

5.4. Example: `fn`

For an `fn` definition receiver, fields may be consumed as:

    name -> function name
    args -> argument Structure
    ret  -> return Structure
    body -> function body Structure

The receiver creates or registers an executable definition. The `fn` frame itself is not a function call.

5.5. Same Shape, Different Receivers

The same surface shape can have different semantics under different receivers.

Example:

    (a, b)

As a function argument Structure, it may mean two positional arguments.

As a return layout Structure, it may mean two return fields.

As a model fragment, it may mean a structural model.

As query input, it may mean a tuple of terms.

The receiver defines the interpretation.


6. Mathematical Expression Parser

6.1. Two Syntax Modes in One Parser

Lingvamyxa has one parsing system with two syntax modes:

    native structural syntax
    mathematical expression syntax

Native structural syntax builds ordinary receiver Frames and bounded Structures.

Mathematical expression syntax is entered when the parser detects mathematical expression indicators in an argument position. Indicators include explicit numeric literals and mathematical/operator tokens such as:

    ==
    !=
    <
    >
    <=
    >=
    +
    -
    *
    /

The parser does not need to reinterpret forms such as `i == 1` as ordinary Lingvamyxa receiver syntax first. It detects the mathematical operator token and parses the expression with the expression rules.

6.2. Expression Output

The mathematical syntax returns an expression Structure. This expression Structure is a tree-shaped Structure made of nested Structures.

Example source:

    i == 1

The parser detects this as mathematical syntax because of the `==` token. The exact internal expression-tree layout is not specified in this document. It belongs to the separate mathematical-syntax specification.

The native structural syntax described by this document is not the canonical representation of mathematical expressions. A form such as a receiver call with the name `==` is not defined here as the canonical expression output. It may be omitted entirely from the native receiver set if that makes lexical separation between native syntax and mathematical syntax simpler.

The important semantic rule is that mathematical syntax produces an expression Structure, not a separate fundamental AST type and not an ordinary runtime action.

The expression Structure is consumed later by a receiver that expects an expression, for example the `condition` field of `if`.

?
The mathematical expression syntax is specified separately. It must define operator tokens, precedence, grouping rules, expression Structure layout and translation rules. It may borrow an established mathematical/operator-precedence convention instead of inventing a full new expression language.
?

variant 1:
Use a compact C-like precedence table for arithmetic, comparison and boolean operators.

variant 2:
Use a minimal mathematical table that includes only numeric literals, grouping and explicitly listed mathematical operators.

variant 3:
Use a profile-based expression grammar selected by level, module or build configuration.

---ANSI C---
A translator may lower expression Structures to ANSI C expressions when precedence, evaluation order and side effects are fully known. Otherwise it may lower them to helper calls, temporary Structures or generated evaluator code.
---ANSI C---

6.3. Expressions Are Data Before Consumption

An expression Structure is data until a receiver consumes it as an expression.

For example, the `if` receiver consumes its `condition` field as an expression. A configuration receiver might instead store the same Structure as data.


7. `fn`, `sub` and Structural Closure

7.1. `fn` and `sub` Are Receivers

`fn` and `sub` are definition receivers. Each consumes a Structure and registers an executable definition. During bootstrap they may be present in an L1 prelude table or parser switch.

An `fn` frame consumes a Structure and registers or creates a function definition.

A `sub` frame consumes a Structure and registers or creates a subroutine definition.

7.2. Function Definition Form

Example source:

    fn myFunc (int i, int j = 1, p1, p2) (int r1, int r2)
      print i
      print j
      p1
      p2
    end fn

Strict normal form:

    fn(
      name = myFunc,
      args = (
        int(i),
        int(j = 1),
        p1,
        p2
      ),
      ret = (
        int(r1),
        int(r2)
      ),
      body = (
        print(i),
        print(j),
        p1,
        p2
      )
    )

Equivalent named-field form:

    fn name = myFunc args = (int i, int j = 1, p1, p2) ret = (int r1, int r2)
      print i
      print j
      p1
      p2
    end myFunc

Equivalent reordered named-field form:

    fn args = (int i, int j = 1, p1, p2) name = myFunc ret = (int r1, int r2)
      print i
      print j
      p1
      p2
    end myFunc

The receiver `fn` consumes named fields by name after normalization. Therefore the relative source order of explicitly named fields such as `name`, `args`, `ret` and `body` is not semantically significant unless the `fn` receiver explicitly defines an order-dependent convention.

The names `int`, `boolean` and similar names are primitive/type-constructor receivers when registered in the active receiver set.

7.3. Subroutine Definition Form

Example source:

    sub l5_if (boolean condition) then else
      ...
    end sub

Strict normal form:

    sub(
      name = l5_if,
      args = (
        boolean(condition),
        then,
        else
      ),
      body = (...)
    )

Equivalent named-field form:

    sub name = l5_if args = (boolean condition, then, else)
      ...
    end l5_if

Equivalent reordered named-field form:

    sub args = (boolean condition, then, else) name = l5_if
      ...
    end l5_if

The receiver `sub` consumes named fields by name after normalization. Therefore the relative source order of explicitly named fields such as `name`, `args` and `body` is not semantically significant unless the `sub` receiver explicitly defines an order-dependent convention.

The argument `condition` is a primitive/evaluated argument through the registered constructor `boolean`. The bare names `then` and `else` are structural arguments. No `Struct then` annotation is required.

7.4. Body Names

Variables or names used inside an `fn` or `sub` body do not become arguments automatically. Arguments are defined only by the argument Structure consumed by the definition receiver.

7.5. `end` as General Closing Syntax

`end` is a syntactic closing element. It is analogous to a closing parenthesis for vertical Structures. It has no runtime-return meaning by itself.

The parser recognizes these structural closing and separator forms:

    end
    ---
    end <node-name>
    end <arg0-name>

The forms:

    end
    ---

carry no explicit argument. `end` closes the current vertical Structure. `---` closes or separates the current structural section according to the current nesting state and receiver signature.

The form:

    end <node-name>

closes the current vertical Structure and validates the closing token against the current node/receiver name.

The form:

    end <arg0-name>

closes the current vertical Structure and validates the closing token against the normalized `name` field of the current Structure, if such a field exists. If no normalized `name` field exists, the closing policy may fall back to the first positional field when that field is a string-like name, atom or symbol.

Examples:

    if condition
      bodyCall
    end if

Here `if` validates against the node/receiver name.

    fn myFunc (int i) (int r)
      return i
    end fn

Here `fn` validates against the node/receiver name.

    fn myFunc (int i) (int r)
      return i
    end myFunc

Here `myFunc` validates against the normalized `name` field of the current `fn` Structure. In this form the normalized `name` field is derived from the first positional argument.

    fn name = myFunc args = (int i) ret = (int r)
      return i
    end myFunc

Here `myFunc` also validates against the normalized `name` field, but that field is written explicitly.

    fn args = (int i) name = myFunc ret = (int r)
      return i
    end myFunc

This is also valid because validation uses the normalized `name` field rather than the raw first source argument.

All four forms are valid structural surface forms. A style guide may prefer one form for readability, but the structural core allows all of them.

A translator may implement vertical closure by internal closing handlers. Those handlers are implementation mechanisms. Source semantics only requires that the correct Structure or section is closed and that invalid closing tokens are rejected according to the active closing policy.


8. Runtime Return

8.1. `return` Receiver

Runtime exit from an `fn` or method-like executable body is represented by the `return` receiver/operator.

`return` is not the same as `end`. `end` closes source structure. `return` exits the current executable body.

During bootstrap and lowering, `return` may be implemented as an L1/L2 parser/translator subroutine that receives an argument Structure.

8.2. Return Forms

Return without explicit values:

    return

Return with positional values:

    return(bed.area, 0, 0)

Line-command form:

    return bed.area 0 0

Return with named values:

    return(harvest = bed.area, redApples = 0, greenApples = 0)

All forms build or imply a return argument Structure consumed by the active executable-body receiver.

8.3. Named Return Variables

Return values are ordinary declared return variables inside the executable body when the return signature gives them names.

Example:

    fn estimateHarvest (PlantBed bed) (f32 harvest, f32 redApples, f32 greenApples)
      harvest = bed.area
      redApples = 0
      greenApples = 0
      return
    end fn

The empty `return` returns the current values of the declared return variables.

A non-empty `return` fills the declared return variables before exiting.

Example:

    return(bed.area, 0, 0)

If the return signature is:

    (f32 harvest, f32 redApples, f32 greenApples)

then the positional return values fill:

    harvest
    redApples
    greenApples

If the return fields are unnamed, `return` can still fill them positionally before exiting.

8.4. Return Source Semantics

At the source-semantic level, a multi-value return is a return Structure.

A single primitive return returns one primitive value. A return signature with multiple fields returns a Structure. A return signature with one structural field returns that Structure or a handle/reference to it according to the language-level value model.

Multiple named return fields are ordinary declared return variables inside the executable body. An empty `return` returns their current values as the declared return Structure.

A non-empty `return` first fills the declared return fields positionally or by name and then exits the executable body.

Physical return strategy, storage ownership and low-level runtime representation are translator/runtime implementation details. They are not part of the source-semantic core.

The error mechanism is not specified by this document. A function may represent an erroneous result as one of the values allowed by its declared return type unless a later error-system specification defines a separate convention.

The general error/status system is not specified in this document. It may be defined later as ordinary return values, tagged result Structures, receiver-level diagnostics or another mechanism.

---ANSI C---
Possible return-lowering variants for an ANSI C implementation:

variant 1:
A single primitive source return lowers to a direct C primitive return.

variant 2:
A multi-field source return lowers to a caller-provided output Structure passed through a hidden or explicit implementation-level pointer.

variant 3:
A small return Structure lowers to a C struct returned by value if the translator/runtime profile allows it.

variant 4:
A structural return lowers to a handle/pointer allocated or managed by a runtime arena, heap, region or other implementation-owned storage.

These variants are implementation strategies only. The language-level rule remains that `return` returns the declared primitive value or return Structure.
---ANSI C---


9. Type and Model Forms

9.1. Type and Model Information

Type and model information is expressed by registered receivers and Structures.

Example receiver-level form:

    model Harvest
      field harvest f32
      field redApples f32
      field greenApples f32
    end model

The parser only builds Structures. The active model receiver defines what `model`, `field`, type names and constraints mean.

9.2. Type Constructors

A form such as:

    int i

or:

    PlantBed bed

is meaningful only if `int` or `PlantBed` is a registered primitive/type/model constructor receiver in the active level.

Possible normal form:

    int(i)
    PlantBed(bed)

A receiver such as `fn` may consume these Structures as typed argument declarations.

9.3. Model Definitions

A model definition is a Structure consumed by a model receiver.

Possible form:

    model PlantBed
      field id u32
      field crop Text
      field area f64
      field soilWater f64
      field harvest f64 default = 0.0
      where area > 0.0
      where soilWater >= 0.0
      where soilWater <= 100.0
    end model

Conceptual structural form:

    model(
      PlantBed,
      field(id, u32),
      field(crop, Text),
      field(area, f64),
      field(soilWater, f64),
      field(harvest, f64, default = 0.0),
      where(<expression Structure for `area > 0.0`>),
      where(<expression Structure for `soilWater >= 0.0`>),
      where(<expression Structure for `soilWater <= 100.0`>)
    )

This section does not define a final type language. It only states that model declarations are ordinary Structures consumed by a model receiver. The receiver may interpret `field id u32` as a field named `id` with type `u32`, and `where area > 0.0` as a constraint expression.

?
The model/type declaration syntax is not specified in full in this document. A model/type specification must define canonical model/type receiver forms, field declaration forms, default-value forms, constraint forms, aliases, layouts and relation signatures.
?

variant 1:
Use explicit receiver forms such as `model`, `field`, `where`, `default` and `layout`.

variant 2:
Use compact structural declarations where field declarations are ordinary constructor Structures.

variant 3:
Use L4 registry tables as the primary model syntax and treat source declarations as table-construction sugar.


10. Objects, Configuration and Messages

10.1. Objects as Structures

An object is a Structure or a handle/reference to a Structure. Object declarations, object instances, configuration records and messages are receiver-defined Structures.

10.2. L5 Configuration Example

Example:

    L5
      NorthGreenhouse
        controller = GreenhouseController
        config
          batchSize = 500
          reportMode = Daily
        end config
      end NorthGreenhouse
    end L5

Generic structure:

    L5(
      NorthGreenhouse(
        controller = GreenhouseController,
        config(
          batchSize = 500,
          reportMode = Daily
        )
      )
    )

Whether `NorthGreenhouse` is an object definition, an object instance, a message target or a configuration name depends on the L5 receiver registry.


11. Operators and Receiver Registration

11.1. Operator as Receiver Registration

`operator` is a receiver used during bootstrap or model loading. It registers receiver names, visibility levels and implementations.

Example:

    L4
      operator
        while
        callableFrom = L3
        implementation
          while_func
          level = L2
        end implementation
      end operator
    end L4

Semantic meaning:

    Register a receiver/operator named `while`.
    Make it callable from L3.
    Use implementation `while_func`.
    Treat that implementation as L2-level implementation.

The `operator` frame is not the runtime/control operation being registered.

11.2. Runtime Use of Registered Operators

After registration, runtime/control source may contain:

    L3
      while i < beds.len
        print beds[i].crop
        i = i + 1
      end while
    end L3

Here `while` is the opened frame and therefore may close as `end while`.

The active L3 `while` receiver consumes its argument Structure according to its registered signature, typically as:

    condition -> expression
    body      -> body Structure

11.3. Multiple Level-Specific Implementations

The same surface receiver name may have different implementations at different levels.

Example registrations may define:

    if callable from L3 -> l3_if
    if callable from L4 -> l4_model_if
    if callable from L5 -> l5_if

The active level determines which receiver implementation consumes the Structure.


12. Conditional Structures

12.1. L3 `if`

L3 `if` is a computational control-flow receiver. It consumes:

    condition -> boolean-producing expression
    then      -> executable body Structure
    else      -> executable body Structure

At interpretation time, only the selected body is interpreted.

At translation time, the receiver lowers the condition and body Structures into target control flow.

12.2. L4 `if`

L4 `if` is a model-conditional receiver. It does not execute runtime effects. It may conditionally include, exclude or normalize model Structures, registry entries and constraints.

12.3. L5 `if`

L5 `if` is a message/configuration dispatch receiver. It may conditionally dispatch build, run, query, startup or configuration messages.

12.4. Canonical Vertical Conditional Form

Canonical readable form:

    if mode == debug
      build debugTarget
    ---
      build releaseTarget
    end if

Normal form under signature `if(condition, then, else)`:

    if(
      condition = <expression Structure for `mode == debug`>,
      then = (build(debugTarget)),
      else = (build(releaseTarget))
    )


13. Pointers, References and Callable References

13.1. L3 Passing Model

At L3 and above, explicit pointer syntax is usually unnecessary. Structures, arrays, text, objects and other non-primitive values are passed as references or handles by default.

At L3 and above, ordinary names denote primitives, symbols, handles or Structures according to the active semantic environment. They are not raw function pointers.

13.2. L2 Pointer Constructor

At L2, `^` may be a low-level pointer/reference constructor.

Examples:

    ^p
    ^ PlantBed bed

Possible meanings:

    ^p              untyped reference / void* / pointer to structure
    ^ PlantBed bed  typed pointer/reference if the type model is known

The name `^` may be handled as a parser-level constructor or as a primitive L2 receiver during bootstrap.

13.3. Fn and Sub References

Function/subroutine reference operators are strictly L2 operators.

At L2, reference forms such as `&` and `*` may be used for address-taking and callable-reference construction if they are defined by the L2 operator set.

At L3 and above, names are references to Structures, handles or primitive values. Calls are expressed as receiver Frames and resolved by the active receiver/operator registry, not by raw callable pointers.

?
The exact L2 forms for `^`, `&` and `*` are specified by the L2 memory and callable-reference specification. The structural core only states that raw pointer/address/callable-reference syntax belongs to L2, not to the general high-level source model.
?

variant 1:
Treat `^`, `&` and `*` as built-in L2 parser forms.

variant 2:
Treat them as bootstrap-registered L2 operators with parser support only for tokenization and precedence.

variant 3:
Allow both forms: parser-level recognition for core operators and receiver-level extension for specialized memory models.


14. Arrays, Text and Indexing

14.1. Logical Model

At L3 and above, an array is a Structure or handle/reference to a Structure. Text is also a Structure or handle/reference to a Structure.

The logical array model includes at least a length field and an indirect storage reference. It may also include capacity, encoding, element type and storage handle.

14.2. L2 Lowering

At L2, arrays and text may lower to pointers, length-plus-pointer records or other layout-specific representations.

Example conceptual lowering for an array:

    (len, ptr)

Lowering does not change source semantics.

14.3. Indexing

The mathematical expression parser is specified separately. Indexing is treated as a level-dependent operator/form.

At L2, `[]` is a low-level operator, similar in status to `=`. It uses a computed address and is governed by the L2 memory model.

Example conceptual L2 meaning:

    beds[i] -> element at computed address

subject to the actual L2 layout and pointer rules.

At L3 and above, `[]` accesses an array Structure indirectly and performs bounds checking through the array metadata, at minimum the `len` field.

Example conceptual L3 meaning:

    beds[i] -> index(beds, i)

where `index` receives the array Structure or handle, checks `0 <= i < beds.len`, and returns the element or reports a bounds error.

?
The final array/text specification must define exact index result semantics, slicing, negative indexes if any, multidimensional arrays, text encoding and the boundary between parser form and receiver/operator form.
?

---ANSI C---
Possible array-lowering variants:

variant 1:
L2 array access lowers to computed-address access with no automatic bounds check.

variant 2:
L3+ array access lowers to a length-plus-pointer or length-plus-handle Structure with generated bounds checks.

variant 3:
Dynamic arrays lower to runtime handles with accessor calls when layout is not statically known.
---ANSI C---


15. Field Access

15.1. Dot Form

Named field access uses dotted syntax:

    result.harvest

The dot form is a built-in parser form. It exists so the translator can generate direct field access through known Structures and layouts.

Possible normal form:

    field(result, harvest)

or an internal field-access expression Structure equivalent to it.

15.2. Lowering

If the model/layout of `result` is known, the translator may lower:

    result.harvest

into direct structure access, pointer access or generated accessor code.

If the model/layout is dynamic, the receiver/runtime may perform a checked lookup.

!!!
Field-access failure semantics are not fixed. A final source-semantic rule must define behavior for missing fields, unknown models, dynamic Structures and nullable handles, including whether such cases are compile-time errors, runtime errors or receiver-defined diagnostics.
!!!

---ANSI C---
Possible field-access lowering variants:

variant 1:
Known static layouts lower to direct C struct-field access.

variant 2:
Known pointer layouts lower to direct pointer-field access.

variant 3:
Dynamic Structures lower to checked runtime lookup or generated accessor calls.
---ANSI C---


16. Assignment, Return Structures and Destructuring

16.1. Assignment

Assignment syntax has the form:

    target = value

At L2, `=` may lower to direct storage assignment according to the L2 memory model.

At L3 and above, assignment is receiver/operator-defined over variables, fields, handles and Structures.

?
Assignment, binding, mutability, scope, initialization and reassignment rules are not specified in full in this document. They require a dedicated execution-model specification.
?

16.2. Return Structures

A function may return a Structure with ordered and/or named fields.

Example return signature:

    (f32 harvest, f32 redApples, f32 greenApples)

A return expression may fill this Structure by position:

    return(bed.area, 0, 0)

or by name:

    return(harvest = bed.area, redApples = 0, greenApples = 0)

16.3. Destructuring

Destructuring has the form:

    harvest, redApples, greenApples = toEat(myFilter, Monday)

If the produced value is a Structure with fields named `harvest`, `redApples` and `greenApples`, the semantic meaning is name-based:

    tmp = toEat(myFilter, Monday)
    harvest = tmp.harvest
    redApples = tmp.redApples
    greenApples = tmp.greenApples

The same rule applies when the right-hand side explicitly produces a Structure rather than a named function result. The destructuring target receives fields from the produced Structure.

If the produced Structure has no field names, destructuring may use positional mapping:

    harvest = tmp.field0
    redApples = tmp.field1
    greenApples = tmp.field2

If the produced Structure has field names and a left-hand variable name does not match any field, the assignment is invalid unless an explicit receiver-defined positional destructuring form is used.

---ANSI C---
A translator may implement destructuring by assigning the produced Structure or handle to a temporary service variable and then generating field assignments one by one.

variant 1:
For known static layouts, generated code reads fields directly from the temporary Structure.

variant 2:
For handle-based Structures, generated code reads fields through generated accessors or runtime lookup.

variant 3:
For unnamed Structures, generated code reads fields by fixed positional offsets.
---ANSI C---


17. L4 Non-Executive Semantics

L4 consumes Structures as model/type/contract/registry input. It may:

    register models
    register relation signatures
    check contracts
    normalize schemas
    derive layouts
    derive validators
    update the internal compiler/runtime model
    prepare compilation or self-compilation metadata

L4 does not directly perform ordinary runtime effects by default.

Runtime effect receivers such as file I/O, network send, process launch, database write, ordinary runtime print and thread start are not visible from L4 unless a special compile-time diagnostic or model receiver explicitly exposes a non-runtime effect.

A diagnostic receiver visible from L4 is not the same as L3 runtime `print`.


18. L5 Message and Build Semantics

18.1. L5 Input

An L5 file is a file containing L5 messages and configuration Structures. It is not a special `project` file unless a project receiver is explicitly registered.

The builder may be given a `.lm5`, `.lm3`, `.lmx` or other Lingvamyxa source file. It handles the top-level Structures through active receivers.

18.2. Target Example

Possible L5 build input:

    L5
      target
        app
        kind = executable
        sources = ("src/hello.lm3")
        entry = hello
        output = "build/bin/hello.lm0.exe"
      end target

      build app
    end L5

The `target` and `build` receivers define the build semantics. The core only creates Structures.

18.3. Entry Resolution

The builder either finds an entry/target through receivers, messages and signatures, or reports:

    no entry point

An executable entry wrapper is created from build/target/entry information or from an implicit L3 top-level entry. It is not derived from a source file name.

The symbol `main` may be a conventional entry symbol, but it is not a required startup-file convention.


19. Compilation and Lowering

19.1. Compilation Pipeline

Compilation means:

    Lingvamyxa source
        -> Structures
        -> semantic receiver handling
        -> L1 projection or another implementation target
        -> L0 artifact

This document specifies only the source-semantic side of that pipeline. The exact L1 syntax, L1 file format, L1 compiler interface and L0 build mechanism are outside this document.

---ANSI C---
An ANSI C based translator may use the following implementation pipeline:

    Lingvamyxa source
        -> Structures
        -> semantic receiver handling
        -> generated ANSI C projection
        -> platform C compiler/linker
        -> L0 artifact

Generated/debuggable C projections may preserve source mapping with `#line` directives, comments or a separate source-map file. This is a translator feature, not source syntax.
---ANSI C---

19.2. Source File Extensions

Lingvamyxa source files may use:

    *.lm2    L2-only source
    *.lm3    L3-only source
    *.lm4    L4-only source
    *.lm5    L5-only source
    *.lmx    mixed Lingvamyxa source

Generated/debuggable projections may exist for translator diagnostics and verification. Their exact format and file extensions are implementation-defined.

A debug build may preserve source mapping through an implementation-defined source-map mechanism.

19.3. Per-Level Build Semantics

L2 sources are unsafe modules/libraries/objects. They are compiled, not interpreted as scripts.

L3 sources may be interpreted or compiled. A top-level L3 sequence may become an implicit executable entry.

L4 sources are checked, loaded and registered as model/contract/registry input. They are not launched as programs.

L5 sources are message/configuration/build/startup/query inputs consumed by L5 receivers.

Mixed `.lmx` sources are handled according to level receivers and entry rules. L5 entry messages take precedence if present; otherwise an L3 top-level sequence may become an implicit entry if the builder allows it.


20. Source Semantics and Implementation Lowering

20.1. Logical Argument Structure

Every source call has one logical argument Structure.

Example:

    mySub(1, 2, 3, 4)

Logical source semantics:

    mySub(
      field0 = 1,
      field1 = 2,
      field2 = 3,
      field3 = 4
    )

20.2. Physical Optimization

The logical Structure always exists at the source-semantic level. A translator may optimize away the physical Structure if the observable source semantics are preserved.

This means that the source call:

    f(a, b, c)

is always semantically treated as a call with one argument Structure containing `a`, `b` and `c`.

A concrete translator may pass fields directly, use a handle, use a temporary Structure, inline the call, specialize adapters or apply any other physical strategy. These choices do not change the Lingvamyxa source semantics.

20.3. Return Lowering Independence

The same rule applies to returns. A return signature defines a source-level return value: either a primitive value or a return Structure. The translator may choose any physical return strategy that preserves this source-level result.

The Lingvamyxa source-semantic core does not define physical calling conventions or storage strategies.

---ANSI C---
Possible internal call-lowering variants for an ANSI C implementation:

variant 1:
Pass up to three primitive/reference source fields directly to an internal generated C function. References and handles may be treated as primitive scalar values for this implementation convention.

variant 2:
If more logical fields exist, generate an args Structure and pass a pointer/handle to it.

variant 3:
Generate specialized adapters for concrete call sites, including direct calls, temporary args Structures, inlining or whole-program specialization.

Possible exported ABI variant:

    LmStatus f(LmRuntime *rt, const F_Args *in, F_Ret *out)

This shape is only an implementation option. The language does not know about `LmRuntime`, C function signatures, hidden arguments or slot counting.
---ANSI C---


21. Facts, Rules, Relations and Query

21.1. Relation Mode

Relational mode is a receiver-based semantic mode over Structures. It does not introduce a separate Prolog-like syntax.

A relation frame describes a proposition shape.

Example:

    parent(Astra, NyufNyuf)

As generic Structure:

    parent(Astra, NyufNyuf)

As a fact assertion only when consumed by `fact`:

    fact(parent(Astra, NyufNyuf))

As a query only when consumed by `query`:

    query(parent(Astra, ?who))

21.2. Recommended Level Placement

Recommended placement:

    L4 -> relation signatures, term types, contracts
    L5 -> relation registries, knowledge bases, facts, rules, query messages
    L3 -> ordinary code calls query/solve and consumes results
    L2 -> indexing, unification, search, backtracking, caches

21.3. Facts

Facts may accumulate faster than source modules. Persistent fact storage should be separate from source files.

Recommended division:

    rules/signatures/contracts -> .lm4 / .lm5 / .lmx modules
    accumulating facts         -> persistent store or database backend
    query/relation engine      -> receiver layer over Structures and storage backend

SQLite may be used as a backend, but it is not part of the core syntax.

21.4. Unknowns

A query may contain unknowns such as:

    ?who
    ?x
    ?y

Example:

    query(parent(Astra, ?who))

Meaning:

    find bindings for ?who such that parent(Astra, ?who) is true

Unknowns are not ordinary uninitialized variables. They are logical variables interpreted by relational receivers.

21.5. Rules

A rule defines a relation in terms of other relations.

Example:

    rule(
      ancestor(?x, ?y),
      if(parent(?x, ?y))
    )

Recursive example:

    rule(
      ancestor(?x, ?y),
      if(parent(?x, ?z), ancestor(?z, ?y))
    )

The `rule` receiver registers a logical rule. The inner relation Structures do not execute themselves.

21.6. Unification

Relational search is based on unification. Unification attempts to make two relation Structures compatible by assigning unknowns.

It respects:

    relation name
    argument count
    positional order
    named fields when used
    L4 relation signatures
    contracts and constraints when attached

21.7. Query Result

A query returns a Structure, for example:

    QueryResult(
      bindings = [
        (?who = NyufNyuf)
      ],
      status = success,
      confidence = 1.0
    )

?
The exact syntax and core status of `?name` logical variables, list literals and query result Structures belong to the relation/query specification. That specification must define these forms or map them to registered receivers.
?


22. Structural Grammar Sketch

This grammar sketch describes the structural parser only. It does not define final receiver semantics.

    program             ::= { item }

    item                ::= empty_line
                          | comment_line
                          | line_frame
                          | vertical_frame
                          | expr_line

    compact_frame       ::= name "(" [ argument_list ] ")"

    line_frame          ::= name [ line_arguments ] newline

    vertical_frame      ::= name [ line_arguments ] newline indent
                              { vertical_item }
                            dedent end_form newline

    vertical_item       ::= item
                          | separator_line

    end_form            ::= "end" [ name ]

    separator_line      ::= "---" newline

    argument_list       ::= argument { "," argument } [ "," ]

    argument            ::= named_field
                          | expression_or_structure

    named_field         ::= name "=" expression_or_structure

    bounded_structure   ::= "(" [ argument_list ] ")"

    expression_or_structure
                         ::= mathematical_expression
                          | compact_frame
                          | bounded_structure
                          | atom_or_value

    mathematical_expression
                         ::= parsed by the mathematical expression syntax

This grammar is intentionally incomplete around full assignment, full indexing, full field access, type constructors, literals and relation forms because those areas require final design decisions.


23. Canonical Examples

23.1. Hello World

Source:

    L3
      print Hello World
    end L3

Normal form:

    L3(
      print(Hello, World)
    )

`Hello` and `World` are accepted only if the active L3 `print` receiver and lexical rules allow bare atoms/symbols in that position.

23.2. Function with Structural Return

Source:

    fn estimateHarvest (PlantBed bed) (f32 harvest, f32 redApples, f32 greenApples)
      if bed.crop == Apples
        return(bed.area * 1.7, bed.area * 1.7, bed.area * 1.1)
      end if

      return(bed.area, 0, 0)
    end fn

Semantic outline:

    `fn` consumes a definition Structure.
    `PlantBed bed` is a typed/model constructor Structure if `PlantBed` is registered.
    The return Structure has three named fields.
    `if` consumes condition and body Structures.
    `return(...)` fills the return Structure and exits the current function.
    `end fn` closes the definition Structure.

23.3. Empty Return with Named Return Variables

Source:

    fn estimateHarvest (PlantBed bed) (f32 harvest, f32 redApples, f32 greenApples)
      harvest = bed.area
      redApples = 0
      greenApples = 0
      return
    end fn

Semantic outline:

    Named return fields are local return variables.
    Empty `return` returns their current values.

23.4. L5 Conditional Build

Source:

    L5
      if mode == debug
        build debugTarget
      ---
        build releaseTarget
      end if
    end L5

Normal form:

    L5(
      if(
        condition = <expression Structure for `mode == debug`>,
        then = (build(debugTarget)),
        else = (build(releaseTarget))
      )
    )

23.5. Operator Registration

Source:

    L4
      operator
        if
        callableFrom = L5
        implementation l5_if
      end operator
    end L4

Semantic outline:

    `L4` consumes the body as model/registry input.
    `operator` registers the receiver name `if`.
    `callableFrom = L5` sets visibility.
    `implementation l5_if` names the implementation receiver/subroutine.

23.6. L5-if Implementation Subroutine

Source:

    sub l5_if (boolean condition) then else
      ...
    end sub

Normal form:

    sub(
      name = l5_if,
      args = (
        boolean(condition),
        then,
        else
      ),
      body = (...)
    )


24. Summary Table

    f(a, b)                    compact Frame named f
    f a b                      line command Frame named f
    f ... end f                vertical Frame named f
    (a, b)                     bounded Structure
    name = value               named field in current Structure
    ---                        structural section separator/closer
    end                        close current vertical Structure
    end name                   close current vertical Structure with validation token
    L2/L3/L4/L5                level receiver frames
    sub                        receiver that registers subroutine definitions
    fn                         receiver that registers function definitions
    return                     executable-body return receiver/operator
    operator                   receiver that registers receivers/operators
    if                         registered receiver, semantics depend on level
    while                      registered receiver, semantics depend on level
    mathematical infix         parsed into expression Structure
    []                         L2 address operator; L3+ checked array-Structure access
    .                          built-in parser form for field access
    ^ & *                      L2 pointer/address/callable-reference operators
    relation/fact/rule/query   receiver-defined relational Structures

Core invariant:

    syntax builds Structures;
    receivers give Structures meaning;
    Structures do not execute themselves;
    return exits executable bodies;
    end closes source Structures.


25. Consolidated Open Points

25.1. Source-Semantic or Syntax Uncertainties

!!!
Field-access failure semantics are not fixed. A final source-semantic rule must define behavior for missing fields, unknown models, dynamic Structures and nullable handles, including whether these cases are compile-time errors, runtime errors or receiver-defined diagnostics.
!!!

25.2. External or Undescribed Specification Areas

?
Mathematical expression syntax is not specified in this document. It must define operator tokens, precedence, grouping, expression Structure layout and translation rules. The native structural syntax is not the canonical representation of mathematical expressions.
?

variant 1:
Borrow a compact C-like mathematical precedence table.

variant 2:
Define a smaller numeric-only expression grammar for the first implementation.

variant 3:
Allow profiles so the active level or module can select a mathematical grammar.

?
Model/type syntax is not specified in full. It must define model receivers, field declarations, defaults, constraints, aliases, layouts and relation signatures.
?

?
The L2 memory/operator specification must define exact syntax and semantics for `^`, `&`, `*`, low-level assignment and raw indexing.
?

?
The array/text specification must define indexing, slicing, bounds errors, multidimensional arrays, text encoding and dynamic storage behavior.
?

?
The execution-model specification must define assignment, binding, mutability, scope, initialization and reassignment rules.
?

?
The relation/query specification must define `?name` logical variables, list literals, query result Structures, fact persistence, indexes, transactions and external database integration.
?

?
The general error/status system is not specified. Until specified, erroneous results may be represented as ordinary values allowed by the declared return type or by receiver-defined diagnostics.
?

25.3. ANSI C Implementation Variants

---ANSI C---
These variants are implementation notes for a possible ANSI C based translator. They are not part of Lingvamyxa source semantics.

Call lowering:

variant 1:
Pass a small number of primitive/reference fields directly in internal generated C functions.

variant 2:
Pass an args Structure pointer/handle when the logical argument Structure is large or dynamic.

variant 3:
Generate specialized adapters, inline calls or eliminate physical args Structures when observable source semantics are preserved.

Return lowering:

variant 1:
Return a single primitive as a direct C primitive value.

variant 2:
Return multi-field results through caller-provided output storage.

variant 3:
Return small Structures by value where the implementation profile allows it.

variant 4:
Return handles/pointers to runtime-managed Structures for dynamic or large results.

Destructuring lowering:

variant 1:
Store the returned Structure or handle in a temporary service variable and assign target variables from its fields.

variant 2:
For known layouts, generate direct field access.

variant 3:
For dynamic layouts, generate checked accessors or runtime lookup.

Field and array lowering:

variant 1:
Known field access lowers to direct C struct or pointer access.

variant 2:
L2 indexing lowers to computed-address access under the L2 memory model.

variant 3:
L3+ indexing lowers to checked access through array metadata such as `len`.

The language does not define C slot counting, hidden runtime pointers, hidden output pointers or C storage ownership rules. Those are translator/runtime design choices.
---ANSI C---
