Lingvamyxa v3 draft
Structural core reset

0. Статус документа

Это черновая перепись синтаксического ядра Lingvamyxa после решения радикально свести язык к структурам/frames.
Документ заменяет прежние места спецификации, где `proc`, `func`, `type`, `obj`, `L4:`, `:` или `Tree` трактовались как отдельные фундаментальные конструкции.

Новая формула:

    L0 binaries run.
    L1 ANSI C implements/bootstrap/targets.
    L2-L5 are Lingvamyxa levels.
    Source syntax builds Structures.
    Receivers/procedures consume Structures.
    Mathematics is a second built-in parser that returns Structures.
    Levels restrict the active receiver/operator set.

В минимальном ядре нет отдельного фундаментального Tree-типа: дерево — это структура, содержащая вложенные структуры.


1. Уровни

L0 — native binary artifact / machine code, то, что реально запускает CPU/OS.

L1 — ANSI/ISO C layer. Это переносимый bootstrap/target слой. На L1 пишутся первые процедуры парсера, транслятора, runtime и receiver-ы. L1-файлы Lingvamyxa-проекта могут иметь форму:

    *.lm1.c
    *.lm1.h

L2 — низкоуровневый unsafe-уровень Lingvamyxa. Он ближе всего к C: память, указатели, handles, структуры, явные низкоуровневые операции. L2 компилируется, а не исполняется как casual script.

L3 — алгоритмический/вычислительный уровень Lingvamyxa. Здесь допустимы безопасные top-level действия, вычисления, вызовы процедур, интерпретация ядром и/или компиляция.

L4 — non-executive уровень моделей, типов, протоколов, контрактов, ограничений и registry-описаний. L4 может обновлять/проверять внутреннюю модель компилятора/рантайма, но не выполняет runtime-действия.

L5 — уровень сообщений, конфигурации, объектов, build/run/query/startup receivers, регистрации операторов и высокоуровневого dispatch.

Важно: L2/L3/L4/L5 в source — не section keywords с двоеточием. Это receiver/procedure names, которые меняют активный набор допустимых receivers/operators для вложенной структуры.

Пример:

    L4
      operator
        if
        callableFrom = L5
        implementation l5_if
      end operator
    end L4


2. Онтология минимального ядра

В минимальном ядре есть только два рода значений:

    1. primitive/scalar/reference/handle values
    2. Structure / Frame values

К примитивам относятся числа, bool, atoms/symbols, enum-like values, ссылки/handles/указатели, references на процедуры/functions.

Всё непримитивное является Structure или ссылкой/handle на Structure. Массив на L3 — Structure. Текст на L3 — Structure/handle. Объект — Structure. Frame вызова — Structure. Body функции — Structure. Expression после математического парсера — Structure.

На L2 массив или структура могут lowering-иться в C pointer/primitive representation. На L3 это не требует отдельного surface-синтаксиса указателя.

Отдельного ключевого слова `Struct` в минимальном синтаксисе нет. Голое имя в сигнатуре может означать структурный аргумент, если оно не является primitive/type-constructor.


3. Структурный синтаксический парсер

Structural parser строит только Structures/Frames.

Базовые surface forms:

    f(a, b, c)
    f a b c

    f
      a
      b
      c
    end f

Все три формы являются разными записями структуры вызова `f` с аргументной Structure.

Семантически:

    myProc(1, 2, 3, 4)
    myProc 1 2 3 4

дают одну логическую аргументную структуру из четырёх полей:

    myProc(
      field0 = 1,
      field1 = 2,
      field2 = 3,
      field3 = 4
    )

Structure из одного поля остаётся Structure из одного поля. То, что при lowering она может быть передана как primitive/reference register argument, является ABI-оптимизацией, а не изменением source-семантики.


4. Разделители и границы структур

Круглые скобки создают ограниченную Structure:

    (a, b, c)

Внутри круглых скобок аргументы разделяются запятой или закрывающей скобкой.
Line-command form внутри круглых скобок продолжается до запятой или до соответствующей закрывающей скобки.

Пример:

    if( i==1, print choose hello, print choose world )

нормализуется как три аргумента `if`:

    condition = expr(==(i, 1))
    then      = (print(choose, hello))
    else      = (print(choose, world))

Отступ после строки открывает вертикальную Structure. Перевод строки на том же уровне отступа разделяет элементы текущей Structure. Уменьшение отступа закрывает текущую indentation-Structure.

`end name` остаётся явной закрывающей конструкцией для named vertical frame. Она предпочтительна для читаемости и проверки соответствия открывающего/закрывающего имени.


5. `---` как структурный separator/closer

Строка:

    ---

является синтаксическим structural separator/closer. Это не receiver, не operator и не runtime-действие.

Внутри vertical frame `---` закрывает текущую развернутую структурную секцию на данном уровне и переводит нормализатор к следующему аргументу/секции согласно сигнатуре активного receiver/procedure.

Пример:

    if mode == debug
      build debugTarget
    ---
      build releaseTarget
    end if

при сигнатуре:

    if(condition, then, else)

нормализуется в:

    if(
      condition = expr(==(mode, debug)),
      then = (
        build(debugTarget)
      ),
      else = (
        build(releaseTarget)
      )
    )

`then = (...)` и `else = (...)` — это именованные поля аргументной Structure. Это не вызовы процедур `then(...)` и `else(...)`.

Trailing `---` перед `end name` разрешён как аналог trailing comma: он закрывает последнюю текущую секцию и не создаёт пустую новую секцию.

При желании маленькая структура может быть закрыта только separators:

    if mode == debug
      build debugTarget
    ---
      build releaseTarget
    ---
    ---

Первый `---` закрывает then и открывает else. Второй закрывает else. Третий закрывает внешний `if`. Однако canonical readable форма для named frames — с `end if`.

Для `match` возможно:

    match value
      case 1
        print one
      ---
      case 2
        print two
      ---
      case default
        print other
      ---
    end match

Здесь `case` — обычная Structure. `---` закрывает текущую case-секцию и начинает следующую sibling-секцию.


6. Имена, поля и вызовы

Вызов/Frame:

    name(...)
    name arg1 arg2

создаёт Structure с именем `name`.

Именованное поле:

    name = value

создаёт поле `name` внутри текущей аргументной Structure.

Именованное поле может содержать primitive, reference/handle или Structure. Между “именованное поле” и “Structure” нет противопоставления.

Пример:

    then = (
      build debugTarget
    )

означает: поле `then` содержит Structure. Это не вызов `then`.

После первого именованного аргумента позиционные аргументы в той же argument Structure больше не допускаются:

    f(a, b, c = c1, d = d1)   valid
    f(a, b = b1, c)           error


7. Receivers, procedures и “операторы языка”

В минимальной модели “оператор языка” — это имя зарегистрированной procedure/receiver, обычно из L1 на bootstrap-этапе.

Парсер ядра не должен фундаментально знать смысл имён `func`, `proc`, `operator`, `L2`, `L3`, `L4`, `L5`, `int`, `boolean`, `^`, `if`, `while`.

На раннем bootstrap этапе L1 parser может иметь switch/встроенную таблицу для этих имён, но это bootstrap-реализация, не философия языка.

Receiver/procedure имеет сигнатуру аргументов. Вертикальные секции, `---`, позиционные поля и именованные поля нормализуются относительно этой сигнатуры.

Например implementation `l5_if` описывается как процедура с аргументами:

    condition
    then
    else

Тогда source:

    if mode == debug
      build debugTarget
    ---
      build releaseTarget
    end if

заполняет именно поля:

    condition = expr(==(mode, debug))
    then = (...)
    else = (...)

Отдельная “таблица форм” для `if` не нужна: достаточно зарегистрированной signature procedure/receiver. На практике эта signature может быть получена из L4-описания L1-procedure или из bootstrap metadata.


8. `func` и `proc`

`func` и `proc` не являются фундаментальными keywords. Это receiver/procedure names, которые получают Structure и создают/регистрируют executable definitions.

Пример функции:

    func myFunc (int i, int j = 1, p1, p2) (int r1, int r2)
      print i
      print j
      p1
      p2
    end func

Нормализация:

    func(
      name = myFunc,
      args = (
        int(i),
        int(j = 1),
        p1,
        p2
      ),
      ret = (
        int(r1),
        int(r2)
      ),
      body = (
        print(i),
        print(j),
        p1,
        p2
      )
    )

`int`, `boolean` и подобные имена — primitive/type constructor receivers. Они не обязаны быть hard keywords.

Переменные/имена внутри body не становятся аргументами функции автоматически. Аргументы функции задаются только в args-структуре function/procedure definition.

Пример procedure для L5-if на L3:

    proc l5_if (boolean condition) then else
      ...
    end l5_if

Нормализуется как:

    proc(
      name = l5_if,
      args = (
        boolean(condition),
        then,
        else
      ),
      body = (...)
    )

Здесь `condition` — примитив/evaluated argument через constructor `boolean`. Голые `then` и `else` — структурные аргументы. Отдельного `Struct then` не требуется.


9. `^` и передача структур

На L3 явный `^` обычно не нужен: структуры, массивы, текст, объекты и другие непримитивные значения передаются как references/handles по умолчанию. Структуры не копируются по значению при обычном вызове.

На L2 `^` разрешён как низкоуровневый pointer/reference constructor:

    ^p              untyped reference / void* / pointer to structure
    ^ PlantBed bed  typed pointer/reference, если типизация уже известна

Точная модель типизации ещё определяется через таблицы/модели/контракты, а не через наследование.

Принцип:

    L3 thinks in Structures.
    L2 lowers Structures to pointers/handles/layouts.


10. Математическое синтаксическое ядро

Кроме structural parser у языка есть второе встроенное ядро: mathematical expression parser.

Оно вызывается structural parser-ом внутри argument positions, когда встречаются математические operator tokens:

    ==
    !=
    <
    >
    <=
    >=
    +
    -
    *
    /
    ...

Математический parser нужен как built-in invocation point, потому что infix precedence и группировка должны работать до обычного receiver-dispatch. Его трудно сделать обычным регистрируемым оператором без глобального усложнения API.

Результат mathematical parser — обычная Structure.

Например:

    j == 1

может нормализоваться в:

    ==(j, 1)

или в другой эквивалентный expression-frame. Но фундаментально это всё равно Structure, а не отдельный Tree/AST type.

Для удобства L1/L2 procedures вроде `==(j, 1)` могут существовать как canonical target forms. Но infix source syntax всё равно разбирается встроенным math parser-ом.


11. `if` на L3/L4/L5

`if` не является keyword ядра. Это registered receiver/operator. Его implementation зависит от уровня.

L3 `if` — вычислительный control-flow receiver. При трансляции он получает Structures:

    condition
    then
    else

condition раскрывается в target expression, then/else раскрываются как body structures. При интерпретации condition интерпретируется как boolean-producing expression, после чего интерпретируется выбранная ветка.

L4 `if` — model-conditional receiver. Так как L4 non-executive, L4-if не выполняет runtime-действий. Он может условно включать/исключать/нормализовать model structures, registry entries, constraints.

L5 `if` — message/config dispatch receiver. Он условно отправляет L5-сообщения, например build/run/query/startup messages.

Один surface name `if` может быть зарегистрирован для разных уровней с разными implementations:

    operator
      if
      callableFrom = L3
      implementation l3_if
    end operator

    operator
      if
      callableFrom = L4
      implementation l4_model_if
    end operator

    operator
      if
      callableFrom = L5
      implementation l5_if
    end operator


12. `operator` и регистрация receivers

`operator` — это receiver/procedure, доступная во время bootstrap/model loading. Она заполняет registry допустимых receivers/operators.

Пример:

    L4
      operator
        while
        callableFrom = L3

        implementation
          while_func
          level = L2
        end implementation
      end operator
    end L4

Здесь `operator` не является special colon-form. Это обычная Structure, потребляемая L4/L1 receiver-ом.

L2/L3/L4/L5 receivers меняют активный набор допустимых operators/receivers для своего вложенного body.

До загрузки registry core может иметь bootstrap prelude table с минимальными receivers:

    L2
    L3
    L4
    L5
    operator
    func
    proc
    primitive constructors


13. Evaluation / translation consumption modes

Structure сама себя не исполняет.

Receiver/procedure решает, как потреблять поля аргументной Structure:

    as expression
    as body
    as declaration
    as model fragment
    as config message
    as data
    as delayed branch
    as primitive value

Для `if` это означает:

    condition -> expression
    then      -> body Structure
    else      -> body Structure

Для `func`:

    name -> function name
    args -> argument Structure
    ret  -> return Structure
    body -> body Structure

Это не lazy runtime magic. При трансляции receiver раскрывает свои Structures в target code. При интерпретации receiver интерпретирует нужные Structures согласно своей семантике.


14. Вызовы внутри круглых скобок и L3 Lisp-like форма

Смешение compact-call и line-command допустимо.

Пример:

    myFunc(1, if j==1 myProc(2) 2, (if( i==1, print choose hello, print choose world)), (if i==1 (print hello) (print world)))

Смысл:

    1. Первый аргумент: primitive 1.
    2. Второй аргумент: evaluated if-structure.
    3. Третий аргумент: bounded Structure в скобках.
    4. Четвёртый аргумент: bounded Structure в скобках.

Внутри скобок line-command продолжается до comma или соответствующей закрывающей скобки.

Внешние скобки не означают “raw tree”. Они создают Structure. Будет ли эта Structure переведена/интерпретирована как expression/body/data, решает signature/receiver потребителя.


15. ABI и lowering в L1 ANSI C

Каждый source-вызов имеет одну логическую argument Structure.

L1 lowering может оптимизировать физическую передачу аргументов.

Принцип для internal optimized ABI:

    up to three primitive/reference fields may be passed directly;
    if more logical arguments exist, an args-structure pointer/handle is used;
    translator may generate adapters for concrete call-sites.

Ссылки/handles считаются primitive scalar values.

Публичный/exported ABI для `.lm0` библиотек лучше делать frame-based:

    runtime/context pointer
    input argument structure pointer/handle
    output/result structure pointer/handle or status return

Например:

    LmStatus f(LmRuntime *rt, const F_Args *in, F_Ret *out)

Internal functions внутри whole-target compilation могут быть lowered более агрессивно: direct primitive slots, inline, specialized adapters, elimination of physical argument structures.

Source-семантика от этого не меняется:

    logical Structure always exists;
    physical Structure may be optimized away.


16. Компиляция и entry

Компиляция означает:

    Lingvamyxa source
      -> Structures
      -> semantic receiver processing
      -> L1 ANSI C projection
      -> platform C compiler/linker
      -> L0 artifact

Generated/debuggable L1 projections могут иметь имена:

    *.lm2.c
    *.lm3.c
    *.lm4.c
    *.lm5.c
    *.lmx.c

Editable L1 files:

    *.lm1.c
    *.lm1.h

Сгенерированный C может использовать `#line` для связи с исходным `.lm*` файлом.

Builder не требует специального `project` keyword. Ему можно дать любой `.lm5`, `.lm3`, `.lmx` или другой файл. Он либо находит entry/target через receivers/messages/signatures, либо выдаёт ошибку:

    no entry point

L5 build/config file — это просто L5-file с сообщениями для builder receivers. Специальная сущность `project` не обязательна.

L3 file может быть interpreted или compiled как implicit top-level executable entry.

L4 file не запускается как программа. Он может быть checked/loaded/registered as model.

L2 file компилируется как unsafe module/library/object, но не исполняется как script.

C `main()` для L0 executable генерируется не из имени файла `main`, а из build/target/entry information, полученной из L5 messages или implicit L3 top-level entry.

Имя `main` может быть convention entry symbol для compiled target, но не является обязательной startup-file convention.


17. Факты, правила и хранение

Факты имеют свойство накапливаться, поэтому persistent fact store должен быть отделён от source-файлов.

Правила/relations/contracts могут жить в L4/L5 source modules и registry/model tables.

Facts могут храниться в embedded или external backend, например SQLite, но SQLite не должен быть фундаментом синтаксического ядра.

Рекомендуемое разделение:

    Rules/signatures/contracts:
        .lm4 / .lm5 / .lmx modules

    Accumulating facts:
        persistent store / DB backend

    Query/relation engine:
        receiver layer over structures and storage backend


18. Краткие canonical examples

Hello World на L3:

    print Hello World

Семантически это:

    print(Hello, World)

и логическая argument Structure из двух atom/primitive fields.

Function definition:

    func estimateHarvest (PlantBed bed) (f32 harvest, f32 redApples, f32 greenApples)
      if bed.crop == Apples
        end estimateHarvest(bed.area * 1.7, bed.area * 1.7, bed.area * 1.1)
      end if

      end estimateHarvest(bed.area, 0, 0)
    end func

В этой версии `PlantBed bed` — typed/model constructor form только если `PlantBed` зарегистрирован как type/model receiver. Иначе это просто Structure, смысл которой задаёт type/model layer.

L5 conditional build:

    L5
      if mode == debug
        build debugTarget
      ---
        build releaseTarget
      end if
    end L5

Нормализация:

    L5(
      if(
        condition = expr(==(mode, debug)),
        then = (build(debugTarget)),
        else = (build(releaseTarget))
      )
    )

Operator registration:

    L4
      operator
        if
        callableFrom = L5
        implementation l5_if
      end operator
    end L4

Procedure implementing L5-if in Lingvamyxa-like form:

    proc l5_if (boolean condition) then else
      ...
    end l5_if

Normal form:

    proc(
      name = l5_if,
      args = (
        boolean(condition),
        then,
        else
      ),
      body = (...)
    )


19. Open design points

1. Exact primitive/type-constructor registry format.
2. Exact L4 procedure signature metadata format for L1 implementations.
3. Whether `---` without matching `end name` should be allowed in all contexts or only where receiver signature is complete.
4. Exact expression Structure form: `==(j,1)` versus `expr(op===, left=j, right=1)`.
5. ABI slot counting: whether runtime/context counts against the “four slots” convention.
6. Formal rules for arrays/text/models before the type-table layer is designed.
7. Persistence model for facts/rules and query engine integration.
