19.0.H. Current Revision-1 Bootstrap Operator Inventory (Historical)

The following operator summary reports the current hosted implementation. Its
status words remain useful for migration planning, but every described
namespace/descriptor/static-layout/eager-merge mechanism is non-normative.

The left column below is a historical item label, not a subsection number.
Status words refer to the current bootstrap:

    IMPLEMENTED       the exact spelling and stated semantic contract exist;
    REGISTERED ONLY   the spelling resolves, but the stated contract is absent
                      or has different semantics;
    TABLE/DATA        ordinary Structure/Array-based data, not an operator or
                      a fourth Value category;
    NOT IMPLEMENTED   the following text proposes a concrete source contract.

Later subsection headings describe the full design families. They do not imply
that a source receiver exists; registration and contract status are stated
explicitly below.

    0.  if / else
        IMPLEMENTED statement receivers; L2/L3.

    1.  match / default-pattern receivers
        NOT IMPLEMENTED. Proposed: register `match:` as a statement/expression
        receiver consuming ordered pattern/body pairs; `default` remains an
        ordinary pattern atom.

    2.  while
        IMPLEMENTED statement receiver; L2/L3.

    3.  until
        REGISTERED ONLY as a generic trailer. The post-condition loop contract
        in section 19.4 is NOT IMPLEMENTED. Proposed: give the trailer a
        loop-closing lowering that re-enters the closed frame while false.

    4.  for
        IMPLEMENTED for the compact counter/triplet form in section 19.5:
        `for: int(i, 0) (i < n) i++` plus a vertical or compact body.
        Range-style forms such as `for: i 0 n` remain NOT IMPLEMENTED.

    5.  each
        NOT IMPLEMENTED. Proposed: register a statement receiver over an array
        or iterator descriptor; L3 array traversal uses checked access.

    6.  return
        IMPLEMENTED L2/L3 executable-body receiver; terminal executable close
        is also implemented at definition level.

    7.  break
        IMPLEMENTED for the nearest loop frame; L2/L3.

    8.  continue
        IMPLEMENTED for the nearest loop frame; L2/L3.

    9.  finally
        IMPLEMENTED executable/scope cleanup receiver; L2/L3.

    10. catch / throw / throws
        IMPLEMENTED L2/L3 recoverable failure flow. `throws:` on `fn`/`sub`
        lists names. `throw: Name(arguments)` leaves the current
        executable with a dummy return. `catch: Name (parameters)` is a
        skipped landing pad; after it, execution continues in the same block.
        A throwing call must be a statement or the entire assignment; nested
        throwing expressions are rejected. Duplicate `catch` names in one
        block are an error; a series uses nested `---` blocks. C lowering is
        a same-TU throw channel plus `goto` to the selected catch.

    11. retry / retryable
        NOT IMPLEMENTED. Proposed: register retry-frame and retry-transfer
        statement receivers with explicit cleanup semantics.

    12. assert
        IMPLEMENTED diagnostic statement receiver; L2/L3.

    12a. log / error
        NOT IMPLEMENTED as source receivers. Proposed: explicitly bind
        observation statement receivers whose ordinary Structure fields/links
        select their handlers and policies. An explicit operation Structure may
        reference an observation Table, but no ambient table participates.

    13. redo
        NOT IMPLEMENTED. Proposed: register a loop-frame transfer that repeats
        the current body without advancing its source.

    14. yield
        NOT IMPLEMENTED. Proposed: register a function-body receiver that emits
        an iterator value and persists the resume state in the iterator
        Structure. Exhaustion is `throw: Stop`, caught by `each`; it is not a
        `None` result from `next`.

    15. labelled break / labelled continue
        NOT IMPLEMENTED; current `break` and `continue` are unlabelled. Proposed:
        materialize the label as an explicit control/callable occurrence and
        resolve the optional target through the current activation or an
        explicit graph link. Any backend label index is compiler/control-flow
        work data, not a runtime Namespace.

    16. merge / join
        `merge:` is REGISTERED ONLY for the contract below: its current handler
        composes and binds a named structural descriptor and emits its hosted C
        type/layout projection. It emits no result-object storage and constructs
        no Structure instance. The ordered high-level Structure merge specified
        in section 19.17 is NOT IMPLEMENTED. Replacement: implement the
        Revision-2 runtime fresh-tree `merge` directly; keep any explicit raw
        physical-layout projection as a distinct L2-only adapter operation.
        `join:` currently has legacy source-row behavior; normative `join:`
        consumes explicitly resolved Tables and produces an ordinary arena-owned
        Table reference.

    17. table / source / import / predef
        `table:` constructs an ordinary arena-owned Table and may explicitly
        bind its result. `source` is a table-body projection/lifetime marker, not
        a receiver and not a RegistryView selector. Current static C and
        Registry-row projections are legacy implementation paths.
        `import:` is an IMPLEMENTED ordinary module import. `predef:` is an
        IMPLEMENTED hoisted import, but the current bootstrap excludes it from
        L3. Proposed: admit `predef:` on L3 surfaces too; a selected dependency
        retains its own level and exports only explicit declarations, callable
        records and Structure providers/links;
        Table rows/cells are never imported as names.

    18. cast / implements
        The language form is `implements(varA varB Consumer)` as specified in section
        19.21.3. The hosted translator currently still evaluates a two-name
        first-level subset internally as a migration gap; that is not a source
        receiver and must not be written as `implements(varA varB)`. Translation and
        interpretation use the same source-semantic algorithm once Consumer is
        supplied: resolve `varA` and `varB`, walk Consumer for syntactic paths of
        `varB`, and admit `varA` when every such path is present. Unresolved names
        or paths absent from the supplied live/source Lmx Structures are
        diagnostics. A callable leaf actually invoked by Consumer must also
        have the exact canonical `all_methods_array.sig` required at that call
        site. Field values, unused nested contents, `requires.method`, `method`,
        ordinary rows and `default` are not consulted merely because they exist.
        See section 19.21.3.
        `cast:` is REGISTERED ONLY for high-level conversion semantics: its
        current emitter allow-lists the *target* name in `class.range` or
        `cast.target`, ignores the source and `Consumer`, and lowers to a
        target-language C cast. That is not the primitive-leaf rule of
        sections 2.2.3–2.2.4. Proposed: converters are ordinary receivers
        selected by merge key on the substitution edge; `implements` only
        observes that the key exists and that conversion is not forbidden;
        restrict raw representation/address casts to L2; the current L3 gate
        is missing.

    19. class / relation / rule / query
        `class` has no privileged core table meaning. A Table named `class` is
        ordinary data. `relation` and `rule` may be ordinary descriptor/data
        conventions. An expression `query(Table, coordinates...)` is NOT
        IMPLEMENTED generically; if added, it explicitly receives its Table and
        returns matching data, empty, or ambiguity.

    20. message / validate / execute / emit
        A message is TABLE/DATA: one LMX document whose root is the standard
        message envelope and whose `expression` is ordinary LMX. Its address is
        `endpoint + route`; the envelope fields are defined in section 19.19.1.
        The `send:` statement in item 27 is IMPLEMENTED for transporting these
        bytes, but it does not itself parse or validate the document.
        `validate`, `execute` and `emit` are NOT IMPLEMENTED as source
        operators. Proposed: register expression receivers
        `validate(Message, ExplicitRootOrInputs, ExplicitPolicies) -> ExecutionPlan`
        with `throws: Failure`, and
        `execute(ExecutionPlan) -> Result` with `throws: Failure`, plus an
        `emit:` statement receiver that appends a proposed message to the
        current Message Thread outbox. Failure is `throw`/`catch`, not a second
        return type. These operations belong to L2/L3. The lower-level hosted runtime
        now has FIFO inbox/outbox byte queues and local route delivery, but that
        ABI does not itself parse, validate or execute the LMX document and does
        not make these source operators implemented.

    21. model / descriptor / union / c.union
        `model` is ordinary Structure data. A standalone `descriptor:`
        declaration receiver is NOT REGISTERED by the current bootstrap. Named
        Structure descriptor declarations and the current physical `merge:`
        path do attach normalized first-level descriptor views to their explicit
        namespace bindings and emit hosted type/layout projections without
        emitting Registry field rows or implicit instance storage. Broader
        descriptor content remains ordinary Structure/Array data interpreted by
        selected consumers.
        High-level `union:` is NOT IMPLEMENTED. A future variant
        declaration must create an explicit ordinary description Structure
        without choosing physical storage or attaching it to every value. The
        physical `c.union:` machine-layout receiver is IMPLEMENTED, but its
        required L3 exclusion is not yet enforced. `field.union` is a TABLE/DATA
        layout relation.

    22. operator / receiver / method
        There are no `operator:`, `receiver:` or `method:` declaration receivers.
        The current bootstrap derives initial bindings from `operator.*`,
        `namespace`, `receiver.*`, `method` and `requires.method` Tables. This is
        implementation machinery. A future declarative receiver must explicitly
        create ordinary operation-description data and callable links; it must
        not insert ambient rows or a runtime Namespace as its language meaning.

    23. evidence / validator
        ordinary Structure/Array data, not source operators. Legacy
        `profile.validator` Table lookup exists, but
        the generic validation pipeline is NOT IMPLEMENTED. Proposed: the
        `validate` operation from item 20 returns an ExecutionPlan containing
        validation/authority evidence, or `throw: Failure` with that diagnostic
        as payload; no separate `evidence:` receiver is required.

    24. entry / provides / satisfies / conflict
        ordinary explicit Structure/Table fields, not registered receivers. A program may
        cache `provides`/`satisfies` results in a Table, but `implements(varA varB Consumer)`
        computes compatibility from the supplied live/source Lmx trees, the
        paths used by `Consumer` and exact signatures of callable leaves it
        actually invokes. Structural substitution failure and an explicit
        Table/graph-update conflict remain distinct.

    25. procedural / object / functional / logical
        Consumption modes, not operator spellings. Proposed representation:
        an explicit receiver-descriptor field such as `consumptionMode`.
        Concrete actions remain ordinary resolved calls or explicit `validate`,
        `execute`, `query` and `derive` operations.

    26. provider / codec / toLmx / fromLmx
        provider/codec descriptors are ordinary Structures and generic provider
        selection is not yet implemented. They enter resolution only through
        explicit graph links, an explicitly supplied root or a provider
        returning an Lmx pointer; an operation may use an explicit policy
        Table internally. Legacy `serialization.codec` lookup is IMPLEMENTED.
        `toLmx` and `fromLmx` are
        NOT IMPLEMENTED as source operations; only internal table serialization
        helpers currently exist. Proposed generic methods:
        `toLmx(Value) -> Text` with `throws: Failure` and
        `fromLmx(TargetDescriptor, Text) -> Value` with `throws: Failure`,
        selected through visible callable/codec descriptors rather than parser
        primitives. Encoding failure is `throw`/`catch`, not a union return.

    27. stop / exit / send / reply / await / schedule / thread
        `stop:` is an IMPLEMENTED L2/L3 statement receiver. Its admitted forms
        are `stop:` and `stop: Status`; the optional expression is evaluated at
        the call site and converted to `int`, with omitted status meaning zero.
        It requests cooperative termination of the explicitly executing Message
        Thread only: RUNNING becomes STOPPING, but `stop:` does not itself leave
        the current fn/sub/block or skip its cleanup. The first accepted ordinary
        stop request retains its status; a later fatal diagnostic/runtime failure
        may override that ordinary stop status. The final turn runs local
        collection and then becomes STOPPED.

        `thread:` is an IMPLEMENTED top-level L2/L3 source receiver. Its current
        form is:

            thread: HandlerName (IncomingMessage: message)
                route: "/absolute/local/route"
                handler statements
            end: HandlerName

        The handler has exactly one named parameter with exact descriptor
        `IncomingMessage`; direct source calls of the handler are rejected.
        `route:` is required compile-time metadata, not an executable statement.
        The route is a double-quoted printable-ASCII absolute path beginning
        with `/` and containing no backslash, query or fragment. Duplicate
        routes in one application translation are rejected. A handler may be
        declared directly or supplied by ordinary `import:`. Executable thread
        declarations in `predef:` modules and conditional `os`/`ifdef`/`guard`
        branches are rejected by the current startup profile.

        Each declared handler is materialized as one mailbox Message Thread.
        One invocation handles the one LMX document dequeued for that turn.
        `IncomingMessage.lmx` is a borrowed `const char *` view and
        `IncomingMessage.length` is its byte length; both remain valid only for
        the handler turn. The generated application entry always constructs a
        runtime and attaches its root; when at least one handler is declared it
        also constructs a pool, starts every handler and binds its route.
        Teardown drains cascaded committed work before stopping and joining the
        handlers.

        `send:` is an IMPLEMENTED L2/L3 statement receiver in these bootstrap
        forms:

            send: Route LmxBytes Length
            send: Endpoint Route LmxBytes Length

        The arguments are evaluated exactly once, from left to right. `Route`,
        `Endpoint` and `LmxBytes` lower to byte-addressable C strings in the
        current hosted profile; `Length` is converted to `size_t`. The first
        form uses the current application endpoint. The second admits only an
        absolute HTTP(S) endpoint. A send copies the complete LMX document into
        the current Message Thread's FIFO outbox. It is committed at the common
        end-turn boundary and does not perform a hidden return. An immediate
        address error or a commit-time delivery error requests failure of the
        sending Message Thread.

        The explicit address operands are temporary bootstrap routing
        projections of the envelope's `to.endpoint` and `to.route`; they are not
        a second address model. `LmxBytes` must still contain the complete
        standard message envelope. Until envelope parsing is inserted, the
        caller is responsible for making the explicit projection agree with
        `to`. The validation stage must eventually reject a mismatch.

        Local sends resolve `Route` in the runtime route table. A missing route
        fails with `LM_MESSAGE_STATUS_ROUTE_NOT_FOUND` (64). An HTTP(S) send is
        retained as a remote address but, until the REST/LMX provider is
        configured, fails with
        `LM_MESSAGE_STATUS_TRANSPORT_PROVIDER_NOT_CONFIGURED` (65). Invalid
        address syntax fails with `LM_MESSAGE_STATUS_INVALID_ADDRESS` (66).
        A configured provider reports a native transport failure as
        `LM_MESSAGE_STATUS_TRANSPORT_FAILED` (67), a syntactically valid HTTP
        response which does not admit the message as
        `LM_MESSAGE_STATUS_HTTP_REJECTED` (68), and an invalid provider result
        as `LM_MESSAGE_STATUS_TRANSPORT_PROTOCOL_ERROR` (69). HTTP 2xx admits
        the transport delivery; HTTP 404 maps to the same route-not-found
        status 64 as local lookup. Raw HTTP status numbers never become actor or
        process exit statuses.

        `exit:` is an IMPLEMENTED L2/L3 application receiver:

            exit:
            exit: StatusExpression

        The omitted status is zero; the optional expression is evaluated
        exactly once and converted to `int`. The first accepted application
        exit request selects the ordinary exit-request status. `exit:` is
        cooperative and does not perform a hidden return, jump or lexical unwind: the
        current fn/sub/handler continues through its visible source control flow
        to the common turn boundary. It is available wherever the current
        MessageThread context is explicitly propagated, including managed
        nested functions, but is rejected in an unmanaged external function.

        Request and shutdown are separate phases so an actor never joins
        itself. The requesting Message Thread becomes STOPPING, finishes its
        current outbox and collection boundary, and only then publishes the
        application exit as ready. A delivery or collector failure in that
        requester replaces the requested ordinary status with the requester's
        effective failure status. Once ready, the application controller stops
        the pool and root, waits for declared actors/workers, releases the pool,
        detaches/releases the root and deletes the runtime before returning to
        the host. An actor callback only requests this sequence; it never runs
        join/delete itself.

        Host-process status keeps the existing failure-preserving priority:
        a nonzero effective root status wins; otherwise a nonzero selected
        application exit status wins; otherwise the first nonzero declared
        actor status wins; cleanup failure supplies `1` only if all earlier
        choices were zero. Thus `stop: 3` followed in the same root turn by the
        first `exit: 5` records exit status `5` without rewriting the root's
        already selected status `3`, and the host returns `3`.

        The requester outbox is committed before the shutdown cut. Deliveries
        from other turns are linearized by the runtime mutex: entries admitted
        before the cut follow normal FIFO delivery, while entries that reach
        transport after the cut are cancelled as shutdown work without creating
        a spurious route/transport failure. The current generated application
        has one runtime and at most one application pool. Coordination of
        several independently constructed low-level runtimes/pools remains the
        responsibility of their explicit host controller.

        `reply`, `await` and `schedule` are NOT IMPLEMENTED as source receivers.
        Proposed contracts: `reply` sends the declared result or, on `throw`,
        a failure message with the same name and payload; `await(Future) ->
        Value` with `throws: Failure`; and `schedule(Message, Time)`.

        The explicit host runtime, worker-pool and actor start/join ABI is
        IMPLEMENTED. Its mailbox subset includes mailbox actor start, local
        route binding, owned-LMX FIFO inbox/outbox delivery and current-message
        access during a handler turn. `thread:` now exposes actor construction,
        binding and one-message-per-turn dispatch. Source `send:` now lowers
        over the same ABI.

    28. copy / move / borrow / own
        NOT IMPLEMENTED as source operators; only lower-level ownership/runtime
        helpers exist. Proposed: resolve them through explicitly bound operation
        descriptors whose signatures accept the relevant references/arenas.
        High-level operations may be L2/L3; raw allocator/address operations
        remain L2-only.

    29. watch / derive
        NOT IMPLEMENTED. Proposed: `watch(Query, Handler) -> Subscription` and
        `derive(Query, Rule) -> candidate rows/messages`. `reactive` is a
        profile/mode value, not a separate operator.

    30. service / route / HTTP adapter
        NOT IMPLEMENTED as source receivers. Proposed: `service:` materializes a
        service descriptor and binds it explicitly; `route` explicitly updates
        the route-map value it receives. HTTP remains a provider/transport
        adapter selected through a visible descriptor, not a core operator.

    31. authenticate / verify / authorize / ticket
        NOT IMPLEMENTED as source receivers. Proposed expressions:
        `authenticate(Credential, Verifier) -> AuthEvidence` with
        `throws: Failure`, `verify(Claim, Verifier) -> Evidence` with
        `throws: Failure`, and `authorize(Evidence, Operation) -> Allowed`
        with `throws: Failure`. Ticket creation
        and revocation operate on explicit Ticket Structures; `ticket` itself
        is not an operator.

Current bootstrap receiver/operator summary:

The following list contains exact spellings registered by the current L2
translator. It is an implementation baseline, not a claim that every later
profile family is already a core receiver.

    substrate receivers:   L1
    level receivers:       L2, L3
    definition receivers:  fn, callable, fm, sub
    control statements:    if, else, while, return, stop, break, continue,
                           synchronized, finally, assert
    declarations/values:   descriptor, const, (), [], None, OK, false, true
    module/source:         table, import, predef, join, merge
    machine/build receivers (intended L2-only; current L3 gates incomplete):
                           include, define, ifndef-default, os, ifdef, guard,
                           extern_c, c.struct, c.union, c.enum, c.array
    expression receivers:  cast: TargetDescriptor expression
                           implements(varA varB Consumer)
    modifier/trailers:     external; end, until
    prelude atom consumers:
                           include, define, os, ifdef, fn, layout, constant,
                           alias, forward, prototype, guard, extern_c, unit

The current `merge` handler consumes layout-describing sources, publishes a
composed descriptor under its explicit target name and emits that descriptor's
hosted type/layout projection. It never emits an implicit target object or
materializes a Structure instance; a value must be created separately through
an explicit constructor. It does not yet implement the generic high-level merge
contract. Current `join` still composes legacy source rows; it must become
ordinary Table-to-Table composition. `predef` is admitted in L3. Local-source early prepass still scans only implicit or
explicit L2 surfaces, although ordinary declaration can still materialize
table/join on an explicit L3 surface. Hoisted implicit-`.lm3` handling and `.lm3`
predef targets remain implementation work. These are implementation gaps, not
intended level restrictions. The built-in named-layout fallback remains
implementation debt; physical C layout is only a backend projection.
Named-Structure descriptor declarations and physical `merge:` declarations no
longer publish implicit owner or field Registry rows, instances or object
storage.

The exact `c.array` receiver is registered as an L2-only machine-storage
receiver and is rejected on an active L3 surface. Its nested bracket Frame is a
raw C declarator consumed by `c.array`; it is not dispatched as the ordinary
`[]` ArrayReference constructor.

The current expression operator tables register these exact families:

    prefix:   ++, --, +, -, @, \, !, ~
    postfix:  ++, --
    infix:    +, -, *, /, %, =, !=, <, <=, >, >=, &&, ||,
              &, |, ^, <<, >>, \
    index:    [, ]
    atoms:    ., None, OK, false, true

Tables and profile vocabulary are not source operators merely because they have
names. The current bootstrap currently uses the following Tables to construct
part of its initial namespace and backend configuration:

    class / class.kind / class.present
        legacy classification data; not core class semantics;
    method / requires.method
        legacy data relations; the `implements` receiver does not read
        them;
    namespace / receiver.*
        legacy input used to build explicit receiver bindings;
    operator.prefix / operator.postfix / operator.infix / operator.index
        expression spelling and emitter tables;
    serialization.codec / profile.validator
        codec and validation metadata tables.

Items marked TABLE/DATA above describe ordinary keys, table patterns, result
Structures, runtime roles or proposed profile vocabulary. They do not become
operators merely because they have names. The registered low-level spelling is
`c.union:`, not a generic `union:` receiver. `toLmx` currently appears only in
internal table-serialization helper names and `fromLmx` is absent; neither is a
registered operation-table method yet. A profile makes a proposed term
executable only by explicitly installing an exact receiver binding and its
validation/lowering descriptor.

The current bootstrap implements only unlabelled `break` and `continue`.
Labelled control may be added as a profile extension by registering ordinary
frames such as `outerLoop:` as control targets, but that mechanism is not part
of the implemented summary above.


19.15.H. Revision-1 Iterator/Closure Projection (Historical)

The detailed `iterator(T)`, `next(env)`, closure descriptor and capture rules
below are retained as syntax and implementation research. They are
non-normative until re-specified behind the generic Lmx call/result ABI.

`yield` is valid only inside an `fn` whose return descriptor defines a yield-protocol.

The standard iterator-like profile is expressed by ordinary namespace names:

    iterator(T)

Here `iterator` and `T` are not parser keywords. They are ordinary identifier
values resolved in the active lexical namespace view by the active L3/profile
receiver set. For example, `Text` or `Point` must be visible descriptor names if
they are used in `iterator(Text)` or `iterator(Point)`.

Calling a function admitted by `implements(thatFunction iteratorRequirement eachNextConsumer)` as an iterator source
does not execute its body to completion. It creates an iterator state Structure.

The translator lowers the iterator body into a `next(env)` implementation.

Each `yield` consumes one produced value. It inspects the current function's return descriptor, verifies that the descriptor defines a yield-protocol, checks the produced value against that protocol, emits one value from `next(env)` and records the resume state in `env`.

The `each` receiver consumes Structures admitted by
`implements(source iteratorRequirement eachBody)` by repeatedly
calling their `next(env)` implementation until no
value is produced.

This is the standard lazy-production protocol for sequences. A call to an
function admitted as an iterator source by `implements(thatFunction iteratorRequirement eachNextConsumer)` creates a
resumable state Structure; it does not
force every later produced value immediately. One consumer step asks for one
value, `next(env)` runs until the next `yield` or termination, then the state is
saved for a later step.

For example:

    fn: words () iterator(Text)
        yield: "Hello"
        yield: "World"
    end: words

is not source-semantically:

    words() -> Array("Hello", "World")

It is:

    words() -> iterator state Structure
    next(env) -> "Hello"
    next(env) -> "World"
    next(env) -> throw: Stop

Therefore `yield` provides demand-driven production:

    one value now;
    state saved;
    next value later;
    later value may never be requested.

This does not make all Lingvamyxa evaluation globally non-strict. Without a
receiver/profile that admits deferred consumption, an expression such as:

    print: expensive()

is ordinary value-producing input to the `print` receiver, not automatically a
thunk. Laziness is attached to descriptors and receivers explicitly visible in
the namespace.
Examples of such profiles may be:

    iterator(T)  zero or more T, forced by next(env);
    stream(T)    zero or more T, possibly asynchronous, forced by next/awaitNext;
    thunk(T)     one deferred T, forced by value(thunk) or an equivalent receiver;
    future(T)    one scheduled/deferred T or failure, forced by await(future);
    continuation(T) profile-defined resumable computation.

The common rule is that Structures are data until a receiver consumes them. A
lazy profile is a receiver/descriptor protocol that decides when to
consume the next step. This is different from Haskell-style global laziness:
Lingvamyxa does not make every argument and every data field lazy by default.
That keeps effects, ownership, validation and message scheduling explicit.

Callable partial/capture descriptor capabilities

Partial application and escaping closure capture are separate descriptor
capabilities. They may use the same backend representation, but they answer
different semantic questions:

    callable.partial
        A callable descriptor may consume a call-shaped argument such as
        `addBase(4)` or an explicit `partial(addBase, 4)` as a residual callable.

    callable.capture
        A callable descriptor may receive a nested callable whose environment
        escapes the defining scope. Capture copies used outer slots into that
        environment when the nested definition runs; later mutation writes the
        env fields (section 7.3.3).

    callable.projection
        The backend representation selected for the descriptor. In the first C
        projection profile, `callable.partial` and `callable.capture` require
        `c.closure-struct` or another representation that can store an
        environment.

The hosted bootstrap currently accepts explicit configuration Tables such as:

    table:
        source
        name: `callable.partial`
        columns: class  (value serial)
    end: `callable.partial`

    table:
        source
        name: `callable.capture`
        columns: class  (value serial)
    end: `callable.capture`

    table:
        source
        name: `callable.projection`
        columns: class  (value projection)
        rows:
                 AddX `c.closure-struct`
    end: `callable.projection`

Its explicit profile loader may use another Table to select admitted surface
forms for partial binding:

    table:
        source
        name: `callable.partial.form`
        columns: class (materializer binding)
        rows:
                 `call-frame` lm_trans_materialize_call_frame_partial
                 partial      lm_trans_materialize_partial_callable
    end: `callable.partial.form`

The `call-frame` row admits the existing compact callable-slot spelling:

    callAdd(addBase(4))

The `partial` row admits the explicit spelling:

    callAdd(partial(addBase, 4))

These Tables do not affect the namespace merely by existing. The descriptor
receiver head:

    callable: AddX (int: value) int

is compact sugar for a closure-capable descriptor Structure. Normatively it
binds a descriptor with fields conceptually equivalent to:

    callable.partial[AddX] = 1
    callable.capture[AddX] = 1
    callable.projection[AddX] = c.closure-struct

It produces no Registry rows. Semantic rules test the descriptor's partial and
capture capabilities separately.

For the first L2 translator profile, post-declaration marker operations remain
reserved but rejected:

    lazy X
    eager X

That is, these words may not yet be applied to an already-declared descriptor as
source-level modifiers. Future profiles may admit post-declaration set/override
operations, but they must be explicit compile-time namespace/descriptor updates,
not ambient Table effects or runtime switches.

A descriptor without `callable.partial` does not admit the residual-callable
interpretation through the first L2 translator profile. A compact call in that
position must either be consumed by another explicitly declared
descriptor/receiver protocol or be lowered as an ordinary value-producing call
according to the expected argument type.

A descriptor without `callable.capture` does not admit returning an escaping
nested callable with captured environment. A descriptor whose
`callable.projection` is a bare C function pointer must reject partial binding
and escaping capture unless an explicit adapter or closure representation is
also selected.

19.15.1. Iterator function

Example:

fn: makePoints () iterator(Point)
    yield: Point(1.0 2.0)
    yield: Point(3.0 4.0)
    yield: Point(5.0 6.0)
end: makePoints

Another zero-argument example:

fn: words () iterator(Text)
    yield: "Hello"
    yield: "World"
end: words


Calling:

    makePoints()

creates an iterator state Structure. It does not return an `Array Point` and does not execute all `yield` statements immediately.

P0 reads the first definition structurally as a plain `fn` frame:

    fn(
      makePoints,
      (),
      iterator(Point),
      yield(Point(1.0 2.0)),
      yield(Point(3.0 4.0)),
      yield(Point(5.0 6.0))
    )

The `fn` receiver consumes field 2 as the return descriptor and fields 3..end as the executable body. The `yield` receiver then checks each produced value against the yield-protocol declared by the current function return descriptor.

19.15.2. Iterator state Structure

An iterator state Structure contains enough state to resume execution after each `yield`.

For a simple iterator, generated state may include:

    state index;
    captured arguments;
    local variables that survive across yields;
    cleanup registrations owned by the iterator frame;
    a reference to the generated `next(env)` implementation.

When `yield` is implemented, that state is the same class of arena-owned
environment as nested `fn` capture in section 7.3.3: copied into surviving
slots at iterator creation, then read and written through those slots by
`next`. Source-level code does not depend on the physical layout of this
state Structure. `throw: Stop` from `next` still uses the `catch` rule in
section 19.15.3; it does not require a second capture model.

19.15.3. `next(env)`

The generated `next(env)` implementation executes the iterator until it either
reaches a `yield` or fails.

At a `yield`, `next(env)` returns a produced value and records where execution
must resume. That value may be `None` when `T` admits it. `None` is an
element, not the end of the sequence.

When the iterator is exhausted — the body ends after the last `yield`, or
the body executes `throw: Stop` — `next` does not return a sentinel `T`.
It fails with `Stop`:

    throw: Stop

`iterator(T)` therefore implies that `next` has `throws: Stop` in addition
to any other `throws` declared by the iterator body. `each` catches `Stop`
and ends the loop. A read or parse failure in the iterator body uses a
different name (`throw: ReadError ...` or whatever the body declared) and
is not swallowed by `each`.

This is the same `catch`/`throw`/`throws` rule as section 19.11. Comparing
the produced value with `None` is not the exhaustion test.

19.15.4. `yield` value construction

For the `iterator(T)` profile, the canonical source form is:

    yield: value

The current `fn` return descriptor, such as `iterator(T)`, tells `yield` which
yield-protocol is active. The `yield` tail is the produced value.
`implements(value T yieldNextConsumer)` must hold; any additional
iterator operation checks are ordinary `yield` receiver validation rather than
another compatibility system.

There is no hidden flattening. If `value` itself has an iterator type, then `yield: value` yields that iterator value as the produced value when the active protocol admits it. Flattening or forwarding another iterator requires a separate receiver such as `yieldFrom`.

If `T` is primitive, `value` is checked against that primitive type:

    fn: words () iterator(Text)
        yield: "Hello"
    end: words

If `T` is a Structure descriptor, write the produced Structure explicitly:

    fn: makePoints () iterator(Point)
        yield: Point(1.0 2.0)
    end: makePoints

This example emits one `Point` value when `Point(1.0 2.0)` is a valid
construction under the visible `Point` descriptor.

If `T` is an Array descriptor, `yield` analogously consumes an
ArrayReference. Neither aggregate result is copied by `yield`; iterator
publication follows the descriptor and arena-lifetime contract.

19.15.5. Iterator consumption by `each`

Example:

each: point in makePoints
    draw: point

`each` repeatedly calls `next`. A yielded `Point` is bound to `point`.
`throw: Stop` is caught by `each` and ends the loop. Another `throw` from
`next` is not `Stop` and follows ordinary `catch`/`throws` in the caller
of `each`.

For a zero-argument iterator function, the source may also be written as an explicit compact call:

each: point in makePoints()
    draw: point

Both forms are valid. The bare form gives the callable binding to `each` as an iterator source; the compact-call form creates the iterator state Structure first and gives that Structure to `each`.

Semantic form:

iterator: makePoints

while: true
    result: next iterator\env
    if: not result\hasValue
        break
    ---
    point: result\value
    body


This is semantic pseudocode. A translator may lower it to a direct state machine or inline loop.

19.15.6. Iterator termination

An iterator-like `fn` terminates when its generated `next(env)` reaches the end of the executable body or reaches a profile-defined completion path.

A `yield` after termination is unreachable.

In the core profile, a bare `return` is not a valid `fn` return. If an iterator profile wants an explicit early iterator-completion operator, it must define that receiver/profile rule separately. `return: value` remains an ordinary `fn` runtime return form when admitted by the function's return descriptor; when written in a terminal trailer position, it may also close the `fn`.

`break` and `continue` inside an iterator body operate on the nearest active loop frame inside the iterator body, not on the consumer's `each` loop.

!!!
Iterator close semantics are not fully specified. A final specification must define when iterator-owned `finally` cleanups run if an iterator is abandoned before exhaustion, discarded, moved to another thread or terminated by diagnostic failure.
!!!


19.17.H. Historical Hosted Table Projection

The remainder of the concrete `LmSlice`, root-initializer and namespace-based
Table description in this subsection records the Revision-1 hosted backend. It
is non-normative for Revision 2. It may be used as a compatibility inventory of
syntax and tests, but not as permission to introduce `StructureReference |
ArrayReference`, descriptor-selected layouts, hidden Message-Thread parameters,
eager module materialization or runtime namespace bindings.

In the current hosted C99 profile, an unmarked `table:` directly on an
executable module surface or inside a managed function constructs an
arena-backed, read-only Table ArrayReference. Its binding has the hosted
`LmSlice *` projection. `length` is the number of rows. For a non-empty Table,
`ptr` designates an arena-owned rank-one backing array of row
StructureReferences; every constructed row is a distinct arena-owned Structure.
An inline non-primitive cell constructor likewise materializes its referent in
that arena. An empty Table still has a non-null arena-owned header, with zero
`length` and null `ptr`.

Row access is explicit indexing followed by field-follow:

    orders[0]\id
    orders[i]\total

The former hosted shorthand `orders\id` is not Table row access and is rejected.
`orders\length` and `orders\ptr` expose the current header metadata/backing
bridge. The Table binding and rows are read-only in this bootstrap stage;
indexed field update is rejected rather than emitted as mutable C storage.
ArrayReference-valued Table columns remain pending because the current private
row metadata does not yet carry their complete element/rank contract, so the
hosted translator rejects them explicitly.

Construction evaluates row cells once in source order and publishes the Table
binding only after the complete header, backing and rows have been initialized.
A local Table requires a managed Message Thread context. A direct module Table
uses the source-ordered root initializer of section 19.29.12.2.1 and therefore
inherits its current unique-root-`main`, conditional-wrapper and imported-main
restrictions. A Table constructor in an external function without a managed
Message Thread context is rejected.

The hosted C row layout and all helper/type names used to lower it are private
projection state. They create no namespace-visible row descriptor and reserve
no source spelling; a user declaration that happens to match an older generated
row-type spelling does not conflict with the Table.

The explicit leading `source` form remains a translation-time Table projection
and emits no public runtime Table binding. Source-marked ordered joins are
implemented for that projection. Runtime `join:` lowering is still pending; an
unmarked join is diagnosed rather than silently discarded.

The L2/L3 receiver `join` materializes a new table value from several
table-producing sources:

    join: (sourceTable0 sourceTable1 ... sourceTableN) targetName
        tableFragment
    end: targetName

The bounded first argument is the ordered source-table list. In Revision 2 each
source expression must produce an Lmx reference directly, through traversal
from the containing Structure, or through an explicit root-relative lookup.
Any compatibility operation is an explicit operation over the actual source
and consumer graphs, never a descriptor lookup in an active namespace. The
second argument is the target table short name. The `join` receiver normalizes
that argument as its `name`, so the canonical explicit close is
`end: targetName`; `end: join` remains the admitted receiver/head close
alternative.

The vertical body is an optional target table fragment. It may be written
directly as table body fields such as `columns:` and `rows:`, or as an explicit
nested `table:` descriptor. If an explicit nested `table:` contains `name:`, that
name must match `targetName` after ordinary identifier normalization.

Default table join is ordered:

    1. Evaluate and resolve source Lmx references from left to right.
    2. Determine the target table schema from the explicit body `columns:` when
       present, otherwise from the first source table.
    3. Validate that every source row is compatible with the target schema.
    4. Append source rows in source-list order.
    5. Append body rows after source rows.
    6. Preserve duplicate row keys and duplicate relation facts.

`join` does not silently override, remove or deduplicate rows. If an explicit
consumer later uses last-visible-row, first-visible-row, relation-set or overlay
semantics, that is the consumer's policy, not a hidden side effect of `join`.

Example in an `.lm2` or `.lm3` source module:

join: (`Base.field.class` `Audit.field.class`) `Entity.field.class`
    columns: class  (field class)
    rows:
             flags  u32
end: `Entity.field.class`

Conceptual materialized table value:

table:
    source
    name: `Entity.field.class`
    columns: class  (field class)
    rows:
             # rows from `Base.field.class`
             # rows from `Audit.field.class`
             flags  u32
end: `Entity.field.class`


The remaining subsections define explicit Registry, message, service and runtime
receiver families that were formerly described as separate language levels.
They use only the L2/L3 profiles defined in section 1. A subsection may define
supporting Structures such as RegistryView, Evidence, ExecutionPlan or Message
Thread in addition to its source receiver spellings; those Structures are not
new levels or parser mechanisms.

Mechanism filter:

    A profile term is not a new language mechanism merely because it has a
    name. It remains profile vocabulary while it can be represented as an LMX
    Structure/Array, receiver consumption, explicit Table data, validator evidence,
    ExecutionPlan payload or executor result/failure.

    Provider, replayPolicy, freshness, confidence, calibration, budget, effect
    fence, authority ticket, safeMode and decision-log rows therefore remain
    profile vocabulary. A term becomes core semantics only when the existing
    Structure / Array / receiver / validation / plan / execution pipeline
    cannot represent it without changing that pipeline.


19.18.H. Revision-1 Registry/Namespace Profile (Historical)

The legacy overview and subsections 19.18.1 through 19.18.5 below are retained
for table syntax, examples and implementation history. They are non-normative
in their entirety where they mention `StructureReference`, `ArrayReference`,
visible/attached descriptors, namespace bindings, namespace import or
namespace-based expression resolution. Examples may be reused only after
applying the Revision-2 rules above: explicit Lmx data and links, no semantic
runtime Namespace, and no attached descriptor/type meaning.

A registry is ordinary program data explicitly constructed from Structures and
Arrays. A `RegistryView` is an ordinary view over such data. Each Registry,
Table or RegistryView value is concretely a StructureReference or
ArrayReference according to its visible descriptor; these names denote profile
roles, not additional Value categories. A RegistryView is not an ambient
component of the language machine, is not created merely because a `table:`
form exists, and is never consulted merely because a Structure or Array was
constructed.

`table:` and `join:` produce ordinary arena-owned table references as specified
in section 19.17. A program may explicitly bind such a reference in its
namespace, pass it to a registry/query operation, or derive another table from
it. None of these operations adds names, descriptors or types to a namespace.
Only an explicit declaration, import or namespace operation may do that.

Sections 19.18 through 19.33 describe optional library/profile subsystems that
may use explicit Registry or Table operands. Their tables are data above the
core Value and namespace semantics; they are not a substrate beneath those
semantics. Every registry example has an explicitly supplied
Registry/RegistryView operand or a namespace binding from which that ordinary
value is obtained; no ambient RegistryView is implied.

19.18.1. Registry Keys and a Conventional `class` Table

Inside an explicit registry, `class` may be used as an application-level word
for a named key. A table whose exact name is `class` is an ordinary
classification table by convention only. The name has no grammar privilege and
does not introduce a source-language class, descriptor or namespace binding.

For example, a registry library may accept:

    table:
        name: classes
        columns: key kind
        rows:
            Circle layout
            int    primitive
    end: classes

The result is an ordinary StructureReference or ArrayReference with the Table
role. Binding it as `classes` makes that table available by that name; it does
not bind `Circle` or `int`. Likewise, a table named `Circle` is not the
descriptor of `Circle` merely because the spellings match. A profile may
explicitly convert table rows into descriptor Structures and explicitly import
those descriptors into a namespace, but conversion and import are separate
visible operations.

A registry key can denote anything useful to the registry consumer: a numeric
kind, operation, route, validator, implementation, message form or diagnostic.
It remains ordinary registry data. Constructing an instance, declaring a
descriptor, or resolving an expression never inserts or queries such a key
implicitly.

Language-level structural compatibility is instead defined by descriptors
explicitly bound in the current namespace and by `Consumer`. In
particular, `implements(varA varB Consumer)` does not consult the tables described in this
section; see section 19.21.3.

19.18.2. Relation Tables and Explicit Import/Overlay

Tables can describe relations between registry keys. A binary operation may be visualized
as a sparse matrix:

    table `equals.relations`

              decimal          real             int
    decimal   decimal_eq       decimal_real_eq  decimal_int_eq
    real      real_decimal_eq  real_eq          real_int_eq
    int       int_decimal_eq   int_real_eq      int_eq

The selected cell is the terminal payload returned by table lookup for the
current table and lookup keys. The table name and the keys that selected the
cell are the access path; they are not required to be repeated inside the cell
payload.

A cell may be written in short form as a single atom such as `decimal_int_eq`,
`decimal_int_add` or `int_eq`. A consuming profile normalizes such a short form
to a terminal cell payload kind and payload. Optional result, effect, lifetime,
authority, priority, cost and provenance metadata may be stored in side tables
keyed by the payload class/key or by an implementation-generated cell id.

The canonical source form for a relation table is a table Structure with an
explicit name, column list and dense rows. `columns` is not a registry namespace
item by itself. It is a field consumed by `table`.

Within one explicit registry construction block, two table values with the same
normalized key are an error unless that registry's merge policy says otherwise.
This restriction belongs to the registry consumer; it is not a restriction on
ordinary namespace bindings or on unrelated Table values.

Column syntax is generic:

    atom
        The atom is the column name.

    anonymous Structure
        The first atom is the column name. The remaining atoms are column
        descriptors. Descriptors are ordinary class/key names and may be stored
        as relation rows by the loader.

For example:

    columns: class (spelling char) (cost serial)

means a row-key column named `class`, a column named `spelling` with descriptor
`char`, and a column named `cost` with descriptor `serial`.

Class/key spelling follows the ordinary identifier rule:

    if the class/key name is a valid ordinary Lingvamyxa identifier, write it
        bare;
    if it contains operator characters, whitespace, punctuation, dots, arrows,
        external spellings or any spelling that must round-trip exactly, write
        it as an exact quoted identifier.

For example:

    u32
    result
    implementation
    sqrt_ansi_c
    `+`
    `translator type-->spelling`
    `implementation-->L2 lowering`

The semantic class/key value of an exact quoted identifier is its payload after
backtick unescaping; the backticks are not part of the class/key.

By convention the first column is `class`; it carries the row class/key. Later
column names are also classes. The cell under such a column is the value of
that relation coordinate:

    table:
        name: `translator type-->spelling`
        columns: class (spelling char)
        rows:
            u8  "uint8_t"
            u16 "uint16_t"
            u32 "uint32_t"
    end: `translator type-->spelling`

This means:

    `translator type-->spelling`[u8][spelling]  -> "uint8_t"
    `translator type-->spelling`[u16][spelling] -> "uint16_t"

Here `translator type-->spelling`, class, spelling, u8 and u16 are keys in the
explicit table. The strings `"uint8_t"` and `"uint16_t"` are primitive payloads
for a translator that was explicitly given this table. They do not affect the
meaning of source-language names.

An empty table cell is interpreted by the explicitly invoked table profile. A
registry library may define conventions such as `None.cell`; those conventions
do not define expression-level `None`, primitive descriptors or absence in the
core language.

A profile may store contextual-literal mappings as registry data. The literal
name and its source-language meaning must be declared explicitly in the
namespace. Querying a table may then be part of that declared descriptor's
implementation; the mere presence of the following rows declares nothing.

To prepare optional table-driven mapping data for a contextual literal such as
`None`, `true`, `false`, `OK` or a profile-defined name:

    1. Explicitly declare the contextual-literal descriptor and bind its name
       in the namespace. The declaration must name the literal and supply or
       construct its descriptor Structure; it may explicitly reference the
       mapping Tables prepared below. If the selected profile has no such
       declaration/import operation, the literal cannot be introduced by
       writing Table rows.

    2. Store the literal name as a `contextualLiteral` registry key, for example
       in a conventional classification table:

           table:
               name: `contextualLiteral.classes`
               columns: class (kind class)
               rows:
                        None  contextualLiteral
                        OK    contextualLiteral
                        false contextualLiteral
                        true  contextualLiteral
           end: `contextualLiteral.classes`

    3. For each target value class that wants a class-local meaning, add rows to
       that target class table. The conventional column descriptor is
       `context literal` plus the target class:

           table:
               name: `int8.contextualLiterals`
               columns: class  (`context literal` int8)
               rows:
           end: `int8.contextualLiterals`

           join: (`int8.contextualLiterals`) `Boolean.contextualLiterals`
               columns: class  (`context literal` int8)
               rows:
                        None  -1
                        false 0
                        true  1
                        OK    1
           end: `Boolean.contextualLiterals`

       In this example `Boolean.contextualLiterals[None] = -1`,
       `Boolean.contextualLiterals[false] = 0`,
       `Boolean.contextualLiterals[true] = 1` and
       `Boolean.contextualLiterals[OK] = 1`. The numeric cells are ordinary
       payloads. The Table binding names do not collide with the `int8` or
       `Boolean` descriptor bindings. These cells are not a global empty-cell
       encoding.

    4. If the literal also has a fallback mapping, store it in
       `contextual.literal.value`. The payload points to a value table keyed by
       the expected target class:

           table:
               name: `contextual.literal.value`
               columns: class (value relation)
               rows:
                        None  `None.value`
                        OK    `OK.value`
                        false `false.value`
                        true  `true.value`
           end: `contextual.literal.value`

           table:
               name: `None.value`
               columns: class (value char)
               rows:
                        int     0
                        int8    0
                        Boolean -1
           end: `None.value`

       A class-local row in the mapping Table explicitly referenced by the
       expected target descriptor is preferred. The fallback path is used only
       when the consumer still has an expected class but that descriptor's
       mapping Table does not define a more local contextual value.

    5. Store an optional expression-emitter mapping, for example in
       `expr.atom`:

           table:
               name: `expr.atom`
               columns: class (ansi_c char) (emitter binding)
               rows:
                        None  None  lm_trans_expr_emit_contextual_literal
                        OK    OK    lm_trans_expr_emit_contextual_literal
           end: `expr.atom`

    6. Store an optional receiver mapping under data-specific names which do
       not collide with receiver/descriptor bindings. The Tables remain
       ordinary data and do not themselves bind a receiver:

           table:
               name: `contextualLiteral.receiverTypes`
               columns: class (receiver.type relation)
               rows:
                        None statementAssignment
                        OK   statementAssignment
           end: `contextualLiteral.receiverTypes`

           table:
               name: `contextualLiteral.statementReceivers`
               columns: class (receiver binding)
               rows:
                        None lm_trans_statement_emit_contextual_literal_assignment
                        OK   lm_trans_statement_emit_contextual_literal_assignment
           end: `contextualLiteral.statementReceivers`

Only step 1 changes the namespace. An explicitly declared contextual-literal
descriptor may query the Tables from later steps, so several consumers can
share one data-driven implementation. Before that descriptor is bound in the
namespace, `None`, `OK`, `Red` or `Maybe` have no such language meaning. Empty
source cells remain a separate concern of the explicit table loader.

`FORBIDDEN` is the standard explicit prohibition class/value. It is different
from `None`: `None` is a namespace-declared contextual literal whose descriptor
may explicitly query a referenced mapping Table, while `FORBIDDEN` means the
relation is present and explicitly denied.

Adding a new registry key does not require adding it to every table. Missing
cells become the explicit query operation's empty result after its lookup path
is exhausted.

The same information may be viewed through another table, for example a
class-centered view:

    table `decimal.relations`

              decimal          real             int
    plus      decimal_plus     decimal_real_add decimal_int_add
    minus     decimal_minus    decimal_real_sub -
    equals    decimal_eq       decimal_real_eq  decimal_int_eq

These are not separate semantic systems. They are convenient table layouts over
terminal relation rows.

Registry tables may import or overlay other registry tables. Import here means
explicit table-data composition, not namespace import and not hidden copying of
code or method bodies. A query checks the importing table, then its explicitly
listed bases according to the registry's priority policy.

Example:

    table:
        source
        name: appEquals
        import:
            numericEquals
            textEquals
        priority:
            numericEquals: 20
            textEquals: 10
        String:
            String: string_eq
    end: appEquals

Multiple imports are allowed only when the import order or priority is
explicit. If two imported bases provide the same cell:

    same cell, same payload      -> duplicate, allowed or ignored;
    same cell, different payload -> conflict unless priority/override admits it;
    missing cell                 -> continue lookup in lower-priority bases.

The same rule may be used for registry descriptor rows, validator rows,
operation rows, authority rows or any other relation data. The imported rows
remain table data; they do not become namespace descriptors or source-level
method bodies.

Any finite graph can be decomposed into binary tables by introducing
intermediate keys. For an n-ary expression, the registry may use signature keys,
partial tables or chained binary relations. This is a storage/resolution
technique; source syntax remains ordinary LMX expressions.

19.18.3. Explicit Registry Sources and Mix Definitions

LMX can describe registry data because it can describe Structures and Arrays.
An L2 or L3 module may construct tables, compose them, and pass their references
to an explicitly called registry loader. A `predef` declaration may explicitly
import namespace bindings from another module, but it does not scan that
module's arbitrary tables and does not create a RegistryView implicitly.

Example registry input:

    table:
        name: equalsData
        columns: left right implementation
        rows:
            decimal int decimal_int_eq
            int     int int_eq
    end: equalsData

    Registry: numericRegistry equalsData

Here `equalsData` is an arena-owned StructureReference or ArrayReference with a
Table descriptor, and `numericRegistry` is likewise an ordinary reference
returned by the explicit `Registry` operation. Neither form binds `decimal`,
`int` or `decimal_int_eq` as source names.

Mix bounded forms `{...}` may annotate groups, documentation regions or visual
clusters consumed by an explicit loader. Mix is not a second metadata language
and its marks do not mutate the namespace. Persistence of an explicit registry
value is likewise a library/profile decision.

19.18.4. Namespace Resolution and Explicit Table Queries

An L3 expression is first a Structure. Its names, receiver heads and operators
are resolved from the namespace state at that source point. The resolution may
produce a callable binding directly or a descriptor that explicitly references
Structures, Arrays or a dispatch table. No arbitrary table participates merely
because it exists.

For:

    a + b

the resolver conceptually performs:

    plusDescriptor = namespace.resolve(operator `+`)
    leftDescriptor = descriptor established for a
    rightDescriptor = descriptor established for b
    implementation = plusDescriptor.select(leftDescriptor, rightDescriptor)

The internal `select` operation may query a table explicitly stored in
`plusDescriptor`; that table remains ordinary data reached through the resolved
binding. Missing or ambiguous bindings and selections are diagnostics defined
by the operation descriptor and selected profile.

An explicit registry query is an ordinary call with a Registry/Table reference
as an operand, for example:

    query: numericRegistry equalsData decimal int

Its result does not become the meaning of another expression unless ordinary
source code consumes that result or an explicit namespace operation binds a
descriptor derived from it.

19.18.5. Explicit Registry Cell Payloads

A terminal cell is the payload returned by an explicit registry/table lookup.
It has no special status in the core Value ontology and is ultimately a
Primitive, StructureReference or ArrayReference.

The lookup path is separate from the payload. For example:

    plus[decimal][int] = decimal_int_add

The table `plus` and the lookup keys `decimal` and `int` are already known from
the lookup context. They are not mandatory fields of the returned cell payload.
The returned payload is `decimal_int_add`.

In an implementation view this may be represented as:

    CellKey(table_id, key_id*) -> CellPayload(kind, payload)

The key tuple selects the cell. The payload says what the selected cell means.

A registry library may normalize a terminal cell into a Structure with fields
such as:

    kind
        The payload kind.

    payload
        The value, binding, expression, table key, validator target, message
        target or diagnostic Structure carried by the cell.

Possible profile-defined payload kinds include:

    primitive
        A primitive/scalar value, literal result or terminal L2/L1 lowering
        payload admitted by the active profile. In early bootstrap tables many
        final cells are primitive lowering payloads such as `"uint32_t"`,
        `"sqrt"` or `"=="`.

    binding
        A reference to an executable or lowerable binding, such as an L2/L3
        function/subroutine target, an L1/C symbol, an inline primitive lowering
        rule or a generated trampoline.

    descriptor
        A descriptor-like payload used by this registry consumer. It may be a
        Structure reference or another table key. It is not thereby a
        source-language descriptor. To participate in language resolution, a
        separate explicit conversion/import operation must create the required
        descriptor Structure and bind it in the namespace.

    expression
        An L2/L3 expression Structure admitted by the selected profile.
        The resolver or executor consumes that expression after substitution or
        further resolution.

    tableKey
        An intermediate registry class/key used to continue n-ary or graph
        resolution through another table. A `tableKey` is resolver navigation
        state, not the final semantic descriptor selected for execution,
        validation or projection.

    validator
        A validator target or validation expression that may produce acceptance,
        rejection, diagnostic information or stronger evidence.

    messageTarget
        A message/action target selected for a validated message expression.

    diagnostic
        A rejection, missing relation, ambiguity, conflict or profile-defined
        diagnostic Structure.

    None
        The registry profile's empty query result. Missing row, missing column
        or missing cell may normalize to this result after the explicit lookup
        path is exhausted. This does not define expression-level `None`.

    forbidden
        Explicit prohibition. `FORBIDDEN` is not an empty value; it means the
        relation exists and is denied.

    conflict
        An explicit conflict marker produced by registry loading or resolution.

A short source spelling may normalize directly to a payload. Examples:

    table:
        name: plus
        columns: class (int char) (u32 char)
        rows:
            decimal decimal_int_add None
            u32     None            plus_u32_u32_l2
    end: plus

may normalize conceptually as:

    plus[decimal][int] -> CellPayload(descriptor, decimal_int_add)
    plus[u32][u32]     -> CellPayload(descriptor, plus_u32_u32_l2)

A terminal cell payload is not required to be a heavy record in source form. The
payload atom may itself be a registry class/key. That class/key may then be
used as a key into additional descriptor tables:

    table:
        name: `plus cell-->result`
        columns: class (result char)
        rows:
            decimal_int_add decimal
            plus_u32_u32_l2 u32
    end: `plus cell-->result`

    table:
        name: effects
        columns: class (effect char)
        rows:
            decimal_int_add pure
            plus_u32_u32_l2 pure
    end: effects

    table:
        name: level
        columns: class (level char)
        rows:
            decimal_int_add L2
            plus_u32_u32_l2 L2
    end: level

    table:
        name: `implementation-->L2 lowering`
        columns: class (symbol char)
        rows:
            plus_u32_u32_l2 "+"
    end: `implementation-->L2 lowering`

    table:
        name: cost
        columns: class (cost serial)
        rows:
            decimal_int_add 10
            plus_u32_u32_l2 1
    end: cost

Therefore optional cell descriptor information may be stored inline, derived
from the table and lookup keys, or stored in side tables. Common optional
descriptor rows are:

    result
        Result class, result model, result table key or result expression.

    effects
        Pure/effect/action policy: pure, read-only, mutates receiver, sends
        message, filesystem write or profile-defined effect.

    level / visibleFrom
        The level or profile where the payload is callable or lowerable.

    validators / evidence requirements
        Additional validators or evidence that must hold before the payload may
        be consumed.

    lifetime / ownership
        Primitive value, owned result, borrowed result, moved result, external
        handle, arena-owned result or another profile-defined memory policy.

    authority / capability
        Required permission, ticket, verifier or capability for message/action
        cells.

    priority / cost
        Deterministic ranking information used when a profile admits multiple
        candidate cells.

    conflict policy
        Duplicate, override, replace, prefer, reject or profile-defined conflict
        handling inside the explicit Table/operation consumed by this descriptor.
        It does not govern lexical namespace redeclaration and cannot bypass
        `implements(new old Consumer)`.

    diagnostic policy
        Diagnostic code, severity and message produced for missing, rejected,
        ambiguous or conflicting cells.

    source / provenance
        File, line, receiver, generated origin, builtin origin or imported
        registry origin for diagnostics and incremental rebuilds.

Provider/device descriptor rows may also be attached to binding payloads:

    providerOf
        The provider/device/profile that executes or lowers the payload.

    binding
        The concrete L2/L1/device/service binding selected for the payload.

    precision
        exact, bounded, approximate, calibrated, drifting or another
        profile-defined precision policy.

    latency
        inline, slow, async, remote, cycles-counted or another profile-defined
        execution-time policy.

    determinism
        deterministic, calibrated-deterministic, noisy, sampled or another
        profile-defined repeatability policy.

    confidence
        none, flags, probability, u8 score or another profile-defined confidence
        representation.

    calibration
        none, required, valid, expired, source-specific or another
        profile-defined calibration state.

    fallback
        Alternative cells or payloads when the selected provider is unavailable,
        rejected by policy, too expensive, insufficiently precise or below
        required confidence.

A diagnostic payload may be written explicitly:

    table:
        source
        name: plus
        decimal:
            String:
                diagnostic:
                    code: incompatibleOperands
                    message: "plus(decimal, String) is not defined"
                end: diagnostic
    end: plus

A graph or n-ary relation may use a `tableKey` payload to continue resolution:

    multiply[Matrix][Matrix] -> MatrixMultiplySignature
    MatrixMultiplySignature[leftCols][rightRows] -> matrix_mul_impl

The current bootstrap may still contain hardcoded ANSI C lowering for L2/L1
surface forms. Moving those rules into explicit configuration tables is an
implementation option, not a change to the language's namespace semantics.



19.19.H. Revision-1 Namespace/Descriptor Message Pipeline (Historical)

The legacy subsections 19.19.1 through 19.19.5 below are retained as design
history and examples. They are non-normative wherever they use a runtime
namespace/environment/snapshot, attached or visible descriptors, descriptor
dispatch, implementation bindings, hidden execution context or the term
Validator/Merge for policy selection. Interpret reusable envelope and pipeline
examples only through the Revision-2 pipeline above.

19.19.1. Message

A message is one LMX document. Its root is a standard message envelope and its
`expression` field is a proposed, possibly effectful/action-capable LMX
expression candidate. The whole envelope, including its address and metadata,
is LMX; there is no second message language or mandatory JSON wrapper. A
message may become an action after validation, but it is not concrete before
validation, is not a transport packet and is not executed merely on arrival.

It may be a full LMX subtree or a very small LMX subset. The language does not
bake in a fixed restriction such as "one command only" or "no explicit descriptors".
Those restrictions are policy decisions of the receiving side.

A message expression may be as large as the receiver profile admits. Because
the expression field is ordinary LMX, a message may contain nested expressions,
deferred Structures, local descriptors, validators, calls, control receivers,
Mix marks and other message-producing forms. These forms are not trusted merely
because they appear in the message. They become executable only after
validation/merge has reconciled them with the receiver namespace, visible
descriptors and explicit policies and produced a ConcreteExpression /
ExecutionPlan.

There is no separate Smalltalk-style selector syntax required by the message
model. The selector/call/receiver shape is already an LMX Structure. If a
profile wants selector-like dispatch, it supplies a namespace-visible
descriptor whose implementation may explicitly read a dispatch Table during
validation/merge. Message richness comes from LMX itself, not from a second
message mini-language.

"Effectful/action-oriented" does not mean that every message must mutate
something. A query, read request or validation-only request may also be a
message. The point is that a message is capable of becoming an action after
validation and execution-plan construction.

Example:

    message:
        id: "request-123"
        to:
            endpoint: "https://archive.example.org"
            route: "/inbox/save"
        end: to
        replyTo:
            route: "/inbox/replies"
        end: replyTo
        correlation: None
        expression:
            save:
                file: "report.lmx"
                mode: overwrite
            end: save
        end: expression
    end: message

The message is proposed source data. It may carry a local mini-model, expected
result/effect descriptors, payload data, context, capability claims or
implementation references. These are claims, not authority and not executable
code. HTTP, queues, sockets and files are only transport/storage envelopes for
such proposed expressions.

19.19.1.1. Message Envelope and Address

The standard envelope has these coordinates:

    id
        Opaque identifier of this message. It is unique within the sending
        application for the period in which replies, retries or duplicate
        detection may refer to it. A runtime may generate it when source does
        not provide one.

    to
        Required MessageAddress Structure containing `endpoint` and `route`.

    replyTo
        Optional MessageAddress to which a semantic result or failure message
        is sent. It is independent of the transport-level HTTP response.

    correlation
        Optional opaque identifier relating this message to an earlier
        message. A normal reply sets `correlation` to the request's `id`.
        Correlation is not an address and cannot replace `replyTo`.

    expression
        Required ordinary LMX expression candidate admitted and interpreted by
        the receiving route's validation profile.

A MessageAddress consists of:

    endpoint
        Optional absolute base URI of the destination REST/LMX application.
        The initial network profile admits `http` and `https`. If `endpoint` is
        omitted, the current application is selected. An endpoint identifies
        the application server, not an OS thread, worker, process pointer or
        MessageThread object.

    route
        Required absolute-path reference beginning with `/`. It names an inbox
        route in the destination application's route table. A route row maps
        the path to a MessageThread inbox and declares whether the route is
        local-only or exposed by a transport adapter.

The effective remote request URI is the normalized concatenation of endpoint
and route. For example:

    endpoint = "https://archive.example.org"
    route    = "/inbox/save"
    URI      = "https://archive.example.org/inbox/save"

An application hosted below a URI prefix includes that prefix in its endpoint.
Normalization removes only the joining slash; it does not reinterpret or
decode route segments.

The hosted profile validates the two coordinates before staging a send.
`endpoint` has a case-insensitive `http://` or `https://` scheme, a nonempty
reg-name or bracketed IPv6/IPvFuture host, an optional
decimal port in 1 through 65535, and an optional absolute base path. User-info,
query and fragment components are not MessageAddress coordinates and are
rejected. The endpoint base path and `route` use printable ASCII RFC 3986
`pchar` bytes and valid `%HH` escapes; raw spaces, control/non-ASCII bytes,
backslashes, adjacent path separators and literal `.` or `..` segments are
rejected. Non-ASCII path data is percent-encoded by the producer. The runtime
preserves accepted bytes and escape spelling exactly. If the endpoint ends in
`/` and the route begins in `/`, URI construction removes exactly the endpoint's
final joining slash.

A local address omits endpoint:

    to:
        route: "/inbox/save"
    end: to

The runtime resolves that route directly and appends the message to the target
inbox without an HTTP loopback. This is an optimization only: local and remote
delivery use the same Message envelope, route contract, validation pipeline and
reply rules.

Multiple application instances may be placed behind one endpoint. Instance
selection, load balancing and failover are properties of the endpoint/provider,
not additional MessageAddress coordinates. A deployment that needs to target a
particular instance gives that instance its own endpoint or route.

The message envelope does not contain a trusted `from` field. Source may carry
an identity claim inside ordinary LMX data, but authenticated origin and
authority evidence are supplied by the local runtime or transport ingress and
validated separately. Likewise, knowing an endpoint and route does not itself
grant authority to execute the contained expression.

19.19.1.2. Message Body, External Structures and Mix Cursors

A message expression may contain its body inline, but it is not required to do
so. A message may also carry references, cursors, ranges or capabilities that
identify external LMX Structures, Mix documents, storage objects or streamable
body regions.

Inline body:

    message carries the Structure.

External body:

    message carries a cursor/reference/range/capability to a Structure.

Streamed body:

    cursor operations produce chunks, positions or projected Structures on
    demand.

Such external body references are ordinary LMX values. They are claims until
validation/merge admits them. A receiver may validate the cursor, authority,
range, lifetime and access mode before reading or writing the referenced body.

The referenced body may be read incrementally. The core message model does not
require the whole body to be present in one transport packet or one contiguous
memory block. A profile may provide cursor-based access, chunked reading,
chunked writing, range queries, lazy body loading or stream-like traversal.

Example of a short semantic record that names a larger body:

    message:
        id: "report-42"
        to:
            route: "/reports/process"
        end: to
        expression:
            process:
                body:
                    cursor: reportStore\flightLog\segment42
                    range: current
                    mode: readStream
                end: body
            end: process
        end: expression
    end: message

Mix-aware storage may support multiple cursors over the same document/body.
Cursors expose the current attribute table, Structure context, active Mix sets
and payload-local marks at their current position. Concurrent cursor use is a
runtime/storage profile concern; the language-level rule is that cursor
operations are ordinary validated LMX operations and may produce result/failure
messages like any other expression.

Therefore a small message may name or authorize a large body without carrying
that body inline. Transport envelopes carry enough LMX to identify the proposed
operation and its body references; the body itself may reside in a document
store, MO/ROM storage, local cache, service object, stream or another
profile-defined source. On slow links, the message frame can remain short while
the semantic operation stays full LMX: the receiver reads the body only as
needed and only through validated cursor operations.

The core message model does not define a second canonical wire-schema layer
with built-in binary/text negotiation, schema-version migration, unknown-field
compatibility, backward/forward/full compatibility modes, compression or
encryption semantics. A message is already an LMX expression candidate. If a
message contains archived, compressed, encrypted or externally encoded payload,
the source must say so through ordinary LMX receivers and namespace-visible
descriptors; an operation may additionally receive explicit policy Tables:

    expression:
        archive\read:
            compressedPart

    expression:
        decrypt:
            ticket
            encryptedPart

    expression:
        migrate:
            oldPayload
            targetDescriptor

Compatibility, migration and unknown-field policy are explicit descriptors and
operations of the receiving side. Compression, encryption, serialization and
parsing are ordinary namespace-resolved operations. An operation may query a
Table that it was explicitly given; no ambient table selects it.

Authorization is likewise not a transport-header convention. It is defined by
explicit verifier/policy descriptors used by the validation pipeline.
Capability claims inside a message become authority only after validation
produces authority evidence.

19.19.2. Validator / Merge

The validator receives an incoming message, a namespace environment/snapshot
and explicit policy values. Message validation is namespace/descriptor
resolution plus receiver-context, authority, effect/lifetime and implementation
checks. A Registry or Table may be one of the explicit policy values; it is not
a mandatory or ambient resolution layer.

The validator/merge stage is intentionally split into sub-stages. The exact
implementation may fuse them, but the semantic outputs are distinct:

    intake
        Input message bytes, Structure or in-memory value become an
        IncomingMessageStructure.

    receiver context selection
        The resolved endpoint/route selects a MessageThread inbox, its namespace
        snapshot and explicitly configured policy values. An endpoint/route is
        a delivery address; it does not bypass receiver or operation resolution.

    name resolution
        Names, selectors and operation heads are resolved in the selected
        namespace. Output: ResolvedNames.

    descriptor compatibility
        Argument shape, conversions and operation candidates are checked through
        the resolved descriptors. Output: CandidateExpression.

    validator/evidence
        Explicit validators run or are checked. They may accept, reject, emit
        diagnostics or create evidence. Output: ValidationEvidence.

    authority
        Sender identity and explicit verifier/ticket/capability policies are
        checked. Output: AuthorityEvidence.

    effects/lifetime
        Effect policy, ownership, borrowing, move/copy and lifetime rules are
        selected. Output: EffectLifetimePlan.

    implementation selection
        Abstract operation references are replaced with implementations admitted
        by their resolved descriptors. Output: ConcreteExpression.

    execution-plan construction
        The concrete expression, evidence and lifetime/effect plan are packaged
        into the executable unit accepted by the executor. Output:
        ExecutionPlan.

The validator does not execute the expression.

Algorithmically, Validator/Merge is a descriptor-consuming driver. It hardcodes
only general mechanics such as:

    namespace lookup;
    descriptor-role dispatch;
    evidence accumulation;
    conflict/priority handling;
    dependency cycle and termination rules;
    diagnostic construction;
    execution-plan assembly.

Domain-specific behavior is represented by namespace-visible descriptors and
explicit policy values. A descriptor may reference a Table as ordinary data.

For example:

    save(file: "report.lmx", mode: overwrite)

may validate into:

    impl: archive_save
    args:
        file: Path("report.lmx")
        mode: SaveMode.overwrite
    effects:
        filesystem_write

Validation is therefore not just yes/no. It builds the concrete expression and
execution plan that the executor is allowed to run.

19.19.3. Expression Executor

The executor consumes only an ExecutionPlan produced by validation/merge. That
plan may carry a ConcreteExpression, selected implementation bindings, evidence
and effect/lifetime rules.

It does not decide which implementation is meant. It runs the implementation
already selected by validation:

    ExecutionPlan -> ExecutionContext -> result or `throw: Failure`

The result produced here is an execution result inside the current execution
context. It is not yet a reply message merely because it exists. The consumer of
that result is defined by the surrounding context:

    local expression context        -> value consumed by the caller/expression;
    local rule/generator context    -> value consumed by generation rules;
    message request with `replyTo`    -> value wrapped as a reply ProposedMessage;
    message request without `replyTo` -> value may be discarded, logged or consumed
                                      by profile-defined local rules.

Therefore the message-boundary reply mechanism does not require a separate source-level
`return`. The ordinary L3 `return` receiver exits the current executable body
and produces the declared result value. If that executable body was run as the
implementation of a message request with `replyTo`, the message boundary
wrapper
turns the produced result into a reply message automatically.

The executor may run:

    an L2/L3 lowered function;
    a service handler;
    a scheduled message task;
    a built-in runtime operation;
    a diagnostic/failure action.

19.19.4. Logical Message Generator

After execution, logical rules may produce new messages. A generator is an
ordinary operation selected from the namespace; its descriptor may explicitly
reference a Table of generation rules.

Example rules:

    emit[SaveResult.ok][NotifyService] -> notify_saved
    emit[SaveResult.fail][LogService] -> log_error

The generator creates new proposed messages:

    message:
        to: NotifyService
        expression:
            saved:
                file: "report.lmx"
    end: message

Those messages must still pass validation at their receiving side. Generation
does not bypass the message model.

Execution may also emit messages directly. A validated expression executed by
a Message Thread may produce an ordinary result value, diagnostic, state update and
zero or more outgoing ProposedMessage records. Generated messages are not
trusted merely because they were generated by an execution step. They enter the
same validation/merge, scheduling and execution pipeline as external messages.

19.19.5. Standard Message Pipeline

The standard high-level pipeline is:

    IncomingMessage
        -> intake -> IncomingMessageStructure
        -> receiver context selection -> NamespaceSnapshot + ExplicitPolicies
        -> namespace resolution -> ResolvedNames
        -> descriptor compatibility -> CandidateExpression
        -> validator/evidence -> ValidationEvidence
        -> authority -> AuthorityEvidence
        -> effects/lifetime -> EffectLifetimePlan
        -> implementation selection -> ConcreteExpression
        -> execution-plan construction -> ExecutionPlan
        -> Executor
        -> Result or `throw: Failure`
        -> Boundary Result Consumer
        -> Logical Message Generator
        -> New IncomingMessage(s)

This replaces the older wording where message validation and message execution
were too close together.



19.20.H1. Revision-1 Descriptor/Constructor Model (Historical)

The following material through section 19.20.H4 documents the hosted
Revision-1 implementation and is non-normative. Its descriptor resolution,
per-site/per-name C layout, namespace publication, closure environment and
eager module initialization are replacement targets, not permissible
Revision-2 alternatives.

19.20.H1.1. Historical Structure Construction

For a form such as:

    Circle: circle
        radius: 10.0
        center_x: 0.0
        center_y: 0.0
    end: circle

the normative steps are:

    1. Resolve `Circle` in the namespace state at this source point.
    2. Verify that the binding supplies a structural descriptor accepted by the
       selected construction profile.
    3. Allocate one Structure in the selected current arena.
    4. Initialize its fields according to the descriptor and source body.
    5. Produce a StructureReference and, because this form requests it, bind
       that reference as `circle`.

The operation does not modify the `Circle` binding and does not create
`class.present`, `class.kind`, `class.reference-base`, `layout.backend`,
`field.class` or any other row. Repeating the construction creates another
Structure in an arena; it does not create or update a type-level entity.

The construction body belongs to the new instance. It supplies values to
fields selected from the already resolved descriptor; it does not declare,
extend or replace that descriptor. When an exact first-level field name occurs
more than once, body initializers with that name select its occurrences in
source order. A body initializer for which no corresponding descriptor
occurrence exists is a construction error. Fields omitted by the body are
initialized according to the selected construction profile.

An anonymous/bounded Structure literal may take its field shape directly from
the source Structure instead of resolving a named descriptor. It is still
allocated in the current arena. Its result binding carries the descriptor
derived from that shape, but construction creates no separate descriptor
binding or Table entry.

Top-level/module construction follows the same rule. It uses the module/root
arena selected for that execution context. A backend may realize that arena
with static-duration C storage as an optimization, but source semantics do not
contain a separate static object category.

19.20.H1.2. Historical Anonymous Structure Construction with `():`

The ordinary L2/L3 form:

    (): result
        int: count 3
        @: char text "hello"
        int: count 4
    end: result

constructs one local Structure value without first declaring or resolving a
separate named type. The receiver body is a source-ordered Structure of field
declarations. Each field declaration supplies the descriptor and exact name of
one result field and may supply one initializer. The receiver head must contain
exactly one result-binding name. It is not a variadic declaration and does not
infer a result name from a field.

The normative operation is:

    1. Read the body declarations without publishing `result` or any body field
       as a lexical binding.
    2. Build the pending result descriptor directly from those declarations.
       This descriptor belongs to the pending `result` binding; no additional
       namespace name is invented for it.
    3. If an exact `result` name is already visible, apply the ordinary
       `implements(new old Consumer)` admission rule of section 7.3.1 to the visible
       descriptor, the complete pending descriptor and the remaining known
       uses of the name. On failure, publish nothing and do not replace the
       visible occurrence.
    4. Allocate one Structure referent in the selected current arena.
    5. Initialize its field slots in logical source order.
    6. Publish one StructureReference occurrence named `result`, with the
       pending descriptor attached directly to that binding.

An invisible result name therefore introduces an ordinary local value binding.
A visible result name is a redeclaration, not an in-place overwrite. The
constructor creates no hidden class name, synthetic type entity, constructor
binding or second descriptor binding. In particular, the result name does not
become a reusable constructor merely because its binding carries the descriptor
needed for field-follow, `implements(varA varB Consumer)`, argument checking and return checking.

Explicit field initializers are evaluated once in source order. An omitted
initializer uses the initialization rule of the selected field descriptor and
profile. The hosted C profile zero-initializes an omitted primitive or admitted
machine-address field; a profile that has no initialization rule for an omitted
field must diagnose that construction. Descriptor data does not silently supply
instance defaults.

Field order and repeated exact field names are preserved. In the example above,
`result\[0]count` denotes the first `count`, `result\[1]count` denotes the
second, and unqualified `result\count` denotes the newest, second occurrence.
Repeated names contribute only one name along a used path of the
`implements(varA varB Consumer)` predicate, as specified in sections 2.1 and 19.21.3.

A field initializer may be an existing StructureReference or ArrayReference
whose binding descriptor is admitted for that field. The exact reference is
stored; the nested referent is not copied or embedded. For example, when
`child` is an earlier anonymous Structure value, an inferred field form such
as:

    (): parent
        nested: child
    end: parent

names the field `nested`, obtains its descriptor from the visible `child`
binding and initializes it with that same StructureReference. This does not
turn `child` into a language-level type or constructor. A consumer may likewise
infer a primitive field descriptor from an initializer when the selected
profile defines an unambiguous inference rule; inference is not a second
compatibility algorithm.

The empty form is present and meaningful:

    (): empty

It allocates a distinct arena-owned empty Structure, publishes a binding with a
present empty descriptor and therefore satisfies every consumer whose
`uses(Consumer varB)` is empty. It is not a null reference, missing value or
descriptor declaration.

Construction publishes no Registry or Table rows. The only namespace change is
the explicitly requested result-binding occurrence after successful admission.
An implementation may keep private layout and code-generation metadata, but
that metadata is not a namespace binding and cannot be observed as descriptor
data.

The current hosted C profile initially supports Primitive and admitted
StructureReference fields inside executable bodies and at direct module level
when every field descriptor, physical projection and initializer conversion is
inferable at translation time. Direct module-level construction uses the
source-ordered root-arena initialization boundary of section 19.29.12.2.1. A
body item without an inferable field descriptor, a dynamic field shape or an
unsupported projection is a hosted-backend diagnostic; it must not be guessed
from ANSI C syntax.

Although the source-semantic rule above admits an ArrayReference field, the
current hosted anonymous-Structure projection does not yet preserve the array
element descriptor, shape and rank needed to project such a field. This applies
both to an explicitly array-shaped field declaration and to an inferred field
whose initializer is an existing ArrayReference. The hosted translator must
diagnose either case before emitting a C typedef, allocation or initializer; it
must not discard the shape and lower the initializer as a scalar or raw C
address. Support remains pending dedicated ArrayReference-field projection.

Used-path compatibility also does not imply that two hosted C layouts are
interchangeable. Source-semantically, an anonymous StructureReference admitted
by `implements(thatReference namedRequirement substitutionConsumer)` may be supplied as that function argument, used in an admitted
plain-name rebind, or returned under that named descriptor. Those operations
retain the exact StructureReference and apply the ordinary `implements(varA varB Consumer)`
predicate; they do not require equal field types, field order or backend struct
tags.

The current hosted C projection cannot yet realize those cross-layout cases.
An anonymous construction currently has a private per-site projected C struct,
while a named descriptor may have a different projected struct. Until a
structural adapter, view or representation-independent projection is available,
the hosted translator must diagnose a value flow between distinct anonymous
and named Structure projections, in either direction, before emitting the
argument, field initializer, assignment/rebind or return. It must not rely on
an implicit C pointer conversion, an unchecked cast, coincidentally equal
member offsets or common-prefix layout. This is only a hosted backend
limitation; it does not add layout comparison to `implements(varA varB Consumer)` and does not
change the source-semantic admission result.

Source semantics also admit module/top-level construction in the selected
module or root arena. The hosted profile lowers a direct module-level `():`
site through the common source-ordered initialization mechanism of section
19.29.12.2.1; it does not emit an unowned C static aggregate. Capturing a local
anonymous StructureReference in an actual hosted nested-function closure
remains pending closure-environment lowering; until that lowering is available,
the hosted backend diagnoses the capture. The current hosted projection also
diagnoses an anonymous-construction result name that is already visible,
including a source-semantically compatible redeclaration, until it can project
multiple value occurrences without overwriting a target-language slot. An
incompatible collision is independently rejected by the normative
`implements(new old Consumer)` rule. These are projection limitations, not additional
Value kinds or source-language lifetime rules.

19.20.H2. Historical Descriptor Content and Backend Projection

A structural descriptor is an ordinary StructureReference explicitly bound in
the namespace. Its compatibility surface is the set of name paths that a
consumer actually uses; the program chooses those names and the values behind
them. A hosted C backend may derive a C `struct` declaration,
field offsets, alignment and access code from that descriptor plus compiler
metadata. Those C artifacts are a projection and are not registry facts or
language-visible values unless a program explicitly asks a backend operation to
materialize them.

Declaring that descriptor does not declare a same-name instance. Values stored
inside descriptor data, when a descriptor profile admits them, remain data of
the descriptor itself; they are not hidden defaults for an object. Initializers
for an instance belong to a separate construction operation that resolves the
descriptor and allocates that instance.

The language obtains the `implements(varA varB Consumer)` surface from the name paths of
`varB` used in `Consumer`. The hosted bootstrap currently still materializes a first-level
field-name view as a migration aid; that view is not the predicate. View
presence is distinct from cardinality: a present empty used-path set is
authoritative and is not equivalent to an absent/malformed descriptor. Binding
such a descriptor changes the namespace at that source point; it does not insert
rows into any Table or Registry.

The presence of names is sufficient for those used paths, but is
not an implicit constructor binding. Primitive bindings, imported ABI/layout
bindings and ordinary Structure constructor bindings may all expose comparable
names. A form such as `PlantBed: bed` constructs only when the
resolved `PlantBed` binding also supplies the ordinary constructor behavior of
the active profile. Thus adding virtual first-level names to a primitive or an
ABI value for structural comparison does not silently make `Type: value`
allocate a Structure.

A table may be used to author descriptor data only through an explicit
conversion followed by an explicit namespace declaration/import. Naming a
table `Circle`, `class`, `layout.backend` or `namespace` has no construction or
declaration effect.

19.20.H3. Historical Union and Variant Descriptors

There is no mandatory high-level `union:` declaration receiver. A profile that
supports variants declares an ordinary descriptor Structure whose data lists
the admitted alternatives and operations. It may internally reference a Table
or Array, but membership is visible only through that descriptor binding.

The low-level `c.union:` form is an explicit backend projection. It does not
introduce a distinct core Value kind and must not be inferred from arbitrary
table rows.

19.20.H4. Historical Hosted Bootstrap Divergence

The hosted constructor path recognizes a visible named-Structure constructor in
a form such as `Circle: circle ... end: circle`, allocates a distinct
arena-owned instance, and binds only `circle`. It reads the descriptor already
bound as `Circle` and publishes neither another descriptor occurrence nor
Registry/Table rows. Until the current-arena migration is complete, an
executable/local site selects the MessageThread root arena directly. A direct
module/top-level site receives that same root arena explicitly through the
source-ordered initialization mechanism of section 19.29.12.2.1.

Descriptor declaration does not stand in for explicit construction and creates
no fallback value. A distinct-name typed initializer such as
`Circle: alias circle` forwards the exact visible StructureReference into a
new binding slot; it does not allocate or copy another `Circle`.

The current hosted binding metadata does not yet carry referent constness for a
named StructureReference. A `const:`-wrapped named construction or typed
forwarding is therefore diagnosed before emission, both locally and at module
level, until that qualifier can be preserved by assignment and field-update
validation.

The hosted constructor path does not yet project a second physical C value for
a construction result whose name is already visible. It rejects that case
before publishing the result and identifies occurrence-aware value projection
as the missing backend facility. This is a staged backend limitation: the
source-language admission rule remains `implements(new old Consumer)`, and the early
hosted rejection neither changes that predicate nor makes a compatible result
rebinding invalid in the language.

The hosted named-Structure declaration path publishes a namespace descriptor
(a StructureReference). It must not allocate an instance. The current
bootstrap still also emits a per-name C type/layout projection; that emission
is a defect relative to the one-header projection in section 2 and must not
be required for the descriptor to exist. The hosted physical `merge:`
declaration follows the same rule: it publishes the composed target
descriptor and must not construct a merge-result instance. Either descriptor
can be used by a later explicit constructor.

A present-empty descriptor remains semantically empty. If a C aggregate used
only as a *header* still needs a complete type, a private dummy byte may
exist in that header projection only. The byte is not a descriptor field, is
not a payload slot, is not accessible through field-follow, and does not
participate in `implements(varA varB Consumer)`. It must not appear in the
anonymous field blob.

The compact hosted declaration form currently accepts typed descriptor fields
without instance initializer values. A trailing initializer in a named-
Structure declaration, an inline physical-merge descriptor source or the local
field list of a physical `merge:` declaration is rejected rather than silently
discarded or reinterpreted as an implicit instance default.

The hosted bootstrap exposes normalized `structuralFields` views for
named-structure declarations and the current physical `merge:` path. They do
not create a second descriptor symbol.

The translator may use an implementation-private symbol discriminator to tell
whether a visible descriptor also supplies the hosted constructor behavior.
That discriminator is neither a source Value kind nor a class, role, Table or
additional language-visible descriptor category. Source semantics remain the
ordinary namespace descriptor plus whatever constructor behavior the active
profile explicitly supplies.

The namespace declaration core used by either path fully constructs a pending
descriptor, checks a captured old descriptor with the same predicate as
`implements(new old Consumer)`, and publishes the new occurrence only after that check
succeeds. A failed comparison leaves the namespace unchanged. This is the
source-semantic admission rule; a hosted target may still fail before
publication when it cannot represent an admitted occurrence, as described
below.

The hosted backend does not yet project every same-name namespace occurrence as
an independently addressable Structure/Table row. Ordinary lookup and current
typed lowering use the newest admitted descriptor. Older same-name occurrences
remain namespace state for scope restoration, but explicit source access to a
chosen descriptor occurrence and separate target-type projection of that
occurrence sequence are pending work. The ANSI C collision/fingerprint rules
may consequently reject or suppress a physical layout emission that the source-
level used-path predicate admits; that is a documented backend limitation,
not an additional source-language compatibility rule.

The current hosted translator admits and publishes a structurally identical
repeated named `Structure` or physical `merge:` descriptor and may suppress its
redundant target type declaration. It rejects a compatible but non-identical
repeat before publication because that case requires occurrence-aware target-
type projection. This hosted-backend rejection happens after applying the same
descriptor predicate; it does not make the redeclaration invalid in the
language or remove the admitted occurrence behavior of the namespace core.

Function-local named-Structure descriptors are no longer declared by a separate
function-body prepass during the module declaration phase. When their hosted C
typedefs must precede function bodies, the prelude emitter performs one bounded
two-pass replay inside a temporary namespace scope: it first declares the
function parameters and the directly contained named-Structure descriptor
declarations, then emits their typedefs, and finally leaves that scope.
Descriptors created by this replay do not survive into the later function-body
phase; the body creates its own lexical bindings when it is emitted.

The replay hoists a local typedef only while that declaration is compatible
with the translation-unit projection already emitted at the same canonical C
name. If another function has already hoisted a different local declaration,
the later declaration remains a true block-local typedef and may shadow the
outer C name. An incompatible outer declaration is not a source-language type
conflict and is not diagnosed by the block-local dominance check.

The temporary replay declares descriptor bindings only inside its bounded
namespace scope. Hosted C typedef deduplication is held in the current output's
projection state, not in that lexical scope; it neither extends descriptor
lifetime nor creates Registry data.

The source field stream of the published descriptor is the semantic shape.
A compiler-private `structuralFields` cache of that stream is not a second
descriptor, not a C `typedef`, and not a source value. Named-structure and
physical `merge:` declarations must not publish implicit `owner.field.*`,
`class.present`, `class.kind`, `class.reference-base` or `layout.backend`
Registry rows. They must not emit instance storage. The explicit named-
constructor path separately allocates a StructureReference (header plus
anonymous blob) for the requested value. A per-name C type, if the current
bootstrap still emits one, is projection only.
Repeated target declarations are suppressed only when the
implementation-private per-output projection state described in section
20.2.1.1 proves that the earlier target declaration is identical and is present
wherever the later declaration would be present.

Layout collection, declaration/type-head recognition, top-level lowering,
typed field-chain resolution, physical `merge:` source admission and L2
inline-Table field-type resolution consult the descriptor visible in the active
namespace first. The descriptor's field stream is authoritative, including when
it is empty. A compiler cache of that stream must match it; it must not invent
C members. A named Structure can therefore be used by later declarations and as
a merge source without `class.present` or `layout.backend`. A missing or
malformed field in a present stream does not fall through to Registry data.

All hosted C declaration, signature, field, callable-adapter and ABI projection
paths receive the active namespace. The descriptor field stream supplies
semantic shape only. L2 `@ⁿ` depth applies to typed address slots, not to
StructureReference, ArrayReference or callable Structure (section 11.2).
A C function-pointer spelling has no source address depth. Explicitly
authored ABI reference/layout metadata remains a physical-projection or
compatibility fallback for *imported* names; it may coexist with a descriptor
field stream but cannot change that stream's names and cannot reclassify an
ordinary named Structure as a C pointer kind. Named-structure and physical
`merge:` declarations must not emit that ABI metadata.

Registry field relations are consulted only when the namespace binding has no
structural-field view. This preserves explicitly authored or imported ABI
layouts and remaining legacy producers such as L2 Table row layouts and `fm`
return layouts. The fallback does not publish those rows into the namespace
descriptor and does not make Registry a second source-semantic lookup
environment.

The current hosted C named-layout path is a backend type projection, not a value
materialization path. Remaining generic top-level backing and explicit ABI
Registry fallback are separate implementation debt; neither defines source
semantics or restores an implicit instance to a descriptor declaration.



19.21.H. Revision-1 Namespace/Descriptor Dispatch (Historical)

The remaining old subsections through 19.21.H5 are retained only to document
hosted behaviour and syntax examples. Their active Namespace, binding overlay,
descriptor dispatch, per-name layout and direct C-parameter assumptions are
non-normative replacement targets.

19.21.H1. Historical Operation Dispatch through Namespace Bindings

An operation binding identifies either a directly callable implementation or
an explicit operation descriptor containing the admitted implementations and
their argument/result contracts. A method is an operation entry explicitly
exposed by a candidate descriptor. It is not a hidden backend-class member and
is not discovered by searching unrelated tables.

Conceptually, a multiple-dispatch operation descriptor may contain:

    draw[(Circle, Canvas)] -> draw_circle_on_canvas
    draw[(Button, Canvas)] -> draw_button_on_canvas

This notation describes data reached from the descriptor bound as `draw`; it is
not a global registry relation or new source grammar. The descriptor may
represent the mapping with Structures, Arrays or an explicitly referenced
Table.

Dispatch proceeds as follows:

    1. Resolve the operation name in the active namespace.
    2. Obtain the operation descriptor from that binding.
    3. Obtain argument descriptors from visible bindings and the statically
       established expression state, or through an explicit runtime descriptor
       operation when a profile admits dynamic dispatch.
    4. Select one implementation admitted by the operation descriptor.
    5. Diagnose absence or unresolved ambiguity.

A profile may define fallback, priority or conversion inside the operation
descriptor. No arbitrary table participates merely because it is visible as
data. Constructing an instance does not add an implementation, method,
overload or dispatch coordinate.

19.21.H2. Historical Receiver and Operator Bindings

A receiver binding tells a consumer how a Frame head interprets its argument
Structure. An operator binding tells an expression consumer how a normalized
operator-token form is interpreted.

A receiver or operator enters the namespace only through an explicit
declaration, import, admitted plain-name rebind, or initialization of the
namespace by the selected language profile. Profile initialization is
conceptually an explicit initial namespace; it does not make every runtime
table part of name resolution.

Operator tokens are parsed as operator fields rather than bare identifiers. The
same namespace view may index their bindings by normalized operator identity,
including prefix, postfix, infix and index roles. This is not a separate
source-semantic namespace.

A receiver descriptor records its consumption role, signature and handler
binding. An operator descriptor records its operator role, operand/result
contracts and implementation or dispatch descriptor. A named table declaration
may explicitly bind the resulting Table reference; its row keys, column names
and cells do not thereby become namespace bindings.

The current hosted bootstrap constructs part of its initial receiver/operator
state from tables named `namespace`, `receiver.*` and `operator.*`. This is an
implementation mechanism for producing the initial namespace, not the
normative meaning of those tables and not permission to query arbitrary
RegistryView rows during ordinary name resolution.

19.21.H3. Historical Descriptor-Based `implements`

`implements` is an expression receiver with the form:

    implements(varA varB Consumer)

`varA` and `varB` are single namespace-name atoms, including exact quoted names
when required by the identifier rules. Each of those names resolves to a binding
that carries a descriptor. The binding may be an explicit descriptor declaration
or an ordinary Primitive, StructureReference or ArrayReference value binding
with its descriptor attached. `Consumer` is a namespace name of a block,
function, module body or other Structure whose P0 tree is walked. `implements`
reads the descriptors of `varA` and `varB` and walks `Consumer`; it does not
evaluate, copy or otherwise consume the values of `varA` and `varB`. Thus an
anonymous construction result from section 19.20.1.1 may be an operand by its
result-binding name; this does not create a synthetic type entity for that
result.

There is no two-argument form. A translator or interpreter that applies the
predicate at rebind, argument or return supplies `Consumer` itself; that is not
a source receiver.

A descriptor exposes names along paths. For example, the structural declaration:

    A:
        E: b
        F: c
    end: A

exposes the names `b` and `c`. Nested names participate only when Consumer
actually follows them. Constructor/type heads `E` and `F` do not participate. Primitive
descriptors are ordinary Structures (section 2.2.2). A Primitive leaf is
admitted by the leaf rule in section 2.2.3, not by a second algorithm and not
by a new primitive kind.

The source-semantic evaluation algorithm is:

    1. Resolve `varA` in the active lexical namespace.
    2. Resolve `varB` in the same namespace view.
    3. Resolve `Consumer` to a P0 tree (block, function body, module remainder, or
       explicit Message consumer / used-path list).
    4. If `varA` or `varB` is unresolved, or `Consumer` has no walkable tree and no explicit
       used-path list, report a diagnostic and produce no boolean result.
    5. Obtain the candidate descriptor from `varA` and the requirement descriptor
       from `varB`. If either binding lacks the required descriptor role, report a
       diagnostic.
    6. Collect `paths = uses(Consumer varB)`: syntactic name paths of `varB` in
       Consumer (field-follow / `\`, and nested access in the same Consumer
       after an argument whose expected descriptor is `varB`). Do not count a
       mere declaration of `varB`. Do not follow aliases, callees, computed
       names or heap storage.
    7. For every path, descend the candidate descriptor by those exact names.
       Unqualified names select the newest occurrence (section 2.3). A missing
       name produces `false`. Nested unused structure is not expanded.
    8. When the walk stops at a Primitive leaf, apply section 2.2.3: empty use
       is true; a word-moving use is true when conversion is not forbidden and
       a merge-keyed converter exists or the descriptions already match; fields
       of the primitive description that Consumer actually follows are ordinary
       used paths. `implements` does not invoke the converter.
    9. Produce `true` when every collected path is present and every primitive
       leaf is admitted (an empty path set is `true`); otherwise produce
       `false`.

Equivalently:

    implements(varA varB Consumer)
        iff every path in uses(Consumer varB) is present on varA
            and every primitive leaf of those paths is admitted as in 2.2.3

The translator or interpreter, on the substitution edge where this predicate
was applied, selects a merge-keyed converter if step 8 required one and
inserts that receiver call. Converter failure is a receiver diagnostic at that
edge, not a boolean `false` from `implements`. See section 2.2.4.

Order, duplicate count, the values behind unused names, unused nested contents,
signatures, mutability and other metadata do not affect this predicate.
`validate` is not a hook: if a used path names it, the candidate must expose
that ordinary name along the path.

Name equality is not checked before namespace resolution. Consequently,
`implements(X X Consumer)` is an error when `X` is unresolved. When `varA` and `varB`
resolve to the same valid descriptor, the used-path comparison still determines
the result.

Absence of a descriptor or of its name view is not an empty consumer; it is
malformed/unresolved and produces a diagnostic.

`implements` only reads namespace state and the consumer tree at its source
point. It does not modify the namespace, create evidence rows, materialize a
`satisfies` relation or register either descriptor. If a Table is used to author
descriptor data, an explicit declaration/import must first bind the converted
descriptor.

The source-semantic result is boolean. ANSI C lowering may represent `false`
and `true` as integer constants `0` and `1`.

A translator applies this algorithm while lowering a statically known namespace
state and a known consumer tree. An interpreter applies the same algorithm
against its current namespace state and the current consumer tree. An operation
over arbitrary descriptor or Registry values that are not resolved as namespace
names may use another receiver, but it does not redefine `implements`.

Example. `Equatable` exposes `equals`. `User` exposes `equals` and `hash`.
`Consumer` calls `item\equals`. Then `implements(User Equatable Consumer)` is true
when both descriptors were explicitly declared or imported into the active
namespace. A different Consumer that also uses `hash` as an `Equatable` path
would demand that path of `User`.

Example, two thicknesses. `File` is a Structure with `handle`, `close` and
`read`. `FileManager` calls `f\close` and `f\read`. Then
`implements(u32var File FileManager)` is false: a word has no those paths.
`implements(myFile File FileManager)` is true when `myFile` provides them.
The same `File` as consumer of a primitive `FILE` word that it stores in
`handle` has a thin Consumer; `implements(u32var FILE File)` may be true under
section 2.2.3, and the translator inserts the merge-keyed converter on that
edge. Putting `u32` into `File` by `merge` means `File` has a word field; it
does not mean `File` is `u32`.

The hosted bootstrap currently still evaluates a two-name first-level subset
internally as a migration gap; that is not the language form and must not be
written as a two-argument source receiver. Field types, indices, order, pointer
depth, constness, array shape, legacy `requires.method`, `method`, ordinary
descriptor rows and `default` tables are not consulted. See section 21.7.

Compatible redeclaration uses this same predicate over two descriptor values
and a remaining consumer, but it does not perform the name-based expression
`implements(Name Name Consumer)` through ordinary lookup. The declaration consumer
captures the old descriptor, fully constructs the pending new descriptor without
publishing it, evaluates `implements(new old Consumer)` with Consumer the remaining known
source that still sees the name, and publishes the new binding occurrence only
when the result is true.

19.21.H4. Historical Generic Operations

A generic operation is an ordinary operation binding whose descriptor admits
more than one argument contract. It is not a separate mechanism and does not
begin as unresolved global table coordinates.

For `x = y`, the expression consumer resolves the `=` operator in the active
namespace, obtains the visible descriptors of `x` and `y`, selects an admitted
implementation from the operator descriptor, and obtains the result descriptor
from that operation contract. The descriptor may explicitly reference a Table
as dispatch data; the resolver never searches a global table named `equals`,
`class` or any other conventional name.

19.21.H5. Historical Conditional Forms

A conditional form is consumed by a visible conditional receiver binding. Its
descriptor defines condition, branch and result roles and selects the relevant
interpretation or lowering. A condition may explicitly call a table query or
rule engine, but `if` does not implicitly select descriptor or registry rows.



19.22.H. Revision-1 Descriptor Evidence Profile (Historical)

Subsections 19.22.1 through 19.22.4 below are retained for examples and hosted
implementation history. Their `StructureReference`/`ArrayReference`, visible
descriptor, Namespace, descriptor graph, owner and Validator/Merge language is
non-normative. Descriptor-like records shown there may survive only as
ordinary explicit Lmx data under the rules above; array representation remains
separately unresolved.

19.22.1. Ordinary Data Rule

Descriptor, dispatch, validation, message and authority information may be
stored in ordinary Structures, Arrays or Tables. Storage does not activate the
information. A validator receives its namespace-visible descriptors and any
Registry, EvidenceStore or policy Table as explicit operands.

Examples:

    Circle.field.class[radius] = double
    plus[u32][u32] = plus_u32_u32_l2
    equals[String][String] = string_equals
    validator[LightPassenger][Person] = check_weight
    accepts[ArchiveService][save] = save_message_validator
    authority[user42][ArchiveService.save] = allowed

19.22.2. Evidence

Evidence is an ordinary StructureReference or ArrayReference recording why an
expression was resolved, validated or authorized. It may be compile-time or
runtime. A validator creates evidence when it successfully checks a message or
value against explicit descriptors and policy values.

19.22.3. Validator Evidence

A validator is an explicitly resolved operation that checks data and may create
more specific evidence values. A profile may represent its rules in a Table:

    validator[LightPassenger][Person] = check_weight
    guarantee[LightPassenger][weight] = "<80"

If validation succeeds, later operations may consume a stronger
`LightPassenger` evidence descriptor/reference.

A validator is not required to be a boolean predicate. It may produce:

    acceptance;
    rejection;
    diagnostic;
    stronger evidence;
    obligation for a later stage;
    explicit continuation key;
    conflict/empty/forbidden diagnostic.

Validator dependencies form an ordinary descriptor/value graph. The
Validator/Merge driver must define cycle detection, memoization and
termination/diagnostic rules for the explicit graph it receives.

Projection validators are ordinary validators. A hosted C99 profile may pass
Tables such as `c99.ub.policy` to them as configuration. These rows are profile
data, not a hidden C analyzer or an ambient registry in the language core.

19.22.4. Evidence Lifetime

Evidence is valid only while the descriptors, explicit policy values and memory
state that produced it remain valid. If a value mutates, crosses an arena/owner
boundary or loses authority, dependent evidence is invalidated.



19.24.H. Revision-1 Namespace Consumption Profile (Historical)

Subsections 19.24.1 through 19.24.5 below are retained as a terminology sketch.
References there to a target namespace context, namespace-visible operation
descriptors, state owners or semantic temporary bindings are non-normative.

19.24.1. Procedural Consumption

Procedural consumption runs a resolved expression in an execution context. It
is the executor stage of the message pipeline when the expression originated in
a message.

19.24.2. Object/Event Consumption

Object/event consumption is message validation plus execution against the
target namespace context, explicit policies and state owner.

19.24.3. Functional/Expression Consumption

Functional consumption resolves namespace-visible operation descriptors without
requiring a stateful receiver. If every selected operation is pure, the
expression is pure.

19.24.4. Logical Consumption

Logical consumption derives new values or messages from explicit input data and
results. It belongs to the logical message generator.

19.24.5. Query, Rules and Unification

Rules are ordinary expressions. A rule may receive a Table/Registry, introduce
temporary variables, perform an explicit query, rank candidates and return a
new Table or messages. The same syntax can be used by an interpreter and by
ordinary L3 code.



19.25.H. Revision-1 Namespace/Descriptor Lowering Profile (Historical)

Subsections 19.25.1 through 19.25.6 below are retained for provider examples,
candidate tables and hosted implementation history. Their runtime Namespace,
visible callable/provider descriptor, per-shape argument/return, ordinary C
field projection and eager module assumptions are non-normative. Raw `c.*`
examples remain usable only as explicit L1/L2 foreign substrate; Table examples
remain ordinary explicitly supplied Lmx data.

19.25.1. Pipeline

The high-level pipeline is:

    source LMX
        -> P0 Structure
        -> namespace and descriptor resolution
        -> ExecutionPlan
        -> execution or L1/L0 lowering

An explicit Table/Registry query may occur as an ordinary resolved operation;
it is not a mandatory pipeline stage.

The current bootstrap may merge some of these steps in ANSI C. That is an
implementation stage, not the high-level model.

19.25.2. File Extensions and Level Semantics

Both `.lm2` and `.lm3` modules may construct configuration/Registry/Table values
and describe messages, services, runtime policy, startup and query rules. Only
explicit declarations/imports change the namespace. `.lm2` additionally admits
the low-level machine operations defined in section 20.

19.25.3. Arguments and Return Lowering

Argument and return handling is defined by callable descriptors visible in the
namespace. A backend may use explicit configuration mappings such as:

    parameter_shape[fn][...] -> lowering rule
    return_shape[fm][...] -> result structure rule

The source rule remains that Structures are data. A Structure is lowered as a
call only when its head resolves to a callable/receiver descriptor.

19.25.4. ANSI C Projection

ANSI C projection is a backend operation. It may consult explicitly supplied
lowering Tables whose entries describe:

    C type name;
    C function call;
    inline C operator;
    C struct field;
    pointer access;
    raw `c.*` surface.

`c.*` is a permanent door to the ANSI C namespace/surface. It is not a normal
Lingvamyxa namespace lookup. High-level descriptors should instead refer to a
backend binding such as `sqrt_ansi_c` or `plus_u32_u32_l2`; an explicit backend
profile may map that binding to `"sqrt"` or `"+"`.

19.25.5. Provider and Device Profiles

External libraries, native services, device boards and remote modules are
provider bindings/descriptors explicitly visible in the namespace. They are not
part of source syntax and not semantic parents of the language.

A provider may be:

    CPU/L1 primitive lowering;
    ANSI C library binding;
    bundled bootstrap library such as GMP, MPFR, decNumber, PCRE2, SQLite,
    yyjson, libcurl, CivetWeb, libsodium or another hosted library;
    generated L2/L3 executable;
    analog, photonic, routing, neural or ROM-backed device module;
    remote service binding.

The same source expression may resolve through different explicitly imported
provider descriptors in different namespaces. A provider descriptor may use
ordinary Tables such as:

    table:
        name: `sqrt.dispatch`
        columns: class (result char) (implementation char)
        rows:
            BigFloat BigFloat sqrt_mpfr
            fixedQ16 fixedQ16 sqrt_ana
            f64      f64      sqrt_ansi_c
    end: `sqrt.dispatch`

    table:
        name: `implementation-->L2 lowering`
        columns: class (symbol char)
        rows:
            sqrt_mpfr   "mpfr_sqrt"
            sqrt_ana    "ana_sqrt"
            sqrt_ansi_c "sqrt"
    end: `implementation-->L2 lowering`

    table:
        name: providerOf
        columns: class (provider char)
        rows:
            sqrt_mpfr MPFR
            sqrt_ana ANA_SQRT
            sqrt_ansi_c CPU_C_Libm
    end: providerOf

The namespace-visible `sqrt` provider descriptor explicitly references
`sqrt.dispatch`; the distinct Table binding does not replace the operation
binding.

On a hosted bootstrap machine, `ANA_SQRT` may be simulated by an ANSI C wrapper
around libm or MPFR. On another target, the same binding may lower to a physical
analog board instruction. The source-level `sqrt` expression does not change;
the explicitly imported descriptor/backend profile does.

Provider selection proceeds through the resolved descriptor:

    namespace lookup selects an operation descriptor;
    that descriptor selects an admitted binding;
    explicit provider data describes who/what executes the binding;
    validator checks effects, authority, precision, latency, determinism,
        confidence, calibration, lifetime and fallback policy;
    ExecutionPlan fixes the selected binding so hot execution does not resolve
        provider choice again.

This discipline lets heavy hosted libraries act as earth-bootstrap surrogates
for heterogeneous expansion boards without making those libraries part of the
language. Examples:

    MPFR / GMP / decNumber  -> high-precision math providers;
    FFTW / BLAS / LAPACK    -> signal/matrix provider surrogates;
    PCRE2                   -> pattern/matcher provider;
    SQLite                  -> registry/storage provider;
    yyjson                  -> external adapter provider;
    libcurl / CivetWeb      -> transport/service envelope providers;
    libsodium               -> crypto/auth provider.

Direct `c.*` calls remain possible in L2/L1 substrate code, while ordinary
high-level L2/L3 semantics use namespace-visible operation/provider
descriptors. Replacing MPFR with an `ANA_LOGEXP` provider requires an explicit
import/configuration change, not a rewrite of the source expression.

19.25.6. Codec and Persistence

`toLmx` and `fromLmx` are proposed operation names, not intrinsic parser forms
or current bootstrap receivers. The current code has internal Table-to-LMX
helpers but no generic `fromLmx` operation. A profile that exposes either
operation must bind its callable and codec descriptors explicitly. Every
serializable value should have an explicit codec contract.

An explicitly constructed Registry may be persisted as LMX files, database rows
or cached binary indexes. LMX remains one possible source form.

Portable persistence is structural LMX serialization, not memory imaging. A
runtime may materialize Structures and Arrays using any physical
representation that implements their selected arena contract, but a portable
persistent form records admitted LMX Structures/Arrays, explicit Registry data,
messages, evidence and Message
Thread logical state through codec operations such as `toLmx` and `fromLmx`. Raw process memory,
allocator state, native handles, alignment, endian order and ABI layout are not
portable LMX state unless a profile admits an explicit codec for them.

Binary serialization, if introduced, is a profile-specific codec. Endian and
binary layout belong to that codec profile, not to ordinary LMX source
semantics.



19.28.H. Revision-1 Hosted Message/Thread/Mix Profile (Historical)

Everything from the legacy `19.28.1. Scope` heading below through the end of
section 19.28 is retained for implementation history, algorithms and examples
only. Its concrete C types, worker providers and delivery algorithms remain
historical, but its one-arena ownership, FIFO queues and non-overlapping turns
of one Message are implementations of Revision-2 semantic invariants. It is
non-normative wherever it prescribes a particular arena splice/join algorithm,
an ontology for Mix contrary to its Message-based target, Message
Namespace state, descriptor or
binding dispatch, closure/environment parameters, `StructureReference` or
`ArrayReference` as the final ontology, hidden `LmMessageThread` arguments, or
the old uniform `entry(callable->node)` ABI which omits declared/dynamic values.
Hosted scheduler and
transport code may survive as infrastructure wrappers only when it obeys the
Revision-2 boundary above.

19.28.1. Scope

A Message is a complete LMX machine, not a small envelope. An L3 Thread is
that Message admitted to its own serial execution lane (section 19.28.5), not
necessarily assigned a dedicated OS thread. The
machine has:

    the Message's LMX graph (Structures, arrays, Mix overlay as ordinary
        referents);
    one arena, as the implementation of that graph's storage;
    current Structure graph and scheduler/diagnostic context when running;
    FIFO inbox/outbox queues;
    validation/policy-combination stage, distinct from runtime tree-copy merge;
    executor;
    logical message generator;
    optional application Registry/cache references.

It is not necessarily an operating-system thread. Inside one running Message
at most one callback executes at a time (section 19.28.11.1).

19.28.2. Message Thread

A running Message (an L3 Thread) holds:

    root state in its own graph;
    exactly one owning arena;
    current-turn scheduler/diagnostic state;
    FIFO inbox/outbox queues;
    optional Registry/Table state;
    validator and executor policy;
    diagnostics/failure state.

No raw mutable Lmx reference owned by one Message may point into another
Message's mutable storage in the default profile. Explicit immutable
address-domain pools and explicit foreign handles follow their declared
lifetime profile. In-process delivery may transfer or join storage only under a
separately specified operation.

In this section, "current" or "executing" Message Thread means the explicit
runtime actor selected by the scheduler. It is infrastructure state, not an
extra source-method argument. A scheduler callback may receive an actor handle
and adapt it to a source callable, but every Revision-2 source method itself is
invoked through its exact `all_methods_array {addr,sig}` contract as
`entry(callable->node, declared_actuals..., dynamic_values...)`. If source code
needs access to a Message/actor value, that value must be an explicit Lmx value
supplied as a declared/dynamic input or reached through an explicit graph link.
It is not looked up through a reified runtime namespace, process-global state or
TLS.

19.28.2.1. Message Thread Graph Context and Optional Data Caches

A Message Thread carries no reified runtime Name-to-Binding namespace object.
Source name resolution performed by the translator selects own C working values,
declared values, hidden dynamic values, direct Lmx links, relative structural
traversal, explicit root-relative traversal or callable-pool links. Runtime
arbitrary-text lookup receives an explicit root and walks the current graph
using the `Lmx * -> ShortNameId` reverse index. Method entry receives the
containing Lmx Structure plus the declared/dynamic values named by its exact
signature; no actor context or reified namespace is pushed, merged or popped
around a call.

A Message Thread may additionally own ordinary Registry, RegistryView, Table or
cache references as application/profile state. Such values may contain service
policies, device data, evidence indexes or query material. Validation queries
them only when an explicitly resolved operation receives them.

A cache may index explicit policy values, evidence, validated paths,
address-domain classifications, ShortNameId comparisons or ExecutionPlans. It
is an implementation optimization and must not become a `Name -> Binding`
environment, class universe or type system. Adding a row to an optional
Registry/cache never changes structural lookup or method visibility; changing
the graph requires an explicit graph operation.

Persistent Registry values may live in LMX files, ROM/MO records, databases or
binary indexes. They remain ordinary data. Changes may invalidate caches or
emit messages only under an explicitly installed reactive operation/profile.

19.28.2.2. Root Process, Turns and Cooperative Stop

Message Thread is an L2/L3 runtime reading of a Message: the Message has been
admitted to its own serial L3 execution lane. That lane may migrate among host
workers and is not necessarily a dedicated OS thread. It is not a source level. Every
generated standalone process begins with one root Message, running. Applications,
tests and bootstrap tools use the same rule; a build utility is not exempt merely
because another build stage launches it.

The process entry runs in an unbounded turn loop. Its abstract shape is:

    initialize the root Message and ExecutionContext
    while the Message Thread state admits begin-turn
        reset turn-local diagnostic state
        dequeue/check at most one FIFO inbox item
        execute one root-body or message-handler step
        commit staged outgoing work in FIFO order
        complete required turn cleanup
        run current-Message-Thread collection
        if stop was requested, change STOPPING to STOPPED
    restore the enclosing host execution context
    return the retained Message Thread status

The loop has no predetermined iteration count. It ends only after a cooperative
stop request or a fatal diagnostic/runtime condition is converted into a
failure-dominant stop request and the common end-turn boundary is completed.

Every generated standalone `main` creates one application
`LmMessageThreadRuntime` and one unpooled root `LmMessageThread`, attaches that
root explicitly to the runtime, installs its ExecutionContext and drives
`begin_turn` / body / `end_turn` on the invoking host thread. This attachment
makes the same FIFO outbox and route table available to the root; it does not
put the root into a worker pool. If the translation declares or ordinarily
imports any `thread:` handlers, the generated entry additionally constructs a
pool in that runtime, creates one mailbox actor per declaration, starts it and
binds its exact route. A translation without `thread:` declarations still has
the application runtime and attached root but needs no pool or host worker.

The pool ABI creates an explicit `LmMessageThreadRuntime`, one or more
`LmMessageThreadPool` objects and pool-owned Message Threads. For a pooled
Message Thread, one invocation of its entry callback is one actor turn.
`end_turn` runs local collection. A step actor that remains RUNNING is appended
to the pool's FIFO ready queue for another turn. A mailbox actor is appended
only while its FIFO inbox is non-empty; an empty mailbox is idle rather than
busy-spinning. STOPPING becomes STOPPED at the same boundary.

A pool never executes two turns of the same Message Thread concurrently.
Different Message Threads may execute concurrently up to the pool's worker
count, and one Message Thread may migrate between host workers from turn to
turn. Its arena and durable state belong to the Message Thread, not to a host
worker. During a callback, the actor temporarily records a pointer to the
turn-local ExecutionContext on the executing host stack; the runtime restores
the previous association before that turn leaves the worker.

The native providers wait on the pool condition when no actor is ready. The
`single` provider advances the same FIFO cooperatively while the controller
joins or deletes pool work. Runtime mailbox actors, local inbox/outbox dispatch
and the source `thread:` and `send:` receivers are implemented. Reply,
message validation and remote transport remain future work. A non-mailbox
RUNNING actor whose callback does not request stop remains immediately
runnable. An idle mailbox that is stopped individually or by pool stop is
scheduled for a final stop-only boundary so join cannot wait forever.

After the root completes its final turn, generated teardown detaches it and
requests pool drain. Drain freezes actor/route creation but continues processing
messages already committed to existing routes, including messages generated by
those handlers. Only global quiescence -- no ready or executing actor and no
processable current, inbox or outbox work -- converts the pool to STOPPING.
Generated teardown then joins the declared actors, deletes the pool and runtime,
and releases the root. A startup or lifecycle failure that prevents orderly
detach uses hard stop instead. A nonzero root result by itself is not such a
failure: messages committed by earlier successful turns are still drained.
The current drain primitive is pool-local. A generated source application has
one runtime and at most one application pool, so its application-wide `exit:`
coordinates that root and pool. Several pools in one low-level runtime, or
several independently constructed runtimes, require an explicit host
controller and are outside the current generated source profile.

`stop:` requests termination of the explicitly executing Message Thread:

    stop:
    stop: statusExpression

An omitted status is zero. The optional expression is evaluated at the call
site and converted to `int`. An accepted ordinary request changes RUNNING to
STOPPING and records its status. Further ordinary stop requests are ignored, so
the first accepted stop wins. A fatal diagnostic or collector/runtime failure
is a different channel: it may replace the status recorded by an earlier
ordinary stop with its nonzero failure status, even when that ordinary status
was already nonzero.

Stopping is cooperative. `stop:` does not perform a hidden return, long jump or
scope exit. The current fn/sub/block continues normally and its explicit
control flow and generated cleanup remain visible. A `stop:` executed by a
nested function still targets the explicitly carried Message Thread rather
than merely that function, but the nested function continues until its own
ordinary control flow leaves it. At end-turn, collection runs once, then
STOPPING becomes STOPPED and the loop condition rejects another turn.

For compatibility with existing standalone programs, a `return` in the
generated external process entry is lowered as described in section 19.7:
evaluate the status once, run active generated cleanup, request stop, and reach
the common end-turn boundary. Returns in all other functions remain ordinary
function returns.

`exit:` requests termination of the generated application:

    exit:
    exit: statusExpression

The omitted status is zero and the optional expression is evaluated once and
converted to `int`. The first accepted request selects the ordinary application
exit-request status. Like `stop:`, `exit:` is cooperative: it performs no
hidden return, jump or lexical unwind. The requesting Message Thread continues
along visible source control flow to its common end-turn boundary.

Shutdown has a request phase and a ready phase. The requester becomes STOPPING,
commits its current outbox, finishes current-message cleanup and collection,
and then publishes the exit as ready. A delivery, diagnostic or collector
failure in that final requester turn replaces the ordinary requested status
with the effective failure status. Deliveries from other turns which reach the
runtime only after ready are cancelled as shutdown work rather than reported as
new route or transport failures.

The generated root observes exit state only at turn boundaries. With the
`single` provider it pumps at most one actor turn at each such safe point, then
reads the state again; native providers advance actors on their workers. Once
ready is observed, the controller stops the pool. If the root was not itself
the requester, it enters one synthetic final root turn, requests root stop and
reaches the ordinary common end-turn boundary without executing user body.
Teardown joins declared actors and workers, deletes the pool, detaches and
releases the root, deletes the runtime, and only then returns the selected
status to the host. Actor code requests this sequence but never joins itself.
Final status preserves an existing nonzero effective root status first, then a
nonzero selected application exit status, then the first nonzero declared actor
status, and finally cleanup failure. This distinguishes the application exit
request from an earlier independently selected root failure/status.

The current generated profile deliberately has one runtime and at most one
pool. Application-wide coordination across several manually constructed
low-level runtimes or pools remains the responsibility of their host
controller.

19.28.3. Root State and Handler Frame

Root state is durable state in the running Message's graph.

A handler frame is created when a validated Message is executed. It has local
temporary bindings, cleanup entries and diagnostic context. Its ordinary
Structure and Array bindings are reference slots into this Message's graph.
There is no nested handler arena and no detachable-branch owner. Temporary
referents that remain reachable from the Message root survive end-turn
collection; the rest are dropped with that collection (section 19.29).

19.28.4. Cleanup and Control Exit

Cleanup is local to the current running Message. Control exits such
as `return`, `throw`, `break`, `continue` and cancellation must run required
cleanup before end-turn collection. Collection must not release a referent
that is still reachable through a published return/reference root. A Structure
or Array return first publishes its exact existing reference under the rule in
section 19.29.5; frame cleanup never copies, moves or rematerializes the
returned aggregate.

`stop:` is not an immediate control exit. It changes Message Thread state and
the current execution reaches cleanup through its ordinary visible control
flow. The stopping safe point is the common end-turn boundary.

19.28.5. Message, L3 Thread and Template

A Message is full LMX: a graph of Lmx Structures with any Mix placement/value
projections that belong to that message. It has no runtime lexical namespace.
Scheduler, routing, diagnostics and explicit policy data are runtime roles or
ordinary graph data, not name-resolution state. A Message is not merely a byte
envelope with a small header. Constructing one from a template is an explicit
runtime graph operation; there is no second "lightweight message" ontology.

Mix is to be rewritten into cooperating Messages for concurrency and scaling
(section 19.29.2.1). The current Java implementation has not completed that
rewrite, and a Mix document is not synonymous with a single Message.
Exactly one logical arena is owned by each Message. The physical arena may be a
bump pointer plus backing blocks, another non-moving allocator or a conforming
moving collector; those details are not part of the Lmx header. L3 does not name
allocator internals.

An L3 Thread is a Message admitted to its own serial execution lane.
Inactive Messages have an arena and a graph and have not begun a turn.
Running Messages are L3 Threads. The same ontology covers both: there is no
Thread kind separate from Message.

19.28.5.1. Message pipeline names

Message states:

    IncomingMessage / ProposedMessage
    CandidateMessage / CandidateExpression
    ConcreteExpression / ExecutionPlan
    ScheduledMessage
    ExecutedMessage
    FailedMessage

`ConcreteMessage` or `CandidateMessage` may be used as an implementation name
for a message after descriptor/signature resolution but before all authority/effect
validation has completed.

19.28.6. Historical Hosted Delivery: Join, Activate, Serialize

Historical scope: this subsection is part of 19.28.H, including its use of
`StructureReference`, `ArrayReference` and interned descriptors. The concrete
splice/admission algorithm below is not the selected Revision-2 delivery ABI.
Current guarantees are in 19.28.R2.5 and 19.29.7. Any future splice must preserve
stable references, reverse-index consistency and one owning arena, and arena
membership still does not imply liveness or replace end-turn collection.

A payload leaves one Message only as another Message. L3 has no `own`,
`borrow`, `move`, or whole-branch owner-transfer operators. Assignment and
`return` stay inside the current Message. An optional explicit `copy`
materializes a second graph in the current Message's arena; it is a value
operation, not an ownership operation.

This historical hosted profile defined two forms of in-process delivery from
an inactive Message M to a running Message R:

    Join. At a dispatch safe point of R, splice M's arena block list onto
        R's arena. Pointers inside M's graph stay valid: they address M's
        blocks, and those blocks now belong to R. Then discard M as a
        Message/Thread identity. R continues bumping its current block;
        leftover space in M's last block may be ignored until collection.
        After join there is one Message in this hosted arena profile. Mix nodes
        and projections are part of the Message ontology; their concrete Java
        storage is not yet governed by this hosted splice algorithm
        (section 19.29.2.1).

    Activate. Schedule M as its own L3 Thread. There is no splice. M keeps
        its arena and runs its own turns.

Join is valid only when all of the following hold:

    M is inactive (no executing callback);
    every StructureReference and ArrayReference in M's graph points into
        M's own blocks, or into interned process-root/module descriptors
        that outlive both Messages;
    R holds no StructureReference into M before the splice, and M holds none
        into R except such interned descriptors;
    R and M belong to the same hosted runtime / process.

If M was built in its own arena from a template or by construction into that
arena, the second and third bullets are the construction rule, not a later
analysis. A graph that still points into the sender is not a deliverable
Message.

In that historical profile, Join is the in-process consume path (the handler runs on R and
reads the payload as part of R's graph). Activate is the path where the
Message itself is the actor. They are not mixed for one delivery.

Across process, codec, or runtime: serialize into a new inactive Message's
arena. Block lists cannot be spliced through a wire.

A raw L2 address is not a delivery form. Shared read-only/mmap resources
cross as L2 typed handles under an explicit profile, not as Message graph
edges and not as owner-edges.

19.28.7. Queue, Scheduling and Dispatch

A Message Thread processes messages through the standard pipeline:

    dequeue
    validate/merge
    execute
    generate outgoing messages
    commit outbox
    end-turn collection

This is the full queue-enabled turn profile. In the current hosted bootstrap,
one turn consists of the root-body step followed by the same end-turn
collection boundary. For a pooled mailbox actor, queue dequeue and outbox
flushing are now part of this loop. The source `thread:` receiver supplies the
callback and route binding, and `send:` appends outgoing LMX bytes. Validation,
execute dispatch and source reply are not yet inserted; they do not require a
second process-lifetime mechanism.

The pool ready queue is not a Message Thread inbox or outbox. It
contains runnable `LmMessageThread` references and schedules actor turns only.
It does not carry message payloads. The separate implemented mailbox queues
carry owned LMX bytes and perform local route delivery. Remote outbox entries
cross the per-runtime REST/LMX provider ABI; parsing, validation and semantic
reply routing are later pipeline stages.

Each queue-enabled MessageThread has a FIFO inbox and FIFO outbox. A local route
row maps one route path to one inbox. Receiving appends an owned LMX message to
the target inbox and makes an idle mailbox actor runnable. One mailbox turn
dequeues at most one message. Messages emitted during that turn are appended to
the actor's outbox; the common end-turn boundary resolves and commits them in
FIFO order before turn-local collection can reclaim their source representation.
No user-visible mutable queue is shared between actors.

The hosted ABI currently exposes this subset as
`lm_message_thread_start_mailbox`, `lm_message_thread_bind_route`,
`lm_message_thread_send_lmx`, `lm_message_thread_current_lmx` and queue-count
inspection functions. The send ABI receives
`(sender, endpoint, route, lmx, length)`. NULL or empty endpoint means local;
route is required. Send copies exactly `length` bytes into runtime-owned
storage. The current-message view is borrowed only during the receiving
callback, after which the runtime releases those bytes. The first runtime
profile trusts the caller to supply an LMX document: parsing and validation are
separate future pipeline stages.

An external transport admits a complete LMX body through the transport-neutral
runtime operation:

    int lm_message_thread_runtime_admit_lmx(
        LmMessageThreadRuntime *runtime,
        const char *route,
        const char *lmx,
        size_t length
    );

Admission copies exactly `length` bytes, including embedded NUL bytes, into an
owned message and appends it to the FIFO inbox selected by `route`. A successful
call makes an idle mailbox actor runnable; it does not wait for that actor to
execute the message. The caller may release or modify its source buffer after
the call returns. Calls from concurrent host threads are supported, and their
route lookup, enqueue and application-exit test form one synchronized runtime
operation. The controller must stop and join every transport callback before it
removes routes or deletes the runtime.

A malformed route returns `LM_MESSAGE_STATUS_INVALID_ADDRESS`; a route which is
not bound in a running runtime returns `LM_MESSAGE_STATUS_ROUTE_NOT_FOUND`.
After application exit has been requested, every otherwise valid external
admission returns `LM_MESSAGE_STATUS_APPLICATION_STOPPING`. The same status is
returned when a known route's actor or pool is already stopping or draining.
This admission cut does not change the local outbox rule: messages staged by the
turn which requested exit may still be committed before the runtime reaches its
existing exit-ready cut.

The registered source receiver is:

    send: Route LmxBytes Length
    send: Endpoint Route LmxBytes Length

It is available in L2 and L3 managed MessageThread contexts. Each argument is
evaluated once in source order. The explicit endpoint/route values are the
current bootstrap projection of the complete envelope's `to` address; they do
not replace the address stored in LMX. Source `send:` appends to the current
turn's outbox and returns no source value. It requests failure on an immediate
runtime error but does not leave the current lexical scope.

Outbox publication is a turn boundary. A turn that has already requested
failure discards all of its staged entries. A successful turn publishes entries
in FIFO order. Publication is not a distributed transaction: every staged
entry is attempted in order, the first delivery failure becomes the sender's
status, and entries that deliver successfully either before or after that
failure remain delivered. Application teardown therefore drains successfully
published local work even when the root's final status is nonzero.

For an address without endpoint, outbox commit performs local route lookup. For
an absolute HTTP(S) endpoint it invokes the configured REST/LMX transport
provider. Until that provider is present, delivery fails explicitly with
`LM_MESSAGE_STATUS_TRANSPORT_PROVIDER_NOT_CONFIGURED`; it must not silently
treat the URI as a local route or discard the message. A missing local route
similarly ends the sending actor with `LM_MESSAGE_STATUS_ROUTE_NOT_FOUND`.
Malformed address syntax is rejected before staging with
`LM_MESSAGE_STATUS_INVALID_ADDRESS`.

The hosted transport ABI is installed on one `LmMessageThreadRuntime`, never in
a process-global or thread-local current-runtime variable. Version 1 is:

    typedef int (*LmRestLmxPost)(
        void *context,
        const char *normalized_uri,
        const char *body,
        size_t length,
        unsigned *out_http_status
    );

    typedef void (*LmRestLmxDestroy)(void *context);

    typedef struct LmRestLmxProviderOpsV1 {
        size_t abi_size;
        LmRestLmxPost post;
        LmRestLmxDestroy destroy;
    } LmRestLmxProviderOpsV1;

    int lm_message_thread_runtime_set_rest_lmx_provider(
        LmMessageThreadRuntime *runtime,
        const LmRestLmxProviderOpsV1 *ops,
        void *context
    );

The controller installs, replaces or clears this binding before attaching the
root, constructing a pool, binding routes or requesting exit. The runtime
copies the operation table. On successful installation it owns `context` until
replacement, clearing or runtime deletion and calls `destroy(context)` exactly
once when a non-NULL destroy operation was supplied. Failed installation does
not take ownership. Replacement and destruction occur while no Message Thread
can execute the provider. Reinstalling the exact same operation/context binding
is a no-op; reusing one non-NULL owned context with different operations is
rejected so replacement cannot publish an object which its old destructor then
releases. During a destructor callback, provider mutation, root/pool creation
and recursive runtime deletion are rejected, while read-only runtime status
queries remain available.

At remote outbox commit, the runtime linearizes the operation with the
application-exit cut and snapshots `post` plus `context`. It then releases the
route, pool and actor-state mutexes before invoking `post`. A provider callback
may therefore query the runtime without deadlock. Calls for different actors
may overlap; provider context must be safe for those concurrent calls. URI and
body arguments are borrowed only for the callback. `body` contains exactly
`length` bytes and need not be NUL-terminated or free of embedded NUL bytes.

The hosted outbound adapter is selected at build time by:

    LM_REST_LMX_CLIENT_PROVIDER = auto | none | libcurl | winhttp

`auto` selects WinHTTP on Windows. On a Unix-like host it selects a discovered
system/package libcurl target; if no such target is available it resolves to
`none`. A deployment which uses HTTPS must provide a TLS-enabled libcurl. The
known bundled non-Windows libcurl profile currently has no TLS backend, so
`auto` does not select it and an explicit request for that combination is a
configuration error. `none` deliberately leaves the runtime provider empty,
preserving the explicit `TRANSPORT_PROVIDER_NOT_CONFIGURED` result.

The CMake interface target `lm_rest_lmx_default_client` links the selected
adapter and defines `LM_REST_LMX_INSTALL_DEFAULT_CLIENT`. With that definition,
generated application startup installs the adapter immediately after creating
the application runtime and before attaching the root or exposing routes. An
installation failure releases the still-empty runtime and root and returns a
nonzero host status. Bootstrap translator/build utilities do not link this
target and therefore do not acquire a network-library dependency merely by
using the MessageThread runtime.

Both concrete client backends send one HTTP POST to the already normalized URI,
preserve its accepted path bytes, disable redirects, restrict the request to
HTTP(S), send exactly `length` body bytes, and set `Content-Type` and `Accept`
to `application/lmx`. HTTPS uses the platform/backend certificate and host-name
verification defaults with verification explicitly enabled by the libcurl
adapter. The initial libcurl policy allows 10 seconds for connection setup and
30 seconds for the complete operation. WinHTTP uses 10-second resolve/connect
and 30-second send/receive phase timeouts. A response body is discarded: it is
not a semantic `reply` message.

Provider callback result zero means that a syntactically valid HTTP response
was received and `out_http_status` is defined. Status 200 through 299 admits the
transport delivery. Status 404 maps to
`LM_MESSAGE_STATUS_ROUTE_NOT_FOUND`; every other status in 100 through 599 maps
to `LM_MESSAGE_STATUS_HTTP_REJECTED`. A nonzero callback result maps to
`LM_MESSAGE_STATUS_TRANSPORT_FAILED`; a zero result with an invalid HTTP status
maps to `LM_MESSAGE_STATUS_TRANSPORT_PROTOCOL_ERROR`. The HTTP response body is
not an implicit semantic reply: replies remain complete LMX Messages addressed
through `replyTo` and correlated with `id`.

The inbound side uses the same endpoint-plus-route model. A listener is mounted
at one endpoint base path and removes that prefix byte-for-byte from the raw
HTTP request path; the remaining absolute path is the local MessageThread
route. Neither the provider nor the runtime URL-decodes or canonicalizes the
route. For example, endpoint `http://127.0.0.1:8080/lmx` and route
`/worker/%2Fraw` correspond to request path `/lmx/worker/%2Fraw`, and `%2F`
remains three literal bytes while routes are matched. A query component is not
part of an address and is rejected. The complete envelope inside the LMX body
still contains `to`, `replyTo`, `id` and `correlation`; checking it against the
transport address belongs to the later validation pipeline.

The hosted server ABI is:

    typedef struct LmRestLmxHttpServerOptionsV1 {
        size_t abi_size;
        const char *bind_address;
        unsigned port;
        const char *base_path;
        size_t max_body_bytes;
        unsigned worker_count;
        unsigned request_timeout_ms;
    } LmRestLmxHttpServerOptionsV1;

    int lm_rest_lmx_http_server_start(
        LmMessageThreadRuntime *runtime,
        const LmRestLmxHttpServerOptionsV1 *options,
        LmRestLmxHttpServer **out_server
    );

    int lm_rest_lmx_http_server_start_default(
        LmMessageThreadRuntime *runtime,
        LmRestLmxHttpServer **out_server
    );

    int lm_rest_lmx_http_server_stop(LmRestLmxHttpServer **server);

`start` exposes the listener only after the caller has bound its routes.
The server pointer is an output parameter: `start` initializes it to NULL
before attempting startup, so callers do not have to initialize the slot.
`stop` is blocking, consumes the handle and returns only after listener and
request callbacks have stopped; it is therefore called before route, pool or
runtime destruction. Generated applications start the default server after the
last successful source `thread:` binding and stop it before destructive
teardown. A provider may intentionally be `none`: successful start then returns
a NULL handle and generated startup continues without a listener. Manual users
must preserve the same lifetime order.
Calls which start or stop hosted server instances are serialized by the
application controller; CivetWeb library initialization is process-global and
is not itself a concurrent-start primitive.

The current REST/LMX request profile is deliberately narrow:

    method                 POST
    Content-Type           application/lmx
    body framing           exactly one decimal Content-Length
    successful admission   HTTP 202 with an empty response body

Transfer-Encoding/chunked requests and missing lengths return 411. Malformed
paths, lengths or incomplete bodies return 400; an unbound route returns 404;
other methods return 405 with `Allow: POST`; a body above the configured limit
returns 413; another media type returns 415; application/route shutdown returns
503. An unexpected internal admission failure returns 500. HTTP 202 confirms
only that exact LMX bytes were copied into the route-selected FIFO inbox. It is
not an execution result or a semantic reply.

The hosted inbound adapter is selected at build time by:

    LM_REST_LMX_SERVER_PROVIDER = auto | none | civetweb

`auto` selects an available bundled or package CivetWeb target for a native
pthread or Win32 runtime and otherwise resolves to `none`. CivetWeb is rejected
with the `single` host-thread provider because its callbacks run concurrently
while `single` mutex operations are intentionally no-ops. The CMake interface
target `lm_rest_lmx_default_server` links the selected adapter and enables the
generated lifecycle hooks without adding CivetWeb to bootstrap utilities.

The initial CivetWeb profile is an HTTP listener. HTTPS endpoint identity is
preserved by placing it behind a TLS reverse proxy; enabling direct server-side
TLS later does not change endpoint-plus-route addressing. Files, CGI and cache
serving are disabled, URL decoding and keep-alive are disabled, and every
request is handled by the admission callback. Default runtime settings are
loopback address `127.0.0.1`, port `8080`, empty base path, a 1 MiB body limit,
four HTTP workers and a 10-second request timeout. They may be overridden by
`LM_REST_LMX_LISTEN_ADDRESS`, `LM_REST_LMX_LISTEN_PORT`,
`LM_REST_LMX_BASE_PATH`, `LM_REST_LMX_MAX_BODY_BYTES`,
`LM_REST_LMX_WORKER_COUNT` and `LM_REST_LMX_REQUEST_TIMEOUT_MS`; explicit C API
options may use port zero to request an ephemeral test port.

Dispatch resolves a receiver/operation descriptor in the current namespace. A
descriptor may explicitly query its own Table; there is no ambient registry
dispatch and no hidden object magic.

The execution step may produce result values, diagnostics, state updates and
outgoing ProposedMessage records. Outgoing records re-enter the same message
pipeline at their receiving side.

Core message semantics are intentionally smaller than broker/runtime policy:

    message = proposed, potentially executable/action-capable expression;
    validation/merge -> ExecutionPlan;
    execution -> result or `throw: Failure`;
    boundary -> reply/failure message to `replyTo` or a local continuation.

The core language does not require a broker-style acknowledgement, dead-letter
queue, topic partition, consumer group, transport retry scheduler or supervision
tree as generic message semantics. A message is considered semantically handled
when execution produces its result or failure, just as a local function call is
handled when it returns a value or failure. The boundary difference is only that a
boundary may wrap that result or failure into an ordinary message record.

Scheduling between Messages, supervision and observability policies are
runtime/profile/library concerns around accepted message execution. They may
choose priority among runnable Messages but may not reorder one Message's
already admitted FIFO inbox or interleave two turns of that Message. Examples:

    priority/fairness among different runnable Messages;
    worker mapping and migration between turns;
    queue capacity and overflow policy;
    transport retry after transport/runtime failure;
    pause, resume or cancellation;
    Message Thread restart or termination policy;
    diagnostics, audit, trace, metrics and event history.

Such policies may be described by explicit descriptors or ordinary Tables and may themselves emit
diagnostics or messages, but they are not the meaning of a source message. In
particular, a semantic failure is normally returned to `replyTo` or a local
continuation as a failure message. If that target is absent, expired or
unreachable, the situation belongs to runtime/delivery policy, not to the core
message expression semantics.

19.28.7.1. Autonomous / Constrained Message Profiles

Some profiles need more than generic message execution. Autonomous, low-power,
high-latency, degraded-link, safety-critical or heterogeneous-device systems
may define domain message profiles with explicit tables for command lifecycle
and physical limits.

These features are not implied merely because a message is full LMX. A full LMX
message can express algorithms, nested Structures and calls, but it does not by
itself define command identity, freshness, physical units, safety budgets,
idempotence, replay policy or degraded-mode behavior. Those are explicit
message/profile descriptor fields or policy Tables consumed by
validation/merge and execution.

Typical profile rows include:

    commandId / correlation / dedupKey
        Identity rows used to recognize the same proposed operation again.

    idempotent / duplicatePolicy / retryPolicy / replayPolicy
        Whether repeated admission is allowed, rejected, coalesced, answered
        from an earlier result, replayed from a decision log, or repaired by a
        profile-defined recovery expression.

    resource budgets
        energy, memory, bandwidth, time, storage wear, heat, actuator cycles
        or other profile-defined limits.

    freshness
        sampledAt, validUntil, staleAfter, calibrationValidUntil and related
        evidence windows.

    units and frames
        physical units, coordinate frames, sensor frames, map frames and
        conversion evidence.

    uncertainty / evidence
        confidence, errorBound, distribution, source, calibration, provenance
        and validator-produced evidence.

    plan mode
        propose, validateOnly, execute, recordResult or another explicit
        command lifecycle stage.

    effect fences
        mayRead, mayWrite, mayMove, mayTransmit, mayHeat, maySpendEnergy,
        mayOverwrite, mayWakeDevice and similar effect bounds.

    degradation
        minimumMode, degradedMode, safeMode, fallbackProvider and
        emergencyBinding.

    decision-log categories
        observed, decided, executed, failed, repaired and replayed.

    local-first conflict
        localTruth, importedTruth, conflict, mergeEvidence and authoritySource.

A semantic replay is different from a transport resend. A transport resend is a
delivery/runtime policy around the envelope. A semantic replay is an ordinary
validated LMX operation that reconstructs, repeats, repairs or answers an
accepted command according to idempotence, evidence, authority, freshness and
effect tables. It may use decision-log rows and previous result/failure
messages, but it is still a proposed expression until validation/merge admits
it.

This does not introduce a second `retry` semantics. L3 already has
`retryable` / `retry` as ordinary control receivers: `retryable` creates a
restartable local execution frame, and `retry` re-enters the nearest or named
retryable frame after the appropriate cleanups. An autonomous profile may use
that L3 mechanism inside a concrete plan, for example with retryBudget,
retryLimit, backoff, provider fallback or degraded-mode rows. Message replay is
larger: it may construct or admit a new ProposedMessage or recovery expression
from command identity and decision-log evidence. Transport retry is smaller:
it resends an envelope without changing the source expression semantics.

Likewise, a duplicate command is not handled by a hidden broker rule. The
selected duplicatePolicy may reject it, return the previous result, merge it
with an active operation, enqueue a repair expression, or allow another
execution if the command is declared idempotent and the relevant evidence still
holds.

This keeps the boundary clean:

    message-as-LMX
        gives the executable proposed expression;

    autonomous/constrained profile tables
        give identity, budgets, freshness, uncertainty, replay/idempotence,
        effect fences, degradation and decision-log policy;

    validator/merge
        turns the candidate plus profile rows into a concrete plan, or
        `throw: Failure` with the diagnostic payload;

    executor
        runs only the concrete plan and records a result or `throw: Failure`
        plus evidence rows according to the selected profile.

19.28.8. Reply, Future, Failure and Continuation

Replies and futures are message records. Failures crossing a Message Thread
boundary are data messages, not hidden exceptions. The message carries the
same `throw` name and payload that `catch` would have received in-process.
It is not a second return type.

A result crossing a Message Thread or service boundary is represented as a message.
If a request contains `replyTo`, or a local future/continuation that resolves to
a MessageAddress, the value returned by the executed expression is wrapped into
a reply message addressed to that target. The reply has its own `id` and sets
`correlation` to the request's `id`. A failure is wrapped in the same way.
Reply and failure messages are ordinary LMX message records and must pass the
normal routing and validation rules of the receiving side. `correlation` alone
never selects a destination.

This wrapping is automatic at the message boundary. It is not a second
source-level `return` form. Keep the following meanings separate:

    L3 executable return
        `return` / `return: value` exits the current executable body and
        produces the declared local execution result.

    computational injection
        a pure/monadic "return" notion, if a profile needs it, should be named
        `pure`, `unit` or another profile-defined receiver. It injects a value
        into a computational context; it is not the L3 control-exit receiver.

    message-boundary reply wrapping
        a produced result is wrapped as a reply ProposedMessage only when the
        executing message boundary supplies `replyTo` or a local
        future/continuation that resolves to a MessageAddress.

If a message has no `replyTo` and no profile rule consumes the result, the
result is not forced into a hidden reply. The profile may discard it, log it,
use it for local generation rules, or report that the message kind must declare
a result destination. The important rule is that crossing the boundary uses an
ordinary message record, not a hidden call-stack return.

A reply payload may itself be a Structure, callable descriptor, callable
reference, residual executable or future/continuation record, if the receiving
side admits that payload by its normal validation rules. The message boundary
does not inspect such a value as "code to run" merely because it is callable. It
wraps the produced result as data; the receiver decides later whether that data
is executable, callable, storable, displayable or invalid.

`async`, `await` and `yield`, if present, are scheduling expressions that create
or consume message/continuation records. `yield` is the sequence-oriented lazy
production protocol: it produces one value, records resume state and lets a
consumer such as `next`, `each`, `awaitNext` or a message scheduler request a later
step. This does not imply global non-strict evaluation for every expression.
Deferred single values, futures and streams are ordinary descriptor/receiver
profiles over the same message/continuation model.

19.28.9. Determinism and Atomic Operations

Default deterministic message-runtime profile:

    one active handler per Message Thread;
    no shared mutable raw references across Message Threads;
    communication by messages;
    explicit lower-level synchronization only in admitted L2 profiles;
    L3 synchronization, when provided, uses checked Message Thread or
    high-level coordination receivers.

Atomic operations are low-level implementation operations, not a replacement for
ordinary messages.

19.28.10. World Wide Mix

This section is a document and addressing model. It is not a replacement for
the P0 parser, Mix overlay markup in section 0.0.2, or
`implements(varA varB Consumer)` in sections 2.1 through 2.4 and 19.21.3. The
current hosted bootstrap does not implement World Wide Mix paths, prefix locks
or mirrors.

The target Mix runtime must coordinate independently scheduled Message
participants (section 19.29.2.1). A World Wide Mix placement/addressing tree
does not put an entire document into one Message or one arena. The current Java
cursor threads and page store require a rewrite into this Message model.

Mix here is not only an overlay on LMX source. It is a universal document:
a placement tree of nodes, memory cells at the leaves, and dynamic marks,
cursors and attributes over those positions. World Wide Mix is that document
when a node can be named by a hierarchical path from another carrier. The
Internet is not required for that (section 19.28.10.1).

19.28.10.1. Not the Web and Not a File

The Web combines a URL, bytes and a Content-Type. Meaning appears after
download and a separate parser (HTML, JPEG, JSON). The type lives in a header,
not in how a consumer walks the document.

A disk file is a linear byte sequence addressed by offset from the start.
Insertion in the middle shifts every later address. Editors and networks then
live in a different world from the file.

World Wide Mix is a *placement* tree: where a node sits in the world. LMX is a
*value* tree: which fields a Structure has and what a Consumer touches. They
are different trees. They meet in a cell: a Mix address holds an LMX value
(Structure, Array or Primitive). The path `3.17.4` is not `file\close`.
`implements(varA varB Consumer)` does not number Mix siblings.

Raw input before a receiver is substrate in a cell. After recognition the same
cell may hold an LMX tree with finer leaves. The document need not already be
a «file» or a «picture»; that is decided by the Consumer of the LMX value, not
by the Mix address scheme.

World Wide here is not the Web and not IP. The Internet is not required.
It is the same path of numbers (`3.17.4`) that can be named from another
carrier. The carrier may be anything: RAM, a disk sector, a wire, radio, a
flash drive, a carrier pigeon. Hop codec and occupancy change with the
carrier; the address does not.

A physical link carries a page or a chunk along an already known path. A
pigeon carries a serialized node or a short envelope (path, capability, which
Consumer). That is transport, not Mix topology.

HTTP POST (`application/lmx`) is one way to carry LMX messages. It is a layer
beside Mix (section 19.28.10.15). Without it Mix is the same: bunches,
next/prev, prefix locks, mirrors. Neighbour `3.18` is a neighbour in a bunch,
not a DNS host.

The world is a placement tree, not a socket network. Wide means the address
is not «the file on this machine at byte 12044».

19.28.10.2. Two Trees

    Mix (this section)
        topology: siblings, realm prefix, bunch, lock, mirror, cursor;
        edge: neighbour index, a natural number, written `3.17.4`;
        bunch: the occupied children of one prefix; next/prev only inside it;
        leaf: a cell (memory or a reference to a value);
        overlay of marks on positions of this tree, not a second parse tree.

    LMX (sections 2 and 19.21.3)
        value: Lmx reference; primitive/callable/branch interpretation follows
               the address domain of `data`;
        edge: field name, `file\close`, merge occurrences;
        compatibility: explicit `implements(varA varB Consumer)` over the used
               tree of *that* value;
        P0 source builds this tree; `{...}` places Mix marks *on* it.

Analogies are allowed (thin or fat Consumer, shadowing, «if you did not touch
it, do not require it»). Identity is not:

    inserting a Mix sibling changes index `3.18`, not a Structure field;
    runtime Structure merge appends copied `close` occurrences in forward
        order; `[0]close` remains the default, independently of cell address;
    a 33rd Mix child is a new slot at that level;
    a 33rd LMX field is a new name occurrence in a Structure.

The parser may still build both at once: a P0 Structure and a Mix anchor on
its position. The anchor is addressed by a Mix path; fields are read as LMX.

19.28.10.3. Address: a Path of Integers

There is no bound on the number of levels. An address is a sequence of
non-negative integers (ℕ₀) from the root to a cell. Path length is the depth
of that cell, not the height of the whole tree: branches under one parent may
differ in length (section 19.28.10.6). A level index is any such integer, with
no ceiling.

A cell may be a byte, a word, a buffer or a child Structure. The index counts
neighbours, not bytes. The written path is not LMX source grammar: numbers
separated by dots, of different lengths because the numbers differ.

    3.17.4.1023
    0.0.5
    3.100000

The address is not tied to bytes. Whoever stores it chooses a codec: varint, a
chain of widths matching live fan-out

    5 bits -> 12 bits -> 6 bits -> 10 bits

or anything else. Externally these are the same numbers. `3.17` remains
`3.17` when a slot starts being stored in 12 bits instead of 5. Width is
compression of an integer, not an address type.

A prefix of k numbers names a subtree. A shorter address is a shallower path.
Leading zeros in text do not count: `03.17` = `3.17`.

Storage widths (5 bits, 12 bits) are not different path types. Otherwise a
node that gained a 33rd child would change its address type.

19.28.10.4. How Many Bits Storage Uses

Occupancy is a property of the carrier, not of the address.

    Device RAM
        typically about 5 bits: tens of children. A compact vector of live
        children plus, if needed, a map from path index to local slot.

    Small network
        also about 5 bits, when that is the carrier: tens of machines, not
        thousands of hosts per level. A network here is an example carrier,
        not a required layer.

    Disk
        how many cells fit in a 4 KB sector or a 32 KB cluster (256 Kbit)
        depends on cell size. With a 4-byte pointer: about 10 bits per
        sector, about 12 per cluster. A buffer cell means fewer neighbours
        in the same sector.

A type chain on a path (`u5.u12.u6.u10`) is how that node was serialized, not
what it is called. Mirrors of one page (section 19.28.10.12): RAM and network
are narrow; disk is slightly wider; the number path is one.

Unallocated numbers at a Mix level are simply not allocated. That is not an
LMX unused path: Structure fields and neighbour slots are different trees.

19.28.10.5. Cell, Node, Document

A cell is a leaf: a raw memory region in the Mix store, not a slot of a
Message graph (section 19.29.2.1). Its description is an ordinary Structure
(contract plus architecture: count/integer/opaque, range, spelling); see
section 2.2.2. It is not a closed list of kinds such as «int, FILE, image».
A Message kept in a cell is stored as raw payload. Destruction of that
Message does not walk Mix; a cursor deletes the cell, or deletes itself
from Mix if it is that Message.

A node is a Structure: named or positional fields and child references. On
disk it is on the order of a 4 KB sector or a 32 KB cluster (256 Kbit). In
RAM and on a small network it is sparse, with tens of children.

A document is a root plus a tree of nodes plus a Mix overlay on tree
positions. It is not a filename extension. A file is one way to serialize
node pages.

A Mix position is not a byte offset. It is a dynamic address in the tree (a
path of integers plus a cursor inside the cell when the cell is a buffer).
Inserting or deleting a sibling changes only indices at that level, not
«every byte after the point». Cursors therefore survive edits, as in the Mix
design note.

19.28.10.6. Uneven Branches; next/prev on a Bunch

The Mix tree is not complete and not a grid of one height. Under one parent a
child may be a leaf while a neighbour is a node with a long subtree:

    3.17.4          a leaf, a member of bunch(3.17)
    3.17.5          a node, the same bunch
    3.17.5.0.2      a cell deeper in the second branch

Depth is the length of a particular path, not a world level. There is no ruler
«every cell at depth 4» and no next along such a ruler.

A bunch is the occupied child indices of one prefix:

    bunch(P) = { i ∈ ℕ₀ | P.i is allocated }

Gaps are not in the bunch: if `3.17` holds 0, 4, 5, the bunch is {0, 4, 5},
not 0..5. next/prev is the neighbour in that set, in ℕ₀ order:

    next(3.17.4) = 3.17.5
    prev(3.17.4) = 3.17.0

not `3.17.5.0.2` (that is another bunch, deeper) and not «the next document in
the world».

A cursor has two orthogonal moves:

    down / up      lengthen or shorten the path (the branch);
    next / prev    change the last index inside the same bunch.

next does not climb to the parent, does not descend into a foreign branch, and
does not jump into another prefix's bunch. The end of a bunch is no next, not
«the absolute next Mix». The world root is a bunch too: next there walks
occupied roots, not every disk on the planet.

Connectivity is therefore not absolute. Absolute connectivity would be a
doubly-linked list of all documents at the base, with overflow pouring into
the neighbour on that list. Here neighbourhood is local: if a cell fills, the
writer deepens this branch, takes a free index in *this* bunch, compacts, or
refuses. Walking next is navigation, not a spill chute.

A lock on prefix P covers bunch(P) and every deeper bunch inside P. A mirror
of P mirrors this uneven subtree, not a chain of absolute next links.

19.28.10.7. World-Wide Realm Prefixes

World hierarchy is a path prefix in the placement tree, not the Internet and
not a fixed number of slots «for the planet». How many levels belong to
realm, volume, document or chapter is a profile, not an address canon.

Example meaning (profile, not language):

    first levels     realm / administrator / planet-service
    next             document / volume
    deeper           chapter, section, block, cell

The first level has as many roots as were allocated. Names are not DNS: they
are numbers. A human name, if needed, is a Mix attribute or a Structure field
on the node, not part of the address. The address is stable; the human name
may change.

An LMX message need not carry the body. It carries a path (length plus
indices), a capability, and which Consumer will walk. The body is read by
cursor in chunks. Mix cursors for large bodies are already described with
messages in section 19.19.1.2; here the address is simply hierarchical and
world-wide, with no depth ceiling.

19.28.10.8. Mix Overlay on This Tree

Mix is still not a second parse tree.

The same addresses hold:

    active marks and intervals (colour, link, diagnostic);
    overlapping sets;
    cursors of several consumers;
    locks on path prefixes (section 19.28.10.11);
    attributes such as «still a raw buffer» or «already a File».

The LMX parser still builds P0 Structures and places Mix anchors in parallel.
World Wide Mix adds only that an anchor has a path of integers (`3.17.4`, or
however it is stored locally) that can be sent to another device without
«open my file at byte 12044».

19.28.10.9. Type Lives in the Cell's LMX Value, Not in the Mix Address

The address `3.17.4` does not type the contents. Typing happens when a
Consumer walks the LMX value stored in that cell:

    implements(varA varB Consumer)

    varA       the LMX value in the cell (or what is being substituted);
    varB       a role (File, paragraph, table, raw word);
    Consumer   who walks *value fields*, not Mix neighbours.

Strict mode: FileManager uses `file\close` and `file\read` — a fat LMX used
tree. Relaxed mode: File consumes a primitive FILE into a `handle` field — a
thin LMX leaf, converter selected by merge key.

Until someone asks for File, a Mix cell may hold substrate (JPEG, UTF-8, a
word). Meaning is attached by an LMX Consumer, not by the Mix path and not by
MIME.

19.28.10.10. Merge of Pages and Contracts

A document node may be assembled by merging Structures: a base page plus
audit plus local fields. Merge appends copied children in operand/body order.
The first same-name child remains `[0]` and unqualified lookup; later children
are `[1]`, `[2]`, and so on. Merge does not perform in-place replacement.

The same holds for cell descriptions: `u32` is merge(cell, count/integer) plus
range `0..2^32-1` plus spelling. `FILE` is merge(cell, opaque). On disk both
may occupy one slot in a sector-sized page; the contracts differ.

19.28.10.11. Message Coordination; Historical Prefix-Lock Profile

Common Mix does not define a portable mutex, reader/writer lock, byte-range
lock, prefix-lock algorithm or nested-lock acquisition order. Such algorithms
depend on shared memory, host scheduling and a concrete carrier; they cannot be
ported unchanged across RAM, HTTP, radio, disk and physical mail.

Mutable Mix state belongs to a Message arena. Its L3 Thread receives commands
through FIFO delivery and executes at most one turn at a time. Parallelism is
between distinct Messages/arenas. An operation on a path prefix is therefore a
Message to the owner of that mutable state. A capability for the prefix may be
an ordinary Lmx field of the Message; it grants authority and does not expose a
shared mutable pointer or become a mutex.

An operation spanning several Message owners requires an explicit Message
protocol with stated failure/retry/commit rules. A particular L2/storage
profile may implement native locks, atomics or prefix-lock ordering, and an
application may model a distributed lock as Messages. Neither is an implicit
common-LMX/Mix synchronization primitive.

The older Java/profile design in which writers lock prefixes, readers proceed
under a reader/writer policy, nested locks follow ancestor order and listener
callbacks report release is implementation history. During the Message-style
refactor those callbacks become delivered Messages and the lock algorithm must
not be copied one-for-one. The Structure occurrence rule remains independent:
unqualified lookup still selects the first `[0]` occurrence.

19.28.10.12. Mirrors

A mirror is not a second document and not a git clone as a kind. It is
another path (another realm prefix) whose nodes, for a given reader Consumer,
cover the same fields as the original.

Everyday mirrors exist without a «second document»:

    address             a path of integers;
    RAM / small network storage of about 5 bits per hop, tens of children
                        or machines;
    disk                storage of about 10..12 bits under a sector or
                        cluster.

RAM is a narrow projection of the same page: the Consumer walks the same
path numbers; only live slots sit in memory. A network of tens of machines
is the same kind of narrow projection.

A network mirror is that relation on another prefix:

    primary     the prefix written to;
    mirror      the prefix read from while it catches up.

Writes go to primary through its owner Message's FIFO. The mirror catches up
through change Messages over Mix (as history and undo do), not a new document
version on every edit. It may be read-only or serve the last caught-up page
under an explicit protocol. A thin mark reader may tolerate lag; a writer that
is performing close must not write to a stale mirror.

Commands admitted by one owner are FIFO-linearized. Conflicting changes owned
by different Messages require an explicit coordination protocol rather than a
hidden common lock. As with Mix marks, the occurrence chain is kept; last-wins
is only a projection for a simple renderer; a semantic Consumer may see the
whole chain and merge along its used tree.

A mirror's name is an attribute, not part of the address. A mirror's address
is its own path. Original and mirror are comparable only through
`implements` for a concrete reader, not as «forever the same bytes».

19.28.10.13. What This Model Does Not Do

It does not replace the P0 parser and does not introduce `Value = ℕ₀`.
It does not bound tree depth or the magnitude of a level index.
It does not force branches to one depth and does not make a global
next/prev of all Mix documents.
It does not fix cell size and does not tie addresses to bytes.
It does not become the Web: no mandatory URL text, DNS, or MIME as type.
It does not require the Internet, IP, or HTTP. The carrier may be anything.
It does not version the document on every edit (history is a listener over
Mix).
It does not introduce `flock` on «the whole file» and does not make a mirror
a second document kind.

19.28.10.14. Minimal Core

    address = a path of ℕ₀ integers, written with dots;
    depth is the length of that path; branches under one parent may differ;
    bunch = the occupied children of one prefix; gaps are not in the bunch;
    next/prev only inside a bunch, not an absolute chain of documents;
    hop storage is the carrier's affair (a 5->12->6->10 chain, varint, ...);
    the carrier may be anything: RAM, disk, wire, radio, flash, pigeon;
    the Internet is not required; HTTP is one message transport beside Mix;
    typical occupancy: RAM and a small network about 5 bits, disk about
    10..12;
    RAM node: sparse, about 32 children — a working mirror of the page;
    cursor = path plus offset inside a buffer cell;
    down/up walks a branch; next/prev walks a bunch;
    insert/delete at a level shifts only sibling indices in that bunch;
    coordination = explicit Messages/capabilities; a native/prefix lock is an
        optional L2/storage protocol, not common Mix semantics;
    mirror = another prefix plus a catch-up listener, not a second kind;
    Mix attributes hang on a cursor or interval, not on a byte range;
    `implements(varA varB Consumer)` types the LMX value in the cell, not
    the Mix path.

Realm profiles, page serialization and capabilities on a path prefix are
delivery and carrier around the document, not the document model itself.

19.28.10.15. Relation to REST/LMX and Message Queues

Section 19.28.7 moves *messages*: a complete LMX document as owned bytes into
a FIFO inbox, locally by route or remotely by HTTP POST (`application/lmx`).
The unit is an actor turn. REST/LMX does not place document pages in a
neighbour slot of a Mix path.

One arena per Message, FIFO order and one active turn per L3 Thread are common
semantics. The carrier and host execution mapping are not: the same Message may
travel through an in-process queue, HTTP, wire, radio, flash or physical mail,
and its turns may run cooperatively or on a worker pool without changing that
boundary.

This section places *cells*: a path of integers, cursors, coordination and
mirrors. The unit is a document node. A message may *name* a Mix path instead
of carrying the body (section 19.19.1.2). Transport still ships only the short
envelope; the receiver walks Mix. The two layers stack. They are not the same
tree. Transport is not Mix and need not be IP: the same envelope can go on a
wire, radio, a flash drive or a carrier pigeon. Without HTTP, Mix does not
change.

A Mix sibling (`3.18` next to `3.17`) is next in bunch(`3`), not a host and
not a spill chute. A machine appears only if a profile maps a realm prefix
onto one. Disk-full is storage-profile policy, not an implication of the
path and not «pour into the absolute next»:

    refuse the write;
    compact live slots;
    evict cold cells to a *declared* mirror prefix that published a
    capability.

It is not «when this disk fills, fetch films onto the roommate's disk».
Without a mirror capability the write fails. With one, a Consumer may *pull*
a cell by cursor when it actually uses it. Pushing an unread movie onto an
unrelated neighbour is neither Mix placement nor REST/LMX delivery.

19.28.11. ANSI C Lowering and Boundaries

19.28.11.1. Explicit Runtime and Worker Pool

The hosted runtime distinguishes three objects:

    LmMessageThreadRuntime
        explicit controller context for one or more pools;

    LmMessageThreadPool
        host workers, synchronization, FIFO ready queue and pool-owned actors;

    LmMessageThread
        actor state, the current actor-local ownership domain (a canonical
        `root_owner` plus migration-era sibling allocation shells), current-turn
        ExecutionContext association, entry callback, status and
        turn/collection counters. That domain represents the target one logical
        Message arena but is not yet physically a single `LmOwnArena` object.

There is no process-global root/current Message Thread and no TLS scheduler
binding. The entry ABI is conceptually:

    typedef void (*LmMessageThreadEntry)(
        LmMessageThread *thread,
        void *argument);

`lm_message_thread_start` appends a NEW actor to its pool's ready queue. A
worker removes one actor, marks it executing, runs begin-turn, invokes the entry
with the explicit actor reference, runs collection/end-turn and either stops or
requeues the actor. The scheduled/executing state guarantees at most one active
callback per actor.

Every actor owns its actor-local allocation domain and metadata/index. The
domain follows the actor if later turns run on another worker; it is never
worker-owned or shared between actors. The actor-local collector runs once at
every pool end-turn and calls `lm_own_tree_cut(root_owner)` followed by
`lm_own_arena_reclaim(root_owner)`. Revision 2 does not require or permit a
second source-semantic disposable per-turn arena.

The source-level rule remains message isolation, even when a pool maps many
Message Threads onto fewer host threads.

Current hosted non-overlap is enforced by the pool scheduler and by the
attached generated-root controller contract. A raw unattached actor created
through the low-level ABI is single-controller-only; concurrently calling its
manual turn operations is outside that current ABI contract and is not an
alternative L3 scheduling semantics.

19.28.11.2. Host Thread Provider

The build setting is:

    LM_THREAD_PROVIDER = auto | pthread | win32 | single

`auto` selects `win32` on Windows, `pthread` on Unix-like systems including
macOS and Linux, and `single` where no native backend is selected.

The common implementation ABI includes:

    lm_host_thread_start / lm_host_thread_join;
    lm_mutex_lock / lm_mutex_unlock;
    lm_condition_wait / lm_condition_signal / lm_condition_broadcast;

together with their constructors and deletion operations.

The `pthread` backend uses `pthread_create`, `pthread_join`,
`pthread_mutex_*` and `pthread_cond_*`. The Win32 backend uses
`_beginthreadex`, `WaitForSingleObject`, `CRITICAL_SECTION` and
`CONDITION_VARIABLE`.

The `single` backend creates no OS worker. Host-thread entry runs synchronously;
pool join/delete cooperatively pumps the FIFO ready queue. Mutex operations are
non-blocking compatibility operations, signal/broadcast are successful no-ops,
and `lm_condition_wait` reports failure because a blocking wait cannot make
progress in this provider.

CMake exposes `LM_THREAD_PROVIDER` as a cache setting, defaults it to `auto`,
and links the pthread backend through `Threads::Threads`. Bootstrap/self-build
drivers default to `single` unless the environment selects another provider;
their pthread path adds `-pthread`.

These provider operations are L2/runtime implementation facilities. Selecting
a provider does not expose raw host-thread synchronization as an L3 operation.

19.28.11.3. Lifecycle and Control

For native providers, the host thread which creates an
`LmMessageThreadRuntime` is its controller. For `single`, the outer cooperative
caller is the controller and runtime-local execution depth prevents lifecycle
operations from a callback of that runtime.

One `LmMessageThreadRuntime` defines one connected low-level lifecycle domain.
Pools, actors and raw ABI handles which directly refer to one another must
belong to that same runtime. A raw actor, pool or owner pointer from one runtime
domain into another is invalid; cross-runtime interaction belongs to the
message boundary described below.

Runtime creation/deletion, pool creation/deletion, actor creation/start/join and
pool-wide stop are controller operations. An executing actor callback may
request stop or failure only for that same actor. It may not join itself, join
another actor, stop a peer actor, or create, delete or control its pool or
runtime.

A pool owns every actor created by `lm_message_thread_new_in`. A pooled actor
cannot be individually destroyed and its manual begin-turn/end-turn/collect
operations are rejected; the pool owns those boundaries. Pool deletion requests
stop, joins its workers and destroys its member actors and their arenas. A
deletion attempted while an actor or join lifecycle is active fails and may be
retried after quiescence.

Handles and raw actor pointers are valid only while their owning runtime/pool
lifecycle remains active. Accessors, owner lookup, component operations and
other uses of an actor handle must not execute concurrently with pool/runtime
teardown. The controller must quiesce all such users before deletion; calling
an accessor after successful pool deletion is outside the ABI contract.
Mutexes and conditions may likewise be deleted only after their users have
quiesced.

The host-thread wrapper is likewise controlled by its creator. Its entry
callback cannot join or delete the wrapper which is currently starting it.

19.28.11.4. Message Boundary Status

The controller ABI is infrastructure, not a substitute for Message Thread
communication. Source-level code must not exchange raw foreign actor, pool or
runtime pointers. Cross-actor and cross-runtime communication will use
inbox/outbox Messages with the join, activate, serialize or immutable-sharing
rules of sections 19.28.6 and 19.29.7.

The current `void *argument` entry parameter is a low-level hosted ABI facility;
it does not weaken the Message isolation boundary. `send:` and `thread:` are
implemented by the source and runtime contracts in sections 19.27 and 19.28.7.
`exit:` is implemented for the generated one-runtime, zero-or-one-pool
application profile. `reply`, `await` and `schedule` remain NOT IMPLEMENTED as
generic source operations; multi-runtime shutdown remains an explicit host
controller responsibility.



19.29.5.H. Historical Exact-Reference Return Profile

The remainder of this subsection records the previous hosted arena profile. It
is non-normative for Revision 2 until its observable return claims are restated
against the selected generic Lmx call/result ABI.

For an ordinary Structure or Array result, `return` publishes the exact
reference already produced by its expression. It must not:

    allocate a result object;
    clone or copy the object;
    materialize an aggregate from the object;
    allocate a replacement aggregate in another arena;
    compact or relocate the object;
    change the object's address or identity.

An explicit constructor inside a return expression allocates in the current
Message's arena. The constructor finishes first and produces one reference;
`return` publishes that same reference without a second allocation or copy.
An optional explicit `copy` that is the return expression likewise finishes
first; `return` does not add another object.

Every well-typed ordinary Structure or Array may be returned. An aggregate is
not rejected merely because it was constructed or named inside the returning
function. It already lives in this Message's arena.

The required abstract order is:

    1. evaluate the return expression and obtain its existing reference;

    2. publish that exact reference as the caller, continuation, future or
       enclosing result root of this Message;

    3. let the local frame slot die;

    4. do not collect, compact or allocate on this path.

Out-of-memory must not force a hidden return copy. Collection, if any, waits
for a selected safe point (typically end-turn), at which the published
reference is a live root.

An `fm` multi-field result is itself an ordinary Structure. In the current
bootstrap it is allocated once in the function prologue in the running
Message's arena, its declared fields are filled on each selected return path,
and the same `lm_fm_result` reference is returned. No return path allocates
or copies the result.



19.29.7.H. Historical Hosted Join/Activate/Serialize Profile

The concrete arena-splice and `StructureReference`/`ArrayReference` rules below
describe the Revision-1 hosted Message runtime. They are non-normative until
re-derived for the final generic Lmx allocator and Array ABI.

A payload leaves one Message only as another Message (section 19.28.6). The
admitted forms are:

    Join
        In-process consume: splice the inactive Message's arena onto the
        running receiver, then discard the inactive Message identity.
        Pointers inside the payload stay valid. Preconditions are in
        section 19.28.6: closed graph, inactive sender-payload, same
        runtime, no prior cross-references.

    Activate
        The Message is launched as its own L3 Thread. No splice.

    Serialize
        Across process, codec or runtime: reconstruct the graph in a new
        inactive Message's arena. Block lists cannot be spliced through a
        wire.

There is no whole-branch owner-transfer operator and no borrowed payload
kind. After send, the sender holds no StructureReference into the sent
Message. Same-Message `return` is the exact-reference operation of
section 19.29.5, not a boundary.

Explicit immutable sharing uses an intern or L2 typed handle whose profile
defines cross-Message validity. Neither is a raw mutable StructureReference
crossing the boundary.

The current implemented `send:` accepts already serialized LMX bytes and
copies them into queue storage. Join and activate of live graphs must not
overload that bootstrap argument list ambiguously. `reply`, `await` and
`schedule` remain NOT IMPLEMENTED as generic source operations; they will
use the same Message forms.



19.29.12.H. Revision-1 Hosted C Lowering (Historical)

Everything from 19.29.12.H1 through 19.29.12.H5 records the current/previous
hosted implementation. It is retained as an implementation inventory and
migration reference only. Its `LmOwnArena`, `LmMessageThread`, hidden context,
`T *`, `Result *`, closure, descriptor, private static slot and eager module
initializer forms are not intermediate requirements of Revision 2.

19.29.12.H1. Current Hosted Bootstrap Profile

The current hosted C99 profile uses the `libown` runtime and the concrete arena
type `LmOwnArena`.

Every generated standalone program starts as one root Message Thread. The
generated root runtime state owns a root arena before any ordinary Structure or
Array is materialized, and destroys that arena when the program or root Message
Thread terminates.

The shared actor type is `LmMessageThread`; no separate generated
per-translation-unit thread helper remains. The current actor Structure records:

    root owner arena;
    RUNNING / STOPPING / STOPPED state;
    retained stop status;
    turn and collection counters;
    collector-failure state;
    opaque current-turn ExecutionContext pointer.

The generated external `main` creates an explicit unpooled root
`LmMessageThread` plus an `LmMessageThreadRuntime`, attaches the root to that
runtime, installs its diagnostic ExecutionContext through the explicit root
reference and drives the turn loop described in section 19.28.2.2. When source
`thread:` declarations exist, it additionally constructs one application pool,
starts and route-binds those mailbox actors, then drains committed work, joins
them and releases the pool. Finally it detaches and releases the root/runtime.
It does not acquire a singleton root/current object. The root is the first
ordinary Message Thread instance, not a second memory mechanism and not a
source level.

The worker-pool ABI is implemented in the same runtime library. Generated
standalone `main` functions always construct the application runtime and add a
pool only when they own local/imported `thread:` handlers. The direct root loop
and the pool scheduler share the same actor state, arena, outbox and end-turn
collection semantics.

This rule applies to ordinary applications and to bootstrap tools alike:

    parser;
    trans;
    make;
    finalize;
    buildCore;
    generated tests and utilities.

Thus a generated `make` utility depending on `libown` is modularly correct:
`make` is an executable Message Thread root with the same runtime lifetime
requirements as another generated executable. The build system must order its
stages so that the owner runtime exists before tools linked against it are
built or run.

The essential current arena API includes the explicit executing actor as its
first parameter. In an LMX managed function that argument is supplied by the
hidden `lm_lmx_message_thread` lowering parameter; it is still an ordinary C
parameter and never a global/TLS lookup. `owner_thread` names the actor whose
owner graph contains the arena and is normally the same explicit actor in the
current profile.

arena. Lazy-edge promotion can copy explicit lazy-owned content into a target

set of arena-managed allocations into another arena when the runtime contract
allows it.

`lm_own_array_new_zero` reflects bootstrap and implementation code. Ordinary
generated Structure materialization is being moved to root-arena operations.
Future implementation work may continue reducing uses of the unscoped helpers
where the allocation is semantically part of an owner region.


19.29.12.H2. Current Root-Arena Materialization

The current migrated paths allocate explicitly constructed local and direct
module-level named Structures, local and direct module-level anonymous
Structures, `fm` result Structures, admitted ordinary Arrays in managed Message
Thread contexts (including extent-bearing `[]:` declarations and direct
module-level ArrayReferences), unmarked runtime Tables in managed functions and
directly on executable module surfaces, and closure environments/descriptors in
the root Message Thread arena. A named-Structure or physical-`merge:` descriptor
declaration performs no allocation. A source-marked Table is the separate
translation-time projection described in section 19.17 and has no runtime Table
binding.

Conceptual generated form for an ordinary local Structure is:

    T *value = (T *)lm_own_arena_new_zero(
        lm_lmx_message_thread,
        lm_message_thread_owner(lm_lmx_message_thread),
        sizeof(*value));

The object is allocated once when its source operation materializes it. Local
bindings hold `T *`-shaped references. Assigning or returning such a binding
does not allocate another `T`.

Conceptual generated `fm` result form is:

    Result *lm_fm_result = (Result *)lm_own_arena_new_zero(
        lm_lmx_message_thread,
        lm_message_thread_owner(lm_lmx_message_thread),
        sizeof(*lm_fm_result));

    if (lm_fm_result == 0) {
        /* selected failure convention */
    }

    /* function body */

    lm_fm_result->first = first_value;
    lm_fm_result->second = second_value;
    return lm_fm_result;

The result allocation belongs to function/result materialization in the
prologue. It is not performed by `return`. All return paths publish the same
result reference for that invocation.

An Array constructor allocates its Array header and owned backing storage
in the selected arena through `lm_own_arena_new_zero` and
`lm_own_arena_array_new_zero`. The header is not a structural type descriptor.
Returning the Array publishes the existing ArrayReference; it does not recreate
the header or backing storage.

A closure implementation may similarly allocate an environment Structure and
callable descriptor in the selected arena before a return expression publishes
the descriptor. Returning a closure is not permission to allocate a second
environment or descriptor.

The root ownership strategy keeps independently returned reachable objects
valid and distinct until they cease to be reachable or the Message arena is
destroyed. The current end-turn reclaim pass may release unmarked tracked
allocations; it does not require a nested owner arena. Any later precise
collector must preserve the exact same visible references and live addresses.


19.29.12.H2.1. Hosted Source-Ordered Module Initialization

The hosted ANSI C executable boundary materializes these direct module-level
ordinary value sites in the attached root Message Thread arena:

    named Structure construction;
    anonymous `():` Structure construction, including an empty Structure;
    ordinary `[]:` ArrayReference construction;
    unmarked runtime `table:` construction.

A descriptor declaration, function definition, raw `c.array` declaration or
source-only translation Table is not such a site. The mechanism implements the
ordinary arena rules; it does not introduce a module-static source Value kind.

The backend gives every value-producing source site a stable private identity
derived from the resolved source path and source span. It may emit a C
declaration or private anonymous-layout type needed by that site. For the value
itself it emits only a zero-initialized static reference slot: a `T *`-shaped
slot for a StructureReference or an `LmSlice *`-shaped slot for an
ArrayReference, including the hosted Table projection. The referent,
Array/Table header and every owned backing level or row must be allocated in
the supplied arena. A static Structure instance, static anonymous aggregate,
static ordinary-Array or Table row buffer, or pointer into such backing is not
a conforming implementation of this boundary.

Each site has one private initializer helper whose logical parameters are the
executing `LmMessageThread` and selected `LmOwnArena`. The helper performs the
same validation, allocation and initialization as the corresponding local
constructor. Named and anonymous Structure fields are initialized exactly once
in logical source order. An omitted field follows its ordinary initialization
rule, and an empty `():` site still allocates one non-null, distinct empty
Structure referent. For an ArrayReference, extent expressions are evaluated
exactly once in dimension source order before backing allocation, then present
payload expressions are evaluated exactly once in element source order. The
header and all backing levels belong to the supplied arena. For a runtime Table,
row-cell expressions are evaluated exactly once in row/column source order; the
helper allocates the header, row-reference backing and each row referent before
publishing the private Table slot.

The helper publishes its private reference slot only after that site has
completed successfully. A typed exact-reference initializer forwards the
already visible reference into its own slot without copying or reallocating the
referent. Thus a later binding such as `Point: alias original` has exact
reference identity with `original`; reading either binding after module
initialization observes the same object. Two actual constructor sites allocate
distinct referents even when their descriptors and initializer values are the
same.

Module initialization is an ordered traversal, not a C initializer dependency
accident. Direct sites run in source order. At the first ordinary `import`
occurrence, the imported module's dependency traversal and direct sites run at
that source position before traversal resumes in the importer. A module and
each of its stable source sites run at most once in one generated executable,
keyed by the path produced by the import resolver. Repeated imports that resolve
to the same path therefore neither allocate another instance nor repeat
initializer side effects. A later import cannot retroactively make one of its
bindings visible to an earlier initializer. Modules selected by the established
hoisted `predef` traversal participate once in that traversal's deterministic
order; reaching the same resolved module path again through `predef` or
`import` does not schedule its value sites again.

The current resolver does not canonicalize lexically distinct relative path
spellings such as `x.lm2` and `./x.lm2`; they remain distinct module identities
until portable path normalization is added.

Every helper is emitted after the declarations and callable prototypes needed
by its body. The generated dispatcher is invoked only after the process root
Message Thread has been attached and its root arena is available. It receives
that actor and arena explicitly. It completes before the user `main` body,
before any declared worker actor is started, and before any route or inbound
provider can make worker execution observable. If initialization fails, the
hosted failure path does not enter user `main` or start workers; it tears down
the attached root by the ordinary generated cleanup path. Successfully
published references remain alive until that root arena is destroyed.

Initializer name resolution uses the namespace snapshot immediately before the
site. The pending result slot is not a provisional self-binding. Consequently,
an initializer cannot refer to the result being constructed unless an older
visible occurrence already exists, and it cannot refer to a binding introduced
later in the module traversal. An unresolved self-reference and a forward
reference are hosted diagnostics; the backend must not emit a tentative null
slot and let either expression observe it. The current occurrence-projection
limitations described in sections 19.20.1.1 and 19.20.4 may independently
reject publication of a result whose exact name already has an older visible
occurrence. That limitation does not make the pending occurrence visible as a
self-reference.

The initial hosted boundary is deliberately unconditional. A direct ordinary
value site nested in `os`, `ifdef`, `guard` or another conditionally emitted
top-level wrapper is rejected until conditional namespace replay and a
presence-matched initializer schedule are implemented. A module value inside
an `extern_c` wrapper is likewise rejected until that wrapper participates in
the dedicated slot/helper phases instead of recursively emitting a complete
module pipeline. A module value inside an L2/L3 level receiver nested in an
already active module surface is rejected for the same reason until nested
surface declaration and scheduling are replayed in source order. A local
constructor in an executable `if` remains an ordinary execution-time operation
and is not affected by this restriction.

The complete generated executable must provide exactly one non-imported hosted
`main` definition to own the attached root. A root translation containing
module-level ordinary value sites but no such entry is rejected until an
explicit library/module-initializer ABI is selected. An imported module need
not define `main`; its sites join the importing executable's dispatcher. A
`main` definition supplied by an imported module is rejected, as are multiple
candidate `main` definitions anywhere in the root import graph. A `main`
inside a conditional, `extern_c` or nested level wrapper cannot host this
unconditional module-value schedule and is rejected when module sites exist.
These are
hosted executable-boundary restrictions, not new source Value kinds or general
rules forbidding another runtime profile from exposing an explicit module
initializer.


19.29.12.H3. Generated Cleanup for Explicit Low-Level Resources

An ordinary owner arena can be destroyed as one region. Explicit low-level or
external resources may additionally require generated cleanup before their
owner is released.

A C99 lowering may direct all exits through one cleanup label:

    int lm_generated_handler(
        LmMessageThread *thread,
        const LmMessage *message)
    {
        int status = 0;
        LmResource resource;
        int resource_initialized = 0;

        status = lm_resource_init(&resource);
        if (status != 0) {
            goto exit;
        }
        resource_initialized = 1;

        status = lm_generated_body(thread, message, &resource);
        if (status != 0) {
            goto exit;
        }

    exit:
        if (resource_initialized) {
            lm_resource_destroy(&resource);
        }
        lm_message_thread_safe_point(thread);
        return status;
    }

This example is conceptual. Exact runtime type names and error conventions are
profile-defined. Cleanup of an external resource is not a copy or destructor
for an ordinary Structure or Array referent. The aggregate remains
arena-managed through its reference; cleanup follows the explicit resource
descriptor.

Cleanup ordering must respect dependencies. If one resource's release method
uses another resource, the latter must remain live until the first release
finishes. A generated profile may record cleanup actions in reverse
initialization order or derive ordering from explicit visible descriptors.

A control exit first selects and publishes the surviving result/failure
reference, then retains, detaches or reparents its existing owner region as
required, marks and updates the owner graph, executes required explicit cleanup
and finally reaches its collection/release point. Cleanup must not destroy the
owner region containing an ordinary StructureReference or ArrayReference
already selected as a surviving result.

Possible precise arena operations are:

    void *lm_owner_arena_alloc(
        LmOwnerArena *arena,
        size_t size,
        size_t alignment);

    void lm_owner_arena_reset(LmOwnerArena *arena);
    void lm_owner_arena_destroy(LmOwnerArena *arena);

    int lm_owner_branch_detach(
        LmOwnerBranch *branch,
        LmOwnerBranch **out_detached);

    int lm_owner_branch_reparent(
        LmOwnerBranch *branch,
        LmOwnerBranch *new_parent);

    int lm_owner_branch_transfer(
        LmOwnerBranch *branch,
        LmMessageThread *receiver);

Generated operations may be selected from namespace-visible descriptors:

    release_external_fields
        releases explicitly owned external resources;

    copy_to
        implements an explicit `copy` or `own` operation, not return;

    serialize
        implements a selected message/codec boundary;

    trace_owner_edges
        supports local owner-graph walking or local branch-root reference
        tracking.

The old historical names `LmArena`, `LmBranch` and `LmThread` described this
same conceptual future direction. They are not the current API and should not
be presented as already implemented. The actual bootstrap API remains
`LmOwnArena`/`libown`; the generic future names in this subsection deliberately
avoid implying ABI compatibility.

An explicit future `own` expression may lower to a selected generated method:

    status = lm_copy_to_owner(
        current_owner,
        source_reference,
        &saved_reference);

or to a lazy-owned edge:

    status = lm_add_lazy_owned_edge(
        current_owner,
        source_owner,
        source_reference,
        &saved_reference);

Both lowerings implement an explicit ownership operation. Neither may be used
as the hidden lowering of ordinary `return`.

Whole-branch message transfer may lower by detaching the existing branch from
the sender owner graph, attaching it to the receiver and invalidating all
sender-side handles covered by the transfer contract. The objects are not
copied and retain their identity inside the transferred branch.

Optional per-Message-Thread tracing or reference counting may track owner
roots. It remains local; the source model does not require a global heap scan.


19.29.12.H5. Historical Lowering Requirements and Open ABI Details

A conforming C99 or other backend must preserve:

    StructureReference and ArrayReference representation;
    arena allocation of every ordinary aggregate referent;
    module/root arena lifetime for top-level values;
    stable object identity;
    exact-reference return;
    owner validity across every published reference;
    no raw mutable inter-Message-Thread references;
    explicit copy/serialization/transfer semantics;
    cleanup of declared external resources;
    bounds metadata for checked high-level arrays;
    correct low-level lifetime for explicit L2 machine storage.

The following physical details are implementation/runtime matters rather than
fixed source syntax:

    binary layout of arenas and owner handles;
    lazy-edge table representation;
    immutable-store representation;
    local owner-graph metadata;
    allocation descriptor indexing;
    message serialization format;
    OS-thread and scheduler mapping;
    synchronization primitives;
    status/result conventions;
    generated copy method signatures;
    exact tree-cut promotion algorithm;
    transfer invalidation representation;
    memory-pressure heuristics.

These details may be described by a runtime ABI specification or explicit
backend profile. They must not be allowed to contradict the normative rules in this
section.



19.29.14.H. Historical Hosted Control and Ownership Vocabulary

The detailed control lowering, nested-owner vocabulary, retry contracts and
diagnostic mechanisms in 19.29.14.1–19.29.14.10 below describe the hosted
Revision-1 runtime. They are retained to preserve implementation knowledge and
tests, but are non-normative for the new translator until re-derived for the
selected Revision-2 result ABI. This historical marker does **not** make the
one-arena-per-Message rule or the mandatory local end-turn collection boundary
optional: sections 19.28.R2 and 19.29.0–19.29.4 take precedence wherever the
old text speaks of nested owners, owner regions, several arenas, or another
collection point.

Implementation status for this subsection:

    `return`, `stop`, unlabelled `break`, unlabelled `continue` and `assert`
        have current bootstrap lowering;

    recoverable `catch` / `throw` / `throws`
        have current bootstrap lowering;

    `retryable` / `retry`,
        `redo` and labelled `break` / labelled `continue`
        are PROPOSED memory contracts and NOT IMPLEMENTED as those source
        receivers.

The currently registered `guard:` is an unrelated module/prelude guard. It
does not implement recoverable `throw`/`catch`. References to `catch`, `throw`
and `throws` in this subsection specify their required memory behavior.

Current `stop:` is a cooperative state transition rather than an immediate
control transfer. It reaches collection when execution arrives at the common
end-turn boundary. Ordinary stop requests retain the first accepted status;
diagnostic and collector/runtime failures use the failure-dominant channel so
that a preceding `stop: 0` cannot hide a later fatal condition in the same
turn.

The memory model has one local collection: a reachability walk of the current
Message's Structure graph (section 19.29.4). There is no owner-tree cutting
and no nested owner region.

A control operator does not free memory merely because it changes control flow.
It may leave a frame, handler or the whole running Message. Ordinary `return`
does not collect. Collection runs once per turn, at end-turn
(section 19.29.4).

The collector is local to one Message. It does not:

    stop unrelated Messages;
    scan foreign arenas;
    require one global heap lock;
    perform global tracing as a source-semantic requirement.

It may inspect:

    the current Message's roots and StructureReference slots;
    Array backings in this arena;
    continuation and future roots;
    live L2 `@` pins;
    implementation priority and memory-pressure metadata.

It may:

    mark unreachable chunks and Array backings;
    release them, or compact survivors into fewer blocks (section 19.29.8);
    destroy the Message's arena at termination.

An ordinary Structure or Array `return` does not copy. The collector must
preserve every still-reachable referent's exact reference.

A physically coarse profile may retain reclaimed capacity/blocks until the
entire running Message is destroyed, but it must still execute the semantic
end-turn pass and update liveness/index state. The current hosted bootstrap is
more precise than retain-until-destruction: `lm_own_arena_reclaim` marks its
registered roots/pins and releases unmarked tracked allocations at each
end-turn. This remains a local non-moving bootstrap collector, not a different
global GC.

The unit of collection is the Message arena, not frame/handler/attempt
arenas.


19.29.14.1. Terms: Collection

This document does not define a general high-level source operation which
releases an arbitrary ordinary Structure or Array referent.

The term collection means a local reachability walk of one Message's
Structure graph. It runs once per turn, at end-turn (section 19.29.4).

A collection pass may include:

    marking from Message roots;
    releasing unreachable chunks and Array backings;
    compacting survivors into fewer blocks;
    pinning objects with a live L2 `@`;
    destroying the Message arena at termination.

These mechanisms are not finalization syntax and are not ordinary control-flow
handlers. They are runtime memory machinery of the Message arena.

Logical unreachability is distinct from physical release. A chunk may be
marked reclaimable but retained until a batch safe point. A profile may
compact at end-turn or retain until the running Message is destroyed. These
choices must preserve all live references.

The current hosted bootstrap implements root allocation, arena-wide
destruction at Thread teardown and lazy-edge helpers. At every end-turn it runs
`lm_own_tree_cut(root_owner)` followed by `lm_own_arena_reclaim(root_owner)`;
the latter marks registered roots/pins, conservatively scans pointer-sized
words and releases unmarked tracked allocations. The next step is a precise
address-domain-aware Lmx traversal, not the introduction of nested frame
arenas.


19.29.14.2. Control Exit and Lifetime

Control exits are connected to memory only through Message reachability.

Generic sequence:

    select the control exit;
    evaluate and preserve any result/failure reference required by that exit;
    publish surviving roots of this Message;
    run required explicit resource cleanups in valid dependency order;
    run a local collection pass only at end-turn (section 19.29.4);
    complete the control transfer.

For an ordinary StructureReference or ArrayReference return, section 19.29.5
is normative: evaluate and publish the exact existing reference. Do not
allocate a replacement aggregate.

The control operations relate to safe points as follows:

    `return`, `break`, `continue`
        leave ordinary executable or loop scopes; they are not collection
        safe points;

    labelled `break`, labelled `continue`
        may leave several nested frames; still not collection safe points
        by themselves;

    `throw`
        leaves recoverable failure scopes. Unwind to `catch` does not
        collect. Uncaught `throw` that leaves the turn collects at
        end-turn or termination;

    `retry` / `redo`
        abandon attempt-local bindings; do not collect. The next attempt
        runs in the same turn. Garbage waits until end-turn. There is no
        nested attempt arena;

    `assert`
        if it leaves the turn, collection is that turn's end-turn or
        Message termination;

    `stop`
        requests current-Message termination but does not itself leave
        the current lexical scope; cleanup and collection occur through
        ordinary control flow and the common end-turn boundary;

    running-Message termination
        destroys the Message arena except for interned process-root
        descriptors and explicitly managed L2 resources.

No control operator is a memory operation by itself. Reclamation follows
because roots and reachability change.

`finally` and generated cleanup handlers run because their enclosing scope or
resource contract requires cleanup. They must not invalidate a surviving
result or failure reference. If a cleanup method itself sends a message or
fails, the selected profile must define ordering and diagnostic behavior rather
than leaving partially destroyed ownership state observable.


19.29.14.3. `assert` and Memory

`assert` represents diagnostic invariant failure, not ordinary declared
recoverable failure flow.

When an assertion condition is false, the runtime records an
`AssertionViolation` diagnostic and exits through the diagnostic path selected
by the execution-context profile.

Default Message Thread sequence:

    the assertion condition is false;
    record the AssertionViolation diagnostic;
    preserve diagnostic data in an owner which survives reporting;
    transfer control to the Message Thread diagnostic root;
    terminate the current task or Message Thread by default after reporting;
    run the local collection pass;
    destroy or release the abandoned owner graph according to the termination
        policy.

An assertion violation is not part of the declared `throws` set.

An assertion violation is not caught by `catch` unless a non-default
diagnostic profile explicitly bridges the two channels.

An assertion violation does not execute `throw` merely because both paths leave
the current body.

Assertion exit may reclaim memory because it abandons owner regions. The
reclamation is performed by the local collector, not by an `assert`-specific
free operation.

If a diagnostic profile keeps the Message Thread alive after the assertion,
only regions abandoned by the diagnostic exit are cut. Persistent state still
reachable from the Message Thread root remains owned unless the diagnostic
policy resets, detaches or destroys it.

Diagnostic payloads obey normal ownership rules. If the diagnostic records a
reference to a value in an owner which will be destroyed, the diagnostic must
already have a surviving representation before destruction. This may be a
preallocated diagnostic record, an explicit serialization/copy operation, an
immutable stable value or a detachable existing owner region. The assertion
exit must not silently reinterpret ordinary Structure or Array `return`
semantics.


19.29.14.4. `catch`, `throw`, `throws`

`catch`, `throw` and `throws` define declared recoverable failure flow. They are
distinct from `assert`. They are not the module/prelude `guard:` receiver.

    catch / throw / throws
        declared, expected, recoverable failure path;

    assert
        diagnostic invariant violation path.

`throws` lists the names that may leave the executable. A caller of such
an executable must provide a `catch` for each listed
name or itself declare that name in `throws`. A call that does neither is
rejected.

`throw: Name(arguments)` exits the current executable body. It does not
continue the remainder of that activation after the `throw` site and does not
produce the declared return value. A `catch` that calls the same executable
again starts a new activation from the beginning of that executable. That
re-call is not resumption of the abandoned frame. The
arguments are the throw payload. They bind to the parameters of the selected
`catch: Name (...)`.

`catch: Name (parameters)` is a landing pad in a caller block, not an ordinary
nested `sub` and not a sequential label that is entered on first pass. Its
body runs only when that name is delivered. After the `catch` body completes,
execution continues in the same block at the statements following that
`catch`. Those following statements, up to the next `catch` in the same block
or the end of the block, are the region re-entered or skipped according to
where the `catch` was written: a `catch` before a call re-enters the following
region; a `catch` after a call continues past the `catch`.

Two `catch` receivers with the same name in one block are an error. A series
of same-named `catch` receivers is written as separate nested blocks, each
with its own `catch`. A `throw` is delivered to the `catch` of that name in the
block from which the throwing executable was called, not to a same-named
`catch` in a sibling block.

Default recoverable-failure sequence:

    a condition or callee produces `throw: Name(arguments)`;
    bind the payload arguments in an owner visible to the selected `catch`;
    leave the throwing body; do not resume at the `throw` site;
    mark the abandoned callee frame owners exited;
    update the owner graph;
    run required cleanup for the abandoned frame;
    run a local collection pass if this is a selected safe point;
    run the matching `catch` body in the caller block;
    continue in that caller block after that `catch`.

`throw` does not transfer to the diagnostic root by default.

`throw` does not use the assertion channel.

`throw` does not directly release memory. It creates a possible safe point by
leaving an owner context.

A failure payload which must survive the abandoned owner must already be owned
by a surviving owner, be represented in a preexisting result/failure owner, or
reside in an existing region which can be detached/reparented consistently.
An explicit future `copy`/`own` operation may construct a separate failure
payload before the exit. The failure transfer itself must not accidentally
copy an ordinary payload while claiming to preserve its identity.

If a failure crosses a Message Thread boundary, it uses ordinary message
boundary behavior: copy, serialization or whole-branch ownership transfer. A
raw reference into the failing Message Thread owner graph does not cross.

A translator may lower `throw` as a structured status return from the callee
and a same-function branch or `goto` in the caller to the point after the
selected `catch`. It must not lower `throw` as a `goto` from the callee into
the caller. Root-level `longjmp` is not the default.

`catch` re-entry must not observe an abandoned callee's invalid borrowed
references. A compiler or runtime may reject such a retained borrow, clear the
binding according to its descriptor, or maintain the source owner if the edge
was explicitly established as owned before the failure.

A `throw` of the same name from inside a `catch` body is not a re-entry of that
same landing pad. It is a new failure in the enclosing caller, subject to that
caller's `catch` or `throws`.


19.29.14.5. `retryable`, `retry` and Attempt Arenas

`retryable` defines a restartable frame. `retry` abandons the current attempt
and re-enters the nearest or named retryable frame.

Default retry sequence:

    select the nearest or named retryable frame;
    preserve any retry control metadata in the outer retryable owner;
    abandon the current attempt;
    mark attempt-local owners as abandoned;
    update the owner graph;
    run required attempt cleanup;
    run the local collector at the retry safe point;
    release or retain abandoned attempt arenas according to the implementation
        profile;
    recreate bindings declared inside the retryable frame;
    begin the next attempt.

`retry` is re-execution, not automatic transactional rollback.

It does not roll back external side effects.

It does not automatically restore outer mutable bindings unless the selected
retryable receiver defines and implements a stronger transaction/snapshot
policy.

Values which must survive `retry` belong to an owner outside the abandoned
attempt. A borrow into attempt-local storage cannot remain valid after that
attempt is destroyed. Survival may use an already outer-owned object, a
preallocated retry-state Structure, an existing detachable region, or an
explicit ownership operation performed before retry.

Conceptual distinction:

    attempt-local value
        collectible when the attempt is abandoned;

    value materialized directly in the arena controlled by the outer retryable owner
        survives the abandoned attempt;

    value explicitly copied/owned into the outer owner
        survives according to that explicit operation contract;

    value stored in the Message Thread root
        survives retry unless explicitly replaced, transferred or cut.

This permits repeated attempts to reclaim their temporary regions without a
global tracing collector. Each abandoned attempt loses its local owner graph,
and the next attempt begins with fresh attempt-local bindings.

If a `retry` path carries a diagnostic or reason Structure to the next attempt,
that Structure follows the same rule: it must already live in the outer owner
or an existing surviving region before the attempt arena is cut. Retry does not
perform an implicit return-style promotion or copy.


19.29.14.6. Owner Replacement and Null-Like Removal

A plain-name rebind appends a namespace occurrence and does not remove the
ownership edge held by the preceding occurrence. When an occurrence ceases to
be active, or when an addressable owner replacement, explicit removal or
profile-defined null-like operation actually removes an ownership edge, the
implementation may run the local owner-tree cut procedure.

Conceptual sequence:

    identify the old owner edge;
    establish the replacement edge, if any;
    remove the old edge from the local owner graph;
    determine whether the old branch/subtree still has a surviving owner root;
    process explicit lazy-owned edges reachable from surviving owners;
    promote, pin or redirect those explicit edges as their contracts require;
    preserve a detached branch only when it became an independent surviving
        owner;
    mark every otherwise unreachable region reclaimable;
    physically release according to the implementation profile.

This is the ordinary memory-cutter path for local owner-graph mutation.

It does not scan all objects in the process.

It does not stop other Message Threads.

It does not inspect another Message Thread's private owner graph.

A null-like primitive stored in a field is not necessarily an owner operation.
Whether assigning it removes an ownership edge depends on the field descriptor.
A borrowed view can be cleared without releasing its source owner. An owned
edge removal may make a whole branch collectible. An external handle may
require an explicit close/release operation exposed by a namespace-visible
descriptor.

Replacing one local reference slot does not destroy an ordinary Structure or
Array if another surviving edge or owner root still refers to its region. Conversely,
keeping only an invalid borrowed pointer in an untracked low-level slot does
not keep an owner alive; explicit L2 pointer use follows the low-level lifetime
contract and may become invalid after the owner is released.


19.29.14.7. Emergency Memory Pressure

Emergency memory pressure is runtime policy over owner cancellation and
destruction. It does not turn the language into a global object-by-object
collector.

A runtime may urgently reclaim memory by cancelling, failing, aborting or
destroying selected:

    Message Threads;
    handlers;
    transactions;
    retry attempts;
    branch owners;
    caches or immutable-store generations;
    external-provider mappings.

Selection may use priority, scheduling policy, service-level policy,
diagnostic state, retry count, memory size, responsiveness or explicit resource
budgets.

Default emergency sequence for destroying a Message Thread:

    select a victim Message Thread or task;
    request cooperative cancellation, declared failure, diagnostic termination
        or forced termination according to profile;
    prevent new work from publishing roots into the selected owner graph;
    mark the owner graph abandoned or terminating;
    complete or abort external-resource cleanup according to the emergency
        profile;
    run the local collector if execution state permits it;
    destroy the selected owner regions or complete Message Thread arena graph;
    return the region memory to the implementation allocator;
    emit failure/diagnostic evidence through a surviving supervisor channel.

This is garbage collection by effect because memory is reclaimed
automatically. It is not global tracing by mechanics. The unit selected for
emergency reclamation is an owner region rather than an arbitrary individual
object.

Forced termination may be unable to run ordinary user cleanup safely. A
profile which admits it must distinguish:

    region memory which the runtime can reclaim mechanically;
    external resources which require cooperative close/rollback;
    whole-branch payloads already transferred elsewhere;
    immutable shared storage owned by another provider;
    diagnostic data which must survive in the supervisor owner.

Emergency collection must not reclaim a region which has already been
successfully transferred to another Message Thread. Sender-side termination
invalidates sender handles but does not destroy the receiver-owned branch.

The current hosted bootstrap reclaims unmarked tracked allocations at each
end-turn and releases all remaining arena storage at process/root-thread
termination. Fine-grained emergency victim selection and supervisor policy are
future Message Thread runtime work.


19.29.14.8. Collection Ordering Rule

For every control exit which changes owner lifetime, owner/result state
transitions are ordered before local reclamation.

Required general abstract order:

    1. decide the control exit, recoverable failure, retry, diagnostic exit,
       message transfer or termination;

    2. evaluate result, failure and diagnostic expressions while their source
       owners are valid;

    3. publish exact surviving ordinary StructureReferences or ArrayReferences
       only to same-owner preexisting caller, continuation, handler or
       supervisor roots;

    4. perform any explicitly requested copy, serialization or whole-branch
       transfer operation for an inter-Message-Thread boundary, commit it and
       publish the resulting receiver-owned representation or transferred
       branch to the target message root;

    5. retain, detach or reparent existing owner regions as required, without
       replacing ordinary returned aggregates;

    6. mark affected owners exited, abandoned, transferred or destroyed;

    7. update the local owner graph and remove obsolete edges;

    8. execute required resource cleanup while its dependencies remain valid;

    9. run the local collection pass if the point is selected;

   10. release arenas whose owners are destroyed and whose implementation
       profile permits release now;

   11. complete the control/message transfer.

For ordinary StructureReference or ArrayReference `return`, steps 3 and 5 are
owner/root metadata updates only. They perform no object allocation, clone,
copy, lazy promotion or materialization.

For a future explicit same-Message-Thread `copy`/`own` expression, allocation
belongs to evaluation in step 2 because that operation itself requests a new
owned representation. A boundary copy or serialization may instead allocate in
step 4. The subsequent `return`, if any, still returns exactly the representation
which the explicit operation already produced.

For whole-branch transfer, step 4 changes ownership of an existing region and
invalidates sender-side edges. It need not change object identity.

Borrowed references into a destroyed owner are invalid after the cut/release.
A surviving owner may retain valid data only if:

    it already owned the data;
    the existing data owner remains alive;
    the existing region was detached/reparented/transferred consistently;
    an explicit copy/serialization operation created another representation;
    immutable/external sharing is allowed by the selected profile.

The runtime must avoid a window in which a collector sees a selected result as
unrooted. Publishing or reserving the result edge must occur before the source
owner becomes collectible.

In a precise future implementation, compiler/runtime metadata for a return may
be reserved in the caller/continuation frame before entering the callee. The
callee can then publish a reference without allocating on the return path.


19.29.14.9. Mandatory Message-Boundary Collection Policy

The default Message Thread collector scheduling policy is regular rather than
arbitrary.

In the full default Message Thread model, a local collection pass runs at
message boundaries.

One turn may include any of these events before reaching its single common
end-turn boundary:

    an incoming message payload has been copied, reconstructed by
        serialization, or ownership-transferred into a valid receiver owner;

    an outgoing message payload has been copied, serialized or transferred to
        the target queue, transport or target owner;

    a message handler completes normally;

    a message handler exits by `return`, `throw`, `retry`, `redo`, assertion
        diagnostic exit, cancellation or Message Thread termination;

    a reply/failure has been committed to its future, continuation or target
        message owner.

None of the listed events triggers an additional collection by itself. After
the turn has completed FIFO outbox publication or failed-turn rollback and
released its transient roots, the runtime runs exactly one local collection
pass before continuing ordinary Message processing.

The pass may be a cheap no-op when the local owner graph did not change.

It is local to the current Message Thread.

It does not stop other Message Threads.

It does not scan foreign arena graphs.

It does not require a global heap lock.

It does not perform global tracing collection.

It may inspect only the current Message's graph and one arena, registered
address-domain scanners, continuation roots, message-frame roots, explicit L2
pins/handles and implementation priority metadata.

The collector must preserve:

    owner validity;
    no-escaping-borrow;
    exact ordinary StructureReference/ArrayReference return identity;
    no hidden return allocation/copy/promotion;
    no raw mutable cross-Message-Thread references;
    copy/serialization/whole-branch-transfer boundary rules;
    valid external-resource ownership and cleanup ordering.

The regular processing pattern is one collection per turn, at end-turn:

    receive message
        -> join or activate (section 19.28.6)
        -> execute handler or root-body
        -> commit outbox
        -> turn cleanup
        -> run local collection pass
        -> next turn or stop

Concretely, both the generated direct-root `end_turn` path and every
pool-scheduled end-turn path run actor-local collection. A normal callback turn
increments both turn and collection counters. An actor stopped after it was
queued may skip entry execution but still crosses the final
collection/end-turn boundary before becoming STOPPED.

The collection path first invokes `lm_own_tree_cut(root_owner)` and then
`lm_own_arena_reclaim(root_owner)`. At present `lm_own_tree_cut` promotes
lazy-owned edges; reclaim marks registered roots/pins, conservatively scans
pointer-sized words and releases unmarked tracked allocations. This is a
non-moving bootstrap collector, not yet the precise address-domain-aware Lmx
tracer required by Revision 2, but it is no longer merely an end-turn no-op.

The next precise reclamation step is an address-domain-aware traversal of the
one Message arena. Turn and handler state remain ordinary Lmx nodes/roots in
that arena, not nested owner arenas. Once the turn's transient roots have been
released, the collector may reclaim their unreachable nodes/blocks while
preserving every published result and continuation root. This refinement must
not allocate, copy or promote an ordinary Structure or Array merely because
`return` publishes its reference.

A failed collection records collector failure and uses the failure-dominant
runtime request. It therefore cannot be hidden by an earlier successful
`stop:` or process-entry `return: 0`; the stopping turn retains a nonzero
failure status.


19.29.14.10. Long Message Thread Computations and Supervisor Termination

A Message Thread in the default profile is expected to remain message
responsive.

The default runtime is not required to interrupt arbitrary deep computation
inside one handler merely to run the local collector. If a Message Thread enters
a long computation and does not reach a message boundary or another declared
cooperative yield point within its watchdog limit, a supervisor may cancel,
fail, abort or destroy that Message Thread according to scheduling and
diagnostic policy.

This is intentional. Long computations which must coexist with message
scheduling and regular local collection should be expressed as stepwise or
resumable work.

Possible designs include:

    lazy receiver/operator evaluation;
    iterator or `yield`-style production;
    query/search receivers split into bounded steps;
    continuation messages to the same or another Message Thread;
    futures whose producers execute bounded work units;
    retryable frames with bounded attempts;
    explicit handler-level work slicing;
    profile-defined cooperative yield points.

The corresponding source/runtime operators such as `send`, `await`, `yield`,
`schedule` and `thread` have independent implementation status. The conceptual
memory model does not falsely mark an unimplemented source receiver as
available.

If an algorithm must execute as one long uninterrupted low-level operation, it
belongs to an explicit L2 execution profile with defined memory,
synchronization, cancellation and lifetime behavior. Such a worker is not
automatically a Message Thread merely because it runs on an OS thread. It may
be wrapped by a Message Thread facade which sends it commands and receives
typed results.

Therefore:

    default Message Thread
        message-driven, collected at boundaries, supervisable;

    long Message Thread algorithm
        split into lazy, stepwise, continuation or message-visible units;

    long uninterrupted machine algorithm
        explicit L2 worker/profile, normally hidden behind a high-level
        Structure/handle/message adapter for L3 clients.

Emergency memory pressure uses the same ownership principle. A supervisor may
reclaim memory by terminating low-priority or unresponsive Message Threads. The
memory reclaimed is the selected owner regions or whole selected thread graph,
not individual objects discovered through one process-wide tracing heap.

20.2.H. Historical Hosted `LmSlice` Array Projection

The following `ArrayReference`, `LmSlice`, root-arena, closure-capture and
private-static-slot description records the Revision-1 hosted implementation.
It is non-normative for the Revision-2 Array ABI and must not be used to add a
descriptor prefix, hidden method parameter, namespace binding or per-name C
layout to ordinary arrays.

In the current hosted migration stage, an admitted ordinary `[]:` declaration
inside a managed function or directly on an executable module surface
materializes a persistent `LmSlice` Array header plus arena-owned backing
storage in the executing Message Thread's root owner arena (the generated root
actor's arena at process entry). A direct module site uses the source-ordered
initializer of section 19.29.12.2.1. This applies to both trailing extents and
payload-bearing bracket groups and to repeated declarations. Extent expressions
are evaluated exactly once in source order. The current bootstrap admits
statically typed integer extents in the non-negative `long long` range;
malformed or out-of-range C99 integer literals are rejected before C emission,
and a negative runtime result enters the hosted construction-failure path before
any backing allocation. Untyped `c.*` atoms and calls are not admitted as
ArrayReference extents in this stage, except for the dedicated `c.sizeof(...)`
expression form. Each repeated binding receives a distinct header, and any backing
allocations created for it are distinct rather than shared. Backing storage is
initially zero, after which present initializer elements are assigned in source
order; a multidimensional initializer uses explicit nested groups in this
conservative bootstrap. The hosted header currently stores only `ptr` and the
first-dimension `length`. The translator separately tracks binding-local rank,
element type/address depth and constness; when statically known, it checks them
at typed argument, return and whole-reference-assignment boundaries. Passing,
returning or assigning the ArrayReference publishes the existing header and
does not copy its backing. Prefix `@` applied to the binding addresses the
ArrayReference slot, while `arrayReference\ptr` remains the explicit raw-backing
bridge described below.

At a direct module/top-level site this stage retains only a private static
`LmSlice *` reference slot; the header and backing are root-arena allocations.
The hosted translator rejects such a site when the complete executable has no
unique non-imported root `main`, or when the site is conditionally emitted, as
specified in section 19.29.12.2.1. It also rejects ordinary Array construction
in an external function that has no managed Message Thread context. The current
unchecked indexing projection accepts only an unquoted direct ArrayReference
binding followed by enough immediate bracket suffixes to consume every rank. An
exact-quoted or parenthesized reference or a callable result must first be
rebound to an admitted unquoted ArrayReference binding before a complete index
chain is used. A chain that consumes fewer ranks is rejected until partial-index
Array views are implemented.
Capturing an ordinary ArrayReference through a closure environment, runtime
element descriptors, complete runtime rank/shape/stride/storage metadata in the
Array header, runtime bounds checking for ArrayReference indexing at every rank,
complete multidimensional shape checking and partial-index Array views remain
pending hosted work. Allocation descriptors record owner, count, rank and level
for current backing allocations, but that implementation metadata does not by
itself complete the source-level view contract.

The current hosted validator deliberately accepts a conservative subset of C
constant expressions before emitting top-level storage or an initialized VLA.
Literal/operator expressions and unresolved C macro or enum atoms are admitted;
known runtime bindings, call Frames and call-shaped `c.*(...)` atoms are
rejected. Cast and `sizeof` constant-expression classification is pending a
full C-expression classifier and may therefore be rejected even when a C99
compiler could prove the expression constant. This is a hosted limitation, not
a change to the C99 constant-expression rules above.

Until an explicit raw-storage/ArrayReference adapter receiver is registered,
the hosted translator conservatively rejects a typed boundary expression that
directly contains a `c.array` designator where an ArrayReference is required,
or an ArrayReference where a raw pointer is required. This includes casts and
compound expressions whose result category is not proven independently of their
root storage. For a direct `c.array` chain the hosted classifier tracks declared
rank, consumed postfix indices and element address depth: a rank-one remaining
subarray may decay to its corresponding raw address, and a full-rank index is an
element rather than the whole designator. Partial-array update heads remain
invalid because C arrays are not assignable. It must not emit an incompatible
pointer conversion and delegate the distinction to the C compiler.

The existing hosted spelling `arrayReference\ptr` (and a cast wrapped directly
around that spelling) is the current explicit backing-address bridge. It yields
only the raw data address; it does not carry length, rank or lifetime, and the
consumer is responsible for the missing contract. It is retained for bootstrap
compatibility until the dedicated adapter receiver replaces it.

Names that contain spaces use exact quoted identifiers as ordinary fields:

@: int `second slot`

This declares an address-depth-1 primitive slot with base type `int` and
introduces the exact quoted name `second slot`.

The same short-tail whitespace rule applies to address-depth declarations:

@@@: int ppp

This declares `ppp` as an address-depth-3 slot with base type `int`. The spelling `@@@: int, ppp` is the same declaration with an explicit comma field separator. The spelling `@@@: int; ppp` is different: the semicolon terminates the `@@@:` short form after `int`, so `ppp` is no longer the binding-name field of that declaration. The following `ppp` is parsed as the next source item at the current level.


20.2.1.H. Revision-1 Namespace Descriptor/C Layout Projection (Historical)

The remainder of this subsection is non-normative hosted-translator history.
Its descriptor-to-typedef projection, declaration fingerprints and block-local
typedef replay may remain useful only for explicit raw L2 C artifacts. Applying
them to an ordinary Structure, merge result, callable, source local, Table row
or call context violates Revision 2.

At the parser level, a form such as `Name:` is a Structure/Frame and has no
intrinsic C-layout meaning. A structural descriptor affects resolution only
when an explicit declaration or import binds that descriptor in the namespace.

Constructing an instance resolves its descriptor, allocates one Structure in
the current arena and returns/binds a StructureReference. At module level the
current arena is the module or root arena. Construction does not create
descriptor rows, `layout.backend` facts, field tables or other Registry data.

A backend may derive a physical layout from a namespace-visible descriptor or
from a compile-time-known Structure shape. It may emit an ANSI C `typedef
struct`, accessors or internal layout metadata. These artifacts do not mutate
the namespace and are not Lingvamyxa values. A projected ordinary instance
remains arena-managed; ANSI C automatic/static duration never defines its
source lifetime. Static backing is conforming only when it is an internal
implementation of a module-arena contract.

For example, a descriptor explicitly bound as `LmTransSymbol` may expose the
logical fields `name`, `kind` and `depth`. A hosted backend may project it as:

---ANSI C---
typedef struct LmTransSymbol LmTransSymbol;

struct LmTransSymbol {
    LmP0Text *name;
    LmTransSymbolKind kind;
    unsigned depth;
};
---ANSI C---

This C declaration is a projection, not the identity or definition of the
source descriptor. A Table may be passed to an explicit descriptor-conversion
operation as authoring data, but the table name, keys and cells declare nothing
by themselves.

The current named-Structure fallback is confined to descriptor-driven C
type/layout projection and creates no source value or backing storage. Remaining
top-level untracked static backing in other bootstrap paths is not normative
language semantics and must be removed or confined behind an explicit backend
representation of the module/root-arena contract.

20.2.1.H1. Historical Source Descriptors and Target Projection

The source-semantic input is an explicit descriptor bound in the namespace.
That descriptor is an ordinary Structure. A Table may store descriptor-like
data, but table names and rows do not implicitly introduce descriptors, fields
or namespace bindings.

Type checking and `implements(varA varB Consumer)` read namespace-visible descriptors and
the consumer tree. Backend
layout projection consumes an already resolved descriptor and may choose C
structs, pointers, handles, universal records or accessors without changing
source semantics.

A projected non-primitive Structure field contains a StructureReference or
ArrayReference, never an embedded Lingvamyxa aggregate value. An ArrayReference
may project to a header plus backing allocation, but both remain governed by
their arena contract.

`LmSlice` and similar C records are backend ABI helpers, not mandatory
source-semantic registry classes. Likewise, C `const`, `struct`, `enum`,
`union`, pointer depth, alignment and forward declarations are target concepts.
An explicit backend profile may store projection choices in ordinary Tables,
but those Tables do not define the source namespace or Value ontology.

Thus source description and backend projection may coexist in one bootstrap
translator while remaining one-way dependencies:

    namespace descriptor -> resolved Structure/Array semantics
                         -> selected backend representation

The backend representation never creates the source descriptor retroactively.

A backend may maintain implementation-private projection state to ensure that a
target declaration is emitted once. The hosted C bootstrap scopes this state to
one output translation and shares it across imported declarations, prelude,
prototypes, bodies and bounded lexical-scope replays. It is reset before another
output is translated. This state is not a namespace binding, descriptor,
Registry or Table, and source code cannot observe or modify it. In particular,
a Table or relation named `typedef.emitted` has no privileged effect on backend
output.

Projection-state identity is the identity of the target artifact, not evidence
that a source descriptor exists. For a hosted C typedef managed by this shared
projection state, the collision key is its target identifier namespace, C
lexical scope and canonical emitted C identifier. Each declaration at that key
also carries a normalized complete target-declaration fingerprint and a
structural target-presence path. The fingerprint includes every token that
changes the projected C type, including struct/union/function-pointer category,
ordered fields, effective pointer depth, constness, array shape, return type and
parameters. The current bootstrap uses the exact unguarded declaration bytes
emitted at canonical indentation as this fingerprint, so comparison cannot
drift from generated C.

A prior declaration may suppress a later emission only when their fingerprints
are equal, the prior presence path dominates the later path and the prior
declaration is not later in final target-output order. The hosted C bootstrap
emits the prelude before the body, irrespective of the order in which translator
operations happened to request those outputs. Thus a body claim made first
cannot suppress a later prelude claim. Equal declarations under independent
guards therefore remain separately guarded emissions. A declaration emitted in
one conditional branch is not recorded as unconditional.

Different fingerprints at one collision key are an error whenever their
presence paths may overlap. They may coexist only in branches that the emitted
target structure proves mutually exclusive, such as siblings of the same
`#if`/`#elif`/`#else` group. Independent guards are not assumed exclusive.
Leaving a branch removes it from the active dominance path but does not erase
its declaration from per-output conflict validation. A later unconditional
declaration must consequently be compatible with every earlier conditional
alternative that it can overlap.

True block-local typedef fallback remains scoped to its C block and does not
publish translation-unit projection state or a translation-unit target guard.
It may be skipped only when an identical already-projected declaration dominates
that block. The projection state and generated target guard must not introduce a
source name, establish source compatibility, select a layout, or make a
first-declaration-wins choice.

For C tag-backed projections, a `c.struct` or `c.named-struct` layout is
compatible only with a `c.struct` forward declaration, and a `c.union` or
`c.named-union` layout only with a `c.union` forward declaration. Mixing the tag
families at one projected name is a projection error.

The common projection state covers named structures, physical `merge:`,
non-forward `c.struct`/`c.union` layout typedefs, alias/forward declarations,
function-pointer typedefs and implementation-private generated ABI typedefs.
The latter include callable closure layouts and aliases, capture and binder
environments, `fm` return layouts, Table row layouts and fixed
Message-Thread/runtime prelude types. Their generated names and ordering are
backend constraints and do not define language semantics. Translation-unit and
block-local claims use the same state; local claims additionally carry the
identity of their C lexical scope.

The current hosted bootstrap rejects creation of a lazy callable binder while
emitting a structural conditional branch. Its helper functions cannot yet be
hoisted safely when the source callable or prototype exists only in that
branch. This is an explicit backend limitation, not a source-language
restriction or a license to emit a branch-local typedef outside the shared
collision domain.

True block-local named/merged Structure and Table-row fallback typedefs are
claimed in that common state before emission. Incompatible declarations in one
lexical scope are rejected; an inner scope may explicitly shadow an outer
claim, and sibling scopes do not collide. An identical dominating outer claim
may suppress redundant local output. Local scope claims neither publish
translation-unit guards nor create namespace entries.


21.H. Revision-1 Lexical Namespace Model (Historical)

Everything below this heading is retained solely to explain the old hosted
translator and existing tests. It is non-normative and must not be copied into
the replacement semantic/lowering core.

21.H1. Historical Namespace as Ordered Name-to-Binding State

At every source point, the lexical namespace is conceptually:

    Namespace = Name -> ordered Binding occurrences

A Binding records the visible value/reference or translator-known descriptor
role required to resolve that name. Bindings include variables, functions,
subroutines, receivers, callable/structural descriptors, labels, explicit Table
values and ordinary values.

Conceptual example:

namespace:
    fn: IntToInt (int) int
    factorial: IntToInt
    print: Sub(...)
    fn: AddX (int) int
    String: TypeDescriptor
    int: TypeDescriptor
    ---

The example is notation for name-resolution state. A translator may represent
it with an arena-resident Structure/Table, lexical maps, symbol indexes,
persistent overlays, direct references or any equivalent mechanism. Repeated
exact names and their order are source-semantic; ordinary lookup selects the
newest still-active occurrence.

The rule is shared lexical lookup, not global lookup. A view may be local to an
executable definition, block, receiver context, module, service, explicit
namespace import or runtime profile. Names in the visible chain share lookup and
the same `implements(new old Consumer)` admission rule, but the language does not define
one global dictionary for all programs and services.

Inside one active lexical namespace view, Lingvamyxa does not use separate
function, variable and label namespaces. A name introduced as a variable,
function, subroutine, label, local executable, callable descriptor, receiver,
structural/protocol descriptor or imported descriptor participates in the same
ordered occurrence sequence for that exact name. The newest still-active
occurrence is the one found by ordinary lookup. The value behind it may be used
in any way admitted by the consuming code; the namespace does not choose a
different binding according to whether the next form looks like a call, a
rebind or a control target.

21.H2. Historical Local Namespace View

Entering an executable definition creates a local namespace view.

The local view may be implemented as a persistent overlay, copy-on-write map,
statically resolved lexical environment or another representation preserving
the same behavior. No runtime namespace object is required.

A plain-name rebind inside an executable body applies `implements(new old Consumer)`
and appends the admitted occurrence to the local namespace view. It does not mutate
the preceding or outer occurrence. Updating an addressable field/index location
is instead storage mutation and does not append a namespace occurrence.

Local namespace occurrences do not mutate the outer namespace and do not change
the externally visible descriptor of the executable definition.

21.H3. Historical Compatibility of Local Redeclarations and Rebinds

Local redeclaration and plain-name rebinding use exactly the same rule as every
other namespace redeclaration:

    implements(NewType OldType Consumer)

Consumer is the remaining known source that still sees the name. Every path of
`OldType` that Consumer uses must be present on `NewType`. There is no additional
callable-signature, variance, mutability, effect, ownership or conversion
algorithm in the language core. If an application wants to validate any such
property, it represents that validation as ordinary data and code. A name such
as `validate` participates in `implements(varA varB Consumer)` only when Consumer uses that
path.

The old descriptor is captured before the pending local occurrence is visible.
On success the new occurrence becomes the result of ordinary lookup; on failure
the local namespace is unchanged.

21.H4. Historical Function/Subroutine Name Rebinding

Because function/subroutine names are ordinary namespace bindings, a same-name
local declaration or plain-name rebind uses the common structural rule. There
is no separate callable replacement rule.

Example:

fn: IntToInt (int) int

fn: compute (int(x)) (int)
    fn: `slow path` (int(v)) (int)
    return: v * v
    fn: `fast path` (int(v)) (int)
    return: v << 1
    IntToInt: strategy `slow path`
    if: x < 10
        strategy: `fast path`
return: strategy(x)

Here `strategy` is explicitly introduced as a local binding whose initial value
is reached as `slow path`. Rebinding it to the value reached as `fast path` is
valid only when `implements(fastPath slowPath remainingBody)` holds. The later
call `strategy(x)` is separately
validated by the resolved call consumer.

This operation does not replace `slow path`, `fast path`, `compute`, or any outer namespace binding. It only changes the local namespace view used inside the current executable body.

21.H5. Historical Directional Structural Redeclaration

Redeclaration is neither unrestricted replacement nor nominal type equality. It
is the one directional used-path check from section 7.3.1:
`implements(new old Consumer)` with Consumer the remaining known uses of the name.

Therefore:

    int: x 1
    x: "hello"

is invalid when the pending text value cannot be used as the old `x` in the
remaining known uses of that name.

And:

    factorial: "hello"

is invalid when remaining uses of `factorial` still require paths that the
pending text descriptor does not provide. The fact that one value is
callable is not checked by a second hidden compatibility system.

21.H6. Historical Interaction with Return and Function Names

The canonical return mechanism for an `fn` is `return: value`. When `return: value` is written in a valid terminal trailer position, it also closes the `fn` source frame. The current function name is an ordinary namespace binding, not a separate return syntax.

The same visible name may participate in ordinary function/subroutine lookup,
recursion and local namespace overlay operations. If a plain-name rebind appends
an admitted non-function value under that exact name, ordinary lookup selects
the new occurrence. Later recursive call consumption through that spelling then
fails unless the new value itself admits the requested call.

21.H7. Historical Translation and Optimization

The source semantics allow a local namespace copy or overlay, but implementations do not have to allocate an actual dictionary at runtime.

A translator may optimize local namespace operations by:

    avoiding a copy when no local updates occur
    using copy-on-write for a small number of updates
    representing the overlay as a persistent map
    replacing lookups by direct references when types and bindings are static
    inlining a newest callable occurrence when it is non-escaping
    lowering an admitted callable rebind to a local reference/descriptor update
    rejecting or de-optimizing cases that escape the local namespace view beyond the executable lifetime

The source rule is structural: local declarations and plain-name rebinds append
namespace occurrences only after `implements(new old Consumer)` succeeds when an older
exact-name occurrence is visible. No particular runtime namespace
representation is required.

The current hosted backend does not yet expose source access to an arbitrary
older occurrence or project every occurrence sequence as addressable target
data. Such optimization is conforming only while newest-occurrence lookup and
scope restoration remain observable as specified.

The hosted migration currently applies the descriptor gate when binding named
Structure and physical `merge:` descriptors. General plain-name runtime rebind
lowering and materialization of all binding occurrences remain implementation
work; legacy target-storage assignment is not the normative source model above.

The current low-level hosted bind API transfers unique ownership of a raw
descriptor object and therefore rejects passing the exact descriptor pointer
already owned by the preceding occurrence. That is an implementation memory-
ownership guard, not an additional source compatibility rule. A general rebind
of the same StructureReference remains admissible because
`implements(new old Consumer)` compares used name paths; its lowering must retain,
clone or reference-count the value instead of creating two raw owners.

Closure capture of nested `fn`/`sub`, including after the defining frame
exits, follows section 7.3.3: captured names live in the env Structure.
Rebinding an outer plain name that was not captured remains the ordinary
section 7.3.2 rule in the defining frame.

Escaping local namespace overlays and explicit global/external update syntax
are not specified in this document.

20.2.2.H. Historical L1 Raw-Dump Receiver

The following is the former hosted receiver description. The current L1 is a
separate structural language; raw C belongs only to the last-resort C receiver.
Original text and examples follow unchanged.

20.2.2. L1 Substrate Escape and Level Receivers

`L2` and `L3` are level receivers. `L1` is instead an external-substrate escape
receiver. All three consume one body Structure; since a Structure contains an
ordered field sequence, this is enough to consume any number of source fields.
The bootstrap records this distinction explicitly: `L1` is in
`receiver.substrate`, while only `L2` and `L3` are in `receiver.level`. Thus the
ability to embed a necessary substrate fragment does not make L1 a third
Lingvamyxa source-semantic level.

The `L1` receiver walks its body fields in order. If a field is a string/payload
atom, `L1` writes that payload at the current generated L1 position. This rule is
not tied to one spelling: ANSI-style strings, python-like quoted raw strings and
block strings are all string payload forms. If a field is a Lingvamyxa Structure
or Frame, `L1` dispatches it back to the translator. Thus an `L2` frame can be
nested inside `L1`, and an `L1` implementation fragment can be nested inside
`L2`.

A hosted ANSI C bootstrap profile may provide small L1-output receivers at the
root level and inside `L1`. These receivers are translator conveniences, not
new high-level descriptor/value categories.

Example:

include: "<stdio.h>" "<windows.h>"

This writes:

---ANSI C---
#include <stdio.h>
#include <windows.h>
---ANSI C---

An include string whose payload is already enclosed in `<...>` or `"..."` is
copied as the C include target. Otherwise the payload is treated as a local
quoted include target.

An `os` receiver may select L1 output branches by target platform:

os:
    win:
        include: "<direct.h>" "<windows.h>"
    unix:
        include: "<unistd.h>"
    default:
        "/* fallback L1 text */"
end: os

The bootstrap profile may lower these branch heads to target preprocessor
conditions such as `_WIN32`, `__APPLE__` or `__unix__`. The branch
body is still ordinary L1-output content: string payload, `include`, nested `os`
or another translator receiver admitted by the profile.

In an L2 translator context, `os` also controls which source declarations and
method bodies are compiled for the selected target. The compiler may add their
ShortNameIds, direct links and method-pool records to its compile-time work
table before lowering later L2 bodies; it does not create a runtime namespace.
Platform branches are treated as alternative implementations of a structurally
admitted interface: the same function or Structure name may appear in several
`win`/`mac`/`unix`/`default` branches. Each
same-name occurrence may be validated by the explicit directional
`implements(new old Consumer)` operation before its graph construction/link is
admitted. Branch declarations are considered in source order. The selected
branch emits the actual callable/Structure provider occurrences; ordinary
unqualified structural lookup still selects `[0]`, never the newest occurrence:

os:
    win:
        fn: platformValue () int
            return: 1
        end: platformValue
    default:
        fn: platformValue () int
            return: 2
        end: platformValue
end: os

external:
    fn: main () int
        return: platformValue() = 0
    end: main
end: external

The explicit `c.platformValue()` spelling is still available as a low-level
C-surface escape, but it is not required for names imported by L2 `os`.

The `L2` receiver also consumes one body Structure, but it does not print
standalone strings as ANSI C. The rule is relative to the Structure being
translated to ANSI C: if a string field appears at level 0 of the body that `L2`
is asked to translate, and no receiver consumes that field, it is a compile-time
error. Nested Structures owned by another receiver are not reclassified by this
generic rule; that receiver defines what its own body fields mean. If a receiver
asks `L2` to translate such a nested Structure, the same level-0 rule applies
again inside that translated body. This is a phase error of the active consumer:
for `L2` it is reported by the compiler/translator, while an interpreter profile
would report the corresponding error in its own execution phase. The `c.name`
form is likewise consumed by the `c` receiver/projection: it prints an ANSI C
ordinary identifier only at the position where that explicit receiver is used.

Example:

L2:
    L1:'''typedef enum LmTransSymbolKind {
        LM_TRANS_SYMBOL_VARIABLE = 1,
        LM_TRANS_SYMBOL_FUNCTION = 2,
        LM_TRANS_SYMBOL_PROCEDURE = 3,
        LM_TRANS_SYMBOL_LABEL = 4,
        LM_TRANS_SYMBOL_STRUCTURE = 5
    } LmTransSymbolKind;'''

    fn: main () int
        return: c.LM_TRANS_SYMBOL_VARIABLE
    end: main
end: L2

The enum constants do not become Lmx occurrences or source-visible structural
names. They remain ordinary ANSI C names and are referenced explicitly through
the permanent C surface escape, for example
`c.LM_TRANS_SYMBOL_VARIABLE`.

When the bootstrap translator reads explicit configuration Tables such as
`lm2/trans_registry.lm2`, keys follow the ordinary identifier rule. A valid
ordinary identifier is written bare:

    u32
    prefix
    sqrt_ansi_c

If a key contains operator characters, dots, arrows, whitespace,
punctuation, active structural words in that table position, or any spelling
that must round-trip exactly, it is written as an exact identifier:

    `return`
    `+`
    `!=`
    `c.*`
    `operator.infix`
    `translator class-->spelling`

The backticks are not part of the key. They are the exact-identifier delimiter,
and the resulting atom is an exact identifier, not a string literal.

The same canonicalization rule applies here as in ordinary source: if exact
identifier content is a valid bare identifier, the bare and exact forms name
the same key. This rule is purely lexical and does not make the key a class or
namespace binding.

The current bootstrap first reads configuration from `lm2/core.lm2` and then
from `lm2/trans_registry.lm2`. It uses an explicit loader to convert selected
rows into compiler-private receiver/operator/backend work entries required to
start the translator. That conversion is an implementation mechanism. Loading
the Tables does not create or mutate semantic runtime state, and arbitrary
application Tables are never scanned this way.

At the earliest bootstrap point, the restricted loader recognizes root
`table:` and ordered `join:` Frames because the ordinary receiver bindings do
not yet exist. Only `.lm2` profile candidates are currently accepted. This is a
bootstrap limitation, not a second table model and not source semantics.

For every ordinary `table:` form, the first column is simply the row key by the
selected Table profile. A column named `class`, a Table named `class`, or a key
spelled like source description metadata has no special structural effect. The first
body atom `source`, when present, requests a translation-time/module projection
without a public C table symbol; it does not select a RegistryView. L2 and L3
both produce ordinary Lmx Table values in the owning Message arena. A backend
may optimize their physical representation without changing
that rule.

Inside `columns:`, a bare atom is a column name. An anonymous Structure uses
its first atom as the column name and the remaining atoms as explicit metadata,
for example `(l2 binding)` names column `l2` and records metadata `binding`.
`columns` itself does not publish runtime names; it is consumed by `table`.

Rows are dense. The number of row cells must be divisible by the number of
columns. The loader does not use physical source lines to infer missing cells.
The selected Table profile defines empty-cell representation. Expression-level
`None`, if available, is a separately constructed explicit Lmx value and is not
defined by empty cells. A pretty-printer may align columns; alignment is not
semantic.

A bootstrap implementation may lower Tables to a flat `row: table key payload`
internal representation. That is a temporary backend shape, not a different
semantic model.

L2/L3 may also construct a Table through the `join` receiver in section 19.17:

    join: (BaseTable OverlayTable) TargetTable
        columns: class  (value char)
        rows:
                 local  value
    end: TargetTable

This is not an import directive or parser syntax. It explicitly resolves the
source Table operands, constructs a result Table under the selected runtime
lifetime policy and publishes its Lmx occurrence only when requested by the
form.

Every L2 `fn` and `sub`, including a nested definition, lowers to a uniquely
identified C method entry reachable from any callable Lmx occurrence that may
refer to it in the linked/loaded program. Concrete C linkage may be external or
translation-unit-local behind the generated method pool; reachability and
program-wide identity are mandatory. The `external` receiver wraps exactly one
`fn` or `sub` and additionally requests a directly exported raw ANSI C symbol
for foreign linkage:

L2:
    external:
        fn: main () int
            return: 0
        end: main
    end: external
end: L2

Declaration qualifiers are ordinary receiver composition in the C-profile
projection. For example, `const: @: LmP0Node p` lowers to `const LmP0Node *p`.
The same qualifier form may appear in structure fields, parameters and local
declarations when the active L2 lowering profile supports the corresponding C
declarator role.

Address-producing and address-consuming forms:

    @count              address of the primitive storage location `count`
    p: @count           store that address into an address-depth-1 slot
    pp: @p              store the address of `p` into an address-depth-2 slot
    \p                  raw load through the explicit typed address `p`
    leafs[3]            checked ArrayReference access at index `3`
    \(rawBase + 3)      raw load after address arithmetic when `rawBase` is an
                        explicit typed address from an L2 machine-storage operation
