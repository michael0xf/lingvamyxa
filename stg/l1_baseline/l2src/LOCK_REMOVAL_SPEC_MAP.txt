Removing the executor's shared lock: the spec and model map (6f, 2026-09-15)

Purpose. Mikhail's order of 2026-09-15 stops everything else and puts all effort into removing
every lock in the project except the message collection's own, LmxMsgExec's shared lock first,
together with a full arena per Message. This file says, by line, where Lingvamyxa_spec.txt and
L2_CORE_AND_MESSAGE_MODEL_20260912.md (origin/main 07ad3679, after the deletion of decision 18's item
(5)) already fix who owns each piece of runtime state, gives the census of every lock, event and atomic
primitive in the project by file, lists today's state that lives outside any Message's arena (structs on
integration c067bed9, each with the call that allocates it, so a wrong line is refutable by one grep),
and names the points where the spec is silent or contradicts the order. The three inventories
(LOCK_REMOVAL_INVENTORY.txt for exec.c, LOCK_REMOVAL_INVENTORY_LM1.txt, LOCK_REMOVAL_INVENTORY_TESTS.txt)
cite this map's owner codes in their target-owner column.

1. OWNER CODES (the target-owner column of every inventory line takes one of these)
  M  the Message's own arena: its management state as Structure data, written only on its own lane.
  P  the parent's arena: the parent's scheduler and supervision state about its direct children.
  Q  a mailbox admission under that mailbox's own collection lock, the one cross-lane synchronization.
  T  thread-local state of the OS thread running a lane (the turn identity); nothing shared, no lock.
  X  goes away: it existed only for the shared lock, a host form, or a runtime-level list the target
     does not have.
  S  silent: the spec names no owner, or its text contradicts the order; the line names the question
     (section 5 below) and is decided by Mikhail through the lead before it is coded.

2. WHAT THE SPEC ALREADY SAYS, BY LINE (origin/main 07ad3679)

2.1 19.28.R2.2 Message Thread (11430-11596).
  11432-11435: "An inactive Message becomes an L3 Thread when explicitly launched. Its management state
    is ordinary Structure data, to be implemented in L2, not an external C control model. Native handles
    may back the Message mechanism; they do not replace its ownership and protocols."
  11438-11440: "Every L3 Thread has a FIFO inbox/outbox. It executes at most one turn at a time,
    consuming at most one admitted input per turn. Serial turns make ordinary mutation of its arena safe
    without a source-visible lock."
  11442-11443: "Each live Message context owns that mailbox, a parent capability (except the root), and
    the list of its direct children. Supervision is local to that list."
  11452-11456: "Each parent Message contains the scheduler for its direct children: its policy and
    management state are ordinary private Structure data. Each child may choose a different scheduling
    implementation for its own children. There is no separate language scheduler above Messages, no
    shared global Message registry, and no shared global management lock."
  11470-11474: "A running L3 Thread is a logical serial execution lane, not a promise of a dedicated OS
    thread. Physical workers are an implementation mapping of the parent's scheduler; the OS still
    schedules its threads. Native thread, wait/wake and per-mailbox synchronization primitives support
    Message and do not own its scheduling policy or family tree."
  11492-11506 (Mikhail, 2026-09-14): "one arena, one lane, one writer. A Message's scheduler and
    management state is written only on that Message's own lane; no other thread writes into a
    Message's data, and this holds for the C runtime exactly as for L2 ... A child's readiness is the
    child's own control flag ... A parent therefore keeps no list that another thread appends to ...
    A request to another lane (mapping a child onto the UI lane) is a Message to that lane's mailbox;
    the mailbox's admission lock is the one cross-lane synchronization the model permits."
  11507-11534, ownership of cells (2026-09-14, the review chat's consequences, 0c875197; (5) deleted
  657ce3f9, his 2026-09-15 words recorded after the list at 11535-11540):
    (1) "a Message owns its arena, its scheduler record and cursor, the clearing of its ready flag, its
        mailbox except admission, its native users and handoff-safe marks, its success, and its own
        running clear at end_turn; its lane is whichever thread holds its turn" -> code M.
    (2) "The parent owns the supervision cells about its direct children wherever they sit physically:
        committed, tracked, the last-heard time, the execution mapping written at bind ..., the family
        chain (first and last child, siblings' links, the parent link ...), and the settle writes" ->
        code P.
    (3) "Control flags are single cells with one designated cross-lane writer ...: the parent writes a
        child's running=0 and closing (stop); the sender writes the destination's ready at admission;
        the lane that takes a Message's turn ... clears its ready flag; a late read changes nothing"
        -> the flag is M storage with a named cross-lane writer; no lock.
    (4) "Primitives: mailbox admission under its lock, reference counts, wait signals." (11528-11529;
        the coordinator's sentence, open for Mikhail through the lead) -> Q for admission; reference
        counts and wait signals: S, question 5.2.
    (5) "Runtime-level structures under the executor's lock belong to no Message: the root list, the
        slot list, the retire queue, a lane's own queue." -> DELETED by Mikhail's order of 2026-09-15
        (section 0); it was the coordinator's sentence, not his. The four structures it named need
        owners: question 5.1. No inventory line cites (5).
  11582-11587: "low-level synchronization is used only inside the Message mechanism, for example to admit
    concurrent sends to a recipient's FIFO safely. Other components ... coordinate through Messages, not
    their own locks, atomics, shared mutable management tables or private worker schedulers."
  11590-11594: "Necessary thread, wait/wake and synchronized-mailbox primitives belong to the Message
    implementation in L2 (temporarily L1/native bootstrap). ... This does not permit a hidden C Message
    registry or dispatcher. A coordinator Message owns its state exclusively: other Messages send
    requests, not read or mutate its private tables directly."

2.2 19.29.2 One Message Arena and Allocation Domains (12279-12337), the arena's full description:
  12281-12283: "Every Message, inactive or running, owns one logical arena throughout its turns and
    worker migration. L3 source does not select it, and Lmx has no arena field. The arena may contain
    multiple non-overlapping blocks/address domains."
  12285-12289: "Adopting a non-executing Message or a handoff-safe failed child adds its blocks and
    registered domains to this same logical arena (19.29.7--8). It creates no new source arena kind,
    relocates no native node and clones no graph. Ownership and auxiliary domain metadata move
    together; the former owner cannot free the adopted storage."
  12291-12298: adoption is not lexical reparenting; one arena may hold several lexical trees;
    "Reachability, not membership in the arena's block list, determines what survives end-turn
    collection (19.29.4)."
  12306-12310: "Its mutable storage includes Lmx nodes, child payloads, persistent own fields,
    non-interned primitives, Array descriptors/backing and runtime merge results. Immutable primitive
    pools, linked method code/records and explicitly foreign L2 resources follow their own domain
    contracts. Runtime helpers may derive the arena from a node address and its registered range."
  12312-12324: the recommended bump allocator over a backing-block list; "Filling a block preserves
    existing pointers; allocation fails only if the host refuses another block. Nodes may span blocks
    and a physical domain may span registered ranges."
  12326-12337: "Growth factors, block sizes, free lists and collector algorithms are physical choices;
    the one logical arena and end-turn collection boundary are fixed. ... Parser P0 nodes and derived
    runtime Structures allocate in the owning Message arena like other Structures. A microscopic
    Message whose payload is a string still owns one logical arena."
  Consequence for the map: every record that is "management state" of a Message (its control record,
  mailbox queues, scheduler record, roots, range and block bookkeeping) is arena data of that Message,
  allocated by the arena's own allocator, and freed when that arena goes; a calloc'd C record hanging
  off a pointer is the bootstrap's substitute for it.

2.3 19.29.6 Running Message (12480-12542 before the 2026-09-14 clarifications):
  12482-12488: "It owns exactly one logical arena, a FIFO inbox/outbox, one serial execution lane, a
    parent capability (except the root) and the list of its direct children. ... It contains scheduling
    policy/state for its own direct children; except at the root, its parent contains the scheduler
    responsible for it."
  12489-12492: "No dedicated OS thread per Message is required. Physical execution resources and narrow
    mailbox wait/wake primitives implement that choice, not an external L1/C scheduler, shared global
    Message table or global management lock."
  12495-12505, the components: "the Message's Lmx graph and its one arena; FIFO incoming and staged
    outgoing message queues; selected handler callable Structures and their published-state
    Structures; ... parent-owned scheduler policy/state for direct children."
  12520-12522: "Any Registry, cache or Table of a Message is ordinary Lmx data reachable from explicit
    Message roots in that Message's one arena."
  12524-12531: "Ordinary owned Lmx references inside one Message address its own LMX storage. A boundary
    operation may transfer storage and its range metadata to a new owner without relocation. Such a
    transfer does not itself grant simultaneous aliases to ordinary owned storage, even if immutable."
  12533-12542: "Releasing one Message does not require stopping or scanning every Message in the
    process. Different Messages may execute concurrently on different workers because their mutable
    arenas are isolated. Each Message serializes its own turns; ordinary L3 code therefore requires no
    shared-memory lock for its own graph. Concurrent senders are linearized at the recipient's FIFO
    admission by the Message mechanism. ... Parent supervision uses its own child list, not a scan of a
    shared process-wide Message table."
  12595-12640, the stage-5 clarifications (2026-09-14): the top level is one (Messages created without
    a parent are R0's children; orphans re-root under R0); the host outside a turn has no authority
    left, everything the L1 bootstrap gave the host belongs to R0's turns; the settling lane writes a
    settled Message's cells (the endpoint step).
  12641-12674, stage 5 (f) (2026-09-15): his three sentences under his name (the root's close is its own
    closing end-turn, "running=0 is set, and at the end of its turn the closing Message does the same to
    its children; that is all"; "the executor frees its own memory"; "each of our L3 Threads has its own
    scheduler and garbage collector") and, around them, the coordinator's consequences marked "Mikhail
    may overrule", which are open for him through the lead and are not cited by this map as owners.

2.4 The model.
  Section 25 (1186-1247): a Message is the unit of ownership of an ordinary graph, of the serial execution
    of its turns and of interaction by messages; its control policy is the state of an L2 Structure; the
    native part supplies atomic operations, queues, locks, wait/wake and execution; the four relations
    (Structure.node, the data graph, arena ownership, the Message family) and the fifth, execution
    mapping. Stage-5 items (i)-(v): a runtime without a root does not exist; the entry runs in R0's
    turns; nothing of the host remains outside a turn; the top level is one; the World Wide Mix stub.
  Section 29 (1325-1396): each parent services its direct children; no global walker of all Messages;
    P may run A on its own thread while A spreads A1/A2 over others; then the Russian text of the
    one-arena-one-lane-one-writer clarification and the ownership items (1)-(5), identical to 2.1.
  Section 30 (1397-1417): "Message internally synchronizes its mailbox, execution tables, lifecycle and
    ownership transfer. Application modules need no second scheduler or global lock. A short lock of
    the execution table must not cover a wait on another's mailbox or the execution of a user
    handler." Written for the L1 implementation; under the order the "execution tables" and their short lock go
    with the rest, and only the mailbox's own lock stays: S, question 5.3 (the section's rewrite).

4. RULE FOR THE INVENTORIES
  A line's target owner is M, P, Q, T or X only if the section quoted in 2 names it (cite the line);
  otherwise S with the question number from 5. A lock site whose state is M or P and whose lane today
  is the owner's lane loses the lock and keeps the write (the lane tripwire lmx_msg_test_lane_write
  proves the lane); a site whose lane today is not the owner's lane is a write that must move: either
  to the owner's lane (the parent's step reads the child's own cells, 2.1 11504-11509) or into a
  mailbox admission (Q). No site is removed by making its state atomic; atomics are not in the model
