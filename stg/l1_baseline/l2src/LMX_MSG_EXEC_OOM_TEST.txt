Targeted legacy EXEC OOM fixture
===============================

The observed failure was not a slow build: the OOM capacity assertion called
runtime_delete while two test spin workers still waited for g_cpu_stop. Cleanup
then waited for those workers indefinitely. All32 failure exits in this OOM
scenario now converge on one cleanup path: release g_cpu_stop, disable the
test's allocation-failure injection, stop/join the executor, close fixture
events, then delete the fixture runtime. Production Message semantics unchanged.

This is a bounded repair of an EXISTING native test, granted by Grok162600/
163100, not permission to write new application or core behavior in C.

The same exec_selftest binary supports:
  no arguments             current execution scenarios, EXCLUDING the legacy
                           bind-without-map ready-ring capacity scenario
  --oom-only               only the ready-overflow/FIFO scenario
  --oom-cleanup-failure    deliberately fail the capacity checkpoint while
                           both spin workers are active; cleanup must finish
                           and the process must return1, not hang or pass

The original OOM checks remain: queue full before injected growth failure,
actual fail_hits >0, scan flag, no early/lost delivery, FIFO10/20, exactly-once
worker completion and eventual empty queue. The legacy fixture still assumes
eight fill entries; it is not an adaptive arbitrary-capacity test. A future
queue representation change must not be constrained by this legacy fixture.
Never relax its capacity assertions just to force a green result against a
different queue, or leave workers running on failure.

Separation from mandatory execution checks (2026-09-11)
------------------------------------------------------
Grok173000 reported the new unmapped-only-parent route breaks this fixture's
cap=16/nready=8 expectation: it fills the EXEC ring using bind-without-map.
That is exactly the obsolete behavior being removed, not an accepted language
requirement. The default native Exec invocation now jumps over ONLY this
scenario and emits legacy_ready_oom=SKIPPED with the opt-in runner name.
The remaining context/mapping/liveness/handoff/allocation-failure scenarios
are unchanged. Full/Message/Exec selection in run_lmx still invokes that
current native suite; this one legacy scenario is no longer mandatory there.

All281 lines from oom_scenario through its cleanup were compared with6690a66
and are identical, including capacity, injection-hit, scan, FIFO and every
failure exit. Explicit --oom-only / --oom-cleanup-failure still enter the
original scenario directly; no assertions or source tests were deleted.
