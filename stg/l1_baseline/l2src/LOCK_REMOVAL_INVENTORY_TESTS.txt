3. -LaneCheck as it stands (read from lmx_message_exec.c at c067bed9; see 4 for the measurement)
  The oracle is lmx_msg_test_lane_write(rt, owner, site) (L171), armed by LMX_LANE_CHECK=1 (L1172), set
  by run_port_message -LaneCheck (run_port_message.ps1 L203). It is compiled only with LMX_MSG_EXEC_TEST
  (no-op macro otherwise, lmx_message_exec.h L15). It aborts with "LANE WRITE FAIL site=..." only when
  ALL hold: the calling thread's turn Message (thread-local lmx_turn_msg) is non-zero, belongs to rt, is
  not the owner, is not the owner's parent, and the owner is not settled (handoff_ready with no running
  load). It is called at 14 labelled sites (take_ui x3, bind:affinity x5, take_this, stop_unmap,
  stop_reset, unbind:record, run_child_turn, plus lmx_msg_test_unbind_refused at L199).
  Consequences read from the code, not yet measured:
  - It is keyed on turn identity, not on the lock, so it survives lock removal unchanged.
  - A write made on a thread that holds no turn passes silently (turn == 0 returns at L177). take_this's
    ready_clear (L2966) runs in context_worker before the turn starts, so that site can never fire.
  - Only the 14 labelled sites are checked; a new unlabelled write is not.
  So -LaneCheck proves "no write from inside the wrong turn" at 14 sites. It cannot prove "no write from
  a thread outside any turn" without a tripwire: e.g. record the host thread at runtime_new and fail when
  turn == 0 on any other thread.

4. Measured fact: does -LaneCheck go red when one lane write is moved to another thread? No.
  Where: c067bed9 in a scratch detached worktree, never committed; run_port_message -TranslatorPath
  <pinned gen2> -LaneCheck, launched as run_gates launches it.
  Baseline: exit 0 in 57 s, "lmx_message parity PASS", 0 "LANE WRITE FAIL" in any output.
  Mutation: in child_turn_core the run_child_turn:ready_clear oracle call and m->ready = 0 run on a helper
  thread created and joined at the same point (CreateThread, WaitForSingleObject). A one-time marker,
  "LANE MOVE MUTATION", printed in all four selftest stderr outputs (reference.1/.2 and parity.1/.2 stderr),
  so the moved write ran in both builds on both runs.
  Result: exit 0 in 55 s, the same parity PASS, 0 "LANE WRITE FAIL" in any output. -LaneCheck stays green on
  a lane write moved to a thread that holds no turn, as section 3 reads (turn == 0 returns at L177). It
  needs the tripwire in section 3 before it can prove lane discipline once the lock is gone.
  Counting note: the chain's automatic verdict first said RED, because it counted the two strings inside the
  built parity.exe, reference.exe and lmx_message_exec.o. The counts above are over output files only
  (.c .h .lm1 .lm2 .exe .o excluded), and the baseline's count is 0.
  Tripwire as 6f ruled it (the executor records the thread that attached it; a lane write with no turn from any
  other thread aborts), uncommitted: run A on the unmutated runtime exits 1 in 15 s with "LANE WRITE FAIL
  site=take_this:ready_clear owner=4 turn=none". take_this (exec.c L2940) is called by context_worker, which
  marks the record held_by and clears m->ready before it enters m's turn (lmx_turn_msg is set later, L1313), so
  every worker take is a lane write outside any turn off the bootstrap thread. Not exempted. Three ways went to
  6f for a ruling: the worker enters the turn identity before the take (runtime change), the thread holding the
  owner's run claim counts as its lane (tripwire rule change), or the tripwire lands with this as a known
  violation for the design to remove.
