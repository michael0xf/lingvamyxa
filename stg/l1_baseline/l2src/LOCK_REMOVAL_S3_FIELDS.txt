--- Flags

FLAG-1 (contradiction, CONFIRMED by direct read of the lane loop): LmxMsgBindWait.retired is
bundled into one table row with .gen/.slot/.launch_n ("DEL | ruled (S3 launch wake goes) | S3"),
as if all four fields are pure launch-wait/launch-race bookkeeping that disappears together with
the deleted wait primitive. gen/slot/launch_n genuinely are (they exist only to disambiguate
concurrent launch attempts on the same wait generation). retired is different in kind: it is the
poll-checked "please stop" flag a still-running lane thread reads on its own, without being woken,
to learn it should exit — exactly the polling-without-waking design S3's own ruling describes ("an
owner thread loops forever, looks into its own mailbox each round and waits on no primitive").
Direct evidence in this same file: context_worker (exec.c:3042-3133), the lane thread's own loop,
already checks `mine->retired != 0` at :3063 (right after the launch handshake) and again at :3078
(at the top of every iteration, before it blocks on WaitForMultipleObjects) — the retired check
survives untouched by S3's removal of the blocking wait beneath it. Two of the 11 sites
(join_bind_worker, stop_retire_walk) set retired = 1 specifically to make that poll observe true.
If retired is deleted at S3 along with wait_ev/cv/sig/gen/slot/launch_n, nothing is left to tell a
polling replacement loop to stop — S3's own replacement design needs a field that plays retired's
role to survive, even though the row that names it says DEL at S3. This is exactly the kind of stop
the rule is for: recommend the table split this row, giving .retired its own line with a stage that
reflects it surviving in some form past S3 (or naming explicitly what field takes over its role in
the S3 design), separate from .gen/.slot/.launch_n which can stay DEL/S3 as written.

FLAG-2 (missing type, not a missing field on a documented type): LmxMsgCtxPack — the launch
handshake struct (exec.c:2788-2799: rt, addr, wait, go, and either a Win32 gate HANDLE or a
pthread_mutex_t/cond_t pair) — has no row anywhere in LOCK_REMOVAL_FIELDS.txt, because the table's
own header scopes itself to LmxMsg plus five named scaffolding types (LmxMsgEnv, LmxMsgCopy,
LmxMsgRuntime, LmxMsgBindWait, LmxMsgExecBind) and LmxMsgCtxPack is a sixth, undocumented one. It is
touched at two of the 11 sites (launch_gate_go's pack_gate_signal(pack, 1) and launch_gate_refuse's
pack_gate_signal(pack, 2), exec.c:2831-2841) and exists solely to hand the newly created OS thread
its go/refuse verdict before the caller can safely inspect or join it. Since the ticket's own scope
is "fields of LmxMsg, LmxMsgExecBind, LmxMsgBindWait and LmxMsgRuntime" this is not a violation of
this ticket's rule, but it is the one type among the 11 sites' dependencies with zero ownership
documentation anywhere, and S3's launch_gate_go/launch_gate_refuse deletion cannot be written as a
one-line diff without deciding what happens to LmxMsgCtxPack's own gate mechanism (go/gate/gm/gc)
too — worth a row (or an explicit "out of LOCK_REMOVAL_FIELDS.txt's scope, tracked separately")
before S3's design note is written, so that stage does not stop on an undocumented type instead of
an undocumented field.

FLAG-3 (adjacent, not a contradiction at the stop_event site itself, flagged for visibility):
LmxMsg.ready's row says "DEL (a non-empty mailbray is the readiness; no wake) | proposed (map 5.7;
S3 no wake) | S3" — i.e. the table already expects S3 to delete .ready. lmx_msg_exec_stop (the
function containing the stop_event site) writes rec->msg->ready = 0 via ctx_visit_stop_reset later
in the same function (exec.c:3393, not itself one of the 11 named sites, so not given its own line
above), consistent with .ready still existing at integration 79871822 and being cleared, not yet
deleted. No contradiction: the table's own stage tag already places .ready's deletion at S3, same
stage as this function's other changes, so S3's design note can delete this write together with
the field. Listed only because it sits inside the same function as the stop_event site and a reader
tracing that function's diff needs to know both changes land at once.
