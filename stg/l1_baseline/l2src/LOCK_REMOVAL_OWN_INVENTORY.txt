Lock removal, stage O: the lm2/own.lm2 message-thread runtime inventory
==================================================
Ticket, 2026-09-15 (ba, for d6/lock-removal's stage O): Mikhail ordered the
lock-based message-thread runtime in lm2/own.lm2 deleted whole ("да,
удаляйте целиком"), replaced by the one core. This file is the inventory
that comes first -- nothing is deleted under this ticket.

lm2/own.lm2 and stg/l1_baseline/lm2/own.lm2 are byte-identical (diff -q,
confirmed; 3798 lines each). lm2/own_abi.lm2 and
stg/l1_baseline/lm2/own_abi.lm2 are also byte-identical (1126 lines each).
Every own.lm2/own_abi.lm2 line number below applies to both copies; they
are named together and counted once, per the ticket.

--- 2. Consumers outside own.lm2 and own_abi.lm2 (both copies) ---

Grepped tree-wide, build/ excluded, for every family above (named +
the flagged lm_native_message_thread_* gap): every hit outside
own.lm2/own_abi.lm2 falls into six tiers.

TIER 1 -- THE HEADLINE FINDING, the L2-to-L1 translator's own emitted
boilerplate. lm2/trans_l1_statement.lm2: 123 matches (both copies
identical). This is not a call from the translator's own runtime; it is
literal C source TEXT the translator writes into every program it
compiles. Representative lines (full text, not paraphrased): 829 `thread
= lm_message_thread_new();`, 837 `runtime = lm_message_thread_runtime_new
();`, 861 `lm_message_thread_runtime_attach_root(runtime, thread)`, 875
`while (lm_message_thread_begin_turn(thread)) {`, 889 `lm_message_thread_
end_turn(thread);`, 1138 `lm_lmx_message_thread = lm_message_thread_new
();` (the MAIN program's own thread variable) -- and, far more
pervasively, `lm_own_arena_new_zero(lm_lmx_message_thread,
lm_message_thread_owner(lm_lmx_message_thread), sizeof(*...))` as the
STANDARD allocation call the translator emits for every structure, array,
closure environment and table row a compiled L1/L2 program creates (2493,
2502, 4934, 1713, 3177, 3952, 3956, 5140, 5142, 6772, 6784, 8235, 14102,
14141, 14533, 10661, and more -- 123 total). lm2/trans_l1_expr.lm2: 3
matches, same shape (the array/callable-env allocation helpers). lm2/
trans_text.lm2: 1 match (a scaffold-token recognizer for
"lm_lmx_message_thread"/"lm_message_thread_main_context"/etc., part of
the same emission machinery). lm1/build/trans.lm1.c and lm1/build/
rest_lmx_http_client.lm1.c, rest_lmx_http_server.lm1.c (also matched):
these are GENERATED C, the translator's own build output containing the
same literal strings as data inside trans_l1_statement's compiled form,
or the already-translated REST files (tier 3) -- not independent source,
not counted separately.
WHAT IS LOST: every program the L1/L2 translator compiles is built around
an implicit per-program LmMessageThread as its execution context and
lm_own_arena_new_zero(thread, lm_message_thread_owner(thread), ...) as
the allocator for every heap value. Deleting own.lm2 without a drop-in
replacement providing these exact symbols breaks compilation (undefined
references) of every translated C program in the project, not merely
programs that use threading explicitly. This is a production feature in
the deepest sense: the code generator's own contract.

TIER 2 -- the parser's per-thread registry. lm2/parser.lm2:1401,1417,1426
(both copies, identical content though the surrounding file differs
elsewhere -- an unrelated colon-frame/trailer parsing gap between the two
copies, not touching these three lines). lm_message_thread_component_get/
_attach/_remove store lm_p0_registry_component_destroy as a component on
the CURRENT thread, so the P0 parser registry is created once per
LmMessageThread and torn down when that thread's components are released.
WHAT IS LOST: the parser's registry lifecycle tied to a thread's own
teardown; a replacement needs an equivalent per-execution-context
attach/detach hook, or the registry becomes leaked/global.

TIER 3 -- REST HTTP production code. lm2/rest_lmx_http_server.lm2:453
(`lm_message_thread_runtime_admit_lmx(server\runtime, route, body,
content_length)` -- an inbound HTTP request is admitted into the message-
thread runtime as an LMX message). lm2/rest_lmx_http_client.lm2:310,469,
487 (`lm_message_thread_runtime_set_rest_lmx_provider(runtime, ops,
context)` -- registers/clears the client's outbound REST transport as the
runtime's provider). Both copies identical.
WHAT IS LOST: the REST server's ingress path (turning an HTTP request into
a runtime-admitted message) and the REST client's provider registration
(outbound delivery) both call directly into own.lm2's runtime API; no
substitute exists elsewhere in the tree today (grepped: these are the
only definitions of admit_lmx and set_rest_lmx_provider).

--- 4. Does anything in the L1 baseline (stg/l1_baseline/l2src, lm1) link
own.lm1.c's message-thread part? ---

NO, as currently checked in. l1src/own.lm1 (274 lines, the L1-profile
source) has zero matches for every family above (grepped directly).
stg/l1_baseline/lm1/build/own.lm1.c and lm1/build/own.lm1.c (the checked-
in generated output, both copies) also have zero matches (grepped
directly). buildCore.lm1:521 translates l1src/own.lm1 (not lm2/own.lm2)
into this file; that is the path that actually produced what's checked
in today.

BUT: CMakeLists.txt's `refresh_own_lm1` custom target (tier 6 above)
exists specifically to translate lm2/own.lm2 -- the FULL message-thread
module -- into this exact same output path (lm1/build/own.lm1.c) via
trans.lm0, the L2-to-L1 translator. It is not run by default and nothing
currently checked in was produced by it (confirmed: the checked-in file
has zero message-thread symbols, which the refresh target's own output
would not). This is a documented, deliberate two-profile split (tier 6/7:
stg/l1_baseline/oldchain/README.txt describes exactly this failure mode
by name -- "L2-profile archives that define lm_message_thread_*" vs "L1-
profile ones" that do not, and a link failure ("undefined reference to
`lm_message_thread_new'") when the two are mixed) -- not a bug, not a
contradiction to stop and report, a named build-profile boundary that
answers the question cleanly: today, no; the machinery to make it yes
exists in CMakeLists.txt but is unused.
