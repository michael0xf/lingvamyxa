WHAT THE LOCK DOES TODAY (from the inventories, not from a rule)
L1. Address resolution. A walk from rt->root through every child list turns an LmxMsgAddr into a record
    (msg_find_any_locked, lmx_msg_find, self_or_find). The lock keeps the tree still under the walk. This is 35 of
    exec.c's 41 silent 5.1 lines.
L2. The family tree's own writes: child_link, child_chain_remove, the orphan re-rooting, the root-list unlink in
    endp_try_retire and release_slot.
L3. The execution mapping's cells: exec_bind record fields, mapped, launching, the bind wait's generation.
L4. Control flags read and written across lanes: ready, closing, running, handoff_ready, native_users.
L5. Runtime-level lists: rt->slots/n, e->retire_head, e->reap_head, rt->transport, e->ui_lane.
L6. Wakes: exec_wake_locked signals every worker after any turn; exec_ready routes one wake.
L7. Storage moves at settle: adopt_mark, dispose_mark, transfer_adopted, transfer_graph.
L8. Test setters and counters.

    The design's first item is therefore the kernel in L1, and it has exactly these parts:
    - Lmx, the graph and its Structures;
    - LmxMsg { running; success; handoff_safe; Lmx *root }, the four-field Message record;
    - one arena per Message, reached from its root;

      blocking. The L3 Thread is a model, not an implementation, so the kernel fixes no loop shape; the exit
      conditions exist. User code sets success. running is polled while root executes, and running = 0 written by the
      parent is its stop request, which in the end leaves the loop. At the exit, by return or however, running is set

      очеивдно прерывается по success==1"; "success && !running, с выходом выставляется running = 0. Просто running

      "L3 Thread это модель же а не реализация. Да, 0 это запрос остановки от родителя. Что значит "не выход из

    root reaches; on L2 that is the code working with these Messages; on L1 the code that will be generated, "В

Y. The mailbox's one synchronization as a Java monitor through the synchronized receiver (the target of S3 and S6).

    делается в Java, причем максимально упрощенно (ресивер synchronized в спеке описан), в старом проекте он был даже
    до какой-то степени реализован C:\Nyasha_Planet\lingvamyxa_old_worked_version". The coordinator's rule on it:
    the mailbox's one lock is a Java monitor in its simplest form, entered through the language's synchronized
    receiver on the mailbox object. [Superseded:] wait/notify is the monitor's own condition (one per monitor): notify on
    admission, wait in take.
    RULED 2026-09-15 (Mikhail, verbatim in S3): "тупейший вложенный synchronized по локу на чтение и запись как в

    посмотрит". The mailbox's synchronization is synchronized on the mailbox object for every read and write,
    reentrant as Java's, and nothing else: no wait, no notify, no condition. The empty-mailbox case is open (S3).
    Facts:
    - Spec 20.5.7 (origin/main, 15154-15232): "`synchronized` consumes an object/address expression and a statement
      Structure owned by the `synchronized` receiver. It is a structured synchronization receiver, not a raw
      lock/unlock pair in source syntax." "The core and standard distribution use it, or other low-level
      synchronization, only inside the Message mechanism." The first ANSI C projection lowers it to
      lm_synchronized_enter(lock_handle) ... lm_synchronized_leave(lock_handle). "The runtime hook must implement the
      selected monitor policy, including Java-style reentrant entry for the same thread when that profile is
      selected." The translator registers each active monitor as a cleanup entry, and return, break and continue
      emit the leave before leaving the region. The spec names no wait/notify: that part rests on Mikhail's "в
