L2 open points ledger
=====================

Why this file exists
--------------------
Lingvamyxa_handoff_notes.txt section 4: the spec has ~25 places that say
"remains open" or "has not yet chosen". They are not all to be answered in
advance - they stage. But an autonomous agent that meets one does not stop; it
invents an answer silently, and that is how architecture nobody accepted gets
built. So every unit of work must say which open points it touches and what it
does about each.

This file is that statement, kept per unit and mechanical. It is not a plan and
not a decision record: a point leaves this file only when the decision is
written into the spec, and then this file cites where.

Rules
-----
R1. Before a unit is committed, every open point it touches gets a row here.
R2. A row says exactly one of:
      DECIDED   - the spec already answers it; cite section.
      AVOIDED   - the unit is written so the point does not arise; say how,
                  and name what would make it arise.
      ASK       - the unit cannot proceed without an answer. Stop and ask the
                  user (L2 semantics) or cursor (L1 capability). Do not guess.
R3. No row may say "assumed", "for now" or "probably". If the honest answer is
    a guess, it is ASK.
R4. Writing a value into a field whose meaning is open is not a decision only
    while nothing reads it. The moment a read appears, the row becomes ASK.

Unit 1 - Lmx core and classification by registered address range
----------------------------------------------------------------
Files: lmx.h, lmx_range.lm1, lmx_selftest.lm1, run_lmx.ps1

ABI 14.2  Unit and interpretation of len
    AVOIDED. lmx_cell_init zeroes len as raw storage hygiene. The unit makes no
    claim that len counts children, elements or bytes. Nothing reads len.
    Arises the moment any code reads len, or any range registers a len rule.
    Then: ASK.

ABI 14.3  Empty representation
    AVOIDED, and for the same write. Zero is not claimed to denote empty, and
    the unit never distinguishes null data from zero len from an empty
    Structure. Arises together with 14.2.

ABI 14.8  Arrays: pool block allocation, growth, range registration
    Range registry table: AVOIDED for growth. lmx_ranges_init takes a fixed
    capacity and lmx_range_register refuses to grow past it, so no registry
    growth policy is invented. Registration itself is half-open [lo, hi)
    membership with a stride (the minimum 6.5 already states).

    Pool blocks: DECIDED separately as non-moving chunks with per-block
    registration (SPEC 2 / 6.5; ABI 4.1 / 7.2 / 14.8). Existing addresses
    stay unchanged when a new chunk is added. Registry capacity is not
    that pool-growth rule.

ABI 14.9  Allocation, arenas: physical subdivision into registered ranges
    AVOIDED. The table is one flat global list of ranges. SPEC 6.5 grants that
    range classification is globally available and that this shares no mutable
    cell between Messages, so a global table of BOUNDS is in scope. What is not
    settled is whether ranges are physically subdivided per arena. Arises the
    moment a Message arena exists and wants its own subdivision. Then the flat
    table is wrong and this becomes ASK.

ABI 14.1  Exact structural layout behind data for a non-leaf
    Not touched. Unit 1 classifies leaves and pool entries only; it builds no
    branch storage. Arises at the first non-leaf construction (SPEC 19.20).

L1 10.8   One C TU vs many; init-before-main
    AVOIDED. The selftest composes with predef:, so everything stays one
    translation unit. Arises when service pools must be initialised
    program-wide across modules. Then: ASK work_chat/grok (L1 capability).

L1 10.9   Field image \ vs . vs ->
    Not an open point, and not one this code may reopen. The user has ruled
    Valued member access out everywhere, L1 and L2 alike: if something is
    written with it, it gets fixed. The single admitted route is the explicit
    C door - c.value.field, which lowers to value.field and which l1trans
    already supports today - reserved for extravagant exceptions.

    So \ lowering unconditionally to -> is correct, and address forms here are
    permanent, not a stage waiting on an L1 capability. SPEC 11.2 (around line
    7133) says the same for L2 on its own terms: minimal field-follow is
    address-oriented, value\field is the direct form when the binding is a
    typed address. Taking a pool entry by value would discard the very address
    that classification reads, so the rule and the mechanism agree.

    History, kept because the mistake is instructive. This unit asked for the
    dot and was wrong twice over: it was writing C-shaped records where the
    spec keeps pool entries addressed, and it read an L1 capability question as
    an L2 semantics question. The request was withdrawn in
    work_chat\cursor\inbox\20260908-004726.txt. A grok_bot task to implement
    the dot in L1 was raised off the back of it and had no consumer at all -
    l1src itself never takes a member by value anywhere, and self-hosts to a
    gen1=gen2=gen3 fixed point without it. The user cancelled it directly.

SPEC 11.3.1  `@` of graph payload, declared parameter, hidden through
    DECIDED (docs 20260908-111800, corrected 20260908-115700). After range
    classification, `@x` of an own graph field is the stored payload, not
    `&Lmx.data` and not the C cache. `int` is the example, not the only
    kind. Declared and through parameters are ordinary C parameters: `@x`
    is `&x`, no graph-materialization, no writeback. L1 `p: @ value` remains
    C `&value` (L1_spec.txt) and matches L2 parameter `@`, not L2 own-field `@`.


Unit 2 - typed service pools
----------------------------
Files: lmx.h (LmxPool), lmx_pool.lm1, lmx_pool_selftest.lm1

SPEC 6.5  Array descriptor len
    DECIDED, and by the spec, not by this code. 6.5 says the descriptor has
    exactly two values, length and a pointer to element storage. So
    LmxArrayDesc.len is element count and may be read. This is a DIFFERENT
    field from the len in the Lmx header, which stays unread - SPEC 2 says so
    outright ("Array-descriptor len is a different field").

ABI 14.8  Arrays: pool block allocation, growth, range registration
    DECIDED. lmx_pool_open takes a chunk capacity; lmx_pool_take adds chunks
    when needed, each with its own registered range and the same kind/type.
    Existing addresses stay unchanged. The original fixed-capacity-only unit
    has been superseded; see the chunking correction below and SPEC 2 / 6.5,
    ABI 4.1 / 7.2 / 14.8. Chunk-sizing policy remains open.

ABI 14.4  ShortNameId format, and with it the encoding of sig
    AVOIDED. SPEC 2 says no current use of sig specifies a ready-made binary or
    module ABI. lmx_method_intern stores sig as an opaque unsigned, compares it
    to nothing and derives nothing from it. Arises at the first dispatch that
    reads sig - selecting a method by signature, or checking argument shape.
    Then: ASK.

ABI 14.9  Allocation and arenas
    AVOIDED, and worth restating now that memory is actually allocated. Pools
    call calloc directly because no Message exists yet. 14.9 fixes that every
    Message owns exactly one logical arena and that all dynamic mutable
    ordinary Lmx storage of that Message is allocated there. Arises at the first
    Message. Then pool blocks must come from its arena, and the flat global
    range table may need per-arena subdivision. Then: ASK.

ABI 14.10 / SPEC 21.13 p.4  Method result and failure carrier
    Not touched, deliberately. lmx_method_intern stores addr and this unit
    never calls it; invocation is SPEC 21.8 and a later unit. NOTES section 4
    names 21.13 p.4 the most frequently hit open point, and section 7 names the
    trap: L1 carries throw in two static globals, which is right for L1 and
    wrong for lm2, where each Message has its own arena and Messages may run
    concurrently (SPEC 21.7). The first call generated here reaches ASK.


Unit 3 - the interned character pool
------------------------------------
Files: lmx_chars.lm1, lmx_chars_selftest.lm1

ABI 14.7  Primitive copy and mutation policies
    Half DECIDED, half AVOIDED, and the split is 14.7's own. Its first sentence
    settles this unit outright: "Interned immutable leaves naturally share their
    primitive address." That is implemented and asserted - the same character is
    the same cell, always. What 14.7 leaves open is everything else: mutable
    cells, large numbers, byte buffers, opaque handles, foreign resources, each
    to be specified by physical range. None of those is offered here. Arises at
    the first mutable primitive cell, which 14.9 also requires to live in the
    owning Message's arena. Then: ASK.

SPEC 21.4  Primitives pass by semantic value
    DECIDED, and demonstrated rather than assumed. 21.4 says the callee gets an
    independent value "even when the source Lmx primitive is physically
    represented by a pointer into a registered address range such as
    all_chars_array", and that sharing an immutable atom is an implementation
    detail. The selftest carries 2's worked example for it: two fields holding
    one character hold one address, and reassigning one changes only that
    field's reference while the shared cell and the other field stay put.

    Not an open point, recorded because it is the claim most easily broken by a
    later optimisation. If a field write ever reaches the cell instead of the
    reference, this test fails.

    Limitation stated rather than hidden: immutability is enforced by
    construction - the block is filled once at init and no mutator exists - not
    by the C type. Saying it in the type belongs with the per-range physical
    class policy that 14.7 leaves open.


Unit 4 - WITHDRAWN. There is no name table.
-------------------------------------------
A reverse name index was built and then removed, because the model behind it
was wrong. Kept as a row rather than deleted, so the error is not made twice.

Field names are known at translation time. treeranch resolves to a fixed
index in the branch block; the runtime does pointer arithmetic and the
generated C never sees a name. SPEC 2 says it plainly - "A resolved reference
is used directly and needs no name lookup" - and the type of a void * comes
from the address range it falls in, never from a lookup. The plan this unit was
built for, "enumerate children, ask the index for each short name, compare",
was runtime work for a question already answered at translation time.

SPEC 2 does keep one name aid on the books: the reverse index
Lmx * -> ShortNameId, for runtime TEXTUAL lookup and for reconstructing a
current full path from sibling ordinals and node links. That is diagnostics and
genuinely dynamic access, not ordinary field resolution. If it returns, it
returns for those two things, and its absence until then is what keeps the
compiled path honest.

ABI 14.4 therefore blocks nothing here. It was recorded as blocking unit 6;
that entry was wrong for the same reason.

Constraint carried into unit 5 - occurrence ordinals are naming, not indexing
-----------------------------------------------------------------------------
Recorded because getting it wrong would have shaped unit 4's id and could not
have been undone quietly.

Two brackets that look alike are grammatically different (SPEC 12.3, and 21
states it outright: the bracket in target\[occurrence]field is not the postfix
operator).

    field\[2]field    the third occurrence among children whose SHORT NAME is
                      field. The leading bracket is part of the NAME. Bare
                      field is shorthand for [0]field (SPEC 2).

    field\field[2]    element 2 of the array held by [0]field. The trailing
                      bracket is postfix indexing of the VALUE (SPEC 12.3),
                      which explicitly does not select the nth repeated field.

Consequence for unit 4, which it already satisfies: the ordinal is POSITIONAL.
It comes from the order children are enumerated in, and is not stored. So one
ShortNameId serves every occurrence of a name - SPEC 2 says the index stores
short-name identity, not full paths. Encoding the ordinal into the id would
give three fields named branch three different ids, and [2]branch would stop
being a name and become an address.

Consequence for unit 5, as corrected by the user. In LMX code the field is
simply branch, and priority belongs to the EARLIER occurrence. The [N] form is
a translator-side extension of the name, used to address later duplicates; it
is not how ordinary source spells a field.

So the common path is enumerate children in order, ask the index for each
child's short name, compare, and STOP AT THE FIRST MATCH. Counting to n is only
for the translator's own disambiguated references. The distinction matters for
cost: the ordinary lookup exits early, and only a disambiguated one pays for
the whole branch.

Recorded as it stands. The user notes the spelling is confusing but settled,
and is not to be reopened. That needs ordered
child enumeration, which is ABI 14.1 - the layout behind data for a non-leaf.
Unit 5 therefore opens with an ASK, not with code.

Forward direction of 14.4 IS reached, and the hope that it might not be was
wrong. Asked whether paths could be resolved statically; the answer is that a
static path needs a statically known root occurrence, and only const gives one -
or the 21.11 analysis, which itself rests on an occurrence being replaceable
only by an explicit structural operation with its defining receiver (21.12
cached child positions; NOTES section 3.3). A path not rooted in const resolves
at runtime, by enumeration and short-name comparison.

But the blocking half is narrower than feared. 14.4 lists five open things:

    NEEDED    deterministic generation, and inter-module agreement. In source
              text like tree\[2]branch the name branch is a literal known at
              translation time, so the translator can emit its id as a
              CONSTANT and the runtime only compares.

    NOT YET   conversion from an arbitrary runtime textual path. That is for
              genuinely dynamic lookup, where the name arrives as a string at
              runtime. SPEC 2 allows it; nothing here needs it.

    NOT YET   bit width, byte encoding, reserved ids, collision handling -
              already recorded as untouched under unit 4.

Superseded. 14.1 is now RESOLVED - a non-leaf's data addresses one contiguous
block of Lmx children, sealed at construction - and 14.4 blocks nothing, because
there is no sought id: the translator resolves a field to a block index and the
runtime never compares a name. See the withdrawn unit 4 row.


Unit 5 - reference-value passing
--------------------------------
Files: lmx_ref.lm1, lmx_ref_selftest.lm1

SPEC 21.4  Structure and Array arguments are reference values
    DECIDED, and pinned rather than assumed. 21.4 fixes both halves: the
    reference is copied into the callee's activation and the referent is not
    cloned; rebinding the callee's local reference changes only that local
    reference; a write through the reference mutates the shared referent and is
    visible through every reference and path to it.

    This unit has no open points. It exists because both halves are exactly
    what a later change would break quietly - by cloning on the way in, or by
    passing a reference to the reference so a callee's rebinding escapes. Either
    would still pass every other test in this tree. The helpers therefore do the
    tempting wrong thing locally, rebind and reassign, so the selftest can show
    it does not get out.

    The array case covers the distinction 21.4 draws for Array operations:
    replacing a descriptor's own storage mutates the referent and every holder
    sees it, while assigning a local reference to another Array does not rebind
    the caller. Both are asserted against the same descriptor.

    Not covered, and not by omission: 21.4's last paragraph forbids passing a
    raw Structure or Array pointer as is between Messages, requiring a clone,
    serialization or ownership-transfer boundary. No Message exists yet. Arises
    with the first one, alongside 14.9.


Audit: what may change in a Structure, and what it gives 14.1
--------------------------------------------------------------
Asked to check whether the rule had drifted. It has not, but the first reading
of this audit drew the wrong consequence and is corrected here.

The rule, as the user states it and as the spec bears out: THE NUMBER OF
CHILDREN DOES NOT CHANGE. What may change is the REFERENCE a field holds, and
only where that field is not const - 9.1.1's const fixes the binding, the cell
or reference, and does not reach through it. Unit 3 already carries the worked
example: assigning a primitive field changes its reference and leaves the
shared cell alone.

Every site that mentions appending is consistent with that once merge is read
correctly:

  19.20   construction and merge are distinct operations; merge CREATES A FRESH
          ROOT and copies operand children into it. It does not grow an
          existing structure.
  ~11089  merge appends copied children in operand/body order - into that fresh
          root
  ~11728  the result appends body children, rewrites all copied node pointers
          and re-registers - again the result being built
  21.11   an explicit operation may append, replace, remove or move occurrences
          only when its receiver defines that mutation, and it never reorders
  ~6063   an ordinary assignment neither updates node\[0]i nor appends a child
  ~7684   an explicit append never moves the existing first child from [0]

Corroboration I should have noticed before extrapolating: 14.1's own
requirement list is "stable node addresses, ordered children, deep containment
copying and range classification". GROWTH IS NOT IN IT. Had branches been able
to grow in place, 14.1 would have had to say so.

What this GIVES 14.1, rather than costs it. A contiguous block of Lmx sealed at
construction satisfies every requirement 14.1 states: addresses are stable
because nothing relocates, order is the index, containment copying is a block
copy plus a node rewrite, and the block registers as one range. The candidate
14.1 lists first is therefore viable, and the segmentation the earlier version
of this entry argued for is not needed.

Not a decision - 14.1 remains the user's. Recorded so the contiguous candidate
is not passed over for a cost it does not have.

Method note to self. Twice now a correct local reading produced a wrong
consequence, because I extrapolated from the passage instead of checking it
against the requirement list that governs it. The list is the cheaper check and
comes first.


Correction: N typed service arrays means one per TYPE, not per category
-----------------------------------------------------------------------
Units 1 to 3 registered a range under a KIND - primitive, method, array - which
is the column SPEC 2's table gives for how to read an entry. That is only half
of it. 2 says the implementation has N TYPED service arrays, and 6.5 spells one
of them out: "For every used Array type T the implementation provides a typed
service pool, schematically all_array_of_T."

So a range now carries a concrete type as well, and the address gives that type
outright. A descriptor from all_array_of_int and one from all_array_of_char are
both array descriptors, read alike, and are told apart by which range they land
in - with nothing stored in either to say so. The pool selftest asserts exactly
that pair.

Kind and type are both kept because they answer different questions: kind is how
to read the entry, type is which typed service array it came from.

Not an open point - a misreading, corrected.

Carried into the const rule
---------------------------
The user's rule, recorded before the unit that will need it: if a reference is
const, everything is done WITHOUT touching the node the void * lives in. Not
"the resolution may be cached" - the generated C does not load node->data at
all, because the target is known at translation time. That is 21.8's direct
invocation for callables, and the same for ordinary const fields.

This is the sharp end of NOTES section 3.1, which insists devirtualisation and
checkpoint elision are separate optimisations with separate preconditions. const
gives the first outright. It does not give the second: whether the caller has
dirty own fields across the call is a property of the CALLER, and const on the
callee says nothing about it.


Correction: a typed service array grows, and grows by chunking
---------------------------------------------------------------
Unit 2 refused to grow and recorded that as AVOIDED. That was wrong: a
non-const variable LIVES in the big array of its C type, so the array has to
grow. Corrected, and the growth mechanism is forced rather than chosen.

DECIDED, confirmed by the user on 2026-09-08 and reflected in SPEC 2 / 19.29
and ABI 4.1 / 7.2 / 14.8–14.9: live nodes and service-pool entries never relocate.
The older permission to move after patching all references was a documentation
error, not a supported alternative. Growth needs no reverse-reference inventory
or pointer-patching pass. Allocation failure may terminate the owning Message
and release its arena before a fresh Message is started.

Growth therefore adds a CHUNK, and each chunk registers as one more range with
the same kind and type. A typed service array is a SET of registered ranges, not
one range. Every address handed out before a growth stays valid and still
classifies, which the pool selftest asserts directly: after growth the earlier
entries keep their type and their contents.

Two disciplines share this machinery, and the contrast is the point:

    interned immutable atoms   all_chars_array has its 256 cells from init,
                               addressed by value, never grows (14.7 settled)
    mutable variable cells     handed out one at a time, the array grows to fit

What makes an entry a char is the range it sits in, not which discipline put it
there.

ABI 14.8  Pool block allocation, growth, range registration
    DECIDED in SPEC 2 / 6.5 and ABI 4.1 / 7.2 / 14.8:
    growth is chunking with per-chunk range registration. Still
    open: how big a chunk should be, and whether chunk size should vary. The
    code takes a chunk capacity at open and keeps it, which is a placeholder,
    not an answer.

ABI 14.9  Allocation and arenas
    Unchanged and still ASK at the first Message. Chunks come from calloc
    because no Message exists yet; 14.9 requires them to come from the owning
    Message's one arena.

Cost to watch, recorded now rather than discovered later. Classification scans
ranges linearly, and chunking multiplies the number of ranges. That is fine
while ranges are few and it is on the hot path, so it will need a real lookup
before it is fine at scale. Not a correctness problem, and not solved by
guessing at this stage.


Standing contract: the two optimisations, kept verbatim
--------------------------------------------------------
Not open points. This is the performance model of 21 and the part most easily
lost by a later change that looks locally reasonable. Recorded so that a unit
which generates calls can be checked against it line by line.

A. const, and the internal consequence of immutable

  const fixes the BINDING - the cell, the reference - and is shallow; it does
  not reach through the reference. immutable fixes the VALUE and is deep. They
  are two orthogonal axes, neither a stronger form of the other (9.1.1, 9.1.2).

  If a reference is const, the generated C does not touch the node the void *
  lives in at all: the target is known at translation time. For callables that
  is 21.8's direct invocation - a direct C symbol call, with no walk through the
  descriptor via the node.

  21.5 adds the part that survives suspension: const qualification of an own
  field's backing, INCLUDING a RuntimeImmutable that succeeds while this
  activation is suspended in a call, stays binding on the cache. Neither a later
  own-local assignment nor a checkpoint may bypass it.

  What const does NOT give: checkpoint elision. Whether the CALLER has dirty own
  fields across a call is a property of the caller, and const on the callee says
  nothing about it. NOTES 3.1 insists these are two optimisations with separate
  preconditions and that they fail independently.

B. Own fields as C working locals, with dirty-only checkpoints

  Entry.     Load only OwnUsed(M) - the own fields this body actually reads or
             writes unqualified, or uses to supply an outgoing callee's dynamic
             value - into typed automatic C locals. Each local records and roots
             the exact Lmx occurrence it came from. Other node fields are
             neither loaded nor stored.

             Explicit node\field, reference\field and array[index] are NOT
             folded into this cache. They read or mutate their selected location
             on every execution. Mentioning a field through an explicit path
             does not make it a cached own local.

  Body.      Work in the locals.

  Dirty.     A local becomes dirty only when this activation actually executes
             an assignment or rebind to it since its last successful checkpoint.
             Not inferred by comparing against the graph. Not set because a
             branch might have assigned. Not set by capability: making writable
             access available is not a write, and an outlined helper must report
             the write it actually executed.

  Publish.   Immediately before every outbound call, before every external,
             re-entrant or publishing boundary, and before every exit -
             fallthrough, return, throw, failing assert, stop, cancellation, and
             before yield suspension - write each DIRTY local to its node field,
             in forward source order of the backing fields. A successful store
             clears only its own dirty state. Clean values must not be
             re-published. Declared arguments and dynamic inputs are never
             published automatically.

  Return.    NO RELOAD. The caller continues with its C snapshot; only explicit
             graph paths see the current graph.

  Why no reload, and why not flush-all. 21.6 gives the case outright: outer
  enters with x = 1 clean, calls inner, inner explicitly writes the graph field
  x = 2, outer returns without assigning its local. Flush-all would overwrite 2
  with a stale 1. Dirty-only writes nothing. If outer then executes x = 3, x is
  dirty and the next checkpoint publishes 3.

  NOTES 1.1 derives this from the ontology rather than postulating it: all
  Structure, one sequential thread per Message, a small C stack, and activation
  state living in callable->node rather than in a frame slot. A bare name LOOKS
  like an Algol-60 local and LIVES as an instance field; spill/no-reload is the
  seam between those two natures. Thread safety comes from the same single
  sequential thread - a suspended caller's snapshot cannot be raced, and other
  Messages have disjoint arenas.

C. The related case: values from the enclosing scope

  DynRequired(M) is a separate set from OwnUsed(M). Declared arguments and
  dynamic imported values are activation-local inputs with NO write-back target.
  Assigning or rebinding one changes only this activation and the value it may
  pass further down; it never writes back to the caller and never automatically
  writes node\x. To publish one as method state the program must assign an own
  field or use an explicit graph path.

  A forwarded dynamic name never becomes an own graph field merely by being
  forwarded.


Unit 6 - branch storage
-----------------------
Files: lmx_branch.lm1, lmx_branch_selftest.lm1

ABI 14.1  Exact structural layout behind data
    RESOLVED, and implemented as resolved. A non-leaf's data addresses one
    contiguous block of Lmx children, allocated at construction with exactly the
    count construction produces, and sealed. There is deliberately NO append in
    this unit; growing a Structure is not a thing that happens, and merge builds
    a fresh root of its own final size (19.20).

    The selftest asserts each of the four requirements 14.1 states, rather than
    assuming them: stable addresses (a second lookup returns the same cell),
    ordered children (the block index is the order, and [0] is entry zero), deep
    containment copying (block copy, then each copied child's node rewritten to
    the new parent), and range classification (an interior child classifies like
    the first, because the block is one range).

ABI 14.2  Unit and interpretation of len
    SETTLED FOR THIS RANGE by 14.1's resolution: a branch node's len is its
    child count. This unit is the first place the tree reads an Lmx header's
    len, and rule R4 is what makes that legitimate - a write into a field of
    open meaning stays a non-decision only while nothing reads it, and the read
    became legal exactly when the decision landed.

    Still open for every other physical range. Nothing here reads a leaf's len.

ABI 14.6  Explicit graph references during merge
    AVOIDED, deliberately and visibly. A copied child's payload reference is
    carried across AS a reference and is not followed. 14.6 has not chosen
    whether a reference into the copied subtree is remapped to its copy or keeps
    its original target, so nothing here remaps one, and the selftest asserts
    the copied payload is the same reference the source holds. Arises at the
    first real merge. Then: ASK.

ABI 14.3  Empty representation
    Still open, and now visibly so. lmx_branch_open refuses a zero child count
    rather than deciding what an empty branch looks like. Arises when an empty
    Structure must be told from a null payload. Then: ASK.


Unit 7 - own fields as C working locals, with dirty-only checkpoints
---------------------------------------------------------------------
Files: lmx_own.h, lmx_own.lm1, lmx_own_selftest.lm1

SPEC 21.5, 21.6  DECIDED, and pinned before anything generates it.
    This is the machinery a generated method body carries, written by hand so
    the contract is testable now. It has no open points; it is here because
    both failure modes are SILENT. A flush-all checkpoint and an automatic
    reload each keep every other test in this tree green while destroying the
    semantics, so they get a test that fails on them specifically.

    The selftest carries 21.6's worked case verbatim rather than paraphrasing
    it: outer enters with the field at 1 and its local clean, calls inner,
    inner writes the graph field to 2 through an explicit path, outer returns
    without assigning its local. A flush-all implementation overwrites 2 with
    a stale 1. Asserted directly.

    Also asserted, each ruling out a plausible shortcut:
      a freshly loaded local is clean
      a clean local publishes nothing however many checkpoints it passes
      reading the local after a call returns the entry snapshot, not the graph
      an executed write sets dirty, and only an executed write does
      a dirty local does not reach the graph until a checkpoint
      a successful store clears dirty
      the local is aimed at the exact occurrence it was loaded from
      a sibling field, not being OwnUsed, is neither loaded nor stored

    What is deliberately absent. No helper turns an explicit path into a cached
    local - 21.5 says node\field, reference\field and array[index] read or
    mutate their location on every execution and are not folded into the cache.
    Declared arguments and dynamic inputs have no write-back target and do not
    appear at all.

    Not covered here, and reached later: the publication FAILURE policy. 21.6
    leaves open whether stores are infallible, all-or-nothing after
    prevalidation, or prefix-committing on failure. This unit's checkpoint
    cannot fail on a well-formed local, so it does not choose. Arises when a
    store can fail. Then: ASK.

    Also not covered: 21.5's active-backing conflict policy, for when nested
    code structurally moves, detaches or replaces the occurrence a local was
    loaded from. 21.13 has not chosen between update-detached, checked
    re-resolution and rejection, and explicitly forbids turning the ambiguity
    into a silent [0] lookup. Nothing here moves an occurrence. Then: ASK.

Unit 9 - L2 two-int methods in one unit
---------------------------------------
Files: l2trans.lm1, tests/add.lm2, tests/entry_sum.lm2,
tests/entry_add_ret.lm2, tests/entry_plus.lm2,
tests/entry_swap_formals.lm2, tests/unit_*.lm2,
negatives unknown/arity/unresolved/trailer/dup/loop/recursion

SPEC 21.8 / ABI 6.6  method record {addr, sig}, node first, typed invoke
    DECIDED for throws-none methods in this slice. C entry is
    `T l2_m{i}(Lmx *node, ...)` with backend symbols mangled by
    unit index; intern and find_method keep source names, so a
    source method named malloc does not collide with c.malloc.
    Two-pass: collect declarations+contracts, then validate
    bodies. Intern table is one per translated unit (not reset per
    method). Full contract = L2_SIG_V0 + exact ordered source
    formal-name bytes and types; method name is not interned.
    Matching contracts share an id. rec.sig is that interned id.
    Runtime does not memcmp. Child index is the callable path.
    Closed-unit devirtualization: no graph mutations after
    construction; actuals materialized left-to-right into temps
    before each call (not C argument order). Recursion and
    cycles are an implementation limit (`unsupported recursion`), not
    a language ban. Max 8 methods (9th is `too many methods`).
    Generated `lmx_ranges_init` is 1+N, or 2+N when OwnUsed char
    fields need the interned all_chars pool.
    Source `node` is reserved. Formals emit as `l2_p{i}_{j}`; intern
    keeps source names. Long names / too-deep if are diagnosed before
    dest is opened. Publication: write tmp; if dest exists rename
    dest to dest.bak, or dest.bak.N if dest.bak already exists, so a
    foreign regular bak is kept; rename tmp to dest; on fail restore
    bak; on restore failure report the backup path and do not claim
    dest was restored. Not atomic. No recursive FS. Files not created
    by this run are not deleted.
    Variable arity 1–4; char, int, size_t, or const @(char) formals;
    int or size_t result. Pure &&/|| (no calls) stay one L1 C
    expression with C precedence. Expressions that contain calls
    use guarded if/temps: || splits then &&; parenthesized
    STRUCTURE is a subexpression. The value of &&/|| is int 0 or 1
    (`(x) != 0`), not a raw operand, matching C even when a call
    is added to a previously pure expression. Non-logical size_t
    calls keep a size_t temp; they are not copied into int.
    Actuals are prepared left-to-right once; checkpoint runs after
    those actuals and immediately before the executed call. A
    skipped &&/|| RHS does not prep nested actuals or checkpoints.
    Partial ports: parser_text_predicates.lm2,
    parser_text_line_break.lm2 (lm_p0_line_break_width_at),
    parser_text_starts_python.lm2 (lm_p0_starts_python_string).
    They do not replace l1src. const @(char) is a declared typed
    C-address parameter (SPEC 11.3.1), not an LMX Array descriptor.

SPEC 21.5 / 21.6  own char field of callable->node
    DECIDED from the spec, not from C. `char: quote` in a method
    body is an OwnUsed graph-backed field of the containing
    Structure (`callable->node`), sibling of the METHOD leaves.
    Builder materializes child i with data = all_chars cell.
    Unqualified `quote` is the typed char C cache loaded at entry
    from that exact occurrence. Assignment sets dirty even when the
    value equals the cache. Checkpoint before outbound L2 calls and
    every return publishes only dirty caches by rebinding
    field->data to lmx_char_cell(cache); it does not mutate the
    shared char payload (SPEC 2 / 21.4). Clean never republishes
    (21.6 inner explicit write). No reload after a call. Explicit
    `node\quote` (P0 frame head `node\quote`) writes the graph
    child and does not touch the caller's cache. DynRequired stays
    empty in this slice. No per-activation graph objects. Throws /
    Message / yield / recursion remain implementation limits.

    DynRequired remains empty (no through names in this slice).
    OwnUsed is non-empty for methods that declare `char: name`.
    Not Throws/Message/through. prototype: is emitted so forward
    calls do not depend on C declaration order.

SPEC 11.3.1  declared typed C-address parameter
    DECIDED for this port: `const: @(char source)` is the C

SPEC 21.13.5  record layout

SPEC 21.5–21.6  OwnUsed/DynRequired

ABI 14.9  Message arena
    AVOIDED. calloc/malloc like units 1–7. ASK at first Message.

SPEC 1.7  main
