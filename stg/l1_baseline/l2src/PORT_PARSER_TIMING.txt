PORT_PARSER_TIMING -- where run_port_parser.ps1's ~30 minutes go (survey, 2026-09-14, lingvamyxa-0c)

How the gate reads (read this before proposing a cut)
  run_port_parser is DIFFERENTIAL. For each of the 12 stages it builds a Port executable per driver
  (tests/p0_tree_contract/p0_meta_dump.c and l2src/p0_dump_driver.c). It runs the Ref and the Port executable of
  each driver on the same 36 tests/p0_tree_contract/*.lmx inputs, and it requires the same exit code
  and the same stdout text. It never reads the *.meta.txt, *.tree.txt or *.err.txt expected texts
  in that directory. Those belong to run_p0_tree_contract.ps1 and run_p0_meta.ps1. A one-byte edit
  in an expected text therefore cannot turn this gate red. A one-byte edit in a .lmx input changes Ref
  and Port alike and stays green too. The falsifier for a cut is a one-byte change in a ported L2
  unit that makes the Port's output differ from the Ref's.

Dominant cost
  The goldens account for 95 % of the run. Within them, each process launch takes 1.017 s and the
  byte compare 0.001 s. The launch time is flat across all 12 stages, Ref and Port, both drivers,
  every input, while CPU stayed at 4 %. So the second is a wait, not work.
  The wait is in Start-Process -Wait itself. One benchmark ran after the timed run: the Ref meta executable
  on the same 36 inputs, each launch form in turn, at 3 % load. Its script is in 0c's scratchpad,
  bench_process_start.ps1.
    Start-Process -NoNewWindow -Wait -RedirectStandardOutput (today)   1.019 s per process
    Start-Process -WindowStyle Hidden -Wait (no redirect)             1.017 s per process
    cmd /c "exe input > file", exit from $LASTEXITCODE                0.029 s per process
    System.Diagnostics.Process, stdout ReadToEnd                       0.023 s per process
    Start-Process -PassThru -Redirect, then $p.WaitForExit()           0.010 s per process
    one cmd running all 36 (the executable's own run time)             0.011 s per process
  Evidence equality against today's form, over the 36 inputs (6 of which exit 1: C_nested_short,
  F_star_fence, invalid_eq_unclosed, invalid_triple_unclosed, return_colon_comment_trailer,
  return_colon_empty_trailer):
    cmd /c: stdout bytes identical 36/36, exit codes identical 36/36.
    .NET Process: stdout text identical 36/36, exit codes identical 36/36.
    Start-Process -PassThru + WaitForExit(): bytes identical, but ExitCode was EMPTY on all 36. A
      compare of empty against empty always passes, so the exit-code check would vanish silently.
      Reading $p.Handle before the wait restores it: 0.013 s per process, codes and bytes identical 36/36.
  So 1728 x ~1.0 s = ~29 minutes is PowerShell 5.1's -Wait, not the executables, gcc or the load.

Proposal (no code before the lead's (c) merge and your ruling)
  One cut, in Test-GoldensBetween only: launch each Ref and Port process with
    cmd /c "`"$exe`" `"$input`" > `"$outFile`""   and copy $LASTEXITCODE on the next line,
  instead of Start-Process -NoNewWindow -Wait -PassThru -RedirectStandardOutput. Everything else stays:
  the same 36 inputs x 2 drivers x 12 stages, the same per-input .ref.out/.port.out files, the same
  exit-code compare and text compare, and the same EXIT MISMATCH / OUTPUT MISMATCH lines and throw.
  No cache, no skipped comparison, no parallelism.
  cmd /c is chosen over the faster Start-Process + $p.Handle form because it is the house pattern
  (l1-runner-pitfalls item 1) and has no hidden condition. The Handle form loses the exit code if a
  later edit drops the one `$null = $p.Handle` line, and nothing would turn red.
  Expected: goldens 1758 s -> about 1728 x 0.03 = 50 s, so the run drops from ~1845 s to ~140 s
  (setup 10 + non-golden stage steps 76 + goldens ~50). That is a prediction and is re-measured on the change.

  Falsifiers, each run on the runner as it is today (red first) and again on the change:
  1. A one-byte change in a ported unit that makes the Port's output differ: in a scratch copy,
     l2src/parser_dump_port.lm2 line 65 p0_dump_append_field_count_line " fields=" -> " fieldz=".
     That function is redirected from stage c_parser_dump_slice1 on, and only the dump driver reaches
     it. Expected red: "dump OUTPUT MISMATCH <first input>" and
     "stage c_parser_dump_slice1: N mismatches across 36 goldens x 2 drivers", with the same lines and N
     before and after the cut. Stages a, b and c_parser_alloc stay green. Not measured yet.
  2. The exit-code compare still bites: in a scratch copy of the changed runner, add 1 to the
     captured Port exit code. It must go red at stage a_parser_text with
     "meta EXIT MISMATCH A_compact_f_paren: ref=0 port=1", the first input by name. Today's
     runner with the same mutation must give the same line.
  3. A one-byte change in l2src/parser_stack_stream_port.lm2: the runner keeps no cache of stage
     units (every stage re-runs l2trans, l1trans, dedup and both links on its units each run) and the
     cut adds none. So the change rebuilds d_lifecycle, the only stage whose Units list it, and nothing
     else is downstream of it. Shown by d_lifecycle's parser_stack_stream_port.lm1/.c and both Port
     executables carrying mtimes after the edit, and by the stage's own result for the edited byte.

  Not proposed now, recorded for later: running Ref once per run (its executables do not change across
  stages) would save about 12 x 72 x 0.03 = 26 s after the cut. That is too little to argue identity for.

Rejected alternatives
  - Content-hash cache for translate/compile across stages: everything outside the goldens is 86 s
    (4.7 %). At best a cache saves most of the 27.6 s l2trans and 27 s compile+link, and it adds a
    cache whose key must cover the pinned translators, flags and every header. Not worth it against
    the golden cost.
  - Running the two drivers' comparisons in parallel: this halves wall time only while the 1 s wait
    remains, and it doubles the machine's process churn during shared gate windows. It can be layered
    after the launch cut if still needed.
  - Skipping Ref re-runs: the Ref executables do not change across stages, so their 72 outputs per
    stage are the same bytes every time (876.6 s of Ref launches). Computing them once per run would
    cut half the launches without skipping any comparison: every Port output is still compared.
    The cost is an argument about identity. Ref is built once, outside the loop, so it is a single
    binary. Recorded here as a candidate, not proposed first.

Existing cache hazard found in passing (not a timing cut)
  run_port_parser skips a runtime header or object when the file merely exists
  (`if (Test-Path $objOut) { continue }`). In a warm build\port_parser a changed lmx_*.lm1 does not
  rebuild. This timing run was cold, so the numbers are not affected.
