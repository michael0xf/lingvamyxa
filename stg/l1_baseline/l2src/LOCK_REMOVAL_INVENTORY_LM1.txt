Lock removal inventory -- l2src/lmx_message.lm1
==================================================
Mikhail's order, 2026-09-15 (relayed by 6f): stop all other work, remove
LmxMsgExec's shared lock ("there must be no shared locks; the mail queue
has only its own internal collection lock"). This file is the input: every
`lmx_msg_exec_lock(` and every `*_locked(` call site in lmx_message.lm1,
one line per site -- file:line, enclosing function, the state read and
written under the lock, the lane it runs on today, and the target owner of
that state by the rule (a Message's own fields on its own lane; a parent's
scheduler state as the parent's Structure data; cross-lane only through a
mailbox with its own collection lock), or "silent" where none of the three
fits. lmx_message.lm2 mirrors lmx_message.lm1 line for line; the same grep
count (65) holds on both -- verified below, not assumed.

Read the code before naming state/lane; a site I could not classify from
the code in front of me is marked silent, not guessed. Four "_locked("
sites (lmx_msg_exec_route_locked, _wake_addr_locked, _ui_request_locked,
_take_ui_locked) are C-level externs with no lm1/lm2 body in this file or
anywhere in this worktree (grepped, no match) -- their own internal state
is silent by necessity; only the calling context's lane is visible.

Lanes seen so far: "R0/bootstrap" (the runtime-owner thread outside any
turn, lmx_msg_host_is_owner), "<X>'s own turn" (lmx_msg_exec_holding_turn
true for that Message), "any thread" (no turn/owner check in the function
itself -- callable from any lane, exec lock is the only guard), "unknown,
see caller <name>" (authority is enforced by a caller I have not traced).

Scope widened, 2026-09-15 (relayed by ba, quoting Mikhail verbatim, spec
07ad3679 / 19.28.R2.2 clarification): "блокировка только локальная у
коллекции сообщений может быть, больше блокировок не требуется даже
локальных -- их в проекте не должно быть больше вообще" (the only lock
allowed is the message collection's own local lock; no other lock, not even
a local one, anywhere in the project). This file now also lists every
`lmx_msg_host_lock(`/`_unlock(` and `lmx_msg_mail_lock(`/`_unlock(` call
site in lmx_message.lm1 (lm2 mirrors these too, verified below), each
tagged `class:` -- "allowed" for a mail_lock/mail_unlock pair that guards
only a `\inbox`/`\outbox` push or pop on the Message collection itself (the
one lock the rule permits), "to go" for everything else, including every
exec_lock/`_locked(` entry above (none of those is the mail collection's
own lock) and host_lock (a broader post-vs-shutdown ordering lock, not the
collection lock).

Format: lm1:LINE | function | reads: ... | writes: ... | lane: ... | owner: ...
(exec-lock-family entries also carry a trailing `| class: ...` tag, added
2026-09-15 for the widened scope; host_lock/mail_lock entries below carry
the same tag from the start.)
