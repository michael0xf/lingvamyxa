R0P_GATE_IMPACT: the gate set (l2src/run_gates.ps1) against stage R0P, the root's parent stub
Measured by 0c at integration 7b3a8668, read only: nothing was built or run, 2026-09-15.

R0P gives R0 a parent. The stub is a host/system construct outside the Message model, not a Message any
create_prepare builds; what changes for the gates is that R0 stops being a Message with nothing to poll.
The ruling (the plan, 2026-09-15): R0 is folded into the same poll, poll_mark(R0) with the stub as its
parent, the stub answering as a live parent while the process lives; the stub's own poll of R0 runs in the
host loop at a host setting and, on expiry, leaves the OS process. The attribution there matters and is
kept: "R0 polls it as any child polls its parent" is the coordinator's reading of the spec's liveness
paragraph, not Mikhail's words; his verbatim sentences are the mutual poll and the stub itself.

== The mechanism, read at 7b3a8668 ==

lmx_msg_poll_mark (lmx_message.lm1:2092-2105) is the whole of it. Its guard at 2095 is
    if: m\parent != 0U && (m\state = RUNNING || (m\state = INACTIVE && m\committed != 0))
so a Message with no parent is skipped entirely. Inside, it calls lmx_msg_parent_gone (2074) and only when
that answers non-zero does it set m\closing, call exec_ready, write the address into out[] if there is
room, and increment n (2099-2102). It returns n at 2105.

  **n counts closing-requested Messages, not visited ones.** This is the single most important fact for
  this list: folding R0 into the poll does not add to n while the stub answers as a live parent. n grows by
  one exactly when the stub is gone or expired -- which is the new behaviour the stage introduces, not a
  side effect on existing counts.

lmx_msg_poll_kids (2107-2117) walks first_child/next_sibling recursively, poll_mark per child.
lmx_msg_poll (2119-2133): for who != 0U it poll_marks that one Message (2126); for the sweep (who = 0U) it
calls poll_kids(rt\root) at 2130 and never poll_mark(rt\root). So R0 is absent from the general poll today
-- b5's open point in the pre-read, confirmed here in the code rather than taken over.
lmx_msg_live_query (2430/2444 per the pre-read; lmx_message.h:244 exports lmx_msg_poll) refuses a
parentless Message, which is what liveness_33:372 pins.

  cannot red any of them. If a future test pins an exact count on a SWEEP, that pin is the one to revisit.

== The other numeric channel: live_seq, and why it does not spread ==

live_seq is a PER-MESSAGE cell (lmx_message.h:168, unsigned live_seq), incremented on the queried Message
at lmx_message.lm1:2439 and 2453 with a wrap guard at 2436/2450 (4294967295U). R0 gaining a parent gives R0
its own live_seq traffic; it does not touch any other Message's sequence, so no existing count shifts.
  The one test that names it: lmx_message_selftest.lm1:760-762, "live_seq wrap", which drives the test seam
  lmx_msg_live_test_set_seq (the setter writes m\live_seq: v at 2637) on its own Message to reach the wrap.
  Unaffected: it sets the value it then checks.
Grepped and found empty, so it is recorded as absent rather than unexamined: no runner pins a literal poll
or liveness count ("liveness checks=\d+ failures=0" at run_msg_liveness.ps1:80 captures the number, it does
not fix it), and no test compares a poll/visited/swept/seq count against a literal.
