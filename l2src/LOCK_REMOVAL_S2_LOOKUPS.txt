--- Method and two corrections made before writing this table

Read at b4e1296d (`git checkout -b sonnet/s2-lookups b4e1296d`, S3 landed,
the old lookup paths named by the design's S2 section still present,
matching the ticket's framing). Per-function counts were built by
bucketing every raw match of the four falsifier-grep names to its
enclosing function/subroutine (exec.c: nearest preceding column-0
`name(...) {` opener; lm1: nearest preceding `fn:`/`sub:` line), then
each multi-site function's body was read directly to confirm the bucket,
not trusted from the automated pass alone. Two real errors surfaced and
were fixed before this table was written, both caught by reading the
flagged function's actual body rather than asserting the automated count:

1. exec.c's raw grep initially counted a COMMENT as a call site: line
   1170, "* msg_at_addr() walks a dangling tree..." inside
   lmx_msg_endp_try_retire's own comment block. This is the exact
   mistake LOCK_REMOVAL_SPINE.txt itself records making and fixing at
   c067bed9 ("a comment in lmx_msg_endp_try_retire naming msg_at_addr,
   as a call site; endp_try_retire makes no lookup") -- re-verified here
   independently at b4e1296d and confirmed still the only comment-line
   false positive in exec.c (grep for `#`-led matches in lm1/lm2 found
   none). endp_try_retire is correctly absent from this table.
2. A multi-line C signature, `static int transfer_graph_locked_api(...)`
   opening at exec.c:3044 (four parameter lines, no single line ending
   in `) {`), was invisible to a single-line function-opener regex, so
   its two lookups (self_or_find at 3058, 3059) were first misattributed
   to the preceding function, lmx_msg_transfer_adopted (making it read
   4 instead of 2). Read directly: lmx_msg_transfer_adopted (exec.c:3008)
   has exactly 2 (from, to), matching LOCK_REMOVAL_SPINE.txt's own "(2)"
   exactly and unchanged since c067bed9 (byte-identical body, diffed
   against 7200294b). transfer_graph_locked_api's own 2 are its own row
   below, matching SPINE's separate mention of it by name ("deliver
   form (2)"); its two public callers, lmx_msg_transfer_graph and
   lmx_msg_deliver_graph (exec.c:3128, 3133), are thin wrappers with no
   lookup of their own.
   A parallel miss in lm1: two SPINE-named C1 functions,
   lmx_msg_request_children_close and lmx_msg_exec_ready, are written
   as `sub:` blocks (no return value), not `fn:` blocks; a boundary
   tracker keyed on `fn:` alone merged their calls into the preceding
   function (lmx_msg_orphan_sweep read 1 it does not have; the true
   owners, request_children_close and exec_ready, read 0 each). Fixed by
   tracking `sub:` as a function boundary too; re-verified against each
   flagged function's own body (orphan_sweep walks rt\root\first_child
   directly, no self_or_find call at all; request_children_close and
   exec_ready each have exactly the 1 SPINE already expected).

--- On "contradiction"

The ticket asks to flag any function whose lookup no capability covers,
as a thing to stop on. Every function in this file's two full inventories
(exec.c, lm1/lm2) lands in one of: C1/C2/C3/C5 (the four the ticket
names), C4 (a real fifth capability, spec-ruled, with its own FIELDS
row), Q (the design's own named open question, not new), X (the wrapper
mechanism being deleted, not a caller), or N (the design's own named
resolution, "a read on the owner's lane, or deleted"). Nothing found here
is unnamed or unresolved by the existing design and spec text; this file
adds two lookup sites the primary grep does not (dest_from_src,
runtime_new) and one missing N-list name (runtime_new) worth the lead
adding, but names no contradiction to stop on.
