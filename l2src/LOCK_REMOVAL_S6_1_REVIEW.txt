exec_bind_mode's own guard against unbound_held changed shape, not just
mechanism: the pre-landing code refused *any* bind to the held address
unconditionally; the new comment (exec.c:1633-1644) says this was wrong
-- the executor selftest's own close-path case binds a closing Message on
purpose, and spec 12762-12765 has a child run its closing turn on its own
context there -- so the real guard is narrower, exactly the one address
R0's maintenance is mid-close on, not every closing Message. Read the
cited spec range and the selftest case this comment names before
accepting the narrowing, not just the comment's own claim: spec 12762-
12765 does describe a child's own context running its closing turn as a
normal path, consistent with the narrower guard being correct and the
old blanket refusal being the actual bug.

--- exec_unbound_close without the identity borrow

Confirmed: the pre-landing body did get_tls/set_tls around lmx_msg_end_
turn to impersonate the target's own turn identity before calling it (a
TLS-level borrow). The new body (exec.c:2161-2197) calls lmx_msg_end_turn
directly with no TLS manipulation at all, relying on a new function, lmx_
msg_maintenance_close_ok (lmx_message.lm1:1669-1682), consulted inside
end_turn's own guard (lm1:1692: `require_turn(rt,who) != OK && maintenance_
close_ok(rt,who) = 0` -- a fallback, not a replacement) only when require_
turn's own normal check fails. maintenance_close_ok's own five conditions
read directly: host is owner, the address is NOT bound (no worker
context), the Message exists, it is already marked closing, and it has no
live execution context -- a narrow admission for exactly the "closing,
unbound, no worker" case, not a general bypass. Its own comment cites
spec 12766-12771 for the underlying rule (the close of a handler-less,
lane-less Message is the maintaining lane's own bookkeeping act); the
cited range does describe exactly that closing-without-a-handler case,
read before accepting the citation.

--- The transport move's hold order

Confirmed, and it is a real design move, not a mechanical substitution:
transport is no longer touched under lmx_msg_exec_lock anywhere. lmx_msg_
host_post now does an early unlocked lmx_msg_host_is_shutdown check (a
fast path only, its own comment says so) and a second check *inside*
lmx_msg_mail_lock(root)/mail_unlock(root) right before the actual q_push
-- ordering a late post against runtime_shutdown under R0's own mailbox
monitor, the one lock the model keeps. lmx_msg_host_drain takes the same
root mail_lock/unlock around its own transport-queue push, sequentially
after (not nested with) the earlier inbox-take window, per its own
comment. lmx_msg_runtime_shutdown now locks/unlocks root's mailbox around
its own call to lmx_msg_host_shutdown, so shutdown and a late post are
ordered against each other by the same monitor on both sides. Cited spec
11551 for "the one cross-lane synchronization the model permits" -- not
independently re-verified against the spec text this pass (out of scope
for a lock-removal review; already the standing rule this project has
operated under all session, "no locks except the mailbox collection").
run_port_message.ps1 gained a new gate (its own diff, +13 lines) counting
lmx_msg_mail_lock/unlock calls in every transport-touching function by
name and throwing on any imbalance -- a real, falsifiable regression
guard for this specific property, not just a comment.
