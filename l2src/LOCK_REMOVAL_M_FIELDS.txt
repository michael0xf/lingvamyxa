LOCK_REMOVAL_M_FIELDS: every site of stage M's target (the sequential mapping of
children onto a parent's thread), the fields each touches, and each field's row
in LOCK_REMOVAL_FIELDS.txt (sonnet/m-fields, 2026-09-15, doc-only, no machine).

Method: git grep, at integration c063fd00, for run_child_turn, sched_step, the UI
stepping (lmx_msg_exec_ui_step), AFFINITY_UI and UI_LANE_ID, restricted to l2src's
implementation files (.c/.h/.lm1/.lm2; tests/ and *_selftest.* excluded -- they are
callers, not the mechanism) and to mixa_manager outside vendor/ (no hits there: the
mixa ingress harness only calls lmx_msg_host_post/drain/wait, never these five).
Categories (kernel / functionality / DEL) and owner codes (MSG, L3T, PAR, MBOX,
DEL) are LOCK_REMOVAL_FIELDS.txt's own scheme, from the lead's header at 23cda3c0:
a row whose owner starts with MSG or MBOX is kernel; L3T or PAR is functionality
written on the kernel; DEL is deleted. Rows quoted below are copied verbatim from
that file's current tip on origin/d6/lock-removal (31348421).

Mikhail's ruling this ticket rests on (LOCK_REMOVAL_FIELDS.txt line 21-25, plan on
main): success belongs to root, the main functionality; where the return stands and
what the scheduler still does with its children are implementation, and children
stop with their parent. Separately, the plan states M's own rule in exactly these
terms: "M is an implementation choice the model allows either way" -- the model
does not forbid a child running on its parent's own thread; M removes today's
*mandatory* sequential relay (every child forced through sched_step's round-robin
cursor and run_child_turn), not same-thread execution itself. A site below being
"removed" means the forced relay's own mechanism (the cursor, the claim, the
tail-call chain) goes; nothing here claims same-thread execution becomes illegal.

--- The missing type

FLAG (missing rows, not missing owner): LmxMsgExec. Every site above that reads or
writes e->ui_lane, e->contexts_live, e->stopping, e->unbound_held, or takes/holds
lmx_msg_exec_lock/unlock touches a field of LmxMsgExec -- the executor's own
runtime state (defined in lmx_message_exec.c, not shown in this survey's target
list since it is not one of LmxMsg or the six scaffolding types
LOCK_REMOVAL_FIELDS.txt documents: LmxMsgEnv, LmxMsgCopy, LmxMsgRuntime,
LmxMsgBindWait, LmxMsgExecBind, and b5's added LmxMsgCtxPack). LmxMsgExec is a
seventh, still entirely undocumented type. It is central to exactly this ticket's
subject (e->ui_lane is the UI lane's own LmxMsg*, read at lmx_msg_exec_ui_step and
lmx_msg_exec_take_ui_locked and written wherever the lane is created and consulted
by ui_request_if_ready_locked) and cannot be skipped by M's own design note: the
note will need to say what becomes of the executor's shared table and its lock (a
process/runtime-wide structure today, in tension with the project's standing rule
that the only synchronization anywhere is each L3 Thread's own mailbox) once every
Message maps to its own OS thread. Recommend a row (or a table) for LmxMsgExec
before M's design note is written, on the same precedent as b5's LmxMsgCtxPack
addition for S3.

--- Sites needing a new lock, wait or signal: none found

Every site surveyed above uses only fields already marked DEL or already staged
for deletion in the same direction M is going (affinity, mapped, held/held_by,
ui_pending all DEL at stage M itself), or the pre-existing exec_lock (LmxMsgExec's
own table lock, not introduced by anything M does and not itself in this ticket's
scope -- see the LmxMsgExec flag above). No site's removal, as read at c063fd00,
would require adding a lock, a wait, or a signal that does not already exist
today; if anything, sched_step's and child_turn_core's removal reduces the number
of places rec->held and rec->affinity are checked under the exec lock. This is the
one thing the rule asks to be stated plainly when it is true, not just when it
fails: no contradiction of this kind was found.
