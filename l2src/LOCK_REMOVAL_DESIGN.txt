WHAT THE LOCK DOES TODAY (from the inventories, not from a rule)
L1. Address resolution. A walk from rt->root through every child list turns an LmxMsgAddr into a record
    (msg_find_any_locked, lmx_msg_find, self_or_find). The lock keeps the tree still under the walk. This is 35 of
    exec.c's 41 silent 5.1 lines.
L2. The family tree's own writes: child_link, child_chain_remove, the orphan re-rooting, the root-list unlink in
    endp_try_retire and release_slot.
L3. The execution mapping's cells: exec_bind record fields, mapped, launching, the bind wait's generation.
L4. Control flags read and written across lanes: ready, closing, running, handoff_ready, native_users.
L5. Runtime-level lists: rt->slots/n, e->retire_head, e->reap_head, rt->transport, e->ui_lane.
L6. Wakes: exec_wake_locked signals every worker after any turn; exec_ready routes one wake.
L7. Storage moves at settle: adopt_mark, dispose_mark, transfer_adopted, transfer_graph.
L8. Test setters and counters.

KERNEL. What L1 is for (Mikhail, spec section 2 line 1078 and model section 2, main 1b2708bf), verbatim: "Вы
    пытаетесь писать на Си, а на Си (L1) надо просто пилить ядро _на котором_ уже пилить дальнейший функционал самого
    ядра. Это как я бы попросил на goto имитировать все циклы, а вы бы заменили задание на "написать примеры while и
    for"  -- совершенно разне задачи".
    The design's first item is therefore the kernel in L1, and it has exactly these parts:
    - Lmx, the graph and its Structures;
    - LmxMsg { running; success; handoff_safe; Lmx *root }, the four-field Message record;
    - one arena per Message, reached from its root;
    - the mailbox as the synchronized collection of Messages, the one lock;
    - the thread running turns over its mailbox: a look into the mailbox and a turn when there is a Message, never
      blocking. The L3 Thread is a model, not an implementation. success belongs to Lmx* root, the main
      functionality: by the model no turn of root repeats once success == 1, and where the return stands is the
      implementation's detail. The L3 Thread's scheduler may still do something with its children after that; what
      it does depends on the implementation, since children may run on the same thread. Since the parent's stop
      stops its children too (the checks go both ways), the loop does in the end break on success == 1; the
      implementation decides only where. User code sets success. running is polled while root executes, and running = 0 written by the
      parent is its stop request, which in the end leaves the loop. At the exit, by return or however, running is set
      to 0. An ended L3 Thread reads !running; success && !running is the end by success, and success stays 0 when
      running became 0 without user code setting it (a stop or a failure). Mikhail, 2026-09-15, verbatim: "цикл в L3 Thread
      очеивдно прерывается по success==1"; "success && !running, с выходом выставляется running = 0. Просто running
      опрашивается при выполнении Lmx* root и я же не знаю как кокнретный планировщик устроен и когда выйдет. Но
      условия выхода очевидно есть!"; "то есть цикл не бесконечный -- из него есть выход хоть по return хоть как";
      "L3 Thread это модель же а не реализация. Да, 0 это запрос остановки от родителя. Что значит "не выход из
      цикла"? Как можно остановить не выходя в конечном итоге из цикла?"; and, correcting the lead's "the loop
      leaving on success == 1 is implementation": "просто по модели L3 Thread не может повторять turn когда success ==
      1, это не деталь реализации. Деталь реализации это где будет стоять return."; and: "Однако планировщик L3
      Thread может что-то делать со своими детьми (вот это зависит отреализации так как дети могут крутиться на том

    root reaches; on L2 that is the code working with these Messages; on L1 the code that will be generated, "В

    - Settle mechanics, since today's records are calloc'd in lmx_msg_slot_new and A1 (records from the arena) is a
      later stage:
      (1) Where a closed child's record and its mailbox live afterwards. release_slot already unbinds the child,
          unlinks it from the family chain and clears its root-list place; under S6-2 it stops draining and
          destroying the mailbox. The child's arena is moved into the parent's by the settle that already exists
          (adopt_mark/dispose_mark through lmx_msg_storage_move_all), and the mailbox goes with it as the parent's
          own settled data: its queues and its monitor are kept, and its owner cell is rewritten to the parent
          under that mailbox's own monitor, so a late sender reaching the handle finds the parent's lane without
          any count. The LmxMsg record itself stays allocated until its owner frees it (2), because the sender's
          capability is the mailbox handle and 19.29.7's "not a graph reference into another Message's mutable
          arena" (today 12922) means the handle must stay addressable while the parent lives.
      (1a) A constraint the code turned up that the mechanism above did not anticipate: a settled record loses its
          way back to its owner. lmx_msg_release_slot calls lmx_msg_child_unlink, and child_unlink clears
          child\parent_msg whenever the removal from the chain succeeds (lmx_message.lm1:662). So after today's
          release_slot the record has state RELEASED, no place in the family chain and parent_msg 0 -- nothing in
          it names the parent that now owns its storage, which is precisely what a late sender must follow to be
          refused "on the parent's lane". S6-2 therefore either stops clearing parent_msg on the settle path (the
          unlink removes it from the chain, but the cell keeps naming its owner) or carries the owner in a cell of
          its own. Recorded here before the code chooses, because it changes the mechanism the coordinator
          approved: the sender's handle is the record, and the record must be able to say who owns it now.
          RULED (the coordinator, on this finding): parent_msg is the owner cell -- no second cell. On the settle
          path child_unlink clears only the chain links (the first_child/next_sibling place), never parent_msg, so
          a RELEASED record names the parent whose storage it is now part of, and each upward settle rewrites it to
          the new owner under the record's own mailbox monitor, which is the monitor the admission takes, so that
          read is ordered without any other synchronization. State RELEASED plus parent_msg is one relation --
          "whose storage am I part of" -- and not a second meaning of the field: the live-family readers
          (parent_gone, poll_mark, live_query) run on running Messages and never meet a RELEASED record on a chain.
          Any site that reads parent_msg = 0 as "released" converts to reading the state, and those sites are named
          in the stage's five lines rather than left to the diff.
      (2) Who frees them and when, corrected by the coordinator before any code and checked against the text: a
          parent's own close does NOT free its settled children's records and mailboxes. They are settled upward
          with the rest of its storage, recursively -- storage_move_all carries them and each mailbox's owner cell
          is rewritten to the new owner under that mailbox's own monitor -- and only R0's runtime_delete frees
          anything. The spec already says the shape: the settle runs "bottom-up as 19.29.8 describes (G's arena
          joins C, then C's joins P)" (origin/main 077ee6fd, today 12751), and 19.29.7 has a closing Message's
          mailbox settled into its parent with the rest of its storage.
          My first wording had the parent free them at its own release_slot, which is wrong for the reason the
          correction gives: a handle held by an uncle or by an ancestor would dangle at the parent's close. The
          guarantee I stated -- the memory outlives every sender that could still address it -- holds only for the
          COMMON ANCESTOR of sender and target, and it is the upward settle that makes the common ancestor the
          owner by the time any of them closes.

          the free path end to end rather than reasoning from the sentence:
            * release_slot takes the child off the family chain (lmx_message.lm1:1400 lmx_msg_child_unlink), and
              under S6-2 it keeps parent_msg but nothing puts the record back on any chain;
            * the only other thing holding a record is rt\slots through LmxMsg.alloc_next (the create site,
              lmx_message.lm1:1180-1182);
            * both free paths walk that list and nothing else -- endp_try_retire unlinks from rt->slots
              (lmx_message_exec.c:1202-1218) and runtime_delete walks rt\slots calling slot_free
              (lmx_message.lm1:1029-1040) -- and slot_free is the real free: it destroys m->mail (the mailbox
              monitor, DeleteCriticalSection / pthread_mutex_destroy) and calls free(m) (exec.c:1163-1172).
          So with rt\slots and alloc_next deleted and nothing in their place, a settled record is reachable from
          NOTHING: R0's tree walk at runtime_delete never meets it, slot_free is never called on it, its monitor is
          never destroyed. Every released Message would leak, with its mailbox. Two details 0c added on checking the
          chain independently, both of which tighten it: the retire route is closed TWICE over, since
          endp_try_retire refuses unless refs == 0 AND parent_msg == 0 (exec.c:1189-1194) -- refs is what the stage
