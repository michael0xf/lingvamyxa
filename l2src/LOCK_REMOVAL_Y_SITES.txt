LOCK_REMOVAL_Y_SITES: every site that reads or writes the mailbox rows (inbox,
inbox_tail, mail the monitor, and the runtime's transport/transport_tail pair) at
integration c063fd00, beside the S3 and M files (sonnet/y-sites, 2026-09-15,
doc-only, no machine).

Method: git grep at c063fd00 across l2src's implementation files (lmx_message.lm1,
its lmx_message.lm2 mirror, lmx_message_exec.c, lmx_message_host.c -- host.c has
no hits at all, confirmed below) and mixa_manager outside vendor/ (no hits there
either: only prose in BACKEND_SEAM.txt/PROCESS_SEAM.txt/REVIEW_20260911.txt uses
the word "inbox", no code). Rows per LOCK_REMOVAL_FIELDS.txt (current tip
31348421, header at 23cda3c0): LmxMsg.inbox/.inbox_tail (h:126-127, MBOX, Y3/A3),
LmxMsg.mail (h:180, MBOX, the monitor, Y2), LmxMsgRuntime.transport/.transport_tail
(h:215-216, MBOX, host posts are admissions into R0's mailbox; the queue DEL,
S5/Y3).

Categories used below (the ticket's own three): OWNER = the Message's own thread,
in its own round/turn, reading or taking its own inbox. ADMISSION = a write that
adds an entry to a mailbox (inbox or transport), run by whichever thread is
delivering (a sender's own turn, or the host outside any turn). HOST DRIVE = the
host thread's between-turns maintenance step (drain, pump), outside any turn.
Lock column: EXEC = lmx_msg_exec_lock/unlock (the executor's own table lock, a
different lock from the mailbox monitor); MAIL = lmx_msg_mail_lock/unlock(m) (the
per-Message monitor, m->mail); NONE = no lock at the site itself (the caller
already holds one, noted inline).

Line format: site | file:line range | thread | category | lock

--- Flags

FLAG-1 (contradiction, matches the rule's second named case: "any read outside
the owner and admission"): a whole family of disposal-time sites reads or drains
a Message's inbox (and outbox) from a thread that is NOT that Message's own and
is NOT performing an admission:
  - lmx_msg_release_slot (lmx_message.lm1:1482) drains m's inbox and outbox at
    slot-release time. Its three callers all run on a DIFFERENT Message's own
    thread, disposing of m: lmx_msg_settle_child (1605, the PARENT disposing its
    finished child), lmx_msg_reclaim_orphan (1667, R0 reclaiming a failed
    orphan), and lmx_msg_end_turn's own inline dispose (1784, a parent disposing
    its just-finished child inline at its own turn's end).
  - lmx_msg_drive_one (lmx_message.lm1:2260) reads a candidate descendant's
    lmx_msg_mail_inbox_empty before deciding to close it -- again the maintenance
    DRIVER's thread (R0's, or whichever thread runs the drive sweep), not the
    descendant's own.
  - lmx_msg_endp_try_retire (lmx_message_exec.c:1175) reads a Message's inbox
    emptiness as part of a retire-eligibility check, same driver-thread pattern.
In every one of these, the Message being read is already stopped, failed, or
finished -- never a live owner mid-turn -- so there is no actual concurrent
access today (the MAIL lock makes each individual read/drain safe regardless,
and reentrant locking, Y2's own model, tolerates this cleanly). This is not a
correctness bug now and is not blocked by Y2's plan. It IS, precisely, a site
whose category the ticket's own two named buckets (owner / admission) do not
cover, so it is flagged as the rule asks rather than silently folded into
"owner." Recommend Y's design note name a third category explicitly --
"disposal" or "settle" -- for teardown-time reads of an already-stopped
Message's mailbox by its parent or R0, distinct from both the owner's live take
and a sender's admission.

FLAG-2 (a smaller instance of the same shape, read-only): lmx_msg_inbox_n
(lmx_message.lm1:2345) is a public API with no turn/ownership guard at all --
any thread holding an address can call it to read another Message's inbox
depth (used by tests and mixa's harness today). Same "read outside the owner"
shape as FLAG-1 but read-only and guarded by MAIL internally, so lower severity;
listed separately since it is a live-Message case (the target need not be
stopped), unlike FLAG-1's disposal family.

FLAG-3 (a lock inconsistency, not named by either of the rule's two cases but
found while surveying "which lock covers it today" as the ticket asked):
lmx_msg_exec_ui_nrequests (lmx_message_exec.c:1713-1727) walks e->ui_lane->inbox
under the EXEC lock, not under the UI lane's own MAIL lock the way every other
UI-lane inbox site (lmx_msg_exec_ui_request_locked, lmx_msg_exec_take_ui_locked)
does. Since the UI lane's inbox chain is mutated only under MAIL elsewhere, a
concurrent take (also under MAIL, not EXEC) is not excluded by this read holding
only EXEC -- a lost-update-shaped read (the count could be read mid-mutation)
unless EXEC happens to always be held by whoever else touches the lane at the
same moment. Flagged for the design note to confirm or fix, not asserted as a
live bug (this ticket's scope is doc-only; no build was run to reproduce it).
