Mixa Manager
Architectural model: text rectangle + transparent raster overlay + child console modes
Version: draft 0.4

0. Purpose

0.0. Core visual concept

Mixa Manager is a future cross-platform text-oriented manager application
with a strictly cell-based text surface and an equally sized transparent
raster/graphics overlay.

Its UI is visually close to the Norton Commander / FAR Manager / Midnight
Commander family: panels, command line, menus, viewers, editors, status bars,
keyboard-oriented navigation and fast textual interaction.

It should be able to operate in two different roles:

1. As its own text UI application, similar in spirit to Norton Commander,
   FAR Manager or Midnight Commander, but rendered inside a GUI window.

2. As a terminal host for child console applications, so that programs such
   as FAR, mc, vim, shells, build tools or REPLs can run inside a rectangular
   text viewport owned by Mixa Manager.

The key design idea is that text and graphics are not separate worlds.
Mixa Manager owns a visual rectangular surface consisting of:

    - a text cell rectangle;
    - a transparent raster/vector overlay with the same pixel geometry.

The text rectangle may be produced by Mixa Manager itself, by a child terminal
program through PTY/ConPTY + terminal emulation, or by a simpler pipe-based
stdout/stderr adapter.

The renderer does not need to know which producer created the text screen.

The rest of the document is only a decomposition of this core idea. Section
0.1 defines how child programs are connected. Section 0.2 defines which
terminal-facing features must be made transparent for child programs when the
strong mode is available. Section 0.3 defines the shared visual API used by
both Mixa Manager's own UI and child-program screens.

0.1. Execution model

0.1.1. Full embedded-terminal mode

If the platform and Qt build allow a real pseudo-terminal backend, Mixa Manager
starts a PTY/ConPTY session and runs libvterm inside the application.

    Unix-like platforms:
        PTY / forkpty() / openpty() / posix_openpt()

    Windows:
        ConPTY / CreatePseudoConsole()

    Terminal emulator core:
        libvterm or a compatible terminal-state engine

In this mode, child programs such as FAR, mc, vim, shells, REPLs and full-screen
console applications run inside a Mixa Manager text rectangle. The child program
believes it is connected to a real terminal. Mixa Manager remains the owner of
rendering and may draw a transparent overlay above the child screen.

0.1.2. Norton Commander delegation mode

If the platform or Qt environment does not provide a usable PTY/ConPTY backend,
Mixa Manager uses the lighter Norton Commander style model.

In this mode, Mixa Manager does not embed the child program as a terminal inside
its own viewport. Instead, it delegates the available console/process input and
output to the child application in the same spirit as Norton Commander:

    1. Mixa Manager owns the screen and draws its UI.
    2. The user launches a child command.
    3. Mixa Manager temporarily gives the available console/process IO to the
       child process, or connects the child through the simplest available
       stdin/stdout/stderr mechanism.
    4. The child program runs outside Mixa Manager's embedded terminal model.
    5. Mixa Manager waits for completion or return.
    6. Mixa Manager redraws its own UI.

This mode is intentionally lighter than 0.1.1. It is not a full terminal host
and does not require libvterm. It is the compatibility mode for platforms where
full embedded terminal hosting is not available or not worth implementing.

0.2. Transparent terminal-facing features

The following features must be implemented as transparently as possible for the
child program in mode 0.1.1, and degraded as gracefully as possible in mode
0.1.2:

    Qt key events          -> terminal input sequences
    resize window          -> PTY/ConPTY resize
    mouse events           -> terminal mouse protocol, if needed
    clipboard / paste      -> terminal paste / bracketed paste, if supported
    encoding               -> UTF-8 / selected terminal encoding
    colors / palette       -> terminal colors / Mixa Manager palette mapping

The purpose of this layer is not to invent a new private input/output protocol
for every child program. The purpose is to make the child program see the
nearest possible equivalent of the terminal or console it expects.

In mode 0.1.1 this transparency is implemented through PTY/ConPTY plus a
terminal-state engine.

In mode 0.1.2 transparency is limited: Mixa Manager can pass text, run commands,
inherit or connect standard streams, and redraw itself afterwards, but it does
not promise that full-screen terminal programs can live inside a Mixa Manager
viewport.

0.3. Shared visual API

0.3.0. The module defined by 0.1 provides the visual API used for drawing both
Mixa Manager itself and child-program screens.

This API exposes two equal rectangles:

    TextRect
        a strict rows x cols cell rectangle

    OverlayRect
        a transparent raster/vector rectangle with the same visible extent

The 0.1 module composites OverlayRect over TextRect during output.

The important consequence is that Mixa Manager's own UI, a libvterm-backed
child terminal, and a lightweight NC-style child-output adapter can all end at
the same visual abstraction:

    producer
        ->
    TextRect + OverlayRect
        ->
    Qt renderer

The renderer should not care whether a cell was produced by Mixa Manager's own
file panels, by libvterm, or by a lightweight child-output adapter.


1. Main visual model

This section formalizes 0.0 and 0.3: the common visual surface used by both roles of Mixa Manager.

The core visible object is a text rectangle:

    TextRect
        rows
        cols
        cells[rows][cols]

    Cell
        codepoint / grapheme
        foreground color
        background color
        style flags
        optional metadata

A typical initial configuration may be:

    cols = 80
    rows = 40

The pixel size is derived from the selected monospace font:

    pixel_width  = cols * cell_width
    pixel_height = rows * cell_height

The overlay rectangle is paired with the text rectangle:

    OverlayRect
        width  = cols * cell_width
        height = rows * cell_height
        RGBA pixels and/or vector primitives

Composition order:

    1. background
    2. text cell backgrounds
    3. glyphs / text
    4. transparent raster/vector overlay
    5. optional cursor / selection / UI decorations

OverlayRect must support two coordinate systems:

    Cell coordinates:
        row, col

    Pixel coordinates:
        x = col * cell_width
        y = row * cell_height

This makes the overlay useful for cell-anchored graphics:

    - highlight a rectangular block of cells;
    - draw a border around a table;
    - draw arrows between tokens;
    - place a heatmap over a text table;
    - annotate build output;
    - visualize code/data structures above a strict textual view.

All later modules must end in this visual model. The difference between 0.1.1
and 0.1.2 is not the renderer. The difference is how the TextRect is produced
and how much terminal behavior is available to the child program.


2. Producers

This section maps the two roles from 0.0 and the 0.1 execution model to producers of TextRect content.

Possible producers:

    OwnUIProducer
        Mixa Manager writes directly to TextRect.
        This is used for panels, menus, dialogs, status bars, command line,
        viewers and editors.

    EmbeddedTerminalProducer
        Implements mode 0.1.1.
        Runs a child terminal application through PTY/ConPTY.
        Output is interpreted by libvterm or a compatible terminal core.
        The resulting screen is copied into TextRect.

    NCDelegationProducer
        Implements mode 0.1.2.
        Runs a child program using the lightest available console/process IO
        model. Mixa Manager temporarily yields interaction to the child or
        captures simple output, then redraws itself.
        This producer does not promise embedded full-screen terminal behavior.

    TestProducer
        Synthetic text screens for tests, demos and renderer debugging.

Only EmbeddedTerminalProducer is a real terminal host. NCDelegationProducer is
included because the project must remain useful on platforms where 0.1.1 is not
available.


3. Own UI path

Mixa Manager's own interface should not emulate a terminal for itself.

The native UI path is direct:

    Mixa Manager UI logic
        ->
    TextRect API
        ->
    OverlayRect API, if needed
        ->
    Qt renderer

Examples:

    panel.draw(...)
    menu.draw(...)
    editor.draw(...)
    viewer.draw(...)
    statusLine.draw(...)

The own UI does not generate ANSI escape sequences and does not feed itself
through libvterm. It writes into TextRect directly.

Keyboard input for the own UI is also direct:

    F5        -> CopyCommand
    F6        -> MoveCommand
    Ctrl+R    -> RefreshCommand
    ArrowDown -> MoveSelectionDown

Terminal encoding is used only when focus is inside an EmbeddedTerminalProducer
from 0.1.1. In mode 0.1.2, own UI still remains direct; child execution is a
separate delegated action.


4. Full embedded-terminal mode: 0.1.1

Mode 0.1.1 is the strong mode.

Architecture:

    Qt keyboard/mouse/window events
        ->
    InputNormalizer
        ->
    TerminalInputEncoder
        ->
    PTY / ConPTY input
        ->
    child terminal program
        ->
    PTY / ConPTY output
        ->
    libvterm or compatible terminal emulator core
        ->
    TextRect
        ->
    Qt renderer
        ->
    OverlayRect composition

Platform backends for 0.1.1:

    Linux desktop:
        PTY + libvterm + Qt renderer

    macOS:
        PTY + libvterm + Qt renderer

    BSD-like systems:
        PTY + libvterm + Qt renderer, subject to platform details

    Windows 10 1809+ / Windows 11:
        ConPTY + libvterm + Qt renderer

    ChromeOS Linux/Crostini:
        treated as Linux target when Mixa Manager runs as a Linux application
        inside the Linux environment

Mode 0.1.1 is required when the child program must live inside a Mixa Manager
rectangle while Mixa Manager keeps owning the frame, overlay and surrounding UI.

Examples of children that require 0.1.1 for embedded operation:

    FAR
    mc
    vim
    nano
    top
    less
    shells
    REPLs with terminal behavior
    curses/full-screen terminal applications


5. Norton Commander delegation mode: 0.1.2

Mode 0.1.2 is the light mode.

It preserves the historical Norton Commander idea: a manager application does
not become a terminal host for the child; it temporarily gives the available
console/process IO to the child and returns afterwards.

Classic sequence:

    1. Mixa Manager UI is visible.
    2. User launches a child command.
    3. Mixa Manager stores enough state to redraw itself later.
    4. Child runs through inherited console/process IO or simple pipes.
    5. Child exits or returns control.
    6. Mixa Manager redraws TextRect and OverlayRect.

This is not:

    child terminal inside parent rectangle

It is:

    child instead of parent for a while

Mode 0.1.2 is useful for:

    - simple command execution;
    - build commands;
    - scripts;
    - utilities that produce ordinary text output;
    - platforms where full PTY/ConPTY is not a target;
    - a cheap, familiar NC-like launch behavior.

Mode 0.1.2 should still use the common visual API when control returns:

    NC-style child execution
        ->
    Mixa Manager redraws
        ->
    TextRect + OverlayRect
        ->
    Qt renderer

But it does not use libvterm as the central child-screen model.


6. Pipe / simple output adapter inside 0.1.2

A practical implementation of 0.1.2 may include a simple pipe adapter:

    child stdout/stderr
        ->
    QProcess / platform pipe
        ->
    simple text parser
        ->
    TextRect

This is useful for:

    git status
    compiler output
    logs
    simple scripts
    one-shot command output

This adapter is part of 0.1.2, not a replacement for 0.1.1.

The pipe adapter may parse only simple text features:

    newline
    carriage return
    tab
    optional ANSI colors
    optional clear-screen subset

It should not claim that it can host all full-screen terminal software inside a
Mixa Manager rectangle. That guarantee belongs to 0.1.1.


7. Input model

This section implements 0.2 for both 0.1.1 and 0.1.2.

Keyboard input must not be modeled as "one key press equals one byte".

There are at least three levels:

    Physical/native event:
        scan code, native virtual key, platform modifiers

    Logical key event:
        F1, Enter, Ctrl+Left, Alt+F7, Home, End

    Text input event:
        committed Unicode text, for example:
            a
            я
            é
            λ
            漢

Qt provides useful information at several levels:

    QKeyEvent:
        key()
        modifiers()
        text()
        nativeScanCode()
        nativeVirtualKey()
        nativeModifiers()

    QInputMethodEvent:
        committed text from IME / dead keys / composition

    QAbstractNativeEventFilter:
        platform-native events if deeper integration is needed

The recommended internal path:

    Qt/native event
        ->
    InputNormalizer
        ->
    internal InputEvent
        ->
    FocusRouter

If focus is in Mixa Manager's own UI:

    InputEvent
        ->
    OwnCommandMapper
        ->
    direct TextRect / OverlayRect changes

If focus is in an embedded terminal viewport from 0.1.1:

    InputEvent
        ->
    TerminalInputEncoder
        ->
    PTY/ConPTY input stream

If the current operation is a 0.1.2 delegated child process:

    Mixa Manager passes only what the light mode can honestly pass:
        inherited console/process IO, simple stdin, or platform-specific
        delegated input.

The important rule is that unknown native non-text key events cannot be blindly
sent to a PTY byte stream. If there is no committed text and no known terminal
semantic key, there is no universal byte representation to pass through.


8. Text input

Ordinary text input should be delegated to Qt/OS/input method as much as
possible.

For normal typing:

    QString committedText
        ->
    UTF-8 bytes
        ->
    PTY/ConPTY input in 0.1.1

This means Mixa Manager should not manually derive characters from scan codes
or keyboard layouts.

Qt/OS should handle:

    - Russian layout;
    - Latin layout;
    - dead keys;
    - accents;
    - IME;
    - Unicode text input.

In 0.1.1 the committed Unicode text is sent to the embedded child terminal as
UTF-8 unless a selected terminal profile says otherwise.

In 0.1.2 the same committed text may be sent only when the delegated child IO
model has a meaningful stdin path. Otherwise text input belongs to Mixa
Manager's own UI and the child owns interaction only while the parent is in the
delegated state.


9. Special keys

Special keys implement the non-text part of 0.2.

Examples:

    F1-F12
    arrows
    Insert
    Delete
    Home
    End
    PageUp
    PageDown
    Shift+Tab
    Ctrl+arrows
    Alt+keys
    keypad keys

These keys do not have a universal native byte representation for child
terminal programs.

In 0.1.1 Mixa Manager needs a TerminalInputEncoder:

    Qt key event
        ->
    TerminalKey enum / semantic key
        ->
    terminal profile / libvterm keyboard helper
        ->
    bytes
        ->
    PTY/ConPTY input

Examples of semantic keys:

    TerminalKey::Up
    TerminalKey::Down
    TerminalKey::Left
    TerminalKey::Right
    TerminalKey::Function(5)
    TerminalKey::Home
    TerminalKey::End
    TerminalKey::Insert
    TerminalKey::Delete
    TerminalKey::PageUp
    TerminalKey::PageDown

Correct rule for 0.1.1:

    if event produces committed text:
        send text as UTF-8

    else if event is known terminal key:
        encode through TerminalInputEncoder

    else if event belongs to Mixa Manager itself:
        handle as own command

    else:
        ignore, log, or allow user-configurable binding

For 0.1.2, special keys are either handled by Mixa Manager itself or delegated
only through whatever real console/process mechanism is actually active during
the temporary child run. 0.1.2 must not pretend to be a universal special-key
terminal bridge.


10. Terminal identity and profiles

This section belongs primarily to 0.1.1.

Mixa Manager should define a terminal identity for embedded child programs.

Possible baseline:

    TERM=xterm-256color

Then Mixa Manager must behave consistently enough with that identity:

    - escape sequences;
    - cursor modes;
    - application cursor mode;
    - keypad mode;
    - function keys;
    - alternate screen;
    - color modes;
    - mouse reporting, if enabled;
    - resize behavior.

Input profiles may include:

    xterm-like
    linux-console-like
    windows-terminal-like
    far-compatible tweaks
    custom/user profile

Mode 0.1.2 does not need to claim such a terminal identity unless its current
implementation actually provides a terminal-like adapter. In the normal NC
style case, the child uses the platform's available console/process IO and
Mixa Manager redraws afterwards.


11. Clipboard and paste

Clipboard is part of the 0.2 transparency layer.

Qt can handle OS clipboard integration.

Copy from Mixa Manager:

    TextRect selection
        ->
    QString selectedText
        ->
    QClipboard::setText(...)

Paste into embedded terminal in 0.1.1:

    QClipboard::text()
        ->
    optional normalization
        ->
    UTF-8 bytes
        ->
    PTY/ConPTY input

Bracketed paste should be supported for terminal child programs in 0.1.1:

    ESC [ 200 ~
    pasted text
    ESC [ 201 ~

If libvterm keyboard helpers are used, they may assist with start/end paste
according to terminal mode.

In 0.1.2, clipboard belongs primarily to Mixa Manager's own UI. It may be sent
to a delegated child only if that child has an active stdin/console path under
the current platform implementation.

On X11 there may be both:

    - normal clipboard;
    - primary selection.

On Windows and macOS there is usually only the normal global clipboard model.


12. Mouse input

Mouse input is part of the 0.2 transparency layer, but should be added after
keyboard and text input are stable.

For Mixa Manager's own UI:

    Qt mouse event
        ->
    Own UI hit testing and commands
        ->
    TextRect / OverlayRect changes

For embedded child terminal in 0.1.1:

    Qt mouse event
        ->
    terminal mouse protocol encoder
        ->
    PTY/ConPTY input

Potential supported terminal mouse modes:

    - basic mouse reporting;
    - SGR mouse mode;
    - wheel events;
    - button press/release;
    - drag tracking, if needed.

Mouse reporting in 0.1.1 is mode-dependent. Terminal child programs normally
enable mouse tracking by sending escape sequences. The terminal state layer must
remember whether mouse reporting is active.

In 0.1.2, mouse input remains mostly Mixa Manager's own UI input. During a
classic delegated child run, the child owns whatever platform interaction is
available, but Mixa Manager does not translate mouse events into an embedded
terminal viewport unless 0.1.1 is active.


13. Resize model

Resize is a 0.2 transparency requirement and must be synchronized with 0.3.

When the Qt window or font changes:

    1. measure cell_width and cell_height;
    2. compute cols and rows;
    3. resize TextRect;
    4. resize OverlayRect;
    5. in 0.1.1, notify PTY/ConPTY about the new terminal size;
    6. in 0.1.1, resize libvterm screen;
    7. repaint.

The terminal child in 0.1.1 must be told the same size that Mixa Manager is
actually rendering.

Otherwise:

    - child thinks it has 80x40;
    - renderer shows 100x50;
    - output, cursor, scrolling and overlay alignment become wrong.

In 0.1.2 there may be no embedded child viewport to resize. Resize affects the
Mixa Manager UI and its own TextRect/OverlayRect; any child process uses the
platform's delegated console/process model.


14. Unicode and glyph issues

This section applies to the shared 0.3 visual API regardless of whether content
comes from own UI, 0.1.1 or 0.1.2.

TextRect should not be a naive char[rows][cols].

Important issues:

    - Unicode codepoints;
    - grapheme clusters;
    - combining marks;
    - wide characters;
    - ambiguous-width characters;
    - box-drawing characters;
    - pseudographics;
    - font fallback;
    - bold, underline, italic, inverse;
    - truecolor, 256-color and palette modes.

For a file-manager style UI, box drawing and exact cell alignment are critical.
The visual style should remain sharp, strict and readable.

The renderer should be designed so that pseudographic lines align cleanly with
the cell grid.

In 0.1.1, libvterm or the terminal core contributes terminal semantics, but the
final glyph rendering still belongs to Mixa Manager.

In 0.1.2, the same renderer draws Mixa Manager's own restored UI and any simple
captured output that was converted into TextRect.


15. Renderer choices

Qt is the main application framework.

Possible rendering implementations:

    Simple first version:
        QWidget + QPainter

    Faster version:
        QWindow / QOpenGLWidget / QRhi
        glyph atlas
        overlay as texture
        GPU alpha blending

    Alternative:
        Qt Quick / QML, if it does not make text-cell precision harder

The renderer must support the 0.3 model:

    - fixed cell grid;
    - cached glyph atlas or efficient text drawing;
    - dirty cell repainting later, if needed;
    - RGBA overlay;
    - selection;
    - cursor;
    - scaling / DPI awareness.

The renderer must not know whether a cell came from:

    - OwnUIProducer;
    - EmbeddedTerminalProducer in 0.1.1;
    - NCDelegationProducer / simple pipe adapter in 0.1.2;
    - TestProducer.


16. Platform summary by model mode

The project should classify platforms by supported Mixa Manager mode, while preserving the 0.0 visual idea on every target: Mixa Manager remains a TextRect + OverlayRect application even when only the light child-execution mode is available.

Mode 0.1.1 targets:

    Windows 10 1809+ / Windows 11:
        0.1.1 through ConPTY + libvterm + Qt renderer.
        0.1.2 also available as a fallback/compatibility behavior.

    Linux desktop:
        0.1.1 through PTY + libvterm + Qt renderer.
        0.1.2 also available.

    macOS:
        0.1.1 through PTY + libvterm + Qt renderer.
        0.1.2 also available.

    BSD-like systems:
        0.1.1 through PTY + libvterm + Qt renderer, subject to platform details.
        0.1.2 also available.

    ChromeOS Linux/Crostini:
        0.1.1 when Mixa Manager runs as a Linux application inside the Linux
        environment.
        0.1.2 also available.

Mode 0.1.2-light targets:

    Android:
        supports only the 0.1.2 lightweight version as a project target.
        The application should still use TextRect + OverlayRect for its own UI,
        but it should not require embedded PTY/ConPTY terminal hosting.

    iOS:
        supports only the 0.1.2 lightweight version as a project target.
        The application should still use TextRect + OverlayRect for its own UI,
        but it should not require embedded PTY/ConPTY terminal hosting.

    WebAssembly/browser:
        supports only the 0.1.2 lightweight version as a project target.
        Mixa Manager may render its UI and demonstrate TextRect + OverlayRect,
        but child execution must be limited to in-browser emulation, remote
        backend, or simple model-specific adapters.

    Embedded Linux:
        0.1.1 if the system has normal userspace, process launching and PTY.
        Otherwise 0.1.2-light.

This wording keeps the document tied to the model: every platform is described
by which 0.1 mode it supports.

18. Backend interface sketch

The backend interface should not be called only PtyBackend, because 0.1.2 is
not a PTY backend.

Better base interface:

    class ChildBackend
        start(program, args, environment, cols, rows)
        writeInput(bytes)
        resize(cols, rows)
        terminate()
        kill()

        signal output(bytes)
        signal exited(code)
        signal modeChanged(...)

Implementations:

    UnixPtyBackend:
        mode 0.1.1
        forkpty/openpty/posix_openpt

    WindowsConptyBackend:
        mode 0.1.1
        CreatePseudoConsole and pipes

    NCDelegationBackend:
        mode 0.1.2
        temporarily delegates available console/process IO to child and returns
        control to Mixa Manager afterwards

    PipeProcessBackend:
        mode 0.1.2 helper
        QProcess pipes; useful for simple output, not a terminal

    DummyBackend:
        tests, demos, non-desktop and 0.1.2-light targets

The output of every backend that produces visible text must ultimately be
converted into TextRect or trigger a redraw of Mixa Manager's own TextRect.


19. Important weak spots, expressed through the 0.1 model

The project is realistic, but the weak spots must remain explicit.

1. Mode 0.1.1 is the only real embedded-terminal mode.
   If there is no PTY/ConPTY-equivalent backend, a child program should not be
   promised a live terminal rectangle inside Mixa Manager.

2. Mode 0.1.2 is useful but intentionally lighter.
   It can reproduce the classic NC behavior: launch child, delegate interaction
   or simple IO, return, redraw. It does not replace libvterm-backed hosting.

3. Input is the hardest 0.2 layer.
   Normal text can be delegated to Qt/OS, but special terminal keys need an
   encoder/profile in 0.1.1.

4. Unknown non-text keys cannot be universally passed through.
   PTY/ConPTY input is bytes, not native Qt/OS event objects.

5. Unicode and cell width belong to 0.3 and affect every mode.
   Terminal rendering is not just drawing ASCII.

6. Resize must be synchronized across window, TextRect, OverlayRect, PTY/ConPTY
   and libvterm in 0.1.1.

7. Own UI should not go through terminal emulation.
   Mixa Manager should write directly into TextRect and OverlayRect.

8. Terminal child programs and own UI should share the same visual API, not the
   same input/output path.

9. Overlay must be tied to cell geometry.
   Otherwise text and graphics drift apart.

10. Clipboard is simple for TextRect copy, but terminal paste in 0.1.1 needs
    bracketed paste and mode awareness.

11. Platform notes must be expressed as mode support.
    For example: Android supports only 0.1.2-light as a project target, rather
    than being described vaguely as lacking a full terminal.


20. Final design formula

Mixa Manager is built around the 0.0 visual concept and the following execution modes:

    0.1.1 Full embedded-terminal mode:
        PTY/ConPTY
            ->
        libvterm / terminal core
            ->
        TextRect
            +
        OverlayRect
            ->
        Qt renderer

    0.1.2 Norton Commander delegation mode:
        Mixa Manager UI
            ->
        launch/delegate child through available console/process IO
            ->
        child exits or returns
            ->
        Mixa Manager redraws
            ->
        TextRect
            +
        OverlayRect
            ->
        Qt renderer

    Own UI path:
        Mixa Manager commands
            ->
        TextRect
            +
        OverlayRect
            ->
        Qt renderer

The central abstraction is not stdout.

The central abstraction is:

    TextRect + OverlayRect

The essential difference from a classic Norton Commander clone is therefore
precise:
