Mixa Manager
Architectural note: text UI + raster overlay + embedded terminal backend
Version: draft 0.1

0. Purpose

Mixa Manager is a future cross-platform text-oriented manager application
with a strictly cell-based text surface and an equally sized transparent
raster/graphics overlay.

It should be able to operate in two different roles:

1. As its own text UI application, similar in spirit to Norton Commander,
   FAR Manager or Midnight Commander, but rendered inside a GUI window.

2. As a terminal host for child console applications, so that programs such
   as FAR, mc, vim, shells, build tools or REPLs can run inside a rectangular
   text viewport owned by Mixa Manager.

The key design idea is that text and graphics are not separate worlds.
Mixa Manager owns a visual rectangular surface consisting of:

    - a text cell rectangle;
    - a transparent raster/vector overlay with the same pixel geometry.

The text rectangle may be produced by Mixa Manager itself, by a child terminal
program through PTY/ConPTY + terminal emulation, or by a simpler pipe-based
stdout/stderr adapter.

The renderer does not need to know which producer created the text screen.


1. Main visual model

The core visual object is a text surface:

    TextSurface
        rows
        cols
        cells[rows][cols]

    Cell
        codepoint / grapheme
        foreground color
        background color
        style flags
        optional metadata

A typical initial configuration may be:

    cols = 80
    rows = 40

The window size is derived from the font metrics:

    pixel_width  = cols * cell_width
    pixel_height = rows * cell_height

The overlay surface has the same pixel rectangle:

    OverlaySurface
        width  = cols * cell_width
        height = rows * cell_height
        RGBA pixels and/or vector primitives

Composition order:

    1. background
    2. text cell backgrounds
    3. glyphs / text
    4. transparent raster/vector overlay
    5. optional cursor / selection / UI decorations

The overlay should support both coordinate systems:

    Cell coordinates:
        row, col

    Pixel coordinates:
        x = col * cell_width
        y = row * cell_height

This allows graphics to be anchored to text objects:

    - highlight a rectangular block of cells;
    - draw a border around a table;
    - draw arrows between tokens;
    - place a heatmap over a text table;
    - annotate build output;
    - visualize code/data structures over a strict textual view.


2. Producers

The core renderer should not care where the text comes from.

Possible producers:

    OwnUIProducer
        Mixa Manager writes directly to TextSurface.
        This is used for file panels, menus, dialogs, status bars,
        command line, viewers and editors.

    PtyTerminalProducer
        Runs a child terminal application through PTY/ConPTY.
        Output is interpreted by a terminal emulator core, such as libvterm.
        The resulting terminal screen is copied into TextSurface.

    PipeOutputProducer
        Runs a child process through ordinary stdin/stdout/stderr pipes.
        Suitable for simple commands, logs and compiler output.
        Not a full terminal.

    TestProducer
        Synthetic text screens for tests, demos and renderer debugging.


3. Own UI path

For Mixa Manager's own interface, do not generate ANSI escape sequences and
do not feed them into libvterm.

The native UI path should be direct:

    Mixa Manager UI logic
        ->
    TextSurface API
        ->
    Renderer
        ->
    OverlaySurface composition

Examples:

    panel.draw(...)
    menu.draw(...)
    editor.draw(...)
    viewer.draw(...)
    statusLine.draw(...)

This avoids unnecessary self-emulation.

Mixa Manager's own UI should treat keyboard input as structured input events,
not terminal bytes. For example:

    F5        -> CopyCommand
    F6        -> MoveCommand
    Ctrl+R    -> RefreshCommand
    ArrowDown -> MoveSelectionDown

Terminal encoding is needed only when sending input to a child program running
behind PTY/ConPTY.


4. Full terminal host path

When Mixa Manager runs an interactive child console program inside its own
rectangular viewport, it must act as a terminal host.

Architecture:

    Qt keyboard/mouse/window events
        ->
    InputNormalizer
        ->
    TerminalInputEncoder
        ->
    PTY / ConPTY input
        ->
    child terminal program
        ->
    PTY / ConPTY output
        ->
    terminal emulator core, for example libvterm
        ->
    TextSurface
        ->
    Qt renderer
        ->
    OverlaySurface

Platform backends:

    Unix-like desktop systems:
        forkpty(), openpty(), posix_openpt(), /dev/pts

    macOS:
        forkpty() / openpty()

    Windows 10 1809+ / Windows 11:
        ConPTY / CreatePseudoConsole()

    ChromeOS with Linux/Crostini:
        normal Linux PTY model, if Mixa Manager is built and run as a Linux
        application inside the Linux environment.

    Browser / WebAssembly:
        no normal local PTY/ConPTY for arbitrary local child programs.
        Only UI emulation, in-browser programs, or remote backend.

    iOS / Android:
        possible only with platform-specific limitations and sandboxing.
        Not a primary target for full terminal hosting.

The important distinction:

    Mixa Manager as terminal host:
        child program lives inside a Mixa Manager viewport.

    Classic Norton Commander style:
        parent temporarily gives the whole real console to the child process,
        waits for it to finish, and then redraws itself.

These are different models.


5. Why Norton Commander and FAR are not terminal hosts

Norton Commander in DOS did not emulate a terminal. It was a text UI program
that directly drew its own panels into the DOS/VGA text screen, often through
video memory or BIOS/DOS services.

FAR Manager in Windows is a Win32 console application. It draws its own UI
through the Windows Console API and receives keyboard events from the Windows
console subsystem.

Neither NC nor FAR, in their normal historical roles, was a terminal host for
an embedded child program. When they launched another program, the cheap and
classic trick was:

    1. parent UI is on screen;
    2. user launches child command;
    3. parent gives the real console to the child;
    4. child runs in the same full console;
    5. parent waits;
    6. parent redraws its own panels.

This is not "child inside parent". It is "child instead of parent for a while".

Mixa Manager should support this simple model where useful, but the distinctive
future model is stronger:

    child terminal program inside a Mixa Manager viewport,
    with Mixa Manager still owning rendering and overlay composition.


6. Degraded pipe backend

If PTY/ConPTY is not available, Mixa Manager may still run child processes
through ordinary pipes:

    child stdout/stderr
        ->
    QProcess / platform pipe
        ->
    simple text parser
        ->
    TextSurface

This is suitable for:

    - git status;
    - compiler output;
    - logs;
    - simple scripts;
    - one-shot command output.

It is not suitable as a full replacement for PTY/ConPTY.

Programs such as FAR, mc, vim, nano, top, less, curses applications and many
interactive REPLs expect a real terminal or console-like environment. With
ordinary pipes, they may disable full-screen mode, change buffering, lose
cursor control, or fail to behave correctly.

Therefore the degraded backend should be explicit:

    PipeOutputProducer
        simple output only;
        no guarantee of full terminal semantics.


7. Input model

Keyboard input must not be modeled as "one key press equals one byte".

There are at least three levels:

    Physical/native event:
        scan code, native virtual key, platform modifiers

    Logical key event:
        F1, Enter, Ctrl+Left, Alt+F7, Home, End

    Text input event:
        committed Unicode text, for example:
            a
            я
            é
            λ
            漢

Qt gives useful information at several levels:

    QKeyEvent:
        key()
        modifiers()
        text()
        nativeScanCode()
        nativeVirtualKey()
        nativeModifiers()

    QInputMethodEvent:
        committed text from IME / dead keys / composition

    QAbstractNativeEventFilter:
        platform-native events if deeper integration is needed

The recommended internal path:

    Qt/native event
        ->
    InputNormalizer
        ->
    internal InputEvent
        ->
    FocusRouter

If focus is in Mixa Manager's own UI:

    InputEvent
        ->
    OwnCommandMapper

If focus is in an embedded terminal viewport:

    InputEvent
        ->
    TerminalInputEncoder
        ->
    PTY/ConPTY input stream


8. Text input

Ordinary text should be delegated to Qt/OS/input method as much as possible.

For normal typing:

    QString committedText
        ->
    UTF-8 bytes
        ->
    PTY/ConPTY input

This means Mixa Manager should not manually derive characters from scan codes
or keyboard layouts.

The OS/Qt should handle:

    - Russian layout;
    - Latin layout;
    - dead keys;
    - accents;
    - IME;
    - Unicode text input.

Mixa Manager sends the committed Unicode text to the child terminal as UTF-8,
unless a specific terminal mode requires otherwise.


9. Special keys

Special keys do not have universal "raw native" byte representation for a
terminal child.

Examples:

    F1-F12
    arrows
    Insert
    Delete
    Home
    End
    PageUp
    PageDown
    Shift+Tab
    Ctrl+arrows
    Alt+keys
    keypad keys

For these keys Mixa Manager needs a TerminalInputEncoder.

The encoder should not be a giant hardcoded table directly from Qt key to bytes
if this can be avoided.

Better model:

    Qt key event
        ->
    TerminalKey enum / semantic key
        ->
    terminal profile / libvterm keyboard helper
        ->
    bytes
        ->
    PTY/ConPTY input

Examples of semantic keys:

    TerminalKey::Up
    TerminalKey::Down
    TerminalKey::Left
    TerminalKey::Right
    TerminalKey::Function(5)
    TerminalKey::Home
    TerminalKey::End
    TerminalKey::Insert
    TerminalKey::Delete
    TerminalKey::PageUp
    TerminalKey::PageDown

The child terminal program does not receive Qt events. It receives terminal
input. Therefore unknown non-text key events cannot be blindly passed through.

Correct rule:

    if event produces committed text:
        send text as UTF-8

    else if event is known terminal key:
        encode through TerminalInputEncoder

    else if event belongs to Mixa Manager itself:
        handle as own command

    else:
        ignore, log, or allow user-configurable binding

There is no universal pass-through for "unknown non-text native key events"
through a PTY byte stream.


10. Terminal identity and profiles

Mixa Manager should define a terminal identity for child programs.

Possible baseline:

    TERM=xterm-256color

Then Mixa Manager must behave consistently enough with that identity:

    - escape sequences;
    - cursor modes;
    - application cursor mode;
    - keypad mode;
    - function keys;
    - alternate screen;
    - color modes;
    - mouse reporting, if enabled;
    - resize behavior.

Input profiles may include:

    xterm-like
    linux-console-like
    windows-terminal-like
    far-compatible tweaks
    custom/user profile

Future support may include enhanced keyboard protocols, for example modern
terminal protocols that represent more key combinations than classic VT/xterm.
However, old terminal software will still require conservative xterm/vt-like
behavior.


11. Clipboard and paste

Qt can handle OS clipboard integration.

Copy from Mixa Manager:

    TextSurface selection
        ->
    QString selectedText
        ->
    QClipboard::setText(...)

Paste into embedded terminal:

    QClipboard::text()
        ->
    optional normalization
        ->
    UTF-8 bytes
        ->
    PTY/ConPTY input

Bracketed paste should be supported for terminal child programs:

    ESC [ 200 ~
    pasted text
    ESC [ 201 ~

If libvterm keyboard helpers are used, they may assist with start/end paste
depending on terminal mode.

On X11 there may be both:

    - normal clipboard;
    - primary selection.

On Windows and macOS there is usually only the normal global clipboard model.


12. Mouse input

Mouse input should be optional and added after the keyboard/text path is stable.

For Mixa Manager's own UI:

    Qt mouse event
        ->
    Own UI hit testing and commands

For embedded child terminal:

    Qt mouse event
        ->
    terminal mouse protocol encoder
        ->
    PTY/ConPTY input

Potential supported terminal mouse modes:

    - basic mouse reporting;
    - SGR mouse mode;
    - wheel events;
    - button press/release;
    - drag tracking, if needed.

This should be profile- and mode-dependent. Terminal child programs normally
enable mouse tracking by sending escape sequences. The terminal emulator core
or surrounding terminal state should remember whether mouse reporting is active.


13. Resize model

Resize is a synchronization problem.

When the Qt window or font changes:

    1. measure cell_width and cell_height;
    2. compute cols and rows;
    3. resize TextSurface;
    4. resize OverlaySurface;
    5. notify PTY/ConPTY about new terminal size;
    6. resize terminal emulator screen;
    7. repaint.

The terminal child must be told the same size that Mixa Manager is actually
rendering.

Otherwise:

    - child thinks it has 80x40;
    - renderer shows 100x50;
    - output, cursor, scrolling and overlay alignment become wrong.


14. Unicode and glyph issues

TextSurface should not be a naive char[rows][cols].

Important issues:

    - Unicode codepoints;
    - grapheme clusters;
    - combining marks;
    - wide characters;
    - ambiguous-width characters;
    - box-drawing characters;
    - pseudographics;
    - font fallback;
    - bold, underline, italic, inverse;
    - truecolor, 256-color and palette modes.

For a file manager style UI, box drawing and exact cell alignment are critical.
The visual style should remain sharp, strict and readable.

The renderer should be designed so that pseudographic lines align cleanly with
the cell grid.


15. Renderer choices

Qt is the main application framework.

Possible rendering implementations:

    Simple first version:
        QWidget + QPainter

    Faster version:
        QWindow / QOpenGLWidget / QRhi
        glyph atlas
        overlay as texture
        GPU alpha blending

    Alternative:
        Qt Quick / QML, if it does not make text cell precision harder

The renderer should support:

    - fixed cell grid;
    - cached glyph atlas or efficient text drawing;
    - dirty cell repainting later, if needed;
    - RGBA overlay;
    - selection;
    - cursor;
    - scaling / DPI awareness.

The renderer should not know whether a cell came from own UI, libvterm or pipe
output.


16. Platform summary

Full desktop targets:

    Windows 10 1809+ / Windows 11:
        ConPTY + terminal emulator core + Qt renderer.

    Linux desktop:
        PTY + terminal emulator core + Qt renderer.

    macOS:
        PTY + terminal emulator core + Qt renderer.

    BSD-like systems:
        PTY + terminal emulator core + Qt renderer, subject to platform details.

    ChromeOS Linux/Crostini:
        treat as Linux target inside the Linux environment.

Partial / non-primary targets:

    WebAssembly/browser:
        no local arbitrary child-process PTY;
        possible UI demo, remote backend, or in-browser emulated process.

    Android/iOS:
        possible only with platform-specific restrictions;
        not the baseline for full terminal hosting.

    Embedded Linux:
        possible if the system has normal userspace, process launching and PTY.

19. Important weak spots

The project is realistic, but the weak spots must be acknowledged.

1. No PTY/ConPTY, no full terminal child.
   Pipe output is useful but not a real terminal.

2. Input is the hardest compatibility layer.
   Normal text can be delegated to Qt/OS, but special terminal keys need an
   encoder/profile.

3. Unknown non-text keys cannot be universally passed through.
   PTY/ConPTY input is bytes, not native Qt/OS event objects.

4. Unicode and cell width are easy to underestimate.
   Terminal rendering is not just drawing ASCII.

5. Resize must be synchronized across window, TextSurface, overlay, PTY/ConPTY
   and terminal emulator core.

6. Windows support should target modern Windows only.
   Pre-ConPTY Windows requires old hacks such as hidden console/screen scraping
   or winpty-like compatibility layers.

7. Own UI should not go through terminal emulation.
   Mixa Manager should write directly into TextSurface.

8. Terminal child programs and own UI should share the same visual API, not the
   same input/output path.

9. Overlay should be tied to cell geometry.
   Otherwise text and graphics will drift apart.

10. Clipboard is easy for simple text, but terminal paste needs bracketed paste
    and mode awareness.


20. Final design formula

Mixa Manager should be built around a visual surface, not around stdout.

The central abstraction:

    TextSurface + OverlaySurface

The native Mixa Manager UI writes directly:

    Own UI
        ->
    TextSurface

Embedded terminal programs go through:

    PTY/ConPTY
        ->
    terminal emulator core
        ->
    TextSurface

Simple child commands may go through:

    QProcess pipes
        ->
    simple output adapter
        ->
    TextSurface

All visual output becomes:

    TextSurface
        +
    OverlaySurface
        ->
    Qt renderer

The result is a file-manager-like application that can still host real terminal
programs, while also allowing transparent raster/vector graphics over a strict
text cell grid.

This is the essential difference from a classic Norton Commander clone:

    classic NC clone:
        text UI that temporarily gives the whole console to child programs;

    Mixa Manager:
        owns a GUI text/graphics surface and can embed child terminal sessions
        inside it through PTY/ConPTY + terminal emulation.
