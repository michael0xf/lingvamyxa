создание нового Message. У копий явно переписываются node и ссылки детей/payload
через таблицу исходный адрес -> адрес копии. Общие адресаты и циклы сохраняются.
Когда используется всё соответствующее обычное дерево, копируется всё дерево.
Неизвестный путь не доказывает ненужность. Вечные ветки — явная граница обхода

Исходные объекты не перезаписываются. Прежняя формулировка «merge копирует только
указатели, предки не копируются, node сохраняются» отменена.

independent создаёт Structure с node=0, отсекая только внешнюю лексику.

1.0. §21.5.1, исполняемые тела и аргументы (2026-09-11).

Исполняемый код — часть графа; его аргументы — нет. Правило общее для любых
ресиверов и трейлеров. Роль задаёт потребление, а не позиция последней Structure
в аргументах. if/else/for/while хостят собственные поля в отдельных телах;
вложенные тела образуют настоящую иерархию, но не границу вложенных методов.
Одноимённое присваивание аргументу по §11.3.1 СОХРАНЕНО: со строки bind это
кеш собственного поля тела, без записи в источник аргумента. Аргумент-ссылка
может указывать на существующий граф; правило не удаляет и не копирует его.
В return с вложенным выражением выражение остаётся аргументом. Тело, которое
ресивер исполняет построчно, подчиняется общему правилу и в позиции трейлера.
Договорённость нормативна; реализацию обобщения hosting делаем ПОСЛЕ текущего
Message. Исследование расхождения трёх проходов: mixa_manager/SPEC_DIGEST.txt
§6.1.3.1. Не считать нынешнее ограничение if нормой языка.

1.1. §21.7, genesis note.

Правило spill/no-reload выведено из онтологии, а не постулировано: всё
Structure, один последовательный поток на Message, маленький C-стек.
Structure, на которую указывает invoking_structure, хранит состояние, оставленное
последними публикациями метода, в том числе при выходе из вызовов. Это не
состояние конкретного вызова и не полный снимок последней активации:
аргументы, сквозные значения, рабочие локали и dirty-состояние активации
остаются в C-стеке. Голое имя собственного поля ВЫГЛЯДИТ как локаль
Алгола-60, но сохраняется как поле экземпляра; spill/no-reload — шов между
этими двумя природами. Публикуются только изменённые own-поля, не весь
снимок и не сквозные значения. Неизменённое own-поле не перетирает результат
вложенного вызова. После возврата вызывающий не перечитывается.

Границы публикации заданы §21.6: исходящий LMX-вызов; внешняя/runtime-граница,
способная опубликовать граф или вызвать пользовательский код; каждый выход
(включая fallthrough, return, throw, провал assert, stop, отмену); приостановка
yield. Приватный неубегающий хелпер текущей активации сам по себе такой
границей не является.

Dirty означает ФАКТИЧЕСКИ исполненную запись текущей активацией после
последнего успешного чекпойнта, включая ++/-- и запись через хелпер.
Возможная ветка присваивания, сравнение кэша с графом или просто выдача права
на запись dirty не создают. Грязные поля публикуются в прямом порядке полей
содержащей Structure; успешная запись очищает dirty только своего поля.
Чистые поля повторно не публикуются.

Потокобезопасность даётся тем же одним последовательным потоком: снимок
приостановленного вызывающего нельзя гонять, у других Messages арены не
пересекаются. Ни замка, ни барьера не нужно.

Upward funarg закрыт запретом неявного захвата кадра, а не хипификацией
активаций и не скрытыми цепочками замыканий.

1.2. §9.1.1 и §9.1.2: const и immutable — ДВЕ ОРТОГОНАЛЬНЫЕ ОСИ.

    const              фиксирует ПРИВЯЗКУ (ячейку, ссылку). Неглубокий,
                       за ссылку не дотягивается.
    immutable          фиксирует ЗНАЧЕНИЕ. Универсален: примитив, Structure
                       с деревом, Array с дескриптором и backing. Саму
                       ссылку не морозит.
    const: immutable:  обе оси. Единственный способ получить полную
                       заморозку внутри изменяемой Structure.

Ни один не является более глубокой версией другого. Пример с массивом в
§9.1.1 сделан трёхчастным именно чтобы это показать.

Подтверждено по всей спеке и не нарушается нигде: НИЧЕГО ДЛИННЕЕ ПРИМИТИВА
НЕ ПЕРЕДАЁТСЯ ПО ЗНАЧЕНИЮ. Обычный примитив — по семантическому значению,
Structure и Array — по ссылке-значению. Для immutable сохраняется
идентичность значения, включая примитивный случай (§9.1.2).

1.3. §21.8, блок "Const callables and direct invocation" и следом
"Other const occurrences".

const: fn:, const: sub:, const: fm: фиксируют callable-occurrence, что
позволяет звать C-символ напрямую, без прохода по дескриптору через узел.
Рядом описано, что даёт const на прочих occurrence.

1.4. §11.3.1: `@` — graph payload, declared parameter, hidden through.

Три случая, не смешивать. Канон — Lingvamyxa_spec.txt 11.3.1.

Own graph field: после классификации диапазона `@x` — адрес хранимого
typed payload. `int` был примером общего принципа, не единственным
типом. Не `&Lmx.data` и не C-cache. Array descriptor ≠ element backing;
method record ≠ C entry. `@` cache не открывает; dirty/writeback только
у own cache по §21.6.

Объявленный аргумент: обычный C parameter, `@x` = `&x`. Нет второй
скрытой копии и нет требования найти graph backing. Same-name own bind
сохраняет эту переменную, адрес и время жизни; добавляется связь с checkpoint.
L2 — язык низкого уровня, @ здесь обычное взятие адреса. В L3 оно запрещено.

@: char "hello": поле void * указывает в массив char *, а эти указатели —
прямо на C-строки. Дескриптора длины или Array в этой форме нет; String с длиной
был бы отдельной конструкцией.

Сквозная: обычный скрытый C parameter по §21.3. `@`/raw как в Си.
Изменение binding, в том числе через адрес, локально активации и не
меняет источник. Ссылочные значения: локальность binding не клонирует
referent и не запрещает явную мутацию адресата. Нет own dirty/writeback.

fn даёт имя обычной C-функции и параметры: собственный node, нужные
лексические входы, динамические входы, явные аргументы. Вложенный C-код не нужен.
Число полей Structure постоянно, void * ссылки можно менять; checkpoint
записывает dirty-значения с обычной обработкой изменения типа поля.

Fallback — caller-first, затем лексическая область через node и его предков
до нуля (§21.3). Неявный лексический поиск не запрещён; independent задаёт
нулевой корень. Отсутствие у caller само по себе не является ошибкой.

Исторический `tableKey` живёт только в Lingvamyxa_spec_history.txt:
навигация резолвера, не physical method/Array descriptor.


2. Механика, которую надо понимать перед оптимизацией
-----------------------------------------------------

2.1. Обычный runtime LMX НЕ ЗНАЕТ ИМЁН.

Транслятор разрешает имена полей в индексы массива указателей детей void *. Обычное
исполнение, own-поля, fallback node\field и выбор callable идут по адресам,
без перебора ShortNameId. Это исходный контракт, не будущая оптимизация.
L1-преобразование `p\field` в C `p->field` — другой уровень реализации;
оно не разрешает генерировать отдельный C-member по каждому имени L2-поля.

Таблица Lmx * -> ShortNameId ВСПОМОГАТЕЛЬНАЯ: для операций со строками
и диагностики. Её содержимое — адрес -> короткое имя
Structure из исходника. Строки могут не соответствовать дереву; имена могут
повторяться. Это не дескриптор или уникальный ID. Регистрация узлов,
согласование ID и разрешение коллизий не являются условием исполнения,
merge или копирования. Сигнатуры методов хранятся отдельно.
len структуры — только число детей. data указывает на массив указателей
детей void *. Тип каждого ребёнка определяется по адресу в указателе —
вхождению в массив соответствующего типа T. Адрес ячейки указателя для этого
не используется. Дети не являются записями Lmx; заголовок Lmx есть только
у ребёнка, являющегося структурой. Длина записи Array — отдельное поле.


2.2. Адреса стабильны, пулы растут добавлением блоков.

Служебный типизированный пул не релокирует живые записи. При росте он
получает новый блок в единственной arena Message и регистрирует отдельный
диапазон того же типа. Пул — на используемый тип, не просто на категорию
представления. Служебный пул дескрипторов не путать с backing массива языка.

Ни обратного списка всех держателей ссылки, ни прохода исправления указателей
для роста не нужно. При ресурсном отказе допустимо завершить Message,
освободить его arena и запустить новый; это не продолжение старой активации.
Explicit merge/copy создаёт новый результат, а не перемещает старый объект.


3. Рекомендации по реализации
-----------------------------

3.1. Девиртуализация и снятие чекпойнта — ДВЕ РАЗНЫЕ оптимизации с
РАЗНЫМИ предусловиями. Не сливать их в одно правило "const, значит можно
не думать": они отваливаются независимо.

  * девиртуализация требует статически известного пути выборки к одной
    occurrence (const-путь либо локально построенный callable, который не
    убегает). Тогда прямой addr;
  * снятие чекпойнта требует доказать, что у ВЫЗЫВАЮЩЕГО нет грязных
    own-полей через этот вызов. Это свойство вызывающего, а не
    вызываемого, и const на callable его не даёт.

3.2. Порядок по отдаче на горячем пути:

  1. доказать пустой чекпойнт (§21.12 разрешает "static dirty proofs") —
     основной выигрыш, иначе граф пишется на каждой итерации;
  2. заинлайнить внутренний хелпер — тогда границы нет вовсе. ОСТОРОЖНО:
     инлайн Lingvamyxa-метода не равен private helper из §21.6, у него
     своё own-состояние в своей Structure, граница снимается только
     "after proving identical visible effects";
  3. прямой addr и снятый резолв — приятно, но меньше первых двух.

3.3. Кэширование разрешённой occurrence НЕ ТРЕБУЕТ нового синтаксиса.
§21.11 уже гарантирует, что заменить occurrence может только явная
операция с определяющим её ресивером. Это анализируемое свойство:

    call site может закэшировать разрешённую occurrence (а с ней addr и
    invoking_structure), если между резолвом и использованием нет явной
    структурной операции над этим поддеревом и нет вызова, который мог бы
    её выполнить.

Ложится в уже разрешённые §21.12 "cached child positions". const остаётся
кувалдой для случаев, где анализ не проходит.

3.4. Чего const НЕ даёт, даже когда даёт прямой вызов:

  * invoking_structure не становится статическим просто потому, что
    зафиксирован data: runtime merge копирует используемое окружение тем же
    обходом, что Message, с явным перенаправлением node; compiled entry остаётся
    известным. Callable получает node аргументом. Все методы и их неизменяемые
    дескрипторы общие; при копировании node ссылки на эти дескрипторы сохраняются (§21.8);
  * dirty-only чекпойнт шага 5 остаётся;
  * скрытые динамические значения всё равно выбираются по sig, а
    fallback node\[0]name остаётся рантайм-чтением, если сам не const;
  * порядок вычисления всё равно материализуется явно (§21.8).

3.5. const: fn: в изменяемой Structure оставляет own-поля писучими. Не
тянуться к immutable на содержащее дерево ради прямого вызова: это
заодно заморозит рабочее состояние метода, и любое присваивание own-полю
станет нарушением (§9.1.2, §21.5).


4. Открытые пункты: дисциплина
------------------------------

Оставшиеся вопросы проверяются по текущим определениям и §21.13 спеки,

Решать их все заранее НЕ НАДО — они стадируются, большинство лежит вне

Но обязательно ЯВНО. Автономный агент, наткнувшись на открытый пункт, не

открытые пункты оно задевает и что с ними делать: либо решение уже
записано в спеку, либо инструкция "дойдёшь — остановись и спроси".

РЕШЁН пользователем 2026-09-12:
возвращаемый статус плюс типизированные выходные параметры результата и payload.

5. Форма и пять запретов
------------------------

Целевая архитектура: одна структура, два дескриптора, N служебных
массивов, "ресиверы" — обычные C-функции транслятора, переводящие дерево
P0 в Си.

Спека обводит эту форму забором. Проверяется по дифу механически,
перечитывать 13 тысяч строк не нужно:

  1. никаких пер-именных C-структур: ни typedef struct <Name>, ни
     генерируемого доступа к полям по имени;
  2. в заголовке Lmx только {node, len, data}; имена в заголовок не
     попадают, других пер-узловых метаданных builder не создаёт;
  3. никаких прикреплённых дескрипторов типа и namespace-записей;
  4. в Structure нет vtable и C-метода-члена;
  5. никаких скрытых инфраструктурных параметров, closure и
     capture-объектов.

Пятый самый уязвимый: обёртка всегда появляется под предлогом "иначе не
выразить". На нём поехала прошлая версия транслятора — структура была
верной, наросли обёртки, больше тысячи штук. Разбухание приходит не через
неверную архитектуру, а через машинерию вокруг верной, и накапливается
незаметно, потому что каждый отдельный шаг выглядит оправданным.

Ту же линейку применять к спеке: если реализация секции требует
машинерии, которой в §21 нет, — это сигнал, что либо секцию недопоняли,
либо в неё лезет то, чего там быть не должно.


6. Архитектурное решение: ПРИНЯТО
---------------------------------

РЕШЕНО: lm2 -> L1 -> Си.

Новый L2-транслятор по спеке транслирует СНАЧАЛА В L1, и только потом
транслятор L1 переводит это в Си. Прямая генерация Си из lm2 рассмотрена
и отклонена — не предлагать её заново. Шапка Lingvamyxa_spec.txt и
L1_language_and_translator_spec.txt §4 согласованы с этим маршрутом.

Что следует для планирования:

  * L1 становится ЦЕЛЕВЫМ ЯЗЫКОМ для lm2, а не только языком реализации.
    Значит семантика §21 — dirty-only чекпойнты, own-поля как
    типизированные рабочие локали, sig-типизированные вызовы, скрытые
    динамические значения — должна быть ВЫРАЗИМА в L1. Либо L1 дорастает
    до нужных конструкций, либо lm2-транслятор кодирует их явно через то,
    что уже есть (структуры, массивы, обычные вызовы). Это разные объёмы
    работ и разные риски по разбуханию L1; выбрать лучше ДО первой
    единицы работ;
  * зато вся генерация Си идёт через слой со сходящейся самосборкой, то
    есть покрыта фикспойнтом с первого дня;
  * промежуточное представление читаемо — это LMX-синтаксис, а не
    внутреннее дерево. Отлаживать lm2-генерацию можно по выданному L1,
    не спускаясь в Си.

Лестница бутстрапа: L2-транслятор сначала пишется на L1, потом на себе
самом. Конечная цель — перенести ВСЕ исходники ядра и инструментов на L2,
включая реализацию самого L1-транслятора, и самособирать чистый L2.
Цепочка остаётся L2 → L1 → C: L1 — промежуточный язык этой цепочки и
язык тестов, не постоянный язык ядра/инструментов. Даже исходники
L1-транслятора в итоге переписываются на L2.

Перед продвижением расширенного L1 в сборочную базу L2 нужно проверить
его собственную самосборку: published-C bootstrap, next, check, тесты и
finalize. Продвигается проверенный комплект исходников, генерируемого C
и сборочных средств; изменения живого L2 при этом сохраняются.


7. Смежное: L1 — это не наша спека
----------------------------------

l1src сделан, делает полноценную самосборку и сейчас лишь расширяется
отдельно. По его семантике пишется СВОЯ спека. Это не L2 и не
Lingvamyxa_spec.txt.

Для работы над L2 из этого следует ровно одно, зато важное: РЕШЕНИЯ L1 НЕ
ПЕРЕНОСЯТСЯ НАВЕРХ ПО АНАЛОГИИ. L1 намеренно прост и вправе выбирать
простое; §21 требует другого. Живой пример: throw в L1 несут два
статических глобала — для L1 это нормально, для lm2 не годится вовсе, там
у каждого Message своя арена и Messages могут исполняться одновременно
(§21.7), а контракт payload обязан входить в точную сигнатуру метода
(§21.13 п.4).

Проверяя реализацию L2, всякий раз спрашивать: это следует из §21 или это
привычка, приехавшая снизу?

Общее для L1 и L2 ограничение: Valued-агрегаты и обычный доступ к члену
через точку НЕ используются. Обход идёт по адресам через `\`; в L1
`p\field` прямо даёт C `p->field`, а не выбор между `.` и `->` по типу.
Примитивы по значению этим не запрещаются.

Служебные C-исключения — отдельная дверь, не обычный путь языка:
`c.value.field` даёт явную C-проекцию. Ресивер `C:` оставлен для крайнего
низкоуровневого случая; текущий L1 self-host/bootstrap-профиль его отвергает.
Это не разрешение переносить C-исключения в обычный L1/L2-код.

Важно не спутать одинаково названные ресиверы двух трансляторов. Прямое
L1-преобразование `p\field` в C-член `p->field` НЕ задаёт алгоритм разрешения
L2-пути в Lmx-графе. Файлы l2src/*.lm1 — реализация L2 на языке L1, а не
доказательство того, как уже сгенерированный L2-код будет искать поле.

Текущая карта сборок и поддержанного синтаксиса — L1_spec.txt. Живой L1
находится в l1src, его замороженная копия — в stg/l1_baseline/l1src;
живое ядро L2 на L1 — в stg/l1_baseline/l2src. Корневая и staged-сборки
раздельны: успех одной не означает проверку другой.
