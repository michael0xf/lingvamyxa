# implements(A, B, C) — исходное сообщение и план

This file quotes the original design note and the work plan derived from it.
It is not a specification. Spec changes belong in Lingvamyxa_spec.txt.


## 1. Исходное сообщение

Изучи такую идею. А что если "тип" это просто тот факт, что некая структура A
подходит на роль другой некой структуры B, используемой в некой третьей
структуре C. "используемой" означает что по всей глубине структуры C есть
упоминания структуры B _и каких-то отдельных ветвей структуры B_. У нас же в
языке всё -- структуры или примитивы. Примитивы мы "закрыли" легко просто
таблицей соотношений или в более общем случае -- валидаторами диапазонов (тоже
прелагаю сделать, как вроде в Паскале было где-то), а типизацию структуры,
метод implements, сделать с тремя аргументами. Тогда это будет даже
облегченней, точней и глубже поиска по полям верхнего уровня -- это будет
полноценный поиск по деревьям структур C и B, вовсе без привязки к сравнению
полей верхнего уровня A и B. Потому что типизация фактически и существует для
того чтобы употребить A вместо B. Если нам нужно будет после работы с A
использовать его где-то где использовался B в каком-то втором местах D1..DN,
то мы можем заранее сделать N implements так как дерево кода нам заранее
известно, а всё что выходит за его пределы это уже границы LMX message.


## 2. План

# План: типизация по спеке — употребление, не иерархия типов

## Смысл (идея, которую принимаем)

**Тип — не сущность.** Тип — факт: структура `A` годится на роль структуры `B` **там, где `B` употребляется в структуре `C`**.

«Употребляется» = по всей глубине `C` есть упоминания `B` и **конкретных ветвей** `B` (пути имён). Сравнивать целиком верхний уровень `A` и `B` не нужно: нужны только те ветви `B`, которые `C` реально трогает.

Всё — Structure или Primitive.

- Примитивы: таблица категорий (`class.category` / `class.semantic`) как широкий вход; уже — **валидаторы диапазонов** (в духе Pascal `1..10`), не новые kind.
- Структуры: `implements` только с **тремя** аргументами — поиск по деревьям `C` и `B`, не «все first-level имена B ⊂ A».

Зачем типизация: **употребить A вместо B**. Если A потом пойдёт в места `D1..DN`, где раньше был B, код-дерево известно заранее → N проверок `implements(A, B, Di)`. Всё, что вне этого дерева — **граница LMX Message** (там свой C или явный набор употреблённых путей).

Это тоньше старого first-level сита на жирном наборе (не требуем неиспользуемых полей) и глубже (вложенные ветви, которые C трогает). Худой C → почти Python. Жирный C → жирный набор путей, случайно не совпадёт.

Дерево проверки — дерево употребления C, не полное дерево B. По упомянутой ветке идём до упора. Лист этого дерева:

- примитив → категория + диапазон;
- структура, внутрь которой C больше не лезет → только наличие имени у A (пустая структура — частный случай: наличие и есть вся сверка);
- C передаёт B целиком, без проекции полей → путь ε, смотреть нечего; поля достанет уже `D1..DN` или Message.

Промежуточные узлы — только совпадение имён вдоль пути. Это строгая сверка использованного поддерева, не «A есть полный B».

Факт считается, synthetic type не плодится. `implements(A, B, C1)` не влечёт `implements(A, B, C2)`. Множество путей `uses(C, B)` — временное сито, не новый тип в пространстве имён.

### Двухаргументный `implements(A, B)` выкинут из языка

Как конструкция языка и как неявный приёмник его нет. Без C некого употребления.

| Форма | Значение |
|---|---|
| `implements(A, B, C)` | A закрывает **пути B, упомянутые в C** — это и есть тип, единственная форма |
| rebind / аргумент / return | trans/интерпретатор сам подставляет C (остаток известного дерева, тело callee, потребители return). Это не исходник |
| нет C (чужой Message) | не угадываем: валидатор/envelope несёт употреблённые пути или потребитель |

Старый алгоритм «все first-level имена B ⊂ A» может ещё жить внутри hosted trans как миграционный зазор (§21.7 спеки), пока не подключён `uses(C, B)`. Это не приёмник и не пишется как `implements(A, B)`.

Rebind `i: newValue`: `implements(new, old, C)` с C = остаток известного тела, который ещё видит имя. A = new, B = old.

## Вне скоупа

MIX-порт, `query()`, `validate`/`execute` Message целиком, планета, рекурсивное сравнение *всех* полей A и B, иерархия классов, SQL.

Validator/Merge на границе Message — следующий замах; этот план только готовит **форму сита**, которую Merge потом ест.

## Этап 0 — спека: уточнить, не глава

В §2.1 и §19.21.3 короткий канон (уже в Lingvamyxa_spec.txt):

1. Тип = употребляемость A как B в C.
2. Собрать из C множество путей по B (`B`, `B.foo`, `B.foo.bar`, …).
3. A годится ⇔ каждый такой путь есть у A (имена вдоль пути).
4. Примитив на листе пути: категория из `class.category`; диапазон — валидатор (таблица/`class.range` или явный `min`/`max`), не новый primitive kind.
5. Двухаргументной формы нет. C либо в исходнике, либо его подставляет trans/интерпретатор; иначе граница Message.
6. По-прежнему не смотрим значения, ABI, layout, multiplicity. Не `validate` как hook.

Существующие абзацы «не рекурсируем вложенность B целиком» остаются верными: рекурсия **по употреблению в C**, не по всему B.

## Этап 1 — примитивы (как раньше, плюс диапазон)

Таблица `class.category` в `lm2/trans_registry.lm2` сейчас 9 строк. Добить все примитивы из `class` / `class.semantic`.

API: `lm_trans_class_in_category(name, numeric|integer|…)`.

Убрать список в `lm_trans_registry_descriptor_payload_is_numeric`.

Диапазоны (Pascal-like), минимально:

- не новый синтаксис типа в ядре, если можно строкой/`class.range` / маленьким валидатором «атом в [lo, hi]»;
- общий numeric-алгоритм диапазон не смотрит; валидатор колонки/поля — смотрит.

Тест predef: счётчик строк `class.category` больше не зашит как 9.

## Этап 2 — сбор употребления: пути B в C

Новая маленькая функция trans (имена к стилю `lm_trans_*`):

Вход: P0-дерево `C`, имя/дескриптор `B`.
Выход: множество путей (список атомов имён), которые C читает у B.

C — не интерфейс и не описание типа. Это код или данные, тело вроде generic-класса. `uses(C, B)` обходит это тело и собирает синтаксические пути.

Операционально «упоминание» на первом шаге, без магии:

- field-follow / `\`, компактный доступ к полям, чей корень резолвится в B;
- приёмник, чей аргумент ожидается как B, и дальше вложенный доступ в том же C;
- не считать упоминанием одно только объявление типа B.

Худой C → короткий список путей. Жирный → длинный. Это и есть сито.

Тесты на синтетических `.lm2`: C трогает только `p.a` у B — в множестве один путь `p.a`, нет `x`.

## Этап 3 — `implements(A, B, C)` в trans

Алгоритм:

1. Resolve A, B; C — дерево или имя блока/функции, чьё тело ходим.
2. `paths = uses(C, B)`.
3. Для каждого пути: спуститься по дескриптору A теми же именами. Нет имени → `false`.
4. Лист пути примитив: категория A совместима с категорией листа B (таблица), не strcmp.
5. Пустой набор путей (C не трогает B) → `true` (употреблять нечего).

Неявный rebind/аргумент/return: trans сам подставляет C. Явного двухаргументного приёмника в исходнике нет.

Не ломать существующие тесты `implements` одним махом: сначала 3-arg рядом, потом убрать 2-arg из hosted trans.

Диагностика: `trans: A does not provide B path p.q as used in C`.

## Этап 4 — граница Message

Не реализовать весь validate. Зафиксировать в спеке/статусе:

- внутри модуля C известен → этап 3;
- наружу — Message несёт expression (уже LMX) и/или явный список употреблённых путей; чужой A проверяется против **этого** C, не против «всего B».

Код: достаточно не слать «полный B» как тип через границу. Столб-заглушка лучше, чем случайно оставить 2-arg как единственную правду.

## Этап 5 — критерий готово

- нет хардкод-списка numeric имён;
- `class.category` покрывает примитивы `class.semantic`;
- есть сбор путей `uses(C,B)` и `implements(A,B,C)` с тестами на худой/жирный C;
- двухаргументного приёмника в языке нет; hosted 2-arg first-level — только помеченный fallback внутри trans;
- спека §2.1 / §19.21.3 — тройка, без новой «системы типов»;
- официальный self-build + `--tests core`.

## Порядок коммитов

1. Категории + замена numeric (этап 1) — уже польза, мало риска.
2. Спека уже на тройке (этап 0).
3. `uses(C,B)` + тесты (этап 2).
4. Трёхаргументный `implements` в trans (этап 3).
5. Пометить границу Message (этап 4), не писать Merge.

Каждый шаг: `lm2` → официальный `buildCore` → `--tests core`. Не `LM_THREAD_PROVIDER=win32` на официальном ядре.

## Риск

Раздувается не C в тип, а сборщик упоминаний в интерпретатор. C остаётся кодом/данными.

Держать **синтаксические пути имён** в P0 (как field-follow), не абстрактную интерпретацию.

| Что видит сборщик | Синтаксис (надо) | Dataflow (не надо) |
|---|---|---|
| `y: x`, а `x` это B, потом `y\foo` | путь на `y`, не на B | алиасы: y ≡ B, значит `B.foo` |
| `f(B)`, а внутри `f` есть `p\a` | в этом C путь пустой / `B` целиком | полезть в каждый callee |
| `B.(idx)`, `idx` считается | путь не виден | вычислить idx |
| `if c { B\a } else { B\b }` | оба пути | path-sensitive, один из |
| положили B в список, позже `list[0]\foo` | в C нет `B\foo` | heap / reaching defs |

Если путь не виден синтаксически — это худой Python на потреблении или Message (там свой C), не новый анализатор.
