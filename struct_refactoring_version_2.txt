0. Status and purpose
Статус и назначение
====================

EN

This document records the agreed target architecture for the next
Lingvamyxa translator core and runtime Structure representation. It is a
rewrite contract, not a description of the current implementation.

The parser remains. The translator core after the parser is rewritten.
Compatibility with an accidental C-shaped representation in the current
translator is not a goal. Source semantics are primary; emitted C is a
secondary implementation.

The words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT and
MAY have their usual normative meanings. A section explicitly labelled
UNRESOLVED records a decision that has not yet been made. An unresolved
implementation detail must not be silently answered by restoring runtime
descriptors, per-Structure C types, a separate runtime Name-to-Binding
namespace object, or any other
mechanism prohibited by this document.

RU

Этот документ фиксирует согласованную целевую архитектуру нового ядра
транслятора Lingvamyxa и runtime-представления Structure. Это контракт на
переписывание, а не описание текущей реализации.

Parser сохраняется. Ядро транслятора после parser-а переписывается.
Совместимость со случайно получившимся C-подобным представлением текущего
транслятора не является целью. Семантика исходного языка первична; выдаваемый
C является вторичной реализацией.

Слова MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT и MAY
используются в обычном нормативном смысле. Раздел с явной пометкой
UNRESOLVED фиксирует ещё не принятое решение. Неразрешённую техническую
деталь нельзя молча решать возвратом runtime-дескрипторов, отдельных C-типов
для Structure, отдельного runtime-объекта namespace Name-to-Binding или
другого механизма, запрещённого этим
документом.


0.1. One-sentence contract
Задание одной фразой
--------------------

EN

Keep the existing parser, replace the translator core, represent every
runtime source node by the same three-word Lmx header, keep names outside the
nodes in the sole Lmx-pointer-to-ShortNameId auxiliary table, compile every
method to one program-wide reachable uniquely identified C entry recorded in
`all_methods_array` together with its exact signature, pass the reserved
callable-parent `node` plus the signature's declared and hidden dynamic-caller
arguments, execute used method fields through C working locals with
dirty-only publication before calls and exits, resolve arbitrary textual
absolute paths from an explicit root, and execute merge dynamically by copying
trees when program execution reaches the merge; every Message owns one logical
arena, and every running L3 Thread consumes its FIFO message stream one turn at
a time while different Messages may execute concurrently.

RU

Сохранить существующий parser, заменить ядро транслятора, представлять каждый
runtime-узел исходника одним и тем же трёхсловным заголовком Lmx, держать
имена вне узлов в единственной вспомогательной таблице
Lmx-указатель-в-ShortNameId, компилировать каждый метод в один достижимый во
всей программе уникально идентифицированный C-entry, записанный в
`all_methods_array` вместе с его точной сигнатурой, передавать
зарезервированный `node`-родитель callable вместе с явными и
скрытыми dynamic-caller аргументами сигнатуры, исполнять используемые
поля метода через рабочие C-locals с публикацией только dirty-значений
перед вызовами и выходами,
разрешать произвольные текстовые абсолютные пути от явно переданного корня и
выполнять merge динамически,
копированием деревьев в тот момент, когда исполнение программы дошло до
merge; каждый Message владеет одной логической arena, а каждый исполняемый L3
Thread потребляет свой FIFO-поток сообщений последовательно, по одному turn,
тогда как разные Messages могут исполняться параллельно.


0.2. Mandated core versus open details
Обязательное ядро и открытые детали
-----------------------------------

EN

The following are already decided and are not design options:

1. The parser stays.
2. The translator core is rewritten rather than incrementally adapting the
   existing typed-C projection.
3. Lmx has exactly the common header specified in section 3.
4. A node contains no name, descriptor, type tag, vtable or per-Structure
   layout pointer.
5. No named Structure causes a C typedef or a dedicated C struct layout.
6. A method loads only its own fields actually used through unqualified own
   bindings into C working locals. These locals are the activation's working
   values; the selected callable occurrence's containing Structure
   (`callable->node`) is their published checkpoint, not an activation log.
7. A generated C method receives the reserved `node` value
   `callable->node`, its declared call arguments, and the exact hidden
   dynamic-caller values required by its generated signature.
8. Every generated method has program-wide reachable identity and a unique
   deterministic name; a long name mangled from its complete source path is
   the preferred spelling.
9. Every callable resolves to an immutable `all_methods_array` record
   conceptually containing `{ addr, sig }`. `addr` is the program-wide method
   entry and `sig` is the exact ABI contract which must equal the canonical
   signature expected by every call site that selects it.
10. Merge is a runtime tree-copying operation. Translation never flattens a
    merge into a target C struct.
11. The sole auxiliary node metadata table maps Lmx pointers to ShortNameId.
12. Arbitrary textual absolute runtime path resolution starts at an explicitly
    supplied runtime root and uses
    that table.
13. Dynamic caller visibility is source semantics. It is lowered to hidden C
    arguments and native C activation records, not to a separately allocated
    runtime Name-to-Binding namespace, overlay, capture object or pop stack.
14. Every Message owns exactly one logical arena. Launching that Message as an
    L3 Thread preserves the same arena; the arena belongs to the Message, not
    to whichever host worker happens to execute a turn.
15. All mutable/dynamic source-semantic Lmx nodes and payload storage created
    for a Message, including Structures, published method fields, non-interned
    primitives and ordinary Arrays, belong to that Message arena. C working
    locals belong to native activations rather than the graph. Immutable
    program-wide pools such as `all_chars` and compiled method records/code may
    be shared.
16. Every L3 Thread executes at most one of its turns at a time. Its admitted
    messages and staged outgoing messages are ordered FIFO. Distinct L3 Threads
    may execute concurrently and may migrate among host workers.
17. Mutable Lmx storage is not shared by raw pointer between concurrently
    executing Message arenas. Cross-Message interaction uses explicit Message
    delivery/adoption/serialization rules.
18. Common L3 and Mix concurrency is Message concurrency. Raw threads, shared
    memory, atomics, mutexes and custom synchronization may exist only in an
    explicit L2 profile and do not supply a portable common-LMX algorithm.
19. A Message turn publishes its successful staged FIFO outbox, or rolls it
    back on failure, before local collection of that Message arena. Collection
    runs at the common end-turn boundary; terminating the Message ultimately
    releases its arena after required transfer/cleanup.
20. A through variable (an unqualified use not owned by the method) is copied
    into a private C working local on entry. Primitive values are passed by
    semantic value; Structure and Array reference values are copied as
    references. Rebinding either working local is local to that activation.
21. If the caller has no through binding required by the callee, the value
    falls back to the immediate `node\name` of the selected callable. `node`
    is reserved and cannot be declared, rebound or supplied by caller scope.
22. Apart from the selected method's own dirty-field checkpoint, only an
    explicit graph path such as `node\name` or `ref\name` mutates graph state
    outside that method's private activation. Through working values are never
    written back automatically.
23. An actual write to an own C local marks its runtime dirty flag. Before every
    outbound LMX call, every external/re-entrant/publishing runtime or foreign
    boundary that exposes or controls graph state outside the current activation,
    every `yield` suspension and every activation exit, only dirty own fields
    are stored into `callable->node`; each flag is cleared after its store
    succeeds. A private non-escaping helper used only for the current activation's
    own traversal, classification or explicit graph operation is not a boundary,
    even if it reads or writes the graph and is emitted as C. No reload occurs
    after a call.
24. The C call stack is the sole implicit activation history. Recursive and
    mutually recursive calls intentionally overwrite the published working
    state of method Structures; persistent or branching history requires an
    explicit Structure, Array or Message.
25. `yield` preserves the ordinary stack/continuation state, including working
    locals and dirty state. `retry` is a local control operation, not a call,
    and does not by itself trigger the pre-call checkpoint.

Only the details explicitly identified as unresolved in section 14 remain
open. They may choose among implementations only inside these fixed boundaries.

RU

Следующее уже решено и не является набором вариантов:

1. Parser сохраняется.
2. Ядро транслятора переписывается, а не приспосабливает постепенно
   существующую типизированную C-проекцию.
3. Lmx имеет ровно общий заголовок из раздела 3.
4. В узле нет имени, дескриптора, тега типа, vtable или указателя на layout
   конкретной Structure.
5. Именованная Structure не порождает typedef или отдельный layout struct в
   C.
6. Метод загружает в рабочие C-locals только собственные поля, которые реально
   использует через неквалифицированные own-bindings. Эти locals — рабочие
   значения activation; containing Structure выбранного callable-occurrence
   (`callable->node`) — их опубликованный checkpoint, а не журнал активаций.
7. Сгенерированный C-метод получает зарезервированное значение
   `node`, равное `callable->node`, явные аргументы вызова и точный набор
   скрытых dynamic-caller значений из generated-сигнатуры.
8. Каждый сгенерированный метод имеет достижимую во всей программе identity и
   уникальное детерминированное имя; предпочтительный spelling — длинное имя,
   полученное из полного пути исходника.
9. Каждый callable разрешается в immutable-запись `all_methods_array`,
   концептуально содержащую `{ addr, sig }`. `addr` — вход метода, а `sig` —
   точный ABI-контракт, который обязан быть равен канонической сигнатуре,
   ожидаемой каждым выбирающим этот callable call site.
10. Merge является runtime-операцией копирования дерева. Трансляция никогда
    не превращает merge заранее в целевой C struct.
11. Единственная вспомогательная таблица метаданных узлов отображает
    Lmx-указатель в ShortNameId.
12. Разрешение произвольного текстового абсолютного runtime-пути начинается
    от явно переданного runtime-корня и использует эту таблицу.
13. Dynamic-видимость вызывающего является семантикой исходника. Она
    снижается в скрытые C-аргументы и нативные C activation records,
    а не в отдельно выделенный runtime namespace Name-to-Binding,
    overlay, capture-object или pop-stack.
14. Каждый Message владеет ровно одной логической arena. При запуске Message
    как L3 Thread сохраняется та же arena; она принадлежит Message, а не host
    worker, на котором случайно исполняется конкретный turn.
15. Все изменяемые/dynamic Lmx-узлы и payload исходной семантики, создаваемые
    для Message, включая Structures, опубликованные поля методов, не-interned
    примитивы и обычные Arrays, принадлежат arena этого Message. Рабочие C
    locals принадлежат нативным активациям, а не графу. Неизменяемые глобальные
    пулы наподобие `all_chars`, а также записи/код скомпилированных методов
    могут использоваться совместно.
16. Каждый L3 Thread исполняет не более одного своего turn одновременно. Его
    принятые сообщения и подготовленные исходящие сообщения упорядочены FIFO.
    Разные L3 Threads могут исполняться параллельно и мигрировать между host
    workers.
17. Изменяемое Lmx-хранилище не разделяется сырым указателем между arena
    одновременно исполняемых Messages. Cross-Message взаимодействие использует
    явные правила доставки/adoption/serialization сообщений.
18. Конкурентность общего L3 и Mix является Message-конкурентностью. Raw
    threads, shared memory, atomics, mutexes и custom synchronization допустимы
    только в явном L2-профиле и не образуют переносимого общего алгоритма LMX.
19. Turn Message публикует успешно подготовленный FIFO outbox либо откатывает
    его при failure до локальной collection arena этого Message. Collection
    выполняется на общей границе end-turn; termination Message в итоге
    освобождает его arena после требуемого transfer/cleanup.
20. «Сквозная» переменная (неквалифицированное имя, не принадлежащее
    методу) копируется при входе в private-рабочий C-local.
    Примитив передаётся по семантическому значению; значение ссылки
    Structure/Array копируется как ссылка. Rebind любого такого
    рабочего local остаётся в текущей activation.
21. Если у caller нет требуемого callee сквозного binding, значение
    берётся из непосредственного `node\name` выбранного callable. `node`
    зарезервировано: его нельзя объявить, rebind-ить или передать из
    namespace caller-а.
22. Кроме dirty-checkpoint собственных полей выбранного метода, только явный
    путь графа, например `node\name` или `ref\name`, изменяет graph-state вне
    private activation этого метода. Сквозные рабочие значения никогда не
    записываются обратно автоматически.
23. Фактическая запись в own C-local ставит его runtime dirty flag. Перед каждым
    исходящим LMX-call, каждой external/re-entrant/publishing runtime или foreign
    границей, выносящей graph-state за пределы текущей activation,
    каждой suspension `yield` и каждым выходом activation в `callable->node`
    записываются только dirty own fields; флаг очищается после успешной записи.
    Private non-escaping helper, выполняющий только traversal, classification или
    explicit graph operation текущей activation, не становится границей, даже
    если читает/пишет граф и эмитится как C. Reload после call не делается.
24. Стек C-вызовов — единственная неявная история активаций.
    Recursive и mutually recursive вызовы намеренно перезаписывают
    опубликованное рабочее состояние Structures методов; для живущей
    дольше return или ветвящейся истории нужны явные Structure, Array или
    Message.
25. `yield` сохраняет обычное состояние stack/continuation, включая рабочие
    locals и dirty-state. `retry` — локальная control-операция, а не call, и сама
    по себе не запускает pre-call checkpoint.

Открыты только детали, явно названные неразрешёнными в разделе 14. Их можно
выбирать лишь внутри этих уже зафиксированных границ.


1. Ontology and terminology
Онтология и термины
==========================

1.1. Structure, tree and graph
Structure, дерево и граф
------------------------------

EN

A Structure is not an object, class instance, target-language aggregate or
method table. It is a source-semantic structure represented at runtime by Lmx
nodes.

The source containment relation is a tree. Every non-root Lmx node has one
source parent, recorded by node. Following node repeatedly therefore reaches
one root and must never form a cycle.

References stored as data may point to nodes outside the containment
subtree. Together with those reference edges, the complete runtime memory may
be a graph and may expose many paths to the same node. Those extra graph edges
do not change the node parent relation.

The word object MUST NOT be used to justify object identity rules, method
dispatch tables, inheritance, hidden receiver objects or per-instance
namespaces. The implementation deals with Structures and references.

RU

Structure не является объектом, экземпляром класса, агрегатом целевого языка
или таблицей методов. Это структура семантики исходного языка, представленная
в runtime узлами Lmx.

Отношение вложенности исходника является деревом. У каждого Lmx-узла, кроме
корня, есть ровно один исходный родитель, записанный в node. Поэтому
последовательный переход по node обязан приводить к одному корню и никогда не
может образовывать цикл.

Ссылки, лежащие в data, могут указывать на узлы вне поддерева вложенности.
Вместе с такими рёбрами ссылок вся runtime-память может быть графом и давать
много путей к одному узлу. Эти дополнительные рёбра графа не меняют
родительское отношение node.

Слово object нельзя использовать для обоснования объектной identity,
таблиц dispatch, наследования, скрытых receiver-объектов или namespace у
каждого instance. Реализация работает со Structure и ссылками.


1.2. Root
Корень
-----------

EN

A live execution graph has a root Lmx node. Starting from any node in its
containment tree, root is obtained by following node until the parent is
absent. Arbitrary textual absolute runtime path lookup begins at an explicitly
supplied root, never at a mutable runtime namespace. Direct resolved pointers
and relative paths keep their own starting node.

The exact representation of the absent parent is an ABI detail to be fixed;
the normal candidate is a null node pointer. Whatever representation is
selected must be unique and must make root discovery deterministic.

RU

У живого графа исполнения есть корневой узел Lmx. Из любого узла его дерева
вложенности корень получается последовательным переходом по node до
отсутствующего родителя. Поиск произвольного текстового абсолютного
runtime-пути начинается с явно переданного корня, а не с изменяемого runtime
namespace. Уже разрешённые указатели и относительные пути сохраняют собственный
начальный узел.

Точное представление отсутствующего родителя является деталью ABI, которую
ещё нужно закрепить; обычный кандидат — null в node. Выбранное представление
обязано быть единственным и делать нахождение корня детерминированным.


1.3. Physical class versus source meaning
Физический класс и смысл исходника
---------------------------------------

EN

The address range containing data tells the runtime how that payload is
physically handled. This is not static analysis of a named Structure and does
not create a closed language-level class hierarchy.

For example, an address inside all_chars identifies character storage. An
address inside a registered callable range identifies executable method
storage or a callable record. An address inside an Lmx-node allocation range identifies Lmx
storage. Empty data has its selected empty representation.

The runtime may use different ranges for other primitive stores, arrays or
opaque cells. Range boundaries are substrate facts. They are not descriptors
attached to each node.

RU

Диапазон адресов, в который попадает data, говорит runtime, как физически
обращаться с этим payload. Это не статический анализ именованной Structure и
не создание закрытой иерархии классов языка.

Например, адрес внутри all_chars обозначает хранилище символов. Адрес внутри
общей секции методов обозначает исполняемый метод. Адрес внутри диапазона
выделения Lmx-узлов обозначает хранилище Lmx. Для пустого data используется
выбранное представление пустоты.

Runtime может иметь иные диапазоны для других примитивных хранилищ, массивов
или opaque-ячеек. Границы диапазонов являются фактами субстрата, а не
дескрипторами, прикреплёнными к каждому узлу.


1.4. Short name
Короткое имя
----------------

EN

ShortNameId is the compact identity of one path component, not a descriptor,
type, namespace binding or full path. The Lmx node does not contain this ID.
The sole auxiliary node metadata table associates the address of an Lmx node
with its ShortNameId.

A full path is a sequence of short-name components plus any explicitly
defined occurrence selectors. A full path is not cached as mandatory metadata
on every node.

RU

ShortNameId — компактная идентичность одного компонента пути, а не
дескриптор, тип, binding namespace или полный путь. Узел Lmx не содержит этот
ID. Единственная вспомогательная таблица метаданных узла связывает адрес
Lmx-узла с его ShortNameId.

Полный путь является последовательностью компонентов коротких имён плюс явно
определённые селекторы occurrence. Полный путь не кэшируется как обязательные
метаданные каждого узла.


1.5. Mix and Message ontology
Онтология Mix и Message
-------------------------

EN

Mix belongs to the same Message/Lmx graph ontology described by this document.
Its placement edges, value edges, cursors, marks, locks, mirrors and messages may
play different operational roles while remaining parts of one Message/Lmx graph
universe. The target Mix architecture is a Message-based graph.

The current Java Mix implementation is a transitional procedural,
multithreaded implementation in a different concurrency paradigm. It is
implementation evidence only and requires a complete Message-style refactoring.
Its current worker, cursor and notification mechanics do not change the target
ontology and are not an excuse to add a runtime namespace, attached descriptor
or per-Structure C layout.

The one-arena-per-Message ownership rule, FIFO order and single-turn-at-a-time
execution of one L3 Thread are part of the common L3 semantics, not optional
backend profiles. What remains selectable is the number and kind of host
workers, physical arena block strategy, collection algorithm and concrete
transport. Mix therefore cannot standardize the Java implementation's locks
and independently multithreaded cursor algorithms as common LMX semantics;
those operations must be refactored into Messages and transport-independent
Message protocols. HTTP and physical mail are merely different transports for
the same semantic boundary.

RU

Mix принадлежит той же Message/Lmx-онтологии графа, которая описана этим
документом. Рёбра размещения и значения, курсоры, метки, локи, зеркала и
сообщения могут играть разные операционные роли внутри одной Message/Lmx-
вселенной графа. Целевая архитектура Mix является Message-based графом.

Текущая Java-реализация Mix — переходная процедурная многопоточная реализация в
другой парадигме конкурентности. Она служит только свидетельством текущего
кода и требует полного рефакторинга в Message-style. Её нынешние workers,
курсоры и notifications не меняют целевую онтологию и не разрешают добавлять
runtime namespace, attached descriptor или per-Structure C layout.

Правило одной arena на Message, FIFO-порядок и исполнение не более одного turn
одного L3 Thread одновременно входят в общую семантику L3, а не являются
необязательным backend-профилем. Выбираемыми остаются количество и вид host
workers, физическая стратегия блоков arena, алгоритм collection и конкретный
транспорт. Поэтому Mix не может перенести локи и независимо многопоточные
алгоритмы курсоров Java-реализации в общую семантику LMX: операции должны быть
перестроены в Messages и transport-independent Message-протоколы. HTTP и
физическая почта являются лишь разными транспортами одной семантической
границы.


2. Preserved parser and replaced translator core
Сохраняемый parser и заменяемое ядро транслятора
================================================

2.1. Parser boundary
Граница parser-а
---------------------

EN

The current parser remains the source-front-end boundary. Its job is to
recognize source syntax and produce the source tree with source positions,
ordering, nesting and spelling required by later stages.

The parser is not responsible for:

* creating runtime descriptors;
* selecting C struct layouts;
* expanding merge;
* deciding C field offsets;
* creating a runtime namespace;
* flattening nested methods into descriptor fields;
* deciding which source Structures are C types.

Small parser corrections are outside this architecture rewrite unless an
independent parser defect is demonstrated. The rewrite begins after the
parser's tree.

RU

Текущий parser остаётся границей входного front-end. Его задача — распознать
синтаксис исходника и выдать дерево исходника с позициями, порядком,
вложенностью и spelling, необходимыми следующим стадиям.

Parser не отвечает за:

* создание runtime-дескрипторов;
* выбор layout C struct;
* раскрытие merge;
* вычисление смещений C-полей;
* создание runtime namespace;
* превращение вложенных методов в поля дескриптора;
* решение, какие Structure исходника являются C-типами.

Мелкие исправления parser-а не входят в эту архитектурную переделку, пока не
показан независимый дефект parser-а. Переписывание начинается после дерева,
выданного parser-ом.


2.2. Rewrite boundary
Граница переписывания
--------------------------

EN

The old translator core MUST NOT be treated as the architecture and patched
until its generated C superficially resembles Lingvamyxa. Its assumptions
about per-name C types, descriptors, typed members, top-level-only callable
emission, lexical capture structs or compile-time merge are not the base of
version 2.

The new core consumes the parser tree and emits:

1. runtime construction operations for Lmx trees;
2. runtime lookup operations based on root and ShortNameId;
3. runtime merge calls at the original execution sites;
4. one global C implementation symbol for every executable source method,
   including methods nested in named Structures;
5. registration/construction operations that associate every live named node
   with its ShortNameId;
6. calls whose exact ABI is taken from the selected method's
   `all_methods_array` signature, including reserved `node` and hidden
   dynamic-caller values;
7. C working locals and runtime dirty flags that implement method working state
   and publish only dirty own fields at required call/exit checkpoints.

Existing code may be consulted as an inventory of syntax and tests. Reusing a
helper is allowed only when its semantics and representation already satisfy
this document. Existing generated-C snapshots are not proof of semantic
conformance.

RU

Старое ядро транслятора нельзя считать архитектурой и латать до тех пор, пока
его C-вывод внешне не станет похож на Lingvamyxa. Его предположения об
отдельных C-типах на каждое имя, дескрипторах, типизированных members,
эмиссии callable только верхнего уровня, C-структурах lexical capture или
compile-time merge не являются основой версии 2.

Новое ядро принимает дерево parser-а и выдаёт:

1. runtime-операции построения деревьев Lmx;
2. runtime-поиск на основе корня и ShortNameId;
3. runtime-вызовы merge в исходных местах исполнения;
4. один глобальный C-символ реализации для каждого исполняемого метода
   исходника, включая методы внутри именованных Structure;
5. операции регистрации/построения, связывающие каждый живой именованный
   узел с его ShortNameId;
6. вызовы, точный ABI которых берётся из сигнатуры выбранного метода в
   `all_methods_array`, включая зарезервированный `node` и скрытые
   dynamic-caller значения;
7. рабочие C-locals и runtime dirty flags, реализующие рабочее
   состояние метода и публикующие только dirty own fields на
   обязательных checkpoints call/exit.

Существующий код можно использовать как перечень синтаксических конструкций и
тестов. Повторно использовать helper можно только тогда, когда его семантика
и представление уже соответствуют этому документу. Снимки сгенерированного C
не доказывают семантического соответствия.


2.3. Translation-unit locality
Локальность единицы трансляции
-----------------------------------

EN

Translating HashArray.lm2 translates declarations and executable bodies
declared by that source unit. It MUST NOT scan a directory and pre-compose
the complete Array tree into a static HashArray layout.

References to Structures supplied by another unit must lower to an already
resolved Lmx pointer, an explicit root-relative lookup, or a runtime provider
that returns an Lmx pointer. References to code lower to entries in the common
callable physical class. The term "runtime binding" must not mean a hidden
Name-to-value map. The build/link layer may compile the supplying unit
separately. Runtime module loading is a possible profile mechanism, but it is
not implicit compile-time merge.

The translator must recursively discover executable definitions inside the
current parser tree. Current-unit locality does not mean top-level-only
traversal.

RU

Трансляция HashArray.lm2 переводит объявления и исполняемые тела, объявленные
этой единицей исходника. Она не должна сканировать директорию и заранее
собирать полное дерево Array в статический layout HashArray.

Ссылки на Structure из другой единицы обязаны снижаться в уже разрешённый
Lmx-указатель, явный lookup относительно root либо runtime provider,
возвращающий Lmx-указатель. Ссылки на код снижаются во входы общей физической
категории callable. Термин "runtime binding" не может означать скрытую map
Name-to-value. Build/link слой может отдельно скомпилировать предоставляющую
их единицу. Runtime-загрузка модулей возможна как механизм профиля, но она не
является неявным compile-time merge.

Транслятор обязан рекурсивно находить исполняемые определения внутри текущего
дерева parser-а. Локальность текущей единицы не означает обход только
верхнего уровня.


3. The sole Lmx node header
Единственный заголовок узла Lmx
===================================

3.1. Required C shape
Обязательная форма C
-------------------------

The common representation is exactly:

    typedef struct Lmx Lmx;

    struct Lmx {
        Lmx *node;
        size_t len;
        void *data;
    };

EN

The field order is normative. node is first, len is second, and data is
third. Every runtime source node starts with this representation.

The common header MUST NOT be extended with any of the following:

* descriptor pointer;
* type pointer or type tag;
* field name or ShortNameId;
* source path;
* vtable or method table;
* class or layout table;
* field-offset table;
* runtime namespace pointer;
* lexical environment pointer;
* reference count;
* capacity word;
* per-node allocator kind.

If an implementation needs allocation bookkeeping, section boundaries,
debugging information or ownership metadata, that information is external to
the semantic Lmx node and cannot become a fourth mandatory header word. This
does not make ownership non-semantic: the rule that every Message owns exactly
one arena is normative. Only the arena/range bookkeeping is kept outside each
three-word node.

RU

Порядок полей нормативен. Сначала находится node, затем len, затем data.
Каждый runtime-узел исходника начинается с этого представления.

Общий заголовок нельзя расширять ни одним из следующих полей:

* указатель на дескриптор;
* указатель типа или тег типа;
* имя поля или ShortNameId;
* путь исходника;
* vtable или таблица методов;
* таблица class или layout;
* таблица смещений полей;
* указатель на runtime namespace;
* указатель lexical environment;
* счётчик ссылок;
* слово capacity;
* per-node вид allocator-а.

Если реализации нужны метаданные allocation, границы секций, отладочная
информация или ownership, эти данные находятся вне семантического узла Lmx и
не могут стать обязательным четвёртым словом заголовка. Это не делает
ownership несемантическим: правило ровно одной arena у каждого Message
нормативно. За пределами трёхсловного узла находится лишь bookkeeping
arena/диапазонов.


3.2. Meaning of node
Смысл node
----------------

EN

node is the parent in the source containment tree as materialized by this
particular runtime tree.

For every contained child c of parent p:

    c->node == p

For a copied tree, node points into the copy. A merge MUST NOT leave a copied
child's node pointing to the corresponding parent in the source tree.

A reference edge to an already existing Lmx node does not change that
referent's node. One node has one containment parent even when several graph
paths reach it.

node is not a descriptor pointer, next-sibling pointer, namespace frame,
owner object, class link or C inheritance link.

For a callable occurrence, this same header field supplies the reserved source
word `node`: generated invocation passes `callable->node`. Consequently source
`node\field` begins at that already selected parent and looks for its immediate
child `field`; it does not apply a second `->node`. The caller cannot replace
this reserved value with a dynamically visible binding.

RU

node является родителем в дереве вложенности исходника, материализованном
именно этим runtime-деревом.

Для каждого вложенного ребёнка c родителя p:

    c->node == p

В скопированном дереве node указывает внутрь копии. Merge не имеет права
оставлять node скопированного ребёнка указывающим на соответствующего
родителя исходного дерева.

Ребро-ссылка на уже существующий Lmx-узел не меняет node этого референта. У
одного узла один родитель вложенности, даже когда к нему ведёт несколько
путей графа.

node не является указателем на дескриптор, next-sibling, frame namespace,
owner object, class link или ссылкой C-наследования.

Для callable-occurrence это же поле header даёт зарезервированное слово
исходника `node`: generated-вызов передаёт `callable->node`. Поэтому
`node\field` в исходнике начинается от уже выбранного родителя и ищет его
непосредственного ребёнка `field`; второй `->node` не выполняется.
Caller не может заменить это reserved-значение dynamic-binding-ом.


3.3. Meaning of len and data
Смысл len и data
------------------------------

EN

data is the only payload pointer. It may address structural Lmx storage,
primitive storage, a callable payload in the common callable physical class, array
storage, opaque substrate storage, or the selected empty representation.

Even a primitive byte is not embedded into the data word. The data word
contains a pointer to that byte. For the canonical example:

    Lmx:
    . char: '!'
    . #<...>

the payload of the char leaf points to the address of the corresponding
element in the global C array all_chars.

For a non-leaf structural payload, len supplies the bounded extent needed to
walk its contained data. For a leaf, len supplies the extent under the rule of
that payload range. The exact unit of len for every range is UNRESOLVED in
section 14; it MUST NOT be guessed from a per-Structure C type.

data is intentionally void pointer rather than Lmx pointer because the final
leaves are primitive storage or emptiness. A consumer MUST classify the
address range before treating data as Lmx storage.

RU

data является единственным указателем payload. Он может адресовать
структурное хранилище Lmx, хранилище примитива, callable-вход в общем
диапазоне методов, хранилище массива, opaque-субстрат или выбранное
представление пустоты.

Даже примитивный байт не встраивается в слово data. Слово data содержит
указатель на этот байт. В каноническом примере:

    Lmx:
    . char: '!'
    . #<...>

payload листа char указывает на адрес соответствующего элемента глобального
C-массива all_chars.

Для нелистового структурного payload поле len задаёт ограниченный размер,
необходимый для обхода вложенных данных. Для листа len задаёт размер по
правилу диапазона этого payload. Точная единица len для каждого диапазона
остаётся UNRESOLVED в разделе 14; её нельзя угадывать из C-типа конкретной
Structure.

data намеренно имеет тип void pointer, а не Lmx pointer, потому что конечными
листьями являются примитивные хранилища или пустота. Consumer обязан сначала
классифицировать диапазон адреса и только потом обращаться с data как с
хранилищем Lmx.


3.4. No runtime descriptors
Отсутствие runtime-дескрипторов
-----------------------------------

EN

The fixed Lmx header replaces the need for a descriptor prefix. There is no
separate runtime descriptor object at the front of an instance and no pointer
from an instance to a shared descriptor.

Names, layout and field kinds are not recovered by loading a descriptor from
the node. Structural navigation uses data, len, address-range classification
and the ShortNameId side table. Callable ABI is recovered only after the leaf
has been classified as callable: its immutable `all_methods_array` record
supplies `{ addr, sig }`. That program-wide method record is machine/link data,
not a descriptor attached to the Lmx node or a per-Structure source type.

Source words historically called descriptors may still be ordinary parsed
source Structures if the language exposes them as data. They have no
privileged runtime layout and cannot control the representation of another
node merely by being called a descriptor.

RU

Фиксированный заголовок Lmx заменяет необходимость префикса-дескриптора. В
начале instance нет отдельного runtime-объекта дескриптора, а в instance нет
указателя на общий дескриптор.

Имена, layout и виды полей не извлекаются загрузкой дескриптора из узла.
Структурная навигация использует data, len, классификацию диапазона адресов и
side table ShortNameId. ABI callable получается только после классификации
листа как callable: его immutable-запись в `all_methods_array` даёт
`{ addr, sig }`. Эта глобальная запись метода — машинные/link-данные, а не
присоединённый к Lmx-узлу descriptor или per-Structure тип исходника.

Слова исходника, исторически называвшиеся descriptors, всё ещё могут быть
обычными распарсенными Structure, если язык предоставляет их как данные. У
них нет привилегированного runtime-layout, и они не могут управлять
представлением другого узла только потому, что названы descriptor.


3.5. No per-Structure target layout
Отсутствие target-layout на каждую Structure
------------------------------------------------

EN

The translator MUST NOT emit:

    typedef struct Array { ... } Array;
    typedef struct HashArray { ... } HashArray;

or semantic equivalents used to navigate source fields by C member access.
It MUST NOT select sizeof(Array), offsetof(HashArray, field), a generated
member name, or a closed field-kind vector as the meaning of a source
Structure.

All named and anonymous Structures use Lmx. A backend optimization may only
be introduced later if it is observationally identical and the generic Lmx
representation remains the semantic contract. Such optimization is outside
the initial rewrite.

RU

Транслятор не должен выдавать:

    typedef struct Array { ... } Array;
    typedef struct HashArray { ... } HashArray;

или семантический эквивалент, используемый для перехода по полям исходника
через C member access. Он не должен считать sizeof(Array),
offsetof(HashArray, field), сгенерированное имя member-а или закрытый вектор
видов полей смыслом Structure исходника.

Все именованные и анонимные Structure используют Lmx. Оптимизацию backend-а
можно добавить позднее только при наблюдаемой эквивалентности и сохранении
общего представления Lmx как семантического контракта. Такая оптимизация не
входит в начальное переписывание.


4. Address ranges
Диапазоны адресов
=====================

4.1. Range-directed physical interpretation
Физическая интерпретация по диапазону
------------------------------------------

EN

The runtime determines the physical class of data by testing the address
against known, disjoint ranges or linker-section bounds. It does not inspect
a descriptor or generated C type.

At minimum, the architecture requires distinguishable storage for:

* structural Lmx payload;
* callable payloads that resolve to method entry addresses;
* each primitive storage family that requires distinct physical handling;
* emptiness.

Additional ranges for arrays, opaque handles or profile-specific substrate
may be provided without changing Lmx.

All dynamic mutable ranges used by ordinary source values are owned by the one
arena of the containing Message. One logical arena may own many backing blocks
and many disjoint ranges: structural child blocks, non-interned primitive
cells, Array payloads and other physical classes remain one ownership/lifetime
domain even though their addresses classify differently. Global immutable
ranges such as `all_chars` and the method pool, and explicit foreign L2
resources, are the stated exceptions.

Range tests MUST be deterministic for the complete lifetime of every live
payload. Overlapping ranges with ambiguous interpretation are forbidden.
Moving a live allocation between ranges without updating its Lmx references
is forbidden.

RU

Runtime определяет физический класс data проверкой адреса по известным
непересекающимся диапазонам или границам linker section. Он не читает
дескриптор и не использует сгенерированный C-тип.

Как минимум архитектура требует различимых хранилищ для:

* структурного payload Lmx;
* callable payloads, разрешаемых в адреса входов методов;
* каждого семейства примитивных хранилищ, которому требуется отличающееся
  физическое обращение;
* пустоты.

Дополнительные диапазоны для массивов, opaque handles или
profile-specific substrate могут быть добавлены без изменения Lmx.

Все dynamic mutable диапазоны обычных source values принадлежат одной arena
содержащего их Message. Одна логическая arena может владеть многими backing
blocks и многими непересекающимися диапазонами: структурные блоки детей,
не-interned ячейки примитивов, Array payloads и другие физические категории
остаются одним доменом ownership/lifetime, хотя их адреса классифицируются
по-разному. Явными исключениями являются глобальные immutable диапазоны
наподобие `all_chars` и method pool, а также explicit foreign L2 resources.

Проверка диапазона обязана быть детерминированной всё время жизни каждого
живого payload. Пересекающиеся диапазоны с неоднозначной интерпретацией
запрещены. Перемещение живого allocation между диапазонами без обновления
его Lmx-ссылок запрещено.


4.2. Range information is not a second node table
Информация о диапазонах не является второй таблицей узлов
------------------------------------------------------------

EN

The rule that the ShortNameId map is the sole auxiliary Lmx-node table does
not forbid fixed linker bounds or allocator-wide range boundaries. Those
bounds classify storage regions; they do not map individual Lmx nodes to
semantic metadata.

There MUST NOT be a hidden parallel per-node table for descriptor, type,
layout, namespace, field offset or method owner. If a proposed implementation
needs such a table, it violates the architecture rather than completing an
unresolved detail.

RU

Правило, по которому map ShortNameId является единственной вспомогательной
таблицей Lmx-узлов, не запрещает фиксированные linker bounds или общие
границы диапазона allocator-а. Эти границы классифицируют области хранения,
а не отображают отдельные Lmx-узлы в семантические метаданные.

Скрытая параллельная per-node таблица descriptor, type, layout, namespace,
field offset или owner метода запрещена. Если предлагаемая реализация требует
такой таблицы, она нарушает архитектуру, а не завершает открытую деталь.


4.3. C portability boundary
Граница переносимости C
----------------------------

EN

Comparing unrelated object pointers with relational C operators is not a
portable range test. A concrete C profile SHOULD compare appropriately
converted integer addresses, use linker-provided membership helpers, or use
allocator/section APIs with defined behavior.

Likewise, ISO C does not universally guarantee interchangeability of object
pointers and function pointers. The requirement is semantic: callable payloads
must belong to one recognizable physical class and resolve through immutable
`{addr, sig}` records to entries invokable with their exact ABI.
Direct code addresses in one or more sections and pointers to correctly typed
callable records are allowed profile alternatives. The exact portable or
platform-specific representation is an UNRESOLVED profile decision.

RU

Сравнение несвязанных object pointers реляционными операторами C не является
переносимой проверкой диапазона. Конкретный C-профиль должен сравнивать
корректно преобразованные целые адреса, использовать предоставленные linker
membership helpers либо API allocator/section с определённым поведением.

Кроме того, ISO C не гарантирует на всех платформах взаимозаменяемость
указателей на объект и указателей на функцию. Нормативно требуется следующее:
callable payloads принадлежат одной распознаваемой физической категории и через
неизменяемые записи `{addr, sig}` разрешаются во входы, вызываемые по их точному
ABI. Прямые адреса кода в одной или нескольких секциях и указатели
на корректно типизированные callable-record являются допустимыми альтернативами
профиля. Точное переносимое или platform-specific представление остаётся
решением профиля с пометкой UNRESOLVED.


5. Names, paths and the sole side table
Имена, пути и единственная side table
==========================================

5.1. Required table
Обязательная таблица
-------------------------

EN

The runtime maintains exactly one auxiliary mapping associated with Lmx
nodes:

    Lmx address  ->  ShortNameId

This table supplies the short name of a node. It does not supply a descriptor,
type, complete path, C layout, lexical depth, callable signature or namespace
frame.

Whenever a named runtime node is constructed, the implementation registers
its address and ShortNameId. Whenever merge copies a named node, it registers
the new address with the same ShortNameId. Positional or anonymous occurrences
must either receive a reserved positional ShortNameId under the selected ABI or
be explicitly excluded from textual-name lookup; this choice is unresolved in
section 14. The copied node is a new key; the source mapping remains unchanged.

Table lifecycle must agree with node lifetime. A dead address must not later
resolve to a stale name if storage is reused.

Reconstructing the full current path of a known occurrence requires more than
concatenating these short names. At each parent the runtime enumerates the
ordered children and computes the occurrence's zero-based ordinal among siblings
with the same ShortNameId. If equal-name siblings exist, the path emits the
corresponding `[k]name` selector; it may emit `[0]name` explicitly although plain
`name` selects that same first occurrence. This calculation uses only the
reverse index, bounded child enumeration and `node`; it adds no forward
namespace or cached full path.

RU

Runtime поддерживает ровно одно вспомогательное отображение, связанное с
узлами Lmx:

    адрес Lmx  ->  ShortNameId

Таблица сообщает короткое имя узла. Она не сообщает descriptor, type, полный
путь, C layout, lexical depth, callable signature или frame namespace.

При создании каждого именованного runtime-узла реализация регистрирует его
адрес и ShortNameId. Когда merge копирует именованный узел, он регистрирует
новый адрес с тем же ShortNameId. Позиционные или анонимные occurrences
должны либо получать зарезервированный positional ShortNameId в выбранном
ABI, либо быть явно исключены из текстового name lookup; этот выбор открыт в
разделе 14. Скопированный узел является новым ключом; отображение исходного
узла не меняется.

Жизненный цикл таблицы обязан совпадать с жизненным циклом узлов. Мёртвый
адрес не должен позднее разрешаться в устаревшее имя при повторном
использовании памяти.

Для восстановления полного текущего пути известного occurrence недостаточно
просто склеить короткие имена. На каждом parent runtime перечисляет ordered
children и вычисляет нулевой ordinal occurrence среди siblings с тем же
ShortNameId. При наличии одноимённых siblings путь выдаёт соответствующий
селектор `[k]name`; `[0]name` можно писать явно, хотя plain `name` выбирает то же
первое occurrence. Расчёт использует только reverse index, ограниченное
перечисление children и `node`; forward namespace либо cached full path не
добавляется.


5.2. What the table is not
Чем таблица не является
-----------------------------

EN

The table is not the dynamic caller namespace. Registering a node does not
push a binding, shadow a caller binding, capture an outer scope or make a name
visible. Node names are stable structural facts; call activity does not reorder
or overlay the side table.

Dynamic caller visibility nevertheless exists as source semantics. The
translator represents its current bindings by native C arguments and C working
locals in each ordinary call-stack activation. It MUST NOT allocate a second
Name-to-Binding dictionary, copy a whole namespace table, search a runtime
binding stack or use the Lmx-to-ShortNameId table in the reverse direction as a
dynamic environment. C return naturally discards the callee's private working
slots; no namespace-object pop is performed.

RU

Таблица не является dynamic namespace caller-а. Регистрация узла не делает
push binding, не shadow-ит binding вызывающего, не захватывает внешний scope
и не делает имя видимым. Имена узлов — стабильные структурные факты;
активность вызовов не переупорядочивает и не накладывает side table.

Dynamic-видимость caller-а тем не менее существует как семантика
исходника. Транслятор представляет её текущие bindings нативными
C-аргументами и рабочими C-locals каждой обычной activation стека
вызовов. Он не должен выделять второй словарь Name-to-Binding,
копировать целую namespace-table, искать по runtime-стеку bindings или
использовать Lmx-to-ShortNameId в обратном направлении как dynamic
environment. C-return естественно удаляет private-слоты callee; pop объекта
namespace не выполняется.


5.3. Root-based path lookup
Поиск пути от корня
------------------------

EN

Every arbitrary textual absolute runtime path is resolved from an explicitly
supplied root. This rule does not apply to an already resolved Lmx pointer or a
relative field path.

Conceptually:

1. Receive or derive the explicit root selected by the operation.
2. Convert or parse the requested path into ShortNameId components and
   occurrence selectors.
3. At the current parent, enumerate bounded structural children through
   data and len.
4. Query the side table for each candidate child's ShortNameId.
5. Select the requested occurrence.
6. Continue with the selected child until the path is exhausted.

This is the semantic lookup for an arbitrary textual absolute path even when
the translator emits a faster
equivalent sequence for a constant path. An optimization MUST NOT change the
answer after a runtime merge.

If code already holds an Lmx pointer, that pointer is the resolved value and is
used directly. An explicit relative path `base\field` starts from the resolved
`base`. Reserved `node\field` starts from `callable->node` and selects its
immediate child; it does not follow another parent link. None of these
operations resets the start point to root.

A bare unqualified `field` is not this structural-path algorithm. It resolves
to an own working local or to the dynamic caller value described in sections 6
and 9, with immediate `node\field` as the fallback only when the caller has no
such binding. Structural traversal MUST NOT search a dynamic environment,
descriptor or per-type field-offset table; dynamic binding MUST NOT masquerade
as root/path traversal.

RU

Каждый произвольный текстовый абсолютный runtime-путь разрешается от явно
переданного root. Это правило не относится к уже разрешённому Lmx-указателю
или относительному пути поля.

Концептуальный алгоритм:

1. Получить или вывести явный root, выбранный операцией.
2. Преобразовать или распарсить запрошенный путь в компоненты ShortNameId и
   селекторы occurrence.
3. В текущем родителе перечислить ограниченное множество структурных детей
   через data и len.
4. Получить ShortNameId каждого кандидата из side table.
5. Выбрать запрошенный occurrence.
6. Продолжать с выбранным ребёнком до исчерпания пути.

Это является семантическим lookup произвольного текстового абсолютного пути,
даже тогда, когда транслятор выдаёт более
быструю эквивалентную последовательность для константного пути. Оптимизация
не имеет права менять ответ после runtime merge.

Если код уже имеет Lmx-указатель, этот указатель является разрешённым
значением и используется прямо. Явный относительный путь `base\field`
начинается от разрешённого `base`. Reserved-путь `node\field` начинается
от `callable->node` и выбирает его непосредственного ребёнка; второго перехода к
родителю нет. Ни одна из этих операций не сбрасывает начальную точку к root.

Одиночное неквалифицированное `field` не является этим алгоритмом
структурного пути. Оно разрешается в own working local либо dynamic-значение
caller-а по разделам 6 и 9; непосредственное `node\field` служит fallback
только когда такого binding нет у caller-а. Структурный traversal не ищет в
dynamic environment, descriptor или per-type field-offset table; dynamic binding не
маскируется под root/path traversal.


5.4. Parent-relative access
Доступ относительно родителя
---------------------------------

EN

`node` is a reserved source word, not an ordinary ShortNameId or a binding that
can be declared, shadowed, rebound or supplied by the caller. In a method it is
the actual parent stored in the selected callable occurrence, exactly
`callable->node`. Therefore `node\field` is explicit immediate-parent access
from the callable and bypasses dynamic caller visibility.

Further structural traversal may continue only when written explicitly. No
unqualified name performs a transitive walk through source parents. The
implementation MUST preserve the concrete parent selected by a runtime copy;
after merge, the copied callable's rewritten `node` supplies the new immediate
parent. It must not restart at root unless the source explicitly requests an
absolute root-based path.

RU

`node` — зарезервированное слово исходника, а не обычный ShortNameId или
binding, который можно объявить, shadow-ить, rebind-ить или получить от
caller-а. Внутри метода это реальный родитель выбранного callable-occurrence,
точно `callable->node`. Поэтому `node\field` — явный доступ к immediate-parent
callable, обходящий dynamic-видимость caller-а.

Дальнейший структурный traversal продолжается только когда он написан явно.
Никакое неквалифицированное имя не идёт транзитивно по родителям исходника.
Реализация сохраняет конкретного родителя runtime-копии: после merge
переписанный `node` скопированного callable даёт нового immediate-parent.
К root перехода нет, если исходник явно не запросил абсолютный root-based путь.


5.5. Repeated names
Повторяющиеся имена
------------------------

EN

Children remain ordered, and repeated ShortNameId values are permitted.
Merge MUST preserve all occurrences rather than overwriting a node in place.
The plain spelling of a field is defined as the designated default occurrence,
including the agreed equivalence:

    path\field == path\[0]field

Occurrence numbers follow the ordered child sequence from its beginning.
`[0]` is the first child having that ShortNameId, `[1]` the next, and so on.
A later merge input does not become default merely because it was appended
later. This direction is fixed and must be stable before and after merge.

RU

Дети сохраняют порядок, и повторяющиеся значения ShortNameId разрешены. Merge
обязан сохранять все occurrences, а не заменять узел на месте. Обычная запись
поля определяется как выбранный default occurrence, включая
согласованную эквивалентность:

    path\field == path\[0]field

Номера occurrences следуют по упорядоченной последовательности детей от её
начала. `[0]` — первый ребёнок с таким ShortNameId, `[1]` — следующий и так
далее. Более поздний вход merge не становится default только потому, что был
добавлен позже. Это направление закреплено и обязано быть стабильным до и
после merge.


6. Methods, dynamic caller ABI and working state
Методы, ABI dynamic caller-а и рабочее состояние
=================================================

6.1. Every executable method becomes program-wide reachable code
Каждый исполняемый метод становится достижимым во всей программе кодом
----------------------------------------------------------

EN

Every executable fn or sub body in the current source unit, including a body
nested inside any named or anonymous Structure, MUST produce live C code.
Traversal that emits only top-level bodies is non-conforming.

The generated method implementation must be reachable from any Lmx callable
occurrence in the linked/loaded program. The concrete C linkage may be external
or may be mediated by a generated method pool/registration unit; a translation-
unit-private spelling is conforming only if that mediation still makes its
entry program-wide addressable. It MUST NOT be emitted as an unrelated
zero-returning stub merely because the source method is nested or appears in a
Structure.

The same source definition produces the same deterministic symbol name in
repeatable builds under the same path-normalization profile.

RU

Каждое исполняемое тело fn или sub текущей единицы исходника, включая тело
внутри любой именованной или анонимной Structure, обязано породить живой
C-код. Обход, который эмитит только тела верхнего уровня, не соответствует
архитектуре.

Сгенерированная реализация метода обязана быть достижима из любого
Lmx-callable occurrence в слинкованной/загруженной программе. Конкретный C
linkage может быть external либо опосредован generated method pool / единицей
регистрации; spelling, закрытый внутри translation unit, допустим лишь если
это опосредование всё равно делает entry адресуемым во всей программе. Метод
не должен превращаться в не связанную с телом заглушку, возвращающую ноль,
только потому, что он вложен или находится в Structure.

Одно и то же определение исходника порождает одно и то же детерминированное
имя символа в повторяемых сборках с одинаковым профилем нормализации путей.


6.2. Program-wide path mangling
Mangle полного пути во всей программе
------------------------------------------

EN

A method entry requires a deterministic program-wide unique implementation
identity. The preferred human-readable C spelling is derived from the complete
source path rather than merely the final method word, replacing path separators
with underscores and escaping other invalid C characters. Whatever scheme the
backend selects MUST contain or encode enough normalized information to
distinguish at least:

* source module or file path;
* every containing source Structure component;
* the method's own short name;
* repeated same-name definitions at distinct source positions.

Long names are expected and accepted. The mangling must produce a valid C
identifier and avoid collisions across the whole linked program. It MUST NOT
depend on allocation addresses or translation order.

The exact escaping alphabet, hash fallback and maximum linker-name policy are
UNRESOLVED, but collision freedom and determinism are mandatory.

RU

Вход метода требует детерминированной уникальной во всей программе
implementation identity. Предпочтительный читаемый C-spelling получается из
полного пути исходника, а не только из последнего слова метода: разделители
пути заменяются подчёркиваниями, остальные недопустимые C-символы escaping-ся.
Какая бы схема ни была выбрана backend-ом, она обязана содержать или кодировать
достаточно нормализованной информации, чтобы различать как минимум:

* путь модуля или файла исходника;
* каждый компонент содержащей Structure исходника;
* собственное короткое имя метода;
* повторные одноимённые определения в разных позициях исходника.

Длинные имена ожидаемы и допустимы. Mangling обязан выдавать допустимый
C-идентификатор и исключать коллизии во всей слинкованной программе. Он не
должен зависеть от адресов allocation или порядка трансляции.

Точный escaping alphabet, hash fallback и политика максимальной длины имени
linker-а остаются UNRESOLVED, но отсутствие коллизий и детерминизм
обязательны.


6.3. Generated method signature and reserved `node`
Generated-сигнатура метода и reserved `node`
---------------------------------------------------

EN

Three related identities are distinct. A source method has one generated C
entry and immutable method record. The graph may contain many callable Lmx leaf
occurrences whose `data` identifies that record. Every selected callable
occurrence has one persistent containing Structure, `callable->node`, whose own
fields are the published working state used for that selected call. Runtime
merge may copy/rebase an occurrence while retaining the same method record.
Throughout this document, "method Structure" is shorthand for this selected
containing Structure; it never means the callable leaf and never means a fresh
per-invocation graph object.

Older wording that says `node` is taken "from the descriptor" is interpreted
only as shorthand for these two concrete facts: the selected callable
occurrence supplies `callable->node`, and its immutable method record supplies
`{addr,sig}`. It does not restore an attached descriptor object or a
per-Structure type/layout record.

Every generated method has an exact C signature. Its first semantic input is
the reserved value:

    Lmx *node = callable->node

`node` is the concrete Structure containing the selected callable occurrence.
The caller evaluates this field but does not choose, shadow or replace its
value. Source `node` is reserved under every spelling, including an exact quoted
identifier, and cannot be declared, dynamically supplied or rebound. After
runtime merge, the copied callable's rebased parent supplies the value.

The remaining signature contains the declared call ABI and exactly the hidden
dynamic-caller values the translated body requires. Here a hidden argument is
a C parameter generated for an unqualified source name not declared as a
parameter at that source call boundary. Hidden dynamic values are required
language lowering, not forbidden infrastructure. A method still MUST NOT
receive an unrelated `LmMessageThread *`, `Arena *`, `ExecutionContext *`,
`Namespace *` or descriptor merely as ambient context; arena ownership is
derived from `node` or its registered allocation range.

Parameter order, value category and return/failure convention are part of
`sig`. The exact result channel remains section 14.10 work, but no call may
guess a prototype, erase a signature or invoke through an incompatible C
function-pointer type.

RU

Три связанные identity различаются. У исходного метода есть одно generated
C-entry и immutable method record. Граф может содержать много callable
Lmx-листьев, `data` которых идентифицирует эту запись. У каждого выбранного
callable-occurrence есть одна постоянная containing Structure,
`callable->node`; её own fields являются опубликованным рабочим состоянием
выбранного вызова. Runtime merge может скопировать/rebase occurrence, сохранив
тот же method record. Во всём документе «Structure метода» является сокращением
для этой выбранной containing Structure; это никогда не callable-лист и не
свежий per-invocation graph-object.

Старая фраза «`node` берётся из дескриптора» является только сокращением двух
конкретных фактов: выбранный callable-occurrence даёт `callable->node`, а его
immutable method record даёт `{addr,sig}`. Она не возвращает attached descriptor
object либо per-Structure запись type/layout.

У каждого generated-метода есть точная C-сигнатура. Её первый семантический
вход — зарезервированное значение:

    Lmx *node = callable->node

`node` — конкретная Structure, содержащая выбранный callable-occurrence. Caller
вычисляет это поле, но не выбирает, не shadow-ит и не заменяет его значение.
`node` в исходнике зарезервирован при любом spelling, включая exact quoted
identifier: его нельзя объявить, динамически передать или rebind-ить. После
runtime merge значение даёт rebased-родитель скопированного callable.

Остальная сигнатура содержит явный ABI вызова и ровно те скрытые
dynamic-caller значения, которые нужны транслированному телу. Здесь
скрытый аргумент — C-параметр, сгенерированный для неквалифицированного
имени исходника, не объявленного параметром на этой границе вызова.
Скрытые dynamic-значения — требуемое снижение семантики языка, а не
запрещённая infrastructure. Метод всё так же не должен получать посторонний
`LmMessageThread *`, `Arena *`, `ExecutionContext *`, `Namespace *` или descriptor как
ambient context; arena выводится из `node` или его registered allocation range.

Порядок параметров, категория значений и return/failure-соглашение входят в
`sig`. Точный канал результата остаётся работой раздела 14.10, но вызов не
может угадывать prototype, стирать сигнатуру или вызывать через
несовместимый тип C function pointer.


6.4. Through variables and dynamic caller visibility
Сквозные переменные и dynamic-видимость caller-а
----------------------------------------------------

EN

An unqualified name first selects the current activation's nearest own binding
chosen by the source declaration rules: a declared formal/result or an own
field/receiver-defined local of the selected containing Structure, represented
by its C working value. Otherwise it is a through name supplied by the current
caller activation. Consequently a callee requiring `x` receives the caller's
current declared/formal/local/own-field value when any such binding is nearest,
then an inherited through value, and only then the callee's immediate
`node\[0]x` fallback. An explicit
`node\field`, `reference\field` or `array[index]` expression is never resolved
through this C-local channel. The translator computes two distinct sets:

* `DynRequired(M)`: M's free bare names plus transitive names required by exact
  callees, excluding names satisfied by an own binding;
* `OwnUsed(M)`: own graph-backed fields read/written unqualified by M or needed
  to supply an outgoing callee's dynamic value.

Its compile-time namespace maps each selected source name to the corresponding
C expression; it is compiler work state, not an emitted runtime dictionary.

For recursive and mutually recursive call-graph components, this dependency
computation MUST reach a fixed point. A value required only by a deeper callee
still belongs to each intervening signature needed to carry it down the dynamic
chain, unless that call site resolves it from an own binding. This is forwarding
of values through exact C activations, not lexical capture.

An own or through C value may itself contain a callable Lmx occurrence selected
at runtime. The compiler resolves the activation binding and exact Consumer call
signature; it need not know one concrete occurrence. At execution the selected
occurrence's method record must have exactly that canonical `sig` before its
typed `addr` is invoked.

At method entry every used through value is copied into a private C working
local:

* a primitive is copied by semantic value;
* a Structure or Array reference value is copied as the same reference.

Rebinding either local affects only the current activation. A primitive update
does not update the caller's value. Rebinding a Structure/Array local does not
rebind the caller's reference. Mutation of the referenced material is possible
only through an explicit path such as `reference\field` or an Array element
operation and is visible to other references to that same material inside the
Message.

If the caller activation has no required through binding, lookup falls back to
the immediate `node\name` of the selected callable. It does not search a chain
of lexical source parents. The fallback is copied by the same primitive-versus-
reference rule and remains local; changing the unqualified working value never
writes it back to `node\name`. Only source spelling that explicitly names the
path can mutate that graph field. If neither the caller chain nor the immediate
fallback supplies the required name, the call is rejected by translation or
runtime admission; no empty/global/lexical value is invented.

A through value modified by a method is passed in its current local form to a
deeper callee that requires the same name. Return never propagates that rebind
upward. Thus visibility is transitive down the dynamic call chain, not through
an implicit lexical-parent walk and not by shared mutable binding slots.

RU

Неквалифицированное имя сначала выбирает ближайший own binding текущей
activation по правилам деклараций исходника: declared formal/result либо own
field/receiver-defined local выбранной containing Structure, представленный его
рабочим C-value. В противном случае это сквозное имя, получаемое от текущей
activation caller-а. Поэтому callee, требующий `x`, получает ближайшее текущее
declared/formal/local/own-field значение caller-а, затем inherited through-value
и лишь затем непосредственный fallback `node\[0]x` callee. Явное
`node\field`, `reference\field` или `array[index]` никогда не разрешается через
этот канал C-local. Транслятор вычисляет два разных множества:

* `DynRequired(M)`: свободные bare names M плюс транзитивные имена, требуемые
  точными callees, кроме имён, удовлетворённых own binding;
* `OwnUsed(M)`: own graph-backed fields, которые M читает/пишет
  неквалифицированно либо должен передать как dynamic value callee.

Compile-time namespace связывает каждое выбранное имя исходника с
соответствующим C-выражением; это служебное состояние compiler-а, а не
выдаваемый runtime-словарь.

Для recursive и mutually recursive компонентов call graph вычисление этих
зависимостей обязано достигать fixed point. Значение, нужное только более
глубокому callee, всё равно входит в каждую промежуточную сигнатуру, необходимую
для его передачи вниз по dynamic-цепочке, если call site не разрешает его из
собственного binding. Это forwarding значений через точные C-активации, а не
лексический capture.

Own либо through C-value может само содержать callable Lmx-occurrence,
выбранный в runtime. Compiler разрешает activation binding и точную Consumer
call-signature, но не обязан знать один конкретный occurrence. При исполнении
method record выбранного occurrence обязан иметь в точности этот канонический
`sig` до typed-вызова его `addr`.

При входе в метод каждое используемое сквозное значение копируется в
private-рабочий C-local:

* примитив копируется по семантическому значению;
* значение ссылки Structure или Array копируется как та же ссылка.

Rebind любого local влияет только на текущую activation. Изменение примитива не
меняет значение caller-а. Rebind local Structure/Array не rebind-ит ссылку
caller-а. Изменение самого referenced-материала возможно только явным путём,
например `reference\field`, либо операцией элемента Array и видно другим
ссылкам на тот же материал внутри Message.

Если в activation caller-а нет требуемого сквозного binding, lookup переходит к
непосредственному `node\name` выбранного callable. Он не ищет по цепочке
лексических родителей исходника. Fallback копируется по тому же правилу
примитива/ссылки и остаётся локальным: изменение неквалифицированного
рабочего значения никогда не пишет его обратно в `node\name`. Только явно
написанный в исходнике путь может изменить это graph-field. Если ни caller-chain,
ни immediate fallback не дают требуемого имени, translation/runtime admission
отклоняет call; empty/global/lexical значение не придумывается.

Изменённое методом сквозное значение передаётся в его текущей локальной
форме более глубокому callee, которому нужно то же имя. Return никогда не
передаёт этот rebind обратно вверх. Таким образом, видимость сквозна вниз по
dynamic-цепочке вызовов, а не по неявному пути лексических родителей и не
через общие mutable binding slots.


6.5. C working locals, dirty publication and no reload
Рабочие C-locals, dirty-публикация и отсутствие reload
---------------------------------------------------

EN

At entry the translator creates C working locals only for `OwnUsed(M)` fields.
It loads their current values from the selected `callable->node`. A
`DynRequired(M)` value is instead a hidden activation input and never becomes an
own backed field merely because M forwards it. An explicit structural path
reads or mutates the current graph/referent on every execution and is not
silently converted into a no-reload own-field cache. An unused field is neither
loaded nor later stored merely because it exists in that Structure.

Every binding classified as an own graph-backed field must resolve to its
declared direct occurrence before entry. Normal runtime construction creates it
in the containing Structure before the callable is admitted, and merge copies
it with that Structure. If later structural mutation removes a required own
field, invocation fails; it is not silently reclassified as a through value or
immediate-node fallback.

For every loaded own field the C activation retains the exact selected Lmx
occurrence and keeps it rooted, rather than retaining only a ShortNameId. Normal
payload assignment checkpoints that occurrence. If nested code structurally
moves, detaches or replaces the occurrence while the activation is suspended,
however, the later publication target is an unresolved conflict policy in
section 14.22. A bootstrap may forbid/reject that structural mutation; it MUST
NOT silently re-resolve a different `[0]` child, reinsert the old occurrence or
pretend that writing a detached occurrence still writes "into its node". A
moving collector must patch or pin every retained active reference.

Every loaded own local has a runtime dirty state, initially clear. An actual
execution-time write or rebind of that local marks it dirty. Static
"may be assigned somewhere in this method", control-flow presence of a dead
assignment, or inequality between a cached local and current graph storage MUST
NOT by itself mark the local dirty. `++`, `--`, compound updates and an operation
that actually writes through granted access count as writes. Merely making
writable access available does not. An outlined helper must report the executed
write, or generated lowering must otherwise instrument it; capability alone
cannot dirty a clean snapshot.

Immediately before every outbound LMX-call boundary, every external,
re-entrant or publishing runtime/foreign boundary capable of exposing or
controlling graph state outside the current activation, invoking user code or
calling back into LMX, every `yield` suspension, and every
activation-destroying exit, the
generated method checkpoints only dirty own fields to the selected
`callable->node`. Each dirty flag is cleared only after the corresponding store
succeeds. A clean field MUST NOT be stored. A previously flushed field is clean
until another actual local write. Through/declared values are never part of this
automatic publication. Falling through the end of a body counts as an exit;
`return`, `throw`, rethrow, failing `assert`, `stop` and cancellation are exit
forms when they destroy the generated C activation.

The callable, call arguments, dynamic/fallback operands, return value or throw
payload are evaluated exactly once into required working temporaries before the
checkpoint that transfers control. Every nested call, recursion, mutual
recursion and synchronous callback is an LMX call boundary. A private,
non-escaping helper used only for the current activation's own traversal,
address classification or explicit graph operation is not a semantic boundary,
even if it reads or writes the graph and the backend emits it as a C function.
A call that may publish/escape state, invoke user code, re-enter LMX or transfer
control outside the activation is a boundary; every uncertain external call is
treated conservatively as one.

For `return` and `throw`, the backend evaluates/roots the result or payload,
checkpoints pre-cleanup dirty state, executes applicable `finally` cleanups,
checkpoints own fields dirtied by those cleanups, and only then destroys the C
activation/transfers control. The final checkpoint remains required when a
cleanup makes its last assignment without another call.

Dirty fields are considered in the forward source/child-occurrence order of
their backing fields in the selected containing Structure. It is fixed that the
intended outbound call or normal exit cannot proceed until every required dirty
value has been published successfully and that a successful store clears only
its own dirty state. Whether checkpoint stores are guaranteed infallible,
prevalidated/all-or-nothing, or prefix-committing on failure remains the explicit
ABI/error-policy choice in section 14.23. The selected policy must specify which
dirty flags remain set, report failure without recursively entering the same
failing epilogue, and must not smuggle in an undeclared rollback log.

There is no automatic reload after a call. The caller's C working locals remain
its activation snapshots. Explicit `node\field`, `reference\field` and Array
operations observe and mutate current graph state. Therefore a clean cached
local and an explicitly mutated graph field may intentionally differ. A later
actual write to that C local makes it dirty, and its next checkpoint
intentionally overwrites the published field. This rule is deterministic
because one Message executes only one turn/call chain at a time.

RU

При входе транслятор создаёт рабочие C-locals только для полей `OwnUsed(M)`.
Их текущие значения загружаются из выбранного `callable->node`. Значение
`DynRequired(M)` вместо этого является hidden input activation и не становится
own-backed field лишь потому, что M передаёт его дальше. Явный
структурный путь при каждом исполнении читает или меняет текущий graph/referent и
не превращается молча в no-reload cache own-field. Неиспользуемое поле не
загружается и не записывается позже лишь потому, что оно есть в Structure.

Каждый binding, классифицированный как own graph-backed field, обязан до entry
разрешиться в свой declared direct occurrence. Обычное runtime construction
создаёт его в containing Structure до admission callable, а merge копирует его
вместе с этой Structure. Если поздняя structural mutation удалила требуемое own
field, invocation завершается failure; оно не переклассифицируется молча в
through value либо immediate-node fallback.

Для каждого загруженного own-field C-activation сохраняет и root-ит точный
выбранный Lmx-occurrence, а не только ShortNameId для нового lookup. Обычный
checkpoint payload-assignment пишет этот occurrence. Если nested code во время
suspension структурно переместил, отсоединил или заменил occurrence, destination
следующей публикации определяется ещё открытой conflict-policy раздела 14.22.
Bootstrap может запретить/отклонить такую structural mutation; он не вправе
молча заново выбрать другой `[0]` child, вставить старый occurrence назад или
делать вид, что запись detached occurrence всё ещё происходит «себе в узел».
Moving collector обязан patch-ить либо pin-ить каждую active-reference.

Каждый загруженный own local имеет runtime dirty-state, изначально clear.
Фактически исполнившаяся запись или rebind этого local ставит dirty. Статическое
«ему могут где-то присвоить в этом методе», наличие assignment в
неисполнившейся ветви или неравенство cached local и текущего graph storage сами
по себе не маркируют local dirty. `++`, `--`, compound update и операция,
фактически записавшая через предоставленный writable access, считаются
записью. Сам факт предоставления writable access недостаточен: outlined helper
обязан сообщить о состоявшейся записи либо lowering обязан иным способом
инструментировать её; одна возможность записи не делает clean snapshot dirty.

Непосредственно перед каждой границей исходящего LMX-call, каждой external,
re-entrant или publishing runtime/foreign границей, способной вынести либо
контролировать graph-state за пределами текущей activation, вызвать user code
или callback/re-entry в LMX, каждой suspension `yield` и каждым уничтожающим
activation выходом generated-метод пишет в выбранный `callable->node` только dirty own
fields. Каждый dirty flag очищается только после успешной записи. Clean field не
записывается. Ранее flushed field остаётся clean до следующей фактической записи
в local. Сквозные/declared значения никогда не входят в эту автоматическую
публикацию. Достижение конца тела является выходом; `return`, `throw`, rethrow,
failing `assert`, `stop` и cancellation являются exit-формами, когда уничтожают
generated C-activation.

Callable, аргументы call, dynamic/fallback operands, значение return или payload
throw вычисляются ровно один раз в нужные working temporaries до checkpoint,
передающего управление. Любой nested call, recursion, mutual recursion и
synchronous callback является LMX call-границей. Private non-escaping helper,
выполняющий только traversal, address classification либо explicit graph
operation текущей activation, не является semantic boundary, даже если читает
или пишет граф и эмитится как C-функция. Call, который может публиковать/выносить
state, вызвать user code, re-enter LMX либо передать управление наружу, является
границей; любой сомнительный external call считается ею консервативно.

Для `return` и `throw` backend вычисляет/укореняет result либо payload,
checkpoint-ит pre-cleanup dirty-state, исполняет применимые `finally` cleanups,
checkpoint-ит own fields, изменённые этими cleanups, и только затем уничтожает
C-activation/передаёт управление. Финальный checkpoint обязателен, когда cleanup
сделал последнюю запись без ещё одного вызова.

Dirty fields рассматриваются в прямом source/child-occurrence порядке их
backing fields в выбранной containing Structure. Закреплено, что предполагаемый
outbound call либо normal exit не выполняется, пока каждое требуемое dirty-value
не опубликовано успешно, а успешный store очищает только свой dirty-state.
Будут ли checkpoint stores гарантированно infallible,
prevalidated/all-or-nothing либо prefix-committing при failure — явный открытый
выбор ABI/error-policy раздела 14.23. Выбранная policy обязана определить
оставшиеся dirty flags, сообщить failure без рекурсивного входа в тот же failing
epilogue и не прятать необъявленный rollback-log.

Автоматического reload после call нет. Рабочие C-locals caller-а остаются
snapshots его activation. Явные `node\field`, `reference\field` и Array-операции
наблюдают и изменяют текущее graph-state. Поэтому clean cached local и явно
изменённое graph-field могут намеренно различаться. Следующая фактическая
запись в этот C-local делает его dirty, а его следующий checkpoint намеренно
перезаписывает опубликованное поле. Правило детерминировано, потому
что один Message исполняет только один turn/call-chain одновременно.


6.6. `all_methods_array` and the common callable class
`all_methods_array` и общая категория callable
---------------------------------------------------

EN

Every generated entry is represented in the program-wide immutable method
array by the conceptual record:

    all_methods_array[i] = { addr, sig }

`addr` identifies the globally reachable implementation. `sig` describes the
complete source and physical invocation contract:

* ABI version and target calling convention;
* the fixed reserved structural `node` parameter;
* every declared formal's canonical source name/position, required, optional or
  default mode, semantic value/reference contract, exact C ABI type and pass
  mode;
* every hidden through value's canonical ShortNameId/name identity, semantic
  copy mode, exact C ABI type and pass mode, in physical parameter order;
* the source result contract and exact physical return/out-result convention;
* every declared throw identity/name, payload contract and propagation ABI; and
* an explicit varargs prohibition or a complete canonical varargs shape.

Dynamic entries use a deterministic canonical order selected by the signature
ABI version. A profile may use canonical ShortNameId/name order or another
link-stable algorithm; the choice is not source-visible, but every translation
unit and adapter for that ABI must agree. Hidden-name
identities are canonical across translation units: a linker may relocate local
ShortNameIds to program-wide identities, or `sig` may carry canonical name bytes
or collision-checked stable hashes. Raw translation-unit-local numeric IDs MUST
NOT be compared. The exact C spelling/encoding of `sig` remains ABI work; the
presence of both fields and exact canonical signature equality at use are
normative.

A callable Lmx leaf has `data` in the registered `all_methods_array`/method-
record physical domain. It does not contain a signature, descriptor or vtable
in its Lmx header. Runtime classification obtains the immutable record. A call
site invokes `addr` only through the exact function type described by `sig`.
Varargs guessing, erasing the prototype to `void (*)(void)`, or treating all
methods as a single one-pointer C function type is non-conforming.

The physical domain may use linker sections or an equivalent generated array
on PE/COFF, ELF, Mach-O or another target. A merge copy retains the same method
record while rebasing the callable occurrence's `node`; it does not compile or
duplicate the method.

Code received later through a Message or module mechanism MUST NOT be invoked
as an address with an unknown C signature. It first passes validation and is
then translated and compiled into a registered method record, or is interpreted
through a future interpreter preserving the same exact `sig` contract. Only
after that admission may its callable occurrence enter the method domain.

RU

Каждый generated-entry представлен в immutable-массиве методов всей программы
концептуальной записью:

    all_methods_array[i] = { addr, sig }

`addr` идентифицирует глобально достижимую реализацию. `sig` описывает полный
source и physical invocation contract:

* ABI-version и target calling convention;
* фиксированный зарезервированный structural-параметр `node`;
* canonical source name/position каждого declared formal, required/optional/
  default mode, semantic value/reference contract, точный C ABI type и pass mode;
* canonical ShortNameId/name identity каждого hidden through value, semantic
  copy mode, точный C ABI type и pass mode в физическом порядке параметров;
* source result contract и точный physical return/out-result convention;
* identity/name каждого declared throw, payload contract и propagation ABI; и
* явный запрет varargs либо полную canonical varargs shape.

Dynamic entries идут в детерминированном canonical order, выбранном версией
signature ABI. Профиль может выбрать порядок canonical ShortNameId/name или
другой link-stable алгоритм; source semantics от выбора не зависит, но все
translation units и adapters этого ABI обязаны совпадать. Identity скрытых имён
каноничны между translation units: linker может
релокировать локальные ShortNameIds в program-wide identity, либо `sig` может
хранить canonical name bytes или stable hashes с проверкой коллизий. Raw
локальные числовые IDs разных translation units сравнивать нельзя. Точные
C-spelling/encoding `sig` остаются работой ABI; наличие обоих полей и точное
равенство канонических сигнатур при использовании нормативны.

`data` callable-листа Lmx входит в registered физический домен
`all_methods_array`/method-record. Он не содержит сигнатуру, descriptor или vtable в
заголовке Lmx. Runtime-классификация получает immutable-record. Call site
вызывает `addr` только через точный тип функции, описанный `sig`. Угадывание
varargs, стирание prototype до `void (*)(void)` или трактовка всех методов как
одного однопараметрического C-типа не соответствует архитектуре.

Физический домен может использовать linker sections либо эквивалентный generated-
массив на PE/COFF, ELF, Mach-O или другой цели. Копия merge сохраняет ту же
запись метода, rebasing `node` callable-occurrence; она не компилирует и не
дублирует метод.

Код, позднее полученный через Message- либо module-механизм, нельзя вызывать как
адрес с неизвестной C-сигнатурой. Сначала он проходит validation, затем
транслируется и компилируется в зарегистрированную method-record либо
интерпретируется будущим интерпретатором, сохраняющим тот же exact `sig`
contract. Только после такого admission его callable-occurrence входит в
method-domain.


6.7. Callable compatibility in `implements`
Совместимость callable в `implements`
-----------------------------------------

EN

`implements(A, B, Consumer)` remains directional and consumer-driven. It
examines only paths/leaves actually used by `Consumer`. When a used leaf is
consumed as a callable, its `sig` is part of that used leaf and validation must
establish `sig(A.p) == sig(B.p) == ExpectedSig(Consumer,p)` at that call site.
Different `addr` values are allowed when their canonical `sig` values are
equal; an unused callable leaf does not impose an unrelated whole-Structure
check. There is no implicit arity adapter, variance or ignored signature
position once Consumer actually invokes the leaf.

This is not a nominal type system or an attached descriptor. It is the minimum
structural obligation needed to prevent a call site compiled for one exact C
prototype from jumping to an incompatible method after rebind, reference
selection or merge.

RU

`implements(A, B, Consumer)` остаётся направленным и зависящим от Consumer.
Он рассматривает только пути/листья, реально используемые `Consumer`. Когда
используемый лист потребляется как callable, его `sig` входит в этот лист, а
validation обязана установить
`sig(A.p) == sig(B.p) == ExpectedSig(Consumer,p)` в этом call site. Разные
`addr` допустимы при равных canonical `sig`;
неиспользуемый callable-лист не требует посторонней проверки всей Structure.
После фактического использования leaf нет неявного arity adapter, variance или
игнорируемой позиции сигнатуры.

Это не nominal type system и не attached descriptor. Это минимальное структурное
обязательство, не позволяющее call site, скомпилированному для одного
точного C-prototype, прыгнуть в несовместимый метод после rebind, выбора по
ссылке или merge.


6.8. Invocation
Вызов
---------------

EN

Conceptually, invocation performs these steps:

1. Resolve the call-capable activation binding or explicit structural/path
   expression, evaluate the resulting callable Lmx occurrence exactly once and
   retain/root it. An own, declared or hidden dynamic C value may itself hold the
   runtime-selected occurrence.
2. Classify its data in the common callable domain and obtain its immutable
   `{ addr, sig }` record.
3. Prove exact canonical equality between the selected `sig` and the signature
   expected by the Consumer call site, including every hidden through position.
4. Evaluate all declared operands exactly once, in specified source order, into
   typed working temporaries.
5. Select/copy every hidden through operand exactly once, in `sig` order, into
   typed working temporaries. Each copies the current caller value or, when
   absent, the selected callable's immediate `node\name` fallback. If both are
   absent, validation/admission rejects the call before publication. Thus every
   call operand and fallback is fixed before publication.
6. Publish only dirty own fields of the caller and clear their flags after
   successful stores.
7. Invoke `addr` through the exact C prototype described by `sig`, using the
   already evaluated operands.
8. Receive the result/failure by the selected ABI and continue without
   reloading the caller's working locals.

Any nested call reached while evaluating steps 1, 4 or 5 establishes its own
normal boundary. Generated C MUST materialize this order explicitly and MUST
NOT rely on C's unspecified argument-evaluation order. In particular, the
checkpoint cannot retroactively change the selected callable or fallback copy.

The C activation record established by this exact call is the dynamic caller
namespace implementation. No separate namespace object is installed or
restored. A method copied by merge keeps the same `{ addr, sig }`; its rewritten
`node` provides the new structural fallback/context. Thus Array.resize may be a
live method in a runtime HashArray copy without another C compilation.

RU

Концептуально вызов выполняет следующие шаги:

1. Разрешить call-capable activation binding либо явное structural/path
   expression, вычислить полученный callable Lmx-occurrence ровно один раз и
   удержать/root-ить его. Own, declared либо hidden dynamic C-value само может
   хранить occurrence, выбранный в runtime.
2. Классифицировать его data в общем callable-домене и получить immutable-запись
   `{ addr, sig }`.
3. Доказать точное каноническое равенство выбранного `sig` и сигнатуры,
   ожидаемой Consumer call site, включая каждую hidden through position.
4. Вычислить все declared operands ровно один раз, в заданном source order, в
   typed working temporaries.
5. Выбрать/скопировать каждый hidden through operand ровно один раз, в порядке
   `sig`, в typed working temporaries. Каждый копирует текущее значение caller-а
   либо, при его отсутствии, непосредственный fallback `node\name` выбранного
   callable. Если отсутствуют оба, validation/admission отклоняет call до
   публикации. Поэтому все operands/fallback вызова зафиксированы до публикации.
6. Опубликовать только dirty own fields caller-а и очистить их флаги после
   успешных stores.
7. Вызвать `addr` через точный C-prototype, описанный `sig`, используя уже
   вычисленные operands.
8. Получить result/failure по выбранному ABI и продолжить без reload рабочих
   locals caller-а.

Любой nested call при вычислении шагов 1, 4 или 5 устанавливает собственную
обычную boundary. Generated C обязан явно материализовать этот порядок и не
полагаться на unspecified порядок вычисления аргументов C. В частности,
checkpoint не может задним числом изменить выбранный callable или fallback-copy.

C activation record, созданный этим точным вызовом, является реализацией
dynamic namespace caller-а. Отдельный namespace-object не устанавливается и не
восстанавливается. Метод, скопированный merge, сохраняет тот же `{ addr, sig }`;
его переписанный `node` даёт новый структурный fallback/context. Поэтому Array.resize
может быть живым методом runtime-копии HashArray без ещё одной C-компиляции.


6.9. Activation history, recursion, `yield` and `retry`
История activation, recursion, `yield` и `retry`
--------------------------------------------------

EN

The C call stack is the only implicit activation history. The containing
Structure of the selected callable occurrence (`callable->node`) contains the
method's published working state and is not a call log. Any history intended to
survive return or to split between branches MUST be represented by an explicit
Structure, Array or Message. The side effect of polluting the caller's biography
through incorrectly constructed recursive calls is a memory-consuming
architectural error whose use Lingvamyxa deliberately makes dangerous and
logically impossible.

Before a recursive or mutually recursive call, the current activation publishes
only its dirty own fields. A nested activation through the same callable
occurrence may publish new values into the same containing Structure. An
occurrence copied by merge may identify the same method record but a different
containing Structure. On return the suspended caller is not reloaded; its C
working locals remain its snapshots. If it later writes one and reaches another
checkpoint, that dirty value intentionally overwrites the currently published
field. This overwrite semantics is deliberate. Code that needs a recursion
biography must build it explicitly instead of relying on method-state pollution.

`yield` is a semantic dirty-only checkpoint before suspension and then preserves
normal stack/continuation state, including current working locals, hidden
dynamic values and their cleared/remaining dirty flags. It does not reload on
resume and is not transformed into a fabricated method-Structure activation
log. A later `next` caller does not replace the producer activation's dynamic
values. If a private continuation survives an end-turn collection, every Lmx
reference it retains is a registered collector root until resume/close.

`retry` is a control operation inside the current activation, not a call; it does
not create a new call frame and does not trigger a checkpoint merely by being
`retry`. It preserves current C values and graph mutations and performs no
implicit rollback. Any actual call evaluated by repeated execution follows the
ordinary call rule.

A synchronous callback into the same Message is another nested C activation in
the same serial turn and follows materialize/checkpoint/call/no-reload. A foreign
adapter may retain already materialized typed values only for that synchronous
call; its retained Lmx references are collector roots. An asynchronous callback
cannot preserve an implicit returned C frame: same-Message work is a later FIFO
Message turn carrying explicit Structure/Message state, and cross-Message work
uses clone/serialization/transfer. A foreign thread cannot concurrently re-enter
one Message's mutable graph under common L3 semantics.

Direct tail recursion may be lowered to a loop and proven redundant checkpoints
may be removed only if all observable state/publication ordering is unchanged.
No finite backend promises an infinitely growing native C stack.

RU

Стек вызовов является единственной неявной историей активаций. Structure метода
содержит рабочее опубликованное состояние метода и не является журналом вызовов.
Любая история, предназначенная для переживания возврата или разделения между ветвями,
должна быть представлена явной Structure, Array или Message. Побочный эффект
загрязнения биографии вызывающего, при неграмотно составленных рекурсивных вызовах,
это съедающая память архитектурная ошибка, использование которой Lingvamyxa намеренно делает опасной и логически невозможной.

Перед recursive или mutually recursive call текущая activation публикует только
свои dirty own fields. Nested activation через тот же callable-occurrence может
опубликовать новые значения в ту же containing Structure. Скопированный merge
occurrence может идентифицировать тот же method record, но другую containing
Structure. После return suspended caller не reload-ится; его рабочие C-locals
остаются его snapshots. Если позже он запишет один из них и достигнет
следующего checkpoint, это dirty-значение намеренно перезапишет текущее
опубликованное поле. Эта overwrite-семантика намеренна. Код, которому нужна
биография recursion, обязан построить её явно, а не зависеть от загрязнения
состояния метода.

`yield` является semantic dirty-only checkpoint перед suspension, а затем
сохраняет обычное состояние stack/continuation, включая рабочие locals, hidden
dynamic values и их очищенные/оставшиеся dirty flags. При resume reload нет, и
yield не превращается в выдуманный activation-log в Structure метода. Более
поздний caller `next` не заменяет dynamic values producer activation. Если
private continuation переживает end-turn collection, каждая удерживаемая им
Lmx-reference является registered collector root до resume/close.

`retry` — control-операция внутри текущей activation, а не call; она не создаёт
новый call frame и не запускает checkpoint только потому, что это `retry`.
Текущие C-values и graph mutations сохраняются, скрытого rollback нет. Любой
фактический call при повторном исполнении следует обычному правилу call.

Synchronous callback в том же Message является ещё одной nested C-activation в
том же serial turn и следует materialize/checkpoint/call/no-reload. Foreign
adapter может удержать уже материализованные typed values только на время этого
synchronous call; его Lmx-references являются collector roots. Async callback не
может сохранить неявный вернувшийся C-frame: работа того же Message становится
поздним FIFO turn с явным Structure/Message-state, а cross-Message работа
использует clone/serialization/transfer. Foreign thread не может конкурентно
re-enter mutable graph одного Message в общей L3-семантике.

Прямая tail recursion может быть lowered в loop, а доказанно избыточные
checkpoints удалены только при сохранении всего наблюдаемого state/order
publication. Ни один конечный backend не обещает бесконечно растущий native C
stack.


7. Runtime Structure construction
Построение Structure в runtime
====================================

7.1. No generated static Structure instances
Нет сгенерированных статических instance Structure
-------------------------------------------------------

EN

Source Structures are materialized at runtime. The translator MUST NOT emit a
static C instance whose member layout is the permanent meaning of a source
Structure.

Global substrate such as all_chars, linker method sections, immutable source
bytes or generated C functions is not thereby a static source Structure. The
prohibition concerns prebuilt semantic Structure instances and their
per-Structure layouts.

When execution does not reach a Structure-producing expression, that runtime
Structure is not materialized merely because its source declaration was
translated.

RU

Structure исходника материализуются в runtime. Транслятор не должен выдавать
статический C instance, layout members которого является постоянным смыслом
Structure исходника.

Глобальный субстрат, такой как all_chars, linker section методов,
неизменяемые байты исходника или сгенерированные C-функции, не становится от
этого статической Structure исходника. Запрет относится к заранее
построенным семантическим instance Structure и их отдельным layouts.

Если исполнение не дошло до выражения, производящего Structure, такая
runtime-Structure не материализуется только потому, что её объявление было
переведено.


7.2. Stable node addresses
Стабильные адреса узлов
----------------------------

EN

The node parent link and the ShortNameId side table make the Lmx address part
of live runtime identity. Therefore a live node MUST NOT move without
rewriting all references and its side-table key.

In particular, growing a child sequence with an ordinary realloc that moves
embedded Lmx nodes is invalid unless no reference can observe the old
addresses and every node relationship and table key is rebuilt atomically.
Allocation occurs in the owning Message's arena. The initial implementation
SHOULD prefer stable blocks in that arena or fresh tree construction.

RU

Родительская ссылка node и side table ShortNameId делают адрес Lmx частью
живой runtime identity. Поэтому живой узел нельзя перемещать без
переписывания всех ссылок и его ключа в side table.

В частности, увеличение последовательности детей обычным realloc, который
перемещает встроенные Lmx-узлы, недопустимо, если старые адреса могут
наблюдаться и все отношения node и ключи таблицы не перестраиваются атомарно.
Allocation происходит в arena Message-владельца. Начальная реализация должна
предпочесть стабильные блоки этой arena или построение нового дерева.


7.3. Primitive leaves
Примитивные листья
-----------------------

EN

A primitive leaf remains an Lmx node. Only its payload is primitive storage.
For an interned immutable primitive such as a character, copying the Lmx node
copies the pointer to the canonical primitive cell.

Writing a source variable represented by such a node changes which primitive
cell its data references; it MUST NOT mutate the shared all_chars cell.

The copy policy for mutable, non-interned or opaque primitive storage is
UNRESOLVED. It must be specified per physical range without adding a
per-Structure descriptor.

RU

Примитивный лист остаётся Lmx-узлом. Только его payload является примитивным
хранилищем. Для interned immutable примитива, например символа, копирование
Lmx-узла копирует указатель на каноническую ячейку примитива.

Запись source variable, представленной таким узлом, меняет то, на какую
примитивную ячейку ссылается data; она не должна изменять общую ячейку
all_chars.

Политика копирования mutable, non-interned или opaque примитивного хранилища
остаётся UNRESOLVED. Она должна определяться для физического диапазона без
добавления descriptor конкретной Structure.


7.4. One Message arena and payload placement
Одна arena Message и размещение payload
-------------------------------------------

EN

Every Message owns exactly one logical arena. The arena is the semantic memory
boundary of that Message and remains attached to it when the Message is
scheduled as an L3 Thread or migrates between host workers. "One arena" does
not require one contiguous homogeneous allocation: the arena may own a list of
stable blocks and several disjoint registered address ranges.

The arena contains every mutable or dynamically constructed source-semantic
value owned by the Message:

* Lmx occurrence headers for Structures, fields, methods, explicitly
  represented/published declared arguments, results and the published fields of
  method Structures; this never requires fresh implicit argument/result nodes
  per activation, and C working locals are activation storage rather than
  additional graph occurrences;
* branch/child storage addressed by Structure `data`;
* non-interned primitive cells constructed for that Message;
* ordinary Array headers, shapes, elements and backing storage once the exact
  Array payload ABI is fixed;
* runtime merge results and every fresh occurrence copied into them;
* Message envelope and other explicitly source-visible state represented as
  Lmx nodes.

Opaque host continuation/stack storage used to suspend a turn is activation
machinery, not a source graph occurrence or an implicit Lmx call log. It follows
the continuation scheduler's physical lifetime while preserving the semantic C
locals and dirty flags specified in section 6.9.

Immutable program-wide substrate is not duplicated merely to satisfy arena
ownership. `all_chars`, immutable intern pools, generated method code and
immutable method records may live in registered global ranges. The Lmx
occurrence which refers to such substrate still belongs to its Message arena.
Mutable foreign storage is represented only by an explicit L2 handle and its
declared lifetime/synchronization contract.

An implementation may recover the owning arena from the address range
containing the reserved `node` argument, or from equivalent allocator
metadata. A generated source method therefore allocates relative to the arena
of that `node`. Its declared and hidden through-value operands do not select or
replace the arena, and it does not receive a hidden arena, MessageThread or
allocator parameter. Address-range-to-arena/domain metadata classifies storage
regions and is not another per-node semantic table.

Migration note: the current hosted runtime has a canonical Message
`root_owner` plus a registry of additional `LmOwnArena` allocation shells and
passes MessageThread/arena state through generated helpers. For Revision 2 the
registry is interpreted/refactored as physical blocks/ranges of one logical
Message arena. The extra shells and hidden generated arguments are not multiple
semantic arenas and are not the final source-method ABI.

RU

Каждый Message владеет ровно одной логической arena. Arena является
семантической границей памяти этого Message и остаётся связанной с ним, когда
Message планируется как L3 Thread либо мигрирует между host workers. «Одна
arena» не означает одно непрерывное однородное allocation: arena может владеть
списком стабильных блоков и несколькими непересекающимися зарегистрированными
диапазонами адресов.

В arena находятся все изменяемые или динамически построенные source-semantic
значения, принадлежащие Message:

* заголовки occurrences Lmx для Structures, полей, методов, явно
  представленных/опубликованных объявленных аргументов, результатов и
  опубликованных полей Structures методов; это никогда не требует свежих
  неявных узлов аргументов/результатов для каждой activation, а рабочие C locals
  являются хранилищем активации, а не дополнительными occurrences графа;
* хранилище ветвей/детей, адресуемое `data` Structure;
* не-interned ячейки примитивов, построенные для этого Message;
* заголовки, shape, элементы и backing storage обычных Arrays после фиксации
  точного ABI Array payload;
* результаты runtime merge и все свежие occurrences, скопированные в них;
* envelope Message и другое явно видимое исходнику состояние, представленное
  Lmx-узлами.

Opaque host-хранилище continuation/stack, используемое для приостановки turn,
является machinery активации, а не occurrence графа исходника или неявным Lmx
call log. Оно следует физическому lifetime планировщика continuation, сохраняя
семантические C locals и dirty flags по разделу 6.9.

Неизменяемый глобальный субстрат программы не дублируется только ради arena
ownership. `all_chars`, immutable intern pools, сгенерированный код методов и
неизменяемые method records могут лежать в зарегистрированных глобальных
диапазонах. Ссылающийся на такой субстрат occurrence Lmx всё равно принадлежит
arena своего Message. Изменяемое foreign storage представляется только явным
L2 handle с объявленным контрактом lifetime/synchronization.

Реализация может определить arena-владельца по диапазону адреса, содержащему
зарезервированный аргумент `node`, либо по эквивалентным metadata allocator-а.
Поэтому сгенерированный метод исходника выделяет память относительно arena
этого `node`. Объявленные operands и скрытые сквозные значения не выбирают и
не заменяют arena; скрытый параметр arena, MessageThread или allocator методу
не передаётся. Metadata address-range-to-arena/domain классифицируют области
хранения и не являются другой семантической per-node таблицей.

Примечание о миграции: текущий hosted runtime имеет канонический Message
`root_owner`, registry дополнительных allocation shells `LmOwnArena` и
протаскивает состояние MessageThread/arena через generated helpers. Для
Revision 2 этот registry трактуется/рефакторится как физические blocks/ranges
одной логической arena Message. Дополнительные shells и скрытые generated
arguments не являются несколькими семантическими arena и не являются
финальным ABI методов исходника.


8. Runtime merge
Runtime merge
================

8.1. Execution-time operation
Операция времени исполнения
--------------------------------

EN

merge is executed only when control reaches the source operation containing
that merge. It is not a translator invocation, compiler callback, directory
scan, descriptor composition or link-time layout operation.

The translated C at that source site calls the generic runtime merge over
runtime Lmx values. The merge implementation needs no C knowledge of Array,
HashArray or any other source Structure name.

Consequently:

* a merge in an untaken branch performs no copy;
* a merge in a method runs when that method reaches it;
* a runtime merge result can be supplied to another runtime merge;
* no language-level new operation is required;
* construction happens because merge itself is a value-producing runtime
  operation.

RU

merge выполняется только тогда, когда управление дошло до содержащей его
операции исходника. Он не является вызовом транслятора, callback компилятора,
сканированием директории, композицией descriptors или link-time операцией
layout.

Сгенерированный C в этом месте исходника вызывает общий runtime merge над
runtime-значениями Lmx. Реализации merge не требуется C-знание об Array,
HashArray или имени любой другой Structure исходника.

Следовательно:

* merge в непройденной ветке ничего не копирует;
* merge внутри метода работает тогда, когда этот метод дошёл до него;
* результат runtime merge можно передать следующему runtime merge;
* отдельная операция языка new не требуется;
* создание происходит потому, что merge сам является производящей значение
  runtime-операцией.


8.2. Copy, do not connect
Копировать, а не соединять
-------------------------------

EN

merge creates a new result root. For every operand from left to right it copies
the operand root's direct children, in order, beneath the new result root; it
does not insert the operand root itself as an extra named child. It then copies
the explicit vertical merge body according to the same ordered rule. Thus
merging Array into HashArray produces `HashArray\resize`, not
`HashArray\Array\resize` merely because Array was an operand.

It MUST NOT implement composition by placing links to the source tree where
copied nodes are required. For each copied containment node:

1. allocate a distinct Lmx node;
2. copy or construct its len and data according to the physical range;
3. register the new Lmx address with the source node's ShortNameId when that
   occurrence participates in named lookup (or apply the selected positional
   convention);
4. set node to the corresponding parent in the new tree;
5. recursively copy its contained children;
6. preserve the ordered field sequence and repeated names.

The source tree remains valid and unchanged. Mutation of structural fields in
the result must not mutate the corresponding source tree merely because merge
was implemented with links.

What to do with explicit non-node reference edges whose target lies inside or
outside the copied subtree is UNRESOLVED in section 14. This question does not
permit replacing the required containment copy with a link.

RU

merge создаёт новый root результата. Для каждого operand слева направо он
копирует прямых детей root-а operand-а, по порядку, под новый root результата;
сам root operand-а не вставляется дополнительным именованным ребёнком. Затем
по тому же упорядоченному правилу копируется явное вертикальное тело merge.
Поэтому merge Array в HashArray даёт `HashArray\resize`, а не
`HashArray\Array\resize` только из-за того, что Array был operand-ом.

Он не должен реализовывать композицию размещением ссылок на исходное дерево
там, где требуются скопированные узлы. Для каждого копируемого узла
вложенности:

1. выделить отдельный Lmx-узел;
2. скопировать или построить его len и data по правилу физического диапазона;
3. зарегистрировать новый адрес Lmx с ShortNameId исходного узла, если
   occurrence участвует в именованном lookup (либо применить выбранное
   positional-соглашение);
4. установить node в соответствующего родителя нового дерева;
5. рекурсивно скопировать вложенных детей;
6. сохранить упорядоченную последовательность полей и повторяющиеся имена.

Исходное дерево остаётся допустимым и неизменным. Изменение структурных полей
результата не должно менять соответствующее исходное дерево только потому,
что merge был реализован ссылками.

Поведение явных не-node рёбер-ссылок, цель которых находится внутри или вне
копируемого поддерева, остаётся UNRESOLVED в разделе 14. Этот вопрос не
разрешает заменять требуемую копию дерева вложенности ссылкой.


8.3. Ordered composition
Упорядоченная композиция
-----------------------------

EN

merge preserves source ordering. Multiple input trees are consumed in their
source-specified order, and the explicit merge body is placed according to
the language's ordered merge rule. Equal ShortNameId values remain separate
occurrences.

For any repeated ShortNameId, `[0]` is the first occurrence in this result
order, `[1]` is the next, and so on. Appending a later operand never changes
which preserved earlier occurrence is selected by the unqualified name.

No occurrence is deleted, renamed or overwritten merely to fit a C struct
member namespace. Runtime lookup selects among the preserved occurrences.

RU

merge сохраняет порядок исходника. Несколько входных деревьев потребляются в
заданном исходником порядке, а явное тело merge размещается по
упорядоченному правилу merge языка. Одинаковые ShortNameId остаются
отдельными occurrences.

Для каждого повторённого ShortNameId `[0]` является первым occurrence в этом
порядке результата, `[1]` — следующим и так далее. Добавление более позднего
operand никогда не меняет того, какой сохранённый ранний occurrence выбирает
обычное имя.

Ни один occurrence не удаляется, не переименовывается и не перезаписывается
только ради соответствия namespace members в C struct. Runtime lookup
выбирает среди сохранённых occurrences.


8.4. HashArray / Array consequence
Следствие для HashArray / Array
------------------------------------

EN

Suppose Array declares runtime fields and methods, and HashArray contains a
merge that consumes Array.

Translation of HashArray emits the HashArray source bodies and a runtime
merge call. It does not embed a statically expanded Array layout in
HashArray.

Before execution reaches that merge, the runtime HashArray result containing
Array's copied nodes does not exist. When execution reaches it, merge copies
the Array tree and installs copied method nodes in the new HashArray tree.
Those method nodes carry callable payloads resolving to the already compiled
program-wide reachable Array method entries.

The machine code must already be linked or loaded before it can be invoked.
The phrase code appears in HashArray means that a callable Lmx node with that
entry address appears in the new runtime tree. It does not mean that merge
invokes a compiler or generates machine instructions.

RU

Пусть Array объявляет runtime-поля и методы, а HashArray содержит merge,
потребляющий Array.

Трансляция HashArray выдаёт тела исходника HashArray и runtime-вызов merge.
Она не встраивает статически раскрытый layout Array в HashArray.

До того как исполнение дошло до этого merge, runtime-результата HashArray,
содержащего скопированные узлы Array, не существует. Когда исполнение доходит
до merge, он копирует дерево Array и помещает скопированные узлы методов в
новое дерево HashArray. Эти узлы методов указывают на уже скомпилированные
глобальные входы методов Array в общей секции методов.

Машинный код обязан быть слинкован или загружен до вызова. Фраза «код
появляется в HashArray» означает, что callable-узел Lmx с этим адресом входа
появляется в новом runtime-дереве. Она не означает, что merge вызывает
компилятор или генерирует машинные инструкции.


9. Dynamic caller visibility without a runtime namespace object
Динамическая видимость вызывающего без runtime-объекта namespace
==================================================================

9.1. Source semantics and C lowering
Семантика исходника и lowering в C
-------------------------------------

EN

Lingvamyxa has dynamic caller visibility: an unqualified name used by a method
may be supplied by the current caller. The implementation does not represent
that visibility by a mutable Name-to-Binding table, overlay or stack. For every
exact call site, the translator resolves the required through-name set and
lowers those values to exact hidden C parameters recorded in the callable
signature. Native C parameter slots and the native C call stack are the runtime
representation of the dynamic visibility chain.

A primitive through value is copied by semantic value. A Structure or Array
through value copies the reference value as-is. Rebinding either copied value
inside the callee is local to that activation and is never written back to the
caller automatically. Mutation of referenced material requires an explicit
path through the reference. If the caller supplies no binding for an
unqualified name required by the callee, lookup falls back to the immediate
reserved `node\name`; it never walks a transitive lexical-parent chain.

The translator may use compile-time name tables while consuming the parser
tree, computing exact call dependencies and emitting C expressions. Those
tables are implementation working data, not runtime language values. The only
runtime name metadata attached to ordinary graph identity remains the reverse
`Lmx * -> ShortNameId` side table used for structural traversal.

RU

В Lingvamyxa есть динамическая видимость вызывающего: неквалифицированное имя,
используемое методом, может быть предоставлено текущим вызывающим. Реализация
не представляет эту видимость изменяемой таблицей, overlay или стеком
Name-to-Binding. Для каждого точного call site транслятор разрешает требуемый
набор сквозных имён и понижает эти значения в точные скрытые параметры C,
записанные в сигнатуре callable. Нативные слоты параметров C и нативный стек
вызовов C являются runtime-представлением цепочки динамической видимости.

Сквозное примитивное значение копируется по семантическому значению. Для
сквозной Structure или Array копируется само значение-ссылка как есть.
Перепривязка любой такой копии внутри вызываемого локальна для этой активации и
никогда автоматически не записывается обратно вызывающему. Изменение материала
по ссылке требует явного пути через эту ссылку. Если вызывающий не предоставляет
binding для требуемого вызываемым неквалифицированного имени, lookup откатывается
к непосредственному зарезервированному `node\name`; сквозного прохода по цепочке
лексических родителей нет.

Транслятор может использовать compile-time таблицы имён при обработке дерева
parser-а, вычислении точных зависимостей вызова и выдаче выражений C. Эти таблицы
являются служебными данными реализации, а не runtime-значениями языка.
Единственной runtime-metadata имени, связанной с обычной identity графа,
остаётся обратная side table `Lmx * -> ShortNameId`, используемая структурным
traversal.


9.2. Call boundaries and published working state
Границы вызова и опубликованное рабочее состояние
---------------------------------------------------

EN

Method entry loads only own fields used through unqualified own bindings into C
working locals and clears their runtime dirty flags. Explicit paths continue to
access the graph directly. An actual local write or reference rebind marks the
corresponding own field dirty. At every semantic boundary defined by 6.5, only
dirty own fields are published to the selected `callable->node`; each flag is
cleared after its store succeeds. Clean cached fields must not overwrite graph
mutations made by a nested call or an explicit path. There is no automatic
reload after a call: an unqualified local keeps its activation snapshot, while
an explicit graph path observes current graph state.

There is no namespace push/pop or namespace cleanup on entry and return. The C
stack itself creates and destroys hidden through-value slots and working locals.
Recursion and callbacks therefore need no separate namespace stack. Activations
through the same callable occurrence do, however, checkpoint into the same
published containing Structure, so recursive or mutually recursive activations
intentionally overwrite that working published state. Persisted or branched
activation history must be an explicit Structure, Array or Message, never an
implicit namespace or per-call graph clone.

The ShortNameId side table may use hashing for performance, but it is not a
dynamic visibility namespace: its key is a concrete node address and its value
does not change with call nesting. Runtime merge changes the containment tree,
parent links and available structural paths; it does not merge call-scope
tables.

RU

При входе метод загружает в рабочие C locals только собственные поля,
используемые через неквалифицированные own-bindings, и очищает их runtime dirty
flags. Явные пути продолжают обращаться прямо к графу. Фактическая локальная
запись или перепривязка ссылки помечает соответствующее собственное поле dirty.
На каждой semantic boundary из 6.5 только dirty собственные поля публикуются в
выбранный `callable->node`; каждый флаг очищается после успешной записи. Чистые
кэшированные поля не должны затирать изменения графа, сделанные вложенным
вызовом или явным путём. Автоматической перезагрузки после вызова нет:
неквалифицированный local сохраняет snapshot своей активации, тогда как явный
путь графа наблюдает текущее состояние графа.

При входе и return нет push/pop либо cleanup объекта namespace. Сам стек C
создаёт и уничтожает слоты скрытых сквозных значений и рабочие locals. Поэтому
рекурсии и callbacks не нужен отдельный стек namespace. Однако активации через
один callable-occurrence делают checkpoint в одну и ту же опубликованную
containing Structure, поэтому рекурсивные или взаимно рекурсивные активации
намеренно перезаписывают это рабочее опубликованное состояние. Сохраняемая либо
ветвящаяся история активаций обязана быть явной Structure, Array или Message, а
не неявным namespace или per-call клоном графа.

Side table ShortNameId может использовать hashing для производительности, но
она не является namespace динамической видимости: её ключ — конкретный адрес
узла, а значение не меняется из-за вложенности вызовов. Runtime merge меняет
дерево вложенности, родительские ссылки и доступные структурные пути; он не
мержит таблицы scope вызовов.


9.3. L3 Message concurrency is semantic
L3 Message-конкурентность является семантикой
------------------------------------------------

EN

The scalable concurrency unit of common LMX is a Message. A Message owns one
arena and, while admitted for execution, is an L3 Thread. Each L3 Thread has an
ordered FIFO inbox and stages outgoing Messages in FIFO order. It executes at
most one turn at a time; one turn consumes at most one admitted input Message,
updates only state owned by that Message arena, stages output and reaches the
common turn boundary. Another turn of the same L3 Thread cannot overlap it.

At that boundary a successful turn publishes its staged outbox in FIFO order;
a failed turn rolls the staged outbox back. The current inbox item and
turn-local roots are then released as required, and collection runs locally for
that Message arena. Ordinary `return`, loop transfer or nested call return is
not a collection boundary. Termination completes the final boundary and then
releases the Message arena after surviving transfers and explicit resource
cleanup.

Different L3 Threads may run concurrently. They may be mapped to one
cooperative host loop, a fixed worker pool or other host machinery and may move
between workers from turn to turn. That mapping is not source-visible, but the
one-arena ownership, FIFO order and absence of overlapping turns for one L3
Thread are source-semantic guarantees.

This is why common L3 requires no portable shared-memory synchronization
algorithm. Mutable Lmx nodes of one running Message are not directly mutated by
another running Message. Interaction is an explicit Message transfer. A
transport may be an in-process queue, HTTP, a file, radio or physical mail;
transport latency and representation do not change the Message boundary.

L2 may deliberately expose a raw OS thread, shared address, atomic, mutex,
condition or custom scheduler. Such a program must state and prove its own
memory, ordering, cancellation and lifetime rules. It is a low-level individual
engineering solution, not a synchronization rule that can be lifted into
common LMX or Mix.

Consequently the procedural Java Mix implementation must not be preserved by
translating its locks and independently running cursor threads one-for-one.
Mix's portable/common operations, cursors, mirrors and mutations must be
re-expressed as Message-owned state and FIFO Message interactions. Optional
distributed coordination protocols may themselves be explicit Messages, but
no local Java mutex or OS-thread identity becomes Mix semantics.

RU

Единицей масштабируемой конкурентности общего LMX является Message. Message
владеет одной arena и во время допуска к исполнению является L3 Thread. Каждый
L3 Thread имеет упорядоченный FIFO inbox и подготавливает исходящие Messages в
FIFO-порядке. Он исполняет не более одного turn одновременно; один turn
потребляет не более одного допущенного входного Message, изменяет только
состояние, принадлежащее arena этого Message, подготавливает выход и достигает
общей границы turn. Другой turn того же L3 Thread не может пересекаться с ним.

На этой границе успешный turn публикует подготовленный outbox в FIFO-порядке,
а failed turn откатывает его. Затем освобождаются текущий inbox item и
turn-local roots, когда это требуется, и локально запускается collection arena
этого Message. Обычный `return`, переход цикла или return вложенного вызова не
является границей collection. Termination завершает последнюю границу и затем
освобождает arena Message после surviving transfers и явного cleanup ресурсов.

Разные L3 Threads могут работать параллельно. Они могут отображаться на один
кооперативный host loop, фиксированный worker pool или другой host-механизм и
переезжать между workers от turn к turn. Это отображение не видно исходнику, но
владение одной arena, FIFO-порядок и отсутствие пересекающихся turns одного L3
Thread являются гарантиями исходной семантики.

Именно поэтому общему L3 не требуется переносимый алгоритм shared-memory
синхронизации. Изменяемые Lmx-узлы одного исполняемого Message не изменяются
напрямую другим исполняемым Message. Взаимодействие является явной передачей
Message. Транспортом может быть внутрипроцессная очередь, HTTP, файл, радио или
физическая почта; задержка и представление транспорта не меняют границу
Message.

L2 может намеренно открыть raw OS thread, общий адрес, atomic, mutex, condition
или custom scheduler. Такая программа обязана сама задать и доказать правила
памяти, порядка, cancellation и lifetime. Это низкоуровневое индивидуальное
инженерное решение, а не правило синхронизации, которое можно поднять в общий
LMX или Mix.

Следовательно, процедурную Java-реализацию Mix нельзя сохранять посредством
буквального переноса её локов и независимо работающих cursor threads.
Переносимые/общие операции, курсоры, зеркала и изменения Mix должны быть
выражены заново как принадлежащее Messages состояние и FIFO-взаимодействия
Messages. Необязательные протоколы распределённой координации сами могут быть
явными Messages, но локальный Java mutex или identity OS-thread не становится
семантикой Mix.


10. Required conceptual runtime operations
Обязательные концептуальные операции runtime
================================================

EN

The exact C spellings are not fixed, but the runtime must provide the
equivalent of these operations:

1. Allocate a stable Lmx node or bounded Lmx subtree.
2. Establish and validate the `node` parent relation.
3. Register `Lmx * -> ShortNameId` and remove or invalidate that registration at
   the end of the node lifetime.
4. Derive the owning Message and its one arena from the reserved `node` address
   or equivalent allocation-range metadata, without an ambient generated-method
   argument.
5. Find a root by following `node`.
6. Classify `data` by address range.
7. Enumerate structural children using `data` and `len`.
8. Find a child occurrence by ShortNameId, including indexed repeated names.
9. Resolve an arbitrary textual absolute path from an explicit root and an
   explicit relative path from its supplied Structure.
10. Interpret reserved `node\field` from the callable occurrence's immediate
    parent and use it as fallback for a required unqualified name absent from
    the current caller.
11. Resolve a callable payload to an immutable `all_methods_array` record
    `{addr, sig}`, verify exact call-site compatibility with `sig`, and invoke
    `addr` with the reserved `callable->node`, declared operands and exact hidden
    through values.
12. Copy primitive through values by semantic value and Structure/Array through
    values by reference value, without automatic write-back on return.
13. At method entry, load only used own fields into C working locals and
    initialize their runtime dirty flags clear.
14. Mark an own field dirty only when its working local is actually written or
    rebound; at every semantic boundary defined by 6.5 and every
    `return`/`throw`, store only dirty own fields and clear each flag after its
    store succeeds.
15. Resume after a call without automatically reloading working locals.
16. Copy a containment tree while rebasing `node` and copying name IDs.
17. Merge ordered runtime trees and a runtime body into a fresh result in the
    current Message arena.
18. Admit incoming Messages into a per-L3-Thread FIFO, execute no more than one
    turn of the same L3 Thread concurrently, and publish staged output in FIFO
    order.
19. At the common end-turn boundary, publish or roll back the outbox first and
    then collect the owning Message arena; release the arena at Message
    termination after required transfer/cleanup.

These operations may be fused or specialized. Their observable behavior may
not depend on a per-Structure descriptor, C typedef or separately allocated
runtime Name-to-Binding namespace object.

RU

Точные имена в C не закреплены, но runtime обязан предоставлять эквивалент
следующих операций:

1. Выделить стабильный Lmx-узел или ограниченное поддерево Lmx.
2. Установить и проверить родительское отношение `node`.
3. Зарегистрировать `Lmx * -> ShortNameId` и удалить либо инвалидировать эту
   регистрацию в конце lifetime узла.
4. Определить Message-владельца и его единственную arena по адресу
   зарезервированного `node` либо эквивалентным metadata диапазона allocation,
   не добавляя ambient-аргумент сгенерированного метода.
5. Найти root последовательным переходом `node`.
6. Классифицировать `data` по диапазону адреса.
7. Перечислить структурных детей с помощью `data` и `len`.
8. Найти occurrence ребёнка по ShortNameId, включая индексированные повторные
   имена.
9. Разрешить произвольный текстовый абсолютный путь от явно переданного root и
   явный относительный путь от переданной Structure.
10. Интерпретировать зарезервированный `node\field` от непосредственного
    родителя occurrence callable и использовать его как fallback требуемого
    неквалифицированного имени, отсутствующего у текущего вызывающего.
11. Разрешить payload callable в неизменяемую запись `all_methods_array`
    `{addr, sig}`, проверить точную совместимость call site с `sig` и вызвать
    `addr` с зарезервированным `callable->node`, объявленными operands и точными
    скрытыми сквозными значениями.
12. Копировать сквозные примитивы по семантическому значению, а сквозные
    Structure/Array — по значению ссылки, без автоматической обратной записи при
    return.
13. При входе в метод загружать только используемые собственные поля в рабочие
    C locals и инициализировать их runtime dirty flags как clean.
14. Помечать собственное поле dirty только при фактической записи либо
    перепривязке его рабочего local; на каждой semantic boundary из 6.5 и перед каждым
    `return`/`throw` записывать только dirty собственные поля и очищать каждый
    flag после успешной записи.
15. После вызова продолжать исполнение без автоматической перезагрузки рабочих
    locals.
16. Скопировать дерево вложенности с rebasing `node` и копированием name ID.
17. Смержить упорядоченные runtime-деревья и runtime-тело в новый результат в
    текущей arena Message.
18. Принимать входящие Messages в FIFO каждого L3 Thread, не исполнять
    одновременно более одного turn того же L3 Thread и публиковать
    подготовленный выход в FIFO-порядке.
19. На общей границе end-turn сначала публиковать либо откатывать outbox, затем
    выполнять collection arena Message-владельца; при termination освобождать
    arena после обязательного transfer/cleanup.

Эти операции можно объединять или специализировать. Их наблюдаемое поведение
не может зависеть от descriptor конкретной Structure, C typedef или отдельно
выделенного runtime-объекта namespace Name-to-Binding.


11. Translator pipeline required by this architecture
Pipeline транслятора, требуемый архитектурой
================================================

11.1. Structural outline
Структурная схема
----------------------

EN

The replacement core has the following conceptual stages:

1. Receive the unchanged parser tree and walk the complete current source unit
   recursively, including executable bodies at every nesting depth.
2. Assign deterministic ShortNameId values or references to the short-name
   identity mechanism.
3. Assign a deterministic collision-free program-wide identity to every
   executable method body, preferably a complete-path-mangled C spelling.
4. Analyze each method's declared operands, used own fields, actual local write
   sites, unqualified through-name requirements and statically known forwarding
   requirements of its callees.
5. Construct the exact callable signature from reserved `node`, declared
   operands, hidden through values and the chosen result convention; derive an
   exact expected signature at every callable call site.
6. Emit declarations for every program-wide method and immutable
   `all_methods_array` records `{addr, sig}` which make each implementation
   reachable through the common callable physical class.
7. Emit each method body with its exact C prototype. At entry, load only used
   own fields into C working locals and initialize per-local runtime dirty flags.
8. Emit actual-write dirty marking and a dirty-only publication checkpoint at
   every semantic boundary defined by 6.5 and every `return`/`throw`; emit no automatic post-call
   reload and no automatic through-value write-back.
9. At each call site, resolve/validate the callable record, evaluate declared
   operands and hidden through values according to the exact expected signature,
   and pass reserved `callable->node` as the non-replaceable first input.
10. Emit runtime builders/evaluators for explicit Structure, Array and Message
    expressions. C working locals remain activation storage rather than fresh
    implicit Lmx graph nodes.
11. Preserve merge as a runtime call at its execution position and register
    newly constructed named nodes in the sole reverse side table.
12. Emit direct-reference and relative structural traversal where the source
    has a resolved/current Lmx pointer; emit root-based traversal only for an
    explicitly absolute/arbitrary textual path. Never emit ordinary Structure
    access as a generated C member access.

This outline does not require multiple compiler passes with these exact
names. It specifies information flow and effects.

RU

Новое ядро имеет следующие концептуальные стадии:

1. Получить неизменённое дерево parser-а и рекурсивно обойти всю текущую
   единицу исходника, включая исполняемые тела на любой глубине вложенности.
2. Назначить детерминированные ShortNameId или ссылки на механизм identity
   короткого имени.
3. Назначить каждому исполняемому телу метода детерминированную уникальную во
   всей программе identity, предпочтительно C-spelling, mangled из полного
   пути.
4. Проанализировать объявленные operands, используемые собственные поля,
   места фактических локальных записей, требования неквалифицированных
   сквозных имён и статически известные требования forwarding его callees.
5. Построить точную сигнатуру callable из зарезервированного `node`,
   объявленных operands, скрытых сквозных значений и выбранного соглашения
   результата; получить точную ожидаемую сигнатуру каждого call site callable.
6. Выдать объявления всех глобально достижимых методов и неизменяемые записи
   `all_methods_array` `{addr, sig}`, делающие каждую реализацию доступной через
   общую физическую категорию callable.
7. Выдать тело каждого метода с его точным прототипом C. При входе загрузить
   только используемые собственные поля в рабочие C locals и
   инициализировать runtime dirty flag каждого такого local.
8. Выдать marking dirty при фактических записях и dirty-only checkpoint
   публикации на каждой semantic boundary из 6.5 и перед каждым `return`/`throw`; не выдавать
   автоматическую post-call перезагрузку или обратную запись сквозных значений.
9. В каждом call site разрешить/проверить запись callable, вычислить
   объявленные operands и скрытые сквозные значения по точной ожидаемой
   сигнатуре и передать не заменяемый `callable->node` первым входом.
10. Выдать runtime builders/evaluators для явных выражений Structure, Array и
    Message. Рабочие C locals остаются хранилищем активации, а не новыми
    неявными Lmx-узлами графа.
11. Сохранить merge как runtime-вызов в его позиции исполнения и выдавать
    регистрацию новых именованных узлов в единственной обратной side table.
12. Выдать direct-reference и относительный структурный traversal там, где
    исходник имеет разрешённый/current Lmx-указатель; traversal от root
    выдавать только для явно абсолютного/произвольного текстового пути.
    Обычный доступ к Structure никогда не выдавать как generated C member.

Эта схема не требует compiler passes именно с такими названиями. Она задаёт
поток информации и эффекты.


11.2. Static knowledge the translator may use
Допустимое статическое знание транслятора
----------------------------------------------

EN

Rejecting static Structure type analysis does not require the translator to
forget syntax. It may and must know:

* the parser-tree nesting and source positions;
* the spelling of path components;
* which parsed forms define executable bodies;
* the source order of children and merge inputs;
* constant ShortNameId values for constant path components;
* which program-wide method identity/entry implements a source method;
* which runtime helper implements a source operation;
* which own fields a method body actually reads or writes and which writes mark
  their working locals dirty;
* which unqualified values the method requires from a caller, including the
  exact forwarded requirements of statically known callees;
* the value category and order of declared and hidden inputs, the result
  convention, and therefore the exact method/call-site signature;
* which callable leaf of an `implements(A, B, Consumer)` check is actually used
  and which exact signature that leaf requires.

It must not turn that knowledge into a mandatory closed C layout for a
Structure. Syntax knowledge selects generic runtime operations; it does not
create source-level C types.

RU

Отказ от статического анализа типа Structure не требует, чтобы транслятор
забыл синтаксис. Он может и обязан знать:

* вложенность дерева parser-а и позиции исходника;
* spelling компонентов пути;
* какие распарсенные формы определяют исполняемые тела;
* порядок детей и входов merge в исходнике;
* константные ShortNameId константных компонентов пути;
* какой глобальный C-символ реализует метод исходника;
* какой runtime helper реализует операцию исходника;
* какие собственные поля тело метода фактически читает либо пишет и какие
  записи помечают их рабочие locals dirty;
* какие неквалифицированные значения метод требует от вызывающего, включая
  точные forwarded-требования статически известных callees;
* категорию значения и порядок объявленных и скрытых входов, соглашение
  результата и, следовательно, точную сигнатуру метода/call site;
* какой callable leaf проверки `implements(A, B, Consumer)` фактически
  используется и какую точную сигнатуру этот leaf требует.

Он не должен превращать это знание в обязательный закрытый C-layout
Structure. Знание синтаксиса выбирает общие runtime-операции, а не создаёт
C-типы уровня исходника.


11.3. Nested callable emission
Эмиссия вложенных callable
-------------------------------

EN

The recursive source walk must treat an executable body as executable
regardless of its nesting depth. A method nested in Array receives its own
global path-mangled implementation symbol.

The node created for that method at runtime stores in `data` a callable-domain
payload identifying an immutable `all_methods_array` record `{addr, sig}`. The
record provides the implementation address and its exact callable signature;
neither value is a per-Structure descriptor. The node's ShortNameId is stored
only in the reverse side table. Its reserved `node` link records the concrete
immediate parent in that runtime tree and becomes the first input when the
callable is invoked.

A descriptor-only callable declaration without a body must not silently
receive a fake executable implementation. Its exact non-executable runtime
form is UNRESOLVED if not already specified elsewhere.

RU

Рекурсивный обход исходника обязан считать исполняемое тело исполняемым
независимо от глубины вложенности. Метод внутри Array получает собственный
глобальный path-mangled символ реализации.

Узел, создаваемый для этого метода в runtime, хранит в `data` payload
callable-домена, идентифицирующий неизменяемую запись `all_methods_array`
`{addr, sig}`. Запись предоставляет адрес реализации и точную сигнатуру
callable; ни одно из этих значений не является descriptor конкретной Structure.
ShortNameId узла хранится только в обратной side table. Его зарезервированная
ссылка `node` записывает конкретного непосредственного родителя в этом
runtime-дереве и становится первым входом при вызове callable.

Callable-декларация без тела, содержащая только описание, не должна молча
получать фальшивую исполняемую реализацию. Её точная неисполняемая
runtime-форма остаётся UNRESOLVED, если не определена отдельно.


12. Prohibited implementation shortcuts
Запрещённые сокращения реализации
======================================

EN

The following are explicitly non-conforming:

1. Generating one typedef struct per named source Structure.
2. Placing a descriptor pointer, tag or name inside every Lmx node.
3. Emitting field access as a fixed C member offset that fails after dynamic
   merge.
4. Treating fn or sub inside a Structure as metadata while omitting its body.
5. Generating a zero-returning stub for an un-emitted nested method.
6. Translating merge by concatenating C member declarations.
7. Performing merge during translation or program startup when source control
   has not reached it.
8. Representing a merge result as references to source containment children
   instead of a new copied tree.
9. Treating reserved `node` as an ordinary declared/hidden argument which the
   caller may replace, shadow or rebind, or interpreting `node\field` with a
   second parent hop after `callable->node`.
10. Omitting a required through value from the exact C signature and recovering
    it from a global, thread-local, mutable Name-to-Binding table or overlay.
11. Passing a primitive through value as a caller-writable cell, automatically
    writing back any through value on return, or making callee reference
    rebinding change the caller's binding.
12. Materializing each implicit activation local as a fresh Lmx graph node, or
    conversely keeping dirty method state only in C locals across a mandatory
    publication checkpoint.
13. Loading unused own method fields merely because they exist in the method
    Structure.
14. Deciding dirty state from static may-write analysis, from value inequality,
    or from branch reachability instead of the runtime event of an actual local
    write/rebind.
15. Flushing all loaded fields, flushing a clean cached field, omitting a dirty
    flush at any semantic boundary defined by section 6.5 or at an
    activation-destroying `return`/`throw`, or clearing a dirty flag before its
    store succeeds.
16. Automatically reloading C working locals after a call or automatically
    reconciling them with explicit graph mutation.
17. Creating closure/lexical-environment structs, per-call Lmx activation
    clones or another implicit activation log as the semantics of nested calls.
18. Implementing dynamic caller visibility with a runtime namespace stack,
    Name-to-Binding dictionary or overlay object.
19. Adding a second per-node metadata map for type, descriptor, layout, path,
    owner or callable signature. A program-wide immutable method record is not
    per-node metadata.
20. Erasing callable prototypes into one universal one-pointer or variadic C
    type, invoking a method through an incompatible function-pointer type, or
    accepting a runtime `sig` mismatch.
21. Declaring `implements(A, B, Consumer)` successful while a callable leaf that
    is actually used at the Consumer site has an incompatible exact signature.
22. Looking up an arbitrary textual absolute path relative to whichever C
    function happens to execute instead of using its explicitly supplied Lmx
    root. This prohibition does not redirect relative/direct-reference
    traversal to root.
23. Giving method symbols short names that can collide across files or nested
    Structures.
24. Depending on a whole-directory translation scan to know the shape of a
    merge input.
25. Calling a compiler from runtime merge.
26. Classifying a `data` payload by a per-Structure generated type rather than
    its address range.
27. Allowing two turns of one Message to overlap or sharing its mutable arena
    tree with another concurrently running Message without a full explicit
    clone and Message transfer.
28. Treating `retry` as a call checkpoint or destroying/reconstructing ordinary
    call-stack and dirty-local state merely because execution yields.

RU

Следующее явно не соответствует архитектуре:

1. Генерация отдельного typedef struct для каждой именованной Structure.
2. Размещение descriptor pointer, tag или имени внутри каждого Lmx-узла.
3. Эмиссия доступа к полю как фиксированного C member offset, перестающего
   работать после динамического merge.
4. Обращение с fn или sub внутри Structure как с metadata при пропуске тела.
5. Генерация возвращающей ноль заглушки вместо неэмитированного вложенного
   метода.
6. Трансляция merge конкатенацией объявлений C members.
7. Выполнение merge во время трансляции или старта программы, когда управление
   исходника до него не дошло.
8. Представление результата merge ссылками на исходных детей вложенности
   вместо нового скопированного дерева.
9. Обращение с зарезервированным `node` как с обычным объявленным/скрытым
   аргументом, который вызывающий может заменить, shadow или rebind, либо
   интерпретация `node\field` со вторым подъёмом к родителю после
   `callable->node`.
10. Пропуск требуемого сквозного значения из точной сигнатуры C с последующим
    восстановлением из global/thread-local изменяемой таблицы, dictionary или
    overlay Name-to-Binding.
11. Передача сквозного примитива как доступной для записи ячейки вызывающего,
    автоматическая обратная запись любого сквозного значения при return либо
    изменение binding вызывающего при перепривязке ссылки вызываемым.
12. Материализация каждого неявного local активации как свежего Lmx-узла графа
    либо, наоборот, сохранение dirty-состояния метода только в C locals через
    обязательную границу публикации.
13. Загрузка неиспользуемых собственных полей метода только потому, что они
    присутствуют в Structure метода.
14. Определение dirty по статическому may-write, неравенству значений или
    достижимости ветки вместо runtime-события фактической записи/rebind local.
15. Flush всех загруженных полей, flush чистого кэшированного поля, пропуск
    dirty flush на любой semantic boundary из раздела 6.5 либо при уничтожающем
    activation `return`/`throw`, либо очистка dirty flag до успешной записи.
16. Автоматическая перезагрузка рабочих C locals после вызова либо их
    автоматическое согласование с явным изменением графа.
17. Создание closure/lexical-environment structs, per-call клонов Lmx-активации
    или другого неявного журнала активаций как семантики вложенных вызовов.
18. Реализация динамической видимости вызывающего runtime-стеком namespace,
    dictionary Name-to-Binding либо объектом overlay.
19. Добавление второй per-node map для type, descriptor, layout, path, owner
    или callable signature. Глобальная неизменяемая запись метода не является
    per-node metadata.
20. Стирание прототипов callable в один универсальный one-pointer либо variadic
    C-тип, вызов метода через несовместимый function-pointer type или принятие
    несовпадения runtime `sig`.
21. Признание `implements(A, B, Consumer)` успешным, когда фактически
    используемый в Consumer call site callable leaf имеет несовместимую точную
    сигнатуру.
22. Поиск произвольного текстового абсолютного пути относительно случайно
    исполняемой C-функции вместо использования явно переданного root Lmx. Этот
    запрет не перенаправляет относительный/direct-reference traversal к root.
23. Короткие имена символов методов, способные столкнуться между файлами или
    вложенными Structure.
24. Зависимость от сканирования всей директории для знания shape входа merge.
25. Вызов компилятора из runtime merge.
26. Классификация payload `data` по generated type конкретной Structure вместо
    диапазона адреса.
27. Пересечение двух turns одного Message либо совместное использование его
    mutable arena-дерева другим параллельно исполняемым Message без полного
    явного clone и передачи Message.
28. Обращение с `retry` как с checkpoint вызова либо уничтожение/пересоздание
    обычного состояния стека вызовов и dirty locals только из-за `yield`.


13. Conformance examples and required tests
Примеры соответствия и обязательные тесты
=============================================

13.1. Uniform primitive leaf
Единый примитивный лист
----------------------------

EN

Given a char field containing exclamation mark:

* the field itself is an Lmx node;
* its node points to its concrete containing parent;
* its Lmx address maps to the ShortNameId for char;
* its data points at all_chars['!'];
* no char member is embedded in a generated Structure typedef;
* copying the tree creates a new field Lmx and copies the canonical character
  pointer.

RU

Для поля char, содержащего восклицательный знак:

* само поле является Lmx-узлом;
* его node указывает на конкретного содержащего родителя;
* адрес его Lmx отображается в ShortNameId для char;
* его data указывает на all_chars['!'];
* member char не встраивается в generated typedef Structure;
* копирование дерева создаёт новый Lmx поля и копирует указатель на
  канонический символ.


13.2. Nested live method
Живой вложенный метод
--------------------------

EN

A method Array/resize nested inside Array must:

* produce one program-wide reachable C entry with a deterministic unique name,
  preferably including the source unit and Array/resize path;
* be available through the common callable physical class;
* have an exact C prototype whose first input is reserved `node` and whose
  remaining declared and hidden through inputs match its immutable `sig`;
* have its actual source body emitted;
* be referenced by the callable-domain payload in `data` of its runtime method
  node through an `all_methods_array` record `{addr, sig}`;
* execute the real body when resolved and invoked.

A test that merely finds a similarly named C stub is insufficient.

RU

Метод Array/resize внутри Array обязан:

* породить один достижимый во всей программе C-entry с детерминированным
  уникальным именем, предпочтительно включающим единицу исходника и путь
  Array/resize;
* быть доступным через общую физическую категорию callable;
* иметь точный C-прототип, первым входом которого является зарезервированный
  `node`, а остальные объявленные и скрытые сквозные входы соответствуют его
  неизменяемому `sig`;
* иметь сэмитированное настоящее тело исходника;
* адресоваться через callable-domain payload в `data` его runtime-узла метода
  посредством записи `all_methods_array` `{addr, sig}`;
* исполнять настоящее тело при разрешении пути и вызове.

Теста, который только находит похожую по имени C-заглушку, недостаточно.


13.3. Runtime HashArray merge
Runtime merge HashArray
----------------------------

EN

A conformance test must demonstrate:

1. Translating HashArray does not emit a HashArray C struct containing Array
   members.
2. Before control reaches merge, no merged HashArray tree has been allocated.
3. Reaching merge allocates a new tree.
4. Array's direct children are copied directly under the HashArray result root;
   no additional Array root child is inserted.
5. Every copied child's node points into the new tree.
6. Every named copied node has the correct ShortNameId side-table entry, with
   the selected positional convention applied to unnamed occurrences.
7. Array method nodes in the result retain callable payloads resolving to the
   original immutable `{addr, sig}` method records.
8. Invoking a copied Array method validates the exact expected `sig`, supplies
   `copied_callable->node` as reserved `node` (the new HashArray containing
   Structure), and supplies every declared and hidden operand required by that
   signature.
9. The source Array tree remains structurally unchanged.
10. The resulting HashArray can itself be an input to another merge.

RU

Тест соответствия обязан показать:

1. Трансляция HashArray не выдаёт C struct HashArray с members Array.
2. До достижения merge управление не выделяло merged-дерево HashArray.
3. Достижение merge выделяет новое дерево.
4. Прямые дети Array копируются непосредственно под root результата
   HashArray; дополнительный ребёнок-root Array не вставляется.
5. node каждого скопированного ребёнка указывает внутрь нового дерева.
6. Каждый именованный скопированный узел имеет правильную запись ShortNameId
   в side table; к безымянным применяется выбранное positional-соглашение.
7. Узлы методов Array в результате сохраняют callable payloads, разрешаемые в
   исходные неизменяемые записи методов `{addr, sig}`.
8. Вызов скопированного метода проверяет точный ожидаемый `sig`, предоставляет
   `copied_callable->node` как зарезервированный `node` (новую содержащую
   Structure HashArray) и предоставляет все объявленные и скрытые operands,
   требуемые этой сигнатурой.
9. Исходное дерево Array структурно не меняется.
10. Получившийся HashArray сам может быть входом следующего merge.


13.4. Root lookup
Поиск от корня
-------------------

EN

A path test must create at least three nested levels, supply the same explicit
root and arbitrary textual absolute path from method contexts at different
depths, and obtain the same root-selected node. A separate test must prove that
reserved `node` equals the concrete `callable->node` occurrence parent and that
`node\field` selects its immediate child without another parent hop and without
resetting to root. Both must continue to pass after runtime merge rebases the
callable and adds repeated short names.

Structural path resolution must be independent of C working locals and hidden
through-value slots. Conversely, unqualified dynamic caller visibility must be
implemented by those exact C slots rather than by structural lookup, except for
the defined immediate `node\field` fallback.

RU

Тест пути обязан создать как минимум три уровня вложенности, передать один и
тот же явный root и произвольный текстовый абсолютный путь из контекстов
методов на разной глубине и получить один и тот же выбранный от корня узел.
Отдельный тест обязан доказать, что зарезервированный `node` равен конкретному
родителю occurrence `callable->node`, а `node\field` выбирает его
непосредственного ребёнка без второго подъёма к родителю и без сброса к root.
Оба обязаны продолжать работать после runtime merge, который rebases callable
и добавляет повторные короткие имена.

Разрешение структурного пути обязано быть независимо от рабочих C locals и
слотов скрытых сквозных значений. И наоборот, неквалифицированная динамическая
видимость вызывающего должна реализовываться этими точными C-слотами, а не
структурным lookup, кроме определённого fallback к непосредственному
`node\field`.


13.5. C working locals and dirty publication
Рабочие C locals и dirty-публикация
--------------------------------------

EN

Required tests must demonstrate all of the following:

* method entry loads only own fields actually used through unqualified own
  bindings; an explicit graph path is never replaced by the no-reload cache,
  and an unused own field is neither loaded nor spuriously stored;
* every loaded field starts clean, an actually executed write/rebind marks it
  dirty even when the assigned value compares equal, and a write in an untaken
  branch does not mark it dirty;
* at each 6.5 LMX/observable-call, yield and activation-exit boundary, dirty own
  fields are stored and each flag is cleared only after its store succeeds;
* a `return`/`throw` with `finally` checkpoints pre-cleanup state and then
  checkpoints cleanup writes immediately before the C activation disappears;
* an induced checkpoint-store failure follows the profile selected under
  14.23, exposes exactly the stores/dirty flags that policy declares, and never
  enters the intended call/normal exit after incomplete publication;
* a clean cached field is not flushed. In particular, if a nested callee uses an
  explicit reference/path to mutate that field's graph node, a later checkpoint
  for another dirty field does not overwrite the nested mutation;
* after that call, the unqualified C local still holds its entry/current-
  activation snapshot while an explicit path observes the new graph value;
  there is no automatic reload or reconciliation;
* an explicit write to the local after return marks it dirty and intentionally
  publishes over the then-current graph value at the next checkpoint.

RU

Обязательные тесты должны показать всё следующее:

* при входе метод загружает только собственные поля, фактически используемые
  через неквалифицированные own-bindings; явный graph path не заменяется
  no-reload cache, а неиспользуемое собственное поле не загружается и ложно не
  записывается;
* каждое загруженное поле начинает clean, фактически исполненная запись/rebind
  помечает его dirty даже при равном присваиваемом значении, а запись в
  непройденной ветке не помечает dirty;
* на каждой semantic boundary, yield и activation-exit из 6.5 dirty
  собственные поля записываются, а каждый flag очищается только после успешной
  записи;
* `return`/`throw` с `finally` checkpoint-ит pre-cleanup state, а затем прямо
  перед исчезновением C-activation checkpoint-ит записи cleanup;
* искусственно вызванный failure checkpoint-store следует выбранной по 14.23
  policy, показывает ровно объявленные ею stores/dirty flags и не переходит к
  предполагаемому call/normal exit после неполной публикации;
* clean кэшированное поле не flush-ится. В частности, если nested callee через
  явную ссылку/путь изменил узел графа этого поля, последующий checkpoint ради
  другого dirty-поля не затирает nested-изменение;
* после такого вызова неквалифицированный C local всё ещё хранит snapshot
  входа/текущей activation, тогда как явный путь видит новое значение графа;
  автоматического reload или согласования нет;
* явная запись local после return помечает его dirty и намеренно публикует
  поверх текущего значения графа при следующем checkpoint.


13.6. Generated-C structural checks
Структурные проверки сгенерированного C
-------------------------------------------

EN

Automated checks SHOULD reject generated output containing architecture
regressions such as:

* per-source-Structure typedef struct definitions;
* descriptor fields in Lmx;
* generated runtime Name-to-Binding namespace push/pop calls;
* closure environment structs or fresh per-call Lmx activation graphs for
  implicit working locals;
* nested-method stubs;
* erased one-pointer/variadic source-method signatures, missing hidden through
  operands or an invocation through an incompatible C function-pointer type;
* eager loads of unused own fields, unconditional all-field flushes, static
  dirty decisions or automatic post-call reloads;
* compile-time-expanded merge members;
* direct C member access used as the only implementation of a dynamic source
  path.

Positive checks should verify symbol uniqueness, immutable
`all_methods_array {addr,sig}` membership, exact call-site validation, root
lookup, side-table population, runtime merge timing and the dirty-only
checkpoint rules.

RU

Автоматические проверки должны отвергать generated output со следующими
архитектурными регрессиями:

* typedef struct на каждую Structure исходника;
* descriptor fields в Lmx;
* сгенерированные runtime-вызовы push/pop namespace Name-to-Binding;
* structs closure environment или свежие per-call Lmx-графы активации для
  неявных рабочих locals;
* заглушки вложенных методов;
* стёртые one-pointer/variadic сигнатуры методов, отсутствующие скрытые
  сквозные operands или вызов через несовместимый тип function pointer C;
* eager-загрузки неиспользуемых собственных полей, безусловные flush всех
  полей, статическое определение dirty либо автоматический post-call reload;
* раскрытые во время трансляции members merge;
* прямой C member access как единственную реализацию динамического пути
  исходника.

Положительные проверки должны подтверждать уникальность символов, присутствие
в неизменяемом `all_methods_array {addr,sig}`, точную проверку call site, lookup
от root, заполнение side table, timing runtime merge и правила dirty-only
checkpoint.


13.7. Through values, fallback and `implements`
Сквозные значения, fallback и `implements`
------------------------------------------------

EN

A call-chain test must pass an unqualified primitive and an unqualified
Structure/Array reference through at least two nested methods. It must prove
that the primitive is copied by semantic value, the reference value is copied
as-is, local rebinding changes neither caller binding, and mutation occurs only
when the callee uses an explicit path through the copied reference. Nothing is
automatically written back on return.

The same test must omit one required caller binding and prove that the callee
uses its immediate `node\name` field, not a transitive lexical ancestor. It
must also compare two implementations in an `implements(A, B, Consumer)` site:
different `addr` values with exactly equal canonical `sig` are accepted, while
a mismatched signature of the callable leaf actually used by Consumer is
rejected. An unused callable leaf imposes no compatibility requirement.

RU

Тест цепочки вызовов обязан передать неквалифицированный примитив и
неквалифицированную ссылку Structure/Array сквозь как минимум два вложенных
метода. Он обязан доказать, что примитив копируется по семантическому значению,
значение ссылки копируется как есть, локальная перепривязка не меняет ни один
binding вызывающего, а изменение происходит только при использовании
вызываемым явного пути через скопированную ссылку. При return ничего
автоматически не записывается обратно.

Тот же тест обязан пропустить один требуемый binding вызывающего и доказать,
что вызываемый использует своё непосредственное поле `node\name`, а не
сквозного лексического предка. Он также обязан сравнить две реализации в call
site `implements(A, B, Consumer)`: разные значения `addr` с точно равным
canonical `sig` принимаются, а несовпавшая сигнатура фактически используемого Consumer
callable leaf отвергается. Неиспользуемый callable leaf не накладывает
требования совместимости.


13.8. Activation history, recursion, `yield`, `retry` and Messages
История activation, recursion, `yield`, `retry` и Messages
-----------------------------------------------------------

EN

A recursive and mutually recursive test must prove that ordinary C stack
frames keep each activation's local snapshots and dirty flags, while every
pre-call checkpoint through one callable occurrence publishes into the same
containing Structure. A
nested activation may therefore overwrite published method state without
destroying the suspended caller's locals; no implicit activation history may
be reconstructed from that Structure. A version requiring history must use an
explicit Structure, Array or Message.

A suspension test must show that `yield` preserves the ordinary continuation,
working locals and dirty flags. A `retry` containing no actual call creates no
frame and triggers no pre-call checkpoint. Message tests must additionally show
that one Message turn has no concurrent peer mutating its arena tree, that
sharing with another running Message requires full explicit clone/transfer, and
that FIFO/end-turn rules remain unchanged.

RU

Recursive- и mutual-recursive-тест обязан доказать, что обычные frames стека C
сохраняют snapshots locals и dirty flags каждой activation, тогда как каждый
pre-call checkpoint публикует в один и тот же occurrence Structure метода.
Поэтому nested activation может перезаписать опубликованное состояние метода,
не уничтожая locals приостановленного вызывающего; из этой Structure нельзя
восстанавливать неявную историю activation. Вариант, которому нужна история,
обязан использовать явную Structure, Array или Message.

Тест приостановки обязан показать, что `yield` сохраняет обычную continuation,
рабочие locals и dirty flags. `retry`, не содержащий фактического вызова, не
создаёт frame и не запускает pre-call checkpoint. Message-тесты дополнительно
обязаны показать, что у одного turn Message нет конкурентного соседа,
изменяющего его arena-дерево, что sharing с другим исполняемым Message требует
полного явного clone/transfer и что правила FIFO/end-turn не меняются.


14. Explicitly unresolved items
Явно неразрешённые вопросы
=============================

EN

This section is exhaustive for known open architecture details at the time of
writing. These questions must be answered before their corresponding runtime
interfaces are frozen. They do not reopen the mandatory decisions in section
0.2.

14.1. Exact structural layout behind data

The Lmx header is fixed, but the exact memory layout addressed by data for a
non-leaf is not yet fixed. Candidates include a contiguous sequence of Lmx
nodes, a stable arena block, or another bounded representation compatible
with data plus len. The chosen layout must support stable node addresses,
ordered children, deep containment copying and range classification. This is
only a payload-layout choice: every mutable representation chosen here belongs
to the containing Message's one arena.

14.2. Unit and interpretation of len

The unit of len must be fixed for every physical range: child count, element
count, byte count or another explicit unit. One field may have
range-dependent meaning, but each range must have exactly one rule.

14.3. Empty representation

The exact distinction among null data, zero len, an explicitly present empty
Structure and an empty primitive/array buffer must be fixed. Unit and absence
must not become indistinguishable accidentally.

14.4. ShortNameId format

The bit width, deterministic generation, inter-module agreement, collision
handling, reserved IDs and conversion from an arbitrary runtime textual path
are open. The result must still require only the Lmx-pointer-to-ShortNameId
node table.

14.5. Positional and anonymous occurrence naming

Repeated named occurrence numbering is fixed: `[0]` is the first matching
child in result order and higher indexes proceed forward. What remains open is
whether positional/anonymous containment occurrences receive reserved
ShortNameId values and participate in the sole reverse table, or are excluded
from textual-name lookup and addressed only by structural position. The choice
must preserve copying, path diagnostics and the rule that no second per-node
metadata table is introduced.

14.6. Explicit graph references during merge

Containment descendants are copied and node is rebased. For a non-containment
reference stored in the copied tree, it remains to decide whether:

* every such reference preserves its original target; or
* a reference to a node inside the copied subtree is remapped to the
  corresponding copy while an external reference preserves its target.

If remapping is selected, merge needs a temporary old-address-to-new-address
work map. That temporary algorithmic map is not persistent node metadata and
must disappear after the copy.

14.7. Primitive copy and mutation policies

Interned immutable leaves naturally share their primitive address. Policies
for mutable cells, large numbers, byte buffers, opaque handles and foreign
resources remain to be specified by physical range. Every ordinary mutable
primitive cell created for a Message is nevertheless allocated in that
Message's arena; only its exact physical class/copy policy remains open.

This open question concerns copying graph payloads and merge operands. It does
not reopen through-value semantics: a primitive hidden through operand is
always copied by semantic value at a call, while a Structure/Array hidden
operand copies its reference value as-is.

14.8. Arrays

It remains to define which address range and data/len convention represents
ArrayReference, including rank, shape and element storage. This must not add
a per-Structure header or descriptor. The chosen ordinary Array header,
shape, elements and mutable backing belong to the containing Message arena.

14.9. Allocation, arenas and reclamation

Arena ownership is not open: every Message owns exactly one logical arena, and
all dynamic mutable ordinary Lmx storage of that Message is allocated there.
That arena remains with the Message across L3 turns and host-worker migration.
Open details are its block/slab/bump implementation, physical subdivision into
registered ranges, collector/tracer/compactor algorithm, bulk-destruction
mechanics, side-table cleanup, out-of-memory behavior and address reuse. Memory
pressure may request failure/termination or influence work at the next boundary,
but it does not add another graph-collection point. Local collection at the
common end-turn boundary,
after successful FIFO outbox publication or failed-turn rollback, is fixed.
Live address
identity must remain stable, either by not moving a live node or by atomically
rewriting every reference and re-keying its side-table entry as specified in
section 7.2.

14.10. Exact method return ABI

The method input model is fixed: the non-replaceable first input is reserved
`node = callable->node`, followed by the method's declared operands and exact
hidden through values, all described by immutable `sig`. What remains open is
the exact C return type/convention and where success, failure and source return
values live in the runtime graph. Whatever convention is chosen becomes part
of `sig` and must match exactly at the call site.

14.11. Physical representation of published method state

The Structure containing the selected callable occurrence is fixed as the
method's published working state. Native C stack frames are fixed as the sole
implicit activation history; used own fields are working C locals, hidden
through values are C parameters, and dirty-only checkpoints/no-reload are fixed.

What remains open is the exact physical representation and helper ABI for each
published own field, declared graph operand and result inside ordinary Lmx
payload classes. That choice may not introduce a per-call activation subtree,
a per-Structure descriptor or a runtime Name-to-Binding object, and may not
change the fixed method signature or publication semantics.

14.12. Descriptor-only callable forms

The runtime representation and diagnostics for fn/sub declarations without a
body remain to be fixed. They must not be implemented as fake executable
zero-returning methods.

14.13. Method-section portability

The exact implementation for PE/COFF, ELF, Mach-O and other supported
profiles, including the physical `all_methods_array {addr, sig}` representation,
typed-function-pointer storage, section bounds, signature-ID encoding and
dead-code elimination retention, remains open. Program-wide reachability,
immutable exact signatures and exact typed invocation are fixed.

14.14. Path-mangling encoding

Path normalization, escaping, case rules, source-root identity, occurrence
encoding, linker length limits and optional collision-resistant hash fallback
remain open. Global uniqueness and reproducibility are fixed.

14.15. Top-level evaluation and reuse

Runtime merge timing is fixed: it occurs when control reaches it. It remains
to decide whether a particular top-level named value is evaluated once and
retained, evaluated per explicit consumption, or controlled by a separately
specified binding lifetime. Translation itself must not eagerly materialize
the merge.

14.16. Module linkage and loading

It remains to define how a module guarantees that referenced method entries
and Structure providers/references have been linked or loaded, and how modules
agree on the exact `sig` encoding. This mechanism must not be a hidden
Name-to-value runtime namespace. Runtime merge does not compile missing code or
adapt incompatible signatures.

14.17. Multiple roots and cross-root references

The lifetime and lookup behavior of multiple Messages, modules or execution
graphs, and the legality of explicit references between their roots, remain
to be defined within a fixed isolation boundary. Concurrently executing
Messages cannot share an ordinary mutable Lmx node by raw pointer. Delivery
must copy/serialize into the destination or new Message arena, adopt/transfer
storage only under an explicit rule that removes conflicting ownership, or
refer to explicitly immutable/global/foreign substrate. Arbitrary lookup
inside one graph still begins at that graph's root.

14.18. Concurrency

Common L3 concurrency is fixed: one Message owns one arena; one L3 Thread
executes no more than one turn at once; its admitted inbox/outbox order is FIFO;
different Message arenas may execute concurrently. Therefore allocation,
ShortNameId registration and merge within one Message have one semantic writer
and need no source-visible synchronization.

Suspending with `yield` does not admit an overlapping turn over the same
Message arena and does not replace ordinary stack/continuation state with graph
history. Its continuation preserves C working locals and dirty flags. `retry`
is not a call and creates neither a call frame nor a pre-call checkpoint merely
by itself.

Open implementation details are atomic linearization of concurrent admissions,
worker scheduling/fairness between Messages, queue capacity/backpressure,
initialization of global immutable method/range registries and collector
coordination. L1 may synchronize those substrate mechanisms internally. An
explicit L2 shared-memory/thread profile may define its own atomics, locks and
memory order, but that custom contract is not common L3 or Mix semantics and
must not introduce a shared mutable runtime namespace.

14.19. Error handling and transactional merge

It remains to define whether a failed merge leaves no result, a partial
inaccessible allocation reclaimed with an arena, or an explicit failure
Structure. Published results must never expose half-rebased node links or
missing ShortNameId mappings.

14.20. Optimization policy

Caching constant path components, specializing range checks or sharing
immutable substrate may be considered after the generic implementation is
correct. Any optimization must remain observably equivalent after arbitrary
runtime merge and must not make static C layout part of language semantics. It
must also preserve dynamic caller value semantics, used-only entry loads,
runtime actual-write dirty marking, dirty-only publication at section 6.5
semantic boundaries and activation exits,
the absence of automatic through-value write-back and post-call reload, and the
observable distinction between an activation snapshot and an explicit path to
current graph state.

14.21. Explicit navigation above the immediate method parent

Reserved `node` and immediate `node\field` are fixed: `node` already equals
`callable->node`, and the field operation makes no second parent hop. The exact
source spelling/receiver for intentionally obtaining a still higher containment
ancestor is not yet fixed. It must be explicit and cannot restore automatic
lexical-parent search. Repeating ordinary field segments must not acquire an
implicit ancestor meaning merely as an implementation shortcut.

14.22. Structural mutation of an active own-field backing occurrence

Ordinary payload updates preserve the selected own occurrence and are already
covered by dirty publication. What a suspended activation must do if nested code
explicitly removes, moves or replaces that exact occurrence is not yet fixed.
The profile must choose rejection/locking, update of the still-live detached
identity, re-resolution with an explicit conflict check, or another stated
policy. It may not silently choose a different `[0]` child or reinsert data while
claiming that this follows from no-reload. Until this policy is selected, the
bootstrap may reject structural mutation of an active backing occurrence.

14.23. Checkpoint-store failure

The success rule is fixed: every dirty own value required by the boundary is
published before the outbound call/normal exit, and each successfully published
value becomes clean. The failure behavior remains open: the implementation may
make those stores infallible, prevalidate and commit atomically, or define a
deterministic prefix-commit diagnostic. The chosen result/throw ABI must state
visible stores and dirty flags, prevent the intended transfer on incomplete
publication, and avoid recursive re-entry into the same failing epilogue. No
transaction log or rollback is implied unless explicitly selected.

RU

Этот раздел исчерпывающе перечисляет известные открытые архитектурные детали
на момент написания. На вопросы нужно ответить до фиксации соответствующих
runtime-интерфейсов. Они не открывают заново обязательные решения раздела
0.2.

14.1. Точный структурный layout за data

Заголовок Lmx закреплён, но точный layout памяти, адресуемой data нелистового
узла, ещё не закреплён. Варианты включают непрерывную последовательность
Lmx-узлов, стабильный arena block или другое ограниченное представление,
совместимое с data и len. Выбранный layout обязан поддерживать стабильные
адреса узлов, порядок детей, глубокое копирование вложенности и
классификацию диапазона. Это только выбор payload-layout: любое выбранное
здесь изменяемое представление принадлежит одной arena содержащего Message.

14.2. Единица и интерпретация len

Для каждого физического диапазона нужно закрепить единицу len: число детей,
число элементов, число байтов либо иную явную единицу. Одно поле может иметь
зависящий от диапазона смысл, но у каждого диапазона обязано быть ровно одно
правило.

14.3. Представление пустоты

Нужно закрепить точное различие между null data, нулевым len, явно
присутствующей пустой Structure и пустым буфером примитива/массива. Unit и
отсутствие не должны случайно стать неразличимыми.

14.4. Формат ShortNameId

Открыты разрядность, детерминированная генерация, межмодульное согласование,
обработка коллизий, зарезервированные ID и преобразование произвольного
runtime-текстового пути. Результат всё равно обязан требовать только таблицу
узлов Lmx-pointer-to-ShortNameId.

14.5. Именование позиционных и анонимных occurrences

Нумерация повторных именованных occurrences закреплена: `[0]` — первый
совпадающий ребёнок в порядке результата, более высокие индексы идут вперёд.
Открытым остаётся, получают ли позиционные/анонимные occurrences вложенности
зарезервированные ShortNameId и участвуют ли в единственной reverse table,
либо исключаются из текстового name lookup и адресуются только структурной
позицией. Выбор обязан сохранить копирование, диагностику путей и запрет на
вторую per-node metadata table.

14.6. Явные ссылки графа при merge

Потомки вложенности копируются, а node rebased. Для не-containment ссылки,
лежащей в копируемом дереве, нужно выбрать:

* каждая такая ссылка сохраняет исходную цель; либо
* ссылка на узел внутри копируемого поддерева перенаправляется на
  соответствующую копию, а внешняя ссылка сохраняет цель.

Если выбрано перенаправление, merge требуется временный work map
old-address-to-new-address. Эта временная алгоритмическая map не является
постоянными metadata узла и обязана исчезнуть после копирования.

14.7. Политики копирования и изменения примитивов

Interned immutable листья естественно совместно используют адрес примитива.
Для mutable cells, больших чисел, byte buffers, opaque handles и внешних
ресурсов политики ещё нужно определить по физическому диапазону. Однако любая
обычная mutable ячейка примитива, созданная для Message, выделяется в arena
этого Message; открыты только её точная физическая категория и copy policy.

Этот открытый вопрос относится к копированию payloads графа и operands merge.
Он не открывает заново семантику сквозных значений: скрытый сквозной примитив
при вызове всегда копируется по семантическому значению, а скрытый operand
Structure/Array копирует значение ссылки как есть.

14.8. Массивы

Нужно определить диапазон адресов и соглашение data/len для ArrayReference,
включая rank, shape и element storage. Это не должно добавлять
per-Structure header или descriptor. Выбранные обычные заголовок Array, shape,
элементы и mutable backing принадлежат arena содержащего Message.

14.9. Allocation, arenas и освобождение

Arena ownership не открыт: каждый Message владеет ровно одной логической
arena, и всё dynamic mutable обычное Lmx-хранилище этого Message выделяется в
ней. Эта arena остаётся с Message между L3 turns и при миграции между host
workers. Открыты block/slab/bump реализация arena, физическое разбиение на
зарегистрированные диапазоны, алгоритм collector/tracer/compactor, механика
bulk destruction, cleanup side table, out-of-memory и повторное использование
адресов. Memory pressure может запросить failure/termination либо повлиять на
работу на следующей границе, но не добавляет другой graph-collection point.
Локальная collection
на общей границе end-turn после успешной публикации FIFO outbox либо rollback
failed turn закреплена. Identity живого адреса обязана оставаться стабильной: узел либо не
перемещается, либо реализация атомарно переписывает все ссылки и re-key его
записи side table по разделу 7.2.

14.10. Точный ABI результата метода

Модель входов метода закреплена: первым не заменяемым входом является
зарезервированный `node = callable->node`, после него идут объявленные operands
метода и точные скрытые сквозные значения; всё это описывает неизменяемый
`sig`. Открыты точный C return type/convention и место success, failure и source
return values в runtime-графе. Выбранное соглашение становится частью `sig` и
обязано точно совпадать в call site.

14.11. Физическое представление опубликованного состояния метода

Structure, содержащая выбранный occurrence callable, закреплена как
опубликованное рабочее состояние метода. Нативные frames стека C закреплены как
единственная неявная история активаций; используемые собственные поля являются
рабочими C locals, скрытые сквозные значения — параметрами C, а dirty-only
checkpoints и отсутствие reload закреплены.

Открыты точное физическое представление и helper ABI каждого опубликованного
собственного поля, объявленного graph operand и результата внутри обычных
классов payload Lmx. Этот выбор не может вводить per-call поддерево активации,
descriptor конкретной Structure или runtime-объект Name-to-Binding и не может
изменять закреплённую сигнатуру метода либо семантику публикации.

14.12. Callable-формы без тела

Нужно закрепить runtime-представление и диагностику fn/sub declarations без
тела. Их нельзя реализовывать как фальшивые исполняемые методы, возвращающие
ноль.

14.13. Переносимость секции методов

Открыта точная реализация для PE/COFF, ELF, Mach-O и других поддерживаемых
профилей, включая физическое представление `all_methods_array {addr, sig}`,
хранение typed function pointer, границы секций, кодирование ID сигнатуры и
удержание символов при dead-code elimination. Глобальная достижимость,
неизменяемые точные сигнатуры и точный typed-вызов закреплены.

14.14. Кодирование path mangling

Открыты нормализация пути, escaping, правила регистра, identity source root,
кодирование occurrences, ограничения длины linker и необязательный
collision-resistant hash fallback. Глобальная уникальность и
воспроизводимость закреплены.

14.15. Top-level evaluation и повторное использование

Timing runtime merge закреплён: он происходит при достижении управлением.
Нужно решить, вычисляется ли конкретное top-level именованное значение один
раз и сохраняется, вычисляется при каждом явном consumption либо управляется
отдельно заданным lifetime binding. Сама трансляция не должна eager
материализовать merge.

14.16. Linkage и загрузка модулей

Нужно определить, как модуль гарантирует, что referenced method entries и
providers/ссылки Structure слинкованы или загружены, а также как модули
согласуют точное кодирование `sig`. Этот механизм не должен быть скрытым
runtime namespace Name-to-value. Runtime merge не компилирует отсутствующий
код и не адаптирует несовместимые сигнатуры.

14.17. Несколько корней и cross-root ссылки

Нужно определить lifetime и lookup нескольких Messages, modules или execution
graphs, а также допустимость явных ссылок между их корнями внутри уже
закреплённой границы изоляции. Одновременно исполняемые Messages не могут
разделять обычный mutable Lmx-узел сырым указателем. Delivery обязана
копировать/сериализовать данные в arena назначения или нового Message,
adopt/transfer storage только по явному правилу, устраняющему конфликтующее
ownership, либо ссылаться на явно immutable/global/foreign субстрат.
Произвольный lookup внутри одного графа всё равно начинается от корня этого
графа.

14.18. Concurrency

Конкурентность общего L3 закреплена: один Message владеет одной arena; один L3
Thread исполняет не более одного turn одновременно; порядок принятого
inbox/outbox является FIFO; разные arena Messages могут исполняться
параллельно. Поэтому allocation, регистрация ShortNameId и merge внутри одного
Message имеют одного семантического писателя и не требуют видимой исходнику
синхронизации.

Приостановка через `yield` не допускает пересекающийся turn над той же arena
Message и не заменяет обычное состояние stack/continuation историей графа. Его
continuation сохраняет рабочие C locals и dirty flags. `retry` не является
вызовом и само по себе не создаёт ни call frame, ни pre-call checkpoint.

Открыты реализация атомарной линеаризации одновременных admissions,
scheduling/fairness между Messages, capacity/backpressure очереди,
инициализация глобальных immutable реестров методов/диапазонов и координация
collector. L1 может синхронизировать этот субстрат внутри реализации. Явный L2
shared-memory/thread профиль может определить собственные atomics, locks и
memory order, но такой custom contract не является семантикой общего L3 или
Mix и не должен вводить общий mutable runtime namespace.

14.19. Обработка ошибок и транзакционность merge

Нужно решить, оставляет ли неудачный merge отсутствие результата, частичный
недоступный allocation, освобождаемый arena, либо явную failure Structure.
Опубликованный результат никогда не должен показывать наполовину rebased
node или отсутствующие отображения ShortNameId.

14.20. Политика оптимизаций

Кэширование компонентов константного пути, специализация range checks или
совместное использование immutable substrate можно рассматривать после
корректной общей реализации. Любая оптимизация обязана оставаться наблюдаемо
эквивалентной после произвольного runtime merge и не должна делать
статический C layout частью семантики языка. Она также обязана сохранять
семантику сквозных значений вызывающего, used-only загрузки при входе,
runtime-marking dirty по фактической записи, dirty-only публикацию на semantic
boundaries раздела 6.5 и выходах activation, отсутствие автоматических write-back сквозных значений и post-call
reload, а также наблюдаемое различие между snapshot активации и явным путём к
текущему состоянию графа.

14.21. Явная навигация выше непосредственного родителя метода

Reserved `node` и непосредственное `node\field` закреплены: `node` уже равен
`callable->node`, и field-operation не делает второго parent-hop. Точное source
spelling/receiver для намеренного получения ещё более высокого containment
ancestor пока не закреплено. Оно обязано быть явным и не может возвращать
автоматический поиск по lexical parents. Повторение обычных field segments не
получает неявное ancestor-значение как shortcut реализации.

14.22. Structural mutation активного backing occurrence собственного поля

Обычные payload updates сохраняют выбранный own occurrence и уже покрываются
dirty publication. Поведение suspended activation, когда nested code явно
удалил, переместил или заменил именно этот occurrence, пока не закреплено.
Профиль обязан выбрать rejection/locking, update всё ещё живой detached identity,
повторный lookup с явной conflict-check либо другую описанную policy. Он не может
молча выбрать другой `[0]` child или вставить данные назад, утверждая, что это
следует из no-reload. До выбора policy bootstrap может отклонять structural
mutation активного backing occurrence.

14.23. Failure checkpoint-store

Success-rule закреплено: каждое dirty own-value, требуемое границей, публикуется
до outbound call/normal exit, и каждое успешно опубликованное значение становится
clean. Failure-поведение открыто: реализация может гарантировать infallible
stores, prevalidate и commit-ить атомарно либо определить детерминированный
prefix-commit diagnostic. Выбранный result/throw ABI обязан задать видимые
stores и dirty flags, не допустить предполагаемый transfer при неполной
публикации и избежать рекурсивного входа в тот же failing epilogue. Transaction
log/rollback не подразумевается без явного выбора.


15. Initial rewrite sequence
Начальная последовательность переписывания
===============================================

EN

The following order is recommended because each step establishes an invariant
needed by the next:

1. Freeze parser regression tests and define the parser-tree adapter boundary.
2. Introduce the exact Lmx header without per-Structure extensions.
3. Preserve/implement exactly one logical arena per Message and derive it from
   reserved method `node`, without ambient MessageThread/arena/context method
   parameters.
4. Implement stable node allocation in that arena and the sole reverse
   `Lmx * -> ShortNameId` side table.
5. Implement address-range classification for structural data, `all_chars` and
   the common callable physical class.
6. Implement direct/relative traversal, reserved immediate-parent
   `node\field`, and explicit-root arbitrary textual path lookup.
7. Implement deterministic collision-free method identities, preferably with
   full-source-path C mangling, plus one canonical exact-signature encoding.
8. Recursively discover every method and analyze used own fields, actual write
   sites, declared operands, hidden through-name dependencies and call-site
   expected signatures.
9. Emit every live body with its exact C prototype and register immutable
   `all_methods_array {addr,sig}` records in the common callable class.
10. Emit used-only entry loads, C working locals, runtime dirty flags,
    actual-write marking, dirty-only checkpoints at every semantic boundary
    defined by 6.5 and every
    `return`/`throw`, and no automatic post-call reload/write-back.
11. Emit exact call sites which validate `sig`, pass `callable->node`, declared
    operands and hidden through values, using immediate `node\name` only as the
    specified absent-caller fallback.
12. Implement generic containment-tree copy with `node` rebasing and name-table
    registration.
13. Implement ordered runtime merge at execution sites, allocating the result
    in the current Message arena.
14. Preserve/implement the per-L3-Thread FIFO inbox/outbox and the invariant
    that turns of one Message never overlap while distinct Messages can run
    concurrently without shared mutable trees.
15. Preserve/implement publish-or-rollback followed by local Message-arena
    collection at every common end-turn boundary.
16. Add tests for runtime-produced merge inputs, nested methods, repeated names,
    exact callable signatures and `implements` compatibility.
17. Add tests for dynamic caller propagation, value/reference copy semantics,
    fallback, dirty-only publication, no reload, recursion/callback overwrite,
    explicit history, `yield` and `retry`.
18. Add concurrency tests proving arena isolation, FIFO admission/publication,
    non-overlapping same-Message turns, end-turn collection ordering and
    parallel distinct Messages.
19. Rebuild the translator with the new core only after these runtime invariants
    pass independently.

This sequence is guidance, not permission to retain an incompatible old core
behind adapters.

16. Acceptance criteria
Критерии приёмки
====================

EN

The architecture rewrite is complete only when all of the following are true:

1. Existing parser behavior required by the language remains intact.
2. No generated named Structure requires a dedicated C struct or typedef.
3. The only common node header is `node`, `len`, `data` in that order.
4. An ordinary runtime node contains no name, signature or descriptor.
5. The only auxiliary persistent per-node name mapping is
   `Lmx * -> ShortNameId`.
6. Arbitrary textual absolute paths resolve from an explicit root; explicit
   direct/relative paths retain their supplied start and remain correct after
   merge.
7. Dynamic caller visibility is lowered to exact hidden C value parameters and
   native C stack slots; runtime contains no separately allocated mutable
   Name-to-Binding namespace/overlay object.
8. Every nested executable method has a real program-wide reachable body with
   a deterministic unique, preferably full-source-path-mangled C identity.
9. Reserved `node` is non-shadowable and non-rebindable, always equals the
   selected `callable->node`, and makes `node\field` immediate-parent access
   without a second parent hop.
10. Every source method and call site has one exact canonical C signature:
    reserved `node`, declared operands, exact hidden through values and the
    selected result convention; the selected callable `sig` equals it.
11. Every callable payload resolves through the common physical class to an
    immutable `all_methods_array {addr,sig}` record; calls reject mismatched
    `sig` and use the exact typed function-pointer invocation.
12. `implements(A, B, Consumer)` validates the exact signature of every
    callable leaf actually used by Consumer; distinct addresses with equal
    canonical `sig` are allowed and unused callable leaves add no requirement.
13. Method entry loads only actually used unqualified own fields into C working locals and
    initializes their runtime dirty flags clear; implicit activations do not
    create fresh local Lmx subtrees.
14. Only an actually executed local write/rebind marks its own field dirty. At
    every 6.5 LMX/observable-call, yield and activation-exit boundary, only dirty
    own fields are stored, and each flag clears only after its store succeeds.
15. Clean cached fields never flush, and working locals never automatically
    reload or reconcile after a call.
16. Primitive through values copy by semantic value; Structure/Array through
    values copy the reference value as-is. Rebinding is activation-local, there
    is no automatic write-back, and mutation requires an explicit reference
    path.
17. A required unqualified binding absent from the caller falls back only to
    the callee's immediate reserved `node\name`, never a transitive lexical
    parent chain.
18. The native C stack is the sole implicit activation history. The selected
    callable occurrence's containing Structure is published working state, not
    a call log; recursive/callback overwrite is intentional and durable history
    is an explicit Structure, Array or Message.
19. `yield` preserves ordinary continuation, working locals and dirty flags;
    `retry` alone is not a call and creates no frame or pre-call checkpoint.
20. merge allocates a new containment tree only when execution reaches it.
21. merge copies nodes and rebases `node` rather than connecting containment by
    links, while preserving order and repeated occurrences.
22. merge accepts results that were themselves produced at runtime.
23. A copied method retains its immutable `{addr,sig}` record and invokes the
    original body with copied `callable->node` plus exact declared/hidden
    operands, not with the source owner or root.
24. HashArray translation does not require static analysis of Array's C layout
    or a whole-directory scan.
25. Self-hosting and regression tests validate semantic behavior rather than
    only the visual shape of generated C.
26. Mix is represented within the common Message/Lmx graph ontology; the
    current Java procedural/multithreaded implementation is not treated as the
    target architecture.
27. Every Message owns exactly one logical arena, every dynamic mutable ordinary
    Lmx node/payload of that Message is allocated in it, and methods derive it
    from reserved `node` without hidden MessageThread/arena/allocator/context.
28. One L3 Thread never executes two turns of one Message concurrently; admitted
    input and staged output preserve FIFO order, while distinct Messages can
    execute concurrently without sharing mutable arena trees absent an explicit
    full clone/transfer.
29. Common Mix contains no transplanted Java/OS shared-memory synchronization
    algorithm; concurrency is expressed through Message ownership and delivery,
    independently of HTTP or any other transport.
30. Every turn publishes its successful FIFO outbox or rolls it back on failure
    before local collection of the Message arena; Message termination releases
    that arena only after required transfer and cleanup.

Failure of any item means that the version-2 core is not yet implemented,
even if individual examples compile.

RU

Архитектурное переписывание завершено только тогда, когда истинно всё
следующее:

1. Требуемое языком поведение существующего parser-а сохранено.
2. Ни одна generated именованная Structure не требует отдельного C struct или
   typedef.
3. Единственный общий заголовок узла содержит `node`, `len`, `data` именно в
   этом порядке.
4. Обычный runtime-узел не содержит имени, сигнатуры или descriptor.
5. Единственное вспомогательное постоянное per-node отображение имени —
   `Lmx * -> ShortNameId`.
6. Произвольные текстовые абсолютные пути разрешаются от явно переданного root;
   явные direct/relative пути сохраняют переданный start и остаются правильными
   после merge.
7. Динамическая видимость вызывающего понижается в точные скрытые C-параметры
   значений и нативные слоты стека C; в runtime нет отдельно выделенного
   mutable-объекта namespace/overlay Name-to-Binding.
8. Каждый вложенный исполняемый метод имеет настоящее глобально достижимое тело
   с детерминированной уникальной, предпочтительно mangled из полного пути
   исходника, identity C.
9. Зарезервированный `node` нельзя shadow или rebind; он всегда равен
   выбранному `callable->node`, а `node\field` даёт непосредственный доступ
   родителя без второго подъёма.
10. Каждый метод исходника и call site имеет одну точную каноническую сигнатуру
    C: зарезервированный `node`, объявленные operands, точные скрытые сквозные
    значения и выбранное соглашение результата; `sig` выбранного callable равен
    ей.
11. Каждый callable payload разрешается через общую физическую категорию в
    неизменяемую запись `all_methods_array {addr,sig}`; вызов отвергает
    несовпадающий `sig` и использует точный typed function pointer.
12. `implements(A, B, Consumer)` проверяет точную сигнатуру каждого фактически
    используемого Consumer callable leaf; разные адреса с равным canonical `sig`
    разрешены, а неиспользуемые callable leaves не добавляют требования.
13. При входе метод загружает только фактически используемые
    неквалифицированные собственные поля в
    рабочие C locals и очищает их runtime dirty flags; неявные активации не
    создают свежих локальных Lmx-поддеревьев.
14. Только фактически исполненная запись/rebind local помечает собственное поле
    dirty. На каждой boundary LMX/observable-call, yield и выхода activation из
    6.5 записываются только dirty собственные поля, а каждый flag очищается лишь
    после успешной записи.
15. Clean кэшированные поля никогда не flush-ятся, а рабочие locals никогда
    автоматически не reload-ятся и не согласуются после вызова.
16. Сквозные примитивы копируются по семантическому значению, Structure/Array —
    по значению ссылки как есть. Rebind локален для activation, автоматического
    write-back нет, а mutation требует явного пути через ссылку.
17. Требуемый неквалифицированный binding, отсутствующий у вызывающего,
    откатывается только к непосредственному зарезервированному `node\name`
    вызываемого, но не к сквозной цепочке лексических родителей.
18. Нативный стек C — единственная неявная история активаций. Containing
    Structure выбранного callable-occurrence является опубликованным рабочим
    состоянием, а не call log; overwrite при recursion/callback намеренен, а
    долговечная история является явной Structure, Array или Message.
19. `yield` сохраняет обычную continuation, рабочие locals и dirty flags;
    `retry` сам по себе не является вызовом и не создаёт frame либо pre-call
    checkpoint.
20. merge выделяет новое дерево вложенности только при достижении его
    исполнением.
21. merge копирует узлы и rebases `node`, а не соединяет вложенность ссылками,
    сохраняя порядок и повторные occurrences.
22. merge принимает результаты, которые сами были произведены в runtime.
23. Скопированный метод сохраняет неизменяемую запись `{addr,sig}` и вызывает
    исходное тело с `callable->node` копии плюс точными объявленными/скрытыми
    operands, а не с исходным owner или root.
24. Трансляция HashArray не требует статического анализа C-layout Array или
    сканирования всей директории.
25. Самосборка и regression tests проверяют семантическое поведение, а не только
    внешний вид сгенерированного C.
26. Mix представлен внутри общей Message/Lmx-онтологии графа; текущая
    процедурная многопоточная Java-реализация не считается целевой архитектурой.
27. Каждый Message владеет ровно одной логической arena, каждый dynamic mutable
    обычный Lmx-узел/payload этого Message выделяется в ней, а методы определяют
    её по зарезервированному `node` без скрытого
    MessageThread/arena/allocator/context.
28. Один L3 Thread никогда не исполняет два turns одного Message одновременно;
    принятый вход и подготовленный выход сохраняют FIFO-порядок, а разные
    Messages могут исполняться параллельно без общих mutable arena-деревьев при
    отсутствии явного полного clone/transfer.
29. Общий Mix не содержит перенесённого Java/OS алгоритма shared-memory
    синхронизации; конкурентность выражается через ownership и доставку
    Messages независимо от HTTP или любого другого транспорта.
30. Каждый turn публикует успешный FIFO outbox либо откатывает его при failure
    до локальной collection arena Message; termination освобождает arena только
    после обязательного transfer и cleanup.

Невыполнение любого пункта означает, что ядро версии 2 ещё не реализовано,
даже если отдельные примеры компилируются.
