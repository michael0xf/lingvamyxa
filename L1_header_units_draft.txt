L1 header units - bounded design draft
Status: proposal for agreement. Nothing implemented, no test covers any of it.

Requested by Codex before implementation: a minimal real source, the exact
generated header, both consumers, the build flow, the list of files to change,
and the list of decisions taken. This is that.


1. Naming, already decided

    source            mixa_core.h.lm1
    generated header  mixa_core.lm1.h      (build output directory)

The final extension stays .lm1, so the source-selection rule of L1_spec 1.1 and
the extension dispatch do not move. The .h. infix on the SOURCE selects header
output mode. The .lm1. infix on the GENERATED file keeps its existing meaning:
it marks an output, exactly as name.lm1.c does.

The body is ordinary L1 with no wrapper receiver, by the same principle that
makes a .lm1 document root the unit body: no h: and no L1:.


2. What the MVP must cover, from inventory rather than guess

Counted across the three real headers in the tree:

                        mixa_core.h   lmx.h   p0.h
    typedef struct           2          7      22
    typedef enum             1          2       0
    forward declaration      0          2       0
    function-pointer typedef 0          1       2
    #define                  1          2      46
    union                    0          0       0
    prototypes               0          1      21

Two results settle open questions Codex raised:

  UNION IS NOT NEEDED. Zero occurrences anywhere. Excluded from the MVP, and
  not to be added speculatively.

  FUNCTION-LIKE MACROS ARE ALMOST NOT NEEDED. Exactly one in the whole tree:
  LM_UNUSED(x) ((void)(x)) in p0.h. Every other #define is either an include
  guard, which becomes automatic, or an integer constant. Excluded from the
  MVP; p0.h keeps that one by hand until there is a second consumer.

So the MVP is: struct, enum, function-pointer typedef, integer constant,
prototype, and an automatic include guard. Six things.


3. Spelling, reusing existing forms wherever one exists

Only THREE new receivers. The rest already exist in L1 and are reused rather
than reinvented, which is also what keeps this from becoming a second C surface.

  NEW      struct:     aggregate definition
  NEW      enum:       enumeration
  NEW      fnptr:      function-pointer typedef
  EXISTS   define:     object-like macro, already an L1 unit-level item (1.2)
  EXISTS   prototype:  already an L1 unit-level item (1.2)
  none     forward declaration - emitted automatically, see 4.3

Field spelling inside struct: is ordinary L1 declaration spelling, unchanged.
That is the point: a struct body is a list of declarations, and L1 already
knows how to spell those.


4. Worked example: the real mixa_core

4.1. Source - mixa_manager\mixa_core.h.lm1

    # Cell and TextRect for the Mixa Manager visual model, sections 1 and 14 of
    # Old_Mixa_Manager_Qt_model.txt.

    include: "<stddef.h>"

    enum: MixaStyle
        MIXA_STYLE_BOLD 1
        MIXA_STYLE_UNDERLINE 2
        MIXA_STYLE_REVERSE 4
    end: MixaStyle

    struct: MixaCell
        unsigned: codepoint
        uchar: fg
        uchar: bg
        uchar: flags
        uchar: width
    end: MixaCell

    struct: MixaTextRect
        size_t: rows
        size_t: cols
        @: MixaCell cells
    end: MixaTextRect

4.2. Generated - build\mixa\mixa_core.lm1.h

    /* generated by l1trans from mixa_manager/mixa_core.h.lm1 */
    #ifndef LM_H_MIXA_MANAGER_MIXA_CORE
    #define LM_H_MIXA_MANAGER_MIXA_CORE

    #include <stddef.h>

    typedef enum MixaStyle {
        MIXA_STYLE_BOLD = 1,
        MIXA_STYLE_UNDERLINE = 2,
        MIXA_STYLE_REVERSE = 4
    } MixaStyle;

    typedef struct MixaCell MixaCell;
    struct MixaCell {
        unsigned int codepoint;
        unsigned char fg;
        unsigned char bg;
        unsigned char flags;
        unsigned char width;
    };

    typedef struct MixaTextRect MixaTextRect;
    struct MixaTextRect {
        size_t rows;
        size_t cols;
        MixaCell * cells;
    };

    #endif

4.3. Why the forward typedef is emitted for every struct

Every struct definition is preceded by its own typedef struct X X;. That is not
decoration: it makes a self-referential field work with no extra spelling. lmx.h
needs exactly this today -

    struct LmxChunk { ... LmxChunk *next; };

and with the typedef emitted first, the source writes @: LmxChunk next and
nothing else is required. Emitting it unconditionally also removes the need for
any explicit forward-declaration form, which is why the table in section 3 has
none.

4.4. Guard identity

    LM_H_ + unit path relative to the repository root, uppercased, every
    non-alphanumeric character replaced by an underscore.

Derived from the path, not the basename, so mixa_manager/mixa_core.h.lm1 and
some_other_dir/mixa_core.h.lm1 cannot collide. Deterministic and portable: it
carries no absolute machine path.


5. Both consumers

5.1. External C - a platform backend, hand-written C

    #include "mixa_core.lm1.h"

    void mixa_backend_present(const MixaTextRect *rect) { ... }

Ordinary #include of the GENERATED header. Nothing special.

5.2. Internal L1 - another unit in the same chain

    predef: "mixa_manager/mixa_core.h.lm1"

predef on the SOURCE. It makes the same declarations visible with no duplicate
definition: the header unit is the single owner of those types, and a unit that
predefs it does not re-emit them into its own C.

The existing raw form include: "some_handwritten.h" is untouched and remains a
separate case, for headers this mechanism does not own.


6. Build flow

    1. translate every *.h.lm1 to its .lm1.h in the build output directory
    2. translate every *.lm1 to its .lm1.c
    3. compile

Headers first, because step 3's consumers include them. Generated output never
lands on top of a source: mixa_core.h.lm1 is a source and is never written to.

A header-only unit does not have to produce an empty .c, and should not.

One emitter, one pipeline. The header mode is a mode of the existing emitter,
not a second parser - the declaration spelling inside is the same L1 the
emitter already lowers.

Failure must not leave a mismatched pair. If translation of a unit fails, its
previous .lm1.h stays untouched or is removed, but a half-written one is never
published - the same discipline run_seed already uses when it stages into a
unique directory and only then publishes.

Staleness: a .lm1.h older than its source is a build error, not a silent reuse.


7. Files this touches

    l1src\l1trans.lm1        header output mode; struct: / enum: / fnptr:
                             emission; automatic forward typedef; guard
                             derivation; prototype: and define: already exist
    l1src\buildCore.lm1      header pass before the C pass
    tests\l1\                new fixtures, positive and negative
    tests\l1\run_smoke.ps1   wire them, gated by generation
    L1_spec.txt              1.1 already records the naming; 5 and 6 to follow
                             implementation, not precede it

Not touched: parser.lm1 and p0.h. This adds no P0 syntax - struct:, enum: and
fnptr: are ordinary frames that P0 already parses. That is the main reason to
prefer this shape over anything resembling a C parser.


8. Decisions taken, listed so they can be rejected individually

    D1  union excluded from the MVP. Evidence: zero occurrences.
    D2  function-like macros excluded. Evidence: exactly one, LM_UNUSED.
    D3  three new receivers only: struct:, enum:, fnptr:. define: and
        prototype: reused as-is.
    D4  struct fields use ordinary L1 declaration spelling, unchanged.
    D5  forward typedef emitted automatically for every struct; no explicit
        forward-declaration form.
    D6  guard derived from the repository-relative path, not the basename.
    D7  header-only units emit no .c.
    D8  predef on the source is the internal consumer; include: of the
        generated header is the external one.
    D9  a stale generated header is an error, not a silent reuse.

    OPEN, deliberately not decided here:
      - whether a header unit may contain anything executable at all. The MVP
        says no, but the rule is not written into 1.2 yet.
      - where the build output directory for headers is, exactly. Section 6
        says "the build output directory"; the concrete path belongs with
        buildCore, not with this draft.
      - the .lm2.h analogue. That is the next L2 contract and is deliberately
        absent here.
