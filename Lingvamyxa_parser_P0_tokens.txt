Lingvamyxa Parser P0 Instruction: Tokens

Status

This file is an implementation instruction for the first structural parser.
It is not a replacement for Lingvamyxa_spec.txt.

This file defines tokenization and spelling recognition only. It does not decide
which receiver heads are normal heads and which receiver heads act as trailer
roles. Trailer-role recognition is described separately in:

    Lingvamyxa_parser_P0_trailer_roles.txt

P0 tokenization must preserve the central language rule:

    source syntax builds Structures;
    identifiers are identifier values;
    receivers and semantic context decide what those identifiers mean.

Therefore the lexer must not decide that an identifier is a variable, binding,
field, selector, atom, enum value, type, boolean, label, callable or trailer.
It only recognizes spelling forms and structural separators.


1. Tokenization Layers

P0 uses several lightweight modes instead of one flat token stream:

    source-level normalization
        maps physical lines to source levels and line events.

    structural line scanner
        recognizes colon frames, delimiters, comments, disabled items and
        bounded Structures.

    atom/operator scanner
        recognizes identifiers, exact identifiers, numbers, character constants,
        strings and operator-token fields.

While building the structural tree, P0 keeps compact operator spellings inside
the same tokenization pass. A non-quoted spelling chunk that contains characters
not allowed inside a bare identifier is split as if those characters had token
boundaries around them. For example, `2+2`, `i<n`, `a*b` and `arr[i+1]` become
ordinary field sequences containing values and operator-token fields. Later
receivers consume those fields.


2. Source-Level Events

The source-level normalization prepass produces:

    SOURCE_LEVEL(K)
        Integer source level for a physical line.

    EMPTY_LINE
        Formatting whitespace. Ignored by P0. Not a close token.

    RAW_COMMENT_BLOCK
        A run of `*` characters at column 0 with length 3 through 80 opens a
        raw ignored block. The closing fence must also appear at column 0 and
        must have the same run length as the opener. The fence line contains
        only the `*` run and optional spaces/tabs; no trailing `#` comment or
        title text is allowed. Fence-looking lines with a different `*` run
        length inside the block are ignored as raw comment content. The
        contents are not tokenized.

    BLOCK_STRING_LITERAL
        A run of `=` characters at column 0 with length 3 through 80 opens a
        block string. The closing fence must also appear at column 0 and must
        use the same run length as the opener. The opening and closing fence
        lines contain only the `=` run and optional spaces/tabs; no trailing
        `#` comment or title text is allowed. Physical lines between the fences
        are one STRING_LITERAL value.

    LINE_TEXT(K, text)
        Physical source line content after indentation/source-level handling.

    EOF
        End of file.

Canonical dotted notation:

    leading dots in the indentation zone define SOURCE_LEVEL(K).
    spaces/tabs in that indentation zone are readability only.

Relaxed indentation notation:

    leading spaces/tabs before ordinary source text are mapped to SOURCE_LEVEL(K)
    by the indentation-stack rule.

Leading dots outside the indentation zone are ordinary source text only if a
future profile explicitly admits that form. In P0, dot is not field access.


3. Whole-Line Structural Forms

These are recognized after source-level normalization and before ordinary atom
scanning:

    DELIM_DOTTED(K)
        A canonical dotted delimiter line. It contains only dots/spaces/tabs
        before newline and at least one dot.

    DELIM_DASH(K)
        A dash-fence line at source level K: a run of `-` characters of length
        3 through 80 after leading indentation/source-level handling. The line
        may contain optional whitespace after the dash fence and an optional
        trailing `#` comment. It may not contain another source item.

    COMMENT_LINE
        A line whose content begins with `#` after indentation/source-level
        handling. Ignored by P0.

    DISABLED_ITEM
        `%` immediately after the source-level zone marks the following source
        item disabled; optional horizontal whitespace after `%` is ignored. The
        normal P0 subtree is not built for the disabled body. P0 records an
        inactive placeholder and runs a lightweight disabled-block validator
        over the disabled range. That validator checks source-level nesting,
        accepted structural trailers, balanced parenthesized forms, quoted-token
        closure and block-string closure.

`---`, `----`, and longer runs up to length 80 are DELIM_DASH only as standalone
structural lines. Inside ordinary text, `-` is just part of the source spelling
consumed by a later parsing layer.


4. Structural Punctuation

P0 structural punctuation tokens:

    COLON       :
        Mandatory visible marker between head spelling and body in a physical
        short colon-form. The head role is positional; COLON is retained for
        navigation, tooling and a clear head/body boundary. A short colon-form
        has an implicit argument level one step deeper than its own source
        level. COMMA terminates an open short form at any scan depth. Physical
        newline is not a trailer; after newline, the following source level
        decides whether the open short form continues or is completed. RPAREN
        closes the bounded Structure itself and completes any open short form
        inside that bounded context.

    COMMA       ,
        Trailer at the current scan depth. For a short form, COMMA terminates
        the current open short form and does not add another field to the
        current short tail. When no short form is open at that scan depth,
        COMMA may be optional conventional list notation. A trailing COMMA with
        no following item is accepted as a cosmetic marker at any block level,
        including file/root level 0.

    LPAREN      (
    RPAREN      )
        Compact Frame argument lists and bounded Structures. Expression grouping
        is a later consumer/parser concern over the produced Structure.

    LBRACKET    [
    RBRACKET    ]
        Needed for L2 indexing forms and symbolic receiver heads such as `[]`.

    BACKSLASH   \
        L2 raw-load / field-follow token in L2/expression profiles.

    AT_RUN      @, @@, @@@, ...
        Reserved L2 address-depth operator family `@^n`.

    HASH        #
        Starts a line comment outside strings, exact identifiers and other
        literal forms.

P0 structural syntax does not use:

    =
        as assignment or named-field syntax.

    .
        as field access. Leading dots are source-level units only in the
        indentation zone; inside a number such as `.5` or `1.0`, dot belongs
        to the numeric literal; inside an exact identifier, dot is data.

    ->
    &
    *
    ^
        as native pointer/field syntax.


5. Identifier and Literal Tokens

P0 atom tokens:

    NUMERIC_LITERAL
        ANSI C / C99 numeric literal spelling.
        Examples: 0, 123, 0x7B, 1.0, .5, 1e9, 0x1.8p+2.

    STRING_LITERAL
        ANSI C / C99 string literal spelling. It is a value, not an identifier.
        An unescaped physical newline before the closing double quote is a
        syntax error. The only physical-line continuation is ANSI C
        backslash-newline line splicing before tokenization. While inside the
        string literal, the following physical line is not treated as a new
        source-level line; spaces/tabs physically written after the spliced
        line ending remain ordinary string-literal characters. Lingvamyxa does
        not add source-level string wrapping or implicit adjacent-string
        concatenation.
        After the closing double quote, the next source character must be a
        field boundary: horizontal whitespace, a physical line break, comma,
        `(`, `)`, or the end of the source item.
        The P0 lexer may preserve original spelling and decoded value metadata.

    PYTHON_STRING_LITERAL
        Python-like triple-quoted string spelling. It starts with exactly three
        double quotes or exactly three single quotes in ordinary token position
        and closes at the next unescaped matching triple delimiter. Physical
        line breaks inside the literal are string content. `#`, `:`, `,`, `(`,
        `)`, dash fences, source levels and tail cutters are not recognized
        inside the literal before the closing delimiter. Backslash is ordinary
        raw text in this literal form. A run of exactly three matching quote
        characters closes the literal; a run of four or more matching quote
        characters is literal content and value decoding emits one fewer quote
        character than the source run. After the closing triple delimiter, the
        same field-boundary rule applies. P0 preserves source spelling.

    CHARACTER_CONSTANT
        ANSI C / C99 single-quoted character constant spelling. It is a numeric
        value, not a string and not an identifier. Escape rules and
        backslash-newline line splicing follow the selected ANSI C / C99 L1
        profile.
        After the closing single quote, the same field-boundary rule applies.

    EXACT_IDENTIFIER
        Backtick-delimited exact identifier using SQLite-compatible
        grave-accent quoted identifier content rules: zero or more non-zero
        characters and/or escaped backtick pairs before the closing backtick.
        Two backticks inside the spelling represent one literal backtick.
        Physical newlines inside an exact identifier follow SQLite-style quoted
        identifier behavior: the newline and any following indentation are
        ordinary identifier content and are preserved exactly. Source-level
        events, comments and structural punctuation are not recognized inside
        the exact identifier before the closing backtick.
        After the closing backtick, the same field-boundary rule applies.

    BARE_WORD
        Portable core form:

            [A-Za-z_][A-Za-z0-9_]*

        Unicode identifier starts/continues may be admitted by a later profile.

Bare identifiers are single BARE_WORD tokens. Multi-word names and external
spellings must use EXACT_IDENTIFIER.

Examples:

    PlantBed
        one BARE_WORD.

    `second branch`
        one EXACT_IDENTIFIER whose exact spelling is second branch.

    `red     apples`
        one EXACT_IDENTIFIER whose repeated spaces are preserved.

    `properties.lm5`
        one EXACT_IDENTIFIER whose exact spelling is properties.lm5

    "properties.lm5"
        one STRING_LITERAL value, not an identifier

    """properties.lm5"""
        one PYTHON_STRING_LITERAL value, not an identifier


6. Head Mode

Before the first structural COLON on a physical line, P0 scans in head mode.

Head mode preserves the head spelling as an identifier/receiver spelling. It
does not decide whether that spelling is a normal frame head, a label head, a
profile trailer head, a binding, a selector or a callable.

P0 head spellings:

    bare word head
        print:
        outerLoop:

    exact identifier head
        `select`:
        `properties.lm5`:
        `slow path`:

    symbolic/reserved head
        []:
        @:
        @@:
        @@@:

    profile head path
        System\out\println:

The last form is treated as one head spelling in P0 head mode if the selected
profile admits backslash-separated receiver heads. The backslash has no
raw-load or field-follow operator meaning in head mode.

The spellings `end`, `until`, `return`, `if`, `then`, `else`, `for`, `while`,
`match`, `model`, `route`, `message`, `print` and similar words are not lexical
keywords. They are head or atom spellings. Their role is assigned by parser
context, trailer-role profile or receiver consumption.


7. Inline Body and Bounded-Structure Mode

After COLON, P0 scans the rest of the physical line as an ordinary short-tail
Structure unless the line opens a bounded continuation.

Field separators:

    horizontal whitespace in ordinary short-tail form
    horizontal whitespace between simple bounded fields when no short form is open
    physical newline/source-level composition for ordinary fields
    RPAREN closing the current bounded Structure; if a short form is open
        inside that bounded Structure, the short form is completed as part of
        closing that bounded context
    source-level boundary

Whitespace behavior:

    all ordinary short-tail fields
        whitespace separates fields:

            print: 1 2 3

        means:

            print(1, 2, 3)

    identifier and exact-identifier fields
        bare identifiers and exact identifiers are separate atomic fields:

            stack: PlantBed `2 dim`

        means two fields:

            PlantBed
            `2 dim`

    comma after an ordinary short-tail field
        does not add another field to the current head:

            stack: PlantBed, `2 dim`

        means that `stack` receives only `PlantBed`. The exact identifier
        `2 dim` is parsed as the next item at the current scan depth.

    comma when no short form is open
        may mark simple data item separation for conventional notation and may
        appear as a trailing cosmetic marker with no following item.

P0 must not use receiver signatures to insert hidden nesting while parsing the
ordinary short tail or bounded body. Receiver signatures operate after the
parser tree exists.

A short colon-form is a source-item form. Several short forms may appear on one
physical line when COMMA closes the earlier source item. Short forms may also
appear inline inside another short form or inside a bounded Structure:

    call(int: a b, ret: int)
        means call(int(a, b), ret(int))

    call(int: a, b)
        means call(int(a), b)

The comma after `a` terminates `int: a`; it does not add `b` to the `int`
tail.


8. Operator Token Fields

P0 structural parsing records operator-looking spellings as fields in the same
tree as ordinary source items. The token `=` is not structural assignment and
not named-field syntax.
Spellings such as `+`, `-`, `*`, `/`, `%`, `=`, `<`, `>`, `not`, `and`, `or`,
`true` and `false` are ordinary fields at this layer unless they appear inside
strings or exact identifiers.

When a compact non-quoted spelling contains invalid bare-identifier characters,
P0 splits it into valid bare/numeric pieces and operator-token pieces. Later
receivers may consume those fields as mathematical, boolean, indexing, update
or profile-specific forms.


9. Token Summary

Required P0 token/event names:

    SOURCE_LEVEL
    EMPTY_LINE
    LINE_TEXT
    RAW_COMMENT_BLOCK
    COMMENT_LINE
    DISABLED_ITEM
    DELIM_DOTTED
    DELIM_DASH
    COLON
    COMMA
    LPAREN
    RPAREN
    LBRACKET
    RBRACKET
    BACKSLASH
    AT_RUN
    NUMERIC_LITERAL
    STRING_LITERAL
    PYTHON_STRING_LITERAL
    CHARACTER_CONSTANT
    EXACT_IDENTIFIER
    BARE_WORD
    OPERATOR_TOKEN
    EOF

Trailer-role names such as END_NAMED, TERMINAL_RETURN and UNTIL_CLOSE are not
lexer tokens. They are profile-level roles assigned above tokenization.
