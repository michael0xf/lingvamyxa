--- Proposed run_mixa_parity_gates.ps1 shape (no code yet)

Runs the ten runners with a known, accepted state today (the seven
PASS plus the three allowlisted below), skipping app_controller and
audio_mp3 until each has its own accepted, bounded diagnosis (or is
explicitly excluded by name, a one-line decision for whoever accepts
this proposal):

  - A per-runner table, same shape as l2_parity_module_table.ps1's own
    convention: @{ Script = "run_mixa_X_l2_parity.ps1" (or @{ Script =
    "run_mixa_l2_parity.ps1"; Args = @("-Module","app_window") } for
    dispatcher-driven ones); ExpectVerdict = "PASS" | a specific
    non-pass verdict string; TimeoutSeconds = <int> }.
  - Per-runner timeout via Start-Process -PassThru plus
    Wait-Process -Timeout (or a background job with Wait-Job -Timeout,
    matching this session's own established "PS 5.1 stderr under
    EAP=Stop" and "cmd /c, never Start-Process -Wait" runner-invocation
    lessons for the INNER native calls each script itself makes --
    this OUTER per-runner timeout is a different layer, wrapping the
    whole child powershell.exe process, and needs its own kill-on-
    timeout path so one hung runner cannot block the rest).
  - The allowlist is the ExpectVerdict field itself: a runner PASSES
    the gate when its own verdict this run equals ExpectVerdict, not
    only when it equals "PASS" -- so backend_ctors_win32/backend_win32
    passing means "still EXPECTED_CORE_BARRIER, unchanged", and
    app_window passing means "still PARITY_FAILURE with the SAME l2trans
    defect", not a silent acceptance of any red. A DIFFERENT non-pass
    verdict, or a different diagnostic under the same verdict name, is
    itself a gate failure to report, not to absorb -- the same "a
    further red is its own finding" rule this whole thread's own
    tickets have already used throughout.
  - One line per runner in the gate's own summary: name, expected,
    actual, seconds, PASS/FAIL-the-gate. A single non-zero exit if any
    row's actual != expected.
  - Cost: 166.2s measured today for all twelve candidates (ten of
    which the gate would actually run) -- under three minutes total,
    comfortably inside a single "lead's builds keep priority" slot,
    and each runner's own individual timeout should be set generously
    above ITS OWN measured time here (a 3x margin, matching this
    thread's own per-runner "stop past three minutes" convention, so
    e.g. app_fmpanel's own 26.9s measured today gets roughly a 90s
    cap) rather than one global timeout for the whole gate.

--- Where it sits in the landing's union base

A step of its own, immediately after run_mixa.ps1 (the union base's
existing first mixa step) and before/alongside run_ingress_harness.ps1
(its second) -- not folded into either, since both of those are
selftest suites with their own existing pass/fail shape, while this
gate's own allowlist logic (expected-verdict-by-name, not just exit
code) is a genuinely different check. Three mixa steps in the landing
after this proposal: run_mixa.ps1, run_mixa_parity_gates.ps1 (new),
run_ingress_harness.ps1 -- order among the three not load-bearing
(measured independent today: no runner here touches shared build
state another step depends on), so run_mixa_parity_gates.ps1 landing
between the other two, or after both, are both fine; putting it
directly after run_mixa.ps1 groups "the two things that read the pinned
translator and build/run mixa code" before the third, narrower ingress-
specific harness.
