mixa_file_win32 -- port to clean L2 (ticket 20260913-114500)
====================================================================

Status: source and parity harness COMPLETE. mixa_file_win32.h/mixa_
file_win32.lm1/mixa_file.h are UNTOUCHED and remain the sole
implementation and the parity oracle. Translation against the CURRENT
main frontend fails with an already-known compiler barrier ("unknown
foreign type") -- expected, not a defect.

This ticket was deliberately chosen (per its own text) to expose
compiler needs beyond the pure-arithmetic modules ported so far:
[]: ulong, []: long, @/@@ wchar_t, opaque Win32 HANDLE, out-parameters
via @@:, and direct external Win32 API calls. All of these were
preserved exactly, with the smallest honest adapter, not approximated.

Files
---------
  mixa_manager/mixa_file_win32_l2.h.lm1 (new) -- self-contained header
    (only <stddef.h> for size_t; does NOT include the real mixa_file_
    win32.h or windows.h). Declares the 7 status/mode constants and
    struct: MixaFile with the opaque Win32 HANDLE field spelled as a
    plain `@: void handle` -- HANDLE is PVOID (void*) under the Win32
    ABI, so this is genuinely, not approximately, layout-identical to
    the real `HANDLE handle` field. Verified via a dedicated sizeof/
    offsetof probe BEFORE writing the .lm2 source: sizeof=16, handle=0,
    mode=8, is_open=12, byte-identical both sides.
  mixa_manager/mixa_file_win32_l2_win.h (new, plain C, not .lm1) -- a
    tiny system-header adapter: `#define WIN32_LEAN_AND_MEAN` followed
    by `#include <windows.h>`, nothing of mixa_manager's own. Exists
    because L1's own `include:` line syntax only ever emits bare
    #include directives with no interleaved #define, so the real
    header's own WIN32_LEAN_AND_MEAN + <windows.h> pairing needed a
    small standalone reproduction rather than reusing the oracle's own
    mixa_file_win32.h (which also declares the REAL MixaFile struct we
    are deliberately not reusing, per this segment's established
    practice of always declaring the L2 module's own struct).
  mixa_manager/mixa_file_win32.lm2 (new) -- complete translation of all
    7 functions (mixa_file_utf8_to_wide, mixa_file_invalid_handle,
    mixa_file_open, mixa_file_close, mixa_file_append, mixa_file_read,
    mixa_file_seek, mixa_file_size). EVERY function body is UNCHANGED
    L1-family text -- no algorithmic adaptation was needed anywhere;
    the only difference from the real source is the top predef:/
    include: lines. Preserves exactly:
      - ulong/long typed locals and Win32 API parameters (access,
        share, disp, attr, gle in mixa_file_open; nwritten/to_write in
        mixa_file_append; nread/to_read in mixa_file_read; lo/hi/rc in
        mixa_file_seek and mixa_file_size)
      - @@: wchar_t out-parameter in mixa_file_utf8_to_wide and the
        @@: MixaFile out-parameter in mixa_file_open (double-pointer
        "fill an owned handle" convention, never flattened to a single
        pointer or an integer handle id)
      - the opaque-handle sentinel pattern: mixa_file_invalid_handle()
        computes INVALID_HANDLE_VALUE as `(cast:(@:void)(cast:(size_t)
        -1))`, matched by pointer-equality comparisons everywhere a
        handle is checked, never touched as an integer
      - every direct Win32 API call via the c. namespace (Create
        FileW, CloseHandle, WriteFile, ReadFile, SetFilePointer,
        GetFileSize, GetLastError, SetLastError, MultiByteToWideChar),
        resolved through mixa_file_win32_l2_win.h rather than through
        any manager-owned header
      - the >4GiB-offset and >4GiB-size refusals (explicit `size_t >
        4294967295U` guards, since this first slice's Win32 calls are
        the 32-bit SetFilePointer/GetFileSize path, not the 64-bit Ex
        variants)
  mixa_manager/tests/mixa_file_win32_abi_probe_real.c / _l2.c (new) --
    dedicated probe pair (not reused from any other module).
  mixa_manager/tests/mixa_file_win32_parity_harness.lm1 (new) -- one

What would unblock the L2 side
-----------------------------------

return gaps. Re-running run_mixa_file_win32_l2_parity.ps1 once it lands
will automatically proceed into the real build+run+diff comparison.
