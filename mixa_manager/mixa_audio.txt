mixa_audio — audio playback seam (ClearShell "MP3" button, ticket 20260911-154950)
==================================================================================

Purpose
-------
One bounded slice: portable playback API for the desktop ClearShell port, backed
on Windows by the system MCI layer. The main executable is NOT wired to it yet
(same honest status as the app seam): this slice delivers the self-contained
playback core, its deterministic headless selftest, and a real win32/MCI smoke
test.

Design
------
A PORTABLE controller (mixa_audio.lm1) owns all playlist/state-machine logic and
talks to a DEVICE through a function-pointer vtable (MixaAudioVTable in
mixa_audio.h.lm1). Two devices exist:

  * mixa_audio_win32.lm1    real backend: MCI (winmm), links -lwinmm
  * fake (test-only)        deterministic backend embedded in the selftest

The win32 device is an MCI alias owned by one MixaAudio instance:
  open "<path>" type <waveaudio|mpegvideo> alias mixa<N>
  set mixa<N> time format milliseconds
  status mixa<N> length|position|mode
  play / seek / stop / close

WAV is guaranteed via the waveaudio MCI driver. MP3 rides the mpegvideo MCI type
and therefore depends on a system MP3 renderer (declared honestly: on machines
without one, MP3 probe succeeds but load fails with MIXA_AUDIO_ERR_BACKEND).

End of track is NOT signalled to us (no MCINOTIFY in this slice): the caller (or
a future loop) calls mixa_audio_poll(), which queries 'status mode' and advances
to the next item when the device reports stopped. Documented, not hidden.

Semantics (reference parity: AudioServiceBinder)
------------------------------------------------
* next/prev move the playlist position by ONE and reset to the start of that
  file (the binder's "bump one second" behavior is not carried over; the
  ClearShell UI buttons mean skip).
* next/prev on the last/first item wrap ONLY when is_loop is set; otherwise the
  mode machine just ends (MIXA_AUDIO_MODE_ENDED) / rewinds.
* next_file/prev_file probe candidates and skip files that fail probe
  (missing, dir, unsupported ext); play_* also re-ini so stop() remembers the
  exact seek point of the OLD track in set_list order.
* Classify is purely extension-based, case-insensitive: "mp3" and "wav" from
  the device's audio_exts. Only Probe (which checks existence) wraps missing
  files as MIXA_AUDIO_ERR_MISSING, dirs/unknown ext as ERR_UNSUPPORTED.
* is_random priority is NOT the reference's: AudioServiceBinder.nextFile/
  prevFile treat isRandom as a full REPLACEMENT for the sequential scan (a
  fully random pick with its own random-order retry, never touching the
  sequential/isLoop paths at all). This port instead always tries the
  immediate sequential neighbor FIRST regardless of is_random, falling back
  to the random pick only when that fails -- so a valid immediate neighbor
  is always played sequentially even with "shuffle" on. This is an existing,
  already-tested, intentional simplification (see tests/mixa_audio_selftest.
  lm1's own T12 comment, "the linear next scan has no candidates at the
  tail" -- the test author deliberately picked a starting position where
  the sequential scan is guaranteed empty specifically to exercise the
  random fallback), not a newly found defect; recorded here explicitly so
  it reads as a documented delta rather than something nobody noticed.

Fixed (ticket 20260912-054054's audio-backlog review): mixa_audio_next_file
and mixa_audio_prev_file's is_loop wrap now retry the CURRENT position
itself once every OTHER index has been exhausted, matching
AudioServiceBinder.nextFile/prevFile's own final `if (checkFile(start))
return true;` inside their isLoop branch, which this port had dropped.
Without it, a looped playlist where the current track is the ONLY entry
that still probes OK reported END instead of restarting it. New tests
mixa_audio_selftest.lm1 T13b: a 2-item list where the OTHER item is marked
skip and the current one is not, for both next_file (pos=0) and prev_file
(pos=last); a companion no-is_loop check on the identical setup confirms
the retry is gated to the isLoop branch only, exactly like the reference
(genuinely ends there). Confirmed the fix is load-bearing by reverting it
and re-running: the new next_file check fails with END (rc=8) as expected,
not a vacuous pass. 85 checks, 0 failures, two hash-identical runs
build/mixa/opencode/audio_seam/run_20260912_054916_355_a5ff9849/ and
run_20260912_054930_357_72943f15/. run_audio_native_selftest.ps1 (24/0,
real MCI, run_20260912_054949_248_7d8bb9f8/) unaffected -- next_file/
prev_file's is_loop wrap is portable-layer logic, not device-specific.

Testing
-------
Run from mixa_manager:

    ./run_audio_selftest.ps1         # fake device, deterministic, 85 checks
    ./run_audio_native_selftest.ps1  # real MCI, 30 checks (plays ~8 s silence)

Both runners pin the compiler SHA256 (65D5A5ED127CA1BAEBDD1D500A5B74CEEA63EC
1985EAC52EDEF28EFEB261C936), translate the concrete header first (the portable
header predefs it), use strict gcc flags, and run in isolated
build/mixa/opencode/<seam>/run_<timestamp>_<guid>/ dirs.

The fake selftest covers: create with per-table name/exts, classification,
probe of every device error class, full start/stop/resume/seek/progress/
duration/position/poll cycles in both loop modes, next/prev wrap + play_next/
play_prev rewind, skip-on-failed-probe, END handling, destroy, and null-argument
negatives, plus is_loop wrap-retry-current coverage (85 checks, 0 failures).

The native selftest drives the REAL win32 backend: it generates an 8 kHz /
8-bit / 8 s digital-silence WAV named "My Sound 8s.wav" (space in the path to
exercise MCI quoting) and asserts create/cur_file-empty, classification,
missing-file start returns ERR_MISSING, play reports playing, poll does NOT
advance a playing track, duration ~8000 ms, seek-to-3000 while playing, stop
remembers the position, and resume, plus native MCI failure coverage (T5b,
added under ticket 20260912-054054's audio backlog): a plain-text file named
with a ".wav" extension passes probe (which only checks existence/extension,
not content -- mixa_audio_win32_dev_probe's own GetFileAttributesW +
extension check) but must fail at load() when MCI's real "open ... type
waveaudio" command rejects its non-RIFF content -- a genuine backend
failure, not an injected fault. Asserts the exact MIXA_AUDIO_ERR_BACKEND
code, that is_playing() stays false, and that a SUBSEQUENT legitimate load
on the good fixture still succeeds afterward -- the failed MCI open does
not leak the alias or leave device state stuck (30 checks, 0 failures, two
hash-identical runs
build/mixa/opencode/audio_native_seam/run_20260912_055506_092_def998fe/ and
run_20260912_055517_067_a75a8f1d/). The runner now also hashes both
implementation files (mixa_audio_win32.lm1, mixa_audio.lm1), not just their
headers -- closing the gap ticket 20260912-011300 flagged ("Audio runner

Known L1 findings while porting (see also PORT_OF_CLEARSHELL.txt)
-----------------------------------------------------------------
* Const pointers are spelled `const: @(char name)` (name INSIDE the parens) for
  BOTH parameters and locals; `const: @(char) name` fails to translate.
* Casting a subscript/array element or casting inside an if:/while: condition
  is miscompiled by l1trans; use the double-cast form
  `(cast: (int) (cast: (unsigned char) expr))` or hoist into an int local.
* `(cast: unsigned) expr` always miscompiles; declare `unsigned: v` and compare
  directly against literals (GetFileAttributesW attribute checks).
* The common header predefs the concrete header, so cross-header types
  (MixaAudioVTable) must live in the COMMON header; the concrete header alone
  cannot reference them. The win32 table prototype therefore sits in
  mixa_audio.h.lm1, and the fake-only selftest simply never calls it.
* In wide string formatting `%s` is the NARROW-string specifier and `%ls` the
  wide one; passing a char* to %ls silently mangles MCI commands (status
  length/position came back 0 until the %s fix).

No part of this slice runs at startup or touches the main executable. The next
wiring step (separate ticket) attaches the "MP3" button to a MixaAudio instance
built from mixa_audio_win32_table(), feeding it a directory listing and calling
mixa_audio_start/poll/play_next/play_prev/stop/progress.

Button/App integration scope (ticket 20260912-055800): checked directly
against the reference before building anything, rather than assumed. The
"MP3" button (ClearShell.mp3(), ~L7634) and "App" button
(ClearShell.app(), ~L7564) each open a WHOLE nested sub-panel of their
own (Mp3Adapter: prevFile/prev/pause/next/nextFile/random/repeat buttons
plus a SeekBar and duration/timer display; App similarly opens its own
adapter panel) -- neither is a single hit-one-button-call-one-function
integration like Share's Send button was. PORT_OF_CLEARSHELL.txt already
sequences both as their OWN later stages ("Current queued OpenCode
sequence: nested same-app short-message window, then App/shortcut
adapters, then MP3/audio adapters"), consistent with STATUS.txt's "Full
file-manager features come later... not an excuse to expand the first
runnable milestone." Building either full sub-panel now would be
inventing scope, not closing a small backlog item.

What already works today with zero new code: mixa_button_dispatch_hit
(mixa_manager/mixa_button_dispatch.h.lm1/.lm1, built for Share) is
generic -- any button with no wired action already opens the real "нет
функции" window. That is the honest, currently-correct behavior for a
hypothetical MP3 or App button until their real sub-panels exist. Closing
the audio backlog's "button/App integration" item at this milestone on
that basis; the real Mp3Adapter/appAdapter sub-panels remain queued as
their own future stage per the sequencing above, not silently dropped.
