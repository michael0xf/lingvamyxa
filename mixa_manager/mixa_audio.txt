mixa_audio — audio playback seam (ClearShell "MP3" button, ticket 20260911-154950)
==================================================================================

Purpose
-------
One bounded slice: portable playback API for the desktop ClearShell port, backed
on Windows by the system MCI layer. The main executable is NOT wired to it yet
(same honest status as the app seam): this slice delivers the self-contained
playback core, its deterministic headless selftest, and a real win32/MCI smoke
test.

Design
------
A PORTABLE controller (mixa_audio.lm1) owns all playlist/state-machine logic and
talks to a DEVICE through a function-pointer vtable (MixaAudioVTable in
mixa_audio.h.lm1). Two devices exist:

  * mixa_audio_win32.lm1    real backend: MCI (winmm), links -lwinmm
  * fake (test-only)        deterministic backend embedded in the selftest

The win32 device is an MCI alias owned by one MixaAudio instance:
  open "<path>" type <waveaudio|mpegvideo> alias mixa<N>
  set mixa<N> time format milliseconds
  status mixa<N> length|position|mode
  play / seek / stop / close

WAV is guaranteed via the waveaudio MCI driver. MP3 rides the mpegvideo MCI type
and therefore depends on a system MP3 renderer (declared honestly: on machines
without one, MP3 probe succeeds but load fails with MIXA_AUDIO_ERR_BACKEND).

End of track is NOT signalled to us (no MCINOTIFY in this slice): the caller (or
a future loop) calls mixa_audio_poll(), which queries 'status mode' and advances
to the next item when the device reports stopped. Documented, not hidden.

Semantics (reference parity: AudioServiceBinder)
------------------------------------------------
* next/prev move the playlist position by ONE and reset to the start of that
  file (the binder's "bump one second" behavior is not carried over; the
  ClearShell UI buttons mean skip).
* next/prev on the last/first item wrap ONLY when is_loop is set; otherwise the
  mode machine just ends (MIXA_AUDIO_MODE_ENDED) / rewinds.
* next_file/prev_file probe candidates and skip files that fail probe
  (missing, dir, unsupported ext); play_* also re-ini so stop() remembers the
  exact seek point of the OLD track in set_list order.
* Classify is purely extension-based, case-insensitive: "mp3" and "wav" from
  the device's audio_exts. Only Probe (which checks existence) wraps missing
  files as MIXA_AUDIO_ERR_MISSING, dirs/unknown ext as ERR_UNSUPPORTED.
* is_random priority is NOT the reference's: AudioServiceBinder.nextFile/
  prevFile treat isRandom as a full REPLACEMENT for the sequential scan (a
  fully random pick with its own random-order retry, never touching the
  sequential/isLoop paths at all). This port instead always tries the
  immediate sequential neighbor FIRST regardless of is_random, falling back
  to the random pick only when that fails -- so a valid immediate neighbor
  is always played sequentially even with "shuffle" on. This is an existing,
  already-tested, intentional simplification (see tests/mixa_audio_selftest.
  lm1's own T12 comment, "the linear next scan has no candidates at the
  tail" -- the test author deliberately picked a starting position where
  the sequential scan is guaranteed empty specifically to exercise the
  random fallback), not a newly found defect; recorded here explicitly so
  it reads as a documented delta rather than something nobody noticed.

Fixed (ticket 20260912-054054's audio-backlog review): mixa_audio_next_file

Known L1 findings while porting (see also PORT_OF_CLEARSHELL.txt)
-----------------------------------------------------------------
* Const pointers are spelled `const: @(char name)` (name INSIDE the parens) for
  BOTH parameters and locals; `const: @(char) name` fails to translate.
* Casting a subscript/array element or casting inside an if:/while: condition
  is miscompiled by l1trans; use the double-cast form
  `(cast: (int) (cast: (unsigned char) expr))` or hoist into an int local.
* `(cast: unsigned) expr` always miscompiles; declare `unsigned: v` and compare
  directly against literals (GetFileAttributesW attribute checks).
* The common header predefs the concrete header, so cross-header types
  (MixaAudioVTable) must live in the COMMON header; the concrete header alone
  cannot reference them. The win32 table prototype therefore sits in
  mixa_audio.h.lm1, and the fake-only selftest simply never calls it.
* In wide string formatting `%s` is the NARROW-string specifier and `%ls` the
  wide one; passing a char* to %ls silently mangles MCI commands (status
  length/position came back 0 until the %s fix).

MP3 stage 3 -- directory-to-playlist feeding + top-level MP3 button
-------------------------------------------------------------------
Ticket 20260912-065230 asked for one composed stage: accepted directory-
to-playlist feeding plus a real top-level MP3-button dispatch opening
the accepted audio panel, all exercised by a single test. That shape ran
into a hard toolchain limit, so what shipped is the same functionality
split across two real modules with two real test suites. The limit, the
split and what is NOT covered are all recorded below rather than
smoothed over.

The limit: l1trans's "import path table" holds exactly 16 imports
--------------------------------------------------------------------
This is a DIFFERENT limit from the "too many header type names" one
already recorded above; that one is generous and this combined chain
does not trip it. Bisected against the pinned stable65D5 compiler
(SHA256 65D5A5ED...C936) with predef-only probe files that contain no
logic at all -- so the count is of FILES reached transitively, not of
code:

  probe with 16 imports (mixa_audio_panel chain 13 + mixa_dir chain 3)
      -> exit 0, translates cleanly
  the same probe plus ONE more import (mixa_audio_launch.h.lm1)
      -> exit 1, "l1trans error: mixa_manager/mixa_audio_launch.h.lm1:
         0:0: import path table full"

Smallest reproducer (7 predef lines, no test logic whatsoever):

  predef: "mixa_manager/mixa_audio_panel.h.lm1"
  predef: "mixa_manager/mixa_audio_panel.lm1"
  predef: "mixa_manager/mixa_dir.h.lm1"
  predef: "mixa_manager/mixa_dir_win32.h.lm1"
  predef: "mixa_manager/mixa_dir_win32.lm1"
  predef: "mixa_manager/mixa_audio_launch.h.lm1"
  predef: "mixa_manager/mixa_audio_launch.lm1"
  (plus an empty main that returns 0)

Two things were checked and ruled out before concluding this, because
both looked plausible at first and both are wrong. (1) It is not caused
by redundant top-level predefs in a test file: trimming a test's own
predef block from 12 lines to 4 moved which file the error was reported
against but did not fix it. (2) It is not an edge/statement count that
redundant paths inflate: removing a genuinely redundant predef edge
(mixa_audio_launch.h.lm1's own predef of mixa_dir.h.lm1, which
mixa_dir_win32.lm1 already reaches anyway) changed nothing at all,
because the target file was still in the set. The table counts distinct
files reached, and 17 of them is one too many.

What this rules out
-------------------
A single module that both enumerates a directory and opens the panel
needs the mixa_dir chain (3 files) AND the mixa_audio_panel chain (13
files) plus its own 2 = 18. That is over the table no matter how the
test around it is written, because the cost is in the TYPES the unit
must see, not in the test code -- a one-line smoke test of that module
costs exactly as many imports as an exhaustive one. Wiring the dispatch
through the accepted mixa_button_dispatch_hit is over the table for the
same reason: it re-pulls mixa_app_window (2 files already reachable via
mixa_audio_panel) plus its own 2.

What shipped instead
--------------------
mixa_audio_scan.h.lm1 / .lm1 (8 imports): directory-to-playlist
scanning only. Enumerates ONLY through mixa_dir_list_open/next/close,
preserves that seam's own observed order append-only, skips directory
entries, builds full UTF-8 paths under a checked bound, and filters ONLY
through mixa_audio_is_audio_path. No duplicated Win32 directory calls
and no duplicated codec-extension rules. Hands back an owned snapshot in
MixaAudioScanResult; on any failure hands back nothing and frees
everything that attempt allocated, closing the directory on every path.
The snapshot travels in a struct rather than through a char*** out-
parameter because a triple pointer is a form this codebase has nowhere
else, while an owned struct field is what every module here already uses.

mixa_audio_launch.h.lm1 / .lm1 (15 imports): everything after scanning.
Takes an owned snapshot via mixa_audio_launch_set_items, feeds it
through the accepted mixa_audio_set_list, starts playback, and opens the
accepted MixaAudioPanel, driven by a real top-level button hit through
mixa_audio_launch_hit. That hit-test is manual -- mixa_button_panel_hit,
the same primitive mixa_button_dispatch_hit dispatches on, in the same
manual pattern already accepted inside mixa_app_panel_hit and
mixa_audio_panel_hit -- because the accepted dispatch module does not
fit, as recorded above. A miss returns NONE and opens nothing, leaving
the fallback decision to the caller exactly as a dispatch miss does.
List/audio/panel statuses are kept separate (list_status, audio_status,
panel_status) so a caller can show the exact failing stage in the
existing nested error window.

NOT done -- stated plainly
--------------------------
1. The two-call glue that joins the halves (scan a directory, hand the
   snapshot to the launch context) needs all 18 imports again and
   therefore cannot be compiled in ANY single translation unit under
   stable65D5. It is not written and is not claimed. It belongs with the
   App/main-loop wiring this ticket already defers; until the toolchain
   table grows, joining these two halves has to happen in a unit that
   does not also carry both chains' types.
2. mixa_audio_scan's own per-entry 300-byte path bound is defensive-only
   on this platform and is NOT exercised. Reaching it needs a full path
   over 300 bytes, and a stock Windows MAX_PATH is 260: no such file can

What was built
--------------
mixa_mp3_open_dir scans a directory through mixa_audio_scan and hands
the snapshot to mixa_audio_launch_set_items, then runs the launch.
mixa_mp3_hit is the real top-level button: a hit re-scans the directory
it is pointed at and opens the panel over what is there NOW, which is
what a user pressing MP3 expects; a miss takes no action, opens nothing
and does not even scan.

The scan runs to completion BEFORE any teardown, so a directory that has
gone missing or refused enumeration leaves the context exactly as it
was. A failed refresh cannot blank a working panel. The selftest asserts
this by capturing the audio instance pointer before the failed hit and
requiring it to be the same pointer afterwards -- proving nothing
changed, rather than merely proving something is non-null.

The split is KEPT even though it could now be folded back. Only this
composition module and its test need the candidate; mixa_audio_scan (8
imports) and mixa_audio_launch (15) each still build and test under
stable65D5, so nothing already accepted starts depending on an
unpromoted compiler.

The scratch instance, stated rather than hidden: scanning filters
through the accepted mixa_audio_is_audio_path, whose signature takes a
MixaAudio even though it only reads the vtable's audio_exts. So
mixa_mp3_open_dir creates one MixaAudio purely to ask that question and
destroys it before the launch creates the instance that actually plays
-- one extra device open and close per press. A vtable-level extension
predicate on the accepted audio seam would remove it; that is a change
to an accepted API and was not made unasked.
