mixa_manager L2 parity runner inventory
========================================

Built for the runner-uniformity ticket (20260914-003000/001000 and
follow-ups), at lingvamyxa-d6's request, before proposing a single
parameterized runner design. Extracted mechanically from the 52
run_mixa_*_l2_parity.ps1 files on main as of this commit, not from
memory. Columns:

  probe        = has a dedicated ABI-probe struct-layout check before
                 the main gate (yes/no)
  exec         = "diff" = builds+runs both oracle and L2 sides and
                 byte-diffs their trace; "build-only" = never executes
                 the L2 side at all (no second trace to diff)
  extra_deps   = count of extra real-dependency .o files linked into
                 the L2-side harness executable, beyond the harness
                 object and the module's own translated .o (0 = links
                 only itself)
  barrier_set  = which of the three known-barrier substrings this
                 runner's $KnownBarrier regex OR's together:
                 U=unknown foreign type, I=incompatible entry
                 signature, A=unsupported own array declaration
  fixture      = "none" (no filesystem fixture at all, passes "" to
                 both sides), "shared-pattern" (own $FixtureDir /
                 $L2FixtureDir or $OracleFixtureDir / $L2FixtureDir
                 pair, same shape as everyone else), or a named
                 bespoke fixture helper
  norm         = fixture-root trace normalization present (yes/no) --
                 only relevant when fixture != none
  runtime_trio = whether this runner builds the L2 runtime header/
                 object set (Add-L2RuntimeSupport after this ticket,
                 or still hand-rolled) -- "conv" = already converted to
                 the shared helper, "raw" = still hand-rolled, "n/a" =
                 doesn't need it (no runtime graph calls)

  mechanical extraction relies on for extra_deps -- it builds
  $l2LinkArgs as a PowerShell array first (a different code shape from
  every other runner), so its true extra-dep count was not extracted
  automatically here; visually it links 2 real dependency objects
  (appWindowO-equivalent + appWin32O-equivalent) plus the runtime trio.
** app_main's count is from reading the file directly (comment: "13
   objects + headers" for the always-built REAL win32 chain, plus a
   second, smaller object list for the headless behavioral harness --
   17 is the union of distinct object variables on its own link line,
   not directly comparable to the other rows' single-executable count).

Shared boilerplate across all 52 (already identical or now-identical
after prior tickets):
  - pin-hash verification block (Test-Path + Get-FileHash + compare to
    a literal 64-hex-char string) -- IDENTICAL in all 52 files, the
    literal hash string re-pasted 52 times. This is real duplication;
    see the note at the end.
  - $GccStd guard-flag assembly -- identical in all 52.
  - $RunTimestamp/$RunGuid/$RunDir scaffolding -- identical shape,
    differs only in the per-module base-dir name.
  - Invoke-Cmd helper function -- byte-identical in all 52 (modulo the
    dot-source block this ticket is adding).
  - the oracle-side translate/compile/link/run block -- identical
    SHAPE per module (varies only in which real dependency objects it
    links, which is exactly module-specific data).
  - the $KnownBarrier check and EXPECTED_CORE_BARRIER/UNEXPECTED_
    FAILURE branching -- identical shape, varies only in which barrier
    substrings are OR'd (3 known combinations across the corpus, see
    barrier_set column).
  - the final PASS/PARITY_FAILURE branch and $Summary here-string
    format -- identical shape modulo which variables it interpolates.

Module-specific, NOT reducible to a shared function without losing
information:
  - which real dependency .o files get built and linked (0 to ~17,
    different variable names, different translate/compile call chains
    -- this is a per-module dependency graph, not a flat list, since
    dependency objects each need the SAME real-dependency chain the
    corresponding *_selftest.ps1 already established).
  - which of the 3 known-barrier substrings apply (module-specific,
    tracks what l2trans actually reports for that module's own
    syntax).
  - whether the L2 side is ever executed at all (app_main: no).
  - whether an ABI probe runs first (app_controller, buttons: yes).
  - fixture shape: none / the common $FixtureDir+$L2FixtureDir pair /
    a bespoke fixture (audio_win32's WAV generator, console_window's
    inline literal paths).
  - link libraries (-lgdi32/-luser32/-lkernel32 for real win32 exes,
    $GccLibs, $LinkLibs, or nothing, depending on whether the module's
    dependency chain touches Win32 APIs).

The falsifying check, per your instruction 3
----------------------------------------------
app_main is the module whose logic does not fit a per-module DATA
table. It isn't just "different parameters" -- it has a structurally
different CONTROL FLOW from the other 51: no second execution, no
trace diff, no PASS-via-comparison, a "13 objects + headers" real
dependency chain reused from a different, already-accepted script
(run_win32_smoke_selftest.ps1) rather than built fresh from a per-
module list, and its own reasoning for skipping the ABI probe
entirely (documented in its own 45-line header comment) that doesn't
generalize to any table row. A single parameterized runner whose
per-module input is a data table (fixture shape, barrier substrings,
object list) would need a real escape hatch for app_main -- either a
separate script (defeating "one runner") or a full mini-DSL inside the
table for "which steps run at all" (which is a second parameterized
system hiding inside the first).

Everything else in the 52 DOES fit a flat per-module table: dependency
object list, barrier substrings, fixture shape, and link libraries are
all data, not control flow, for 51 of the 52 rows.

Recommendation (for lingvamyxa-d6 to accept, adjust, or reject)
------------------------------------------------------------------
- One parameterized run_mixa_l2_parity.ps1 -Module <name> for the 51
  rows that share control flow (build oracle, translate L2, on
  success build+link+run L2, diff traces byte-for-byte, else known-
  barrier/unexpected-failure branch). Per-module data as a small
  PowerShell hashtable table (name -> @{ Deps=@(...); BarrierSet=@(...);
  Fixture="none"|"shared"|<bespoke script block>; LinkLibs=... }),
  either inline in the new runner or in one data file it dot-sources.
- app_main stays its own script (run_mixa_app_main_l2_parity.ps1,
  unchanged) -- it is a build-only, no-diff check with its own real
  dependency chain and its own reasoning for skipping the ABI probe;
  forcing it into the table is the "table that fits nothing" case you
  warned against.
- The pin hash: move the single 64-hex-char literal into
  lib_l2_runtime_support.ps1 (a new $ExpectedL1Hash-exporting
  variable, or a function both the new parameterized runner and
  app_main's own script call) so it is asserted from one place instead
  of pasted 52 times, per lingvamyxa-e2's review note. This is
  independent of the parameterized-runner decision and can land in the
  same lib file this ticket is already touching.
