What the Lingvamyxa spec requires of Mixa Manager
==================================================
Read 2026-09-11 against Lingvamyxa_spec.txt at 82a1901 (15320 lines).

This is a DIGEST FOR THIS APPLICATION, not a summary of the language. It records
what the Message model obliges us to do and what it forbids, with line numbers,
so the app does not have to re-derive it. The spec is the authority; where this
file and the spec disagree, the spec wins and this file is stale.

SCOPE OF THE READING, stated so nobody over-trusts it. Read closely: 19.28.R2.1
through R2.6 (11157-11400), 19.29.6 Running Message (12106), 19.29.7 Boundary
(12209), 19.29.7.1 the implementable slice (12237-12623) in full, 19.29.7.2
(12623), 19.29.8 handoff through today's diff, and 19.32.10-21 crypto by
heading. NOT read: the language core 0-19.27, 19.28.10 World Wide Mix, and
sections 20 and 21 beyond what the Message text cites.


1. THE ONE THING THAT BINDS US MOST

19.28.R2.2, near line 11225:

    "Throughout the language core and complete standard distribution, low-level
    synchronization is used only inside the Message mechanism... Other
    components, including Mix, builders and bundled applications, coordinate
    through Messages, not their own locks, atomics, shared mutable management
    tables or private worker schedulers."

mixa_manager is a bundled application. So we get no mutex, no atomic, no shared
management table, no private worker pool of our own - ever, not merely for now.
Everything concurrent we want must be Messages.

Reinforced at 19.28.R2.6: "A C worker pool owning a shared process-wide Message
registry is forbidden", and in 19.29.7.1 the exec-host prototype
(LMX_MSG_EXEC_HOST_V0.txt) is called "evidence, not the accepted architecture"
and "must not be promoted to the application as-is."

3. THE SHAPE OF A TURN

19.28.R2.3 (11302) and 19.29.6 (12106):

    one turn dequeues AT MOST ONE admitted input from the FIFO
    -> policy combination -> execute an admitted callable
    -> stage results and outgoing Messages in FIFO order
    -> common cleanup / publication / scheduling boundary

    no more than one turn of a Message executes at a time
    serial turns make arena mutation safe with no source-visible lock
    the C stack is the sole implicit activation history and is NEVER copied
      into the Message graph automatically

21.10 yield is an activation dirty-only checkpoint. 19.29.7.1: "Staging then
yield in one turn does not commit." Publication happens at end_turn.

A failed turn discards its staged outbox and does NOT undo external effects
already performed.


4. CREATE, SEND, STOP - the contract we will actually call

create (19.29.7.1, from 12280)
    reserves a child identity and a DISTINCT INACTIVE ARENA during the parent's
      turn, and copies initialData into it
    Mix path = parent path with one integer APPENDED from the parent's child
      counter. Concatenation, not arithmetic: 34.3 gives 34.3.1 then 34.3.2,
      and that child's first child is 34.3.1.1. First allocated child is 1.
    retry of the same (parent, create_id) returns the SAME child and path and
      consumes no counter value
    an ABORTED reservation is not reused - a later retry of that create_id gets
      a new slot and a NEW path segment
    the child DOES NOT RUN before the creator's successful end-turn publication
    a failed parent turn releases uncommitted children
    LmxMsgAddr, the mailbox slot, is NOT the Mix path

send (from 12330)
    stages a transport-owned COPY of the envelope. No raw pointer, no caller
      closure, NO UI OBJECT crosses.
    staging status means only that the sending turn accepted it for its outbox.
      It is not admission and it is not execution.
    dedup key is (recipient, sender, id), so two senders' local id=1 do not
      collide
    sender staging is invisible to the receiver

stop (from 12363)
    KIND_STOP is internal close control, NOT KIND_CANCELLED outcome data
    admission sets a CLOSING FLAG. It does not enqueue handler-visible work,
      does not mark STOPPED, does not free an executing arena.
    the target finishes its current turn, then at end_turn exits its loop and
      requests the same orderly close of its children
    ordinary end_turn WITHOUT a close request does not terminate the Message

envelope fields: id, correlation (19.31.4 - the result or failure is an ordinary
Message whose correlation equals the request id), replyTo.


5. WHO OWNS A COPY JOB - and what the spec actually says

An earlier revision of this section said flatly that a long copy is NOT a child
of the window. Mikhail corrected it: copying IS a child of the window, and if
the window wants to hand the job to some task owner it does that through a
Message and closes. He is right, and the spec is narrower than I made it.

19.29.7.1, near 12376, is CONDITIONAL on intent:

    "Jobs MEANT TO OUTLIVE A UI are created under an explicitly longer-lived
    controller; the UI is only a reply target."

It says nothing against a copy being the window's own child. That is the
ordinary case, and the natural one: the copy is the window's business, it
reports to the window, and it goes when the window goes.

What the spec does refuse is the OTHER thing - expecting a child to keep running
after its parent closed. In the same stop() paragraph:

    "there is no orphan-continuation exception for copy jobs"

A closing parent asks its direct children to close at its end_turn, and a child
whose parent vanished requests its own close through the liveness poll. So
"child of the window" and "survives the window" are simply incompatible; nothing
grants copy jobs an exemption.

5.1. So the decision is made AT CREATE TIME, by whoever creates

    window creates the worker        the copy is the window's, and closes with it
    controller creates the worker    it outlives the window; window is replyTo

Both are legitimate. Which one to use is an application choice about what the
job is FOR, not a rule the language imposes.

5.2. Handing off later: the spec has no operation for it

Mikhail asked whether the spec really says that, and how the author intends a
Message to be forwarded at all when its whole control surface is two flags. The
honest answer, after re-reading the text rather than my note about it:

THE SPEC DOES NOT SAY RE-PARENTING IS DEFERRED. It does not mention re-parenting
at all. An earlier revision of this section claimed the deferred list covered
it; that was wrong. The deferred list (19.29.7.2, verbatim) is ARENA and GRAPH
work:

    graph-copy and graph-reference retargeting; join/splice of already-running
    live arenas; codec/wire serialization; multi-owner split/link as addressed
    request/result; activation of an already-running Message; full incoming
    LMX-text/arena ownership transfer

Those are about MEMORY. A parent-child link is a different thing entirely - by
12315 it is two authorities: "the child's authority to observe parent liveness
and the parent's authority to request stop". Merging arenas and reassigning
supervision are not the same operation, and I treated one as evidence about the
other.

What IS true is narrower and, for our purposes, the same in effect: no operation
exists that moves a RUNNING Message anywhere.

    create      makes a new child under the creator
    send        moves an ENVELOPE, not a Message
    stop        closes; it does not relocate
    adoption    exists only for a NON-EXECUTING Message (19.29.7) and for a
                FAILED arena going to its parent (19.29.8)
    lmx_message.h has no transfer, adopt-running or reparent entry point

And "activation of an already-running Message" is explicitly deferred, which
closes the one route that might have been read as a transfer.

So a running job today can be closed or left alone. Moving it means re-issuing
the remaining work to another owner, which the spec supports through "Recorded
progress may survive separately" - the new owner creates its OWN child and
resumes from the carried progress.

5.2.1. RESOLVED - the question was mine and it was malformed

Mikhail answered it, and the answer is already in the spec; I had assembled the
pieces wrongly rather than found a gap.

    A DELIVERED MESSAGE HAS NO PARENT. It writes success=1 and running=0 and
    joins the receiver's arena. From that moment the parent treats it as
    delivered and removes it from its list. In normal operation a Message
    schedules itself; shutting it down on a timeout is force majeure. And a
    Message closes ITSELF when the parent stops answering its periodic polls.

Verified in the text, 12595-12601:

    "When the child finishes its assigned operation, it sets success=1 and then
    running=0. This also applies to a DELIVERY-ONLY MESSAGE with no executing
    thread; its executor marks the completed delivery. The parent's
    control-state check observes success and removes the child from active
    assignment/liveness tracking."

with 19.29.7: adoption of a NON-EXECUTING Message at the consuming end-turn
transfers ownership into the receiver's one logical arena, with stable block
addresses.

So a running Message is never moved, because nothing needs moving. What travels
is DELIVERY AS AN ASSIGNMENT: a Message whose job is its own delivery completes
by arriving, leaves its parent's list, and its storage joins the receiver. No
parent changes, so the Mix-path objection I raised dissolves with it - there is
no path to reassign.

Why I got it wrong, since the shape is worth recognising: I was looking for an
operation that moves a running worker between supervisors. The model has no such
operation and needs none, and its absence read to me as a missing feature rather
than as a different design. Absence of an operation is evidence about the model
before it is evidence about a gap.

5.3. Staging is not completion - this part stands

At 12500:

    "Deliver(Message, target) completes when that delivery finishes; CopyFile
    (source, target) completes when that file copy finishes. Enqueueing or
    staging a copy request is not completion of CopyFile."

A progress bar that advances when the request is staged is reporting something
that has not happened. Per-item progress and failure are KIND_PROGRESS /
KIND_ITEM payload data, and continue-versus-stop is APPLICATION POLICY carried
in the request, not a core intrinsic - ours to decide and to write down.

A worker may send KIND_CANCELLED to a UI without shutting the UI down, and
explicit stop(worker) closes that worker only.


6. CONTROL FLAGS - the supervision mechanism, and what it does not prove

19.29.7.1, from 12525:

    every Message starts running=1, success=0, including one with no executing
      thread
    uint_fast8_t, belonging to the MESSAGE, not to its arena
    running means PERMISSION TO CONTINUE, not that an OS thread exists. Zero
      requests closure for that incarnation and is never reset to revive it.
    only ACTUAL COMPLETION of the assigned operation sets success=1; on finish
      the child sets success=1 and THEN running=0
    the parent's scheduler READS its direct children's flags on each of its own
      turns - no Message needed for that - and may set a child's running=0 on an
      emergency deadline without waiting or freeing the child's arena
    generated code checks the flag on method entry before loading used own
      fields, on loop backedges, and on method exit. On 0 it aborts to the
      execution root of that L3 Thread, never terminating an OS thread that may
      also run the parent or siblings.

What the flags DO NOT mean, spelled out in the spec because it is the obvious
wrong reading:

    success=0 means success has NOT BEEN OBSERVED, not proof of failure, even
      when running=0
    neither running=0 nor running=0 with success=0 proves quiescence or final
      failure
    observers must not rely on an indivisible snapshot of both flags, nor infer
      arena reclamation from either
    a liveness response (alive) is NOT completion
    all children reporting DELIVERY success is not an application-result barrier

6.1. How the L2 translator actually places these - read-only check, 2026-09-11

Checked in stg/l1_baseline/l2src/l2trans.lm1 because it decides what our wrapped
modules will contain. It matches 19.29.7.1 exactly.

STANDARD RECEIVERS ARE NOT METHODS. `if`, `while` and `for` carry no method
identity, no own-state loading, no dirty flags and no checkpoint:

    methods exist only from fn:/sub:  - l2_fn_close(fr, nm, "fn") / "sub" at
      4591/4593; everything method-scoped is indexed by a method index into the
      l2_m_* tables
    if/while emit straight through   - 6543 and 6579 write the L1 `if:` /
      `while:` with the condition token and nothing else
    the checkpoint is method-keyed   - l2_emit_checkpoint opens with
      "if: mi < 0 || ind = 0 -> return: 0" and then iterates
      l2_m_uses[l2_own_off(mi, i)], the per-method used-own table. No method,
      no checkpoint. It is emitted after actuals, immediately before a call and
      before return - never on entering a block.
    own-field loading EXCLUDES if    - the two lazy load sites, 6746 and 6788,
      are both guarded by l2_frame_head(stmt, "if") = 0, and a nested-if own
      declaration is refused outright (3306, "unsupported own declaration").

6.1.1. But a `for` DOES have fields, and they ARE restored at method entry

This is the part that surprised me, so it is written out. A non-method nested
structure is not uniformly stateless - `for` and `if` differ, and the difference
is `l2_scope_push`.

    only `for` pushes a scope. All five l2_scope_push sites (3183, 3274, 3509,
      4938, 6605) are guarded by l2_for_cstyle or an end-named `for`. `if` never
      pushes one.
    so an own declaration nested in a `for` is ACCEPTED (l2_scope_n != 0), and
      one nested in an `if` is REFUSED. Depth alone decides nothing; the scope
      stack does.

And the prologue restores them, in two passes after the entry poll (7019-7060):

    pass 1, per `for` structure: if any used own field belongs to it
      (l2_own_fid[oi] = k), emit a handle for the STRUCTURE ITSELF -
          l2_h{k}: lmx_branch_child(node, {l2_for_uchild[k]}U)
      so the `for` is a real Lmx child of the method node with a fixed child
      index, not a syntactic bracket.

    pass 2, per used own field: declare the working local, its graph handle and
      its dirty flag, then resolve the handle THROUGH ITS OWNER -
          fid >= 0   l2_q{k}_from: lmx_branch_child(l2_h{fid}, {fchild}U)
          fid <  0   l2_q{k}_from: lmx_branch_child(node, {uchild}U)
      and load the value: lmx_int_value / lmx_size_value / lmx_char_value of
      l2_q{k}_from\data.

So the answer to "are the fields of nested non-method structures restored on
method entry" is: for a `for`, YES - in bulk, in the prologue, through the
`for`'s own graph node. For an `if`, the question does not arise, because it
cannot own a field.

Note the whole prologue path is guarded by l2_m_alias[...] < 0 - aliased fields
(a same-named argument sharing the own declaration) are not restored here. Those
are the lazy 6746/6788 sites.

6.1.2. `if` substructures are VIRTUAL - they get no runtime graph identity

Mikhail asked: an `if` has at least two substructures, so are they virtual? In
the current implementation, yes. The child-index layout function (4036-4064)
builds the runtime graph under a method node like this:

    node
      +-- own field 0          uchild 0      direct fields first,
      +-- own field 1          uchild 1        consecutive
      +-- for#0                uchild 2      the `for` IS a node
      |     +-- hosted field   fchild 0        its fields are ITS children
      |     +-- hosted field   fchild 1
      +-- for#1                uchild 3
    l2_unit_base = next free index

An own field with host 0 gets a uchild under node; one with a host gets an
fchild under that host's `for`. Then every `for` in the table takes a uchild of
its own. `if` appears NOWHERE in this: there is no l2_if_* table anywhere in
l2trans.lm1, no index, no handle, no entry in the layout.

So the two bodies of an `if` exist in the parse tree as LM_P0_NODE_STRUCTURE and
become nested L1 control flow in the output, and that is all they are. They have
no runtime node to hold anything.

What reifies a structure is HOSTING A FIELD, and only `for` can host one -
l2_scope_host() returns the innermost pushed scope, and only `for` pushes. The
prologue goes further and emits a `for` handle only when some used field
actually belongs to it (the `hu` test at 7020-7029), so even a `for` is reified
at runtime only when it has something to hold.

6.1.3. Open question worth putting to Codex

Is this a decision or a limitation? The wording in the generated notes is
"Nested if own-decl is UNSUPPORTED own declaration", and "unsupported" reads
like the latter. In the language model a Structure is a Structure; if an `if`
body is one, a field declared inside it must eventually have somewhere to live,
and the layout function above has no slot to give it. Either the layout grows a
host kind, or the refusal is principled and should say why rather than
"unsupported". Not ours to answer.



THE ONE THING A LOOP DOES GET is the cancellation poll, and it is not activation
state - one flag load and test, c.lmx_msg_poll_escape(). l2_emit_poll is called
at exactly three kinds of site:

    6589, 6679   inside the loop body after the condition is retested - backedge
    7016         the method prologue - entry
    6705/6758/6768   before return - exit

which is 19.29.7.1's "method entry before loading used own fields, on loop
backedges, and on method exit", implemented literally.

Note the poll is NOT method-bound the way the checkpoint is: l2_emit_poll uses
mi only to choose the return form, and with mi < 0 it still emits a poll.

Fast path: an ordinary load and test. Relaxed atomics are permitted ONLY where
they compile to the same instructions as a volatile load or store of that type;
no lock, no read-modify-write, no fence, no helper call. Verify per target, and
if it does not hold, REPORT the unsupported fast path rather than substituting
something more expensive.


7. LIVENESS - who watches whom

Automatic polling has ONE direction: CHILD TO PARENT (12466). The child's
end_turn is the check and send opportunity. If the parent is absent, DEAD,
STOPPED, RELEASED or sustained-nonresponsive, the child requests its OWN orderly
close. A live idle parent keeps children alive.

Do NOT add a second mandatory automatic parent-to-child probe. But observation
is SYMMETRIC in effect: a parent may track expected communication from a direct
child and request its close after prolonged silence under its own policy, and
the parent reads the child's control flags directly during its own turns.

Timeout means LACK OF EXPECTED COMMUNICATION. Not proof of death, not proof of
completion.

Normal parent close already asks children to close at the parent's end_turn; the
poll is only the fallback for a parent that died abruptly.

Cadence and timeout are host settings - explicitly "not language constants and
not the mail-watcher interval."


8. ARENAS, AND THE HANDOFF RULE ADDED TODAY

Every Message owns exactly ONE logical arena. Ordinary local delivery TRANSFERS
OWNERSHIP WITHOUT CLONING; the delivered storage must be independently
transferable, and the sender cannot keep using it through mutable aliases.
Native addresses of transferred blocks stay stable. Copy and serialization
require an explicit operation or codec contract.

19.29.8, changed 2026-09-11:

    after final SUCCESSFUL completion, reclaim the Message's own execution
      history by default; keeping it requires explicit program data
    after final NON-SUCCESSFUL completion, TRANSFER its logical arena to its
      direct parent's lifecycle endpoint WITHOUT COPYING. The parent adopts the
      blocks and retains the failed root.
    each closing Message settles only its DIRECT children. In P -> C -> G with C
      and G failed: G's blocks join C, then C's blocks join P. No ancestor scan
      of grandchildren, no global crash manager, no graph clone.
    required external-resource cleanup precedes handoff; retaining a failed
      graph does not retain live file, socket or device handles

So failure evidence travels UP and survives in the parent, while success is
discarded. Consistent with worker death, where the KIND_DEAD diagnostic "lives
in the survivor, not in the dying arena."


9. WHAT THE OWNER ASKED FOR NEXT (PORT_OF_CLEARSHELL, 2026-09-11)

After the bounded calculator syntax module: the file manager's ORIGINAL FILE
OPERATIONS and ALL BUTTON AND PANEL BEHAVIOUR. Preserve ClearShell algorithms

    an action whose function is not yet implemented OPENS A NESTED INSTANCE OF

The application is its own dialog. That is an architectural requirement wearing
the clothes of a placeholder, and building it the easy way once makes the hard
way impossible later.


10. ALSO NEW, FOR AWARENESS ONLY

19.32.10-21 defines a Crypto Provider contract. L3 owns intent, key
relationships, policy and algorithm identity; the provider owns primitives,
secret representation and target storage. KeyRef is an opaque handle, never a
byte array by definition, and generation must not publish private bytes into the
Lmx graph. Targets: C99 with libsodium as one provider - also serving MIR, Wasm
linear memory and RISC-V through the L2 to L1 to C99 route - plus direct L3 JVM,
Wasm-GC, Lua and .NET CIL binding the same contract to JCA, a WebCrypto or host
capability, a Lua host module and System.Security.Cryptography. Detail in
include_languages/Lingvamyxa_Crypto_Provider_Seven_Targets_Implementation_EN.md.
Nothing here touches mixa_manager yet.

A managed L3 backend may MOVE objects while preserving reference identity; the
native profile must not - live nodes and service-pool entries stay at stable
addresses, and compaction by relocation is forbidden rather than merely
deferred. Our backend is native.
