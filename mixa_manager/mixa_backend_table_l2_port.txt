Scope
-----
Clean-L2 port of mixa_backend_table: dispatch forwards to whatever
concrete backend a live MixaBackend was opened against (open/present/
poll/clipboard_get/clipboard_set/glyph/close, all plain single-hop
forwards through backend->vt) plus the multi-backend registry
(mixa_backend_tables/table_by_name/default_table) built lazily from
per-build constructor lists (mixa_backend_ctors_headless/_win32),
never naming a platform backend itself so a headless-only link stays
free of Win32. 11 public functions, 209-line real body.

No dedicated ABI probe pair, and no L1 header unit to predef at all
-------------------------------------------------------------------------
Like mixa_pump.h before it, mixa_backend.h has no .h.lm1 counterpart
anywhere in this codebase -- real, plain, hand-written C (its own top
comment records converting it as planned future work, "H2", blocked on
run_mixa.ps1's own .h.lm1 -> .lm1.h conversion step not yet being
written). MixaBackend's own field (vt) is dereferenced via `\` with no
L1-level struct: declaration, proven safe by the established "`\`
defers to gcc" finding.

Barrier (current main) -- SAME DIAGNOSTIC TEXT, a further distinct
construct
-----------------------------------------------------------------------
l2trans error: mixa_manager\mixa_backend_table.lm2:9:1: incompatible
entry signature

Line 9 is `fn: mixa_backend_ctors_count () size_t` -- a BARE, BODYLESS
forward declaration (the module's own real, legitimate pattern: the
actual implementation lives in mixa_backend_ctors_headless.lm1/mixa_
backend_ctors_win32.lm1, separate per-build files, exactly the
"declare then link" shape this codebase already uses, and the exact
shape every parity harness this whole session relies on for its own
cross-object forward declares -- but ALWAYS fed only through l1trans
before now, never l2trans). Isolated with a minimal fixture:

    fn: probe_bodyless () size_t
    fn: main () int
    return: 0

reproduces the identical diagnostic regardless of the declared
function's own parameters or return type. This shares the SAME
diagnostic text as the fnptr-typedef-parameter finding already
cataloged for mixa_remove (ticket 20260913-171800), but the
TRIGGERING CONSTRUCT is fundamentally different: there, a function
WITH a body took a bare fnptr-typedef PARAMETER; here, the barrier
fires on a function that has NO BODY AT ALL, regardless of its
signature. This suggests l2trans's own "entry" model requires every
declared function to carry a body -- a structural constraint on cross-
translation-unit forward declaration that the "declare then link"
pattern (used throughout every module and harness this whole session,
always under the STABLE l1trans) may not carry over to l2trans
unchanged. Recorded here explicitly per the coordinator's own standing
request to report any new construct precisely, even when the
diagnostic text matches something already seen.
