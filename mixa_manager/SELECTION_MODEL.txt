Mixa Manager - the selection model
Ported from ClearShell FSync.java. Port it whole; do not simplify it.


1. Why this document exists

File operations are the most dangerous feature in a manager, and this selection
model is the part of ClearShell the language owner singles out as unlike
anything he has met elsewhere. It has run for seven years without a failure.

That history is the reason for the standing instruction: PORT IT AS IT IS. If a
piece of it looks unnecessary, the burden is on the reader to explain seven
clean years, not on the code to justify itself.

But weigh the evidence correctly, because the owner is explicit about its
limits: this was PHONE use, and not heavy. Seven years without a failure is
strong evidence about the EVERYDAY paths - select some files, deselect one,
copy. It says very little about the deep ones, which on a phone may simply never
have been reached.

So both halves hold at once, and the port must honour both: port the model
unchanged, AND test it properly rather than treating it as already
battle-hardened. A desktop manager will do heavier file work in a week than a
phone did in seven years, and it will be the first thing to reach the corners.


2. The intent, which explains the shape

Stated by the language owner: this is used INSTEAD OF "select all" and then
excluding what is not wanted - and the same mechanism works on the DIRECTORY
TREE, at any depth. He has not met it in any other manager.

Read that before the mechanism, because it changes what the mechanism is. It is
not a compact encoding of a selection. It is a different OPERATION:

    "everything under here, except these"

expressed directly, composably, and at any depth of the tree.

A flat list of paths cannot do this at all - not slowly, but not at all. "Select
all" in a flat model means enumerating, and enumerating a large tree is exactly
what nobody can afford. So other managers offer "select all" only within one
visible directory, and excluding from a whole tree is not on the menu because
their representation cannot hold the answer.

It also explains, in hindsight, why the consolidation keeps one level below the
top. If the everyday use is "select a subtree, then select a bigger tree around
it, then drop the bigger one", the inner selection is not redundant bookkeeping
- it is the user's earlier, still-wanted answer, and losing it would be losing
work.

2.1. The mechanism

Selection is NOT a list of selected files. It is:

    selected      a set of explicitly selected paths
    exceptions    path -> the selected ancestor it is excluded FROM
    reverse index ancestor -> the set of paths excluded under it

A path counts as selected if it is in `selected`, OR if some ancestor is in
`selected` and nothing between them excludes it.

So selecting a directory selects everything beneath it WITHOUT enumerating
anything. Deselecting one file inside a million-file tree stores ONE exception.
The cost of a selection is the number of user gestures, not the number of files
- which is the whole point, and why nothing gets materialised before an
operation can start.

3. The operations

3.1. select(file)

    already selected            -> log a conflict, do nothing
    currently an exception      -> remove the exception; then add an explicit
                                   selection ONLY if it is still not selected
                                   by inheritance
    otherwise                   -> add an explicit selection

The middle case is the one to get right: after cancelling an exception the file
may already be covered by an ancestor, and adding an explicit entry as well
would leave a redundant one behind.

3.2. removeSelect(file)

    remove any explicit selection; if there was one, DROP every exception
      registered under it - they are meaningless once it is gone
    then, if it is still selected by inheritance, record an exception against
      the ancestor that selects it
    if neither applied, the call did nothing - report that

3.3. The query, and the consolidation inside it

Walking up from the file:

    the file itself is an exception          -> not selected
    a parent is an exception                 -> stop. If a lower selected
                                                ancestor was already found,
                                                that one wins; otherwise not
                                                selected
    a parent is selected                     -> remember it, keep walking

Remembering while walking up gives the ancestors ordered topmost-first. The
topmost wins.

The query also CONSOLIDATES: when several nested ancestors are selected, the
lower ones are folded into the topmost and their exceptions are re-pointed at
it. A read operation mutating the structure is unusual and is deliberate here -
it is what keeps the representation from accumulating redundant nested
selections over a long session.

The lower-selection-wins rule is not a detail. It is what lets a user select a
tree, exclude a subtree, and then re-select something inside the excluded part.


4. The consolidation loop: RESOLVED by test. There is no bug.

I flagged `while (excessSelects.size() > 1)` in FSync.isSelect2 as possibly an
off-by-one, on the grounds that it leaves one nested selection unconsolidated. I
then said it produced no wrong answer, then said that was unproven. It is now
settled by running the algorithm rather than reading it: THE ORIGINAL IS
CORRECT, and the "tidier" > 0 would be a data-loss bug.

Method: the algorithm was transcribed faithfully - select, removeSelect,
isSelect2, isSelect3, with Array.pop taking from the end - and the two variants
were run against each other on random operation sequences, comparing the ANSWER
at every node after every operation.

They diverge. Shortest case, four operations:

    select   /a/b
    select   /a
    select   /a/b/c
    deselect /a

    original (> 1):  /a/b and everything under it REMAIN SELECTED
    variant  (> 0):  everything is deselected

The original is right. The user explicitly selected /a/b before selecting /a,
and deselecting /a must not destroy that earlier, independent choice.

Why one level is exactly enough, which is the part that makes it principled
rather than lucky. With four nested explicit selections a single query
consolidates the original to {/a, /a/b} and the variant to {/a}. Deselecting /a
then leaves the original covering everything under /a/b - which is precisely
what /a/b, /a/b/c and /a/b/c/d covered between them. Keeping the second-topmost
preserves the COVERAGE, because the deeper selections are subsumed by it.
Keeping none loses it. So `> 1` is the minimal representation that survives
losing the top, and that is not an off-by-one.

Ported code must therefore reproduce `> 1`. Changing it to `> 0` silently
discards a user's selection.

4.1. Why nested explicit selections are rare, which is why this never showed

select() on a child of an already-selected directory is a NO-OP - it reports a
conflict and adds nothing. So nested explicit selections arise ONLY when the
child is selected BEFORE the ancestor. That is an uncommon order on a phone,
which is consistent with seven years of light use never reaching it.

4.2. The tests the port owes

These are the cases, and they are not optional - they are the ones that
distinguish a correct port from a plausible one:

    the four-operation sequence above, asserting /a/b stays selected
    four nested explicit selections child-first, one query, deselect the top,
      assert the coverage of the survivor equals the union of what was lost
    select a child of an already-selected directory: assert it is a no-op
    deselect inside a selected tree, then re-select something inside the
      excluded part: the lower selection must win over the higher exception

5. What the port must not do

Do not "simplify" this into a flat set of paths. The flat version is what every
other manager does, it is what makes selecting a large tree slow or impossible,
and it is precisely what this model avoids.

Do not materialise a selection into a list before an operation. Copy, move and
overwrite take the SELECTION, and walk it lazily - FSync's own copy, move,
overwrite and moveOverwrite all take the current directory and the selection
rather than an array of files.
