mixa_share L2 port (share chain ticket 20260913-192700, module 1 of 6:
mixa_share, mixa_share_action, mixa_share_button, mixa_share_win32,
mixa_backend_table, mixa_backend_headless)
==========================================================================

Scope
-----
Clean-L2 port of mixa_share, the portable file-share seam (ClearShell
"Send e-mail" button, ticket 20260911-210200): title derivation
(ClearShell parity -- first two non-blank words leading-space-joined,
UTF-8-safe 32-byte-truncated fallback only when zero qualifying words
exist), owned-copy request lifecycle, and a vtable-driven asynchronous
begin/poll/cancel/destroy protocol matching the audio/app seam shape.
15 public functions plus 4 internal helpers, 453-line real body.

No dedicated ABI probe pair
------------------------------
Like every prior "predef the real header directly" module, this port
declares no L2-only struct of its own -- MixaShareRequest/
MixaShareVTable are reached via the REAL mixa_share.h.lm1 predef'd
directly, identically on both the real oracle and this L2 port. No
second struct layout exists to diff.

    Real L1-vs-L2 harness (one source, compiled/linked twice),

    partial commit, a directory soft-skipped and counted; a backend

    destroy before completion freeing the pending registration so a
    later independent request is unblocked (no leak); a second begin()

    rejection for every TERMINAL event (HANDED_OFF/CANCELLED/FAILED),
    not just PENDING, while a fresh NONE request still allows its first
    begin(); and null-argument negatives. 56 checks.

What would unblock the L2 side
--------------------------------
The same closed foreign-type allowlist gap already reported for every
prior module this segment. Fable's own ticket note confirms the const-
pointer-RETURN shape isolated for mixa_copy is already closed on the
core branch (cd12da13) and will disappear once that lands; this
module's own barrier (a custom-struct PARAMETER) is the original,
still-open shape. Landing the core integration onto main would be
expected to clear it without further changes to this module's own L2
header or .lm2 body.
