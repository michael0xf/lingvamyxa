Mixa Manager - the first runnable version
Mode 0.1.2. Scope, and what is deliberately outside it.


1. The mode is chosen, not defaulted

The first version is MODE 0.1.2, Norton Commander DELEGATION - the light mode
from Old_Mixa_Manager_Qt_model.txt section 5. Decided by the language owner
after establishing what a terminal actually is.

The distinction is not a technicality. A terminal is a PROTOCOL OVER A BYTE
STREAM: the child sends characters, and some of them are commands - move the
cursor, clear the screen, set a colour, switch to an alternate screen. The
screen is ADDRESSABLE and STATEFUL, and emulating a terminal means writing the
interpreter for that protocol.

We are not writing one. In 0.1.2 the console appends text to a file and shows
the file. The child gets a command and a place to write, and that is all.

The consequence, stated so it is not reported later as a bug: a program that
EXPECTS a terminal - vim, htop, anything full-screen - will emit escape
sequences and we will display them as garbage. That is correct behaviour for
0.1.2. Mode 0.1.1, with PTY or ConPTY and a terminal core, exists precisely for
those programs, and it is a later milestone.


2. What the first version does

    opens a text file and shows it in the LOWER layer
    edits lines, wrapping BY CHARACTER, never by word - as a console does
    a cursor in the lower layer, which is where a cursor belongs
    Enter takes the line from its start UP TO THE CURSOR, sends it plus a
      newline to the OS, and the child's output arrives at the same place, as if
      the cursor were writing it
    all of it lands in the FILE - the scrollback is not a buffer, see FILE_SEAM
    the UPPER layer draws, semi-transparently, over the console
    one button on it: F1 help, which writes its text into the console, ending
      with a newline


3. What is outside it

    no PTY, no ConPTY, no escape-sequence interpretation - that is 0.1.1
    no panels, no directory listing, no file operations beyond the console's
      own file. FILE_SEAM 3.5 cuts that down to append, read and size
    no word wrap
    no selection model in the UI - the model exists and is tested, but nothing
      selects anything yet
    no menus


4. Order of work

    glyphs, so anything is visible at all
    the process seam - spawn, read, write, status, kill, close
    the console: file-backed text, cursor, character wrap, editing
    Enter: line start to cursor, to the OS, output appended
    the F1 button on the overlay

The button can be built EARLIER than the process work and independently of it -
it needs the drawer, input routing and a write to the console, none of which
depend on running a child. It is a good early proof that the whole path is
connected.


5. What the first run LOOKS like, so nobody 'fixes' it

Mikhail, 2026-09-10: the first run will look odd - one F1 Help button, and the
cursor below it.

It will, and that is correct. Written down because it looks like three separate
bugs and is none of them.

    ONE button at the BOTTOM LEFT. ClearShell places buttons by construction
      order only - freshLayout does x += width + margin within a line, and
      nothing right-anchors or centres anything. Checked in the source: About
      sits where it sits because of the buttons declared before it, not because
      it is aligned to an edge. With a single button there is nothing before it,
      so x is 0 and it lands bottom left. No algorithm moves it, and none should
      be added to.

    THE CURSOR AT THE TOP, THE BUTTON AT THE BOTTOM, AND NOTHING BETWEEN THEM.
      Mikhail, correcting himself a minute later: the file is empty, so the
      cursor is at the TOP of the screen and the button is at the bottom - they
      do not meet at all on the first run.

      Which settles a question the documents had been carrying loosely. The
      console is FILE-ANCHORED, not bottom-anchored: line one is drawn at the
      top, the cursor sits at the end of the file, and the view follows the
      cursor. "Input on the bottom line, output scrolling upward" describes the
      STEADY state, once the file is longer than the screen - it is not the
      initial one, and a real Norton session behaves the same way, filling from
      the top before it ever scrolls. Nothing pins the input line to the bottom
      row.

      The cursor meets the panel only later, when the file has grown past the
      screen, and then it simply passes beneath it - the lower layer is a full
      text screen and the panel floats over it (UI_MODEL 1.1). That is the model
      working, not a collision.

    A NEARLY EMPTY SCREEN. One button and a file is the whole of 0.1.2. The
      lists, the second panel kind and the horizontal scroll all exist in the
      model and none of them are in this version.

F1 here corresponds to ClearShell's About, which calls mainHelp. Ours writes its
help text into the console rather than opening a dialog, because in 0.1.2 the
console IS the output surface and a dialog would be the first thing invented
rather than ported.
