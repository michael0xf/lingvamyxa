mixa_audio_mp3 -- clean L2 port notes
========================================

Ticket 20260913-232000/231500 Part 2, module 5 of 8.

Scope
-----
mixa_audio_mp3.lm1 is the MP3 composition: scan a directory through
mixa_audio_scan, then hand the snapshot to mixa_audio_launch. This is
the two-call glue ticket 20260912-065230 originally asked for and which
the STABLE pinned compiler could not translate at all in one unit --
it needs 22 imports (the mixa_dir chain + the full mixa_audio_panel
chain), two over stable65D5's 16-import table. mixa_mp3_open_dir scans
then hands over the snapshot only on success (a missing/refused
directory leaves whatever the panel was already showing exactly as it
was); mixa_mp3_hit is the real top-level button, re-scanning on every
press so the panel always reflects what is on disk now. Scanning asks
the vtable directly about extensions (mixa_audio_vt_is_audio_path), so
a press opens exactly one device -- the one that plays, not a scratch
instance.

GENUINE DEVIATION FROM EVERY OTHER MODULE THIS SESSION, stated plainly:
the real mixa_audio_mp3.lm1 cannot be translated by the pinned stable
compiler (65D5A5ED...) at all -- a hard compile failure ("import path
table full"), unrelated to the clean-L2 closed-type-allowlist barriers
this whole effort otherwise tracks. An earlier Claude session already
solved this once (ticket 20260912-084943), reusing Codex's own read-only
CANDIDATE compiler (SHA256 24A1B57B6C831C7B45630DF8CA61A7441376B4EB8EF9
46B1F08FC41957290B09, at build/codex/l1-import-capacity/build/
import_capacity/run_20260912_084844/l1trans.exe), which removes the
import cap. This port reuses that exact same precedent for the ORACLE
side only (headers, module translation, harness translation, and
compile) -- not a new exception invented for this ticket. stable65D5's
own hash is independently re-verified unchanged on every run, and both
hashes are pinned in the runner. The L2-side attempt (l2trans.exe,
itself always built from stable65D5) uses the STABLE compiler
throughout, matching every other module -- l2trans's own import
handling is unrelated to l1trans's fixed-size table and has never
needed the candidate; confirmed empirically (l2trans hits its own
closed-type barrier immediately, well before any import concern could
matter).

mixa_audio_mp3.lm1 and mixa_audio_mp3.h.lm1 are the parity oracle and
were NOT modified. The chain it predefs (mixa_audio_scan, mixa_audio_
launch, and everything they in turn predef) is a real, unmodified
dependency, embedded unchanged. The candidate compiler binary is
read-only and untouched (verified via git status).

Barrier confirmed
------------------
Attempting the complete .lm2 translation with a scratch build of
l2trans (built from stable65D5, as always) fails with:

    l2trans error: mixa_manager/mixa_audio_mp3.lm2:11:24: unknown foreign type

Line 11 is `fn: mixa_mp3_open_dir (@: MixaAudioLaunchCtx ctx; ...) int`
-- column 24 is the start of `@: MixaAudioLaunchCtx ctx`, a custom
struct in a plain (non-const) `@:` parameter position. CONFIRMS-MATCHES
the original, most common closed-type-allowlist barrier shape -- not a
new construct. This also confirms l2trans's own frontend hits its
closed-type barrier long before any import-count concern could ever
surface for this module, on the STABLE-built l2trans.exe.
