mixa_app_window L2 port (ticket 20260913-153000)
===================================================

Scope
-----
Clean-L2 port of mixa_app_window, the nested same-app missing-function
window: a dynamically-growing stack of framed regions (single-button
or two-button variant), each saving/restoring its own covered parent
cells verbatim, hit-testing the TOP window only. 11 public functions,
534-line real body.

    Real L1-vs-L2 harness (one source, compiled/linked twice), scenario

    window's own region, repeated open/close cycles (40x), no depth cap
    (9 stacked layers forcing a real grow past the initial capacity),
    sentinel-preserving negative preflight rejections (oversized

Barrier (current main)
-----------------------
l2trans error: mixa_manager\mixa_app_window.lm2:4:33: unknown foreign type

Line 4 is mixa_app_window_stack_init's own first custom-struct
parameter (`@: MixaAppWindowStack stack`) -- the module's own first
real function taking a custom struct type in a `@:` position, matching
the SAME closed-type-allowlist barrier family hit by every module
ported this segment. Confirmed identically across TWO separate runs of
the dedicated runner (byte-identical diagnostic, same line/column,
both runs).

Oracle-side results
--------------------
- ABI probe pair: byte-identical across all 16 fields (MixaAppWindow
  sizeof=88, MixaAppWindowStack sizeof=32).
- Parity harness (oracle side): 162/162 checks PASS, exit 0. Reproduced
  identically across two separate runs of the dedicated runner.
- Existing mixa_app_window_selftest.lm1 (run via run_app_window_
  selftest.ps1, unmodified, owned by another agent -- only executed,

- run_mixa.ps1 full regression sweep: all suites report ok, no new
  failures.

What would unblock the L2 side
--------------------------------
The same closed foreign-type allowlist gap already reported for every
prior module this segment: l2trans's current type checker refuses any
custom struct type reaching a `@:`/const: @(...) position. Landing the
core integration already in progress on origin/codex/core-integration
onto main would be expected to clear this barrier without further
changes to this module's own L2 header or .lm2 body.
