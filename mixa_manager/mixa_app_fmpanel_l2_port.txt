mixa_app_fmpanel L2 port (ticket 20260913-150500)
====================================================

Scope
-----
Clean-L2 port of mixa_app_fmpanel, the visible file-manager panel
(scrolling list, keyboard highlight, mouse wheel/drag scrollbar,
delete confirmation dialog, Copy Here integration). The largest
module ported in this migration segment: 959 lines / 20 functions in
the real mixa_app_fmpanel.lm1.

Files (new, this ticket)
-------------------------
- mixa_manager/mixa_app_fmpanel_l2.h.lm1
    L2 ABI header. Predefs the REAL mixa_file_manager.h.lm1 and
    mixa_selection_walk.h.lm1 directly (mirrors the real oracle's own
    two predef lines exactly), giving real MixaFm/MixaFmEntry/
    MixaSelWalkSink/etc. types and their prototypes for free. Predefs
    this segment's own previously-committed mixa_highlight_l2.h.lm1

    forward-declared here inside a prototype: block rather than as a
    bare top-level fn: in the .lm2 file, since a bodyless top-level
    declare with a custom-struct parameter here trips "incompatible
    entry signature" before reaching the real "unknown foreign type"
    barrier (see Barrier below).

Real dependency linking (worth recording)
------------------------------------------
mixa_file_manager.lm1 and mixa_selection_walk.lm1 both predef the
FULL bodies of mixa_dir_win32.lm1 and mixa_selection.lm1 directly (not
just their headers) -- building both as separate objects and linking
them together produces duplicate-symbol errors. The real oracle itself
never compiles mixa_file_manager.lm1/mixa_selection_walk.lm1 as their
own objects for exactly this reason; mixa_app_controller.lm1 instead
predefs mixa_fm_copy.lm1 (full body), which itself predefs the full
bodies of mixa_file_manager.lm1 and mixa_copy.lm1 (which predefs the
full body of mixa_selection_walk.lm1) -- l1trans dedupes a predef
chain within ONE translation unit, so this yields every mixa_fm_*/
mixa_dir_*/mixa_selection_*/mixa_selection_walk/mixa_copy_* symbol
exactly once. This runner mirrors that exact real pattern: builds
mixa_fm_copy.lm1 as the single real dependency object (plus mixa_
draw.lm1, mixa_highlight.lm1, and the real mixa_pump_*/mixa_backend_*
seam mixa_fm_copy.lm1 itself calls for copy-progress reporting --
mixa_pump.lm1, mixa_backend_table.lm1, mixa_backend_headless.lm1,
mixa_backend_ctors_headless.lm1, mixa_event_fifo.lm1 -- the identical
link list already used by the existing run_app_fmpanel_e2e_selftest.
ps1 for the real mixa_app_controller-driven E2E suite).

Barrier (current main)
-----------------------
l2trans error: mixa_manager\mixa_app_fmpanel.lm2:81:31: unknown foreign type

Line 81 is mixa_app_fmpanel_cell_at's own first custom-struct
parameter (`@: MixaTextRect rect`) -- the module's own first real
function taking a custom struct type in a `@:`/const: @(...) position,
matching the SAME closed-type-allowlist barrier family hit by every
module ported this segment. Confirmed identically across TWO separate
runs of the dedicated runner (byte-identical diagnostic, same line/
column, both runs).

A bodyless top-level mixa_draw_fill forward declare was hit FIRST when
placed directly in the .lm2 file (line 44:1, "incompatible entry
signature" -- the same bodyless-declare-plus-custom-struct-parameter
variant already known from mixa_console_window and mixa_cmdline_
dispatch this segment); moving it into the L2 header's own prototype:
block instead resolved that and surfaced the expected barrier above.

Oracle-side results
--------------------
- ABI probe pair: byte-identical across all 37 MixaAppFmPanel fields
  (real vs. L2 header), including the by-value-embedded focus field's
  own offset (2296) and total sizeof (2400).
- Parity harness (oracle side): 39/39 checks PASS, exit 0. Reproduced
  identically across two separate runs of the dedicated runner.
- run_mixa.ps1 full regression sweep: all suites report ok, no new
  failures.

What would unblock the L2 side
--------------------------------
The same closed foreign-type allowlist gap already reported for every
prior module this segment (mixa_pointer, mixa_file_win32, mixa_
process_marker, mixa_console_window, mixa_cmdline, mixa_cmdline_
dispatch, mixa_app_main, mixa_app_path, mixa_help): l2trans's current
type checker refuses any custom struct type reaching a `@:`/const:
@(...) position (or, per mixa_app_main/mixa_help this segment, certain
bare scalar/pointer entry signatures with no custom struct at all).
Landing the core integration already in progress on origin/codex/
core-integration onto main would be expected to clear this barrier
without further changes to this module's own L2 header or .lm2 body.
