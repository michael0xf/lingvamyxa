Why a real font backend could not be used for this harness
------------------------------------------------------------------
The existing headless backend (mixa_backend_headless.lm1's own mixa_
headless_glyph) unconditionally sets `out->missing = 1` for EVERY
codepoint -- it has no font at all, by design ("Headless has no font.
Report MISSING rather than inventing coverage"). Using it would make
the entire real glyph-coverage-blending code path in mixa_composite_
paint_glyph (the bulk of this module's own new logic beyond mixa_
composite.lm1) permanently unreachable, exactly the "ordinary glyph
composition" coverage this ticket explicitly asks for. A real win32
backend needs live GDI/font state this harness has no business
depending on. The minimal test-double vtable above drives the REAL,
unmodified dispatch chain (mixa_backend_glyph -> backend->vt->glyph)
with fully deterministic, hand-computable coverage data instead.
