--- DESIGN ---

D1. The UI lane is a full L3 Thread, launched by R0, running on the UI (Win32 message-pump) OS thread. It owns one
    arena, one FIFO inbox/outbox (19.28.R2.2 11438-11440), and no children of its own that get their own thread --
    the "lane" is not a parent that maps work onto other lanes; it is the leaf lane other Messages address when
    they want screen/window work done, exactly as 19.28.R2.2 11503-11506 already describes ("a Message to that
    lane's mailbox").

D2. What today calls mixa_backend_poll/mixa_pump_drain becomes the UI lane's own admission path: a Win32 event
    PeekMessageA drains today (F4) is translated into an admitted Message in the UI lane's own inbox, the same
    shape 19.28.R2.2 11438 already requires of every L3 Thread, not a second, parallel event queue next to it.
    mixa_pump.lm1's hand-rolled MixaEventFifo (F3) is what the lane's own inbox replaces; mixa_backend_win32.lm1's
    poll function (F4) keeps its exact non-blocking shape and becomes the lane's event SOURCE, not its scheduler --
    matching BACKEND_SEAM 7's own distinction ("The backend is an EVENT SOURCE feeding that loop's inbox").

D3. The lane's scheduler is not a pool, not a wait primitive, not own.lm2's shape. Per Mikhail's newest words: it
    is an L2 Structure, in the lane's own arena, holding the ordered list of Messages currently attached to this
    lane (a Message becomes "attached" the same way any child becomes attached to a parent's scheduler, 19.28.R2.2
    11452-11456: "ordinary private Structure data"). Event-driven: an admitted Message in the lane's own mailbox
    IS the event; running that Message's one turn IS the reaction. No condition variable, no semaphore, no thread
    pool, no blocking wait inside the scheduler's own code (SCOPE, Mikhail's newest words) -- this rules out
    anything shaped like own.lm2's route_mutex/work_ready/state_mutex/stopped_condition (this branch's own
    LOCK_REMOVAL_OWN_INVENTORY.txt) as a model for the UI lane, even though own.lm2's runtime is mixa_manager's
    only working precedent for a message-thread pool today.

D4. Its C is whatever the L2-to-L1 translator emits (SCOPE, "на Си пишет транслятор"). This design names the
    Structure's fields and the scheduler's algorithm at the L2 level; it does not name a C struct, a C function
    signature, or a C synchronization primitive. Where an equivalent of D2/D3 requires a call into the runtime
    (admission into the lane's own mailbox, taking the lane's own turn), the design names the L2-visible
    operation (the runtime's public send/recv/begin_turn/end_turn surface, or their eventual replacements per this
    branch's other stage work) and leaves the emitted C to the translator, not to this document.

D5. One attached Message's turn at a time, in the order of its own mailbox (the ticket's own wording, matching
    19.28.R2.2 11438-11440's "at most one turn at a time, consuming at most one admitted input per turn"). The
    lane's scheduler does not run a whole queue per invocation; each time the lane is given a chance to run (D6),
    it takes the next attached Message whose own mailbox has an admitted input, runs exactly that Message's one
    turn, and returns. No fairness policy beyond FIFO order is proposed (matching BACKEND_SEAM 7.1's existing rule,
    "one turn, no scheduler... turns taken in FIFO order").

D6. What makes the lane run at all is the OS's own event surface (Win32's message queue), not a primitive this
    design adds. The lane's own turn -- deciding which attached Message goes next (D5) and running it -- happens
    each time the UI thread is given control by the OS after an event arrives; this is the same non-blocking-poll
    shape mixa_backend_win32.lm1 already has (F4), read as the lane's own "am I given a chance to run" check, not
    as a scheduler-owned wait.

--- QUESTIONS (two answers each, neither decided here) ---

Q1. How does the UI lane's own thread idle between events (BACKEND_SEAM 7.2's still-open question, cited under
    F2, not closed by this design)?
    Answer A: the backend (Win32's message queue) exposes a waitable handle (MsgWaitForMultipleObjects) that the
      lane's own thread waits on directly -- no scheduler-level primitive, the OS's own blocking call, which is
      not a lock and not covered by "no locks in the project" (it synchronizes with the OS, not with another
      Message).
    Answer B: the scheduler owns the platform wait outright (BACKEND_SEAM 7.2's second named shape) -- the lane's
      thread blocks on GetMessage (a real block, not PeekMessage's drain) as its own turn boundary, and every
      other admission into its mailbox rides in through the same Win32 message queue (a PostMessage to the lane's
      own window), so the OS queue IS the lane's mailbox admission path and no separate cross-thread primitive is
      needed at all.
    Both keep "no locks but the message collection's own" (neither is a lock); they differ in whether the Win32
    message queue and the L3 Thread mailbox are the same queue (B) or two queues the lane's own turn bridges (A).

Q2. Does a non-UI Message's send to the UI lane (19.28.R2.2 11503-11506's "a Message to that lane's mailbox")
    cross an OS thread boundary through the lane's own mailbox admission alone, or does it need a Win32-specific
    wake (PostMessage to the lane's window) to make the UI thread notice before its next natural event?
    Answer A: admission alone is sufficient if Q1 is answered B (the same queue), since posting into the lane's
      own mailbox already rides the Win32 queue that wakes GetMessage.
    Answer B: if Q1 is answered A (two queues), admission into the lane's own L3-Thread mailbox needs its own
      explicit nudge (a PostMessage carrying no payload, purely a wake) so the lane's thread does not wait on
      MsgWaitForMultipleObjects past a sender's admission.
    This question is downstream of Q1, not independent of it.

Q3. Is the lane's scheduler Structure attached to the lane's own arena directly, or is it the lane Message's own
    "scheduler for its direct children" per 19.28.R2.2 11452-11456, even though the lane launches no threads for
    what it schedules (SCOPE, "запускает никаких потоков")?
    Answer A: it is exactly that clause's scheduler -- the attached Messages are the lane's "direct children" in
      the ownership sense (2.1(2) in this branch's LOCK_REMOVAL_SPEC_MAP.txt, "the parent owns the supervision
      cells about its direct children"), just never mapped onto their own OS thread.
    Answer B: "attached" is a different relation than "child" -- a Message can be attached to the UI lane for one
      piece of screen work while its real parent (whoever created it) is elsewhere in the tree, so the lane's
      scheduler is closer to 19.29.6's "scheduling policy/state for its own direct children" read loosely, or it
      needs its own named relation the spec does not yet have a word for.
    This question decides whether D3's Structure reuses the ownership rules already settled for parent/child
    (2.1(2)) or needs a new rule Mikhail has not stated.

--- ACCEPTANCE (red-first) ---

A test that attaches two Messages to a UI lane Structure (built directly, no runtime stepping involved) and
admits an input into each one's own mailbox in a chosen order, then calls the lane's own turn-taking function
once per expected turn and asserts: (1) the two Messages' turns run in the order their inputs were admitted, not
the order they were attached; (2) exactly one turn runs per call to the lane's own turn-taking function (D5); (3)
no OS thread, wait primitive, or the runtime's own stepping machinery (map_child, sched_step, or their
replacements) is invoked anywhere in the test -- the lane's own code walks its attached list and runs one turn,
nothing else. Red today because none of D1-D6 exists yet; the test is the same shape as this branch's other reds
(a counter/tripwire asserting the property, not yet green because the property is not yet implemented).
