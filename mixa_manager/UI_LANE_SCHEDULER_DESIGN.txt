F3. Today's stand-in for "one Message, one turn": mixa_manager/mixa_pump.lm1. mixa_pump_drain (23-61) calls

F5. No centralized "app main loop" or dedicated UI OS thread exists in mixa_manager today. The only non-test

F6. mixa_manager/SPEC_DIGEST.txt:28-30 (already in the tree, read 2026-09-11): "mixa_manager is a bundled

--- DESIGN ---

D1. The UI lane is a full L3 Thread, launched by R0, running on the UI (Win32 message-pump) OS thread. It owns one
    arena, one FIFO inbox/outbox (19.28.R2.2 11438-11440), and no children of its own that get their own thread --
    the "lane" is not a parent that maps work onto other lanes; it is the leaf lane other Messages address when
    they want screen/window work done, exactly as 19.28.R2.2 11503-11506 already describes ("a Message to that
    lane's mailbox").

D2. What today calls mixa_backend_poll/mixa_pump_drain becomes the UI lane's own admission path: a Win32 event
    PeekMessageA drains today (F4) is translated into an admitted Message in the UI lane's own inbox, the same
    shape 19.28.R2.2 11438 already requires of every L3 Thread, not a second, parallel event queue next to it.
    mixa_pump.lm1's hand-rolled MixaEventFifo (F3) is what the lane's own inbox replaces; mixa_backend_win32.lm1's
    poll function (F4) keeps its exact non-blocking shape and becomes the lane's event SOURCE, not its scheduler --
    matching BACKEND_SEAM 7's own distinction ("The backend is an EVENT SOURCE feeding that loop's inbox").

D3. The lane's scheduler is not a pool, not a wait primitive, not own.lm2's shape. It is an L2 Structure, in the
    lane's own arena, holding the ordered list of Messages currently attached to it -- ANSWERED, Q3 below:
    "attached" is not the parent/child launch relation; it is a Message the lane received and whose storage
    attached to the lane's own arena on receipt (19.29.7, 19.29.2), scheduled the way 19.28.R2.2's 2026-09-14
    clarification already names ("it allocates execution to the Messages that L3 Thread attached"). Event-driven:
    an admitted Message in the lane's own mailbox IS the event; running that Message's one turn IS the reaction.
    No condition variable, no semaphore, no thread pool, no blocking wait inside the scheduler's own code (SCOPE,
    Mikhail's newest words) -- this rules out anything shaped like own.lm2's route_mutex/work_ready/state_mutex/
    stopped_condition (this branch's own LOCK_REMOVAL_OWN_INVENTORY.txt) as a model for the UI lane, even though
    own.lm2's runtime is mixa_manager's only working precedent for a message-thread pool today.

D4. Its C is whatever the L2-to-L1 translator emits (SCOPE, "на Си пишет транслятор"). This design names the
    Structure's fields and the scheduler's algorithm at the L2 level; it does not name a C struct, a C function
    signature, or a C synchronization primitive. Where an equivalent of D2/D3 requires a call into the runtime
    (admission into the lane's own mailbox, taking the lane's own turn), the design names the L2-visible
    operation (the runtime's public send/recv/begin_turn/end_turn surface, or their eventual replacements per this
    branch's other stage work) and leaves the emitted C to the translator, not to this document.

D5. One attached Message's turn at a time, in the order of its own mailbox (the ticket's own wording, matching
    19.28.R2.2 11438-11440's "at most one turn at a time, consuming at most one admitted input per turn"). The
    lane's scheduler does not run a whole queue per invocation; each time the lane is given a chance to run (D6),
    it takes the next attached Message whose own mailbox has an admitted input, runs exactly that Message's one
    turn, and returns. No fairness policy beyond FIFO order is proposed (matching BACKEND_SEAM 7.1's existing rule,
    "one turn, no scheduler... turns taken in FIFO order").

D6. The lane's own thread wait is the platform's own thread wait on its own mailbox -- ANSWERED, Q1 below: not a
    second waitable handle alongside the OS queue, and not a bare non-blocking poll either. The scheduler owns the
    platform wait outright; admission into the lane's mailbox is delivered through that same platform queue (a
    thread message on Win32), so there is exactly one wait, on exactly one queue, and it is the lane's own
    mailbox wait that 19.28.R2.2's 2026-09-15 sentence names for every L3 Thread, not a UI-specific mechanism.

--- ANSWERED (6f's review against main, 2026-09-15; implementation within Mikhail's words, not new spec
sentences -- written so here, with the citations, per 6f's instruction) ---

Q3 (settled first, because it settles Q1/Q2). "Attached" is Mikhail's own word, not this design's: 19.28.R2.2's
2026-09-14 clarification (11483-11486, cited above) already says the scheduler "allocates execution to the
Messages that L3 Thread attached (a consumer schedules the Messages it attached)" -- a relation distinct from
parent/child launch. His 2026-09-15 sentences make the relation concrete: 19.29.2's "arenas attach on
consumption" and 19.29.7's "on receipt a Message that is not an L3 Thread attaches to the recipient's arena" (both
cited above). So: a Message the UI lane received and attached to its own arena is what the lane schedules; the
lane owns it as its arena's content, not as a supervised child under 2.1(2)'s parent/child ownership clause. D3
above states this directly rather than as an open question.

Q1 (thread idle). His 2026-09-15 sentence in 19.28.R2.2 (11570-11574, cited above), "synchronization is only
local, in the mailbox of each L3 Thread; there is none else in the project": a thread waits only for its own
mailbox. On the UI thread, the lane's wait is the platform's own thread wait, and the mailbox's wake is delivered
through that same platform queue (a thread message on Win32) -- the scheduler owns the platform wait outright;
there is no second waitable handle alongside it. D6 above states this directly.

Q2 (cross-lane wake) follows from Q1: admission into the lane's mailbox wakes the thread through the platform
queue itself, no separate Win32 primitive (no bare PostMessage-as-pure-wake alongside a payload-carrying one; the
admission IS the wake). D2/D6 above already describe one queue, one wait; this is that same fact restated as the
answer to what was Q2.

--- ACCEPTANCE (red-first) ---

A test that attaches two Messages to a UI lane Structure (built directly, no runtime stepping involved) and
admits an input into each one's own mailbox in a chosen order, then calls the lane's own turn-taking function
once per expected turn and asserts: (1) the two Messages' turns run in the order their inputs were admitted, not
the order they were attached; (2) exactly one turn runs per call to the lane's own turn-taking function (D5); (3)
no OS thread, wait primitive, or the runtime's own stepping machinery (map_child, sched_step, or their
replacements) is invoked anywhere in the test -- the lane's own code walks its attached list and runs one turn,
nothing else. Red today because none of D1-D6 exists yet; the test is the same shape as this branch's other reds
(a counter/tripwire asserting the property, not yet green because the property is not yet implemented).
