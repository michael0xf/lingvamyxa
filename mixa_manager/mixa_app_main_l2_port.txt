====================================================================

No ABI probe this ticket
----------------------------
mixa_app_main's own main() touches NO struct field of any kind.
MixaAppController is genuinely opaque (a plain C `typedef struct
MixaAppController MixaAppController;` with no body anywhere this file
can see), and MixaBackendVTable is only ever passed through as an
opaque pointer returned by mixa_backend_default_table(), never
dereferenced. There is no ABI-relevant layout this port introduces or
depends on. The "smallest honest header adapter" this ticket's own
instruction 2 asks for is, here, none at all: both mixa_app_controller.h
and mixa_backend.h are plain, hand-written C headers, included directly
in the .lm2 file exactly like the real oracle does -- no predef, no new
struct declaration, nothing to probe.

Line 27 is main() ITSELF: `fn: main (int: argc; @: @(char) argv) int`.
This is a GENUINELY NEW, more fundamental diagnostic location than any
of the preceding sixteen ports this segment reported: every prior
report was about a custom mixa_manager struct type (a MixaXxx pointer
parameter or return type) hitting the closed-type allowlist. This
module's own main() references NO custom struct anywhere in its own
signature -- its parameters are the plainest possible C entry shape,
`int argc, char **argv`, spelled in L1 as `int: argc; @: @(char) argv`.
The frontend currently rejects even this canonical, struct-free entry
signature. Per this ticket's own text (Codex has implemented core

cmdline.lm2's own gate as 61/61 on Codex's own integration branch) --
on CURRENT MAIN, however, stg/l1_baseline/l2src/l2trans.lm1's own
source hash is UNCHANGED from every prior report this entire segment

confirming that integration has not yet landed on main; this report is
therefore the diagnostic a fresh main-branch build actually produces
