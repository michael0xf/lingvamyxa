mixa_fm_remove L2 port (ticket 20260913-161000)
==================================================

Scope
-----
Clean-L2 port of mixa_fm_remove, the thin wire between mixa_remove_
selected_run and the file-manager view (no traversal/delete logic of
its own: hands fm\sel straight to the operation, then unconditionally
refreshes fm's current directory afterward, since remove -- unlike
copy -- can touch nodes across many different directories in one call
and has no single destination to compare against). 1 public function,
19-line real body.

No dedicated ABI probe pair this ticket
------------------------------------------
Unlike every prior module ported this segment, mixa_fm_remove declares
NO new struct of its own. Its one function takes only the already
real, unmodified MixaFm and MixaRemoveSink, reached via the REAL mixa_
file_manager.h.lm1/mixa_remove.h.lm1 predef'd DIRECTLY (identically on
both the real oracle and this L2 port -- see the header below), so
there is no second, L2-declared struct layout to diff against an ABI
probe would be comparing a type against itself. The parity that
matters here is entirely behavioral, covered by the harness.

Barrier (current main)
-----------------------
l2trans error: mixa_manager\mixa_fm_remove.lm2:4:30: unknown foreign type

Line 4 is mixa_fm_remove_selected's own first custom-struct parameter
(`@: MixaFm fm`) -- the module's own (and ONLY) real function taking a
custom struct type in a `@:` position, matching the SAME closed-type-
allowlist barrier family hit by every module ported this segment.
Confirmed identically across TWO separate runs of the dedicated runner
(byte-identical diagnostic, same line/column, both runs).

What would unblock the L2 side
--------------------------------
The same closed foreign-type allowlist gap already reported for every
prior module this segment: l2trans's current type checker refuses any
custom struct type reaching a `@:`/const: @(...) position. Landing the
core integration already in progress on origin/codex/core-integration
onto main would be expected to clear this barrier without further
changes to this module's own L2 header or .lm2 body.
