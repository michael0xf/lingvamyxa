6. Found today and not yet reported upstream

L1 cannot spell `const T *const *` as a return type: nested const in the paren
form yields `const const T **`. grok_bot worked around it with a 34-line
hand-written C file, mixa_backend_tables.c, holding the registry array, and
documented the reason at the top of it.

Probed on 65D5A5ED rather than taken on report. Four spellings, none reaching
`const VT *const *`, and TWO of them compile while giving a type the source does
not say:

    const: @(const: @(VT))  -> const const VT **   warns, compiles, inner const
                                                   collapses; effective type is
                                                   const VT **
    @@: const VT            -> const **            TYPE NAME DROPPED, gcc falls
                                                   back to implicit int
    const: @@(VT)           -> const VT **         valid C, wrong type
    const: @(VT)            -> const VT *          single pointer

This is L1_spec OPEN POINT 10.13, "const pointer spelling order", which was
already listed as open - so it is a decision waiting rather than a defect. The
two silent-wrong-code cases are worth a diagnostic whichever way 10.13 goes.

PRIORITY: URGENT, by Mikhail - "L1 has to be finished, in priority." My first
message called it not urgent; that was my judgement and he overruled it. I had
priced it as one hand-written C file in one application, which is what it is for
us today - but the shape that cannot be spelled is A READ-ONLY TABLE OF READ-ONLY
THINGS, which is what every dispatch table, registry and lookup array wants to
be, and each one that cannot say it becomes either a mutable global or another
hand-written C source.

Three messages to Codex, 2026-09-10, work_chat/claude/outbox/:
    032534  the case, the four return-position spellings, the workaround
    032706  priority correction, at Mikhail's instruction
    032804  the full matrix across parameter / local / return

The matrix adds a sharper statement of 10.13: NO position expresses a
const-qualified POINTER. Every const: spelling reaches the referent, none
reaches the slot - so L1 has no way to say "this pointer will not be rebound",
which L1_spec 9.1.2 says is exactly what const is for. And three spellings
someone would reach for BECAUSE no correct one exists emit garbage that
compiles: const const VT **, const ** (implicit int), and const * VT (name and
type transposed). None is refused.

No rebuild, gate run or promotion asked for. Not verified against l1src,
deliberately: the observation was handed over rather than a diagnosis.

RESOLVED for the application, 03:34, by a bridge Codex proposed and I verified.
Name the inner pointer type in the ABI header and qualify the ALIAS:

    typedef const MixaBackendVTable *MixaBackendTableRef;
    fn: mixa_backend_tables (@: size_t count) const: @(MixaBackendTableRef)

generates `const MixaBackendTableRef *`, which by C typedef qualification IS
`const MixaBackendVTable *const *` - qualifying a typedef'd pointer type
qualifies the POINTER. Ran on 65D5A5ED: compatible with the exact prototype
under -Werror, writes to the slot AND to the pointee both rejected, reads clean.

So the hand-written C registry goes away and the registry becomes ordinary L1;
only the typedef stays in the already-permitted ABI header. Ticketed to
grok_bot, to land before his Task 25 report.

The language gap is NOT closed by this and must not be recorded as closed. The
bridge NAMES a type to get a qualifier onto a pointer; L1 still cannot SAY
"const pointer", and every future case needs another alias in a handwritten
header. Codex has passed both reports to Grok for a priority bounded L1 source
review. Full matrix with complete input files sent to both at 033409.

Still open from the same probing:
    a module-level `@: T x` emits without STATIC and indented, so a registry
      slot leaks a name out of its unit. Asked grok_bot whether L1 can spell
      static at all; if not, that is a separate report.
    the three silent-output spellings in section B of the matrix - const const
      VT **, const ** on implicit int, and const * VT with name and type
      transposed. Codex agrees these are a diagnostic issue independent of
      10.13. Not ours to fix.

6.1. Every L1 gap we know of - all reported, priority by the owner

Mikhail, 2026-09-10: pass all the language holes to Codex to be fixed in
priority. Sent as one list at 033812 to Codex and Grok, with the reproducible
fixtures at mixa_manager/tests/l1_gaps.

    A  no spelling for a const-qualified POINTER. 10.13. Bridged by naming a
       type in a handwritten header; every future case needs another alias.
    B  three spellings emitted compiling garbage instead of diagnosing:
       const const VT **, const ** on implicit int, const * VT transposed.
       FIXED by Grok, root l1src commit 5f03a70, candidate binary
       build/l1trans/iso_033430/l1trans.exe (D328DD1D). NOT promoted - STG
       stays 65D5A5ED.

       Verified here independently rather than taken on report: all three now
       diagnose, the five valid spellings generate BYTE-IDENTICAL C on both
       translators, and - the one that mattered - the typedef bridge survives.
       His rule rejects const: wrapping a visible const: form, and a foreign
       typedef name is not one, so const: @(VTRef) still yields
       const VTRef * and still matches const VT *const * under -Werror. Asked
       him to confirm that is deliberate: if it is incidental it could regress
       the day the translator learns more about foreign headers, and the
       registry migration depends on it.
    C  NO INTERNAL LINKAGE. `static:` is refused, "unsupported L1 form", and
       every module-level object is a global. So the lazily built singleton -
       the only way to have a table, given D - is a name in the program's
       namespace, and two units naming their cache alike collide at link time.
       No workaround FOUND inside L1 - stated that way deliberately. Only
       `static:` and `external:` were probed; `prototype:` and header units
       were not.
    D  no struct-typed LOCAL, so anything value-shaped becomes calloc + free.
    E  fnptr: exists only in header units, which are not promoted to STG, so
       the vtable's types live in a handwritten C header.

`external:` is NOT L1's static - checked, not assumed. It is a grouping receiver
for PROTOTYPES: `external: fn: h (int: a) int` emits `int h(int a);` and
`external: @: int g` is refused with "external without fn". Declare-elsewhere,
the opposite direction from confine-to-here.

Four of the five end the same way: something cannot be said in L1, so it moves
into a handwritten C file. Individually small; together they are why
mixa_manager now contains hand-written C SOURCE and not only headers.
