How to read the table
----------------------
Columns: module | commit (introduced the .lm2) | .lm1->.lm2 diff lines
| known-barrier bucket | oracle checks | current parity verdict.

Verdict values: PASS (full L2 translation + build + run, byte-
identical trace to the oracle — a real completed port), EXPECTED_CORE_
BARRIER (translation stops at an already-cataloged compiler gap, not a
pass), UNEXPECTED_FAILURE (stops at something else — sometimes a real,
newly-surfaced compiler gap; sometimes a harness/test bug on this
side; not yet triaged for every row below), PARITY_FAILURE (both
sides built and ran but traces differ — none currently).

Every verdict below was run fresh on 2026-09-14 against the current
pinned compiler (722AC86E..., post Stage A bare-name resolution),
not carried over from an older snapshot. The barrier-bucket column is
the LAST diagnostic actually recorded for that module in its own port
note or in this session's own work; for modules whose first stop has
since moved (the ulong-domain and Stage-A work landing this week), the
verdict column is current but the bucket text may describe an earlier
stop — flagged inline with "(moved)" wherever this session directly
observed the shift today. Treat a bucket without that flag as
"probably still accurate, not re-confirmed against today's exact
line:col."

Parameterized runner (run_mixa_l2_parity.ps1 -Module <name>)
--------------------------------------------------------------
35 of the modules above are driven by the single parameterized runner
(mixa_manager/run_mixa_l2_parity.ps1 + l2_parity_module_table.ps1)
instead of their own run_mixa_<module>_l2_parity.ps1 script: app_path,
audio_button, audio, audio_launch, audio_panel, audio_scan,
audio_win32, calculator_syntax, dir_win32, file_win32, fileio_win32,
pointer, process_marker, process_win32, share, text_rect, event_fifo,
cmdline, pump, audio_mp3, fm_copy, fm_remove, buttons, help,
app_window, backend_ctors_headless, backend_headless, backend_table,
copy, remove, share_button, share_win32, remove_confirm,
selection_walk, cmdline_dispatch.

Kept as their own script permanently, by explicit decision (cut
complexity rather than model every bespoke shape in the table):
app_main (build-only, no second execution, no trace diff -- different
control flow, not just different data), app_controller (array-shaped
link-argument list instead of every other runner's inline string),
app_panel (real .lnk-fixture WScript.Shell COM setup + a test-owned
oracle-source override -- genuinely bespoke, not worth the schema
cost), backend_win32 (no runtime-object-link block, no L1Root
push-location for headers, different -I flags -- not a copy-paste-
with-a-missing-line case).

Not yet migrated (batch 4, waiting on d6's ulong translator commit so
it lands as one pass with the seven ulong re-runs, per e2): button_
dispatch, composite, composite_glyphs, console_window, draw, highlight
(inline non-Build-RealDep dependency-build patterns, not yet verified
against the parameterized engine's assumptions), selection (needs a
new dependency shape -- a plain-C file, tests/mixa_selection_alloc_
fault.c, compiled directly without an l1trans translation step first,
which the engine doesn't support yet), tiles (same inline-pattern
question as button_dispatch/draw/etc).

Known real compiler gaps (not app-side bugs, do not attempt to work
around; owned by lingvamyxa-d6)
--------------------------------------------------------------
- wchar_t anywhere in a foreign-type position (4 syntactic shapes
  confirmed this session: out-parameter, const-pointer-shaped return,
  double-indirection out-parameter, plain non-const return).
- ulong as an own-array element type (file_win32, process_marker
  directly confirmed moving to this exact stop today; the translator
  half of the fix is in d6's gates now).
- process_win32's own next stop (46:64, "unknown foreign type") is
  Stage B, a separate, later piece of work.
- remove_confirm: "unknown field path root" on a declared-typed
  global's own field access after a cast-assignment inside a nested
  if -- confirmed via a direct, isolated repro this session (a plain
  field write through a declared foreign-pointer global already
  fails, independent of the cast).
- file_manager (as ported here): "unknown method" on a call through a
  function-pointer-typed local variable -- confirmed via a direct,
  isolated repro this session.

Recorded debt
--------------
- mixa_console_window.c is hand-written C living inside mixa_manager.
  CODING_RULES.txt section 0 forbids this -- application logic belongs
  in L1 (moving to L2), never hand-written C, with narrow platform-ABI
  adapters as the only identified exception and this is not one.
  mixa_console_read_window's own body needs porting to mixa_manager/
  mixa_console_window.lm1 itself. Not fixed here; flagged for whoever
  picks up console_window's own batch-4 work, since its own runner
  already predefs/compiles this file and would need to stop doing so
  once the port lands. Owner: mixa_manager (this chat).

Toolchain
----------

l1trans.exe and build/l1trans/gen3/l1trans.exe, both read from a
single source of truth: stg/l1_baseline/l2src/L1_PIN.txt (one line,
the pin's SHA256, nothing else -- a promotion is now a one-line change
to that file, not the historical 73 separate literal-hash edits).
Current pin (as of this table): 722AC86E256D28EB462EE244D92B5E7188792
EC0A0F5B300957622672EBAB466. mixa_manager/lib_l2_runtime_support.ps1
exposes Get-L1Pin/Assert-PinnedL1Translator for any script that needs
to check it.
