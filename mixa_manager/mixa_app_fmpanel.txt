mixa_app_fmpanel -- first visible file-manager panel in the production controller
================================================================================
(ticket 20260913-032000, PORT_OF_CLEARSHELL.txt section 1.1 priority)

What this closes
-----------------
Makes the accepted production controller (mixa_app_controller.lm1, the
SAME code the real Win32 entrypoint runs) visibly render and operate the
first real file-manager panel: the current directory path, its entry
listing, and a Delete action reaching the already-accepted mixa_fm_
remove_selected operation behind a real, drawn, same-app Cancel/OK
confirmation. This is the production integration boundary the prior two
tickets' own reusable modules (mixa_remove/mixa_fm_remove, ticket
20260913-021200; mixa_remove_confirm, ticket 20260913-023700) were built
toward -- and, as it turned out, could not be wired in AS WRITTEN, for
two real, measured reasons recorded below.

Two genuine architectural blockers found, and how each was resolved
-------------------------------------------------------------------------

1. A real MixaButton naming collision. mixa_backend.h declares `typedef
   enum MixaButton {MIXA_BUTTON_LEFT, MIDDLE, RIGHT} MixaButton;` (mouse
   buttons); mixa_buttons.h declares `typedef struct MixaButton {char
   *label; ...} MixaButton;` (one UI button). Both are real, already-
   accepted, unrelated headers -- but mixa_app_controller.lm1's own
   translation unit needs mixa_backend.h (for MixaEvent), and reusing
   mixa_app_window.h.lm1 (the accepted nested-window module, which
   itself needs mixa_buttons.h) would need BOTH in the same translation
   unit. Confirmed as a real, reproducible compile error by actually
   trying the combination (via a probe extending mixa_console_window.lm1
   with a buttons predef, immediately reverted once this surfaced) --
   not assumed from reading the headers alone.

   Resolution: every "button" mixa_app_fmpanel draws is a raw drawn cell
   region with a raw bounds-check hit-test -- the exact same style
   mixa_help's own F1 button and mixa_fm_copy_here_hit's own rect check
   already establish, for the identical reason category (this codebase
   already has TWO precedents for "avoid the button-panel machinery
   inside the production controller's own translation unit," both
   predating this ticket). mixa_app_window.h.lm1/.lm1 and mixa_remove_
   confirm.h.lm1/.lm1 remain exactly as accepted -- untouched, still
   fully tested by their own selftests -- for callers that do not share
   mixa_app_controller.lm1's own mixa_backend.h dependency.

2. A real duplicate-symbol risk. mixa_app_controller.lm1 already predefs
   mixa_fm_copy.lm1 (real), which itself real-compiles mixa_file_
   manager.lm1/mixa_selection.lm1/mixa_selection_walk.lm1/mixa_dir_
   win32.lm1 into mixa_app_controller.o. Predef-ing mixa_remove.h.lm1 or
   mixa_fm_remove.h.lm1 (even header-only) into mixa_app_controller.lm1
   itself overflows its own already-documented-at-ceiling import table
   (confirmed directly: a probe copy with those two predef lines added
   produced "import path table full", not inferred). And even from a
   FRESH sibling file with its own budget, predef-ing mixa_remove.lm1/
   mixa_fm_remove.lm1's REAL implementations would double-define mixa_
   fm_.../mixa_selection_.../mixa_dir_... symbols against mixa_app_
   controller.o's own already-real copies of the exact same functions
   at final link -- the identical class of hazard mixa_console_window.
   lm1's own header comment already documents for draw/text_rect/
   composite/tiles, just for a different symbol family.

   Resolution: mixa_app_fmpanel.lm1 predefs ONLY the relevant HEADERS
   (mixa_file_manager.h.lm1, mixa_selection_walk.h.lm1) -- giving it
   types and prototypes, compiling NO real mixa_fm_.../mixa_selection_
   .../mixa_dir_... symbols of its own -- and reimplements the small
   (~40-line) delete walk-glue (on_dir_enter/on_file/on_dir_done,
   mirroring mixa_remove.lm1's own logic exactly) directly against
   symbols that are ALREADY real and ALREADY linked via mixa_app_
   controller.o's own existing mixa_fm_copy.lm1 chain (mixa_selection_
   walk, mixa_dir_remove, mixa_selection_deselect). A deliberate, small,
   disclosed local duplication to escape a confirmed toolchain
   constraint -- not a divergent reimplementation of the operation's own
   semantics, and not touching mixa_remove.lm1/mixa_fm_remove.lm1
   themselves at all (both remain exactly as accepted, still used
   wherever the button-panel/no-mixa_backend.h constraint does not
   apply -- mixa_remove_confirm's own selftest, for instance).

New module: mixa_app_fmpanel.h / _impl.h / .lm1
----------------------------------------------------
Same opaque-handle split mixa_app_controller.h/_impl.h already
establish. mixa_app_fmpanel_open/_close/_render/_hit/_confirm_is_open --
see mixa_app_fmpanel.h's own comment for the full contract. Rendering:
row 0 is the current directory path (mixa_fm_cur_dir); rows 1 through
however many the given geometry offers are entry names (mixa_fm_name),
prefixed with a marker when mixa_fm_is_selected -- clipped to real
screen rows, never capping fm's own entry count (no arbitrary entry/path
limit anywhere: fm's own snapshot and MixaSelection remain exactly the
already-accepted, uncapped, growable structures). The action row (Delete,
Copy Here) draws only once at least one entry is selected.

Confirmation is a small, self-contained save/restore (the same MixaCell-
snapshot-and-restore mechanic mixa_app_window.lm1 already established,
reimplemented here buttons-free for the same reason as the walk-glue
above) with two raw hit regions (Cancel, OK). OK invokes the walk-glue
exactly once, refreshes fm afterward (mixa_fm_refresh, matching mixa_fm_
remove_selected's own unconditional-refresh discipline), and -- only on
an observed failure -- leaves the confirmation's own dismissal followed
by a plain informational relabel of the SAME region showing the exact
failing path and status, dismissed the same way. Cancel never calls the
walk-glue at all, so it cannot touch the filesystem or selection by
construction.

Copy Here's own label is drawn but its click is NOT invoked from inside
this module: mixa_app_fmpanel_hit returns a distinct value (2) for it,
and mixa_app_controller.lm1's own step() -- which already owns the real
MixaFmCopyHereCtx via c\loop\ctx -- calls mixa_fm_copy_here_action
itself on seeing that value. This keeps mixa_app_fmpanel free of any
dependency on MixaFmCopyHereCtx and reuses the EXACT SAME accepted
action its keyboard (Ctrl+V) path already invokes -- one function, two
real ways to reach it, never a second implementation.

Wiring into mixa_app_controller.lm1
----------------------------------------
Purely additive: one new `include:` (mixa_app_fmpanel.h, a plain header,
zero import-table cost, the same "include:, not predef:" discipline
mixa_app_path.h/mixa_help.h/mixa_cmdline_dispatch.h already establish),
one new opaque field on MixaAppController (`struct MixaAppFmPanel
*fmpanel;`), one open() call (geometry: list rows 0-21, action row 22 --
one row above F1 Help's own row 23, never overlapping it), one render()
call at each of the three existing mixa_console_window_present call
sites (the exact cadence pending-line refresh already uses), one close()
call, and the mouse-hit dispatch checked FIRST in step()'s own existing
mouse-handling block (before mixa_help_hit) -- while fmpanel's own
confirmation is open, every click belongs to it, mirroring mixa_app_
window's own already-established "top nested surface only" contract, so
F1 Help correctly never reacts to a click meant for the confirmation
underneath it. Existing console/F1/window-visibility behavior is
untouched: no existing function's own body changed, only new calls
added alongside them.

mixa_app_controller.h also gained one small, borrowed, read-only
getter -- mixa_app_controller_fm -- for exactly the same reason its
existing introspection functions (text_rect/upper_rect/cwd/etc.) exist:
so a real production-controller test can select real entries through the
real mixa_fm_select API before driving a synthetic click, without a
second, test-only selection model.

A test-authoring mistake found and fixed along the way (not a product
bug)
-------------------------------------------------------------------------
The first draft's click coordinates assumed MixaEvent's mouse row/col
were already half-cell values (per mixa_backend.h's own documented "text
cell = half >> 1" contract) and computed them directly. Empirically none
of the resulting clicks landed anywhere near their intended targets. A
temporary debug trace (printing the RAW event row/col mixa_app_
controller.lm1's own step() actually received, alongside what fmpanel_
hit was called with) showed the headless backend does its own pixel-to-
half-cell conversion first (dividing by cell_dim/2, exactly mirroring
mixa_win32_poll's own real `cx*2/cell_width` formula for actual Win32
mouse messages) -- so the test needed to push PIXEL coordinates, not
pre-converted half-cell ones. Fixed by computing pixel_row = desired_
half_row * (text_cell_height/2), pixel_col = desired_half_col *
(text_cell_width/2), verified against the exact build's own real cell
metrics (8x16) rather than assumed. All temporary debug printf calls (in
both mixa_app_controller.lm1 and mixa_app_fmpanel.lm1) were removed
before the final passing run recorded above.

Part II -- production file-manager row selection by click (ticket 20260913-040213)

visible entry row now selects or deselects that REAL entry through the
existing mixa_fm_select/MixaSelection API -- no second, panel-only
selection model anywhere.

mixa_app_fmpanel_hit gained one new region check, ordered after the
confirm-open and action-row checks (so Cancel/OK and Delete/Copy Here
keep first claim on their own rows, unchanged from Part I) and before
the final miss return: a click landing in the list area's own entry
rows (list_row+1 .. list_row+list_rows-1, matching render()'s own row

never cached in the first place -- every hit recomputes `idx` from
whatever mixa_fm_count/is_selected report AT THE MOMENT of the click,
which is always the CURRENT post-refresh snapshot once mixa_fm_remove_
selected's own unconditional refresh (already established in Part I)
has run. The same real mixa_fm_select call already used by every other
selection path (a future click-to-select ticket, this test) means this
required no change to mixa_fm_remove_selected/mixa_remove_selected_run
themselves.

A real, previously-undiscovered production bug found and fixed
-------------------------------------------------------------------
This ticket's own E2E test's first Ctrl+V invocation displayed "Copy:
FAIL 101" (MIXA_COPY_ERR_ARG) where a real "copy onto own parent"
conflict (MIXA_COPY_ERR_EXISTS, 104) was expected. Tracing the real call
chain found mixa_fm_copy_selection's own existing null-pointer guard
(`if: fm=0 || dest_root_utf8=0 || sink=0 -> return: MIXA_COPY_ERR_ARG`)
rejecting the call outright, because mixa_app_controller.lm1's own
mixa_app_loop_open call had ALWAYS passed a literal `0` (a true null
pointer, not a zeroed struct) for the sink parameter -- since the feature
was first wired, in every prior ticket this session that exercised Copy
Here. Copy Here has never performed a real copy in production before
this fix; every invocation short-circuited with ERR_ARG before ever
reaching mixa_copy_run.

Fixed by adding `struct MixaCopySink *copy_sink;` to MixaAppController's
own concrete struct (mixa_app_controller_impl.h), allocating it via
c.calloc(1U, c.sizeof(c.MixaCopySink)) alongside the controller's other
Stage-2 allocations, passing c\copy_sink (not `0`) to mixa_app_loop_open,
and freeing it in mixa_app_controller_close. A zeroed MixaCopySink still
has every callback field null, so mixa_copy_invoke's own already-
established "f=0 -> propagate status or GO" default behavior is entirely
unchanged -- only the OUTER pointer is no longer null, satisfying the
guard without altering the filesystem/copy semantic contract this
ticket's own scope explicitly forbade touching. This is the single most
significant finding of this ticket: a real end-to-end test caught a
production defect no unit test could have (mixa_fm_copy_selection's own
existing unit coverage necessarily passes a real sink, since exercising
the ERR_ARG branch on purpose is exactly what a unit test for that guard
would do -- only driving the actual production wiring end to end surfaces
that the wiring itself never passed one).

Data-seam limitation disclosed, not worked around
-------------------------------------------------------
The ticket asked, if the existing status lacks enough information to
show the exact failed path, to report that exact limitation rather than
invent one. MixaFmCopyHereCtx\last_status is a bare numeric status code
with no accompanying path field at all (unlike MixaRemoveConfirmCtx,
which does track failing_path from its own walk-glue). The copy-result
display therefore shows only the real STATUS ("Copy: FAIL 104"), never a
specific failing path -- disclosed here rather than crossing into a new
file API or inventing a parallel path-tracking mechanism, both of which
the ticket explicitly forbade.

Part IV -- production file-manager panel vertical scrolling (ticket 20260913-044900)
============================================================================================
Closes the vertical-scrolling gap Parts I/II both disclosed: UI_MODEL 1/
5.7.2's own "a single list -- vertically, in its own bounds and its own
scrollbar" and 5.7.1's own asymmetric view/highlight rule, PORT_OF_
CLEARSHELL 2.5's "each list scrolls inside its own bounds and keeps its
own position, with its own vertical scrollbar."

What was added
-----------------
MixaAppFmPanel gained two pieces of real state: view_top (the index of
the first entry currently drawn) and highlight_idx (the keyboard-moved
CURRENT entry, -1 meaning none established yet -- mouse click-to-select
from Part II is entirely unaffected and stays selection-based, never
highlight-based; the two are deliberately independent, exactly FAR/
Norton's own "marked" vs "cursor" distinction).

The list's own rightmost column (list_col+list_cols-1) is now a real,
drawn vertical scrollbar, reserved unconditionally so the entry-column
width and the scrollbar's own hit-test region never shift depending on
the current entry count. render() draws a dim track over the visible
rows and a single brighter thumb cell at a position proportional to
view_top/max_scroll (an integer computation, no scaling, per Mixa_
Manager_RENDERING_DOCTRINE.txt). hit() maps a click on that column to a
proportional view_top, touching no selection and no highlight -- UI_
MODEL 5.7.1's own "the view may leave the highlight" mouse-only rule.

Keyboard Up/Down (mixa_app_fmpanel_key, called from mixa_app_controller.
lm1's step() before its existing cmdline key chain -- neither key had any
prior meaning there, so nothing is stolen from the console) move highlight_
idx by one, establishing it at 0 on the very first Up or Down if none
exists yet, clamped to fm's own real [0, count-1] range -- no fixed cap
invented. Every highlight move re-derives whether the view must follow it
("any HIGHLIGHT movement brings the view back," 5.7.1) using the same
"first/last visible row" arithmetic render() itself uses.

A directory CHANGE (detected by comparing mixa_fm_cur_dir's own string
against what the panel last saw) resets both view_top and highlight_idx
to the top of the NEW listing -- an old scroll position from an unrelated
directory would point at meaningless entries once the listing is entirely
different. A refresh WITHIN the same directory (e.g. after Delete) only
CLAMPS view_top to the new, possibly smaller max_scroll and clamps
highlight_idx into the new count -- it does not reset either, since the
identity of what is being looked at has not changed, only its contents.
Both rules live in one new helper, mixa_app_fmpanel_clamp_view, called at
the top of every render() (and, redundantly but harmlessly, at the top of
mixa_app_fmpanel_key -- see the real bug below for why that redundancy is
NOT hiding the actual view-following logic).

A real bug found and fixed while writing this ticket's own E2E test
-------------------------------------------------------------------------
The scrollbar's own click-to-scroll worked in isolation but a click ALSO
disappeared the instant the very next frame rendered -- the scroll always
snapped straight back to wherever the (still-established, from an earlier
Up/Down) keyboard highlight was. The first version of mixa_app_fmpanel_
clamp_view had copied the SAME "bring the view back to the highlight"
logic that belongs in mixa_app_fmpanel_key into clamp_view itself -- and
clamp_view runs unconditionally on EVERY render(), not only after an
actual highlight move. So a mouse-driven scroll would take effect for
exactly one hit(), then get overwritten by the very next render()'s own
clamp_view call before the test (or a real user) ever saw it settle.
UI_MODEL 5.7.1 is explicit that this must NOT happen: "the VIEW may leave
the highlight" via a mouse move, and only a highlight MOVE -- not a
render -- brings the view back. Fixed by removing the view-follows-
highlight branch from clamp_view entirely, leaving it only in mixa_app_
fmpanel_key (the one place a highlight actually just moved); clamp_view
itself only clamps view_top to the current max_scroll and highlight_idx
to the current count, both real invariants that must hold on every
render regardless of how the count changed. Caught only because the E2E
test drove a REAL scrollbar click through a REAL subsequent render
tick, not a single isolated hit() call -- the same "a genuine end-to-end
proof catches what a narrower check cannot" pattern this session has hit
repeatedly (the sink=0 Copy Here bug in Part III, the READ/APPEND
console-handle bug from ticket 010249).

Part V -- real mouse-wheel event and file-panel scrolling (ticket 20260913-053000)
==========================================================================================
Closes the "No mouse wheel" gap Part IV named: mixa_backend.h's own
MixaEvent contract gains a real wheel representation, populated from the
real Win32 window input path, routed through the production controller
to mixa_app_fmpanel -- not a scrollbar-click stand-in this time, an

Backend-seam extension (mixa_backend.h, hand-written C header)
--------------------------------------------------------------------
A new MixaEventKind, MIXA_EVENT_MOUSE_WHEEL, distinct from MIXA_EVENT_
MOUSE rather than a flag on it: a wheel event carries a DIRECTION/
MAGNITUDE instead of a button state, and a distinct kind means every
existing MIXA_EVENT_MOUSE consumer (every button/click hit-test in this
codebase) simply never sees it, rather than having to newly ignore a
zero button mask on a mouse-shaped event it did not expect. MixaEvent
gains one field, `int wheel_delta` -- already-normalized NOTCH count
(Win32's own WM_MOUSEWHEEL delta pre-divided by WHEEL_DELTA=120, so no
consumer needs that constant), positive away from the user ("scroll
up"), negative toward ("scroll down") -- Win32's own sign convention,
kept rather than inverted so a future port does not have to guess which
way is which. row/col are reused unchanged (same HALF-cell contract
mouse events already use); buttons is 0 for a wheel event, not a new
"no buttons" sentinel.

Win32 backend (mixa_backend_win32.lm1)
------------------------------------------
mixa_win32_poll gained one new branch for WM_MOUSEWHEEL (522), alongside
the existing WM_LBUTTONDOWN/UP/RBUTTONDOWN/UP/MBUTTONDOWN/UP/MOUSEMOVE
branch it already had. The one real Win32 quirk this message has that no
other handled message in this file does: its lParam is SCREEN
coordinates, not client-relative like every other mouse message here --
so a single ScreenToClient call converts it before the SAME pixel ->
half-cell division every other mouse branch already performs. wParam's
high word is the signed delta (divided by 120 here, once, so mixa_app_
fmpanel_wheel and any future consumer never has to); the low word carries
the identical MK_* flag bits mixa_win32_mouse_mods already reads, so the
full wParam is passed through unmodified exactly like the click branch
already does. A delta that divides to exactly 0 (a sub-notch smooth-wheel
report, rarer but real) is treated as no event at all -- the poll loop
simply continues to the next message rather than delivering a wheel
event with nothing to do.

Headless backend (mixa_backend_headless.lm1)
-------------------------------------------------
mixa_headless_push_event's own pixel -> half-cell conversion, previously
gated on `kind = MIXA_EVENT_MOUSE` only, now also covers MIXA_EVENT_
MOUSE_WHEEL -- the identical conversion, extended to the new kind rather
than duplicated, so a pushed wheel event's row/col behave exactly like a
pushed mouse event's for any test driving the headless backend.

mixa_app_fmpanel (new function: mixa_app_fmpanel_wheel)
-------------------------------------------------------------
Takes the already-converted upper-cell (cell_row, cell_col) and a signed
notch count. UI_MODEL 5.7.1's own asymmetric rule, already applied
identically to the scrollbar-track click in Part IV: moves the view
ALONE, touching neither the keyboard highlight nor any selection. Anywhere
over this panel's own list area (the path row, every entry row, and the
scrollbar column alike -- an ordinary file manager scrolls on a wheel
turn no matter which of those the pointer happens to sit over) consumes
the event and moves view_top by notches (clamped to the current real
[0, count-visible] range, one row of movement per notch -- a deliberate,
disclosed simplification; no OS-configurable "lines per notch" setting
is read or invented). The action row and anything outside the panel's
own bounds is a genuine miss (returns 0), so the caller's other handlers
still see it.

----------------------------------------

Part VI -- real vertical scrollbar-thumb dragging (ticket 20260913-060000)
==================================================================================
Closes the "No scrollbar thumb DRAG" gap Part V named, building on main
commits 7b4a5676 (vertical scrolling) and 81061041 (mouse wheel).

The thumb becomes proportionally sized
------------------------------------------
Part IV's own thumb was a fixed 1 row tall -- a disclosed simplification
that had no way to express "grabbed away from its own first row," since
there was only ever one row to grab. This ticket needed that concept for
real, so the thumb's own height is now the classic scrollbar ratio:
thumb_h = visible^2 / count (integer division), clamped to [1, visible].
A new shared helper, mixa_app_fmpanel_scroll_geom, computes visible/
count/max_scroll/thumb_h/track_room (track_room = visible - thumb_h, how
many track rows the thumb has left to move within) once, used by
render(), the track/thumb hit-test, and the drag-continue path alike --
so the three can never compute a different thumb position from the same
state. mixa_app_fmpanel_thumb_off(view_top, max_scroll, track_room) maps
the CURRENT view_top onto that room proportionally; it is the exact
formula render() already used in Part IV/V, extracted so hit() can ask
"is this click on the thumb" using the identical position render() just
drew.

Drag state
--------------
Two new fields on MixaAppFmPanel, ordinary per-instance state, not
globals: drag_active (nonzero while a drag is in progress) and
drag_grab_offset (the row within the thumb, 0 = its own first row, where
the press landed -- fixed for the whole drag). A press exactly on the
current thumb sets both and changes nothing else (requirement 1's own
"without changing file selection or keyboard highlight," and no
immediate view jump either -- the one thing a naive "snap the thumb's
top under the cursor" implementation would get wrong, and exactly why
requirement 2 asks for a defined, tested grab offset). A press elsewhere
on the track keeps the EXACT Part IV jump-to-position formula unchanged
(requirement 5).

This backend seam does not distinguish "just pressed" from "still held
and moving," and that turns out not to matter
-----------------------------------------------------------------------------------
mixa_backend.h's own MIXA_EVENT_MOUSE carries only a buttons bitmask and
a position -- there is no separate "this is WM_LBUTTONDOWN" vs "this is
WM_MOUSEMOVE while held" signal anywhere in the seam, and adding one was
out of this ticket's own scope (it did not ask for a backend change, and
this ticket needed none). So mixa_app_fmpanel_hit's own drag-continue
branch is checked FIRST, before anything else in the function, and
treats EVERY call while drag_active is set as "the drag continues,"
regardless of whether the underlying platform event was a fresh press or
a held move -- both report identically at this seam, and both should do
the identical thing (move the thumb to track the cursor's current row,
honoring the grab offset). The only place this could matter is a
double-click landing exactly back on the thumb while STILL dragging,
which would just be interpreted as "still dragging, moved to this row" --
indistinguishable in effect from an ordinary drag continuation, so this
is not a real gap.

Release
----------
mixa_app_fmpanel_release(p) clears drag_active unconditionally
(idempotent when no drag is active). mixa_app_controller.lm1's step()
calls it on every MIXA_EVENT_MOUSE where the left button is NOT held --
a real button-up and an ordinary hover-move with no button at all report
identically (buttons=0) at this seam, and mixa_app_fmpanel_release
treats them identically on purpose: requirement 3's own "motion without
an active drag changes nothing" holds either way, since a drag that was
never active has nothing to end, and a real release correctly ends one
that was.

Shrink/refresh safety during a drag
------------------------------------------
The drag-continue path recomputes mixa_app_fmpanel_scroll_geom fresh
from the CURRENT real mixa_fm_count on every single call -- never a
value cached at drag-start. If a shrink (e.g. a real refresh triggered
from outside the click UI, the exact scenario this ticket's own test
proves) leaves no track room to drag within (max_scroll = 0 or
track_room = 0), the drag ends gracefully right there rather than
dividing by a room that no longer exists; the SAME clamp_view() call
render() already makes every frame (Part IV) independently pulls view_
top down to the new bound regardless, so even a stale value between the
drag ending and the next render is corrected before anything is drawn.

The real geometry problem, and why a "focus gutter" was the answer
------------------------------------------------------------------------------
mixa_highlight_set calls mixa_draw_frame, which refuses nrows<2 (a real,
measured constraint -- Part IV already found this reading mixa_draw.lm1
directly, which is exactly why Part IV used reverse-video as a disclosed
stand-in instead). A real list entry is exactly one text row tall.
Framing the full entry row would need 2 real rows, and mixa_draw_frame's
own top/bottom edges span the FULL frame width between the corners --
so a naive 2-row-tall, full-width frame would overwrite a NEIGHBORING
entry's own name text with border glyphs, which requirement 1's own "do
not... overwrite the underlying row fill" explicitly forbids.

The fix: reserve a fixed, permanently-blank 2-column "focus gutter"
(MIXA_APP_FMPANEL_FOCUS_GUTTER_COLS) at the START of every entry row AND
the path row. Framing a NARROW 2-row x 2-col region entirely inside that
gutter never touches real text on either row, on either side of it --
for a 2x2 region, mixa_draw_frame's own top/bottom edges have ZERO width
between the corners (c_last = col+1 is the SAME column the corner loop
already covers), so the frame draws EXACTLY 4 corner glyphs and nothing
else. This is a real, disclosed rendering-only change: the entry-row
HIT-TEST region (list_col..list_col+entry_cols) is completely unchanged,
so no click-based test from any earlier ticket needed to change; only
one existing test (mixa_app_fmpanel_e2e_selftest.lm1) asserted the exact
COLUMN a rendered character appears at, and was updated (col2 -> col4)
with a comment explaining why.

Which adjacent row the frame borrows
------------------------------------------
The highlighted entry's own row is always one half of the 2-row frame;
the frame prefers extending DOWN into the next row (blank gutter there
too, safe) unless that would reach the action row's own real Delete/
Copy Here/result content (requirement 1's own "row fill" concern again,
this time for a DIFFERENT row's real content) -- in that one case (the
LAST visible entry row) it extends UP instead, which is always safe
since the row above a real entry row is either another real entry row
or the path row, both gutter-reserved.

Move, scroll off/on, and cleanup
-------------------------------------
mixa_highlight_set's own already-accepted contract does the "move"
half of requirement 2 for free: calling it again at a NEW position
automatically restores the OLD one first (same target rect only), so
render() just calls it fresh with the CURRENT frame position on every
tick a highlight is visible -- no separate move/redraw logic needed.

"Disappear when off-screen due to mouse-only viewport movement"
(requirement 2's other half) falls out of the SAME visibility check
Part IV's own render() already performs for drawing the highlighted
row's own marker: highlight_idx visible iff view_top <= highlight_idx <
view_top+visible, re-derived from the CURRENT view_top on every render,
never cached. A scrollbar/wheel/drag move (UI_MODEL 5.7.1's own
asymmetric rule, established across tickets 044900/053000/060000) can
change view_top without moving highlight_idx, so the SAME highlighted
entry can go from visible to not visible across two renders with no
index change at all -- exactly this check catches that and calls mixa_
highlight_clear.

Cleanup (mixa_app_fmpanel_close) calls mixa_highlight_release, which
frees bookkeeping only (its own documented contract -- it does not
restore cells, since by the time a panel closes there is usually nothing
sensible left to restore into). The embedded MixaHighlight (a complete,
plain-C struct, not opaque) needs no separate allocation of its own --
mixa_app_fmpanel_open/close just call mixa_highlight_init/release on the
address of the embedded field, the same "one struct owns everything it
needs" shape MixaAppFmPanel itself already has inside MixaAppController.

Selection stays a separate, real state (requirement 4)
-------------------------------------------------------------
The mouse-driven "* " selection marker (an entirely different, pre-
existing mechanism) is drawn exactly as before; the keyboard-focused
row's TEXT no longer changes color at all (the reverse-video swap is
gone) -- focus is now shown ENTIRELY by the frame in the gutter, not by
anything touching the entry's own text cells. An entry can be selected,
focused, both, or neither, independently and simultaneously, exactly the
FAR/Norton "marked" vs "cursor" distinction this document has named
since Part IV.

Part VIII -- selection preserved by stable path identity: a correction, not a fix (ticket 20260913-071906)
====================================================================================================================
This ticket asked to fix "the concrete portable state bug disclosed in
mixa_app_fmpanel.txt Part V/VII: an unrelated selected entry is lost
when a delete/refresh rebuilds the directory listing." Investigating it
properly (not just re-asserting the earlier claim) found that IT DOES
NOT REPRODUCE AS A DEFECT. This Part documents the investigation, why
the earlier disclosure was wrong, and the real (unmodified) mechanism
that already does the right thing -- correcting Parts V and VII above
rather than leaving a stale claim standing.

What Part V/VII actually observed
--------------------------------------
Both earlier tickets' own selftests selected an entry (e00.txt in the
wheel ticket, e05.txt in the focus-frame ticket) in an EARLY scenario,
then in a LATER, unrelated scenario selected and deleted a DIFFERENT set
of entries (e10..e29, or whichever real entry sat at index 2) WITHOUT
ever deselecting the first one. Both selftests then observed that first
entry gone too, and both concluded its selection had been "lost."

Traced directly with a temporary debug trace inside mixa_sel_remove_
selected_at (added, used to print exactly what mixa_selection_walk's own
delete-glue was removing and why, then fully removed -- never committed):
the first entry (e00.txt / e05.txt) was the VERY FIRST thing removed
from mixa_selection's own `selected` array during the delete walk --
because it was STILL AN EXPLICIT, ACTIVE SELECTION at that exact moment,
never having been deselected since the earlier scenario. mixa_selection_
walk (SELECTION_MODEL.txt's own accepted, unmodified design) walks EVERY
currently-selected root, not "whatever was selected in this particular
gesture" -- there is no such narrower scope anywhere in the model. So
the first entry was correctly, intentionally deleted ALONGSIDE the
entries the test author actually meant to delete, because it genuinely
was still part of "the current selection" the whole time.

This is not data loss. SELECTION_MODEL.txt's own stated design (section
2, "used INSTEAD OF select-all-then-exclude... the same mechanism works
on the directory tree at any depth") is explicit that selection is
PERSISTENT and CUMULATIVE across gestures by design -- and this ticket's
own requirement 5 ("do not change... delete semantics") confirms Delete
must keep operating on the WHOLE current selection, not a narrower
per-gesture subset. An entry left marked from an earlier, forgotten
gesture being swept into a later delete of the WHOLE selection is
exactly what a persistent multi-select model is supposed to do. The
actual defect was in the two EARLIER TESTS' OWN construction (forgetting
to deselect the "control" entry between scenarios), not in mixa_
selection, mixa_file_manager, or mixa_app_fmpanel.

The one construction where "distinct" can actually hold
-------------------------------------------------------------
For "select A, delete distinct B, A remains selected" to be achievable
AT ALL without changing delete semantics, A must not be part of the
selected set the delete walks -- meaning B's own removal cannot go
through the SAME real, selection-driven Delete gesture A is also marked
for. The only construction consistent with that AND with every other
constraint this ticket sets (no delete-semantic change, no core/L2
touch) is B being removed EXTERNALLY (any real disk change outside the
app's own selection-based Delete UI) followed by a same-directory mixa_
fm_refresh. Verified directly with a throwaway scratch probe before
writing the real test (translated, compiled, and linked against the
actual, already-built production objects from a prior real test run;
executed; output inspected; then deleted -- never part of any committed
source): selecting a.txt, removing a DISTINCT, never-selected b.txt with
a raw `c.remove`, then calling mixa_fm_refresh, already reports a.txt
still selected with its own index correctly re-resolved -- zero source
changes needed anywhere.

Why this already works, mechanically
------------------------------------------
mixa_selection stores its OWN independently-owned copies of every
selected path string (mixa_sel_strdup, on mixa_selection_select).
mixa_fm_refresh only rebuilds mixa_fm's own entries array (mixa_fm_
build re-enumerates and re-allocates fresh MixaFmEntry objects with
fresh path strings) -- it never touches mixa_selection at all, and
mixa_fm_is_selected always re-derives its answer by re-reading the
CURRENT entry's own fresh path string and asking mixa_selection_query
with it, never from a cached index-to-selected mapping. So a refresh
that removes an unrelated entry, adds new ones, or reorders everyone
else's own index cannot desynchronize a surviving entry's own selection
from its own (possibly new) index -- the query is always keyed by the
entry's actual current path, at the moment it is asked, not by any
numeric position. The requirement's own "no new entry may become
selected because its numeric index was reused" is therefore
structurally impossible already, not merely untested -- verified
directly rather than left as an assumption (this ticket's own test
proves it: five brand-new sibling files, never selected, added right
before a refresh that also renumbers a surviving selected entry, and
none of the five ever reports selected).
