A genuine L1 grammar limitation found and worked around (not assumed,
empirically confirmed by isolating minimal reproductions)
------------------------------------------------------------------------
mixa_core.h's own real MixaCell declares fg/bg/flags/width/alpha as
scalar `unsigned char`. This L1 grammar has NO scalar byte-type keyword
usable as a STRUCT FIELD:
  - `unsigned char: name` as a struct field -> "struct field expects a
    declaration frame" (a two-word type token is not recognized there).
  - bare `char: name` as a struct field -> "unsupported L1 form".
  - `[]: unsigned char name 1` (array field, two-word element type) ->
    "struct field array cannot have initializer" (the []: field parser
    appears to mis-split a two-word element type, treating the array-
    size argument as a bogus initializer).
  - `[]: char name N` (array field, SINGLE-word element type) DOES work
    and is already used elsewhere in this codebase (mixa_app.h.lm1's own
    accepted MixaAppEntry). A 1-element array of a given base type has
    IDENTICAL size and alignment to a scalar of that same base type in
    C, so `[]: char fg 1` (emitting `char fg[1];`) is byte/offset-exact
    to the real `unsigned char fg;` -- confirmed via the ABI probe pair
    above (sizeof(MixaCell)=12 both, every one of its 5 single-byte
    field offsets identical both, sizeof(MixaTextRect)=24 both).
  - The one real, honest consequence: this L2 field is SIGNED char, not
    unsigned. Every store in mixa_tile_fill_button truncates correctly
    regardless of signedness (assignment truncation is bit-identical
    either way), but READING the value back as a full-range int requires
    an explicit `(cast: (int) (cast: (unsigned char) field))` -- the
    parity harness's own alpha check (values up to 255) hit exactly this
    sign-extension the first time it was written (200 read back as -56)
    and was fixed by adding that intermediate unsigned-char cast; the
    harness's own comment at that exact line documents why. This is a
    real, minor, worth-recording grammar limitation, not a workaround
    for a compiler refusal of the OWN task -- a bodyless top-level `fn:`
    (mixa_highlight.lm1's own precedent) is likewise only valid inside a
    .lm1 IMPLEMENTATION file; inside a .h.lm1 HEADER unit it must be
    wrapped in a `prototype:` block (mixa_app.h.lm1's own established
    style) -- confirmed empirically (a bare fn: there fails with
    "executable body"), and mixa_tiles_l2.h.lm1 already uses the correct
    form.
  - Struct-field array WRITES from a caller need pointer arithmetic, not
    indexing, to reach the array-typed field: `cells[i]\field` fails
    ("cells[i]" is a value, and `\` always emits `->`, requiring a
    pointer on its left); `p: cells + i` then `p\field` works, matching
    the SAME idiom mixa_selection.lm1 already uses throughout for its
    own MixaSelRev arrays (`r: sel\revs + i`). The harness's own SCN 5
    setup uses this pattern.
  - A stray, unrelated testing artifact also cost real time here and is
    worth recording: l1trans's own predef-path resolution behaves
    differently when the SOURCE file's own path is a relative,
    repo-rooted path versus an absolute path outside the repo (e.g.
    under a temp directory) -- an otherwise byte-identical file fails
    with a misleading "unsupported L1 form" when invoked from an
    absolute /tmp path, and succeeds when invoked with the source path
    relative to the repo root. All isolated syntax probes for this
    ticket were re-run from inside mixa_manager/ (repo-relative) once
    this was discovered, and the earlier /tmp-based "unsupported L1
    form" results were discarded as testing artifacts, not real
    findings.
