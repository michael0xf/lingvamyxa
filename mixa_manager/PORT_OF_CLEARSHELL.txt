Mixa Manager - a desktop port of ClearShell
Framing document. Read this before the others.


1. What this project is

Mixa Manager is a DESKTOP PORT OF CLEARSHELL, with its functionality, its
layout and its behaviour. The differences are details, and this document is
where they are listed.

Stated by the language owner on 2026-09-09, and it changes how the other
documents should be read. They are not an independent design that happens to
cite ClearShell; they are a DELTA against it. Where they are silent, ClearShell's
behaviour is the answer - not "undefined", not "our choice later".

    reference source:
    C:\Nyasha_Planet\git\clear_shell\ClearShell\app\src\main\

The practical rule that follows: before designing anything, look at how
ClearShell does it. Reinventing something it already solves is the error mode
here, and inventing a DIFFERENT solution to a problem it solved is worse than
copying the solution badly.


2. The deltas established so far

INCOMPLETE. The language owner began listing differences and the list is not
finished; these are the ones fixed so far. Add to it rather than deducing new
differences from silence.

2.0. The general rule: port the PRESENTATION, not the IMPLEMENTATION

Stated by the language owner with the calculator as the worked example.

The calculator's INSIDES are not worth porting: we will have a whole language of
our own, and it is what will do the calculating. Its APPEARANCE is ported in
full.

So the split runs through every feature, not around them:

    presentation, layout, behaviour, wording, colours   ported, in full
    internals that our own language or platform supersedes   not ported;
                                                             reimplemented

The trap this avoids is porting an implementation because it came attached to a
look we wanted, and then being stuck maintaining a second-rate copy of something
our own language does better.

2.0.1. Everything visible becomes pseudographics - "pseudo-pseudographics"

In ClearShell a button IS a system widget. Here it is DRAWN: characters in
cells, through the one drawing API. So what ports is the button's appearance and
geometry, never the widget.

That needs no new drawer primitive - a button is a framed label, which is text
plus pseudographics - and it must not be allowed to grow one. See DRAWING.txt:
if the text layer could not accept the call, it does not belong in the drawer.

It does have one consequence that is easy to miss. Android gives ClearShell
hit-testing for free: a view knows it was touched. A DRAWN button knows nothing.
So mapping a click to a button is OUR work, and it is why the backend seam
reports mouse position in CELL coordinates rather than pixels - the backend
converts once and every consumer agrees.

2.1. Rendering

  ClearShell    Android widgets draw the text; the output lives in a system
                editing widget and is saved by a button
  here          two CELL GRIDS drawn by us, one drawer for both, glyphs from
                the system font used pixel for pixel and never scaled.
                See Mixa_Manager_RENDERING_DOCTRINE.txt

2.2. The console

  ClearShell    output kept in memory with head, line and tail limits; the
                middle is dropped when a command is noisy; there is an editing
                widget behind it
  here          the scrollback IS A FILE. There is no editing widget to hold
                it and we render it ourselves anyway. See FILE_SEAM.txt

2.3. Layer arrangement

  ClearShell    text input attached at the TOP; beneath it, the camera image
  here          Norton-style: input on the BOTTOM line, output scrolling
                upward, and the panel layer semi-transparent OVER the console
                so the output stays readable beneath it

2.4. The button panels

  ClearShell    the application panel is at the top
  here          the application panel LIES AT THE BOTTOM, on the upper layer,
                because that is where a Norton-style command line already is.
                It is not a band below the console: the console's text screen
                runs full height underneath it and the cursor can pass beneath
                the panel - UI_MODEL 1.1

  unchanged     the per-list panel is that list's header, and the header is
                STICKY - scrolling the list does not carry it away

2.5. Vertical scrolling

  ClearShell    the whole panel moves vertically - a concession to a narrow
                phone screen
  here          each list scrolls inside its own bounds and keeps its own
                position, with its own vertical scrollbar; one shared
                horizontal scrollbar for the row of lists

2.6. Graphics

  ClearShell    Android views, images, a camera preview
  here          NO graphical elements at all. Everything is pseudographics in
                cells. Images are a future third layer, a plain buffer, and are
                kept out of the drawer on purpose. See DRAWING.txt


2.7. Keyboard: FAR Manager, not ClearShell

Take as many hot keys from FAR Manager as apply, and invent the rest.

So there are TWO reference sources and they do not overlap:

    ClearShell    appearance, layout, behaviour, feature set
    FAR Manager   key bindings

Where they conflict, that split decides it: the keys come from FAR, the look
from ClearShell. Where a FAR key implies a feature ClearShell does not have,
that is one of the things we invent - and it gets written down here, like every
other delta.

2.8. Focus and highlighting: absent from the source, must be built

ClearShell has no highlighting, and that is not an omission - it is a touch
interface, where there is no "current element" to show. FAR and Norton are
KEYBOARD interfaces: something is always current, and focus moves between
elements. That difference is not a detail; it is a whole mechanism the port
cannot copy because the source does not contain it.

So we build:

    a focus model - which element is current, and how focus moves between
      lists, items, buttons and panels
    a highlighted rendering for ANY element, not only list rows

What this does NOT need is any new drawing capability, and that is worth
checking rather than assuming. Highlighting is a change of ATTRIBUTES, and
MixaCell already carries fg, bg and MIXA_STYLE_REVERSE. So a highlighted button
is the same cells with different attributes - the drawer does not learn about
focus, and the single-API property survives.

Colours for it come from ClearShell's palette, which already distinguishes a
translucent highlight at alpha 96 from a panel body at 240.


3. What is ported unchanged, and must not be redesigned

3.1. The layout METHOD

One quantity is MEASURED - the height of real text in the real font - and
everything else is an integer shift of it: button height, width at 1.75 of the
height, margin at a thirty-second. No pixel constants and no fractions.
ClearShell.java, init(), around line 697.

Our measured unit is the CELL, so the translation is direct: every dimension is
an integer number of cells.

3.2. The button panel algorithm

ClearShell.java, freshLayout(), around line 1772:

    buttons are arranged in EXPLICIT LINES, not auto-wrapped
    within a line   x += button width + margin
    between lines   y += button height + margin
    a null entry is a SEPARATOR, advancing x by half a button height
    panel height is max(y + button height), width is max(x + button width)
    the panel sits inside a HORIZONTAL SCROLL

The last point is the one to port carefully, because it is the reason the
interface survives any screen. When the buttons do not fit, they are NOT
shrunk, NOT re-wrapped and NOT dropped - the panel SCROLLS. Overflow is a
scrolling problem, never a scaling problem, which is the rendering doctrine
appearing again in a place that has nothing to do with fonts.

3.3. Colours

Taken as-is. ClearShell.java: panel backgrounds at alpha 240, translucent
highlights at alpha 96, opaque foreground text. See UI_MODEL.txt section 3.

3.4. Functionality

The feature set is ClearShell's and is to be read from its source rather than
guessed: roots list, name filter, sorts including by time, zip archives browsed
as directories, rename, remove selected, create, save and save-as, load, run OS
command, viewers, links, help. This document does not restate it - it names
where it lives.

Stated by the language owner after I invented a cursor rule that the old

Consult in this order, and stop at the first that answers:

       FILE_SEAM, SELECTION_MODEL, CODING_RULES - and
       Mixa_Manager_RENDERING_DOCTRINE.txt at the root.

    2. Old_Mixa_Manager_Qt_model.txt. IF IT IS NOT IN THE NEW DOCS, LOOK IN THE

4.1. And when you diverge, say that you diverged

Finding an answer in an older source and choosing differently is legitimate -
the layers have changed since, so some of it no longer fits. What is not
legitimate is diverging silently, which leaves two documents contradicting each
other and no way to tell which was considered.

UI_MODEL 1.0.3 is the worked example: the old model draws the cursor above the
overlay, we now put it in the lower layer, and the section says so and says why.

5. Observations from reading the source

The source is now in the repository at mixa_manager/clearshell_reference/ - Java
only, Android manifest and res/ deliberately omitted. Line numbers below are
from that copy and were correct when written; if one has drifted, the name is
what to search for.

Recorded here at the END of this document, and appended to rather than
rewritten, so the reasoning stays with the port that used it.

5.1. Layout is derived, never constant
    com/mtk/shell/ClearShell.java  init(), ~697

One quantity is MEASURED - a real Button, real font, real text, then
getMeasuredHeight(). Everything else is an integer shift of it: height plus a
quarter, width (h<<1)-(h>>2), margin h>>5, and 1.5 of the longer screen side.
There is no pixel constant and no fraction anywhere in it. This is the reason it
works from a tablet to an mp3 player, and it is the rendering doctrine written
before we wrote it down.

5.2. Overflow is a SCROLLING problem, never a scaling one
    com/mtk/shell/ClearShell.java  freshLayout(), ~1772

Buttons sit in EXPLICIT LINES, not auto-wrap. Inside a line x += width + margin;
between lines y += height + margin; a null entry is a separator advancing
h>>1. Panel height and width come from the maxima. The panel then sits inside a
horizontal scroll - so when buttons do not fit they are not shrunk, not
re-wrapped and not dropped. They scroll.

5.3. The row of lists IS the path
    com/mtk/shell/StorageList.java  initParent() ~287, up-operation ~185,
    dirs.get(position) ~468

dirs holds the chain from the disk root to the CURRENT directory - the last
element is where you are, not the parent - and positions holds, per level, the
index of the entry descended through. Going up pops the rightmost list and
restores its remembered cursor.

5.4. There is no ".." and the parent concept is still richer than ".."
    com/mtk/shell/ClearShell.java  getView() ~4889

The literal string does not occur anywhere in the source. Instead every list
opens with an ancestor block: isParent is position < dirsSize(), so the first
rows are the whole path - roots entry, disk root, down to the current directory
- before the directory's own contents. Directories then files.

I searched for the string, failed to find it, and concluded the mechanism was
absent. It was not. Do not repeat that: absence of a spelling is not absence of
a concept.

5.5. The ancestor gradient is COMMENTED OUT
    com/mtk/shell/ClearShell.java  ~9452

A scale factor shading ancestor rows by depth exists but is disabled. Do not
port it as live behaviour without asking - "fixing" a deliberate omission is a
way to make the port wrong while looking careful.

5.6. Command execution, and what the console log needs
    com/mtk/shell/ClearShell.java  ~13700 and ShellOutputCapture ~13464

The command is wrapped in a script that prints a MARKER line carrying exit
status and working directory, tab separated. stderr is merged into stdout, and
stdin is closed so that a command like cat does not wait forever. Output is then
captured with head, line and tail limits, and the MIDDLE IS DROPPED when a
command is noisy - which is what we do not port, because our scrollback is a
file. The marker line we do port; see FILE_SEAM.txt.

5.7. mtk/map and com/mtk/map are a LIBRARY, not shell code

They are a published one - OverlappingTreesPlainMap, shipped as mtkmap-*.jar.
Item, Tag, Array and the tables live there. Item is worth reading for its own
sake: Named, IValue, IPointer, ISrc, IStorage, children addressed by name,
pointers, tags - which is recognisably the same ontology as Lmx, arrived at
independently in Java.

5.8. The selection model
    com/mtk/shell/FSync.java

Documented separately and at length in SELECTION_MODEL.txt, including the
consolidation loop that I twice suspected of being a defect and which testing
showed to be correct and load-bearing.
