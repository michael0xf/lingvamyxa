--- Fix: app_win32's mixa_app_win32.lm2:463 `@ dslot[0]` through the
    explicit adapter (spec 11.3.1, 12.2), one site

Cause: l1trans's own l2trans is stricter than l1trans about own-Array
element addressing. `@ dslot[0]`/`@ lslot[0]` is exactly what the real,
accepted oracle mixa_app_win32.lm1:464 already writes (the L2 port is a
faithful copy of that line); l1trans accepts it (oracle: 58 checks, 0
failures) but l2trans's own l2_check_fields (l2trans.lm1:10072-10075)
rejects `@` directly in front of a resolved own-array-index pattern,
per 12.2's own rule: "A raw element-storage pointer is a different
value, obtained through an explicit low-level adapter when admitted."
The admitted adapter, confirmed from this SAME file's own already-
passing code (mixa_app_win32.lm2:292 `mixa_app_utf8_to_wide(path_utf8,
wslot)`, :302 `c.WriteFile(hfile, text, (cast: (ulong) n), wrote, 0)`
-- both pass a size-1 own-array BARE, no `@`, no index, as a call
actual): l2trans's own l2_check_actual_fields sets l2_decay_ok while
checking a call actual, and a bare own-array name in that position
decays to its backing pointer (l2trans.lm1:9965's own comment) -- for
a size-1 array that IS the element-0 address `@ dslot[0]` meant, with
no L2-visible `@`.

Fix, one site only, per the ticket: mixa_app_win32.lm2:463 changed from
`mixa_app_read_file_utf8(entry_path_utf8, @ dslot[0], @ lslot[0])` to

--- Port design note: app_controller's opaque fmpanel header -- what an
    L2 declaration would need, and why the earlier predef draft
    overflowed the import path table (no code, per the ticket)

mixa_app_controller_l2.h.lm1's own header comment (lines 5-59, written
at the port's own commit 12aa8b44) already records this in full; this
note restates it against the specific symbol part 3's diagnosis named,
mixa_app_fmpanel_close, and traces the actual overflow.

What an L2 declaration for mixa_app_fmpanel_close would need: not just
a bare `prototype: fn: mixa_app_fmpanel_close (@: MixaAppFmPanel p)
void end: prototype` block (the "declare then link" form already used
for mixa_cell_at in mixa_tiles_l2.h.lm1 and mixa_tile_fill_button in
mixa_buttons_l2.h.lm1) -- that form only works when the parameter type
can stay a plain opaque name. Here it cannot: MixaAppFmPanel embeds
MixaHighlight BY VALUE (mixa_app_fmpanel_l2.h.lm1:105, `MixaHighlight:
focus`, confirmed by that file's own comment lines 13-35), and a
by-value embedded field needs the translator to know its real layout
to compute MixaAppFmPanel's own size/offsets -- an opaque forward name
cannot supply that (this is the SAME distinction mixa_app_controller_l2
.h.lm1's own comment already draws for the OTHER, safely-opaque fields:
"a DEREFERENCED struct field needs L1-known layout -- true for the
by-value-embedding case... but NOT true for plain pointer-field
dereference"). So the declaration mixa_app_fmpanel_close needs is the
FULL chain: predef mixa_app_fmpanel_l2.h.lm1 itself (giving
MixaAppFmPanel's own real, field-accurate struct plus the function's
own prototype).

Why that overflows: mixa_app_fmpanel_l2.h.lm1 is not a leaf -- it
predefs three further chains of its own (mixa_file_manager.h.lm1,
mixa_selection_walk.h.lm1, mixa_highlight_l2.h.lm1), each potentially
carrying more. The earlier draft of mixa_app_controller_l2.h.lm1 tried
predefing this full closure alongside the controller's OTHER by-value-
adjacent needs (fm_copy + console_window_l2 + help_l2 + cmdline_l2 +
cmdline_dispatch_l2 + app_path_l2 + app_fmpanel_l2) and hit `l1trans
error: mixa_manager/mixa_app_fmpanel_l2.h.lm1:0:0: import path table
full` -- reproduced directly by that draft's own author (mixa_app_
controller_l2.h.lm1:37-40), overflowing the pinned stable65D5 l1trans's
16-file cap by a wide margin, not by one file. The accepted header
avoids this by keeping MixaAppFmPanel (and every other struct this
controller only ever touches through a pointer field) genuinely opaque,
reached via the real, plain `#include "mixa_manager/mixa_app_fmpanel.h"`
instead -- correct for l1trans (which resolves `\` dereference through
gcc, never needing L1-level field knowledge for a pointer field, per
that header's own comment lines 27-34) but insufficient for l2trans,
whose own unsupported-body guard needs an L2-recognized callable frame
for mixa_app_fmpanel_close specifically, which a plain #include never
supplies. That gap -- l2trans needing what l1trans does not -- is the
open question a real fix would have to resolve, not addressed here.

--- Diagnosis: why app_window's L2 trace stops silently after check 15
    of 162 (no fix -- root cause is in l2trans.lm1 itself, outside
    mixa_manager's own scope)

Reproduced directly under gdb (`gdb -batch -x <run> ./parity_l2.exe`,
the exact object this dispatcher run built): SIGSEGV in strlen, called
from mixa_button_panel_add, called from l2_uCC211EFB79C1B967_m9 (the
L2-generated body of mixa_app_window_open), called from main. The
crash is the FIRST call this whole test sequence ever makes to
mixa_button_panel_add -- every earlier CHK (open hb0 through open too
small) returns ERR from an early guard before reaching it; "open long
msg rejected" (harness line 198, the check whose own CHK line never
prints) is the first call to survive every early guard and reach it.

mixa_button_panel_add itself is the REAL, unmodified object (Build-
RealDep in run_mixa_l2_parity.ps1 always translates mixa_buttons.lm1
via l1trans, never mixa_buttons.lm2 -- confirmed already in this
audit's own duplicate-symbol section) -- identical on both the oracle
and L2 sides, so the bug is not in that function's own body. The
generated call site itself matches the real .lm1 source exactly
(mixa_app_window.lm2:244, byte-identical to mixa_app_window.lm1:254):
`mixa_button_panel_add(panel, 0U, MIXA_APP_WINDOW_BTN_LABEL, ...)`.

Root cause, found by reading the actual generated C
(app_window_l2.c:4197-4204) and its own gcc warnings (l2mod_compile_
stderr.log): l2trans stages every `define:`d constant argument to this
call through an intermediate temp it types uniformly as `int`,
regardless of the constant's real type --
    int l2_t3; l2_t3 = MIXA_APP_WINDOW_BTN_LABEL;   // a `char *` constant
    int l2_t4; l2_t4 = MIXA_APP_WINDOW_BTN_FG;       // genuinely numeric
    int l2_t5; l2_t5 = MIXA_APP_WINDOW_BTN_BG;
    int l2_t6; l2_t6 = MIXA_APP_WINDOW_BTN_ALPHA;
gcc's own warnings name exactly this: ":4198:11: warning: assignment to
'int' from 'char *' makes integer from pointer without a cast
[-Wint-conversion]" and ":4295:42: warning: passing argument 3 of
'mixa_button_panel_add' makes pointer from integer without a cast
[-Wint-conversion]" -- neither is covered by this runner's own
-Werror set (incompatible-pointer-types/discarded-qualifiers/implicit-
function-declaration/implicit-int catch different diagnostics, not
-Wint-conversion), so it compiles silently. On this 64-bit target the
pointer truncates to its low 32 bits in l2_t3 (an int), then widens
back on the call with garbage high bits -- the crash's own rcx at the
strlen frame, 0x4ebf1611, is exactly that shape: a 32-bit-looking value
where a real heap/text-segment pointer would be. FG/BG/ALPHA survive
the same treatment only because they are genuinely small numeric
constants an int can hold intact.

This is an l2trans.lm1 type-inference defect (the checkpoint/staging
codegen for a define:'d call-actual constant does not consult the
constant's own type, or the callee's own parameter type, when choosing
the temp's C type) -- not a one-site mixa_manager fix, not a missing
runtime module, and not an oracle-side divergence (the oracle passes
because it links the REAL object directly with no such staging).
Reported as a finding for whoever owns l2trans/core L2 work; not fixed
here, per this session's own role boundary and the ticket's own "a fix
if it is one site" condition -- it is not.

The two candidate shapes, and what each breaks:

(a) tiles_l2.h.lm1 includes the real mixa_core.h and drops its own
`struct: MixaCell`/`struct: MixaTextRect`. Breaks field-level L2
access broadly: every module that reads/writes a MixaCell/MixaTextRect
field through L2's own `\` field-follow (composite_glyphs's own
`cell\fg`/`\bg`/`\alpha`, fixed earlier in this exact audit thread;

highlight all touch these fields the same way) needs L1-known field
layout, which a plain opaque `include:` cannot supply -- this is
tiles_l2.h.lm1's own header comment's exact reasoning for declaring
these structs itself rather than including the real header, already
written before this note. This candidate reverses that reasoning
tree-wide, not just for app_controller.

(b) the real side takes the L2 header's declaration -- mixa_core.h (or
whatever real code currently defines these structs) includes the
L1-generated tiles_l2.h.lm1 output instead of defining them itself.
Breaks the oracle/L2 dependency direction for a FOUNDATIONAL header:
mixa_core.h is real, hand-written C, included directly by dozens of
unmodified real files having nothing to do with L2 porting; making it
depend on l1trans's own generated output would mean the entire real
side needs l1trans to run and produce mixa_tiles_l2.lm1.h before
mixa_core.h itself can be preprocessed -- inverting which side is the
source of truth for two of this tree's most foundational types, a
build-order and architecture change affecting the whole codebase, not
scoped to app_controller at all.

Recommendation: neither of the two above -- both are tree-wide changes
for a conflict that, traced just above, is not actually live anywhere
except the one attempted fix. A narrower option, verified directly
