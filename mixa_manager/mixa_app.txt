mixa_app — app/shortcut launcher seam (ClearShell "App" button, ticket 20260911-154200)
=========================================================================================

Purpose
-------
One bounded slice: read the real desktop app list (Windows shortcuts and URL
shortcuts) as opaque launchers, and expose the minimal UI-callable surface the
ClearShell "App" button needs: classify, inspect, create/read/remove our own
shell list entries, invoke one entry, and enumerate. No equivalent module
existed in this codebase before this slice.

The key design decision is OPAQUE references: a stored launch reference is the
ORIGINAL .lnk/.url file itself, never a flattening to target+arguments. The
native launcher contract (invocation via ShellExecuteExW with the "open" verb)
preserves the original target, arguments, working directory and verb semantics
for free, and shortcuts never get silently re-targeted on other machines.

Classification (case-insensitive extension; attributes are checked first)
------------------------------------------------------------------------
  reparse point (FILE_ATTRIBUTE_REPARSE_POINT)  -> MIXA_APP_KIND_FS_LINK
                                                  (recognized; NOT a launcher)
  directory                                      -> MIXA_APP_KIND_UNSUPPORTED
  "*.lnk"                                        -> MIXA_APP_KIND_SHELL_LINK
  "*.url"                                        -> MIXA_APP_KIND_URL_LINK
  anything else                                  -> MIXA_APP_KIND_UNSUPPORTED
  MIXA_APP_KIND_REGISTERED (reserved)            -> documented Windows gap; not implemented

Semantic guarantees
-------------------
* Inspection NEVER executes a target: it only reads attributes, derives the
  label (basename minus .lnk/.url), records the source path as the opaque
  reference, and optionally resolves a shell icon tag ("path,index") via
  SHGetFileInfoW with SHGFI_ICONLOCATION. That call returns a string and never
  triggers the target.
* Invocation goes through ShellExecuteExW (fMask SEE_MASK_FLAG_NO_UI = 1024,
  nShow SW_SHOWNORMAL). The stored reference is the ORIGINAL launcher file, so
  a dropped-in replacement .lnk with the same name updates behavior without a
  code/entry change. Url links are invokable but the test suite deliberately
  does not invoke them (would open a browser).
* Filesystem links are recognized but never interchanged with launcher
  shortcuts; a caller cannot create our own entry from an FS link
  (ERR_UNSUPPORTED).
* Corrupt but readable ".link" entry files surface as MIXA_APP_ERR_IO during
  enumeration (never silently skipped). Missing entries, files and dirs are
  MIXA_APP_ERR_MISSING (ERROR_FILE_NOT_FOUND / ERROR_PATH_NOT_FOUND only).

Our own entry format (file suffix ".link")
------------------------------------------
  header line "mixa-app-link-v1" then one value per line:
      kind=N        label=...    has_icon=0/1    icon=...    launch=...
  Values must not contain a newline (checked at creation). The icon and launch
  references are opaque strings; launch must be an absolute path to the
  original .lnk/.url.

L1 findings recorded while porting (see also PORT_OF_CLEARSHELL.txt)
-------------------------------------------------------------------
* COM (IShellLinkW) is not expressible in L1, so shortcut metadata is never
  flattened; the concrete seam is OS-shipped data formats only. The "hard"
  COM-based target resolution the reference uses is deliberately dropped:
  the opaque-reference design replaces it.
* No two-level member chains (a\b\c) anywhere in the codebase; the enumerator
  passes its internal WIN32_FIND_DATAW to helpers (mixa_app_ffd_is_dir /
  mixa_app_list_build_path) instead.
* Helpers must be defined before use; sub:/fn: mixing with the prototype
  block works (app_window precedent).
* Native wide-string pattern is built byte-by-byte (no L"\\*.link" literal);
  Unicode fixture names are covered via explicit UTF-8 byte arrays.

Testing
-------
Run from mixa_manager:

    ./run_app_selftest.ps1

The runner is patterned on run_app_window_selftest.ps1 (compiler SHA256
65D5A5ED127CA1BAEBDD1D500A5B74CEEA63EC1985EAC52EDEF28EFEB261C936) and runs in
an isolated build/mixa/opencode/app_seam/run_<timestamp>_<guid>/ dir. It also:
  * compiles the harmless fixture exe (mixa_app_fixture_invoke.c) that only
    writes a marker file and exits;
  * builds REAL .lnk fixtures via WScript.Shell COM (including the unicode +
    space name "sp ace-файл.lnk"), a .url INI file, a broken-target .lnk and a
    junction (mklink /J);
  * links the test with -lshell32 and passes the fixture dir as argv[1].

The selftest asserts: inspect-only-never-launches (marker absent before invoke),
classification of every fixture kind, label/ref/icon invariants (unicode names
as exact UTF-8 bytes), create/read/remove round trips, enumerate + skip + END of
*.link entries, empty and corrupt directories, ERR_LAUNCH on a broken target
(no UI), a real launch that produces the marker file (bounded poll), and
null-argument negatives throughout.

Integration point (ticket 20260912-055917): DONE at the component boundary
------------------------------------------------------------------------
mixa_manager/mixa_app_panel.h.lm1/.lm1 (new) is the real App/shortcut button
panel: it opens a real nested same-app window (mixa_app_window's own stack/
save-restore/frame mechanism, UNMODIFIED) populated with one real button per
entry enumerated from a real directory through this module's own accepted
mixa_app_list_open/_next/_close path, preserving enumeration order and each
entry's own label/launch_ref verbatim. Hitting an entry button invokes it
through the existing mixa_app_invoke seam (which itself re-reads the entry's
own ".link" file, not its launch_ref -- MixaAppPanel captures that file's own
path from MixaAppList's own utf8_path at the moment it is yielded, alongside
the display fields, specifically so invocation stays correct). Hitting the
window's own OK button dismisses the whole panel and releases the panel's own
entry array/button panel. An enumeration failure is reported as an exact
status without pushing any window; a caller (real UI code, once it exists)
decides whether/how to surface that through the existing nested failure UI,
matching mixa_share_button's own precedent of keeping the generic dispatch
layer action-agnostic.

tests/mixa_app_panel_selftest.lm1 (new, 29/0, two hash-identical runs
build/mixa/claude/app_panel/run_20260912_061330_466_26e8b1be/ and
run_20260912_061350_230_b448c94b/) exercises this with the real module path
throughout -- two REAL .lnk fixtures (built by the runner via WScript.Shell,
the same accepted approach run_app_selftest.ps1 already uses) pointing at the
same harmless fixture exe with distinct -marker arguments, two real ".link"
entries via mixa_app_entry_create, real enumeration whose order/labels/
launch_refs are checked against an independent oracle enumeration (not
assumed alphabetical/creation order), a real invoke of EACH entry producing
its own distinct real marker file (bounded poll, same pattern as the existing
T15), the panel staying open after a successful invoke (a deliberate,
documented choice -- not a forced dismiss), correct dismiss-and-release via
the underlying window's own OK button, a real ERR_MISSING enumeration failure
(nonexistent directory) correctly reported without opening any window and
then surfaced through a caller-opened nested error window with the exact
status readable back from the drawn cells, and a real empty (but existing)
directory opening a valid zero-entry panel rather than being treated as an
error. run_app_selftest.ps1 (73/0) and run_app_window_selftest.ps1 (180/0)
both re-run unaffected.

Limitations, stated honestly: the entry-button panel does not check its own
drawn width against the window's interior the way mixa_app_window_open
already does for its message/OK button -- a directory with enough entries (or
long enough labels) to overflow ncols would currently just draw past the
window's own bounds rather than being rejected up front; not exercised here
since the test's own fixtures are small by design. No live pump-loop
orchestrator exists in this codebase to drive this from a real App-button
event -- this closes the component/integration-test boundary the ticket
asked for, not a running application. The MP3/audio nested panel (the
audio backlog's own remaining item) is explicitly a separate, later,
multi-stage effort per PORT_OF_CLEARSHELL.txt's own sequencing, not
attempted here.
