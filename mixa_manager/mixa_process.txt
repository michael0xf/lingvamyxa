mixa_process -- owner-local Windows process seam (ticket 20260912-144000)
=========================================================================

Read PROCESS_SEAM.txt sections 1-7, FIRST_VERSION.txt sections 1-4, and
FILE_SEAM.txt before writing this, as asked. The seam is exactly the six
operations PROCESS_SEAM.txt section 3 names -- spawn/read/write/status/
kill/close -- and nothing else: no PTY, no ConPTY, no escape-sequence
interpretation, no in-band marker parsing (PROCESS_SEAM 4.1's marker is
explicitly deferred to a separate pure module/stage, per the ticket's
own item 7), no Message/thread/mutex/queue integration (PROCESS_SEAM
section 6 names that as later work, once the core boundary exists).

Design
------
mixa_process.h and mixa_process_win32.h are both plain hand-written C
headers, reached via ordinary include: everywhere (the same route
mixa_file.h/mixa_backend.h already use) -- costs nothing against
l1trans's own import table, and per ticket item 8 this is exactly why
declarations live in a small header unit with the implementation as its
own separate L1 unit: pinned65D5 import capacity is never stressed by
this module at all, since nothing here is nested-predef'd by anything
else (unlike mixa_fm_copy's own measured 15-file chain).

MERGED STDOUT+STDERR (PROCESS_SEAM 4): ONE pipe is created; its write end
is set as BOTH hStdOutput and hStdError in STARTUPINFOW. There is
structurally only one writer set for the child, so arrival order can
never be reordered by construction -- not a runtime property asserted
after the fact, a property of there being only one pipe.

STDIN LIFETIME (PROCESS_SEAM 4 / ticket item 2), the exact rule: if
stdin_enabled is 0, the pipe's write end (ours) is closed immediately
once the child is confirmed started, so a child that reads stdin (e.g.
ClearShell's own `cat` example) sees EOF on its very first read rather
than hanging forever waiting for input nobody will send. If enabled, the
write end stays open for explicit write() calls; there is no separate
"close stdin only" operation -- ending it is exactly what close()/kill()
already do, matching the seam's own fixed six-operation shape rather
than growing a seventh. write() on a disabled-stdin process is
MIXA_PROC_ERR_ARG, not a silent no-op.

PROCESS-TREE KILL (ticket item 3): a Windows Job Object with
JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE. The child is spawned SUSPENDED,
assigned to the job, THEN resumed -- eliminating the classic race where
a child spawns its own descendant before the parent gets a chance to
assign it to the job (nested-job support on modern Windows would likely
cover that case anyway, but suspending first removes the race entirely
rather than relying on it). kill() calls TerminateJobObject, which
reaches every process in the job, descendants included, since the
default job policy does not grant breakaway. close() ALSO closes the
job handle, and with kill-on-job-close that kills anything still running
even if a caller only ever calls close() and never kill() -- verified
directly (see Testing) via a real cmd.exe -> ping.exe chain, not assumed
from the API's own documentation alone.

NON-BLOCKING READ (PROCESS_SEAM 3, ticket item 4): PeekNamedPipe first,
so an empty-but-still-running pipe returns MIXA_PROC_OK with *got==0
immediately -- never waits for output the way the read the seam
explicitly refuses (the loop belongs to the Message, not to this seam,
same discipline BACKEND_SEAM's own poll() already established for the
display seam). A CONFIRMED broken pipe (the child's own write end is
gone, i.e. it exited) is reported as the DISTINCT MIXA_PROC_EOF, latched
in the MixaProcess struct after the first observation -- a caller can
tell "nothing right now, maybe later" from "nothing ever again" without
guessing from a byte count alone.

EXACT EXIT CODE (ticket item 5): status() uses WaitForSingleObject(h, 0)
as the AUTHORITATIVE running/exited signal -- WAIT_TIMEOUT means running,
WAIT_OBJECT_0 means exited -- and only calls GetExitCodeProcess once
exited is confirmed that way. This deliberately avoids the well-known
Win32 ambiguity of reading GetExitCodeProcess alone (a legitimately-
exited process whose real exit code happens to equal STILL_ACTIVE, 259,
cannot be told apart from a still-running one by that call alone);
WaitForSingleObject's own signal state has no such ambiguity, so the
question does not need to be asked of GetExitCodeProcess at all. No
model contradiction was found needing to be reported -- this is
implementation work, resolved directly, not a genuine seam conflict.

NO FIXED CAPS (ticket item 6): the command-line buffer CreateProcessW
requires MUTABLE is allocated from the string's own real length
(MultiByteToWideChar's own reported size), not a fixed buffer; no 16/64/
128/1040-style constant appears anywhere in this module. The only
platform-imposed limit (Windows' own ~32K command-line length) is left
to the OS API to report as its own real failure, not pre-checked or
artificially capped here.

Known gaps, stated honestly
----------------------------
- The in-band marker line (PROCESS_SEAM 4.1: exit status + new working
  directory printed after the command, tab-separated) is NOT implemented
  -- the ticket's own item 7 explicitly asks for it to stay a separate
  pure module/stage, not folded into this commit.
- No Message/inbox/outbox integration (PROCESS_SEAM section 6) -- an
  explicit, later, cross-owner boundary, not attempted here.
- Handle inheritance uses plain bInheritHandles=TRUE rather than a
  PROC_THREAD_ATTRIBUTE_HANDLE_LIST restricting exactly which handles
  the child inherits; ClearShell's own ProcessBuilder reference does not
  use that narrower mechanism either, and this module's own inheritable
  handles are limited to the two pipe ends anyway (SetHandleInformation
  strips inheritance from the ends this side keeps), so the practical
  exposure is already small -- named here as a real, deliberate scope
  boundary rather than silently assumed away.


PART II -- review corrections (20260912-144500)
----------------------------------------------------------------------
Codex reviewed commit 2c6c305f and found three concrete contract/
ownership issues before treating it as integration-ready. All three
fixed here, real bugs, not stylistic disagreements:

1. OWNERSHIP SPLIT: mixa_process_close(MixaProcess *p) closed OS handles
   but never freed the struct, leaving every ordinary caller with a
   separate free(p) obligation the opaque API itself never advertised,
   and making the "idempotent double-close" claim untestable without a
   dangling-pointer risk (a second close() on a freed struct would read
   is_closed on freed memory). Fixed by changing the signature to
   mixa_process_close(MixaProcess **p): it now frees the object AND nulls
   the caller's own slot. A second close() on the same slot sees NULL and
   is a safe no-op BY CONSTRUCTION -- there is no internal flag being
   read on freed memory, because there is nothing left to read. Every
   call site (tests, and this module's own internal cleanup) updated;
   the OLD close() body survives as a private mixa_process_release()
   helper, called once from the new close() before the free.

2. SHELL DELEGATION WAS MISSING: PROCESS_SEAM's own text promises "the
   command line goes to the platform shell as one string", but spawn()
   called CreateProcessW(NULL, wcmd, ...) directly on the caller's own
   command -- the FIRST TOKEN was executed directly, never through
   cmd.exe. The original "spawn failure is distinct" test exercised
   exactly this wrong behavior (a raw nonexistent .exe path with no
   shell involved at all). Fixed: spawn() now builds "cmd.exe /c
   \"<command_line_utf8>\"" (the same effective single-argument shape
   ClearShell's own ProcessBuilder("cmd","/c",command) produces) and
   hands THAT to CreateProcessW, sized from the caller string's own real
   length via checked arithmetic (mixa_process_build_shell_cmdline, no
   fixed cap). The contract is reframed exactly as the review asked:
   MIXA_PROC_ERR_SPAWN now means the SHELL ITSELF could not start (an
   invalid working directory is the real, direct way to prove this,
   since cmd.exe is essentially always present); an unknown command is
   an ordinary STARTED child (the shell) whose own nonzero exit code and
   merged error text are observed through status()/read() like any
   other, never compressed into spawn()'s own return value. The selftest
   now proves BOTH halves of this distinction as two separate scenarios,
   and every other scenario's own command string had its manual "cmd /c"
   prefix removed (spawn() now supplies it internally -- writing it in
   the caller's command would test double shell delegation, not the real
   contract).

3. STDIN-DISABLED WAS NOT A REAL PIPE: with stdin_enabled=0, no pipe was
   created at all and STARTUPINFOW.hStdInput was left NULL -- Windows
   treats a NULL standard handle as "no redirection", not as a closed
   pipe, so a disabled-stdin child did not actually get the promised
   ordinary-EOF pipe semantics; it inherited whatever (if anything) the
   parent's own console stdin was. Fixed: a real stdin pipe is now
   created in BOTH modes -- the child always inherits a genuine pipe read
   end. When disabled, THIS side's own write end is closed immediately
   after the child is confirmed started, giving the child real
   ERROR_BROKEN_PIPE / zero-byte-EOF semantics on its own first read,
   not an ambiguous missing handle. Proven, not just asserted: the
   fixture (tests/mixa_process_fixture.c) gained a new "stdincheck" mode
   that does a raw ReadFile on its own STD_INPUT_HANDLE and reports
   exactly one of "DATA:<n>", "EOF" (ERROR_BROKEN_PIPE or a genuine
   zero-byte successful read) or "INVALID:<code>" (anything else,
   notably ERROR_INVALID_HANDLE) -- something a plain C stdio fgets()
   could never distinguish. The selftest's own new scenario 5b spawns
   this mode with stdin disabled and asserts "EOF", explicitly asserting
   the ABSENCE of "INVALID" so a regression back to the old missing-
   handle bug would be caught by name, not just by a vaguer behavioral
   symptom.

TESTING, updated and extended: tests/mixa_process_selftest.lm1 grew from
