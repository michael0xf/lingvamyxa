A real bug found and fixed in the harness itself (not in mixa_text_rect)
------------------------------------------------------------------------
The harness's own first draft declared `rect` as a raw stack array
(`[]: MixaTextRect rect 1`) and used it immediately without
initializing it. Unlike a `c.calloc`'d struct (the pattern every prior
harness in this session used), a bare stack array is NOT zero-filled:
`rect\cells` started as garbage, not NULL. The very first
`mixa_rect_open` call was then falsely refused (the real function's own
`if: rect\cells != 0: return 1` double-open guard read that garbage as
"already open"), and the harness's own SCN 2 call to `mixa_rect_release`
then called `c.free()` on that same garbage pointer -- a genuine heap
corruption (Windows STATUS_HEAP_CORRUPTION, 0xC0000374), caught
immediately by simply running the harness once before ever attempting
the L2 side or committing. Fixed with an explicit `c.memcpy`-free zero:
`c.memset(rect, 0, c.sizeof(c.MixaTextRect))` right after declaration,
documented at that exact line so it is not silently reintroduced.
