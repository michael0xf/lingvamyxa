Mixa Manager - the process seam
Third seam. Display, files, processes: three boundaries, three small surfaces.


1. Why a third seam rather than a corner of an existing one

BACKEND_SEAM is pixels out and events in. FILE_SEAM is names and bytes. Running
a program is neither: it is a child with its own lifetime, two streams and an
exit status, and it fails in ways neither of the others has - a command that does
not exist, one that never terminates, one that waits on input nobody will send.

Folding it into either would make both harder to port and would force a headless
display backend to know about processes.


2. What it is for, exactly

The first user of this is deliberately small, from the language owner:

    the console holds text. Pressing Enter takes the line from its start up to
    the CURSOR, sends it plus a newline to the OS, and the child's output
    arrives at the same place - as if the cursor itself were writing. All of it
    lands in the file.

That is ClearShell's "Run OS Command" and it is mode 0.1.2 from the old model -
delegation, not terminal hosting. There is no PTY, no terminal emulation and no
child screen. The child gets a command and a place to write.

Which settles a design question before it is asked: THE CONSOLE IS NOT A
TERMINAL. It is a text file being edited, into which a child's output is
appended. Everything a terminal implies - cursor addressing, colour escapes,
alternate screens - is out of scope until mode 0.1.1, and this seam is not the
place it will arrive.


3. Operations

    spawn      a command line, a working directory. Returns a handle, or
               reports that it could not start - which is DIFFERENT from a
               command that started and failed, and callers need to tell them
               apart

    read       drain available output into a caller's buffer. NEVER BLOCKS,
               for the same reason poll does not: the loop belongs to the
               Message, and a read that waits puts the wait inside a source
               that cannot see the Message's other work

    write      send bytes to the child's input

    status     running, or exited with a code

    kill       terminate it, and mean it - the child and its children

    close      release the handle

Six again, and not by imitation: the same lifetime shape produces the same
count. If a seventh is needed it will be because something here cannot be
expressed, and that is evidence rather than an inconvenience.


4. Rules taken from ClearShell, which has run this for years

Read out of its ProcessBuilder use rather than invented:

    STDERR IS MERGED INTO STDOUT, in arrival order. Splitting them reorders
      them, and for reading a build log the order IS the information.

    STDIN IS CLOSED unless the caller means to write. ClearShell closes it
      explicitly, with the comment that otherwise a command like `cat` waits
      forever for input nobody will send. That is a real hang, not a theoretical
      one.

    THE CHILD RUNS IN A PROCESS GROUP where the platform supports it, so that
      kill reaches its descendants. A shell that spawns a compiler must not
      leave the compiler running.

    THE WORKING DIRECTORY IS EXPLICIT, and the command may change it. ClearShell
      recovers the new one by having the script print it after the command,
      alongside the exit status.

4.1. The marker line

The child's exit status and final directory come back IN BAND, printed after the
command as a marker line carrying both, tab separated - ClearShell's approach,
and we keep it.

In band looks like a hack and is not. The console's scrollback is an ordinary
file that the user can open, search and copy; a sidecar index of command
boundaries would have to be kept in step with it, and would be wrong the moment
someone edited the file. A marker line travels with the text it describes.

It follows that the marker must be unguessable enough not to occur in real
output - ClearShell derives one per command from a counter and a high-resolution
time - and that a caller which finds no marker must treat the command as having
produced no status rather than inventing one.


5. What this seam does NOT do

No PTY, no ConPTY, no terminal emulation, no job control, no shell parsing - the
command line goes to the platform's shell as one string, and what that shell
does with it is the shell's business.

No output limits. ClearShell keeps head, line and tail limits and drops the
middle of noisy output because it holds the text in memory. Ours goes to a file,
so there is nothing to drop; see FILE_SEAM section 2.


6. Background jobs become MESSAGES, and ClearShell already has the right shape

Instruction from the language owner: shape ClearShell's threads as separate
Messages with inbox and outbox. Worth knowing why that is a first: the
translator - parser, trans, make, finalize, buildCore - is ONE root Message, so
the concurrent half of 19.29.6 has never been exercised by anything. This is the
first place two Messages exist at once, the same way mixa_manager was the first
application code in L1.

6.1. The mapping, and it is NOT one to one

I first wrote "one to one". That is wrong and the language owner said so:
ClearShell has no Messages. What carries over is the RHYTHM - where it posts per
directory, we take a turn per directory. The MECHANISM is entirely different,
and the difference is the whole cost of the port.

    each background job          a Message with its own arena
    runOnUiThread                a send to the UI Message's inbox
    the UI's drain-and-process   the pump, which already exists and is tested

A Java thread SHARES THE HEAP with the UI thread. A Message does not: it has its
own arena and nothing crosses without an explicit copy. So a posted closure and
a sent message are not the same thing wearing different clothes.

6.1.1. What that actually costs, from a real closure

FolderCalculator's post, in FSync.java:

    if (item.adapter.closed)      { sizes().remove(directory); run = false; }
    else if (!isSelect(item))     { sizes().remove(directory); run = false; }
    item.format();
    item.panel.invalidate();

That is not "post a result". It READS UI state to decide whether the job should
continue, WRITES run = false INTO THE BACKGROUND JOB to stop it, mutates a
shared table, and triggers a redraw.

Under the Message model none of it works directly. The job cannot hold a
reference to item - that is another Message's graph. The UI cannot set a flag
inside the job's arena. The shared table cannot be shared.

So the port INVERTS THE CONTROL FLOW: the job sends a RESULT, the UI decides for
itself, and if it wants the job stopped it sends a CANCEL to the job's inbox.
One shared closure becomes two messages travelling in opposite directions.

Which is why the inbox/outbox pair is needed per job in BOTH directions, not
only job to UI.

6.1.2. And it closes the loop on chunking

A job can only notice a cancel BETWEEN CHUNKS. So turn-per-chunk is not only
about not losing progress to a failed turn - it is the only place cancellation
can be observed at all. Two independent reasons for the same structure, which is
usually a sign the structure is right.

Four jobs, from clearshell_reference: FSync (copy, move, overwrite),
FolderCalculator (directory sizes), FileNameFinder (search by name), and command
execution.

6.2. Two rules from the spec that a file manager must not get wrong

19.29.14: a FAILED TURN DISCARDS ITS STAGED OUTBOX. So a long job must publish
per turn rather than accumulate - computing a whole tree in one turn and staging
every result means a failure at the end discards all of them. That is
structural, not a performance choice.

CHECKED, AND CLEARSHELL ALREADY CHUNKS THIS WAY. FolderCalculator posts inside
its loop, one directory at a time, not at the end. So the GRANULARITY carries
over and we do not have to invent it - but only the granularity, see 6.1. The answer was in the source and
I derived it from the spec instead - the same answer, but PORT_OF_CLEARSHELL
section 4 says to look at the source first for a reason.

19.29.14 again: "Outbox rollback does not roll back previously published
own-field or explicit graph mutations." A FAILED COPY LEAVES FILES COPIED - they
cannot be uncopied - so the protocol must report WHAT WAS DONE rather than
present the operation as all or nothing. For a manager that is not a detail:
"the copy failed" without "900 of 1000 arrived" is the difference between a
recoverable situation and a mess.

6.3. Message shape, already decided elsewhere

19.31.4: "the semantic result/failure is an ordinary LMX Message with
correlation equal to the request id". So request/reply correlation is settled
and does not need inventing.

6.4. What still needs agreement

19.29.7 leaves the cross-Message operation set unresolved. Proposed to Codex and
awaiting his view: COPY ONLY, of numbers and UTF-8 byte strings, which covers
all four jobs - a size is a number, a search hit is a path, progress is a count
and a path, output is bytes. None hands over a graph. Join, activation,
adoption and graph-reference retargeting stay deferred, which is exactly the
part 19.29.7 calls unresolved.
