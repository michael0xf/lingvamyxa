==============================
Ticket 20260912-090426 laid out the preparation (section 1-5 below,
kept as written); ticket 20260912-092435 authorized and delivered the
first bounded implementation, in mixa_copy.h.lm1 / mixa_copy.lm1 /

PART A -- preparation (20260912-090426), unchanged from the original
----------------------------------------------------------------------

Reference read: clearshell_reference/com/mtk/shell/FSync.java, classes
CopyAction (956-1123), OverwriteAction (1126-1150), MoveAction (1151-),
MoveOverwriteAction (1193-), plus cc2 (686-717) which queues the roots.


1. How the reference actually copies
-------------------------------------
It does NOT pre-walk the selection. cc2 queues ONE action per effective
top root (the "isSelect2(src) == null" filter already ported in
mixa_selection_walk), and each action expands as it RUNS:

  CopyAction.run:
    source missing            -> sourceNotFound, throws
    source unreadable         -> sourceNotRead, throws
    source is a directory     -> copyFolder, returns
    dest exists && !overwrite -> destinationAlreadyExists, throws
    otherwise                 -> stream copy, then complete(source)

  CopyAction.copyFolder:
    create dest (or, when overwriting a non-directory, delete and
      mkdir), recording it in the newFiles map
    for each child: if not in newFiles, make newDest and queue a child
      action through newAction()
    complete(source)

  CopyAction.newAction(src, dst):
    if src is NOT an exception -> queue a child action, return true
    else                       -> removeException(src), skip it

So exceptions are consulted at EXPANSION time, and consuming an
exception removes it. Overwrite differs only in isOverwrite() and in
queueing OverwriteActions for children.

Buffer: 64KB (0xffff), or the file's own length when smaller.


2. Two hazards found in the reference that the port must carry
---------------------------------------------------------------
(a) DESTINATION INSIDE SOURCE. The newFiles map is not bookkeeping -- it
    is a loop guard. copyFolder records every destination directory it
    creates, and the child loop skips any source entry that is itself
    one of those destinations (line 1096). Without it, copying a
    directory into a subdirectory of itself descends forever and fills
    the disk. The walk shipped in mixa_selection_walk has NO such guard,
    because it only reads; a copy built on it must add one. This is the
    single most important thing the implementation stage owes.

(b) SELECTION DRAINS AS THE COPY PROCEEDS. complete() calls
    removeSelect2 on each finished source, so a half-finished copy
    leaves exactly the unfinished part still selected. That is a real
    behaviour to preserve, not an incidental detail: it is what makes a
    retry after a failure copy only what did not get copied. It also
    means the copy MUTATES the selection while walking it -- the same
    class of hazard review 20260912-090426 raised about the root scan,
    and the reason the walk now snapshots before querying.


3. How this lands on what is already built
--------------------------------------------
mixa_selection_walk already provides: effective top roots by the
reference's own filter, lazy descent in the seam's observed order,
excluded subtrees skipped, lower explicit selections inside an excluded
subtree still reached, each effective path visited once, ordered
dir-enter / file / dir-complete callbacks with cancellation and verbatim
error propagation, and exact cleanup on every exit.

That is a good fit for a copy: on_dir_enter creates the destination
directory, on_file copies one file, on_dir_done marks a destination
complete. The differences from the reference to decide explicitly:

  - the reference expands a work queue and can be paused/resumed
    between items; the walk is a single recursive pass. For the first
    bounded copy stage a single pass is enough, and cancellation is
    already supported. A resumable queue is a later question, not a
    silent omission.
  - the reference removes an exception when it skips a child; the walk
    only reads the selection. Draining behaviour (2b) therefore has to
    live in the copy layer, not be bolted into the walk.
  - the walk deliberately does not mutate the selection. If the copy
    drains selection as it goes, it must do so without invalidating the
    walk underneath it -- easiest if the copy records what completed and
    applies the deselections AFTER the pass, or if it drives its own
    queue from the walk's root list rather than from inside callbacks.
    This needs deciding before code is written.

4. What the implementation stage still needs decided
------------------------------------------------------
1. Where destination paths are formed and bounded (the walk hands out
   absolute source paths; a copy needs source-root-relative suffixes to
   rebuild under the destination).
2. The loop guard of (a): recorded destinations, or a cheaper prefix
   test of "is this entry inside the destination root".
3. Whether the first stage is copy-only, or copy plus overwrite. The
   reference's overwrite differs in two lines, but the failure surface
   (deleting an existing non-directory to make a directory) is much
   larger and is where real data loss would come from.
4. Drain-the-selection timing, per (2b) and section 3.
5. The I/O seam. There is no accepted file read/write seam in tracked
   mixa_manager -- mixa_dir covers directories only, and the untracked
   legacy mixa_file* is explicitly out of bounds. A copy needs one, and
   proposing it is part of the next stage rather than something to
   invent quietly here.

Item 5 is the real blocker for implementation and is reported as such;
everything else above is a decision I can take with the reference in
hand once the seam question is settled.


5. Testing posture for the implementation stage
-------------------------------------------------
Mutations only in owned fixtures, per the ticket. Every case the
reference distinguishes is reachable with real files under a run
directory: missing source, unreadable source, destination exists with
and without overwrite, directory into a fresh destination, destination
nested inside the source (the loop guard), an excluded child skipped, a
lower explicit selection inside an excluded subtree still copied, and
cancellation part-way leaving exactly the unfinished remainder selected.
No user files, and no writing outside the fixture root -- which for a
copy means the destination root itself must be asserted to be inside the
fixture tree before a single byte is written.


PART B -- what was built (20260912-092435)
--------------------------------------------

1. mixa_fileio: the file-content seam
Tracked, separate name (mixa_fileio_win32.h.lm1 / .lm1 wired through a
portable mixa_fileio.h.lm1), following mixa_dir's own split exactly.
Does not touch or promote the untracked legacy mixa_file*.

Scoped to what copy-only needs: mixa_fio_open_read, mixa_fio_open_
write_new (CREATE_NEW only -- an existing destination is refused by
Windows itself, ERROR_FILE_EXISTS, not a redundant check), mixa_fio_
read, mixa_fio_write, mixa_fio_close.

Deterministic fault seam: read/write take an optional MixaFioFaultVTable
whose hook is asked, with the real byte offset moved so far, before the
real ReadFile/WriteFile call; a refusal fails that call with no real I/O
attempted for it, while everything moved before the hook fires stays
real on disk. An explicit per-call argument, not a module global -- the
mistake already fixed once this session in mixa_share_win32.lm1.

Evidence: 24 checks, 0 failures, two hash-identical runs. Confirmed
load-bearing by breaking the CREATE_NEW flag and by bypassing the fault
check on each of read and write in turn.

2. mixa_copy: the first bounded copy stage
Copy-only, no overwrite. Drives mixa_selection_walk over the accepted
MixaSelection, computing each destination path by substituting the
walk's own effective-root prefix for dest_root and rebuilding the rest
under it (a small owned stack of destination-directory paths, pushed on
dir-enter and popped on dir-done, bounded at MIXA_COPY_MAX_DEPTH=256 as
a defensive-only ceiling -- real recursion depth is limited by the C
stack of the walk it drives long before that could fill).

A destination DIRECTORY that already exists is not an error: it is
merged into, exactly matching the reference's own copyFolder (dest.
exists() && dest.isDirectory() proceeds silently). Only a destination
FILE that already exists is refused, since this stage is explicitly
without overwrite.

Events and cancellation reuse mixa_selection_walk's own GO/STOP/
verbatim-failure protocol directly rather than inventing a second one.
MixaCopySink's own status codes are deliberately rebased to start at 100
(MIXA_COPY_ERR_ARG=101 and up) so they can never collide with
MIXA_SEL_WALK_ERR_*'s own small range (0-7): mixa_copy_run does not try
to guess which domain a returned non-OK/non-CANCELLED value came from,
and does not need to, because the two ranges are structurally disjoint.
OK (0) and CANCELLED (7) are shared rather than rebased, since both
domains already agree on what they mean.

Per-item failure vs structural failure, a real asymmetry worth stating
plainly: an ordinary FILE conflict (ERR_EXISTS on open_write_new, a
real I/O failure) is reported to the sink and then the SINK decides
whether the whole copy continues (GO) or stops -- exactly mirroring the
reference's own per-action independence, where one file's conflict does
not stop its siblings. A DIRECTORY-level STRUCTURAL failure --
destination-inside-source, a directory that cannot be created or exists
as a non-directory, the path-length bound -- always stops descent into
that directory regardless of what the sink returns; the sink still
observes the exact failure, but cannot override it. This was a real bug
in the first draft (see section 3) and is now enforced unconditionally
in mixa_copy_on_dir_enter, not left to caller discretion, because it is
a safety property (bounding descent), not a UX choice.

Selection draining, the decision flagged as open in Part A section 3:
a fully-completed effective ROOT (not every nested entry) is deselected
the moment its own subtree finishes with no failure anywhere in it,
tracked with a single root_had_failure flag set the instant any
structural or per-item failure is reported inside the current root and
reset when a new root begins. A root that fails partway, or is
cancelled, stays selected, so re-running mixa_copy_run against the same
selection and destination naturally retries only what did not finish --
confirmed directly (scenario 4: cancel on the 2nd event, retry
completes the remainder, the root is then deselected).

Destination-inside-source (Part A hazard (a)): checked once, up front,
per effective root -- the destination is refused if it equals the
root's own source path or is a real descendant of it (a same-prefix
sibling like "dest1x" against "dest1" is correctly NOT treated as
nested). This is a genuine behavioural divergence from the reference,
which instead lets the whole tree start copying and silently skips
children that happen to already be one of the just-created destination
directories (its newFiles map). The upfront refusal here is stricter --
it terminates that root's attempt entirely rather than copying around
the problem -- which is why the ticket's own wording ("destination-
inside-source termination") is honoured literally rather than the
reference's own continue-around-it behaviour. Chosen because it is
simpler, provably safe, and does not need the reference's per-child
bookkeeping; recorded here as a deliberate choice, not a silent one.

3. Two real bugs the selftest caught while being built, both confirmed
load-bearing by reverting and re-running
--------------------------------------------------------------------
(a) The structural-vs-per-item asymmetry above was NOT enforced in the
    first draft: mixa_copy_on_dir_enter reported a nested-destination
    refusal to the sink but then returned whatever the sink chose,
    exactly like an ordinary per-item failure. Since this selftest's own
    sink continues past reported failures by design (matching the
    reference's per-action independence for ordinary conflicts), the
    walk kept descending into the directory that had JUST been refused,
    computing further destinations off a stack that was never pushed for
    it (falling back to dest_root itself) and copying real files to the
    wrong place while still reporting overall success. Reverting the
    fix reproduced exactly this: files copied under the destination
    root directly, aggregate status OK, despite the directory-level
    refusal.
(b) A test-fixture bug, not a module bug, exposed a real property of the
    accepted selection model worth recording here since it will recur:
    selecting a child of an already-selected ancestor is a no-op
    (SELECTION_MODEL.txt section 3.1), so a test scenario that leaves an
    ancestor selected from an earlier failure and then tries to select
    one of its children in isolation silently does nothing -- and a
    later deselect() of that same "child" then RECORDS AN EXCEPTION
    against the still-selected ancestor instead of being a no-op,
    quietly narrowing what the ancestor's own selection covers. Fixed by
    giving scenarios that need an isolated root their own clean
    selection state rather than accumulating stale selections across
    scenarios. Confirmed load-bearing the same way: removing the
    isolation reproduced the exact conflict-then-silent-exclusion chain.

4. Evidence
run_copy_selftest.ps1 -- 40 checks, 0 failures, two hash-identical runs.
Content equality across a real multi-level tree; existing-destination
preservation (every conflicting file refused, nothing on disk
disturbed); an existing destination directory merged into while a
conflicting file inside it is still refused and a new file beside it is
still created; cancellation on a specific event followed by a full
retry that completes exactly the remainder and only then deselects the
root; a real I/O failure via the fault hook leaving no partial file
behind, the source still selected, and a clean retry afterward;
nested-destination termination both for a strict descendant destination
and for a destination equal to the source itself, with no directory
created and nothing copied; a prefix-sharing sibling destination
("dest1x" against "dest1") correctly NOT treated as nested; and
argument negatives including a trivially-successful empty selection.

Regressions unaffected: fileio 24/0, selection_walk 100/0,
file_manager 144/0.

Both fixed modules build and test under stable65D5 (no candidate
compiler needed): mixa_fileio, mixa_selection_walk and mixa_copy
together reach 11 distinct predef'd files against the accepted
translator's own 16-import table, comfortably inside it.

5. Limitations, stated plainly
1. Copy only. No move, no overwrite, no rename, no delete -- matching
   the ticket's own explicit scope for this stage.
2. Retry re-walks the WHOLE remaining selection from scratch each time;
   there is no persisted partial-progress record beyond what the
   selection model itself already tracks (which roots are still
   selected). For this stage's own size that is adequate; a large
   in-progress tree would re-verify already-copied entries on every
   retry via the ordinary already-exists refusal rather than skipping
   them outright.
3. MIXA_COPY_MAX_DEPTH (256) is defensive-only, per the note above --
   real recursion depth is bounded by the walk's own C stack usage
   first, matching the equivalent limitation already accepted for
   mixa_selection_walk.
4. No live Message pump; no user files touched by any test.


PART C -- wired into the file-manager view (20260912-121231)
----------------------------------------------------------------
mixa_fm_copy.h.lm1 / mixa_fm_copy.lm1 / tests/mixa_fm_copy_selftest.lm1
/ run_fm_copy_selftest.ps1. One function, mixa_fm_copy_selection(fm,
dest_root_utf8, sink, fv): calls mixa_copy_run(fm\sel, dest_root_utf8,
sink, fv) directly -- no traversal or file I/O of its own -- then calls
mixa_fm_refresh(fm) ONLY when dest_root_utf8 equals mixa_fm_cur_dir(fm),
since copy is the only thing that can have changed what the currently-
viewed directory shows (a copy never touches a source directory's own
listing) and refreshing anything else would be a wasted, meaningless
re-scan. Matches the reference directly: FSync.copy(fileAdapter) reads
fileAdapter.getStorageList().getCurrentDir() as the destination, and a
completed action's invalidate(path) calls item.adapter.refresh() for
whichever adapter is showing that path.

fm\sel is read directly as a struct field (already public in
mixa_file_manager.h.lm1, the same way callers throughout this codebase
already read other modules' struct fields directly) -- no new accessor
needed. Every copy contract already tested in mixa_copy stays exactly as
it was, because this module adds no logic to the copy path itself: it
only decides WHEN to refresh afterward.

No destination-picker UI exists in the accepted Win32 surface, so this
stops at the headless action boundary the ticket asked for -- a real UI
trigger can call mixa_fm_copy_selection directly once one exists, the
same way mixa_mp3_hit already calls into mixa_mp3_open_dir. Inventing a
folder-picker dialog to close this ticket was out of scope and was not
done.

Evidence: 45 checks, 0 failures, two hash-identical runs. Every scenario
drives selection through real mixa_fm_select calls on indices from a
real mixa_fm listing (not bare paths), and navigates the view with real
mixa_fm_enter/mixa_fm_goto_root calls, matching how this would actually
be triggered. Covered: a selected file and a selected directory copied
together while viewing the destination, with the completion refresh
showing both new entries without a manual refresh call from the test;
cancellation on a directory's own first event (genuinely mid-subtree,
not an already-atomic single-file completion) leaving that root
selected and the unrelated current view undisturbed, then a retry that
completes it and drains the selection; an injected mid-file I/O failure
on a fixture never touched before that scenario (so the fault hook is
genuinely reached rather than short-circuited by an unrelated existing-
file conflict), leaving the source selected, the partial destination
file cleaned up, and the view still usable, then a clean retry; an
existing-file conflict surfacing the exact ERR_EXISTS status while
viewing the destination, with its content undisturbed and the view
correctly showing the (unrefreshed-but-still-valid) listing; nested-
destination refusal leaving the view and selection untouched; and
argument negatives.

Confirmed load-bearing by breaking the one piece of real logic this
module adds: removing the conditional mixa_fm_refresh call failed the
same-directory-copy scenario exactly as expected (the newly copied
entries did not appear in the listing).

Two test-authoring bugs surfaced and fixed while building this suite,
both about VIEW NAVIGATION state carried across scenarios rather than
anything in the module under test -- worth recording since the same
class of mistake bit mixa_copy.lm1's own tests earlier (stale
SELECTION state there; stale VIEW-NAVIGATION state here):
  - a scenario that looked up an entry by name after an earlier scenario
    had navigated the view into a different directory silently resolved
    to the WRONG entry (same basename, different real path) in that
    other directory, corrupting the selection with an unintended second
    root.
  - a fault-injection scenario reused a fixture file already copied to
    the same destination by an earlier scenario, so the real
    existing-file conflict fired before the fault hook was ever reached,
    making the "I/O failure" assertion untestable. Fixed with a fixture
    file dedicated to that one scenario.
Every scenario now explicitly returns the view to a known directory
(mixa_fm_goto_root) before looking up the next gesture's target by name.

Regressions unaffected: file_manager 144/0, selection_walk 100/0,
fileio 24/0, copy 40/0.

Remaining real integration gap, stated plainly: there is still no
accepted Win32 destination-picker gesture (a folder-browse dialog, a
paste-into-current-view button) wired to mixa_fm_copy_selection. The
action boundary is real, tested and ready to be called; nothing decides
WHEN a user triggers it yet. That UI work is out of this stage's scope
by the ticket's own instruction and is the next real boundary once
someone picks a destination-selection gesture to accept.


PART D -- Copy Here trigger through the existing controller/button
convention (20260912-122500)
----------------------------------------------------------------------
Closes the exact gap Part C named. MixaFmCopyHereCtx / mixa_fm_copy_
here_action / mixa_fm_copy_here_hit -- added directly into the ALREADY-
ACCEPTED mixa_fm_copy.h.lm1/.lm1 rather than as separate files, and that
choice was measured, not stylistic: l1trans's import path table holds
exactly 16 imports, mixa_fm_copy's own existing chain already reaches
15, and a probe with a genuinely separate pair of new files (mixa_fm_
copy_here.h.lm1/.lm1) overflowed at exactly 17. Extending the module
that is already in the chain costs zero additional files.

The action follows mixa_share_button.h.lm1's own established
MixaButtonActionFn adapter shape exactly -- (@: void ctx) int, result
surfaced back through the ctx struct's own fields -- the same pattern
mixa_share_send_button_action already uses. Destination is always
mixa_fm_cur_dir(fm), matching FSync.copy's own "Paste selected" gesture
(fileAdapter.getStorageList().getCurrentDir()).

NOT wired through mixa_button_dispatch_hit or mixa_buttons' MixaButton
Panel/mixa_button_panel_hit: both measurably overflow the same table in
this combination, reproduced directly with two 7-line probes (mixa_fm_
copy.h.lm1's own comment carries the exact reproducer text). Even the
narrower manual-dispatch PRIMITIVE (mixa_button_panel_hit's own
dependency, mixa_buttons+mixa_tiles+mixa_text_rect) is unaffordable here
-- one level past what forced MP3 stage 3's own manual-dispatch
substitution, since there even that substitute's own dependency was
still in budget. mixa_fm_copy_here_hit is therefore a small, dependency-
free rectangle hit-test (explicit row/col bounds, no MixaButtonPanel)
standing in for the accepted primitive for exactly this reason -- not a
claim of being it, and not a modal framework.

PATH LIFETIME (the ticket's own requirement 3), proven, not asserted:
mixa_fm_copy_here_action takes an owned copy of mixa_fm_cur_dir(fm)
before calling mixa_fm_copy_selection and frees it after. The borrowed
pointer is genuinely unsafe to pass through directly -- mixa_fm_copy_
selection's own completion refresh, on the match this scenario always
produces since the destination IS the current directory, frees and
reallocates fm's own cur_dir through mixa_fm_refresh.

Proof method: a poisoning MixaFmAllocVTable (already-accepted injection
seam) whose free() overwrites a buffer's own content before releasing
it, so a use-after-free read is directly observable as corrupted
content rather than relying on the allocator happening to reuse the
same address. The selftest's own dedicated scenario takes the borrowed
mixa_fm_cur_dir(fm) pointer, calls mixa_fm_copy_selection with it
DIRECTLY (bypassing the safe action on purpose), and shows the pointer's
content really does change to corrupted/reused bytes after the call
returns. Confirmed the real action's own owned-copy fix matters the same
way it was verified elsewhere this session: reverted it to use the
borrowed pointer and re-ran the full functional suite under the
poisoning allocator -- it stayed green. That is itself a real, honestly-
reported finding: nothing downstream in mixa_fm_copy_here_action's own
call chain re-reads the pointer after mixa_fm_copy_selection returns, so
the corruption has no OBSERVABLE effect in this specific call graph.
The bug is still real undefined behaviour regardless -- exactly the same
"the fix stands on its own merits even when today's code doesn't
visibly trip on it" reasoning already used for the walk's root-scan fix
in the 090426 review -- and a caller who stores mixa_fm_cur_dir(fm) for
any later reuse (logging, a second action, anything) would hit it for
real. The owned copy is restored and is what ships.

Empty selection is explicit and distinct (MIXA_COPY_HERE_NOTHING_
SELECTED, 200 -- chosen well clear of both the walk's 0-7 range and
mixa_copy's own rebased 100+ range) rather than silently no-op'd or
folded into an existing error code, satisfying the ticket's own "must be
explicit and tested" requirement; it touches neither the filesystem nor
fm's own view.

Evidence: 41 checks, 0 failures, two hash-identical runs. A real hit
inside the button's own bounds triggers Copy Here into the current
directory with a selected file AND a selected directory, real fixture
content, using the SAME poisoning allocator throughout (not just in the
dedicated probe) so a regression in the real path would also be caught
functionally. Covered: a miss outside the button bounds invoking nothing;
a real hit copying both selections with content verified and the
completion refresh showing both new entries; the empty-selection no-op;
existing-file conflict surfacing the exact status with the view left
usable; cancellation on a directory's own first event (genuinely
mid-subtree) leaving that root selected, then a retry that drains it;
an injected I/O failure on a fixture untouched by any earlier scenario
(so the fault hook is genuinely reached), leaving the source selected,
the partial file cleaned up, the view usable, then a clean retry;
argument negatives.

Two more fixture-reuse bugs found and fixed while building this suite,
same class as Part C's own findings, worth naming precisely since a
THIRD instance of it appearing is a pattern, not a coincidence: the
path-lifetime probe scenario (which does a REAL copy as a side effect of
proving the hazard) was originally sharing the same destination
directory as the later functional scenarios, so its own real copy of
top.txt silently pre-empted a later scenario's fresh-copy assumption
with a real EXISTS conflict; and the cancel/retry scenario reused a
directory (srcdir) an EARLIER scenario had already fully copied into the
SAME destination, so its own "retry" hit real conflicts for the content
underneath rather than completing cleanly. Both fixed by giving the
probe and the cancel/retry scenario their own dedicated, previously-
untouched destination directories. Pattern for future stages: any
scenario that performs a REAL copy as a side effect (including ones
whose primary point is proving something else, like the poisoning
probe) needs its own destination, not a shared one, or it will silently
poison a LATER scenario's fixture assumptions.

Regressions unaffected: fm_copy (original suite) 45/0, file_manager
144/0, selection_walk 100/0, fileio 24/0, copy 40/0, share_button 20/0
(the closest existing precedent for this same action-adapter shape).

Remaining real gap, stated plainly: mixa_fm_copy_here_hit's own
rectangle bounds are supplied by the CALLER (no real top-level button
registry entry exists for "Copy Here" in the accepted Win32 app surface
yet, since none of app_window/buttons/tiles/text_rect are reachable
alongside this module's own dependency weight). The action and its
hit-test are both real and callable the moment a real button geometry
and a real trigger point (a paste keystroke, a context-menu entry) are
accepted; deciding that geometry is UI work, not something this ticket
asked for or that was done here.
