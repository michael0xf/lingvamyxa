Barrier (current main) -- TWO distinct diagnostics found and reported
-----------------------------------------------------------------------
In FILE ORDER (the committed .lm2, unmodified, matching the real
oracle's own function order exactly):

  l2trans error: mixa_manager\mixa_app_controller.lm2:4:1: unknown
  foreign type

Line 4 is `fn: main_alloc (size_t: n) @: void` -- a NEW barrier
variant never hit by any prior module this segment: a bare `@: void`
(void-pointer) RETURN TYPE, not a custom struct at all. Isolated via a
dedicated minimal .lm2 fixture (`fn: zz_probe_alloc (size_t: n) @:
void` / `return: c.malloc(n)`, no predef of anything) -- reproduces the
IDENTICAL diagnostic with zero custom-struct involvement, confirming
the trigger is the bare void-pointer return itself, not anything in
the predef chain. main_alloc's own signature cannot be changed to dodge
this: it must match MixaFmAllocFn's real fnptr contract exactly
(`fnptr: MixaFmAllocFn (size_t: n) @: void` in mixa_file_manager.h.
lm1), so this diagnostic is reported as-is rather than worked around.

Continuing independent of that barrier (per this ticket's own
instruction), a scratch reorder moving main_alloc/main_free to the end
of the file (diagnostic purposes only -- NOT applied to the committed
.lm2, which keeps the real oracle's own exact function order) surfaces
the SAME already-familiar closed-type-allowlist barrier every prior
module this segment hit, at the module's own first custom-struct

  l2trans error: .../mixa_app_controller.lm2 (reordered):5:32: unknown
  foreign type

on `mixa_app_controller_close`'s own `@: MixaAppController c`
parameter.

Both diagnostics confirmed identically across TWO separate runs of the

What would unblock the L2 side
--------------------------------
Two gaps, both in l2trans's current type checker: (1) a bare void-
pointer return type is refused outright (a NEW, narrower finding this
ticket contributes -- no prior module's own first function happened to
return `@: void`); (2) the already-reported closed foreign-type
allowlist gap refusing any custom struct type in a `@:`/const: @(...)
position. Landing the core integration already in progress on origin/
codex/core-integration onto main would be expected to clear both
without further changes to this module's own L2 header or .lm2 body.
