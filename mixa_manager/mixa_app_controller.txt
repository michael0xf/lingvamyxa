mixa_app_controller -- reusable app-controller seam and its E2E headless proof
================================================================================
(ticket 20260913-010249, FIRST_VERSION.txt end-to-end wiring requirement)

What this closes
-----------------
mixa_app_main.lm1's own event/edit/Enter/process-poll/F1/render orchestration
(built up across the prior three tickets: Copy Here, F1 Help, editable command
line + Enter dispatch, pending-line rendering) had never once been executed by
any automated suite -- it was build-link-only. The ticket names this exact
risk directly: "mixa_app_main wiring is only build-linked." This work extracts
that orchestration into a reusable seam so the SAME production logic can run
headless under test, then proves it end to end -- and in doing so found a real
production defect that had been silently breaking every Help/Enter-echo/
command-output write since the feature was first wired two tickets ago (see
"The production bug" below).

The extraction: mixa_app_controller.h/_impl.h/.lm1
----------------------------------------------------
Every stage that used to live directly inside mixa_app_main's own main() --
resource setup, the per-tick event/edit/dispatch/render body, and teardown --
moves unchanged into MixaAppController's open()/step()/running()/close() seam.
step() performs exactly ONE tick and never loops internally; this is what lets
the identical step() implementation serve a real window's own Win32 message
pump (driven by main()'s own while loop) and a synthetic, test-injected event
stream (driven by an E2E test's own loop) with zero branching on which backend
is active anywhere in the seam itself. mixa_app_main.lm1 is now a thin owner:
it resolves the backend table, opens the controller, loops step() while
running() and no error was reported, and closes it -- nothing else.

Same opaque-handle split already established for mixa_file.h/mixa_file_win32.h
and mixa_cmdline_dispatch.h/_impl.h: mixa_app_controller.h is a plain C header
with an opaque typedef, reached via include:, so mixa_app_main.lm1 itself
needs no predef at all. The concrete struct lives in mixa_app_controller_
impl.h, included only by mixa_app_controller.lm1, using struct-tag-only
forward decls (struct MixaAppLoop *, struct MixaConsoleView *, struct
MixaConsolePending *, struct MixaFmAllocVTable *) for every L1-typed field --
the same mechanism mixa_cmdline_dispatch_impl.h already established for
MixaProcessMarkerScanner. A first attempt at putting the concrete struct
directly inside mixa_app_controller.lm1 via struct: ... end: hit "unsupported
L1 form" (local struct: blocks are only valid inside .h.lm1 files); moving it
into a plain hand-written header fixed it immediately.

By moving mixa_fm_copy.h.lm1/.lm1 and mixa_console_window.h.lm1's own predef
weight OUT of mixa_app_main.lm1 and into this new, separate translation unit,
mixa_app_controller.lm1 gets its OWN fresh 16-file import budget, and
mixa_app_main.lm1 itself no longer needs any predef -- resolving the same
"import path table full" ceiling this project has hit and worked around
several times before, without inventing a new mechanism.

The production bug
-------------------
Live, while building the E2E test's Enter-dispatch scenario: mixa_cmd_
dispatch_start reported success (rc=0) but the fixture console file stayed
0 bytes on disk. A temporary debug printf around the dispatch_start call
confirmed the return code was really 0 -- the failure was happening silently
one level deeper.

Root cause: mixa_app_controller_open's own Stage 5 opened the console file
briefly in APPEND mode (only to guarantee it exists), closed it, then
reopened it in READ mode -- and kept that single READ-mode handle assigned to
BOTH help_ctx\console_file (F1 Help's own write target) AND the console_file
argument passed to mixa_cmd_dispatch_start (Enter dispatch's own write
target, and the target its internal marker-scanner sink appends real command
output to). mixa_file_append's own accepted contract (mixa_file_win32.lm1)
explicitly rejects any append attempt on a non-APPEND-mode handle with
MIXA_FILE_ERR_ARG before writing a single byte -- so EVERY Help write, every
Enter-echoed command line, and every byte of real command output had been
silently failing in the real production wiring since the day each feature was
first wired in. This was invisible until now because mixa_help_selftest.lm1
and mixa_cmdline_dispatch_selftest.lm1 each open their OWN independent
APPEND-mode test file directly -- neither ever exercised the real controller's
own cross-wiring, and mixa_app_main.lm1 itself had never been executed by any
automated suite before this ticket's own E2E test. This is exactly the class
of defect the ticket's own opening sentence predicted an E2E proof would
catch.

Fix: a second, persistent APPEND-mode handle, console_file_append, opened in
Stage 5 alongside the existing READ-mode handle (closed alongside it in
mixa_app_controller_close). help_ctx\console_file and the mixa_cmd_dispatch_
start call now both use console_file_append; the original READ-mode handle
stays dedicated to the view's own rendering pass, which only ever reads.

The E2E proof: tests/mixa_app_controller_e2e_selftest.lm1
------------------------------------------------------------
include:-only (no predef at all) against mixa_app_controller.h, mixa_backend_
headless.h, mixa_file.h -- reaches everything through plain C headers, so it
needs no import-table budget of its own. Runs as a separate multi-object link
via the new run_app_controller_e2e_selftest.ps1 (mirroring run_app_loop_
selftest.ps1's own header-translation/object-compile pattern, since predef-ing
mixa_app_controller.lm1 + mixa_process_marker.lm1 + mixa_process_win32.lm1
together in ONE translation unit was measured to overflow the import table --
predef costs sum within a single file even when each is individually
affordable elsewhere).

Covers, using mixa_headless_push_event to inject synthetic keyboard/mouse
events with no live window at any point:
  - argument negatives: open(0, vt, root) and open(&c, 0, root) both report
    MIXA_APP_CONTROLLER_ERR_ARG.
  - initial state: an empty file, cursor at (0,0), file_size 0.
  - typing "echo e2e-hist" one character at a time, verifying the pending
    line and cursor render correctly in the TEXT layer, including a real
    Cyrillic codepoint typed and then backspaced.
  - Enter: the exact command bytes are echoed and the child spawns.
  - F1 Help pressed and a further keystroke typed WHILE the command is still
    running, reaching the text_rect check at all being the responsiveness
    proof itself (step() never blocks on the running child).
  - a bounded drain loop (cap 500 ticks / 10ms poll) draining real command
    output into the file/view.
  - completion: last_exit_code is 0, cwd is non-null, the real output
    ("e2e-hist") is present in the file, and no completion marker text ever
    leaked into it.
  - final render: history plus a new pending line together (see "A test-side
    understanding fixed" below).
  - a second controller opened, a real ~30-second command started
    (ping -n 30 127.0.0.1), and close() called on it while still running --
    verified to return promptly rather than hang, proving kill-and-mean-it
    through the full controller stack, not just the underlying process seam.

A test-side understanding fixed
----------------------------------
The final-render assertion first assumed mixa_app_controller_cursor_row/col()
report the pending line's OWN post-content cursor (one past its last
character). A debug scan across the rendered rect proved the pending
character actually lands AT the getter-reported (row, col), not one before
it: these getters simply return the console view's own cursor_row/col, which
represent the FILE's own end-of-committed-content position -- i.e. exactly
where render() begins drawing pending content from -- not any pending-
adjusted value (that adjusted position is computed internally inside
mixa_console_view_render and is never exposed to any caller). The assertion
was corrected to check for the pending character directly at (pend_row,
pend_col); no product code changed for this one -- it was a test-authoring
mistake, not a bug.

Is FIRST_VERSION 0.1.2 runnable-feature complete?
-----------------------------------------------------
Every FIRST_VERSION.txt feature item now has BOTH a focused unit-level proof
AND, as of this ticket, a real end-to-end proof that the SAME production
wiring (not a parallel test-only copy) performs: empty-file startup, by-
character typed editing with pending-line/cursor rendering, Enter echoing
exact bytes and spawning a real child, UI/F1 responsiveness while a command
runs, real output draining into the file/view, marker-hiding with cwd/status
recovery, and a final render showing history plus a new pending line
together. Cleanup/failure injection (argument negatives, kill-a-running-
command-on-close) is covered through the existing seams' own established
mechanisms, and no fixed capacity limit was introduced anywhere in this
change.

The one item this ticket does NOT close: mixa_app_main.lm1's real Win32
entrypoint itself is still never executed by any automated suite (only
built/linked) -- the E2E proof exercises the identical orchestration logic
through the headless backend, by design, but a live window has still never
been driven end to end. Whether that gap disqualifies "runnable-feature
complete" is Codex's own call to make, not mine; it is named here exactly
because this ticket's own premise is that untested wiring hides real bugs,
and one real bug (above) was found this way -- the same risk plausibly still
applies to the Win32-specific message-pump path that this ticket did not
touch.
