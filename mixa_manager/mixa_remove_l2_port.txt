mixa_remove L2 port (ticket 20260913-171800)
===============================================

Scope
-----
Clean-L2 port of mixa_remove, the recursive remove-selected operation
(porting FSync.java's del()/DelAction/removeSelect2) -- the direct
dependency mixa_fm_remove (already ported, ticket 20260913-161000)
wires to the file-manager view. Together the two give the whole remove
path a clean-L2 source. 6 functions, 126-line real body.

-------------------------

    L2 ABI header. Predefs the REAL, unmodified mixa_remove.h.lm1
    directly -- mirrors the real oracle's own single predef line
    exactly (same pattern as mixa_fm_remove_l2.h.lm1 this segment).
    Gives real MixaRemoveSink/MixaRemoveState and, transitively via
    mixa_remove.h.lm1's own predef of mixa_selection_walk.h.lm1 (itself

    predef'd files: mixa_remove.h.lm1, mixa_selection_walk.h.lm1,
    mixa_dir.h.lm1 -- 3, nowhere near the 16-file import-table cap.

    The real 126-line body copied unchanged, all 6 functions preserved

- mixa_manager/tests/mixa_remove_parity_harness.lm1
    Real L1-vs-L2 harness (one source, compiled/linked twice), all 9
    scenarios drawn directly from the existing, already-accepted mixa_
    remove_selftest.lm1: a real nested tree with strict postorder

A new barrier trigger shape, precisely isolated
---------------------------------------------------
l2trans error: mixa_manager\mixa_remove.lm2:15:25: incompatible entry
signature

Line 15 is mixa_remove_invoke's own first parameter (`MixaRemoveNodeFn:
f`) -- a bare fnptr-TYPEDEF parameter, NOT a custom struct at all. This
is the module's own first real custom-named type in file order (the
module's very first function, mixa_remove_map_dir_status, uses only
plain int and never triggers anything), and it fires under "incompatible
entry signature" rather than the more common "unknown foreign type"
diagnostic every other module's own first-custom-struct-parameter case
produces. A distinct, newly-observed trigger shape worth recording
precisely for the eventual core-integration reconciliation, alongside
this segment's other two prior discoveries this session (mixa_app_
controller's bare void-pointer-return and this one). Confirmed
identically across TWO separate runs of the dedicated runner (byte-
identical diagnostic, same line/column, both runs).

What would unblock the L2 side
--------------------------------
Two related gaps in l2trans's current type checker: the already-
reported closed foreign-type allowlist refusing custom struct types in
a `@:`/const: @(...) position, and (this ticket's own finding) the SAME
class of refusal for a bare fnptr-typedef parameter. Landing the core
integration onto main would be expected to clear both without further
changes to this module's own L2 header or .lm2 body.
