mixa_buttons L2 port (ticket 20260913-154000)
================================================

Scope
-----
Clean-L2 port of mixa_buttons, the application button panel (dynamic
lines/items, label-driven width, layout maxima, hit-test, nine-slice
tile rendering) -- the real dependency mixa_app_window still linked
as L1. 12 public functions, 387-line real body.

Barrier (current main)
-----------------------
l2trans error: mixa_manager\mixa_buttons.lm2:18:29: unknown foreign type

Line 18 is mixa_button_panel_init's own first custom-struct parameter
(`@: MixaButtonPanel panel`) -- the module's own first real function
taking a custom struct type in a `@:` position, matching the SAME
closed-type-allowlist barrier family hit by every module ported this
segment. Confirmed identically across TWO separate runs of the
dedicated runner (byte-identical diagnostic, same line/column, both
runs).

Oracle-side results
--------------------
- ABI probe pair: byte-identical across all 27 fields (MixaButton
  sizeof=64, MixaButtonLine sizeof=24, MixaButtonPanel sizeof=104).
- Parity harness (oracle side): 68/68 checks PASS, exit 0. Reproduced
  identically across two separate runs of the dedicated runner.
- Existing mixa_buttons_selftest.lm1 (already part of run_mixa.ps1's
  own regression sweep, unmodified): "mixa buttons ok", both the
  isolated and full-sweep runs.
- run_mixa.ps1 full regression sweep: all suites report ok, no new
  failures.

What would unblock the L2 side
--------------------------------
The same closed foreign-type allowlist gap already reported for every
prior module this segment: l2trans's current type checker refuses any
custom struct type reaching a `@:`/const: @(...) position. Landing the
core integration already in progress on origin/codex/core-integration
onto main would be expected to clear this barrier without further
changes to this module's own L2 header or .lm2 body.
