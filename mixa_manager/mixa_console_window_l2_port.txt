mixa_console_window -- port to clean L2 (ticket 20260913-121500)
====================================================================

Status: source and parity harness COMPLETE. mixa_console_window.h.lm1/
mixa_console_window.lm1 are UNTOUCHED and remain the sole implementation
and the parity oracle; its own real dependencies (mixa_draw.lm1, mixa_
composite.lm1, mixa_file.h, mixa_backend.h, mixa_core.h) are likewise
untouched. Translation against the CURRENT main frontend fails with an
already-known compiler barrier ("unknown foreign type") -- expected,
not a defect.

Design: this module is the FIRST in this segment to predef two full
REAL dependency modules (mixa_draw.lm1 and mixa_composite.lm1) directly,
mirroring the oracle's own design exactly (which relies on l1trans's
own predef deduplication across their shared mixa_text_rect.lm1/mixa_
tiles.lm1 dependency -- the real header's own comment documents this as
"4 distinct files total, deduped"). This was the smallest-honest choice:
rather than re-declaring MixaCell/MixaTextRect a SECOND time via an L2
header (as every prior port did) or fighting a duplicate-symbol link
problem by trying to "declare then link" two real objects that both
transitively contain mixa_text_rect's own body, the L2 .lm2 file simply
predefs the same two real files the oracle predefs, becoming a single,
fully self-contained translation unit for everything except real file
I/O and backend presentation -- exactly matching the oracle's own
compiled shape.

Files

  mixa_manager/mixa_console_window_l2.h.lm1 (new) -- declares ONLY
    this module's own two structs (MixaConsoleView, MixaConsolePending)
    plus the 4 status constants. MixaFile is NOT re-declared: mixa_
    file.h is a plain, hand-written C header that only forward-declares

    zero adaptation needed. MixaCell/MixaTextRect/MixaBackend/MixaU8 are

    plain-C production header for MixaConsoleView/MixaConsolePending
    themselves (like mixa_process_marker) -- both ABI-probe sides are
    l1trans-generated, one from the real .h.lm1, one from this header.

What was actually tried (both genuine construction issues, fixed)
------------------------------------------------------------------------
  1. An earlier draft of the .lm2 file added explicit L1-level bodyless
     forward declares for mixa_file_seek/read/size and mixa_backend_
     present ("declare then link", matching every prior port's own
     convention for genuinely cross-module real functions). This hit a
     DIFFERENT diagnostic -- "incompatible entry signature" -- on the
     very first such declare, using MixaFile's own intentionally-opaque
     forward-declared type as a bodyless declaration's own parameter.
     Re-checking the real oracle showed it writes NO such forward
     declares at all for these three functions -- it relies purely on
     the plain C prototypes already in the include:'d mixa_file.h/mixa_
     backend.h for ordinary C-level linkage, the same way every C
     program calls a function declared in an included header without
     any language-level "forward declare" ceremony. Removing the three
     unneeded L1-level declares (matching the real file's own, simpler
     approach) restored the FIRST-hit diagnostic to the already-tracked
     "unknown foreign type" barrier family, now at the module's own
     first real function definition -- consistent with every other port
     this segment, not a new construct.
  2. The harness's own first run: the full present() pipeline scenario
     failed 3 checks because the test's own rgba buffer was sized 6400
     bytes for an 80x40-pixel RGBA frame that actually needs 80*40*4 =
     12800 bytes -- a genuine test-construction bug (undersized buffer
     caused mixa_composite's own real size-check to refuse the call),
     not a module defect. Fixed by correcting the buffer/size constant
     to 12800; all 39 checks passed on the immediately following run.
