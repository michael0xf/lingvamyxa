Scope
-----
Clean-L2 port of mixa_share_button: the Send-button adapter matching
mixa_button_dispatch.h.lm1's MixaButtonActionFn shape (`@: void ctx`
int), a thin composition over mixa_share_action_send that reports
sent_count/skipped_dirs/last_status/out_r back through the MixaShare
SendCtx struct's own fields. 1 public function, 15-line real body.

No dedicated ABI probe pair
------------------------------
Declares no L2-only struct of its own -- MixaShareSendCtx is reached
via the REAL mixa_share_button.h.lm1 predef'd directly, identically on
both the real oracle and this L2 port.

Barrier (current main) -- a GENUINELY NEW trigger shape
------------------------------------------------------------
l2trans error: mixa_manager\mixa_share_button.lm2:7:5: unsupported own
array declaration

Line 7 is `[]: size_t sent 1` inside mixa_share_send_button_action's
own body -- a LOCAL ARRAY of a BUILT-IN type (size_t), with ZERO custom
structs or fnptrs anywhere in the function up to that point (the
custom-struct local `ctx` on line 5 is never even reached as the
trigger; this array declaration two lines later fires first). Isolated
with a minimal standalone fixture, reachable from main so l2trans does
not skip it as dead code:

    fn: probe_arr_sz () int
        []: size_t x 1
        x[0]: 0U
    return: 0
    fn: main () int
    return: probe_arr_sz()

This reproduces the identical "unsupported own array declaration"
diagnostic. Cross-checked against the SAME shape with `int`/`char`
element types instead of `size_t` -- both translate CLEANLY under
l2trans with no error at all. This confirms the trigger is specifically
a LOCAL ARRAY OF size_t, not arrays in general and not any custom type
involvement. This is a fifth distinct barrier trigger shape this whole
session (after: custom-struct parameter; void-pointer return; fnptr-
typedef parameter; const-qualified pointer return), and the first one
whose diagnostic TEXT itself differs from every prior shape ("unknown
foreign type" / "incompatible entry signature" have both appeared
before; "unsupported own array declaration" has not). Reported
explicitly per the coordinator's own standing request to record any
new construct precisely. Confirmed identically across TWO separate
runs of the dedicated runner (byte-identical diagnostic, same line/
column, both runs) plus the standalone minimal-fixture reproduction
above.
