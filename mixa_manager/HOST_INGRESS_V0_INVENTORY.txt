Host ingress V0 vendored copy: removal inventory
==================================================
Ticket, 2026-09-15 (6f): the lock census found a vendored copy of the host
ingress V0 in mixa_manager/vendor/lmx_msg_host_ingress_v0 (its own
l2src/lmx_message_host.c and lmx_message.lm1 with the host lock: 3
host_lock calls, 2 EnterCriticalSection, 3 pthread_mutex_lock, 6
pthread_cond_). Under "no locks in the project at all except the message
collection's own" (2026-09-15, Mikhail), that copy cannot stay. This file
inventories it: what calls in, what builds it, what today's runtime gives
instead, and the lock-primitive count against the census. No deletion in
this commit -- that lands only after the lead's stage on the host forms
names it.

commit ee4b2d91 / contract commit c6fa2758, five files by blob+SHA256:

--- (2) Which mixa_manager tests and runners build it ---

mixa_manager/tests/mixa_ingress_host_harness.c, built by
mixa_manager/run_ingress_harness.ps1: translates the vendored
lmx_message.lm1 with the pinned stable l1trans, compiles it and the
vendored lmx_message_host.c (WITHOUT -DLMX_MSG_HOST_TEST, the production
build), links both against the harness with -I pointing at the vendor
directory (run_ingress_harness.ps1:68, `$inc = @("-I", $pinInc)`), verifies
by nm that no test-only symbols leaked into the production host.o, runs
the harness, then runs it a second time with --force-join-timeout to
capture an expected-failure diagnostic path. This is the ONLY runner in
mixa_manager that builds any file under the vendor directory -- confirmed
by grepping every mixa_manager/*.ps1 for "vendor" or "lmx_msg_host_ingress_v0"
(mixa_manager/run_ingress_harness.ps1 is the only match besides this
ticket's own inventory file and mixa_console_window.txt, a design note
that only mentions the pin's existence).

mixa_manager/tests/mixa_share_native_smoke.lm1 and
mixa_manager/tests/mixa_win32_smoke_harness.c, named in the ticket as
harnesses with events/Interlocked counters from the lock census -- checked
directly (grepped both files and their runners, run_share_native_smoke.ps1
and run_win32_smoke_selftest.ps1, for "vendor", "lmx_message", "host_ingress"
and any bare "lmx_msg_" symbol): zero matches in all four files. Neither
references the vendored copy, includes either of its headers, or links
against it. Their own WaitForSingleObject/CreateEvent/Interlocked use
(already in the spec map's own census, section 2.5: "the ingress and win32
harnesses 2-4 events and 4 Interlocked") is for harness-internal
cross-thread coordination (a worker thread's own completion, not a message
admission) and is unrelated to the vendored ingress copy's host lock. This
corrects the ticket's framing: of the three named files, only
mixa_ingress_host_harness.c actually builds or calls into the vendored
copy; the other two are independent harnesses that happen to share the
same lock-census paragraph in LOCK_REMOVAL_SPEC_MAP.txt because they also
use native Win32 primitives, not because they touch this vendored tree.

--- Summary ---

The vendored copy is a frozen, architecturally older snapshot (a flat
rt\tab array instead of a linked slot list, a separate host_lock-guarded
rt\host_head/host_tail ingress queue instead of direct admission into
R0's own mailbox) pinned solely so mixa_manager/tests/mixa_ingress_host_harness.c,
run by mixa_manager/run_ingress_harness.ps1, does not track live
stg/l1_baseline/l2src. Of its 28 exported names, 11 are actually called,
all from that one harness, 15 call sites. Every one of those 11 has a
same-named, same-role equivalent in today's live lmx_message.lm1 except
host_wait, which lives in the live lmx_message_host.c (a sibling file,
itself still carrying its own host lock today, out of this file's scope)
-- silent, no map question number assigned since this is a different
file's design question, not lmx_message.lm1's.

No file was edited, moved, or deleted by this ticket. The deletion of the
vendor directory and the rewrite of run_ingress_harness.ps1 (and, if
Mikhail's "one arena, arenas attach on consumption" ruling extends to a
foreign OS thread's post, of the harness itself) are their own commit
after the lead's stage on the host forms names it, per the ticket.
