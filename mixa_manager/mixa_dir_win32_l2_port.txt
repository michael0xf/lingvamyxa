mixa_dir_win32 L2 port (dependency-order continuation after
mixa_selection_walk)
==========================================================================

Scope
-----
Clean-L2 port of mixa_dir_win32, the Win32 directory seam (FILE_SEAM
section 4): UTF-8 path conversion, FindFirstFileW/FindNextFileW/
FindClose-based listing, GetFileAttributesW-backed remove-target check,
CreateDirectoryW/MoveFileW/DeleteFileW/RemoveDirectoryW. 22 functions,
385-line real body.

No dedicated ABI probe pair
------------------------------
Like mixa_fm_remove/mixa_remove/mixa_selection_walk before it, this
module declares no L2-only struct of its own -- MixaDir and
MixaDirEntry are reached via the REAL mixa_dir_win32.h.lm1/mixa_dir.h.
lm1 predef'd directly, identically on both the real oracle and this L2
port. No second struct layout exists to diff.

Barrier (current main) -- CONFIRMED-MATCHING, not novel
-----------------------------------------------------------
l2trans error: mixa_manager\mixa_dir_win32.lm2:9:54: unknown foreign
type

Line 9 is mixa_dir_utf8_to_wide's own out-parameter (`@@: wchar_t
out_w`), column 54 landing on `wchar_t` itself -- a BUILT-IN type, not
a custom struct. This is the SAME barrier shape already discovered and
documented much earlier in the whole session at ticket 114500 (mixa_
file_win32): "the barrier fires on wchar_t itself, one function earlier
than the module's own custom struct." Confirmed identically across TWO
separate runs of the dedicated runner (byte-identical diagnostic, same
line/column, both runs).

What would unblock the L2 side
--------------------------------
The same closed foreign-type allowlist gap already reported for every
prior module this segment, now further confirmed to also cover a
built-in type (wchar_t) in an out-parameter position, not only custom
structs -- matching the earlier ticket 114500 finding exactly. Landing
the core integration onto main would be expected to clear this barrier
without further changes to this module's own L2 header or .lm2 body.
