A real correctness point handled carefully (not a bug this time --
verified correct on the first try, but worth recording since it is a
GENUINE functional concern, unlike the write-only field adaptations the
earlier tiles/text_rect/draw ports needed)
------------------------------------------------------------------------
mixa_composite is the first ported module that READS a MixaCell's own
bg/fg/alpha fields back for real arithmetic (every earlier port only
WROTE them). Since mixa_tiles_l2.h.lm1's own struct declares these as
SIGNED 1-element char arrays (this L1 grammar's own closed field-type
set has no scalar unsigned-byte keyword -- see that file's own
comment), a bare `sa: cell\alpha[0]` read for a stored value >=128 would
sign-extend through char->int->unsigned promotion into a huge, WRONG
unsigned value -- not merely a test-check artifact this time, but a
real bug in the blend math itself (alpha and palette-index bytes
legitimately range 0-255). Every one of the 8 field reads in this
port (bg/fg/alpha, both layers) was written with an explicit
`(cast: (unsigned) (cast: (unsigned char) cell\X[0]))` reinterpret from
the start; the harness's own scenario 1 deliberately used alpha=200 and
bg=5 (both >=128) specifically to exercise this, and it produced the
exact hand-derived RGB values on the first run.
