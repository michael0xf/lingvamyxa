mixa_share — file-share seam (ClearShell "Send e-mail" button, ticket 20260911-210200)
========================================================================================

Purpose
-------
Stage 1 of a bounded slice: the portable request/lifecycle API for ClearShell's
"Send e-mail" action, generalized to the native OS share surface (Windows:
IDataTransferManagerInterop / DataTransferManager / ShowShareUIForWindow;
see NEXT_CLAUDE_TICKET_FILE_SHARE_20260911.md section 4). This stage delivers
the self-contained portable controller and its deterministic fake-backend
selftest. No Windows COM/WinRT adapter and no button integration yet — both
are honestly out of scope for this checkpoint (see "Remaining stages" below).

Reference behavior (ported from ClearShell.java)
-------------------------------------------------
Read directly, not summarized secondhand:
  ClearShell.java  email() / email(Contact) / email2(Contact) / sendEmail(...)
                   ~L12500-12635
  FSync.java       popSelectedListFroEmail() ~L1604

  - The "Send e-mail" button (ClearShell.this::email, ~L2218) calls
    email() -> email(extractEmails()) -> email2(contact) -> sendEmail(...).
  - popSelectedListFroEmail() pops only FILES from the current selection
    (removeSelect() as it goes -- consuming selection is a side effect of
    the reference action); directories are skipped with a warning dialog,
    not silently dropped and not a hard failure.
  - sendEmail derives a title from the message text: the first two
    non-blank space-delimited words, concatenated as " word1 word2"
    (note the reference's own leading space from `title = title + " " +
    word`, preserved here exactly, not "fixed"). If no such words exist
    (blank/all-whitespace text), title falls back to the text itself,
    truncated to the first 32 characters.
  - ACTION_SEND for 0-1 files, ACTION_SEND_MULTIPLE for >1; file content
    goes through FileProvider URIs with granted read permission; an app
    chooser is shown. This module models that shape (single vs multiple,
    a chooser/share-UI hand-off) without being Android-specific.

Design decisions
----------------
* No process-global mutable state in the PORTABLE controller (the lesson
  from the audio-seam review): every field lives on MixaShareRequest,
  allocated per-instance. The win32 backend must follow the same rule once
  it's implemented (a real DataTransferManager registration is inherently
  per-window, not per-process, so this should hold naturally).
* Text/title/file paths are owned strdup'd allocations, never a fixed
  staging buffer -- the reference's own title derivation has no length cap
  on the two-word branch, and Unicode/space/apostrophe paths are data, not
  shell syntax, so nothing here silently truncates.
* set_files probes every path before committing anything (atomic replace):
  a genuinely missing/unreadable path is a hard MIXA_SHARE_ERR_MISSING (no
  partial commit), while a directory in the selection is soft-skipped and
  counted via out_skipped -- matching the reference's "warn, don't fail"
  handling of directories in popSelectedListFroEmail, while still treating
  an outright missing file as the caller's bug (unlike the reference, whose
  selection can't reference nonexistent files by construction).
* Async model is POLL-based, not callback-reentrant: begin() marks the
  request PENDING and hands off to the backend; poll() is the only point
  where backend state (a real DataRequested/dispatcher-queue callback, one
  day) is allowed to update portable request state, keeping OS-affine work
  off any thread that might be touching Message-owned data directly.
* mixa_share_destroy() calls the backend's destroy() BEFORE freeing any
  portable field, specifically so a real backend can unregister a pending
  native callback/token while the request is still fully valid. The fake
  backend's stale-registration tests in the selftest exist to keep this
  ordering honest: destroying a request mid-flight must free its backend
  registration slot, and a second, independent request must then be able
  to begin() cleanly (proving no leaked handler blocks or cross-contaminates
  an unrelated request).
* begin() only allows the transition from MIXA_SHARE_EVENT_NONE (a fresh,
  never-started request). Every other event -- PENDING, HANDED_OFF,
  CANCELLED, FAILED -- is terminal for that request; call destroy() and
  create a new one instead. The header documented this from the start; an
  early implementation only checked for PENDING, silently allowing a
  restart after HANDED_OFF/CANCELLED/FAILED (caught in review, fixed, and
  covered by dedicated tests for all three terminal events plus the
  NONE-allows-first-begin case).
* The concrete win32 stub header does not `include: "<windows.h>"` (or any
  other platform header) even though it will need COM/WinRT declarations
  once the Windows adapter is implemented (caught in review; the initial
  stub had a copy-pasted include it didn't yet use for anything). Second
  review round: removing the include there is NOT by itself sufficient --
  the portable header still `predef:`s the concrete one, and predef order
  pulls the concrete file's content into any translation unit that only
  wanted the portable contract, includes and all. Adding a native include
  to the concrete header once the adapter needs one would restore the
  exact same leak, just relocated. The actual portable->concrete
  dependency needs resolving (or native includes isolated behind a
  boundary nothing portable-only predefs) before that point, not assumed
  solved by which specific file the include line lives in. mixa_audio_
  win32.h.lm1 and mixa_app_win32.h.lm1 have this identical structural leak
  today (both predef'd by their portable headers, both already including
  windows.h) -- a systemic characteristic of this predef pattern, not
  something introduced here or unique to Share.

L1 findings while porting
--------------------------
* mixa_audio.lm1's own `@@: char items` convention (not `const char**`) is
  the correct spelling for a caller-owned array-of-strings parameter here
  too: C does not allow an implicit char** -> const char** conversion (a
  well-known qualifier-safety rule), so a `const: @(@(char) ...)` prototype
  parameter rejects a plain `char *arr[N]` argument at the call site with
  -Werror=incompatible-pointer-types. Matched the existing convention
  instead of fighting the language.
* A global test-only pointer for the fake backend's single pending-request
  slot is a PLAIN pointer declaration (`@: MixaShareRequest g_fake_pending`),
  not the array-style `@: (@: Type) name` pattern (which declares a pointer-
  to-pointer) -- easy to reach for the wrong one when copying an existing
  array declaration as a template.
* There is no `(void): expr` discard/cast-to-void spelling in this L1; an
  unused function parameter that isn't otherwise dead code doesn't need one
  (argc was already used later in this file's main(), making the attempted
  suppression both invalid syntax and unnecessary).
* A literal `"` character in a Windows filename is illegal at the OS level
  (NTFS forbids `< > : " / \ | ? *`); fopen() on such a path fails silently
  and the resulting "missing" file is a test-fixture bug, not a module bug.
  Found by getting an unrelated-looking crash (strcmp on a NULL returned by
  file_at after the whole probe-everything-first set_files call correctly
  aborted with ERR_MISSING) and tracing it back with gdb + a temporary debug
  printf, not by guessing. The Unicode/space/apostrophe coverage in the
  selftest keeps the metacharacter-handling intent without an illegal name.

Testing
-------
Run from mixa_manager:

    ./run_share_selftest.ps1

45 checks, 0 failures. Covers: title derivation (two-word, one-word,
long-word, all-blank-fallback, UTF-8-safe 32-byte truncation, explicit
override), single-file and multi-file begin/poll-to-completion, cancel(),
text-only sharing (with and without CAP_TEXT_ONLY), multi-file rejection
without CAP_MULTIPLE, incomplete-vtable rejection at create, missing-file
hard error with no partial commit, directory-in-selection soft-skip,
begin() rejecting a missing required platform context, destroy-before-
completion correctly freeing the backend's pending-registration slot (and
a subsequent independent request completing cleanly afterward -- the
stale-callback/leak scenario from the ticket's acceptance criteria),
begin() rejected on every terminal event (PENDING, HANDED_OFF, CANCELLED,
FAILED individually) while NONE still allows the first begin(), and
null-argument negatives throughout.

This is a fake-backend-only, platform-independent test; it does not exercise
real Windows share UI and is not offered as such (see remaining stages).

Windows-adapter feasibility (researched, not yet implemented)
----------------------------------------------------------------
Checked whether this toolchain can express the required COM/WinRT calls
before committing to an implementation, per the ticket's explicit
instruction. Findings, in the order needed:

* IDataTransferManagerInterop (the classic-HWND -> WinRT bridge) is
  declared as a plain-C ABI struct (a `lpVtbl` member, not a C++ class) in
  MinGW's own bundled header, x86_64-w64-mingw32/include/shobjidl.h, along
  with convenience call macros (IDataTransferManagerInterop_GetForWindow,
  _ShowShareUIForWindow) that hide the This->lpVtbl->Method(This,...)
  double-indirection behind a normal-looking macro call -- no two-level
  member chain needs writing in L1 source for these.
* RoGetActivationFactory (roapi.h) and WindowsCreateString (winstring.h),
  needed to obtain the interop factory from a runtime-class-name HSTRING,
  are both in MinGW's bundled headers too.
* The actual WinRT interfaces the interop bridge hands back --
  IDataTransferManager, IDataPackage, IDataRequestedEventArgs -- are NOT in
  MinGW's bundled headers, but ARE present as plain-C MIDL-generated ABI
  declarations (the __x_ABI_CWindows_C... naming convention, ordinary
  vtable structs, not C++/WinRT's winrt:: template projection) in the full
  Windows 10 SDK already installed on this machine at
  C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\winrt\
  windows.applicationmodel.datatransfer.h. Using them needs an extra -I
  path added to the compile step; not an L1 language limitation, a build-
  configuration one.
* The harder-looking piece: registering a DataRequested event handler
  means IMPLEMENTING a callback interface (providing a vtable), not just
  consuming one -- a different shape from anything the app/audio seams
  needed so far. Confirmed this specific instantiation --
  ITypedEventHandler<DataTransferManager*, DataRequestedEventArgs*> --
  has a genuine plain-C fallback declaration in the same SDK header
  (search for __FITypedEventHandler_2_Windows__CApplicationModel__
  CDataTransfer__CDataTransferManager_Windows__CApplicationModel__
  CDataTransfer__CDataRequestedEventArgs): a 4-method vtable struct
  (QueryInterface, AddRef, Release, Invoke) and an interface struct with a
  single `lpVtbl` member -- structurally identical to every vtable this
  codebase already builds via calloc + sequential `\field: fn` assignment
  (mixa_audio_win32_table, mixa_app's table, this module's own
  fake-backend vtables). Building the SAME shape to hand OUT to Windows,
  instead of only ever consuming one, should not need anything new from L1
  itself -- the memory layout is what the ABI cares about, not which
  direction the vtable is used in.

Minimal reproducer, actually built (not just read from headers): an L1
unit declaring pointers of type `IDataTransferManagerInterop` and
`__x_ABI_CWindows_CApplicationModel_CDataTransfer_CIDataTransferManager`,
including all of windows.h/roapi.h/winstring.h/shobjidl.h/windows.
applicationmodel.datatransfer.h. l1trans translated it cleanly (exit 0),
confirming these unusually long SDK identifiers are not an L1 parser
problem. The first compile attempt failed: adding the SDK's winrt
directory via plain `-I` shadows MinGW's OWN compatible roapi.h with the
SDK's MSVC-oriented one (`#pragma region` -- not something GCC's
preprocessor accepts), because -I search order puts it before MinGW's
bundled headers. Fixed by using `-idirafter` for the SDK path instead of
-I: MinGW's own headers (which already have everything except the WinRT
interfaces) are found first, and the SDK path is only consulted for what's
genuinely missing (windows.applicationmodel.datatransfer.h itself, plus
whatever headers it internally chains to, e.g. Windows.Foundation.h,
IVectorChangedEventArgs.h). With that one flag, the reproducer compiled
with zero warnings and ran correctly. The exact working compile line:

    gcc -std=c99 <other existing flags> \
      -idirafter "C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\winrt" \
      <source>.c -o <exe>

Conclusion: nothing found requires handwritten C or a C++ dependency, and
the toolchain question is now answered rather than assumed -- add
`-idirafter` for that one SDK path to whatever compile step builds the
Windows adapter (run_share_selftest.ps1's native-smoke-test stage, once it
exists), the same GccArgs pattern the other runners already use. Remaining
unknowns are volume of new L1 code (HSTRING/factory setup, the handler
object's four methods, DataPackage population) and linking against
runtimeobject/ole32 for RoGetActivationFactory/RoInitialize, not
language- or toolchain-expressibility blockers.
