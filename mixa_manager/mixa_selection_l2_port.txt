mixa_selection -- port to clean L2 (ticket 20260913-075100)
====================================================================

Status: BLOCKED at the FIRST real compiler barrier, per this ticket's
own instruction 5 ("stop at the FIRST real compiler barrier... do not
work around it"). mixa_selection.h/mixa_selection.lm1 are UNMODIFIED and
remain the sole implementation and the parity oracle -- there is nothing
to compare an L2 port against yet, because no L2 port of the real module
exists or could be started past its own first function.

Goal (unchanged from the ticket)
------------------------------------
Port the isolated mixa_selection module from its current L1 source to
"clean" L2 (the language implemented by stg/l1_baseline/l2src/l2trans.
lm1, translating .lm2 -> L1 -> C99, per L2_CORE_SELFHOST_HANDOFF_
20260911.md section 1), preserving the accepted persistent path-identity
selection behavior (SELECTION_MODEL.txt), and preparing mixa_manager for
the later full L1-to-L2 migration.

Step 1: audit (done)
-------------------------
mixa_selection.h declares 2 structs (MixaSelection, MixaSelRev, both
plain char*/char**/size_t/int fields, no exotic types) and 5 public
functions (mixa_selection_init/release/select/deselect/query).
mixa_selection.lm1 additionally defines 17 internal (non-exported, but
still real, file-scope L1) helper functions -- 22 functions total. Every
single one of the 22 takes at least one parameter typed as a pointer to
MixaSelection or MixaSelRev (or both), and 3 of them (mixa_sel_rev_
ensure, mixa_sel_find_covering, indirectly others) RETURN a `@: MixaSelRev`
or `@: char` pointer derived from one. C standard library dependencies:
strlen, malloc, calloc, memcpy, free, strcmp, sizeof -- all ordinary,
already used identically elsewhere in this codebase's own accepted L2
leaf-function examples (see below), never in question.

Step 2/5: the first real compiler barrier
-----------------------------------------------
The current L2 frontend (stg/l1_baseline/l2src/l2trans.lm1, itself
written in L1 and rebuilt fresh from source by this ticket's own runner
below -- it is NOT a stable, hash-pinned artifact the way the L1
translator is) type-checks every `@:` pointer formal/return type and
every `const: @(...)` formal against a CLOSED, HARDCODED allowlist, read
directly rather than assumed:

  - bare `@:` pointer type: only `char`, `void`, `int`, `size_t` are
    accepted (l2trans.lm1, the frame-head-"@@" formal handler, ending in
    `return: l2_error(path, node, "unknown foreign type")`).
  - `const: @(...)` formal: the same four, PLUS a small, closed set of
    the L2 compiler's own bootstrap self-hosting parser types --
    `LmP0Document`, `LmP0IndentStack`, `LmP0Text`, `L2ImmutQuery` -- each
    individually gated by name, never a general "any predef'd struct
    name is acceptable" branch.

There is no general mechanism in the current frontend generation for a
NEW, manager-owned struct type (declared via an ordinary predef'd
header, exactly the way mixa_manager already writes L1 headers) to be
used as a function parameter, return type, or local variable at all. The
struct declaration itself is not rejected -- the SAME MixaSelRev struct
compiles and links fine as an ordinary L1 unit -- only its use in one of
those three positions inside a `.lm2` file is.

Since mixa_selection's own entire API is built on exactly that shape
(every one of its 22 functions), this is not a narrow edge case that a
workaround could route around without either (a) misrepresenting the
module's own real, typed API as something it is not (e.g. flattening
every `MixaSelection*`/`MixaSelRev*` parameter into an untyped `@: void`
with manual casts everywhere, silently discarding the module's own real
type safety), or (b) inventing a fixed cap or private extension to the
type checker -- both of which this ticket's own instruction 5 explicitly
forbids ("do not work around it with a new fixed cap and do not change
core"). mixa_selection.lm1/l2src/l2trans.lm1 were not touched to test
either avenue.

Steps 3/4/6, given the block
---------------------------------
Instruction 3 (parity test scenarios: empty selection, select/query,
duplicate select, deselect, cumulative multi-select, independently-owned
path bytes, refresh-style index reorder independence, walk order,
allocation-failure rollback) and instruction 4 (run the parity test

against the L1 one. None exists, because the port cannot progress past
its own first function under the current L2 frontend -- there is no
partial, working L2 port to write these scenarios against without
resorting to exactly the workarounds instruction 5 forbids. Ticket
20260913-071906's own already-accepted E2E selftest (tests/mixa_app_
fmpanel_selrefresh_e2e_selftest.lm1) already exercises every one of
these behavioral scenarios against the real, accepted L1 implementation
and remains the authoritative coverage for mixa_selection's own real,
observable behavior; it is unaffected by this ticket (no source files
changed).

What would unblock this
----------------------------
The L2 frontend's own type-checker (the `@:`/`const: @(...)` formal/
return-type allowlist cited above, in l2trans.lm1, owned by the core
team per this ticket's own boundary) would need a general mechanism to
accept a predef'd, manager-owned struct type by name -- not specific to
MixaSelection/MixaSelRev, but the same general capability any future L1-
to-L2 leaf-module port will need for its own structs. This is squarely
core/compiler work, out of this ticket's own mixa_manager-only scope and
not attempted here.

Second barrier: bare `@@:` (pointer-to-pointer) RETURN type rejected
------------------------------------------------------------------------
  mixa_manager\mixa_selection.lm2:48:1: incompatible entry signature

Line 48 is exactly `fn: mixa_sel_grow_ptrs (...) @@: char` -- the growable
pointer-array helper's own real, load-bearing return type (it returns a
possibly-reallocated `char**` slots array), not a struct type at all.
Confirmed by reading l2trans.lm1 directly, not assumed: the general
(non-main) leaf-function signature checker at l2_collect_decls (around
line 5072-5104) recognizes, for a function's return type, only a bare
`int`/`size_t`/`LmP0TrailerRole` atom or a single `@:` pointer frame
(char/LmP0Text/LmP0IndentStack, else "unknown foreign type" -- the
already-known barrier); there is NO branch there for a `@@:` frame head
at all, so it falls straight through to the generic "incompatible entry
signature" error at line 5103-5104. This is a DIFFERENT diagnostic from
a DIFFERENT code path than the struct-type barrier.

Notably `@@:` IS accepted in a PARAMETER position (l2_typed_formal,
lines 4874-4899, types 17-20 for char/void/int/size_t) -- confirmed by
testing a `@@: char slots` formal with a plain `@: char` return
separately (scratch-only, not committed): parsing proceeded past the
parameter with no complaint. Only the RETURN position lacks any `@@:`
branch. This asymmetry is exact and reproducible, not inferred.

Not worked around: mixa_selection.lm2 keeps the real `@@: char` return

semantics) -- it was not rewritten to an out-parameter or a flattened

Both barriers, together, mean: the complete mixa_selection.lm2 file as
written is real, faithful, and ready, but cannot fully translate under
the CURRENT L2 frontend for two independent, structural reasons --
(1) no manager-owned custom struct type in `@:`/`const: @(...)`
position (function 3 onward), and (2) no `@@:` return type on an
ordinary leaf function at all (function 2, mixa_sel_grow_ptrs, hit
before barrier 1 is even reached during a straight top-to-bottom
translation). Both are core/compiler-owned surface gaps in l2trans.lm1,
not mixa_manager defects.
