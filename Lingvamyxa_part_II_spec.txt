9.3. Model Definitions

A model definition is a Structure consumed by a model receiver. One possible direction is to derive a model from a condition function:

L4:
    model:
        name: PlantBed
        condition: plantBedCondition
end: L4

L3:
    fn: plantBedCondition (
        u32(id)
        Text(crop)
        f64(area)
        f64(soilWater)
        f64(harvest 0.0)
    ) (boolean)
        return: area > 0.0 && soilWater >= 0.0 && soilWater <= 100.0
    end: plantBedCondition
end: L3

In this direction, the formal argument Structure of `plantBedCondition` defines the model slots and defaults. The boolean return descriptor and the explicit `return:` body define the validation predicate.

Another possible direction is an `autoModel` receiver that receives a model name and two Structure arguments: one declaration Structure and one condition Structure.

Example:

L4:
    autoModel: PlantBed
        vars:
            u32: id
            Text: crop
            f64: area
            f64: soilWater
            f64: harvest 0.0
        ---
        condition:
            area > 0.0
            soilWater >= 0.0
            soilWater <= 100.0
        ---
end: L4

This section does not define a final type/model language. It only states that model declarations are ordinary Structures consumed by model receivers.

?
The model/type declaration syntax is only partially specified. The preferred direction avoids a separate `field` receiver and uses declaration-context type constructors such as `u32: id` and `f64: harvest 0.0`. Still unspecified: canonical alias syntax, explicit layout syntax, relation signature syntax, and whether canonical model definitions use condition functions, `autoModel`, or both.
?

variant 1:
Define models through condition functions. Function input bindings define model slots and the boolean body defines validation.

variant 2:
Define models through an `autoModel` receiver with explicit child Structures such as `vars(...)` and `condition(...)`.

variant 3:
Allow both forms and define one as canonical normalization for the other.

9.4. Normalized Model Descriptor

A model receiver may normalize its input into a model descriptor. This document uses the term `ModelSpec` for that normalized descriptor. `ModelSpec` is not a magical built-in source keyword; it is the conventional semantic result produced by receivers such as `model`, `autoModel`, imported schema receivers or future mapping receivers.

A minimal `ModelSpec` contains:

    name
    vars
    defaults
    conditions or validator
    layout policy
    derivation requests
    source/provenance metadata

`name` is the model name registered in the shared namespace.

`vars` is the ordered Structure of slots/bindings. Field order is part of the logical model and may be used for positional construction, return Structures, destructuring, layouts, relation signatures and serialization.

`defaults` are default initial values for slots. They may be represented directly in `vars`, for example `f64: harvest, 0.0`, or materialized as a separate descriptor view.

`conditions` or `validator` define which values are valid instances of the model. Conditions may be listed as expression Structures or delegated to a boolean function.

`layout policy` describes how stable or externally constrained the slot order/representation is. The physical representation is still a lowering decision unless an explicit layout receiver fixes it.

`derivation requests` describe which artifacts may be derived from the model, such as constructors, validators, accessors, relation signatures, serializers or documentation schemas.

`source/provenance metadata` records the source receiver, file, line, import or external origin of the descriptor for diagnostics and incremental rebuilds.

9.5. Union Descriptors and Variant Membership

A `union` receiver defines a closed set of allowed model variants.

Example:

L4:
    union: Shape
        Circle
        Square
        Triangle
    ---


Conceptual normalized descriptor:

UnionSpec:
    name: Shape
    variants:
        Circle
        Square
        Triangle
    ---


At source-semantic level, a value of `Shape` is a value whose concrete variant is one of the listed model names. A concrete variant value may be injected into the union when the expected type is the union.

Example:

    Circle: 10.0

creates a `Circle` value through the `Circle` constructor. If the expected type is `Shape`, the translator/receiver may inject that value into `Shape` by attaching the variant name `Circle` and the concrete `Circle` value.

Conceptual source meaning:

Shape:
    tag: Circle
    payload:
        Circle
            radius: 10.0
        ---
    ---


`tag` is the variant name. `payload` is the concrete value produced by the variant constructor. The union does not create the payload by itself.

The physical representation of a union value is not defined by this structural core. A translator may use tagged inline storage, tagged handles, model-id plus value-handle pairs, pointer-based payloads or another representation.

9.6. Registry Facts Generated by Structural Descriptors

Model, union, operator and behavior descriptors may be represented internally as typed facts. For example, a model descriptor for `Circle` may materialize facts such as:

    model: Circle
    slot: Circle radius f64

A union descriptor may materialize facts such as:

    union: Shape
    variant: Shape Circle
    variant: Shape Square
    variant: Shape Triangle

These facts are registry facts. They are not ordinary runtime assertions unless a receiver exposes them to a runtime query system. The fact representation gives one uniform way to index, query, validate and derive registry information.

9.7. Model Extension and Conflict Policy

A model name has one structural `ModelSpec` unless an explicit extension/refinement receiver defines controlled composition. A second independent structural model definition for the same name is a conflict.

Adding constraints, behavior, generic methods, union membership or documentation to an existing model must be explicit through registered receivers such as `refineModel`, `behavior`, `method`, `variant`, `extendUnion` or future extension forms.


10. L5 Behavior, Objects, Messages and Facts

10.1. L4 Model vs L5 Behavior

The word `model` may appear at different levels, but the source semantics must distinguish two roles:

    L4 structural model -> slots, types, defaults, constraints, layout and derivations
    L5 behavior model   -> messages, selectors, method implementations and object dispatch

The canonical term for the L5 role in this document is `behavior`. If a future L5 profile allows the receiver name `model`, it must consume Structures as an L5 behavior/message descriptor, not as the L4 structural `ModelSpec` receiver.

10.2. Behavior Descriptor

A behavior descriptor attaches message responses to an existing model name.

Example:

L5:
    behavior: Circle
        message: drawOn drawCircleOn
        message: area circleArea
    ---


Conceptual descriptor:

BehaviorSpec:
    model: Circle
    messages:
        drawOn: drawCircleOn
        area: circleArea
    ---


The implementation names `drawCircleOn` and `circleArea` are ordinary executable bindings and must be visible in the shared namespace. Duplicate message selectors for the same model are conflicts unless an explicit override/refinement receiver defines another policy.

A behavior descriptor does not redefine the structural fields of `Circle`. It attaches message behavior to the structural model already registered under `Circle`.

10.3. Runtime Object Value

An L5 object value is a Structure or handle/reference to a Structure together with enough model information to resolve behavior. Conceptually:

object:
    model: Circle
    slots:
        radius: 10.0
    ---


The `slots` layout and validation come from the L4 `ModelSpec`. The message table comes from the L5 `BehaviorSpec` or from registry facts materialized from it.

10.4. Message Send

A message send has a receiver object, a selector and an argument Structure.

Example source form:

    shape: drawOn canvas

Conceptual send fields:

    receiver shape
    selector drawOn
    args (canvas)

Resolution:

    model shape\model
    method lookupMessage(model, drawOn)
    call method(shape, canvas)

The receiver object is passed as the first semantic argument to the selected implementation.

If `shape\model` is `Circle`, and the behavior registry contains:

    message: Circle drawOn drawCircleOn

then the send lowers or interprets as:

    drawCircleOn(shape, canvas)

10.5. Message Lookup Strategies

The source semantics require lookup by `(model, selector)`. The implementation may use dictionaries, selector indexes, method tables, inline caches or static lowering when the receiver model is known.

If no message exists for `(model, selector)`, the behavior is not fixed by this document. A strict profile may report an error. A dynamic L5 profile may route the send to a `doesNotUnderstand` receiver.

!!!
L5 message-missing behavior is not fixed. A final L5 behavior specification must decide whether missing messages are compile-time errors, runtime errors, `doesNotUnderstand` sends, receiver-defined diagnostics or query failures.
!!!

10.6. L5 Facts and Rules

L5 may store registry information as typed facts and rules. Examples:

    fact: model Circle
    fact: slot Circle radius f64
    fact: behavior Circle
    fact: message Circle drawOn drawCircleOn
    fact: variant Shape Circle
    fact: method draw Circle drawCircle

The same information may also be materialized as descriptors such as `ModelSpec`, `UnionSpec`, `BehaviorSpec`, `OperatorSpec` or `GenericMethodSpec`. Descriptors and facts are two views of one registry model.

L5 rules may derive registry facts from other facts. For example, a rule may derive that a generic operation is complete for a union when every union variant has a registered method implementation.

10.7. L5 Configuration and Build Example

Example:

L5:
    target:
        app
        kind: executable
        sources: ("src/hello.lm3")
        entry: hello
        output: "build/bin/hello.lm0.exe"
    ---

    build: app


The `target` and `build` receivers define build semantics. They may also emit registry facts used by the builder. The structural core only creates Structures and specifies that L5 receivers consume them as messages, configuration, behavior descriptors, facts, rules or build/query requests.

11. Operators and Receiver Registration

11.1. Operator as Receiver Registration

`operator` is a receiver used during bootstrap or model loading. It registers receiver names, visibility levels and implementations.

Example:

L4:
    operator:
        while
        callableFrom: L3
        implementation:
            while_func
            level: L2
end: L4

Semantic meaning:

    Register a receiver/operator named `while`.
    Make it callable from L3.
    Use implementation `while_func`.
    Treat that implementation as L2-level implementation.

The `operator` frame is not the runtime/control operation being registered.

11.2. Runtime Use of Registered Operators

After registration, runtime/control source may contain:

L3:
    while: i < beds\len
        print: beds[i]\crop
        i: i + 1
end: L3

Here `while` is the opened frame and therefore may close as `end: while` or be closed implicitly by `end: L3`.

The active L3 `while` receiver consumes its argument Structure according to its registered signature, typically as:

    condition -> expression
    body      -> statement Structure

11.3. Multiple Level-Specific Implementations

The same surface receiver name may have different implementations at different levels.

Example registrations may define:

    if callable from L3 -> l3_if
    if callable from L4 -> l4_model_if
    if callable from L5 -> l5_if

The active level determines which receiver implementation consumes the Structure.

11.4. Generic Operations and Method Registration

A generic operation is a registered receiver whose implementation is selected by a dispatch rule rather than by one fixed executable definition.

Example:

L4:
    operator: draw
        callableFrom: L3
        dispatchBy: firstArgumentModel
        domain: Shape
    ---

    method: draw Circle drawCircle
    method: draw Square drawSquare
    method: draw Triangle drawTriangle


The `operator: draw` frame registers `draw` as a callable generic receiver. The child Structure `dispatchBy: firstArgumentModel` says that the concrete implementation is selected by the model of the first argument. The child Structure `domain: Shape` restricts or documents the generic domain.

Each `method` frame registers one dispatch entry:

    method <generic-name> <model-name> <implementation-name>

Example semantic facts:

    generic: draw
    dispatchBy: draw firstArgumentModel
    domain: draw Shape
    method: draw Circle drawCircle
    method: draw Square drawSquare
    method: draw Triangle drawTriangle

The implementation names are ordinary `fn` or `sub` bindings and must satisfy the signature contract of the generic operation. For example, if `draw` returns no value, each drawing implementation is normally a `sub`. If `draw` returns a `DrawCommand`, each implementation must return a compatible value.

11.5. Dispatch from Union Domain

If a generic operation has a union domain, the union variants and method facts together define complete dispatch.

Example union facts:

    variant: Shape Circle
    variant: Shape Square
    variant: Shape Triangle

Example method facts:

    method: draw Circle drawCircle
    method: draw Square drawSquare
    method: draw Triangle drawTriangle

At a call site:

    Shape: shape
    draw: shape

translation may derive:

match: shape
    ---
        Circle c
        drawCircle: c
    ---
        Square s
        drawSquare: s
    ---
        Triangle t
        drawTriangle: t
    ---


The `match` form checks the union tag/variant name, extracts the payload as the concrete model and calls the registered implementation. If the first argument is statically known to be `Circle`, the call `draw: c` may lower directly to `drawCircle: c`.

Completeness for a union domain is a registry check: for every `variant(Shape, V)`, there must be a compatible `method(draw, V, Impl)` unless a default or fallback method is explicitly registered.

11.6. Generic Operation vs L5 Message

A generic operation such as `draw: shape` dispatches through a generic operation registry:

    (generic name, first argument model) -> implementation

An L5 message send such as:

    shape: drawOn canvas

dispatches through the receiver object's behavior table:

    (receiver\model, selector) -> implementation

Both mechanisms may be represented as registry facts. They are different source-semantic forms. A generic operation is centered on the operation name. A message send is centered on the receiver object.

12. Conditional Structures: L4/L5 Extract
12.2. L4 `if`

L4 `if` is a model-conditional receiver. It does not execute runtime effects. It may conditionally include, exclude or normalize model Structures, registry entries and constraints.

12.3. L5 `if`

L5 `if` is a message/configuration dispatch receiver. It may conditionally dispatch build, run, query, startup or configuration messages.

12.4. Conditional Forms

Short positional conditional form:

if: mode = debug
    build: debugTarget
    build: releaseTarget

Normal form under signature `if(condition, thenBody, elseBody)`:

    if(
      <expression Structure for `mode = debug`>,
      (build(debugTarget)),
      (build(releaseTarget))
    )

The same conditional may be written with explicit named branch Structures:

if: mode = debug
    then:
        build: debugTarget
    else:
        build: releaseTarget

This builds:

    if(
      <expression Structure for `mode = debug`>,
      then(build(debugTarget)),
      else(build(releaseTarget))
    )

The short positional form is valid when the active `if` receiver assigns sibling child Structures to semantic fields by signature order. Named vertical form remains available for readability or when a style/profile requires explicit names.

17. Registry Descriptor Core

17.0. Status and Boundary

Sections 17-21 define the concrete registry/evidence core used by L4 and L5.
They replace the older generic statement "registry as facts" with explicit
instructions for descriptor construction, fact materialization, evidence graph
construction, consumption modes and lowering.

These sections do not change P0 syntax. P0 builds Structures, Frames,
Atoms/values and MIX nodes. Receivers consume those Structures and decide
whether they are model descriptors, behavior descriptors, facts, messages,
queries, build targets or ordinary values.

The registry core has these mandatory concepts:

    ModelSpec
        structural data descriptor: slots, field types, defaults, constraints,
        layout policy, validators and generated structural operations.

    BehaviorSpec
        behavior descriptor: selectors, method signatures, method targets,
        message dispatch entries, role behavior and dynamic dispatch policy.

    MessageSpec
        message descriptor or contract: receiver/target model or role,
        selector, payload shape, expected result, declared effects,
        validation requirements, transfer policy and implementation query.
        A message descriptor describes when a message Structure may become an
        executable message. It does not execute the message by itself.

    RelationSpec
        typed relation descriptor: relation name, argument slots, argument
        types, admissible unknown/binding positions and validation rules.

    ValidatorSpec
        named contract descriptor: admissible input models/roles, guarantees,
        write-channel checks and read evidence.

    OperatorSpec
        operation descriptor: operator/receiver spelling, arity, argument
        matcher, result rule and lowering target.

    GenericMethodSpec
        selector/generic descriptor: abstract selector name, signature shape,
        accepted domain and dispatch query.

    BuildTargetSpec
        build descriptor: target name, kind, sources, entry, output artifact,
        profile and implementation target.

    EvidenceFact
        normalized registry fact derived from source descriptors, generated
        descriptors, runtime value construction, validator checks or imported
        persistent fact stores.

17.1. Level Responsibilities

L3 contains ordinary executable definitions and values. L3 may define concrete
`fn` and `sub` targets. Those targets are not executed merely because their
names appear in descriptors.

L4 consumes Structures as descriptor input. L4 may register or normalize:

    models;
    relation signatures;
    validators;
    operator descriptors;
    generic method descriptors;
    concrete type descriptors;
    layout descriptors;
    generated accessors/constructors/destructors;
    compiler/runtime metadata.

L4 does not directly perform ordinary runtime effects by default. Runtime effect
receivers such as file I/O, network send, process launch, database write,
ordinary runtime print and thread start are not visible from L4 unless a
compile-time diagnostic/model receiver explicitly exposes a non-runtime effect.

L5 consumes Structures as behavior, message, registry, build, query and startup
input. L5 may register or normalize:

    behavior descriptors;
    message descriptors, contracts and routes;
    message validation and dispatch evidence;
    role descriptors;
    adapter descriptors;
    facts;
    rules;
    queries;
    build targets;
    startup entries;
    service descriptors.

L5 may query descriptors and facts created by L4. L5 may add behavior and
domain facts. L5 may produce build/startup decisions. L5 is not a special
`project` file unless a project receiver is explicitly registered.

17.2. Required Descriptor Shapes

A `ModelSpec` must at least be able to represent:

    name
        registry name of the model.

    slots
        ordered structural fields.

    slot name
        semantic field name.

    slot type
        primitive type, pointer/reference type, model type, role type,
        validator type, union/domain type or profile-defined type expression.

    default value
        optional source Structure/value used when the field is not supplied.

    constraints
        validator links or condition Structures attached to the model or slot.

    layout policy
        implementation choice: inline component, pointer component, external
        resource, slice, array, arena-owned edge, borrowed edge or other
        profile-defined storage policy.

A `BehaviorSpec` must at least be able to represent:

    model or role name
        the registry entry whose behavior is being described.

    selector
        message/generic method name.

    input signature
        normalized argument descriptor.

    result signature
        normalized result descriptor.

    effect signature
        declared effect/effect-domain descriptor, such as pure, local state
        change, message send, I/O, build-time effect or profile-defined effect.

    implementation target
        concrete L3 `fn`/`sub` or implementation descriptor selected by the
        behavior entry.

    origin
        source descriptor that introduced the candidate.

    conflict policy
        local override, overload, drop, alias, prefer, replace or profile rule.

A `MessageSpec` must at least be able to represent:

    receiver or target requirement
        target model, role, service, thread, behavior entry or profile-defined
        receiver class accepted by the message.

    selector
        message name, receiver name, operation tag or event selector.

    payload signature
        normalized argument Structure descriptor, including field names,
        positional fields, validators and transfer requirements.

    result signature
        normalized result descriptor or reply payload descriptor.

    effect signature
        effect/effect-domain descriptor used by the type/evidence layer to
        decide whether the message is admissible in the current context.

    validation requirements
        facts, validators, capabilities, state predicates or other evidence
        required before the message may be executed or scheduled.

    implementation query
        registry/query shape that resolves the message to a concrete L3 target,
        L5 handler, service route or profile-defined action.

    transfer and scheduling policy
        copy/move/serialize/immutable-share policy, priority, ordering and
        optional reply/failure channel requirements.

A `RelationSpec` must at least be able to represent:

    relation name;
    argument count;
    positional argument names;
    argument type/evidence requirements;
    which positions may be unknown in a query;
    which validators apply to accepted bindings.

A `ValidatorSpec` must at least be able to represent:

    validator name;
    accepted concrete models;
    accepted roles/domains;
    required conditions;
    guarantees after successful validation;
    write-channel or read-channel where the validation applies.

An `OperatorSpec` must at least be able to represent:

    spelling;
    prefix/postfix/infix or receiver form;
    accepted argument shape;
    result type/evidence rule;
    lowering target or semantic receiver.

A `GenericMethodSpec` must at least be able to represent:

    selector;
    normalized input signature;
    normalized result signature;
    accepted domain or role;
    dispatch query over registry/evidence facts.

A `BuildTargetSpec` must at least be able to represent:

    target name;
    target kind;
    source list;
    entry name or entry query;
    output artifact;
    profile;
    selected L1/L0 implementation target.

17.3. Source Receivers That Create Descriptors

A `model` receiver consumes a Structure and produces or updates a `ModelSpec`.

Example:

L4:
    model: Circle
    . vars:
    . . f64: radius
    . condition:
    . . radius > 0.0
    end: Circle
end: L4

The normalized model must expose at least:

    model Circle
    slot Circle radius f64
    validator/condition Circle radiusGreaterThanZero

A `behavior` receiver consumes a Structure and produces or updates a
`BehaviorSpec`.

Example:

L5:
    behavior: Circle
    . message: drawOn drawCircleOn
    . message: area circleArea
    end: Circle
end: L5

The normalized behavior must expose at least:

    behavior Circle
    message Circle drawOn drawCircleOn
    message Circle area circleArea

A `validator` receiver consumes a Structure and produces or updates a
`ValidatorSpec`.

Example:

L5:
    validator: LightPassenger
    . accepts: Person
    . accepts: Alien
    . guarantee: weightLessThan 80
    end: LightPassenger
end: L5

The normalized validator must expose at least:

    validator LightPassenger
    accepts LightPassenger Person
    accepts LightPassenger Alien
    guarantee LightPassenger weightLessThan 80

A `relation` receiver consumes a Structure and produces or updates a
`RelationSpec`.

Example:

L4:
    relation: method
    . Symbol: genericName
    . Symbol: modelName
    . Symbol: implementationName
    end: method
end: L4

A `target` receiver consumes a Structure and produces or updates a
`BuildTargetSpec`.

Example:

L5:
    target:
    . app
    . kind: executable
    . sources: ("src/hello.lm3")
    . entry: hello
    . output: "build/bin/hello.lm0.exe"
    ---

    build: app
end: L5

The build receiver must resolve `app` through the target registry. It must not
infer the executable entry solely from the file name.

17.4. Registry Entry as Decomposed Class-Like Object

A class-like source concept is not a monolithic syntax category. It is a
registry entry accumulated from descriptors and facts attached to the same name.

For a registry name `Circle`, the registry may contain:

    ModelSpec
        slots and validators.

    BehaviorSpec
        selectors and method targets.

    ValidatorSpec links
        guarantees and accepted value evidence.

    Derivation descriptors
        constructors, accessors, serializers, copy/destroy operations and C
        layout projections.

    Relation facts
        role, union, adapter, method and build relations.

The parser does not know that this is a class-like object. It only produces
Structures. The active receivers build and normalize the descriptors.

18. Registry Facts and Evidence

18.0. Fact Store Rule

The registry is a typed fact store plus materialized descriptor views. A fact is
a normalized typed Structure. A descriptor may materialize facts, and facts may
materialize descriptor views. The source semantics require consistency between
these views, not one privileged physical storage form.

The following core fact shapes are mandatory for the registry/evidence model.
Exact concrete spelling may be profile-defined, but an implementation must be
able to represent the same information.

Model facts:

    fact: model ModelName
    fact: slot ModelName slotName SlotType
    fact: modelValidator ModelName ValidatorName
    fact: slotValidator ModelName slotName ValidatorName
    fact: layout ModelName layoutDescriptor

Behavior facts:

    fact: behavior ModelOrRoleName
    fact: message ModelOrRoleName selector implementationName
    fact: method ModelOrRoleName selector inputSignature implementationName
    fact: overload ModelOrRoleName selector inputSignature
    fact: override ModelOrRoleName SourceName selector inputSignature

Role and adapter facts:

    fact: role RoleName
    fact: roleMessage RoleName selector inputSignature
    fact: implements ModelName RoleName
    fact: delegates ModelName RoleName componentName
    fact: adapter SourceType TargetType adapterName

Validator and guarantee facts:

    fact: validator ValidatorName
    fact: accepts ValidatorName TypeOrRoleName
    fact: guarantee ValidatorName guaranteeName guaranteeValue
    fact: validates bindingOrContainerName ValidatorName

Value evidence facts:

    fact: valueModel valueName ModelName
    fact: valueSatisfies valueName ModelOrRoleOrValidatorName
    fact: valueSlot valueName slotName SlotType
    fact: valueMethod valueName selector inputSignature implementationName
    fact: valueGuarantee valueName guaranteeName guaranteeValue

Message evidence facts:

    fact: messageCandidate messageId
    fact: messageReceiver messageId receiverValueOrTarget
    fact: messageSelector messageId selector
    fact: messagePayload messageId payloadDescriptorOrValue
    fact: messageExpectedResult messageId resultDescriptor
    fact: messageEffect messageId effectDescriptor
    fact: messageRequires messageId validatorOrEvidence
    fact: messageValidated messageId ValidatorName
    fact: messageImplementation messageId implementationName
    fact: messageStatus messageId proposedOrTypedOrValidatedOrScheduled

Build facts:

    fact: target targetName
    fact: targetKind targetName kind
    fact: targetSource targetName sourcePath
    fact: targetEntry targetName entryName
    fact: targetOutput targetName outputPath

18.1. Evidence Graph

A composed working object/value is also an evidence graph.

The evidence graph is not a separate inheritance hierarchy and not a new
runtime heap model. It is the normalized registry-visible set of facts saying
that a concrete value, its fields, components, projections, validators, roles
and behavior entries satisfy particular descriptors.

For a concrete value, the evidence graph may contain:

    its concrete model;
    the fact that it satisfies its concrete model;
    roles it satisfies;
    validators it has passed;
    guarantees produced by those validators;
    slots known on the value;
    methods available for the value;
    adapters or projections available for the value;
    ownership/security/capability facts when the active profile supplies them;
    message candidates, message contracts and validated-message evidence when
        the value is used as a receiver, payload or proposed action.

Example concrete values:

L3:
    Button: okButton
    . label: "OK"
    . enabled: true
    ---

    ToggleButton: powerToggle
    . label: "Power"
    . enabled: true
    . checked: false
    ---
end: L3

After model construction, behavior registration and validator checks, an
implementation may expose:

L5:
    fact: valueModel okButton Button
    fact: valueModel powerToggle ToggleButton

    fact: valueSatisfies okButton Button
    fact: valueSatisfies powerToggle ToggleButton

    fact: valueSatisfies okButton ClickableRole
    fact: valueSatisfies powerToggle ClickableRole

    fact: valueSlot okButton label String
    fact: valueSlot okButton enabled bool

    fact: valueSlot powerToggle label String
    fact: valueSlot powerToggle enabled bool
    fact: valueSlot powerToggle checked bool

    fact: valueMethod okButton press (MouseEvent) buttonPress
    fact: valueMethod okButton press (KeyEvent) buttonKeyPress

    fact: valueMethod powerToggle press (MouseEvent) toggleButtonPress
    fact: valueMethod powerToggle press (KeyEvent) toggleButtonKeyPress

    fact: valueGuarantee okButton enabled true
    fact: valueGuarantee powerToggle enabled true
end: L5

The exact fact names are profile-defined. The mandatory rule is that a composed
working value can be consumed as evidence facts about that value.

18.2. Validator Evidence

Validator/type contracts use the same registry-fact mechanism. A validator
checks whether a Structure may be consumed in a declared role. The role may be a
value, binding, field, type parameter, operator operand, message receiver,
message payload, write channel, read view, handler candidate or profile-defined
consumption position.

A typed container or view does not become a generic container class merely
because it validates contents. The container remains storage. Registry facts
attach a named validator/contract to the value, binding, field, write channel,
message field or view that must be checked.

Example:

L5:
    fact: validator LightPassenger
    fact: accepts LightPassenger Person
    fact: accepts LightPassenger Alien
    fact: guarantee LightPassenger weightLessThan 80
    fact: validates passengers LightPassenger
end: L5

A write into `passengers` must satisfy `LightPassenger`. A value read from
`passengers` may carry registry-visible evidence that it satisfies
`LightPassenger`, including documented guarantees such as `weightLessThan 80`.
IDEs and diagnostics should show these guarantees as part of the value's
available type information.

The same mechanism validates messages. A raw or proposed message is not yet an
action. It becomes a typed or validated message only when the registry/evidence
layer proves that its receiver, selector, payload, result, effect and
implementation requirements are satisfied. This is analogous to Haskell-style
constraint/evidence resolution: the message Structure is accepted only when the
required evidence is available, derivable or explicitly checked at validation
time.

18.3. Evidence Lifetime and Invalidations

Evidence is valid only while the facts that produced it remain valid.

An implementation must invalidate or recompute evidence when:

    a value is mutated in a way that can break a validator;
    a slot used by a guarantee changes;
    ownership/capability evidence expires;
    a behavior descriptor is replaced during a build/runtime update;
    an adapter/projection changes its source component;
    a persistent fact store reloads or invalidates facts;
    a proposed or typed message depends on receiver, payload, capability,
        permission, state or implementation evidence that has changed before
        the message is scheduled or executed.

A profile may choose static-only evidence, runtime evidence, cached evidence or
persistent evidence. It must define when cached evidence becomes stale.

19. Entry Composition and Conflict Resolution

19.0. Entry Receiver Status

The `entry` receiver is a compact registry-construction form. It may gather
structural properties and behavior candidates in one source block. It is not an
inheritance form and it does not change P0 syntax.

The parser builds an ordinary Structure. The `entry` receiver normalizes that
Structure into `ModelSpec`, `BehaviorSpec`, facts, roles, adapters and
derivations.

19.1. Entry Short Form

Example:

    entry: Button import: Widget Clickable
    . drop:
    . . slot: Widget theme
    . alias:
    . . slot: Widget enabled widgetEnabled
    . vars:
    . . String: label
    . . bool: enabled true
    . methods:
    . . draw: (Canvas(c)) buttonDraw override(Widget)
    . . press: (MouseEvent(e)) buttonPress override(Clickable)
    . . press: (KeyEvent(e)) buttonKeyPress overload
    end: Button

The first field after `entry` is the introduced registry name. `import:` is an
ordinary named argument frame. It lists sources whose model and behavior
candidates are imported into the new registry entry.

    entry: Button import: Widget Clickable

means:

    introduce registry entry `Button`;
    import structural slot candidates from `Widget` and `Clickable`;
    import behavior candidates from `Widget` and `Clickable`;
    apply local exclusions, aliases, slots and methods.

This is multiple source import into one registry entry. It is not subtype
inheritance. A `Button` value is not automatically assignable to a `Widget`
value unless a role, delegation, component projection, union membership or
adapter relation says so explicitly.

19.2. Normalized Descriptor View

The example may normalize conceptually to:

L4:
    model: Button
    . import: Widget Clickable
    . drop:
    . . slot: Widget theme
    . alias:
    . . slot: Widget enabled widgetEnabled
    . vars:
    . . String: label
    . . bool: enabled true
    end: Button

L5:
    behavior: Button
    . import: Widget Clickable
    . draw: (Canvas(c)) buttonDraw
    . press: (MouseEvent(e)) buttonPress
    . press: (KeyEvent(e)) buttonKeyPress
    end: Button

L5:
    fact: imports Button Widget
    fact: imports Button Clickable
    fact: override Button Widget draw (Canvas)
    fact: override Button Clickable press (MouseEvent)
    fact: overload Button press (KeyEvent)
    fact: aliasSlot Button Widget enabled widgetEnabled
    fact: dropSlot Button Widget theme
    fact: implements Button WidgetRole
    fact: implements Button ClickableRole
end: L5

The exact fact names are profile-defined. The mandatory rule is that the
compact `entry` form decomposes into explicit registry descriptors and evidence
facts.

19.3. Member Keys and Origins

Composition is checked over normalized member keys.

For structural slots:

    slot key = normalized slot name

For methods:

    method key = selector + normalized input signature + normalized result signature

Each imported candidate carries an origin:

    origin = source entry descriptor + member kind + member key

Origins distinguish a harmless diamond from a real conflict.

19.4. Conflict Rules

Composition must not use silent last-wins behavior.

Required conflict rules:

    same imported origin through multiple paths
        collapses to one candidate.

    same slot key from different origins
        conflict unless `drop`, `alias`, `replace` or a profile-defined merge
        rule resolves it explicitly.

    same method key from different origins
        conflict unless `override`, `prefer`, `drop` or another explicit rule
        resolves it.

    same method selector with a different signature
        allowed only when the local declaration or imported descriptor marks
        the relation as `overload`.

    local member with the same key as an imported candidate
        requires `override(...)` or `replace(...)`; otherwise it is a duplicate
        definition error.

    local member with the same selector and a different method signature
        requires `overload`; otherwise it is an accidental overload error.

The import source order may be used for deterministic diagnostics. It must not
choose the winner of a semantic conflict by itself.

19.5. Exclusion, Alias, Override and Overload

The composition profile uses these control forms:

    drop
        removes an imported candidate before final conflict checking.

    alias
        imports a candidate under a new local name or selector.

    override(Source)
        replaces the imported method candidate with the same method key from
        `Source`.

    prefer(Source)
        selects one imported implementation when two sources provide the same
        method key and the profile permits imported selection.

    replace(Source)
        replaces an imported slot or method explicitly.

    overload
        admits a method with the same selector but a different signature.

Example:

    entry: ToggleButton import: Button Switch
    . drop:
    . . method: Switch draw (Canvas)
    . alias:
    . . slot: Button enabled buttonEnabled
    . vars:
    . . bool: checked false
    . methods:
    . . draw: (Canvas(c)) toggleButtonDraw override(Button)
    . . press: (MouseEvent(e)) toggleButtonPress override(Button)
    . . press: (KeyEvent(e)) toggleButtonKeyPress overload
    end: ToggleButton

Here `ToggleButton` imports candidates from `Button` and `Switch`, removes the
`Switch.draw` candidate, preserves `Button.enabled` under another local slot
name, overrides the imported mouse `press`, and explicitly adds a key-event
overload.

20. Consumption Modes

20.0. Rule

A composed object/value can be consumed in several modes. Each mode consumes the
same descriptors and evidence facts differently. The modes do not create
separate object systems.

A message is the common Structure used by the object/event, type/evidence,
procedural and logical layers. A message is not an action merely because it
exists. A message may be proposed by a logical rule, built by an object/event
receiver, checked by the type/evidence layer, scheduled by the runtime and only
then executed by the procedural machine.

The required modes are:

    procedural consumption
        executes a selected concrete L3 `fn` or `sub` target.

    object/event consumption
        builds or accepts a message Structure and selects a message behavior
        implementation by message dispatch.

    type/evidence consumption
        validates a raw or proposed message Structure against target, selector,
        payload, result, effect, capability and implementation requirements,
        producing a typed/validated message with evidence.

    functional/expression consumption
        resolves a generic expression or operator over abstract data types.

    logical consumption
        treats descriptors/evidence as facts and derives bindings, answers,
        evidence, diagnostics or proposed message Structures.

Only messages admitted by the active validation/scheduling profile may be
executed. Logical prediction proposes messages; it does not execute them.

20.1. Procedural Consumption

Concrete L3 targets are ordinary procedures/functions.

Example:

L3:
    sub: buttonPress
        # concrete procedure body omitted
    end: buttonPress

    sub: toggleButtonPress
        # concrete procedure body omitted
    end: toggleButtonPress
end: L3

Behavior descriptors register these names as implementation candidates for
normalized selectors and signatures. They do not execute the procedures merely
because the names exist.

20.2. Object/Event Consumption

An object/event receiver consumes the evidence graph to build, validate and
resolve a message. The source form creates a message candidate. The validation
layer must prove that the receiver, selector, payload and effects satisfy the
registered message contract before the procedural target is invoked.

Example:

    send: okButton press MouseEvent(...)

Conceptual raw message:

RawMessage
    receiver: okButton
    selector: press
    payload: MouseEvent(...)
---

Conceptual validation/lookup:

    value          = okButton
    selector       = press
    signature      = MouseEvent
    model          = registry valueModel(okButton)
    role/evidence  = registry valueSatisfies(okButton, ClickableRole)
    payloadCheck   = registry payload satisfies MouseEvent
    implementation = registry valueMethod(okButton, press, MouseEvent)
    result/effect  = registry message result/effect descriptors

Result:

ValidatedMessage
    receiver: okButton
    selector: press
    payload: MouseEvent(...)
    implementation: buttonPress
    evidence:
        valueSatisfies okButton ClickableRole
        payloadSatisfies MouseEvent
        messageAccepted press (MouseEvent)
---

The procedural machine then executes the selected concrete target:

    buttonPress(okButton, MouseEvent(...))

For:

    send: powerToggle press MouseEvent(...)

the same validation/lookup resolves to:

    toggleButtonPress(powerToggle, MouseEvent(...))

If the concrete model is known statically, a translator may lower directly to
the concrete L3 target after validation. If the value is known only through a
role/reference, the translator may lower through a behavior table, method lookup
cache or another selected profile strategy.

20.3. Functional/Expression Consumption

A functional/expression receiver consumes the same evidence graph differently.

Assume a generic expression written against an abstract clickable value:

    press(control, event)

This expression does not name `buttonPress` or `toggleButtonPress` directly. It
asks the registry/evidence graph which pure or admitted operation is available
for the concrete value currently bound to `control`.

For:

    control = okButton
    event   = MouseEvent(...)

the resolver may query:

    valueSatisfies control ClickableRole
    valueMethod control press (MouseEvent) ?implementation

and resolve:

    implementation = buttonPress

For:

    control = powerToggle
    event   = MouseEvent(...)

the same generic expression resolves:

    implementation = toggleButtonPress

Thus a generic expression over an abstract data type is not a separate language
mechanism. It is a Structure consumed against the evidence graph of concrete
values and registry descriptors.

20.4. Logical Consumption

A logical receiver consumes the same graph as facts.

Example query:

    query:
    . valueSatisfies ?value ClickableRole
    . valueMethod ?value press (MouseEvent) ?implementation
    end: query

Possible solutions:

    ?value = okButton
    ?implementation = buttonPress

    ?value = powerToggle
    ?implementation = toggleButtonPress

No message is dispatched by this query. No button is pressed. Logical mode only
consumes the evidence graph and derives bindings.

Logical mode may also propose new messages from facts, goals and rules. A
proposed message is data until it is accepted by type/evidence validation and
scheduling.

Example conceptual proposal:

query:
. valueSatisfies ?value ClickableRole
. valueGuarantee ?value enabled true
. goal: userWantsClick ?value
. propose:
. . message:
. . . receiver: ?value
. . . selector: press
. . . payload: MouseEvent(...)
end: query

The proposed message then returns to the validation path described by
object/event consumption. The query itself does not execute the proposed
message.

20.5. Generic Dispatch as Query

Generic dispatch may be derived by querying registry facts.

For a call:

    draw: shape

where `shape` has type/evidence `Shape`, the translator may query:

    variant: Shape ?model
    method: draw ?model ?implementation

For a concrete call:

    Circle: c
    draw: c

the translator may query:

    method: draw Circle ?implementation

and lower directly to the returned implementation.

20.6. Message Lookup and Validation as Query

Message lookup and message validation may also be represented as queries over
facts. This gives the message layer a Haskell-like evidence shape: a message may
be executed only when the resolver can derive the constraints/evidence required
by its receiver, selector, payload, result and effects.

For a send:

    shape: drawOn canvas

where `shape` has model evidence `Circle`, the runtime or translator may query:

    valueModel: shape Circle
    message: Circle drawOn ?implementation
    payloadAccepted: drawOn canvas ?payloadEvidence
    messageEffect: drawOn ?effect
    messageResult: drawOn ?result

and produce a validated message containing the returned implementation and
validation evidence. The implementation is called only after this validation
step:

    drawCircleOn(shape, canvas)

A profile may combine lookup and validation into one query relation such as
`message_handler` or `message_accepts`, but it must preserve the distinction
between a raw/proposed message and an executable validated message.

20.7. Query, Rules and Unification

A query asks for bindings that satisfy relation Structures. Unknowns such as
`?model`, `?implementation` and `?value` are logical variables interpreted by
relational receivers. They are not ordinary uninitialized variables.

A rule defines a relation in terms of other relations.

Example conceptual form:

rule:
    completeGeneric: draw Shape
    if:
        variant: Shape ?model
        method: draw ?model ?implementation

The exact syntax for rule heads, rule bodies, conjunction, disjunction,
negation and aggregation belongs to the relation/query receiver profile.

Unification attempts to make two relation Structures compatible by assigning
unknowns. It respects:

    relation name;
    argument count;
    positional order;
    semantic named fields when used;
    L4 relation signatures;
    contracts and constraints when attached.

A query returns a Structure, for example:

QueryResult
    bindings
        binding: ?model Circle
        binding: ?implementation drawCircle
    ---
    status: success

21. Lowering and Physical Implementation

21.0. Compilation Pipeline

Compilation means:

    Lingvamyxa source
        -> P0 generic Structures
        -> receiver normalization
        -> typed registry descriptors and evidence facts
        -> type/evidence/query checking
        -> L1 projection or another implementation target
        -> L0 artifact

This document specifies the source-semantic side of that pipeline. The exact L1
syntax, L1 file format, L1 compiler interface and L0 build mechanism are
implementation profile details.

21.1. Source File Extensions

Lingvamyxa source files may use:

    *.lm2    L2-only source
    *.lm3    L3-only source
    *.lm4    L4-only source
    *.lm5    L5-only source
    *.lmx    mixed Lingvamyxa source

Generated/debuggable projections may exist for translator diagnostics and
verification. Their exact format and file extensions are implementation-defined.

21.2. Per-Level Build Semantics

L2 sources are unsafe modules/libraries/objects. They are compiled, not
interpreted as scripts.

L3 sources may be interpreted or compiled. A top-level L3 sequence may become
an implicit executable entry.

L4 sources are checked, loaded and registered as model/contract/registry input.
They are not launched as programs.

L5 sources are message/configuration/build/startup/query inputs consumed by L5
receivers.

Mixed `.lmx` sources are handled according to level receivers and entry rules.
L5 entry messages take precedence if present; otherwise an L3 top-level
sequence may become an implicit entry if the builder allows it.

21.3. Logical Argument Structure

Every source call has one logical argument Structure.

Example:

    mySub(1, 2, 3, 4)

Logical source semantics:

    mySub(
      field0(1),
      field1(2),
      field2(3),
      field3(4)
    )

The logical Structure always exists at the source-semantic level. A translator
may optimize away the physical Structure if observable source semantics are
preserved.

For ordinary direct `fn`/`sub` call lowering, a single top-level
bounded/anonymous Structure supplied as the whole call argument Structure is
the canonical spelling of "use these N fields as the call arguments". This
exception exists because the call argument list itself is a Structure, so a
one-field argument list containing only one Structure is otherwise
indistinguishable from that Structure used as the physical argument-list
wrapper. This is a one-level argument-list equivalence only; it is not
evaluation or execution of that Structure.

21.4. Return Lowering Independence

A return signature defines a source-level return value: either a primitive
value, pointer/reference value or a return Structure. The translator may choose
any physical return strategy that preserves this source-level result.

The same one-level wrapper equivalence may apply to returns when the selected
receiver/profile explicitly defines that physical lowering. It is still not
execution of a Structure.

21.5. Type Reconciliation Algorithm

When a receiver, assignment target, message argument, field, validator, message
contract or query expects type/evidence `E` and the source expression or message
Structure produces type/evidence `A`, the translator should return a typed match
result, not just a boolean.

The result must distinguish at least:

    exact match;
    named-field unpack;
    explicit component projection;
    role/delegation match;
    validator evidence match;
    union/domain membership;
    explicit adapter/conversion;
    message contract match;
    rejection.

Suggested order:

    1. If E and A are the same concrete type/evidence, accept exact match.

    2. If E is a concrete model and the source is a Structure, match source
       fields to model fields by name, then check each field recursively.

    3. If A contains a component of type E, accept only when the source
       expression explicitly requests that component, for example `oak\plant`.

    4. If E is a role/protocol/reference type, query the registry for an
       implementation or delegation relation from A to E.

    5. If E is a validator/contract, require proof that A satisfies that
       validator or insert a validation step when the profile permits runtime
       validation.

    6. If E is a union/domain and A is a listed member, wrap A with the union
       tag/descriptor.

    7. If an explicit adapter exists and the active profile permits it, lower
       through the adapter.

    8. If E is a message contract, reconcile the receiver, selector, payload,
       result, effect, capability and implementation requirements. If all
       required evidence is available, return a validated-message match carrying
       that evidence and the selected implementation. If some requirements are
       permitted runtime checks, return a typed message plus required validation
       steps. Otherwise reject.

    9. Otherwise reject and report expected type/evidence, actual type/evidence
       and available explicit projections/adapters/validators/message contracts.

Multiple assignment and Structure consumption are named-field unpacking. They
are not inheritance and not implicit structural subtyping.

Message validation is a type/evidence reconciliation over a Message Structure.
It may transform a RawMessage or ProposedMessage into a TypedMessage or
ValidatedMessage. It must preserve why the validation succeeded: target role,
payload validator, capability, effect permission, result descriptor and selected
implementation are evidence, not hidden side effects.

21.6. ANSI C Projection Profile

An ANSI C based translator may use this implementation pipeline:

    Lingvamyxa source
        -> P0 generic Structures
        -> receiver normalization
        -> typed registry descriptors and evidence facts
        -> generated ANSI C projection
        -> platform C compiler/linker
        -> L0 artifact

For every concrete `ModelSpec`, an ANSI C translator should prefer ordinary C
structs and typed pointers for concrete normalized models.

Example:

L4:
    model: Plant
    . vars:
    . . f64: height
    . . i32: age
    ---

    model: Oak
    . vars:
    . . Plant: plant
    . . i32: acornCount
    ---
end: L4

One possible C99 projection:

---ANSI C---
    typedef struct LmPlant {
        double height;
        int32_t age;
    } LmPlant;

    typedef struct LmOak {
        LmPlant plant;
        int32_t acornCount;
    } LmOak;
---ANSI C---

This is composition. It is not inheritance.

Behavior calls may lower directly when statically known:

---ANSI C---
    lm_circle_area(&circle);
---ANSI C---

Role or dynamic behavior calls may lower through a behavior table:

---ANSI C---
    ref.behavior->area(ref.object, args);
---ANSI C---

Both forms are implementation choices for the same source-level rule: behavior
is resolved from registry facts and descriptors, not from implicit C struct
inheritance.

21.7. ANSI C Projection API Shape

A C99 translator should expose a projection layer that consumes typed
descriptors, not raw parser nodes.

Conceptual API:

---ANSI C---
    int lm1_emit_struct_decl(
        LmWriter *out,
        const char *c_name,
        const LmModelSpec *model);

    int lm1_emit_struct_typedef(
        LmWriter *out,
        const char *c_name,
        const LmModelSpec *model);

    int lm1_emit_type_ops(
        LmWriter *out,
        const char *c_name,
        const LmModelSpec *model);
---ANSI C---

Type checking should expose the selected lowering path:

---ANSI C---
    typedef enum LmTypeMatchKind {
        LM_TYPE_MATCH_EXACT,
        LM_TYPE_MATCH_NAMED_UNPACK,
        LM_TYPE_MATCH_COMPONENT_PROJECTION,
        LM_TYPE_MATCH_ROLE_DELEGATION,
        LM_TYPE_MATCH_VALIDATOR_EVIDENCE,
        LM_TYPE_MATCH_UNION_MEMBER,
        LM_TYPE_MATCH_ADAPTER,
        LM_TYPE_MATCH_REJECT
    } LmTypeMatchKind;

    typedef struct LmTypeCheckResult {
        LmTypeMatchKind kind;
        LmTypeId expected;
        LmTypeId actual;
        LmSymbol projection_field;
        LmSymbol adapter_name;
        LmSymbol validator_name;
        LmDiagnostic diagnostic;
    } LmTypeCheckResult;
---ANSI C---

The exact ABI is implementation-defined. The important rule is that type and
evidence checking must preserve why a match succeeded.

21.8. Memory Model Connection

For every concrete `ModelSpec`, the implementation may derive:

    destroy
        release owned/external fields according to edge policies.

    copy_to
        copy a value into another owner/arena.

    tree_cut
        maintain deferred owner-copy and lazy-owned edges when a local branch
        is cut or detached.

    serialize
        materialize messages or service-boundary payloads.

    field_projection
        provide explicit component projection helpers.

Inside one parser tree, arena or L5 Thread owner, ordinary typed C pointers are
allowed. Owner metadata is needed at owner roots and cross-owner edges, not on
every local child pointer.

21.9. Lmx Codec Receivers

Every language value should have a Lingvamyxa-native codec path:

    toLmx: value
    fromLmx: lmx
    fromLmx: lmx Type

`toLmx` produces a canonical Lingvamyxa representation of a value.
`fromLmx: lmx` parses or decodes Lmx representation into generic Structures
and scalar atoms. `fromLmx: lmx Type` parses or decodes Lmx representation and
then consumes the result through the expected type receiver, validator or
registry descriptor.

This codec contract applies to everything in the language, including primitive
values, strings/text, exact identifiers, generic Structures, concrete model
values, arrays, slices, validated containers, registry facts, descriptors,
messages and service payloads.

The important rule is:

    Lmx representation is data.
    P0 structural parsing and operator-tokenization build Structures.
    Type receivers and validators grant typed meaning.

21.10. Fact Persistence

Facts may accumulate faster than source modules. Persistent fact storage may be
separate from source files.

Recommended division:

    signatures/contracts/rules       -> L4/L5 source modules
    generated registry facts         -> compiler/runtime registry
    accumulating domain facts        -> persistent store or database backend
    query/relation engine            -> receiver layer over Structures and storage backend

SQLite or another database may be used as a backend, but it is not part of the
core syntax.

23. L4/L5 Canonical Examples
23.4. L5 Conditional Build

Source:

L5:
    if: mode = debug
        then:
            build: debugTarget
        else:
            build: releaseTarget
end: L5

Conceptual form:

    L5(
      if(
        <expression Structure for `mode = debug`>,
        (build(debugTarget)),
        (build(releaseTarget))
      )
    )

The semantic roles `condition`, `then` and `else` are assigned by the active `if` receiver signature.

23.5. Operator Registration

Source:

L4:
    operator:
        if
        callableFrom: L5
        implementation: l5_if
end: L4

Semantic outline:

    `L4` consumes the body as model/registry input.
    `operator` registers the receiver name `if`.
    `callableFrom: L5` sets visibility.
    `implementation: l5_if` names the implementation receiver/subroutine.

23.6. L5-if Implementation Subroutine

Source:

sub: l5_if (boolean(condition)) then else
return

Conceptual form:

        else
      ),
      body(...)
    )

27. L5 Thread and Message Model

27.0. Scope

The L5 Thread model defines the default high-level execution and communication
model of Lingvamyxa. It is the companion of the section 30 memory model and the
registry/evidence model from sections 17-21.

An L5 Thread is not necessarily an operating-system thread. It is a logical
execution unit with isolated state, a local arena graph, an execution context
and a message queue. An implementation may lower an L5 Thread to an OS thread,
a fiber, a coroutine, an event-loop task, an actor, an embedded scheduler
entity or another runtime execution unit.

The semantic requirement is isolation, not a particular scheduler primitive:

    L5 Thread -> isolated execution tree + local memory graph + message queue

No raw reference owned by one L5 Thread may point directly into another L5
Thread. Inter-thread communication is by typed messages, whole-branch transfer,
serialization or implementation-approved immutable sharing.

Terminology in this section is strict:

    L5 Thread
        the source-semantic active unit visible to L3/L4/L5 programs, UI code,
        event-driven code and services.

    L2 Thread
        a future low-level Lingvamyxa primitive for implementation-facing
        operations such as explicit concurrency over shared memory arrays.

    L1 Thread
        a host/substrate thread or task used by the external L1 implementation
        and by the L1-L2 runtime binding.

L1 Threads and future L2 Threads are not visible as ordinary programming
objects above L2. A runtime may map one or more L5 Threads to L1/L2 threads,
fibers, event loops or platform tasks, but that mapping does not change the
source-semantic L5 Thread model.

27.1. L5 Thread

An L5 Thread owns:

    root state;
    current handler frame;
    current ExecutionContext;
    message queue;
    optional outbox or delivery buffer;
    local branch arenas;
    temporary frame/handler arenas;
    local immutable value store or intern table, if supplied by the profile;
    local registry view/cache, if supplied by the profile;
    local failure/event queue, if supplied by the profile.

An L5 Thread may process one handler at a time by default. This gives the
default L5 profile single-threaded reasoning inside each isolated execution
tree. Parallelism is obtained by creating multiple L5 Threads and exchanging
messages between them.

The implementation may execute several L5 Threads on the same OS thread, or one
L5 Thread per OS thread, or use a work-stealing/event-loop implementation. This
does not change the source-level rule that L5 Threads do not share mutable raw
references.

27.2. Root State

The root state is the durable state of an L5 Thread. Long-lived owned branches
that must survive a single message handler are reachable from the root state or
from another branch reachable from the root state.

Values created inside a handler are temporary unless they are:

    stored into root state as owned values;
    copied into an owned branch reachable from root state;
    transferred as a whole owned branch to another L5 Thread;
    returned through a reply/future/result mechanism;
    explicitly retained by a profile-defined persistent store.

A borrowed value received from another owner or another message frame may not
be stored in root state as a raw borrow. To retain it, the program must create
an owned copy or receive ownership of the whole branch.

27.3. Handler Frame and ExecutionContext

A handler frame is the dynamic execution frame created when an L5 Thread
processes a message. It has its own temporary arena or temporary allocation
epoch.

The handler frame may contain:

    parameters and message payload views;
    local variables;
    temporary Structures;
    temporary query results;
    continuation state for yield/await-like receivers;
    failure/status state;
    cleanup records for owned local resources.

When the handler completes normally or by failure, frame-local temporaries are
released as a group and owned local resources are cleaned in reverse
initialization order. Borrowed payloads do not extend the lifetime of their
source.

Each L5 Thread owns one current ExecutionContext. The ExecutionContext is
thread-local runtime infrastructure, not an ordinary user data model.

Conceptual Structure:

ExecutionContext:
    Thread: currentThread
    CleanupStack: cleanupStack
    DiagnosticRoot: diagnosticRoot
    Diagnostic: currentDiagnostic
    FrameDepth: currentDepth

The ExecutionContext stores active `finally` cleanup registrations for the
current thread. It also stores the diagnostic root used by `assert` and other
thread-root diagnostic exits.

27.4. Cleanup Stack and Control Exit

A cleanup stack is a LIFO stack of active cleanup entries.

Conceptual entry:

CleanupEntry:
    cleanupSub
    cleanupEnv
    frameDepth
    scopeDepth

`finally` pushes a cleanup entry into the current thread ExecutionContext.

Normal frame/scope exit runs cleanup entries owned by the exited frame/scope.
Diagnostic thread exit runs all remaining cleanup entries in the current
thread. Cleanup entries are removed when they are executed. A cleanup must not
execute twice.

Cleanup is part of handler/frame lifetime. It is not a hidden cross-thread
exception mechanism. If cleanup failure is admitted by a profile, that failure
must be represented by ordinary failure/status/diagnostic data for the current
thread or handler.

27.5. Message Structure

A message is a Structure that may become executable only after validation. A
profile may choose exact field names, but the conceptual fields are:

    receiver          target L5 Thread, object, behavior or service selector;
    selector          message name / receiver name / operation tag;
    payload           typed or untyped argument Structure awaiting validation;
    expected result   optional result/reply descriptor;
    effect descriptor optional effect/effect-domain descriptor;
    validation        required validators, capabilities, permissions or state facts;
    implementation    selected handler target after validation/dispatch;
    transfer mode     copy, move, serialize, immutable-share or profile-defined mode;
    reply channel     optional Future/Task/reply receiver;
    failure channel   optional failure receiver or result sink;
    priority          optional scheduling priority;
    ordering key      optional stable ordering key;
    metadata          profile-defined tracing, security, capability or scheduling data.

The payload is a Structure, not a raw pointer bag. The receiver consumes the
Structure according to its registered receiver signature, type model and message
descriptor.

A message may pass through conceptual states:

    ProposedMessage
        a candidate produced by logic, UI, another message handler or another
        receiver. It is data only.

    RawMessage
        a constructed message Structure whose fields have not yet been fully
        validated.

    TypedMessage
        a message whose receiver, selector and payload have been assigned
        type/evidence descriptors, but which may still require runtime checks.

    ValidatedMessage
        a message whose required evidence has been proved or checked and whose
        implementation/result/effect descriptors are known.

    ScheduledMessage
        a validated message accepted by the scheduler or queue profile.

    ExecutedMessage
        a message consumed by the procedural execution target.

    FailedMessage
        a message rejected by validation, scheduling or execution.

Only a message state admitted by the active validation/scheduling profile may be
placed in an executable queue. Logical prediction and message construction do
not execute messages.

27.6. Message Transfer Modes

The standard conceptual transfer modes are:

    copy
        Deep-copy the payload into the receiver-owned arena, receiver message
        arena or another receiver-local owner.

    move
        Transfer ownership of a whole owned branch arena from the sender to the
        receiver. Sender-side raw references/handles into that branch become
        invalid after transfer.

    serialize
        Encode the payload into bytes/text/records, then reconstruct it in the
        receiver. This is the default safe form across process, machine,
        storage or untrusted boundaries.

    immutable-share
        Share an immutable value handle only when the implementation profile
        guarantees immutability, thread-safe publication and lifetime stability.

    external-handle
        Pass a descriptor/capability to an explicit low-level or external
        resource. The resource itself is not an ordinary mutable L5 branch.

The default safe transfer mode is copy or serialization. Move is an optimization
and a semantic transfer of ownership. Immutable-share is valid only for values
that cannot be mutated through any alias. Shared mutable data is outside the
default L5 model and must be represented through explicit L2/L3 synchronization
or a checked higher-level abstraction.

27.7. Borrowed Payloads

Received payloads are borrowed by default during handler execution. A borrowed
payload is valid only for the current handler frame, message frame, arena epoch
or owner lifetime that produced it.

The no-escaping-borrow rule applies:

    a borrowed payload may not be stored in root state;
    a borrowed payload may not be sent as a raw reference to another L5 Thread;
    a borrowed payload may not be retained by a continuation unless its
        owner/arena lifetime covers the continuation;
    a borrowed payload may not outlive the message or branch that owns it.

To keep received data after the handler returns, the handler must perform
owner-copy into its own L5 Thread memory graph or receive/move a whole owned
branch.

27.8. Queue, Inbox/Outbox and Scheduling

Each L5 Thread owns at least one conceptual message queue. The default
scheduling profile is deterministic:

    messages are processed one handler at a time;
    FIFO ordering is used within equal priority;
    equal ordering keys preserve stable insertion order;
    a handler runs until it returns, fails, yields or awaits;
    no other handler mutates the same L5 Thread root state concurrently.

A profile may add priorities, deadlines, fairness windows, cooperative yields,
preemption points or real-time scheduling. Such profiles must specify whether
they preserve deterministic ordering.

The default L5 model avoids data races by construction: root state is local to
one L5 Thread and is mutated by at most one active handler in the default
profile.

Canonical cooperative thread loop:

initialize ExecutionContext
establish diagnostic root

while: running
    checkInbox
    body
    flushOutbox


run all remaining finally cleanups
terminate thread

The loop is conceptual. A runtime may lower it to an OS thread, event-loop task,
actor turn, fiber or scheduler step if the same L5 message and cleanup semantics
are preserved.

Sending a message validates/schedules a message according to the active profile,
appends the admitted message to a synchronized FIFO container and returns.

Basic operation:

    send: target message

Semantic effect:

    build or accept a Message Structure;
    validate the message contract when the profile requires immediate validation;
    append the admitted message to the target thread inbox;
    do not execute the handler in the sender thread;
    return immediately.

An implementation may use an outbox as a physical batching layer:

    enqueue message into current thread outbox;
    later flush the outbox into target inboxes.

The outbox is optional. The source-level message model requires asynchronous
delivery and transfer semantics, not a particular buffering strategy.

Handlers must not execute while the inbox synchronization lock is held.

Safe pattern:

localMessages: drain inbox under lock

each: message in localMessages
    dispatchMessage: message

Unsafe pattern:

synchronized inbox
    dispatchMessage: message

The unsafe pattern is forbidden by this profile because it executes user/L5
behavior while holding the inbox lock.

27.9. Dispatch and Validation as Registry Query

Message dispatch is not special object magic. It is resolved through receiver
signatures, descriptors and the logical registry/query layer. The same query
layer may validate the message before dispatch.

A dispatch/validation query may use facts such as:

    receiver type;
    receiver role/evidence;
    selector name;
    payload type/evidence;
    protocol/behavior descriptor;
    capability descriptor;
    visibility level;
    expected result descriptor;
    effect descriptor and effect permission;
    target implementation;
    failure contract;
    transfer policy;
    current state facts admitted by the profile.

Conceptual query:

query:
    relation: message_accepts
    receiver: ?receiverType
    selector: parse
    payload: SourceText
    result: ?resultType
    effect: ?effect
    implementation: ?impl
    evidence: ?evidence

The result of this query is a typed/validated message descriptor. The handler
implementation is invoked by the scheduler only after the message has the
evidence required by the active profile. This is the message analogue of
Haskell-style constraint resolution: a message send is accepted only when the
registry can derive the required receiver, selector, payload, effect, result and
implementation evidence, or when the profile inserts explicit runtime
validation steps.

Generic dispatch, behavior lookup, operator/message specialization and
validation may all use the same registry facts and relation rules described in
sections 18 and 20.

If the target belongs to the current thread and the source form is a local L5
message, the translator/runtime may use direct synchronous dispatch as an
optimization after validation. If the target belongs to another thread or the
source form is an explicit event send, delivery is asynchronous through the
target inbox.

27.10. Reply, Future and Task Structures

A message may request a reply. The reply mechanism is represented by a typed
Structure rather than by hidden control flow.

Conceptual forms:

    Result T E      completed value or failure;
    Future T E      pending result with a reply channel;
    Task T E        scheduled computation with continuation state;
    ReplyChannel    receiver/message target for result delivery.

A request is an asynchronous send with a correlation id and reply target. A
reply is an ordinary message carrying the same correlation id.

Request flow:

    requester sends request message to target inbox;
    requester continues executing its thread loop;
    target eventually handles request;
    target sends reply message to requester inbox;
    requester eventually handles reply during ordinary message processing.

No thread blocks waiting for a reply in the base profile. A synchronous call is
a profile-level convenience over message sending plus waiting for a reply inside
the same scheduler domain. Such a profile must define timeout, cancellation,
inbox-pumping wait and deadlock behavior. An asynchronous call sends a message
and receives a Future/Task-compatible Structure.

Reply payloads obey the same transfer rules as ordinary message payloads: copy,
whole-branch move, serialization or immutable-share.

27.11. Failure Propagation, Assert and Diagnostics

Failures are not hidden cross-thread exceptions. A failure crossing an L5 Thread
boundary is represented as a typed message/result/failure Structure.

Inside one handler, a profile may use local failure control such as
guard/fail/throws/handler labels, as described by the failure model. Across L5
Thread boundaries, the failure must be materialized as data:

    Result\Err;
    failure message;
    rejected Future/Task;
    reply-channel failure payload;
    profile-defined event.

This preserves the no-raw-reference and no-hidden-cross-thread-control-flow
rules.

When an L3 `assert` condition is false in the default thread profile:

    an AssertionViolation diagnostic is created;
    active cleanups in the current thread ExecutionContext are executed;
    control transfers to the thread diagnostic root;
    the current thread/task terminates by default after diagnostic reporting.

In an ANSI C runtime, the transfer may be implemented by `setjmp` at the thread
root and `longjmp` from the assertion failure path.

---ANSI C---
Conceptual implementation:

    typedef struct ExecutionContext {
        CleanupStack cleanupStack;
        jmp_buf diagnosticRoot;
        Diagnostic currentDiagnostic;
    } ExecutionContext;

    _Thread_local ExecutionContext *LX_CTX;

    void lx_assert_fail(Diagnostic d) {
        ExecutionContext *ctx = LX_CTX;
        ctx->currentDiagnostic = d;
        run_all_cleanups(ctx);
        longjmp(ctx->diagnosticRoot, 1);
    }

This implementation note does not define ordinary `fail`. Declared `fail`
remains structured recoverable control flow.
---ANSI C---

27.12. Await and Continuations

`async` and `await`, if provided by a profile, are surface forms over L5 message
scheduling and continuation state. They are not a separate concurrency model.

An async procedure returns a Future/Task-compatible Structure. Calling it
schedules or constructs a task rather than necessarily running the body to
completion immediately.

An await receiver consumes a Future/Task-compatible Structure. If the value is
not ready, the current handler/procedure continuation is stored in a
scheduler-visible continuation Structure, control returns to the L5 scheduler,
and the continuation resumes when a result message arrives.

Conceptual lowering:

    await future
        -> store continuation state
        -> suspend current handler/procedure
        -> return control to scheduler
        -> resume by result message

Values that survive across an await boundary must be owned by the continuation,
stored in an arena whose lifetime covers the continuation, immutable with
stable lifetime, or copied into continuation state. Frame-local borrows may not
survive await unless the owner lifetime is statically known to cover the
continuation.

Thus await obeys the same memory model as messages:

    borrow before await -> cannot escape await unless lifetime-stable
    owner value         -> may be stored in continuation state
    immutable value     -> may be shared if profile permits
    branch value        -> may be moved or copied

27.13. Yield and Message Scheduling

`yield` and `await` are related but distinct.

    yield
        emits a produced value checked by the current function's yield-protocol
        and records resume state.

    await
        waits for a Future/Task/message result and records resume state.

Both lower to explicit continuation state. Both must respect the same lifetime
rules for local values, borrowed payloads and branch arenas. Neither introduces
hidden shared mutable state between L5 Threads.

27.14. Determinism, Progress and Deadlock Properties

The deterministic profile of L5 execution is:

    one active handler per L5 Thread;
    stable queue ordering;
    no shared mutable raw references across L5 Threads;
    message payload transfer by copy, serialization or whole-branch move;
    deterministic handler code unless it uses declared nondeterministic
        receivers;
    explicit ordering for time, external I/O and scheduler interaction.

A nondeterministic or real-time profile may relax ordering, introduce
priorities, interact with external event loops or process messages under
deadlines. Such a profile must mark the nondeterministic sources and must not
pretend they are ordinary deterministic structural evaluation.

The synchronized inbox/outbox model avoids ordinary lock-order deadlocks if:

    inbox/outbox locks are held only for short append/drain operations;
    user code and L5 message handlers do not execute while holding those locks;
    the base profile does not block while waiting for replies.

This does not prove protocol termination. A message protocol may still fail to
make useful progress, send messages forever, exhaust memory or starve some
tasks. Those are architecture/protocol properties, not synchronization-lock
deadlocks in the mailbox mechanism.

27.15. Atomic Operations and L5 Messages

L5 message dispatch is not the universal mechanism for all computation.

L2 and L3 ordinary computation remains direct:

    primitive arithmetic;
    comparisons;
    field-follow access;
    array access;
    direct fn/sub calls;
    loops and branches;
    generated low-level operations.

L5 messages are used for behavior, configuration, object/service interaction,
active objects and high-level event delivery.

Lingvamyxa does not require Smalltalk-style message dispatch for every atomic
operation.

27.16. ANSI C Lowering Strategy

A minimal C99 runtime may represent an L5 Thread as a structure containing root
state, queues, arenas, execution context and scheduler metadata:

---ANSI C---

typedef struct LmThread LmThread;
typedef struct LmMessage LmMessage;
typedef struct LmBranch LmBranch;
typedef struct LmArena LmArena;

typedef LmStatus (*LmHandlerFn)(LmThread *thread, const LmMessage *message);

struct LmThread {
    LmArena *state_arena;
    LmArena *temp_arena;
    LmQueue *queue;
    void *root_state;
    LmRegistryView *registry;
    ExecutionContext *context;
};

---ANSI C---

A message enqueue operation lowers to:

    construct typed payload;
    copy/move/serialize according to transfer mode;
    enqueue message into receiver queue;
    return status or Future/Task handle.

A scheduler step lowers to:

    pop next message according to scheduling profile;
    resolve handler by registry/query or precomputed dispatch table;
    create handler frame / reset temp arena;
    invoke handler;
    deliver reply/failure if required;
    release handler temporaries.

A whole-branch move lowers to detaching an owned LmBranch from the sender and
attaching it to the receiver. The sender must not retain valid raw references
into the moved branch.

27.17. Boundaries, Non-Goals and Open Points

The structural core does not define the binary layout of queues, futures,
branch handles, registry caches, scheduler locks, wake-up mechanisms, OS-thread
mapping, coroutine ABI, serialization format or network transport.

Those belong to runtime profiles and L1/L2 lowering specifications.

The core rule is stable:

    L5 Thread -> isolated state and arena graph
    communication -> typed messages
    retention -> owner-copy or ownership transfer
    waiting -> continuation state
    dispatch -> logical registry/query layer
    shared mutable memory -> outside default L5, explicit L2/L3/profile construct

Open points for runtime profiles:

    cleanup failure policy during cleanup processing;
    scheduling fairness, inbox drain limits and priority rules;
    inbox capacity, backpressure, message dropping and overflow diagnostics;
    message ordering across multiple senders beyond FIFO after append;
    object ownership migration between threads;
    shared immutable object publication rules;
    source forms for `send`, `request`, `reply`, thread creation and shutdown;
    interaction between persistent registry event logs and runtime inboxes.

30. Memory Model

30.0. Scope

This section defines the structural memory model used by Lingvamyxa source semantics above the raw L1 implementation layer.

The model is intentionally region-oriented. It is not a global garbage-collected heap model and it is not a Rust-style per-variable ownership calculus. It treats high-level Structures as branch-owned memory regions, uses borrowed references by default when data is obtained from outside the current owner, and isolates L5 Threads from one another.

The memory model is semantic. A translator may lower it to stack allocation, arenas, reference-counted branch handles, local owner-tree walkers, copy-on-write Structures, immutable value stores, direct C storage, generated resource-release paths or another implementation strategy that preserves the rules below.

30.1. Core Rules

The following rules are normative for the structural memory model:

    1. A branch Structure may own an arena.
    2. Leaf Structures normally do not own arenas.
    3. Heap children of a branch are allocated inside the nearest owning branch arena.
    4. Destroying a branch arena destroys all memory allocated inside it.
    5. Borrowed references into an arena do not extend the arena lifetime.
    6. To keep a borrowed branch beyond its owner scope or message frame, the value must be copied into an owned branch of the current owner.
    7. L5 Threads have isolated arena graphs.
    8. No raw reference may cross an L5 Thread boundary; shared mutable memory is forbidden at L5.
    9. Messages cross L5 Thread boundaries only by copy, serialization or whole-branch ownership transfer.

These rules are the high-level memory contract. Lower levels may expose unsafe storage, addresses and explicit buffer operations, but those operations do not weaken the L5 isolation rule.

30.2. Branch Arenas

A branch arena is a memory region owned by a branch Structure or by another owner that plays the same role, such as a frame, handler, module state or L5 Thread root.

The intended shape is:

    root branch
        branch arena
            child Structure
            child array
            child text
            child expression tree
            child decimal storage

Leaf Structures may be stored inline, in their parent arena, or in implementation-defined compact storage. They normally do not own separate arenas because an arena per leaf would add overhead without improving lifetime management.

A branch far from the leaves may own an arena for the whole sub-tree. When the branch is destroyed, detached or locally collected, the arena can be released as one unit. This is the common case for documents, ASTs, message payloads, configuration trees, model descriptors and high-level runtime state.

30.3. Owner, Borrow and Owner-Copy

An owner is a scope, branch, arena, frame, handler, L5 Thread root or other region that is responsible for the lifetime of a Structure.

A borrowed value is a reference or handle into someone else's owned memory. Borrowing does not transfer release responsibility and does not extend the lifetime of the source arena.

Values obtained from outside the current owner are borrowed by default. This includes values read from an incoming message, values obtained from another branch, and views into an existing Structure.

To retain such a value after the current frame, handler or owner lifetime ends, the program must create an owned copy:

    owner: saved m\payload

Conceptual meaning:

    copy `m\payload` into an arena owned by the current owner;
    bind `saved` to that owned copy.

A plain binding of an external value may remain a borrow/view:

    borrow: view m\payload

Conceptual meaning:

    bind `view` as a borrowed view valid only while the source owner is valid.

A profile may choose a different surface spelling for owner-copy, but it must preserve the semantic distinction between borrowed retention and owned retention.

30.4. No Escaping Borrow

The no-escaping-borrow rule is a consequence of the core rules.

A borrowed reference is valid only inside the frame, handler, arena epoch, branch lifetime or owner lifetime that produced it. It may not be stored in longer-lived state and may not be sent to another L5 Thread as a raw reference.

Invalid Lingvamyxa-shaped pattern:

L5:
    handler: retainPayload m
        saved: m\payload
    ---
end: L5

when `saved` outlives the message frame and `m\payload` is borrowed.

Valid Lingvamyxa-shaped pattern:

L5:
    handler: retainPayload m
        owner: saved m\payload
    ---
end: L5

Here the payload is copied into an owned branch of the current L5 Thread or current persistent owner.

If a borrowed value must be sent to another L5 Thread, it must be copied, serialized or included in a whole-branch ownership transfer according to the message rules.

30.5. L5 Thread Memory

An L5 Thread owns an isolated memory tree or forest.

Source-shaped descriptor of the conceptual components:

L5:
    Thread:
        rootState:
        messageQueue:
        currentHandlerFrame:
        temporaryArenas:
        branchArenas:
        immutableValueStore:
        internTable:
    ---
end: L5

Raw references inside one L5 Thread may point only into memory owned by that same L5 Thread or into explicitly shared immutable storage admitted by the implementation profile. Raw references from one L5 Thread into another L5 Thread are invalid.

This makes the unit of memory management local. Releasing memory for one L5 Thread does not require stopping or scanning all L5 Threads in the system.

30.6. Message Boundary

The L5 Thread boundary is a memory boundary.

A message payload may cross the boundary in one of three ways:

    copy
    serialization
    whole-branch ownership transfer

Copy means that the receiver receives an owned copy in one of its own arenas or receives a borrowed message-frame value that must be owner-copied before retention.

Serialization means that the sender converts the payload to a byte/text/record representation and the receiver reconstructs its own Structure from that representation.

Whole-branch ownership transfer means that the sender transfers ownership of an entire branch arena to the receiver. After the transfer, the sender no longer owns that branch and must not use raw references into it.

A message must not contain raw borrowed references into the sender's private arena graph unless the receiver is the same L5 Thread and the active profile explicitly treats the message as an intra-thread frame.

30.7. Temporary Arenas, Tree Cutting and Thread Destruction

Temporary values may be allocated in a frame arena, handler arena or transaction arena and released as a group when that frame, handler or transaction ends.

Long-lived values must be reachable from an owner such as the L5 Thread root state, a branch root, a module state Structure or another persistent owner.

When a branch or subtree is cut from the local owner tree, an implementation may run an automatic tree-cut procedure for that L5 Thread. This procedure may promote deferred-owned edges, pin source owners that are still needed, detach branch roots, or mark local memory as no longer reachable from the thread root.

This procedure is not a general garbage collector in the source semantics and it is not a separately invoked language operation. It is part of the local structural memory machinery of one L5 Thread. Since one L5 Thread processes one handler at a time in the default profile, this procedure does not require cross-thread coordination or global stopping.

Actual memory release is a coarser implementation event. In the default model, memory may remain owned by the L5 Thread until that L5 Thread is destroyed. Explicit shared or externally managed L2 resources, such as large shared arrays, have their own explicit destruction/lifetime contracts. Until such L2 shared resources are introduced, destroying an L5 Thread is the ordinary mechanism that releases its local memory graph.

30.8. Immutable Values and Interning

High-level values may be immutable by default. A variable or Structure field may bind a handle to an immutable value rather than owning mutable storage directly.

An implementation may maintain an immutable value store or intern table:

    hash(value) -> canonical immutable object

Equal immutable values may share storage. Since immutable values cannot be changed through any alias, sharing them does not create mutable aliasing problems.

Examples of values suitable for interning or immutable storage:

    atoms
    symbols
    strings
    numeric constants
    normalized decimal constants
    small immutable arrays
    model descriptors
    expression trees

Interning is an optimization and a representation strategy. The source rule is that mutation of a high-level immutable value creates a new value or a new branch, not an in-place update through an alias.

30.9. Low-Level Interaction

L2 and implementation-facing L3 profiles may expose explicit mutable storage, arrays, buffers, typed addresses and unsafe operations. Such values are not magically immutable and may require explicit release or generated release code.

When a low-level mutable buffer is embedded into a high-level Structure, the Structure must declare whether the edge is owned, borrowed or externally managed. An owned edge is released when the owner is destroyed. A borrowed edge is not released by the borrowing owner and must not outlive the external owner. An externally managed edge follows a profile-defined lifetime contract.

The high-level branch-arena model does not prohibit low-level code. It only requires that raw low-level references do not escape their valid owner lifetime or cross an L5 Thread boundary in violation of the L5 isolation rule.

30.10. Source Receivers and Lifetime Policy Forms

Ownership and lifetime policy should be expressed through ordinary receivers, identifiers and argument Structures. The memory model does not introduce a separate ownership grammar.

L2 storage/allocation receivers remain the low-level unsafe layer:

    stack: T name
    heap: T name
    static: T name
    []: name size
    @: T p

An L2 or implementation-facing profile may allow policy arguments on declaration/allocation receivers:

    heap: Buffer data owner(frame)
    heap: Buffer data external(release freeBuffer)
    []: bytes n owner(branch)

These arguments are ordinary Structures consumed by the active receiver signature. They do not create C-like declaration syntax.

L3 profiles may expose safe memory-operation receivers:

    owner: saved m\payload
    borrow: view m\payload
    copy: dst src
    move: dst src

`owner: saved value` creates an owned copy in the current owner according to the active type/model descriptor. `borrow: view value` creates a borrowed view whose lifetime is bounded by the source owner. `copy` creates an independent value according to the target context. `move` transfers a value or branch when the active descriptor permits transfer and invalidates or empties the source binding according to the profile.

The exact-head readable spelling:

    `owner saved`: m\payload

may be supported by a profile as a readable variant of the same owner-copy operation. If `owner` is consumed as the ordinary receiver identifier, the canonical receiver-level form is:

    owner: saved m\payload

Both spellings consume ordinary Structures. Neither introduces a new grammar category.

The source meaning of an owned edge is an ownership contract, not a mandatory immediate physical deep copy. An implementation may satisfy owner-copy semantics by:

    immediate deep copy;
    immutable sharing;
    copy-on-write;
    source-owner pinning;
    deferred owner-copy with automatic promotion during local tree-cut / owner-detach processing.

Deferred owner-copy means that an edge is semantically owned by the target owner, but the implementation may temporarily point to storage owned by the source owner. When the local owner tree is cut or an owner is detached, every still-live deferred-owned edge that would otherwise lose its source storage must either be promoted by copying the referenced value into the target owner, redirected to an immutable/shared representation, or keep the source owner pinned inside the same L5 Thread memory graph.

This is valid only when the observable ownership contract is preserved. For mutable values, deferred owner-copy requires a freeze, copy-on-write, explicit mutation barrier or immediate copy; otherwise the target would observe later source mutations instead of the value it retained. For immutable high-level Structures, source text, interned values, model descriptors and parser trees, deferred owner-copy is often a natural implementation strategy.

Promotion is part of the automatic local tree-cut procedure, not a memory release/destruction operation and not a separately invoked source operation. It may allocate new storage, but that allocation belongs to ownership maintenance inside one L5 Thread. Actual memory release is performed later by destroying the L5 Thread memory graph or by destroying explicit L2/external resources with their own lifetime contracts.

L4 model/type descriptors may attach memory-edge policies to fields and payloads:

L4:
    model: MessageEnvelope
        vars:
            MessagePayload: payload owned
            Text: view borrowed
            SQL: nativeHandle external(release close)
        ---
    ---
end: L4

Such descriptors may materialize registry facts such as:

L5:
    fact: edge MessageEnvelope payload owned
    fact: edge MessageEnvelope view borrowed
    fact: release MessageEnvelope nativeHandle close
    fact: copyPolicy MessageEnvelope payload deep
    fact: transferPolicy MessageEnvelope payload forbidden
end: L5

The exact relation names are registry/profile details. The source rule is that L4 descriptors define the ownership contract used by L3/L5 consumption and by L1 lowering.

L5 message and sharing receivers may select boundary behavior explicitly:

    send: worker m\payload copy
    send: worker m\payload serialize
    send: worker m\payload transfer
    intern: value
    share: value immutable

At an L5 Thread boundary, raw mutable references are invalid. `copy`, `serialize` and `transfer` are the ordinary policies for crossing the boundary. Immutable sharing is permitted only when the implementation profile can preserve immutability and thread-safety.

30.11. ANSI C Lowering Strategy

---ANSI C---
An ANSI C translator may implement this memory model with the following mechanisms:

    LmArena for branch, frame and handler regions;
    LmBranch or equivalent root handles for arena-owned branches;
    generated resource-release paths for L2/L3 resource values;
    frame/handler arena reset at safe exits;
    deep-copy functions for owner-copy;
    lazy-owned edge tables for deferred owner-copy;
    source-owner pinning or promotion during local tree-cut / owner-detach processing;
    serialization functions for message payloads;
    ownership-transfer functions that detach one LmBranch from a sender and attach it to a receiver;
    optional per-L5-Thread local tracing or reference counting for branch roots;
    no global heap scan as a source-semantic requirement.

Possible runtime declarations:

    typedef struct LmArena LmArena;
    typedef struct LmBranch LmBranch;
    typedef struct LmThread LmThread;

    typedef enum LmEdgeKind {
        LM_EDGE_OWNED,
        LM_EDGE_LAZY_OWNED,
        LM_EDGE_BORROWED,
        LM_EDGE_EXTERNAL,
        LM_EDGE_TRANSFERRED
    } LmEdgeKind;

    typedef struct LmTypeOps {
        void (*destroy)(void *value);
        int  (*copy_to)(LmArena *arena, void *dst, const void *src);
        int  (*serialize)(void *writer, const void *src);
        void (*trace)(void *owner_walker, void *value);
    } LmTypeOps;

    typedef struct LmEdge {
        LmEdgeKind kind;
        LmBranch *source_owner;
        LmBranch *target_owner;
        const LmTypeOps *type_ops;
        void *value;
        void **patch_slot;
    } LmEdge;

    struct LmBranch {
        LmArena *arena;
        const LmTypeOps *type_ops;
        void *root;
        LmThread *owner_thread;
        unsigned flags;
    };

Possible arena API:

    void *lm_arena_alloc(LmArena *arena, size_t size, size_t align);
    void  lm_arena_reset(LmArena *arena);
    void  lm_arena_destroy(LmArena *arena);

The exact status/result type is implementation-defined. A profile may use `int`, an `LmStatus` enum, receiver diagnostics or another error convention.

Generated type/model operations may be derived from L4 descriptors:

    destroy       clears owned edges and external resources;
    copy_to       implements owner-copy and ordinary deep copy;
    serialize     implements message serialization;
    trace         supports optional local owner-tree walking or reference tracking.

An owner-copy form such as:

    owner: saved m\payload

may lower to:

    saved = lm_copy_to_owner(current_owner, m_payload);

or to inlined field-by-field copy when the type/model layout is statically known.

If the implementation uses deferred owner-copy, the same form may lower to a lazy-owned edge:

    saved = lm_lazy_owner_edge(current_owner, m_payload);

The lazy edge is still semantically owned by `current_owner`. During automatic local tree-cut or owner-detach processing, if the source owner would no longer remain reachable, the runtime must either promote the edge:

    lm_tree_cut_promote_lazy_edges(source_owner);

or keep the source owner pinned inside the same L5 Thread memory graph until no lazy-owned edges refer to it.

For immutable values, promotion may be unnecessary if the implementation can prove stable lifetime and immutability. For mutable values, the runtime must use immediate copy, freeze, copy-on-write or a mutation barrier before lazy ownership can preserve source semantics.

L5 message crossing may lower as:

    copy       -> deep-copy payload into receiver-owned arena or message-frame arena;
    serialize  -> encode to bytes/text/records, then reconstruct on receiver side;
    transfer   -> detach an `LmBranch` from the sender, attach it to the receiver and invalidate sender-side raw references/handles.

A generated C function may lower scope resource release to a single C99 exit label:

    int lm_generated_handler(LmThread *thread, const LmMessage *m)
    {
        int status = 0;
        LmArena *temp_arena = lm_thread_temp_arena(thread);
        LmResource resource;
        int resource_initialized = 0;

        status = lm_resource_init(&resource);
        if (status != 0) {
            goto exit;
        }
        resource_initialized = 1;

        status = lm_generated_body(thread, m, &resource);
        if (status != 0) {
            goto exit;
        }

    exit:
        if (resource_initialized) {
            lm_resource_destroy(&resource);
        }
        lm_arena_reset(temp_arena);
        return status;
    }

For high-level immutable Structures, the translator may represent bindings as handles into an immutable store. For low-level mutable resources, the translator must preserve the declared owned/borrowed/external lifetime edge.

30.12. Shared Low-Level Resources and Large Read-Only Data

The L5 memory model is intentionally message- and branch-oriented. It is the default safe model for active objects, behavior dispatch, high-level events, configuration and query handling. It should not be used to pretend that large shared raw buffers are ordinary per-thread message payloads.

If a program needs a large resource that many L5 Threads read directly, such as a large numeric table, shared index, memory-mapped dataset, model-weight array or external database page cache, that resource belongs in an L2 or implementation-facing L3 profile as an explicit low-level/shared resource.

Example conceptual L2 forms:

L2:
    static: BigArray table shared(readonly)

L2:
    static: BigArray table shared(readonly) externalLifetime

The exact receiver names and policy arguments are profile-defined. The semantic point is that the resource is not an ordinary mutable L5 branch. It is a shared immutable or externally managed low-level object with an explicit lifetime contract.

L4 may describe such a resource as a model/descriptor:

L4:
    model: BigArray
        field: data @f64 borrowed
        field: len u64
        access: shared readonly

The L4 descriptor may record that the data edge is borrowed from low-level storage, shared only under read-only access, externally managed, memory-mapped or protected by another explicit runtime contract. L5 may use the descriptor and receive handles/selectors/facts about the resource, but ordinary L5 message passing does not send raw mutable references to it.

Shared immutable data may be read by many L5 Threads when the implementation profile guarantees immutability and thread-safe publication. Since no thread can mutate the shared value through an alias, this does not violate the L5 no-shared-mutable-memory rule.

Shared mutable data is different. If multiple threads must write or coordinate over the same resource, the resource must be represented through explicit L2/L3 synchronization or atomic constructs such as locks, read-write locks, atomics, barriers, memory-order policies or transactional receivers. Those constructs are unsafe or implementation-facing unless a higher-level profile wraps them in a checked abstraction.

Therefore:

    L5 default       -> copy, serialization, whole-branch ownership transfer
    L5 shared read   -> immutable / read-only / externally published resource
    L2/L3 explicit   -> shared mutable buffers, atomics, locks and external lifetimes

The long-term bootstrap direction is that L1 should shrink to the target/backend substrate. Language-visible rules for shared resources, memory edges, synchronization and lifetime should move upward into L2, L3, L4 and L5 descriptors/receivers. L1 remains the implementation layer used to lower those rules to C99, platform APIs, libraries and native binaries.

30.13. Control Exit, Assert Diagnostics and Thread-Local Collection

The memory model has two distinct memory mechanisms:

    L5 Thread local collection;
    owner-tree cutting / local memory-cutter machinery.

Memory reclamation is performed by these mechanisms as described in this
section.

A control operator does not free memory merely because it is a control operator.
It may, however, leave a frame, handler, retry attempt, transaction arena,
branch owner or whole L5 Thread. Such an exit changes the local owner tree and
creates a collector safe point.

The L5 Thread local collector may run at defined safe points:

    after normal frame completion;
    after handler completion;
    after transaction completion;
    after return;
    after break;
    after continue;
    after labelled break;
    after labelled continue;
    after fail;
    after retry;
    after redo;
    after assert diagnostic exit;
    after owner replacement;
    after owner removal;
    after local branch/subtree detachment;
    before or during L5 Thread termination;
    under implementation-defined memory pressure.

The collector is local to one L5 Thread.

It does not stop other L5 Threads.

It does not scan foreign arena graphs.

It does not require a global lock in the default L5 model.

It may inspect the current L5 Thread owner tree, local arena graph, branch
ownership metadata, deferred-owned edges, borrowed edges, local reachability
metadata and implementation priority metadata.

The collector may:

    cut unreachable local branches;
    release frame-local arenas;
    release handler-local arenas;
    release transaction arenas;
    release abandoned retry-attempt arenas;
    release detached branch arenas;
    promote deferred-owned edges when required;
    pin source owners when required;
    copy surviving data into surviving owners when required;
    detach surviving branch roots as independent owners;
    destroy the whole L5 Thread arena graph when the L5 Thread terminates.

Actual memory release is implementation-defined. A profile may release memory
immediately after a local cut, batch releases until the end of the current
handler, or retain local memory until the whole L5 Thread is destroyed.

This is a technical memory collection mechanism by effect, because it
automatically reclaims memory. It is not a global tracing collector by
mechanics. Its unit of collection is an owner region:

    frame arena;
    handler arena;
    retry-attempt arena;
    transaction arena;
    branch arena;
    whole L5 Thread arena graph.

30.13.1. Thread-Local Collection and Owner-Tree Cutting

This document does not define a separate source-level memory-release operation.

The term collection means a Thread-local memory collection pass.

The term owner-tree cutting means a local structural update of the current
L5 Thread owner tree.

A collection pass may include:

    owner-tree cutting;
    arena reclamation;
    deferred-owner promotion;
    source-owner pinning;
    branch detachment;
    whole-thread arena destruction.

These mechanisms are not finalization code and not ordinary control-flow
handlers. They are local memory machinery attached to owner lifetime and to the
current L5 Thread arena graph.

30.13.2. Control Exit and Owner Lifetime

Control exits are connected to memory only through owner lifetime.

Generic sequence:

    control exit is selected;
    affected frame, handler, attempt, transaction or branch owners are marked
    as exited, abandoned, detached or destroyed;
    the owner tree is updated;
    the L5 Thread local collector may run at this safe point;
    unreachable local owner regions may be cut;
    actual arena release follows the implementation profile.

Therefore:

    return / break / continue:
        leave ordinary control scopes and may create collection safe points;

    fail:
        leaves recoverable failure scopes and may create collection safe points;

    retry:
        abandons the current retry attempt and may create a collection safe point;

    redo:
        abandons or restarts the current repeatable unit according to receiver
        semantics and may create a collection safe point;

    assert:
        exits through the diagnostic path and may create a collection safe point;

    thread termination:
        destroys the whole L5 Thread owner graph unless the implementation
        profile preserves selected externally managed resources.

No control operator is a memory operation by itself. Memory is reclaimed because
the operator changes owner lifetime.

30.13.3. `assert` and Memory

`assert` is diagnostic invariant failure, not recoverable failure flow.

If an `assert` condition is false, the runtime records an
`AssertionViolation` diagnostic and exits through the diagnostic path defined by
the execution-context profile.

Default thread-profile sequence:

    assert condition is false;
    record AssertionViolation diagnostic;
    transfer control to the thread diagnostic root;
    terminate the current thread/task by default after reporting the diagnostic;
    run the L5 Thread local collector;
    destroy or release the L5 Thread arena graph according to the thread
    destruction policy.

An `assert` violation is not part of the declared `throws` set.

An `assert` violation is not caught by ordinary failure labels or failure
handlers.

An `assert` violation does not execute `fail`.

An `assert` violation may still cause memory reclamation because it abandons
frames, handlers, attempts or the whole current L5 Thread. The reclamation is
performed by the L5 Thread local collector, not by a special `assert` memory
rule.

If a runtime profile allows a diagnostic root to keep the L5 Thread alive after
an assertion violation, then only the owners abandoned by the diagnostic exit
are cut or released. Persistent state still reachable from the L5 Thread root
remains owned by that L5 Thread unless the diagnostic policy explicitly
destroys, resets or detaches it.

30.13.4. `guard`, `fail`, `throws` and Handlers

`guard`, `fail`, `throws` and failure handlers define declared recoverable
failure flow.

They are distinct from `assert`.

    guard / fail / throws / handlers:
        declared, expected, recoverable failure path

    assert:
        diagnostic invariant violation

`guard` may detect an expected failure condition and select a failure path.

`fail` exits the current executable body with a declared failure label and an
optional payload.

Default failure sequence:

    guard detects an expected failure condition;
    fail creates a declared failure label and optional payload;
    control exits to the nearest visible handler or caller failure channel;
    affected frame, handler or attempt owners are marked as abandoned or exited;
    the L5 Thread local collector may run at this safe point;
    a structured failure result is delivered to the handler or caller.

`fail` does not transfer to the thread diagnostic root.

`fail` does not use the `assert` channel.

`fail` does not directly free memory. It creates a collection safe point because
it exits the current owner context.

A failure payload that must survive the abandoned owner must be owned by a
surviving owner. If the payload is borrowed from the failing frame, handler or
attempt, it must be owner-copied into a surviving owner before it is retained
beyond that owner lifetime.

If a failure payload crosses an L5 Thread boundary, it must cross by copy,
serialization or whole-branch ownership transfer. A raw reference into the
failing L5 Thread arena graph must not cross that boundary.

Failure handlers may be lexical handlers, executable labels, caller-side
receivers or L5 event/message handlers according to the final handler syntax.
In all variants, memory safety is governed by the same owner, borrow,
owner-copy and message-boundary rules.

30.13.5. `retryable`, `retry` and Attempt Arenas

`retryable` defines a restartable frame.

`retry` abandons the current attempt and re-enters the nearest or named
retryable frame.

Default retry sequence:

    select nearest or named retryable frame;
    abandon the current attempt;
    mark attempt-local owners as abandoned;
    run the L5 Thread local collector at the retry safe point;
    release or retain abandoned attempt arenas according to the implementation
    profile;
    recreate local bindings declared inside the retryable frame;
    re-enter the retryable frame.

`retry` is re-execution, not transactional rollback.

`retry` does not roll back external side effects.

`retry` does not automatically restore outer bindings unless the retryable
receiver defines a stronger rollback policy.

Values that must survive `retry` must be owned by an outer owner that is not
abandoned by the retry. A borrowed value or attempt-local branch cannot be
retained across retry unless it is copied or transferred into such an outer
owner.

Example conceptual distinction:

    retry attempt-local value:
        collectible when the attempt is abandoned

    value owner-copied into outer retryable owner:
        survives the abandoned attempt

    value stored in L5 Thread root:
        survives retry unless explicitly replaced, removed or cut

Therefore `retry` may free memory repeatedly without invoking a global tracing
collector. Each abandoned attempt loses its attempt-local owner graph, and the
next attempt starts with fresh local bindings.

30.13.6. Owner Replacement and Null-Like Removal

When a binding update, owner replacement, explicit removal or profile-defined
null-like operation cuts a branch from the local owner tree, the implementation
may run the automatic local tree-cut procedure.

Conceptual sequence:

    old owner edge is removed or replaced;
    old branch/subtree is no longer reachable from the local owner tree;
    deferred-owned edges reachable from still-live owners are promoted, pinned
    or redirected;
    detached branch roots are preserved only if they became independent owners;
    otherwise the old branch/subtree becomes locally unreachable;
    actual arena release occurs according to the implementation profile.

This is the ordinary memory-cutter path for local owner-tree mutation.

It is not required to scan all objects in the process.

It is not required to stop other L5 Threads.

It does not inspect foreign L5 Thread arena graphs.

30.13.7. Emergency Memory Pressure

Emergency memory pressure is an implementation/runtime policy over owner
destruction.

A runtime may reclaim memory urgently by cancelling, failing, aborting or
destroying selected L5 Threads, handlers, transactions, retry attempts or branch
owners according to priority, scheduling policy, diagnostic policy or
service-level policy.

Default emergency sequence for destroying an L5 Thread:

    select a victim L5 Thread or task;
    request cancellation, declared failure, diagnostic termination or forced
    termination according to profile;
    mark the selected owner graph as abandoned or terminating;
    run the L5 Thread local collector;
    destroy the selected owner graph or the whole L5 Thread arena graph;
    return the memory owned by that graph to the implementation allocator.

This is a technical garbage-collection mechanism by effect, because it
automatically reclaims memory.

It is not a global tracing collector by mechanics.

Its unit of collection is not an individual object. Its unit of collection is
an owner region:

    frame arena;
    handler arena;
    retry-attempt arena;
    transaction arena;
    branch arena;
    whole L5 Thread arena graph.

30.13.8. Collection Ordering Rule

For every control exit that changes owner lifetime, the owner-state transition
is ordered before local collection.

Required abstract order:

    1. decide the control exit, failure exit, retry exit, diagnostic exit or
       termination;
    2. mark the affected owners as exited, abandoned, detached or destroyed;
    3. apply failure, retry, return, diagnostic or termination transfer according
       to the active receiver/profile;
    4. update the local owner tree;
    5. run the L5 Thread local collector if this point is selected as a
       collection safe point;
    6. release arenas whose owners are destroyed or whose implementation profile
       permits immediate release.

Borrowed references into a destroyed owner are invalid after that owner is cut
or released.

A surviving owner may retain data only if that data is already owned by the
surviving owner, copied into it, serialized through it, or transferred to it as
a whole branch according to the message and ownership rules.

30.13.9. Mandatory Message-Boundary Collection Policy

The default L5 collector scheduling policy is not profile-arbitrary.

In the default L5 model, the L5 Thread local collector runs at message
boundaries.

A message boundary is reached when one of the following events is completed:

    an incoming message has been received and its payload has been copied,
    serialized into, or ownership-transferred into a valid owner of the
    receiving L5 Thread;

    an outgoing message has been sent and its payload has been copied,
    serialized into, or ownership-transferred to the target queue, transport or
    target owner;

    a message handler has completed normally;

    a message handler has exited by return, fail, retry, redo, assert diagnostic
    exit or thread termination.

At each message boundary, the L5 Thread runtime must run one local collection
pass before continuing ordinary message processing.

The collection pass may be a cheap no-op when no local owner-tree or arena
state changed.

The collection pass is local to the current L5 Thread.

It does not stop other L5 Threads.

It does not scan foreign arena graphs.

It does not require a global lock.

It does not perform global tracing collection.

The collection pass may inspect only the current L5 Thread owner tree, local
arena graph, branch ownership metadata, deferred-owned edges, borrowed edges,
local reachability metadata and implementation priority metadata.

The collector must preserve:

    owner validity;
    no-escaping-borrow;
    no raw cross-thread references;
    message-boundary ownership rules;
    copy / serialization / whole-branch-transfer rules for inter-thread data.

This rule deliberately keeps ordinary collection simple and regular:

    receive message
        -> run local collection pass
        -> execute or schedule handler work

    send message
        -> commit payload transfer
        -> run local collection pass
        -> continue current handler

    finish handler
        -> run local collection pass
        -> wait for or receive next message

30.13.10. Long L5 Computations and Supervisor Termination

An L5 Thread is expected to remain message-responsive.

The default L5 runtime is not required to interrupt arbitrary deep computation
inside one handler in order to run the collector. If an L5 Thread enters a long
computation and does not reach a message boundary or another declared yield
point within the runtime watchdog limit, the supervising L5 Thread may cancel,
fail, abort or destroy that L5 Thread according to the scheduling and diagnostic
policy.

This is intentional.

Long computations in L5 must be written as stepwise or resumable computations if
they need to coexist with message scheduling and regular memory collection.

Valid designs include:

    lazy receiver/operator evaluation;
    iterator/yield-style computation;
    query/search receivers that split work into bounded steps;
    continuation messages sent back to the same or another L5 Thread;
    retryable frames whose attempts are bounded;
    explicit handler-level work slicing;
    profile-defined cooperative yield points.

If a computation must run as a long uninterrupted low-level operation, it should
be lowered to L2/L3 semantics with explicit threading, memory, synchronization
and lifetime rules. Such L2/L3 worker threads are not ordinary message-driven L5
Threads unless wrapped by an L5 owner/message facade.

Therefore the default rule is:

    L5 Thread:
        message-driven;
        regularly collected at message boundaries;
        supervisor may terminate it if it stops reaching boundaries;

    long L5 algorithm:
        must be split into lazy/stepwise/message-visible units;

    long uninterrupted low-level algorithm:
        belongs to explicit L2/L3 execution semantics.

Emergency memory pressure uses the same ownership principle. A supervising
Thread may reclaim memory by terminating low-priority or non-responsive L5
Threads. The memory reclaimed is the memory owned by the selected owner regions
or by the whole selected L5 Thread arena graph. The runtime does not need to
find individual unreachable objects inside a global heap.

30.14. Future L2/L1 Low-Level Threads, Shared Blocks and `freemem`

This structural memory model does not define the complete surface language for
standalone C-like L2 execution threads, raw shared memory blocks, direct
allocator calls or explicit `freemem`-style memory release.

Those mechanisms belong to future L2 and L1-facing implementation profiles.
They are lower-level than the default L5 Thread memory model. L1 Threads are host/substrate execution resources used by the L1-L2 runtime binding; L2 Threads, when introduced, are low-level Lingvamyxa primitives for explicit shared-memory work. Neither kind is visible as an ordinary programming object above L2.

The default L5 model remains:

    L5 Thread local collection;
    owner-tree cutting / local memory-cutter machinery;
    message-boundary transfer by copy, serialization or whole-branch ownership
    transfer;
    no raw mutable reference crossing an L5 Thread boundary.

A future L2/L1 profile may define C-like receivers or operations for:

    creating standalone L2 execution threads;
    joining, cancelling or terminating those L2 threads;
    allocating raw memory blocks;
    allocating shared memory blocks;
    mapping memory-mapped files or external buffers;
    synchronizing shared mutable blocks with atomics, locks, barriers or
    profile-defined memory-order rules;
    releasing raw/shared blocks with an explicit low-level operation such as
    `freemem`.

Conceptual future profile sketch:

L2:
    thread: workerThread workerEntry workerArgs
    mem: sharedBlock bytes shared(mutable)
    freemem: sharedBlock
end: L2

This sketch is not normative source syntax. It only marks the implementation
area reserved for future L2/L1 profiles.

An L2 execution thread is not automatically an L5 Thread.

An L2 thread may expose raw addresses, shared mutable buffers and platform
synchronization because it belongs to the low-level implementation-facing
domain. Such code must obey the explicit L2/L1 profile rules for lifetime,
memory ordering, synchronization and release.

Higher Lingvamyxa levels should not directly depend on raw `freemem` or raw
shared-memory access. L3/L4/L5 code should see typed handles, descriptors,
capabilities, messages, adapters or checked wrappers. The low-level `freemem`
operation, when provided, is hidden behind those wrappers and is not part of the
ordinary high-level owner-copy / collection / memory-cutter model.

Therefore `freemem` is not:

    an L5 Thread local collection pass;
    an owner-tree cutting operation;
    a message-boundary memory rule;
    a high-level destructor/finalization mechanism.

It is an explicit low-level release primitive for memory allocated by the
matching L2/L1 allocation profile.

Future revisions must define at least:

    exact L2 source spelling;
    allocation ownership and release contracts;
    shared block publication rules;
    memory ordering and synchronization requirements;
    thread start/join/cancel semantics;
    interaction with L5 wrapper handles and service adapters;
    diagnostics for double release, use-after-release and cross-level escape;
    which operations are unsafe or implementation-facing.

Until such a profile is specified, the normative high-level rule is that L5
Threads communicate by messages and local owner regions, while standalone L2
threads and raw shared blocks remain hidden L2/L1 implementation mechanisms.

32. Reactive Registry, Query Receivers, and Agent Candidates

This section defines the reactive layer of the L5 registry.

It extends the registry/evidence model from sections 17-20 with message-visible
reactions. It does not redefine what a fact, rule, evidence item, candidate,
validator or accepted registry state is.

The registry is not passive storage. Inserting, updating or removing accepted
registry state may emit a typed registry event message. Deterministic query
receivers may react to that event and derive ordinary typed facts, messages,
diagnostics or indexes from the accepted registry model. Agent receivers may
also react to the same events, but their output is always a candidate Structure
until ordinary validation accepts it.

The core rule can be summarized as a conceptual equation block, not as
Lingvamyxa source:

    accepted registry state = typed semantic authority
    query receiver          = deterministic derivation over accepted state
    registry event          = message produced by accepted state change
    agent                   = optional hypothesis generator
    candidate               = untrusted proposed Structure
    validator               = semantic gatekeeper

Canonical trust rule:

    deterministic query may derive;
    agent may propose;
    validator disposes;
    accepted registry state is authority.

32.1. Boundary of This Section

The reactive registry layer is not a separate Prolog-like language, not an AI
subsystem and not a hidden global object runtime.

It is the message-visible form of structural knowledge changing over time.

Sections 17-20 define the registry descriptors, facts, evidence graph,
composition rules, candidates and consumption modes. This section only adds:

    registry event messages;
    deterministic query receivers subscribed to those messages;
    optional agent receivers subscribed to those messages;
    validation of derived or proposed Structures;
    deterministic processing order and loop control.

32.2. Registry Events

A registry event is an ordinary typed message emitted by the registry after an
accepted transaction or profile-defined change.

Minimal event kinds are:

    registryFactAdded
    registryFactRemoved
    registryRuleAdded
    registryRuleRemoved
    registryFactChanged
    registryRuleChanged
    registryTransactionCommitted
    registryTransactionRejected

Example:

message:
    type: registryFactAdded
    transaction: 1842
    fact:
        relation: operator
        name: `+`
        leftType: decimal
        rightType: decimal
        resultType: decimal
        implementation: decNumberAdd
end: message

The event is not a special control-flow primitive. It is a typed message
delivered by the L5 message model.

32.3. Deterministic Query Receivers

A deterministic query receiver subscribes to registry events and runs formal
queries over accepted registry state.

Example receiver intent:

receiver:
    name: numericDomainCompletenessChecker
    on: registryFactAdded
    when:
        relation: operator
end: receiver

When an operator fact is added, the receiver may ask deterministic queries such
as:

query:
    relation: requiredOperator
    domain: decimal
    operator: ?op
end: query

and:

query:
    relation: operator
    domain: decimal
    name: ?op
end: query

The receiver can then derive an ordinary diagnostic Structure:

diagnostic:
    severity: warning
    message: decimal numeric domain is incomplete
    missing: (`-`, `*`, `/`, compare)
end: diagnostic

This requires no AI. It follows from formal accepted facts and rules.

32.4. Agent Receivers and Candidate Output

An agent receiver is also a message receiver, but its output is not trusted.

An agent receiver may use heuristics, pattern matching, external tools,
LLM-based tools or human-assisted tools. Its output is always a candidate
Structure. A candidate is data, not authority.

Example:

agent:
    name: numericImplementationAgent
    on: registryFactAdded
    relation: operator
end: agent

After observing:

    operator +(decimal, decimal) -> decNumberAdd

the agent may propose:

candidate:
    kind: fact
    fact:
        relation: operator
        name: `*`
        leftType: decimal
        rightType: decimal
        resultType: decimal
        implementation: decNumberMultiply
end: candidate

This is not inserted into the registry yet.

A candidate should carry provenance metadata:

candidate:
    source: `agent:numericImplementationAgent`
    event: 1842
    confidence: optional
    payload: omitted
end: candidate

The confidence value is advisory metadata only. It does not affect formal
acceptance unless a receiver explicitly uses it as non-semantic metadata.

32.5. Validation Cycle

Validation converts a candidate or derived proposal into either an ordinary
typed Structure or a diagnostic.

The validation cycle is:

    candidate received
      -> parse/check candidate shape
      -> check declared relation/type
      -> query registry for conflicts and requirements
      -> check implementation availability
      -> check L-level visibility
      -> check memory/message constraints
      -> accept or reject

Accepted example:

accepted:
    candidate: 921
    becomes: registryFactAdded
end: accepted

Rejected example:

diagnostic:
    severity: error
    candidate: 921
    reason: implementation decNumberMultiply is not visible from L1 profile
end: diagnostic

A rejected candidate may be stored for diagnostics, logs, training data,
explanation, or ignored.

32.6. Processing Order and Loop Control

For one registry transaction, processing order is deterministic.

    1. Commit source fact/rule into a registry transaction.
    2. Emit a registry event message.
    3. Run deterministic query receivers in stable registry order.
    4. Validate and enqueue their derived ordinary messages/facts/diagnostics.
    5. Run agent receivers, if enabled by profile/configuration.
    6. Convert agent output into candidate Structures.
    7. Validate candidates using ordinary validators and query receivers.
    8. Commit accepted candidates as ordinary facts/rules/messages.
    9. Store or ignore rejected candidates as diagnostics.

Agent receivers must not mutate registry state directly.

Reactive registry systems can loop.

Example:

    fact added
      -> receiver derives fact
      -> fact added
      -> same receiver derives same fact again

The runtime should track:

    transaction id
    event id
    candidate id
    source receiver
    deduplication hash
    reaction depth

Minimal safety rules are:

    the same fact is not inserted twice into one registry model;
    the same receiver/event pair is not repeated in one transaction unless explicitly allowed;
    reaction depth may be limited by profile;
    cyclic derivations must converge, be rejected, or produce a diagnostic.

32.7. L5 Thread and Message Boundaries

Registry events are messages.

Query receivers and agent receivers run inside an L5 Thread.

No raw reference from another L5 Thread may be stored in a candidate or accepted
fact.

Message payloads received from outside are borrowed by default. To retain them,
the receiver must owner-copy them into the current L5 Thread arena or receive a
moved whole branch.

This keeps the reactive registry compatible with the L5 memory model.

32.8. Minimal Bootstrap Profile

The bootstrap implementation may support only:

    fact insertion;
    registryFactAdded event;
    linear fact scan;
    deterministic query receivers;
    candidate validation;
    diagnostic output.

Rules, unification, indexing, AI agents and compiled query plans may be added
later.

Bootstrap profile:

    facts: yes
    rules: optional
    query variables: simple named placeholders
    backtracking: optional
    agent receivers: optional
    validation: required
    diagnostics: required

This still preserves the architecture:

    registry event
      -> deterministic receiver
      -> candidate/ordinary output
      -> validation
      -> accepted structure or diagnostic

32.9. Standard Statement

The reactive registry layer defines how accepted structural knowledge changes
cause typed reactions.

A fact or rule insertion, removal or update may emit a typed registry event
message.

Deterministic query receivers may subscribe to registry events and derive
ordinary typed Structures from existing accepted facts and rules.

Agent receivers may also subscribe to registry events, but their output is
always a candidate Structure and is not trusted.

Every candidate must pass normal type, query, registry, memory, message and
validation rules before it can become an ordinary fact, rule or message.

Rejected candidates are diagnostics, not failed control flow.

The registry, query engine and validators form the trusted semantic path. Agent
receivers are advisory producers of candidate Structures only.

33. HTTP Lingvamyxa REST Microservice Runtime and Built-in HTTP Client/Server Profile

This section defines the built-in HTTP Lingvamyxa REST service profile for Lingvamyxa service instances.

The profile is outside the minimal core syntax, but it is a built-in L5 service and transport profile. It is not the execution model of Lingvamyxa and it does not replace the L5 Thread/message model. Instead, it provides a standard HTTP transport for typed Lingvamyxa messages between service instances, service Thread groups and external HTTP clients.

HTTP is the transport envelope. REST routes are registry descriptors. The payload model is Lingvamyxa Structure serialization, not JSON by default.

The HTTP Lingvamyxa REST profile maps external or remote HTTP requests into standard typed L5 messages, dispatches them through the ordinary L5 registry/query/message model, and maps reply or failure messages back into HTTP responses.

The compact model is a conceptual summary, not Lingvamyxa source:

    REST route = descriptor
    HTTP request = incoming transport event
    Lingvamyxa payload = serialized Structure/message
    service = L5 Thread bundle
    dispatch = registry/query
    state = isolated L5 memory tree

33.1. Service Instance

A Lingvamyxa service instance is a bundle of L5 Threads running under one service runtime.

A service instance normally contains:

    root service configuration;
    one registry model;
    one message router;
    one or more service L5 Threads;
    optional HTTP server adapter Thread;
    optional HTTP client adapter Thread;
    optional storage/event-log Thread;
    optional agent/query/validation Threads;
    optional diagnostics and monitoring Threads.

An L5 Thread inside a service instance is still an isolated execution tree. It owns its local state, arenas, frames, message queue and registry view/cache according to the L5 memory and message model.

The service bundle is not a shared mutable heap. It is a managed set of isolated L5 Threads connected by standard typed messages.

33.2. Registry, Router and Event Log

A service instance has a registry and a message router.

The registry stores accepted facts, rules, route descriptors, service descriptors, receiver descriptors, type descriptors and implementation descriptors.

The router receives typed messages and resolves their target receiver through the registry/query layer.

The service may have an optional storage or event-log component. A simple implementation may persist:

    accepted registry facts;
    registry transactions;
    incoming HTTP request summaries;
    outgoing HTTP request summaries;
    messages;
    replies;
    failures;
    diagnostics;
    candidate Structures.

SQLite may be used as one implementation backend for this service-local persistence, but storage is not part of the core language semantics.

33.3. HTTP Lingvamyxa REST as a Built-in Service Transport Profile

HTTP Lingvamyxa REST is a built-in service transport profile.

It is not the minimal core syntax and it is not the canonical in-memory representation of a Structure. The canonical internal object is still the typed Lingvamyxa message owned by an L5 Thread.

The profile exists to provide a standard HTTP transport for typed Lingvamyxa messages, route descriptors, service-to-service calls, diagnostics, tests, external clients and deployment environments.

External HTTP request data is converted into typed Lingvamyxa Structures before dispatch. Lingvamyxa reply or failure messages are serialized back into HTTP responses after execution.

JSON may exist as an optional external adapter for compatibility, but it is not the default payload model of the HTTP Lingvamyxa REST profile.

33.4. HTTP Request to L5 Message

An incoming HTTP request is treated as an external event.

The HTTP server adapter receives:

    method;
    path;
    query parameters;
    headers;
    body bytes;
    remote peer metadata;
    request id;
    optional authentication context;
    optional timeout/deadline.

The adapter converts the HTTP request into a typed incoming message.

Example abstract message:

    message:
    . type: httpRequest
    . id: "request-1842"
    . method: POST
    . path: "/calculator/add"
    . headers: omitted
    . body: decodedRequestBody
    . peer: omitted
    end: message

If the route declares Lingvamyxa input, the request body is parsed as serialized Lingvamyxa Structure data and converted into a typed L5 message before route dispatch.

If a route explicitly declares a legacy JSON adapter, the JSON body is parsed by that adapter and converted into a Lingvamyxa Structure before route dispatch.

The result of this conversion is a normal L5 message:

    message:
    . to: calculator
    . selector: add
    . payload:
    .. a: 2
    .. b: 3
    . replyTo: httpAdapter("request-1842")
    end: message

33.5. L5 Message to HTTP Response

HTTP responses are produced from reply or failure messages.

A successful reply message may map to HTTP 200, 201, 202 or another route-declared success status.

A failure message may map to HTTP 400, 401, 403, 404, 409, 422, 500 or another route-declared failure status.

The mapping is descriptor-driven.

Example reply message:

    message:
    . type: reply
    . request: "request-1842"
    . ok: true
    . result: 5
    end: message

Example Lingvamyxa response body produced by the adapter:

    response:
        ok: true
        result: 5
    end: response

Example failure message:

    message:
    . type: failure
    . request: "request-1842"
    . code: invalidPayload
    . diagnostic: "field 'a' is required"
    end: message

Example Lingvamyxa failure response body produced by the adapter:

    response:
        ok: false
        error:
            code: invalidPayload
            diagnostic: "field 'a' is required"
        ---
    end: response

The HTTP text body is external serialized representation. The internal failure is a typed Lingvamyxa Structure.

33.6. L5 Service/Route Descriptor Profile

HTTP Lingvamyxa REST routes belong to the L5 service/route descriptor profile.

A route descriptor maps an external HTTP shape to an internal message target.

Example:

    route:
    . method: POST
    . path: "/calculator/add"
    . input: lingvamyxa
    . output: lingvamyxa
    . to: calculator
    . selector: add
    . successStatus: 200
    end: route

Equivalent compact descriptor:

    route(method(POST), path("/calculator/add"), input(lingvamyxa), output(lingvamyxa), to(calculator), selector(add), successStatus(200))

A route descriptor may specify:

    HTTP method;
    path pattern;
    query parameter schema;
    header requirements;
    input adapter;
    output adapter;
    target receiver;
    selector;
    payload mapping;
    authentication requirement;
    authorization rule;
    timeout;
    success status mapping;
    failure status mapping;
    rate or resource policy;
    visibility level.

Route descriptors are ordinary registry facts. They may be indexed, validated, queried, generated, documented and lowered through the same logical registry layer as operator, method, model and behavior descriptors.

33.7. Dispatch Through Registry/Query

An HTTP Lingvamyxa REST request is not dispatched by hard-coded string switches unless the implementation chooses that as a lowering optimization.

The semantic dispatch path is:

    HTTP request
      -> route descriptor lookup
      -> input adapter
      -> typed L5 message
      -> registry/query dispatch
      -> receiver handler
      -> reply/failure message
      -> output adapter
      -> HTTP response

Route lookup is a query over accepted route descriptors.

Example abstract query:

    query:
    . relation: route
    . method: POST
    . path: "/calculator/add"
    . target: ?target
    . selector: ?selector
    . input: ?inputAdapter
    . output: ?outputAdapter
    end: query

The query result determines how the adapter constructs the internal message.

33.8. Lingvamyxa Structure Serialization Adapter

Lingvamyxa Structure serialization is the default payload adapter for the HTTP Lingvamyxa REST profile.

It may be used for:

    incoming REST payloads;
    outgoing REST responses;
    service-to-service HTTP envelopes;
    diagnostics;
    tests;
    external agent input/output;
    debugging dumps.

Serialized Lingvamyxa payloads represent ordinary Lingvamyxa Structures. They preserve receiver frames, positional fields, named fields, ordered Structures, typed scalar values and exact quoted identifiers according to the selected serialization profile.

A Lingvamyxa serialization adapter should preserve:

    string values;
    integer values;
    decimal and real values according to declared type;
    boolean values;
    null/none markers if admitted by schema;
    arrays as ordered Structures;
    objects/records as named-field Structures;
    receiver frames;
    exact quoted identifiers;
    type descriptors when required by the route schema.

A Lingvamyxa serialization adapter must reject or mark ambiguous conversions when the route schema requires a type that the serialized payload cannot represent safely.

JSON may be supported as a legacy or interoperability adapter, but JSON is not the default payload model of this profile and does not define Lingvamyxa message semantics.

33.9. Built-in HTTP Server Profile

The HTTP server profile allows a Lingvamyxa service instance to listen for incoming HTTP requests.

The server adapter is represented as one or more L5 Threads or as a hosted native adapter that injects messages into an L5 Thread.

The server adapter owns no application state except adapter-local state such as sockets, request buffers, temporary arenas, route caches and connection metadata.

Application state belongs to service L5 Threads and follows the isolated L5 memory tree model.

A hosted C99 implementation may use an external embedded HTTP server library. This is an implementation detail and does not change the Lingvamyxa service model.

33.10. Built-in HTTP Client Profile

The HTTP client profile allows a Lingvamyxa service instance to send messages to external HTTP endpoints or other Lingvamyxa services.

The client adapter converts an outgoing Lingvamyxa message into an HTTP request and converts the HTTP response into a reply or failure message.

Example outgoing service message:

    message:
    . to: remoteService
    . selector: `calculator.add`
    . payload:
    .. a: 2
    .. b: 3
    . transport: httpLingvamyxaRest
    . endpoint: "http://service-b/lm/message"
    end: message

The HTTP client adapter may produce:

    HTTP method;
    target URL;
    headers;
    serialized body;
    timeout;
    retry metadata;
    correlation id.

The response is converted back into a typed reply/failure message and delivered to the original L5 Thread through the normal message scheduler.

33.11. Lingvamyxa-to-Lingvamyxa Service Communication

Lingvamyxa services communicate by standard Lingvamyxa messages.

HTTP Lingvamyxa REST is the standard built-in HTTP transport profile for those messages.

Other transport profiles may include:

    local in-process queue;
    SQLite-backed queue;
    file/event-log transport;
    HTTP Lingvamyxa REST;
    legacy REST/JSON over HTTP;
    binary Structure over HTTP;
    binary Structure over TCP;
    platform message bus;
    embedded device transport.

The semantic boundary is the typed message, not the transport encoding.

A remote Lingvamyxa service must not receive raw pointers, borrowed references or direct arena references from another service.

A message crossing a service boundary must be copied, serialized or transferred as a whole owned branch under a transport that explicitly supports ownership transfer.

The default HTTP Lingvamyxa REST profile is copy/serialize only.

33.12. Service Boundaries and Memory Rules

Direct cross-service raw references are forbidden.

A service boundary obeys the same rules as an L5 Thread boundary, with stronger default isolation:

    no raw pointer crosses the boundary;
    no borrow crosses the boundary;
    no service may store a reference into another service's arena;
    no service may mutate another service's local state directly;
    payloads are copied or serialized by default;
    retained incoming data must be owner-copied into the receiver service;
    failures are messages, not exceptions crossing memory spaces.

An incoming HTTP payload is borrowed only for the duration of the HTTP adapter frame unless converted into an owned message payload.

A retained request body, parsed Structure or decoded payload must be copied into an arena owned by the receiving L5 Thread or service bundle.

33.13. Service State

Service state is an isolated L5 memory tree.

The HTTP Lingvamyxa REST adapter does not own domain state. It receives HTTP events and injects typed messages.

The target L5 Thread owns and updates its own state according to the L5 memory model.

Within one L5 Thread, message handling is sequential unless a different scheduling profile is explicitly declared.

Across L5 Threads, communication is by messages only.

Across service instances, communication is by serialized or copied messages only.

33.14. Failure Mapping

Internal failures are typed failure messages.

The HTTP Lingvamyxa REST adapter maps them to HTTP status codes and response bodies.

The route descriptor may define the mapping.

Example:

    failureMap:
    . invalidPayload: 400
    . unauthorized: 401
    . forbidden: 403
    . notFound: 404
    . conflict: 409
    . validationFailed: 422
    . internalFailure: 500
    end: failureMap

The absence of a route-level mapping uses the service profile default.

A failure response should preserve a typed code and a diagnostic Structure where possible.

33.15. Module-loaded Service Endpoints

A Lingvamyxa service host may derive HTTP Lingvamyxa REST endpoints from loaded *.lmx modules.
Loaded modules materialize typed registry facts. Route descriptors may be
explicitly declared or derived by deterministic query receivers from public
service/method descriptors. Endpoint activation is transactional: a new endpoint
map becomes visible only after parsing, type checking, route derivation and
validation succeed.
              
HTTP Lingvamyxa REST exposure is never implied by procedure existence alone.
Only descriptors visible to the HTTP Lingvamyxa REST service profile may be exposed.

33.16. Security and Capabilities

HTTP server and client access should be capability-controlled.

A handler should not acquire network access implicitly.

A service configuration may grant:

    listen capability;
    outbound HTTP capability;
    route exposure capability;
    remote endpoint capability;
    authentication capability;
    storage capability.

Example descriptor:

    service:
    . name: calculatorService
    . capabilities:
    .. `http.listen`: "127.0.0.1:8080"
    .. `http.outbound`: false
    .. `storage.sqlite`: "calculator.db"
    end: service

This keeps HTTP as an explicit service capability rather than hidden global access.

33.17. Implementation Profile: Hosted C99

A hosted C99 implementation may provide the HTTP Lingvamyxa REST service profile by linking external libraries.

A typical implementation profile may use:

    embedded HTTP server library for incoming HTTP;
    HTTP client library for outgoing HTTP;
    Lingvamyxa Structure serializer/parser for default payloads;
    optional JSON parser/emitter library for legacy JSON adapter;
    SQLite for optional registry/event-log persistence;
    PCRE2 for route patterns or text processing if enabled.

For example, one possible hosted C99 profile is:

    HTTP server: CivetWeb
    HTTP client: libcurl
    Lingvamyxa serializer: implementation-owned
    legacy JSON adapter: yyjson
    storage: SQLite
    regex: PCRE2

These library choices are non-normative. They are implementation tools, not part of the core language semantics.

33.18. Minimal Bootstrap Service Profile

The minimal HTTP Lingvamyxa REST service profile may support only:

    one service instance;
    one HTTP server adapter;
    one /lm/message endpoint;
    Lingvamyxa Structure request body;
    Lingvamyxa Structure response body;
    local message router;
    synchronous request/reply;
    simple failure mapping;
    no authentication;
    no streaming;
    no service discovery;
    no retry system.

Minimal endpoint:

    POST /lm/message

Example request body:

    message:
        to: calculator
        selector: add
        payload:
            a: 2
            b: 3
        ---
    end: message

Internal message:

    message:
    . to: calculator
    . selector: add
    . payload:
    .. a: 2
    .. b: 3
    end: message

Example response body:

    response:
        ok: true
        result: 5
    end: response

This minimal profile is enough to expose a Lingvamyxa L5 Thread bundle as a simple HTTP Lingvamyxa REST microservice.

33.19. Standard Statement

A Lingvamyxa service instance is a bundle of isolated L5 Threads connected by standard typed messages.

The bundle has a registry, a message router and optional storage or event-log components.

HTTP Lingvamyxa REST is a built-in L5 service transport profile, not a core language syntax.

HTTP requests are converted into standard typed L5 messages.

HTTP responses are produced from reply or failure messages.

Routes are L5 service/route descriptors stored as typed registry facts.

Lingvamyxa Structure serialization is the default payload model for this profile.

JSON is only an optional legacy/interoperability adapter.

Lingvamyxa-to-Lingvamyxa services communicate by standard Lingvamyxa messages over a selected transport profile.

Direct cross-service raw references are forbidden.

Service boundaries obey the L5 memory and message model.

36.En. Core Authentication, Delegated Tickets and Guarantees

36.En.0. Status of This Section

This section describes the core authentication shape used by the registry and
runtime model. It is intentionally smaller than a full external identity system.

Core authentication is not OAuth, Kerberos, passkeys or an operating-system
login. Those systems may be adapters above the core. The core provides the
primitive model:

    principal;
    primary credential;
    verifier;
    delegated ticket;
    capability;
    guarantees attached to a validated flow.

An external authentication module does not replace the core model. It may obtain
or prove an external session and then request a local delegated ticket from the
core.

36.En.1. Primary Credential and Verifier

A primary credential is the ordinary local credential for a principal. In the
password profile, the user enters a password through the Lingvamyxa
authentication UI, and the core checks it against a stored verifier.

The verifier is not a password and must not be accepted by any UI or public API
as an input credential. It is a core-owned checking record.

Conceptual shape:

    principal = system or registry user
    primary secret = user-entered password
    primary verifier = password verifier record stored by the core

The password itself is never stored by the core. The verifier may be replaced
when the user changes the password or when the selected password-verifier
parameters are migrated.

36.En.2. Default Installation Credential

A simple local installation may create the first principal from the current
system user name:

    principal name = system user name
    primary secret = empty string
    primary verifier = verifier("")

This is a bootstrap convenience, not a high-assurance login. It avoids turning
installation into a fake security ceremony. The user may replace the empty
password with an ordinary password later. Replacing the primary verifier is a
security event and invalidates delegated tickets according to section 36.En.3.

36.En.2.1. Verifier Realms and Protected Objects

The principal namespace may be shared, but verifier realms are independent.

A verifier realm is a protected credential area:

    (realm, principal) -> verifier

The default realm may use the empty-string verifier and represent ordinary
local presence. This is enough for unprotected local work and for identifying
which system user owns the current flow.

When the user wants to protect something, the user creates a new verifier realm
and attaches it to an object, module or archive:

    protected L5 module;
    protected `.lmx` module;
    protected `.lmz` data archive;
    protected local registry area;
    protected service admin surface.

For example:

L5:
    fact: authRealm Default
    fact: authRealm AdminModule
    fact: authRealm WorkArchive

    fact: principal alice source SystemUser

    fact: credential Default alice primary PasswordVerifier
    fact: credential AdminModule alice primary PasswordVerifier
    fact: credential WorkArchive alice primary PasswordVerifier

    fact: protects AdminModule `admin.lmx`
    fact: protects WorkArchive `work.lmz`
end: L5

The same principal may have credentials in several realms. The system does not
assume that equal human password text across two realms means one login should
unlock both. If a protected object requires `AdminModule`, a prior login to
`Default` or `WorkArchive` is not enough unless an explicit trust bridge or
delegated ticket says so.

This keeps the default experience light while making protection explicit:

    ordinary local identity
        -> default realm, possibly empty verifier

    important module/archive/data
        -> its own verifier realm

Password reset is realm-local. Resetting the default realm may replace its
verifier with `verifier("")` or another bootstrap verifier, but it must not
reset protected object realms automatically. A `.lmz` archive or protected
module that has its own verifier realm remains protected after the default
login is reset.

This avoids the common failure mode where control over an email account or a
global account reset grants access to every local document. A reset recovers
ordinary access to the application or realm being reset; it does not decrypt or
unlock independently protected data.

36.En.2.2. Explicit Protection Instead of Global Lockout

The default realm should make ordinary local work boring. It should avoid
permanent `access denied` behavior for unprotected services, directories and
applications. If a service or directory is not declared protected, the empty or
bootstrap verifier may be enough for ordinary access.

System services and dangerous administrative surfaces may belong to an admin
realm with a sysadmin verifier. Ordinary user services may remain in the
default realm. When a user or administrator decides that a particular service,
directory or archive is important, they create a new verifier realm for that
object.

Encrypted data should belong to its own protection realm:

    protected directory
        -> separate verifier realm
        -> separate encryption key material

    `.lmz` archive
        -> separate verifier realm
        -> archive-local encryption key material

This is different from treating the whole disk as one secret. Full-disk
encryption may protect a powered-off stolen device, but it mixes device
recovery, operating-system access, ordinary files and truly protected data into
one global mechanism. If the global secret is lost, the whole machine may be
lost. If it is unlocked, too much may be unlocked.

Lingvamyxa protection should keep recovery and secrecy separate:

    system recovery
        -> reset default realm, reinstall, recreate ordinary access

    protected data recovery
        -> requires the protected realm credential or its recovery policy

Forgetting the default password should not destroy the computer. Forgetting a
protected archive or protected directory verifier may make that protected data
unrecoverable, and that is the honest cost of real encryption.

36.En.2.3. Multiple Verifiers, Session Quorum and Creator Parent

The data model must not assume that one realm/principal pair has only one
verifier. A principal in a realm may have several verifier slots. This supports
special policies without changing the core syntax later:

    (realm, principal, verifierSlot) -> verifier

The first bootstrap profile may require only one verifier slot, but stored
auth data and registry facts should leave room for multiple slots.

A minimal accepted session may also require more than one authenticated
principal inside the same module or realm. This is a session policy, not a new
source syntax rule:

    accepted session =
        principal alice authenticated in AdminModule
        principal bob authenticated in AdminModule

The exact policy language may later define `all`, `any` or threshold forms. The
important constraint for now is that a session identity is allowed to contain
more than one principal.

User/principal creation should record a creator parent:

    parent principal -> created principal

The root parent for ordinary local users is the system process or system
bootstrap principal. The parent relation is provenance, not authority. A parent
does not gain access to content protected by the created user's verifier realms
unless a separate fact, ticket, capability or shared realm grants that access.

36.En.3. Delegated Module Ticket

An OAuth-like or OS-session-like module may be allowed to act as a robot user
for a principal. It does not receive the user's primary password and does not
receive the primary verifier.

After successful primary authentication, the core may issue a delegated ticket:

    holder    = `OAuth.lmx` or another trusted module
    principal = local user represented by the ticket
    scope     = permitted action set, for example loginAs principal
    lifetime  = optional time limit
    nonce     = random ticket nonce

The delegated ticket is a bearer credential for the holder module. It should be
kept only as long as needed. A profile may keep it in memory only, persist it
through an OS secret store, or require renewal after every process restart.

The core does not have to store a second verifier for every delegated ticket.
The preferred compact profile is a stateless ticket:

    ticket_body =
        principal,
        holder,
        scope,
        issuedAt,
        expiresAt,
        nonce

    ticket_key =
        KDF(core_secret, current_primary_verifier, principal, holder, scope)

    ticket_mac =
        MAC(ticket_key, ticket_body)

    ticket =
        ticket_body + ticket_mac

`core_secret` is a core-owned random secret. A profile that wants delegated
tickets to survive process restart must store it as protected core state. A
profile that wants delegated tickets to be session-only may keep it only in
memory, which invalidates all delegated tickets on restart. `core_secret` is not
derived from the user's password.

When the holder presents the ticket, the core recomputes the key from the
current primary verifier and checks the MAC. If the primary verifier has changed
because the user changed the password or because verifier parameters were
migrated, the old ticket no longer validates.

This gives the desired rule:

    primary verifier changed
        -> previously issued delegated tickets fail validation

The ticket is not the user's password. The user's password cannot be recovered
from the ticket. The ticket is still a secret while it is valid, because whoever
holds it may exercise its scope.

36.En.4. External Authentication Modules

An OAuth/OIDC-like module may use an external provider session as a way to avoid
asking the user for the primary password again. For example, if the system
browser or OS account still has an active provider session, the module may
obtain a fresh external proof and ask the core to issue a new delegated ticket.

The external proof is not the core password model. It is an adapter input:

    external session proof
        -> module validation
        -> request local delegated ticket
        -> core ticket validation later

If the external provider session is gone, the module may run the Lingvamyxa
authentication UI and ask the user to authenticate with the primary credential.

If the user logs out from the external provider after a local delegated ticket
has been issued, the local ticket remains valid unless the selected policy
requires live external-session proof for every use or uses a very short ticket
lifetime.

36.En.5. Authentication Evidence Facts, Validators and Guarantees

This subsection is an authentication profile over the registry/evidence
machinery from sections 18-20. It does not define the general registry model
again.

The exact authentication fact names are profile-defined. A profile may describe
the model with ordinary registry-visible evidence facts:

L5:
    fact: authRealm Default
    fact: authRealm OAuthRealm
    fact: principal alice source SystemUser
    fact: credential Default alice primary PasswordVerifier
    fact: credential OAuthRealm alice primary PasswordVerifier
    fact: authModule `OAuth.lmx`
    fact: mayRequestTicket `OAuth.lmx` OAuthRealm alice
    fact: ticketScope `OAuth.lmx` OAuthRealm loginAs alice
    fact: ticketInvalidatedBy `OAuth.lmx` OAuthRealm primaryVerifierChange
end: L5

After a ticket is validated, the flow receives ordinary registry-visible
evidence:

    principal = alice
    realm     = OAuthRealm
    holder    = `OAuth.lmx`
    scope     = loginAs alice
    assurance = delegatedTicket

Receivers may require these facts or guarantees just as they may require model
validators:

L5:
    fact: requires updateProfile Authenticated
    fact: requires issueTicket PrimaryAuthenticated
    fact: grants ticket `OAuth.lmx` loginAs alice
end: L5

This keeps authentication close to the same fact/validator/guarantee machinery
used by structural models. Authentication is not a separate global role table.
It is a way to attach validated authority to an L5 flow.

36.En.6. ANSI C / libsodium Runtime Sketch

---ANSI C---
The default ANSI C / C99 security substrate uses the bundled libsodium source
archive, vendored as `third_party/libsodium.zip` and expanded into
`build/third_party/` by the full local build. It is a vendored, verified source
dependency, not a live package-manager dependency.

The runtime must call `sodium_init()` once before using the security substrate.

Possible C99 mapping:

    primary verifier:
        `crypto_pwhash_str()` using the selected Argon2id password profile.

    primary password check:
        `crypto_pwhash_str_verify()`.

    password verifier migration check:
        `crypto_pwhash_str_needs_rehash()`, if the selected profile wants
        automatic parameter migration.

    random ticket nonce and core secret:
        `randombytes_buf()`.

    secure password buffers owned by the Lingvamyxa prompt:
        `sodium_malloc()`, `sodium_mlock()`, `sodium_memzero()`,
        `sodium_munlock()` and `sodium_free()` where supported.

    ticket key derivation:
        a libsodium keyed hash or KDF over
        `core_secret`, `current_primary_verifier`, `principal`, `holder` and
        `scope`.

    ticket authentication:
        `crypto_auth()` / `crypto_auth_verify()` or an equivalent selected
        libsodium MAC profile over the serialized ticket body.

The primary verifier string must not leave the core as an input credential. It
may be read by the core as local derivation material for delegated-ticket
validation. A standard profile should combine it with a core-owned secret when
deriving the ticket MAC key, so that stealing only the verifier is not enough to
forge tickets.

If the Lingvamyxa prompt owns the password input path, the plaintext password
should live in a locked secret buffer and be wiped immediately after
verification. If the password comes from an external UI toolkit, the runtime can
only wipe the buffers it owns; it cannot retroactively protect toolkit-internal
copies.
---ANSI C---

36.En.7. Standard Statement

The core authentication model is credential-neutral but verifier-centered.
Primary password authentication, OS session adapters and OAuth-like modules all
lead to the same local result: a validated flow with explicit facts, scopes and
guarantees.

The principal namespace may be common, but verifier realms are independent.
The default realm may be light and empty-password based; protected modules,
archives and service surfaces declare their own verifier realms.

Delegated modules receive tickets or capabilities, not the user's password and
not the primary verifier. A stateless delegated ticket may be validated against
the current primary verifier, which causes password changes and verifier
migrations to invalidate older module tickets automatically.


36.Ru. Core-аутентификация, делегированные tickets и guarantees

36.Ru.0. Статус раздела

Этот раздел описывает форму core-аутентификации для registry и runtime model.
Она намеренно меньше, чем полноценная внешняя identity system.

Core-аутентификация не является OAuth, Kerberos, passkey или login-ом
операционной системы. Эти системы могут быть adapters над core. Core задает
базовую модель:

    principal;
    primary credential;
    verifier;
    delegated ticket;
    capability;
    guarantees, привязанные к проверенному flow.

Внешний модуль аутентификации не заменяет core model. Он может получить или
доказать внешнюю session и затем попросить core выдать локальный delegated
ticket.

36.Ru.1. Primary credential и verifier

Primary credential - это обычный локальный credential principal-а. В password
profile пользователь вводит пароль через Lingvamyxa authentication UI, а core
проверяет его по сохраненному verifier.

Verifier не является паролем и не должен приниматься никаким UI или публичным
API как входной credential. Это core-owned проверочная запись.

Концептуальная форма:

    principal = system или registry user
    primary secret = пароль, введенный пользователем
    primary verifier = password verifier record, хранимый core

Сам пароль core никогда не хранит. Verifier может быть заменен, когда
пользователь меняет пароль или когда выбранные параметры password verifier
мигрируются.

36.Ru.2. Credential при установке по умолчанию

Простая локальная установка может создать первый principal из имени текущего
system user:

    principal name = system user name
    primary secret = empty string
    primary verifier = verifier("")

Это bootstrap convenience, а не high-assurance login. Так установка не
превращается в фальшивую security-церемонию. Пользователь может позже заменить
пустой пароль обычным паролем. Замена primary verifier является security event
и инвалидирует delegated tickets по правилу из раздела 36.Ru.3.

36.Ru.2.1. Verifier realms и protected objects

Principal namespace может быть общим, но verifier realms независимы.

Verifier realm - это защищенная credential-область:

    (realm, principal) -> verifier

Default realm может использовать empty-string verifier и обозначать обычное
local presence. Этого достаточно для незащищенной локальной работы и для
понимания, какой system user владеет текущим flow.

Когда пользователь хочет что-то защитить, он создает новый verifier realm и
привязывает его к объекту, модулю или архиву:

    protected L5 module;
    protected `.lmx` module;
    protected `.lmz` data archive;
    protected local registry area;
    protected service admin surface.

Например:

L5:
    fact: authRealm Default
    fact: authRealm AdminModule
    fact: authRealm WorkArchive

    fact: principal alice source SystemUser

    fact: credential Default alice primary PasswordVerifier
    fact: credential AdminModule alice primary PasswordVerifier
    fact: credential WorkArchive alice primary PasswordVerifier

    fact: protects AdminModule `admin.lmx`
    fact: protects WorkArchive `work.lmz`
end: L5

Один и тот же principal может иметь credentials в нескольких realms. Система не
считает, что одинаковый человеческий password text в двух realms означает, что
один login должен открыть оба. Если protected object требует `AdminModule`,
предыдущего login в `Default` или `WorkArchive` недостаточно, если явный trust
bridge или delegated ticket не говорит обратного.

Так default experience остается легким, а protection становится явной:

    ordinary local identity
        -> default realm, possibly empty verifier

    important module/archive/data
        -> its own verifier realm

Password reset является realm-local. Сброс default realm может заменить его
verifier на `verifier("")` или другой bootstrap verifier, но он не должен
автоматически сбрасывать protected object realms. `.lmz` archive или protected
module со своим verifier realm остается защищенным после reset default login.

Так избегается обычная ошибка, когда контроль над email account или global
account reset дает доступ ко всем локальным документам. Reset восстанавливает
обычный доступ к приложению или realm, который сбрасывают; он не decrypt-ит и
не unlock-ит независимо защищенные данные.

36.Ru.2.2. Явная защита вместо global lockout

Default realm должен делать обычную локальную работу спокойной. Он должен
избегать постоянного `access denied` behavior для незащищенных services,
directories и applications. Если service или directory не объявлены protected,
empty или bootstrap verifier может быть достаточным для ordinary access.

System services и опасные administrative surfaces могут принадлежать admin
realm с verifier сисадмина. Обычные user services могут оставаться в default
realm. Когда пользователь или администратор решает, что конкретный service,
directory или archive важен, он создает для этого объекта новый verifier realm.

Encrypted data должны принадлежать собственному protection realm:

    protected directory
        -> separate verifier realm
        -> separate encryption key material

    `.lmz` archive
        -> separate verifier realm
        -> archive-local encryption key material

Это отличается от подхода, где весь диск считается одним secret. Full-disk
encryption может защитить выключенное украденное устройство, но смешивает
device recovery, operating-system access, ordinary files и truly protected data
в один global mechanism. Если global secret потерян, можно потерять всю машину.
Если он unlocked, слишком многое оказывается unlocked.

Lingvamyxa protection должна разделять recovery и secrecy:

    system recovery
        -> reset default realm, reinstall, recreate ordinary access

    protected data recovery
        -> requires the protected realm credential or its recovery policy

Забытый default password не должен уничтожать компьютер. Забытый verifier от
protected archive или protected directory может сделать эти protected data
невосстановимыми, и это честная цена настоящего encryption.

36.Ru.2.3. Multiple verifiers, session quorum и creator parent

Data model не должна предполагать, что у пары realm/principal есть только один
verifier. Principal в realm может иметь несколько verifier slots. Это
поддерживает особые политики без изменения core syntax позже:

    (realm, principal, verifierSlot) -> verifier

Первый bootstrap profile может требовать только один verifier slot, но stored
auth data и registry facts должны оставить место для нескольких slots.

Минимально accepted session тоже может требовать больше одного authenticated
principal внутри одного module или realm. Это session policy, а не новое
правило source syntax:

    accepted session =
        principal alice authenticated in AdminModule
        principal bob authenticated in AdminModule

Точный policy language позже может задать `all`, `any` или threshold forms.
Важное ограничение сейчас: session identity может содержать больше одного
principal.

Создание user/principal должно записывать creator parent:

    parent principal -> created principal

Root parent для обычных local users - system process или system bootstrap
principal. Parent relation является provenance, а не authority. Parent не
получает доступ к content, защищенному verifier realms созданного user-а, если
отдельный fact, ticket, capability или shared realm не выдает такой доступ.

36.Ru.3. Delegated module ticket

OAuth-like или OS-session-like модулю можно разрешить действовать как
robot-user для principal-а. Он не получает primary password пользователя и не
получает primary verifier.

После успешной primary authentication core может выпустить delegated ticket:

    holder    = `OAuth.lmx` или другой доверенный модуль
    principal = локальный user, которого представляет ticket
    scope     = разрешенный набор действий, например loginAs principal
    lifetime  = опциональное время жизни
    nonce     = random ticket nonce

Delegated ticket является bearer credential для holder-модуля. Его следует
держать только столько, сколько нужно. Профиль может держать его только в
памяти, сохранять через OS secret store или требовать перевыпуска после каждого
restart процесса.

Core не обязан хранить второй verifier для каждого delegated ticket.
Предпочтительный компактный профиль - stateless ticket:

    ticket_body =
        principal,
        holder,
        scope,
        issuedAt,
        expiresAt,
        nonce

    ticket_key =
        KDF(core_secret, current_primary_verifier, principal, holder, scope)

    ticket_mac =
        MAC(ticket_key, ticket_body)

    ticket =
        ticket_body + ticket_mac

`core_secret` - core-owned random secret. Профиль, которому нужно переживание
delegated tickets через restart процесса, должен хранить его как protected core
state. Профиль, которому нужны только session-only delegated tickets, может
держать его только в памяти; тогда restart инвалидирует все delegated tickets.
`core_secret` не выводится из password пользователя.

Когда holder предъявляет ticket, core заново считает key из текущего primary
verifier и проверяет MAC. Если primary verifier изменился из-за смены пароля
или миграции verifier parameters, старый ticket больше не валидируется.

Получается нужное правило:

    primary verifier changed
        -> ранее выпущенные delegated tickets не проходят validation

Ticket не является паролем пользователя. Пароль пользователя невозможно
восстановить из ticket. При этом ticket остается secret на время своей
валидности, потому что тот, кто держит ticket, может использовать его scope.

36.Ru.4. Внешние authentication modules

OAuth/OIDC-like модуль может использовать внешнюю provider session, чтобы не
просить у пользователя primary password повторно. Например, если system browser
или OS account все еще имеет активную provider session, модуль может получить
свежий external proof и попросить core выдать новый delegated ticket.

External proof не является core password model. Это вход adapter-а:

    external session proof
        -> module validation
        -> request local delegated ticket
        -> core ticket validation later

Если внешняя provider session исчезла, модуль может запустить Lingvamyxa
authentication UI и попросить пользователя пройти primary credential.

Если пользователь вышел из внешнего provider-а после того, как локальный
delegated ticket уже выдан, локальный ticket остается валидным, если выбранная
policy не требует live external-session proof для каждого использования или не
использует очень короткое время жизни ticket.

36.Ru.5. Authentication evidence facts, validators и guarantees

Этот подпункт является authentication-профилем поверх registry/evidence-механики
разделов 18-20. Он не определяет общую registry model заново.

Точные имена authentication facts задаются профилем. Профиль может описывать
модель обычными registry-visible evidence facts:

L5:
    fact: authRealm Default
    fact: authRealm OAuthRealm
    fact: principal alice source SystemUser
    fact: credential Default alice primary PasswordVerifier
    fact: credential OAuthRealm alice primary PasswordVerifier
    fact: authModule `OAuth.lmx`
    fact: mayRequestTicket `OAuth.lmx` OAuthRealm alice
    fact: ticketScope `OAuth.lmx` OAuthRealm loginAs alice
    fact: ticketInvalidatedBy `OAuth.lmx` OAuthRealm primaryVerifierChange
end: L5

После validation ticket flow получает обычное registry-visible evidence:

    principal = alice
    realm     = OAuthRealm
    holder    = `OAuth.lmx`
    scope     = loginAs alice
    assurance = delegatedTicket

Receivers могут требовать эти facts или guarantees так же, как они требуют
model validators:

L5:
    fact: requires updateProfile Authenticated
    fact: requires issueTicket PrimaryAuthenticated
    fact: grants ticket `OAuth.lmx` loginAs alice
end: L5

Так authentication остается рядом с той же fact/validator/guarantee machinery,
которую используют structural models. Authentication не становится отдельной
глобальной таблицей ролей. Это способ привязать проверенную authority к L5
flow.

36.Ru.6. ANSI C / libsodium runtime sketch

---ANSI C---
Default ANSI C / C99 security substrate использует bundled libsodium source
archive, импортированный как `third_party/libsodium.zip` и распаковываемый в
`build/third_party/` полной локальной сборкой. Это vendored, проверенная source
dependency, а не живая package-manager dependency.

Runtime должен вызвать `sodium_init()` один раз перед использованием security
substrate.

Возможная C99 mapping:

    primary verifier:
        `crypto_pwhash_str()` с выбранным Argon2id password profile.

    primary password check:
        `crypto_pwhash_str_verify()`.

    password verifier migration check:
        `crypto_pwhash_str_needs_rehash()`, если выбранный профиль хочет
        automatic parameter migration.

    random ticket nonce and core secret:
        `randombytes_buf()`.

    secure password buffers, которыми владеет Lingvamyxa prompt:
        `sodium_malloc()`, `sodium_mlock()`, `sodium_memzero()`,
        `sodium_munlock()` и `sodium_free()`, где поддерживается.

    ticket key derivation:
        libsodium keyed hash или KDF над
        `core_secret`, `current_primary_verifier`, `principal`, `holder` и
        `scope`.

    ticket authentication:
        `crypto_auth()` / `crypto_auth_verify()` или другой выбранный
        libsodium MAC profile над serialized ticket body.

Primary verifier string не должен выходить из core как входной credential. Core
может читать его как локальный derivation material для validation delegated
ticket. Standard profile должен смешивать его с core-owned secret при выводе
ticket MAC key, чтобы кражи одного verifier было недостаточно для подделки
tickets.

Если Lingvamyxa prompt владеет password input path, plaintext password должен
жить в locked secret buffer и затираться сразу после verification. Если пароль
приходит из внешнего UI toolkit, runtime может затирать только собственные
buffers; он не может задним числом защитить toolkit-internal copies.
---ANSI C---

36.Ru.7. Короткая формула

Core authentication model является credential-neutral, но verifier-centered.
Primary password authentication, OS session adapters и OAuth-like modules
приводят к одному локальному результату: validated flow с явными facts, scopes
и guarantees.

Principal namespace может быть общим, но verifier realms независимы. Default
realm может быть легким и empty-password based; protected modules, archives и
service surfaces объявляют собственные verifier realms.

Delegated modules получают tickets или capabilities, а не password пользователя
и не primary verifier. Stateless delegated ticket может валидироваться через
текущий primary verifier; поэтому смена пароля и verifier migration
автоматически инвалидируют старые module tickets.
