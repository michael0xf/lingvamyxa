Lingvamyxa Part II Specification
================================

Part II: L4-L5 Registry, Messages, Runtime Services and Authentication

This part describes the high-level runtime model. It is intentionally written
around one mechanism:

    LMX expressions + registry tables -> resolved expressions -> execution or
    lowering.

Semantic core:

    Message
        Proposed LMX expression candidate; an external or internal request for
        action or computation.

    L3 expression
        Structure tree describing algorithmic composition: which operations,
        receivers, values and nested expressions are connected, and what result
        is requested.

    Registry classes + relation tables
        Meaning space. Any meaningful term may be a registry class/key: value
        class, operation, field, validator, message kind, evidence, authority,
        service route or implementation binding.

    L2/L1 procedural bindings
        Executable leaves: primitive lowering, C/L1 target, L2 function,
        L2 procedure or other low-level implementation.

    Validator/Merge
        Table-walking resolver. It reads registry tables, accumulates evidence
        and builds a ConcreteExpression / ExecutionPlan.

    Executor
        Minimal runner of already resolved plans. It calls the selected
        procedural bindings and emits result/failure/outgoing-message records.

Short formula:

    Message supplies the candidate.
    Expression supplies the structural algorithm.
    Registry tables supply compatibility and selected cells.
    Procedural bindings supply executable leaves.
    Validator/Merge turns candidates into concrete plans.
    Executor runs only concrete plans.

World-description formula:

    User describes the world. L4 stores relations, L3 stores computable
    structures, L5 stores proposed actions/messages. The analytical engine
    continuously classifies the active world enough to resolve, validate and
    execute current work.

    The L-levels define language strata. The analytical engine is not another
    source language level such as `L6`; it is an active interpretation,
    translation and runtime machine operating over existing strata, especially
    L3, L4 and L5.

Registry query principle:

    Strict classification happens in L4 registry tables. Type checking, class
    resolution, overload resolution and provider selection are logical
    resolution/checking processes over those tables. A SQL-like query is the
    reference mental model, but an implementation may use any equivalent
    algorithm that reads the same L4 facts and produces the same selected cells,
    diagnostics and evidence.

    The source of truth is the registry schema: table existence, table rows,
    table imports/overlays and cell payloads. In-memory rows, hash tables,
    SQLite indexes, binary indexes and per-thread RegistryCaches are caches or
    materialized views of that registry schema. They may optimize lookup, but
    they do not define a second type system.

    In this sense Lingvamyxa uses analytical typing. Classification starts in
    the static interpretation/translation/compilation stages, where receivers
    and validators query L4 data, and continues at runtime through the active L5
    RegistryView. The model is the L4 registry data itself, predominantly table
    data. SQLite, generated C arrays, hash indexes or other stores are
    projections/materializations of L4, not the model that L4 must be mapped
    onto.

    L4 is therefore not merely metadata for the compiler. It is the analytical
    layer of the language. L3 expressions describe computation; L5 messages
    describe proposed actions, effects and runtime boundaries; L4 supplies
    knowledge, classification and derived decisions that both L3 and L5 may
    query. A minimal implementation may start with table lookup, but the model
    is intended to admit rule-based reasoning, unification, backtracking and
    resolution over L4 facts and derived relations.

    A table named `X`, when present in an L4 schema, is the descriptor table for
    class/key `X`. The table named `class` is an index/classification table over
    class keys; it is not the only source of class existence. If a class has no
    dedicated descriptor table yet, it may still be referenced through `class`
    or through other relation tables.

Mechanism filter:

    A profile term is not a new language mechanism merely because it has a
    name.

    A term remains profile vocabulary when it can be expressed as:

        LMX Structure;
        receiver/profile consumption;
        registry row/cell;
        validator evidence;
        ExecutionPlan payload;
        executor result/failure.

    Examples include provider, replayPolicy, freshness, confidence,
    calibration, budget, effect fence, authority ticket, safeMode and
    decision-log rows. These names are important for particular systems, but
    they do not become core semantics while they pass the filter.

    A term should be promoted to core semantics only when it cannot be modeled
    by the existing Structure / receiver / registry / validation / plan /
    execution pipeline without changing that pipeline.

The old section number is shown in parentheses after each new heading.


1. Core Table Model (old 17, 18, 19, 20, 21)
--------------------------------------------

1.1. Class (new, old 17-21)
~~~~~~~~~~~~~~~~~~~~~~~~~~~

In Part II, `class` is the general word for a named registry form/table/key.
When this wider meaning must be distinguished from an object-oriented class,
this document may use the phrase `registry class`.

The strongest source form for a class is a table with the same name:

    table:
        name: Circle
        ...
    end: Circle

This table is the descriptor table for class/key `Circle`. The `class` table is
an index and classification table that may reference `Circle`, group it, attach
kind information or make it discoverable. It is not a mandatory central list
that alone creates the class. Conversely, a class/key may be referenced in the
`class` table or in other relation tables before a dedicated descriptor table is
introduced.

This is wider than an object-oriented class and wider than a value/storage
type. The following names may all be classes in this general sense:

    decimal
    u32
    equals
    plus
    Array
    Circle
    Message
    Validator
    AuthTicket
    None
    FORBIDDEN
    spelling
    implementation
    result

A class is meaningful because tables contain rows that mention it or are owned
by it. A concrete value class, such as `decimal`, usually has representation
tables. An operation class, such as `Equals`, usually has implementation
tables. A message class, validator class, evidence class or service route class
may also be represented by tables.

A class instance is any concrete Structure accepted by that registry form. It
may be an object-like value, an operation-selection record, a validator record,
a message, an evidence record, an authority ticket or a service descriptor.

The language does not need a separate primary mechanism for interface, trait,
generic constraint or overload set. These are class/table patterns. A
traditional object class is one possible class profile, not the definition of
the term.

This is why a Lingvamyxa class is not a Java/C++/C# class as a base concept.
It is not primarily a code container with hidden method lookup and inheritance.
It is a registry form/table/key. A class may describe object-like values, but
it may also describe operations such as `Equals`, validators, messages,
evidence records, authority rows, routes or implementation-selection keys.
Object-style classes are built from the same table mechanism rather than being
the root of the mechanism.

1.2. Relation Tables and Class/Table Import/Overlay (new, old 18, 19, 20.5, 20.6, 21.5)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Tables describe relations between classes. A binary operation may be visualized
as a sparse matrix:

    table equals

              decimal          real             int
    decimal   decimal_eq       decimal_real_eq  decimal_int_eq
    real      real_decimal_eq  real_eq          real_int_eq
    int       int_decimal_eq   int_real_eq      int_eq

The selected cell is the terminal payload returned by table lookup for the
current table and lookup keys. The table name and the keys that selected the
cell are the access path; they are not required to be repeated inside the cell
payload.

A cell may be written in short form as a single atom such as `decimal_int_eq`,
`decimal_int_add` or `int_eq`. A consuming profile normalizes such a short form
to a terminal cell payload kind and payload. Optional result, effect, lifetime,
authority, priority, cost and provenance metadata may be stored in side tables
keyed by the payload class/key or by an implementation-generated cell id.

The canonical source form for a relation table is a table Structure with an
explicit name, column list and dense rows. `columns` is not a registry namespace
item by itself. It is a field consumed by `table`.

Within one registry source module, two `table` declarations with the same
normalized name are an error. Later registry merge may combine different source
modules through explicit import/overlay/conflict rules, but a single module must
not contain two independent descriptor tables with the same name.

Column syntax is generic:

    atom
        The atom is the column name.

    anonymous Structure
        The first atom is the column name. The remaining atoms are column
        descriptors. Descriptors are ordinary class/key names and may be stored
        as relation rows by the loader.

For example:

    columns: class (spelling char) (cost serial)

means a row-key column named `class`, a column named `spelling` with descriptor
`char`, and a column named `cost` with descriptor `serial`.

Class/key spelling follows the ordinary identifier rule:

    if the class/key name is a valid ordinary Lingvamyxa identifier, write it
        bare;
    if it contains operator characters, whitespace, punctuation, dots, arrows,
        external spellings or any spelling that must round-trip exactly, write
        it as an exact quoted identifier.

For example:

    u32
    result
    implementation
    sqrt_ansi_c
    `+`
    `translator type-->spelling`
    `implementation-->L2 lowering`

The semantic class/key value of an exact quoted identifier is its payload after
backtick unescaping; the backticks are not part of the class/key.

By convention the first column is `class`; it carries the row class/key. Later
column names are also classes. The cell under such a column is the value of
that relation coordinate:

    table:
        name: `translator type-->spelling`
        columns: class (spelling char)
        rows:
            u8  "uint8_t"
            u16 "uint16_t"
            u32 "uint32_t"
    end: `translator type-->spelling`

This means:

    `translator type-->spelling`[u8][spelling]  -> "uint8_t"
    `translator type-->spelling`[u16][spelling] -> "uint16_t"

Here `translator type-->spelling`, class, spelling, u8 and u16 are
registry classes/keys. The strings `"uint8_t"` and `"uint16_t"` are terminal
primitive payloads for the active L2/L1 lowering profile unless another table
explicitly treats those spellings as registry classes.

An empty table cell is interpreted through the declared class/domain of that
cell. A table profile may define its typed empty-cell behavior through
`None.cell`; expression-level `None` values are defined through `None.value` or
through the target class's contextual-literal table. Primitive classes are still
ordinary registry classes, not a separate Java-style type universe. A hosted
bootstrap implementation uses `None`, not a separate semantic class of absence.

Contextual literals are ordinary L4 registry facts, not parser keywords. A
contextual literal is a class/key whose concrete payload is selected by the
expected target class supplied by a declaration, assignment target, call slot,
operator slot, comparison peer or other consumer.

To introduce a new contextual literal such as `None`, `true`, `false`, `OK` or
a profile-defined name:

    1. Declare the literal name as a `contextualLiteral` class/key. The usual
       place is the `class` table:

           table:
               name: class
               columns: class (kind class)
               rows:
                        None  contextualLiteral
                        OK    contextualLiteral
                        false contextualLiteral
                        true  contextualLiteral
           end: class

    2. For each target value class that wants a class-local meaning, add rows to
       that target class table. The conventional column descriptor is
       `context literal` plus the target class:

           table:
               name: int8
               columns: class  (`context literal` int8)
               rows:
           end: int8

           join: (int8) Boolean
               columns: class  (`context literal` int8)
               rows:
                        None  -1
                        false 0
                        true  1
                        OK    1
           end: Boolean

       In this example `Boolean[None] = -1`, `Boolean[false] = 0`,
       `Boolean[true] = 1` and `Boolean[OK] = 1`. The numeric cells are ordinary
       payloads. They are not a global empty-cell encoding.

    3. If the literal also has a fallback mapping, register it in
       `contextual.literal.value`. The payload points to a value table keyed by
       the expected target class:

           table:
               name: `contextual.literal.value`
               columns: class (value relation)
               rows:
                        None  `None.value`
                        OK    `OK.value`
                        false `false.value`
                        true  `true.value`
           end: `contextual.literal.value`

           table:
               name: `None.value`
               columns: class (value char)
               rows:
                        int     0
                        int8    0
                        Boolean -1
           end: `None.value`

       A class-local row in the expected target table is preferred. The fallback
       path is used only when the consumer still has an expected class but the
       class table does not define a more local contextual value.

    4. If the literal may appear as an expression atom, bind it through the
       active expression profile, for example `expr.atom`:

           table:
               name: `expr.atom`
               columns: class (ansi_c char) (emitter binding)
               rows:
                        None  None  lm_trans_expr_emit_contextual_literal
                        OK    OK    lm_trans_expr_emit_contextual_literal
           end: `expr.atom`

    5. If the literal may be used as a statement receiver for contextual
       assignment, bind the receiver vocabulary as ordinary namespace data:

           table:
               name: namespace
               columns: class (receiver.type relation)
               rows:
                        None `receiver.statement`
                        OK   `receiver.statement`
           end: namespace

           table:
               name: `receiver.statement`
               columns: class (receiver binding)
               rows:
                        None lm_trans_statement_emit_contextual_literal_assignment
                        OK   lm_trans_statement_emit_contextual_literal_assignment
           end: `receiver.statement`

With those rows, `None: target`, `Boolean: flag OK`, a call argument containing
`None` and `if: value = None` all use the same table-driven path. The syntax
supplies the surrounding consumer; the registry supplies the contextual value.
Adding another name such as `Red` or `Maybe` is another set of rows, not a
parser change. Empty source cells in tables remain a separate table-loading
concern and should be declared through `None.cell` when a typed empty cell must
not materialize a row.

`FORBIDDEN` is the standard explicit prohibition class/value. It is different
from `None`: `None` is the typed empty/contextual value selected by the active
table profile, while `FORBIDDEN` means the relation is present and explicitly
denied.

Adding a new class does not require adding it to every table. Missing cells
become the resolver's empty result after the full lookup path is exhausted.

The same information may be viewed through another table, for example a
class-centered view:

    table decimal

              decimal          real             int
    plus      decimal_plus     decimal_real_add decimal_int_add
    minus     decimal_minus    decimal_real_sub -
    equals    decimal_eq       decimal_real_eq  decimal_int_eq

These are not separate semantic systems. They are convenient table layouts over
terminal relation rows.

Classes and tables may import other classes or tables. Import here means
explicit table extension/overlay, not hidden copying of code or method bodies. A
lookup first checks the importing table/class, then the explicitly imported
bases according to the declared priority policy.

Example:

    table: appEquals
        import:
            numericEquals
            textEquals
        priority:
            numericEquals: 20
            textEquals: 10
        String:
            String: string_eq
    end: appEquals

Multiple imports are allowed only when the import order or priority is
explicit. If two imported bases provide the same cell:

    same cell, same payload      -> duplicate, allowed or ignored;
    same cell, different payload -> conflict unless priority/override admits it;
    missing cell                 -> continue lookup in lower-priority bases.

The same rule applies to class descriptors. A class may import another class to
reuse field rows, validator rows, operation rows, authority rows or any other
registry relation rows. The imported rows remain table data; no source-level
method body is copied merely because a class imports another class.

Any finite graph can be decomposed into binary tables by introducing
intermediate keys. For an n-ary expression, the registry may use signature keys,
partial tables or chained binary relations. This is a storage/resolution
technique; source syntax remains ordinary LMX expressions.

1.3. Registry Source and MIX Definitions (new, old 17.3, 18, 32)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The source of registry rows is LMX itself. A profile may load one or more LMX
files before interpreting or translating a target file:

    registry:
        file: core/classes.lmx
        file: core/operators.lmx
        file: service/messages.lmx
    end: registry

Those files are parsed as ordinary LMX structures. They may use MIX bounded
forms `{...}` to mark groups, documentation regions, visual clusters or active
sets. MIX marks are not a separate metadata language; they are bounded LMX forms
whose result goes to the MIX overlay stream.

Example sparse registry source:

    table:
        name: equals
        columns: class (decimal char) (int char)
        rows:
            decimal decimal_eq decimal_int_eq
            int     int_decimal_eq int_eq
    end: equals

The interpreter/resolver must be able to consume such LMX/MIX definitions and
load registry tables. In a compiled profile, this step may run at build time.
In a live L5 profile, the same table source may be loaded at runtime.

1.4. Expression Resolution (new, old 20, 21.5)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

An L3+ expression is first a Structure. Class resolution does not change the
source tree. It selects table cells.

Algorithmically, this is a logical query against the active RegistryView. The
resolver asks relation tables for coordinates such as operation, receiver,
argument classes, result class, validators, effects, authority and executable
binding. A SQL-like query is the simplest way to describe the required result,
but the implementation may use linear arrays, hash tables, SQLite, generated C
arrays or another equivalent resolver. Those structures are
cache/materialized-view forms of the L4 registry tables, not the semantic
authority.

For:

    a + b

the resolver performs:

    op = plus
    row = class(a)
    column = class(b)
    cell = plus[row][column]

If the full lookup path returns `None`, the expression is invalid in that
registry unless the consuming receiver/profile explicitly admits `None`. If the
selected cell is `FORBIDDEN`, the expression is rejected with an explicit
prohibition diagnostic. If exactly one non-None cell is selected, the expression
becomes resolved. If a table profile admits multiple candidates, priority/cost
tables must reduce them to one candidate or report ambiguity.

For a generic expression, some coordinates are initially unknown:

    sum: xs

The resolver derives requirements from the expression body, for example:

    length[class(xs)]
    at[class(xs)][index_class]
    plus[element_type][element_type]
    zero[element_type]

Generic resolution is the process of filling those table coordinates with
concrete classes and terminal cells. There is no special generic syntax required
by this model.

1.5. Terminal Cell Payloads and Descriptors (new, old 21)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A terminal cell is the payload returned by a registry table lookup.

The lookup path is separate from the payload. For example:

    plus[decimal][int] = decimal_int_add

The table `plus` and the lookup keys `decimal` and `int` are already known from
the lookup context. They are not mandatory fields of the returned cell payload.
The returned payload is `decimal_int_add`.

In an implementation view this may be represented as:

    CellKey(table_id, key_id*) -> CellPayload(kind, payload)

The key tuple selects the cell. The payload says what the selected cell means.

The minimal normalized terminal cell payload has two fields:

    kind
        The payload kind.

    payload
        The value, binding, expression, table key, validator target, message
        target or diagnostic Structure carried by the cell.

Mandatory payload kinds are:

    primitive
        A primitive/scalar value, literal result or terminal L2/L1 lowering
        payload admitted by the active profile. In early bootstrap tables many
        final cells are primitive lowering payloads such as `"uint32_t"`,
        `"sqrt"` or `"=="`.

    binding
        A reference to an executable or lowerable binding, such as an L2/L3
        function/subroutine target, an L1/C symbol, an inline primitive lowering
        rule or a generated trampoline.

    descriptor
        A registry descriptor. In this draft the only mandatory descriptor form
        is a class/key reference: the cell names another registry class/key and
        the resolver may continue through tables selected by the consuming
        profile. Structured descriptor records, callable descriptor payloads,
        provider descriptor records and other descriptor forms are reserved for
        later revisions. A descriptor is the semantic entity or materialized
        semantic view selected by the cell: it may summarize registry rows,
        inferred facts, profile data and validation evidence. It is not merely a
        table-walking cursor. If the payload exists only to continue lookup
        through another table coordinate, use `tableKey`.

    expression
        An L2/L3/L4/L5 expression Structure admitted by the selected profile.
        The resolver or executor consumes that expression after substitution or
        further resolution.

    tableKey
        An intermediate registry class/key used to continue n-ary or graph
        resolution through another table. A `tableKey` is resolver navigation
        state, not the final semantic descriptor selected for execution,
        validation or projection.

    validator
        A validator target or validation expression that may produce acceptance,
        rejection, diagnostic information or stronger evidence.

    messageTarget
        A message/action target selected for a validated message expression.

    diagnostic
        A rejection, missing relation, ambiguity, conflict or profile-defined
        diagnostic Structure.

    None
        The standard empty result of resolution. Missing row, missing column or
        missing cell normalize to the resolver's empty result after the full
        lookup path is exhausted. In table source, an intentionally empty cell
        is expressed through `None.cell`.

    forbidden
        Explicit prohibition. `FORBIDDEN` is not an empty value; it means the
        relation exists and is denied.

    conflict
        An explicit conflict marker produced by registry loading or resolution.

A short source spelling may normalize directly to a payload. Examples:

    table:
        name: plus
        columns: class (int char) (u32 char)
        rows:
            decimal decimal_int_add None
            u32     None            plus_u32_u32_l2
    end: plus

may normalize conceptually as:

    plus[decimal][int] -> CellPayload(descriptor, decimal_int_add)
    plus[u32][u32]     -> CellPayload(descriptor, plus_u32_u32_l2)

A terminal cell payload is not required to be a heavy record in source form. The
payload atom may itself be a registry class/key. That class/key may then be
used as a key into additional descriptor tables:

    table:
        name: `plus cell-->result`
        columns: class (result char)
        rows:
            decimal_int_add decimal
            plus_u32_u32_l2 u32
    end: `plus cell-->result`

    table:
        name: effects
        columns: class (effect char)
        rows:
            decimal_int_add pure
            plus_u32_u32_l2 pure
    end: effects

    table:
        name: level
        columns: class (level char)
        rows:
            decimal_int_add L2
            plus_u32_u32_l2 L2
    end: level

    table:
        name: `implementation-->L2 lowering`
        columns: class (symbol char)
        rows:
            plus_u32_u32_l2 "+"
    end: `implementation-->L2 lowering`

    table:
        name: cost
        columns: class (cost serial)
        rows:
            decimal_int_add 10
            plus_u32_u32_l2 1
    end: cost

Therefore optional cell descriptor information may be stored inline, derived
from the table and lookup keys, or stored in side tables. Common optional
descriptor rows are:

    result
        Result class, result model, result table key or result expression.

    effects
        Pure/effect/action policy: pure, read-only, mutates receiver, sends
        message, filesystem write or profile-defined effect.

    level / visibleFrom
        The level or profile where the payload is callable or lowerable.

    validators / evidence requirements
        Additional validators or evidence that must hold before the payload may
        be consumed.

    lifetime / ownership
        Primitive value, owned result, borrowed result, moved result, external
        handle, arena-owned result or another profile-defined memory policy.

    authority / capability
        Required permission, ticket, verifier or capability for message/action
        cells.

    priority / cost
        Deterministic ranking information used when a profile admits multiple
        candidate cells.

    conflict policy
        Duplicate, override, replace, prefer, reject or profile-defined conflict
        handling.

    diagnostic policy
        Diagnostic code, severity and message produced for missing, rejected,
        ambiguous or conflicting cells.

    source / provenance
        File, line, receiver, generated origin, builtin origin or imported
        registry origin for diagnostics and incremental rebuilds.

Provider/device descriptor rows may also be attached to binding payloads:

    providerOf
        The provider/device/profile that executes or lowers the payload.

    binding
        The concrete L2/L1/device/service binding selected for the payload.

    precision
        exact, bounded, approximate, calibrated, drifting or another
        profile-defined precision policy.

    latency
        inline, slow, async, remote, cycles-counted or another profile-defined
        execution-time policy.

    determinism
        deterministic, calibrated-deterministic, noisy, sampled or another
        profile-defined repeatability policy.

    confidence
        none, flags, probability, u8 score or another profile-defined confidence
        representation.

    calibration
        none, required, valid, expired, source-specific or another
        profile-defined calibration state.

    fallback
        Alternative cells or payloads when the selected provider is unavailable,
        rejected by policy, too expensive, insufficiently precise or below
        required confidence.

A diagnostic payload may be written explicitly:

    table: plus
        decimal:
            String:
                diagnostic:
                    code: incompatibleOperands
                    message: "plus(decimal, String) is not defined"
                end: diagnostic
    end: plus

A graph or n-ary relation may use a `tableKey` payload to continue resolution:

    multiply[Matrix][Matrix] -> MatrixMultiplySignature
    MatrixMultiplySignature[leftCols][rightRows] -> matrix_mul_impl

The current bootstrap may still contain hardcoded ANSI C lowering for L2/L1
surface forms. Those hardcoded rules are terminal cell payloads that have not
yet been moved into registry tables.


2. Four-Stage Message Model (new, old 20.2, 20.6, 27.5, 27.9)
-------------------------------------------------------------

2.1. Message (new, old 20.2, 27.5)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A message is a proposed, possibly effectful/action-capable LMX expression
candidate addressed to a receiver. It may become an action after validation,
but it is not concrete before validation, is not a transport packet and is not
executed on arrival.

It may be a full LMX subtree or a very small LMX subset. The language does not
bake in a fixed restriction such as "one command only" or "no explicit classes".
Those restrictions are policy decisions of the receiving side.

A message expression may be as large as the receiver profile admits. Because
the expression field is ordinary LMX, a message may contain nested expressions,
deferred Structures, local descriptors, validators, calls, control receivers,
MIX marks and other message-producing forms. These forms are not trusted merely
because they appear in the message. They become executable only after
validation/merge has reconciled them with the receiver registry and produced a
ConcreteExpression / ExecutionPlan.

There is no separate Smalltalk-style selector syntax required by the message
model. The selector/call/receiver shape is already an LMX Structure. If a
profile wants selector-like dispatch, it reads that Structure through registry
tables during validation/merge. Message richness therefore comes from LMX
itself, not from a second message mini-language.

"Effectful/action-oriented" does not mean that every message must mutate
something. A query, read request or validation-only request may also be a
message. The point is that a message is capable of becoming an action after
validation and execution-plan construction.

Example:

    message:
        from: user42
        to: ArchiveService
        expression:
            save:
                file: "report.lmx"
                mode: overwrite
    end: message

The message is proposed source data. It may carry a local mini-model, expected
result/effect descriptors, payload data, context, capability claims or
implementation references. These are claims, not authority and not executable
code. HTTP, queues, sockets and files are only transport/storage envelopes for
such proposed expressions.

2.1.1. Message Body, External Structures and MIX Cursors
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A message expression may contain its body inline, but it is not required to do
so. A message may also carry references, cursors, ranges or capabilities that
identify external LMX Structures, MIX documents, storage objects or streamable
body regions.

Inline body:

    message carries the Structure.

External body:

    message carries a cursor/reference/range/capability to a Structure.

Streamed body:

    cursor operations produce chunks, positions or projected Structures on
    demand.

Such external body references are ordinary LMX values. They are claims until
validation/merge admits them. A receiver may validate the cursor, authority,
range, lifetime and access mode before reading or writing the referenced body.

The referenced body may be read incrementally. The core message model does not
require the whole body to be present in one transport packet or one contiguous
memory block. A profile may provide cursor-based access, chunked reading,
chunked writing, range queries, lazy body loading or stream-like traversal.

Example of a short semantic record that names a larger body:

    message:
        to: ReportService
        expression:
            process:
                body:
                    cursor: reportStore\flightLog\segment42
                    range: current
                    mode: readStream
    end: message

MIX-aware storage may support multiple cursors over the same document/body.
Cursors expose the current attribute table, Structure context, active MIX sets
and payload-local marks at their current position. Concurrent cursor use is a
runtime/storage profile concern; the language-level rule is that cursor
operations are ordinary validated LMX operations and may produce result/failure
messages like any other expression.

Therefore a small message may name or authorize a large body without carrying
that body inline. Transport envelopes carry enough LMX to identify the proposed
operation and its body references; the body itself may reside in a document
store, MO/ROM storage, local cache, service object, stream or another
profile-defined source. On slow links, the message frame can remain short while
the semantic operation stays full LMX: the receiver reads the body only as
needed and only through validated cursor operations.

The core message model does not define a separate canonical wire-schema layer
with built-in binary/text negotiation, schema-version migration, unknown-field
compatibility, backward/forward/full compatibility modes, compression or
encryption semantics. A message is already an LMX expression candidate. If a
message contains archived, compressed, encrypted or externally encoded payload,
the source must say so through ordinary LMX receivers, descriptors and registry
tables:

    expression:
        archive\read:
            compressedPart

    expression:
        decrypt:
            ticket
            encryptedPart

    expression:
        migrate:
            oldPayload
            targetClass

Compatibility, migration and unknown-field policy are validator/merge rules of
the receiving side. Compression, decompression, encryption, decryption,
serialization and parsing are ordinary operations selected by tables and
executed only after validation admits them. Content negotiation, when needed, is
ordinary LMX data and table resolution, not hidden transport magic.

Authorization is likewise not a transport-header convention. It is the
auth/evidence model defined by the registry and validation pipeline. L5 Threads
follow that model by default: capability claims inside a message become
authority only after validation produces authority evidence.

2.2. Validator / Merge (new, old 18.2, 20.6, 21.5, 27.9)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The validator merges the incoming message with the receiver registry. Message
validation is expression resolution plus receiver-context, authority,
effect/lifetime and implementation checks.

The validator/merge stage is intentionally split into sub-stages. The exact
implementation may fuse them, but the semantic outputs are distinct:

    intake
        Input message bytes, Structure or in-memory value become an
        IncomingMessageStructure.

    receiver registry selection
        The target receiver, service, thread or object selects the applicable
        receiver-local registry tables and produces a ReceiverRegistryView.

    name resolution
        Names, selectors, operation heads and referenced registry keys are
        resolved in the selected view. Output: ResolvedNames.

    signature/class resolution
        Argument shape, class coordinates, conversions and overload candidates
        are checked by table lookup. Output: CandidateExpression.

    validator/evidence
        Validator cells run or are checked. They may accept, reject, emit
        diagnostics or create evidence. Output: ValidationEvidence.

    authority
        Sender identity, verifier/ticket/capability policy and authority tables
        are checked. Output: AuthorityEvidence.

    effects/lifetime
        Effect policy, ownership, borrowing, move/copy and lifetime rules are
        selected. Output: EffectLifetimePlan.

    concrete-cell substitution
        Abstract or unresolved operation references are replaced with concrete
        terminal cells. Output: ConcreteExpression.

    execution-plan construction
        The concrete expression, evidence and lifetime/effect plan are packaged
        into the executable unit accepted by the executor. Output:
        ExecutionPlan.

The validator does not execute the expression.

Algorithmically, Validator/Merge is the small table-walking driver of the
semantic core. It does not hardcode what `plus`, `authority`, `validator`,
`payload` or `messageTarget` mean. It hardcodes only the general mechanics:

    lookup;
    payload-kind dispatch;
    evidence accumulation;
    conflict/priority handling;
    dependency cycle and termination rules;
    diagnostic construction;
    execution-plan assembly.

Everything domain-specific is represented by registry tables and terminal cell
payloads.

For example:

    save(file: "report.lmx", mode: overwrite)

may validate into:

    impl: archive_save
    args:
        file: Path("report.lmx")
        mode: SaveMode.overwrite
    effects:
        filesystem_write

Validation is therefore not just yes/no. It builds the concrete expression and
execution plan that the executor is allowed to run.

2.3. Expression Executor (new, old 20.1, 20.3, 27)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The executor consumes only an ExecutionPlan produced by validation/merge. That
plan may carry a ConcreteExpression, selected terminal cells, evidence and
effect/lifetime rules.

It does not decide which implementation is meant. It runs the implementation
already selected by validation:

    ExecutionPlan -> ExecutionContext -> result / failure

The result produced here is an execution result inside the current execution
context. It is not yet a reply message merely because it exists. The consumer of
that result is defined by the surrounding context:

    local expression context        -> value consumed by the caller/expression;
    local rule/generator context    -> value consumed by generation rules;
    L5 request with reply target    -> value wrapped as a reply ProposedMessage;
    L5 request with no reply target -> value may be discarded, logged or consumed
                                      by profile-defined local rules.

Therefore the L5 reply mechanism does not require a separate source-level
`return`. The ordinary L3 `return` receiver exits the current executable body
and produces the declared result value. If that executable body was run as the
implementation of an L5 request with a reply target, the L5 boundary wrapper
turns the produced result into a reply message automatically.

The executor may run:

    an L2/L3 lowered function;
    a service handler;
    a scheduled L5 task;
    a built-in runtime operation;
    a diagnostic/failure action.

2.4. Logical Message Generator (new, old 20.4, 32, 33)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

After execution, logical rules may produce new messages. The generator is also
table-driven.

Example rules:

    emit[SaveResult.ok][NotifyService] -> notify_saved
    emit[SaveResult.fail][LogService] -> log_error

The generator creates new proposed messages:

    message:
        to: NotifyService
        expression:
            saved:
                file: "report.lmx"
    end: message

Those messages must still pass validation at their receiving side. Generation
does not bypass the message model.

Execution may also emit messages directly. A validated expression executed by
an L5 Thread may produce an ordinary result value, diagnostic, state update and
zero or more outgoing ProposedMessage records. Generated messages are not
trusted merely because they were generated by an execution step. They enter the
same validation/merge, scheduling and execution pipeline as external messages.

2.5. Standard Message Pipeline (new, old 20, 27.9, 32)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The standard high-level pipeline is:

    IncomingMessage
        -> intake -> IncomingMessageStructure
        -> receiver registry selection -> ReceiverRegistryView
        -> name resolution -> ResolvedNames
        -> signature/class resolution -> CandidateExpression
        -> validator/evidence -> ValidationEvidence
        -> authority -> AuthorityEvidence
        -> effects/lifetime -> EffectLifetimePlan
        -> concrete-cell substitution -> ConcreteExpression
        -> execution-plan construction -> ExecutionPlan
        -> Executor
        -> Result / Failure
        -> Boundary Result Consumer
        -> Logical Message Generator
        -> New IncomingMessage(s)

This replaces the older wording where message validation and message execution
were too close together.


3. Structural Descriptors as Tables (old 9.3-9.7, 17.2, 17.3)
-------------------------------------------------------------

3.1. Model Definitions (old 9.3)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Structural model declarations create registry table rows.

Example:

    Circle:
        f64: radius
        Point: center
    end: Circle

normalizes to rows such as:

    class Circle
    field[Circle][radius] = f64
    field[Circle][center] = Point

No separate "slot" concept is required by the language. A source field may lower
to a physical C field, a property accessor, a computed projection or another
profile-defined representation.

3.2. Normalized Model Descriptor (old 9.4)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A normalized descriptor is a table view over a source structure:

    model name;
    field names;
    field declared classes;
    default values;
    validators;
    ownership/lifetime policy;
    lowering policy.

These rows are consumed by the resolver, validator, serializer, IDE and
lowering profile.

3.3. Union and Variant Membership (old 9.5)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Union descriptors are relation tables:

    member[Shape][Circle] = true
    member[Shape][Rectangle] = true

Dispatch over a union is a table query. A generic operation over a union is
complete only when the required operation has cells for all admitted variants,
or when a profile defines a fallback cell.

3.4. Generated Rows and Extension Policy (old 9.6, 9.7)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Descriptors generate table rows. Extension is table insertion. Conflict policy
is table policy:

    same key, same terminal value      -> duplicate, allowed or ignored;
    same key, different terminal value -> conflict unless an override table
                                         explicitly admits it;
    missing row/column/cell            -> relation absent.


4. Operation Tables, Operators and Receivers (old 10, 11, 12, 23.4-23.6)
-----------------------------------------------------------------------

4.1. Operation Dispatch as Tables (old 10)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

L5 operation dispatch is not object magic. It is a set of tables mapping
receiver/class and selector/expression shape to concrete implementations.

Example:

    draw[Circle][Canvas] = draw_circle_on_canvas
    draw[Button][Canvas] = draw_button_on_canvas

An object may physically contain a class descriptor or may be statically known.
Both cases select table cells.

4.2. Receiver Registration (old 11.1, 11.2)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A receiver/operator is a registry entry that tells the resolver how to interpret
a head/operator in a given context.

Current bootstrap receivers such as:

    fn
    fm
    sub
    if
    while
    return
    synchronized
    c.*
    @
    \
    []

may still be implemented directly in L2/L1. In the high-level model they are
operation table entries with terminal lowering rules.

4.3. Generic Operations (old 11.4, 20.5)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A generic operation is an expression with unresolved table coordinates. It is
not a separate language mechanism.

Example:

    x = y

requires:

    equals[class(x)][class(y)]

The result class and implementation are read from the selected cell.

4.4. Conditional Forms (old 12)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Conditional forms are expressions with control-lowering cells.

At L4, `if` may select descriptor/table rows. At L5, `if` may select message,
configuration or startup expressions. The syntax is the same; the table context
changes.


5. Registry Rows, Evidence and Validation (old 17-21)
-----------------------------------------------------

5.1. Row Store Rule (old 18.0)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

All descriptor, operation-dispatch, validation, message and authority
information may be stored as rows in registry tables.

Examples:

    field[Circle][radius] = f64
    plus[u32][u32] = plus_u32_u32_l2
    equals[String][String] = string_equals
    validator[LightPassenger][Person] = check_weight
    accepts[ArchiveService][save] = save_message_validator
    authority[user42][ArchiveService.save] = allowed

5.2. Evidence (old 18.1)
~~~~~~~~~~~~~~~~~~~~~~~~

Evidence is the current set of rows proving that an expression has been
resolved, validated or authorized.

Evidence may be compile-time or runtime. A validator creates evidence when it
successfully resolves a message or value against the receiving registry.

5.3. Validator Evidence (old 18.2)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A validator is an expression/table cell that checks data and may create more
specific evidence rows:

    validator[LightPassenger][Person] = check_weight
    guarantee[LightPassenger][weight] = "<80"

If validation succeeds, later expressions may use the stronger table coordinate
`LightPassenger`.

A validator is not required to be a boolean predicate. It may produce:

    acceptance;
    rejection;
    diagnostic;
    stronger evidence;
    obligation for a later stage;
    tableKey for continued resolution;
    conflict/None/FORBIDDEN payload.

Validator dependencies are ordinary registry graph dependencies. The
Validator/Merge driver must therefore define cycle detection, memoization of
evidence and termination/diagnostic rules, but it does not need custom
semantics for each validator class.

Projection validators are ordinary validators. For example, a hosted C99
profile may expose `c99.ub.policy` rows for dangerous projection patterns and
`profile.validator` rows for concrete checks such as formatted-output argument
validation. These rows are profile vocabulary, not a separate hidden C static
analyzer inside the language core.

5.4. Evidence Lifetime (old 18.3)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Evidence is valid only while the rows and memory state that produced it remain
valid. If a value mutates, moves across an owner boundary or loses authority,
dependent evidence is invalidated.


6. Entry Composition and Conflict Resolution (old 19)
-----------------------------------------------------

6.1. Entry as Table Bundle (old 19.0-19.2)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

An entry such as `Button`, `Circle`, `ArchiveService` or `equals` is a bundle of
table rows, not a class hierarchy node with hidden copied-code semantics.

Composition means adding rows under one or more tables.

6.2. Import / Provides / Satisfies (old 19.1-19.4)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

`import`, `provides` or `satisfies` do not merge arbitrary implementations.
They add relation rows:

    provides[Array][Indexed] = true
    provides[Array][Sized] = true

The concrete model owns representation and primitive operations. External
roles/contracts are derived views over those operations.

6.3. Conflicts (old 19.3-19.5)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Conflicts are table conflicts. If two rows compete for the same key and no
priority/override table resolves them, the resolver reports ambiguity.

There is no implicit "last wins" rule.


7. Consumption Modes (old 20)
-----------------------------

7.1. Procedural Consumption (old 20.1)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Procedural consumption runs a resolved expression in an execution context. It
is the executor stage of the message pipeline when the expression originated in
a message.

7.2. Object/Event Consumption (old 20.2)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Object/event consumption is message validation plus execution against a target
registry and state owner.

7.3. Functional/Expression Consumption (old 20.3)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Functional consumption is resolution of expression cells without requiring a
stateful receiver. If all selected cells are pure, the expression is pure.

7.4. Logical Consumption (old 20.4)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Logical consumption derives new rows or new messages from existing rows and
results. It belongs to the logical message generator.

7.5. Query, Rules and Unification (old 20.7)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Rules are expressions over registry tables. A rule may introduce temporary
variables, perform table lookup, rank candidates and emit rows. The same syntax
can be used by the interpreter/resolver and by ordinary L5 code.


8. Lowering and Physical Implementation (old 21)
------------------------------------------------

8.1. Pipeline (old 21.0)
~~~~~~~~~~~~~~~~~~~~~~~~

The high-level pipeline is:

    source LMX
        -> P0 Structure
        -> registry table loading
        -> expression resolution
        -> ExecutionPlan
        -> execution or L1/L0 lowering

The current bootstrap may merge some of these steps in ANSI C. That is an
implementation stage, not the high-level model.

8.2. File Extensions and Level Semantics (old 21.1, 21.2)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

L4 sources primarily add registry/configuration rows. L5 sources primarily
describe messages, services, runtime policy, startup and query rules.

8.3. Arguments and Return Lowering (old 21.3, 21.4)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Argument and return handling is table-driven:

    parameter_shape[fn][...] -> lowering rule
    return_shape[fm][...] -> result structure rule

The source rule remains that Structures are data. A Structure is lowered as a
call only when the resolver selects a function/procedure/receiver cell for it.

8.4. ANSI C Projection (old 21.6, 21.7)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

ANSI C projection is a lowering table family. Cells may lower to:

    C type name;
    C function call;
    inline C operator;
    C struct field;
    pointer access;
    raw `c.*` surface.

`c.*` is a permanent door to the ANSI C namespace/surface. It is not a normal
Lingvamyxa namespace lookup. Ordinary L3+ registry tables should not use
`c.*` spellings as registry classes/keys. Use a registry class/key such as
`sqrt_ansi_c` or `plus_u32_u32_l2`, then map that class/key through an L2/L1
lowering table to a primitive symbol or lowering payload such as `"sqrt"` or
`"+"`.

8.5. Provider and Device Profiles
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

External libraries, native services, device boards and remote modules are
provider profiles over registry bindings. They are not part of the source
syntax and not semantic parents of the language.

A provider may be:

    CPU/L1 primitive lowering;
    ANSI C library binding;
    bundled bootstrap library such as GMP, MPFR, decNumber, PCRE2, SQLite,
    yyjson, libcurl, CivetWeb, libsodium or another hosted library;
    generated L2/L3 executable;
    analog, photonic, routing, neural or ROM-backed device module;
    remote L5 service binding.

The same source expression may resolve to different terminal cells in different
RegistryViews. For example:

    table:
        name: sqrt
        columns: class (result char) (implementation char)
        rows:
            BigFloat BigFloat sqrt_mpfr
            fixedQ16 fixedQ16 sqrt_ana
            f64      f64      sqrt_ansi_c
    end: sqrt

    table:
        name: `implementation-->L2 lowering`
        columns: class (symbol char)
        rows:
            sqrt_mpfr   "mpfr_sqrt"
            sqrt_ana    "ana_sqrt"
            sqrt_ansi_c "sqrt"
    end: `implementation-->L2 lowering`

    table:
        name: providerOf
        columns: class (provider char)
        rows:
            sqrt_mpfr MPFR
            sqrt_ana ANA_SQRT
            sqrt_ansi_c CPU_C_Libm
    end: providerOf

On a hosted bootstrap machine, `ANA_SQRT` may be simulated by an ANSI C wrapper
around libm or MPFR. On another target, the same provider entry may lower to a
physical analog board instruction. The source-level `sqrt` expression does not
change; only the registry view and provider bindings change.

The resolver/validator must treat provider selection as ordinary table
resolution:

    operation table chooses a semantic cell;
    terminal cell payload names a binding;
    provider side tables describe who/what executes that binding;
    validator checks effects, authority, precision, latency, determinism,
        confidence, calibration, lifetime and fallback policy;
    ExecutionPlan fixes the selected binding so hot execution does not resolve
        provider choice again.

This discipline lets heavy hosted libraries act as earth-bootstrap surrogates
for heterogeneous expansion boards without making those libraries part of the
language. Examples:

    MPFR / GMP / decNumber  -> high-precision math providers;
    FFTW / BLAS / LAPACK    -> signal/matrix provider surrogates;
    PCRE2                   -> pattern/matcher provider;
    SQLite                  -> registry/storage provider;
    yyjson                  -> external adapter provider;
    libcurl / CivetWeb      -> transport/service envelope providers;
    libsodium               -> crypto/auth provider.

Direct `c.*` calls remain possible in L2/L1 substrate code, but ordinary L3+
semantics should go through registry cells and provider validation. Removing
MPFR and installing an `ANA_LOGEXP` provider should not require rewriting the
source expression; it should require changing provider rows, bindings and
RegistryView policy.

8.6. Codec and Persistence (old 21.9, 21.10)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

`toLmx` and `fromLmx` are operation tables. All language values, including
primitive values and low-level handles admitted by a profile, should have
explicit codec rows if they are serializable.

Persistent registry rows may be stored as LMX files, generated database rows
or cached binary indexes. LMX remains the source form.

Portable persistence is structural LMX serialization, not memory imaging. A
runtime may materialize structures in memory using whatever representation the
selected L1 substrate provides, but a portable persistent form records admitted
LMX Structures, registry rows, messages, evidence and L5 Thread logical state
through codec receivers such as `toLmx` and `fromLmx`. Raw process memory,
allocator state, native handles, alignment, endian order and ABI layout are not
portable LMX state unless a profile admits an explicit codec for them.

Binary serialization, if introduced, is a profile-specific codec. Endian and
binary layout belong to that codec profile, not to ordinary LMX source
semantics.


9. L4/L5 Canonical Examples (old 23.4-23.6)
-------------------------------------------

Examples in this section are illustrative. They must be read as registry table
definitions plus expressions, not as special syntax.

Example operator cell:

    table:
        name: equals
        columns: class (u32 char) (decimal char)
        rows:
            u32     u32_eq None
            decimal None decimal_eq
    end: equals

Example L5 conditional route:

    route:
        when:
            equals[userRole][admin]: true
        send:
            to: AdminService
            expression:
                openPanel
    end: route


10. Remaining Open Points (old 25)
----------------------------------

Open points for this part:

    exact optimized storage layout for CellKey -> CellPayload and optional side tables;
    whether the first registry backend is hash tables, SQLite or both;
    resolver ranking/ambiguity defaults;
    how much of current L2 hardcoded lowering moves into registry tables first;

11. L5 Thread and Message Runtime (old 27)
------------------------------------------

11.1. Scope (old 27.0)
~~~~~~~~~~~~~~~~~~~~~~

An L5 Thread is a minimal LMX machine:

    isolated state tree;
    local registry view/cache;
    message queue;
    validator/merge stage;
    executor;
    logical message generator;
    local memory owner.

It is not necessarily an operating-system thread.

11.2. L5 Thread (old 27.1)
~~~~~~~~~~~~~~~~~~~~~~~~~~

An L5 Thread owns:

    root state;
    local arenas/owner tree;
    current ExecutionContext;
    inbox/outbox queues;
    registry view;
    validator and executor policy;
    diagnostics/failure state.

No raw mutable reference owned by one L5 Thread may point directly into another
L5 Thread in the default profile.

11.2.1. L5 Thread Registry View and Cache
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

An L5 Thread does not own a complete global registry. It owns a local
RegistryView and may own a RegistryCache.

The RegistryView is an overlay/import/cache view over registry sources such as:

    builtin/core tables;
    module tables;
    service tables;
    device/profile tables;
    imported base registry tables;
    thread-local rows;
    runtime evidence rows.

Lookup, validation and execution-plan construction are performed against the
current RegistryView. The view may cache selected cells, resolved names,
validator evidence, authority evidence, lowered bindings and ExecutionPlans.
The cache is an implementation optimization and does not define a separate
namespace, class universe or type system. It is a materialized view of registry
tables selected by import/overlay/profile policy.

Persistent registry sources may live in LMX files, ROM/MO records, generated
database rows, server-side registry storage or cached binary indexes. A small
node is not required to keep all persistent rows in RAM. It may keep only the
active view and the cache entries required by its current messages, services and
handlers.

Local transient rows and evidence may be added by the L5 Thread according to
the active profile. They are local overlays unless explicitly exported through a
validated registry-change message or another admitted persistence operation.

Registry changes may invalidate affected cached rows or emit registry-change
messages according to the reactive registry profile.

11.3. Root State and Handler Frame (old 27.2, 27.3)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Root state is durable state owned by the L5 Thread.

A handler frame is created when a validated message is executed. It owns local
temporary state, cleanup entries and diagnostic context.

11.4. Cleanup and Control Exit (old 27.4)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Cleanup is local to the current handler/frame/thread owner. Control exits such
as `return`, `fail`, `break`, `continue` and cancellation must run registered
cleanup before the owner is cut or reused.

11.5. Message Structure (old 27.5)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Message states:

    IncomingMessage / ProposedMessage
    CandidateMessage / CandidateExpression
    ConcreteExpression / ExecutionPlan
    ScheduledMessage
    ExecutedMessage
    FailedMessage

`ConcreteMessage` or `CandidateMessage` may be used as an implementation name
for a message after class/signature resolution but before all authority/effect
validation has completed.

11.6. Transfer Modes and Borrowed Payloads (old 27.6, 27.7)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Across L5 Thread boundaries, payloads cross by:

    copy;
    serialization;
    whole-branch ownership transfer;
    immutable/shared profile handle.

A borrowed raw reference may not cross into another L5 Thread as a raw mutable
reference.

11.7. Queue, Scheduling and Dispatch (old 27.8, 27.9)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

An L5 Thread processes messages through the standard pipeline:

    dequeue
    validate/merge
    execute
    generate outgoing messages
    run local collection safe point

Dispatch is a registry query, not object magic.

The execution step may produce result values, diagnostics, state updates and
outgoing ProposedMessage records. Outgoing records re-enter the same message
pipeline at their receiving side.

Core message semantics are intentionally smaller than broker/runtime policy:

    message = executable proposed expression;
    validation/merge -> ExecutionPlan;
    execution -> result / failure;
    boundary -> reply/failure message to caller, reply target or continuation.

The core language does not require a broker-style acknowledgement, dead-letter
queue, topic partition, consumer group, transport retry scheduler or supervision
tree as generic message semantics. A message is considered semantically handled
when execution produces its result or failure, just as a local function call is
handled when it returns a value or failure. The L5 difference is only that a
boundary may wrap that result or failure into an ordinary message record.

Delivery, ordering, scheduling, supervision and observability policies are
runtime/profile/library concerns around accepted message execution. Examples:

    FIFO or priority ordering;
    one message at a time or interleaving;
    queue capacity and overflow policy;
    transport retry after transport/runtime failure;
    pause, resume or cancellation;
    L5 Thread restart or termination policy;
    diagnostics, audit, trace, metrics and event history.

Such policies may be described by registry tables and may themselves emit
diagnostics or messages, but they are not the meaning of a source message. In
particular, a semantic failure is normally returned to the sender, reply target
or continuation as a failure message. If that target is absent, expired or
unreachable, the situation belongs to runtime/delivery policy, not to the core
message expression semantics.

11.7.1. Autonomous / Constrained Message Profiles
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Some profiles need more than generic message execution. Autonomous, low-power,
high-latency, degraded-link, safety-critical or heterogeneous-device systems
may define domain message profiles with explicit tables for command lifecycle
and physical limits.

These features are not implied merely because a message is full LMX. A full LMX
message can express algorithms, nested Structures and calls, but it does not by
itself define command identity, freshness, physical units, safety budgets,
idempotence, replay policy or degraded-mode behavior. Those are ordinary
registry/message/profile relations consumed by validation/merge and execution.

Typical profile rows include:

    commandId / correlation / dedupKey
        Identity rows used to recognize the same proposed operation again.

    idempotent / duplicatePolicy / retryPolicy / replayPolicy
        Whether repeated admission is allowed, rejected, coalesced, answered
        from an earlier result, replayed from a decision log, or repaired by a
        profile-defined recovery expression.

    resource budgets
        energy, memory, bandwidth, time, storage wear, heat, actuator cycles
        or other profile-defined limits.

    freshness
        sampledAt, validUntil, staleAfter, calibrationValidUntil and related
        evidence windows.

    units and frames
        physical units, coordinate frames, sensor frames, map frames and
        conversion evidence.

    uncertainty / evidence
        confidence, errorBound, distribution, source, calibration, provenance
        and validator-produced evidence.

    plan mode
        propose, validateOnly, execute, recordResult or another explicit
        command lifecycle stage.

    effect fences
        mayRead, mayWrite, mayMove, mayTransmit, mayHeat, maySpendEnergy,
        mayOverwrite, mayWakeDevice and similar effect bounds.

    degradation
        minimumMode, degradedMode, safeMode, fallbackProvider and
        emergencyBinding.

    decision log classes
        observed, decided, executed, failed, repaired and replayed.

    local-first conflict
        localTruth, importedTruth, conflict, mergeEvidence and authoritySource.

A semantic replay is different from a transport resend. A transport resend is a
delivery/runtime policy around the envelope. A semantic replay is an ordinary
validated LMX operation that reconstructs, repeats, repairs or answers an
accepted command according to idempotence, evidence, authority, freshness and
effect tables. It may use decision-log rows and previous result/failure
messages, but it is still a proposed expression until validation/merge admits
it.

This does not introduce a second `retry` semantics. L3 already has
`retryable` / `retry` as ordinary control receivers: `retryable` creates a
restartable local execution frame, and `retry` re-enters the nearest or named
retryable frame after the appropriate cleanups. An autonomous profile may use
that L3 mechanism inside a concrete plan, for example with retryBudget,
retryLimit, backoff, provider fallback or degraded-mode rows. Message replay is
larger: it may construct or admit a new ProposedMessage or recovery expression
from command identity and decision-log evidence. Transport retry is smaller:
it resends an envelope without changing the source expression semantics.

Likewise, a duplicate command is not handled by a hidden broker rule. The
selected duplicatePolicy may reject it, return the previous result, merge it
with an active operation, enqueue a repair expression, or allow another
execution if the command is declared idempotent and the relevant evidence still
holds.

This keeps the boundary clean:

    message-as-LMX
        gives the executable proposed expression;

    autonomous/constrained profile tables
        give identity, budgets, freshness, uncertainty, replay/idempotence,
        effect fences, degradation and decision-log policy;

    validator/merge
        turns the candidate plus profile rows into a concrete plan or a
        diagnostic;

    executor
        runs only the concrete plan and records result/failure/evidence rows
        according to the selected profile.

11.8. Reply, Future, Failure and Continuation (old 27.10-27.13)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Replies and futures are message records. Failures crossing an L5 Thread
boundary are data messages, not hidden exceptions.

A result crossing an L5 Thread or service boundary is represented as a message.
If a request contains a reply target, future, continuation or correlation id,
the value returned by the executed expression is wrapped into a reply message
addressed to that target. A failure is wrapped into a failure message. Reply
and failure messages are ordinary message records and must pass the normal
validation rules of the receiving side.

This wrapping is automatic at the message boundary. It is not a second
source-level `return` form. Keep the following meanings separate:

    L3 executable return
        `return` / `return: value` exits the current executable body and
        produces the declared local execution result.

    computational injection
        a pure/monadic "return" notion, if a profile needs it, should be named
        `pure`, `unit` or another profile-defined receiver. It injects a value
        into a computational context; it is not the L3 control-exit receiver.

    L5 reply wrapping
        a produced result is wrapped as a reply ProposedMessage only when the
        executing message boundary supplies a reply target, future,
        continuation or correlation id.

If a message has no reply target and no profile rule consumes the result, the
result is not forced into a hidden reply. The profile may discard it, log it,
use it for local generation rules, or report that the message kind must declare
a result destination. The important rule is that crossing the boundary uses an
ordinary message record, not a hidden call-stack return.

A reply payload may itself be a Structure, callable descriptor, callable
reference, residual executable or future/continuation record, if the receiving
side admits that payload by its normal validation rules. The message boundary
does not inspect such a value as "code to run" merely because it is callable. It
wraps the produced result as data; the receiver decides later whether that data
is executable, callable, storable, displayable or invalid.

`async`, `await` and `yield`, if present, are scheduling expressions that create
or consume message/continuation records. `yield` is the sequence-oriented lazy
production protocol: it produces one value, records resume state and lets a
consumer such as `next`, `each`, `awaitNext` or an L5 scheduler request a later
step. This does not imply global non-strict evaluation for every expression.
Deferred single values, futures and streams are ordinary descriptor/receiver
profiles over the same message/continuation model.

11.9. Determinism and Atomic Operations (old 27.14, 27.15)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Default deterministic L5 profile:

    one active handler per L5 Thread;
    no shared mutable raw references across L5 Threads;
    communication by messages;
    explicit lower-level synchronization only in admitted L2/L3 profiles.

Atomic operations are low-level implementation operations, not a replacement for
ordinary L5 messages.

11.10. ANSI C Lowering and Boundaries (old 27.16, 27.17)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A C99 runtime may represent an L5 Thread as a structure containing:

    root state pointer;
    queue;
    registry view pointer;
    current execution context;
    owner/arena graph;
    scheduler fields.

The source-level rule remains message isolation, even if the runtime maps many
L5 Threads onto fewer OS threads.


12. Memory Model (old 30)
-------------------------

12.1. Core Rule (old 30.0, 30.1)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Memory is region/owner oriented. L5 Threads own isolated arena graphs. No raw
mutable reference crosses an L5 Thread boundary in the default model.

12.2. Branch Arenas and Owners (old 30.2, 30.3)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

An owner may be a branch, frame, handler, module state or L5 Thread root.
Borrowed values are valid only inside the owner/lifetime that produced them.

Ownership policy is table data:

    ownership[array_new] = returns_owned
    ownership[array_at] = returns_borrowed
    transfer[Message.payload] = copy

12.3. Message Boundary (old 30.4-30.6)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

An L5 message boundary is a memory boundary. A payload that must survive in the
receiver is copied, serialized or transferred as a whole owned branch.

12.4. Local Collection (old 30.7, 30.13)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Collection is local to one L5 Thread. It may run at message boundaries,
control-exit safe points, retry points, diagnostics and thread termination. It
does not stop other L5 Threads.

12.5. Immutable and Low-Level Resources (old 30.8, 30.9, 30.12, 30.14)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Immutable/shared and externally managed resources are explicit low-level
profile objects. They are not ordinary mutable L5 branches. L5 code sees typed
handles, descriptors or messages.


13. Reactive Registry and Query Receivers (old 32)
--------------------------------------------------

13.1. Reactive Layer (old 32.1-32.3)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Registry changes may produce events. Events are messages. Query receivers run
inside L5 Threads and consume registry tables through the same message pipeline.

13.2. Agent Candidates (old 32.4-32.6)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

An agent receiver may propose candidate rows or candidate messages. A validator
must accept, reject or rank the candidate before it becomes effective.

13.3. Boundaries and Bootstrap (old 32.7-32.9)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Reactive registry processing obeys L5 Thread memory/message boundaries. A
minimal bootstrap may implement only:

    row inserted;
    query receiver;
    candidate row;
    validation;
    accepted row.


14. HTTP Lingvamyxa REST Profile (old 33)
-----------------------------------------

14.1. Status (old 33.0)
~~~~~~~~~~~~~~~~~~~~~~~

HTTP Lingvamyxa REST is a built-in service transport profile. It is not the
core execution model.

14.2. Service Instance (old 33.1)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A service instance is a bundle of L5 Threads connected by standard messages.
The bundle is not a shared mutable heap.

14.3. HTTP to Message (old 33.3-33.7)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

HTTP request handling is:

    HTTP request
        -> route table lookup
        -> IncomingMessage
        -> receiver validator/merge
        -> executor
        -> result/failure message
        -> HTTP response mapping

Routes are registry rows. External HTTP data becomes an LMX message before
service dispatch.

14.4. Serialization, Client/Server and Service Boundaries (old 33.8-33.19)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Serialization adapters are codec operation tables. HTTP client/server adapters
are L5 services or hosted native adapters that inject messages into L5 Threads.
Service boundaries obey the same memory and authority rules as L5 Thread
boundaries, with stronger default isolation for remote input.


15. Core Authentication and Authorization (old 36.En, 36.Ru)
------------------------------------------------------------

15.1. Status (old 36.En.0, 36.Ru.0)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Authentication and authorization are not a separate role system. They are
registry tables, validators and evidence attached to an L5 flow.

15.2. Primary Credential and Verifier (old 36.En.1, 36.Ru.1)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A verifier is a protected table cell/value that can validate a primary
credential without storing the credential itself.

The default password verifier may use libsodium password hashing in the C99
runtime profile.

15.3. Default Installation Credential (old 36.En.2, 36.Ru.2)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A fresh installation may have a system user name and an empty primary password.
This is not global security policy. It is the default verifier table state. A
user or administrator may replace it with a stronger verifier.

15.4. Verifier Realms and Protected Objects (old 36.En.2.1-2.3, 36.Ru.2.1-2.3)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Protected objects may have their own verifier realm:

    protected module;
    protected L5 service;
    protected archive;
    protected directory;
    protected administration operation.

Password reset may reset an access verifier to an empty/default state. It does
not recover separately encrypted content whose key depended on the old verifier.

A protected object may require:

    one verifier;
    multiple verifiers for one user;
    a quorum of users/sessions;
    creator-parent tracking.

Parent/creator rows do not grant content rights by themselves.

15.5. Delegated Ticket (old 36.En.3, 36.Ru.3)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

After primary credential validation, the runtime may issue a delegated ticket
for a module or service. The ticket is represented as table/evidence data:

    ticket[user][module] = ticket_id
    ticketAuthority[ticket_id][operation] = allowed
    ticketExpiry[ticket_id] = time

Changing or resetting the primary verifier invalidates dependent tickets by
table policy.

15.6. External Authentication Modules (old 36.En.4, 36.Ru.4)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

OAuth or OS-login modules are ordinary L5 modules that can obtain authority
only through validator/evidence rows admitted by the receiver. They do not
replace the core verifier table. They may request or receive delegated tickets
after the primary policy allows it.

15.7. Authentication Evidence Rows (old 36.En.5, 36.Ru.5)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Authentication validation emits evidence:

    authUser[flow] = user
    authVerifier[flow] = verifierRealm
    authTicket[flow] = ticketId
    authority[flow][operation] = allowed
    guarantee[flow] = sessionQuorumSatisfied

Message validators may require these rows before producing a ConcreteExpression
or ExecutionPlan.

15.8. ANSI C / libsodium Runtime Sketch (old 36.En.6, 36.Ru.6)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

A C99 runtime profile may use libsodium for:

    password hashing/verifier creation;
    random ticket material;
    constant-time comparisons;
    secure memory helpers where the runtime owns the memory region.

UI password entry is outside libsodium's control unless the UI layer is also
implemented with memory handling that the runtime owns.

15.9. Standard Statement (old 36.En.7, 36.Ru.7)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Authentication is a validation/evidence layer over the message pipeline.

    credential/verifier -> validator -> authority evidence -> message validation

Authorization is table lookup over that evidence. It is not a separate global
role hierarchy.


16. Standard Summary
--------------------

Part II reduces to these rules:

    class = named registry form/table/key;
    table named X = descriptor/source table for class/key X when present;
    table class = index/classification relation, not the only class source;
    class/table import = explicit table import/overlay with priority/conflict policy;
    table row/column/cell = relation;
    missing row/column/cell = no relation;
    strict classification = L4 registry data;
    analytical typing = registry queries during static stages and L5 runtime;
    analytical engine = active machine over L3/L4/L5 strata, not L6 syntax;
    L4 analysis = knowledge/classification/derived decisions queried by L3
                  expressions and L5 messages;
    rules/unification/backtracking/resolution = admissible L4 analysis
                  mechanisms over facts and derived relations;
    type/class resolution = logical query over the active registry view;
    in-memory registry rows/indexes/caches/SQLite = materialized views, not semantics;
    expression = Structure requiring table cells;
    message = proposed possibly effectful/action-capable LMX expression candidate;
    message expression = ordinary LMX admitted by receiver policy;
    validation = staged merge from IncomingMessageStructure to ExecutionPlan;
    executor = run only ExecutionPlans produced by validation/merge;
    provider = registry-described executor/lowering backend, not language syntax;
    autonomous/constrained profiles = explicit tables for budgets, freshness,
                uncertainty, idempotence/replay, effect fences, degradation and
                decision logs;
    L3 retry/retryable = local execution-frame restart, not transport resend;
    generator = create proposed messages from result/state/table rules;
    L3 return = executable-body control exit producing local execution result;
    L5 reply = boundary wrapper from result/failure to ordinary message record;
    L5 Thread = minimal isolated LMX machine that receives, validates, executes
                and sends messages;
    L5 RegistryView = local overlay/import/cache over persistent registry
                      sources, not a full per-thread registry copy;
    memory/auth/service rules = table/evidence policies over the same pipeline.
