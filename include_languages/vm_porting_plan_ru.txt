Проще всего -- загнал generated-C и собрал стандартным иснтрументом:
    1    MIR            L1        MIR.md + C API           L1/L2 №2 #как первый опыт
    2    WASM linear    L1        W3C core + binary        L1/L2 №1 #в каждом браузере
    3    RISC-V ISA     L1        unprivileged spec        L1/L2 №5 
Популярней всего, JVM в каждом устройства = реальная польза, но надо написать компилятор:
    4    JVM classfile  L3        JVMS                     L3 №1
Много браузеров, связан с 2 но тоже надо писать компилятор:
    5    WASM GC        L3        W3C GC (Wasm 3.0)        L3 №2
Игровая индустрия громадная:
    6    Lua 5.4        L3        lopcodes / manual        L3 №5
Много VM, но там где уже заведомо есть EXE и JVM, Lua по охвату больше Unity:
    7    .NET CIL       L3        ECMA-335 III             L1 №6 / L3 №3

Вычеркиваем:
Больше похож на мультиплатформенный язык чем на платформу для языков, 
ломает герметичность:
* BEAM           L3        формат OTP beam          L3 №4
"Годность L1: да, тяжело." -- не катит для команды из нескольких ИИ-агентов:
* LLVM IR / bitcode  (.bc) + lli / ORC JIT  [L1]  



План портирования на VM -- открытые bytecode-цели (русский)
===========================================================

Статус

Снимок 2026-09-08. Это не план поставки и не обязательство делать
второй бэкенд. Сводка из:

    L1_to_vm_research_ru.txt    C-машины для Translator-L1
    L2_to_vm_research_ru.txt    ядро L2 = машина L1 + Lmx/Messages
    L3_to_vm_research_ru.txt    высокоуровневое подмножество
                                (управляемый рейтинг)

English text: vm_porting_plan_en.txt

В этом файле рекомендуемые кучи L1 и L3, и только те VM, чей
bytecode или ISA публично заданы так, что сторонний компилятор
может их выдавать. Закрытые, внутренние и машины вида «выдай
исходник и надейся» -- вне списка. Порядок -- использование в
мире, самые частые сверху; один рейтинг, L1 и L3 вместе. Это не
порядок технической годности из заметок L1/L2 и не из заметки L3.


0. Фильтры
----------
Цель попадает сюда, только если одновременно:

  1. Она в рекомендуемой куче L1_to_vm_research_ru.txt
     (Layer M у L2 -- тот же список) *или* в рекомендуемой
     куче L3_to_vm_research_ru.txt (выше разделителя в том
     файле).
  2. Это настоящая виртуальная машина или переносимая ISA, а не
     библиотека нативной генерации кода.
  3. Написание её виртуального кода задокументировано в публичной
     спецификации или основном руководстве (двоичный формат,
     текстовый IR, или оба). Третья сторона может сделать
     принтер, не разбирая JIT.

Сняты по (2) или (3), хотя исследование L1 их любит как нативные
пути: TinyCC / libtcc (натив, нет bytecode), QBE (SSA IL в
ассемблер, нет образа VM), sljit / Cranelift / libgccjit /
asmjit / GNU Lightning / DynASM / libjit / libfirm (JIT/codegen,
нет переносимого файла bytecode). У HashLink есть файл .hl и
списки опкодов в блоге Haxe, но нет первоклассной спеки
писателя; L3 помечает его как слабый. Здесь не ранжируется.

Сняты, потому что *ни одно* из исследований не рекомендует их
как ISA: bytecode Python, JS-движки, LuaJIT (FFI -- это L2, не
L3), Pawn/AMX, Umka, AngelScript, семейство CPython, PyPy,
Janet/Wren/mruby/Tcl/Berry, Guile/Smalltalk, Julia-VM, eBPF,
SPIR-V, Knuth MIX/MMIX, Parrot, com.mtk.map как ISA. У части из
них bytecode как раз документирован; они проваливают отображение
языка, а не бумагу.

«Закрытая» в этом файле значит: нет публичного рецепта выдать
тот код, который машина реально исполняет (IR HotSpot C2,
внутренний V8 Ignition, трассы LuaJIT, .pyc CPython,
привязанный к версии). JVM classfile и CIL ECMA-335 -- открытые
форматы. JVM здесь как ISA L3, не как ISA ядра L1.


1. Две поверхности, один рейтинг
--------------------------------
Рекомендуемые списки L1 и L2 -- те же машины (линейная память
WASM, MIR, LLVM, TinyCC, RISC-V, unmanaged CIL, нативные JIT).
L2 не открывает лучшую VM. Он только добавляет ограничения поверх
L1: неперемещаемые заголовки Lmx, классификация диапазонов, одна
арена на Message (L2_to_vm_research_ru.txt §1).

Выбранная поверхность компиляции *ядра* по-прежнему
**Translator-L1**.

  Выбранный маршрут транслятора уже такой:

      L2  ->  Translator-L2  ->  текст L1 (P-L1text)
          ->  Translator-L1  ->  C99

  P-C99 (C напрямую из L2) отвергнут. VM-бэкенд, который может
  гонять живое ядро, -- это VM-бэкенд для L1 (Layer M). Прямой
  L2->wasm / L2->CIL -- третий маршрут, граница транслятора его
  не выбирает.

  L1 -- это программа на C в орфографии L1 (L1_spec.txt).
  Указатели, goto, libc, сплошные массивы, FILE* уже имеют
  локальное отображение. Путь A -- оставить C-принтер, скормить
  wasi-sdk или c2m -- проверяет VM без правок l1trans.

  Layer S у L2 (положить Lmx/Messages на объекты JVM, таблицы
  Lua, процессы BEAM) -- это как раз куча «не рекомендуется»
  для ядра. Брать L2 поверхностью, чтобы гнаться за этими VM,
  значит идти против spec 2 и L1_language spec 4.1.

L3 -- другая *поверхность*, не другой файл рейтинга. В L3 нет
адресной арифметики (спека 1.4). Его рекомендуемые bytecode-VM
-- JVM classfile, wasm-gc, managed CIL, BEAM, Lua 5.4 -- стоят
здесь в том же порядке популярности, что и машины L1. Mix --
не ISA Java. com.mtk.map -- шаблон пересекающихся деревьев, не
Mix. Целевая перепись -- сотрудничающие Message в модели
стиля Smalltalk (спека 19.29.2.1, WorldWideMix.txt). Это не
bytecode L1 и не повод предпочитать JVM вместо CIL, и не повод
выдавать classfile из L1.

Два отображения не сливать. Линейная память WASM -- куча L1;
wasm-gc -- куча L3. Unmanaged-указатели CIL -- отображение L1;
управляемые объекты CIL -- отображение L3 (один bytecode, две
строки годности). У JVM / BEAM / Lua 5.4 нет строки L1.

L2 по-прежнему важен как *рантайм* на выбранной VM L1:
bump-арены, неперемещаемые узлы, FIFO-ходы Message. Линейная
память WASM и C-VM это уже дают. Отдельная ISA не нужна.


2. Что здесь значит «популярность»
---------------------------------
Заметки L1/L2 ранжируют по *годности* (модель памяти C, потом
размер). Заметка L3 -- по *годности* (значения графа/таблиц/
Message, проверка границ). Этот файл пересортировывает обе
рекомендуемые кучи вместе по тому, *какая доля мира уже
использует этот bytecode/ISA как то, что компиляторы выдают и
рантаймы исполняют*.

3. Цели по рангу (чаще используемые сверху)
-------------------------------------------

1. JVM classfile  (include_openjdk.txt) -- самая используемая
   прикладная bytecode-VM  [L3]
        Настоящая bytecode-VM. Java Virtual Machine
        Specification документирует формат classfile и набор
        инструкций. javac, ASM, BCEL и каждый JVM-язык
        (Kotlin, Scala, Clojure, Groovy) -- публичные писатели.
        Это не закрытый IR HotSpot: classfile -- поддерживаемый
        контракт компилятора. Android ART исполняет DEX,
        полученный из этого classfile. com.mtk.map в этом
        каталоге -- Java-шаблон, не Mix и не причина этого
        места.

        Почему это место: Java в TIOBE сент. 2026 №4 при 7.54%;
        SlashData Q1 2025 23.2 млн разработчиков Java -- больше,
        чем C# (11.1 млн); SO 2025 29.4%. Kotlin добавляет
        6.3 млн (SlashData), TIOBE №26 0.67%, в основном тот же
        classfile. Android и корпоративные серверы реально
        *исполняют* этот bytecode в масштабе, с которым не
        сравнится ни одна другая управляемая ISA. Выше WASM
        как *выдаваемая и исполняемая* прикладная ISA; WASM
        по-прежнему впереди по простаивающим установленным
        браузерным VM.

        Годность L3: лучшая в каталоге L3 (заметка L3 №1).
        Structure -> объекты, Array -> массивы JVM с проверкой
        границ, таблицы -> коллекции, Message -> объекты плюс
        очередь. Перемещающий GC допустим -- L3 адресов не
        видит. Годность L1/L2: нет. Нет сырых указателей,
        слово класса, перемещающий GC. Не выдавать classfile
        из Translator-L1.

        Документация bytecode:
            Java Virtual Machine Specification
            https://docs.oracle.com/javase/specs/

2. WebAssembly, линейная память  (include_wasm.txt) -- самая
   используемая переносимая bytecode-VM  [L1]
        Bytecode W3C, двоичный формат (.wasm) и текстовый
        (.wat) оба специфицированы. Ядро спеки написано так,
        чтобы компиляторы могли выдавать модули; это не
        внутренний дамп JIT. Рантаймы уже в каталоге: Wasmtime
        C-API, Wasmer, WAMR, wasm3. WASI preview 1 закрывает
        ввод-вывод класса FILE* через preopen
        (wasmtime --dir=.).

        Почему это место: VM стоит в каждом крупном браузере
        (миллиарды установленных рантаймов). Chrome 2025:
        ~5.5% визитов затрагивают Wasm; HTTP Archive 2025:
        ~43 тыс. сайтов, 2% из топ-1000. CNCF: 31% cloud-native
        разработчиков используют (edge/serverless, не только
        веб). C/C++ (wasi-sdk / Emscripten), Rust, C#/Blazor,
        Go, Kotlin и другие уже это выдают. Web Almanac 2025:
        .NET/Mono+Blazor -- большая доля опознанных web-Wasm
        модулей; CIL и Wasm в природе пересекаются.

        Годность L1: линейная память wasm32 -- куча C;
        i32/i64/f32/f64; br / br_if / br_table закрывают
        goto/switch; указатели на функции -> table +
        call_indirect. Лимиты: 4 ГБ (memory64 сырой), нет
        тождества хостового FILE*, у WASI p1 нет сети,
        указатели guest/host копируются (include_wasm.txt
        §5.4). Годность L2: линейная память не переезжает --
        тождество Lmx родное. Годность L3: только как
        L3 -> L1 -> C -> wasi-sdk; больше машины, чем нужно
        исходному L3. Для WASM L3 предпочитать пункт 5
        (wasm-gc).

        Документация bytecode:
            https://webassembly.github.io/spec/
            https://www.w3.org/TR/wasm-core-2/
            двоичный формат -- глава "Binary Format".

        Путь A: l1trans -> .c -> wasi-sdk clang (wasm32-wasip1)
        -> .wasm -> wasmtime/WAMR. Путь B: принтер L1 -> wasm.

3. LLVM IR / bitcode  (.bc) + lli / ORC JIT  [L1]
        Промышленный compiler IR. LangRef документирует каждую
        инструкцию; IRBuilder / текстовый .ll -- поддерживаемый
        способ это писать. lli и ORC JIT это исполняют.
        clang -emit-llvm -- путь A, как только есть C из L1.

        Почему это место: IR за Clang (C в TIOBE №2 10.28%,
        C++ №3 8.67% -- делят с GCC), Rust (TIOBE №10 1.34%,
        SO 14.8%), Swift (TIOBE №18 0.83%), Julia и
        необязательный Zig. Тулчейн платформы Apple и Android
        NDK -- Clang/LLVM. llvm-project ~40.3 тыс. звёзд на
        GitHub. Это использование как цели компиляции: почти
        никто не возит lli как промышленную VM. Bitcode (.bc)
        в собственной документации LLVM *не* стабильная
        сериализация -- выдавать текстовый IR или C++ API,
        bitcode оставлять артефактом.

        Годность L1: да, тяжело. Понижение C ABI -- работа
        фронтенда. Ломает правило каталога «без многогигабайтного
        SDK» как вендоренный embed; годится как необязательный
        бэкенд разработчика. L2: тот же Layer M, что у L1;
        не ISA для Lmx. L3: только через L1, не ISA формы L3.

        Документация bytecode:
            https://llvm.org/docs/LangRef.html
            https://llvm.org/docs/BitCodeFormat.html
            (bitcode = кодировка реализации; контракт
            пишущего -- LangRef)

4. .NET CIL  (include_dotnet.txt) -- массовая прикладная VM
   [L1 unmanaged + L3 managed]
        Настоящая bytecode-VM. ECMA-335 Partition III -- набор
        инструкций CIL; Partition II -- метаданные. ilasm,
        ildasm, System.Reflection.Emit, Mono.Cecil / dnlib --
        публичные писатели. CoreCLR -- MIT на GitHub
        (dotnet/runtime ~18.3 тыс. звёзд). Это не закрытый
        Microsoft IR: набор инструкций -- стандарт ECMA.
        NativeAOT остаётся в Removed каталога (полный SDK,
        сборка под каждую цель); этот пункт -- CIL + CoreCLR,
        не NativeAOT.

        Почему это место: C# в TIOBE сент. 2026 №5 при 4.22%;
        SlashData Q1 2025 ~11.1 млн разработчиков C#; SO 2025
        27.8% респондентов; RedMonk янв. 2026 №4 (в ничьей).
        Visual Basic (TIOBE №7, 2.55%) -- тот же CLR. GitHub
        Octoverse 2025: C# в горстке языков, которые держат
        новые репозитории. Unity и корпоративные Windows/
        серверные приложения реально *исполняют* CIL, в отличие
        от bitcode LLVM. Ниже JVM, потому что у Java больше
        разработчиков; ниже LLVM, потому что LLVM наследует
        C/C++/Rust как compiler IR.

        Годность L1: правдоподобно, тяжело. В CIL есть
        unmanaged-указатели, localloc, cpblk, initblk, calli,
        goto. unsafe C# / ILAsm / C++/CLI могут выразить
        C-подобную память; libc становится P/Invoke. Один
        CoreCLR на процесс; прогрев JIT. L2: держать Lmx на
        unmanaged-куче -- перемещающий GC для управляемых
        объектов. Годность L3: да (заметка L3 №3). Тот же
        bytecode, управляемое отображение: объекты, GC,
        массивы. Unsafe-кучи L3 не нужны и не должны быть
        отображением L3. Mix не выбирает Java или C#: это
        перепись в Message-модель, не остаток CLR/JVM. JVM
        впереди CIL по годности L3 как отображение объектов
        и по популярности (больше разработчиков), не потому
        что Mix живёт на JVM.

        Документация bytecode:
            ECMA-335 (6-е издание): Partition III (CIL),
            Partition II (Metadata)
            https://www.ecma-international.org/publications-and-standards/standards/ecma-335/

5. WASM GC  [L3]
        Та же VM W3C, что в пункте 2, другая куча. Reference
        types, structs, arrays; ими управляет GC хоста.
        Задумана как бэкенд высокоуровневых языков, не как
        куча C. Стандартизирована в Wasm 3.0. Хост по-прежнему
        может быть Wasmtime/WAMR из include_wasm.txt. Это не
        линейная память wasm32 (пункт 2) и не wasm-gc как куча
        L2 (L2 отвергает, потому что L2 наблюдает адреса).

        Почему это место: все крупные браузеры возят
        (Chrome 119, Firefox 120, Safari 18.2). Chrome
        Platform Status: ~0.224% загрузок страниц -- примерно
        в 25 раз меньше фактического использования, чем Wasm
        в целом (~5.5%). Компиляторы, которые это выдают
        сегодня: Kotlin/Wasm, Dart/Flutter, TeaVM.
        Установленный рантайм -- набор браузеров; доля
        «выдали и исполнили» ещё мала. Ниже CIL, потому что
        прикладных разработчиков на wasm-gc намного меньше,
        чем на C#; выше RISC-V-как-программной-VM, потому что
        фича стоит в каждом браузере.

        Годность L3: да, переносимо (заметка L3 №2). Проверка
        границ и перемещающий GC родные. Mix -- библиотека/
        рантайм Message-модели в госте, не остаток Java.
        Годность L1/L2: нет -- переезжает и тегирует; неверная
        куча WASM для Lmx.

        Документация bytecode:
            https://webassembly.github.io/spec/
            GC / heap types в ядерной спеке (Wasm 3.0)
            https://github.com/WebAssembly/gc

6. RISC-V как переносимая ISA  [L1]
        Не скриптовая VM: настоящий набор инструкций с
        публичной кодировкой. Скомпилировать C из L1
        тулчейном riscv32/riscv64; гонять на mini-rv32ima /
        Spike / QEMU user. Указатели, newlib, goto -- родные.
        «Bytecode» здесь -- машинная кодировка RISC-V,
        документированная как любая ISA.

        Почему это место: большой и растущий кремний (SHD
        Group / RISC-V International: миллиарды embedded SoC
        в год, прогноз ~34% релевантного кремния к 2031;
        Ubuntu ~95% покрытия пакетов против amd64). Это
        использование железа. Как *программная* VM -- учёба и
        инструментарий (QEMU, Spike). Assembly в целом --
        TIOBE №16 при 0.89%; RISC-V -- его доля. Ниже wasm-gc,
        потому что прикладных компиляторов, выдающих RISC-V
        как образ VM, меньше; выше Lua, потому что ISA --
        публичный стандарт с индустриальным органом.

        Годность L1/L2: да. Один hart / одно адресное
        пространство, если рантайм сам не режет память по
        договорённости. L3: только через L1.

        Документация bytecode:
            RISC-V Unprivileged ISA (последняя ратификация)
            https://riscv.org/technical/specifications/
            кодировка -- главы "RV32/RV64I Base Integer
            Instruction Set".

7. Lua 5.4  (include_lua.txt)  [L3]
        Документированная opcode-VM (lopcodes, lua_dump /
        lua_load). Таблицы могут нести графы в духе Structure;
        указатели не нужны. GC PUC Lua здесь не правило
        стабильности L3. Корутины -- не FIFO-ходы Message,
        это остаётся библиотекой. Компиляция в bytecode Lua
        слабее JVM/wasm-gc (Lua обычно embed/eval VM). Годится
        для наброска интерпретатора L3 или Lua-принтера; не
        первая боевая ISA L3.

        Почему это место: SlashData Q1 2025 ~2.3 млн
        разработчиков Lua; TIOBE сент. 2026 №31 при 0.57%.
        Игры и встраивания (и Luau на Roblox как диалект)
        реально гоняют это семейство bytecode. Нет в верхней
        горстке SO 2025, процитированной выше. Ниже RISC-V,
        потому что сообщество языка меньше, чем у C#, и нет
        кремниевой истории; выше BEAM, потому что Lua пишут
        больше разработчиков, чем Erlang/Elixir.

        Годность L3: набросок (заметка L3 №5). Годность
        L1/L2: нет. Теговые значения, нет кучи C. LuaJIT --
        *не* этот пункт: L3 отвергает FFI как лазейку L2.

        Документация bytecode:
            https://www.lua.org/manual/5.4/
            https://www.lua.org/source/5.4/lopcodes.h.html

8. BEAM (Erlang / Elixir)  [L3]
        Документированный файл .beam в стиле IFF (чанки Code /
        AtU8 / ExpT) плюс OTP genop.tab. Ближайший аналог
        Message Thread: изолированные кучи, FIFO-почта, не
        больше одного хода, много параллельных процессов.
        Каталог убрал его как встраивание в процесс (C-node /
        sidecar). Как *цель компилятора* L3 копирующий GC
        процесса приемлем -- в L3 нет адресной арифметики.
        Отображение: Message -> процесс, граф Structure ->
        maps/tuples, merge -> копия. Всё ещё порт языка, не
        готовая ISA. Цель Mix -- Message в стиле Smalltalk
        (19.29.2.1), поэтому BEAM Mix-образный; это годность,
        не это место по популярности.

        Почему это место: Elixir и Erlang в TIOBE 51-100.
        Ими восхищаются (SO 2025) больше, чем ими пользуются.
        Телеком и часть веб-бэкендов реально гоняют BEAM;
        число разработчиков заметно ниже Lua и C#. Выше MIR,
        потому что BEAM -- промышленная bytecode-VM с
        индустриальным рантаймом, а не проект C-IR.

        Годность L3: да, Messages (заметка L3 №4). Годность
        L1/L2: нет. Нет заголовка Lmx, перемещающий GC
        процесса.

        Документация bytecode:
            https://www.erlang.org/doc/man/beam_lib.html
            OTP lib/compiler/src/genop.tab
            https://happi.github.io/theBeamBook

9. MIR  (vnmakarov/mir) -- лучшая выделенная C-виртуальная
   машина  [L1]
        Нет в каталоге. Типизированный C-подобный IR, текстовая
        и двоичная формы, интерпретатор, JIT, C API. c2mir
        компилирует подмножество C11 (без VLA/complex/atomics/
        TLS) плюс несколько GNU-расширений. Операнды памяти
        C-образные. alloca, хостовый printf, goto, switch,
        метка-как-значение. Двоичный MIR ~в 10 раз меньше и
        быстрее читается, чем текст. JIT geomean ~91% gcc -O2
        на их малом C-наборе; интерпретатор ~в 6-10 раз
        медленнее JIT. Десятки KLOC C, не LLVM. Хосты: x86_64,
        aarch64, ppc64le, s390x, riscv64 Linux; x86_64/aarch64
        macOS.

        Почему это место: GitHub ~2.6 тыс. звёзд / ~180 форков.
        Нет в TIOBE, SO, RedMonk. Почти ни один язык, кроме
        C-через-c2m, в него не целится. Последнее по
        *использованию*, первое среди выделенных C-VM по
        *годности* (заметки L1/L2 ставят №2). В списке, потому
        что рекомендуется, открыт, и IR задуман для написания
        (текстовый MIR, двоичный MIR, C API, m2b/b2m).

        Путь A: L1 -> C -> c2m -> .bmir. Путь B: принтер L1
        -> MIR. L2: арены Message -- обычные C bump-списки.
        Изоляции в стиле Wasm нет; изоляция -- не раздавать
        указатели между аренами. L3: только через L1; куча C
        больше машины, чем нужно исходному L3.

        Документация bytecode:
            https://github.com/vnmakarov/mir
            MIR.md (набор инструкций, типы, модули)
            mir.h / C API; утилиты m2b, b2m, c2m


4. Намеренно отсутствует
------------------------
Не рекомендуется как ISA ни для L1, ни для L3, даже если
популярно:

    bytecode Python   Python TIOBE №1 17.76%, SO 57.9%. Не ISA
                      L1 и не ISA L3; .pyc привязан к версии.
                      Интерпретатор L3 *на* Python -- sidecar.
    JS-движки         JavaScript TIOBE №6 / SO 66%. Значения,
                      не указатели; bytecode часто внутренний.
                      У L3 только набросок, не рекомендуется.
    LuaJIT            Популярное встраивание. Bytecode по-
                      прежнему значения Lua; FFI -- лазейка L2
                      в C. Не строка Lua 5.4 выше.

Натив, не bytecode-VM (исследование L1 рекомендует, здесь сняты
правилом «документировать написание bytecode»):

    TinyCC / libtcc   самый короткий in-process прогон C из L1
    QBE               нативный SSA-бэкенд
    sljit             уже вендорен; JIT-ассемблер
    Cranelift и др.   библиотеки codegen / JIT

Рекомендован L3, но здесь не ранжируется:

    HashLink          типизированная VM Haxe, файл .hl есть;
                      спека писателя -- блог/дамп, не основное
                      руководство. L3 помечает как слабый.
                      Крошечная экосистема.

Ещё не существует:

    Собственный bytecode L2/L3 (Layer I). Исполнялся бы *на*
    пунктах 1-9. Не выбор каталога.

6. Если когда-нибудь пробовать бэкенд
-------------------------------------
Сначала самое дешёвое; независимо от сортировки по популярности.
Две поверхности, не смешивать.

  L1 (ядро):

  1. Поверхность -- Translator-L1, не Layer S L2 и не
     L3-в-JVM.
  2. Проверка гипотезы без нового принтера: C из l1trans через
     wasi-sdk и через c2m. Фикстуры: smoke L1 в stg/l1_baseline,
     libc_abi (fopen/memcpy), указатели own.lm1; затем
     самотесты Lmx в l2src, если ядро в скоупе.
  3. Линейная память WASM (здесь №2, в L1/L2 №1).
     Одна память/инстанс на Message, если изоляция кодируется
     на границе VM.
  4. MIR (здесь №9, в L1/L2 №2), если нужна малая VM с
     хостовым libc вместо песочницы.
  5. LLVM как добавка разработчика, не вендоренный рантайм.
  6. Не начинать L1 с CIL, JVM, Lua, BEAM, Python или wasm-gc.
     CIL в этом списке ради полноты открытых популярных VM;
     это не первый принтер L1, который писать.

  L3 (высокоуровневое подмножество):

  7. Не тащить в отображение L3 правило L2 «узлы никогда не
     перемещаются». Первый семантический эксперимент:
     подмножество hello.lm3 (print, fn/sub, each/for,
     field-follow Structure, table) -> classfile JVM
     (здесь №1, годность L3 №1) или wasm-gc (здесь №5,
     годность L3 №2). Массивы с проверкой границ обязательны.
  8. FIFO Message и Mix остаются библиотекой/рантаймом на этой
     VM. Mix не Java: переписать как сотрудничающие Message
     (стиль Smalltalk, 19.29.2.1), независимо от JVM/CIL.
  9. Проверка через L1 бесплатна (L3 -> L1 -> wasi-sdk / c2m)
     и не проверяет ISA формы L3.
  10. Не начинать L3 с Lua, BEAM, FFI LuaJIT, Pawn, Prolog
      или bytecode Python.

Путь A (C как IR) повторно использует self-host для L1. Путь B
-- второй принтер внутри l1trans.lm1, не новый язык. Принтер
L3-в-JVM / L3-в-wasm-gc был бы новым профилем, не текущим
гейтом P-L1text.
