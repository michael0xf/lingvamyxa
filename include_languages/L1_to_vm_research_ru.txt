L1 во виртуальные машины -- исследовательская заметка (русский)
==============================================================

Статус

Снимок 2026-09-08. Это не план поставки и не обязательство делать
второй бэкенд L1. Компаньон lingva_bindings.txt (каталог встраивания)
и L1_spec.txt (что Translator-L1 реально понижает сегодня).

English text: L1_to_vm_research_en.txt

Вопрос

Какие виртуальные машины реалистичны как цели компиляции для
Translator-L1 (исходники .lm1 в l1src/ и stg/l1_baseline/l1src/),
чтобы L1 выдавал виртуальный код такой машины вместо ANSI C99
или рядом с ним?

Метод

  1. Прочитаны L1_spec.txt, libc_abi.lm1, own.lm1 и каталог в этом
     каталоге (что такое L1 и что каталог уже знает).
  2. Каждый рантайм каталога оценён как цель bytecode L1, а не как
     встраиваемый гостевой язык (исходная работа каталога).
  3. Вне каталога -- машины, которыми реально пользуются как
     бэкендами C-подобных языков.

Файл не выдумывает возможности L1. Реализованный L1 -- это образ
C99 из L1_spec.txt.

Цели идут от самой подходящей к самой неподходящей. Первая куча
может принять текущий L1 (l1trans, parser, own) без переписывания
языка. После разделителя -- остальные, в конце самая худшая.


0. Каталог и бэкенд компилятора
-------------------------------
include_languages/ -- каталог чужих рантаймов, которые Lingvamyxa
может встроить и вызвать через C ABI (Python, Lua, JVM, хост WASM,
...). Это обратная задача к этой заметке.

  Вопрос каталога:  Lingvamyxa хостит X и исполняет исходник X.
  Эта заметка:      L1 компилируется в виртуальный код X, и X его
                    исполняет.

Рантайм может легко встраиваться и всё равно быть плохой целью L1.
Lua и CPython -- типичный случай.


1. Что L1 требует от машины
---------------------------
Translator-L1 -- это compile-time, syntax-directed lowerer из
.lm1 без обёртки в одну единицу трансляции ANSI C99 (L1_spec.txt
§0, §3). Живой корпус (l1trans, parser, own, make, libc_abi) --
это программа на C в орфографии L1.

Нужно отобразить без переписывания языка:

  Указатели и взятие адреса
      префикс @x -> &x этой привязки L1; префикс \p -> *p;
      field-follow p\field -> p->field; глубина @ / @@ -> * / **.
      own.lm1 -- malloc/calloc/realloc/free и стеки указателей.
  Целые и вещественные ширины C
      int, void, char, size_t, unsigned, long, short, uchar,
      float, double, ulong, u8..u64, i8..i64, FILE, несколько
      typedef LmP0*.
  Сплошные массивы
      [] и [][] как прямоугольные массивы C, не рваные ряды
      указателей и не онтология Array из L2.
  Неструктурное управление
      if/else, while, for, break, continue, switch/case/default
      (провал как в C), метки + goto. throw/catch/finally уже
      понижаются в static-канал плюс goto, не setjmp и не
      исключения C++.
  Библиотека C
      libc_abi.lm1: fopen/fclose/fread/fwrite, memcpy, strlen,
      getenv, system, FILE*.
  Раздельная компиляция как сейчас
      один выходной путь C на запуск CLI; import встраивает
      единицы L1.

Реалистичной VM поэтому нужна C-модель памяти (байтовая память,
указатели как адреса), ширины целых и float, goto или лёгкое
понижение goto, и libc либо слой системных вызовов класса WASI.
Машины tagged-value / object-ref не проходят этот порог для
текущего self-host, и дело не во вкусе.

Два способа реализации, по возрастанию цены:

  A. Оставить C-принтер; отдать .c в C-to-VM (wasi-sdk, c2mir,
     clang -emit-llvm). Проверка цели без правки l1trans.
  B. Второй принтер в l1trans.lm1, который пишет IR/bytecode VM
     тем же локальным отображением, что C-принтер.

A -- дешёвый эксперимент. B -- настоящий второй бэкенд.

Канонический пайплайн сегодня (L1_spec.txt §4): L1 -> один C99 TU
-> gcc. Любой VM-бэкенд должен либо съесть этот C, либо повторить
локальное отображение (@ -> *, \p -> *p, p\field -> p->field,
include -> #include, throw -> static-канал + метки).


2. Ранжированные цели (самая подходящая первая)
-----------------------------------------------

1. WASM  (include_wasm.txt) -- лучший переносимый образ VM
        Единственная запись каталога, которая реально является
        целью компиляции C. Линейная память wasm32 -- это куча/
        стек C; типы значений i32/i64/f32/f64; br / br_if /
        br_table закрывают goto и switch; указатели на функции --
        table + call_indirect. wasi-libc даёт FILE* (хост должен
        открыть каталоги; обычный грант -- wasmtime --dir=.).
        Рантаймы уже названы в каталоге: Wasmtime C-API, Wasmer,
        WAMR, wasm3.

        Ограничения: потолок wasm32 4 ГБ (memory64 ещё сырой);
        нет тождества хостового FILE*; WASI preview 1 без сети;
        system() и произвольный libc отсутствуют; указатели
        guest/host не совпадают -- копирование через линейную
        память, как уже описано в include_wasm.txt §5.4.
        L1 throw-как-goto не требует setjmp.

        Самый дешёвый путь: l1trans -> .c -> wasi-sdk clang
        (wasm32-wasip1) -> .wasm -> wasmtime/WAMR/wasm3.
        Прямой L1->wasm имеет смысл, только если мешает шаг C.

2. MIR  (vnmakarov/mir) -- лучшая специализированная C-VM
        В каталоге нет. Типизированный C-подобный IR, текст и
        двоичный формат, интерпретатор, JIT, C API. c2mir
        компилирует подмножество C11 (без VLA/complex/atomics/TLS)
        плюс несколько расширений GNU. Операнды памяти как в C
        (типизированные load/store с base/index/scale). alloca,
        хостовый printf, goto, switch, label-as-value,
        setjmp/longjmp через C. Двоичный MIR до ~10× компактнее
        и быстрее читается, чем текст. JIT geomean около 91%
        gcc -O2 на их малом C-наборе; интерпретатор ~в 6-10 раз
        медленнее JIT. Десятки KLOC на C, не LLVM. Цели: x86_64,
        aarch64, ppc64le, s390x, riscv64 Linux; x86_64/aarch64
        macOS.

        Путь A: L1 -> C -> c2m -> .bmir (l1trans не трогать).
        Путь B: L1 -> MIR в трансляторе (то же отображение, что
        у C-принтера).

        Хостовый libc и настоящие указатели; без песочницы WASM.
        Обратная сторона include_wasm: нет изоляции по
        capabilities.

3. LLVM bitcode (.bc) + lli / ORC JIT
        Индустриальный IR. clang -emit-llvm уже есть, поэтому
        путь A сразу доступен, как только есть C из L1. Прямой
        принтер L1->LLVM -- полноценный компиляторный проект;
        понижение C ABI -- работа фронтенда (в отличие от QBE/MIR).
        Тяжело вендорить как встраивание (не проходит правило
        каталога «без многогигабайтного SDK»). Нормален как
        необязательный бэкенд разработчика.

4. TinyCC / libtcc  (include_tinycc.txt)
        Не виртуальная машина. Компилирует C в нативный код
        в процессе. Поскольку L1 уже печатает C99, это кратчайший
        путь «запустить L1 без gcc», уже набросан как приёмник tcc.
        Стоит среди подходящих целей, чтобы не путать с bytecode
        ISA -- это практическая замена VM внутри процесса.

5. RISC-V как переносимая ISA
        Не скриптовая VM: скомпилировать C из L1 тулчейном
        riscv32/riscv64, исполнить на mini-rv32ima / Spike /
        QEMU user. Указатели, newlib, goto -- родные. Имеет смысл,
        если нужный «виртуальный код» -- кодировка настоящей
        машины, а не SSA IR. Учебный и встраиваемый; в каталоге
        нет.

6. .NET CIL  (include_dotnet.txt)
        Настоящий bytecode. В CIL есть unmanaged-указатели,
        localloc, cpblk, initblk, calli и goto. unsafe C# / ILAsm /
        C++/CLI могут выразить C-подобную модель памяти. libc
        становится P/Invoke. Один CoreCLR на процесс; разогрев
        JIT; тяжелее WASM и MIR. NativeAOT уже в Removed каталога
        (полный SDK, компиляция под каждую цель).

7. QBE
        Малый C99 SSA IL (~10-14 KLOC), C ABI в бэкенде, asm
        через системный ассемблер. Нет интерпретатора -- нативный
        бэкенд, не образ VM. cproc использует его как бэкенд
        компилятора C. Geomean на наборе MIR около 65% gcc -O2
        (JIT MIR ~91%). Windows ABI в QBE 1.3.

8. sljit  (уже вендорится: third_party zherczeg-sljit*.tar.gz)
        Лёгкий JIT-ассемблер, его использует PCRE2 в этом дереве.
        Нет переносимого файла bytecode. Разумное нативное JIT-
        понижение, если у L1 появится бэкенд машинного кода.

9. Cranelift, libgccjit, asmjit, GNU Lightning, DynASM, libjit,
   libfirm / cparser
        То же семейство: кодогенераторы / JIT-библиотеки, не
        переносимые образы VM. Cranelift уже сидит внутри
        Wasmtime. libfirm большой и LGPL2.


================================================================
не рекомендуется
================================================================

10. JVM classfile  (include_openjdk.txt)
        В Java bytecode нет сырых указателей. Panama
        MemorySegment, sun.misc.Unsafe или Graal Sulong (LLVM
        bitcode на Graal) могут имитировать кучу C; это другой
        компилятор, не «эмитируй .class из L1». Исторические
        C-to-JVM (NestedVM, LLJVM, Cibyl) были мучительны. Не
        первый бэкенд. OpenJDK в этом каталоге остаётся
        встраиванием библиотек Maven. Наименее плохой в куче
        нерекомендуемых только потому, что off-heap обходы
        существуют.

11. HashLink
        Типизированный bytecode Haxe с hl.Bytes / низкоуровневыми
        ссылками. GC и объектная модель -- Haxe, не C. Только
        набросок подмножества.

12. Pawn / AMX  (include_berry.txt)
        Документированный P-code, C-подобный исходник, песочница
        из ячеек. Адреса -- смещения ячеек в данных AMX, не
        char* / FILE*. Потребовал бы урезанный L1 (без хостового
        malloc, без libc FILE). Self-host l1trans.lm1 не влезет.

13. Umka
        Статическая типизация, компиляция в bytecode, свои
        указатели и GC. Свой язык, не C ABI. Тот же вердикт
        «только подмножество», что у Pawn.

14. AngelScript  (include_angelscript.txt)
        Типизированный C++-подобный bytecode. Объекты
        регистрируются в движке; нет кучи C.

15. LuaJIT  (include_luajit.txt)
        Bytecode Lua -- это значения Lua. FFI LuaJIT вызывает C;
        это не C-ISA, в которую эмитируют. Моделировать память L1
        как гигантский uint8 userdata -- это генерировать Lua, а
        не компилировать в bytecode LuaJIT.

16. Lua 5.4  (include_lua.txt)
        Та же tagged-value машина без лазейки FFI.

17. QuickJS-ng, Duktape, MuJS
        Значения JavaScript, нет указателей.

18. CPython, WASI-CPython, Pyodide  (include_python*.txt)
        Bytecode Python. Из L1 .pyc не эмитируют.

19. Janet, Wren, mruby, Tcl, Berry, Gravity, Pocketlang
        Динамические встраиваемые VM. Не та модель.

20. PyPy  (include_python_pypy.txt)
        Семантика Python плюс перемещающий GC. На RPython можно
        написать интерпретатор L1 -- это создать VM, а не
        целиться в PyPy.

21. Julia  (include_julia.txt)
        Сама Julia компилируется в LLVM. Bytecode Julia-VM для
        L1 не существует.

22. BEAM / MoarVM / YARV; eBPF; SPIR-V; Knuth MIX / MMIX; Parrot
        Чужие модели (акторы/Perl/Ruby, фильтры ядра, GPU,
        учебный MIX, не связанный с Lingvamyxa Mix,
        Lingvamyxa_MIX_design_note.txt). Parrot мёртв.

23. com.mtk.map (исходники Java-контейнера Mix)
        Это не VM.


3. Если когда-нибудь пробовать второй бэкенд
--------------------------------------------
Сначала самое дешёвое из рекомендуемой кучи:

  1. Проверка гипотезы без нового принтера: сгенерированный C из
     l1trans через wasi-sdk и через c2m. Если parser.lm1 / own.lm1
     живы -- цель реальна. Первые фикстуры: smoke в
     stg/l1_baseline/tests/l1, затем пользователи libc_abi
     (fopen/memcpy), затем указатели own.lm1.
  2. WASM (переносимый образ).
  3. MIR (малая C-VM, хостовый libc).
  4. TinyCC (натив в процессе).
  5. sljit (свой JIT, без переносимого bytecode).

Не начинать с пунктов после разделителя. Путь A (C как IR) повторно
использует self-host. Путь B -- второй принтер внутри l1trans.lm1,
не новый язык.
