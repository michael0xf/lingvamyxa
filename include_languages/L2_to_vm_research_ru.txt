L2 во виртуальные машины -- исследовательская заметка (русский)
==============================================================

Статус

Снимок 2026-09-08. Это не план поставки и не обязательство делать
второй бэкенд L2. Компаньон L1_to_vm_research_ru.txt (C-машины),
lingva_bindings.txt (каталог встраивания) и Lingvamyxa_spec.txt
Revision 2 (контракт L2/L3).

English text: L2_to_vm_research_en.txt

Вопрос

Какие виртуальные машины реалистичны как цели компиляции исходников
L2, чтобы транслятор L2 выдавал виртуальный код такой машины вместо
выбранного пайплайна L2 -> L1 -> C99 или рядом с ним?

Свидетельства «что такое L2»:

  Lingvamyxa_spec.txt                 нормативный L2/L3
  lm2/                                старый hosted-транслятор (L2 -> C
                                      через таблицы, registry, trans_l1_*)
  stg/l1_baseline/l2src/              живое ядро замены на L1 (единицы
                                      Lmx + первый l2trans)
  L1_language_and_translator_spec.txt граница Translator-L2 (P-L1text
                                      выбран; P-C99 отвергнут)

Метод

  1. Прочитаны онтология L2, правила Message/арен и машинная
     поверхность.
  2. Каждый рантайм каталога оценён сначала как *машина* для
     сниженного L2 (тот же порог, что L1_to_vm_research_ru.txt,
     плюс нужды рантайма L2), затем как *семантическая ISA*
     (отобразить Lmx / Messages / tables / merge на значения этой VM).
  3. Вне каталога -- акторные VM, неперемещаемые кучи и графовые
     машины.

Файл не выдумывает возможности L2. Открытые пункты ABI остаются
открытыми (l2src/OPEN_POINTS.txt).

Цели идут от самой подходящей к самой неподходящей. Первая куча
может принять ядро L2 после L2->L1->C без переписывания онтологии.
После разделителя -- остальные, в конце самая худшая.


0. Каталог и бэкенд компилятора (то же разделение, что у L1)
-----------------------------------------------------------
include_languages/ -- каталог чужих рантаймов, которые Lingvamyxa
может встроить и вызвать. Это обратная задача к этой заметке.

  Вопрос каталога:  Lingvamyxa хостит X и исполняет исходник X.
  Эта заметка:      L2 компилируется в виртуальный код X, и X его
                    исполняет.

L1_to_vm_research_ru.txt отвечает на вопрос C-машины. L2 к этому
не сводится. L2 -- это граф + рантайм Message, который *использует*
машину L1/C; сам он не единица трансляции C.


1. Что такое L2
---------------
L2 -- полный уровень Lingvamyxa (спека 1.3). L3 -- тот же язык без
низкоуровневой машинной поверхности (сырые адреса, c.array,
непроверяемый индекс, атомики, include/define/os, префикс @).
Компиляция, интерпретация и смешанное исполнение -- выбор бэкенда/
профиля, не граница L2/L3 (спека 1.3).

Выбранный маршрут транслятора (handoff notes §6, L1_language spec 4.3):

    исходник L2  ->  Translator-L2  ->  текст L1 (P-L1text)
                 ->  Translator-L1  ->  C99
    P-C99 (эмит C99 прямо из L2) отвергнут как бэкенд L2.

Живая замена совпадает с этим маршрутом: l2src/l2trans.lm1 печатает
.lm1 для адаптера `main` из §1.7 плюс один лист сложения §21.8.
Старый lm2/trans.lm2 печатает .lm1.c через hosted-ядро Namespace/
дескрипторов; это ядро НЕ должно быть семантическим фундаментом
замены (L1_language spec 4.1).

1.1 Онтология, которую VM должна сохранить
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Каждое вхождение Structure -- один заголовок (спека 2, l2src/lmx.h):

    struct Lmx { Lmx *node; size_t len; void *data; };

  - `node` -- родитель включения (ациклическое дерево). Прочие
    ссылки могут разделяться и циклиться.
  - `data` классифицируется тем, *в какой зарегистрированный
    диапазон адресов попадает указатель*. Нет поузлового тега типа,
    имени, vtable или обязательного префикса схемы.
  - Типизированные служебные пулы: примитивы (all_chars_array, ...),
    all_methods_array {addr, sig}, дескрипторы all_array_of_T
    {len, data} с отдельным сплошным прямоугольником элементов.
  - Имена вычищены из обычного исполнения. Рантайм идёт по адресам
    и индексам детей. Вспомогательная карта только: Lmx* -> ShortNameId.
  - Живые узлы Lmx и записи пулов **никогда не перемещаются**. Пул
    растёт добавлением нового неперемещаемого блока. Коллектора с
    патчем указателей нет (спека 2, 19.29.1).
  - Массив `[]:` -- дескриптор + backing, не массив C. `c.array` --
    отдельная форма машинного хранения L2.

1.2 Рантайм, который VM должна хостить
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
  Message
      корень и его достижимый граф Lmx. Одна логическая арена на
      Message (19.28, 19.29.2). Изменяемый граф не разделяется
      сырыми указателями между Message. Неизменяемые примитивные
      атомы и записи методов можно разделять.

  L3 Thread
      активированный Message. FIFO-inbox, не больше одного хода
      одновременно. Разные Message могут исполняться параллельно.
      Изоляция -- граница арены, не видимый из исходника замок.

  Call ABI (21 / 19.28.R2.3)
      typed_entry(invoking_structure, declared_actuals...,
                  dynamic_values_selected_by_sig...).
      Сгенерированные исходные методы НЕ должны обрастать скрытым
      аргументом Arena / MessageThread / Namespace / descriptor.

  merge
      копирование всего ИСПОЛЬЗУЕМОГО графа и лексического дерева до нуля во
      время исполнения ТЕМ ЖЕ обходом, что создание нового Message. У копий
      явно переписываются node и ссылки детей/payload через таблицу копирования;
      independent обрывает внешнюю лексику. Использование всего дерева копирует
      всё дерево. Методы и их известные неизменяемые дескрипторы остаются общими;
      копирование node не меняет ссылки METHOD и не генерирует новый код.

  implements(varA varB Consumer) / RuntimeImplements(...)
      совместимость относительно потребителя, не номинальная
      решётка классов и не runtime Namespace.

  Mix
      оверлейная разметка; целевая перепись -- сотрудничающие
      Message в модели стиля Smalltalk (19.29.2.1). com.mtk.map
      -- Java-шаблон пересекающихся деревьев, не Mix.

  Машинная поверхность L2 (раздел 20)
      @ / \ / field-follow, слоты глубины адреса, c.array,
      непроверяемый индекс, внешние вызовы, низкоуровневый sync.
      Поэтому полный L2 всё равно нуждается в C-подобной подложке,
      даже когда L3 -- нет.

1.3 Две разные работы «скомпилировать L2 в VM»
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
    Слой M -- машина
        Исполнить ядро L2 и сгенерированные методы после
        L2->L1->C (или L2->L1->VM). ISA должна подходить L1
        (указатели, goto, libc) *и* неперемещаемой bump-куче,
        записям методов из указателей на функции и желательно
        нескольким изолированным кучам (по одной на Message).
        Это L1_to_vm_research_ru.txt плюс изоляция арен.

    Слой S -- семантическая ISA
        Эмитировать bytecode этой VM как смысл приёмников L2:
        обход графа, merge, посылка сообщения, table/query,
        implements(). Значения VM *были бы* Lmx/Messages. Это
        отображение языка, не бэкенд C. Правила тождества спеки
        (неперемещаемые узлы, классификация диапазонами, без
        скрытых аргументов, без поузловых тегов) бьются с
        типичными объектными VM.

    Слой I -- интерпретатор L2
        Спека допускает интерпретацию. Собственного bytecode
        Lingvamyxa (dispatch приёмника, merge, send, операции
        графа) ещё нет. Он сидел бы *на* машине слоя M. Это не
        выбор из каталога.

Старый lm2/ ничем из этого не является как VM: это hosted-компилятор
L2->C на явных таблицах (core.lm2, table.lm2, trans_registry.lm2).
Полезен как корпус приёмников и раскладок, не как bytecode ISA.

Ранжирование ниже -- слой M (может ли там жить текущее ядро). Слой S
отмечен, где меняет вердикт. L3 снимает машинную поверхность, но не
Lmx, арены, merge, Messages и implements(); высокоуровневая VM,
которая не умеет неперемещаемый трёхсловный узел, всё равно валит
L3. Не считать «L3 как Python» стратегией компиляции (спека 1.4).


2. Ранжированные цели (самая подходящая первая)
-----------------------------------------------

1. WASM, линейная память  (include_wasm.txt) -- лучший переносимый слой M
        Лучшее совпадение в каталоге, чуть удачнее, чем для L1.
        Линейная память wasm32 не перемещает объекты -- правило
        тождества Lmx родное. Один экземпляр модуля / одна память
        на Message -- правдоподобная кодировка изоляции 19.29.2
        (гранты capabilities уже совпадают с полномочиями inbox).
        Записи методов -- funcref + table. wasi-libc закрывает
        машинный/C край L2 так же, как у L1.

        Ограничения: wasm32 4 ГБ на память (арена одного Message
        должна влезть); WASI p1 без сети; wasi-threads ещё опытны,
        если один процесс хостит много параллельных Thread;
        указатели guest/host по-прежнему копируются
        (include_wasm.txt §5.4).

        Слой S: WASM -- C-машина, не ISA Lmx. Не выдумывать
        Structure на wasm-gc (wasm-gc в куче нерекомендуемых).

        Путь: L2 -> L1 -> C -> wasi-sdk, или позже L2 -> L1 ->
        wasm-принтер. Прямой L2 -> wasm -- третий маршрут, граница
        транслятора его не выбирает (бэкенд L2 -- P-L1text).

2. MIR  (vnmakarov/mir) -- лучшая специализированная C-VM для ядра
        Хостовые указатели, libc, JIT + интерпретатор, двоичный
        MIR. Арены Message -- обычные C bump-списки (рекомендованная
        реализация спеки 19.29.2). Путь: L2 -> L1 -> C -> c2m, или
        позже принтер L1 -> MIR. Изоляции в стиле WASM нет;
        изоляция -- не раздавать указатели между аренами, и это
        уже правило языка. Слой S: нет -- C-машина, не ISA Lmx.

3. LLVM bitcode (.bc) + lli / ORC JIT
        Как у L1, тяжело. Нормален как бэкенд разработчика для
        сниженного L1, который уже несёт ядро L2.

4. TinyCC / libtcc  (include_tinycc.txt)
        Не VM. Кратчайший нативный запуск сниженного L1/C внутри
        процесса, включая единицы ядра l2src. Годится хостить
        арены Message в памяти процесса. Слой S: нет.

5. Интерпретатор RISC-V
        Как у L1. Указатели и newlib родные. Один hart / одно
        адресное пространство, пока рантайм сам не разрежет
        памяти по соглашению.

6. .NET CIL unmanaged  (include_dotnet.txt)
        Слой M лучше, чем у JVM. unsafe-структуры, interior
        pointers, `fixed`, неуправляемые кучи. Lmx как трёхсловная
        структура в unmanaged-арене представим. У управляемых
        объектов по-прежнему перемещающий GC -- держать Lmx вне
        managed-кучи. Слой S: у объектов CIL есть типы и GC; та же
        драка за тождество. TPL Dataflow / Orleans -- акторные
        библиотеки, не L2. Правдоподобный unmanaged-хост; не
        первая ISA.

7. QBE / sljit / Cranelift / libgccjit / asmjit / GNU Lightning /
   DynASM / libjit / libfirm
        Native/JIT, не переносимые образы VM. sljit уже вендорится.
        QBE -- нативный бэкенд, не интерпретатор L2. Cranelift уже
        сидит внутри Wasmtime.

8. Собственный bytecode L2 (слой I) -- пока не существует
        Если его когда-нибудь спроектируют, поверхность опкодов
        по спеке примерно такова:

            граф:      alloc-in-arena, set/get data, перечисление
                       детей, классификация указателя диапазоном,
                       merge-copy, ShortNameId
            вызов:     typed_entry(node, declared..., dynamic...)
            сообщение: enqueue FIFO, один ход, copy/adopt между
                       аренами
            машина:    только L2 @ \ c.array unchecked, или trap
                       на L3

        Этот bytecode генерировал бы Translator-L2 рядом с текстом
        L1 или вместо него и исполнялся бы на пунктах 1-7. Это не
        JVM, Lua, BEAM и не WASM GC. Пока ISA нет, единственный
        реалистичный «компилятор L2 в виртуальный код»:

            Translator-L2 -> L1 -> (Translator-L1 -> C -> VM слоя M)


================================================================
не рекомендуется
================================================================

9. JVM classfile  (include_openjdk.txt)
        Слой M: плохая куча для Lmx. HotSpot перемещает объекты и
        хранит слово класса; спека 2 запрещает и то и другое как
        модель Lmx. Off-heap (Panama MemorySegment, Unsafe, direct
        ByteBuffer) может хостить Lmx -- тогда JVM есть хост
        процесса, не ISA L2. Sulong исполнял бы LLVM bitcode
        сниженного C, слой M в обход.

        Слой S: com.mtk.map -- Java-шаблон пересекающихся деревьев,
        не Mix. Цель Mix -- сотрудничающие Message в модели стиля
        Smalltalk (19.29.2.1), не ISA JVM. Отображать Lmx на
        java.lang.Object, implements() на интерфейсы или merge на
        clone() -- значит протащить hosted-модель
        дескрипторов/Namespace, которую транслятор замены
        наследовать не должен. Акторы в духе Akka рифмуются с
        Message Thread, но делят перемещающую кучу.

        Оставить JVM как встраивание каталога Tier 1, если гость --
        библиотеки Java. Не компилировать ядро L2 в classfile и
        не считать шаблон Mix.

10. BEAM (Erlang / Elixir)
        Ближайший аналог Message Thread: изолированные кучи, FIFO-
        почта, не больше одного хода, нет разделяемых изменяемых
        данных. Каталог убрал его как *встраивание в процесс*
        (C-node / sidecar). Как *цель* L2 валит слой M (нет сырых
        адресов, нет заголовка Lmx, нет записей методов C) и валит
        тождество спеки: поколенческий GC процесса *перемещает*
        термы. Компилировать L2 в BEAM -- переписать L2 как Erlang.
        Полезно как метафора планировщика, не как bytecode.

11. Graal / Truffle / RPython
        Инструментарий, чтобы *написать* интерпретатор слоя I с
        JIT. Не набор опкодов L2. GraalVM Native Image в
        catalog-Removed (компиляция под каждую цель).

12. HashLink
        Типизированная VM Haxe с низкоуровневыми байтами. GC и
        объектная модель -- Haxe. Не Lmx.

13. Pawn / AMX, Umka, AngelScript  (include_berry.txt,
    include_angelscript.txt)
        Малые типизированные или ячеечные VM. Ячейки Pawn -- не
        заголовки Lmx. У Umka есть указатели и GC -- максимум
        набросок подмножества L3. AngelScript регистрирует объекты,
        нет кучи C. Не хостят l2src и изоляцию Message.

14. Lua 5.4 / LuaJIT  (include_lua.txt, include_luajit.txt)
        Слой M: bytecode Lua -- не C-машина. FFI LuaJIT может
        вызвать ядро, сниженное в L1; это встраивание, не
        компиляция в Lua. Слой S: GC PUC Lua инкрементальный и
        неперемещающий, ближе чем HotSpot, но таблицы именованы и
        тегированы; Lmx безымянен и классифицируется диапазоном.
        Корутины -- не FIFO-ходы Message.

15. wasm-gc
        Перемещает и тегирует объекты, против спеки 2. Неправильная
        куча WASM для Lmx. Нужная WASM -- линейная память (пункт 1).

16. QuickJS / Duktape / MuJS
        Значения JS, перемещающие или уплотняющие кучи в зависимости
        от движка, нет Lmx.

17. CPython, WASI-CPython, Pyodide
        Слой M: нет. Слой S: CPython в основном не перемещает
        (refcount + cycle GC), но каждый объект тегирован и
        именован. Bytecode Python -- это Python. Интерпретатор L2
        *на* Python -- sidecar, не цель компилятора.

18. SWI-Prolog / Warren Abstract Machine
        Пограничный в lingva_bindings.txt, потому что Lingvamyxa
        называет себя логическим языком, а implements() -- предикат.
        WAM -- унификация и откат, не граф Lmx, не FIFO Message,
        не адреса раздела 20. Sidecar Prolog для запросов
        совместимости -- вопрос встраивания.

19. Janet, Wren, mruby, Tcl, Berry, Gravity, Pocketlang
        Динамические встраиваемые VM. Слой M нет. Слой S был бы
        портом L3 с другой моделью тождества.

20. PyPy
        Семантика Python плюс перемещающий GC.

21. GNU Guile / семейство Scheme; Smalltalk / Self / Newspeak
        Перемещающий или консервативный GC, имена/классы в рантайме.
        Привкус dispatch приёмников -- не арены Message.

22. Julia
        Компилируется в LLVM; bytecode Julia-VM для L2 нет.

23. com.mtk.map как ISA L2
        Java-шаблон пересекающихся деревьев, не Mix и не
        виртуальная машина ядра L2.


3. Если когда-нибудь пробовать VM-бэкенд
----------------------------------------
Сначала самое дешёвое; совпадает с выбранной границей транслятора.

  1. Не писать принтер L2->classfile / L2->Lua / L2->BEAM.
     Это бьётся со спекой 2 и L1_language spec 4.1.
  2. Проверка гипотезы на слое M без нового принтера L2: самотесты
     Lmx в l2src и L1, выданный l2trans, через wasi-sdk и c2m.
     Первые фикстуры: l2src/tests/entry_*.lm2 и run_lmx.ps1.
  3. WASM, линейная память (не wasm-gc), одна память или экземпляр
     на Message, если изоляция кодируется на границе VM.
  4. MIR, хостовый libc, bump-арены как обычный C.
  5. TinyCC, уже в каталоге.
  6. Mix не на JVM. Переписать как сотрудничающие Message
     (стиль Smalltalk, 19.29.2.1). Это работа языка, не
     bytecode L2. com.mtk.map остаётся шаблоном.
  7. Собственный bytecode L2 (пункт 8) -- проект языка. Исполнялся
     бы всё равно на пунктах 1-7.

L1 нужна C-модель памяти; динамические VM валятся, потому что нет
указателей. L2 нужна та же C-модель *под* стабильным тождеством Lmx,
классификацией диапазонами, одной неперемещаемой ареной на Message,
FIFO-ходами, merge как копией графа, записями методов {addr,sig}.
Динамические VM валятся дважды. WASM и MIR остаются наверху, потому
что линейные / C-кучи не перемещают узлы. JVM из-за Mix не
поднимается: Mix -- перепись в Message-модель, не остаток Java.
BEAM поднимается как метафора 19.28 и цели Mix в стиле Smalltalk
и остаётся вне списка целей компилятора.
